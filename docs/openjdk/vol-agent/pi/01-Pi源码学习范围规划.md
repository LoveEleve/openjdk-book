## 一、项目基本信息

- 项目名：Pi
- 版本基线：`main`
- 技术栈：TypeScript + 多包 monorepo（ai / coding-agent / agent / tui / session-backends / server/client/protocol）
- 核心形态：AgentSessionRuntime 共享内核 + interactive/print/rpc 多形态 + SQLite 持久化 + 双层工具系统 + skills / search / trust / telemetry

---

## 二、项目根问题（Project Thesis）

### 1. root problems

1. **如何把一个 Agent runtime 做成可在多种交互形态下复用的共享内核，而不是每种前端各写一套执行逻辑。**
2. **如何在会话级状态机中同时容纳 steering、follow-up、compaction、retry、overflow recovery、bash abort 等复杂控制流。**
3. **如何把工具系统、技能系统、会话持久化、上下文压缩和模型抽象分层，而不是糊成一个大框架。**

### 2. design theses

- Agent loop 必须和前端模式解耦，才能支撑 interactive / print / rpc 多形态共用。
- 会话状态不是消息列表，而是显式状态机（pending / steering / follow-up / compaction / retry 等）。
- 工具与技能都不是单层实现，而是 harness 抽象层 + coding-agent 具体层的双层设计。
- 持久化不是附加功能，而是围绕 SQLite 的 session / lanes / records / facts 真相层。

### 3. architectural promises

- 多种交互形态背后共享同一 AgentSessionRuntime。
- 上下文压缩、状态归约和工具执行有完整行为契约测试。
- 会话、分支、事实、记录有结构化存储模型。
- trust / settings / resource loader / provider composer 等外围层都不应破坏主执行骨架。

### 3.5 sharpened thesis

更锋利的一句话：

> **Pi 的本质不是“另一个会调模型的工具”，而是把 Agent 做成一个可跨多形态前端复用、由显式会话状态机驱动、并通过存储与归约器维持一致性的共享运行时。**

### 重点源码域
- `agent/src/agent-loop.ts`
- `agent/src/agent.ts`
- `agent/src/proxy.ts`

### 关键问题
- 为什么 Pi 也需要双层循环？
- tool execution mode 是如何驱动 loop 的？
- continue / prepareNextTurn 是怎么进入控制流的？

## P-2 AgentSession 状态机（核心中的核心）

## 四、横切专题（Crosscutting Tracks）

## P-X1 多形态共享内核
- interactive / print / rpc 三模式共享 `AgentSessionRuntime`
- 这是 Pi 最独特、最值得抬高的横切专题之一

## P-X2 会话状态机与控制流
- steering / follow-up / pending / retry / compaction / overflow recovery
- 不是单篇专题，而是多模块共同约束的一条主线

## P-X3 工具系统双层抽象
- harness tools 与 core tools 的关系，是理解 Pi 架构层次的关键

## P-X4 事件归约器 / RecordLog
- reducer / records / lanes / facts 共同决定持久状态的一致性

## P-X5 trust / project-trust / settings / resource-loader
- 这些不是“配置层小功能”，而是在控制前缀、路径和能力暴露的外围控制面

## 五、认知风险点（Cognitive Risks）

### 1. 错觉：Pi 只是一个大而全的聊天 CLI
- 实际风险：忽略了它的多形态共享运行时设计。
- 应纠正为：Pi 更像“同一内核驱动多前端”的 runtime 系统。

### 2. 错觉：Agent loop 看懂了就等于看懂了 Pi
- 实际风险：低估 AgentSession 状态机在系统中的中心地位。
- 应纠正为：loop 是骨架，状态机才是复杂度汇合点。

### 3. 错觉：只有一套工具系统
- 实际风险：看不见 harness 工具层和 core 工具层的分工。
- 应纠正为：Pi 有双层工具体系，必须理解它们的角色差异。

### 4. 错觉：skills 只是提示词集合
- 实际风险：低估其在 runtime / context / tools 之间的作用。
- 应纠正为：skills 也是运行时能力层的一部分。

### 5. 错觉：SQLite backend 只是会话存档
- 实际风险：看不见 records / lanes / facts 的事件与知识模型价值。
- 应纠正为：Pi 的存储层其实是产品④的重要蓝图之一。

### 6. 错觉：Print / RPC mode 只是薄外壳
- 实际风险：看不到“多形态共享内核”这条高价值设计主线。
- 应纠正为：Pi 的核心价值之一就是前端模式解耦。

## 六、分析边界

### UI 要不要进主线？
- **不要。**
- TUI 视觉组件不进第一轮主线，只保留原生输入/按键/terminal 层作为系统编程面参考。

### demo / example 要不要进主线？
- **不要。**
- 先看 runtime 骨架、状态机、存储和工具体系。

### test 代码要不要关心？
- **要。**
- 尤其是：
  - `agent-session-concurrent.test.ts`
  - `reducer.test.ts`
  - `compaction-serialization.test.ts`
  - tool / skill / provider 相关契约测试

### 非 Linux / 非主流平台要不要进主线？
- **不要。**
- `_windows.go` 等默认后置。

### provider 同构实现要不要全读？
- **不要。**
- 先读抽象层和典型 provider 样本，不在第一轮把几十个 provider 全摊开。

## 八、工程问题学习点

Pi 值得学的工程问题，不是“怎么调模型”，而是：

1. 如何让一个 Agent 内核同时支撑 interactive / print / rpc 三种形态
2. 如何把会话状态机做到足够强，容纳 steering/follow-up/compaction/retry
3. 如何组织双层工具系统与双层技能系统
4. 如何用 SQLite 把 sessions / lanes / records / facts 组织成长期状态层
5. 如何把 provider / auth / models / constrained sampling 做成大规模抽象层
