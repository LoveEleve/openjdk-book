## 一、这一章真正的问题

Agent 每次调用模型，真正决定它能不能继续理解任务的，不是完整历史有多少，而是：

> **这一轮模型到底看见了什么，以及历史被压缩后还保留了什么。**

Pi 的上下文系统要同时解决：
- 会话 entry 如何转成模型消息
- 压缩切点如何选择
- 工具调用和工具结果如何保持完整
- 分支摘要如何参与下一次压缩
- 文件操作如何在摘要后保留
- token 估算如何控制预算

所以这一章不是“压缩代码”，而是：
> **Pi 如何定义模型可见上下文，并在长期运行中保持它的语义完整。**

---

## 二、先给结论：Pi 把上下文构建做成三段管线

Pi 的 context 构建不是直接拿 session entries 过滤一下，而是三段式：

1. 推导 session 状态：thinking level / model / active tools
2. 构建上下文条目：应用 compaction 和 transforms
3. 把条目映射成模型消息

这三段分开非常重要，因为它把：
- 会话状态
- 历史过滤
- 模型消息

拆成了三个不同层次。

如果混在一起，后面压缩、分支、模式切换和扩展都会互相污染。

---

## 三、为什么 deferred assistant 消息不能进入上下文

Pi 对 `stopReason === "deferred"` 的 assistant 消息做了过滤。

这说明它区分：
- 已经完成并有稳定语义的 assistant 输出
- 只是中间状态、延迟完成或未定稿的 assistant 输出

如果把 deferred 消息也塞给模型：
- 模型可能把未完成内容当事实
- 下一轮会建立在半成品之上

所以这条规则真正保护的是：
> **模型上下文只接受已经具有稳定语义的消息。**

---

## 四、压缩切点为什么不能随便落在 toolResult 上

Pi 的 `findCutPoint` 不是简单按字符切，而是按 token 预算寻找合法切点。

合法切点包括：
- user
- assistant
- bashExecution
- custom
- branchSummary
- compactionSummary

而 `toolResult` 不能单独成为切点。

原因非常关键：

> **工具结果必须和触发它的请求保持语义完整。**

如果把 tool call 留在上下文里，却把 tool result 切掉：
- 模型看到的是一个没有完成的协议过程
- 下一轮很容易误判工具状态

所以这里的设计不是“压缩得更精确”，而是：
> **压缩不能破坏消息协议的配对关系。**

---

## 五、为什么 split turn 要单独摘要前缀

如果压缩切点刚好落在一个 turn 中间，Pi 不会简单把前半段和后半段拼起来。

它会：
1. 摘要完整历史
2. 对被切断的 turn 前缀单独摘要
3. 把这段前缀上下文提供给保留的后缀

这说明 Pi 承认：
- turn 不是任意消息集合
- turn 内部有上下文依赖

所以 split turn 的处理是在保护：
> **即使切点落在轮次中间，后半段也不能失去前半段的必要语义。**

---

## 六、为什么 retainedTail 必须嵌入 compaction 条目

Pi 的 compaction entry 不只是存一个 summary，
还内嵌 `retainedTail`。

这带来一个很重要的性质：
- 下一次压缩时，retainedTail 可以重新作为虚拟消息参与压缩

也就是说，Pi 没有把“尾巴”当一次性临时变量，而是把它放进了持久会话结构里。

这使得多轮压缩仍然可以连续工作，而不是每次压缩都从完全不同的边界重新开始。

---

## 七、为什么摘要请求必须缓存隔离

Pi 对摘要请求显式设置：
- `cacheRetention: none`
- 独立 `sessionId`

原因不是摘要不重要，而是：

> **摘要请求的内容不可稳定复用，不应该污染主执行链的前缀缓存。**

这和 Reasonix 的缓存优先哲学、OpenCode 的上下文工程是相通的：
- 主执行链保持稳定
- 辅助审查/摘要调用隔离

---

## 八、为什么 summary 需要结构化格式和增量更新

Pi 的摘要 prompt 不是一句“请总结历史”，而是要求固定段落：
- Goal
- Constraints & Preferences
- Progress
- Key Decisions
- Next Steps
- Critical Context

第二次压缩以后还会使用 update summary：
- 保留旧信息
- 增加新进展
- 把进行中移动到 Done
- 删除过时内容

这说明 Pi 把摘要看成：
> **持续演进的任务状态，而不是每次重新生成的一段总结。**

这对长跑 Agent 非常关键，因为全量重写摘要很容易：
- 丢掉旧决策
- 改写关键路径
- 让上下文叙事漂移

---

## 九、为什么文件操作必须进入摘要元数据

压缩时，Pi 会从工具调用中提取：
- read files
- written files
- edited files

然后以 XML 标签追加到摘要：
- `<read-files>`
- `<modified-files>`

这说明上下文压缩不仅要保留“说了什么”，还要保留：
> **这轮 Agent 实际看过和改过什么。**

否则压缩以后，模型可能知道结论，却不知道：
- 哪些文件已经读过
- 哪些文件变过
- 下一步该从哪里继续

这是一种非常强的“证据和进度元数据保留”设计。

## 十、这一章真正解决了哪些工程问题？

### 1. 如何把会话树转换成稳定的模型上下文
Pi 的解法：状态推导 → 条目过滤 → 消息映射三段管线

### 2. 如何在压缩时保持工具协议完整
Pi 的解法：toolResult 不单独作为切点

### 3. 如何处理切在 turn 中间的压缩
Pi 的解法：turn prefix 单独摘要

### 4. 如何让多轮压缩保持历史连续性
Pi 的解法：retainedTail 内嵌 + 全量/增量摘要双 prompt

### 5. 如何让压缩后仍知道文件进度
Pi 的解法：read/written/edited 三态文件元数据

### 6. 如何让摘要请求不污染主执行缓存
Pi 的解法：cacheRetention none + 独立 sessionId

## 十一、读者最容易学错的地方

### 错觉 1：context.ts 只是把消息过滤一下
错，它先推导状态，再过滤条目，再映射消息。

### 错觉 2：压缩可以从任意字符位置切
错，必须对齐合法消息边界，尤其不能切开 tool call/result 语义。

### 错觉 3：retainedTail 是临时尾巴
错，它被嵌入 compaction entry，参与后续压缩。

### 错觉 4：摘要就是重新总结一次
错，后续会基于上一份摘要增量更新。

### 错觉 5：文件操作只是工具细节
错，它是压缩后继续执行所需的进度元数据。

## 十二、分析边界

### 为什么这里不先展开 AgentSession 的所有状态机
因为本章聚焦模型可见上下文和压缩算法，不重复完整会话状态机。

### 为什么不先展开 provider tokenizers
Pi 使用角色化估算，第一轮先看估算策略和压缩边界，不先陷入供应商 tokenizer 细节。

### 为什么测试是关键证据
压缩切点、工具结果配对、摘要序列化、UTF-8 截断等语义必须通过测试确认。

## 十三、读者分层路由

### beginner
先抓住：
1. 模型看到的不是全部历史，而是一个经过构建的视图
2. 压缩不是删除，而是摘要 + 尾巴 + 新消息
3. 工具请求和结果不能被压缩拆开

### intermediate
重点看：
- buildSessionContext 三段管线
- findCutPoint
- retainedTail
- split turn
- 文件操作元数据

### advanced
重点看：
- 摘要请求缓存隔离
- usage 优先 / 估算兜底
- 结构化摘要的增量更新
- 多轮压缩的语义连续性

## 十四、迁移清单

### 可迁移思想 1：条目→消息三段管线
- 可迁移到：有丰富会话条目和多种消息来源的 Agent
- 前提：状态推导、条目过滤、消息映射需要解耦
- 不适合直接照搬到：简单线性消息系统

### 可迁移思想 2：合法消息边界压缩
- 可迁移到：有工具调用协议的 Agent
- 前提：tool call/result 有配对语义
- 不适合直接照搬到：没有工具协议的纯文本聊天

### 可迁移思想 3：摘要增量更新而不是全量重建
- 可迁移到：长跑、多轮压缩的系统
- 前提：历史决策需要保连续性
- 不适合直接照搬到：短会话一次性摘要

### 可迁移思想 4：压缩保留文件操作元数据
- 可迁移到：源码分析、编码 Agent、工作区修改 Agent
- 前提：后续执行依赖“已读/已改文件”信息
- 不适合直接照搬到：不读写文件的通用聊天系统
