## 一、这一章真正的问题

读 Pi 的时候，最容易先看到的是：
- 它有很多工具
- 它也有 skills
- interactive-mode 里又能展示技能块
- system prompt 还能自动列技能清单

如果只停在这个层面，你会觉得：
- 工具很多
- 技能也很多
- 但没看出真正的结构

这一章真正要回答的是：

> **为什么 Pi 不满足于“一套 tools / 一套 skills”，而要刻意做出 harness 层和 core 层两套能力抽象。**

也就是说，它在解决的不是“功能怎么更多”，而是：
- 通用抽象和编码专用能力怎么分层
- 运行时能力如何被提示、加载、覆盖、扩展和远程化

---

## 二、先给结论：Pi 把能力系统拆成两层，是为了让“共享内核”和“具体产品形态”都成立

Pi 的工具和技能并不是简单重复两套实现，而是在明确回答：

### harness 层
- 放通用抽象
- 可跨模式 / 跨产品形态复用
- 更偏能力定义和协议

### core 层
- 放 coding-agent 具体需要的能力
- 更偏 UI、渲染、专用工具、扩展集成

所以这不是“代码重复”，而是：
> **一层负责通用 Agent 能力抽象，一层负责具体产品形态的实现。**

如果不这样分层，Pi 就会两头坏：
- 要么抽象层太薄，无法复用
- 要么产品层太重，通用内核被 UI / coding 场景绑死

---

## 三、为什么 AgentTool 契约是工具系统真正的主线

在 Pi 里，真正重要的不是 read / write / bash / grep 这些工具名字，
而是它们共同服从的 `AgentTool` 契约。

这个契约最关键的字段是：
- `label`
- `prepareArguments`
- `execute`
- `executionMode`

这意味着 Pi 对工具的理解不是：
- 一组函数

而是：
> **一组会被 loop 消费、会参与执行模式决策、会向模型返回结构化结果的运行时能力。**

其中尤其重要的是：
- `executionMode` 允许单工具覆盖默认的顺序/并行策略
- `addedToolNames` 允许工具在执行后为系统引入新能力
- `terminate` 可以让工具结果影响当前工具批控制流

这说明 Pi 的工具系统不是“静态工具箱”，而是：
> **会影响 loop 和会话推进语义的能力系统。**

---

## 四、为什么 core 工具层会比 harness 工具层更重

既有笔记已经说明：
- harness 版工具更通用
- core 版工具更多，也更重
- core 版里每个工具通常有两种暴露方式：
  - `createXxxTool`
  - `createXxxToolDefinition`

这说明什么？

说明 Pi 在这里并不是只在“增加功能”，而是在做：

> **工具能力从 runtime 协议对象，进一步变成可扩展、可注册、可被 UI / 扩展系统消费的定义对象。**

换句话说：
- harness 工具更像 loop 直接消费的能力
- core 工具更像 coding-agent 产品形态下的能力定义层

所以 core 层更重是合理的，因为它在承载：
- 专用工具
- 渲染细节
- 定义包装
- 扩展桥接
- 远程执行适配

## 五、为什么 `OutputAccumulator` 值得单独拎出来

这不是一个普通 util。

它解决的是一个 Agent 工具系统里特别现实的问题：

> **工具输出可能极大，但 runtime 不能因此无限吃内存，也不能让模型或 UI 丢失关键信息。**

Pi 的做法是：
- 内存滚动 tail（上限 2×预算）
- 超限才落临时文件
- 多字节 UTF-8 裁剪安全
- snapshot 时给出截断信息 + 完整输出路径

这说明 Pi 在工具输出上的原则是：

> **输出不只是数据，它还必须服从上下文预算、UI 可读性和恢复语义。**

所以 `OutputAccumulator` 实际上是：
- 工具系统
- 上下文管理
- UI 反馈
- 产物追踪

共同的交叉点。

## 六、为什么 Skills 不是 prompt 附件，而是另一条能力系统

Pi 的 skills 也有两层：
- harness `skills.ts`
- core `skills.ts`

而且它们的设计非常成熟：
- 技能来自 `SKILL.md`
- frontmatter + 正文
- 命名和 description 有硬校验
- 多源合并（user/project/path）
- 符号链接去重
- 名称碰撞有诊断
- system prompt 只注入技能清单，不注入正文
- 正文按需通过 read 工具加载

这说明 Skills 在 Pi 里不是：
- 提示词片段集合

而是：
> **一套被发现、校验、注入、按需读取、并受工具能力约束的运行时知识能力层。**

它和 Tool 系统之间不是从属关系，而是两条平行但互相协作的能力线：
- Tool = 执行能力
- Skill = 引导 / 方法 / 结构化知识能力

---

## 七、为什么“没有 read 工具就不注入技能清单”这么值钱

这句很小，但非常成熟。

Pi 的判断是：
- 如果当前工具集中没有 `read`
- 就不要往 system prompt 注入 `<available_skills>`

因为模型即使看到了技能清单，也没办法真的去读取 `SKILL.md`。

这说明 Pi 在做一个很重要的判断：

> **提示词内容必须与系统真实能力集一致。**

这比“多给模型一点提示”成熟得多。

它和我们前面在工具协议、权限系统里看到的思想是一致的：
- 不要向模型谎报能力
- 能力和提示必须严格对齐

---

## 八、为什么技能块格式值得重视

Pi 里 skill invocation 有统一格式：
- `<skill name="..." location="..."> ... </skill>`

这个格式不是渲染细节，而是：
- 用户主动 `/skill:` 调用的展开产物
- 模型通过 read 获取技能正文后的统一包装
- UI 折叠渲染的输入
- export-html 的消费对象

也就是说，它不是“某一层自创格式”，而是：
> **技能系统的统一调用协议。**

这很重要，因为一旦有了统一格式：
- 用户路径
- 模型路径
- UI 路径
- 导出路径
都能复用同一套语义。

## 九、这一章真正解决了哪些工程问题？

### 1. 如何让通用 Agent 能力和具体产品形态能力分层
Pi 的解法：harness tools / core tools 双层，harness skills / core skills 双层

### 2. 如何让工具能力既能被 loop 消费，又能被扩展系统注册
Pi 的解法：AgentTool ↔ ToolDefinition 双向桥接

### 3. 如何让长工具输出既不炸内存，也不丢完整结果
Pi 的解法：OutputAccumulator 有界内存 + 按需落盘

### 4. 如何让技能进入上下文而不撑爆上下文
Pi 的解法：技能清单注入 + 正文按需读取

### 5. 如何让提示词内容和实际能力集严格一致
Pi 的解法：无 read 不注入 skills；system prompt 按工具集动态组装

这一章真正要学的，不是“Pi 有很多工具和 skills”，而是：

> **Pi 如何把执行能力和引导能力都做成分层、可组合、可动态显露的能力系统。**

## 十、读者最容易学错的地方

### 错觉 1：两套工具系统只是重复代码
错。它们分别在解决通用抽象和具体产品形态的问题。

### 错觉 2：skills 就是 prompt 片段
错。它是被发现、校验、注入、按需加载和渲染的一整套能力层。

### 错觉 3：OutputAccumulator 只是输出优化
错。它在保护内存、UI、上下文和恢复语义。

### 错觉 4：`/skill:` 和模型自动读 skill 是两套逻辑
错。两者最终都收敛到同一个技能块协议。

### 错觉 5：只要技能存在，就应该注入给模型
错。没有 read 能力时注入技能清单是无效甚至误导性的。

## 十一、分析边界

### 为什么这里不先深挖某个具体 leaf tool
因为这一章关心的是能力系统的分层和协议，不是单个工具本身的业务逻辑。

### 为什么这里不先展开 provider / model 层
因为 provider 抽象是另一条主线，这一章先站稳 tools + skills 这条能力系统主线。

### 为什么测试是关键证据
多源技能合并、冲突诊断、调用包装、输出有界、双创建函数，这些行为很多要靠测试契约才能看清楚。

- 动态工具注册（addedToolNames）的系统意义

## 十三、迁移清单

### 可迁移思想 1：能力系统双层抽象
- 可迁移到：既有通用 runtime 又有具体产品形态的 Agent 系统
- 前提：你真的需要复用内核，不只是复制功能
- 不适合直接照搬到：小而单一的 Agent 原型

### 可迁移思想 2：工具与定义双形态
- 可迁移到：需要同时服务 loop 和扩展系统的工具层
- 前提：工具既是执行对象，也是注册对象
- 不适合直接照搬到：没有插件/扩展系统的极简 Agent

### 可迁移思想 3：技能清单注入 + 正文按需读取
- 可迁移到：上下文预算敏感的 Agent
- 前提：技能文本体量大、种类多
- 不适合直接照搬到：技能极少且极短的场景

### 可迁移思想 4：提示词严格跟随能力集变化
- 可迁移到：任何支持动态切换工具集/模式的系统
- 前提：系统能重建 prompt
- 不适合直接照搬到：固定工具集、固定上下文的简单系统
