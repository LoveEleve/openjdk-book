# Pi 横向对比锚点

> 用途：从 Pi 第一卷中抽出后续与 OpenCode / Reasonix / Hermes / dsh 对比时可直接复用的比较维度。

---

## 一、Pi 整体画像

一句话定义：

> **Pi 是把 Agent 做成一个可跨多形态前端复用、由显式会话状态机驱动、并通过会话树与能力分层维持一致性的共享运行时。**

---

## 二、最核心的 10 个对比锚点

## P-A1 执行骨架
- Pi 的做法：`AgentLoop` + `AgentSession`
- 对比问题：其他项目的复杂度中心是在 loop、controller、event store，还是会话状态机？

## P-A2 多形态共享内核
- Pi 的做法：interactive / print / rpc 共用 `AgentSessionRuntime`
- 对比问题：其他项目有没有真正共享的运行时内核？

## P-A3 控制流收束
- Pi 的做法：steering / follow-up / retry / compaction / abort 都进入 session 状态机
- 对比问题：其他项目把复杂控制流收进哪里？

## P-A4 工具系统分层
- Pi 的做法：harness tools + core tools 双层抽象
- 对比问题：其他项目的工具系统是一层直连，还是也有运行时层与具体层分离？

## P-A5 技能系统分层
- Pi 的做法：skills 在 harness 和 core 都存在
- 对比问题：其他项目的 skills 是提示词资产，还是运行时能力层？

## P-A6 会话真相层
- Pi 的做法：JSONL 追加写 + `parentId` 树 + `leaf` 分支语义
- 对比问题：其他项目的历史是线性的、事件流的，还是树形探索结构？

## P-A7 系统状态与模型状态分离
- Pi 的做法：`custom` / `session_info` / `label` 可持久化，但不进入 LLM 上下文
- 对比问题：其他项目如何区分系统真相与模型可见视图？

## P-A8 压缩语义
- Pi 的做法：summary + tail + new messages 重建上下文
- 对比问题：其他项目的压缩是删历史、写快照，还是正式状态转换？

## P-A9 事实层
- Pi 的做法：records / lanes 记录轨迹，facts 记录长期知识
- 对比问题：其他项目是否把“发生过什么”和“以后该记住什么”分开？

## P-A10 模型能力层
- Pi 的做法：provider / api / auth / models + ProviderComposer
- 对比问题：其他项目是 provider 适配集合，还是统一模型能力层？

---

## 三、一句话结论

如果只用一句话概括 Pi：

> **它代表了共享运行时路线的 Agent 架构版本——复杂度不落在前端壳上，而落在显式会话状态机、可分支持久层和分层能力系统上。**
