## 一、这一章真正的问题

一个 Agent 如果只能在当前进程里跑，就很难称为长期运行系统。

它还必须回答：
- 会话怎么持久化？
- 压缩之后旧历史去哪？
- 走错路怎么回退？
- 分支怎么保留？
- 事实和原始会话轨迹怎么区分？
- 上次分析到哪里，下一次怎么继续？

所以这一章真正的问题是：

> **Pi 如何把短期执行状态、长期会话树、事实知识和历史轨迹组织成一个可恢复、可分支、可迁移的持久层。**

---

## 二、先给结论：Pi 的会话不是线性消息流，而是一棵可分支的持久化树

最容易犯的错，是把 session 理解成：
- 一个 JSON 数组
- 每次追加一条消息
- 最后按顺序读回来

Pi 的设计明显更强：
- JSONL 追加写
- 每个 entry 有 id / parentId
- `leaf` 指向当前分支位置
- branch 可以回到旧节点
- 后续追加会形成新分支

这意味着：

> **会话不是线性历史，而是探索路径树。**

这对源码学习型 Agent 特别重要，因为分析过程天然存在：
- 走错路径
- 回退
- 换方向
- 保留旧探索结果
- 从一条分支导出独立成果

所以 SessionManager 在 Pi 里不是“存消息”，而是：
> **持久化探索过程。**

---

## 三、为什么 JSONL 追加写 + 树形 entry 适合 Agent 会话

Pi 的会话文件使用 JSONL，每一行是一个 entry。

这个选择有几个重要好处：

### 1. 追加写天然适合长会话
不用每次重写整个文件，后续状态可以继续追加。

### 2. entry 有 parentId，允许分支
新 entry 不只是排在最后，而是挂在当前 leaf 上。

### 3. header 保存会话身份与 cwd
会话可以被恢复、列表化、迁移。

### 4. 版本迁移可以显式进行
旧 session 文件不是静默猜，而是经过版本迁移后再加载。

这说明 Pi 的持久层关注的不是“存下文本”，而是：
> **存下可以继续演进的会话结构。**

---

## 四、为什么压缩是“摘要 + 尾巴 + 新消息”三段式

Pi 的压缩不是把旧历史直接删掉。

它会构造：
1. compaction summary
2. `firstKeptEntryId` 之后仍重要的尾巴
3. compaction 之后的新条目

这样做解决的是：

- 旧历史过长，不能全部进上下文
- 但最近关键工具结果 / 用户指令不能丢
- 新消息必须继续连在摘要之后

所以模型看到的是一个“精简后的上下文视图”，而持久层仍然保留完整历史。

这和前面 OpenCode / Reasonix 的核心思想一致：

> **模型可见视图可以压缩，但系统历史不能随便丢。**

---

## 五、为什么 branch 不是复制文件，而是移动 leaf

Pi 的 branch 操作非常优雅：
- 不修改旧历史
- 只把 `leaf` 移回某个旧 entry
- 后续 append 自动形成新分支

这意味着：

> **分支是“改变未来写入位置”，而不是“重写过去”。**

这是一种非常适合分析型 Agent 的模型：
- 原来的探索路径仍然存在
- 你可以从中间节点重新开始
- 不同方向之间互不覆盖

`branchWithSummary` 进一步把被放弃路径压成摘要，避免读者完全丢失探索背景。

而 `createBranchedSession` 则可以把当前分支提取成一个新的独立会话。

这非常像：
- 一次源码探索形成多个分支
- 最后把一条清晰主线导出成正式成果

## 六、为什么 CustomEntry 不应该进入 LLM 上下文

Pi 的 entry 类型不只有 message，还有：
- custom
- label
- session_info
- model change
- thinking level change
- compaction
- branch summary

其中 `CustomEntry` 的设计特别关键：
- 它可以持久化扩展状态
- 但不参与 LLM 上下文

这说明 Pi 明确区分了：

### 系统持久化状态
- 给扩展 / 管理面 / 恢复逻辑用

### LLM 可见上下文
- 只放真正需要影响模型推理的内容

如果所有状态都直接塞进上下文：
- token 会膨胀
- 扩展实现会污染模型行为
- 内部元数据会被模型误读

所以 CustomEntry 的真正价值是：
> **允许持久化状态存在，但不污染模型心智。**

---

## 七、为什么 facts 和 records / history 必须分层

Pi 的存储层不仅有会话记录，还有 facts。

这是一个很重要的分层：

### records / lanes
记录：
- 发生过什么
- 哪条会话路径走过什么
- 哪个分支被选择

### facts
记录：
- 系统认为应该长期保留的事实
- 可被后续任务重新使用的结构化知识

这两者不能混在一起，因为：
- 轨迹不是事实
- 对话内容不是稳定知识
- 某次探索中间结果不一定值得常驻

所以这层的设计价值是：
> **把“发生过什么”和“以后应该记住什么”分开。**

这也是 Pi 对产品④知识库最直接的参考之一。

---

## 八、为什么无效会话不立即落盘

Pi 有一个很值得学的策略：
- 在第一条 assistant 消息产生前，先只保留内存状态
- 真正产生有效 assistant 输出后，再开始写文件

这解决的是：
- 用户只输入了一句话
- 但模型没有实际产出
- 不应该生成大量垃圾会话文件

所以 Pi 在这里做了一个很清楚的判断：

> **持久化应该记录有意义的执行成果，而不是所有瞬时尝试。**

这和源码学习场景非常契合：
- 无效探索不污染长期知识库
- 真正产出才进入持久层

## 九、为什么要做断链容错、分块加载和 header 快速读取

这部分看起来像存储工程细节，实际上是长期会话系统能不能活下来的基础。

### 1. 断链容错
如果 parent 缺失：
- 不让整个文件崩
- 把孤儿条目当 root 保留

这体现的是：
> 内容先保住，结构可以降级。

### 2. 分块加载
大文件不全量读进内存，而是：
- 1MB buffer 分块
- StringDecoder 处理多字节边界
- 坏 JSON 行跳过

### 3. header 快速读取
找最近会话时，只读：
- header
- 文件 stat

不加载完整历史。

这三件事共同解决的是：
> **会话越来越多、越来越大之后，系统仍然能稳定打开、列举和恢复。**

## 十、这一章真正解决了哪些工程问题？

### 1. 如何持久化可分支的探索历史
Pi 的解法：JSONL 追加 + parentId 树 + leaf

### 2. 如何让压缩不丢完整历史
Pi 的解法：summary + 尾巴 + 新增消息的上下文重建

### 3. 如何让走错路的分析可回退且不覆盖旧路径
Pi 的解法：branch / branchWithSummary / createBranchedSession

### 4. 如何让内部扩展状态不污染 LLM 上下文
Pi 的解法：CustomEntry / label / session_info 分层

### 5. 如何把事实与原始轨迹分开
Pi 的解法：facts vs records / lanes / history

### 6. 如何保证大规模会话文件可恢复、可列举、可迁移
Pi 的解法：分块加载、坏行容错、header 快速读取、并发列表加载

## 十一、读者最容易学错的地方

### 错觉 1：JSONL 就是简单日志
错。parentId + leaf 让它成为会话树。

### 错觉 2：branch 会修改旧历史
错。它只是移动未来写入位置。

### 错觉 3：compaction 会删除旧内容
错。它只改变模型可见视图，完整历史仍在持久层。

### 错觉 4：所有 entry 都应该进入 LLM 上下文
错。custom / label / session_info 等属于系统持久化状态。

### 错觉 5：facts 就是 history 的另一种名字
错。facts 是长期知识，history 是原始轨迹。

## 十二、分析边界

### 为什么这里不先看 TUI 会话选择器
因为当前重点是存储模型和恢复语义，不是用户如何点选会话。

### 为什么要看 JSONL 损坏容错和加载性能
因为长期会话系统的核心难题是“文件越来越大、历史越来越多后还能不能稳定工作”。

### 为什么 facts 不和 message 一起看
因为事实层和轨迹层是不同的知识模型，混在一起会导致长期知识污染。

## 十四、迁移清单

### 可迁移思想 1：会话用追加树存储
- 可迁移到：分析探索、调试、计划分支型 Agent
- 前提：系统允许回退和多路径探索
- 不适合直接照搬到：严格线性、无分支的交互系统

### 可迁移思想 2：完整历史与模型上下文分离
- 可迁移到：有 compaction 的长跑 Agent
- 前提：系统要支持按需恢复完整历史
- 不适合直接照搬到：无持久化、只做短对话的系统

### 可迁移思想 3：CustomEntry 不污染上下文
- 可迁移到：插件、事实、扩展状态需要持久化的 Agent
- 前提：系统能区分管理状态和模型状态
- 不适合直接照搬到：没有扩展状态的极简系统

### 可迁移思想 4：header 快速读取 + 分块加载
- 可迁移到：会话数量和单文件都可能增长的大型系统
- 前提：文件格式支持快速 header 与增量读取
- 不适合直接照搬到：小规模内存应用
