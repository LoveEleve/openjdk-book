## 一、这一卷到底在讲什么？

如果只看单篇标题，你会觉得 Pi 这一卷讲了很多模块：
- loop
- session
- runtime
- tools
- skills
- storage
- compaction
- provider

但如果把这些篇章真正收回来，Pi 第一卷其实只在讲一件事：

> **Pi 如何把 Agent 做成一个可跨 interactive / print / rpc 多形态复用、由显式会话状态机驱动、并通过存储、压缩和能力抽象维持一致性的共享运行时。**

也就是：Pi 不是“功能很多”，而是：

```text
Agent Loop
  ↓
AgentSession 状态机
  ↓
AgentSessionRuntime / Modes
  ↓
双层工具与技能系统
  ↓
Session 持久化 / 会话树 / facts
  ↓
Context / Compaction
  ↓
LLM / ProviderComposer / 模型能力层
```

这正是我们在范围规划里给它下的判断：
> Pi 的本质不是另一个会调模型的工具，而是一个共享运行时。

## 二、Pi 最值得记住的 6 个系统判断

## 1. Loop 不是核心，Session 才是核心

Pi 当然有 Agent loop，但 loop 主要负责：
- 推进当前 turn
- 消费 tool continuation
- 处理 steering / follow-up 的注入时机

真正把复杂度收束起来的，是 `AgentSession`：
- pending
- steering
- follow-up
- compaction
- retry
- overflow recovery
- bash abort
- extension runner

这说明 Pi 最成熟的地方，不是“能跑几轮”，而是：
> **它把复杂控制流收进了显式会话状态机。**

---

## 2. 多前端不是多套逻辑，而是同一内核的不同壳

Pi 从一开始就坚持：
- interactive
- print
- rpc

都共享同一个 `AgentSessionRuntime` / `AgentSession` 语义核心。

这意味着：
- 前端不自己发明状态机
- 不同模式不各写一套执行逻辑
- 生命周期语义不会因为 UI 变化而分裂

所以 Pi 的关键不是“支持多模式”，而是：
> **多模式背后只有一个运行时内核。**

---

## 3. 工具和技能都不是单层实现

Pi 的另一个高价值判断是：
- harness 层保留运行时抽象
- core / coding-agent 层承接具体能力与策略

这在 tools 和 skills 上都成立。

它解决的是：
- 如何让运行时内核保持稳定
- 如何让具体产品能力不断扩展
- 如何让模式壳、会话层和能力层彼此解耦

所以这里最值得迁移的不是某个 tool，而是：
> **能力抽象要分层，不能把运行时和具体能力揉在一起。**

---

## 4. 会话真相不是线性消息流，而是可分支的探索树

Pi 的会话存储不是普通聊天记录：
- JSONL 追加写
- entry 带 `parentId`
- `leaf` 决定当前分支位置
- branch / branch summary / createBranchedSession
- label / custom / session_info

这说明 Pi 从一开始就承认：
- 会话会回退
- 会话会分叉
- 会话会导出清晰主线

所以 SessionManager 真正存的不是消息，而是：
> **探索过程。**

---

## 5. 压缩不是删历史，而是重建模型可见视图

Pi 的 compaction 不是“裁掉旧消息”这么简单。

它真正做的是：
- 生成 summary
- 保留仍有执行意义的尾巴
- 用摘要 + 尾巴 + 新消息重建上下文

这和 Session 状态机、持久层、上下文工程是绑在一起的。

因此 Pi 的压缩不是外围优化，而是：
> **会话状态转换的一部分。**

---

## 6. 模型接入层不是 provider 列表，而是模型能力平面

Pi 的 `ai/` 体系拆成：
- provider
- api
- auth
- models
- provider composer

这说明它关心的不是“接几家模型”，而是：
- 如何统一模型能力描述
- 如何处理多供应商差异
- 如何把 OAuth / API key / runtime credentials 收进系统
- 如何把 constrained sampling 和 context clamp 变成运行时能力

所以这一层最值得记住的是：
> **Pi 在做统一模型能力层，而不是 provider 大杂烩。**

---

## 三、Pi 最值得迁移的思想

### 1. 共享运行时内核
不要让不同交互形态各写一套执行逻辑。

### 2. 显式会话状态机
把 steering、follow-up、retry、compaction 收进统一状态机。

### 3. 双层能力抽象
运行时层和具体工具/技能层解耦。

### 4. 可分支会话树
把探索历史建模成树，而不是线性消息数组。

### 5. 系统状态与 LLM 可见状态分离
`custom` / `session_info` 可以持久化，但不进入上下文。

### 6. 压缩作为正式状态转换
摘要不是附属品，而是上下文重建的一部分。

### 7. 模型能力层分层
provider / api / auth / models 各司其职。

## 五、一句话结论

Pi 第一卷最本质的收获，不是“它支持很多模式”，而是：

> **它展示了一个 Agent 系统如何通过共享运行时、显式会话状态机、可分支持久层和分层能力抽象，把多形态前端统一成同一个内核。**
