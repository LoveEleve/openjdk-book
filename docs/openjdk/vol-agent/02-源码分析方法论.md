# 源码分析方法论

> 目标：不是“把源码看一遍然后总结”，而是建立一套能稳定产出高质量源码学习书的分析方法。
> 定位：作为 `vol-agent/` 下 5 个 Agent 项目反向分析、以及后续源码学习 Agent 产品设计的统一方法论基线。

---

## 一、一句话方法论

> **从项目根问题出发，沿着主线机制、横切专题、风险边界、时间演进与目标导向，重建系统。**

也就是说，分析源码不是先问：
- 有哪些包
- 有哪些类
- 有哪些 API

而是先问：
1. 这个项目到底在解决什么问题？
2. 它靠哪些核心机制成立？
3. 哪些约束横切全局、支配多个模块？
4. 哪些地方最容易学错、用错、排障失败？
5. 读者为什么会在这些地方学不会？

---

## 二、分析主线

## 2.1 先找项目根问题（Project Thesis）

先回答：
- 这个项目为什么存在？
- 它在替使用者消化什么复杂度？
- 它在拿什么换什么？

典型产物：
- `project thesis`
- `root problems`
- `design theses`
- `architectural promises`

例子（以 Netty 为例）：
- 高并发 I/O 如何避免线程同步开销
- 内存如何减少分配、复制和 GC
- 事件传播如何统一表达，同时保持性能与可扩展性
- 上层协议如何建立在统一骨架之上

如果这一步没做，后面所有阅读都会退化成“记模块”。

---

## 2.2 再找主线机制（Mainline Mechanisms）

不要先列模块，要先识别：

> **没有哪些机制，这个系统就不成立？**

这些通常是：
- 执行骨架
- I/O 抽象边界
- 事件传播主链
- 内存模型
- 发送路径
- 异步控制回路

例子（Netty）：
- EventLoop / EventExecutor
- Channel / Unsafe
- Pipeline / HandlerContext
- ByteBuf
- PooledByteBufAllocator
- OutboundBuffer / write / flush
- Promise / Future / task queue

典型产物：
- `mainline mechanisms`
- `layer classification`
- `why_core`

---

## 2.3 再找横切专题（Crosscutting Tracks）

真正难的地方，往往不在模块目录里，而在多个模块共享的约束：
- 所有权 / 引用计数
- 线程亲和
- 背压
- 池化与复用
- leak / failure boundary
- 演进与兼容边界

好的源码分析，不只是按模块讲，而是同时建立：
- **主线机制**
- **横切专题**

典型产物：
- `crosscutting tracks`
- `constraint map`

---

## 2.4 建立理解依赖拓扑（Dependency Topology）

源码学习最容易失败的原因之一是顺序错了。

所以不是按“用户怎么用”来排，而是按：

> **不理解 B，就无法真正理解 A**

例子：
- 不理解 EventLoop，就很难理解 Channel 生命周期
- 不理解 Pipeline，就很难理解 codec
- 不理解 ByteBuf 所有权，就很难理解发送路径和池化行为

典型产物：
- `dependency topology`
- `chapter order`
- `source-order vs user-order`

---

## 2.5 抽取认知风险点（Cognitive Risks）

源码分析不能只讲“它怎么工作”，还要讲：
- 哪些地方最容易误解？
- 哪些地方最容易误用？
- 哪些地方最容易形成“看着懂了，其实没懂”的幻觉？

典型风险：
- 把 API 当机制
- 把兼容层当核心
- 不理解 flush / write 的分离
- 不理解引用计数的所有权边界
- 把 EventLoop 当普通线程池

典型产物：
- `cognitive risks`
- `failure boundaries`
- `anti-patterns`
- `risk hotspots`

---

## 2.6 做深度分层（Depth Layering）

不是所有章节都一样重要。

需要分成：
- `A`：项目本质、依赖中心、复杂度高、误区多
- `B`：核心支撑层
- `C`：外围协议、案例、应用层

如果所有章节都一样重，分析一定会浅。

典型产物：
- `depth map`
- `importance ranking`
- `hard-point mining`

---

## 2.7 最后才生成书级结构（Book Structure）

前面做完，最后才长出：
- 主线章节
- 横切专题章节
- 风险章节
- 演进章节
- 迁移章节
- 自测章节

最终输出不是一份“总结”，而是一套：
> **帮助读者真正学会这份源码的认知脚手架**

---

## 三、分析边界规则（Analysis Boundary Rules）

源码分析方法论不只是“怎么分析”，还必须回答：

> **什么默认不应该进入主线？**

否则 Agent 很容易失真成“看起来丰富，实际上主次跑偏”。

### B1. UI 默认不进主线
除非 UI 本身承载项目核心设计。

- 对于 Netty / JVM / MySQL / RPC 框架 / Agent runtime 这类系统：
  - UI 不是主线
  - UI 通常属于 `application layer` 或 `C 深度`
- 对于前端框架 / IDE / 图形系统：
  - UI 可能就是主线

### B2. 非 Linux / 非主流生产路径默认后置
除非它会改变对主机制的理解。

- 默认优先解释：
  - Linux 路径
  - 主流生产路径
- 平台分支（Windows / macOS / kqueue / epoll / io_uring 等）默认：
  - 差异提示
  - 或后置专题

### B3. Demo / example 默认不进主线
它们可以作为：
- 案例层
- 验证层
- 章节尾部辅助材料

但不能反客为主替代系统主线。

### B4. 测试代码默认不进主线
但测试在这些场景里很重要：
- API 预期行为
- 边界条件
- 失败用例
- 作者认为最关键的不变量

所以测试代码定位应是：
> **证据增强层，不是主线机制层。**

### B5. benchmark / microbench 对性能导向项目必须纳入证据体系
对：
- Netty
- JVM
- 并发库
- 内存池
- 数据库

benchmark 很重要，因为它告诉你：
> 作者到底在优化什么。

### B6. 第三方依赖默认不进主线
除非它是关键路径的真实承载者。

例如：
- 某条关键执行路径实际上落在第三方 native transport / allocator / runtime 上
- 那它才值得进入正文主线

否则：
- 只做边界提示
- 不抢主线

### B7. 废弃 / 兼容代码默认不进主线
只在两种情况下引入：
1. 它能解释“为什么现在会这样设计”
2. 它能解释“哪些是兼容层而不是核心机制”

### B8. 平台差异只在影响机制本质时进入正文
否则只做差异提示。

## 四、为什么这套方法论比普通源码总结强？

普通源码总结通常只做了：
- 文件梳理
- 模块介绍
- API 说明

这套方法论额外解决的是：
- 从哪开始
- 先学什么
- 为什么这样设计
- 哪些约束横切全局
- 哪里最容易学错
- 哪些是主线，哪些是外围
- 哪些地方值得拉深
- 如何迁移到别的项目

也就是说，它不是“信息整理方法”，而是：
> **认知工程方法**

---

## 五、最终的标准分析链路

完整链路应该是：

```text
项目根问题
  ↓
主线机制
  ↓
横切专题
  ↓
理解依赖拓扑
  ↓
认知风险点
  ↓
深度分层
  ↓
分析边界规则
  ↓
书级结构
```

一句话总结就是：

> **根问题 → 主线机制 → 横切专题 → 风险边界 → 深度分层 → 分析边界规则 → 书级结构**

## 六、分析强化规则（建议补充）

### 6.1 分析视角选择规则

不是所有章节都该用同一种分析套路。需要先判断：

- 执行骨架类机制 → 先看执行语义 / 顺序保证 / 调度边界
- 内存类机制 → 先看所有权 / 生命周期 / 分配与释放语义
- 发送路径类机制 → 先看数据流、缓冲、背压与 flush 边界
- 协议层 → 先看它建立在什么主线机制之上，而不是先看 API
- 装配层 / 工具层 → 先看它怎样连接主线，而不是把它误当成系统本体

目的不是写出“多视角内容”，而是避免所有章节都变成一套模板口吻。

### 6.2 章节完成 / 停止条件

源码分析最容易无限展开，所以要定义“这一章什么时候算真正学懂了”。

一个章节至少应满足：

1. 能解释它在系统中的职责
2. 能解释它与前后机制的依赖关系
3. 能给出至少 2 个真实 `file:line` 证据
4. 能指出至少 1 个失败边界 / 风险点
5. 能说清它最容易被误解的地方
6. 能把它挂到至少 1 条横切专题上

满足这些后，才算章节可以收口，而不是继续无止境扩写。

### 6.3 反伪洞察规则

源码分析里最常见的伪深度是：
- “这里体现了解耦”
- “这里用了经典模式”
- “这里是为了性能”

这些话可能没错，但太泛，无法真正帮助读者理解源码。

一条洞察至少满足以下 3 条中的 2 条，才算有价值：

1. 它能解释一个具体设计选择
2. 它能解释一个具体风险 / 失败边界
3. 它能帮助迁移到别的项目

否则就只是“看起来像懂了”的废话。

### 6.4 主机制 vs 重要机制 区分规则

不是所有重要机制都是主机制。

- **主机制**：没有它，系统不成立
- **重要机制**：虽然不是骨架，但对理解 / 性能 / 安全非常关键
- **外围机制**：建立在主机制之上的应用层、协议层或工具层

这个区分能防止把 LeakDetector、HTTP、示例工程、Bootstrap 这些内容拉成主线。

### 6.5 认知错觉点（Illusion Points）

除了“风险点”，还要单独识别“看起来懂了其实没懂”的错觉：

- 以为 EventLoop 就是线程池
- 以为 Pipeline 就是责任链
- 以为 ByteBuf 只是更好用的 ByteBuffer
- 以为池化只是为了性能
- 以为案例路径就是主线机制

这些错觉点不是简单误用，而是认知层面的伪理解，必须主动拆掉。

## 七、进一步的系统性补充

### 7.1 读者分层路由规则

同一套源码，不同读者应该走不同的分析路径：

- **beginner**
  - 先 thesis → 主机制 → 前置认知桥 → 再看源码证据
  - 优先建立“系统为什么存在、骨架怎么成立”的直觉
- **intermediate**
  - 直接进入主机制 + 横切专题
  - 背景桥降级成附注，只在卡点处补
- **advanced**
  - 压缩背景桥
  - 重点放在 trade-off、风险边界、演进和跨项目迁移

也就是说，分析方法不能只说“怎么分析源码”，还要说：
> **针对什么层次的读者，以什么顺序、多少背景密度去分析。**

### 7.2 项目类型分类器（Project Archetype Classifier）

不同项目类型，主线机制结构不同，不能一套模板看所有源码。

应先识别项目大类，例如：
- 网络框架型（如 Netty）
- 运行时 / VM 型
- 数据库型
- Agent / orchestration 型
- 前端框架型
- 工具链型

然后按项目类型决定：
- 哪些主机制优先
- 哪些横切机制最重要
- 哪些边界规则适用
- 哪些章节角色更容易出现

例如：
- Netty：执行骨架 / 发送路径 / 内存模型优先
- Agent：loop / context / evaluator / tool / sandbox 优先
- 数据库：存储结构 / 并发控制 / 崩溃恢复优先

### 7.3 证据层级模型（Evidence Hierarchy）

证据本身也有层级，不能一视同仁。

建议分成：
- **主证据**：当前章节主线源码中的 `file:line`
- **辅助证据**：测试、benchmark、注释、文档
- **外围证据**：第三方依赖、平台差异、外围模块
- **风险证据**：异常处理、释放路径、失败分支
- **演进证据**：git blame / log / show

规则：
- 主结论只能由主证据或明确的风险证据支撑
- 辅助证据不能替代主线源码证据
- 演进证据只能解释“为什么现在这样”，不能替代当前实现
- 外围证据只能出现在差异说明或附加讨论中

### 7.4 最终读者能力判据（Reader Outcome Model）

一份分析最后是否真的有价值，不只看：
- 结构像不像书
- 痛点是否被覆盖

还要看：
> **读者读完之后，是否真的获得了新的能力。**

至少应能带来这些能力提升：
1. 能解释系统为什么这样设计
2. 能说清主线机制与横切机制的关系
3. 能指出关键 trade-off
4. 能从症状回推高风险边界
5. 能把学到的思想迁移到相似项目
6. 能复述自己的理解，而不是只背 API

也就是说，最终验收不仅要问“这本书写得对不对”，还要问：
> **读者读完之后，会不会比之前更会。**

## 八、这份方法论在 vol-agent 中的用途

后续在：
- `pi/`
- `reasonix/`
- `hermes/`
- `opencode/`
- `dsh/`

下面分析 5 个 Agent 项目时，不该只是“看它们有哪些模块”，而应该围绕这套方法论去问：

1. 它是怎么识别项目根问题的？
2. 它有没有主线机制与横切机制的区分？
3. 它有没有处理读者最容易学错的地方？
4. 它有没有分析边界规则（UI / demo / test / 非主流路径）？
5. 它有没有根据读者分层做路径路由？
6. 它有没有项目类型识别能力？
7. 它有没有明确的证据层级模型？
8. 它最后产出的，是“目录”，还是“认知脚手架”？
9. 它有没有明确的视角切换、停止条件和反伪洞察机制？
10. 它最终到底能不能让读者“更会”。

也就是说，这份方法论既是：
- 后续 5 个 Agent 分析的统一坐标系
- 也是源码学习 Agent 产品设计的总方法论基线
