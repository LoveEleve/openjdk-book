# dsh 共享执行世界源码解析：为什么 fs、shell、subprocess、sandbox 必须指向同一个世界

> 解析对象：`sandbox/`、`subprocess/`、`shell/`、`fs/`
> 定位：dsh 第十份真正源码解析，验证“共享执行世界 + capability seam + 同步边界”这条副作用主线。
> 关联机制分析：`dsh/07-高价值专题清单.md`

---

## 一、解析对象

- 文件名：`sandbox/`、`subprocess/`、`shell/`、`fs/`
- 行数范围：`packages/sandbox/` 与 `packages/subprocess/` 的共享环境绑定、策略检查、执行与回传主流程；闭环材料明确覆盖 sandbox 核心约 452 行、subprocess 核心约 428 行及测试契约
- 核心函数/方法：sandbox world 建立、fs/shell/subprocess provider 绑定、调用策略检查、结果返回
- 入口事件/命令：Agent 通过工具或 provider 请求读写文件、执行 shell、启动子进程
- 出口事件/返回：同一执行世界内的文件视图、进程视图和策略边界下的副作用结果

## 二、调用链

```text
工具或运行时请求副作用能力
  → capability seam 解析到 fs / shell / subprocess provider
  → provider 绑定到同一个 sandbox world
  → 调用前检查策略与权限边界
  → 在共享世界内执行文件/命令/进程操作
  → 把结果回传给 session / tool result / 后续步骤
```

## 三、状态转换

| 状态 | 进入条件 | 离开条件 | 关键行 |
|------|----------|----------|--------|
| world initialized | sandbox 世界建立 | provider 绑定完成 | sandbox init 段 |
| provider bound | fs/shell/subprocess 挂入 ctx | 开始接收调用 | provider mount 段 |
| policy checked | 某次调用到达 | 放行或拒绝 | policy/guard 段 |
| executing | 调用在共享世界内运行 | 返回结果或失败 | execute 段 |
| world reused | 后续能力调用继续落在同一环境 | 生命周期结束 | world reuse 段 |

## 四、关键分支

| 分支 | 判断条件 | line | 结果 |
|------|----------|------|------|
| same world binding | 多能力共享同一 sandbox 实例 | provider bind 段 | 文件与进程看到同一执行环境 |
| per-call policy | 当前调用策略不同 | policy 段 | 同一 provider 在不同调用上可有不同边界 |
| shell vs subprocess | 需要 shell 语义还是裸进程语义 | provider route 段 | 走不同执行接口但同属一世界 |
| fs mutation visible | 前一步改文件后下一步读取 | shared world 段 | 后续能力立刻看到同一状态 |
| sandbox denial | 世界边界禁止当前动作 | guard 段 | 返回拒绝/失败而非越界执行 |

## 五、数据流

- 输入来源：tool call、fs/shell/subprocess capability 请求、当前 sandbox 配置与策略
- 传递路径：capability seam → provider bind → shared world execute → result 回流
- 输出去向：文件状态变化、命令输出、子进程状态、会话/tool result 中的副作用结果

## 六、测试契约

| 测试名 | 位置 | 验证内容 |
|--------|------|----------|
| escalation 契约 | `packages/sandbox/tests/escalation.spec.ts` | 验证 read-only → workspace-write → danger-full-access 的严格升级阶梯与 fail-closed |

## 七、总结

- 核心结论：dsh 的共享执行世界不是实现细节，而是 capability seam 真正落地后的边界保证：不同能力看到的是同一个环境，而不是各自的幻觉副本。
- 可迁移点：如果 Agent 同时有 fs、shell、subprocess 等副作用能力，它们最好共享同一执行世界，否则验证、恢复和后续推理都会失真。
- 易错点：把这些能力拆成互不相关的 provider；那样文件修改、命令执行和进程状态会来自不同世界，系统一致性会被破坏。
