## 一、这一章真正的问题

dsh 和其他 4 个项目最本质的区别不是“功能更多”，而是：

> **dsh 选择了一个“一切皆插件”的架构。**

这意味着：
- 没有特权核心
- 所有能力都是可替换插件
- 扩展 = 在旁边挂插件，不是改核心

这一章真正要回答的是：

1. 为什么 dsh 选择 Cordis 作为插件框架？
2. 五想法（插件、上下文、inject、事件、可逆效果）如何构成“一切皆插件”的基础？
3. 四分派模式（emit / waterfall / parallel / serial）各自对应什么场景？
4. 为什么“注册 = 可逆效果”是热重载和插拔安全的基础？

## 二、先给结论：Cordis 不是“又一个 ioc 容器”，而是一个“插件运行时”

最容易犯的错，是把 Cordis 理解成：
- 一个 ioc 容器
- 一个依赖注入框架

这不对。

更准确的理解是：

> **Cordis 是一个插件运行时：插件 = 服务 + 类型化事件 + 可逆效果。**

它不是在帮你管理依赖，而是在帮你：
- 定义插件
- 声明依赖
- 发布事件
- 注册可逆效果

---

## 三、五想法如何构成“一切皆插件”的基础

### 1. 插件 = 实现 Service 的对象
插件可以是函数插件（可选 inject + apply(ctx)），也可以是 Service 子类（生命周期挂载）。

### 2. 上下文 = 服务仓库
服务声明在 ctx 上（ctx.tools / ctx.llm / ctx.sessions），其他插件按键找服务，不 import 具体实现。

### 3. inject 声明依赖
命名所需服务 → 等它们存在 → 加载顺序由服务需求表达，不是手动 boot 排序。

### 4. 类型化事件
TS 声明合并声明事件名，按 emit / waterfall / parallel / serial 分派。

### 5. 注册 = 可逆效果
prompt sections / tool schemas / adapters / providers / listeners 经 ctx.effect() / ctx.on() 安装，reload / teardown 可预测回滚。

这五想法构成的基础是：**没有特权核心，一切皆插件。**

## 四、四分派模式各自对应什么场景

Cordis 定义了四种分派模式，这不是实现细节，而是事件契约的一部分。

| 模式 | 等待？ | 顺序 | 返回值 | 场景 |
|------|--------|------|--------|------|
| emit | 否 | 注册序 | 无 | fire-and-forget 通知 |
| waterfall | 否 | 注册序 | 有 | 中间件链，短路即设计 |
| parallel | 是 | 并行 | 无 | 无依赖并行监听 |
| serial | 是 | 注册序 | 有 | 有序依赖监听 |

特别重要的是 waterfall：
- `around-middleware` 模式
- 监听器收 `(...args, next)`
- 调 `next()` 委托
- 不调 = 短路

这意味着：**单决策事件，策略监听器拥有决策时不调 next，仅注解/观察必须委托。**

## 五、dsh 为什么选择“一切皆插件”作为架构哲学

dsh 选择 Cordis 不是因为“插件多”，而是因为：

**可替换性即架构。**

这意味着：
- 模型适配器是插件，可以换
- 工具注册表是插件，可以换
- 会话日志是插件，可以换
- Agent 循环本身也是插件，可以换

没有特权核心，扩展 = 在旁边挂插件。

这和 OpenCode 的“plugin / skills”不同——OpenCode 是有核心的，dsh 没有。
