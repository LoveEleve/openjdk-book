# 会话与真相层：Agent 到底记住了什么

> 前置：`05-agent-foundations` 四篇
> 本篇任务：理解 Agent Runtime 的会话模型和真相层（truth layer），知道"系统承认发生了什么"和"模型以为发生了什么"为什么必须区分。

---

## 一、这一章真正的问题

前几章我们把 Agent 建成了"循环调模型 + 调工具"的系统。但这还不够：

> 如果 Agent 在调工具过程中崩溃了，下次怎么恢复？
> 如果用户在两台设备上问同一个问题，怎么看到同一段历史？
> 如果模型"以为"它刚才写过文件，但实际没写成功，怎么办？

这一章要回答：
1. 会话（session）到底是什么？
2. 真相层（truth layer）解决什么问题？
3. 事件溯源（event sourcing）是什么？
4. 为什么"模型可见历史" ≠ "系统真相"？

## 三、直觉方案为什么不够好

### 直觉方案 1：把历史都放在内存里

> Agent 每轮把消息都存在一个内存数组里，模型每次都能看到。

问题：
- 崩溃后内存清空，历史全丢
- 跨进程/跨设备无法共享
- 无法审计"到底发生了什么"

### 直觉方案 2：只记录模型看得见的消息

> 把发给模型的每条消息都存下来，作为会话历史。

问题：
- 工具调用、权限拒绝、内部错误没有记录
- 恢复后只知道"聊过什么"，不知道"做过什么"
- 模型以为发生的事 ≠ 系统真实发生的事

## 四、正式机制

### 1. 会话（Session）

会话 = 一个 Agent 任务从开始到结束的完整上下文。

它包含：
- 用户输入
- 模型输出
- 工具调用和结果
- 系统内部事件

### 2. 会话 ≠ 消息列表

最容易犯的错误，是把会话想成"消息数组"。

更准确的理解：会话是**一组有结构的事件**，消息只是其中一种。

### 3. 真相层（Truth Layer）

真相层的核心问题：

> 什么事件一旦被系统承认，就是"真实发生过的"？

比如，一个 Agent 任务里：
- 模型说"我写好了文件" → 这是**声明**，不是真相
- 工具确实返回了写入成功 → 这才是**系统认可的真相**

真相层必须把"声明"和"事实"分开。

### 4. 事件溯源（Event Sourcing）

事件溯源是一种持久化方案：

> 不存"当前状态"，只存"一串事件"，当前状态可以由事件重放重建。

```text
事件流：
  1. user_said("分析项目")
  2. tool_called("read_file", "main.py")
  3. tool_result("main.py", "def hello(): ...")
  4. assistant_said("我看了 main.py")
  ...

当前状态 = 重放整个事件流得到
```

优点：
- 完整历史可追溯
- 崩溃恢复 = 从事件重放
- 可以回到任意时间点

### 5. 投影（Projection）

事件源本身是"append-only"的。为了让模型能消费，需要把事件转成模型能看的视图。

这就是投影（projection）：

```text
事件流
  → 投影规则
  → 模型可见消息列表
```

投影规则决定：
- 哪些事件进入模型可见视图
- 哪些事件只作为系统痕迹（不进入模型上下文）
- 如何把工具结果压缩成适合模型的格式

### 6. 三个层次必须分开

一个成熟的 Agent Runtime 必须区分：

```text
真相层：系统承认发生了什么（事件源）
模型层：模型这一轮看到什么（投影视图）
用户层：用户看到什么（结果展示）
```

> 注意：这是"视图分离"视角的三个层次，和 `../14-五项目横向专题：真相层、上下文层与恢复边界.md` 的"系统支柱"视角（真相层 / 上下文层 / 恢复边界）是两种切法，不冲突：
> - 本文的"模型层" ≈ 横向专题的"上下文层"（都是"模型能看见什么"）
> - 本文的"用户层"是横向专题没有的（用户视角）
> - 横向专题的"恢复边界"由本文第 03 篇《完成判定与恢复》承接
>
> 先理解本文的视图分离，再读横向专题的系统支柱，两套框架可以互补使用。

这三者混在一起，是整个 Agent 系统最常见的混乱来源。

## 五、最小实现 / 伪代码

### 1. 最小事件源

```python
class EventLog:
    def __init__(self):
        self.events = []        # 追加写的事件
        self.seq = 0            # 事件序号

    def append(self, type, data):
        self.seq += 1
        event = {"seq": self.seq, "type": type, "data": data}
        self.events.append(event)
        return event

    def replay(self):
        """从事件流重建状态。"""
        state = {}
        for event in self.events:
            # apply_event 是投影/归约函数，依次把事件应用到当前状态
            # 例如：user_said → 更新 messages，tool_called → 记录已调用
            apply_event(state, event)
        return state

    def load_events(self, session_id):
        """从持久化存储加载事件（简化：直接返回内存列表）。"""
        return self.events

    def flush(self):
        """确保事件已持久化（简化：空实现）。"""
        pass

# 追加写（append-only，永不修改历史）
log = EventLog()
log.append("user_said", {"text": "读 main.py"})
log.append("tool_called", {"name": "read_file", "args": {"path": "main.py"}})
log.append("tool_result", {"path": "main.py", "content": "def hello(): ..."})
```

### 2. 事件 → 模型视图

```python
def project_to_messages(events):
    """把事件源投影成模型可见消息。"""
    messages = []
    for e in events:
        if e["type"] == "user_said":
            messages.append({"role": "user", "content": e["data"]["text"]})
        elif e["type"] == "assistant_said":
            messages.append({"role": "assistant", "content": e["data"]["text"]})
        elif e["type"] == "tool_result":
            # 工具结果只保留摘要，避免上下文爆炸
            content = e["data"]["content"][:2000]
            messages.append({"role": "tool", "content": content})
        # 其他事件（权限拒绝、内部错误）不进入模型视图
    return messages
```

### 3. 崩溃恢复

```python
# 崩溃前：事件已经落盘
# 崩溃后：从最后一个持久化事件继续
class SessionStore:
    def __init__(self, log):
        self.log = log

    def checkpoint(self):
        self.log.flush()   # 确保事件已持久化

    def resume(self):
        # 重放全部事件，重建状态
        state = self.log.replay()
        # 从最后一个 assistant 消息之后继续
        return state
```

## 六、复杂度与边界

1. **事件源只追加、不修改**
   - 写错了就追加一个"修正事件"，而不是改旧事件
   - 这是审计和恢复的基础

2. **投影规则决定模型看到什么**
   - 投影错误 = 模型看到错误上下文
   - 投影规则要稳定、可测试

3. **事件会越来越多**
   - 长会话事件量巨大
   - 需要 checkpoint / 压缩 / 归档

4. **真相层不等于模型心智**
   - 模型"以为"的 ≠ 系统"承认"的
   - 完成判定必须基于真相，而不是模型声明

## 七、论文与真实系统映射

事件溯源本身是分布式系统的经典模式（Event Sourcing、CQRS），应用到 Agent Runtime 后有明显价值。

在真实 Agent 系统里：
- **OpenCode**：EventV2 是 durable truth，SessionRunner 从事件重放继续
- **dsh**：Session log 是事件源，"模型可见即已记录"是核心不变量
- **Pi**：SessionManager 用 JSONL 追加 + parentId 实现会话树
- **Hermes**：DeliveryLedger 记录"是否送达"，是真相层的一部分
- **Reasonix**：Checkpoint 保存会话和文件状态

这些项目共同证明了：**事件源 + 投影 ** 是 Agent Runtime 的通用地基。

## 一句话结论

> **会话不是消息列表，而是一组有结构的事件。真相层回答"系统承认什么"，事件溯源让"当前状态可从事件重放重建"，投影决定"模型看到什么"。"真相"、"模型视图"和"用户视图"必须分开，这是 Agent Runtime 的第一地基。**
