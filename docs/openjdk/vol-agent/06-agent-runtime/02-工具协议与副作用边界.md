## 三、直觉方案为什么不够好

### 直觉方案 1：工具收到调用就执行

> 模型说调什么，系统就执行什么。

问题：
- 模型可能调了不该调的工具
- 工具可能调用了不该操作的路径
- 没有权限控制，完全开放

### 直觉方案 2：执行完就忘

> 工具执行完，把结果给模型，这件事就结束了。

问题：
- 崩溃后不知道"这个工具到底执行完没有"
- 重复调用可能造成重复副作用
- 多个工具同时操作同一文件可能冲突

## 四、正式机制

### 1. 工具调用的完整协议

工具调用不是"函数调用"，而是三步协议：

```text
1. 授权（Authorize）：这个工具在当前上下文中是否允许调用？
2. 执行（Execute）：执行工具，记录结果
3. 结算（Settle）：把结果回注上下文，确保幂等
```

每一步都独立于模型——模型只负责"意图"，系统负责"落地"。

### 2. 权限控制

权限系统回答三个问题：

#### 谁可以调用？
- 当前 Agent 的身份
- 当前会话的 scope

#### 可以调什么？
- 哪些工具在白名单里
- 哪些路径可以操作

#### 需要审批吗？
- 有些操作自动放行
- 有些操作需要用户确认
- 有些操作直接拒绝

### 3. Stale Rejection（过期拒绝）

OpenCode 的一个关键设计：工具调用被注册时带一个"身份"。

当模型真正调用工具时，系统检查：

> 这个工具身份和当前注册的相同吗？

如果不同（比如工具被卸载、替换、scope 变化），调用被拒绝。

这就是 stale rejection——防止"模型用旧的能力做新的事"。

### 4. 工作区一致性（Workspace Lease）

当 Agent 修改文件时，必须保证：

> 一个任务在执行期间，工作区不会被其他任务同时修改。

Reasonix 的 WorkspaceLease 做法：

- **读者不租约**：只读操作不需要工作区独占权
- **写者从第一次变更开始持有租约，直到任务完成**

这样 review / verify 阶段看到的文件状态和执行期间一致。

### 5. 幂等与崩溃恢复

工具执行可能崩溃在"中间状态"：

```text
模型意图：编辑文件 A
系统动作：创建临时文件 → 修改 → 重命名 → 删除原文件
崩溃点：可能发生在任意一步之后
```

恢复策略：
- 记录执行进度（已执行到哪一步）
- 崩溃后从进度点继续
- 已知完成的步骤不重复

## 五、最小实现 / 伪代码

### 1. 带权限的工具调用

```python
class PermissionChecker:
    def __init__(self):
        self.allowlist = {}   # 工具名 → 权限配置

    def check(self, tool_name, args, context):
        """检查工具调用是否允许。"""
        if tool_name not in self.allowlist:
            return {"allow": False, "reason": "工具未注册"}

        rule = self.allowlist[tool_name]
        # 检查参数
        for key, constraint in rule.get("param_constraints", {}).items():
            if key in args and not constraint(args[key]):
                return {"allow": False, "reason": f"参数 {key} 不满足约束"}

        # 检查是否需要审批
        if rule.get("need_approval", False):
            return {"allow": "ask", "reason": "需要人工审批"}

        return {"allow": True}

# 用例
checker = PermissionChecker()
checker.allowlist["read_file"] = {
    "param_constraints": {"path": lambda p: p.startswith("/workspace/")},
    "need_approval": False,
}
checker.allowlist["delete_file"] = {
    "param_constraints": {"path": lambda p: p.startswith("/workspace/")},
    "need_approval": True,
}
```

### 2. 幂等工具执行

```python
class ToolExecutor:
    def __init__(self):
        self.executed = set()   # 已完成的调用 id
        self.results = {}       # 已完成调用的结果

    def execute(self, call_id, tool_name, args, fn):
        if call_id in self.executed:
            return {"idempotent": True, "result": self.results[call_id]}

        result = fn(**args)
        self.executed.add(call_id)
        self.results[call_id] = result
        return {"idempotent": False, "result": result}
```

## 六、复杂度与边界

1. **权限系统不能太细也不能太粗**
   - 太细：每步都审批，Agent 无法工作
   - 太粗：危险操作可能被绕过

2. **工作区租约不是文件锁**
   - 它保护的是"任务语义的一致性"
   - 不是"一次写操作"，而是"整个任务期间"

3. **Stale rejection 是"协议安全"**
   - 模型看到的能力和系统实际的能力必须是同一代的
   - 过期工具调用必须拒绝

4. **幂等不能依赖工具本身**
   - 工具可能是不可幂等的（如"发送邮件"）
   - 系统层需要记录哪些调用已执行

## 七、论文与真实系统映射

在真实 Agent 系统里：
- **OpenCode**：PermissionV2（action×resource + deny 优先 + stale rejection）
- **Reasonix**：WorkspaceLease（写者租约持续到任务完成）
- **dsh**：沙箱政策每调用一次 + 升级阶梯 + fail-closed
- **Hermes**：SecretScope、authz、SelfRepoGuard
