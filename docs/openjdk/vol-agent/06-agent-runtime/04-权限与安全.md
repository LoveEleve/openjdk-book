## 三、直觉方案为什么不够好

### 直觉方案 1：不设权限，Agent 什么都能做

> Agent 是我自己的工具，信任它就行。

问题：
- 模型可能被 prompt injection 攻击
- 工具结果可能被篡改
- 一台设备上的 Agent 可能访问不该访问的资源

### 直觉方案 2：权限写在代码里，不可配置

> 每个工具函数自己检查权限。

问题：
- 权限逻辑分散在多个工具，难以治理
- 无法跨工具做审批
- 难以审计"谁在什么时候调了什么"

## 四、正式机制

### 1. 权限模型：action × resource

一个成熟的权限系统应该基于"动作 × 资源"：

```text
action: 读、写、执行、删除
resource: 文件、目录、API、网络

权限规则：
  allow read on /workspace/*
  deny write on /etc/passwd
  ask on /data/*
```

这样比"工具名白名单"更精确，因为同一个工具（如 bash）在不同资源上的风险完全不同。

### 2. 沙箱隔离

沙箱 = 限制 Agent 能做的事。

常见沙箱策略：

```text
read-only：只能读，不能写
workspace-write：只能在指定工作区写入
full-access：完全访问（危险）
```

dsh 的沙箱设计：
- 政策每调用一次（per-call policy），不是固定 provider
- 升级阶梯：严格从低到高
- 升级需用户审批

### 3. 凭证管理（Secret Scope）

Agent 需要 API key、token 等凭证。

问题：
- 凭证不能写死在代码里
- 凭证不能随便暴露给模型
- 不同 scope 的凭证应该隔离

Hermes 的 SecretScope 做法：
- 凭证按 profile 隔离
- 运行时注入环境变量
- 模型看不到凭证原文

### 4. Prompt Injection 防御

Prompt Injection 是 Agent 特有的安全问题：

```text
攻击者：在工具结果中注入恶意指令
模型：把恶意指令当成系统指令执行
后果：Agent 执行了攻击者想要的操作
```

防御措施：
- 区分"系统指令"和"用户数据"
- 对工具结果做净化
- 关键操作需要审批
- 使用系统 prompt 的"不可变性"

### 5. 安全治理

安全治理 = 让安全成为系统的一部分，而不是事后补救。

包括：
- 审计日志：记录每个工具调用
- 限流：防止异常调用
- 审批：高风险操作须人工确认
- 回滚：必要时能撤销操作

## 五、最小实现 / 伪代码

### 1. action × resource 权限检查

```python
class ActionResourcePermission:
    def __init__(self):
        self.rules = []

    def add_rule(self, action, resource_pattern, effect):
        # effect: "allow" | "deny" | "ask"
        self.rules.append({
            "action": action,
            "resource": resource_pattern,
            "effect": effect,
        })

    def check(self, action, resource):
        # deny 永远优先
        for rule in self.rules:
            if rule["action"] == action and resource.startswith(rule["resource"]):
                if rule["effect"] == "deny":
                    return {"allow": False, "reason": "deny"}
                if rule["effect"] == "ask":
                    return {"allow": "ask", "reason": "需要审批"}

        for rule in self.rules:
            if rule["action"] == action and resource.startswith(rule["resource"]):
                if rule["effect"] == "allow":
                    return {"allow": True}
                break

        return {"allow": False, "reason": "无匹配规则，默认拒绝"}

# 配置
perm = ActionResourcePermission()
perm.add_rule("read", "/workspace/", "allow")
perm.add_rule("write", "/workspace/", "allow")
perm.add_rule("write", "/etc/", "deny")
perm.add_rule("delete", "/", "ask")

# 检查
print(perm.check("read", "/workspace/main.py"))       # allow
print(perm.check("write", "/etc/passwd"))             # deny
print(perm.check("delete", "/workspace/tmp"))         # ask
```

### 2. 凭证隔离

```python
class SecretScope:
    def __init__(self):
        self.secrets = {}

    def set(self, scope, key, value):
        if scope not in self.secrets:
            self.secrets[scope] = {}
        self.secrets[scope][key] = value

    def get_for_agent(self, scope):
        """Agent 只能看到其 scope 内的凭证。"""
        return self.secrets.get(scope, {})

    def get_raw(self, scope, key):
        """系统内部获取，不暴露给模型。"""
        return self.secrets.get(scope, {}).get(key)

# 不同 Agent 不同 scope：隔离
secret_scope = SecretScope()
secret_scope.set("agent_code", "GITHUB_TOKEN", "ghp_xxx")
secret_scope.set("agent_web", "OPENAI_API_KEY", "sk-xxx")
```

## 六、复杂度与边界

1. **权限不是越多越好**
   - 太严：Agent 无法正常工作
   - 太松：安全风险

2. **沙箱不能完全阻止泄漏**
   - 模型可以通过编码、隐写术等方式泄漏信息
   - 沙箱减少"主动泄露"，但不能完全消除

3. **Prompt Injection 没有完美防御**
   - 所有的防御都能被绕过
   - 多层防御 + 审批是关键

4. **凭证管理不能依赖模型**
   - 模型不能"知道"凭证
   - 凭证注入由系统完成，模型不可见

## 七、论文与真实系统映射

在真实 Agent 系统里：
- **OpenCode**：PermissionV2（action×resource + deny 优先 + saved approvals）
- **dsh**：沙箱三模式（read-only / workspace-write / full-access）、每调用政策
- **Hermes**：SecretScope、authz、SelfRepoGuard
- **Reasonix**：Permission + WorkspaceLease
