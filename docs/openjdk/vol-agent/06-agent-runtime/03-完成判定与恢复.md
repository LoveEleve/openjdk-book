## 三、直觉方案为什么不够好

### 直觉方案 1：模型说"完成了"就是完成了

> 模型输出 Final Answer，系统就认为任务完成。

问题：
- 模型可能自信地宣布完成，但工作没做完
- 模型可能编造结果
- 没有验证，无法保证质量

### 直觉方案 2：崩溃后重新开始

> Agent 崩溃了，下次让用户重新提一遍任务。

问题：
- 长时间任务白费
- 工具调用可能已经产生副作用
- 用户体验极差

## 四、正式机制

### 1. 完成判定的四个层次

#### 第 1 层：模型声明
- 模型输出 Final Answer 或类似信号
- 不可信，因为模型可能"自以为完成了"

#### 第 2 层：确定性验证（GoalGate）
- 在模型宣布完成前，先跑确定性验证
- 如：检查文件是否真的存在、测试是否通过
- 验证失败 → 把失败证据回注给模型，让它继续

#### 第 3 层：独立审查器（Evaluator / Judge）
- 用另一个模型（或同模型的另一个视角）独立检查
- 评审器输出：complete / continue / blocked / uncertain
- 独立于执行器，防止"执行者自说自话"

#### 第 4 层：证据审计
- 所有判定必须有证据支持
- 证据账本可追溯

### 2. 停止条件

Agent 不能无限运行。必须有多层停止条件：

```text
正常停止：模型输出 Final Answer，且通过验证 + 审查
强制停止：超过最大步数 / 超时
错误停止：检测到不可恢复的错误
用户中断：用户主动停止
停滞停止：多轮没有任何进展
```

### 3. 崩溃恢复策略

#### 事件源恢复
- 所有事件已持久化
- 崩溃后重放全部事件，重建状态

#### 检查点恢复
- 定期保存完整状态快照（checkpoint）
- 崩溃后从最近的 checkpoint 继续

#### 幂等重试
- 已经执行过的工具调用不会重复执行
- 系统记录每个工具调用的结果

### 4. 可观测性

可观测性在恢复中的三个作用：

```text
崩溃前：记录发生了什么
崩溃时：保存最后状态
崩溃后：帮助定位原因
```

Hermes 的 LifecycleLedger 就是一个典型：用哨兵文件记录进程状态，崩溃后下一生命能知道"上一生命怎么死的"。

## 五、最小实现 / 伪代码

### 1. 多层完成判定

```python
def is_complete(task, model_output, verifier, evaluator):
    # 第 1 层：模型声明
    if "Final Answer" not in model_output:
        return False, "模型未声明完成"

    # 第 2 层：确定性验证
    gate_result = verifier.verify(task, model_output)
    if not gate_result["passed"]:
        return False, f"验证失败：{gate_result['reason']}"

    # 第 3 层：独立审查
    judge_result = evaluator.judge(task, model_output)
    if judge_result["verdict"] != "complete":
        return False, f"审查器判定：{judge_result['verdict']}"

    return True, "完成"
```

### 2. 崩溃恢复

```python
class SessionRecovery:
    def __init__(self, event_log):
        self.log = event_log

    def recover(self, session_id):
        # 1. 从持久化存储加载事件
        self.log.events = self.log.load_events(session_id)
        # 2. 重放事件，重建状态
        state = self.log.replay()
        # 3. 检查哪些工具调用已执行
        executed_calls = [e for e in self.log.events
                          if e["type"] == "tool_call_completed"]

        # 4. 从最后一个未完成的 turn 继续
        last_state = state.get("last_assistant_state", {})
        return last_state, executed_calls
```

### 3. 停滞检测

```python
def detect_stall(events, max_stalled_steps=3):
    """检测 Agent 是否陷入停滞（重复调同一工具）。"""
    recent_tool_calls = [e for e in events[-10:] if e["type"] == "tool_called"]
    if len(recent_tool_calls) < max_stalled_steps:
        return False, None

    # 检查是否一直在调同一个工具
    tool_names = [e["data"]["name"] for e in recent_tool_calls]
    if len(set(tool_names)) == 1:
        return True, f"停滞：一直在调 {tool_names[0]}"

    return False, None
```

## 六、复杂度与边界

1. **独立审查器也有偏差**
   - 审查器本身也是模型，有自己的偏差
   - 需要设计评审 prompt 和评判标准

2. **恢复不能保证完全无副作用**
   - 有些工具调用（如"发送邮件"）不可逆
   - 需要记录并通知用户

3. **停滞检测有误报**
   - 模型可能确实需要多调几次同一工具
   - 阈值需要实际调优

4. **可观测性不能影响主流程**
   - 记录失败不应阻塞 Agent 运行
   - Hermes 的 fail-silent 原则：账本失败不影响主流程

## 七、论文与真实系统映射

在真实 Agent 系统里：
- **Reasonix**：Goaleval（独立审查器，fail-closed，四态 outcome）
- **Hermes**：GoalJudge（auxiliary 模型独立审查 + 自动暂停阈值）
- **Hermes**：GoalGate（确定性验证先于模型声明）
- **Hermes**：DeliveryLedger / LifecycleLedger（崩溃归因）
- **OpenCode**：SessionRunner 从事件恢复
- **Reasonix**：Checkpoint + Transaction 恢复

> **完成判定不是模型宣布的，而是系统验证的。真正的完成 = 模型声明 + 确定性验证通过 + 独立审查器通过。崩溃恢复不是从头开始，而是从事件源、checkpoint 和幂等记录中继续。**
