# 五项目横向专题：真相层、上下文层与恢复边界

> 对比对象：OpenCode / Reasonix / Pi / Hermes / dsh
> 核心问题：一个 Agent 系统如何回答“什么是真的、模型看什么、出错后从哪里恢复”。
> 关联文档：`06-5项目横向对比总锚点.md`、各项目第一卷总复盘、各项目 `analysis/` 源码解析。

---

## 一、为什么要单独比较这三个层次？

很多 Agent 架构比较只比较：
- 谁的 loop 更复杂
- 谁支持更多工具
- 谁接入更多模型

但真正决定 Agent 能不能长期运行的，通常是下面三个问题：

1. **真相层**：系统认定“已经发生”的事实是什么？
2. **上下文层**：模型下一轮真正能看见什么？
3. **恢复边界**：发生中断、崩溃、压缩或并发变化后，系统从哪里继续？

这三个问题必须一起看。

如果只做真相层，没有上下文层：
- 系统虽然记住了历史，但模型可能看不到正确视图。

如果只做上下文层，没有恢复边界：
- 当前请求看起来正确，但崩溃后无法继续。

如果只做恢复边界，没有真相层：
- 系统可以恢复某个状态，却无法证明这个状态为什么是真的。

所以一个成熟 Agent 的基本结构应该是：

```text
真相层：承认发生了什么
  ↓
上下文层：决定模型看见什么
  ↓
恢复边界：决定失败后从哪里继续
```

## 二、五个项目的一句话对照

| 项目 | 真相层 | 上下文层 | 恢复边界 |
|------|--------|----------|----------|
| OpenCode | EventV2 + SessionInput + durable event store | SystemContext + Context Epoch + Compaction | event sequence / session execution / snapshot |
| Reasonix | Controller 状态 + PlanContract + Checkpoint | 固定缓存前缀 + transient tail + bounded evidence | FileSnap + MsgIndex + revision/token 重验证 |
| Pi | JSONL 会话树 + parentId + leaf + facts | summary + retainedTail + message projection | branch / compaction entry / session reload |
| Hermes | DeliveryLedger + LifecycleLedger + evidence ledger | Prompt Cache + compression + 双态记忆 | pending/attempting 状态、sentinel、验证证据 |
| dsh | Session event log | Surface / Projection 从事件源派生模型视图 | append-only event history + watermark/snapshot |

这张表已经能看出五条不同路线：
- OpenCode 偏事件溯源 runtime
- Reasonix 偏联合事务与任务恢复
- Pi 偏探索型会话树
- Hermes 偏运行后可追责的账本
- dsh 偏事件源与插件投影

---

## 三、OpenCode：真相是事件，恢复是可重放执行协议

### 1. 真相层：EventV2

OpenCode 不把 session 理解成消息数组，而是：
- durable event
- sequence
- aggregate
- projector
- replay

所以它的基本问题是：
> 这个事件是否被正式提交、是否能被重放、是否会造成分叉？

`commitDurableEvent` 把：
- seq 校验
- owner 校验
- projector
- commit callback
- event insert

收进一个提交协议里。

这说明 OpenCode 的真相层最接近：
> **事件一旦提交，就成为系统承认的历史事实。**

### 2. 上下文层：SystemContext

模型看到的 system context 不是静态字符串，而是多个 source 的组合：
- instructions
- skills
- environment
- references
- runtime sources

这些 source 经过：
- initialize
- reconcile
- replace

决定当前 generation 是否稳定。

因此 OpenCode 明确区分：
- 事件真相
- 当前上下文视图
- 上下文源是否暂时 unavailable

### 3. 恢复边界：执行协议

OpenCode 的恢复不是简单 reload session 文件，而是：
- 从 durable event 还原状态
- 从 queue 恢复待处理输入
- 通过 SessionRunner 继续 turn
- 通过 compaction 转移重建 context epoch

所以它的恢复边界是：
> **从可重放事件和可重新驱动的执行协议继续。**

### 4. OpenCode 的核心取舍

优点：
- 事件、投影、执行、重放语义非常统一
- 适合做平台化、可观测、可审计 runtime

代价：
- event / projector / sequence / epoch / runner 复杂度较高
- 需要严格维护 durable 与 live-only 的边界

---

## 四、Reasonix：真相是任务状态与联合快照，恢复必须重新验证

### 1. 真相层：任务契约 + checkpoint

Reasonix 的真相不只是“发生过哪些事件”，还包括：
- 当前任务目标
- 计划契约
- success criteria
- evidence ids
- 文件快照
- 消息边界
- session revision
- mutation sequence

所以 Reasonix 的真相层更像：
> **一个受任务契约约束的联合状态。**

它不仅要知道“发生了什么”，还要知道：
- 这次变更是否在计划范围内
- 这份证据是否仍然有效
- 当前工作区版本是否还是原来的世界

### 2. 上下文层：缓存优先的变化分层

Reasonix 把：
- system prompt
- 首个用户 turn

当成尽量稳定的缓存前缀。

变化信息进入：
- transient tail
- compact summary
- bounded evidence

这使它的上下文层同时服务于：
- provider prefix cache
- 长跑成本控制
- evaluator 有界输入

### 3. 恢复边界：Prepare/Commit 重验证

Reasonix 最重要的恢复判断是：

> **prepare 通过，不等于 commit 时仍然可以提交。**

因为 prepare 与 commit 之间可能发生：
- 新的写入者出现
- workspace token 改变
- 文件指纹变化
- session revision 变化
- plan 过期

所以恢复/回滚必须：
1. 先建立联合 checkpoint
2. prepare 检查
3. commit 再检查
4. 先持久化发布意图
5. 再执行文件动作
6. 持久化逐步完成结果

### 4. Reasonix 的核心取舍

优点：
- 恢复边界非常强
- 能同时保护任务、文件、会话和并发语义

代价：
- checkpoint 与事务模型较重
- 许多简单任务也要承受 revision、token、lease、evaluator 等控制复杂度

## 五、Pi：真相是可分支会话树，上下文是树的一个可压缩视图

### 1. 真相层：Session Tree

Pi 不把 session 存成线性消息数组，而是：
- JSONL append
- `parentId`
- `leaf`
- branch
- branch summary
- custom / label / session_info
- facts

所以 Pi 的真相层最像：
> **一个记录探索过程的持久化树。**

这特别适合分析型 Agent：
- 走错路可以回退
- 旧路径不会被覆盖
- 不同探索方向可以并存
- 最后可以导出一条清晰分支

### 2. 上下文层：摘要与尾巴

Pi 的模型上下文不是整棵树，而是：
- 当前分支
- compaction summary
- retainedTail
- 新消息

压缩时还要保护：
- tool call / tool result 配对
- split turn 前缀语义
- 文件读写元数据
- deferred assistant 不进入上下文

因此 Pi 的上下文层是：
> **会话树在当前执行位置上的语义投影。**

### 3. 恢复边界：分支与 compaction entry

Pi 的恢复不是“恢复到上次消息末尾”，而是：
- 从 JSONL 重建会话树
- 根据 leaf 找到当前路径
- 根据 compaction entry 重建模型视图
- 根据 branch 选择未来写入位置

它的恢复边界更接近：
> **恢复到一条探索路径，而不是恢复到一个线性时间点。**

### 4. Pi 的核心取舍

优点：
- 非常适合探索、回退、分支和长期分析
- 完整历史与模型上下文分层清楚

代价：
- 树形会话比线性 session 更难理解和维护
- 分支、摘要、facts、context view 之间需要保持语义一致

## 六、Hermes：真相是账本，恢复首先回答“结果有没有送达、进程怎么死”

### 1. 真相层：多个专用账本

Hermes 没有把所有问题都压进一个事件 store，而是建立了多个职责清晰的账本：
- DeliveryLedger：响应是否送达
- LifecycleLedger：上一生命如何结束
- VerificationEvidence：验证留下什么证据

所以 Hermes 的真相层是：
> **围绕运行后追责问题建立的专用账本集合。**

它并不只关心“模型做了什么”，还关心：
- 用户最终有没有收到
- 进程崩溃前发生了什么
- 验证是否真实运行过

### 2. 上下文层：缓存优先与双态知识

Hermes 把 prompt cache 视为架构约束：
- system prompt 尽量稳定
- skill 注入避免破坏缓存前缀
- compression 是有限的重写边界
- 冻结记忆进入稳定上下文
- 活态写入保持在变化层

所以它的上下文层同时承载：
- 多平台运行
- 技能注入
- 长期记忆
- 压缩和缓存稳定

### 3. 恢复边界：交付状态与生命哨兵

Hermes 的恢复边界非常具体：
- `pending`：发送还没开始，可以直接重投
- `attempting`：可能已发送，重投要带标记
- `failed`：确定失败，重启成为重试边界
- `delivered`：保持终态

生命周期方面：
- sentinel=running 但下次启动未见 exited → 不洁死亡
- heartbeat 携带死亡前内存样本
- OOM 只做保守启发标注

Hermes 的恢复问题是：
> **系统死了以后，下一生命能不能解释并继续处理未完成义务。**

### 4. Hermes 的核心取舍

优点：
- 对多平台长期运行和运行后可解释性非常强
- 交付、生命周期、验证都有明确责任边界

代价：
- 账本和守卫较多
- 系统整体更偏守护进程/平台代理，而不是轻量 runtime

## 七、dsh：真相是 Session 事件源，上下文和投影都只是派生层

### 1. 真相层：Session Event Log

dsh 的核心判断是：

> **模型可见即已记录。**

这意味着：
- 新模型可见输入必须先成为 session event
- session event 再通过 Surface 投影成模型消息
- 持久化后端只是事件源的订阅者

因此 dsh 的真相层最纯粹：
> **事件源是唯一真相，JSONL/SQLite/Projection 都是派生物。**

### 2. 上下文层：Surface / Projection

dsh 不把上下文构建看成独立 prompt 工程，而是：
- user/message 直通
- assistant/message 投影
- tool/result 投影
- 其他 trace 事件不进入模型视图

这让模型上下文天然受 Session 事件源约束。

### 3. 恢复边界：watermark + replay

dsh 的 projection 可以：
- 从 snapshot 恢复
- 读取 watermark
- 继续消费 watermark 之后的事件
- 没有 snapshot 时全量 replay

这里必须强调：
- snapshot 不是权威真相
- watermark 只表示已消费到哪里
- 事件源仍然是恢复依据

### 4. dsh 的核心取舍

优点：
- 插件化和事件源语义非常统一
- 多后端、多投影、多能力都能围绕同一个 session event log 展开

代价：
- 对事件契约和追加不变性要求极高
- 插件之间的事件语义边界必须长期稳定

## 八、五种恢复哲学的真正差异

| 项目 | 恢复的核心动作 | 恢复所信任的东西 | 最怕什么 |
|------|----------------|------------------|----------|
| OpenCode | 重放事件并重新驱动 runner | durable event + sequence | 事件分叉、投影不一致 |
| Reasonix | 恢复联合快照并重验证提交 | checkpoint + revision/token | 世界已变化却套用旧计划 |
| Pi | 重建会话树并选择分支 | JSONL tree + leaf + compaction entry | 分支/摘要语义丢失 |
| Hermes | 扫描账本并恢复未完成义务 | delivery/lifecycle sentinel | 结果丢失、异常死亡不可解释 |
| dsh | replay 事件并追平 projection | session event log + watermark | snapshot 被误当真相 |

可以把它们压缩成五句话：

- OpenCode：**恢复过去发生的事件。**
- Reasonix：**恢复一个经过重新验证的联合状态。**
- Pi：**恢复一条可继续探索的历史分支。**
- Hermes：**恢复尚未履行完的运行义务。**
- dsh：**恢复事件源派生出的投影状态。**

## 九、五种上下文哲学的真正差异

| 项目 | 模型上下文的本质 | 压缩/更新方式 | 关键保护对象 |
|------|------------------|---------------|--------------|
| OpenCode | source 集合 + epoch | reconcile / replace / compaction | system semantic stability |
| Reasonix | 固定前缀 + transient tail | 单阈值 compact + bounded evidence | cache prefix 与恢复边界 |
| Pi | 当前分支的消息视图 | summary + retainedTail | tool 协议、split turn、文件进度 |
| Hermes | 缓存稳定的长期上下文 | compression + 双态记忆 | prompt cache 与知识治理 |
| dsh | event log 的 Surface 投影 | append/replace projection | 模型可见与日志一致 |

这五种做法没有谁绝对更好，关键在产品形态：

- 如果你要做平台化 runtime，学 OpenCode。
- 如果你要做受控长跑任务，学 Reasonix。
- 如果你要做探索型分析 Agent，学 Pi。
- 如果你要做多平台长期代理，学 Hermes。
- 如果你要做插件化框架，学 dsh。

## 十、从五个项目提炼出一套通用设计

如果要设计一个新的长期 Agent，可以把五个项目的优点组合成下面这套最小架构：

### 1. 一个明确的真相层
选择一种：
- durable event
- session tree
- task/checkpoint state
- ledger

但必须明确：
> 什么东西一旦提交，就被系统承认是真的？

### 2. 一个独立的上下文投影层
不要让模型直接读取内部存储。
应明确：
- 哪些事实进入上下文
- 哪些只是 trace
- 哪些需要 summary
- 哪些内容必须保持缓存稳定

### 3. 一个正式的恢复边界
恢复不能只靠“重新读最后几条消息”。
至少要定义：
- sequence / revision
- branch / leaf
- watermark
- delivery state
- workspace token

### 4. 一个明确的压缩契约
压缩必须说明：
- 什么不能丢
- 什么不能独立切断
- summary 是否进入真相层
- 多次压缩是否可增量演进

### 5. 一个失败语义分类
至少区分：
- 尚未开始
- 可能已开始
- 已完成
- 确定失败
- 状态未知

否则恢复时只能粗暴重试，最终会制造重复副作用或错误状态。

## 十一、最值得迁移的 10 个工程原则

1. **事件真相、模型视图、持久化载体不要混为一谈。**
2. **模型上下文必须是内部真相的受控投影。**
3. **压缩是状态转换，不是字符串截断。**
4. **恢复边界必须包含版本或水印。**
5. **prepare 通过不等于 commit 仍然安全。**
6. **完整历史与模型可见历史应该分层。**
7. **发送义务、生命周期和验证证据值得独立建账。**
8. **snapshot 是恢复加速器，不应轻易成为唯一真相。**
9. **工具结果和模型可见结果需要有界化。**
10. **每个系统都必须明确“什么状态可以继续，什么状态必须暂停”。**

---

## 十二、一句话结论

五个项目放在一起，真正拼出的不是五套不同 Agent，而是一个共同的工程问题：

> **Agent 要长期运行，必须同时拥有可信的真相层、受控的上下文层和可验证的恢复边界；OpenCode、Reasonix、Pi、Hermes、dsh 只是分别从事件、任务、探索、账本和插件五条路线给出了不同答案。**
