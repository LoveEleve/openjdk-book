# 五项目横向专题：完成判定与停止语义

> 对比对象：OpenCode / Reasonix / Pi / Hermes / dsh
> 核心问题：Agent 如何知道什么时候完成、什么时候继续、什么时候必须暂停。
> 关联文档：`06-5项目横向对比总锚点.md`、各项目完成判定与执行骨架正文。

---

## 一、为什么“停止”比“继续调用模型”更难？

Agent 的执行循环并不难写，真正难的是定义：

- 模型说完成时，系统是否相信？
- 没有新工具调用时，系统是否应该停止？
- 验证失败时，是重试、继续、暂停还是结束？
- 审查器不可用时，默认应该放行还是阻塞？
- 用户输入到来时，它属于当前 turn 还是下一阶段任务？

因此，一个成熟 Agent 必须把停止语义拆成至少三层：

```text
执行层：当前 turn 是否已经收敛
  ↓
验证层：目标是否满足完成条件
  ↓
控制层：系统是否允许继续或必须暂停
```

---

## 二、五个项目的一句话对照

| 项目 | 完成判定中心 | 默认停止/继续倾向 | 最重要的停止信号 |
|------|--------------|------------------|------------------|
| OpenCode | runner/tool/step 收敛，无独立 evaluator | 执行协议驱动 | queue、continuation、step、interrupt |
| Reasonix | Goaleval 独立审查器 | fail-closed | complete/continue/blocked/uncertain |
| Pi | AgentSession + loop hook | 由 session/模式决定 | follow-up、steering、retry、stop hook |
| Hermes | GoalGate + GoalJudge + 守卫族 | 有界 fail-open | gate、judge verdict、自动暂停 |
| dsh | Phase/turn/step + 插件事件 | 由事件和插件契约决定 | Phase、InboxTarget、dispatch 结果 |

---

## 三、OpenCode：停止是执行协议收敛，不是独立目标审查

OpenCode 的执行骨架主要回答：
- 当前 turn 是否还需要 continuation
- 是否还有工具 fiber 未结算
- queue 是否还有 durable 输入
- 是否触发 compaction 或 interrupt

因此它的停止语义偏执行器内部：

```text
queue 无新输入
  + 当前 provider turn 已结束
  + 工具已 settle
  + 没有 continuation
  → runner 停止
```

这套设计的优点是执行边界清晰、协议一致；代价是它没有像 Reasonix/Hermes 那样把“目标是否真的完成”抽成独立审查器。

OpenCode 更适合的理解是：
> **它擅长判断当前执行是否收敛，不主动定义所有业务目标是否完成。**

---

## 四、Reasonix：完成是独立审查器授予的继续许可

Reasonix 把完成判定从执行器中分离出来，Goaleval：
- 无工具
- 无完整历史
- 有界输入
- 独立 usage source
- fail-closed

它输出四种结果：
- `complete`
- `continue`
- `blocked`
- `uncertain`

这使得执行协议变成：

```text
RunLoop 完成一轮
  → Goaleval 审查证据
  → complete：允许结束
  → continue：允许下一轮
  → blocked：暂停等待外部条件
  → uncertain：默认不能安全结束
```

Reasonix 的核心判断是：
> **没有独立 evaluator，系统就没有资格自称已经完成。**

它适合高风险、长跑、需要验收契约的任务系统；代价是每轮执行都要承受额外审查成本。

---

## 五、Pi：停止是会话级控制流的收敛

Pi 不把完成判定集中到一个 evaluator，而是把停止语义分散到：
- AgentLoop
- AgentSession
- steering/follow-up 队列
- `prepareNextTurn`
- `shouldStopAfterTurn`
- retry / compaction / abort

Pi 的关键区分是：
- 当前 turn 是否结束
- 会话是否还有 follow-up
- 是否有 steering 要在下一步注入
- 当前前端模式是否要求继续

因此 Pi 的停止语义更像：

```text
当前 turn 结束
  → 检查 steering / follow-up / pending
  → 有则继续或开启新 turn
  → 无则交给 session/mode 的 stop 规则
```

Pi 的优势是灵活，适合交互式与探索型 Agent；代价是“完成”更多依赖会话和模式组合，而不是一个统一的目标判定器。

---

## 六、Hermes：先过确定性门，再由独立审查器判定

Hermes 把完成语义拆成两道门：

### 第一层：GoalGate
- 跑确定性 shell 验证
- 验证失败时把证据回注
- 工作区未变化时可复用失败指纹

### 第二层：GoalJudge
- auxiliary 模型独立判断
- 输入 goal、last response、contract、subgoals、后台进程
- 输出 done/continue/wait/skipped

所以 Hermes 的完成路径是：

```text
模型声称完成
  → GoalGate 确定性验证
  → 失败：继续修复
  → 通过：GoalJudge 独立审查
  → done：结束
  → wait：停泊
  → continue：继续
  → judge 连续失败超阈值：自动暂停
```

Hermes 的关键取舍是：
> **验收场景可以 fail-open，但必须有界。**

这比单纯 fail-open 或 fail-closed 更具体：它允许系统暂时继续，但不允许无限循环。

---

## 七、dsh：停止是 Phase、Inbox 与事件分派共同决定的

dsh 没有把完成判定抽成独立 GoalJudge，而是通过：
- `Phase`
- `turn/step`
- `InboxTarget`
- `emit/serial/waterfall`
- `turn-stopping`

共同定义停止语义。

它更关注：
- 当前 Agent 是否 running
- 当前输入应该进入 next-step 还是 next-turn
- 插件是否拦截、修改或短路当前事件
- turn 结束时是否仍有 pending inbox

所以 dsh 的停止语义是：
> **运行时事件契约的收敛结果，而不是某个中心化 evaluator 的判定结果。**

这与 dsh 的“一切皆插件”立场一致：停止策略本身也可以由插件扩展。

---

## 八、五种停止哲学的真正差异

| 停止哲学 | 代表项目 | 它最信任什么 | 适合场景 |
|----------|----------|--------------|----------|
| 执行收敛 | OpenCode | 当前 turn/queue/工具协议 | 通用 runtime |
| 独立审查 | Reasonix | 有界证据与 evaluator | 高风险任务 |
| 会话控制 | Pi | session 状态与用户交互 | 探索/交互型 Agent |
| 门 + 审查 | Hermes | 确定性验证与 auxiliary judge | 项目验收/多平台长期运行 |
| 事件契约 | dsh | 插件事件与 Phase 状态机 | 可替换框架 |

## 九、设计新 Agent 时应该先回答的 8 个问题

1. 当前 turn 结束和任务完成是否是同一件事？
2. 完成判定是否需要独立于执行器？
3. 验证失败是否回注给模型？
4. evaluator 不可用时是 fail-open 还是 fail-closed？
5. 当前输入属于当前 step、当前 turn，还是下一阶段任务？
6. stop 是否允许被插件、用户或后台任务改变？
7. 连续不确定或失败是否有自动暂停阈值？
8. 系统是否能解释“为什么停止”以及“为什么没有停止”？

---

## 十、一句话结论

五个项目共同说明：

> **Agent 的完成不是模型输出中的一句话，而是执行收敛、证据验证和控制面许可共同形成的状态；不同项目只是分别把主导权交给了 runtime、evaluator、session、验收门或插件事件。**
