# 源码学习 / 源码分析痛点清单

> 迁移说明：本文件从 Source-Code-Agent 项目内的产品/规划讨论中抽离，作为后续 5 个 Agent 项目反向分析的统一问题基线。
> 目标：先明确“人为什么学不会源码”，再反推一个 Agent 应该如何解决这些问题。

---

## 一、起点类痛点

### 1. 不知道入口在哪里
- 症状：仓库太大，不知道先看哪个类、哪个函数、哪个模块。
- 根因：入口分散；README 不可靠；很多库型项目并没有清晰的 main。
- 后果：一开始就陷入随机游走，越看越乱。

### 2. 不知道项目到底在解决什么问题
- 症状：看见一堆类和包，但不知道系统的核心矛盾是什么。
- 根因：没有先抽出项目根问题（project thesis / root problem）。
- 后果：后面所有阅读都变成“记事实”，而不是“理解设计”。

### 3. 不知道哪些是核心，哪些是外围
- 症状：每个模块看起来都挺重要，主次不分。
- 根因：没有 mainline mechanism / support mechanism 的划分。
- 后果：读了很多，抓不住本质。

---

## 二、顺序类痛点

### 4. 学习顺序错误，中途卡死
- 症状：看 A 时发现必须先懂 B。
- 根因：目录不是按“理解依赖”排序，而是按“教程习惯”排序。
- 后果：中途不断回跳，形成认知断裂。

### 5. 把 API 使用顺序误当成源码理解顺序
- 症状：教程看着顺，但源码读不通。
- 根因：把“用户如何调用”当成“系统如何成立”。
- 后果：最后只会用，不会解释源码主线。

### 6. 章节颗粒度不合理
- 症状：一章太大读不动，太小又看不出结构。
- 根因：没有机制聚类。
- 后果：信息负担失衡。

---

## 三、抽象类痛点

### 7. 看见模块，看不见机制
- 症状：记住了类名、包名，但不知道这些代码在体现什么设计。
- 根因：没有机制抽象。
- 后果：源码分析退化成“文件导览”。

### 8. 抽象概念记不住
- 症状：EventLoop / Arena / Pipeline 这类词看完就忘。
- 根因：没有类比锚点。
- 后果：理解无法沉淀。

### 9. 知道怎么用，不知道为什么这么设计
- 症状：会 API，不懂设计 trade-off。
- 根因：Why-before-How 缺失。
- 后果：遇到变化或故障就失去判断力。

### 10. 看懂局部，看不懂整体协作
- 症状：单个类略懂，但系统为什么成立还是不清楚。
- 根因：缺少主线骨架叙事。
- 后果：无法形成系统直觉。

---

## 四、横切类痛点

### 11. 横切机制被埋起来了
- 症状：引用计数、背压、线程亲和到处都有，但没有整体理解。
- 根因：没有 crosscutting tracks。
- 后果：只能零散记忆，无法迁移。

### 12. 把局部技巧误当核心机制
- 症状：案例、协议层、外围模块反而被学得最重。
- 根因：主线/外围分层缺失。
- 后果：学习重心错位。

### 13. 看不到多个机制背后的共同约束
- 症状：多个模块被同一原则支配，但读者意识不到。
- 根因：横切机制没有显式建模。
- 后果：系统洞察缺失。

---

## 五、风险类痛点

### 14. 只会正常路径，不会异常路径
- 症状：能解释 happy path，但出问题不会排查。
- 根因：没有 failure boundary / failure mode 章节。
- 后果：学完也不会 debug。

### 15. 不知道哪里最容易误用
- 症状：API 会用，但经常踩坑。
- 根因：没有 anti-pattern / misuse catalog。
- 后果：理解不稳定，工程风险高。

### 16. 不知道哪里最容易泄漏 / 乱序 / 线程误用
- 症状：出了问题不知道先看哪里。
- 根因：没有 risk hotspots。
- 后果：排障时间极长。

---

## 六、深度类痛点

### 17. 不知道重点在哪
- 症状：每章看起来都差不多重要。
- 根因：没有深度分层（A/B/C）。
- 后果：主次失衡。

### 18. 深的地方没拉深，浅的地方写太多
- 症状：外围协议和核心机制写得一样重。
- 根因：没有重要度排序。
- 后果：大量精力浪费在非关键点上。

### 19. 看似全面，实际上没有抓住难点
- 症状：目录完整，但真正最难的地方没讲透。
- 根因：没有 hard-point mining。
- 后果：阅读后仍然无法解释系统精髓。

---

## 七、时间维度类痛点

### 20. 把兼容层当核心机制
- 症状：历史包袱和主干机制混在一起。
- 根因：没有时空溯源（git 演进 / version-aware notes）。
- 后果：理解重心放错。

### 21. 不知道某个实现是历史产物还是当前主路径
- 症状：把旧实现当现在核心。
- 根因：没有版本感知。
- 后果：误判设计意图。

---

## 八、迁移与输出类痛点

### 22. 学完 A，不会迁移到 B
- 症状：换个项目就不会了。
- 根因：没有 transferable concepts / cross-project analogy。
- 后果：学习不能迁移。

### 23. 看着懂，讲不出来
- 症状：好像明白，但复述不出来。
- 根因：没有 explain-back / self-test 机制。
- 后果：形成“幻觉式理解”。

### 24. 不知道这套知识对自己目标有什么意义
- 症状：学了很多，但和面试、工作、自学目标脱节。
- 根因：没有 goal-aware planning。
- 后果：学习动力和结构都不稳定。

---

## 九、这份清单的用途

后续在 `vol-agent/` 下分析 Pi / Reasonix / Hermes / OpenCode / dsh 时，每个项目都应该回答：

1. 它解决了上述哪些痛点？
2. 它是怎么解决的？
3. 它解决得有多深？
4. 它没解决哪些痛点？
5. 哪些机制值得迁移到我们自己的源码学习 Agent 里？

也就是说，这 24 个痛点不是产品附录，而是后续 5 个 Agent 深度分析的统一评估坐标系。
