# 五项目横向专题：工具协议与副作用边界

> 对比对象：OpenCode / Reasonix / Pi / Hermes / dsh
> 核心问题：Agent 如何把模型意图变成受控、可追踪、可恢复的外部副作用。
> 关联文档：`06-5项目横向对比总锚点.md`、各项目 Permission / Tool / Workspace / Capability 正文。

---

## 一、为什么工具不是普通函数？

模型产生的 tool call 不是可信的本地函数参数，而是：
- 外部生成的意图
- 可能缺字段或类型错误
- 可能引用旧能力
- 可能触发文件、进程、网络或平台副作用
- 可能在等待审批、取消或崩溃时处于半完成状态

因此工具系统至少要回答：

1. 这个能力当前还存在吗？
2. 这个调用是否被允许？
3. 参数和结果是否符合契约？
4. 副作用发生到哪一步了？
5. 结果是否进入模型上下文和持久历史？
6. 失败后能否安全重试？

---

## 二、五个项目的一句话对照

| 项目 | 工具/能力模型 | 副作用控制中心 | 最重要的保护 |
|------|---------------|----------------|--------------|
| OpenCode | opaque handle + settlement pipeline | PermissionV2 + ToolRegistry | stale rejection、schema、bounded output |
| Reasonix | 任务控制面中的工具动作 | Permission + WorkspaceLease | writer lease、任务级一致性 |
| Pi | harness/core 双层工具 | AgentSession + tool result 语义 | 错误结果回注、并行执行顺序稳定 |
| Hermes | 长期代理工具与平台能力 | SecretScope / authz / 验证守卫 | 凭证隔离、验收门、生命周期审计 |
| dsh | 五事件工具协议 + capability seam | Cordis 事件/guard + shared world | 插件守卫、事件日志、共享执行世界 |

---

## 三、OpenCode：工具是受 registry 管控的协议对象

OpenCode 最明确地拒绝把工具当作裸函数：
- 工具值是不透明句柄
- registry 掌握真实运行时定义
- 输入经过 schema 解码
- 输出经过 schema 编码与投影
- 旧注册对象会被 stale rejection 拒绝
- 超大输出进入 ToolOutputStore，模型只看 bounded preview

它的工具管线可以写成：

```text
tool handle
  → resolve current registry identity
  → decode input
  → permission assert
  → execute
  → encode/project result
  → bound/store output
  → settle into model + durable events
```

OpenCode 的副作用哲学是：
> **工具必须先成为 runtime 管控的协议对象，才能成为可执行能力。**

---

## 四、Reasonix：工具动作必须服从任务和工作区生命周期

Reasonix 的重点不是把每个工具做成复杂 registry，而是把副作用放入任务控制面：
- Permission 决定动作是否允许
- WorkspaceLease 决定谁拥有工作区修改权
- writer 从首次变更开始持有租约直到任务完成
- review/verify 在同一工作区语义中运行

这意味着 Reasonix 关注的不是单次调用，而是：

```text
动作授权
  → 工作区写入权
  → 任务执行
  → review / verify
  → completion / recovery
```

Reasonix 的副作用哲学是：
> **一次允许并不等于整个任务期间都安全，工作区所有权必须延续到验收完成。**

---

## 五、Pi：工具失败也要成为模型可见事实

Pi 的工具系统有两个重要判断：

### 1. 工具可以并行，但结果必须按调用顺序回到上下文

这样同时保证：
- 运行效率
- 模型看到的协议顺序稳定

### 2. 工具准备阶段失败不能直接打死 loop

例如：
- 工具不存在
- 参数无效
- beforeToolCall 阻止
- abort

这些情况会被包装成模型可见的错误 `ToolResultMessage`，让模型根据事实重新规划。

Pi 的副作用哲学是：
> **工具失败不是进程级异常，而是模型下一步推理必须看到的上下文事实。**

---

## 六、Hermes：能力边界与验收边界必须一起看

Hermes 的副作用保护不仅是权限判断，还包括：
- SecretScope
- authz
- SelfRepoGuard
- verification_stop
- kanban_stop
- GoalGate

这说明 Hermes 关心两类边界：

### 能不能做
- 凭证是否可见
- 当前身份是否授权
- 是否能访问特定项目/平台

### 做完是否算完成
- 确定性验证是否通过
- 交付是否真正送达
- 任务是否满足 contract
- judge 是否允许停止

Hermes 的副作用哲学是：
> **允许执行和允许宣布完成是两道不同的门。**

---

## 七、dsh：工具是插件事件管线，副作用依赖共享执行世界

dsh 把工具拆成事件协议：
- pre
- post
- execute
- code-dispatch-log
- result

同时通过 Cordis 的：
- waterfall
- serial
- parallel
- emit

让插件可以：
- 拦截
- 修改
- 短路
- 记录
- 异步观察

再通过 capability seams 和 shared execution world 保证：
- fs
- shell
- subprocess
- sandbox

看到的是同一个现实环境。

dsh 的副作用哲学是：
> **副作用边界不是某个工具的私有逻辑，而是插件事件、能力缝和共享世界共同定义的运行时契约。**

---

## 八、五种副作用边界的真正差异

| 项目 | 边界主要放在哪里 | 典型失败处理 | 适合场景 |
|------|------------------|--------------|----------|
| OpenCode | registry + permission + settlement | 拒绝、结构化错误、bounded result | 平台化 runtime |
| Reasonix | task controller + workspace lease | blocked、冲突、暂停恢复 | 长跑代码任务 |
| Pi | session loop + tool result | 错误回注模型、继续规划 | 交互/探索 Agent |
| Hermes | authz + secret + verification gate | 拒绝、暂停、验收不通过 | 多平台长期代理 |
| dsh | plugin event + capability seam + shared world | guard 短路、事件失败、共享世界拒绝 | 插件化框架 |

---

## 九、设计新 Agent 时应该先回答的 9 个问题

1. tool call 的身份如何确认，旧工具如何失效？
2. 输入和输出 schema 谁负责校验？
3. permission 是按工具名，还是按 action × resource？
4. approval 是同步返回，还是会话内 pending state？
5. 工具失败是异常、结果，还是新的模型事实？
6. 大输出如何同时满足模型上下文和完整审计？
7. 工作区写权限覆盖一次调用，还是整个任务生命周期？
8. 工具执行与验证/完成判定是否共享同一现实世界？
9. 副作用发生到一半崩溃后，系统如何区分未开始、进行中、成功和未知？

---

## 十、一句话结论

五个项目共同说明：

> **工具调用的核心不是“怎么执行函数”，而是如何把模型意图、授权、执行、输出、日志、工作区和恢复语义串成一个不会越过边界的协议。**
