## 一、这一章真正的问题

Hermes 之前各章都在讲：
- 系统怎么推进执行
- 系统怎么学习
- 系统怎么被保护

但还有一个更基础的问题没回答：

> **系统运行之后，到底“发生过的事”能不能被可靠地追责。**

这一章真正要回答的是：

1. 最终响应有没有真正送达？
2. 崩溃前最后发生了什么？
3. 上一轮生命周期是正常退出还是被杀死？
4. 这些问题的答案能不能在系统重启后仍然被找到？

## 二、先给结论：Hermes 把“交付”和“生命周期”做成了持久化、可追责、可恢复的账本系统

最容易犯的错，是把这两者看成：
- 一个日志
- 一个审计工具

这太浅了。

更准确的理解是：

> **DeliveryLedger 和 LifecycleLedger 是 Hermes 为“运行后的可解释性”做的持久化系统。**

它们不是记录“发生了什么”，而是在回答：
- 这个响应到底有没有交付？
- 上次崩溃前最后的遥测是什么？
- 这次启动是不是异常引起的？

所以这章的核心不是“数据结构”，而是：
> **Hermes 如何让系统死后还能被解释。**

---

## 三、为什么 DeliveryLedger 不是简单日志，而是 at-least-once 交付的核心

Hermes 的 DeliveryLedger 不是“记录一下发了什么”。

它有一个三检查点状态机：
- pending（发送从未开始）
- attempting（已开始发送，但未确认成功）
- delivered / failed（确定性终态）

这个状态机在解决的是一个真实问题：

> **最终响应生成后，在真正交付给平台之前崩溃，可能导致响应永远丢失。**

如果没有这个账本：
- tokens 已经烧了
- 响应文本只在 Python 局部变量里
- 崩溃后，没有人知道这个响应应该被发出去

Hermes 的做法是：
- 先 record_obligation(pending)
- 再 mark_attempting
- 最后 mark_delivered/failed
- 崩溃后，sweep_recoverable 认领未完成行，重新投递

所以它不是在“记日志”，而是在：
> **定义“已交付”的语义边界。**

---

## 四、为什么 pending/attempting/delivered/failed 的崩溃语义是分开的

Hermes 对每个状态的崩溃语义做了显式声明：

- pending：发送从未开始，直接重投，无重复风险
- attempting：可能已发送，带可见标记重投
- failed：确定性拒绝一次，重启是自然重试边界
- delivered：无事，保留期后清除

这个设计非常值钱，因为很多系统在处理崩溃恢复时只会做一件事：
- 一律重试

但 Hermes 区分了：
- 没动过（pending）
- 可能动了（attempting）
- 确定失败了（failed）
- 确定成功了（delivered）

这直接决定了：
- 重投时要不要带标记
- 重投后用户会不会收到重复消息

所以 Hermes 的交付账本不只是在“记”，而是在：
> **为恢复语义提供确定性区分。**

---

## 五、为什么 LifecycleLedger 中的哨兵状态机是运行可解释性的基石

LifecycleLedger 不是“日志”，它也是一个状态机。

它的核心是：
- 哨兵文件 `gateway.lifecycle.json`
- phase = running / exited
- 每次启动读哨兵，判断上一生命是否正常退出

这解决的是：

> **SIGKILL / OOM / VM 死之后，没有任何 handler 可以跑，系统怎么知道上一生命是怎么死的。**

Hermes 的做法是：
- 心跳 30s 嵌入内存采样
- 不洁死亡时携带死亡前最近的内存样本
- OOM 启发标注（保守，只提示不判定）
- 判定前传给下一生命

所以这不是“监控”，而是：
> **崩溃归因的持久化基础设施。**

---

## 六、为什么心跳内存采样和 OOM 启发标注很关键

LifecycleLedger 中有一个很容易被低估的点：
- 心跳不仅证明“还活着”
- 还携带死亡前最近的内存样本

这意味着：
- 下次启动时，如果发现上一生命是不洁死亡
- 系统可以解释“当时内存情况”

更重要的是：
- 这个样本本身就是崩溃后唯一的幸存记录
- 因为不洁死亡时，没有任何 handler 可以运行

所以 Hermes 在做的不是“心跳”，而是：
> **死亡前最后一刻的遥测快照。**

---

## 七、为什么所有权守卫和原子写对账本系统很重要

DeliveryLedger 和 LifecycleLedger 都涉及一个关键问题：
- 谁写的、谁改的、谁认领的

### 所有权守卫
- mark_exited 会检查哨兵 pid 是否等于当前进程 pid
- 如果是 --replace 场景，旧进程不能改写新进程的哨兵

### 原子写
- 哨兵文件本身就是取证对象
- 如果写它时崩溃，下一次读到的可能是半写垃圾
- 所以必须 temp + replace + fsync

这说明 Hermes 对账本系统的要求是：
> **账本不仅不能丢，还不能被错误地改写或读坏。**

---

## 八、为什么 attempts 预算只花在真发送上

DeliveryLedger 的一个设计非常值得学：
- attempts 预算只花在真实发送上
- 如果某个平台本 boot 连接失败，sweep 不认领该平台的行

这解决的是：
- 预算不会因为“平台不可达”而被消耗
- 所以每次重投都是真正可能成功的

这和“有了预算就能重试”不同，Hermes 更谨慎：
> 每次重试预算必须花在真正可能成功的动作上。

## 九、这一章真正解决了哪些工程问题？

### 1. 如何保证最终响应不因崩溃而丢失
Hermes 的解法：DeliveryLedger + 三检查点 + sweep_recoverable

### 2. 如何区分“没动过”、“可能动了”、“确定失败了”、“确定成功了”
Hermes 的解法：pending / attempting / delivered / failed 四态

### 3. 如何在系统被杀死后仍能解释死亡原因
Hermes 的解法：LifecycleLedger + 哨兵状态机 + 心跳内存采样

### 4. 如何防止账本被错误改写或读取
Hermes 的解法：所有权守卫 + 原子写

### 5. 如何让重试预算不被浪费在不可达平台上
Hermes 的解法：deliverable_platforms 过滤

所以这章真正要学的，不是“账本代码”，而是：

> **Hermes 如何把“交付”和“生命周期”做成运行后可解释的持久化系统。**

### 为什么这里不先展开具体平台适配器细节
因为这章先讲交付和生命周期账本本身，而不是每个平台如何发送消息。

因为 Hermes 的 OOM 启发标注是有意保守的——只标注，不判定。分类交给人类。

### 为什么账本和主流程必须分离
因为账本失败不应该阻塞消息发送，这是 Hermes 明确的设计原则。

## 十三、迁移清单

### 可迁移思想 1：交付状态机 + 崩溃恢复
- 可迁移到：任何需要 at-least-once 回复的 Agent 系统
- 前提：回复交付是业务语义的一部分
- 不适合直接照搬到：纯流式或无需持久回复的系统

### 可迁移思想 2：哨兵状态机 + 不洁死亡检测
- 可迁移到：长期运行、需要崩溃归因的 Agent 系统
- 前提：系统不是一次性进程
- 不适合直接照搬到：极短生命周期进程

### 可迁移思想 3：心跳带环境遥测
- 可迁移到：需要崩溃分类的守护进程
- 前提：死亡前有正常心跳可以采样
- 不适合直接照搬到：无心跳机制的轻量进程

### 可迁移思想 4：主数据优先
- 可迁移到：任何观测/可靠性层
- 前提：辅助层失败不应阻塞主链路
- 不适合直接照搬到：无主链路/辅助层区分的小系统
