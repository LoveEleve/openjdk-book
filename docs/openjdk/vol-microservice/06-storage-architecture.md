## 现在真正该问的，不再是“要不要分库分表”，而是“分片后数据在哪里、请求如何路由、事务如何完成、查询如何聚合、数据如何迁移”

前几篇已经把通信、服务治理、缓存和消息都讲清楚了。但只要你继续往存储层看，就会碰到一个非常现实的问题：

单个数据库的容量、I/O、连接和维护窗口迟早会撞墙。

很多团队在单库撑不住时，第一反应是“分库分表”。但真正做过的人都会发现：分库分表不是“把一个大库复制成很多小库”，而是：

- 数据到底放在哪个分片；
- 请求按什么规则路由到哪个分片；
- 跨分片的查询、排序、分页怎么聚合；
- 原来一个本地事务能搞定的，现在怎么落地；
- 从 4 库 32 表扩到 8 库 64 表，怎么不停机搬迁。

任何一个环节没想清楚，形式上“拆了”，实际上可能比不拆更糟——比如订单明明创建在 order_db_3，查询却只扫了 order_db_0。

先把总图记住：

```text
容量/并发/维护瓶颈
  → 垂直或水平拆分
  → 选择 shard key / global ID
  → 重新设计查询/事务
  → 代理或客户端路由
  → re-sharding / 校验 / 切流
  → 监控跨片延迟 / 热点 / 复制 / 一致性
```

这篇最该先记住的一句话是：**分库分表不是“把表切小”，而是把容量、路由、事务、查询、ID 和迁移责任从数据库转移到整个架构；一旦拆分，数据库便利性会转化为应用和平台责任。**

## 一、单库瓶颈：拆分解决什么，不解决什么

### 1. 最朴素的错误世界：单表超过某个固定行数，就必须分片

这个规则在“行数 = 瓶颈”的假设下很诱人，但单库真正撞墙的地方往往不是行数单值，而是：

- 索引和行宽；
- 访问模式和缓存命中；
- I/O 和内存压力；
- 并发和连接数；
- 维护窗口和执行计划。

所以“单表超过 N 行就分片”是一个危险的机械规则。它把容量和 workload 判断偷换成了行数阈值。

### 2. 存储演进的最小路线图

```text
单库:
  所有表/读写/资源共享

读写分离:
  主库写 + 副本读
  → 扩展读
  → 引入复制延迟/读己之写问题

垂直拆分:
  order/user/inventory → 业务域/实例边界
  → 隔离资源与团队边界
  → 跨域 join/事务变复杂

水平分片:
  同一逻辑表按 shard key
  → 多库多表
  → 单片容量/流量下降
  → 路由、跨片聚合和迁移复杂
```

### 3. 为什么不能先用简单行数阈值决定是否分片

因为“行数”只是一个信号，不是通用阈值。同样 1 亿行，可能因为：

- 索引合理、查询局部、缓存命中率高而轻松扛住；
- 也可能因为宽行、全扫、热点列而早早卡死。

所以分片前要先确认优化器、索引、归档、读写分离和硬件是否已到合理边界。分片是架构变化，不是行数换算。

### 4. 本节最该记住的结论：单库撞墙的本质是容量、并发、I/O、连接和维护窗口的综合瓶颈，不是单表行数；分片前先确认索引、归档、读写分离和优化器是否已到边界

一句最短人话是：**单库像一座中央仓库，拆分不是因为货物超过某个神奇箱数，而是因为道路、货架、进出货和维护已经互相堵住。**

## 二、分片键：数据模型的“重力中心”

### 1. 第二个朴素误解：分片键就是给表加一个取模字段

分片键看起来像“对某个字段取模”，但它实际决定了：

- 路由命中率；
- 数据局部性；
- 热点分布；
- 跨片查询范围；
- 全局 ID 设计；
- 迁移和扩容方式。

所以它不是一个 hash 输入，而是数据放置与一致性边界。

### 2. 分片键候选与跨片查询的最小图

```text
选择候选:
  user_id → 同用户订单聚合方便
  tenant_id → 租户隔离/路由清晰
  time/range → 范围归档友好, 可能热点
  hash → 分布均匀, 范围查询困难

跨片查询:
  无 shard key
  → fan-out
  → 各片过滤/排序/聚合
  → coordinator merge
  → 延迟受最慢分片和返回量影响

关联表:
  共享 shard key → 可能保留局部 join
  不同 key → 反范式/应用聚合/搜索索引
```

### 3. 为什么分片键一旦选错，后面很难补救

因为它嵌入路由、主键、索引、事务和查询模型：

- 非分片键查询需要全片扫描或额外全局索引；
- 热点键会让单片先饱和；
- 全局 ID 还要考虑有序性、时钟回拨、唯一性和迁移（所谓“时钟回拨”，指的是生成 ID 依赖的机器时钟被调回时，可能产生与之前相同的 ID，从而带来唯一性风险）。

所以分片键的选择，实际上是在一开始就为整个数据模型画好了“重力中心”。

### 4. 一个更具体的失败场景：按 user_id 分片，但报表要“最近 7 天金额超阈值”扫全片

假设：

- 订单表按 user_id 分片；
- 一个分析查询是“最近 7 天金额超过阈值的用户”；
- 这个查询没有 user_id 约束；
- 结果必须 fan-out 到所有分片，各自过滤、排序、聚合，再由 coordinator merge。

单个分片很快，但总延迟被最慢分片卡住。这不是 SQL 写错了，而是分片键和查询模型不匹配。这里要补一句下一步的方向：要么给这类分析查询单独建分析型索引或仓库，要么接受 fan-out 的成本并优化最慢分片——你几乎不可能让一个按 user_id 分片的表，在所有跨片分析查询上又快又省。

### 5. 本节最该记住的结论：分片键是这个数据模型的重力中心，决定局部性、热点和跨片代价；选错后很难补救，因为它嵌入路由、主键、索引、事务和查询模型

一句最短人话是：**分片键像仓库分区规则；按客户分仓方便查某客户，按日期分仓方便清理历史，但跨规则查询都要跨仓找货。**

## 三、分布式事务：订单、库存、积分如何落地

### 1. 第三个朴素误解：分库分表后，原来单库的事务还能继续用

单库事务之所以“舒适”，是因为所有资源管理器共享一个本地提交点。分库以后这个前提消失了：

- 网络超时让“调用失败”和“远端未提交”无法直接等价；
- 多个资源管理器有独立日志和故障状态；
- 部分成功是常态而不是异常。

所以分库以后，分布式事务真正要处理的是：业务不变量、允许的中间态、恢复方式和运维能力，而不是只看框架注解。这里还要补一句关键桥接：分片键的选择和事务边界必须一起设计——如果能选一个让大多数操作集中在同一分片内的 shard key，很多跨片事务问题就从源头被减少了。

### 2. 分片后的事务方案菜单

```text
XA / 2PC:
  多资源 prepare/commit
  → 原子边界更直接
  → 阻塞/锁/协调恢复成本

TCC:
  Try 预留
  → Confirm/Cancel
  → 业务侵入、重试/幂等/空回滚

Saga:
  本地步骤
  → 失败逆序补偿
  → 中间态可见

本地消息表 + MQ:
  本地事务写业务+消息
  → 消费者幂等/重试/对账
  → 最终一致
```

### 3. 本节最该记住的结论：分库分表后，很难保留单库事务的舒适性，因为资源管理器不再共享本地提交点；真正的选择是业务不变量、中间态、恢复和运维能力，而不是只看框架注解

## 四、Re-sharding：数据迁移比第一次分片更难

### 1. 第四个朴素误解：从 4 库 32 表扩到 8 库 64 表，停写一次、拷贝、再启动就行

这个“停库搬迁”方案在概念上最简单，但生产通常不能接受停机窗口，而且迁移期间仍有并发写。

### 2. Re-sharding 的最小流程

```text
准备:
  定义新 shard map/双读策略

全量:
  批量迁移历史数据
  → 控制速率/校验/记录进度

增量:
  双写、CDC/binlog 捕获或变更日志
  → 补齐全量迁移期间新增修改

校验:
  行数/checksum/业务抽样/版本

切换:
  灰度读新
  → 停止旧写/完成尾差
  → 只读新路由
  → 观察后清理旧数据
```

这里“双读”不是一个无脑动作，它有明确的语义边界：在迁移完成、读请求切到新路由之前，客户端仍可能读到尚未同步的旧分片数据。所以切换前要做尾差校验，切换时灰度读新并保留回退能力，否则双读期间客户端会因为新旧分片数据不一致而看到错误结果。

### 3. 为什么分片数量也不是越多越好

分片多了不一定好事：

- 连接数增长；
- 元数据膨胀；
- 空表比例上升；
- 迁移成本增加。

所以 re-sharding 的目标不是“尽量多分片”，而是“用刚好够的分片解决容量和流量问题，并让迁移成本可控”。

### 4. 本节最该记住的结论：Re-sharding 需要在不停机时同时处理全量、增量、校验和切流；分片数量不是越多越好，连接、元数据、空表和迁移成本都会随分片增长

一句最短人话是：**Re-sharding 像营业中的仓库换分区：旧仓继续接单，新仓同步搬货，最后要对账、切换门牌，再拆旧仓。**

## 五、代理与客户端路由：隐藏复杂度不等于消除复杂度

### 1. 第五个朴素误解：接一个分库中间件，应用就能无感地继续用单库

这个“无感”体验在短期原型阶段可能成立，但分片边界迟早会暴露在如下场景：

- 无 shard key 的查询；
- 跨片 join；
- 分页和排序；
- 事务；
- 错误重试；
- 数据迁移。

中间件能集中策略，但也可能成为新的容量、故障和版本兼容边界。所以“让应用无感”通常只是短期体验，分片边界的复杂度最终仍要被应用和平台理解。

### 2. 路由责任的最小图

```text
Proxy:
  应用连接统一入口
  → 代理解析 SQL/分片键
  → 路由/改写/聚合
  → 统一治理
  → 增加网络跳数与代理状态

Client SDK:
  应用/驱动本地路由
  → 少一跳/控制直接
  → 所有服务必须升级/理解 shard map

共同限制:
  无 shard key 的查询、跨片 join、分页、排序、事务
  → 都需要额外策略
```

### 3. 本节最该记住的结论：代理能隐藏接入方式，不能消灭分片语义；路由层的透明性必须以可解释的 SQL 和事务限制为代价说明

## 六、把本篇收成一张图：分库分表是重新定义数据、路由、事务、聚合和迁移

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：订单为什么明明创建了却查不到。答案已经闭环了，因为它可能被路由到了另一个分片，而查询没有带 shard key。

单库瓶颈不是行数单独决定的；分片键是这个数据模型的重力中心；分库后事务很难保留单库舒适性；re-sharding 需要全量、增量、校验和切流同时正确；代理能隐藏接入但不能消灭分片语义。所以分库分表真正改变的，是数据在哪里、请求如何路由、事务如何完成、查询如何聚合和数据如何迁移。

把这一切压成最短总图，就是：

```text
容量/并发/维护瓶颈
  → 垂直或水平拆分
  → 选择 shard key/global ID
  → 重新设计查询/事务
  → 代理或客户端路由
  → re-sharding/校验/切流
  → 监控跨片延迟/热点/复制/一致性
```

所以本篇最该记住的一句话是：**分库分表不是“把表切小”，而是把容量、路由、事务、查询、ID 和迁移责任从数据库转移到整个架构；一旦拆分，数据库便利性会转化为应用和平台责任。**

## 七、几个最容易说错的地方

### 单表超过固定行数就必须分片？

不是。真正瓶颈取决于索引、行宽、访问模式、缓存、I/O、并发和维护窗口，行数只是信号。

### 分片键就是给表加一个取模字段？

不是。它决定路由命中、局部性、热点和跨片查询，是整个数据模型的重力中心。

### 分库后原来的本地事务还能继续用？

不是。资源管理器不再共享本地提交点，分布式事务要显式处理部分成功、中间态和补偿。

### 从 4 库扩到 8 库，停写拷贝再启动就行？

不是。生产通常不能接受停机窗口，re-sharding 要同时处理全量、增量、校验和切流。

### 接一个分库中间件就能无感用单库？

不是。分片边界会在事务、分页、排序、重试和迁移中暴露，复杂度最终仍要被应用和平台理解。

## 收束：分库分表真正的门槛，不是“把表切小”，而是接受“数据库便利性转化成了应用和平台责任”

回到开头那个问题：订单为什么明明创建了却查不到。答案已经闭环了：因为分片把数据放到了不同的库表，而查询如果没有正确携带 shard key，就可能只扫了错误的那个分片。分库分表的价值在于扩容和数据隔离，但代价是把容量、路由、事务、查询、ID 和迁移责任从数据库转移到整个架构。它不是一个可以无脑套用的扩容开关，而是一整套需要重新设计和持续维护的架构方案。

这就是为什么说：**分库分表不是“把表切小”，而是把容量、路由、事务、查询、ID 和迁移责任从数据库转移到整个架构；一旦拆分，数据库便利性会转化为应用和平台责任。** 只要这条主线站稳，下一篇进入服务边界设计时，你就不会再把微服务拆分看成“把一个类的包拆开”，而会自然去问：服务边界是否真的对应业务不变量，还是只是把单体切成了分布式泥球。
