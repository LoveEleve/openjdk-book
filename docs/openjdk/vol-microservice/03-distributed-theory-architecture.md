## 现在真正该问的，不再是“全系统选 CP 还是 AP”，而是“每个数据、每个操作和每个故障窗口，你到底需要怎样的一致性、延迟、可用性和补偿”

前两篇已经把通信底座和 RPC 治理讲清楚了。但很多初学者在真正设计微服务架构时，仍然会卡在一个更根本的问题上：

“ZooKeeper 是 CP 的，Kafka 是 AP 的，Redis 是最终一致的，MySQL 是强事务的——这么多一致性模型放在同一个系统里，真的没问题吗？”

这个问题的答案，恰恰是微服务架构最大的共识之一：**CAP 不是系统级标签，而是数据级和操作级的选择。**

一个系统同时使用 ZK 做协调、Redis 做缓存、MySQL 做核心事务、Kafka 做异步消息，不是因为架构师没想清楚，而是因为不同数据和服务对一致性、可用性和延迟的要求本来就不同。

- 配置中心的变更顺序比临时可用性更重要；
- 商品列表的缓存短暂旧读是可以接受的；
- 库存扣减不能超卖，必须强一致或幂等加补偿；
- 订单状态可以靠最终一致和补偿收敛。

所以“这个系统是 CP 还是 AP”是一个没有意义的问题。真正有意义的问题是：**每一条数据路径、每一个操作，在分区故障发生时的承诺是什么。**

先把总图记住：

```text
业务不变量
  → 数据/操作级一致性 SLA
  → 选择 CP / AP / 最终一致 / 客户端一致
  → 协调服务 / 数据库 / 消息 / 缓存各自承诺
  → 读写路由、重试、幂等、fencing、补偿
  → 故障演练验证用户可见结果
```

这篇最该先记住的一句话是：**CAP 不是系统级标签，而是按数据、操作和故障场景定义 SLA；一套微服务架构可以同时包含多种一致性模型。**

## 一、CAP 在工程里不是系统标签，而是操作级 SLA

### 1. 最朴素的错误世界：学完 CAP 要给整个系统打一个 CP 或者 AP 的标签

这是 CAP 定理最容易出现的过度简化。很多人学完“C、A、P 三者不可兼得”之后，第一反应就是给系统分类：

- 这个系统是 CP；
- 那个系统是 AP；
- 所以选型就结束了。

但真正在工程里，你面对的不是“一个系统”，而是“很多个数据路径”。同一个系统里可以同时存在：

- 库存扣减（强一致优先）；
- 商品列表（短暂旧读可接受）；
- 配置中心（顺序与一致优先）；
- 订单状态（最终一致加补偿）。

所以 CAP 的落地单位不是系统，而是操作和数据的 SLA。

### 2. 操作级一致性 SLA 的最小图

```text
库存扣减:
  不允许超卖/重复扣减
  → 强一致/串行化/幂等优先

商品列表:
  短暂旧读可接受
  → 可用性/缓存命中优先

配置中心:
  变更顺序/单一视图重要
  → CP 协调服务

订单状态:
  需要状态机/幂等/最终收敛
  → 按操作分别定义读写语义

PACELC:
  分区时看 C/A
  正常时看 Latency/Consistency
```

### 3. 为什么一个架构同时出现 CP 和 AP 不是矛盾

因为“一致性”的根本单位不是“这台机器”或“这个数据库”，而是“这个操作在分区故障下的可见性承诺”。

- 配置中心用 CP 模型，保证同一时刻所有节点看到的配置版本一致；
- 缓存用 AP 模型，短暂旧读可以用最终一致性收敛；
- 事务核心用强一致或幂等加补偿保护。

它们各自服务于不同的业务不变量，放在同一个架构里不是矛盾，而是分工。

### 4. 本节最该记住的结论：CAP 的落地单位不是系统，而是操作和数据路径；同一系统可以同时包含 CP、AP 和最终一致，关键是每条数据路径的 SLA 必须被显式声明

一句最短人话是：**城市交通不是所有道路都追求同样规则：消防通道优先可靠，商业街优先可达，临时停车区允许最终清理；关键是标明每条路的约束。**

## 二、ZooKeeper/etcd：强一致协调服务不是缓存

### 1. 第二个朴素误解：ZooKeeper 和 etcd 就是“存配置的 Redis”，所以用 Redis 也可以替代

这个误解源于“它们都存 key/value”这个表面相似性。但三者的定位完全不同：

- Redis 的主要职责是缓存和快速存取；
- ZK/etcd 的主要职责是协调语义：顺序、版本、租约、成员、watch。

它们不是“更快更慢的同类”，而是“解决不同问题的不同系统”。

### 2. ZK/etcd 的最小协调图

```text
注册:
  instance → key / ephemeral / lease
  → session / lease 失效后可清理

配置:
  write → 有序提交
  → watch / 读取当前版本

选主/锁:
  lease / 临时节点 + fencing / 版本
  → 不能只依赖客户端本地超时

etcd / ZK:
  都可提供 CP 类协调语义
  → 具体线性读、watch、租约和成员管理以版本为准
```

### 3. 为什么 Redis 的高可用缓存不能替代 ZK/etcd 的协调语义

因为协调需要的东西，缓存不提供：

- 顺序和版本化写入；
- 租约与会话语义；
- 可靠性变更通知（watch）。

Redis 的复制和故障切换可能会返回旧值或丢写入，这在缓存场景下可以接受，但在协调场景下则可能造成错误决策。

### 4. 一个更具体的失败场景：用 Redis 存配置，主从切换后客户端读到旧配置

假设：

- 配置更新在主库成功写入；
- 主库故障；
- 新主库尚未完全同步旧配置；
- 客户端读到旧配置，做出错误决策。

在缓存场景下旧读可以接受，但配置协调场景下可能造成选主错乱、路由错误或服务中断。这就是为什么 ZK/etcd 用共识和租约来保证协调语义，而不是单纯靠主从复制。

### 5. 本节最该记住的结论：ZK/etcd 不是 Redis 的慢替代品，而是为协调语义（顺序、版本、租约、watch）设计的 CP 系统；缓存和协调服务是不同职责，不能互相替代

一句最短人话是：**ZK/etcd 像会议室管理系统，Redis 像茶水间零食柜；两者都存 key/value，但一个是用来协调会议顺序和权限，一个是用来快速取用。**

## 三、分布式锁：Redis、ZK 与 fencing token 的安全级别

### 1. 第三个朴素误解：`SET lock NX EX 30` 加上主从同步，就是一个安全的分布式锁

这个想法在缓存和限流场景里经常成立，但在跨资源协调里可能不够。

因为分布式锁真正的安全边界，不是“拿到锁那一刻”，而是“锁过期后旧持有者还能不能继续写资源”。

### 2. 锁方案的最小安全图

```text
Redis lease:
  SET key NX EX
  → 简单 / 低延迟
  → 主从切换、暂停、过期与脑裂边界需评估

ZK / etcd:
  版本 / 临时节点 / 租约
  → 顺序竞争与 watch
  → 仍需正确处理会话和重连

fencing:
  每次获取锁得到递增 token
  → 下游资源验证 token
  → 旧持有者即使恢复也不能覆盖新写
```

### 3. 为什么 Redlock 的争议最终都落在“fencing 有没有被验证”

Redlock 的设计走得比普通 Redis 锁更远，但它的争议核心仍在于：如果资源端只相信“客户端自称持锁”，而不验证 fence token，那么即使锁算法在多数节点上达成一致，旧客户端在 GC 暂停后恢复时仍可能不知道自己已经过期。

所以真正安全的锁，不是“拿锁的技术够好”，而是“失去锁后，旧持有者还能不能产生副作用”。只有 fencing token 或者租约过期后的版本校验，才能从资源层切断旧写。fencing 的典型实现是：锁服务在授予锁时签发一个单调递增的令牌号，客户端每次写资源时带上令牌，下游资源校验令牌版本，发现旧令牌就直接拒绝——这样即使旧持有者恢复，也无法覆盖新持有者的写入。

### 4. 一个更具体的失败场景：GC 暂停 40 秒，锁过期后旧客户端继续写

假设：

- 客户端 A 拿到 Redis 锁 EX 30 秒；
- A 发生 Full GC 40 秒；
- 锁过期，客户端 B 拿到新锁；
- A 恢复后继续写资源。

如果资源端不验证 token，A 的写入就会被接受，B 的写入也可能同时存在。这时问题不是“锁算法不够好”，而是“没有 fencing 机制把旧客户端隔离开”。

### 5. 本节最该记住的结论：分布式锁的安全边界不在“拿锁方式”，而在“失去锁后旧持有者能否继续写”；fencing token 或版本校验是资源层的最后防线

一句最短人话是：**锁像仓库钥匙，租期结束后旧钥匙必须被门禁拒绝；仅仅发一把新钥匙、却不检查钥匙版本，旧管理员仍可能回来开门。**

## 四、Paxos/Raft 在架构中的角色：共识是底座，不是业务语义

### 1. 第四个朴素误解：用了 Raft 或 Paxos 的系统，业务查询就是强一致的

这个误解非常普遍，因为共识看起来已经很强了：

- 日志有序；
- 多数派提交；
- 副本一致。

但“共识日志一致”与“业务查询永远最新”之间还有很长的路：

- 上层读路径可能走缓存；
- 异步索引可能滞后；
- 事务隔离级别可能允许旧读；
- 故障切换后的路由也可能读到还未同步的副本。

### 2. 共识层与上层的语义图

```text
共识层:
  quorum + term/ballot + ordered log
  → 复制一致状态

上层:
  etcd → key/value/lease/watch
  ZooKeeper → znode/session/watch
  Kafka → partition log/offset/ISR
  TiKV → region/raft/transaction

注意:
  共识日志一致
  ≠ 业务查询永远最新
  ≠ 跨系统事务自动原子
```

### 3. 为什么“用了 Raft”不等于“实现了强一致数据库”

因为共识只保证它复制的状态机输入/提交语义是确定的。但用户看到的可见性，还取决于：

- 读路径是否经过共识；
- 缓存是否可能返回旧值；
- 异步索引和物化视图的滞后；
- 事务隔离级别如何定义“当前读”；
- 故障切换后路由是否可能落到未同步的副本。

所以共识是底座，不是业务语义的自动保证。这里还要补一个读者立刻会碰到的读路径边界：同一套共识系统，读取时也分不同路径。比如 etcd 提供线性化读（走 quorum）和序列化读（本地读）两种选择，ZK 从 follower 读也可能返回相对旧的值。如果只知道“共识 = 强一致”，却不知道读路径也要显式选择，业务就可能读到旧数据，并误以为共识实现出了问题。

### 4. 本节最该记住的结论：共识（Paxos/Raft）只保证复制日志的一致，不保证业务查询永远最新；上层读路径、缓存、事务和故障路由仍然决定用户看到什么

一句最短人话是：**共识像发电站保证电网频率稳定，但不保证你的台灯开关一定亮着——中间还有传输、变压器和开关。**

## 五、分层一致性与 Quorum：架构是多个模型的叠加

### 1. 第五个朴素误解：架构选型就是选一个“最一致”的数据库，把所有问题都扔给它

这个想法在“一个数据库包打天下”的时代也许成立，但微服务架构里，数据从来不会只住在一个地方。

- 配置层：CP 协调服务；
- 数据库层：本地事务 + 复制延迟；
- 消息层：分区内有序；
- 缓存层：最终一致；
- 文件/对象存储：最终一致。

所以架构的一致性承诺，不是“系统选了什么”，而是“每一层分别承诺了什么，以及层与层之间的边界在哪里”。

### 2. 分层一致性的最小图

```text
配置层:
  强顺序 / 版本 / 租约

数据库层:
  本地事务 / 复制延迟 / 读己之写

消息层:
  分区内顺序 / 至少一次 / 重复消费

缓存层:
  失效 / 双写 / 异步刷新 / 最终一致

NWR 类模型:
  R / W 与副本数的组合影响读写交集
  → 不脱离副本拓扑/故障/读修复定义强一致
```

### 3. 为什么不能把 `R+W>N` 直接等同于全局强一致

因为 quorum 交集只说明某些读写会相遇，但真正语义还取决于：

- 副本版本号；
- 读修复是否执行；
- 故障节点是否被排除；
- 并发写是否冲突；
- 冲突解决策略如何定义；
- 线性化点是否被保证。

所以 `R+W>N` 只是一个必要条件，不是充分条件。

### 4. 本节最该记住的结论：架构的一致性承诺是每一层语义的叠加，不是“系统选了什么”的一锤子买卖；`R+W>N` 只是必要条件，不是充分条件

## 六、把本篇收成一张图：架构不是选 CP 还是 AP，而是操作级 SLA 的显式声明

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：8 个服务同时使用 ZK、MySQL、Kafka、Redis，为什么这不矛盾。答案已经闭环了。

CAP 的落地单位不是“系统”，而是“操作和数据路径”。ZK/etcd 提供强一致协调语义，不能和 Redis 缓存互相替代。分布式锁的安全边界不在拿锁，而在 fencing token 从资源层切断旧写。Paxos/Raft 提供共识底座，但不是业务强一致的自动保证。分层一致性把每一层的承诺显式写出来，而不是用一个标签概括整个系统。

把这一切压成最短总图，就是：

```text
业务不变量
  → 数据/操作级一致性 SLA
  → 选择 CP / AP / 最终一致 / 客户端一致
  → 协调服务 / 数据库 / 消息 / 缓存各自承诺
  → 读写路由、重试、幂等、fencing、补偿
  → 故障演练验证用户可见结果
```

所以本篇最该记住的一句话是：**CAP 不是系统级标签，而是按数据、操作和故障场景定义 SLA；一套微服务架构可以同时包含多种一致性模型。**

## 七、几个最容易说错的地方

### 一个系统只能有一种一致性模型？

不是。不同数据和操作对一致性、可用性和延迟的要求不同，可以共存。

### Redis 可以替代 ZooKeeper 做协调？

不是。ZK/etcd 提供顺序、版本、租约和 watch 这些协调语义，Redis 的职责是缓存。

### `SET NX EX` 加上主从主备，就是安全的分布式锁？

不是。锁的安全边界不在拿锁方式，而在失去锁后旧持有者能否继续写资源。

### 用了 Raft 的系统，业务查询就是强一致的？

不是。共识只保证复制日志的一致，上层读路径、缓存和事务隔离级别仍决定用户看到什么。

### 架构的强一致就是靠 `R+W>N` 保证的？

不是。`R+W>N` 只是必要条件，实际语义还取决于副本版本、冲突策略和线性化定义。

## 收束：架构的一致性不是“选一个标签”，而是“为每一条数据路径写一份承诺”

回到开头那个问题：8 个服务同时使用不同一致性模型的系统，为什么这不矛盾。答案已经闭环了：因为它们服务的是不同的业务不变量。配置中心需要强一致和顺序，缓存可以接受短暂旧读，核心事务需要强一致或幂等补偿，消息队列提供分区内有序。架构设计之所以能把这些差异放在一起，不是因为“允许混乱”，而是因为每条数据路径的一致性边界都被显式声明了。

这就是为什么说：**CAP 不是系统级标签，而是按数据、操作和故障场景定义 SLA；一套微服务架构可以同时包含多种一致性模型。** 只要这条主线站稳，下一篇进入缓存策略时，你就不会再把缓存看成“存一份数据给另一个服务加速”，而会自然去问：缓存层的一致性承诺是什么，缓存与数据库之间的边界如何设计失效、更新和回源。
