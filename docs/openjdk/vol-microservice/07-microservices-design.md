# 微服务边界设计：什么时候拆分，什么时候只是制造分布式单体

## 现在真正该问的，不再是“服务拆了多少个”，而是“每个服务是不是真的能独立部署、独立扩容、独立交付，并且跨服务依赖是可控制的”

前几篇已经把通信、服务治理、缓存、消息、存储都讲清楚了。但很多团队在推进微服务架构时，最后碰到的最棘手的问题不是“技术栈选哪个”，而是：

“拆了 20 个服务，改一个订单接口要通知 3 个团队，每次上线要协调 5 个服务的版本——这到底比单体好在哪？”

这正是微服务拆分最容易被忽视的门槛：**如果服务之间强同步依赖、共享数据库、必须同批发布，那就只是把单体部署架构切成了分布式单体，并没有获得微服务应有的收益。**

所以微服务设计的第一步，不是“选 RPC 框架”或“画架构图”，而是先问清楚：一个服务是不是真的能独立改变、独立部署、独立扩容，并且它的数据归属是清晰的。

先把总图记住：

```text
业务语言/数据 owner
  → bounded context/aggregate 边界
  → 独立部署/扩容/团队验证
  → RPC/event/API 契约
  → 网关/BFF 适配
  → 观察同步依赖、事务和故障传播
  → 不满足边界时合并服务
```

这篇最该先记住的一句话是：**微服务拆分的成功标准不是服务数量，而是边界内聚、数据归属清晰、独立交付和可控制的跨服务依赖。**

## 一、单体与微服务：不是二选一，而是组织和变化问题

### 1. 最朴素的错误世界：服务越多，架构越先进

这个误解在“微服务 = 先进”的宣传下非常普遍。但每一个服务都增加：

- 部署单元；
- 监控和告警；
- 网络和权限边界；
- 版本和兼容性管理；
- 跨服务故障排查。

所以服务数量本身不是目标，只有当服务能带来独立发布、独立扩容和团队自治时，数量才有意义。

### 2. 单体/微服务/绞杀者迁移的最小图

```text
模块化单体:
  一个部署单元
  → 进程内调用/本地事务
  → 运维简单
  → 独立扩容/发布边界较弱

微服务:
  多部署单元/独立数据边界
  → 独立发布/扩容/团队自治
  → RPC/监控/配置/故障/分布式事务成本

绞杀者迁移:
  新功能先落在新服务
  → 旧单体边界逐步替换
  → 避免一次性重写/大爆炸迁移
  → 把迁移风险拆成可回滚的小步
```

### 3. 为什么“服务越多越先进”是错的

因为每个服务都增加运维、监控、网络、版本和故障边界。如果服务之间：

- 强同步依赖；
- 共享数据库；
- 必须同时发布；

那就只是分布式单体，不是微服务。服务数量应该服从变化边界和团队交付能力，而不是技术时髦度。

### 4. 本节最该记住的结论：微服务的收益来自独立发布、扩容、团队自治和数据边界，代价是网络、运维和一致性复杂度；不满足这些条件时，模块化单体可能是更好的选择

一句最短人话是：**微服务拆分像把一座工厂分成多个车间；车间能独立换班和扩容，但原料、运输和总装协调会变复杂。**

## 二、DDD、数据边界与变化频率：以高内聚而不是用户量拆分

### 1. 第二个朴素误解：按数据库表机械拆分，把 order 表放到 order 服务，user 表放到 user 服务，自然就是微服务

这个想法在“按表分配”的层面很直观，但它忽略了服务边界真正的核心：**业务语言、事务边界、数据所有权和变化频率。** 这里要补一句 06 篇的衔接：如果拆分同时伴随分库分表，服务边界错误和数据边界错误会叠加放大，两个问题一起更难收拾。

### 2. 拆分的最小判定图

```text
DDD:
  bounded context → 业务语言/规则边界
  aggregate → 一致性与修改边界
  domain event → 跨边界通知
  → 事件 Schema 本身也是跨边界版本契约

数据驱动:
  一个核心数据由一个服务拥有
  → 其他服务通过 API/event 访问

变化频率:
  高频独立发布/扩容模块
  → 有理由成为独立服务

合理性检查:
  能否独立部署?
  能否独立扩容?
  是否有清晰数据/团队 owner?
  跨服务调用是否会形成强同步链?
```

### 3. 为什么 DDD 聚合不等于“一聚合一个服务”

DDD 的 bounded context 和 aggregate 是业务边界，但服务边界还要考虑：

- 部署单元；
- 团队规模；
- 数据归属；
- 运行依赖。

一个服务可以包含多个聚合，只要这些聚合在业务和数据上合理、且能独立部署。反过来，一个聚合如果变化频率或数据隔离需求很强，也可能拆成独立服务。

### 4. 一个更具体的失败场景：订单和库存互为服务，但每次订单状态变化都要同步改库存

假设：

- 订单服务改了订单状态；
- 库存服务必须同步更新库存锁定；
- 每次修改都要跨服务、跨网络、跨事务；
- 一支发布单要同时改两个服务。

这时你就要问：订单和库存真的是两个独立服务，还是它们其实共享同一个业务边界？如果它们总是同时变化、同时部署，那合并成一个服务可能更简单。

### 5. 本节最该记住的结论：拆分要同时看业务语言、事务边界、数据所有权和变化频率，而不是按用户量或数据库表机械拆分；如果总是同时变化、同时部署，合并可能更健康

一句最短人话是：**DDD 的 bounded context 是起点，但服务边界还要看部署、团队、数据和运行依赖。**

## 三、Spring Cloud、Dubbo 与生态选择：选的是运行体系

### 1. 第三个朴素误解：框架选型就是比 RPC QPS

这个误解在“所有框架都差不多，快慢决定一切”的假设下很常见。但框架选型不只影响 RPC 速度，还影响：

- 注册发现；
- 配置管理；
- 路由和容错；
- 协议和序列化；
- 观测和运维；
- 团队招聘和生态发展。

### 2. 框架选型的最小图

```text
Spring Cloud 体系:
  HTTP/RPC + Gateway/Config/Discovery/Resilience
  → 更贴近 Spring/Web 生态

Dubbo 体系:
  Provider/Consumer/Registry/Protocol/Serialization
  → Java RPC/服务治理能力集中

Alibaba/其他组件:
  Nacos/Sentinel/Seata/RocketMQ 等
  → 统一生态也带来供应商/组件耦合

选择维度:
  语言/协议/延迟/治理/生态/运维/迁移
```

### 3. 为什么“性能更高”不能独立决定框架

因为性能只是选择维度之一。更重要的是：

- 协议的成熟度和跨语言支持；
- 序列化方式和演进能力；
- 运维工具和观测集成；
- 团队生态和招聘难度；
- 供应商锁定和迁移成本。

所以框架选型是一个运行体系的选择，不是单点 benchmark 的胜负。

### 4. 本节最该记住的结论：框架选型不止于 RPC 速度，还影响注册发现、配置、路由、协议、序列化、观测、运维和团队生态；性能只是选择维度之一

## 四、API、网关与 BFF：外部一个接口，内部不必暴露七个服务

### 1. 第四个朴素误解：网关就是一个反向代理，路由一下就行

网关确实承担路由、认证和限流，但这只是它的一部分。网关还经常扮演：

- 协议转换；
- 请求聚合；
- 响应裁剪；
- 版本兼容。

但这里有一个陷阱：如果把领域编排全部放进网关，网关就会变成难以拆分的分布式单体。

### 2. 网关/BFF 的最小图

```text
Gateway:
  path/host → route
  → JWT/auth/rate limit
  → protocol/observability

BFF:
  Web/Android/iOS 各自需要的聚合视图
  → 调多个服务
  → 组合结果/适配字段

API evolution:
  additive change first
  → v1/v2 或兼容字段
  → 灰度/迁移/弃用窗口
```

### 3. 为什么 API 版本兼容是服务边界的一部分

因为服务无法强迫所有调用方同时升级。破坏性变更会沿调用图扩散，导致：

- 调用方必须在同一时间窗口内改完；
- 改不完就报错；
- 跨团队协调成本成倍增长。

所以 API 版本兼容不是“可选的代码细节”，而是服务边界契约的一部分。

### 4. 本节最该记住的结论：网关承担路由、认证、限流和聚合，但不能把领域编排全放进网关；API 版本兼容是服务边界契约的一部分，不是可选的代码细节

## 五、把本篇收成一张图：微服务拆分的成功标准不是服务数量，而是边界内聚、数据归属清晰和独立交付

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：20 个微服务中改一个订单接口要通知 3 个团队，拆分到底带来了什么。答案已经闭环了——如果服务之间强同步依赖、共享数据、必须同批发布，那就只是分布式单体，并没有获得微服务应有的收益。

单体/微服务/绞杀者迁移各有适用场景。DDD 的 bounded context 是起点，但服务边界还要看部署、团队、数据和运行依赖。框架选型是运行体系的选择，不是单点 benchmark 的胜负。网关能聚合但不能过度编排，API 版本兼容是服务边界契约的一部分。

把这一切压成最短总图，就是：

```text
业务语言/数据 owner
  → bounded context/aggregate 边界
  → 独立部署/扩容/团队验证
  → RPC/event/API 契约
  → 网关/BFF 适配
  → 观察同步依赖、事务和故障传播
  → 不满足边界时合并服务
```

所以本篇最该记住的一句话是：**微服务拆分的成功标准不是服务数量，而是边界内聚、数据归属清晰、独立交付和可控制的跨服务依赖。**

## 六、几个最容易说错的地方

### 服务越多，架构越先进？

不是。每个服务增加部署、监控、网络、版本和故障边界，数量必须服从变化边界和团队能力。

### 按数据库表机械拆分就是微服务？

不是。拆分要看业务语言、数据所有权、变化频率和独立部署能力，不是按表分配。

### 框架选型就是比 RPC QPS？

不是。选型是运行体系的选择，还影响注册发现、配置、协议、序列化、观测和团队生态。

### 网关就是路由一下就行？

不是。网关还承担聚合、协议转换、认证和版本兼容，但过度编排会制造新单体。

### API 版本兼容是可选细节？

不是。它是服务边界契约的一部分，破坏性变更会沿调用图扩散。

## 收束：微服务真正的门槛不是“把代码拆开”，而是“拆开后还能独立交付”

回到开头那个问题：20 个微服务中改一个订单接口要通知 3 个团队，拆分到底带来了什么。答案已经闭环了：如果服务之间强同步依赖、共享数据、必须同批发布，那就只是分布式单体，并没有获得微服务应有的收益。微服务拆分的真正目标不是“拆多少”，而是“拆完后每个服务能独立部署、独立扩容、独立交付，并且跨服务依赖是可控制的”。

这就是为什么说：**微服务拆分的成功标准不是服务数量，而是边界内聚、数据归属清晰、独立交付和可控制的跨服务依赖。** 只要这条主线站稳，下一篇进入韧性模式时，你就不会再把限流和熔断看成“独立配置的几个参数”，而会自然去问：当一个服务变慢时，哪些韧性模式能阻断级联故障，它们又分别需要什么代价。
