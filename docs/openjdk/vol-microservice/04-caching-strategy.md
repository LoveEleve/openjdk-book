## 现在真正该问的，不再是“缓存快不快”，而是“缓存把数据复制到了多少层，每一层的失效、延迟和修复路径是什么”

前几篇已经把架构中的一致性语义讲清楚了：CAP 不是系统级标签，而是操作级 SLA。不同数据路径可以选择不同的一致性承诺。

缓存是一致性挑战最集中的地方。因为它做的就是把数据复制到更快、更近的存储层，而**每复制一次，就多一层失效、延迟和修复问题**。

商品价格改了，但 CDN 还在 TTL 内、本地缓存还没过期、Redis 还没收到失效通知，用户看到的仍然是旧价格。这不是“缓存坏了”，而是“失效传播的时间和路径”还没被考虑到。

所以缓存真正的设计问题不是“选哪个缓存最快”，而是：

- 缓存了几层？
- 每层怎么失效？
- 失效传播延迟多少？
- 短暂不一致时用户看到什么？
- 缓存和数据库长期不一致时怎么修复？

先把总图记住：

```text
request
  → CDN/edge?
  → reverse proxy cache?
  → application local cache?
  → Redis/distributed cache?
  → MySQL authoritative data

update:
  DB updated
  → invalidate/refresh Redis
  → invalidate local cache/CDN
  → each layer has its own TTL/propagation delay
```

这篇最该先记住的一句话是：**引入缓存就等于复制数据；每复制一层，就新增一条失效、延迟、故障和修复路径。缓存的正确设计不是追求绝对强一致，而是让不一致窗口、用户语义、兜底和修复都可测量。**

## 一、多级缓存：一次读请求可能经过五个副本

### 1. 最朴素的错误世界：数据在 MySQL 里改了，读请求自然就会拿到新值

这个想法在只有一个数据库的情况下成立，但一旦引入缓存，情况就完全不同。

一个典型的商品详情请求，在到达 MySQL 之前可能经过：

- CDN 边缘节点；
- 反向代理缓存（如 Nginx）；
- 应用本地缓存（如 Caffeine）；
- 分布式缓存（如 Redis）。

每一层都有可能返回旧值。所以“MySQL 已经更新了”不等于“用户看到了新值”。

### 2. 多级缓存的最小读路径图

```text
request
  → CDN/edge?
  → reverse proxy cache?
  → application local cache?
  → Redis/distributed cache?
  → MySQL authoritative data

update:
  DB updated
  → invalidate/refresh Redis
  → invalidate local cache/CDN
  → each layer has its own TTL/propagation delay
```

### 3. 为什么不像 CPU cache 一样在所有业务缓存上实现全局一致协议

CPU cache 可以在硬件层面维护缓存一致性协议（MESI 等），但业务缓存不行：

- 缓存层跨进程、跨机器、跨供应商和跨网络；
- 失效消息本身可能延迟、丢失或重复；
- 没有全局总线和共享时钟。

所以工程上通常选择明确的最终一致窗口、TTL、版本号和对账，而不是为每层维持昂贵的全局序。

### 4. 本节最该记住的结论：缓存层越多，读延迟越低的机会越大，但一致性和失效传播越复杂；工程上不追求硬件级缓存一致性，而是设计可测量的失效窗口和修复路径

一句最短人话是：**多级缓存像多地书店都存了一本商品目录；总部改价后，要通知每家书店换页，任何一家延迟都会让顾客看到旧价格。**

## 二、Redis：数据结构、持久化和高可用是三种不同能力

### 1. 第二个朴素误解：Redis 只是一个“更快的 Map”

这个误解忽略了 Redis 的三个关键能力：

- 丰富的数据结构；
- 持久化策略；
- 高可用/集群方案。

这三者分别解决不同问题，但很多人把它们混成一个“快”字。

### 2. Redis 的三层能力图

```text
数据结构:
  String/Hash/List/Set/ZSet
  HyperLogLog/Bitmap/Geo 等

持久化:
  RDB snapshot
  AOF command log
  混合/配置策略

高可用:
  replication
  Sentinel failover
  Cluster sharding

使用前:
  明确数据丢失窗口、故障切换、淘汰和内存上限
```

### 3. 为什么 Redis“快”不能简单归因于单线程

单线程是 Redis 架构的一个特征，但不是“快”的唯一原因。真正让 Redis 快的是：

- 内存数据结构；
- 高效的 I/O 多路复用；
- 命令复杂度低。

但单线程也意味着：慢命令会阻塞其他命令，持久化 fork 会影响响应时间，热点 key 竞争会降低吞吐。

所以 Redis 的“快”需要一个更完整的解释：它快在内存和事件循环，但单线程也限制了它的并发模型和命令复杂度。

### 4. 本节最该记住的结论：Redis 的价值来自数据结构、内存模型和高可用/持久化三者的组合；使用前必须明确数据丢失窗口、故障切换行为和内存上限

一句最短人话是：**Redis 像前台高速货架，取货快但容量有限；RDB/AOF 是库存快照/流水，Sentinel/Cluster 是备用店和分仓。**

## 三、Cache Aside、Read/Write Through、Write Behind：谁负责一致性

### 1. 第三个朴素误解：先写数据库再删缓存，就不会有一致性问题

先写 DB 再删缓存确实是最常用的模式，但它仍然存在短暂的不一致窗口：

- 线程 A 写 DB；
- 线程 A 删缓存；
- 线程 B 并发读，缓存未命中，回源到 DB 读旧值。

如果再遇到“先删缓存再写 DB”的误操作，窗口还会更大。

所以缓存更新模式的选择，本质上是“谁负责缓存和数据库之间的一致性，以及愿意接受多长的窗口”。这里要先把两条容易混淆的路径分开：`Cache Aside` 的标准路径是“先写 DB 再删缓存”，并发读仍可能在删缓存之前读到旧值并写回；而“先删缓存再写数据库”是另一种更脆弱的写法——它在缓存删除到数据库提交之间留有更大窗口，更容易让旧值长期驻留，通常被当作反模式而不是推荐方案。

### 2. 三种缓存更新模式的最小图

```text
Cache Aside:
  read miss → 应用读 DB → 写 cache
  update → 应用写 DB → invalidate cache

Read/Write Through:
  应用调用 cache
  → cache 层负责回源/写 DB

Write Behind:
  应用先写 cache
  → cache 异步批量写 DB
  → 性能高, 崩溃/丢失/延迟风险更高
```

### 3. 为什么延时双删不是严格一致方案

延时双删的做法是“写 DB → 删缓存 → 等 N 秒 → 再删一次”。这个方法依赖“延时足够覆盖并发读写窗口”的经验假设。但慢请求、长事务、GC 暂停、网络抖动都可能超出估计。

所以延时双删是一种工程经验，不是可验证的一致方案。版本号、消息失效和对账比单纯 sleep 更可验证。

### 4. 一个更具体的失败场景：先删缓存再写数据库，并发读在缓存删除后回源读到旧值

假设（注意：这里说的是反模式，不是推荐的 Cache Aside 标准路径）：

- 缓存 key 被删除；
- 一个并发读请求在写数据库之前回源到 DB，读到旧值；
- 然后把旧值写回缓存；
- 新值写入 DB 后，缓存里已经存了旧值。

这时就出现了“缓存长期存旧值”的问题。它和 Cache Aside“先写 DB 再删缓存”里那个更短的并发窗口并不是同一回事。先写 DB 再删缓存可以减少这个窗口，但不能完全消除。

### 5. 本节最该记住的结论：不同的缓存更新模式把一致性责任分配给不同角色；没有一种模式能完全消除不一致窗口，关键是让窗口可测量、可修复

一句最短人话是：**Cache Aside 像应用自己管理书店库存；Through 像仓库管理员统一补货；Write Behind 像先在前台记订单、晚些时候再入总账，速度快但断电风险更大。**

## 四、binlog、消息、TTL 与对账：把缓存最终修回来

### 1. 第四个朴素误解：删了缓存，下次读就能拿到最新值

这个说法在“删缓存 → 下次读回源到 DB”这个路径上是对的，但它忽略了：

- 删缓存操作本身可能失败；
- 应用更新数据库后，删缓存之前进程崩溃；
- 缓存还可能有 CDN 和本地缓存等多层副本。

所以需要一个更可靠的机制来修复缓存和数据库之间的差异。

### 2. binlog 异步失效的最小图

```text
DB transaction commit
  → binlog
  → CDC/Canal parser
  → cache invalidation topic
  → consumer DEL/refresh key

失败防线:
  message retry/idempotency
  Redis TTL
  periodic reconciliation(DB vs cache)
  version/timestamp check

最终一致窗口:
  DB commit → event delivery → cache consumer
  + retry/backoff + TTL/repair delay
```

### 3. 为什么 binlog 异步失效仍不能承诺 100% 强一致

因为：

- CDC 可能失败或延迟；
- MQ 可能积压；
- 消费者可能崩溃；
- 更上层的 CDN 和本地缓存还可能保留旧值。

所以可靠系统不是假装没有窗口，而是把窗口、重试、TTL、对账和告警明确化。

### 4. 本节最该记住的结论：binlog 异步失效是一个可靠的兜底机制，但它不消除不一致窗口，而是把窗口、重试、TTL 和对账变成可管理的系统组件

一句最短人话是：**binlog 是总部出库流水，消息是通知各门店换价签；通知失败时 TTL 是自动过期，对账是夜间盘点。**

## 五、雪崩、穿透、击穿与热点：四类缓存故障不是一回事

### 1. 第五个朴素误解：给 Redis 加节点就能解决所有缓存问题

扩容可以改善容量，但缓存故障不都是容量问题：

- 雪崩是时间集中；
- 穿透是无效请求；
- 击穿是单 key 重建竞争；
- 热点是访问分布偏斜。

所以防御方案必须区别对待，不能靠一招打天下。

### 2. 四类故障的最小防御图

```text
雪崩:
  大量 key 同时过期/缓存集群故障
  → TTL jitter/预热/多级缓存/限流/降级

穿透:
  查询大量不存在 key
  → 空值短 TTL/Bloom filter/参数校验

击穿:
  一个热点 key 过期
  → singleflight/互斥重建/逻辑过期

热点:
  单 key/分片被极高频访问
  → 本地缓存/热点副本/分片散列/限流
```

其中 singleflight/互斥重建把并发回源合并成一个请求，代价是其他请求被串行等待；逻辑过期则人为在 key 里保留一个过期时间，返回旧值的同时后台异步刷新，代价是用户短暂读到更加过期的数据。两种方案都减少回源竞争，但分别引入请求串行或旧值窗口，不是零成本的。

### 3. 为什么不能用“加 Redis 节点”解决所有缓存问题

因为四类故障的触发机制不同：

- 雪崩：大量 key 同时过期，与节点数量无关；
- 穿透：查询不存在 key，节点再多也挡不住；
- 击穿：单个热点 key 重建，与总容量无关；
- 热点：访问分布集中在少数 key，加节点反而可能放大跨分片开销。

所以防御方案必须和限流、熔断、降级、消息和数据库容量一起设计。

### 4. 本节最该记住的结论：雪崩、穿透、击穿和热点是四种不同触发机制的缓存故障，必须用不同防线分别防御；扩容能改善容量，不能自动解决回源风暴、重建竞争和恶意参数

## 六、把本篇收成一张图：引入缓存就等于复制数据，每层都需要设计失效、修复和兜底

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：MySQL 价格已经更新，页面却仍显示旧价格。答案已经闭环了。

多级缓存让一次读请求可能经过 CDN、代理、本地缓存、Redis 和 DB 五层，每层都有自己的 TTL 和失效传播延迟。Redis 的价值来自数据结构、内存模型和高可用/持久化的组合。缓存更新模式把一致性责任分配给不同角色。binlog 异步失效、TTL 和对账构成多层防线。雪崩、穿透、击穿和热点需要分别防御。

把这一切压成最短总图，就是：

```text
write DB
  → commit/binlog
  → invalidate Redis/local/CDN
  → read miss 回源 DB
  → 重建 cache
  → TTL/对账修复残留差异
```

所以本篇最该记住的一句话是：**引入缓存就等于复制数据；每复制一层，就新增一条失效、延迟、故障和修复路径。缓存的正确设计不是追求绝对强一致，而是让不一致窗口、用户语义、兜底和修复都可测量。**

## 七、几个最容易说错的地方

### 缓存层越多，读越快，一致性也越容易保证？

不是。缓存层越多，读延迟越低的机会越大，但失效传播和修复路径也越复杂。

### Redis 快只是因为单线程？

不是。单线程是特征，但快的真正原因是内存数据结构和高效 I/O 多路复用。

### 先删缓存再写数据库的窗口很小，不会出问题？

不一定。并发读可能在缓存删除后、写数据库前回源到旧值，旧值可能被写回缓存。

### binlog 异步失效能保证 100% 强一致？

不是。CDC、MQ 和消费者都可能失败或延迟，CDN 和本地缓存还可能在更上层保留旧值。

### 加 Redis 节点就能解决所有缓存故障？

不是。雪崩、穿透、击穿和热点的触发机制不同，需要分别防御。

## 收束：缓存的价值在于“更快”，但代价是“多一份副本，多一份失效和修复路径”

回到开头那个问题：MySQL 价格已经更新，页面却仍显示旧价格。答案已经闭环了：因为缓存把数据复制到了多层，每一层都有自己的 TTL 和失效传播延迟。缓存设计的核心不是“用哪个缓存最快”，而是“缓存了哪些层、每层怎么失效、失效的窗口多大、长期不一致时怎么修复”。

这就是为什么说：**引入缓存就等于复制数据；每复制一层，就新增一条失效、延迟、故障和修复路径。缓存的正确设计不是追求绝对强一致，而是让不一致窗口、用户语义、兜底和修复都可测量。** 只要这条主线站稳，下一篇进入消息驱动时，你就不会再把消息队列只看成“解耦工具”，而会自然去问：消息队列的削峰、重复消费、顺序消费和最终一致边界如何与缓存层和数据库层一起设计。
