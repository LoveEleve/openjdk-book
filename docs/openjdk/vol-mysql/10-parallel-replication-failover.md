## 现在真正该问的，不再是“副本有没有跟上”，而是“副本为什么跟不上，哪些事务可以并行，哪些事务必须等，切换时哪个副本才真正拥有完整世界”

上一篇已经把复制的五段接力讲清楚了。你已经知道：

- 主库提交后，binlog 事件经过 DUMP / IO thread / Relay Log / SQL thread 五段接力才到达副本回放；
- 位点和 GTID 分别用文件和集合描述进度；
- 半同步在异步基础上增加 ACK 等待；
- `Seconds_Behind_Master` 是近似信号，不是精确的“副本已追上”的证明。

如果只停在这里，你可能会形成一层自然但危险的半结论：

“副本跟不上，那就多开几个线程，让回放并行起来。”

这个直觉的方向是对的，但真实世界里的并行回放没有这么简单。因为副本不能随便把任意两个事务拿来并行回放。它必须回答：

- 这两个事务修改了同一行吗？
- 它们有没有提交顺序依赖？
- 并行回放时，检查点和崩溃恢复怎么保证不丢不重？
- 延迟指标到底该看哪一段？

而故障切换又会进一步追问：

- 候选副本的事务集合到底全不全？
- 它是过滤副本、延迟副本，还是全量副本？
- 切换后，剩下的副本指向新主时，GTID 集合会不会有问题？

所以本篇先回答并行回放，再回答故障切换。

先把总图记住：

```text
主库提交
  → binlog / GTID
  → DUMP / IO thread / Relay Log
  → Coordinator 判断依赖并分发到 Worker
  → Worker 并行回放
  → 提交顺序推进 / checkpoint
  → GTID executed / 延迟观测
  → 故障切换时用 GTID 集合 + 角色语义决定晋升
```

这篇最该先记住的一句话是：**并行复制的本质不是“多开几个线程”，而是“在不破坏依赖和提交顺序的前提下最大化并行度”；故障切换的本质不是“切得最快”，而是“确认事务集合和角色语义后选择最完整的副本”。**

## 一、DATABASE 与 LOGICAL_CLOCK：并行回放的第一前提，不是“开了多少线程”，而是“哪些事务被证明彼此不冲突”；WRITESET 只是 LOGICAL_CLOCK 模式下的一种增强

### 1. 最朴素的错误世界：副本回放慢，就把并行线程数开大，自然就追上

这几乎和“优化 SQL 慢 → 加更多连接”是同一个心态：把问题简化成“资源不够，多加资源就好”。

但副本回放慢的核心，往往不是“线程不够”，而是“事务之间有依赖，无法并行”。如果两个事务都修改同一行，它们必须按顺序回放，不能随机并发。如果两笔事务之间在逻辑上必须保持提交顺序，副本也不能随意颠倒它们的可见顺序。

所以并行回放的本质不是“并行”，而是“证明哪些事务可以并行”。

### 2. DATABASE：按库分桶，最简单但最粗的并行策略

`DATABASE` 模式把事务按所在数据库（schema）分桶：

- 不同库的事务可以并行；
- 同库内仍然串行化。

```text
事务修改 db1.t1
  → 分发到 worker A
事务修改 db2.t2
  → 分发到 worker B
A 和 B 可以同时回放
```

它在多租户、多 schema 的场景下很有效，但单库高负载时并行度几乎为零。

### 3. LOGICAL_CLOCK：利用主库组提交信息，让同一批次内的事务可并行

这是更精细的并行策略。主库在 Group Commit 时，会给每笔事务打上 `last_committed` / `sequence_number` 等依赖信息。副本收到这些信息后，可以判断：

- 如果两笔事务的 `last_committed` 指向同一批已完成的事务，且它们之间没有隐含依赖，那么它们可以并行回放。

```text
事务 A：last_committed=5, sequence_number=6
事务 B：last_committed=5, sequence_number=7
→ A 和 B 可以并行

事务 C：last_committed=7, sequence_number=8
→ C 必须等 A 和 B 都完成后才能开始
```

这个策略的关键在于：它依赖的“主库提交时的依赖关系”，而不是副本自己猜测。所以并行度取决于主库的组提交行为和工作负载，不取决于副本的线程数。

### 4. WRITESET：在 LOGICAL_CLOCK 基础上进一步判断写集合是否冲突

`WRITESET` 更进一步：它不只依赖主库的提交顺序，还根据事务的写集合（修改了哪些行/键）来判断两个事务是否真正冲突。这里要先纠正一个非常关键的事实边界：**在 MySQL 8.x 里，`slave_parallel_type`/`replica_parallel_type` 其实只有 `DATABASE` 和 `LOGICAL_CLOCK` 两个取值；WRITESET 并不是第三种 parallel_type，而是 `LOGICAL_CLOCK` 模式下、配合 `transaction_write_set_extraction` 启用后才生效的写集合依赖增强。** 所以正文不再把它叫成“第三种模式”，而是把它理解成“LOGICAL_CLOCK 的一种增强路线”。

- 如果两笔事务的写集合没有交集，且没有其他依赖约束，那么它们可以并行；
- 如果写集合有交集，即使它们属于同一组提交批次，也必须串行。

```text
事务 A：修改行 id=1
事务 B：修改行 id=2
→ 写集合不冲突，可以并行

事务 C：修改行 id=1
→ 写集合与 A 冲突，必须等 A 完成
```

WRITESET 的并行度通常比纯粹的 LOGICAL_CLOCK 更高，但它依赖主键/唯一键来提取写集合，并且必须真正启用 `transaction_write_set_extraction`（例如 `XXHASH64` 或 `MURMUR32`）。如果这个开关没开，写集合依赖根本不会生效；如果表没有主键，WRITESET 也可能无法有效提取冲突信息，从而退化为更低的并行度。

### 5. 为什么并行度不是“副本线程数”，而是“证明事务不冲突”

三种模式的共同底线是：

- 并行回放的前提是证明事务不冲突；
- 线程数只是执行资源，不是并行度的来源；
- 如果事务之间全部有依赖，即使开 100 个 worker，也只能串行执行。

### 6. 一个更具体的失败场景：单表高并发写入，DATABASE 和 LOGICAL_CLOCK 都并行不起来

假设业务全部在同一个数据库里，而且全部写入同一张热点表：

- `DATABASE` 模式：所有事务都在同一个 db 桶里，串行。
- `LOGICAL_CLOCK` 模式：主库组提交时可能把多个事务标记为同一批，但它们在副本回放时因为共享同一行，仍然需要 Lock 等待，无法真正并行。
- `WRITESET` 模式：如果表有主键，同一行的事务仍然冲突，无法并行；不同行的事务可以并行。

所以真正决定并行度的，不是“你配了多少 worker”，而是“你的业务负载里，有多少事务是真的不冲突的”。

### 7. 本节最该记住的结论：8.x 的并行类型主要是 `DATABASE` 与 `LOGICAL_CLOCK`；WRITESET 是 `LOGICAL_CLOCK` 模式下开启写集合依赖的增强，而不是第三种独立 parallel_type。DATABASE 按库、LOGICAL_CLOCK 按提交依赖、WRITESET 进一步按写集合碰撞证明事务不冲突；并行度来自证明独立性，不是盲目开更多线程

一句最短人话是：**并行回放像仓库拆单：不同楼层的订单、同一批同时付款的订单、彼此不抢同一货架的订单，可以交给不同工人；真正抢同一货架的仍得排队。**

## 二、MTS：Coordinator 分发、Worker 回放与提交顺序，并行复制真正的运行时

### 1. 第二个朴素误解：打开并行复制后，事务就被自动均匀分配到所有 worker 上了

这只是最理想的情况。真实 MTS 运行时，Coordinator 需要：

- 读取 relay log 中的事务边界；
- 根据并行策略判断依赖并决定分配到哪个 worker；
- 监控 worker 完成进度；
- 在需要时执行 checkpoint 推进回放进度。

Worker 也不是“收到事务就执行，完全不考虑别人”。它们还要：

- 在启动事务前确认依赖是否满足；
- 在执行过程中保持提交顺序；
- 在完成后上报进度，供 Coordinator 做 checkpoint。

### 2. Coordinator 不是“随机分发”，而是“按依赖关系分配”

MTS 的 coordinator 并不总是把下一笔事务直接丢给空闲 worker 就完事。它需要先判断：

- 这笔事务依赖哪些更早的事务；
- 这些依赖事务是否已经在某个 worker 上完成；
- 如果尚未完成，当前事务必须等待。

这个过程在 `wait_for_last_committed_trx()`（`sql/rpl_mta_submode.cc:515`）这类路径中体现。它不是简单的轮询，而是依赖等待。

### 3. Worker 要维护提交顺序，不能因为并行就乱序提交

并行回放虽然允许事务并行执行，但副本往往还要保持提交顺序与主库一致。`slave_preserve_commit_order` 这类配置就是用来控制这个行为的：

- 开启时，事务提交顺序与主库一致，但可能降低并行度；
- 关闭时，并行度更高，但提交顺序可能和主库不同。

这里没有“哪个方案绝对正确”，只有“业务是否关心副本上事务的提交顺序与主库一致”。

### 4. Checkpoint 与崩溃恢复：MTS 恢复时的逻辑和单线程不同

MTS 的日志位置推进不是单个事务一笔一笔落盘，而是由 coordinator 在确认所有 worker 都已经完成到某个安全位置后，再推进 checkpoint。

如果副本在 checkpoint 之后崩溃：

- 重启后，MTS 从 checkpoint 位置开始读取 relay log；
- 已经完成但 checkpoint 尚未推进的事务，会交给 MTS recovery 协议来处理：它会依靠 worker checkpoint、low-watermark 和 worker 回滚重放，尽量只把“可能需要重放”的事务再执行一遍；
- 在常规行事件下这种重放通常是可接受的，但不要把“通常可接受”写成“天然幂等不会错”——若 `slave_exec_mode` 未设为 `IDEMPOTENT`，或副本上有触发器、statement event、非确定性 SQL，重放并不总是无害。
- `mts_recovery_groups()`（`sql/rpl_replica.cc:6210`）和 `mts_finalize_recovery()`（`sql/rpl_rli.cc:431`）这类路径正是处理 MTS 恢复时的事务边界与 worker 协调的。

### 5. 一个更具体的失败场景：worker 数量增加后，吞吐反而下降

假设你开了 8 个 worker，但所有事务都依赖同一行：

- 所有事务都必须等前一个完成后才能开始；
- 7 个 worker 在空转，只有 1 个在工作；
- 额外的上下文切换和协调成本反而让吞吐下降。

这时你看到的不是“并行度提升”，而是“同样的事，花了更多协调成本”。

### 6. 本节最该记住的结论：MTS 运行时包括 Coordinator 依赖分发、Worker 回放与提交顺序、Checkpoint 推进和崩溃恢复；并行度不仅取决于依赖，还受 worker 数量和提交顺序约束影响

一句最短人话是：**MTS 像总调度员给多个工位发工单，工位数量变多并不保证整体更快；如果所有工单都依赖同一前置步骤，其他工位仍会空转。**

## 三、延迟指标与 Relay 基础设施：SBM 只是一个近似，真正的延迟分析要拆成四段

### 1. 第三个朴素误解：`Seconds_Behind_Master = 0` 就说明副本和主库完全一致

这一条在 09 篇已经讲过，但并行复制的场景下更复杂。因为 MTS 下：

- 某些 worker 可能已经提交，某些还在等待；
- 提交顺序可能和主库不同；
- SBM 的计算方式基于 SQL thread 当前执行的事件时间戳，但 MTS 下 SQL thread 是 coordinator，它可能已经读到了更靠后的事件，但 worker 还在回放之前的事务。

所以 SBM 在 MTS 下不是更精确，而是更模糊。

### 2. 延迟至少可以拆成四段

更可靠的延迟分析，至少要把“主库生成”、“网络传输”、“Relay 落盘”、“applier 执行”四段拆开：

- 主库生成：事务从提交到写入 binlog 的时间；
- 网络传输：DUMP 到 IO thread 接收的时间；
- Relay 落盘：IO thread 接收后写入 relay log 的时间；
- Applier 执行：coordinator 依赖判断 + worker 回放 + 提交等待的时间。

### 3. Relay Log 基础设施不只是文件，还包括 master/replica info 和 recovery 策略

Relay Log 不只是 IO thread 写入、SQL thread 读取的中间文件，它还包括：

- 记录 IO thread 和 SQL thread 进度的元信息文件；
- 崩溃恢复时，`relay_log_recovery` 是否丢弃未完成的 relay log；
- MTS 下，checkpoint 位置和 worker 完成状态。

### 4. 为什么大事务在 MTS 下仍然可能堵住所有 worker

大事务的 binlog event 很大，无论它分配到哪个 worker：

- 该 worker 需要很长时间回放；
- 其他 worker 如果依赖它，也必须等待；
- 即使不依赖，coordinator 可能因为 checkpoint 推进策略而等待所有 worker 完成。

所以大事务在 MTS 下的延迟问题，不是“并行能解决的”，而是“大事务的 binlog 传输和回放占用了大量时间”。

### 5. 本节最该记住的结论：SBM 在 MTS 下不是更精确，而是更模糊；真实延迟分析要拆成四段，Relay 基础设施包括文件、元信息和恢复策略，大事务在 MTS 下仍然可能堵住所有 worker

一句最短人话是：**SBM 像航班预计晚点分钟数；归零不代表行李、乘客和清洁都同步完成，只表示当前估算看起来已经追平。**

## 四、多源、过滤与延迟复制：复制拓扑的运维扩展，但同时改变了“副本是否代表主库”的含义

### 1. 第四个朴素误解：多源、过滤和延迟复制只是“功能扩展”，不影响故障切换的可用性

这是运维里最危险的理解之一。多源、过滤和延迟复制确实带来了很多灵活性，但它们也改变了副本的事务完整性和故障切换可用性：

- 过滤副本只包含主库的部分数据，不能直接晋升为完整主库；
- 延迟副本的事务可能落后很久，不适合实时读；
- 多源副本有自己的事务集合，和主库不是一一对应关系。

所以不能把“副本”当成一个统一的概念。要区分全量副本、过滤副本、延迟副本和多源副本，它们各自的事务集合和可用性不同。

### 2. 多源复制：同一个副本从多个主库拉取数据

多源副本通过 channel 隔离每个主库的复制链路：

- 每个 channel 有独立的 IO thread 和 relay log；
- applier 可以共享或独立，取决于配置；
- 每个 channel 的 GTID 集合是独立的，不能混用。

### 3. 复制过滤：副本只应用部分对象

复制过滤通过 `replicate_do_db`、`replicate_ignore_db`、`replicate_do_table` 等配置实现。它适用于：

- 将部分表从主库复制到副本；
- 减少副本的存储和回放压力；

但故障切换时，过滤副本的事务集合不完整，不能直接晋升。

### 4. 延迟复制：人为推迟事务的应用时间

延迟复制通过 `CHANGE MASTER TO MASTER_DELAY=N` 实现：

- 副本接收到事务后，等待 N 秒再开始回放；
- 如果主库发生了误操作，这个窗口就是恢复时间；
- 但延迟副本对实时业务不可替代，也不能直接晋升。

### 5. 一个更具体的失败场景：故障切换时错误晋升了过滤副本，导致数据丢失

假设：

- 全量副本 A 和过滤副本 B；
- 主库故障后，运维误将 B 晋升为新主库；
- B 只包含部分表，其他表的数据完全丢失；
- 应用开始读写新主库，发现数据不完整，但已经无法回退。

这不是 B 的“复制延迟”问题，而是 B 的“事务集合”问题。B 从来就不包含完整的数据。

### 6. 本节最该记住的结论：多源、过滤和延迟复制改变了副本的语义和可用性；故障切换时必须区分副本的类型和事务集合，不能把过滤副本当成全量副本晋升

一句最短人话是：**普通副本像主仓镜像，多源副本像几个仓库汇总报表，延迟副本像保险箱里的历史快照；用途不同，不能互相替代。**

## 五、Failover 与复制恢复：选对副本比“最快切”更重要

### 1. 第五个朴素误解：故障切换时，选延迟最小的副本晋升就对了

延迟最小当然有帮助，但它不是充分条件。你需要确认：

- 候选副本的 GTID executed 集合是否完整；
- 候选副本是否有过滤、延迟或只读限制；
- 候选副本的 relay log 是否已经回放完毕；
- 半同步下，主库 ACK 的事务是否已经到达并回放。

### 2. 故障切换的核心是事务集合，不是延迟

GTID 让事务集合的对比变得简单：

- 副本发送自己的 `gtid_executed` 集合；
- 候选副本之间对比集合，选最完整的；
- 如果候选副本的集合缺失某些事务，需要从其他副本补齐。

这里必须再补一个最容易翻的边界：**候选副本“真正可用”的事务集合，应以 `gtid_executed` 减去 `gtid_purged` 后的结果为准。** 因为 `gtid_purged` 里的事务已经被宣告不再需要或已经无法再补；如果某些事务已经被 purged，它们几乎不可能从任何现有副本找回。切换选型时只对比 `gtid_executed`，会把一段“已经不可补齐”的空洞误当成完整集合。

```text
故障发生
  → 冻结原主
  → 检查候选副本：
      GTID executed 集合
      relay / worker 状态
      半同步 / 提交边界
      只读 / 过滤 / 延迟属性
  → 选择最完整且语义合适的副本晋升
  → 其他副本重新指向新主
  → 校验缺失事务 / 补偿 / 一致性
```

### 3. 为什么半同步的 ACK 不能代替事务集合检查

半同步的 ACK 只说明主库提交时至少有一个副本收到了 binlog 事件。但：

- 这个副本可能因过滤、延迟或配置而不适合晋升；
- 主库在 ACK 之后、副本回放之前宕机，ACK 窗口内的副本可能还未回放；
- 切换时仍然需要结合 GTID executed 集合判断。

### 4. 为什么切换后要防止双主写

故障切换时，如果原主库最终恢复并重新加入集群，而新主库已经接受了一部分写入，两者可能产生冲突数据。这就是为什么故障切换时通常需要：

- 确认原主库已经停止业务写入，并通过 `read_only`/`super_read_only` 等机制把它真正冻结成只读；
- 区分两件事：`SET sql_log_bin=0` 控制的是这之后的语句是否写 binlog，不是“禁止这台实例被写入”；防双主写/脑裂的主防线是停止应用写 + 原主隔离 + 只读锁，不能把两者说成同一件事；
- 确认所有副本都指向新主库，而不是继续指向原主库。

### 5. 一个更具体的失败场景：切换后，一部分副本的 GTID 集合比新主库还大，导致复制断裂

假设：

- 主库 A，副本 B 和 C；
- A 故障后，B 晋升为新主库；
- C 在切换时尚未完成 A 的某些事务；
- C 指向新主库 B 时，发现 C 的 GTID 集合中某些事务在 B 上不存在；
- C 认为这些事务是“缺失的”，但 B 无法提供它们，复制断裂。

这种情况在切换前必须检查候选副本的 GTID 集合是否完整，或者通过其他手段补齐。

### 6. 本节最该记住的结论：故障切换的核心不是切换速度，而是确认候选副本的事务集合、角色语义和恢复窗口；GTID 让集合对比更方便，但不能替代集合维护和故障演练

一句最短人话是：**切换不是“谁最快”，而是“谁最完整”。**

## 六、把本篇收成一张图：并行复制的前提是证明事务不冲突，故障切换的前提是确认事务集合

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：副本为什么跟不上，并行复制为什么不总是生效，故障切换时选哪个副本。答案已经闭环了。

并行复制的本质，不是“多开 worker”，而是“证明事务彼此不冲突”。DATABASE、LOGICAL_CLOCK、WRITESET 分别从库、提交依赖和写集合碰撞三个层次提供证明。MTS 运行时把依赖判断、worker 回放、提交顺序和 checkpoint 组织成一套可运行的框架。但并行度仍受业务负载特征和提交顺序约束的限制。

故障切换的核心则不是“切得最快”，而是“选最完整的副本”。GTID 让事务集合的对比变得简单，但过滤副本、延迟副本和多源副本各有不同的事务集合，不能混淆。

把这一切压成最短总图，就是：

```text
主库提交
  → binlog / GTID
  → DUMP / IO / Relay
  → Coordinator + Worker 并行回放
  → GTID executed 推进
  → SBM / 四段延迟分析
  → 多源 / 过滤 / 延迟改变语义
  → failover 以事务集合和角色语义为准
```

所以本篇最该记住的一句话是：**并行复制的本质不是“多开几个线程”，而是“在不破坏依赖和提交顺序的前提下最大化并行度”；故障切换的本质不是“切得最快”，而是“确认事务集合和角色语义后选择最完整的副本”。**

## 七、几个最容易说错的地方

### 并行回放是不是 worker 越多越好？

不是。并行度来自事务依赖，不是 worker 数量。worker 太多反而可能增加协调成本和上下文切换。

### DATABASE 模式是不是适合所有场景？

不是。它只适合多 schema 场景，单库下并行度几乎为零。

### LOGICAL_CLOCK 和 WRITESET 是不是后者总比前者好？

不一定。WRITESET 依赖主键/唯一键来提取写集合，无主键表上可能退化，不一定比 LOGICAL_CLOCK 强。

### MTS 下 SBM 为 0 是不是就说明副本和主库完全一致？

不是。MTS 下 SBM 可能因为 coordinator 读到了更靠后的事件而显示 0，但 worker 还在回放之前的事务。

### 过滤副本能不能直接晋升为主库？

不能。过滤副本只包含部分数据，事务集合不完整，不能替代全量副本。

### 故障切换时，是不是选延迟最小的副本就对了？

不是。延迟最小只是参考，还要确认候选副本的 GTID 集合、过滤/延迟属性、只读状态和角色语义。

## 收束：复制和故障切换最危险的习惯，不是“延迟高”，而是“你以为是并行回放，其实都在等同一把锁；你以为是全量副本，其实只是过滤副本”

回到开头那个问题：主库 1000 TPS，副本为什么跟不上，并行复制开大线程数为什么有时不生效，故障切换时选哪个副本最安全？答案已经完整闭环了。并行复制的本质不是“多开 worker”，而是“证明事务彼此不冲突”。DATABASE、LOGICAL_CLOCK、WRITESET 分别从不同粒度证明独立性。MTS 运行时在依赖判断、worker 回放、提交顺序和 checkpoint 之间做协调。故障切换的核心则是确认候选副本的事务集合和角色语义，而不只是延迟最小。

这就是为什么说：**并行复制的本质不是“多开几个线程”，而是“在不破坏依赖和提交顺序的前提下最大化并行度”；故障切换的本质不是“切得最快”，而是“确认事务集合和角色语义后选择最完整的副本”。** 只要这一条站稳，后面进入备份恢复、高可用架构和集群管理层时，你就不会再被“并行度靠线程数”或“切换靠延迟”这类半结论误导。
