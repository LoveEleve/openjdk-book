## 现在真正该问的，不再是“Redo 为什么能让已提交修改不丢”，而是“为什么事务世界里还非得再长出 Undo、Group Commit、Crash Recovery 和 Purge 这几条看起来互相打架的时间线”

上一篇已经把 InnoDB 的持久化主账钉住了。你已经知道：

- 事务提交时，不一定要求数据页已经刷回表空间；
- Redo 先把页修改的重建方法记住；
- Log Buffer 和 MTR 把底层页修改组织成可延迟结算的一组日志单元；
- LSN 把日志进度、脏页进度和恢复起点拉进同一坐标系；
- Checkpoint 决定哪些旧日志终于可以被安全忘掉。

如果只停在这里，你会自然得出一个危险的半结论：

“那不就行了吗？只要崩溃后能按 Redo 把页重放回来，事务这件事就已经讲完了。”

这恰恰是 MySQL 事务语义最容易被讲糊的地方。因为真实数据库里，持久化只是一半故事，另一半是：

- 有些事务在崩溃前还没真正提交成功，你不能把它们也一起恢复成既成事实；
- 有些事务已经提交成功，但旧版本仍然不能立刻删除，因为别的读者还在看旧快照；
- 一个事务既在改 InnoDB 页，又在写 binlog，若两边边界不一致，复制和主库本地状态就可能裂开；
- 后台清理若太激进，会把仍被 ReadView 需要的历史版本提早抹掉；太保守，又会把 Undo/history 长到可怕。

所以本篇真正要讲清的，是事务系统里四条经常被误混成一条的时间线：

1. **提交线**：什么时候可以对客户端宣布“这笔事务成功了”；
2. **回滚线**：未提交或失败事务的修改怎样被撤销；
3. **可见性线**：已提交旧版本为什么还要为一致性读继续留着；
4. **清理线**：历史版本什么时候终于可以物理删除。

先把总图记住：

```text
执行期：
  改 Buffer Pool 页
  → 生成 Redo
  → 同时生成 Undo / 版本链线索
  → binlog 先写在事务私有 cache 中

提交期：
  Group Commit 协调 binlog 持久化与引擎提交边界

崩溃后：
  Checkpoint 之后重放 Redo
  → 再区分哪些事务已提交、哪些需要按 Undo 回滚

运行中：
  已提交旧版本仍可能服务 ReadView
  → Purge 只能在最后一个需要它的读者走掉后再清理
```

这篇最该先记住的一句话是：**事务不是一个瞬间，而是四类语义时间线：已提交修改怎样重建、未提交修改怎样撤销、提交边界怎样对外成立、历史版本什么时候可被忘掉。而真正站在这些时间线背后服务的机制，主要是 Redo、Undo、Group Commit 和 Purge——机制不等于语义，别把“四条时间线”误读成“四个平行组件”。**

## 一、如果每个事务都自己单独 fsync binlog、再自己单独和引擎提交对齐，吞吐会先被固定同步成本活活掐死

### 1. 最朴素的错误世界：既然事务提交这么严肃，那每个事务就各自把自己的 binlog 和引擎状态单独同步到最稳边界

这个想法和上一篇里“每次事务都同步刷数据页才算安全”是同一种直觉：既然提交这件事这么关键，那当然越独立、越一事务一结算越保险。

把它翻成更具体的流程，就是：

- 事务执行时一边改 InnoDB 页、一边把自己的 binlog event 写进事务私有缓存；
- 到提交时，自己单独把 binlog cache 刷到 binlog 文件；
- 再单独做一次 `fsync`；
- 最后再去完成引擎提交与返回。

这个流程从语义上看很清晰：谁的事务谁自己结账，不和别人混。问题在于，数据库最怕的恰恰不是“每次多一点 CPU 逻辑”，而是**每个事务都要独自承担一次最贵的同步固定成本**。

高并发场景里，真正拖慢提交路径的，往往不是把几条 event 从内存写到文件里，而是：

- 每个事务都要独立撞一次 `fsync`；
- 每次撞的都是持久化边界最贵的那一层；
- 很多相邻事务明明可以共享一次同步过路费，却被人为拆成无数单独过桥动作。

### 2. Group Commit 真正优化的，不是“日志写入逻辑”，而是“固定同步成本如何被多事务摊薄”

这一步必须先抓住最根本的成本结构。数据库日志持久化最吓人的不是“内容很多”，而是即使内容不多，只要你要跨过一次真正的稳定边界，那笔代价就会非常像高速公路收费站：

- 你一辆车过去要停；
- 十辆车排成一队一起过去，虽然还是得停，但总停车次数大幅下降；
- 若十辆车都各自单独跑一趟，那你的吞吐就先被收费站拍死了。

Group Commit 的精髓就在这里：**它不是把很多事务揉成一笔大事务，而是把很多相邻提交事务的“必须付的固定同步过路费”合并摊销。**

这就是为什么它的价值从来不只是“更快一点”，而是决定数据库高并发提交场景到底能不能撑住。

### 3. 这也解释了为什么 Group Commit 必须按阶段组织，而不能只说“大家一起提交了”

只说“大家一起提交”太粗了，因为事务提交里至少有两套需要对齐的世界：

- Server 层和复制世界关心的是 binlog；
- InnoDB 引擎层关心的是 Redo、页状态和内部事务提交边界。

如果你只把 Group Commit 理解成“很多事务一起刷一次盘”，你就会忽略最关键的问题：**它们到底在哪个阶段结成批、哪一阶段共享同步、哪一阶段才真正对外宣布成功。**

教学上可以先压成一个最小阶段图：

```text
事务执行
  → binlog event 先写进各自的 binlog cache

Group Commit 批处理阶段
  → FLUSH：多事务 cache 批量落到 binlog 文件
  → SYNC：共享一次或少数几次持久化同步成本
  → COMMIT：引擎侧真正完成提交并释放相关资源
```

这里最重要的不是死背阶段名，而是理解：提交不是一句话，而是 Server 层日志、持久化边界和引擎完成态逐层对齐的过程。同时要特别提醒一句：**FLUSH/SYNC/COMMIT 这种三阶段划分是教学抽象，不是某一版源码里固定不变的函数调用栈。** 具体到某次提交，哪些事务结成一批、在哪一步共享同步、引擎提交与 binlog 的协调顺序，都会随 MySQL 版本、`sync_binlog`、`innodb_flush_log_at_trx_commit` 和复制模式变化。你不能把这张简化图当成所有实现都照抄的源码流程。

### 4. 三阶段各自到底在替哪一层结账，值得逐个拆开看

只把三阶段当成一张图，还是太容易变成“三个名词”的背诵。为了让这条主链路真正站住，值得把每阶段各自负责的“账”单独讲清楚：

- **FLUSH（把 binlog cache 落到 binlog 文件）**：事务执行期把 binlog event 先写进各自的事务私有缓存，这一步还没真正进 binlog 文件。FLUSH 阶段是在把一批事务的 cache 内容真正搬到 binlog 文件里。它解决的是“内容从哪里来、落到哪个文件”，但此刻还不代表已经过了稳定持久化边界。
- **SYNC（把 binlog 文件同步到持久化边界）**：这一步才真正撞向“硬件/文件系统层说了算”的同步成本。多事务能在这一层共享一次或少数几次同步，也正是 Group Commit 最值钱的落点。若你把它误解成 FLUSH 或 COMMIT，就会把最贵的固定成本摊到错误阶段。
- **COMMIT（引擎侧完成提交并释放相关资源）**：binlog 内容已经就位后，引擎侧才真正把事务标记为完成、释放锁和相关资源。它回答的是“InnoDB 内部什么时候承认这笔事务算数”。

一句话总结三阶段分工：**FLUSH 负责把内容放进文件，SYNC 负责让内容越过持久化边界，COMMIT 负责让引擎正式承认提交。**

### 5. 内部 XA：为什么“Server 层提交”和“引擎层提交”必须被绑成一条不可随意拆开的线

这正是 02 篇桥接里承诺过、但一直没真正兑现的概念：内部 XA。

简单说，MySQL 在提交一个普通事务时，往往要协调两套“都想说算数”的对象——binlog（Server 层/复制世界）和 InnoDB 事务（引擎世界）。如果两者各自在互不知情的情况下宣布“我提交了”，就可能出现前面说过的两种裂缝：引擎认了但 binlog 没有，或 binlog 像有了但引擎还没完成。

内部 XA 的思路，是把这种协调当成一次两阶段的原子协议来对待：先把 binlog 侧准备好、并持久化到合适边界；再让引擎侧完成提交；最后在两边都确认后，才对客户端宣布成功。这样“复制世界看到什么”和“引擎本地看到什么”终于能在提交边界上对齐，而不是各说各话。

这里同样要守住事实边界：**内部 XA 的具体阶段顺序、prepare/commit 的落地细节，会随 MySQL 版本、binlog 格式、组提交实现和复制模式显著变化。** 本篇只建立“为什么要用两阶段去协调两套提交世界”的心智模型，不把某一版源码里的阶段函数名或调用顺序写成固定契约。

### 6. 如果 binlog 和引擎提交边界不一致，你会得到两种都非常糟的裂缝

这就是为什么 Group Commit 不能只是“写快一点”的技巧，它其实还在替一致性兜底。

如果引擎先提交了、本地页和 Redo 也认账了，但 binlog 这边还没到正确边界，你就可能得到这种灾难：

- 主库本地觉得事务已经成功；
- 复制链路却根本没看到对应 binlog；
- 主从数据世界从这一刻开始裂开。

反过来，如果 binlog 先对外表现得像已经算数，而引擎提交边界没对齐，又会得到另一种同样糟糕的状态：

- 复制或恢复侧以为这事务已经存在；
- 引擎自身却没把它当成最终完成。

也就是说，**Group Commit 优化的是同步成本，但它保护的其实是跨日志层与引擎层的提交边界一致性。**

证据位上，这层最值得回到 binlog cache、Group Commit 分阶段路径、binlog 刷盘与引擎提交协调、一致性配置接口去看：它们共同支撑“Group Commit 不只是批量刷盘，而是在协调两套日志世界的提交边界”的判断。具体阶段细节和内部 XA 顺序会随版本变化，但这条设计目标是稳定的。

### 7. 一个更具体的失败场景：高并发短事务明明业务很轻，却在提交边界突然集体卡顿

想象一个交易或订单系统，高峰期大量事务都非常短：

- 改几行；
- 生成几条 binlog event；
- 立刻提交。

如果每个事务都独自去做一次最贵的同步动作，你会在线上看到非常典型的现象：

- SQL 本身执行并不复杂；
- Buffer Pool 命中率也不错；
- CPU 看起来没有先炸；
- 可一到提交时，TPS 突然顶不住，P95/P99 延迟开始一簇一簇抬头。

真正的问题并不在“查询复杂”，而在“大家都在单独撞同步边界”。Group Commit 正是在这里把“每单自己过桥”改成“成批过桥”，让数据库不会因为提交边界过路费太贵而先死在最短事务场景里。

### 8. 本节最该记住的结论：Group Commit 真正值钱的地方，是把多事务提交时最贵的同步固定成本摊薄，同时继续协调 binlog 与引擎提交边界，避免复制世界和本地引擎世界裂开

一句最短人话是：**Group Commit 不是把事务混成一锅，而是让很多人共搭一班去银行盖章的班车。**

## 二、Undo 真正不是“失败事务的垃圾桶”，而是同时给回滚和 MVCC 历史版本续命的第二本账

### 1. 第二个朴素误解：有了 Redo，事务失败时大不了靠它把页恢复回去，Undo 只是额外的辅助材料

上一篇已经把 Redo 讲得很重，很容易让读者自然滑进一个误区：

- Redo 既然能保证崩溃后把已提交页修改重新补回去；
- 那事务失败或回滚时，是不是也只要“别让 Redo 生效”或者“再做个反向重放”就够了。

这正好会把 Undo 的独立角色抹掉。因为 Redo 和 Undo 根本不是同一类账：

- Redo 关注的是“如何把已经承诺过的修改重新做出来”；
- Undo 关注的是“如果这笔修改不该算数，怎样把它撤回去，以及在它已经被后续版本覆盖后，旧读者还能不能继续看到历史视图”。

所以 Undo 从第一性上就不是 Redo 的附件，而是另一套完全不同的职责体系。

### 2. Undo 的第一职责：未提交事务必须能撤回自己的影响

这一条最好理解。一个事务更新到一半，如果后来：

- 主动 `ROLLBACK`；
- 死锁检测选中它做牺牲品；
- 崩溃恢复判定它未真正提交成功；

那系统必须有办法把它已经做过的那些页级影响撤回去。光知道“如何重做”不够，你还得知道“如何撤销”。

这就要求在修改发生时，系统除了记录“新的样子怎样重建”，还要留住足够的旧信息，让未来真需要回滚时能把逻辑效果撤回来。

### 3. Undo 的第二职责：已提交旧版本也不能立刻扔，因为别的 ReadView 可能还在看它

这一点才是 Undo 最容易被低估的地方。

假设事务 T1 把某行从旧值改成新值，并且已经成功提交。直觉上你可能会说：“那旧值已经没用了，可以删掉了。”

可如果此时还有另一个一致性读事务，它的 ReadView 比 T1 更早，它就仍然可能需要看到那份旧版本。也就是说，对系统来说：

- 从“最新状态”视角看，旧值已经被覆盖；
- 从“某个仍在活跃的老快照”视角看，旧值还在提供合法现实。

这就是为什么 Undo 不能被讲成“只为失败事务服务”。它同时也是 MVCC 历史版本的承重墙。

### 4. 版本链不是额外装饰，而是“当前记录 + 向后追旧版本”的真实访问路径

只要接受“旧版本可能还要被看”，一个很自然的问题就冒出来：这些旧版本放哪？

MySQL/InnoDB 的关键做法是：当前聚簇记录上保留指向旧版本线索，例如 roll pointer 一类线索；当某个读者发现当前版本对自己不可见时，就顺着 Undo 链往回找更早的历史版本。

```text
当前记录
  → trx_id / roll pointer
  → 指向更老的 Undo 版本
  → 更老版本还可继续向前链接

一致性读
  → 看当前版本是否对 ReadView 可见
  → 不可见则沿版本链回溯
  → 找到第一个对自己可见的历史版本
```

这说明 Undo 的价值不是“回滚时偶尔拿一下”，而是它直接进入了运行时一致性读路径。这里还要补一句导航边界：本篇只讲了聚簇记录上的版本链线索；二级索引也有自己的 MVCC 语义——它不会每次都记完整历史，而是通过回表到聚簇记录后再做可见性判断。二级索引 MVCC 的细节会放到后面 `07-acid-mvcc-locks.md` 展开，这里先不把它当作已讲完的既成事实。

### 5. 一个更具体的失败场景：如果事务一提交就把 Undo 扔了，长查询会先看到一个没有过去的世界

想象一个分析线程或长事务先开始了快照读，它的 ReadView 固定在较早时间点。此时另一批短事务不断更新一行又一行，并且频繁提交。

如果系统在每次提交后都立刻删掉旧 Undo：

- 这些短事务当然很爽；
- 当前最新版本也都写好了；
- 可那个仍在跑的老快照事务一旦沿版本链回溯，就会发现“历史根本没了”。

结果不是“读到最新值”这么简单，而是整套一致性读语义会直接塌掉：它承诺自己看到的是某个时间点上的稳定世界，可系统已经把那个世界的证据主动碎纸了。

所以 Undo 必须同时为“撤销未提交修改”和“保留已提交历史版本”服务，这两者缺一不可。

### 6. 为什么 Undo、回滚段和表空间布局不能被压成一句“就是旧值日志”

一旦 Undo 既承担回滚，又承担历史版本保留，你就会明白它绝不只是“一串旧值记录”这么简单。系统还得继续回答：

- 这些记录怎样被组织；
- 哪些事务的 Undo 彼此如何分段管理；
- 如何找到它们；
- 何时允许重用和回收。

所以回滚段、Undo 页、Undo 表空间这些东西并不是实现噪音，而是因为 Undo 本来就不是一次性的临时便签，而是一批会继续活在系统里的历史账单。

证据位上，这层最值得回到 Undo Log、roll pointer、回滚段与 MVCC 历史链路径去看：它们共同支撑“Undo 是回滚账 + 历史账”的判断。具体页布局和回滚段组织会随版本变化，但“提交后旧版本可能继续活着”这条主线是稳定的。

### 7. 本节最该记住的结论：Undo 不只是失败事务回滚工具，它还是 MVCC 历史版本的底稿；没有它，未提交撤销和已提交旧快照可见性都站不住

一句最短人话是：**Redo 负责把新账补出来，Undo 负责把不该算数的账撤回去，还顺手把旧账本留给还在查历史的人。**

## 三、Crash Recovery 真正不是“重放 Redo 然后万事大吉”，而是先把页恢复到可解释状态，再区分哪些事务该留下、哪些事务必须撤回

### 1. 第三个朴素误解：重启恢复就是从 Checkpoint 后一直重放 Redo，重放完系统自然就回到正确状态了

如果只盯着上一篇，这个误解其实非常自然。毕竟我们已经知道：

- Checkpoint 之后的 Redo 记录着恢复起点之后的修改；
- 崩溃后只要把这些记录重放回去，数据页就能回到更接近崩溃前的状态。

问题在于，崩溃前的数据库世界并不只有“已提交事务的页修改”，还包括一批可能进行到半路的事务：

- 它们可能已经改了 Buffer Pool 里的页；
- 可能已经生成了部分 Redo；
- 可能 binlog/cache/引擎提交边界还没完全走到位；
- 也可能根本不该算成功。

如果你只是机械地 Redo 到底，就可能把本来不该留的修改也一起重新做出来。那系统恢复的就不是“最后一个逻辑正确世界”，而是“崩溃瞬间所有碰过页的东西都被硬复现”。

### 2. 崩溃恢复第一步是先把页恢复到“可继续判断事务状态”的地步

所以恢复的第一阶段虽然以 Redo 为主，但它真正解决的不是“恢复就此结束”，而是：

- 先把页和底层结构恢复到一个可解释、可继续处理的状态；
- 让系统有能力继续判断哪些事务已经真正完成，哪些还没完成。

这一步很像灾后先把楼体扶正。你先得有一栋还能进人检查的楼，后面才谈得上哪间房该交付、哪间房得拆回去重建。

### 3. 之后才是第二层判断：哪些事务是已提交，哪些只是留下了半成品

一旦页结构和日志进度回到可解释状态，系统还要继续面对一个更像事务语义的问题：

- 哪些事务在崩溃前已经真正跨过了提交边界；
- 哪些事务只是写了一半、改了一半、记录了一半；
- 哪些逻辑效果应该留下，哪些必须借 Undo 撤回。

也就是说，恢复不是单阶段，而是至少包含：

1. 用 Redo 把底层页状态拉回可解释区间；
2. 再判断哪些事务已经真正提交、哪些必须借 Undo 撤回。

这里最值得钉住的一个事实边界是：**“区分已提交/未提交”不是靠恢复时另查一张神秘事务状态表，而是主要落在日志和事务自身携带的信息上。** 在 InnoDB 这类引擎里，Redo 重放阶段会推进到能读出“这个事务是否已经跨过提交边界”的地步——事务提交与否的信息往往就写在日志记录和相关内部状态里；对于判定为未真正提交的事务，恢复再借 Undo 把它们已经产生的页级效果撤回去。也就是说，区分动作不是“页恢复完之后，再去翻一张全局事务表”，而是日志、提交标记和 Undo 在恢复现场共同把账重新对出来的过程。具体怎么编码、按什么顺序扫描，会随版本和实现变化，但“靠日志/提交标记 + Undo 回滚”这条主线是稳定的。

### 4. 一个更具体的失败场景：只会 Redo、不处理未完成事务，系统重启后会看见“本来没提交成功”的脏历史

想象一个事务 T2 在崩溃前做了下面这些事：

- 改了几张页；
- 相关 Redo 已经部分写入日志；
- 可真正的引擎提交边界和外部可见提交还没成立。

如果恢复只会“从 checkpoint 后把能看到的 Redo 全部重做一遍”，那 T2 这些本不该对世界永久生效的修改，就会被你在重启后重新做成既成事实。这样用户看到的是：

- 事务崩溃前没真正提交成功；
- 重启后数据里却像它已经做完了。

这正是数据库最不能犯的错误之一。所以恢复的难点从来不只是“有没有日志”，而是**怎么把已提交与未提交重新分出界。**

### 5. 这也是为什么 Group Commit、Redo 和 Undo 在崩溃恢复里根本分不开

如果篇章切得太碎，读者很容易把三者理解成：

- Group Commit 是性能优化；
- Redo 是持久化；
- Undo 是回滚和 MVCC。

这三句话单独都对，但一到崩溃恢复现场，它们会重新缠回同一根线上：

- Group Commit 定义了提交边界怎样和 binlog/引擎保持一致；
- Redo 定义了哪些页修改能被重新拉回；
- Undo 定义了哪些未完成效果必须被撤销。

也就是说，恢复时系统不是分别调用三块功能，而是在重新回答一个整合问题：**最后一个逻辑上能对外承诺的世界到底是哪一个。**

证据位上，这层最值得回到 checkpoint 之后的 redo 扫描、事务提交状态判定、Undo 回滚路径以及复制/binlog 协调边界去看：它们共同支撑“恢复 = 先把页世界扶正，再把事务世界分账”的主线。

### 6. 本节最该记住的结论：Crash Recovery 不是“重放 Redo 就结束”，而是先用 Redo 恢复可解释页状态，再靠日志提交标记与 Undo 把不该留下的半成品撤回去

一句最短人话是：**灾后重建不是把所有施工都继续做到头，而是先把楼扶正，再判断哪些房间已经验收，哪些还得撤回。**

## 四、Purge 真正麻烦的不是“清理旧版本”这个动作，而是它必须等到最后一个还在看旧快照的人彻底走掉

### 1. 第四个朴素误解：事务既然已经提交了，旧版本和 delete-marked 记录当然应该尽快删掉，越快越省空间

这个想法非常符合一般人的空间直觉：

- 新版本已经对外生效；
- 旧版本只是历史；
- 那就赶紧删掉，别占地方。

可 MVCC 世界里，空间能不能回收从来不只看“最新写者是不是提交了”，而更要看：**有没有人还在合法地使用旧版本。**

### 2. Purge 不面对“事务写者”，而是在面对“最老仍然活着的读者”

这是最该钉住的角色转换。很多读者会本能地把 Purge 看成“写入完成后的清理工”。更准确的说，它真正盯的是读者边界：

- 只要还有某个 ReadView 可能合法地看到旧版本；
- 那旧版本和相关 Undo 就不能物理清理；
- delete-marked 记录也不能急着真正抹掉。

所以 Purge 的推进速度，不只由写者有多快决定，更由“最老那个还没走的快照读者”决定。

### 3. 长事务为什么会把 history list、Undo 和清理压力一起拖住

这就是线上最常见也最容易被误判的场景。一个长事务或长时间快照读看起来也许没干很多事，只是“开着没动”。可从 Purge 视角看，它可能在做一件极其昂贵的事：

- 它把自己的 ReadView 固定在一个很早的时间点；
- 后面无数短事务继续更新、继续提交；
- 旧版本本来已经过时，但因为这个最老读者还活着，系统不敢删；
- Undo/history list 就一路往后堆。

所以很多“TPS 明明正常，为什么 Undo 表空间越来越肥、Purge 跟不上、甚至连 Buffer Pool 压力都一起变怪”的现象，根本原因不是写流量本身，而是**最老那个读者还不肯走。**

### 4. 一个更具体的失败场景：报表事务开了一小时，在线业务每秒都在更新，Purge 被迫不停给旧世界续命

想象一个典型混合负载：

- 在线业务每秒更新大量订单、库存或账户行；
- 一个报表事务为了“看一份一致快照”开着不提交，持续跑很久；
- 新版本当然不断产生，短事务也都很快提交；
- 可那份老报表快照仍然要求系统保留它开始那一刻之后的大量历史版本。

这时 Purge 的处境不是“懒得清”，而是它根本没有资格清。你表面上看到的是：

- 事务都提交了；
- TPS 也还在跑；
- 可历史链越来越长，Undo/history 越堆越厚。

这不是 Purge 线程能力差，而是业务读者把清理边界硬钉在了过去。

### 5. Purge 真正清理的不只是 Undo 文本记录，还包括历史版本的物理残影

Purge 最容易被简化成“删掉 Undo”。更完整的说法是，它在安全边界到达后，继续把：

- 不再被任何 ReadView 需要的旧版本；
- 某些 delete-marked 但还未真正物理清除的记录；
- 对应可回收的 Undo/history 痕迹；

逐步清走。

也就是说，它不是单一文件清理工，而是 MVCC 历史世界的拆迁队。

### 6. 为什么“事务提交了”与“历史马上消失”必须被强行拆开

这是本篇最后一条必须站稳的边界。事务提交只说明：

- 新版本对未来读者可以变成正式现实；
- 未提交状态不再成立。

它不说明：

- 所有老读者都已经离开；
- 历史版本已经没有观察者；
- 相关 Undo 已可以马上释放。

所以 Purge 的存在，就是在强迫你承认：**提交边界和历史消失边界是两件完全不同的事。**

证据位上，这层最值得回到 ReadView 最老边界、Undo history list、delete-marked 记录与 Purge 线程推进路径去看：它们共同支撑“最后一个旧读者离开之前，历史没有资格物理死亡”这句判断。

### 7. 本节最该记住的结论：Purge 不是提交后的附属清洁工，而是 MVCC 历史世界的守门人；它只能在最后一个仍需要旧版本的读者离场后，才开始真正拆旧世界

一句最短人话是：**Purge 不是写者说删就删，而是得等最后一个还在查旧档案的人把文件还回来。**

## 五、把本篇收成一张图：事务不是一个点，而是提交、回滚、可见性和清理四条互相错位的时间线

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：Redo 已经保证“已提交修改可重建”，为什么数据库还非得再长出 Group Commit、Undo、Crash Recovery 和 Purge 这么多角色。答案现在已经闭环了。

因为数据库事务从来不是“写了、提交了、结束了”这么单线条的故事，而是至少四条同时存在又互相约束的时间线：

- **提交线**：什么时候可以对外宣布“这笔事务成功了”——主要由 Group Commit 协调 binlog 与引擎提交边界承担，同时摊薄同步固定成本；
- **回滚线**：未提交或失败事务的修改怎样被撤销——由 Undo 承担；
- **可见性线**：已提交旧版本为什么还要继续服务旧 ReadView——也由 Undo 保留的历史版本承担，是 Undo 的另一面职责；
- **清理线**：历史版本什么时候终于有资格物理消失——由 Purge 承担，等最后一个仍需要旧版本的读者离场后再拆旧世界。

注意这里的映射关系：四条时间线是四类语义，但背后并不是四个完全独立的组件。Undo 同时扛起“回滚”和“可见性”两条线，Redo 扛“重建”线，Group Commit 扛“提交边界”线，Purge 扛“清理”线。别把这四条时间线误读成四个平行黑盒。

把这一切压成最短总图，就是：

```text
执行：
  改 Buffer Pool 页
  → 生成 Redo
  → 生成 Undo / 版本链线索
  → 事务 binlog 先写到私有 cache

提交：
  Group Commit 协调 binlog 持久化与引擎提交

崩溃：
  checkpoint 后重放 Redo
  → 再判断哪些未完成事务必须借 Undo 撤回

运行中：
  ReadView 仍可能需要旧版本
  → Purge 等安全边界到来后再物理清理
```

所以本篇最该记住的一句话是：**MySQL 事务不是一个瞬间，而是一组互相错位的账本：Redo 让已提交修改可重建，Undo 让未提交修改可撤回，Group Commit 让 binlog 和引擎边界别裂开，Purge 则让旧世界在最后一个读者走后才真正消失。**

## 六、几个最容易说错的地方

### Group Commit 是不是只是“很多事务一起刷 binlog，所以更快一点”？

不够准确。它真正协调的是多事务共享同步成本，以及 binlog 与引擎提交边界别裂开。

### Undo 是不是只在事务失败时才有用？

不是。它除了支持回滚，还为 MVCC 一致性读保留已提交历史版本。

### Crash Recovery 是不是从 checkpoint 后把 Redo 一路重放到底就结束？

不是。Redo 先把页状态恢复到可解释区间，之后还要区分哪些事务该留下、哪些必须借 Undo 撤回。

### 事务一提交，旧版本是不是就应该立刻删除？

不是。只要还有活跃 ReadView 可能合法看到旧版本，Purge 就还不能越过那条边界。

### Purge 慢，是不是就说明后台线程性能不够？

不一定。更常见的根因是长事务或老快照读一直拖着最老安全边界不往前走。

## 收束：真正成熟的事务系统，不是“保证提交成功”就完了，而是把“没提交怎么办、老版本谁还在看、什么时候能忘掉历史”一起讲通

回到开头那个问题：一个事务修改了 InnoDB 页、写了 binlog，恰好在提交中途断电，重启后如何判断它算成功还是失败？现在答案已经完整闭环了。因为数据库并不是只在维持“最新值”这一条时间线，它还要同时维护提交边界、回滚能力、旧快照可见性和历史清理边界。Redo 解决的是“已承诺修改怎样重建”，Undo 解决的是“未承诺修改怎样撤回、旧快照怎样继续成立”，Group Commit 解决的是“Server 层 binlog 与引擎提交别各说各话”，Purge 解决的是“旧世界什么时候终于能合法拆掉”。

这就是为什么说：**事务不是一把锁、一次提交或一条日志，而是一套互相错位的时间经济学。** 只要你把这四条时间线看成同一件事的不同账本，后面再去看 B+Tree 页、聚簇/二级索引、MVCC、锁冲突和复制链路时，就不会再把它们当成零散机制，而会看到它们其实都在服务同一件事：让数据库既能并发地改、稳妥地记、必要时撤、还能让老读者暂时住在旧世界里。
