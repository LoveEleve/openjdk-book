## 现在真正该问的，不再是“事务是不是原子的”，而是“同一张表上，为什么有些读可以看旧版本继续走，有些读却必须把别人挡住，为什么连还不存在的记录也会被锁住”

前面几篇已经把事务和索引的两条大线铺得很清楚了：

- Redo 让已提交修改可重建；
- Undo 让未提交修改可撤回，并把旧版本留给一致性读；
- Group Commit 对齐 binlog 与引擎提交边界；
- Purge 只在最后一个旧读者离开后才敢清理历史；
- 聚簇/二级索引、回表、页结构和空间组织决定了一条查询到底要走哪条物理路径。

如果只停在这里，读者很容易形成一个危险但很常见的半结论：

“既然有 MVCC，看旧版本不就行了吗？那锁是不是只是偶尔补刀，甚至很多时候都不重要？”

这恰恰是 InnoDB 并发控制最容易被讲糊的地方。因为事务系统真正同时在服务的，不是一类读写，而是至少三类完全不同的动作：

1. **一致性读**：我只想看一个对自己合法的快照，不想因为别人正在写就被卡住；
2. **当前读**：我不只是看，我还想确认“现在最新的记录是不是这个”，甚至要锁住它后续别变；
3. **写入**：我不只要改当前值，还得防止并发写、并发插入和谓词范围变化把逻辑搞穿。

所以 InnoDB 不可能只靠一套机制包打天下。它必须把“看历史”和“管现在/未来”拆成两套并发语义：

- 普通一致性读尽量走 MVCC，不让读者为了别人写入频繁排队；
- 当前读和写入则依赖锁，甚至要把“还不存在的行”所在的间隙一起保护起来。

先把总图记住：

```text
事务控制
  → ACID / BEGIN / COMMIT / ROLLBACK / SAVEPOINT

隔离级别
  → 决定哪些并发异常可以发生、哪些必须被挡住

一致性读
  → 当前版本不可见?
  → ReadView + Undo 版本链回看旧版本

当前读 / 写
  → 沿索引路径建立 Record / Gap / Next-Key / Insert Intention Lock
  → 保护现在和未来的可见记录集合
```

这篇最该先记住的一句话是：**InnoDB 并发控制不是“MVCC 或锁”的选择题，而是“普通读看历史版本，当前读和写保护现在与未来”的组合题。**

## 一、ACID 与事务控制：`COMMIT` 不是一句“结束”，而是把回滚、持久化、可见性和后续清理同时钉进边界

### 1. 最朴素的错误世界：事务就是一组 SQL，要么都成功要么都失败，剩下都属于实现细节

这个理解在入门层面不算错，但一到真实并发环境就完全不够。因为一笔事务从开始到结束，至少牵动四类完全不同的约束：

- **Atomicity**：中途失败时，哪些修改必须一起撤回；
- **Consistency**：结果是否违反约束、索引、引用完整性或引擎内部结构不变量；
- **Isolation**：别的事务在你进行到一半时，到底能看到什么；
- **Durability**：你说“提交成功”的那一刻，未来崩溃后凭什么还能找回来。

如果把事务只理解成“多条 SQL 打包”，你会天然低估后面所有并发与恢复问题：为何还需要 Undo、Redo、ReadView、Gap Lock、Purge，以及为什么某些 DDL/控制语句会隐式提交。

### 2. `BEGIN / COMMIT / ROLLBACK / SAVEPOINT` 不是四个语法糖，而是在改同一条事务边界的状态机

教学上可以先压成一条最小状态线：

```text
BEGIN / autocommit=0
  → 事务开始

执行期
  → 约束 / 锁 / Undo / Redo / MVCC 一起参与

COMMIT
  → 对外承认“这笔事务成功了”

ROLLBACK
  → 借 Undo 撤销尚未承诺的逻辑效果

SAVEPOINT
  → 在同一事务内部留一个回退点
```

最重要的是别把 `SAVEPOINT` 误听成“小事务”。它不是另起一笔账，而是在同一笔事务里留一个“回到这里”的内部标记。也别把 `COMMIT` 误听成“磁盘都已经刷好了”——前几篇已经说过，真正跨过的首先是提交边界，不是数据页一定原位落盘。

### 3. 为什么某些语句会隐式提交，这不是语法怪癖，而是边界冲突

只要事务里做的是普通 DML，`BEGIN → UPDATE → COMMIT` 这套直觉都还成立。可一旦掺进某些 DDL 或控制语句，系统就会遇到一个边界冲突：

- 你一边想保留当前事务语义；
- 另一边又想修改元数据、切换表结构或改变某些全局状态；
- 这两类动作对锁、恢复和可见性的要求往往不是同一个维度。

所以所谓“隐式提交”并不是语法层的小陷阱，而是在告诉你：某些操作根本不适合继续假装和当前那笔普通事务共用同一条边界。

### 4. Durability 不能被理解成“客户端看见成功 = 物理介质一定已经万无一失”

这一点前几篇已经反复钉过，但在事务篇里必须再收一遍。因为很多人对 ACID 的直觉还是：`COMMIT` 返回成功，那应该就表示“这事已经完整落盘”。

更准确的说法是：Durability 的真实边界受以下几层共同影响：

- Redo 与 binlog 的刷盘策略；
- `innodb_flush_log_at_trx_commit`、`sync_binlog` 等配置；
- 文件系统与设备缓存模型；
- 这笔事务到底是单机 durability，还是还要考虑复制世界的一致性。

所以 ACID 里的 D 不是一句“磁盘一定写好了”能概括的，而是“系统已经跨过它承诺的那条可恢复边界”。

### 5. 本节最该记住的结论：事务控制不是“几条 SQL 的胶带”，而是把原子回滚、恢复边界、可见性语义和后续清理一起钉在同一套生命周期里

一句最短人话是：**事务像一份合同：回滚线、可见性线和持久化线不是附录，而是合同正文的一部分。**

## 二、隔离级别：并发异常不是“数据库运气差”，而是你允许了某些观察窗口继续存在

### 1. 第二个朴素误解：隔离级别只是一张“脏读/幻读/不可重复读”对照表，背完就算懂了

这张表当然重要，但它最大的问题是太静态了。它很容易让人以为隔离级别只是一个记忆游戏：

- RU 允许脏读；
- RC 不允许脏读但可能不可重复读；
- RR 再强一点；
- SERIALIZABLE 最强。

真正的难点不在表格，而在：**这些异常到底是怎么通过“观察窗口”出现的。**

也就是说，你不能只背“会不会”，还得理解“为什么会”。

### 2. READ UNCOMMITTED / READ COMMITTED / REPEATABLE READ / SERIALIZABLE 真正在重写什么

教学上可以先压成最小直觉：

```text
READ UNCOMMITTED
  → 允许看到未提交修改

READ COMMITTED
  → 每条语句更像看自己当下的新视图

REPEATABLE READ
  → 事务内普通一致性读维持相对稳定的视图

SERIALIZABLE
  → 更强隔离，更高等待/锁代价
```

但真正要钉住的是：这四级区别，不只是在“能不能看到脏数据”，还在于：

- 一致性读什么时候取视图；
- 当前读和锁定读什么时候要保护范围；
- 某条语句看到的是“事务开始时的世界”还是“当前语句时刻的世界”；
- 系统愿意让多少并发灵活性换取多少稳定视图。

### 3. 为什么“普通读”与“当前读”必须被分开理解

这是隔离级别最容易被讲成一锅粥的地方。

- **一致性读（consistent read）**：你只是想读一个对自己合法的快照；
- **当前读（current read）**：你想看到“现在最新的记录”并且往往还要继续锁住它，例如 `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`。

这两类读不是同一种观察行为，所以隔离级别也不是“一条规则同时管住它们”。InnoDB 在普通读上会更积极地用 MVCC 降低阻塞，在当前读和写上则更依赖锁与范围保护。

### 4. 一个更具体的失败场景：为什么同一事务里两次查同一条件，会看到不同世界

想象一个事务在 RC 下执行：

- 第一次 `SELECT` 时，看到了当下提交可见的结果；
- 别的事务随后提交了一批修改；
- 第二次 `SELECT` 再执行时，又重新取了新的可见世界。

从“我明明还在同一事务里”的直觉看，这会很反人类；从 RC 的世界观看，它又完全合法，因为 RC 更像“每条语句看自己的新快照”。

这说明隔离级别的关键不是“事务是不是同一笔”，而是“视图什么时候被固定、什么时候允许刷新”。

### 5. 为什么 InnoDB 默认 RR，不等于“它只靠 MVCC 就解决了一切”

InnoDB 默认 RR 常被误听成“那我只要理解版本链就够了”。这并不成立。因为 RR 虽然让普通一致性读更稳定，但：

- 当前读仍然必须处理并发写；
- 唯一性检查和范围谓词仍然会把锁引进来；
- 幻读防护不是一条抽象标签，而要靠 Gap / Next-Key 一类范围锁具体落地。

证据位上，这层已经能落到真实源码：`MVCC::view_open()`（`storage/innobase/read/read0read.cc:529`）、`trx_assign_read_view()`（`storage/innobase/trx/trx0trx.cc:2318`）体现了 ReadView 如何被打开和挂到事务上；而 `lock_clust_rec_read_check_and_lock()`（`storage/innobase/lock/lock0lock.cc:5514`）与 `lock_sec_rec_read_check_and_lock()`（`storage/innobase/lock/lock0lock.cc:5465`）则体现了当前读/锁定读路径根本不是“只看旧版本”那套逻辑。这些锚点共同支撑“普通读和当前读必须分开理解”的判断。

### 6. 本节最该记住的结论：隔离级别不是一张死表，而是在决定“视图何时固定、当前读何时必须看最新并加锁、系统愿意放行多少观察窗口”

一句最短人话是：**隔离级别像会议室透明度规则：普通参会者能看到哪个版本的会议纪要，和谁有权当场改议程，不是同一条规定。**

## 三、MVCC：一致性读之所以不想等，是因为它宁可看旧世界，也不愿和当前写者硬碰硬

### 1. 第三个朴素误解：MVCC 就是“每行保存很多版本”，然后读者自己随便挑一个看

这句话方向不算错，但太粗了。真正决定 MVCC 能不能站住的，不是“版本很多”，而是：

- 当前记录上怎么挂住历史链索引；
- 读者怎么判定当前版本对自己可不可见；
- 发现不可见后，又按什么规则顺着历史链往回找。

所以 MVCC 不是一个“数据库有很多副本”的模糊概念，而是一套围绕 ReadView 和 Undo 历史链的可见性协议。

### 2. ReadView 不是“事务启动时间戳”这么简单，它是一张活跃事务的边界表

读者最容易偷懒的地方，是把 ReadView 脑补成“某个时间点快照”。更准确的说法是，ReadView 不只是一个单点时间，而是一组边界信息：

- 当前事务自己的身份；
- 哪些事务在视图生成时仍活跃；
- 可见与不可见事务 ID 的上下边界。

也就是说，它不是“时间戳”，而是一张判定当前版本是否对我合法的规则表。

### 3. 一致性读真正发生了什么：先看当前版本，发现不合法，再沿 Undo 版本链往回追

这条逻辑一定要打成读者脑中的动画：

```text
读取聚簇记录
  → 看当前版本上的 trx_id / roll pointer
  → 用 ReadView 判断当前版本是否可见
  → 若可见：直接返回当前版本
  → 若不可见：沿 roll pointer 找更老的 Undo 版本
  → 找到第一个对当前视图合法的版本
```

这就是为什么 MVCC 让普通读不必和写者硬碰硬。它不是阻止别人写，而是允许读者说：“你继续改你的，我先去历史链上看一个对我合法的旧世界。”

### 4. 二级索引为什么不能“自己就把所有版本判断完”

这一步很关键，因为它会直接连回第五篇的回表。很多人会误以为：既然二级索引也是索引记录，那它上面直接判断可见性不就行了？

真实情况更接近：二级索引往往只能先帮你把候选记录定位出来；真正的版本可见性判断，很多时候仍然要回到聚簇记录和 Undo 链这条主线上完成。也就是说：

- 二级索引帮助你先找到“可能是它”的候选；
- ReadView + Undo 帮你决定“这个版本对我算不算真”。

这也是为什么二级索引和 MVCC 会天然跟回表纠缠在一起。

### 5. MVCC 为什么不能完全替代锁

这必须讲得很狠。MVCC 真正擅长的是：**让普通一致性读不必为了别人的写入排队。** 但它不解决：

- 你现在就要改这一行时，别人能不能同时改；
- 唯一性检查和约束怎么保护；
- 你要锁定“当前最新值”时，怎么防止别人继续动；
- 你要防止某个谓词范围里突然冒出新行时，怎么保护“未来变化”。

这些都不是“看旧版本”能解决的问题，所以当前读和写仍然必须把锁拉回来。

证据位上，这层可以落到 `MVCC::view_open()`（`storage/innobase/read/read0read.cc:529`）、`MVCC::get_view()`（`storage/innobase/read/read0read.cc:478`）、`trx_assign_read_view()`（`storage/innobase/trx/trx0trx.cc:2318`）以及 `row_undo` / `roll pointer` 相关路径：它们共同支撑“普通读先做可见性判断，再沿 Undo 历史链回看旧版本”的主线。

### 6. 一个更具体的失败场景：把 MVCC 当成万能屏障，会在当前读和唯一性检查上直接翻车

假设你有一个队列任务表，多个 worker 都在：

```sql
SELECT * FROM task WHERE status='READY' ORDER BY id LIMIT 1 FOR UPDATE;
```

如果你把这件事当成“普通一致性读 + MVCC 够了”，就会立刻出问题：

- 你不是只想看一个旧快照；
- 你想锁住“当前最新可处理的那条任务”；
- 你还要防止别人同时来抢同一条。

这时候 MVCC 不能替你解决当前值争抢，它必须和锁一起工作。MVCC 只负责“普通读少等”，不负责“该锁的现在和未来别乱动”。

### 7. 本节最该记住的结论：MVCC 不是多版本摆在那里任你挑，而是 ReadView + Undo 历史链共同定义的可见性协议；它让普通读少等，但不会替当前读和写扛掉锁的责任

一句最短人话是：**MVCC 像图书馆的旧版馆藏：读者可以先看旧版不打断作者写新稿，但你要改稿、抢稿或封锁书架时，还是得动锁。**

## 四、Record / Gap / Next-Key / Insert Intention：InnoDB 锁住的有时不是“这一行”，而是“这段索引空间的现在和未来”

### 1. 第四个朴素误解：锁一行就是锁这一行，记录不存在就没东西可锁

这是关系型数据库锁最经典的错觉。很多人会觉得：

- 已存在的记录可以锁；
- 不存在的记录自然没法锁；
- 所以“锁不存在的行”听上去就像玄学。

可一旦你真正进入范围查询和谓词保护的世界，这个直觉立刻崩掉。因为数据库有时要保护的不是“这一行现在长什么样”，而是“这个范围里未来能不能再冒出新行”。

### 2. Record Lock：锁的是当前已经存在的索引记录

这层最容易理解。Record Lock 站在“已存在记录”这一层：

- 这条索引记录现在归我看着；
- 别人别同时来改它，或者按语义别来拿走它。

如果你的语句是精确命中某一条索引记录，那么 Record Lock 往往就是第一层锁语义。

### 3. Gap Lock：锁的不是行，而是行与行之间的空地

这一步是最反直觉，但也是 InnoDB 谓词范围保护的核心。Gap Lock 关心的不是一条已经存在的记录，而是：

- 某两个索引值之间的空隙；
- 某个范围里现在还没被占住的位置；
- 别的事务能不能在这个空地里插出一条本来不该现在出现的新记录。

所以它锁的是“未来变化的入口”，不是当前某行的内容。

### 4. Next-Key Lock：为什么“查一段范围”会让“还不存在的 15”也一起被围起来

InnoDB 最常被用户吐槽的经典现场是：

```sql
SELECT * FROM t WHERE id BETWEEN 10 AND 20 FOR UPDATE;
```

然后另一个事务去插 `id=15`，也被挡住。直觉上会很不服：15 这行原本又不存在，凭什么也要等？

答案就在 Next-Key Lock。它大致可以理解成：

- 对当前命中的记录做 Record Lock；
- 同时把前方或相关间隙也一起围起来。

这样做的目的不是故意扩大锁，而是为了防止“你锁定的范围在你眼皮底下长出新记录”，从而让谓词结果集在事务期间偷偷变化。也就是说，它保护的是“这段索引范围对应的现实”，不只是“当前已经存在的几条记录”。

### 5. Insert Intention：不是“插入就一定互斥”，而是提前申报我要在哪块空地建房

另一个容易讲错的点是：一听到插入和 Gap Lock，很多人会脑补成“凡是插入都彼此卡死”。

Insert Intention 的意义恰恰在于细化这件事：

- 多个事务若要插入不同位置，往往并不需要彼此完全串行；
- 系统先申报“我要在这块间隙里插”，再去和真正冲突的 Gap / Next-Key 约束协调；
- 所以它不是“插入专用的大锁”，而是插入动作的一种意图声明机制。

### 6. 为什么锁范围沿索引路径建立，而不是沿 SQL 文本字面范围建立

这是最值得和第五篇索引篇接回来的地方。你写的是 SQL 谓词，最终上锁的却往往是**实际走到的索引路径和索引范围**。这意味着：

- 有合适索引时，锁范围可以更精确；
- 没有合适索引时，扫描范围可能扩大；
- 同样一句 SQL，不同索引与访问路径会把锁成本放到不同位置。

所以“为什么这句查询锁了这么大一段”很多时候不是锁系统心情不好，而是你的索引路径本来就把它带到了更宽的范围上。

证据位上，这层已经有真实落点：`lock_sec_rec_read_check_and_lock()`（`storage/innobase/lock/lock0lock.cc:5465`）和 `lock_clust_rec_read_check_and_lock()`（`storage/innobase/lock/lock0lock.cc:5514`）分别体现了二级/聚簇记录当前读检查与加锁路径；`lock_sec_rec_cons_read_sees()`（`storage/innobase/lock/lock0lock.cc:272`）与 `lock_clust_rec_cons_read_sees()`（`storage/innobase/lock/lock0lock.cc:235`）又恰好把“普通一致性读如何看版本”和“当前读如何加锁”拉开。它们共同支撑“锁范围沿索引路径建立，而不是沿 SQL 文本字面建立”的判断。

### 7. 一个更具体的失败场景：没索引的范围更新，把锁范围悄悄放大到你完全没预料的程度

设想你有一条：

```sql
UPDATE task SET worker_id=7 WHERE status='READY';
```

如果 `status` 没有合适索引：

- 扫描路径就可能变得更粗；
- 系统为了找到满足谓词的行，会沿更大的访问范围推进；
- 相关锁范围和等待影响也会被一起放大。

于是你本来只是想“更新 READY 状态任务”，最后却发现大量本不该受影响的并发写入也开始等你。这不是锁“抽风”，而是访问路径和锁范围一起被放大了。

### 8. 本节最该记住的结论：Record 锁当前记录，Gap 锁间隙，Next-Key 锁记录加间隙，Insert Intention 锁插入意图；InnoDB 真正在保护的不是一行静态数据，而是某段索引空间的现在和未来

一句最短人话是：**Record Lock 是给已有房间上锁，Gap Lock 是把两栋房之间的空地也围起来，Next-Key 是房间和门前空地一起封锁，Insert Intention 是先登记“我要在这块空地建房”。**

## 五、把本篇收成一张图：普通一致性读看历史版本，当前读和写保护现在与未来，隔离级别则在两者之间分配成本

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：两个事务同时读写同一行时，MySQL 到底靠什么避免脏读、覆盖更新和幻读，为什么有时不用锁也能读，有时却连还不存在的行都要锁住。答案现在已经闭环了。

因为 InnoDB 并发控制从来不是单一武器，而是两套机制的组合：

- **一致性读**：通过 ReadView 和 Undo 历史链，尽量让普通读者去看一个对自己合法的旧世界，而不是和写者正面冲突；
- **当前读 / 写**：通过 Record / Gap / Next-Key / Insert Intention Lock，保护当前记录和将来可能插入这个范围的新记录。

隔离级别真正做的，不是贴标签，而是在决定：

- 普通读的视图何时固定；
- 当前读要不要立即看到最新值并加锁；
- 系统愿意让多少观察窗口继续开放，愿意让多少并发改成等待。

把这一切压成最短总图，就是：

```text
事务控制
  → ACID / BEGIN / COMMIT / ROLLBACK / SAVEPOINT

一致性读
  → ReadView + Undo 版本链
  → 尽量少阻塞普通读

当前读 / 写
  → Record / Gap / Next-Key / Insert Intention
  → 保护现在和未来的记录集合

隔离级别
  → 决定普通读与当前读的边界和成本
```

所以本篇最该记住的一句话是：**InnoDB 并发控制不是“全靠 MVCC”或“全靠锁”，而是普通读尽量看旧版本少等人，当前读和写则用索引锁保护现在与未来；隔离级别决定两者怎么混合。**

## 六、几个最容易说错的地方

### MVCC 是不是有了它就基本不用锁了？

不是。MVCC 主要解决普通一致性读少阻塞的问题，当前读、写入、唯一性检查和范围保护仍然必须靠锁。

### ReadView 是不是一个简单的“事务开始时间戳”？

不够准确。它更像一张活跃事务边界表，用来判断当前版本和历史版本对这个读者是否合法可见。

### Gap Lock 是不是数据库故意把不存在的行也拿来吓人？

不是。它保护的是某段索引范围的未来变化，防止谓词结果在事务期间被新插入行悄悄改写。

### 二级索引能定位记录，是不是就能自己完成全部 MVCC 判断？

不是。很多时候二级索引只是先找到候选，真正版本可见性还要回到聚簇记录和 Undo 历史链判断。

### 隔离级别是不是只要背一张“脏读/幻读”表就够了？

不够。真正要理解的是普通读和当前读分别怎么工作，视图何时固定，锁范围又怎样沿索引路径建立。

## 收束：并发控制最难的地方，不是“锁会不会用”，而是“什么时候该看旧世界，什么时候必须把新世界围起来”

回到开头那个问题：两个事务同时读写同一批记录时，为什么有时读者不用等，有时却连不存在的行也要被锁住？因为 MySQL/InnoDB 真正同时维护的，是两种完全不同的读写语义：普通一致性读想尽量不和写者硬碰硬，于是走 ReadView + Undo 历史链；当前读和写则要保护当前真实记录和未来会落进谓词范围的新记录，于是把锁沿索引路径铺开到记录、间隙和组合范围上。

这就是为什么说：**并发控制的核心不是“加不加锁”，而是“哪类读看历史、哪类读看现在、哪类写要把未来一起围起来”。** 只要这条主线站稳，后面去理解死锁检测、MDL、NOWAIT、SKIP LOCKED、锁优化和热点缓解时，就不会再把它们误听成分散技巧，而会知道它们其实都在替同一件事服务：让事务既别读脏、也别把系统互相拖死。
