## 现在真正该问的，不再是“有没有索引”，而是“为什么一张表既可能因为索引结构不对而查不到，也可能因为统计失真而选错计划，还可能因为 DDL 看着在线却把业务一起卡住”

前面五篇已经把 MySQL 的结构、持久化和普通 B+Tree 索引打得很深了。你已经知道：

- Server 层和 InnoDB 通过 Handler 契约分开；
- Buffer Pool、Redo/Undo、Purge 和后台线程让“快提交、后结算”成为可能；
- 聚簇索引、二级索引、页目录、行格式、表空间把“查一行”拆成多层物理路径；
- 页分裂、页合并、回表、覆盖索引、前缀索引和基数共同决定普通索引的收益与代价。

如果只停在这里，很容易形成第二层危险误解：

“索引系统讲完了。剩下无非是多建几个索引、少回几次表。”

这恰恰是数据库优化和变更里最容易翻车的地方。因为索引系统真正要同时承受的，远不止“结构上能不能查到”：

- 某些查询根本不是“按 key 找一行”，而是“文本里有没有某个词”，这时 B+Tree 的世界观就不够了；
- 有两棵索引都能查到结果时，优化器必须猜哪棵更便宜，而它能不能猜对，又依赖统计信息和 Histogram；
- 结构再合理，如果线上每次加索引都得把表锁死、停机重建，那这套索引也没有工程价值；
- DDL 即使号称在线，最后的元数据锁、复制延迟、磁盘空间和回切阶段也一样可能把业务拖死。

所以本篇真正要讲的，是索引系统的三层现实：

1. **查询结构层**：普通 B+Tree 不够时，倒排/FULLTEXT 为什么会出现；
2. **估算模型层**：优化器为什么需要统计信息和 Histogram，为什么它又经常估错；
3. **变更工程层**：结构能查，不代表能不停机地演进；`INSTANT/INPLACE/COPY`、MDL、pt-osc 分别在替什么买单。

先把总图记住：

```text
索引系统三层账本

查询结构：
  B+Tree 负责 key → row
  FULLTEXT 负责 term → document set

估算模型：
  table/index stats + histogram
  → 让优化器决定到底选谁

变更工程：
  INSTANT / INPLACE / COPY / 外部影子表
  → 决定结构怎样在业务不停的情况下改掉
```

这篇最该先记住的一句话是：**索引不是一棵树，而是一整套系统：结构决定能不能查，统计决定会不会被选，DDL 决定能不能安全演进。**

## 一、FULLTEXT：它不是“更快的 LIKE”，而是把“按 key 找记录”这件事彻底改写成“按词找文档集合”

### 1. 最朴素的错误世界：文本搜索也还是一棵 B+Tree 的事，只要把字符串建索引就行

如果你已经熟悉 B+Tree，最自然的想法就是：

- `content` 是一个字符串列；
- 那就给 `content` 建普通索引；
- 搜索“包含 database”不也还是在列里找字符串吗？

这个直觉在 `=`、前缀匹配甚至某些排序场景还勉强成立，可一旦你要做的是：

```sql
WHERE content LIKE '%database%'
```

问题就出来了。B+Tree 真正擅长的是“从有序 key 空间里导航到某个前缀、范围或精确值”。而 `'%database%'` 这种“中间包含某词”的搜索，天然没有一个稳定可导航的左边界：

- 词可能出现在文本任意位置；
- 同一篇文本可能包含很多词；
- 你真正关心的不是“content 这个完整字符串排序在哪里”，而是“哪个词出现在哪些文档里”。

也就是说，**全文搜索不是普通 B+Tree 查找的一点点变体，而是搜索语义本身变了。**

### 2. FULLTEXT 真正改写的是“索引项是什么”

这就是 FULLTEXT 最关键的转向。普通索引里，索引项大致是：

- 一行里某个列的值；
- 再加上能定位回记录的主键或地址信息。

而 FULLTEXT 里，索引项的核心不再是“整列值”，而是：

- 文本被切出来的词项（term）；
- 以及“这个词出现在了哪些文档/行里”的倒排列表（postings）。

```text
建立全文索引
  文本列
    → tokenizer / ngram / 语言规则
    → term
    → document / row postings

查询 MATCH ... AGAINST
  查询词分解
    → 查 term 的倒排列表
    → 合并候选
    → 过滤 / 相关性排序 / 布尔计算
```

这和 B+Tree 完全不是同一套问题。B+Tree 更像按身份证号找人；倒排索引更像书后索引：先找关键词，再列出它出现在哪些章节。

### 3. 为什么 FULLTEXT 不能被简化成“更快的 LIKE”

这一点必须明确拆开。FULLTEXT 与 LIKE 的最大区别不只是速度，而是语义边界完全不同：

- 会不会分词；
- 停用词是否被忽略；
- 最小词长是否会丢词；
- 自然语言模式与布尔模式如何排序和过滤；
- 中文/日文/韩文到底靠词典分词还是 ngram 切分。

这就是为什么你不能把 FULLTEXT 讲成“替代 `%...%` 的更高性能版本”。它引入的是另一套搜索语义，而不是同一语义的纯性能优化。

证据位上，这层已经可以落到真实源码：例如 `ngram_parse()`（`plugin/fulltext/ngram_parser/plugin_ngram.cc:46`）与 `ngram_parser_parse()`（`plugin/fulltext/ngram_parser/plugin_ngram.cc:199`）直接体现了 ngram parser 如何把文本切成词项；`mecab_parser_parse()`（`plugin/fulltext/mecab_parser/plugin_mecab.cc:248`）则进一步说明不同 parser 会给 FULLTEXT 带来不同语言切分行为。这些真实路径共同支撑“FULLTEXT 首先是分词/倒排语义，而不是更快的字符串扫描”这句判断。

### 4. 一个更具体的失败场景：把中文全文搜索当成普通字符串匹配，会在“能不能查到”这一层先翻车

想象你有一个文章表，`title` 和 `content` 都是中文。你想搜“数据库内核”，如果你按普通 `LIKE '%数据库%'` 去理解：

- 搜索的只是一个字面子串；
- 没有分词；
- 没有停用词规则；
- 没有词项相关性排序。

可一旦上 FULLTEXT：

- 使用 ngram parser 时，切词粒度会直接影响索引大小和召回率；
- 使用词典分词时，词边界又会改写“数据库内核”到底被当成几个 term；
- 查询结果不再只是“有没有包含”，而会开始受模式和分词行为影响。

这时最危险的错误不是“慢”，而是“查出来的东西根本和你以为的语义不是一回事”。

### 5. 为什么 FULLTEXT 更新不是免费的

倒排索引最容易被低估的另一面，是更新维护成本。你更新一篇文本，不是简单改一个字段值，而是要：

- 把旧词项对应的 postings 关系处理掉；
- 把新词项重新分解并插进去；
- 重新维护词项到文档集合的映射。

所以 FULLTEXT 的代价和普通 B+Tree 不是同一类型：它优化的是全文检索语义，买单的是分词、倒排维护和更复杂的更新路径。

### 6. 本节最该记住的结论：FULLTEXT 不是更快的 LIKE，而是把“整列值 → 记录”的索引世界改写成“词项 → 文档集合”的倒排世界；分词规则、停用词、语言模型和更新维护成本都属于它的语义一部分

一句最短人话是：**B+Tree 是按身份证号找人，FULLTEXT 是先查词条再列出所有提到它的文章。**

## 二、统计信息与 ANALYZE：优化器之所以会突然换计划，不是“脾气变了”，而是它靠的本来就是估算，不是逐行真知

### 1. 第二个朴素误解：两个索引都能用时，优化器总能直接知道哪一个更快

这也是一个非常自然的误解。既然数据库已经知道表有多少行、索引长什么样，那它应该像神一样，精确知道：

- 走 A 索引大概要查几行；
- 走 B 索引大概要查几行；
- 最后自然选出最优路径。

问题在于，优化器大多数时候并没有逐行真知。它看到的，更多是一套统计近似：

- 大概多少行；
- 大概多少不同值；
- 大概多少页；
- 某个谓词看起来大概能把结果缩小到什么程度。

所以优化器不是“知道正确答案”，而是在用统计信息和成本模型做一个尽量靠谱的赌注。

### 2. ANALYZE TABLE 真正在干的，不是“刷新缓存”，而是重建优化器看世界的那副地图

这就是 `ANALYZE TABLE` 的真正作用。它不会让查询魔法变快，它更像在更新优化器对这张表和这些索引的地图认知：

- 表大概多少行；
- 索引页数如何；
- 不同值分布大概怎样；
- 选择性估计还能不能继续信。

```text
ANALYZE TABLE
  → 重新采样 / 统计
  → 更新 table / index 相关统计信息
  → 优化器之后再生成计划时
      基于新的近似世界观做判断
```

也就是说，`ANALYZE TABLE` 不是在“修数据”，而是在“修优化器的脑补模型”。

### 3. 为什么同一条 SQL 有时会突然换计划

这正是统计信息最让人困惑、也最值得讲透的现象。你明明没改 SQL，为什么计划突然变了？

真实原因往往不是优化器心情不好，而是：

- 数据量变了；
- 分布倾斜变了；
- 自动统计刷新了；
- 手工 `ANALYZE` 后采样结果变了；
- 某次重启/新版本后成本模型也变了。

换句话说，SQL 文本没变，并不代表优化器眼里的“这张表长什么样”没变。计划变化，本质上是地图变化之后的路线重算。

证据位上，这层已经可以落到真实源码：`dict_stats_analyze_index()`（`storage/innobase/dict/dict0stats.cc:1988`）、`dict_stats_analyze_index_low()`（`storage/innobase/dict/dict0stats.cc:1669`）与 `dict_stats_analyze_index_level()`（`storage/innobase/dict/dict0stats.cc:794`）清楚体现了 InnoDB 如何采样索引并计算统计；`estimate_rowcount()`（`sql/sql_optimizer.cc:5936`）则把“优化器如何把统计翻成行数估计”这一层直接暴露出来。这些锚点共同支撑“优化器在估算，不是在逐行提前执行”这句判断。

### 4. 一个更具体的失败场景：索引明明没坏，计划却突然变差

想象一张订单表，原本 `status='PAID'` 只占很小比例，走这个索引看起来很划算。后来业务策略变了，90% 订单都很快进入 `PAID`，但统计信息还是旧的：

- 优化器还以为 `PAID` 非常稀疏；
- 于是坚持走二级索引；
- 实际上它会扫出大量行、再大量回表；
- 最后比全表扫描还难看。

这时最危险的误判是：“索引坏了。” 真实情况往往是：**索引没坏，优化器对索引效果的估计坏了。**

### 5. 统计信息为什么不能被当成“实时真值表”

这一点尤其重要。很多工程师第一次看到 `innodb_table_stats` / `innodb_index_stats` 之类对象时，会自然把它们当成数据库内部的一组精确监控表。

更准确的理解是：它们属于优化器视角的统计模型，不是实时逐行真值。里面的数字：

- 可能来自采样；
- 可能有误差；
- 可能滞后；
- 目的首先是帮助优化器估算，而不是给你提供逐条精确盘点。

### 6. 本节最该记住的结论：优化器并不直接知道哪条路径一定最快，它靠的是表/索引统计信息与成本模型做近似判断；`ANALYZE TABLE` 的价值在于刷新这套近似世界观，而不是神奇地修好 SQL

一句最短人话是：**优化器像导航软件，统计信息就是路况模型；地图过期了，路线就会开始走歪。**

## 三、Histogram：当“平均值”不够时，优化器需要一张列值分布图，但它仍然只是近似，不是神谕

### 1. 第三个朴素误解：只要有索引统计里的不同值个数，优化器就已经足够聪明

如果一列有 100 个不同值，你很容易会脑补：那平均下来每个值差不多 1% 的行，优化器估算应该也八九不离十。

问题在于，真实数据分布经常不是平均的。比如：

- 99% 的行都是 `status='PAID'`；
- 只有 1% 落在其他状态；
- 或某个 `tenant_id` 特别大、吞掉了大部分行。

这时只知道“不同值个数”几乎等于没用，因为真正决定计划的是分布，而不是平均值本身。

### 2. Histogram 的价值：把“平均世界观”升级成“分桶后的近似分布图”

Histogram 真正补的是这层空白。它不再只给优化器一个“这列有多少不同值”的数字，而是给它一张更像分布图的东西：

- 哪些值或值域更常见；
- 哪些比较稀有；
- 某个谓词大概会命中哪一桶。

```text
列分布
  → 分桶（例如 singleton / equi-height）
  → 记录不同桶的频率或范围

WHERE status = rare_value
  → 估算更接近真实选择性
```

这让优化器终于不再只能靠“平均每个值差不多”的朴素模型。

### 3. Histogram 不是索引，也不是逐行真知

这一步必须说透。Histogram 最容易被误讲成两种极端：

- 一种是把它讲成“又一类索引”；
- 另一种是把它讲成“知道列里每个值精确有多少行”。

这两种都不对。Histogram：

- 不会替你把查询路径直接变成可导航结构；
- 它只是改进优化器估算；
- 它依然是采样、分桶、近似表达。

也就是说，它帮助的是“选谁”，不是“怎么查”。

### 4. 一个更具体的失败场景：低基数状态列在高度倾斜时，平均值把优化器带进沟里

假设订单表里：

- `status='PAID'` 占 99%；
- `status='FAILED'` 占 1%。

如果优化器只有平均基数概念，它会把这列理解成“每个状态差不多都占一些”，从而高估或低估某些查询的过滤性。于是：

- 查询 `status='FAILED'` 时，它可能没意识到这其实非常稀疏；
- 查询 `status='PAID'` 时，它又可能误以为这个条件仍有明显过滤力。

Histogram 存在的意义，就是让优化器至少知道：这些值分布根本不平均。

### 5. 为什么有 Histogram 仍然不保证计划一定正确

这正是另一个必须掐掉的误解。Histogram 很有用，但它仍然只是近似模型：

- 分桶本身会损失精度；
- 采样会带来误差；
- 列之间相关性常常超出单列 Histogram 能表达的能力；
- 参数化查询、Join 相关性和成本模型仍然会继续引入偏差。

所以 Histogram 不是“保证计划正确”的神谕，而是“让平均值模型别太离谱”的补丁。

证据位上，这层现在也能落到真实源码：`update_histogram()`（`sql/sql_admin.cc:621`）、`send_histogram_results()`（`sql/sql_admin.cc:349`）与 `handle_histogram_command()`（`sql/sql_admin.cc:1625`）体现了 Histogram 如何被更新和管理；`Column_statistics_impl::histogram()`（`sql/dd/impl/types/column_statistics_impl.h:112`）则说明列统计作为独立对象进入数据字典。它们共同支撑“Histogram 是列分布统计对象，不是查询结构本身”的判断。

### 6. 本节最该记住的结论：Histogram 在统计信息只有平均值不够时，给优化器一张近似分布图；它改善的是选择性估算，不是直接提供索引能力，也不保证每次都估对

一句最短人话是：**平均身高告诉不了你“160cm 以下有多少人”，Histogram 至少给优化器一张分桶后的身高分布图。**

## 四、Online DDL：`INSTANT`、`INPLACE`、`COPY` 真正区分的，不是谁“高级”，而是谁在为结构变更买单、谁会被卡住

### 1. 第四个朴素误解：Online DDL 就是“在线改表，不锁、不停机、没代价”

这几乎是线上 DDL 最经典的误解。很多人一听“在线 DDL”，就会脑补成：

- 业务继续跑；
- 表结构后台自己改；
- 大家互不影响。

现实没有这么温柔。所谓 Online DDL，真正要回答的是：

- 这次变更需不需要重写整表；
- 需不需要后台扫描或构建新索引；
- 最后的元数据切换会不会卡住别人；
- 复制、磁盘空间和后台 I/O 会不会先被拖爆。

所以“在线”只是一个方向，不是一张免死金牌。

### 2. `INSTANT`：最便宜，但它之所以便宜，正因为它只改了一小部分东西

`INSTANT` 最容易被误解成“最先进所以最好”。更准确的说法是：它很便宜，恰恰因为它常常只改元数据，不重写整表，也不大动数据页。换句话说，它不是“什么都能在线搞”，而是“只有那些足够像元数据变更的操作，才能便宜到这个程度”。

证据位上，这层已经可以落到 `commit_instant_ddl()`（`storage/innobase/dict/dict0inst.cc:197`）与 `dd_commit_inplace_update_instant_meta()`（`storage/innobase/handler/handler0alter.cc:4193`）这些真实路径：它们共同支撑“INSTANT 的便宜来自更偏元数据侧，而不是重写整表”这句判断。

### 3. `INPLACE`：不一定复制整表，但可能在后台真正重建、扫描、吃 I/O

`INPLACE` 的危险就在于名字太容易让人误以为“都在原地轻改几下”。实际上很多 `INPLACE` 操作虽然不需要像 `COPY` 那样完整拷出一份新表，但仍然可能：

- 在引擎内部重建索引；
- 扫描大量数据页；
- 长时间吃掉后台 I/O；
- 在最后切换阶段卡住元数据锁。

所以 `INPLACE` 的本质更像“尽量让重活留在引擎内部完成”，而不是“没有重活”。

### 4. `COPY`：不是“老实现”，而是最诚实地承认“这次变更就是要搬一整套库存”

`COPY` 看起来笨，但它其实很诚实：

- 建一张新表；
- 把老表数据整批搬过去；
- 再在合适时机切换。

代价当然大：空间翻倍、复制拓扑受影响、锁和切换时延都更显著。但有些变更就是没有更轻的路可走。此时 `COPY` 不是“过时做法”，而是对代价最直接的承认。

### 5. Online DDL 生命周期真正要看的，是 MDL、后台构建和最后切换这三刀

这一节最重要的不是背 `ALGORITHM` 名字，而是把生命周期拆成三刀：

1. **开场**：要拿哪些 MDL，谁会被挡住；
2. **中段**：后台有没有扫描/构建/复制，I/O 和复制会不会抬头；
3. **收尾**：最后的元数据切换是否还要短暂封门。

```text
DDL 开始
  → 获取 MDL
  → prepare / build / catch-up
  → commit metadata
  → 释放或升级锁
```

证据位上，这层已经可以落到 `mysql_inplace_alter_table()`（`sql/sql_table.cc:13329`）、`prepare_inplace_alter_table()`（`storage/innobase/handler/handler0alter.cc:1433`）、`commit_inplace_alter_table()`（`storage/innobase/handler/handler0alter.cc:1588`）和 `commit_instant_ddl()`（`storage/innobase/dict/dict0inst.cc:197`）这些真实路径。它们共同支撑“Online DDL 真正区分的是谁在买单、结构在哪一层被改”这条主线。

### 6. 一个更具体的失败场景：DDL 看着在线，业务却在最后切换时突然全部卡住

最典型的线上翻车不是“DDL 一开始就报错”，而是：

- 你看着它在后台慢慢跑，以为很平稳；
- 前面几十分钟业务也没明显波动；
- 结果到最后 commit metadata / rename / 切换阶段，元数据锁一收紧；
- 一个长事务或空闲事务正好占着锁；
- 整批 DML / SELECT 开始排队。

于是使用者的体感是：“明明都快结束了，怎么突然全站卡住？”

这恰恰说明 Online DDL 的危险从来不只在“中段跑多久”，还在最后那一刀切换。你不把生命周期拆开，就会在最需要警惕的时刻放松戒备。

### 7. 本节最该记住的结论：`INSTANT/INPLACE/COPY` 的区别，不是谁更先进，而是谁在结构变更时为元数据、后台重建、空间和切换代价买单；Online DDL 不等于无锁无代价

一句最短人话是：**INSTANT 像改目录，INPLACE 像营业中换货架，COPY 像开新店搬库存；都可能在交接时短暂封门。**

## 五、MDL 与 pt-online-schema-change：真正的上线风险不是“DDL 能不能跑”，而是“跑到哪一步时谁会被挡住、谁会被拖慢、谁能撤回”

### 1. 第五个朴素误解：只要不用原生 DDL、改用 pt-online-schema-change，就等于彻底没锁、没风险

这和“Online DDL = 无代价”是同一种心态：想找一个工具或模式，一劳永逸地屏蔽所有上线风险。

可现实里的风险从来不是“用了哪个名字的工具”这么简单，而是：

- 你是否清楚自己现在是在拿什么锁；
- 后台是否在吃大量 I/O；
- 复制延迟有没有被拉长；
- 触发器会不会让写路径继续变重；
- 出问题时有没有暂停和回滚策略。

### 2. MDL：不是“DDL 才有的古怪锁”，而是任何表结构变更都绕不过去的门禁

只要你要改表结构、切换元数据，系统就必须先确保“不会有人在你改到一半时，还按旧定义继续冲进来”。这就是 MDL 最值钱也最容易让线上卡死的地方。

- 长事务可能一直不放手；
- 空闲事务也可能意外拖住门；
- 你明明只想最后短暂切一下，却发现那一下一直切不进去。

证据位上，这层可以直接落到 `open_table_get_mdl_lock()`（`sql/sql_base.cc:2596`）和 `MDL_lock::can_grant_lock()`（`sql/mdl.cc:2396`）这类路径：它们共同支撑“DDL 是否会被挡住，根本上是门禁何时能放行”的判断。

### 3. pt-online-schema-change：不是“真正零锁”，而是把风险重新分配到影子表、触发器和最终切换上

pt-osc 真正做的，不是让 DDL 消失，而是把这次结构变更改写成另一套工程流程：

```text
创建影子表
  → 在新表上应用目标结构
  → 触发器同步新老表增量变更
  → 分批复制历史数据
  → 最后短暂 rename 切换
  → 清理旧表
```

这样做能绕开某些原生 DDL 的局限，但代价也很真实：

- 触发器会给写路径持续加税；
- 分批复制会争用 I/O；
- 最终 rename 还是要面对 MDL 切换；
- 外键、复制拓扑和失败恢复都会变复杂。

所以 pt-osc 不是“免费在线”，而是**把风险从原生 DDL 的某些时刻，换成一条更长、更可控、但同样要持续观察的影子迁移链。**

### 4. 一个更具体的失败场景：影子表跑得很顺，复制延迟却悄悄越拉越长

很多时候，业务不会立刻在主库上报错，真正先冒头的是从库或复制链：

- 主库还在分批复制历史数据；
- 触发器继续同步增量写；
- 主库 I/O 账看着还能扛；
- 可从库回放开始变慢，延迟悄悄被越拉越长。

等你只盯主库时，问题已经在复制侧先烂掉了。这就是为什么上线验证必须把“复制延迟”和“回滚策略”也列入观测，而不是只看主库 TPS。

### 5. 所以上线真正要看的，不只是“能不能执行”，而是“有没有一套可停、可观、可回退的流程”

一个成熟的上线判断，至少要同时看：

- 锁：谁在挡、谁会被挡；
- I/O：后台构建或影子复制是否已经吃满；
- 复制：延迟、追平时间和下游风险；
- 回滚：如果卡在中途，如何暂停、限速、放弃或切回。

也就是说，DDL 上线从来不是“跑了一个命令”，而是一场带观测和撤退路线的工程操作。

### 6. 本节最该记住的结论：MDL 决定“最后那道门什么时候开”，pt-online-schema-change 决定“你把风险分摊到哪些中间步骤”；它们都不是免死金牌，只是在用不同方式重排上线成本

一句最短人话是：**影子表方案像营业中搭新仓库：旧仓库继续接单，触发器同步新货，最后切门牌；真正的难点不是能不能搭，而是全程谁在替你付税。**

## 六、把本篇收成一张图：索引系统同时有查询结构、估算模型和变更工程三层现实

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：为什么普通索引查不到“包含哪些词”，优化器又可能明明有索引还估错行数，DDL 看着在线却仍然会把业务卡住。答案现在已经闭环了。

因为索引系统从来不只是“一棵树”：

- **查询结构层**：FULLTEXT 把“整列值 → 记录”的世界改写成“词项 → 文档集合”的倒排世界；
- **估算模型层**：统计信息和 Histogram 让优化器对“会返回多少行、哪个计划更便宜”形成近似世界观；
- **变更工程层**：`INSTANT/INPLACE/COPY`、MDL、影子表和触发器决定这套结构怎样在线演进，而不把业务直接拖死。

把这一切压成最短总图，就是：

```text
查询结构：
  B+Tree / FULLTEXT

估算模型：
  ANALYZE / table-index stats / histogram
  → 优化器选择执行计划

结构变更：
  INSTANT / INPLACE / COPY / 影子表方案
  → MDL / I/O / replication / rollback 一起决定上线成本
```

所以本篇最该记住的一句话是：**索引系统同时有“能不能查”“会不会被选”“能不能安全改”三层现实；结构、统计和 DDL 不是附属专题，而是索引生命周期的三个面。**

## 七、几个最容易说错的地方

### FULLTEXT 是不是“更快的 LIKE”？

不是。它先改写的是查询语义和建索引方式：分词、停用词、最小词长、相关性与布尔模式都会影响结果。

### 有了统计信息和 Histogram，优化器是不是就能总选对计划？

不是。它们都是估算模型，不是逐行真值；采样、分桶、列相关性和成本模型都可能继续让它估错。

### ANALYZE TABLE 是不是刷新一次就会让 SQL 稳定变快？

不是。它更新的是优化器的地图，不是直接优化数据本身；地图更新后，计划可能变好，也可能因为采样变化而换成另一条路。

### Online DDL 是不是就等于不阻塞、不停机？

不是。它只是在不同算法下重排阻塞和代价；MDL、最后切换、复制和 I/O 仍然可能把业务卡住。

### pt-online-schema-change 是不是原生 Online DDL 的无脑替代？

不是。它只是把风险从原生 DDL 的某些时刻，换成影子表、触发器、分批复制和最终 rename 的整条工程流程。

## 收束：索引真正难的地方，不是“建不建”，而是“语义、估算和变更三层现实要一起成立”

回到开头那个问题：普通索引为什么查不到“包含哪些词”，优化器为什么会估错，DDL 为什么会看着在线却把业务卡住？因为索引系统真正管理的从来不是单一的数据结构，而是三层同时在说话的现实：全文搜索先改语义，统计与 Histogram 改优化器世界观，Online DDL 与 MDL/pt-osc 则在重排上线时谁来买单。

这就是为什么说：**索引生命周期不是“建出来就完了”，而是“先决定查询结构，再持续喂优化器正确地图，最后还得让结构能安全地变”。** 只要这三层心智站稳，后面进入 MVCC、锁、隔离级别和死锁时，你就不会再把“为什么计划会变”“为什么 DDL 会卡住”误听成两个无关问题，而会知道它们其实都在事务与并发世界里继续追问同一件事：谁能看、谁能改、谁要等谁。
