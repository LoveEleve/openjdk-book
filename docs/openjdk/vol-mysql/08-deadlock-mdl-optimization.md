## 现在真正该问的，不再是“锁会不会等待”，而是“这个等待到底保护了什么、谁持有、谁被挡、是否已经形成环，以及我应该减少哪一种成本”

上一篇已经把并发控制的主线钉住了：

- 普通一致性读用 ReadView + Undo 历史链，尽量不为了别人的写入排队；
- 当前读和写用 Record/Gap/Next-Key/Insert Intention Lock，保护现在和未来的记录范围；
- 隔离级别决定视图什么时候固定、当前读什么时候要看最新并加锁；
- 索引访问路径决定锁范围，没索引或范围太宽时，锁影响可能一起放大。

这些结论能解释很多行锁现象，但还解释不了线上最难看的另外几类问题：

- 一个事务只执行过 `SELECT`，却迟迟不提交，为什么 `ALTER TABLE` 一直进不去；
- 两个事务都在等待，为什么一个只是慢，另一个却会被 MySQL 主动回滚；
- SQL 行锁看起来不多，所有线程却在 InnoDB 内部 semaphore、mutex 或 rw-lock 上耗着；
- `innodb_lock_wait_timeout` 调大以后，业务为什么反而更久才恢复；
- `NOWAIT` / `SKIP LOCKED` 为什么有时是解药，有时却会改变业务结果。

所以本篇先把锁问题拆成三层：

1. **对象定义层：MDL**，保护表、库、对象定义和 DDL 切换；
2. **数据访问层：行锁/范围锁**，保护记录、间隙和当前读/写路径；
3. **引擎结构层：mutex/rw-lock**，保护 Buffer Pool、字典、索引和其他内部共享结构。

先把总图记住：

```text
症状：SQL 慢 / DDL 卡 / deadlock
  → 先区分 MDL、行/范围锁、内部锁
  → 再收集持有者、等待者、SQL、索引、事务时间线
  → 找长事务 / 大范围扫描 / 资源获取顺序 / 内部热点
  → 缩短事务、缩小范围、统一顺序或改变等待语义
  → 复测吞吐、P99、死锁率、复制影响和业务正确性
```

这篇最该先记住的一句话是：**锁排障第一步不是调大 timeout，而是判断“哪一层锁、谁持有、谁等待、等待关系是否成环”；只有先定责，优化动作才不会把错误的成本继续放大。**

## 一、MDL：DDL 为什么会被一个“什么都没做”的事务卡住

### 1. 最朴素的错误世界：事务当前没有运行 SQL，就不可能还持有任何会影响别人的锁

这是线上最容易误判的一句话：

“这个连接现在是 Sleep，线程又没跑 CPU，怎么可能挡住 DDL？”

问题在于，“当前是否正在执行 SQL”和“事务是否仍然持有对象访问生命周期”不是一回事。一个事务可能：

- 先执行了一条普通 `SELECT`；
- 读完结果后一直不提交；
- 连接池把它留在空闲状态；
- 但它的对象定义访问关系和事务生命周期仍然没有完整收口。

此时另一个会话执行 `ALTER TABLE`，需要拿更强的元数据锁，就可能一直排队。业务看到的表象是“DDL 卡住”，真正的持有者却是一条看起来什么都没做的空闲连接。

### 2. MDL 保护的不是行内容，而是“大家对这个对象的定义应该保持一致”

行锁关心的是某条记录、某个间隙能不能被并发修改；MDL 关心的是：

- 这个表的列定义是什么；
- 表名、索引、元数据结构是否正在切换；
- 一个语句开始使用某个表定义后，别人能不能在中途把它替换掉。

所以 MDL 是对象定义层的门禁。它不是 InnoDB 的 Record Lock，也不是“再大一点的行锁”。它保护的是“表这个对象在被使用期间，定义别突然换成另一个世界”。

### 3. 普通读与 DDL 为什么申请不同强度的 MDL

教学上可以先用一个简化模型理解：

```text
普通读 / 写
  → 申请相容的 shared MDL
  → 使用表定义并执行语句
  → 在事务 / 语句生命周期结束时释放或转换

DDL
  → 申请更强的 exclusive MDL
  → 等待冲突的 shared MDL 释放
  → 执行结构变更 / 切换定义
  → 释放或转换 MDL
```

这个图不是某一版源码的固定调用栈，而是为了说明强弱关系：普通访问需要在“有人使用定义”期间保持一致，DDL 则需要更强的排他门禁去切换定义。

真实源码锚点上，`open_table_get_mdl_lock()`（`sql/sql_base.cc:2596`）体现了打开表时获取 MDL 的入口；`MDL_lock::can_grant_lock()`（`sql/mdl.cc:2396`）则直接落在“当前请求能不能被授予”这一层。两处共同支撑“DDL 卡住首先是门禁授予问题，而不是表里某一行恰好被锁住”的判断。

### 4. DDL 入口就可能被挡，不要只盯最后元数据切换

MDL 风险至少有两个时间点：

- **开场拿门票**：DDL 一开始就申请 MDL，如果已有长事务或空闲事务持有冲突锁，它可能根本进不了准备阶段；
- **收尾切门牌**：DDL 中段已经做了大量后台工作，最后提交元数据时又要升级或重新申请更强门禁，此时也可能被新的持有者挡住。

这两个事故的体感不同：

- 入口被挡：DDL 看起来“根本没开始”，等待者一直挂着；
- 收尾被挡：DDL 已经跑了很久，业务却在最后切换时突然一起排队。

如果排障只看 DDL 自身的进度，就会把第一类误判成“DDL 执行慢”，把第二类误判成“突然出现了全库故障”。真正要问的是：**它卡在申请门票，还是卡在最后换门牌。**

这里还要再补一个容易被低估的放大链：DDL 自己被挡住，往往不是终点，而是起点。只要它已经在同一对象上排队，后续新的查询、写入或其他变更请求，也可能继续在这条门禁队列上累积，最后把“一个 ALTER 在等”放大成“整批业务都像突然变慢”。所以很多线上 DDL 事故表面看起来像“最后某一步突然全站抖动”，本质上却是前面一条看不见的 MDL 队列已经堆了很久。

### 5. 一个更具体的失败场景：连接池里的空闲事务把全站 DDL 卡在门口

想象一个连接池：

- 某个请求开启事务并执行 `SELECT`；
- 业务异常后没有提交或回滚；
- 连接被放回池里，但事务仍然活着；
- 运维随后执行 `ALTER TABLE orders ADD COLUMN ...`。

此时你可能看到：

- ALTER 会话长期等待；
- CPU 很低；
- 表上的普通查询似乎仍在运行；
- `SHOW PROCESSLIST` 里真正的问题连接甚至显示为 `Sleep`。

如果只盯当前 SQL，根本找不到原因。必须把 MDL 持有者、事务开始时间、连接池归属和等待者一起拉出来看。

### 6. 本节最该记住的结论：MDL 保护的是对象定义，不是行内容；空闲事务也可能持有影响 DDL 的生命周期关系，DDL 既可能在入口申请时被挡，也可能在最后切换时被挡

一句最短人话是：**住户不在客厅走动，不等于他已经把钥匙交回物业；装修队要拆墙，先得确认整栋楼的钥匙都在。**

## 二、死锁与 wait-for graph：等待不是问题本身，等待关系成环才是系统必须主动打破的灾难

### 1. 第二个朴素误解：两个事务都在等，等久一点总有一个会先完成

这在单向排队场景里成立：T2 等 T1，T1 最终释放，T2 就能继续。但死锁不是“队列长”，而是等待关系形成了闭环：

- T1 持有 A，等待 B；
- T2 持有 B，等待 A。

此时双方都在等对方先放手，而对方正因为等你所以无法放手。无论 timeout 设成 1 秒还是 1 小时，循环依赖本身都没有被消除。

### 2. wait-for graph：把“谁在等谁”变成一张可以检查环的图

死锁检测最值得记住的不是某个报错字符串，而是它背后的图模型：

```text
T1
  持有 row A
  → 请求 row B
  → 等待 T2

T2
  持有 row B
  → 请求 row A
  → 等待 T1

wait-for graph
  T1 → T2
  T2 → T1
  → 出现环
  → 选择 victim
  → 回滚 victim
  → 释放锁
  → 另一事务继续
```

真实源码可以落到 `lock_wait_build_wait_for_graph()`（`storage/innobase/lock/lock0wait.cc:651`）和 `lock_wait_handle_deadlock()`（`storage/innobase/lock/lock0wait.cc:1133`）：前者构造等待关系，后者处理已经确认的死锁。而真正把被选中的牺牲者标记并从等待中撤下去，还可以继续落到 `lock_wait_rollback_deadlock_victim()`（`storage/innobase/lock/lock0wait.cc:693`）。这三处连起来，才把“成环 → 选 victim → victim 被回滚并释放等待”这条主线讲完整。

### 3. 为什么 MySQL 必须选择一个 victim，而不是让所有事务一起失败

死锁已经发生后，系统必须打破环。最直接的方式是回滚其中一个事务，让它释放手里的锁：

- 另一个事务获得继续前进的机会；
- 被回滚事务返回错误，应用负责重试或放弃；
- 资源不会因为循环等待一直被占住。

Victim 的选择不是“谁报错都一样”。回滚一个已经修改很多数据的事务，代价可能很大；但具体 victim 选择会结合实现、事务状态和回滚成本变化，不能把某个经验口诀当成跨版本契约。

### 4. 为什么把 `lock_wait_timeout` 调大不能治死锁

`lock_wait_timeout` 处理的是“等了多久还没成功”的超时边界，不是“等待图有没有环”。把它调大通常只会：

- 让死锁参与者占住资源更久；
- 延后错误返回；
- 放大连接堆积和业务尾延迟；
- 让恢复窗口变得更难控制。

所以死锁处理的正确方向是：让 InnoDB 检测环并回滚 victim，应用把 deadlock 当作可重试错误，同时保证操作幂等、重试次数有界、事务边界清楚。

### 5. 一个更具体的失败场景：两个接口各自按不同顺序更新同一批订单

假设接口 A 按订单号从小到大更新两行，接口 B 按从大到小更新同两行：

```text
接口 A：lock order 10 → request order 20
接口 B：lock order 20 → request order 10
```

高并发下，A 和 B 很容易各自拿到第一把锁，然后互相等第二把。你可能在线上看到：

- 两条 SQL 都不复杂；
- 单条执行计划也没有明显异常；
- 但某些请求突然报 deadlock；
- 重试后大多又能成功。

这不是数据库随机抽风，而是两个业务路径把资源获取顺序写成了相反方向。

### 6. 本节最该记住的结论：死锁是 wait-for graph 出环，不是普通等待变慢；检测要打破环、回滚 victim，应用则必须把回滚后的重试做成有界且幂等

一句最短人话是：**两辆车互相堵住时，加长红灯时间不会让道路变宽，必须让一辆车倒车。**

## 三、死锁与 MDL 诊断：一条错误日志只是结果，真正的根因藏在持有者、等待者、访问路径和事务时间线里

### 1. 最朴素的错误世界：看到 `Deadlock found` 或一个 ALTER 等待，就知道根因了

错误信息只能告诉你结果：

- 有一个事务被回滚了；
- 或者一个 DDL 正在等待；
- 但它不会自动替你解释谁先拿了什么、谁又请求了什么、为什么这个锁一直不释放。

所以诊断不能只看一行结果，而要把多个证据拼成同一条时间线。

### 2. 死锁诊断：从 `LATEST DETECTED DEADLOCK` 还原两条资源路径

死锁现场至少要收集：

- 事务 ID、线程 ID、SQL；
- 当前持有的锁；
- 正在等待的锁；
- 索引、记录、间隙和锁模式；
- 哪个事务最终被选为 victim。

`SHOW ENGINE INNODB STATUS` 中的 `LATEST DETECTED DEADLOCK` 提供了非常重要的现场线索，但它是结果快照，不是完整历史。你还要把它和实际 SQL、索引路径、事务开始时间一起对照。

### 3. MDL 诊断：从 metadata_locks 找到“谁挡住了门”

MDL 和 InnoDB 行锁不是同一张表、同一套对象。排查 DDL 时，要单独看：

- 哪个线程持有对象定义锁；
- 哪个线程在等待更强 MDL；
- 对象名称和锁类型是什么；
- 持有者的事务开始了多久；
- 它当前是否只是 `Sleep`。

真实源码上，`open_table_get_mdl_lock()`（`sql/sql_base.cc:2596`）和 `MDL_lock::can_grant_lock()`（`sql/mdl.cc:2396`）说明了打开对象与授予门禁的路径；线上则应把 `performance_schema.metadata_locks`、threads/processlist 与事务视图联合看。

### 4. 为什么必须把 EXPLAIN/索引路径放进锁诊断

锁范围沿实际索引访问路径建立。一个看似简单的范围 UPDATE，如果没有合适索引，可能扫描和锁住远超业务预期的记录范围；一个二级索引查询，如果大量回表，又可能放大锁持有时间。

所以诊断不能只看“锁名”，还要问：

- 实际用了哪棵索引；
- 扫了多少行；
- 是精确查找还是范围扫描；
- 是否发生大量回表；
- 事务在锁住之后做了多少非数据库工作。

### 5. 一个更具体的诊断顺序：先定层，再画图，最后回到业务代码

遇到“SQL 慢 / DDL 卡 / deadlock”时，可以按这个顺序：

```text
第一步：分层
  MDL? 行/范围锁? 内部 mutex/rw-lock?

第二步：收证据
  持有者 / 等待者 / SQL / 索引 / 事务开始时间

第三步：画关系
  谁持有资源
  谁等待资源
  是否成环

第四步：回到业务
  事务是否太长
  锁顺序是否不统一
  索引是否过宽或缺失
  是否把网络/日志/计算放在持锁区间内
```

这一顺序很重要，因为“调大超时”“加连接”“重启数据库”都可能只是把症状暂时压下去，却没有改变资源关系。

可以把这条顺序再压成一句更好复述的口诀：**先判断锁对象，再看访问路径，最后回到业务顺序。** 先分清是 MDL、行/范围锁还是内部锁；再看实际 SQL 走了哪棵索引、扫了多大范围、是否大量回表；最后再追业务代码里事务边界、拿锁顺序和非数据库工作是不是被塞进持锁区间。先后顺序不能反过来，不然你很容易一上来就改 SQL 或改参数，却连自己在和哪一层资源打架都没看清。

### 6. 本节最该记住的结论：死锁日志、metadata_locks、事务视图和 EXPLAIN 必须拼在一起看；错误信息只是判决，持有者/等待者/索引路径和时间线才是案情

一句最短人话是：**排查像看交通事故重播：不仅要知道两车撞了，还要知道谁先占哪条车道、信号灯什么时候变、后车为什么继续驶入。**

## 四、锁优化：减少等待不是盲目加并发，而是减少持有时间、缩小范围、统一顺序或明确改变等待语义

### 1. 缩短锁生命周期：事务越长，锁和死锁窗口越大

最先该优化的通常不是某个神秘参数，而是事务边界：

- 事务里不要做长时间网络调用；
- 不要拿着数据库锁去等待用户输入；
- 不要在事务里塞大量无关计算；
- 能小批量提交的，不要把所有任务包成一个巨型事务。

事务越长，持锁时间越长，别人等你的时间越长，等待图形成环的窗口也越大。

### 2. 缩小锁范围：合适索引往往同时改善查询和锁影响

索引不只是让查询快，也决定当前读/写需要扫描和保护多大范围：

- 精确索引可以减少扫描记录；
- 合适的复合索引可以缩小范围；
- 没有索引时，扫描和锁影响可能一起扩大。

但加索引也不是无脑答案。它可能增加写维护、页分裂、空间和 Buffer Pool 压力，所以优化时要把锁收益和索引维护成本一起算。

### 3. 统一资源获取顺序：让所有事务按同一方向拿锁

如果业务路径都按主键从小到大处理，那么 T1/T2 更不容易因为顺序相反形成 ABBA。统一顺序适用于：

- 批量更新多行；
- 转账同时修改多个账户；
- 订单与库存跨表更新；
- 多资源分阶段占用。

它不是要求所有事务都串行，而是让它们在必须竞争时遵守同一套顺序，降低等待图成环概率。

### 4. NOWAIT 与 SKIP LOCKED：把“必须等”改写成“立即失败”或“跳过”

这两种语义非常强，但不能只看吞吐：

- `NOWAIT`：遇到冲突立即报错，适合业务愿意快速失败并自行重试/降级的场景；
- `SKIP LOCKED`：跳过已经被锁住的行，适合特定任务队列，避免 worker 全部堵在同一批任务上。

它们改变的不只是等待时间，而是业务结果本身：

- NOWAIT 让等待变成错误；
- SKIP LOCKED 让当前查询故意不看完整集合。

这里最该钉住的一句是：**`SKIP LOCKED` 牺牲的是结果集完备性，不只是等待时间。** 你拿到的结果集，从定义上就不再代表“当前所有符合条件的对象”，而是“当前没被别人锁住、我此刻先能拿到的那一批对象”。

所以不能把它们当成“更快的锁配置”，必须确认业务能接受遗漏、乱序和重试。

### 5. 隔离级别调整：降低 Gap Lock 可能减少等待，但也会改变观察语义

从 RR 调整到 RC，有时可以减少某些 Gap Lock 和范围等待，但它也会改变一致性读和并发异常边界。你不能只因为“锁少了、吞吐高了”就直接切换隔离级别，还要验证：

- 业务是否能接受同一事务内不同语句看到不同提交状态；
- 当前读和普通读是否仍然满足正确性；
- 队列、扣款、库存等逻辑是否会被新的可见性窗口影响。

### 6. 一个更具体的失败场景：为了减少等待，改成 SKIP LOCKED，却悄悄漏处理任务

想象一个任务队列：

- worker A 锁住了任务 1，正在处理；
- worker B 使用 `SKIP LOCKED` 查询下一批任务；
- B 跳过任务 1，很快拿到任务 2、3。

吞吐可能上升，但如果调度器没有重试和最终确认机制，任务 1 可能因为异常、长时间处理或 worker 崩溃而被延迟很久。也就是说，SKIP LOCKED 的收益是减少等待，代价是结果集不再代表“当前所有符合条件的任务”。

证据位上，锁定读的精确行为应结合目标 MySQL 版本的语句实现、锁路径和文档核对；本篇只建立优化选择必须同时评估等待、顺序、遗漏和幂等的机制边界。

### 7. 本节最该记住的结论：锁优化不是“让更多线程同时冲”，而是缩短生命周期、缩小访问范围、统一资源顺序，或明确把等待改成失败/跳过

一句最短人话是：**优化锁像整理仓库：少拿一会儿、少封几排货架、按同一顺序取货，或者明确告诉工人没货就先走。**

## 五、InnoDB 内部锁与显式锁：数据锁之外，还有保护引擎共享结构的另一层并发现场

### 1. 第五个朴素误解：SQL 行锁不多，数据库就不可能还有严重锁竞争

这只说明你没有在看正确的层。InnoDB 内部还要保护：

- Buffer Pool 结构；
- 索引结构；
- 字典缓存；
- 日志和后台线程共享状态；
- 各种队列、链表和内部对象。

这些共享结构不一定对应一条用户表记录，所以 `data_locks` 或死锁日志未必能解释它们的全部等待。

### 2. mutex、rw-lock、spin 与 os_wait：内部锁类型和等待策略不是同一层概念

可以先用一个抽象模型理解：

```text
内部共享结构被访问
  → mutex / rw-lock：决定这是什么类型的互斥或读写保护
  → spin：短等待时先原地观察
  → os_wait：等待拉长后转入操作系统等待
```

这里必须把层级再钉清楚：**`mutex` 和 `rw-lock` 更像锁原语本身；`spin` 与 `os_wait` 更像这些锁在不同等待长度下采用的等待策略或阶段。** 把四者全压成同一层“锁类型”，会让读者误以为 `spin` 和 `os_wait` 也是可以与 mutex/rw-lock 并列选择的独立锁，而不是“同一把内部锁在短等待时先自旋、等太久再睡下去”的常见行为。

所以这不是把四个 API 当成同义词，而是在把“锁住什么”和“怎么等这把锁”这两层拆开。

### 3. 为什么内部锁等待不能只靠 SQL 行锁监控解释

一个线程可能没有等待任何记录，但在 Buffer Pool、索引、字典或日志内部结构上等待。另一个线程可能看起来 SQL 很短，却因为持有内部资源而让整个热点路径排队。

这类问题要结合：

- `SHOW ENGINE INNODB STATUS` 的 SEMAPHORES 线索；
- `perf` 看 CPU 是否烧在自旋；
- `ftrace`/bpftrace 看调用路径与调度；
- Buffer Pool、I/O、线程数和 workload 一起解释。

### 4. 显式表锁与用户级锁又是另一层

`LOCK TABLES`、`GET_LOCK()`、`FLUSH TABLES WITH READ LOCK` 等显式机制，不应和 InnoDB 行锁、MDL、内部 mutex 混成一套：

- 表锁保护的是更粗粒度的用户对象；
- `GET_LOCK()` 是应用自定义协调；
- FTWRL 还可能影响备份、DDL 和复制操作。

诊断时必须先问清“这把锁是谁创建的、保护什么对象、谁负责释放”。

### 5. 本节最该记住的结论：SQL 行锁只是并发现场的一层；内部 mutex/rw-lock 保护的是引擎结构，显式表锁/用户锁又是另一套对象，三者不能用同一张监控表解释

一句最短人话是：**你没看到有人堵在门口，不等于仓库里面没有人挤在同一条传送带旁。**

## 六、把本篇收成一张图：先分层定责，再用等待图和资源账本决定优化动作

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：DDL 为什么会被空闲事务卡住，两个事务为什么会互相等死，SQL 行锁不多时为什么内部仍可能拥堵。答案已经闭环了。

锁问题至少分三层：

- **MDL**：保护表、对象和定义切换；
- **Record/Gap/Next-Key**：保护数据记录和索引范围；
- **内部 mutex/rw-lock**：保护 InnoDB 自己的共享结构。

而诊断和优化要沿同一条路径走：

```text
症状
  → 分层：MDL / 行锁范围 / 内部锁
  → 收集：持有者 / 等待者 / SQL / 索引 / 事务时间线
  → 建图：谁持有资源、谁等待资源、是否形成环
  → 处理：victim 回滚 / 缩短事务 / 缩小范围 / 统一顺序
  → 选择：NOWAIT / SKIP LOCKED / 隔离级别调整
  → 验证：吞吐 / P99 / 死锁率 / 复制延迟 / 业务正确性
```

所以本篇最该记住的一句话是：**锁排障第一步不是调大 timeout，而是确认锁属于哪一层、等待关系是否成环、资源获取顺序是什么；优化也不是盲目加并发，而是让正确的等待更短、让不该等待的路径更早失败或安全跳过。**

## 七、几个最容易说错的地方

### 空闲事务什么都没做，是不是就不可能阻塞 DDL？

不是。它可能仍然持有对象定义和事务生命周期相关的锁，DDL 需要把持有者、等待者和事务开始时间一起查出来。

### 把 `innodb_lock_wait_timeout` 调大，是不是就能治死锁？

不能。timeout 只改变等待多久失败，不会消除 wait-for graph 里的循环依赖。

### 死锁是不是数据库设计失败，应用不需要重试？

不是。死锁是并发资源获取的正常风险，应用应把它当作可重试错误，并保证重试有界、操作幂等。

### 加索引是不是一定能减少锁等待？

不一定。索引可能缩小扫描和锁范围，也可能增加写维护、页分裂和缓存压力；必须结合实际访问路径验证。

### `NOWAIT` / `SKIP LOCKED` 是不是只改变性能，不改变业务结果？

不是。NOWAIT 把等待改成错误，SKIP LOCKED 故意跳过已锁对象，都会改变业务语义。

### SQL 行锁没问题，是不是说明 InnoDB 没有锁竞争？

不是。内部 mutex/rw-lock、spin/os_wait 和显式表锁可能在另一层形成瓶颈。

## 收束：锁优化的本质不是让所有人都更快，而是让每种等待都落在正确的层、正确的时间和正确的业务语义里

回到开头那个问题：一条 ALTER 被卡住，业务查询也变慢时，究竟是哪一层出了问题？现在答案已经完整闭环了。先看 MDL 是否在入口或收尾被长事务挡住，再看行/范围锁是否因为索引路径过宽形成等待，最后再看 InnoDB 内部 mutex/rw-lock 是否在结构热点上拥堵。

两个事务互相等待时，别把 timeout 当成解药；先看 wait-for graph 是否成环，让 InnoDB 回滚 victim，应用再用有界、幂等的方式重试。减少锁等待时，也不要只追求更多并发：缩短事务、缩小扫描范围、统一资源顺序，或者明确使用 NOWAIT/SKIP LOCKED，都是在改变不同的等待成本和业务语义。

这就是为什么说：**锁问题不是一条“锁慢了”的错误信息，而是一张资源关系图。** 只有把 MDL、行锁、内部锁、索引路径、事务边界和业务重试放到同一张图里，死锁、DDL 阻塞和内部热点才会从“偶发玄学”变成可以诊断和治理的工程问题。
