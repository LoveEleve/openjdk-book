## 现在真正该问的，不再是“故障了怎么办”，而是“先切流、先修副本、还是先做恢复，以及怎么判断恢复真的完成了”

前面几篇已经建立了一套完整的复制与故障切换心智。你已经知道：

- 复制是五段接力，位点/GTID 描述进度，半同步缩小确认窗口；
- 并行复制的本质是证明事务不冲突，MTS 运行时依赖 coordinator/worker/checkpoint 协调；
- 故障切换的核心是确认候选副本的事务集合和角色语义，而不只是延迟最小。

如果只停在这里，你仍然可能在一场真实事故里反复踩坑：

- 主库宕机了，是先切流量还是先确认事务集合？
- 误删数据后，应该用逻辑备份、物理备份，还是直接回放 binlog？
- 复制报错了，应该先跳过还是先排查数据漂移？
- 切换成功后，怎么判断新主库真的“恢复了”？

所以本篇把故障处理的完整流程分五段：

1. **计划切换**：在受控窗口内平稳切主；
2. **紧急故障转移**：先隔离旧主防脑裂，再选最完整副本；
3. **复制中断与数据不一致修复**：先区分链路、GTID 和数据内容三类问题；
4. **备份与 PITR**：全量备份 + binlog 回放，才能恢复到任意时间点；
5. **基准测试与恢复后验收**：数据回来了，不等于服务就恢复了。

先把总图记住：

```text
planned switchover
  或 emergency failover
  → 防脑裂 / 选副本
  → 检查 GTID / Relay / 延迟 / 角色
  → 必要时 checksum / sync / 重建
  → 用全量备份 + binlog 做 PITR
  → 恢复后压测 / 验收 / 监控
```

这篇最该先记住的一句话是：**故障处理不是“把服务拉起来”就结束，而是先确认事务集合和防脑裂，再选择修复或恢复路径，最后验证性能与容量，才算真正恢复。**

## 一、Planned Switchover：在受控窗口内平稳切主，核心是“先追平、再冻结、再切流、后验证”

### 1. 最朴素的错误世界：计划切换就是把从库设成主库，再把应用指向它

这个直觉在最简单场景里也许能工作，但离“平稳切换”还差得很远。因为：

- 候选副本是否真的追平了主库的事务集合；
- 主库的写入是否已经被正确拦截；
- 应用连接池、外部任务、定时脚本是否还在继续写旧主；
- 切换后，新主库的只读标志、复制角色和监控是否已经更新。

所以计划切换要做的是“在可控边界内完成切换”，而不是“比谁手快”。

### 2. 计划切换的三段流程

教学上可以先压成三段：

```text
准备
  → 检查复制健康 / GTID / Relay / applier 状态
  → 选择候选副本

追平
  → 确认候选副本赶上主库事务集合

冻结旧主写入
  → read_only / super_read_only 或业务层写门禁
  → 确保不再产生新事务

切换
  → 提升候选为新主
  → 修改应用 / 代理 / Router 指向
  → 验证读写
```

“追平”这一步最容易偷懒，因为它看起来只是个“差多少”的问题。更严格的做法至少包含：

- 比较主从两边的 `gtid_executed` 集合，而不是只看 `Seconds_Behind_Master`；
- 确认 applier/worker 已经没有“已接收但未提交”的事务，或者把这部分可接受差异显式记下来；
- 确认待提升副本的 `read_only`、过滤或延迟属性不会让它在晋升后立刻丢失业务写入。

这里可以吸收 10 篇的一个结论：SBM 为 0 不代表 GTID 集合完全一致，尤其在 MTS 下。所以“追平”的判据应该是“事务集合对齐”，而不是“延迟数字很小的近义词”。

### 3. 为什么“追平后立刻切流”仍然不够

追平只说明候选副本的事务集合和主库一致。但：

- 应用写入是否已被正确拦截；
- 连接池中是否有旧主长连接继续写入；
- 外部任务或定时脚本是否还在继续写旧主；
- 只读标志是否真正生效。

所以计划切换不仅是“追平 → 切流”，还要确认“真的没有人在写旧主了”。

“冻结旧主写入”也不只是执行一条 `SET GLOBAL read_only=1` 就完事。你还要验证：

- 当前长连接、连接池持有的旧会话是否会因为权限不足而被真正拒绝写；
- 外部 Cron/ETL/数据导入任务是否还握有其他写入口；
- 代理和 Router 的写路由是否已经在改切前就把写导向新主；
- `super_read_only` 是否能挡住一些会穿透 `read_only` 的系统/管理员写入。

如果这些没确认，你可能一边在“做计划切换”，一边旧主还在被偷偷写入。等你在新主上开放写后，两边各自积累了新事务，就变成了一次非计划式故障转移。

### 4. 为什么 planned switchover 追求的是可控边界，不是秒级速度

计划切换的前提是“受控窗口”。在这个窗口里：

- 你有时间检查候选副本的状态；
- 你有时间确认旧主写入已被正确冻结；
- 你有时间验证新主库的读写是否正常；
- 如果发现问题，还可以回退。

所以计划切换的第一目标不是“快”，而是“可控”。这里的回退也有讲究：如果在切换一半时发现新主异常，你最好能回到旧主继续服务，而不是被夹在“旧主已冻结、新主还没就绪”的中间态里。因此“切换脚本要可回滚”和“切换速度”同样重要。

### 5. 本节最该记住的结论：计划切换的核心是“先追平、再冻结、再切流、后验证”；它追求的是可控边界，不是秒级速度

一句最短人话是：**平稳切主像电力检修切换：先确认备用线路承载正常，再停旧线路供电，最后让全楼改接新线路。**

## 二、Emergency Failover：先隔离旧主防脑裂，再选“最接近完整真相”的副本

### 1. 第二个朴素误解：主库宕机了，第一反应就是立刻切流量

这个直觉在很多场景下是对的，但“立刻切”不等于“不确认”。因为：

- 旧主可能只是网络分区，不是真的挂了；
- 候选副本的事务集合可能不完整；
- 切到过滤副本或延迟副本，反而可能造成更大的数据损失。

所以紧急故障转移的第一步不是“切”，而是“先尽可能隔离旧主，再选最接近完整真相的副本”。

### 2. 紧急故障转移的三段流程

```text
事故
  → 主库失联 / 不可写 / 网络分区

第一步：隔离旧主
  → 防止旧主恢复后继续写（脑裂）

第二步：评估候选副本
  → GTID executed / Relay / applier / 只读状态 / 过滤或延迟属性
  → 选择“最接近完整真相”的副本

第三步：晋升并切流
  → 其他副本重新指向新主
  → 记录可能缺失事务和补偿策略
```

### 3. 为什么“延迟最小的副本”不总是最佳候选

这一点在 10 篇已经讲过，但紧急场景下更关键。因为你没有时间慢慢对比：

- 候选副本可能是过滤副本，数据不完整；
- 可能是延迟副本，事务落后很多；
- 可能正在回放一个大事务，虽然 GTID 集合看起来完整，但某些事务还没完全提交；
- 可能半同步下收到了 ACK 但还没回放。

所以选副本时，不是只看 SBM 或 GTID 集合，还要看角色语义。更进一步，还要评估“最接近完整真相”的副本是否有资格晋升：

- 它的 `read_only` 是否关闭、能否接受业务写；
- 它是否有过滤或延迟复制，导致事务集合不再是主库的完整集合；
- 它在半同步下是否真的已经回放，而不是只收了 ACK；
- 它当前是否正在执行一个大事务，导致虽然 `gtid_executed` 看起来对齐，实际部分快照仍不完整。

### 4. 为什么必须防脑裂

脑裂意味着旧主和新主同时接受写入，导致数据分裂。防脑裂的手段包括：

- 尽可能确认旧主已经停止写入；
- 使用 `read_only` / `super_read_only` 或 STONITH 级隔离；
- 确认其他副本都指向新主，而不是继续指向旧主。

一个常见的误区是把“网络分区时，大家以为对方挂了”当成少数派场景。实际上只要你的高可用脚本或人工决策以“联系不上”为触发条件，就必然存在误判风险。所以防脑裂不能只依赖“检查一下”，而要建立：

- 写入口的唯一性约定：同一时刻该写哪个实例，应该有明确共识；
- 旧主隔离的手段：不只靠网络，还要有能切断旧主写能力的机制（只读锁、拒绝用户写、STONITH 等）；
- 旧主重新加入前的补偿流程：不是直接放开让它写，而是先确认它有没有产生过“游离写入”。

### 5. 一个更具体的失败场景：网络分区下，两边都以为是“对方挂了”，各自升级为主库

假设：

- 主库 A 和副本 B 之间网络分区；
- 运维在 B 侧执行 emergency failover，将 B 晋升为新主；
- A 侧网络恢复后，A 仍然认为自己才是主库，继续接受写入；
- 两边都接受写入，数据开始分裂，最终无法合并。

这就是为什么故障切换时必须尽可能隔离旧主，不能只靠“我觉得它挂了”。

### 6. 本节最该记住的结论：紧急故障转移的第一步不是“切”，而是“先隔离旧主防脑裂，再选最接近完整真相的副本”；晋升后还要记录缺失事务和补偿策略

一句最短人话是：**紧急切主像灾后迁移总配电柜：先切断疑似带电的旧线路，再选最完整、最安全的新线路供电。**

## 三、复制中断与数据不一致修复：先分链路、GTID 和数据内容三类，再决定修复还是重建

### 1. 第三个朴素误解：复制报错了，先跳过那条事务，让副本继续跑再说

这是最危险的常见操作之一。跳过一条报错事务，可以让副本继续前进，但：

- 它不解决底层的根本原因；
- 被跳过的事务可能在副本上留下了永久的数据裂缝；
- 这条裂缝可能在未来被 `pt-table-checksum` 发现，或者更糟，直接导致业务层数据不一致。

所以复制报错后，第一反应不是“跳过”，而是“先确认这是哪一类问题”。

### 2. 复制故障至少分三类

教学上可以先压成三类：

```text
链路 / 配置
  server_id 冲突
  包大小 / 网络 / 认证 / 权限问题

复制逻辑
  binlog 缺失
  GTID 集合不匹配
  主键冲突 / DDL 不兼容 / 依赖对象不存在

数据一致性
  pt-table-checksum 校验差异
  → pt-table-sync 或重建副本 / 补数据
```

### 3. 如何判断是“跳过”还是“重建”

没有统一的答案，但有统一的判断顺序：

- 先确认事务集合和拓扑状态；
- 再判断是单条事务异常还是全局数据漂移；
- 如果是单条事务异常，可以 `SET GTID_NEXT` 跳过，但必须确认后续事务不会依赖这一条；
- 如果是全局数据漂移，跳过没有意义，应该考虑重建副本或从备份恢复。

这里要特别提醒一个最危险的操作：在 GTID 下通过 `SET GTID_NEXT=...` 手工“补一笔空事务”来跳过某条已报错事务。它能临时掩盖单条失败，但：

- 它不会把“应该存在的行变更”真正补回来；
- 如果后续事务读取了这条被跳过的数据，副本就会产生不同于主库的结果；
- 你会把“副本当前在哪”骗过，但“这里其实缺了一段事实”并不会被消除。

所以在用 `SET GTID_NEXT` 跳过之前，至少要回答：这条被跳过的事务，孤立地看能接受缺失吗？后面有没有依赖它的其他事务存在？如果答案不确定，“跳过”就不是最优动作，而是“先定位再决定”。

### 4. 为什么 `pt-table-checksum` 和 `pt-table-sync` 不是万能补丁

`pt-table-checksum` 可以找出差异，`pt-table-sync` 可以生成修复 SQL。但它们：

- 不解决根本原因（比如触发不一致的 bug 或配置错误）；
- 在大数据量下可能很慢；
- 如果主库数据还在持续写入，修复过程中可能产生新的差异；
- `pt-table-sync` 生成的修复动作本身也可能改变数据，需要一个“允许修复、能被验证、能回退”的窗口。

所以这些工具更适用于“确认差异范围 + 一次性修复”，而不是“持续修补”。更稳妥的做法是：先冻结或降低写入，跑 checksum 找到差异范围，明确差异对象，再决定是把副本上缺失的行补回去，还是干脆重建副本；而不是一边主库持续写入、一边让 sync 工具追着差异跑。

### 5. 一个更具体的失败场景：跳过一条报错，几个月后才发现数据早就不一致了

假设：

- 复制因为主键冲突报错；
- 运维跳过了那一条事务；
- 副本继续前进；
- 几个月后，业务发现某条数据在两个实例上不一致；
- 但已经无法追溯到几个月前的那条跳过了。

这时已经不是“修复一条事务”的问题，而是“整条数据链可能已经裂了很久”。

### 6. 本节最该记住的结论：复制报错后，先分链路、GTID 和数据内容三类，再决定是跳过、修复还是重建；盲目跳过只是把问题从今天推到未来

一句最短人话是：**复制修复像校账：线路断了先恢复通讯，金额不对要先查明哪几笔账缺失，而不是随手跳过一页。**

## 四、备份与时间点恢复：全量备份只提供基线，binlog 才能让你回到任意时间点

### 1. 第四个朴素误解：有全量备份就够了，误删数据时直接恢复全量就行

全量备份可以让你回到某个时间点，但：

- 如果全量备份是昨天凌晨 2 点，而误删发生在今天下午 3 点；
- 直接恢复全量，你会丢失昨天凌晨 2 点到今天下午 3 点之间的所有数据；
- 要恢复到这个区间内的任意时间点，必须结合 binlog 回放。

所以全量备份 + binlog 才是完整的恢复方案。

### 2. 逻辑备份与物理备份分别适合什么场景

```text
逻辑备份（mysqldump / mydumper 等）
  导出 SQL / 表数据
  → 可跨版本 / 按对象恢复
  → 恢复速度受逻辑导入限制

物理热备（XtraBackup 等）
  拷贝 InnoDB 文件 / 日志
  → 准备并恢复到可启动状态
  → 通常更适合大库全量恢复
```

逻辑备份灵活，适合按表、按库恢复，但恢复速度慢；物理备份适合大库全量恢复，但跨版本兼容性差。

### 3. PITR：全量备份 + binlog 回放，才能恢复到任意时间点

PITR 的核心流程是：

```text
全量备份恢复到某个时间点
  → 从该时间点之后，按时间 / 位置 / GTID 回放 binlog
  → 到达目标时间点后停止
```

PITR 的成败取决于：

- binlog 的连续性（如果 binlog 被 purged 了，可能无法回放到目标时间点）；
- 时间边界的准确性；
- 经过演练的回放流程。

### 4. 为什么“有全量备份”不等于“能恢复到 5 分钟前”

全量备份只提供基线。要恢复到 5 分钟前，你还需要：

- 从全量备份恢复后，回放从备份时间点到 5 分钟前的所有 binlog；
- 如果 binlog 在这段时间内被 purged 了，或者被轮转删除了，就无法回放；
- 如果 binlog 的 GTID 或时间边界不准确，也无法精确停在 5 分钟前。

另一个经常被忽略的点是：PITR 的“回放”不是从主库上直接按 SQL 重放，而是要把 binlog 送到一个恢复实例上执行。你要考虑：

- binlog 里有没有 row event 依赖主键、依赖表结构，恢复到一批历史结构时会不会因为 DDL/索引差异而报错；
- 恢复实例的字符集、排序规则和 sql_mode 会不会让回放结果和主库当时的执行环境不同；
- 误删的可能是整个库或整张表，而 binlog 回放通常是按时间/位置/GTID 顺序推进，如果目标对象已经被 DROP 过，回放时的存在性判断会非常关键。

所以“能恢复到 5 分钟前”的真实含义是“全量基线 + 连续可回放的 binlog + 兼容的回放环境 + 经过演练的流程”四者同时成立，缺一不可。

### 5. 一个更具体的失败场景：binlog 被 purged 了，PITR 只能恢复到 purge 之前

假设：

- 全量备份是 T0；
- 业务在 T1 误删数据；
- 你想恢复到 T1 之前的 T1-1min；
- 但 binlog 在 T0 到 T1-1min 之间被 `PURGE BINARY LOGS` 自动清理了；
- 你只能恢复到 T0，无法恢复到 T1-1min。

所以 binlog 的保留策略直接影响 PITR 的恢复窗口。保留策略要配合全量备份频率和业务恢复要求设计。这里还要强调：备份不是“做了就安全”，还要定期做“恢复演练”，因为：

- 备份文件可能在恢复时才发现损坏；
- 备份工具版本和 MySQL 版本不兼容，恢复可能失败；
- 备份机资源和硬件不足，全量 + binlog 回放可能远比预期慢。

所以“有无备份”和“能否恢复”是两件事，只有像做故障演练一样定期验证恢复流程，才能真正把它变成防线。

另外，误删场景里还有一条更轻量的路：如果业务接受“只找回误操作范围内的差异”，可以用 `binlog2sql`/`MyFlash` 一类工具针对具体事务生成反向 SQL 做闪回。它不是替代全量 + PITR，而是在“小范围误删、回放成本高”时，更快地补回差异对象。要注意这类工具是否支持 row format、能否精确还原时间窗口，以及目标表结构和回放环境的兼容性。

### 6. 本节最该记住的结论：全量备份只提供基线，binlog 才能让你回到任意时间点；PITR 的成败取决于 binlog 连续性和保留策略，而“备份可恢复”必须通过定期的恢复演练验证

一句最短人话是：**全量备份像整座仓库某天的快照，binlog 像之后每天的出入库流水；想回到某个具体时刻，必须两者结合。**

## 五、基准测试与恢复后验收：数据回来了，不等于服务就恢复了

### 1. 第五个朴素误解：数据恢复成功了，业务就可以直接切回去

数据恢复只是恢复的第一层。恢复后你还需要确认：

- 新主库的读写路由是否正确；
- 复制状态是否正常；
- 慢查询、错误日志、锁等待是否异常；
- 新主库的缓存是冷的，性能可能比旧主库差很多。

所以“恢复成功”必须包含性能验收。

### 2. 恢复后至少需要检查什么

```text
恢复后检查
  → 只读 / 写入路由是否正确
  → 复制 / GTID / 只读标志是否符合新角色
  → 慢查询 / 错误日志 / 复制状态是否异常

容量与性能
  → sysbench 或代表性 workload
  → QPS / TPS / P95 / P99
  → 检查连接数、open_files_limit、ulimit、IO / CPU / 锁等待

回归
  → 基线对比
  → 性能下降？新主硬件 / 参数 / 索引 / 缓存热度是否不同
```

### 3. 为什么新主库的缓存是冷的

新主库在晋升之前是副本，它的 Buffer Pool 里缓存的是副本 workload 的热点，不是主库 workload 的热点。晋升后，业务流量切到新主库，缓存需要重新预热。在预热完成之前，查询可能比旧主库慢很多。

这不是“新主库性能差”，而是“缓存还没热起来”。但如果预热时间太长，或者 workload 差异太大，这个影响可能被误判为“新主库性能不行”。

### 4. 为什么恢复后必须做性能基线对比

因为恢复后的系统可能“正确但很慢”。如果只验证数据一致性，不验证吞吐和尾延迟，恢复可能只是把事故从一致性问题变成了可用性问题。

一个典型的“恢复后翻车”路径是：

- 新主库数据一致、复制正常、看起来清凉；
- 你一放量，发现 QPS 没恢复到基线，P99 却在第一波上来；
- 原因不是数据错，而是新主库缓存冷、参数与旧主不同、连接池还没重新预热、大查询在空缓存下把 IO 和锁又顶起来了。

所以恢复后验收要同时覆盖路由、数据、容量和性能四层，缺一不可。sysbench 这类压测只是其中一环，真正要让新主库稳定承接流量，还需要在真实业务流量下观察一段时间，看缓存热度、连接池水位和尾延迟是否回落到可接受区间。

### 5. 容量边界：`open_files_limit`、连接上限和 `ulimit` 为什么常在恢复后变成新事故

恢复后最容易爆的不是 SQL，而是容量边界。因为新主库或被提升的副本，可能：

- `open_files_limit`、`max_connections`、`table_open_cache` 等参数和旧主不同；
- 连接池把大量长连接一次性切到新主，瞬间逼近连接上限；
- 实例的 `ulimit`、内核 fd 限制与旧主不一致；
- 临时表/内存临时池、Buffer Pool 大小没有随角色切换而调整。

这些都不会让数据变错，但会让“已经恢复”的实例在放量时先于业务靠近天花板。所以验收要做的不只是跑一轮 sysbench，还包括检查新主库当前角色下的相关限制是否适配它即将承担的流量。

### 6. 本节最该记住的结论：恢复成功不只是数据一致，还要验证性能、容量、缓存热度和路由；新主库的缓存是冷的，`open_files_limit`/连接上限等容量边界也可能成为新事故源

一句最短人话是：**数据回来了，不等于服务就恢复了；恢复后的系统可能正确但很慢，必须验证吞吐和尾延迟才算真正恢复。**

## 六、把本篇收成一张图：故障处理的核心是事务集合正确性，恢复完成的标志是性能与容量也达标

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：主库故障、误删数据、复制断开时，到底应该先切流、先修副本、还是先做备份恢复，以及“恢复成功”怎么判断。答案已经闭环了。

计划切换的核心是“先追平、再冻结、再切流、后验证”。紧急故障转移的核心是“先隔离旧主防脑裂，再选最接近完整真相的副本”。复制修复的核心是“先分链路、GTID 和数据内容三类，再决定修复还是重建”。备份与 PITR 的核心是“全量备份 + binlog 回放，才能恢复到任意时间点”。恢复后验收的核心是“数据一致 + 性能与容量达标，才算真正恢复”。

把这一切压成最短总图，就是：

```text
planned switchover
  或 emergency failover
  → 防脑裂 / 选副本
  → 检查 GTID / Relay / 延迟 / 角色
  → 必要时 checksum / sync / 重建
  → 用全量备份 + binlog 做 PITR
  → 恢复后压测 / 验收 / 监控
```

所以本篇最该记住的一句话是：**故障处理不是“把服务拉起来”就结束，而是先确认事务集合和防脑裂，再选择修复或恢复路径，最后验证性能与容量，才算真正恢复。**

## 七、几个最容易说错的地方

### 计划切换是不是只要把从库设成主库就行了？

不是。还要确认候选副本的事务集合、冻结旧主写入、修改应用连接、验证只读标志和复制状态。

### 紧急故障切换时，是不是选延迟最小的副本就对了？

不是。延迟最小只是参考，还要确认候选副本的 GTID 集合、过滤/延迟属性、只读状态和角色语义。

### 复制报错后，是不是先跳过事务再说？

不是。先分链路、GTID 和数据内容三类，再决定修复还是重建；盲目跳过可能把问题从今天推到未来。

### 有全量备份是不是就能恢复到任意时间点？

不是。全量备份只提供基线，PITR 还需要连续的 binlog 和正确的保留策略。

### 恢复成功后，是不是数据一致就够了？

不够。恢复后还要验证性能、容量、缓存热度和路由正确性；新主库的缓存可能是冷的，性能可能比旧主库差很多。

## 收束：故障处理最危险的习惯，不是“恢复慢”，而是“以为恢复成功了，其实只是数据回到了某个时间点，性能还没达标，缓存还是冷的”

回到开头那个问题：主库故障、误删数据、复制断开时，到底应该先切流、先修副本、还是先做备份恢复？答案已经完整闭环了。计划切换追求可控边界，紧急故障转移追求防脑裂和选最完整副本，复制修复追求先分类再行动，备份与 PITR 追求全量 + binlog 组合，恢复后验收追求数据一致 + 性能与容量达标。

这就是为什么说：**故障处理不是“把服务拉起来”就结束，而是先确认事务集合和防脑裂，再选择修复或恢复路径，最后验证性能与容量，才算真正恢复。** 只要这条主线站稳，后面进入 Group Replication、InnoDB Cluster 和 ClusterSet 时，你就不会再被“切换速度”或“工具自动化”这类半结论误导，而会始终把事务集合正确性和恢复后验收放在第一位。
