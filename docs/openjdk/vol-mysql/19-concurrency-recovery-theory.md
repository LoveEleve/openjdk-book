## 现在真正该问的，不再是“数据库具体怎么实现”，而是“它凭什么证明崩溃后能恢复到可解释状态，并发后还能等价于某种正确顺序”

前面的 MySQL 主线已经带你看过很多“实现怎么做”：

- Redo/Undo 和崩溃恢复怎么串起来；
- MVCC 和锁怎样一起工作；
- 组复制怎样做冲突检测和提交边界；
- 存储引擎如何在不同阶段支付不同成本。

如果只停在这些工程细节里，你很容易形成另一种新困惑：

“这些实现为什么可以说自己是对的？只是因为它们跑起来像对的吗？”

这就是理论篇存在的意义。数据库理论不是为了让你背下几个著名缩写，而是要回答两个根问题：

- **崩溃后怎样恢复到一个可解释状态？**
- **并发事务怎样保证等价于某种可接受的串行顺序？**

只要这两个问题回答不清，日志、页、锁、版本链和复制看起来再复杂，也只是工程技巧的堆叠，而不是一套能被解释的系统。

先把总图记住：

```text
恢复理论:
  ARIES
  → Analysis / Redo / Undo
  → WAL / LSN / dirty page table / CLR

并发控制:
  OCC
  → 读 / 验证 / 写

  Timestamp Ordering
  → 时间戳全序 + read_TS / write_TS

  SSI
  → 快照读 + 依赖图 + 危险结构检测

替代路线:
  Shadow Paging / COW / MARS / WBL
  → 把恢复成本放到别的阶段
```

这篇最该先记住的一句话是：**数据库理论始终在回答两件事：崩溃后怎样恢复一个可解释状态，并发事务怎样避免形成不可串行化结果；日志、版本、时间戳、冲突图和根指针只是不同答案的工程化表达。**

## 一、ARIES：Analysis、Redo、Undo 如何从崩溃现场重建状态

### 1. 最朴素的错误世界：崩溃后只要把未提交事务删掉，系统自然就对了

这个直觉非常诱人，因为它抓住了一个真实目标：未提交事务不能留下最终副作用。于是很多人会下意识地想：

- 找出没提交的事务；
- 把它们删掉；
- 系统就干净了。

问题在于，崩溃现场从来不是一张干净的逻辑表，而是一个半途停下来的物理世界：

- 有些日志已经落盘；
- 有些页已经刷出；
- 有些页还在内存；
- 有些事务提交了但相关页还没落盘；
- 有些撤销动作自己也只做了一半。

所以“先把未提交事务删掉”根本不是恢复算法，而只是一个抽象愿望。恢复真正要处理的是：**如何在一个半新半旧的物理现场上，重建出一个可继续解释的历史。**

### 2. ARIES 的最小恢复三阶段

```text
Analysis:
  从 checkpoint 附近的恢复边界开始扫描日志
  → 重建 transaction table / dirty page table
  → 判断哪些事务在崩溃时仍未完成

Redo:
  从 dirty page table 推导出的最早必要 LSN 开始
  → 按日志重做历史修改
  → 重做必须可重复/幂等地恢复页状态

Undo:
  对 loser transactions 反向遍历日志
  → 撤销未提交修改
  → 写 compensation log record(CLR)
  → 直到事务完成回滚
```

这三阶段最重要的直觉不是顺序本身，而是各自回答了不同问题：

- Analysis 回答“崩溃现场有哪些事务和脏页仍然在案”；
- Redo 回答“如何先把磁盘拉回到日志所描述的历史”；
- Undo 回答“在这个完整历史上，哪些未提交动作要被正式撤销”。

### 3. 为什么 ARIES 要“先 Redo、后 Undo”

这是恢复理论里最值得被真正记住的地方。

如果你先 Undo，看起来像更直接地“清除坏事务”，但实际上你会立刻撞上问题：

- 你还不知道磁盘上的页是不是已经包含了所有需要被撤销前的历史；
- 某些提交事务的修改可能还没真正落到页上；
- 你在一个不完整现场上撤销，等于一边猜测历史、一边动手修现场。

ARIES 的关键判断是：**先承认历史已经发生，再在完整历史上撤销不该留下来的部分。**

所以它先 Redo，把数据库页恢复到“崩溃前日志所能描述到的那个历史状态”；而这个 redo 起点并不是一句笼统的“从 checkpoint 开始重放”，而是要结合 Analysis 重建出的 dirty page table，找到真正最早需要的 LSN。然后再 Undo，把 loser transactions 反向消除掉。

这就是为什么 ARIES 的恢复不是“重建最终状态”，而是“先重建历史，再重建最终状态”。

### 4. 为什么 CLR（补偿日志记录）不是多余负担

很多读者第一次看到 CLR，会觉得这像恢复时又往日志里添了一层麻烦：

“撤销都在做善后了，为什么还要把善后动作再记一次？”

因为恢复本身也可能被打断。

- 如果你正在 Undo loser transaction，结果又断电；
- 下次恢复时，如果没有 CLR，就很难知道上次哪些撤销已经做过；
- 你可能重复撤销，或者根本不知道该从哪里续做。

所以 CLR 的存在，是为了让“撤销动作本身也成为可恢复历史的一部分”。

这正是 ARIES 的深层一致性：**不仅正常事务要留下可解释日志，恢复过程自己也必须留下可解释日志。**

### 5. 一个更具体的失败场景：只凭页状态恢复，会把“已提交但未落页”的事务误判成丢失

假设：

- 事务 T1 已提交，commit 日志已经安全落盘；
- 但相关数据页尚未刷盘；
- 崩溃发生后，磁盘页上看不到 T1 的新值；
- 如果你只盯页状态，而不先按日志 Redo，就会误以为 T1 没发生过。

这时真正的问题不是“页坏了”，而是“你把日志承诺过的历史忘了”。ARIES 恰恰通过 Redo 先把这种“日志已承诺、页未反映”的历史补回来。

### 6. 本节最该记住的结论：ARIES 的核心不是“回滚未提交事务”，而是用 Analysis 重建现场、用 Redo 先恢复历史、再用 Undo 撤销 loser transaction；恢复本身也必须留下可恢复的 CLR 记录

一句最短人话是：**灾后先按施工日志恢复现场，再撤销未验收工程；撤销动作本身也要记进新的施工记录，避免再次断电后无从继续。**

## 二、OCC：冲突少时，把锁等待换成提交验证

### 1. 第二个朴素误解：乐观并发就是“无锁而且一定更快”

这个误解几乎是 OCC 最常见的宣传口号化版本：

- 不一开始加很多锁；
- 读阶段先自由地读；
- 提交前再统一检查；
- 所以一定更快。

问题在于，OCC 不是取消代价，而是重新分配代价。它把：

- 早期锁等待

换成了：

- 提交时验证；
- 冲突后回滚重试；
- 重试事务的重复计算；
- 应用层的幂等和副作用控制。

所以 OCC 真正适合的不是“所有场景”，而是“冲突低且重试成本可控”的场景。

### 2. OCC 的最小三阶段

```text
Read phase:
  读取数据/计算结果
  → 记录 read set / write set
  → 不长期持有写锁

Validation phase:
  检查与已提交/并发事务的集合是否冲突
  → 向后/向前/并行验证策略
  → 冲突? abort/retry

Write phase:
  验证成功
  → 应用写集合
  → 提交
```

这张图最关键的地方在于：事务真正的“成败判定”被推迟到了验证阶段。

也就是说，OCC 的前半段乐观，不代表整个事务必然乐观到底。它只是说：先假设冲突少，等提交前再统一核账。

### 3. 为什么 OCC 不是“无锁”，而是“把代价放在重试上”

OCC 看起来很轻，是因为它在读阶段不急着长期持有写锁。但这不意味着系统完全没有同步成本。它真正付账的地方在于：

- 验证逻辑本身；
- 冲突事务 abort；
- retry 带来的重复计算；
- 应用副作用必须幂等。

这里还要补一刀边界：应用副作用幂等不是 OCC 理论定义本身的一部分，而是 OCC 落到真实工程系统时不得不额外承担的要求。也正因为如此，OCC 并不是简单的“无锁算法”，而是“用冲突检测和重试来替代一部分锁等待”。

### 4. 一个更具体的失败场景：热点账户高冲突，OCC 退化成不停重试

假设：

- 大量事务同时更新同一个热点账户；
- 每个事务在读阶段都顺利读到了旧值；
- 到验证阶段才发现 write set 高度冲突；
- 结果大量事务 abort/retry，重复执行计算和业务逻辑。

这时如果你还抱着“OCC 无锁所以更快”的直觉，就会完全误判问题。真正慢的不是锁等待，而是重复工作的放大。

### 5. 本节最该记住的结论：OCC 的价值在于把一部分锁等待换成提交验证，但它不会消灭冲突；高冲突、长事务和大 write set 会把代价重新放大成重试与重复计算

一句最短人话是：**多人先各自填表，最后交给柜台统一核对；没有冲突就一起提交，冲突了其中一些人要重填。**

## 三、时间戳排序：用全序决定冲突先后

### 1. 第三个朴素误解：只要给事务编号，顺序自然就对了

时间戳排序看起来非常优雅：给每个事务一个时间戳，全世界都按这个全序来，问题不就解决了吗？

问题在于，“有了顺序编号”并不自动等于“所有读写都合法”。关键不在有没有时间戳，而在：

- 读一个数据项时，这个读会不会违背更晚写入已经建立的顺序；
- 写一个数据项时，这个写会不会落后于已经发生的读/写。

所以时间戳排序不是“发号排队”，而是“让每次读写都接受这个全序约束”。

### 2. 最小时间戳规则图

```text
事务 T 带 timestamp TS(T)
数据项 X 维护 read_TS(X) / write_TS(X)

T 读 X:
  若 TS(T) < write_TS(X)
    → 读违反时间顺序, abort/restart
  否则更新 read_TS(X)

T 写 X:
  若 TS(T) < read_TS(X)
    → 写违反顺序, abort
  若 TS(T) < write_TS(X)
    → 可拒绝、回滚或按 Thomas Write Rule 忽略过时写
  否则更新 write_TS(X)
```

这个模型最关键的地方在于：冲突不是靠锁发现，而是靠“这个操作是否违反全序”来发现。

### 3. 为什么 Thomas Write Rule 不是“旧写都能丢”

Thomas Write Rule 很容易被粗暴理解成：

“如果写晚了，旧写就别写了，直接丢掉。”

这其实很危险。它的成立前提非常具体：

- 这个写已经被一个更晚时间戳的写覆盖；
- 忽略它不会改变最终等价序列；
- 协议本身允许你把这种过时写视为无效。

所以 Thomas Write Rule 是时间戳排序里的一种特定优化，不是一般性的“last-write-wins 万能法则”。

### 4. 一个更具体的失败场景：时间戳顺序没错，但冲突回滚依然非常高

假设：

- 系统严格按时间戳全序运行；
- 多个事务频繁访问同一批热点数据项；
- 顺序约束本身没有逻辑错误；
- 但由于大量事务不断踩到比自己更新的 read_TS/write_TS，abort/restart 频率很高。

这时问题不是“理论不对”，而是“理论把冲突代价付成了高重启率”。时间戳排序保证的是正确顺序，不保证高冲突场景下的体验一定更好。

### 5. 本节最该记住的结论：时间戳排序的核心不是“给事务编号”，而是让每次读写都服从一个全局顺序；Thomas Write Rule 只是其中一种特定过时写优化，不是一般性的丢旧写原则

## 四、SSI：快照读如何检测危险结构

### 1. 第四个朴素误解：有了快照读，读写阻塞少了，可串行化问题应该也就解决了

这是很多人第一次接触快照隔离时最自然的误会：

- 读不怎么挡写；
- 写也不怎么挡读；
- 大家都在各自的快照里工作；
- 那应该既快又正确。

问题在于，快照读减少的是阻塞，不是自动保证串行化。两个事务即使都读到了一个一致快照，也可能在各自写回后共同破坏业务约束。

### 2. SSI 的最小依赖图心智

```text
事务读快照
  → 记录 rw-conflict

事务写入/提交
  → 维护事务依赖图

检测:
  出现可能形成环的危险结构?
  → abort/延迟提交其中一个事务
  → 保证可串行化目标
```

SSI 的关键，不是把所有读都锁起来，而是：

- 允许快照读继续保持低阻塞；
- 但额外跟踪读写依赖；
- 一旦依赖图出现危险结构，就在提交边界 abort/延迟其中一方。

所以 SSI 的真正代价，不在普遍加锁，而在依赖跟踪、冲突记录和提交时回滚。

### 3. 为什么 SSI 不等于“所有读都加锁”

因为那样它就退化成另一套更保守的可串行化实现了。SSI 想保留的是：

- 快照读的并发优势；
- 尽量少的读阻塞；
- 把问题转成危险结构检测。

所以 SSI 的思路不是“读之前先挡住所有潜在写者”，而是“先允许读发生，再判断这些读写依赖会不会最终形成不可串行化结构”。

### 4. 一个更具体的失败场景：两个事务各自读到旧快照，最后共同破坏约束

假设：

- 事务 A 和 B 都读取同一份快照；
- A 看见某个条件成立，于是更新一部分记录；
- B 也看见相同条件成立，于是更新另一部分记录；
- 单看各自都合理，但合在一起破坏了全局业务约束。

这类问题最麻烦的地方是：

- 没有明显读写阻塞；
- 没有简单死锁；
- 每个事务单独看都像正确；
- 错误只在最终组合效果里显现。

SSI 正是为了识别这种“每个人都在旧快照里做了看似合理的决定，但组合后不可串行化”的危险结构。

最小反例可以记成“值班医生”问题：系统要求任一时刻至少有一名医生值班。事务 A 读取快照，看到医生甲和乙都在值班，于是把甲设成下班；事务 B 同时读取同一快照，也看到两人都在值班，于是把乙设成下班。单看每个事务都像合理决定，但最终结果是两人都下班，约束被破坏。这里没有明显锁冲突，也没有简单死锁，问题正是两个快照事务之间形成了危险结构。

### 5. 本节最该记住的结论：SSI 的价值在于保留快照读的低阻塞，同时通过依赖图和危险结构检测保证可串行化；它不是“所有读都加锁”，而是“允许先读，再在提交边界判错”

一句最短人话是：**SSI 允许多人先读旧版文件，但记录谁读了谁将修改的内容；如果关系图显示可能互相矛盾，就让一方重做。**

## 五、Shadow Paging、MARS 与 WBL：WAL 之外的恢复路线

### 1. 第五个朴素误解：恢复理论的主流答案就是 WAL，剩下都只是变种细节

WAL/ARIES 的确是非常强大的主流答案，所以读者很容易觉得：

“恢复问题大概已经定型了，其他方案只是局部小改。”

但恢复理论真正多样的地方在于：你不一定非要把成本放在“原地页更新 + 日志回放”这条路上。

### 2. Shadow Paging / COW 的最小心智图

```text
Shadow paging:
  写新页/新页表
  → 提交时原子切换根指针
  → 旧页保留为旧版本/回收候选

MARS/WBL 等研究路线:
  → 可以先把它们理解成“尝试重新分配恢复路径代价”的代表名字
  → 通过多核、日志组织或版本结构重新安排恢复成本
  → 目标仍是降低同步或写放大

对比:
  WAL/ARIES: 原地页 + 日志 + replay/undo
  Shadow/COW: 新页/新根 + 指针切换
```

这张图最重要的地方在于：恢复并不只有一种风格。

- WAL/ARIES 把“历史重放能力”放在日志链上；
- Shadow/COW 把“完整版本切换能力”放在新页和根指针切换上；
- MARS/WBL 这类名字此处不要求你背实现细节，记住它们共同代表“试图重新分配同步、写放大、并发和恢复边界”的研究方向即可。

### 3. 为什么替代路线没有统一取代 WAL

因为它们不是无代价更优，而是重新分配代价：

- 写放大可能上升；
- 空间回收可能更难；
- 并发控制可能更麻烦；
- 元数据切换可能更敏感；
- 故障模型解释方式也会变化。

所以恢复路线的选择，不是“发现了更先进算法就替掉旧方案”，而是“哪种代价分布更适合这个系统”。

### 4. 本节最该记住的结论：WAL/ARIES 不是唯一恢复路线，Shadow Paging/COW 和其他研究方案都在试图把恢复成本压到不同阶段；没有统一取代谁，只有不同系统对代价分布的不同选择

## 六、把本篇收成一张图：理论不是背缩写，而是解释正确性的两条主线

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：数据库既要扛崩溃，又要允许并发，“正确状态”和“串行等价”究竟如何定义。答案已经闭环了。

ARIES 通过 Analysis、Redo、Undo 和 CLR，把崩溃恢复组织成“先重建现场、再重建历史、最后撤销 loser”的可解释流程。OCC 通过读、验证、写三阶段，把一部分锁等待换成提交时的冲突验证。时间戳排序用全局顺序约束每次读写，Thomas Write Rule 只是其中的过时写优化。SSI 则保留快照读的低阻塞，同时用依赖图和危险结构检测保证可串行化。Shadow Paging、COW 与 MARS/WBL 又提醒你：恢复本身也有多条不同的付账路线。

把这一切压成最短总图，就是：

```text
崩溃恢复:
  ARIES = Analysis → Redo → Undo

并发控制:
  OCC = 读 → 验证 → 写
  T/O = 时间戳全序 + 冲突检查
  SSI = 快照读 + 依赖图危险结构检测

替代恢复:
  Shadow/COW = 新版本写好 → 原子切根
```

所以本篇最该记住的一句话是：**数据库理论始终在回答两件事：崩溃后怎样恢复一个可解释状态，并发事务怎样避免形成不可串行化结果；日志、版本、时间戳、冲突图和根指针只是不同答案的工程化表达。**

## 七、几个最容易说错的地方

### ARIES 恢复就是把未提交事务删掉？

不是。它要先 Analysis 重建现场，再 Redo 重建历史，最后 Undo loser transaction；恢复过程自己也要写 CLR。

### OCC 就是无锁而且一定更快？

不是。它把一部分锁等待换成验证、回滚和重试；高冲突和大 write set 会让代价重新放大。

### 时间戳排序就是给事务编号？

不是。核心是让每次读写都服从全序约束；Thomas Write Rule 也只是特定过时写优化。

### 快照隔离已经很强，SSI 只是更重的锁？

不是。SSI 的关键是依赖图和危险结构检测，不是把所有读都锁起来。

### WAL 是恢复理论唯一正解？

不是。Shadow Paging、COW 和其他研究路线都在把恢复成本放到不同阶段，没有一种答案对所有系统都免费更优。

## 收束：数据库理论的价值，不在于多记几个缩写，而在于你终于能解释“为什么这套实现算正确”

回到开头那个问题：数据库既要扛崩溃，又要允许并发，“正确状态”和“串行等价”究竟如何定义。答案已经闭环了：恢复理论负责解释系统怎样从半新半旧的崩溃现场回到一个可解释状态；并发控制理论负责解释系统怎样允许并发而不产生不可串行化结果。ARIES、OCC、时间戳排序、SSI 和 Shadow/COW，只是不同系统在这两个根问题上的不同工程回答。

这就是为什么说：**数据库理论始终在回答两件事：崩溃后怎样恢复一个可解释状态，并发事务怎样避免形成不可串行化结果；日志、版本、时间戳、冲突图和根指针只是不同答案的工程化表达。** 只要这条主线站稳，下一篇进入 CAP、分库分表和数据库选型时，你就不会再把这些理论当成分散名词，而会自然地把它们看成“架构决策的约束来源”。
