## 现在真正该问的，不再是“这条 SQL 为什么慢”，而是“优化器如何估算代价，日志与执行计划又如何共同形成可验证的证据链”

前几篇已经把 MySQL 的高可用和集群控制平面收稳了。现在开始换视角，回到每个查询本身。

你先记住一个很重要的前提：**优化器不是把“走索引”当作一个开关，它比较的是预计总成本**。低选择性索引、回表成本、排序、临时表、覆盖索引和并发 I/O 都会影响结论。同一句 SQL，在两份数据分布不同的库上，可能走索引，可能全表扫描，可能走不同索引。

这也解释了为什么“加索引就行”这个说法很危险：

“索引加上了，为什么优化器还是不用它？”

因为优化器比较的是“预计总成本”，不是“有没有索引”。索引存在，但如果成本模型认为走索引更贵，它就不会用。这种决策由统计信息和代价模型共同决定，不是由“索引是否存在”这个布尔值决定。

先把总图记住：

```text
输入 SQL
  → 语法/语义解析
  → 规则重写：常量折叠/条件化简/范围改写/部分外连接消除
  → 生成候选访问路径：
      表访问方法/索引/连接顺序/连接算法
  → 结合统计与成本模型估算
  → 选择当前最优计划
  ↓
计划 EXPLAIN(假设) → EXPLAIN ANALYZE(事实) → 慢日志(症状入口) → 系统观测(副作用)
```

这篇最该先记住的一句话是：**优化器不是数据库里的神谕，它只是基于统计和成本模型的预测器；慢查询日志给你症状，EXPLAIN 给你假设，ANALYZE 给你事实，系统观测告诉你副作用。**

## 一、优化器：规则重写只是第一步，代价模型才决定最终计划

### 1. 最朴素的错误世界：写了索引，优化器就应该用

“写了索引，优化器就应该用”这个直觉在“索引越多，查询越快”的朴素推理下很自然。但优化器不会因为“有索引”就走索引，它比较的是预计总成本。

- 低选择性索引：返回大量行，走索引回表可能比全表扫描更贵；
- 回表成本：二级索引回主表拿整行，会增加额外的数据访问成本；
- 排序/临时表：走索引可以避免排序的负担，但如果索引本身不能消除排序，成本可能上升；
- 覆盖索引：索引包含所有需要字段时，不需要回表，预计成本可能下降；
- 运行环境：并发、锁等待、Buffer Pool 命中率和 I/O 状态会影响实际执行时间，但它们不等于优化器每次选计划时直接使用的完整运行时状态。

所以“有索引不用”不是优化器“笨”，而是它依据统计信息、成本表、索引和配置估算后判断“这条路径的预计代价更高”。

### 2. 优化器的完整流水线：从 SQL 文本到执行计划

教学上可以压成一条最小流程：

```text
输入 SQL
  → 语法/语义解析
  → 规则重写(语义保持)
      常量折叠/条件化简/范围改写/部分外连接消除
  → 生成候选访问路径
      表访问方法/索引/连接顺序/连接算法
  → 结合统计与成本模型估算
  → 选择当前最优计划
```

规则重写负责缩小问题空间，代价模型负责从候选路径里选“当前看起来最便宜”的一条。如果只做规则重写而忽略成本，优化器会退化成“盲从规则的机器”；如果只靠代价而忽视重写，很多本来可以提前剪枝的路径又会白费搜索。

两者是配合关系，不是二选一。

### 3. 为什么有索引不等于成本更低：统计、回表、排序和覆盖四个变量

四个变量可以串成一个完整的因果链：

- 统计信息：MySQL 依据表统计和索引统计估算返回行数。如果统计过期，估算自然失真；
- 回表成本：走二级索引拿主键，再回主表拿整行，会增加额外的数据访问成本；
- 排序/临时表：如果查询需要 `ORDER BY`/`DISTINCT`/`GROUP BY`，排序或临时表会成为新增成本。走索引能消除排序，但不总能消除；
- 覆盖索引：索引包含所有需要字段时不需要回表，预计成本可能下降。

所以优化器决定的是一个综合结论：**在给定统计、成本表、索引、配置和内存预算下，哪条路径的预计成本最低**。实际并发、锁等待、Buffer Pool 命中率和磁盘状态则会影响计划执行时的真实耗时。源码中的 `EstimateCostForRefAccess()`（`sql/join_optimizer/cost_model.cc:59`）就是访问路径成本估算的一个具体入口。

### 4. 一个更具体的失败场景：加了索引，优化器仍然全表扫描

假设：

- 表有 100 万行，加了普通二级索引 `idx_status(status)`；
- 查询 `SELECT * FROM t WHERE status='APPROVED' AND amount>1000`；
- 但 `status='APPROVED'` 占比 60%，选择性极低；
- 走二级索引意味着：先扫 `idx_status` 拿到几十万主键，再逐行回表拿整行；
- 优化器估算后判断：全表扫描 + 过滤可能更便宜。

这就是“有索引不用”的根源：不是索引没建，而是成本模型认为走索引更贵。

### 5. 本节最该记住的结论：有索引不等于成本更低，优化器比较的是预计总成本；规则重写缩小问题空间，代价模型选最终计划

一句最短人话是：**优化器像导航软件：先把无效路线删掉，再估算时间、拥堵和收费，最后选“当前看起来最便宜”的路，而不是只看地图上有没有近路。**

## 二、访问方法与联接算法：同样是查表，路径可能完全不同

### 1. 第二个朴素误解：type=ref 一定比 all 快，Hash Join 一定比 Nested Loop 好

“ref 比 all 快”“Hash Join 比 Nested Loop 好”这两个直觉在类型排序和算法口碑上很常见，但它们脱离了数据分布和返回行数就毫无意义。

- `type=ref` 命中高选择性索引时确实比 `all` 好，但如果返回行数占比很大，走索引再回表的成本可能高于全扫；
- Hash Join 在内存预算内做哈希表，构建成本和内存占用都不低，如果外表很小或索引选择性很高，Nested Loop 可能更好。

所以访问方法和联接算法不是“类型排名”，而是在给定数据分布、返回行数、索引、内存预算和排序需求下的选择结果。

### 2. 单表访问方法与多表联接算法：两层不同的决策

单表访问方法：

```text
const    → 常量主键/唯一值快速定位
ref      → 通过索引等值匹配若干行
range    → 索引范围扫描
index    → 全索引扫描
all      → 全表扫描
```

多表联接算法：

```text
Nested Loop → 外表驱动内表，逐行探测
Hash Join   → 构建哈希表 + 探测匹配
```

某些旧版本或特定配置还可能出现 Block Nested Loop 等实现路径，但不能把它当成所有 MySQL 8.x 版本都稳定提供的通用算法。

关键区别是：**单表访问方法决定“一张表怎么取数据”，多表联接算法决定“多张表怎么配对”**。两者互相影响，但不可混为一谈。

### 3. 为什么 EXPLAIN 字段是症状描述，不是性能结论排名

如果读者把 `type` 字段当性能排名，就会掉进“const > ref > range > index > all”这种伪排序陷阱。实际上：

- `type=index` 表示全索引扫描；如果索引很宽，或者查询还需要回表拿非覆盖字段，可能不如全表扫描；
- `type=ref` 返回大量行时，大量回表会让成本爆炸；
- 一个 SQL 的每一个表都有各自的 `type`，跨表比较 `type` 没有意义。

所以正确姿势是：**EXPLAIN 字段是症状描述，不是性能结论排名**。要结合 `rows`、`filtered`、`Extra`（如 `Using filesort`、`Using temporary`）和你对数据分布的理解，才能判断真实效率。

### 4. 一个更具体的失败场景：统计信息误判，让 Nested Loop 重复扫描大表

假设：

- 表 A 实际有 20 万行，表 B 有 200 万行；
- 查询是 `SELECT ... FROM A JOIN B ON A.id=B.a_id`；
- 统计信息误以为 A 经过过滤后只剩几十行，于是选择 A 作为外表，用 Nested Loop 反复探测 B；
- 但 B.a_id 没有合适索引，或者每次探测都要扫描大量 B；
- 实际执行就可能变成几十万次重复扫描，远超优化器原先估算。

这时问题不是“Nested Loop 天生差”，而是外表行数、内表访问成本或索引条件被估错了。若 B.a_id 有高选择性索引，Nested Loop 仍可能是合理选择；若两边都需要大量扫描，Hash Join 或另一种联接顺序可能更合适。数据库索引探测也不能简单写成严格 O(1)，还要考虑 B+Tree 层高、缓存、回表和返回行数。

所以不能拍脑袋说“Nested Loop 就是差”，要看驱动方向、内表访问路径、估算行数和构建/探测成本。

### 5. 本节最该记住的结论：访问方法和联接算法只有在给定数据分布、返回行数、索引、内存预算和排序需求下才有意义；EXPLAIN 字段是症状描述，不是性能结论排名

一句最短人话是：**访问方法像进仓库拿货的路线，联接算法像两张订单如何对账；最短走路路线不一定是最低总时间，算法排名也一样。**

## 三、EXPLAIN 与 EXPLAIN ANALYZE：估算和事实是两张表

### 1. 第三个朴素误解：EXPLAIN 说只扫 100 行，真实就只扫 100 行

EXPLAIN 给出的是优化器视角的计划与估算，不是运行期事实。它受统计信息和成本模型驱动，估算错时会表现为“计划看起来合理、跑起来很糟”。

所以“EXPLAIN 说扫 100 行”只是优化器的预测。真实扫描行数、循环次数和耗时，要由运行期的执行观测来回答。

### 2. EXPLAIN、EXPLAIN FORMAT=JSON/TREE 与 EXPLAIN ANALYZE：三个层次

```text
EXPLAIN:
  id/select_type/type/possible_keys/key/rows/filtered/Extra
  → “优化器以为会发生什么”

EXPLAIN FORMAT=JSON/TREE:
  → 更完整的计划树/代价/附加信息

EXPLAIN ANALYZE:
  → “实际发生了什么”
  → 行数、循环次数、耗时等运行期观测
```

关键区别是：EXPLAIN 是**预测**，EXPLAIN ANALYZE 是**运行期事实**。源码中的 `ExplainAccessPath()`（`sql/join_optimizer/explain_access_path.cc:1665`）负责把访问路径转换为 EXPLAIN 表示，`AddPathCosts()`（`sql/join_optimizer/explain_access_path.cc:796`）则把成本和执行期统计等信息补进输出。ANALYZE 会真正执行目标语句，因此按语句类型和环境谨慎使用；它的支持范围、输出字段和格式也要按目标版本核对，不能把所有查询都直接跑一遍 ANALYZE。

### 3. 为什么只看 EXPLAIN 不够

计划树好看不代表线上在相同参数、并发和缓存状态下也快。EXPLAIN 是“干地质图”，ANALYZE 是“实际进度条”。两者搭配才构成证据链：

- EXPLAIN 告诉你“优化器打算怎么走”；
- ANALYZE 告诉你“真实走了哪步、每步多少行、多少耗时”；
- 偏差大说明估算失真，但也要结合统计、缓存、并发和 I/O 才能定位根因。

### 4. 一个更具体的失败场景：EXPLAIN 估算 100 行，实际扫了几十万行

假设：

- 优化器基于过期统计估算返回 100 行；
- 真实执行却扫了几十万行，耗时数秒；
- 先用 EXPLAIN ANALYZE 找出行数偏差最大的节点，再检查数据分布和索引统计；
- 如果确认统计过期，才考虑 `ANALYZE TABLE` 或 Histogram，并在代表性参数下重新对比计划与实际执行。

这就是“估算错 → 计划错 → 体验差”的完整链条。EXPLAIN 只说预测，ANALYZE 才说事实；更新统计不是固定处方，必须先确认偏差来源并回归验证。

### 5. 本节最该记住的结论：EXPLAIN 给假设，EXPLAIN ANALYZE 给事实；估算和事实偏差大时，要回到统计、索引和数据分布找原因

一句最短人话是：**EXPLAIN 像导航预估时间，ANALYZE 像实际行驶记录；两者偏差大时，说明地图或拥堵模型失真。**

## 四、慢查询日志：从线上症状切进优化器问题

### 1. 第四个朴素误解：线上慢，调低 long_query_time 就能找出所有问题

“调低阈值就能暴露所有慢 SQL”这个直觉在侦察思路上很自然，但慢日志不是“阈值越低越好”：

- 阈值过低放大量短但频繁的语句，日志每天几 GB，信噪比崩坏；
- 阈值过高漏掉关键尾延迟，慢的不是均值而是 99 分位；
- `rows_examined` 高也不一定等于磁盘 I/O 高，可能只是索引没覆盖，回表但数据都在 Buffer Pool。

所以慢日志不是“调参数就万事大吉”，而是“抓入口样本”的第一步。

### 2. 慢查询日志的配置、内容和工具

```text
慢日志配置:
  long_query_time
  min_examined_row_limit
  log_output(FILE/TABLE)

日志内容:
  query time / lock time / rows examined / rows sent / SQL 文本

工具:
  mysqldumpslow / pt-query-digest
  → 归一化模板
  → 统计 TOP N、分位、样例
```

关键是：慢日志把“超过阈值”的 SQL 收集为样本，再交给聚合工具归一化成模板。源码中的 `log_slow_applicable()`（`sql/log.cc:1592`）负责判断语句是否满足慢日志条件，`write_slow()`（`sql/log.cc:682`）负责把满足条件的语句写出。这样你得到的是“哪些 SQL 模板累计耗时最长”，而不是“哪条具体 SQL 很慢”。

这里几个字段不能混为一谈：`query_time` 是语句耗时，`lock_time` 是日志口径下的锁相关时间，`rows_examined` 是执行过程中检查过的行数，`rows_sent` 是返回给客户端的行数。`rows_examined` 既不是 EXPLAIN 的估算 `rows`，也不是 EXPLAIN ANALYZE 某个节点的实际行数；它高只能说明检查行数多，不能单独证明磁盘 I/O 高。

### 3. 慢日志是问题入口，不是根因结论

同一模板可能因参数、统计、并发事务和系统状态产生完全不同成本。有时候慢的是锁等待、复制追赶、磁盘抖动或缓存冷启动，而不是优化器算法本身。所以“抓到一条 TOP SQL”只是起点，真正定位要回到计划、事务等待和系统指标。

### 4. 一个更具体的失败场景：rows_examined 很高，但磁盘 I/O 很低

假设：

- 某 SQL `rows_examined` 显示几十万行；
- 但系统级 I/O 指标很低；
- 说明大量回表命中了 Buffer Pool，没有真正触盘。

如果只盯 `rows_examined` 就断言“磁盘 I/O 高”，会得出错误结论；正确姿势是结合系统指标判断“扫描多但缓存好”，还是“扫描多且触盘多”。

### 5. 本节最该记住的结论：慢日志是问题入口，不是根因结论；阈值、归一化和采样决定你看到的是症状还是噪音

一句最短人话是：**慢日志像急诊分诊单，先把超时病人集中起来；真正病因还要靠影像、化验和病史（计划、统计与系统指标）。**

## 五、从 digest 到计划验证：日志、sys schema 与系统观测要闭环

### 1. 第五个朴素误解：pt-query-digest 找到 TOP SQL，直接加索引就完事了

“定位到 TOP SQL → 加索引”这个直觉在解决问题的效率上很诱人，但它是跳过证据链的赌博：

- 同一模板可能因不同参数产生完全不同成本；
- 慢的可能是锁等待、事务阻塞、复制追赶或磁盘抖动；
- 加了索引可能掩盖真正的问题，例如数据倾斜、统计过期或并发争抢。

所以“定位到 SQL”只是第一步，必须先看等待与资源，再决定优化动作。

### 2. 完整分析闭环：从 SQL 模板到证据链

```text
慢日志 / digest
  → 找出高频/高总耗时/高尾延迟 SQL 模板
  → EXPLAIN/ANALYZE 看访问路径和行数偏差
  → 结合锁等待、I/O、Buffer Pool、CPU
  → 判断是估算错、索引缺失、数据倾斜还是事务阻塞

辅助:
  sys schema / Performance Schema 摘要
  → statement digest / lock waits / file I/O
```

关键是把 SQL 模板、执行计划和系统资源三个维度叠加到同一时间窗口。这样才有资格说“慢的到底是 SQL 本身，还是它背后的系统状态”。

### 3. 为什么“定位到 SQL”不能证明问题就在 SQL 文本

同一 SQL 模板，在不同参数、统计、并发和缓存状态下，成本可以差几个数量级。所以“这条 SQL 慢”可能只是症状，触发它的也许是：

- 缓存冷启动（Buffer Pool 初次填充）；
- 锁等待（某个长时间事务占了行锁）；
- 复制回放延迟或复制线程争用导致读请求等待；
- 磁盘抖动（邻居实例抢占 I/O）。

判断慢因必须把 SQL 模板、事务等待和系统资源观测对齐到同一个时间窗。

### 4. 一个更具体的失败场景：同一模板白天正常，晚上偶发超时

假设：

- 同一 SQL 模板白天 50ms，晚高峰偶发 5 秒；
- EXPLAIN 相同，参数相同；
- 但晚高峰并发报表任务占用大量 I/O 和 CPU；
- 加上锁等待放大，尾延迟被拖到秒级。

只盯模板文本会永远找不到答案，因为它的执行计划真的没变，变的是系统状态。

### 5. 本节最该记住的结论：慢 SQL 分析必须把字符串模板、执行计划、事务等待与系统资源对齐到同一时间窗；优化动作必须和 workload、尾延迟、资源观测一起复测

一句最短人话是：**慢日志告诉你哪条 SQL 慢，但只有把它当成入口，继续走计划和资源证据链，才能区分“SQL 本身的问题”和“SQL 背后的系统状态问题”。**

## 六、把本篇收成一张图：慢日志给出症状，EXPLAIN 给出假设，ANALYZE 给出事实，系统观测给出副作用

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：为什么同一条 SQL 在不同库会选不同计划，慢 SQL 到底怎么定位。答案已经闭环了。

优化器先做规则重写缩小问题空间，再用统计和成本模型从候选路径里选计划。访问方法和联接算法没有绝对排名，只有给定数据分布、返回行数、索引和内存预算下的选择结果。EXPLAIN 是预测，EXPLAIN ANALYZE 是事实。慢查询日志是入口样本，不是根因结论。最后要把字符串模板、执行计划和系统资源对齐到同一时间窗，才能判断“慢的到底是什么”。

把这一切压成最短总图，就是：

```text
慢日志/告警
  → digest 聚合/找模板
  → EXPLAIN 看优化器估算
  → EXPLAIN ANALYZE 看实际执行
  → 对照统计信息/索引/数据分布
  → 再对齐锁/I/O/CPU/缓存证据
  → 调整索引/SQL/统计/参数并回归验证
```

所以本篇最该记住的一句话是：**优化器不是数据库里的神谕，它只是基于统计和成本模型的预测器；慢查询日志给你症状，EXPLAIN 给你假设，ANALYZE 给你事实，系统观测告诉你副作用。**

## 七、几个最容易说错的地方

### 写了索引，优化器就应该走？

不是。优化器比较的是预计总成本，不是“有没有索引”。低选择性、回表成本、排序、临时表和并发状态都会影响结论。

### type=ref 一定比 all 快，Hash Join 一定比 Nested Loop 好？

不是。有没有索引和返回行数是决定因素。`type=ref` 返回大量行时要大量回表，Hash Join 有构建成本和内存占用。

### EXPLAIN 扫 100 行，真实就扫 100 行？

不是。EXPLAIN 是优化器估算，EXPLAIN ANALYZE 才是实际执行观测量。估算错时计划看起来合理，跑起来很糟。

### 调低 long_query_time 就能找出所有慢 SQL？

不是。阈值过低放大量短但频繁的语句，阈值过高漏掉关键尾延迟。`rows_examined` 高也不一定等于磁盘 I/O 高。

### 定位到 TOP SQL，直接加索引？

不是。同一模板可能因参数、统计、并发和系统状态产生不同成本。有时慢的是锁等待、复制追赶或缓存冷启动，而不是优化器算法。

## 收束：SQL 优化不是“看一条 SQL”，而是“看一条 SQL 在一套系统状态下的真实代价”

回到开头那个问题：为什么同一条 SQL 在两份数据分布不同的库上选不同计划。答案已经闭环了：优化器根据统计信息和成本模型选择总成本最低的路径，而统计和成本都来自当前数据分布与系统状态。

这就是为什么说：**优化器不是数据库里的神谕，它只是基于统计和成本模型的预测器；慢查询日志给你症状，EXPLAIN 给你假设，ANALYZE 给你事实，系统观测告诉你副作用。** 只要这条主线站稳，后面进入子查询优化、sys schema 与 Performance Schema 时，你就不会再被“计划排名”这种伪排序限制，而会始终把“估算 vs 事实 vs 系统副作用”三条证据线放在诊断第一位。
