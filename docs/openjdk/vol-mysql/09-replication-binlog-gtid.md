## 现在真正该问的，不再是“主库写完了，副本会不会自动知道”，而是“binlog 怎么被生产、怎么传输、怎么落盘、怎么回放，以及进度到底靠什么描述”

前面几篇已经把单实例事务和锁打得很深了。你已经知道：

- Group Commit 把多个事务的 fsync 合并，并协调 binlog 与引擎提交边界；
- Undo 和 Purge 让未提交修改可撤回、旧版本在最后一个读者离开后才清理；
- MDL 保护对象定义，Record/Gap/Next-Key 保护数据范围，InnoDB 内部锁保护引擎结构；
- 锁等待、死锁和长事务可能放大复制延迟，也会反过来影响主库提交。

如果只停在这里，你很容易形成一层危险的单实例幻觉：

“事务提交了，那这件事不就已经结束了吗？”

在单实例上这当然成立。可一旦进入多实例世界，前台提交只是整个复制链路的起点。一笔事务从“主库已经提交”到“副本已经安全回放”，至少还要经过五段接力：

1. **生产**：binlog event 被主库写进日志，`ordered_commit()` 之类的路径安排好提交顺序和持久化边界；
2. **传输**：DUMP 线程读取 binlog 并发送给副本；
3. **接收与持久化**：副本 IO 线程接收事件并写入 Relay Log；
4. **回放**：SQL/applier 线程读取 Relay Log，重建事务并更新回放进度；
5. **确认**：半同步下主库要等 ACK 才向客户端确认，异步下则直接返回。

所以一次“提交成功”在复制世界里并不是句号，而是事件生产链的起点。

先把总图记住：

```text
主库事务提交
  → binlog event / GTID
  → DUMP 线程发送
  → 副本 IO thread 接收并写入 Relay Log
  → SQL / applier 回放
  → executed 状态推进
  → 半同步 ACK / 延迟观测
```

这篇最该先记住的一句话是：**复制不是数据自己出现，而是事件生产、传输、Relay 落盘、事务回放和进度确认五段接力；位点/GTID 告诉你进度，半同步告诉你确认边界，`Seconds_Behind_Master` 只是近似信号。**

## 一、三线程复制模型：复制不是“主库直接推数据文件”，而是把生产、传输和回放拆成不同角色

### 1. 最朴素的错误世界：副本要么直接读主库数据文件，要么主库把数据文件整份复制过去

如果不了解 binlog 的传输模型，很容易脑补出两种直觉：

- 副本直接连到主库存储上读数据文件；
- 或主库每次提交后，把数据文件整体复制到副本。

这两种在现实中都不成立。因为数据文件包含引擎页、缓存、undo、redo 和实例状态，直接复制无法保证并发、恢复和实例一致性。而“每次提交都复制整份文件”又不可扩展。

所以 MySQL 的答案是把“变更记录”变成可独立传输、可回放的结构化日志：binlog。

### 2. 三线程不是“三个角色任意选”，而是把生产、传输和回放拆成独立的执行链

教学上可以先压成经典模型：

```text
主库方面
  → Binlog Dump / 发送线程
    从 binlog 读取事件，发送给副本

副本 IO thread
  → 接收 binlog events
  → 写入 Relay Log

副本 SQL / applier thread（或 MTS coordinator + worker 组）
  → 读取 Relay Log
  → 重建 / 执行事务
  → 更新回放进度
```

这个模型最重要的价值，不是“三个线程”这个数字，而是把“网络接收”和“本地回放”拆成两个不同的阶段。这样：

- IO thread 可以专注于网络和持久化，不会因为回放慢而被拖住；
- SQL/applier 可以专注回放，不会因为网络延迟而空转；
- 两者之间通过 Relay Log 解耦，也允许并行回放的出现。

### 3. 为什么副本不能只同步主库数据文件，而要依赖 binlog

这个问题在 03 篇的 Group Commit 章节已经露过脸，但在这里必须再收紧一次。binlog 被设计成复制的主要载体，有几个原因：

- binlog 是已经按事务顺序组织好的可传输事件流；
- 它不依赖引擎页的当前状态；
- 副本回放时，不需要和主库的并发控制或缓存状态保持同步；
- 它可以被过滤、重放、拆分、甚至跨版本。

数据文件本身则没有这些属性。所以复制不是“让两个实例的文件长一样”，而是“把一个实例的变更事件流，在另一个实例上按顺序回放出来”。

### 4. 为什么 DUMP 不是“读最新的 binlog 就发”，而是要从文件/位点/GTID 开始

DUMP 线程不是“实时监听 binlog 并立刻广播”。它更像是：

- 先根据副本传来的位点或 GTID 信息，定位到 binlog 里的某个位置；
- 然后从那里开始读取事件，并持续发送给副本；
- 副本掉线重连后，再发一次新的定位请求。

也就是说，DUMP 是“从指定位置开始持续读取”，不是“从最新位置开始无脑广播”。源码上，主库侧的提交顺序和 binlog 持久化边界可以落到 `MYSQL_BIN_LOG::ordered_commit()`（`sql/binlog.cc:8855`），而 GTID 事务的生成和写入则可由 `MYSQL_BIN_LOG::gtid_end_transaction()`（`sql/binlog.cc:1839`）等路径体现。

### 5. 一个更具体的失败场景：IO thread 正常但 SQL thread 卡住，会让 Relay Log 持续膨胀

假设主库写入量很大，IO thread 接收正常，但 SQL thread 因为锁等待、大事务或单线程瓶颈而卡住：

- IO thread 继续接收新事件，Relay Log 持续增长；
- 磁盘空间可能被 Relay Log 吞掉；
- 副本的“接收进度”仍然在前进，但“回放进度”几乎不动。

这时只看 `SHOW REPLICA STATUS` 里的 IO thread 状态，会误以为复制一切正常。真正的问题在 SQL thread 侧。

### 6. 本节最该记住的结论：三线程模型把生产、接收和回放拆成独立阶段，Relay Log 成为 IO 与 SQL 之间的缓冲区；DUMP 按位点/GTID 定位，不是最新广播；IO 正常不代表回放正常

一句最短人话是：**主库是出单仓库，Dump 是发货员，副本 IO 是收货登记，Relay Log 是待处理货单，SQL/applier 是执行工人。**

## 二、Binlog Event：复制传输的不是“SQL 文本”，而是按事务组织的最小叙事单元

### 1. 第二个朴素误解：binlog 就是一串 SQL 语句，副本收到后重新执行一遍就行

如果你只见过 statement-based 复制的名字，或者只看过 `mysqlbinlog` 输出里的 SQL 文本，很容易这样想。

但行格式做主导时，binlog 的核心不是 SQL 文本，而是**描述了“哪个库、哪个表、哪一行、被改成了什么样子”的事件结构**。

### 2. Binlog Event 不是“一条 SQL”，而是“header + data”的事件结构

教学上可以先压成最小模型：

```text
每个 Event
  header（类型、长度、时间戳、日志位置等）
  event data（表结构、行镜像、GTID、XID 等）

典型事件
  GTID_EVENT
  QUERY_EVENT（部分 DDL 或语句）
  TABLE_MAP_EVENT（行事件需要的表结构映射）
  WRITE_ROWS / UPDATE_ROWS / DELETE_ROWS
  XID_EVENT（事务提交标记）
```

也就是说，复制传输的最小叙事单位不是 SQL 语句，而是按事件组织的事务日志。

### 3. `binlog_row_image` 为什么影响事件大小，而不影响“能不能回放”

`binlog_row_image` 控制行事件里记录哪些列：

- `full`：记录所有列；
- `minimal`：只记录必要列（主键、被更新列）；
- `noblob`：记录除 blob 外的所有列。

它影响的是事件大小和网络/磁盘成本，不影响“副本能不能回放”。但这里有一条非常容易被低估的边界：**如果表没有主键或唯一索引，`minimal` 的 before image 将很难定位目标行，副本可能被迫做全表扫描，甚至产生 `ROW_DOES_NOT_EXIST` 或 `DUPLICATE_KEY` 错误。** 所以 `minimal` 不是永远安全的“小事件开关”，它是否安全高度依赖表是否有主键或唯一索引。无主键表上使用 `minimal` 会让复制在 UPDATE/DELETE 时承受更大的回放风险和性能代价。

### 4. 一个更具体的失败场景：statement 格式在某些非确定性 SQL 上让副本重现出和主库完全不同的结果

statement-based 复制在理论上很简洁：把 SQL 文本发给副本，副本重新执行一遍。但一旦 SQL 涉及非确定性函数、`LIMIT` 无排序、触发器、自增列、UUID 或系统变量，副本的执行结果就可能和主库不一样。

这正是行格式被越来越广泛采用的原因。它不依赖 SQL 重新执行的环境，而是直接把行变更的前后镜像或必要信息传过去，副本只需按行重建。

### 5. 为什么 binlog event 格式、header 长度和事件类型不能脱离版本单独讲

MySQL 8.x 和 5.x 的 binlog 事件类型、header 字段和格式有差异，甚至同一版本的不同补丁也会改变细节。所以正文只能建立“event 是复制的最小叙事单位”的机制地图，具体位段、长度和事件类型要按目标版本核对。

### 6. 本节最该记住的结论：Binlog Event 是复制传输的最小叙事单位，行格式携带行镜像，statement 格式依赖 SQL 重执行环境；`binlog_row_image` 影响事件大小但不影响回放能力

一句最短人话是：**Binlog 像仓库的标准出货单：有的写“执行这条指令”，有的写“把这些行改成这些值”；副本按货单重建自己的库存。**

## 三、位点与 GTID：复制进度不是“一个数字”，而是“主库某一时刻的日志位置”或“一组事务身份集合”

### 1. 第三个朴素误解：副本只要知道“我已经追到哪”，那就是一个简单的数字或位置就能解决

这个直觉在单主单从这个最简单拓扑里还能勉强成立，但一旦你有：

- 主库 binlog 滚动；
- 副本重连；
- 主从切换；
- 复制拓扑变更；
- 跨实例校验；

“一个简单的数字”就容易变成“文件+偏移、手写、容易错、切换后更麻烦”的复杂现实。

### 2. 传统位点：`MASTER_LOG_FILE + MASTER_LOG_POS` 是最直接的进度表达，但依赖文件视角

传统位点模式很直观：

- 告诉副本“从哪个 binlog 文件的哪个字节开始拉”；
- 副本按这个位置继续请求；
- 主库 binlog 滚动后，文件多了，位点仍然可以定位。

但它的弱点也很真实：

- 副本重连时，如果主库的 binlog 已经滚动或清理，位点可能已经失效；
- 主从切换后，新主库的 binlog 文件序列通常不同，需要重新计算位点；
- 人工操作时，`MASTER_LOG_FILE` 和 `MASTER_LOG_POS` 容易写错。

### 3. GTID：不再依赖文件名，而是让每笔事务都有一个全局唯一的身份

GTID 的核心思路是：

- 每笔事务在生成时获得一个 `server_uuid:transaction_id` 的全局身份；
- 副本执行后，在 `gtid_executed` 集合里记录它已经执行过的事务；
- 重连或切换时，副本发送自己已执行的 GTID 集合，主库过滤出缺失的事务发送。

```text
GTID 生命周期
  事务提交 / 生成
  → 写入 binlog 和 GTID 状态
  → 副本接收 / 执行
  → executed / purged 集合推进
```

这样，复制进度就不再绑定到某个文件的偏移，而是一组事务身份集合。源码上，GTID 在事务提交时的生成可以落在 `MYSQL_BIN_LOG::gtid_end_transaction()`（`sql/binlog.cc:1839`），而副本侧回放进度的持久化推进可以落在 `Relay_log_info::commit_positions()`（`sql/rpl_rli.cc:2793`）。

### 4. 为什么 GTID 不是“万能的”，它处理的是“缺哪些事务”，不是“数据冲突”

GTID 非常擅长解决“副本需要哪些事务”的定位问题，但它不解决：

- 数据冲突；
- 主库和副本上的数据漂移；
- 跳过某些事务后的数据一致性。

所以 GTID 不是“复制一下子就完美了”，而是“复制定位从手工文件偏移升级为自动事务集合”。

### 5. 一个更具体的失败场景：GTID 已启用，但副本因为 `gtid_purged` 被错误设置而丢失事务

假设在恢复或重建副本时，手动设置了 `gtid_purged`。如果这个集合比实际已经执行的事务范围更大，主库将认为“这些事务副本已经不需要了”，从而跳过它们的发送。结果就是副本丢失了本该回放的事务，但 `gtid_executed` 里却显示“已经执行过了”。

这不是 GTID 的缺陷，而是 GTID 集合的维护需要和真实执行状态一致。如果 `gtid_purged` 被错误设置，GTID 本身不会自动察觉“你的集合声明和实际状态对不上”。

### 6. 本节最该记住的结论：传统位点依赖于 `MASTER_LOG_FILE + MASTER_LOG_POS` 的描述，GTID 则把进度升级为事务身份集合；GTID 解决的是“缺哪些事务”，不是“数据冲突”或“集合被错误设置”

一句最短人话是：**位点像“第 3 本账本第 100 页”，GTID 像每笔交易的全球订单号；换一套账本后，订单号仍能判断哪些交易已经处理。**

## 四、半同步：主库确认的时机，是可靠性与延迟之间的交易

### 1. 第四个朴素误解：只要用半同步复制，数据就一定不会丢，主库确认时副本一定已经落盘了

半同步确实比异步更接近安全，但“半同步”不等于“永不丢”。它至少还要看：

- 确认时机（`after_sync` vs `after_commit`）；
- 超时降级策略；
- 副本的落盘配置；
- 网络故障场景下的行为。

### 2. 半同步的核心：主库在向客户端返回“成功”之前，等一个副本的 ACK

教学上可以先压成最小模型：

```text
事务提交
  → 主库写 binlog / 引擎日志
  → 发送给副本

副本
  → 接收并确认（ACK 到达，通常已写入/刷到 Relay Log，配置相关）

主库
  → 收到满足条件的 ACK
  → 才向客户端返回成功
  → 超时可能降级为异步
```

这个模型的关键是：主库确认的时机，不是“自己已经提交”，而是“至少有一个副本也确认了”。这就把可用性窗口从“单机”推到了“至少一个副本也接到了”。源码上，半同步的确认可以落在 `repl_semi_report_commit()`（`plugin/semisync/semisync_source_plugin.cc:109`）等路径，但具体 ACK 语义和配置需结合版本核对。

这里必须钉一句非常关键的事实边界：**ACK 通常意味着副本已写入/刷到 Relay Log 的配置边界，不自动等于这笔事务已经回放到 InnoDB、对副本读可见。** 如果主库在收到 ACK 后、副本真正回放前宕机，应用可能以为“至少一个副本已经拿到了”，但副本并没有真正提交。这个差异在故障切换场景下极其重要：半同步缩小的是“传输丢失窗口”，不是“回放完成窗口”。

### 3. `after_sync` 与 `after_commit` 在异常窗口上的差异

`after_sync` 和 `after_commit` 的差别，不只是一个配置选项，而是主库在“引擎提交”和“向客户端返回”之间等待 ACK 的时机不同。在异常窗口（如主库在提交后、ACK 返回前宕机）下，两者对客户端可见性的影响不同。具体差异要结合目标版本和故障场景核对，不能仅靠配置名推断。

### 4. 半同步的超时降级为什么不是“出问题就变异步，恢复后自动同步”

半同步超时后降级为异步，是为了不让副本的延迟或网络问题反过来拖死主库提交。但降级后：

- 主库不再等待 ACK；
- 客户端看到的“成功边界”从“至少一个副本已确认”退回到“主库本地已提交”；
- 如果降级后继续发生主库故障，未同步到副本的事务就可能丢失。

所以半同步的价值不是“永不丢”，而是“在正常情况下缩小丢失窗口；发生异常时，系统选择降级而不是卡死”。

### 5. 一个更具体的失败场景：半同步下，主库写完 binlog 但副本还没收到 ACK，此时主库宕机

假设主库完成了 binlog 同步，等待副本 ACK 时宕机：

- 半同步状态下，主库尚未向客户端返回成功；
- 副本可能还没收到这笔事务的 binlog event；
- 如果主库无法恢复，这笔事务的 binlog 可能已经写在主库文件里，但副本没有；
- 应用需要明确自己的故障模型和重试策略。

所以半同步缩小的是“主库提交后、ACK 返回前”的窗口，不是消除窗口本身。

### 6. 本节最该记住的结论：半同步在异步基础上增加了 ACK 等待，缩小了“客户端已确认、副本尚未收到”的窗口，但超时降级、确认时机和故障场景仍然需要结合配置和故障模型一起理解

一句最短人话是：**异步像发快递后立即告诉客户“已寄出”，半同步像等一个分仓回短信“已收到”再确认；短信和货物真正入库仍是不同保障层。**

## 五、Relay Log、延迟与复制基础设施：`Seconds_Behind_Master` 是近似信号，不是完整答案

### 1. 第五个朴素误解：`Seconds_Behind_Master` 为 0，就说明副本和主库完全一致

这是复制监控里最容易被误读的单一指标。`Seconds_Behind_Master` 的计算方式依赖于事件时间戳和 SQL thread 当前位置，但：

- 主从时钟不同步，这个值本身就有偏差；
- 副本空闲时，SQL thread 没有事件可执行，SBM 可能为 0，但主库可能已经提交了新事务；
- 大事务执行时，SBM 可能突然跳很大，但这不是“连不上了”，而是“正在执行一个大事务”；
- 并行回放下，部分事务可能已经提交但某些事务还在等待协调。

所以 SBM 是复制延迟的近似信号，不是精确的“副本数据和主库完全一致”的证明。

### 2. 复制延迟要拆成三段时间看

更可靠的延迟分析，至少要把“主库提交 → 副本收到”、“副本收到 → 副本回放”、“副本回放 → 副本可见”三段拆开：

- 网络传输延迟；
- IO thread 接收和 Relay Log 落盘延迟；
- SQL/applier 回放延迟（包括大事务、锁等待、单线程瓶颈）。

`SHOW REPLICA STATUS` 提供了 IO thread 和 SQL thread 的进度，但真正的“副本读到的数据是否已经赶上主库”还需要结合 GTID executed 和业务读路由判断。

### 3. Relay Log 为什么是 IO 和 SQL 之间的缓冲，而不是无限容量的安全区

Relay Log 是 IO thread 写入、SQL thread 读取的中间文件。如果 SQL thread 回放速度跟不上 IO thread 接收速度：

- Relay Log 持续增长；
- 磁盘空间可能被占满；
- 副本可能开始拒绝接收新事件，或者直接被 IO thread 阻塞。

所以 Relay Log 不是无限缓冲区，它只是把网络接收和本地回放解耦，但不解决“回放太慢”这个根本问题。源码上，IO thread 接收事件后写入 relay log 的路径可以落在 `MYSQL_BIN_LOG::after_write_to_relay_log()`（`sql/binlog.cc:6864`），而 SQL/applier 推进回放进度的 checkpoint 则落在 `Relay_log_info::commit_positions()`（`sql/rpl_rli.cc:2793`）。

### 4. 副本崩溃恢复：SQL thread 回放进度与 relay log 位置推进之间的脆弱窗口

这是复制正确性里非常容易被忽略、却非常关键的一层。SQL thread 在回放事务时，并不是“回放一笔、立刻落盘一笔进度”。它通常：

- 先读取 relay log 中的事件并执行；
- 在一笔事务回放完成后，再把 relay log 位置或 GTID 集合推进到持久化点。

如果副本在这两笔动作之间崩溃：

- 事务已经回放到了 InnoDB 数据页；
- 但 relay log 信息或位置还没有被更新；
- 重启后，副本可能从旧位置重新读取并重放同一笔事务。

对于行格式的 binlog event，重放通常是幂等的，因此不会造成数据错误，但会浪费时间和资源。更重要的是，如果副本恢复时没有正确丢弃未完成的 relay log，它可能从半截位置开始读，读到不完整的事件并报错。这就是为什么 `relay_log_recovery` 和 GTID 持久化机制如此重要：它们确保副本重启后不会把未完成的中继日志当成有效事件，也不会因为回放进度与位置进度不一致而丢失事务或重复回放。

### 5. 为什么大事务会让 `Seconds_Behind_Master` 出现突发或误导

- 执行期间，SBM 开始上升；
- 执行完成后，SBM 又回落到接近于 0 或更低；
- 这不是“网络刚恢复”或“副本突然赶上了”，而是 SQL thread 花了一大块时间在执行同一个事务上。

所以单看 SBM 曲线，很容易把“大事务正在执行”误判成“复制延迟突然飙升”。

### 5. 本节最该记住的结论：`Seconds_Behind_Master` 是复制延迟的近似信号，不是精确答案；延迟应该拆成网络传输、Relay 落盘和回放三段来看，Relay Log 是 IO 与 SQL 之间的缓冲但不是无限安全区

一句最短人话是：**SBM 像车速表，显示的是“此刻正在处理的事件时间戳与当前时间的差”，不一定代表“副本数据已经追上主库”。**

## 六、把本篇收成一张图：复制不是“数据自动同步”，而是事件生产、传输、Relay 落盘、回放和进度确认五段接力

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：主库提交一笔事务后，副本到底靠什么感知“改了哪”，怎么确保不丢不重，以及位点、GTID、半同步和 SBM 分别站在哪一层回答进度。答案已经闭环了。

复制不是“让两个实例的数据文件长一样”，而是把一笔事务的变更先变成 binlog event，再经过生产、传输、Relay 落盘、回放和进度确认五段接力。传统位点用 `MASTER_LOG_FILE + MASTER_LOG_POS` 描述进度，GTID 则升级为事务身份集合。半同步在异步基础上增加 ACK 等待，缩小了“客户端已确认、副本尚未收到”的窗口。`Seconds_Behind_Master` 是近似信号，真正的延迟分析需要拆成网络传输、Relay 落盘和回放三段来看。

把这一切压成最短总图，就是：

```text
主库事务提交
  → binlog event / GTID
  → DUMP 发送
  → IO thread 写入 Relay Log
  → SQL / applier 回放
  → executed 状态推进
  → 半同步 ACK / 延迟观测
```

所以本篇最该记住的一句话是：**复制不是“数据自己出现”，而是事件生产、网络传输、Relay 持久化、事务回放和进度确认五段接力；位点/GTID 告诉你进度，半同步告诉你确认边界，`Seconds_Behind_Master` 只是近似信号。**

## 七、几个最容易说错的地方

### 复制是不是“主库把数据文件同步给副本”？

不是。复制传输的是 binlog event，不是数据文件本身。副本通过回放 binlog 来重建事务，而不是直接复制引擎页。

### 三线程模型是不是“三个线程一定会同时存在”？

它是经典模型，不同版本和配置下可能有不同的线程角色和并行度，但“生产、接收、回放”三段分离的思想是稳定的。

### `binlog_row_image=minimal` 是不是会丢失回放能力？

不会。它只影响事件大小，不影响副本能否回放；但太小的镜像可能在某些场景下需要更多索引信息来定位记录。

### GTID 是不是解决了复制的一切问题？

不是。GTID 解决的是“缺哪些事务”的定位问题，不解决数据冲突、集合被错误设置或复制拓扑变更后的数据一致性。

### 半同步是不是等于“数据绝对不会丢”？

不是。半同步缩小了“客户端已确认、副本尚未收到”的窗口，但超时降级、确认时机和故障场景仍然可能影响最终一致性。

### `Seconds_Behind_Master` 为 0 是不是就说明副本和主库完全一致？

不是。SBM 是近似信号，受时钟、空闲、大事务和并行回放影响，不能单独证明读一致性或零延迟。

## 收束：复制最危险的习惯，不是“延迟很高”，而是“你以为已经同步了，但其实只是事务主库已经提交了”

回到开头那个问题：主库提交一笔事务后，副本到底靠什么知道“改了哪”，怎么确保不丢不重？答案已经完整闭环了。复制不是数据的自动双写，而是 binlog event 的生产、传输、Relay 落盘、回放和进度确认五段接力。一笔事务从“主库提交”到“副本安全回放”，中间经过的每一段都可能成为瓶颈或故障点：传输可能延迟，Relay 可能膨胀，回放可能被锁等待或大事务拖住，半同步可能在超时后降级，SBM 可能只是近似信号。

也正因为如此，排障和设计时最危险的习惯，不是“延迟偏高”，而是“你以为已经同步了，但其实只是主库提交了、binlog 还在路上、Relay 还在排队、或者回放还在等一把锁”。

这就是为什么说：**复制不是“数据文件自动同步”，而是事件生产、传输、Relay 持久化、事务回放和进度确认的五段接力。** 只要把每一段分开看，再结合位点/GTID、半同步和延迟观测把每一段的进度对齐，复制才会从“看起来像自动同步”变成你可以诊断和治理的工程系统。
