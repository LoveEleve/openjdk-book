# 等待分析：真正把慢请求拖长的，往往不是“它在执行太久”，而是它一直在等——等 CPU、等锁、等页、等 I/O、等网络、等定时器，或者等业务队列轮到自己

## 现在真正该问的，不再是“这条路径经过了哪些函数”，而是“这些时间到底花在执行、排队还是等待哪一种资源上”

上一章我们已经把 tracing 的工具箱搭起来了。你知道聚合指标只能告诉你“哪类资源出问题”，而 ftrace、kprobe、tracepoint、BCC、bpftrace 则能把这类异常重新拉回函数、参数和时间线。也就是说，**你现在终于看得见慢路径长什么样。**

可路径看见了，不等于账已经分清。因为一个 1 秒慢请求里，真正属于“CPU 在执行指令”的时间，可能只占其中很小一部分；剩下的大头可能是：

- 线程排在 run queue 里等 CPU；
- 线程睡在锁上等别人放锁；
- 页 fault、回收、swap 或远端 NUMA 访问让它等内存；
- bio、fsync、设备队列让它等磁盘；
- RTT、重传、零窗口、代理回源让它等网络；
- timer/backoff/限流窗口让它等时间；
- 线程池、连接池、消息队列、事件队列让它等业务层排队。

这意味着“慢”这个现象在最后落到时间账本上时，几乎从来都不是一类时间。你不能只说“这个请求花了 1 秒”，还得问：**这 1 秒里，真正执行了多少，剩下又分别卡在了哪类等待上。**

所以本篇最重要的顿悟是：**等待不是一个统称，而是一套必须被拆开的时间账本；只有把 wall-clock 拆成执行、调度、锁、内存、磁盘、网络、时间和业务队列几类等待，你才知道该改线程数、锁粒度、数据布局、批处理、背压还是协议参数。**

先把总图记住：

```text
总时间：
  wall-clock = on-CPU 执行 + off-CPU 等待

等待大类：
  1) CPU 调度等待
  2) 内存等待
  3) 磁盘等待
  4) 网络等待
  5) 锁等待
  6) 时间等待(定时器/退避/限流)
  7) 业务队列等待

分析核心：
  先判断“是执行太多、执行太慢，还是根本没获得服务机会”
  再按等待类型挑工具和优化动作
```

这一篇最重要的一句话是：**性能优化很多时候真正该做的不是“把代码跑得更快”，而是“别让请求在不该排队和不该等待的地方白白耗掉时间”。**

## 一、如果你不先把总时间拆成 on-CPU 和 off-CPU，再进一步把 off-CPU 分类，所有“慢”最后都会被你错归到 CPU 或某个热点函数头上

### 1. 最常见的误解：函数热、CPU 高，就说明请求大部分时间都在执行

上一章刚看完火焰图和 tracing，很多人很自然会把注意力锁死在“谁宽、谁热、谁 CPU 高”。这当然常常有价值，但也很容易误伤。因为很多慢请求里，真正 on-CPU 的时间可能只占一小段，热函数只是“它一旦被调到 CPU 上时做了些什么”，而不是“它为什么整体这么慢”的全部答案。

例如一个线程 1 秒后才返回，其中 30ms 在 CPU 上真正执行，剩下 970ms 都在等锁、等 I/O、等网络。你若只看 on-CPU 火焰图，就会非常容易误以为那 30ms 的函数热点是全部故事，从而在错误层次上继续深挖。

### 2. 为什么 wall-clock 和 CPU time 的差值本身就是第一份关键证据

只要一个请求 wall-clock 很大，而它真正消耗的 CPU time 并不高，你就已经有了强烈信号：**大头不是执行，而是等待。**

这并不自动告诉你等在哪，但至少先把问题从“怎么让 CPU 跑得更快”转成了“为什么这个线程得不到持续推进”。这一步特别值钱，因为它防止你在最开始就掉进“先看热点函数再说”的旧陷阱里。

### 3. 为什么“等待”必须继续拆分，而不能只说一句 off-CPU

因为等锁和等网的优化动作完全不同，等磁盘和等 CPU 调度也完全不同。off-CPU 只是一个大类，它告诉你线程没在运行，但没有告诉你它把时间交给了谁。真正有意义的是继续问：**它是在等资源，还是等别人释放资源，还是等业务逻辑轮到自己。**

所以等待分析本质上是第二次分诊：先把“没在 CPU 上跑”从“在 CPU 上慢”分开，再把“没在 CPU 上跑”的世界继续切成七类。若要把这一节补成更硬的证据位，最关键的落点应回到 wall-clock/CPU time 对照、on/off-CPU 采样、`perf sched`、调度 tracepoint 与等待栈路径：它们共同支撑“总时间差值先证明等待存在，再继续分类等待归属”这句判断。

### 4. 本节最该记住的结论：性能分析里，先把总时间拆成执行与等待，再把等待拆分类别，是防止盯错对象的第一道保险

一句最短人话是：**先分执行和等待，不然你会把每一种慢都误会成算得慢。**

## 二、七维等待：同样 1 秒的慢，等 CPU、等锁、等页、等盘、等网、等 timer、等业务队列，最后对应的是七种完全不同的修法

### 1. CPU 调度等待：线程已经准备好了，却还没轮到它跑

这类等待最容易被误判成“CPU 不忙，所以不是 CPU 问题”。事实上，线程可以因为 run queue 拥堵、优先级、IRQ/softirq 干扰或绑定策略而长期拿不到核心，哪怕总 `%CPU` 看起来并不夸张。这里的问题不是“算不快”，而是“**没获得运行机会**”。证据位上，这层最值得回到 run queue、唤醒延迟、`sched_switch`/调度 tracepoint 与 `perf sched` 相关路径去看：它们共同支撑“线程 runnable 不等于已经 running，CPU 利用率不高也可能存在严重调度等待”的判断。

对应线索通常是 run queue 变长、唤醒延迟增加、off-CPU 栈里停在调度等待点，或 `perf sched` 之类工具显示 runnable 到 running 的等待异常。

### 2. 内存等待：不是只有 OOM 才算内存问题

内存等待可以来自 page fault、回收、swap、THP 分配、NUMA 远端访问、page walk/TLB 行为等。很多系统明明没有 OOM，却已经因为内存压力 stall 在 `some/full` PSI 上，或者因为远端 NUMA 访问把访问时间拉高。

这里的问题不是“内存够不够总量”，而是“**当前这次访问想要的页和数据，取得是不是太慢、太远或太费回收代价**”。

### 3. 磁盘等待：大部分时候你等的不是盘本身，而是排队、fsync 或写回债务

一个请求可能因为 `read()` 真缺页打到设备，也可能因为 `fsync()` 被迫等脏页真正落盘，还可能只是排在块层和设备队列前面。磁盘等待真正常见的形态不是“磁盘完全停了”，而是“**队列和尾延迟开始把服务时间往外拉**”。若要补这一层的证据位，最合适回到 iostat/`/proc/diskstats`、block tracepoint/biolatency 与应用 I/O 时序路径去看：它们共同支撑“磁盘等待的核心常常是排队与尾延迟，而不只是设备总吞吐”的判断。

### 4. 网络等待：从 RTT 到代理回源，很多等待根本不在你的进程本机里

网络等待既可能是单纯 RTT，也可能是重传、拥塞、零窗口、代理回源、TLS 握手、WebSocket 保活，甚至连接池等上游应用网络语义。也就是说，它并不是“网卡带宽不够”这么单一，更多时候是端到端路径某段没给你及时反馈。

### 5. 锁等待：CPU 再快也没用，只要别人没放钥匙，你就在门口站着

锁等待通常表现为线程明明 runnable 或可继续业务逻辑推进，却卡在 futex、mutex、rwsem、自旋锁冲突或用户态互斥体上。它最危险的地方在于：**你继续加线程、加核心，反而可能把争用放大。**

### 6. 时间等待：很多慢请求并不是资源不够，而是系统有意让你等等

退避、定时器、重试窗口、Nagle/Delayed ACK、令牌桶限流、批处理等待窗，都会把时间明确“花在等一下”。这类等待常常不是 bug，而是系统为了平衡吞吐、稳定性或公平性故意引入的节奏控制。它的优化问题就变成：这个等待是否还值得、窗口是否过大、有没有更好的批量边界。

### 7. 业务队列等待：资源没满，但上游框架和业务调度已经在排队

线程池、任务队列、连接池、消息中间件、事件循环 backlog、单线程 actor/mailbox 都可能成为“资源看着都还行，用户却已经在排队”的根源。这里的等待通常根本不在内核，而在应用自己组织并发的方式上。

### 8. 本节最该记住的结论：同一个“慢”必须先被放进正确等待类别，否则后面的工具、归因和优化动作都会偏航

一句最短人话是：**等待这张账单必须先分类，不然你会拿修磁盘的办法去治锁竞争。**

## 三、执行太多、执行太慢和排队：真正该区分的不是“慢不慢”，而是“这次请求到底是在多干活、低效干活，还是根本没轮到它干活”

### 1. 执行太多：工作量本身就超了

如果 CPU time 高、instructions/work 高，而且 on-CPU 栈看起来确实在做大量有意义工作，那问题往往在“干得太多”：算法复杂度不对、重复计算、无意义对象创建、序列化过重、单请求工作量超预期。这里最需要的是减活，不一定是提速。

### 2. 执行太慢：工作量没那么大，但每单位工作做得很低效

这类情况常表现为 wall-clock 和 CPU time 都不低，但 IPC 低、cache/TLB/branch 指标很难看。也就是说，程序确实在做活，只是每份活的执行效率很差。根因可能在数据布局、分支预测、cache 命中、向量化或指令级实现。

这里的关键词不是“少做”，而是“**同样的活做得更值**”。

### 3. 排队/等待：活并不多，效率也不一定差，真正的问题是它总在等轮到自己

这类场景里 wall-clock 很高，但 on-CPU 时间不大，off-CPU 却很重。你若继续死盯热点函数，往往会浪费很多精力，因为真正该优化的是锁粒度、队列深度、I/O 模式、网络等待或线程调度。这里关键词不是“算力”，而是“服务机会”。

### 4. 为什么这三类必须被分清

因为它们对应的动作几乎完全不同：

- 执行太多 → 算法/工作量/批量边界/去重；
- 执行太慢 → 微架构、数据布局、SIMD、缓存、分支；
- 排队/等待 → 锁、I/O、并发模型、背压、调度、队列设计。

把它们混为一谈，是很多优化最后变成“换一组参数碰碰运气”的根源。

### 5. 本节最该记住的结论：真正该先判的是“是不是做了太多工作、是不是低效做工作、还是根本没获得做工作的机会”

一句最短人话是：**太多、太慢、太等，是三种完全不同的慢。**

## 四、优化动作必须和等待类型配对：缓冲、非阻塞、加线程、拆锁、背压、批量、限流都不是万金油，它们各自只对某类等待账单有效

### 1. 为什么“加线程”经常让系统更慢而不是更快

加线程只在“当前主要是可并行 on-CPU 工作”时才大概率有帮助。一旦瓶颈是单锁、单设备、单连接、内存带宽或业务队列，加线程往往只是把竞争、切换和缓存失配再放大一轮。

所以“线程不够”不该成为默认解释，它只是执行太多型问题的一种可能补救。

### 2. 为什么缓冲和批量是把双刃剑

对小 I/O 和小 RPC，缓冲/批量能减少 syscall、设备请求和网络包数量，非常有价值。但它们天然是在用额外等待换更高吞吐。若你现在痛的是尾延迟或交互抖动，而不是吞吐太低，批量窗口再拉大可能反而雪上加霜。

所以一旦你决定“攒一攒再做”，就已经在引入时间等待，必须确认这笔等待账是否值得。

### 3. 为什么非阻塞和 epoll 并不会让后端资源 magically 变快

它们优化的是等待组织方式：少线程、更少无谓扫描、更容易并发管理。若后端磁盘、网络或锁本身才是主瓶颈，epoll 只能避免你在“等”的组织上浪费更多资源，却不能替你把后端做快。

所以 I/O 模型和等待原因必须对齐来看。别拿“用了 epoll”当作资源瓶颈已经解决的证据。证据位上，这层应把 epoll readiness、socket/块 I/O 等待、队列深度与 tracing 时间线放在一起：它们共同支撑“等待模型只改变等待组织，不自动消除资源本身的队列和服务时间”的判断。

### 4. 为什么锁优化永远要先找共享边界，再谈“换 CAS / 无锁”

许多锁问题的第一解法不是上复杂原子原语，而是先减少共享状态、缩短临界区、分片、分层、队列化。如果共享边界根本没动，你就算把 mutex 换成 lock-free，也可能只是把等待换成自旋重试和内存序复杂度。

### 5. 为什么业务队列问题通常最需要背压和丢弃策略，而不是无限扩容

队列一长，延迟自然被拉长。很多服务在业务队列问题上最危险的幻觉，就是“先把队列开大一点”。这会让系统更久之后才爆，但一旦爆就是更长尾的灾难。真正需要的常常是背压、超时、丢弃、降级、限流和工作保鲜策略，而不是无限缓冲。

### 6. 本节最该记住的结论：优化动作只有和等待类型对上号才有效；脱离等待分类谈调优，等于闭着眼换零件

一句最短人话是：**不是所有慢都该加线程，也不是所有慢都该加缓存。**

## 五、四个案例：等待分析真正站得住的时候，不是某个理论讲得通，而是你能拿多源证据证明“这类慢属于这一类等待”

### 1. CPU 调度等待型慢：看起来不忙，实际上总抢不到跑道

典型证据组合是：wall-clock 高、CPU time 低、run queue 和唤醒延迟升高、线程状态频繁 runnable 但迟迟没 running。此时与其抠函数热点，不如先看 CPU 配额、cgroup 限制、IRQ/softirq 热点、绑核、线程数和抢占关系。

### 2. 磁盘长尾型慢：平均吞吐还行，但少数请求在设备前排大队

证据通常是：iostat 看不出整体吞吐有多夸张，但 await/P99 变长、bio trace 拉出尾部、应用某些 fsync 或 page fault 路径被单点拉长。这里优化重点常在 I/O 形状、批量、回写、队列深度和存储栈，而不是 CPU。

### 3. 锁等待型慢：吞吐一开始涨，线程一多就不涨甚至倒退

证据通常是：线程数增加后 CPU 并没有等比例做更多有效工作，off-CPU/lock trace 聚焦在少数锁点，或者热点函数宽度不高但 wall-clock 依然长。这里优先看共享状态和临界区，而不是一味堆更多并发。

### 4. 内存压力型慢：不是 OOM，却开始大面积 stalled

证据常表现为 PSI 抬头、回收/compact/swap 路径出现、page fault 和远端 NUMA 比例上升、cgroup memory pressure 抖动，而进程自己 CPU 却不一定高。这类问题最容易被误判成“磁盘偶尔慢”或“应用偶发卡顿”，实际上根因在工作集和回收策略。

### 5. 本节最该记住的结论：等待分析不是抽象分类，而是要靠资源指标、状态时间线、路径 tracing 和 workload 背景一起把类型坐实

一句最短人话是：**分类不是为了漂亮，而是为了让证据能真正落到正确的修法上。**

## 六、把本篇收成一张图：等待分析真正把“慢”从一个总时间拆成了“执行账、排队账和七类等待账”，从而让优化动作第一次真正有了对象

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：慢查询耗时 1 秒，如何证明它是在算、在等磁盘，还是在等锁。答案首先不是“看 CPU”或“看磁盘”这么单线，而是先把总 wall-clock 时间拆成 on-CPU 和 off-CPU，再把 off-CPU 按 CPU 调度、内存、磁盘、网络、锁、时间和业务队列七类继续分账。只有这样，`TIME_WAIT`、run queue、PSI、queue depth、RTT、futex、sleep/backoff 和线程池 backlog 这些看似分散的现象，才会重新被纳入同一张等待账单里。

接着，你必须继续分清三种大类慢：执行太多、执行太慢、根本没获得服务机会。前两者偏向算法/实现层，最后一种则更偏向等待和排队组织。然后优化动作才有资格登场：缓存和批量对付小 I/O，epoll 改等待组织，加线程只在真正可并行的 CPU 工作上有效，锁问题先缩共享和临界区，业务队列问题更该用背压而不是无限扩容。

把这一切压成最短总图，就是：

```text
总时间：
  on-CPU 执行
  + off-CPU 等待

等待七类：
  CPU 调度 / 内存 / 磁盘 / 网络 / 锁 / 时间 / 业务队列

慢的三种根因：
  执行太多
  执行太慢
  没获得服务机会

优化原则：
  动作必须和等待类型配对
```

所以本篇最该记住的一句话是：**真正高价值的性能优化不是把 CPU 再榨干一点，而是先把总时间拆成不同等待账，再精准对着那张账单里最不该存在的一项动刀。**

## 七、几个最容易说错的地方

### CPU 不高是不是就说明性能问题不在 CPU？

不一定。线程可能主要在等 CPU 调度机会、等锁、等 I/O 或等业务队列，CPU 利用率本身不足以排除 CPU 相关等待。

### 增加线程是不是最通用的提速手段？

不是。若瓶颈在锁、单设备、单队列或带宽墙，加线程常常只会把争用和切换放大。

### queue 深是不是就应该先把队列再开大？

不一定。更深队列会隐藏问题并放大尾延迟，很多场景更需要背压、超时和丢弃策略。

### off-CPU 时间是不是都算 I/O 等待？

不是。锁、调度、内存压力、定时器、业务队列等待都会表现成 off-CPU，必须继续分类。

### 锁等待是不是总该用 lock-free/CAS 解决？

不一定。先减共享、缩临界区、分片通常更稳；CAS 只是把等待换成另一种复杂度。

### tracing 已经看到慢路径，分类是不是可有可无？

不是。慢路径告诉你“经过了哪”，分类才决定你“该改什么”。

## 收束：看懂等待分析之后，你才会真正明白“系统变慢”大多数时候不是“算得不够快”，而是“在错误的地方等了太久”

回到开头那个问题：一次慢请求是在执行太多、执行太慢，还是根本没获得服务机会？现在答案已经完整闭环了。你先把 wall-clock 拆成 on-CPU 和 off-CPU，再把 off-CPU 继续分成 CPU 调度、内存、磁盘、网络、锁、时间和业务队列几类等待。只有把“慢”分账，你才知道该改算法、抠微架构、拆锁、限流、换 I/O 模型，还是该先让系统别在某个队列前白白排这么久。

也正因为如此，你会发现很多性能优化失败不是因为努力不够，而是因为问题从一开始就被错归到了“执行层”。真正痛的也许根本不是 CPU 算不动，而是线程一直没拿到锁、一直在等回源、一直在被 cgroup pressure stall、一直卡在业务队列。把这些等待从总时间里拆出来，才是把“系统很慢”变成“可下手修的系统问题”的那一刻。

这就是为什么说：**等待分析是性能工程里把“模糊的慢”翻译成“具体资源债务”的总账本。** 你不先分账，后面的任何优化都像对着黑箱挥拳。

## 八、误解清单、证据清单与边界清单

### 误解清单

- 热函数宽不自动等于请求大部分时间都在执行；wall-clock 和 CPU time 的差值可能说明大头根本在等。
- off-CPU 不等于只在等 I/O；锁、调度、内存压力、定时器和业务队列都可能表现成 off-CPU 时间。
- 加线程不总是解法；若瓶颈是锁、单设备、单队列或带宽墙，加线程常常只会放大争用和切换。
- 队列深不自动意味着该继续加深队列；更深队列往往只是把尾延迟藏起来。
- tracing 看见了慢路径还不够；不把等待先分类，就不知道该改什么。 

### 证据清单

- 总时间分账：wall-clock vs CPU time、on/off-CPU 采样与等待栈，支撑“先证明大头是在执行还是在等待”的第一刀。
- 调度等待：run queue、唤醒延迟、`sched_switch`/调度 tracepoint 与 `perf sched` 路径，支撑“runnable 不等于已经运行”的判断。
- 内存/磁盘/网络等待：PSI、`/proc/meminfo`、iostat/`/proc/diskstats`、block tracepoint、`ss`/`nstat`/抓包，支撑不同资源等待的分账现实。
- 锁等待：futex、mutex、rwsem、自旋与 off-CPU trace 组合，支撑“锁等待不是 CPU 算不动，而是资源持有关系卡住”的判断。
- 业务队列与时间等待：线程池/连接池/消息队列 backlog、backoff/timer/限流窗口，支撑“很多慢不是资源不够，而是系统有意或被迫在等”的判断。

### 边界清单

- 本文讨论的是等待分析稳定心智模型；off-CPU 采样、锁事件、调度 tracepoint、PSI 与工具接口会随内核和观测方案变化。
- 等待分类是为了指导优化动作，不等于每个等待都能完全拆到单一原因；真实慢请求常常是多类等待叠加。
- on-CPU 低不自动排除 CPU 相关问题；调度等待同样属于“CPU 没给你服务机会”的一类瓶颈。
- 队列、批处理、限流和 backoff 有时是故意设计出来的，不应未经目标定义就一概消灭。
- 本文先讲“时间到底耗在等待谁”；下一篇源码调优才真正回答“当瓶颈已经定位到执行路径和代码层时，该怎么改”。
