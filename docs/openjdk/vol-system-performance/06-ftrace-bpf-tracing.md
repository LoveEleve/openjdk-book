# ftrace、kprobe 与 eBPF：聚合指标告诉你“哪类资源出了问题”，tracing 真正回答的则是“这次慢路径具体经过了哪些函数、参数和等待点”

> 主题：系统性能｜第 6 篇
> 前置文章：`docs/openjdk/vol-system-performance/05-memory-disk-network-observability.md`
> 本篇后续：`07-wait-analysis-optimization.md`
> 版本说明：本文讨论从聚合指标走向路径级 tracing 的稳定心智模型，重点是 ftrace、function_graph、kprobe/uprobes、tracepoint、hist trigger、trace-cmd、BCC 和 bpftrace。具体 attach 点、事件字段、权限、buffer 开销、verifier 约束、符号可用性和工具细节会随内核版本、配置和架构变化。本文不把某一版 `ftrace`、`trace-cmd`、BCC/bpftrace 或 eBPF verifier 规则写成跨版本契约，而把重点放在“什么时候该用函数路径 tracing、什么时候该读参数、什么时候该做结构化事件聚合，以及为什么 tracing 的首要责任不是‘收集更多日志’，而是把异常资源账本接回一条可验证的代码路径”。

## 现在真正该问的，不再是“哪类资源在出问题”，而是“这类资源出问题时，请求在内核或用户态到底经过了哪条慢路径，在哪一步开始排队、重试、锁住或走错分支”

上一章我们已经把子系统观测拆开了：内存要看 Available、PSI、回收和 NUMA；磁盘要看 IOPS、队列和延迟分布；网络要看 socket、协议、设备和抓包；调度要看 run queue、上下文切换和 IRQ 亲和。也就是说，聚合指标已经足够让你判断：**这次故障大概率死在内存、磁盘、网络还是调度某一类资源。**

可一旦你把问题收缩到“就是这条 I/O 慢、这个 socket 重传、这条调度路径延迟高”，下一步最痛的落差马上出现：指标只能告诉你“哪里不对”，却很少能直接告诉你“为什么会沿着这条具体路径不对”。

比如：

- `iostat` 告诉你磁盘 await 高，可某个请求到底是卡在 bio 提交、块层队列、文件系统锁还是 writeback；
- `ss -ti` 告诉你某连接重传多，可哪一段调用链在不断排队、退避、回调；
- PSI 告诉你内存压力在拖慢任务，可到底是哪条 reclaim / compaction / fault 路径在让线程 stalled；
- 调度统计告诉你唤醒延迟大，可到底是谁在持有 CPU、谁在做抢占、谁在唤醒链上慢。

这就把我们带到 tracing 的真正价值：**它不是为了再造一套“更细指标”，而是为了把聚合账本背后的慢路径重新拉成一条带函数名、参数、事件和时间顺序的证据链。**

所以本篇最重要的顿悟是：**tracing 真正要回答的，不是“系统整体怎么了”，而是“某次异常请求、某段内核路径、某个函数参数或某个事件序列，究竟是怎样一步步把前面看到的资源异常制造出来的”。**

先把总图记住：

```text
聚合指标：
  告诉你哪类资源有问题

ftrace：
  看函数路径和调用层次

kprobe / uprobe：
  动态观察入口、返回值和参数

tracepoint / hist / trace-cmd：
  看结构化事件、分布和时间线

BCC：
  现成 eBPF 工具, 快速套用成熟诊断模板

bpftrace：
  用短脚本快速临时构造观测和聚合
```

这一篇最重要的一句话是：**性能 tracing 的本质不是“多收日志”，而是把“某类资源异常”变成“哪条函数路径、哪个参数、哪次等待、哪条事件时间线”这一组可验证的具体现场。**

## 一、如果你只盯聚合计数器，就像只看财务总账；真正的 tracing 价值，在于把“账为什么坏了”追到交易流水和操作路径上

### 1. 聚合指标为什么永远不够当终局证据

聚合指标非常擅长筛方向。它们告诉你磁盘队列在涨、TCP 重传在增、run queue 很长、某个 cgroup memory pressure 很重。问题是，它们往往只告诉你结果，不告诉你路径。

你知道“钱少了”，却不知道到底是哪一笔交易出了问题；你知道“队列长了”，却不知道是谁在持续往里塞、谁在迟迟不消费、哪一段代码持锁过久。聚合指标的粒度天然太粗，不足以做最终归因。

所以一旦目标从“先定位哪类资源”转向“证明具体根因”，你就必须进入 tracing 世界。

### 2. tracing 的第一价值：把抽象资源异常重新落回具体代码路径

这是很多人最容易低估的一点。tracing 真正宝贵的地方，不是“能看到更多事件”，而是它把你从 `%util`、`retrans`、`runq` 这些抽象系统量，重新拉回到函数入口、返回值、tracepoint 字段和真实调用顺序。于是你不再只会说“磁盘慢”，而能进一步说“`balance_dirty_pages` 在这里让线程睡住了”“`tcp_retransmit_skb` 这条路径在这里开始密集出现”“`ext4_da_writepages` 后面的块提交在这一段抖了”。

这一步非常关键，因为只有回到路径，优化动作才会真正具体。

### 3. tracing 为什么又比普通日志更有优势

普通日志当然也能告诉你某些路径发生过，但它有两个天然问题：一是必须提前在源码里埋点，二是在高频路径上极容易把系统本身拖慢。tracing 的价值就在于：**很多观测点可以临时启用、临时过滤、临时聚合，在不改源码或少改源码的前提下快速进入现场。**

这让它特别适合“问题已经发生，但你来不及等下个发布周期加日志”的场景。

### 4. 本节最该记住的结论：从聚合指标到 tracing，本质上是从“知道哪类资源痛”跨到“知道是哪条具体路径让它痛”

一句最短人话是：**指标像总账，tracing 像流水。**

## 二、ftrace：当你最先想知道“这次慢路径到底经过了哪些函数”时，函数级 tracing 是最直接也最容易失控的一把刀

### 1. 为什么函数路径经常是 tracing 的第一直觉入口

很多性能问题一旦从资源层缩小到某个子系统，最自然的追问就是：“一次调用到底经过了哪几层函数，哪一段最长、哪一段重复、哪一段根本不该出现？”

这时 ftrace 非常有吸引力，因为它直接站在函数级世界里回答问题。你不用先设计复杂事件结构，就能先看调用路径长什么样、谁叫了谁、哪些函数形成了深栈和热路径。

### 2. function 和 function_graph 为什么回答的是两类不同问题

单纯 function tracing 更像事件流：哪些函数被调用了，调用频率如何；function_graph 则更像调用关系图，帮助你看到入口、返回和层次嵌套，某种程度上更接近“这次慢路径的执行骨架”。

所以前者像“流水”，后者像“树”。什么时候用哪种，要看你现在是更在意“哪些函数反复出现”，还是“这条调用链长什么样、哪层套哪层”。

### 3. 为什么 ftrace 不能一上来就全开全录

这几乎是 tracing 世界里最常见的自伤方式之一。函数级事件量太大，特别是在调度、网络、内存分配、文件系统这类高频路径上。你若不先过滤 CPU、PID、函数集合和采样窗口，很容易先把 trace buffer 打爆，再把被测系统自己拖慢，最后连你看到的现象都被污染。

所以函数 tracing 的第一纪律，是把范围先收窄。你不是在做全城 CCTV 永久录像，而是在针对一条可疑街道临时架摄像头。

### 4. 本节最该记住的结论：ftrace 最擅长先把“慢路径走了哪些函数”画出来，但它必须从一开始就带着过滤和短窗口纪律使用，否则最先毁掉的可能是测量本身

一句最短人话是：**ftrace 是把很锋利的刀，先圈定切口再下刀。**

## 三、kprobe / uprobe：函数路径知道了还不够时，下一步往往要问“当时传进来的参数和返回值到底是什么”

### 1. 为什么“看见某函数很热”仍然可能离根因差一层

假设你已经用 ftrace 看见 `vfs_read`、`submit_bio`、`tcp_sendmsg` 或某个业务函数总在热点路径上出现，这当然很有帮助。但它仍可能不足以回答：**这次到底是哪个 fd、哪个 inode、哪个大小、哪个返回码让问题发生了？**

因为函数名告诉你“谁被叫了”，却不一定告诉你“它这次拿着什么参数进来、以什么结果返回”。根因很多时候就藏在这些运行时值里。

### 2. kprobe 为什么特别适合做“先验证这个怀疑是不是对的”

kprobe 的吸引力在于不用改内核源码，就能在某个内核符号入口或返回点临时插一个观察点。你若怀疑“这个函数里的 size 参数一到某个值就会抖”“某个返回码在压力时暴涨”，kprobe/kretprobe 往往是非常直接的验证方式。

它更像一根细针：不是帮你看全景，而是帮你刺穿一个已经很具体的怀疑。

### 3. uprobe 为什么提醒你“性能路径不总在内核，很多时候用户态库和业务函数也值得一起看”

如果问题一半在用户态、一半在内核，仅盯内核探针就容易断链。uprobe 则允许你把用户态程序、共享库和解释器路径也纳入临时观测里。这在观察 malloc、加密库、用户态协议解析器、JVM/native 边界等场景时很有价值。

它提醒你：**tracing 的边界不是“内核里发生了什么”，而是“整条问题链路里哪些函数值得被看见”。**

### 4. 为什么动态探针特别需要尊重 ABI、优化和上下文边界

因为探针不是写死源码点。参数寄存器、返回值位置、内联优化、符号消失、架构 ABI 差异都会直接影响你读到的东西是不是你以为的那个值。高频路径再加大量输出，还会迅速把被测对象拖慢。

所以动态探针非常强，但它比函数 tracing 更要求“我到底读的是哪个变量、在哪个点读、这点会不会因为编译优化而变样”。

### 5. 本节最该记住的结论：kprobe/uprobes 最擅长给路径再补上一层“这次到底带着什么参数和返回值”，但越精准，越要尊重 ABI 和上下文边界

一句最短人话是：**ftrace 告诉你谁上场了，kprobe/uprobes 告诉你它上场时手里拿了什么。**

## 四、tracepoint、hist 与 trace-cmd：当你已经知道“要看哪些事件”时，结构化事件和分布聚合通常比海量 printk 更适合长期和高频路径

### 1. 为什么“逐条打印”在性能问题里常常是最笨的证据形式

逐条打印最大的优势是直观，但也最容易把系统自己打爆：格式化文本开销、锁、I/O、日志风暴都会反向污染被测路径。对于高频事件，你往往并不需要“每一条原始样本”，而是更关心：

- 哪个 PID/设备最常发生；
- 延迟分布长什么样；
- 哪个阶段最常卡住；
- 某类事件在时间上怎样突刺。

这就是结构化 tracepoint + histogram 的优势所在。

### 2. tracepoint 为什么是 tracing 里最值得优先考虑的 attach 点之一

因为它们是内核事先设计好的稳定事件接口，字段语义相对明确，版本内兼容性和工具支持通常比任意函数探针更好。你不是在猜某个内部局部变量，而是在接收一个专门定义给观测者看的事件对象。

所以当你知道“我应该看 block_rq_issue/complete、sched_switch、sys_enter_read 这类事件”时，tracepoint 往往比随手在函数入口扎探针更稳妥。

### 3. histogram 为什么值钱

它把“海量事件流”立刻压成了可读分布。尤其在 latency 问题里，直方图经常比均值和单次日志更值钱，因为它直接揭示：是整体都偏慢，还是只有尾部长得很可怕。很多“偶发慢”问题如果没有分布视角，永远会被平均值吃掉。

### 4. trace-cmd / KernelShark 为什么又补了“时间线”这层

事件统计告诉你频率和分布，trace-cmd 这类工具则更像把事件重新按时间铺开。这样你能看见 CPU 调度、块 I/O、唤醒、系统调用和某个关键 tracepoint 之间的时序关系。这一层非常适合解释“先发生了什么，后面哪个现象才被触发”。

### 5. 本节最该记住的结论：tracepoint/hist/trace-cmd 的组合价值在于：既能低侵入地拿到结构化事件，又能把它们压成分布或摊成时间线，而不是沉在无穷 printk 里

一句最短人话是：**printk 让你看见每棵树，tracepoint + hist 先让你看见整片森林的形状。**

## 五、BCC：真正让 eBPF 在生产排障里变得“今天就能用”的，往往不是你自己写程序，而是先借成熟工具把高频问题快速验证掉

### 1. 为什么很多 tracing 问题不值得从零开始写程序

你当然可以自己写 kprobe、tracepoint 和 map 逻辑，但大量常见问题早就有人踩过一遍：谁在 exec、新打开了哪些文件、哪条 TCP 在重传、哪个设备 I/O 延迟抬起来了、哪个 run queue 在长尾等待。若每次都从空白脚本开始，排障节奏会非常慢。

这正是 BCC 工具箱的现实价值：它把很多高频观测套路预先封装成可执行工具。

### 2. BCC 为什么既方便又仍要审慎对待

因为它们的输出并不是“内核真理”，而是某组默认探针、字段解释、过滤范围和单位选择下的观测结果。一个工具很可能完美回答“有没有发生这类事件”，却不足以独自回答“为什么发生”。

所以 BCC 更适合快速验证高频怀疑，而不是让你停止思考底层 attach 点和工作负载语境。

### 3. 本节最该记住的结论：BCC 的价值在于把一批共性 tracing 问题做成即插即用工具，但你仍必须理解它盯着的是哪一层事件、它没盯到什么

一句最短人话是：**BCC 是成熟扳手，不是自动修理工。**

## 六、bpftrace：当现成工具不够用时，它让你可以用几行脚本临时拼出一套“我现在就想看这个参数、这个直方图、这条栈”的观测实验

### 1. 为什么 bpftrace 是 tracing 世界里特别适合“临时实验”的工具

很多排障问题只在这一刻、这一台机上、这一条路径里出现。你不想为它写一整套 C/BPF 项目，也不想改业务代码再上线。这时 bpftrace 的高层语法就很有吸引力：可以非常快地把“这个 tracepoint 按 comm 计数”“这个 kprobe 的返回值做直方图”“这条栈各出现多少次”写成短脚本。

这让 tracing 的试错成本大幅下降。

### 2. 为什么灵活性越高，越需要你自己负责任地控制成本

因为几行脚本就能 attach 到高频路径，也就意味着几行脚本就足以把一台热点机器拖慢。如果你没有 PID/CPU/comm 过滤，没有控制输出频率和采样窗口，又在最热的函数上做大量 map 更新和栈抓取，那么“观测本身制造问题”会非常容易发生。

所以 bpftrace 不是“可以更随便”，而是“更方便地做危险动作”，因此更需要纪律。

### 3. 为什么 bpftrace 结果尤其要和前面的子系统指标再对一遍

因为脚本常常是在回答一个非常具体的小问题：比如哪个进程最常调某个函数、哪类返回值最多、哪个延迟桶最高。它非常适合把一个怀疑戳穿，却不天然给你全局上下文。你仍要回到前面的 USE/RED 和子系统观测图上，问：这条局部现象和总账是不是同一时段、同一路径、同一 workload 的产物。

### 4. 本节最该记住的结论：bpftrace 最大的价值是“把临时观测脚本化”，最大风险也是“因为太容易写，反而忘了控制观测成本和上下文”

一句最短人话是：**bpftrace 像 tracing 世界的 AWK，拿来做快刀小实验特别好，但越方便越不能乱挥。**

## 七、把本篇收成一张图：tracing 真正有用的顺序，不是“哪个工具最酷”，而是“先从聚合账本锁定资源，再选合适粒度把路径、参数、事件和时间线一层层追出来”

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：当聚合指标告诉你“内存、磁盘、网络或调度某一类资源在出问题”之后，怎样把慢路径一路追到函数和参数。答案首先不是“打开所有 tracing”，而是按粒度选工具：ftrace 先看函数路径和调用层次，kprobe/uprobes 补参数和返回值，tracepoint/hist/trace-cmd 看结构化事件、分布与时间线，BCC 快速复用成熟模板，bpftrace 则在现成工具不够时临时构造小实验。

你会发现这些工具不是互斥关系，而像一组由粗到细、由稳到灵活的刀具：

- 指标告诉你哪类资源异常；
- tracing 把异常资源账重新接回代码路径；
- 参数与事件再把路径压成更可证明的现场；
- 时间线和直方图则说明“它究竟何时发生、以什么形状发生”。

把这一切压成最短总图，就是：

```text
聚合指标：
  先定位哪类资源有问题

ftrace：
  看路径和调用关系

kprobe/uprobes：
  看参数和返回值

tracepoint/hist/trace-cmd：
  看结构化事件、分布和时间顺序

BCC/bpftrace：
  复用成熟模板或快速写临时观测脚本
```

所以本篇最该记住的一句话是：**tracing 真正高价值时，并不是因为它能让你“看到更多”，而是因为它能把“资源异常”转译成“具体哪条路径、哪个参数、哪段时间线”这组足以支撑定责和修复的证据。**

## 八、几个最容易说错的地方

### tracing 是不是比聚合指标更高级，所以一开始就该先上 tracing？

不一定。聚合指标擅长先缩小范围，tracing 成本更高、更细，通常更适合在“哪类资源有问题”已经明确之后使用。

### ftrace 是不是可以直接长期全量开在生产环境？

通常不建议。函数事件量很大，必须先做过滤、限时和开销评估，否则 tracing 本身可能污染系统。

### kprobe/uprobes 是不是随便挂哪里都能稳定读到想要的参数？

不是。参数位置、符号、内联和 ABI 约束都可能改变你读到的东西，必须尊重平台和编译现实。

### tracepoint 一定比 kprobe 更强吗？

不一定。tracepoint 通常更稳定、语义更清晰；但若你要看的恰好不是已有 tracepoint 暴露的信息，kprobe 仍然更灵活。

### 有了 BCC 现成工具，是不是就不必理解底层事件和 attach 点了？

不是。否则你会很容易把工具输出当成终局结论，而忘了它默认假设了什么、没看见什么。

### bpftrace 只是几行脚本，所以开销可以忽略吗？

不能这么想。高频事件、栈采样、聚合 map 和输出本身都可能制造显著成本，尤其在线上热点路径上。

## 收束：看懂 ftrace、kprobe 与 eBPF 之后，你才会真正明白“性能 tracing”不是日志放大器，而是一套把资源异常重新钉回执行路径的证据工程

回到开头那个问题：一次慢 I/O、重传或调度延迟，究竟经过了哪些函数、参数和调用路径？现在答案已经完整闭环了。指标先告诉你哪类资源在异动，tracing 再把这类异动重新接回真实路径：ftrace 给你函数骨架，kprobe/uprobes 给你参数与返回值，tracepoint/hist/trace-cmd 给你结构化事件和时间线，BCC 与 bpftrace 则把共性问题工具化、把临时问题脚本化。于是“磁盘慢”“网络抖”“内存卡”终于不再停留在类目，而会变成一条可以被重现、验证和归责的慢路径。

也正因为如此，你会发现 tracing 真正难的从来不是“会不会写脚本”，而是“知道什么时候该看函数、什么时候该看参数、什么时候该看事件分布，以及怎样避免观测本身改变被观测对象”。把这条边界守住之后，下一步等待分析与优化就不再是盲人摸象，而会真正站在一条完整证据链上。

这就是为什么说：**tracing 不是把系统照得更亮，而是把嫌疑人从影子里拽出来。** 亮不够，得能定责。
