# 子系统观测：真正让你把“系统变慢了”继续拆开的，不是再盯一个总利用率，而是分别看内存、磁盘、网络和调度各自在哪本账上开始排队、重试或回收

> 主题：系统性能｜第 5 篇
> 前置文章：`docs/openjdk/vol-system-performance/01-methodology-foundation.md`
> 本篇后续：`06-ftrace-bpf-tracing.md`
> 版本说明：本文讨论子系统观测的稳定心智模型，重点是内存、磁盘、网络和调度四类资源的聚合指标、压力指标、错误指标与时间线证据。具体 `vmstat`、`iostat`、`sar`、`ss`、`ethtool -S`、`numastat`、PSI、`slabtop` 与各类 `/proc` 计数器细节会随内核版本、发行版、存储/网卡驱动和监控系统变化。本文不把某一版工具输出字段、默认阈值或单个告警规则写成跨版本契约，而把重点放在“为什么子系统观测必须同时看资源状态、排队压力、错误和分布，并把聚合指标一路接回真正的压力路径”。

## 现在真正该问的，不再是“CPU 流水线为什么慢”，而是“真实线上请求里，哪一类资源先开始拖后腿——内存、磁盘、网络还是调度”

上一章我们已经把 CPU 这条线钻到了很深：从 IPC/CPI、缓存/TLB、分支预测、perf 和火焰图，一路打到 TMA、Roofline 和 LLVM-MCA。也就是说，**当问题已经明确落在 CPU 和微架构上时，你有了一整套继续细化的工具和模型。**

可系统性能问题并不总先死在 CPU。很多现实中的“慢”其实来自别的资源先开始变形：

- 内存没有马上 OOM，却因回收、cgroup 压力或 NUMA 远端访问让请求停滞；
- 磁盘吞吐不高，却因为队列和尾延迟把用户 P99 顶上去；
- 网络带宽没打满，但连接队列、重传、网卡错误或 softirq 分布已经把请求链拖慢；
- 线程本身 CPU 占用不高，却长时间拿不到运行机会，被 run queue、IRQ 和上下文切换吞掉了时间。

所以本篇真正要回答的核心困惑是：**USE 已经告诉你该继续查资源侧，那怎样把“资源可能有问题”这句话进一步拆回各个子系统自己的账本、队列、错误和分布现实，而不是停留在“CPU 不高、磁盘也不满、可怎么还慢”这种迷雾里。**

本篇最重要的顿悟是：**子系统观测不是再找一个利用率，而是把每类资源都重新拆成四层看——当前状态、排队/压力、错误/重试、以及这些量随时间和分位的形状。**

先把总图记住：

```text
内存：
  不只看 free
  还看 Available、回收、swap、PSI、slab、NUMA 和进程地址画像

磁盘：
  不只看吞吐或 %util
  还看队列、await、P99 分布和 workload 形状

网络：
  不只看带宽
  还看 socket 状态、重传、驱动计数、队列和抓包时间线

调度：
  不只看 CPU 利用率
  还看 run queue、context switch、IRQ/softirq 分布和绑核局部性
```

这一篇最重要的一句话是：**一类资源“忙不忙”从来不等于“是不是瓶颈”；真正让用户感到慢的，往往是该资源前面已经开始排队、回收、重试或调度等待，而这些信号分散在不同账本里。**

## 一、如果你只看系统总量和利用率，不看队列、压力和错误，子系统问题几乎总会被伪装成“资源好像没满，但用户还是慢”

### 1. 最常见的错误观测方式：CPU 看利用率，磁盘看 `%util`，内存看 `free`，网络看带宽

这套观察法之所以流行，是因为它直观、简单、仪表盘好画。但它最大的问题也正是在于太直观：

- CPU 100% 也许很健康，CPU 30% 也可能因为 run queue 和锁而很痛；
- 磁盘 `%util` 60% 不代表请求不在排队；
- `free` 很少不代表内存不够，`free` 很多也不代表 cgroup 和 PSI 没在报警；
- 网络带宽没打满不代表没有重传、接收队列积压或网卡异常。

也就是说，总量/利用率常常只是“看起来像资源还行”的表面和平，而问题真正躲在后面的排队、回收、错误与抖动里。

### 2. 为什么子系统观测一定要同时拉上“排队”和“错误”两类证据

这其实是在把上一章的方法论和这里的工具重新接起来。聚合利用率只会告诉你资源总工作量，排队告诉你请求有没有开始积压，错误告诉你系统是不是在靠重试和降级苟活。真正的性能问题，往往恰好是利用率并不极端，但排队或重试已经开始抬头。

所以子系统观测要从一开始就假设：**很多“慢”不是来自资源满载，而是来自资源前后链路已经不健康。**

### 3. 本节最该记住的结论：子系统分析的第一步不是继续找单一指标，而是承认“资源状态、排队压力、错误重试和分布形状必须一起看”

一句最短人话是：**别再问它满没满，先问它有没有堵、有没有出错、堵在哪里。**

## 二、内存观测：真正该看的不是“还剩多少 free”，而是“工作集、回收、swap、PSI、slab 和 NUMA 是否已经在偷偷让请求停住”

### 1. 为什么 `free` 很少不等于快 OOM，`free` 很多也不等于没内存问题

前面内存卷已经讲过，Linux 会主动把空闲页拿去做 page cache 和可回收缓存，所以 `MemFree` 本身就很容易误导。真正更接近“还可不可以继续舒服活着”的，是 `MemAvailable`、回收行为、swap 变化以及压力停滞时间。

但就算 `MemAvailable` 还不错，系统仍可能在 cgroup 限制、匿名工作集膨胀、NUMA 远端访问、slab 异常、THP 分配或内存压力停顿上先露出症状。所以内存观测一旦深入，也绝不该只停在 `/proc/meminfo` 的总量口径上。

### 2. 为什么 PSI 是内存观测里特别容易被忽略、却非常有价值的一层

很多传统内存指标都在看“有多少页、谁占了多少页、swap 多少、回收多少”。这些都很重要，但它们不直接告诉你：**有多少任务因为内存压力而实际停住了多久。**

PSI（Pressure Stall Information）恰恰补的是这层语义。它把“资源压力已经开始让任务 stalled”这件事量化出来，尤其适合解释那类“看上去没到 OOM，业务已经有体感抖动”的场景。

这也说明性能问题并不是只有资源耗尽这一种边界，资源尚未枯竭也可能已经让应用停住。

### 3. 为什么进程地址画像和内核对象账本都必须同时看

内存问题常常不是“总量不够”，而是某个大户吃错地方。一个进程可能匿名 RSS 高得异常，一个 cgroup 可能 page cache 膨胀，一个驱动或协议栈的 slab cache 可能持续增长，页表自身也可能在海量映射下异常膨胀。

所以你既要看 `smaps_rollup` / PSS / RSS 这种进程画像，也要看 `slabtop`、`PageTables`、`KernelStack`、`SReclaimable`/`SUnreclaim` 这类内核对象账本。否则你只会知道“内存很贵”，却不知道账单写给了谁。

### 4. NUMA 为什么能让“明明还有内存”变成“为什么这台机子就是抖”

在 NUMA 机器上，内存并不是统一池子。本地节点分配和远端节点分配带来的访问延迟、带宽和 page migration 成本都可能让同样的“总内存充足”呈现完全不同的体感。某个服务如果不停踩远端内存、抢错节点或线程在节点间漂移，用户看到的可能就是慢，而监控上总内存仍显得很充裕。

所以 `numastat` 一类视角对多路机器尤其关键。它把“内存在哪个节点”重新带回了观察图。

### 5. 本节最该记住的结论：内存观测的关键不是单看剩余量，而是把“可用量、回收行为、压力停顿、对象归属和 NUMA 位置”一起拼成一张工作集地图

一句最短人话是：**内存慢，常常不是因为“快没了”，而是因为“它已经开始以回收、停顿和远端访问的形式让请求掉速了”。**

## 三、磁盘观测：`%util` 不是磁盘世界的真相，真正能把用户拖慢的往往是队列、分布和工作负载形状

### 1. 为什么磁盘 `%util` 经常会被过度神化

很多人看到 `%util` 就像看到 CPU 利用率一样安心：高了就是磁盘忙，低了就说明磁盘没问题。现实比这复杂得多。设备类型、队列深度、多队列支持、RAID/虚拟设备层、请求大小和并发模式都会改变 `%util` 的解释边界。

所以 `%util` 更适合当线索，不适合当法官。它最多告诉你“这个设备并不闲”，很难单独回答“它是不是瓶颈、用户为什么慢成这样”。

### 2. 为什么 IOPS、吞吐、队列和延迟必须一起看

磁盘世界非常容易出现“一个指标好看，另一个已经烂掉”的情况。高吞吐不代表小请求时延好，IOPS 高也不等于队列没堆，队列短不代表尾部请求没被拉长。只有把请求率、吞吐、平均队列深度和 await 这些量放一起，你才知道当前 workload 更像大顺序流、碎随机流，还是“数量不多但每个都在排大队”。

这也是为什么 iostat 等工具的多列必须联合解释，而不能只拿一列做告警全部逻辑。

### 3. 为什么分布比平均 await 更值钱

平均 await 很容易把少量特别慢的尾部请求抹平。可对很多数据库、日志服务和对象存储来说，恰恰是那一小撮极慢 I/O 把上层 P99 拖垮了。于是 bpftrace/biolatency 或更低层 block tracepoint 的延迟分布视角非常关键：它第一次让你看到“是整体都慢，还是只是尾巴在炸”。

### 4. 为什么 disk benchmark 的 workload 形状必须写进报告里

4KB 随机读、1MB 顺序写、QD=1 和 QD=64 测出来的是完全不同的世界。你若只说“磁盘 80k IOPS”，却不说块大小、并发队列深度、direct/sync 与否、读写比例，这个数字几乎没法解释，也不能拿来和上层业务需求对上。

所以磁盘观测从一开始就必须同时问“当前系统 workload 长什么样”。

### 5. 本节最该记住的结论：磁盘瓶颈的核心不在“忙不忙”，而在“请求以什么形状到来，队列怎么堆，尾部延迟怎么长出来”

一句最短人话是：**磁盘分析不是看转速表，而是看排队和慢车道在哪。**

## 四、网络观测：带宽不是网络世界唯一的真相，socket 队列、重传、驱动计数和时间线才决定“请求为什么卡在网上”

### 1. 为什么“链路带宽没满”不能证明网络不是瓶颈

一条链路可以吞吐远没打满，但 socket 层已经因为 rwnd=0、接收方消费慢、重传、乱序或队列积压开始卡住。另一种常见情况是：问题根本不在链路带宽，而在网卡驱动、RX/TX ring、softirq、qdisc、NAT/conntrack 或某个 L4/L7 代理的状态机里。

所以网络世界的“慢”从来不等于“带宽不够”。

### 2. 为什么 `ss`、`nstat`、`ethtool -S` 和抓包四层证据缺一不可

- `ss -ti` 让你看到单连接级状态：rtt、cwnd、rwnd、retrans、队列长度；
- `nstat`/`/proc/net/snmp` 告诉你协议栈总账：重传、失败、ListenOverflows 等；
- `ethtool -S` 让你看设备级计数：rx_missed、CRC、offload、queue drops；
- `tcpdump`/Wireshark 给你真正的时间线：Seq/Ack、dup ACK、SACK、RST、重传顺序。

只看任何一层都容易误判。网络问题本质上是一条跨 socket、协议、设备和线上时序的联合账。

### 3. 为什么“重传 > 0”也不自动等于“网线坏了”

重传可能来自拥塞、接收端慢、队列抖动、ACK 延迟、NAT/防火墙行为、虚拟网络设备甚至抓包观测位置差异。它当然可能是物理链路问题，但绝不能被机械等同。

所以每次看到 `retrans` 抬头，真正该做的是继续问：**这是谁的重传、发生在什么时段、同一时间线上的 RTT、窗口和设备错误又是什么样。**

### 4. 本节最该记住的结论：网络观测的关键不在“速率多少”，而在“连接、协议、设备和时间线四层证据能否互相解释同一件事”

一句最短人话是：**网慢不一定是带宽小，往往是某一层队列、重传或设备状态先失控。**

## 五、调度与中断：有些“服务慢”其实不是算不动，而是线程总在等 CPU、等 run queue、等 IRQ/softirq 让路

### 1. 为什么进程 CPU 利用率不高，延迟仍然可能很差

这是很多排障里最反直觉的地方。进程本身 CPU 利用率不高，并不代表它能随时拿到 CPU。它可能在 run queue 后面排队、被软中断和 IRQ 挤压、和别的线程抢核、跨 NUMA 节点漂移，或者被唤醒延迟拖住。

也就是说，用户感受到“慢”，并不总是因为线程在 CPU 上跑太久，也可能是因为它根本没能及时获得跑的机会。

### 2. 为什么上下文切换数量和 run queue 不能脱离 workload 语境孤立解读

上下文切换多不自动是坏事：I/O 密集、高并发事件循环本来就会有很多自愿切换；反过来，切换很少也不等于没问题，因为线程可能在长时间抢不到 CPU。run queue 长也要看持续时长、核数、负载分布和调度策略。

所以调度指标最大的陷阱就是把“高/低”直接翻译成好/坏，而不回到工作负载模式和尾延迟体感。

### 3. 为什么 IRQ affinity / irqbalance / 绑核会直接改变网络和存储性能

前面网络卷已经讲过，RX/TX、softirq、NAPI、qdisc、Reactor 线程都在争 CPU。若你让网卡 IRQ、ksoftirqd 和应用线程全挤在同一两个核上，即使机器总算力还富余，也会在局部核上形成热点争抢。IRQ 亲和、RSS、多队列和应用绑核因此会直接改变“包从哪颗核进入、应用在哪颗核消费”的局部性和队列分布。

这说明调度观测和网络/存储问题并不是两本分开的账，它们经常共用同一组 CPU 资源。

### 4. 本节最该记住的结论：调度分析真正关心的是“线程能否在需要时拿到运行机会”，而不只是“它总共占了多少 CPU”

一句最短人话是：**不是每个慢线程都在忙，有些慢线程只是一直没轮到。**

## 六、把本篇收成一张图：子系统观测真正有价值时，不是列更多命令，而是把每类资源的“总量、队列、错误、分布和时间线”重新接回同一条请求责任链

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：`vmstat`、`iostat`、`ss` 这些工具只告诉你“某个子系统怪怪的”，怎样进一步判断到底是谁在排队、谁在丢包、谁在回收。答案首先说明，不能再拿单一利用率当圣杯。内存必须同时看 Available、回收、PSI、slab、进程地址和 NUMA；磁盘必须一起看 IOPS、带宽、队列、await 和延迟分布；网络必须把 socket 状态、协议栈总账、设备计数和抓包时间线拼起来；调度则要回答“线程有没有及时拿到 CPU”和“IRQ/softirq 是否在局部核上把延迟拖高”。

所以子系统观测的核心不是“会不会用 vmstat/iostat/ss”，而是把这些输出重新翻译成每类资源的四层现实：状态、排队、错误、分布/时间线。只有这样，你才能在 CPU 微架构分析之外，继续把性能问题从“机器很忙”缩成“哪个资源链条在先拖慢请求”。

把这一切压成最短总图，就是：

```text
内存：
  看可用量、回收、PSI、对象归属和 NUMA

磁盘：
  看请求率、吞吐、队列和延迟分布

网络：
  看 socket、协议、设备和抓包时间线

调度：
  看 run queue、切换、IRQ/softirq 和局部性
```

所以本篇最该记住的一句话是：**子系统观测不是找一个“最高”的图表，而是把“这类资源有没有开始排队、重试、回收或抢占”一层层拆出来，并把这些证据重新对齐到同一条请求路径上。**

## 七、几个最容易说错的地方

### `free` 很少是不是就说明内存要出事了？

不一定。要结合 Available、PSI、回收行为、swap、cgroup 和工作集来判断，很多健康系统的 `free` 本来就很低。

### 磁盘 `%util` 不高是不是就说明存储没问题？

不一定。队列、延迟分布和 workload 形状一样可能在先拖慢用户请求。

### 网络带宽没满是不是就说明网络不是瓶颈？

不是。socket 队列、重传、驱动丢包、softirq 热点和 NAT/代理状态都可能让网络成为瓶颈，而不先表现为带宽打满。

### 上下文切换很多是不是一定有问题？

不一定。要结合 workload 模式、run queue、等待语义和尾延迟一起解释，高并发 I/O 场景本来就可能切换多。

### 子系统观测是不是可以替代 tracing？

不能完全替代。聚合指标擅长先定位哪类资源在出问题，真正回答“经过了哪条函数路径”通常还得靠 tracing 或更细粒度采样。

### 这些工具是不是有固定通用阈值，一超就说明出事？

不建议机械这么用。设备类型、内核版本、工作负载和部署环境都会改变基线，阈值更多是经验线索，不是自动判决。 

## 收束：看懂子系统观测之后，你才会真正明白“性能问题在哪一类资源”不是一句利用率，而是一条从总量、队列、错误到时间线的证据链

回到开头那个问题：`vmstat/iostat/ss` 告诉你某个子系统异常时，怎样判断谁在排队、谁在丢包、谁在回收？现在答案已经完整闭环了。因为每类资源都要重新按自己的语义去拆：内存看 Available 和 PSI，不只看 free；磁盘看请求、队列和分布，不只看 `%util`；网络看 socket、协议、设备和抓包时间线，不只看带宽；调度看 run queue、切换和 IRQ 局部性，不只看 `%CPU`。只有当这些证据重新接回同一条请求路径，你才有资格说“问题真的先死在这里”。

也正因为如此，你会发现很多所谓“系统很慢”并不是真的缺哪一种资源，而是某种资源开始以排队、回收、重试、唤醒延迟的形式，把后面的整条链拖慢了。聚合指标让你先知道“哪本账在异动”，而下一步 tracing 要做的，正是把“账变坏的那一刻”一路追到内核真实路径。

这就是为什么说：**子系统观测真正有价值的地方，不是报表更丰富，而是它把“资源高低”翻译成“请求在这个资源前面发生了什么”。**

## 下一篇桥接

到这里，聚合指标和子系统账本已经足够告诉你“问题大概死在哪类资源”。下一步最自然的问题就是：**怎样把一次内存分配、一次 block I/O、一个网络包或一次调度等待真正沿函数路径追出来，而不是停在计数器层打转**？

下一篇 `06-ftrace-bpf-tracing.md` 会把这条 tracing 主线补上：ftrace、tracepoint、kprobe、eBPF/bpftrace 分别适合在哪一层插桩，什么时候该用低开销常驻观察，什么时候该做一次针对性深挖，以及怎样把 tracing 结果重新接回前面 USE/RED 和子系统观测的坐标系。那一篇要回答的，不再是“哪类资源有问题”，而是“问题具体经过了哪条路径”。
