# TMA 与 Roofline：当你已经知道 CPU 很忙、IPC 很低、热点在哪时，真正下一步要问的不是“还能不能再快一点”，而是“这些周期究竟卡在流水线哪一类槽位，以及算法从原理上先撞上的是算力墙还是带宽墙”

> 主题：系统性能｜第 4 篇
> 前置文章：`docs/openjdk/vol-system-performance/03-cpu-perf-flamegraph.md`
> 本篇后续：`05-memory-disk-network-observability.md`
> 版本说明：本文讨论 TMA、PMU 精确采样、Roofline 与静态/动态交叉验证的稳定心智模型。具体 Top-down 事件组合、PEBS/IBS/SPE 能力、Roofline 构图方法、uncore 事件与 LLVM-MCA 输出会随 CPU 架构、微架构代际、内核与 perf 版本变化。本文不把某一版 Intel/AMD/ARM 事件编码、perf `-M Topdown*` 支持、STREAM 数值或 LLVM-MCA 报告格式写成跨版本契约，而把重点放在“为什么 IPC 低只是症状、TMA 负责把流水线时间分桶、Roofline 负责把算法放回算力/带宽上界坐标里，以及两者都必须依赖目标 CPU 和 workload 的实测来解释”。

## 现在真正该问的，不再是“热点函数在哪”，而是“这些 cycles 为什么从硬件结构上注定花在这里，以及这份代码是被流水线卡住，还是算法本来就已经撞上了机器的理论天花板”

上一章我们已经把 CPU 分析推进到了很实用的一层：你知道 `%CPU` 不是答案，IPC/CPI 才是第一刀；cache/TLB、branch miss 和 on/off-CPU 火焰图能进一步告诉你“这些 cycles 到底忙在执行、等待数据、猜错路还是被系统路径拖住”。也就是说，你现在已经能从“CPU 高”走到“哪个函数、哪个调用栈、哪类 stall 在主导”。

可如果想再往前走一步，新的问题会非常微架构：

- IPC 低，究竟主要是前端取指供不上、后端在等内存、还是分支投机一直被打脸？
- 某个热点函数 cache miss 很高，它到底是因为算法本身算术强度太低、天然受带宽墙限制，还是只是实现写得差，离屋顶还很远？
- 你看到很多 cycles 花在同一段代码里，那是因为代码真的在做很多有用算术，还是因为流水线端口、依赖链、load/store 单元一直饥饿或堵塞？
- 静态工具说“这个 loop 吞吐应该很好”，动态 perf 却告诉你 Backend Bound 很重，为什么？

这就把我们带到本篇真正的主题：**CPU 性能分析如果想再往下钻，一边得有 TMA 这种“把每个周期归到哪类流水线槽位”的视角，另一边还得有 Roofline 这种“算法从原理上到底更受算力上限还是带宽上限约束”的视角。**

所以本篇最重要的顿悟是：**TMA 负责解释“周期为什么没有退休成有用指令”，Roofline 负责解释“就算实现已经不错，算法从算术强度上先撞的到底是哪堵墙”；前者是微架构归因图，后者是算法-硬件上界图。**

先把总图记住：

```text
你已经知道：
  CPU 利用率高
  IPC/CPI 异常
  热点函数在哪

TMA 继续问：
  周期掉进了哪类槽位
  Retiring / Frontend Bound / Backend Bound / Bad Speculation

PMU/精确采样继续问:
  哪条指令、哪类地址、哪段事件最像根因证据

Roofline 再问：
  算法每搬 1 字节数据做多少计算
  先撞的是带宽墙还是算力墙

LLVM-MCA / 编译器报告：
  静态上这段汇编本来应该跑成什么样
  与动态采样不一致时说明哪里还有隐藏变量
```

这一篇最重要的一句话是：**CPU 分析走到深入阶段时，问题不再只是“谁宽”，而是“周期掉进了哪类硬件槽位、算法又落在机器上界图的哪一侧”。**

## 一、如果你只知道 IPC 低，却不知道低在哪一种槽位，后续优化方向几乎必然会乱撞

### 1. IPC 低为什么只是“体征”，还不是“病名”

上一章我们说过，CPU 忙且 IPC 低，常常意味着大量周期没有有效退休成有用指令。但这只是共同外观，不是共同病因。前端供指不够、分支投机失败、后端等内存、执行端口冲突、load/store 拥堵，都可能把 IPC 拉低。

也就是说，“IPC 低”这句话像发烧：你知道病人不正常了，却还不知道是肺炎、贫血还是中暑。

### 2. 最朴素的错误做法：看到 IPC 低就立刻冲去改热点函数代码

这在很多团队里特别常见。函数热点已经有了，IPC 也低，于是大家自然想：那就赶紧手改代码、消分支、调数据结构、上 SIMD。

问题是，如果你没先知道 stall 究竟主要落在前端、后端、投机还是退休比例上，这些改动几乎是在盲投。比如：

- 真正卡在前端 I-cache/解码，你去调数据布局只会收效很有限；
- 真正卡在后端带宽墙，你一味抠指令级细节并不能把墙推开；
- 真正卡在 bad speculation，你不处理分支可预测性，只做 cache 优化也会事倍功半。

所以你首先需要一套比 IPC 更细、但又比“每条硬件事件各看一点”更可组织的坐标。TMA 就是在回答这个问题。

### 3. TMA 为什么比“单看几个 cache miss 指标”更有结构感

单个 cache miss、branch miss 或端口利用率当然都有价值，但它们常常像一堆零碎化验单：你看见了一些异常，却不容易形成一张一眼能告诉你“主矛盾在哪”的图。

TMA 的高明之处在于，它先不急着把问题拆得过细，而是先按流水线大类把周期分桶：有多少是真正退休的有用工作，有多少浪费在错误投机，有多少卡在前端供给，有多少卡在后端资源与数据供应。这样你能先知道“最大的钱包漏洞在哪个大抽屉里”，再继续往下一层钻。

### 4. 本节最该记住的结论：IPC 低告诉你“这里有病”，TMA 才开始回答“病主要发在前端、后端、投机还是退休效率哪一类区域”

一句最短人话是：**IPC 是警报器，TMA 才是分诊台。**

## 二、TMA：它真正有价值的不是那四个英文标签，而是把“CPU 没退休出有用指令的时间”先粗分成四类互斥的大桶，逼你别在第一步就迷失在细枝末节里

### 1. Retiring 为什么不能简单理解成“越大越好，一高就没问题”

Retiring 代表的通常是流水线最终成功退休出的有用指令比例。这当然是大家希望尽可能高的部分，因为它意味着周期在变成真正推进程序的工作。

但它也不能被粗暴解读成“高就万事大吉”。某些算法本身算术强度很低，即使 Retiring 比例不差，也仍可能整体性能受带宽墙限制；相反，Retiring 很低时当然值得警惕，但你还需要知道挤掉它的到底是哪一类 stall。

所以 Retiring 更像“有效产出桶”，不是一个独立的完结结论。

### 2. Frontend Bound 在提醒你什么

当前端供给不足时，CPU 并不是“算不过来”，而是连足够正确的指令流都拿不到或喂不进去。I-cache miss、ITLB、解码能力限制、过长的取指链、过于复杂的代码布局，都会在这里露头。

这类问题的典型特征是：你也许看不到特别夸张的数据 cache 症状，却会发现 CPU 周期经常空等“下一条能执行的指令”来到面前。对这种场景，单纯去优化数据结构可能并不对症，更该看代码体积、分支布局、内联过度或指令流局部性。

### 3. Backend Bound 为什么常常是最重、也最容易被误会成“CPU 不够强”

Backend Bound 说明前端已经把指令送进来了，但执行后端仍在等：等数据从 cache/memory 来，等 load/store 单元、执行端口、依赖链或者其他资源空出来。很多 memory wall 问题就藏在这里。

它之所以容易被误解，是因为人们常把它翻译成“CPU 算不过来”。可很多时候根本不是 ALU 不够，而是数据供给、带宽、依赖和端口资源让执行单元只能闲着等。

所以 Backend Bound 经常要求你再继续细分：是 core bound 还是 memory bound，是 L1/L2/L3/DRAM 还是 store/load/端口冲突。

### 4. Bad Speculation 为什么是“被错误世界占用的周期”

当分支预测错误、机器走上错误路径又回滚时，一批前面投入的取指、解码和执行资源就变成了白干。Bad Speculation 就是在给这种“错误世界里的劳动”记账。它很重要，因为它提醒你：有时 CPU 不是没事做，而是在忙着做注定要被推翻的工作。

这类问题和 cache/memory 完全不同，根因更多在控制流、数据分布、条件判断和投机准确性。

### 5. 为什么 TMA 的四类不是“最终答案”，而是第一级切面

这点特别重要。TMA 的四个一级类目很有价值，但它们本来就不是终点。真正的意义在于：**先用四大桶决定从哪里继续下钻。**

- Frontend Bound 高，再去看 I-cache、ITLB、decode；
- Backend Bound 高，再去拆 memory/core 方向；
- Bad Speculation 高，再看 branch history、预测失误和控制流；
- Retiring 比例不错，再问算法本身和 Roofline 上界是不是才是主限制。

### 6. 本节最该记住的结论：TMA 的价值在于把 cycles 先分账到四大类，再决定下一步该在前端、后端、投机还是算法层继续深挖

一句最短人话是：**四大桶不是终点，它们只是把“为什么低 IPC”先切成对的几类入口。**

## 三、PMU 与 PEBS / IBS / SPE：计数器给你总账，精确采样才开始告诉你“这类 stall 最常和哪条指令、哪片地址、哪条调用链绑在一起”

### 1. 为什么光有总量计数往往不够把根因钉死

如果你知道 LLC miss 很高、branch miss 也不低，这当然已经很有方向感。但它仍然缺关键的一环：**这些事件最常发生在哪些指令、哪些地址、哪段调用栈上？**

没有位置上下文，你得到的只是“工厂里今天坏件很多”，却不知道坏件主要从哪条生产线出来。优化时就容易停在概念级猜测。

### 2. 精确采样为什么值钱

PEBS、IBS、SPE 这类机制之所以重要，不在于它们 magically 完美，而在于它们能把某些硬件事件采样更可靠地贴近到具体执行点或地址语义上。于是你不只知道“问题很多”，还更有机会知道“问题常在这里爆”。

这让你可以把 TMA 的大类判断进一步压回代码和数据现实，而不只是停留在“后端大概有问题”。

### 3. 为什么说“更精确”不等于“没有误差”

硬件采样仍然受支持范围、skid、multiplexing、频率、权限、buffer 和虚拟化等影响。你得到的是更可信的位置线索，而不是对每一次事件的完整录像。采样始终是抽样，不是全量真相。

所以使用精确采样时，心态应该是“证据更强”，而不是“证据绝对”。

### 4. 本节最该记住的结论：PMU 计数先给出全局方向，精确采样再把方向钉到更可信的执行点和数据点上，但它仍然是采样证据而不是全量录像

一句最短人话是：**普通 PMU 告诉你哪里在着火，PEBS/IBS/SPE 更像告诉你火头常从哪根电线冒出来。**

## 四、Roofline：有些程序根本不是“实现还不够好”，而是算法每搬 1 字节数据只做了太少计算，天然更容易先撞上带宽墙而不是算力墙

### 1. 为什么 CPU 分析不能只盯微架构，不看算法强度

前面几节都在帮助你理解流水线和硬件资源为什么没被充分利用。但如果算法本身每处理一点数据只做很少计算，那么即使实现已经相当不错，程序也可能天然更受内存带宽限制而不是算力限制。你此时继续死抠指令级优化，收益会非常快触顶。

所以 CPU 分析必须再往上抬一层：**这段 workload 的算术强度本来就站在哪一边？**

### 2. Roofline 真正提供的是什么

Roofline 把一个算法放进“算术强度 vs 可达性能”坐标图中。它告诉你：在给定硬件上，这段工作负载理论上会更容易先撞到带宽屋顶，还是先撞到计算吞吐屋顶。你于是能一眼看出，接下来更值得去减少内存流量、提高局部性，还是去做向量化、指令级并行和更强计算利用率。

所以 Roofline 真正的价值，不是画图本身，而是**把“往哪优化”这件事从代码直觉，提升成算法-硬件共同上界判断。**

### 3. 为什么 Roofline 不是“看 FLOP/s 就完事”的 HPC 专属玩具

虽然它在数值计算世界最常见，但其核心思想对很多通用程序一样有启发：只要你的工作负载存在“每单位数据搬运到底做多少有用工作”的差异，它就能帮助你判断“瓶颈更像算力不足还是数据搬运不足”。

你当然不能把所有业务都强行换算成漂亮的 FLOP 图，但“算术强度”和“屋顶”这种思维方式本身非常有用。

### 4. 为什么 Roofline 不能独自给你优化答案

因为它给的是上界与方向，不是代码定位。它告诉你“这里大概是带宽墙”，却不会替你指出“哪一行因为不连续访问拖垮了带宽利用”；也不会告诉你“哪一层 cache 才是真正掉的那层”。这些还要靠前面的 perf/TMA/火焰图/采样再落回实现。

所以 Roofline 是一张导航图，不是修车手册。

### 5. 本节最该记住的结论：Roofline 的价值在于提醒你，有时问题不是实现还不够好，而是算法本身每字节做工太少，天然更早撞上带宽上界

一句最短人话是：**有些程序慢，不是马力不够，而是每箱货刚搬上来就只加工一下又搬走了。**

## 五、LLVM-MCA 与编译器报告：静态预测告诉你“理想情况下这段汇编应该跑成什么样”，它不是现实，但它能在动态事实和源码直觉之间补上一层关键桥梁

### 1. 为什么动态采样和硬件计数还不够

你可以知道某段代码 Backend Bound 很重，也能知道某个函数很宽、某些 load miss 很多。但如果你还想回答“编译器本来有没有机会把这里向量化/展开/调度得更好”“这段汇编在理想资源下理论吞吐本该是多少”，动态证据本身并不能完全回答。

这就需要静态模型和编译器自己的诊断报告来补洞。

### 2. LLVM-MCA 的真正价值

它不在运行程序，而是在给定目标 CPU 和汇编序列的前提下，估计资源冲突、端口压力、吞吐和延迟。于是你得到一份“理想实验室条件下，这段代码应该跑成什么样”的参考。它不能替代 perf，但能在你怀疑“到底是代码结构天然这样，还是运行时环境把它拖坏了”时提供非常有力的对照。

### 3. 编译器报告为什么也很关键

因为很多优化根本不是硬件层直接决定，而是“编译器有没有这样做”。向量化失败、内联没发生、别名分析保守、循环展开策略不符预期，这些都可能把最终机器码推向完全不同的轨道。只看运行结果，不看编译器决策，你可能会在错误的层次上发力。

### 4. 为什么静态和动态证据必须互相约束

如果 LLVM-MCA 说这段汇编理应有不错吞吐，而 perf 却显示 Backend Bound 和 cache miss 很重，那么问题更可能在数据供给和运行时环境；反过来，如果静态上端口冲突和依赖链就已经很差，再高明的 cache 优化也救不了太多。

这说明最好的分析永远不是“只信静态”或“只信动态”，而是两边互相打脸直到剩下真正的解释。

### 5. 本节最该记住的结论：静态模型不是现实，却能告诉你“现实和理想究竟差在哪”，让你分清该怪源码、编译器还是运行时环境

一句最短人话是：**LLVM-MCA 像图纸产能估算，perf 像工厂现场录像；两者不一致时，恰恰最值得深挖。**

## 六、把本篇收成一张图：TMA 负责按流水线大类分账，PMU 负责给事件上证据，Roofline 负责给算法画上界，静态工具则负责告诉你“本来该跑成什么样”

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：IPC 很低，热点函数也看到了，接下来到底该往哪一层再钻。答案首先不是继续盯函数本身，而是先用 TMA 把 cycles 分成 Retiring、Frontend Bound、Backend Bound 和 Bad Speculation 四大桶，知道钱主要花在哪类流水线槽位上。再往下，PMU 和精确采样把这些大类证据逐步钉到更可信的指令、地址和调用链上。

与此同时，Roofline 又把视角抬高了一层：哪怕实现已经不差，你的算法仍可能先撞上带宽墙而不是算力墙。这样一来，“到底该继续抠指令级细节，还是优先减少数据搬运”就不再只是经验判断，而有了硬件-算法上界坐标。最后，LLVM-MCA 和编译器报告再把“理想静态表现”和“现实动态表现”接起来，帮助你区分是代码结构、编译器决策，还是运行时数据供给在主导差距。

把这一切压成最短总图，就是：

```text
CPU 现象：
  IPC/CPI 异常、热点清楚

TMA：
  先问周期掉进哪类大桶

PMU/精确采样：
  再问哪条指令/哪段地址最像证据现场

Roofline：
  再问算法先撞的是算力屋顶还是带宽屋顶

LLVM-MCA/编译器报告：
  再问静态上本来该跑成什么样
```

所以本篇最该记住的一句话是：**高质量 CPU 分析从来不止于“火焰图里哪块最宽”，而是同时把周期分桶、事件取证、算法上界和静态预期四张图对齐后，才真正知道该动哪把刀。**

## 七、几个最容易说错的地方

### IPC 低是不是就等于内存瓶颈？

不一定。前端供给不足、分支预测失误、后端执行资源冲突都可能导致 IPC 低，必须先分桶再下钻。

### TMA 能不能跨 Intel、AMD、ARM 直接照搬一套事件和阈值？

不能。事件、公式、层级和工具支持都强依赖目标微架构，必须先核实平台支持与语义。

### 看到 Backend Bound 高，是不是就说明一定要去做 SIMD 或换更快 CPU？

不一定。它也可能是 memory bound、load/store 依赖、端口冲突或数据布局问题，方向完全不同。

### Roofline 是不是只适合 HPC 算法，对通用程序没价值？

不完全。它最擅长数值计算，但“算术强度 vs 带宽/算力上界”的思维对很多数据密集程序一样有启发。

### LLVM-MCA 输出好，是不是就说明运行时一定快？

不是。它描述的是理想化静态执行可能性，真实程序还受缓存、分支、并发和输入分布影响。

### 火焰图、TMA 和 Roofline 是不是三个互斥替代工具？

不是。它们回答的问题层次不同，最有价值的场景恰恰是把三者与 PMU/编译器证据拼起来看。

## 收束：看懂 TMA 与 Roofline 之后，你才会真正明白“CPU 不够快”不是一句抱怨，而是可以被拆成流水线分账、事件取证和算法上界三层证据的问题

回到开头那个问题：IPC 很低，究竟是前端取指慢、后端等内存，还是分支猜错？现在答案已经完整闭环了。你先用 TMA 把“CPU 周期花到哪里”分成四个大桶，再用 PMU 与精确采样把问题压到更具体的指令和地址现场，同时用 Roofline 判断算法究竟更受算力还是带宽上限约束，最后再拿 LLVM-MCA 和编译器报告去对照“理想静态世界”和“真实动态世界”到底差在什么地方。这样一来，“CPU 慢”就不再只是主观感受，而会被拆成能对应优化方向的硬证据。

也正因为如此，你会发现很多优化争论若只停留在“把这个函数写得更快”是远远不够的。真正高质量的决定需要先回答：你是在和 cache/TLB 墙作战，还是和 branch miss 作战，还是和算法本身的带宽墙作战；你需要的是改代码、改布局、改编译器选项、改数据结构，还是承认这段程序已经很接近硬件屋顶。理解了这些边界，后面的子系统观测和源码级调优才不会继续在错误层次上打转。

这就是为什么说：**微架构分析的价值，不是把 CPU 讲得更复杂，而是把“为什么慢”从一句模糊判断拆成有层次、有边界、有上界的结构化证据。**
