## 现在真正该问的，不再是“这套能力怎样拿来找 CPU/内存问题”，而是“如果问题就在网络数据面或安全边界上，eBPF 能不能不只记录，而是更靠前、更快、更主动地参与处理”

前几篇已经把 eBPF 这条线铺得很完整了：

- 第一篇讲程序怎样进内核；
- 第二篇讲状态、事件和栈证据怎样出来；
- 第三篇讲 libbpf/CO-RE/skeleton 怎样把它做成工程；
- 第四篇讲 bpftrace 怎样把一次观测实验压成脚本；
- 第五篇讲怎样选 tracepoint/kprobe/USDT/PMU 等数据源；
- 第六篇又把 CPU/内存场景里的现成工具链串起来了。

也就是说，到现在为止，**你已经能很好地用 eBPF 看见系统发生了什么。**

新的问题是：当系统问题已经不是“看不见”，而是“包来得太快、连接太多、某些行为根本不该被允许、策略最好在最前面就执行”时，eBPF 能不能从“观测器”再往前走一步，变成数据面或安全决策的一部分？

这就带出了本篇真正的核心困惑：

- 怎样从连接生命周期视角观察谁连了谁、活了多久、在哪个阶段重传最厉害？
- XDP、TC、sockmap/sockhash 这些名字都在“碰网络包”，它们到底离驱动入口多近、能看见多少上下文、能做多大的动作？
- 文件、命令、信号、capability 一类安全审计为何也能被放到同一套 eBPF 思想里？
- LSM BPF 为什么代表“从看见到拦截”的最后一步，同时也伴随最大的误伤风险？

所以本篇最重要的顿悟是：**eBPF 在网络与安全里不是单一工具，而是三种距离：在 socket/trace 层看事件，在 TC/XDP 层碰数据面，在 LSM 层做安全裁决；越靠近入口越高吞吐，也越失去宽上下文和宽容错误的余地。**

先把总图记住：

```text
观测层：
  tcpconnect / tcplife / tcpretrans / opensnoop / execsnoop / capability / signal
  → 先知道谁在发生什么

数据面层：
  XDP / TC / sockmap
  → 更早地放行、丢弃、重定向、加速

安全决策层：
  BPF LSM
  → 从记录走向允许/拒绝

总原则：
  越靠前越快
  但可见上下文更少、策略错误影响更大、回滚要求更严
```

这一篇最重要的一句话是：**eBPF 真正强大的地方，不只是“能看见事件”，而是它允许你按距离选择：先在上层审计，再在中层分流，最后在最前面直接拦截；但每往前一步，都必须拿更多上下文损失和更高失误代价来换。**

## 一、如果你只会用 eBPF 记录“已经发生了什么”，那在网络和安全场景里，你仍然经常会慢半拍：包早进来了，连接早建了，恶意行为也早做完了

### 1. 最朴素的观测思维：有问题再记日志，事后再分析

这当然是很自然的第一步。遇到连接失败、重传飙高、奇怪文件访问、异常 exec 或 capability 请求时，先把事件记下来，后面再排时间线、做聚合、看趋势。前几篇的 tracing 工具链就是围绕这类事后观察问题展开的。

问题在于，某些场景你并不只想“知道发生了”，而是想“别让它先发生那么多”。比如 DDoS 或异常包风暴，若等包完整穿过协议栈、占用 socket/conntrack/queue 资源后再统计，你已经被打了一拳；恶意进程若先打开了不该开的文件、发出了不该发的信号、申请了不该申请的能力，再由事后审计告诉你，损害也可能已经发生。

所以网络与安全场景天然会把 eBPF 往“更靠前”推：不只看，还想更早处置。

### 2. 第二个失败思维：既然越早越好，那所有逻辑都塞进最前面的 XDP 或 LSM

这同样危险。你越往前，越能省资源、越少上下文切换，但你也会迅速失去更丰富的协议语义和业务上下文。最前面的 XDP 看不到完整 socket 世界，LSM 策略一旦写错又可能直接把合法流量或系统关键动作拦掉。

所以“越早越强”并不成立。真正要回答的是：**这件事更像适合观测、适合数据面处理，还是适合安全决策；以及它值得放在多靠前的位置上做。**

### 3. 本篇的总原则：先分清你是在看流量、改流量，还是裁决行为

这就是本篇三大部分存在的原因：

- 连接观测工具链，解决“谁在连、谁在活、谁在重传”；
- XDP/TC/sockmap，解决“包和连接路径上能否更早更快地处理”；
- 安全观测和 BPF LSM，解决“哪些行为要记录，哪些行为要阻断”。

三类问题虽然都能用 eBPF，但目标、上下文和风险级别完全不同。先把这一层分清，后面的工具和 hook 选择才不会乱套。

### 4. 本节最该记住的结论：eBPF 在网络与安全里真正首先要做的，不是“上来就丢包或拒绝”，而是先把问题归类成观测、数据面处理或策略裁决这三种不同距离

一句最短人话是：**先决定你是想看、想分流，还是想拦，再决定把程序挂在哪。**

## 二、连接观测：tcpconnect、tcplife、tcpretrans 之类工具之所以总被一起提，不是因为它们都看 TCP，而是因为它们分别站在“出生、存活、异常”三个不同时刻

### 1. 为什么单看重传或单看连接建立都不够

如果你只看 tcpretrans，你会知道“某些连接在重传”，但不知道它们最初是谁建立的、持续了多久、是不是只在某一类短命连接上异常。如果你只看 tcpconnect，你会知道“谁发起了连接”，却不知道这些连接是否最后一直活着、是否在大量超时前就断掉。单看某一个切面，总会丢掉前后文。

所以成熟的 TCP 观测常常会自然形成一组“生命线工具”：建立、存活、异常各看一段，再把它们拼起来。若要把这一节补成更硬的证据位，最关键的落点应回到这些现成工具各自依附的事件源、字段语义和时间线位置：它们共同支撑“tcpconnect 看出生、tcplife 看履历、tcpretrans 看事故”这组生命周期分工，而不是简单的三个命令名。

### 2. tcpconnect 真正回答的是什么

它最擅长回答“谁在连谁”。一旦你看到连接风暴、意外的上游地址、瞬时高频建连或异常 client 行为，tcpconnect 常常是最先把“连接出生地”抓出来的工具。它更像出生登记簿，不是病历全文。

### 3. tcplife 为什么值钱

连接活了多久、期间收发了多少字节、最终在什么上下文里结束，这些信息能把“只知道建立过”推进成“知道生命周期大概长什么样”。它很适合回答：

- 连接是不是普遍极短命？
- 某类连接是不是很快建立又很快被 reset？
- 是不是某个上游一连上就发很少字节又断掉？

也就是说，它像账单，而不只是门禁记录。

### 4. tcpretrans 为什么不能自动等价于“网线有问题”

前面网络卷已经讲过，重传可能来自拥塞、乱序、ACK 延迟、零窗口、虚拟网络设备乃至代理/回源路径行为。tcpretrans 告诉你“重传发生了，而且发生在这些连接/方向上”，但并不会替你直接下结论“是物理丢包”。

所以它必须回到 `ss -ti`、抓包、网卡统计和 tcplife 的时间线上一起解释。

### 5. 本节最该记住的结论：连接观测真正成熟时，不是背工具名，而是知道 tcpconnect 看“谁生了它”，tcplife 看“它活成什么样”，tcpretrans 看“它在哪个阶段开始出故障”

一句最短人话是：**一个看出生，一个看履历，一个看事故。**

## 三、XDP、TC 与 sockmap：它们都能“碰网络数据”，但本质上分别站在驱动入口、协议栈中部和 socket 数据路径，看到的上下文和能做的动作完全不同

### 1. 为什么 XDP 特别快，也特别克制

XDP 的位置非常靠前：在包刚进驱动/NAPI 的早期就开始做判断。这意味着它能在内核还没付出完整协议栈成本前，尽早决定 `DROP`、`PASS`、`TX` 或 `REDIRECT`。对 DDoS 过滤、简单 ACL、极高吞吐分流来说，这非常有吸引力。

但它也因此天然更受约束：

- 看到的协议上下文更少；
- 很多高级 socket/进程语义还不存在；
- 写错策略的伤害面特别大；
- 驱动模式和硬件支持也更关键。

所以 XDP 的强大来自“早”，它的脆弱也来自“太早”。

### 2. TC 为什么常像“更晚但更懂事”的位置

TC 站得比 XDP 靠后。它已经在更完整的网络栈上下文里，能看到更多协议和路由相关信息，也因此更适合做细粒度分类、整形、标记和重定向。你可以把它理解成：比 XDP 晚，但也比 XDP 看得更多、策略可表达性更强。

这说明 XDP 和 TC 根本不是“谁更先进”的关系，而是“**谁更早、谁更懂、谁更适合当前动作**”的取舍。证据位上，这层最值得回到 XDP/TC attach 位置、返回语义与可见上下文差异上：它们共同支撑“XDP 是门口保安，TC 是更晚但更懂包和策略的分拣台”这句判断。

### 3. sockmap / sockhash 为什么是另一条轴线

它们的关注点已经不再是“包刚进来的时候”，而是 socket 数据路径本身：把某些连接之间的数据转发或数据处理路径做得更高效。它们不是简单的“绕过 TCP/IP 栈”，而是利用内核在 socket 层已经知道的连接上下文做更近连接语义的优化或重定向。

所以它更适合那些“连接已经明确，如何让数据在 socket 世界里走得更少绕”这类问题，而不是 XDP/TC 擅长的早期数据面过滤。

### 4. 为什么“越早越快”永远要和“越早上下文越少”一起看

这是本节最重要的 tradeoff。XDP 很快，但信息少；TC 稍晚，但信息更多；sockmap 更贴近连接语义，但范围不再是“任何入站包”。没有哪一个位置天然通吃，只有你是否真的在解决“此刻这个阶段最适合做的事”。

### 5. 本节最该记住的结论：XDP、TC 和 sockmap 是三种完全不同距离的数据面刀具，区别不在都能改包，而在“它们离数据入口多近、上下文多丰富、回滚和误伤代价多大”

一句最短人话是：**XDP 像门口保安，TC 像大厅分拣台，sockmap 像已经进了房间后的内部传送带。**

## 四、安全观测：opensnoop、execsnoop、capable、signal 这些工具真正回答的，不是“系统安全不安全”，而是“哪些动作已经发生、谁在发起、覆盖盲区在哪”

### 1. 为什么安全观测首先是事件链，而不是结论机

看到某进程 `open` 了敏感文件、`exec` 了可疑命令、请求了某个 capability、向关键进程发了某种 signal，这些都很重要。但每一条工具输出都只是事件证据，不是最后结论。安全问题天然需要时间线和上下文：谁先做了什么、后面跟着什么、这是不是正常业务的一部分、有没有白名单、是否跨 namespace/cgroup。

所以安全观测工具更像一组“警报器 + 事件记录仪”，不是审判官。

### 2. 为什么 execsnoop 和 opensnoop 经常一起用

因为很多异常文件访问本来就和某次进程执行有关：谁启动了某程序，它随后打开了什么路径，这两条线分开看都不完整。把 exec 和 open 放在同一条时间线上，才能看见“谁启动了哪种行为主体，又由它去碰了哪些文件资源”。

### 3. capable 和 signal 为什么特别值钱

文件和进程创建之外，能力请求和信号本身就非常接近“操作系统权力边界”的动作。谁在请求绕过 DAC 的能力、谁在向谁发 `SIGKILL` 或其他重要信号，这些都能非常快地暴露异常控制流或权限滥用。可它们同样需要上下文，不应孤立判案。

### 4. 为什么这些工具也有天然盲区

例如 bashreadline 看不到所有命令执行路径，opensnoop 看见文件被打开却不一定知道业务意图，signal 事件也可能大量来自正常运维和 supervisor 行为。工具不是没价值，而是你必须清楚它们覆盖的是哪一段现实，又漏掉了哪一段现实。

### 5. 本节最该记住的结论：安全观测工具最值钱的地方，是让可疑行为链条有了时间线与主体，而不是替你自动宣判恶意与否

一句最短人话是：**先把谁做了什么记清，再谈好坏。**

## 五、LSM eBPF：当你终于不只想“看到异常”，而想“在关键行为发生前直接拒绝它”时，系统已经从 observability 走到了 policy enforcement，这时最大的风险不再是看不见，而是拦错

### 1. 为什么 LSM eBPF 和前面的观察型工具不在同一个风险等级上

前面那些工具大多是在做事后或并行观测。哪怕脚本写得不完美，常见后果更多是“看错了、漏看了、开销大了”。LSM BPF 则不同：它能直接参与某些安全决策点，返回允许或拒绝。也就是说，它从“观察者”正式变成了“门卫”。

门卫的错误和摄像头的错误并不在一个量级。摄像头误报很烦，门卫误拦会直接影响系统可用性。

### 2. 为什么“先观测，再审计，再阻断”几乎是唯一负责任的推进顺序

如果你没有先用观测确认某类行为确实该拦、确实能被稳定识别，就直接上阻断，很容易在生产环境里把合法流量、合法进程或关键系统动作挡在门外。尤其是 capability、文件访问和网络策略这类边界，一旦规则写偏，影响面非常大。

所以 LSM eBPF 真正成熟的用法，几乎总是：

1. 先观测；
2. 再审计和度量误报；
3. 最后才考虑 enforcement。

证据位上，这层最关键的不是某条具体 LSM hook 名，而是“从审计到阻断”的升级纪律本身：它共同支撑了为什么 BPF LSM 应被当作高风险控制面，而不是看见能 return `DENY` 就直接全线上生产的脚本玩具。

### 3. 为什么它不能简单替代 SELinux / AppArmor

因为它们的策略模型、持久化、审计体系、规则表达和生态完全不同。BPF LSM 非常灵活，适合快速策略、环境特化或结合运行时数据做判断；但传统 LSM 的成熟策略体系和治理经验并不会因此消失。把两者关系讲成“新时代全面替代旧时代”通常都是误导。

### 4. 本节最该记住的结论：LSM eBPF 的真正价值，在于把 eBPF 从“看见”推进到“决定”，而真正的使用纪律是把它当作高风险控制面而不是脚本玩具

一句最短人话是：**看见错，只会误导；拦错，会停业务。**

## 六、综合决策：观测、数据面和安全决策三阶段真正组成了一条成熟的 eBPF 能力升级路径——先知道发生了什么，再决定值不值得更早处理，最后才决定要不要直接阻断

### 1. 为什么很多团队在 eBPF 上卡住，不是因为不会写程序，而是因为没有能力升级顺序

一上来就想用 XDP 抗 DDoS，或者立刻用 LSM 阻断一类行为，看起来很厉害，但如果前面没有足够的观测和统计基础，你经常根本不知道：

- 这类事件真实频率怎样；
- 哪些是误报；
- 哪些字段最稳定；
- 提前下沉一层处理是否值得那份上下文损失和回滚成本。

也就是说，真正的成熟不是“会最强的技术”，而是知道能力应该按什么顺序升级。

### 2. 从 tracing 到 XDP/TC，再到 LSM，本质上是在不断把“反应时机”提前

- tracing：事情发生后或发生时告诉你；
- 数据面：事情刚进入系统时就处理；
- LSM：事情在关键敏感操作真正生效前就裁决。

越往前，越省资源、越主动；但也越容易因为上下文不足或规则错误而误伤。

### 3. 本节最该记住的结论：eBPF 在网络和安全里的成熟使用方式，是一条从观测 → 优化/分流 → 阻断的渐进路径，而不是一上来就把最激进的 hook 打满

一句最短人话是：**先学会看，再学会导流，最后才学会拦。**

## 七、把本篇收成一张图：eBPF 在网络与安全里的真正边界，不是“能不能做”，而是“该在哪一层做、能承受多大误伤、值不值得把动作提前到那个位置”

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：网络连接异常、DDoS、恶意进程和权限滥用能否用同一套 eBPF 思路观察甚至阻断。答案首先不在“用哪条命令”，而在于 eBPF 在网络/安全里天然分成三种距离：连接和行为观测工具站在事件层，看见“谁连接、谁执行、谁请求权限”；XDP/TC/sockmap 站在数据面不同位置，看见“包和连接路径”并决定能否更早丢弃、重定向或加速；LSM BPF 则站在策略裁决点上，正式把“是否允许”变成内核里的强行为。

这三层的本质差别不是语法，而是反应时机、上下文丰富度和误伤风险。越早处理，系统越省资源，越可能在坏事发生前就止损；但你看到的世界也越窄，错判代价也越高。成熟的 eBPF 使用方式因此不是“先上最强”，而是先观测、再数据面优化、最后才在证据充分时上策略阻断。

把这一切压成最短总图，就是：

```text
观测层：
  tcpconnect/tcplife/tcpretrans/opensnoop/execsnoop/capable/signal

数据面层：
  XDP / TC / sockmap

决策层：
  BPF LSM

升级路径：
  先看见
  再分流/优化
  最后阻断
```

所以本篇最该记住的一句话是：**eBPF 在网络与安全里的真正力量，不在于“终于能拦包”，而在于你能按代价和上下文逐层选择：什么时候只看、什么时候改路、什么时候真的不让它过。**

## 八、几个最容易说错的地方

### tcpconnect/tcpretrans 看到重传或连接失败，是不是就能直接认定物理链路有问题？

不能。它们只是连接生命周期事件，还要和 `ss`、抓包、驱动计数、NAT/代理路径等一起解释。

### XDP 是不是一定比 TC 更好？

不一定。XDP 更早、更快，但上下文更少、约束更大；TC 更晚但更懂包和策略。谁更合适取决于你要做的事。

### sockmap 是不是能让所有 TCP 流绕过协议栈？

不是。它能优化某些 socket 数据路径，但能力边界、协议类型和内核实现限制都很具体，不能被宣传成“万能旁路”。

### 安全观测工具是不是天然就是审计系统？

不完全。它们更多是在记录事件证据，真正可长期依赖的审计与取证还需要保留策略、存储、权限和流程设计。

### BPF LSM 能不能直接替代 SELinux/AppArmor？

不能简单这么说。它们的模型、治理、持久化和生态不同，BPF LSM 更像补充性、可编程的策略层。

### 越早拦截是不是越好？

不一定。越早上下文越少、误伤风险越高，只有在证据充分、需求明确时才值得把动作下沉到更早 hook。

## 收束：看懂 eBPF 网络、安全与 XDP 之后，你才会真正明白“可编程内核”最有价值的不是能力越来越强，而是你终于能按距离、风险和上下文精细决定“看、改还是拦”

回到开头那个问题：网络连接异常、DDoS、恶意进程和权限滥用能否用同一套 eBPF 思路观察？现在答案已经完整闭环了。可以，但答案绝不是“都挂一个 probe 就行”。你必须先分清自己站在哪一层：连接和进程事件观测层、TC/XDP 这类数据面处理层，还是 LSM 这种强策略裁决层。前者更安全，后者更主动；前者上下文更丰富，后者反而更克制。把这些层次分清，eBPF 才不是“到处都能上”的神锤，而是一组可以按风险和收益逐步升级的系统刀具。

也正因为如此，你会发现前面几篇里讲的 verifier、Map、RingBuf、tracepoint 选型和 bpftrace 并不是独立知识点，而是你今天能不能在 XDP 或 LSM 层安全落地动作的全部前提。不会观测的人不该先阻断，不会选 hook 的人也不该先去改路径。把这条升级顺序建立起来，eBPF 才会从“会写探针”成长为“会做线上可控的数据平面和安全策略”。

这就是为什么说：**eBPF 真正成熟的能力，不是“能做得更早”，而是“知道什么时候值得更早、什么时候应该停在更稳的边界上”。**

## 九、误解清单、证据清单与边界清单

### 误解清单

- eBPF 在网络与安全里不等于“越早越强”；越靠前上下文越少、误伤风险越高。
- tcpconnect/tcpretrans/execsnoop 这些工具不自动给最终结论；它们更像连接/行为生命周期的不同切面。
- XDP 不等于天然优于 TC；它更早更快，但也更克制、更少上下文。
- sockmap/sockhash 不是万能旁路；它们只在特定连接/数据路径场景下有意义。
- BPF LSM 不是看见能拦就该立刻全上；它首先是高风险控制面，而不是脚本玩具。

### 证据清单

- 生命周期观测：tcpconnect/tcplife/tcpretrans/opensnoop/execsnoop/capable/signal 各自依附的事件源和时间线位置，支撑“出生/履历/事故/行为”分段观测。
- 数据面层次：XDP/TC/sockmap 的 attach 位置、返回语义与上下文差异，支撑“谁更早、谁更懂、谁更适合当前动作”的取舍。
- 安全裁决层：BPF LSM 的 hook 能力与返回语义，支撑“从看见到决定”这条升级路径。
- 升级纪律：先观测、再审计、最后阻断的工程顺序，支撑“策略上线前必须先量误报和回滚成本”的判断。
- 跨卷桥接：前几篇 verifier、Map、RingBuf、探针选型和脚本纪律共同构成“能否安全下探到数据面/安全控制面”的底板。

### 边界清单

- 本文讨论的是 eBPF 网络/安全场景稳定心智模型；XDP mode、redirect 目标、AF_XDP、LSM hook 支持、sockmap/sockhash 能力和驱动限制会随内核与网卡变化。
- 观测、数据面和安全裁决是三种不同风险等级的问题，不应被“都能用 eBPF”这句话压扁成一层。
- 越靠前越快，但也越依赖有限上下文和更严格的错误边界；这不是参数调一调能抹平的差异。
- BPF LSM 与传统 LSM 的关系是补充与分工，不是简单替代叙事。
- 本文先把 eBPF 收束到网络与安全场景；跨到系统编程卷后，重点将回到用户态 fd/I/O/进程/线程这些长期基础语义。
