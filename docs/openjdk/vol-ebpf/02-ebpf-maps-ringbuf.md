## 现在真正该问的，不再是“程序怎样进内核”，而是“程序进去了以后，它产生的状态、事件和栈证据到底应该放哪里、怎么出来、以及为什么不同通道看起来都能传数据，实际上却在语义和代价上完全不同”

上一章我们已经把 eBPF 的执行链立住了：用户态工具把程序变成受限字节码，`bpf()` 负责请求加载，verifier 证明控制流、寄存器、指针和 helper 访问合法，JIT/解释器执行它，hook 类型再决定它在什么上下文、拥有多大能力边界。

那一篇解决的是：**程序如何安全地进入内核。**

可真正把 eBPF 用起来时，新的困难几乎立刻出现：程序每次被 hook 触发都很短，它自己的栈会很快消失。那么：

- 若你想累计计数、维护阈值、保存 PID → 统计映射，状态放在哪？
- 若你想把每次高频事件实时送回用户态，为什么不能直接 `printf`？
- 若你想知道“这次重传/慢 I/O/调度延迟到底是哪条栈路径触发的”，栈回溯为什么又不只是“抓一个 backtrace”那么简单？
- RingBuf 和 Perf Event Array 看起来都能传事件，为什么新旧工具链会偏好不同方案？
- Per-CPU Map 为什么能减少竞争，却又不等于“无代价无锁”？

所以本篇最重要的顿悟是：**eBPF 数据面天然分成三层：Map 负责可查询状态，RingBuf/PerfBuffer 负责高频事件流，调用栈负责把事件重新钉回代码路径。程序能不能用，不只看 verifier 过不过，还要看这三层通道有没有选对。**

先把总图记住：

```text
程序执行：
  事件触发一次 eBPF 逻辑
  逻辑本身短小、受限

状态层：
  Map 保存跨事件、跨程序、跨进程共享的状态和配置

事件层：
  RingBuf / Perf Event Buffer 把高频观测结果送回用户态

归因层：
  kstack / ustack / LBR / ORC 等把事件重新连接到函数路径

用户态：
  libbpf / BCC / bpftrace 消费状态、事件和栈样本
  再把它们转成计数、直方图、时间线或火焰图
```

这一篇最重要的一句话是：**eBPF 程序本体只是“发生时做点事”，真正决定观测质量和开销的，往往是你把状态、事件和栈证据分别放进了哪条通道。**

## 一、如果你把所有状态都塞进程序自己的临时执行上下文，BPF 逻辑一返回，这些数据就跟着一起蒸发了

### 1. 最朴素的错误世界：每次事件来时现算现输，程序结束后什么都不保留

这对一些非常简单的一次性过滤动作也许成立，比如 XDP 程序收到包就丢、就放；tracepoint 程序判断一个条件直接返回。可一旦你的目标变成“长期统计、累积状态、跨事件对账”，这个模型立刻崩掉。

因为 BPF 程序每次执行都像一粒短暂的火花。它跑完就结束，栈帧也消失了。如果你没有一个程序之外的持久状态对象，那么：

- 上一次事件计了多少次？
- 某个 PID 的累计字节数是多少？
- 当前阈值配置应该是什么？
- 这次事件要不要和上一轮的状态一起判断？

这些问题都无处存放。

所以程序本体和状态容器从一开始就必须分开。

### 2. 第二个失败方案：那就所有程序共享一块“通用全局内存”

这听起来比临时栈好多了，但又会很快出问题。不同类型的数据有不同语义：

- 配置常常是固定槽位或低频更新；
- 统计计数要求并发更新尽量轻；
- 高速事件流需要环形传输和用户态消费；
- 某些状态需要按 CPU 分片，而不是全局共享。

如果你只给自己一块“大杂烩全局内存”，很快会在并发更新、内存布局、背压、唤醒和消费模型上一起踩坑。

所以 eBPF 不只是提供“一个共享内存对象”，而是提供了不同 Map 和事件通道，逼你按数据语义选结构。

### 3. eBPF 的核心答案：程序短执行 + 外部状态对象 + 独立事件管道

这正是 Maps、RingBuf 和 Perf Event Buffer 分工的起点：

- 程序负责在事件发生时做局部逻辑；
- Map 负责保存“跨这一次调用”的状态；
- RingBuf / PerfBuffer 负责把高频事件安全、有界、批量地送回用户态；
- 调用栈再负责把“发生了什么”挂回“谁触发了它”。

所以 eBPF 的数据面从来不是“程序自己什么都干完”，而是一套围绕短执行程序搭起来的外围账本与输送系统。

### 4. 本节最该记住的结论：BPF 程序的短生命周期决定了“状态”和“事件输送”必须外包给独立对象，否则观测很快失忆

一句最短人话是：**程序像一次次临时工，Map 和缓冲区才是长期账房与传送带。**

## 二、Maps：真正该先问的不是“我能不能存进去”，而是“这份数据到底更像字典、固定槽位，还是每 CPU 一份副账本”

### 1. 为什么不同 Map 类型不只是“接口不同”，而是并发和内存模型不同

Hash、Array、PerCPU Map 看上去都能保存“键值对”或“某些数据”，但它们解决的问题其实不同：

- Hash 更适合动态对象集合，如 PID、连接、inode、地址等映射；
- Array 更适合固定编号槽位或配置项；
- PerCPU 版本更像把同一逻辑值拆成每 CPU 一本账，减少更新争用。

所以选 Map 类型时，真正要想的不是“能不能把字段放进去”，而是“**数据增长方式、读写模式、并发竞争和聚合方式**”是什么。

### 2. 为什么 PerCPU Map 很容易被过度浪漫化

它确实能减少多个 CPU 争同一个 value 的更新冲突，因为每 CPU 写的是自己的副本。但这不等于它是“免费无锁加速器”。代价至少有两个：

- 内存占用会随着 CPU 数量膨胀；
- 用户态读时常要把每 CPU 副本再聚合成一个总结果。

这意味着 PerCPU Map 不是“更快的普通 Map”，而是“**用空间和后处理换更新竞争下降**”。

### 3. Hash 和 Array 为什么也不能只按“动态/固定”这么粗来看

Hash 通常更灵活，但查找、删除、容量、key 分布和并发行为都会影响成本；Array 固定索引简单，适合配置和小集合，但天然不擅长表示动态稀疏对象世界。某些 map 类型还带预分配、LRU、pinning 和不同 helper 行为差异。

所以 Map 的选择从来不是“接口喜好”，而是数据结构设计题。

### 4. 为什么 pinning 说明 Map 生命周期不应默认绑定到单个 loader 进程

只靠进程持有 fd，Map 生命周期就和那个进程绑定。很多时候你希望程序退出后，统计仍保留、配置仍可被别的消费者接手，这就需要 pin 到 bpffs。这样对象不再只是某进程的私产，而变成内核里可通过路径重新发现和复用的状态实体。

这也再次说明，Map 是一类内核对象，不是脚本里的普通变量。

### 5. 本节最该记住的结论：Map 选型真正决定的是“状态如何增长、怎样并发更新、要不要长期存在以及最终怎样被用户态读回”，而不是简单的“放不放得下”

一句最短人话是：**先问数据长什么样，再选 Map，不要先选 Map 再硬塞数据。**

## 三、RingBuf：当你想把高频事件源源不断送回用户态时，真正的问题不是“能不能发出来”，而是“怎样在固定容量里让生产者和消费者都别把对方拖死”

### 1. 为什么 tracing 事件不能走 printf / syscall 直出路线

高频事件一旦很多，比如每次 `open`、每次 block request、每次调度切换都想往外吐记录，如果你让 BPF 程序逐条打印或频繁做重型输出，系统会很快被观测本身压垮。你不是在测性能，而是在制造另一场性能事故。

所以事件传递必须是：

- 轻量写入；
- 批量消费；
- 有界缓存；
- 明确丢弃或背压语义。

这正是 RingBuf 适合的场景。

### 2. reserve / submit / discard 为什么是一种非常重要的协议

RingBuf 的关键不是“有个环形缓冲区”这么简单，而是写入协议很明确：先 reserve 一段空间，填好数据后再 submit；若发现条件不满足或想丢弃，就 discard。这样用户态就不会看到半条记录、脏记录或尚未写完的事件。

也就是说，RingBuf 不只是内存区域，更像一套“如何安全地把一条完整事件交付给消费者”的写入协议。

### 3. 为什么 RingBuf 仍然不保证“绝对不丢事件”

只要容量是有限的，生产速度又可能远高于消费速度，固定缓冲区迟早会满。满了以后，你只能：

- 让保留失败并丢事件；
- 或以某种方式背压；
- 或改观测策略，降低事件量。

所以 RingBuf 的真正价值不是“绝对可靠”，而是“**在高频事件和有限成本之间提供一个可控、有协议、较轻量的用户态出口**”。

### 4. 为什么它通常比逐条 syscall/日志式输出更适合高频 tracing

因为它把大部分工作前置成了固定内存协议和批量用户态 poll，而不是每个事件都立即唤醒、格式化和跨边界处理。它牺牲了“每条立刻看到”的简单性，换来“整体系统还能活下去”的可持续性。

### 5. 本节最该记住的结论：RingBuf 解决的不是“事件怎么写进内存”，而是“高频事件怎样用最小干扰、安全成帧、允许丢弃/背压地跨越内核到用户态”

一句最短人话是：**RingBuf 不是无限消息管道，而是一条有容量、有协议、有丢弃边界的传送带。**

## 四、Perf Event Array：它没有过时，它只是站在另一种历史和兼容性坐标上——很多成熟工具之所以还爱它，不是因为看不见 RingBuf，而是因为生态已经围着它长好了

### 1. 为什么旧工具链并没有一夜之间全部切到 RingBuf

从纯抽象看，RingBuf 很现代、协议清晰、共享缓冲区语义直接。可真实世界里，BCC 生态、大量现成工具、libbpf/BPF helper 的历史演进，以及每 CPU buffer 这种既有模型，都让 Perf Event Array 仍然保持强存在感。

所以“新代码考虑 RingBuf，老工具还用 PerfBuffer”不是落后，而是生态和兼容性现实。

### 2. Perf Event Array 和 RingBuf 真正的核心差异在哪

不是一句“一个旧一个新”。更实用的理解是：

- Perf Event Array 更像每 CPU 各自一条出站带，天然贴近很多按 CPU 分流的采集场景；
- RingBuf 更像共享事件带，顺序和模型更统一，但也意味着共享容量和协调语义集中化。

两者都能把事件带出内核，但它们的缓冲组织方式、顺序直觉、用户态 API 和历史生态不同。

### 3. 为什么“RingBuf 全面替代 PerfBuffer”这种说法会误导人

因为选择并不只看理论优雅，还看：

- 目标内核版本和 helper 是否支持；
- 你用的是 BCC 现成工具还是 libbpf 自研程序；
- 你更在意全局顺序、每 CPU 局部性还是兼容已有链路；
- 消费者和生态是否已经围绕某种模型铺好了。

这说明数据管道的选择同样是工程折中题，而不是版本号题。

### 4. 本节最该记住的结论：Perf Event Array 和 RingBuf 都是在解决“高频事件怎样离开内核”这件事，只是所选缓冲组织、生态语境和兼容性约束不同

一句最短人话是：**PerfBuffer 更像多窗口售票，RingBuf 更像一条共享传送带。**

## 五、调用栈回溯：很多事件值钱的地方不在“发生了”，而在“是谁在什么路径上把它触发了”；但栈证据从来不是一份单一、完美、零成本的地图

### 1. 为什么事件和计数不够回答“谁触发了它”

你已经知道 TCP 重传多、block I/O 延迟高、调度等待长，这当然有价值。但若你还想继续问“究竟是哪条内核或用户态调用链把它触发出来的”，计数器和事件本身就不够了。你需要把事件重新挂回代码路径，这就是调用栈回溯的价值。

### 2. 为什么 frame pointer、ORC 和 LBR 是三种不同证据，不该混成一个“栈回溯”概念

- frame pointer 给你的是相对直接的栈链，但前提是编译和平台保留了它；
- ORC 更像内核自己的 unwind 元数据体系，适合在不完全依赖帧指针的情况下追栈；
- LBR 记录的是最近的分支历史，更像路径碎片，而不是任意深度的完整调用栈。

所以栈回溯不是一个按钮，而是多种证据源的折中。你要先问：当前平台、当前 workload、当前精度要求适合哪种。

### 3. 为什么火焰图宽度不是“这次调用花了多少时间”

栈样本经常会进一步被折叠成火焰图。这里必须重新强调：火焰图反映的是采样分布，而不是每次调用的精确定时。你看到某条栈很宽，说明“很多样本落在这里”，不等于它是唯一根因，也不等于某次单次执行就一定花了那么长时间。

所以把栈证据转成火焰图之后，你得到的是形状和聚集趋势，不是逐条交易明细。

### 4. 为什么调用栈是第三层证据，而不是总答案

Map 给你状态，RingBuf/PerfBuffer 给你事件，调用栈再把这两者重新接回代码路径。这非常强大，但仍然不是全部：

- 栈可能被优化、裁剪或采样失真；
- 你看到“谁触发了”，仍要回头结合参数和 workload 理解“为什么这个触发频率有意义”；
- 抓到了内核栈，还可能缺用户栈；反之亦然。

所以栈是归因强化器，不是万能解释器。

### 5. 本节最该记住的结论：调用栈让事件从“发生了”变成“哪条路径最常触发它”，但获取方式、完整性和可解释性都必须结合平台和采样边界重新审视

一句最短人话是：**事件告诉你有事了，栈告诉你是谁把事惹出来了。**

## 六、把本篇收成一张图：eBPF 数据面真正成熟时，从来不是“程序跑起来了”，而是“状态、事件和归因三条通道都被选对了，且它们的成本和语义都在控制之中”

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：eBPF 程序进了内核之后，产生的状态、事件和栈证据到底该放哪里。答案首先说明，程序本体只是短执行逻辑，不适合自己长期背状态。Map 于是承担可查询状态和跨事件累积，RingBuf/PerfBuffer 承担高频事件输出，栈回溯则把“发生了什么”重新绑定回“谁触发了它”。

不同 Map 类型对应不同的并发和生命周期现实：Hash/Array 适配不同数据形态，PerCPU Map 用空间换更新竞争下降，bpffs pin 再把对象寿命从单一进程延长到系统级引用。RingBuf 通过 reserve/submit/discard 协议保证单条记录原子可见，但并不提供无限吞吐和绝对零丢失；Perf Event Array 则在生态和每 CPU 组织模型上依然极具现实价值。栈回溯最后补上归因，但它同样受 frame pointer、ORC、LBR、符号和采样边界约束。

把这一切压成最短总图，就是：

```text
状态层：
  Hash / Array / PerCPU Map 保存长期状态和配置

事件层：
  RingBuf / Perf Event Buffer 传高频事件流

归因层：
  kstack / ustack / ORC / LBR 把事件接回代码路径

生命周期层：
  fd 引用与 bpffs pin 让对象能跨进程持续存在

工程判断：
  选择哪条通道, 本质上是在选择并发模型、内存开销、顺序语义和生态兼容性
```

所以本篇最该记住的一句话是：**eBPF 不是只有“程序怎么跑”这一层，真正可用的数据面来自“状态怎么存、事件怎么出、归因怎么做”三条通道的正确分工。**

## 七、几个最容易说错的地方

### Map 是不是只是“BPF 版全局变量”？

不够准确。Map 是受类型、并发、生命周期和访问 helper 约束的内核状态对象，不只是语法上的全局变量替身。

### PerCPU Map 是不是完全无代价的无锁加速方案？

不是。它减少跨 CPU 竞争，但会增加内存占用，并要求用户态按 CPU 副本再聚合。

### RingBuf 是不是能保证高频事件永不丢失？

不能。固定容量、消费速度和背压策略仍会决定丢失和失败边界。

### Perf Event Array 已经过时，只要新项目都该用 RingBuf？

不完全。生态、兼容性、每 CPU 组织方式和目标工具链都会影响选择。

### 栈回溯是不是只要打开一个选项就能得到完整可靠的调用栈？

不是。frame pointer、ORC、LBR 和符号化能力各有边界，采样方式也会影响完整性和偏差。

### 有了状态、事件和栈，是不是就等于根因已经找到？

不一定。它们仍需要和 workload、时间线、业务指标与子系统账本重新对齐，才能构成完整因果链。

## 收束：看懂 Maps、RingBuf 与调用栈之后，你才会真正明白 eBPF 的强大不只在“能插进去”，更在“插进去之后能把哪类事实、以什么代价、用哪种形态带出来”

回到开头那个问题：程序进去了以后，计数、状态和高频事件如何离开内核，以及如何把事件归因到调用栈？现在答案已经完整闭环了。程序只负责在事件发生时做受限逻辑，Map 负责保存长期状态，RingBuf/Perf Event Buffer 负责把高频事件送回用户态，调用栈则把这些事件重新钉回代码路径。只有把这三类通道都选对，你得到的观测才既有解释力，又不会先把系统自己拖死。

也正因为如此，你会发现 eBPF 数据面设计本身就是一门工程：状态应该按什么结构长、事件该走哪条管道、什么时候值得做栈回溯、对象是否需要 pin、用户态消费速度够不够快。这些问题若答错，程序即使 verifier 通过，也只会变成另一个观测噪音源。把它们答对，eBPF 才真正从“能运行的程序”变成“能持续产出高价值证据的观测器”。

这就是为什么说：**eBPF 架构的第一篇解决了‘程序怎么进去’，而本篇真正解决的是‘价值怎么出来’。** 没有后者，前者只是一场安全加载秀。
