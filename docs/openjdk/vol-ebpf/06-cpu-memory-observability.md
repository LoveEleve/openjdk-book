## 现在真正该问的，不再是“探针应该挂在哪”，而是“如果 CPU 跑满、run queue 拉长、OOM 告警出现或 page cache 行为异常，这些现成 eBPF 工具到底各自在盯哪一段生命周期，又该怎样拼起来回答真正的系统问题”

前一篇我们已经把 tracing 数据源选择讲清楚了。你知道 tracepoint/USDT 通常比 kprobe/uprobes 更稳定，动态探针是补静态语义缺口的工具，而不是长期观测默认首选；helper、程序类型和 attach 上下文也决定了“能看”和“能看准”并不是同一件事。

可一旦回到真实生产现场，工程师手里的问题不会写成“我想看这个 tracepoint”，而更像：

- 为什么机器 CPU 很高，究竟是谁在持续产生新进程、谁在 run queue 上等、谁在真正烧 CPU？
- 为什么用户说系统卡，CPU 却不高，是不是线程都在 off-CPU 等锁或等 I/O？
- 为什么内存报警了，究竟是工作集真的膨胀、page cache 被冲掉、slab 变大，还是 cgroup 和 OOM 策略在先发作？
- 为什么明明不是磁盘服务，filetop/biolatency 却能告诉你谁把 page cache 和回收链拖坏了？

这就把我们带到本篇真正的主题：**eBPF 现成工具的价值，不是“命令更多”，而是它们分别站在 CPU 与内存生命周期的不同阶段看问题：谁创建、谁排队、谁执行、谁等待、谁分配、谁回收、谁触发 OOM、谁把文件页和 slab 吃掉。**

所以本篇最重要的顿悟是：**这些工具并不是“症状快捷键”，每个工具只覆盖问题链上的一段；真正的定位能力来自把创建、调度、执行、等待、分配、回收和 I/O 几段重新拼成同一条时间线。**

先把总图记住：

```text
CPU 侧：
  execsnoop 看谁生成了新工作负载
  runqlat 看谁想跑却没轮到
  cpudist 看连续执行片段形状
  profile 看 on-CPU 热点
  offcputime 看离开 CPU 后在等谁

内存侧：
  oomkill 看最后谁被系统处决
  faults 看 page fault 生命周期
  memleak 看分配与释放的失配
  cachestat/cachetop 看 page cache 工作集与命中趋势
  vmscan 看回收和换页压力

文件/块 I/O 侧：
  opensnoop/filetop/biotop/biolatency 把“内存慢”继续拉回具体文件和设备请求
```

这一篇最重要的一句话是：**eBPF 工具真正强的地方，不是某条命令神奇地给你答案，而是它们分别抓住了 CPU/内存问题链上的一个切面，只有把这些切面拼起来，你才会知道请求到底死在哪一段。**

## 一、CPU 工具矩阵：exec、排队、运行片段、热点栈和系统调用各自回答的是“工作是怎么长出来的、怎么排队的、怎么被消费的”不同问题

### 1. 为什么“CPU 高”这个症状至少要被拆成五个不同问题

同样是 CPU 高，可能是：

- 有新进程/新 worker 在疯狂出生；
- 线程 runnable 很多但总轮不到；
- 某些线程在 CPU 上总是长时间霸占；
- 真正的热点函数很宽；
- 系统调用本身把 CPU 烧掉了。

如果你只开一个 profiler，就很可能只看见最后一层热点，而不知道工作负载其实是从更前面的某个阶段异常长出来的。比如一个进程不断 fork/exec，或一个任务调度风暴让 run queue 拉长，你若只看 on-CPU 栈，常会错把“谁在执行”当成“谁制造了问题”。

这就是为什么 CPU 工具矩阵需要先分层：它们盯的是不同生命周期切面，而不是同一个问题的不同 UI。

### 2. execsnoop：为什么“谁在不断创建进程/程序”有时比“谁最占 CPU”更先解释异常

有些性能事故表面上是 CPU 高，实际是异常进程创建风暴：脚本循环起进程、任务调度器失控、短命命令被高频执行。execsnoop 盯的正是这一刻——新的可执行体是谁、什么时候出现、谁在反复制造新工作负载。

这让它和 profile 的关系非常像“入口流量”与“加工热点”的区别。你得先知道货是谁源源不断送进来的，再谈后面哪条工位最宽。若要把这一节补成更硬的证据位，最关键的落点应回到 exec 事件、run queue 延迟、on-CPU/off-CPU 采样和热点栈聚合这些现成工具对应的探针与聚合语义：它们共同支撑“同样是 CPU 问题，谁在创造工作、谁在排队、谁在真正烧 CPU，是三段不同生命周期”的判断。

### 3. runqlat：为什么“线程想运行但没拿到 CPU”是完全不同于“CPU 正在干什么”的另一种真相

runqlat 的核心价值不是“CPU 很忙”，而是“线程从 runnable 到真正获得 CPU 花了多久”。这让它特别适合抓那类 CPU 利用率不一定极端高、但调度等待已经在拉长延迟的场景。

你可以把它理解成“排队时间的分布”，而不是“工作时间的分布”。很多系统用户体感变差，真正原因不是执行更久，而是排队更久。

### 4. cpudist / profile / syscount 为什么三者不能互相替代

- cpudist 更像看“线程连续占住 CPU 的片段形状”，帮助判断工作是否碎、是否长、是否更像计算型还是频繁切换型；
- profile 更像看“CPU 真正花在了哪些栈路径上”；
- syscount 则把注意力拉回用户态/内核态边界，告诉你是不是某些系统调用风暴本身就在烧 CPU。

它们一个看排队后的片段、一个看执行热点、一个看边界行为。你若把其中一个当成总答案，常常就会只看到链路的一段。

### 5. 本节最该记住的结论：CPU 工具矩阵的价值，不在“哪条命令最准”，而在“它们分别覆盖了工作负载生成、排队、执行和系统调用边界四个不同阶段”

一句最短人话是：**先问工作是怎么来的、怎么排的、谁在跑、是不是内核边界烧掉了 CPU。**

## 二、off-CPU、中断与唤醒：CPU 不高但延迟很烂时，真正值钱的不是继续看热点，而是把“线程离开 CPU 后到底在等谁、谁又在什么时候把它叫回来”这条链补齐

### 1. 为什么 on-CPU 热点图无法回答“它剩下的时间去哪了”

on-CPU profile 非常强，但它的边界也很清楚：只看线程在 CPU 上跑时，栈最常落在哪。若一个请求 1 秒里只有 50ms 真在 CPU 上，剩下 950ms 去哪了，它本身并不回答。

这时如果你还继续盯着 on-CPU 热点，很容易在那 50ms 里打转，却完全错过真正的大头。

### 2. offcputime 的真正价值：把“没在 CPU 上跑”的时间重新按阻塞调用栈聚合

offcputime 本质上是在问：**线程离开 CPU 后，时间最常挂在哪些阻塞栈上？** 于是锁、I/O、futex、sleep、等待队列、某些内核路径都会在这里显形。它不是热点执行图，而是等待归因图。

这让它特别适合和 runqlat、profile 做三角定位：

- runqlat 看“可跑但在排队”；
- offcputime 看“不可跑时在等什么”；
- profile 看“真跑起来后在干嘛”。

证据位上，这层最值得回到 off-CPU 栈聚合、调度延迟与 on-CPU 热点三类工具的互补关系上：它们共同支撑“同一个慢请求，可能不是 CPU 算得慢，而是没轮到跑、跑不到头、或者一直在等别人开门”这句判断。

### 3. 为什么 IRQ / softirq 也必须进这张图

很多请求不慢在用户线程自己，而是慢在 CPU 时间已经先被网卡、定时器、存储中断或 ksoftirqd 抢走了。用户线程因此既可能排队，也可能被延后唤醒。所以观察中断/软中断量和分布并不是另一个话题，而是 CPU 等待链路的一部分。

### 4. 本节最该记住的结论：CPU 不高但延迟很高时，真正要补的是“离开 CPU 后的等待账单”和“谁在抢占/唤醒 CPU 机会”的时间线，不是继续单看热点函数

一句最短人话是：**用户线程不跑，不代表它没事干；它可能正在门外排队，也可能正在屋里等别人开门。**

## 三、OOM、fault 与 memleak：内存问题真正难的不是“谁占得多”，而是“这个地址空间问题到底发生在分配、驻留、回收、换页还是最终处决哪一段生命周期上”

### 1. 为什么 OOM 工具本身几乎从来不能单独证明“谁泄漏了”

oomkill 之类工具会告诉你谁在某次 OOM 中被杀了、当时的 cgroup/进程上下文是什么。这非常有用，但它回答的是最后止损发生在哪，而不是谁最早开始把账做坏。真正的泄漏者、缓存膨胀者或长期积压者，未必正好是最终被杀的那个进程。

所以 OOM 工具更像“案发现场记录”，不是“作案动机证明”。

### 2. faults 为什么是内存生命周期中非常关键的中段证据

minor/major page fault 把“地址空间怎么从未就绪走到真正可访问”这段生命周期抓出来了。它告诉你问题更像是：

- 热路径在不断打缺页；
- 工作集没有稳住；
- major fault 把磁盘/换页拉进来了；
- 还是其实只是 minor fault 在建立映射。

所以 faults 不是一个简单的“内存有问题”指标，而是在把内存延迟拆分成“页面怎样到手”的过程证据。

### 3. memleak 为什么需要被特别谨慎地解释

它通常是在盯某类分配/释放不匹配的长期对象，试图保留下疑似未释放的分配栈。但它受限于：

- 观测覆盖的分配器范围；
- 生命周期窗口；
- 采样和对象可见性；
- 某些对象“长寿但正常”的业务现实。

所以 memleak 很适合作为“可疑对象来源”探测器，却不该被当成“法官已宣判”的终局证据。

### 4. 本节最该记住的结论：内存 tracing 最值钱时，是把 OOM、fault、memleak、mmap 和回收事件重新排成同一条生命周期，从而区分“谁在最终死”“谁在不断换页”“谁可能长期不释放”

一句最短人话是：**内存问题不是一个点，而是一条从分配到回收再到处决的长生命周期。**

## 四、cachestat / cachetop / vmscan：缓存命中、工作集和回收压力必须被放在一起解释，不然“命中率低”很容易被当成错误目标

### 1. 为什么 page cache 命中率不是越高越好

命中率高当然常常是好事，但它并不是唯一目标。一次性顺序扫描、批量备份、大型对象流式读取，本来就可能天然把很多数据读一遍就扔，不值得为了提高命中率而强行扩大缓存或改变策略。相反，一个频繁复用的小工作集即使命中率只小幅下滑，也可能严重拉高延迟。

所以缓存分析最重要的不是追逐高命中率，而是判断：**当前 workload 本来应不应该命中，以及 miss 的代价是否真的在伤业务。**

### 2. 为什么 vmscan 和 PSI 要一起看

命中率变差，有时不是访问模式变了，而是内存压力迫使系统不断回收页缓存。此时若只看 cachestat，你会误以为“缓存策略不行”；把 vmscan 和 PSI 拉进来后，才会看到是 reclaim 在不断把命中前提本身拆掉。证据位上，这层最值得回到 cachestat/cachetop、vmscan、PSI 与文件/块 I/O 现成工具的组合上：它们共同支撑“page cache 命中率下降可能是缓存策略问题，也可能是回收压力把缓存现实先拆坏了”的判断。

这说明 page cache 命中率很多时候并不是独立指标，而是整个内存/回收账本的一部分影子。

### 3. 本节最该记住的结论：缓存 tracing 的意义，不是替命中率找一个漂亮数字，而是判断 miss 是 workload 的自然结果，还是内存压力和回收在先把缓存现实拖坏了

一句最短人话是：**别先问命中率高不高，先问这批数据本来值不值得被长期记住。**

## 五、文件/块 I/O 工具链：一次“读文件很慢”最终要被拆成“谁打开了它、谁在高频读写、文件系统层在哪慢、块层哪一段排队最久”这四层证据

### 1. 为什么 opensnoop / filetop / biotop / biolatency 不能互相替代

因为它们分别盯的是文件生命周期的不同段：

- opensnoop 看谁在打开/创建路径；
- filetop 看谁在对哪些文件高频读写；
- biotop 看谁在产生块请求；
- biolatency 看块请求的延迟分布。

你若只看其中一个，就像只看仓库门口、不看传送带、不看装车区一样，很容易错过真正堵点。

### 2. 为什么“某个文件最热”也未必等于“它就是罪魁祸首”

一个热点文件也许被频繁读，但命中 page cache 很好，真正的问题也许在另一个 fsync-heavy 的小日志文件；或者文件层很热，但块层真正慢的是底下另一个设备上的元数据更新。只有把文件级和块级 tracing 对齐，才能知道“这个文件热”和“这个文件真的拖慢请求”是不是同一件事。

### 3. 本节最该记住的结论：文件/块 I/O tracing 的关键不是哪个工具最强，而是把路径、文件对象、块请求和延迟分布连成一条完整证据链

一句最短人话是：**慢文件不是终点，慢块请求也不是起点，得把两者接起来。**

## 六、把本篇收成一张图：场景化 eBPF 观测真正成熟时，不是会背工具名，而是知道它们分别站在 CPU/内存/文件/块 I/O 生命周期的哪一段，必须怎样拼起来才构成证据

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：CPU 跑满、线程排队、OOM 告警、缓存异常出现时，eBPF 现成工具如何真正帮你把问题定位出来。答案首先说明，这些工具并不是症状快捷键，而是分别钉在不同生命周期上的窗口：execsnoop 看工作负载是怎么长出来的，runqlat/cpudist/profile 看它怎么排队和执行，offcputime/IRQ 观察把“为什么不在 CPU 上跑”继续拆开；oomkill/faults/memleak 又把内存生命周期从最终处决回溯到分配和驻留阶段；cachestat/vmscan 把 page cache 和回收重新拼成同一张图；文件/块 I/O 工具则继续把“慢在文件系统”一路拆到具体 block 请求。

真正值钱的地方不是某条命令，而是你知道：

- 它在生命周期的哪一段看；
- 它没看见哪一段；
- 还要拉什么别的工具一起补齐证据链。

把这一切压成最短总图，就是：

```text
CPU：
  谁创建 → 谁排队 → 谁执行 → 谁等待唤醒

内存：
  谁分配 → 谁 fault → 谁回收/换页 → 谁被 OOM 杀

缓存/文件：
  谁访问文件 → 哪些页命中/被回收 → 哪些 block 请求真正慢

方法：
  不看单工具
  只看生命周期拼图是否完整
```

所以本篇最该记住的一句话是：**场景化 eBPF 工具真正帮你的，不是“替你下结论”，而是“把 CPU/内存/文件/块 I/O 的不同阶段重新摆上桌，让你有机会沿时间线和生命周期把结论拼出来”。**

## 七、几个最容易说错的地方

### execsnoop/profile/offcputime 选一个看就够了吗？

不够。它们分别看工作负载生成、on-CPU 热点和 off-CPU 等待，覆盖的是不同生命周期阶段。

### oomkill 抓到被杀进程，是不是就等于找到了泄漏根因？

不是。它更像最终处决现场，还要结合分配、fault、memleak、cgroup 和工作集趋势回看整个生命周期。

### 缓存命中率下降，是不是一定应该先加内存？

不一定。先要判断这是工作集自然变化、一次性扫描，还是 vmscan/回收压力在先拖坏缓存现实。

### filetop 或 biotop 排名第一的对象，是不是一定就是问题源头？

不一定。要结合延迟分布、缓存命中和上层 workload，看“热”是否等于“害人最重”。

### eBPF 现成工具是不是比系统性能卷那些聚合指标更“接近真相”？

不一定。它们更接近路径切面，但依然有采样、字段、事件频率和覆盖边界，必须和聚合指标互相验证。

### 场景化工具够多，是不是就不需要自己再写 tracing 了？

不一定。现成工具能快速覆盖共性问题，但具体业务路径和特殊参数仍可能需要自定义脚本或 libbpf 工具补洞。

## 收束：看懂 CPU/内存 eBPF 工具之后，你才会真正明白“可观测性工具箱”不是一堆命令，而是一张覆盖生命周期不同切面的镜子阵列

回到开头那个问题：CPU 使用率 100% 或内存告警出现时，怎样从“哪个指标高”推进到“哪个进程、哪个路径造成”？现在答案已经完整闭环了。你不会再把 execsnoop、runqlat、profile、offcputime、oomkill、memleak、cachestat、filetop 当成一堆平铺工具名，而会知道它们分别站在 CPU/内存/文件生命周期的不同阶段：谁创造工作、谁排队、谁执行、谁等待、谁分配、谁回收、谁真正触发 I/O。只有把这些镜子摆在正确顺序里，你才会从“系统慢”走到“问题具体死在这条路径的这一步”。

也正因为如此，你会发现最危险的不是工具不够多，而是拿错工具回答错问题。CPU 高时只看 profile，会漏掉 run queue；OOM 时只看 oomkill，会漏掉长期工作集；磁盘慢时只看 biotop，会漏掉 page cache 和回收。把这些工具按生命周期组织起来，才是场景化可观测真正的价值。

这就是为什么说：**成熟的 eBPF 观测不是会列工具清单，而是会拼时间线和生命周期。** 工具只是窗口，真正重要的是你知道自己正在看的是哪一段故事。

## 七、误解清单、证据清单与边界清单

### 误解清单

- eBPF 现成工具不等于一个比一个“更接近真相”；它们只是分别站在 CPU/内存/文件/块 I/O 生命周期的不同切面上。
- CPU 高时只看 profile 不够；谁在创建工作、谁在排队、谁在 off-CPU 等待，常常比热点本身更早解释异常。
- oomkill 抓到被杀进程不自动等于找到泄漏根因；它更像最终处决现场，而不是整条生命周期起点。
- page cache 命中率下降不一定先怪缓存策略；vmscan/PSI 可能在更前面就把缓存前提拆坏了。
- filetop/biotop 排名第一不等于它一定是源头；“最热”还要结合延迟分布、缓存现实和 workload 判断。 

### 证据清单

- CPU 生命周期：execsnoop、runqlat、cpudist、profile、offcputime 与中断/软中断相关工具，支撑“谁创造工作、谁排队、谁执行、谁等待”四段切分。
- 内存生命周期：oomkill、faults、memleak、cgroup/PSI、工作集画像，支撑“最终处决、缺页、长期失配和压力停顿”这些不同阶段。
- 缓存与回收：cachestat/cachetop、vmscan、PSI 的组合，支撑“命中率下降到底是访问模式变了，还是回收压力先把缓存现实拆坏了”。
- 文件/块 I/O：opensnoop、filetop、biotop、biolatency 这类工具，支撑“把内存慢继续压到文件对象和设备请求”的路径证据。
- 证据拼接：现成工具输出与 perf、PSI、`/proc`、工作负载时间线互相验证，支撑“单个工具几乎永远不够独立定案”的方法论。

### 边界清单

- 本文讨论的是 eBPF/BCC/bpftrace 现成工具的场景化观察心智模型；字段、参数、Map 聚合方式和 attach 点会随内核、工具链和 workload 变化。
- 现成工具很适合快验，但不自动替代自定义脚本或 libbpf 工程；特殊业务路径仍可能需要自己补洞。
- 工具输出站位不同：有的看入口流量，有的看排队，有的看执行，有的看最终处决，不可混成同一层结论。
- 高事件频率、栈采样、Map 聚合和用户态消费速度仍然决定开销上界；脚本能跑不等于长期安全。
- 本文先讲“怎样看 CPU/内存问题”；下一篇才真正把 eBPF 推到数据面最前面，回答“怎样直接动手”。
