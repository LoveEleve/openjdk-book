# 为什么 HikariCP 里的 `close()` 不等于关闭连接，而是在决定这条连接还能不能继续活着

> 本文基于 HikariCP 7.0.2 当前源码。本文不把连接归还写成一个简单的 `close()` 调用，也不把它写成“用完放回池里”的口头描述，而是专门解释：在 HikariCP 里，连接用完之后其实会进入一条完整的后半链——先清理状态、再判断命运，最后要么被归还复用，要么被标记驱逐并真正退出。

## 为什么连接已经“用完”了，HikariCP 却还要做这么多事

从普通 JDBC 直觉看，连接的后半段好像很简单：

- 拿到一个 `Connection`
- 执行 SQL
- 用完后 `close()`
- 事情结束

这个模型在非池化世界里大体成立，因为 `close()` 大多数时候真的意味着：
- 底层物理连接被关闭

但一旦进入 HikariCP，这个理解立刻不够用了。因为在池化世界里，`close()` 不再只是“关闭资源”，它还必须回答两个更难的问题：

- 这条连接现在还能不能继续活着，供下一次借出使用？
- 如果不能继续活着，它应该是在什么地方被真正驱逐和关闭？

也就是说，连接在 HikariCP 里不是“用完即死”的一次性资源，而是一条被长期管理的生命体。它前半段被借出，后半段就必须被判断、清理、重置，再决定是继续活还是退出。

所以，本文真正要回答的问题不是“`close()` 内部做了什么”，而是：

**为什么在 HikariCP 里，连接用完之后不会直接结束，而必须先进入一条决定它命运的归还与驱逐链？**

## 先看失败方案：为什么不能把归还理解成“放回池里”

### 失败方案一：`close()` 就是关闭底层 JDBC 连接

这是最自然的 JDBC 直觉。

如果没有连接池，这句话通常没什么问题。

但在 HikariCP 里，如果每次 `close()` 都真的把物理连接关掉，那前面借出链做的事情就几乎全废了：

- 借出前的池内管理失去意义
- 连接复用失去意义
- keepalive / maxLifetime / HouseKeeper 都失去前提

所以在池化世界里，`close()` 不再天然等于“杀死连接”，而是更像：

- 当前调用方宣告“我这轮用完了”

后面至于连接是不是继续活着，还要看池自己的判断。

### 失败方案二：归还就是把连接原样放回池里

这个误解比第一种稍微进了一步，但仍然不够。

因为如果连接只是原样被塞回池里，就会出现一整串明显风险：

- 上一轮请求留下的事务状态怎么办
- 自动提交、只读、隔离级别、catalog、schema 这些状态谁来恢复
- 打过标记的连接是不是还能继续借出去
- 某次异常是否已经说明这条连接不该再活着了

所以归还链绝不只是“放回去”，它更像一次清场：

- 把这条连接从“当前调用者的私人物品”重新清回“池内公共资源”的可用状态

### 失败方案三：异常驱逐只是边角逻辑

有些人会把 `checkException()` 这类逻辑看成异常路径里的附属补丁，觉得正常主线里根本不重要。

这个理解同样不对。

因为驱逐决策真正决定的是：

- 这条连接还配不配继续待在池里
- 下一个调用者拿到的是不是已经坏掉的连接
- 这次异常究竟只是业务失败，还是连接级失败

也就是说，异常驱逐并不是尾巴，而是在决定一条连接“还能不能继续活着”的生命史判断点。

## 连接后半段的最小总图

如果把 HikariCP 里的连接后半段先压缩成最小模型，它可以写成下面这样：

```text
ProxyConnection.close()
   -> close statements / rollback if needed
   -> inspect dirty state
   -> reset connection state
   -> recycle to pool
   -> or mark evicted and close later
```

如果再换一种更容易理解的拆法，这条链可以分成三段职责：

```text
[归还前清理]
close statements / rollback / dirtyBits

   ->

[命运判断]
checkException / evicted / alive-or-not

   ->

[后半段分支]
requite for reuse  OR  close/evict for exit
```

这张图最重要的价值，不是让读者背几个方法名，而是先把三个问题分开：

### 一、归还前清理
回答：一条连接在回到池里之前，哪些历史状态必须先被抹掉？

### 二、命运判断
回答：这条连接现在是还能继续活，还是已经该被驱逐了？

### 三、后半段分支
回答：它最后会进入“继续复用”分支，还是“准备退出”分支？

只要先把这三段职责分开，后半链为什么这么重，就不再难理解。

## 一、`ProxyConnection.close()`：这不是物理关闭，而是连接后半链的入口

在 HikariCP 里，调用方拿到的并不是裸连接，而是代理连接。前一篇已经解释过，这是为了让池在交付之后仍然保留控制权。

这也意味着：
- `close()` 第一次看起来像“结束动作”
- 但在池内部，它其实只是后半链的入口

方法级锚点很明确：
- `ProxyConnection.close()`: `com/zaxxer/hikari/pool/ProxyConnection.java:240`

也就是说，调用方执行 `close()` 的真正含义是：

- “我这轮用完了，请池来判断这条连接接下来怎么办”

这一步的重要性在于，它把控制权从调用方重新交回池中心。如果没有代理这一层，连接生命史在交付给调用方时就断掉了；而有了代理这一层，归还、驱逐、状态重置、后续复用才有机会继续被统一管理。

所以：
- 对调用方来说，`close()` 是结束
- 对池来说，`close()` 才是后半链真正开始的地方

## 二、为什么归还前一定要先清事务、清语句、清状态

一条连接在当前请求里用过之后，最危险的不是“没放回池里”，而是：

- 放回去之前看起来还活着
- 但里面带着上一轮留下的脏状态

所以在 HikariCP 的后半链里，归还前清理是第一件真正必须发生的事。

这里至少有三类东西要被处理：

### 1. 语句资源
如果当前调用方还留下未关闭语句，后续复用时就会把资源残留带进下一轮。归还前不先把这些状态收好，连接就算逻辑上回池了，运行时也还是脏的。

### 2. 事务状态
如果当前连接不是自动提交，或者有未完成事务，那么归还前就必须把事务边界收回去。否则下一位调用者拿到的就不是“新的可用连接”，而是“别人业务半路用过的连接”。

### 3. 连接属性状态
自动提交、只读、事务隔离级别、catalog、network timeout 等状态，一旦被业务代码改过，就必须在归还前恢复默认值。否则连接池就不再提供“稳定的一致连接”，而变成“带历史残留的随机连接”。

也就是说，后半链的第一步不是“把连接放回去”，而是：

**先把它恢复成下一轮可以安全再用的状态。**

所以，归还前清理在 HikariCP 里不是附属步骤，而是复用成立的前提。

## 三、为什么 `dirtyBits` 不是小技巧，而是状态重置的控制面

如果每次归还都把所有可能被改动的连接状态无脑重置一遍，当然也能工作。

但这样做有一个明显问题：
- 没必要的状态修改也会被每次重复执行
- 这会把归还链变得更重

所以 HikariCP 没有这么粗糙地处理，而是通过 `dirtyBits` 这种位掩码去追踪：

- 这轮请求到底改过哪些连接状态

这样在归还时，池就不需要盲目全量重置，而可以更精确地恢复真正被污染过的部分。

这件事看起来像一个小优化，但它其实说明了一条更大的设计取舍：

- 归还链既要保证状态干净
- 又不能让状态清理本身变成新的负担

所以 `dirtyBits` 并不是“优化彩蛋”，而是“正确性和性能同时兼顾”的控制面。

对应的硬锚点包括：
- `dirtyBits` 字段：`com/zaxxer/hikari/pool/ProxyConnection.java:57`
- 归还链里只有在 `dirtyBits != 0` 时才触发 `resetConnectionState(...)`：`com/zaxxer/hikari/pool/ProxyConnection.java:254`
- 实际重置入口：`com/zaxxer/hikari/pool/PoolBase.java:213`

## 四、`checkException()`：为什么异常会改变连接的命运

清理完状态以后，还不能马上宣布这条连接可以继续活。因为连接还有可能在这一轮使用中已经暴露出更深的故障。

这就是 `checkException()` 这类逻辑存在的原因。

它最重要的意义在于：

- 并不是所有异常都只属于业务语义
- 某些异常其实已经在告诉池：这条连接本身可能出问题了

也就是说，后半链不能只问：
- 现在状态干不干净

还要继续问：
- 这条连接本身还值不值得继续活着

所以 `checkException()` 的地位很关键。它不是“顺手看一下异常”，而是在做一件本质性的事：

证据：`com/zaxxer/hikari/pool/ProxyConnection.java:151`

**把一次请求里的异常结果，上升成对连接生命史的命运判断。**

如果判断它应该退出，那接下来走的就不是“归还复用”分支，而是“驱逐退场”分支。

## 五、`recycle()` / `requite()`：继续活着的连接是怎样回到池里的

如果一条连接通过了前面的清理和命运判断，那它就有资格进入“继续活着”的分支。

这时候真正发生的就不再是“继续被当前调用方持有”，而是：

- 它重新回到池的可用候选集合里

这条回归路径里，关键动作就是：
- `PoolEntry.recycle()`
- `ConcurrentBag.requite()`

证据：`com/zaxxer/hikari/pool/PoolEntry.java:77`
证据：`com/zaxxer/hikari/pool/PoolEntry.java:99`
证据：`com/zaxxer/hikari/util/ConcurrentBag.java:187`

也就是说，归还不是抽象概念，而是把这条连接重新变成池内可供下一轮候选获取的对象。

所以“继续活着”这件事，并不是一个静态状态，而是一个明确的后半链分支：

- 清理干净
- 没被驱逐
- 回到池内
- 等待下一轮被借出

也正因为如此，借出链和归还链从来不是两个无关流程，而是同一条连接生命史的前后半段。

## 六、为什么驱逐不是额外功能，而是后半链的另一条出口

如果连接通过不了命运判断，它就不会再走 `recycle/requite` 这条“继续活着”的路。

这时候它进入的，就是另一条分支：

- 驱逐
- 关闭
- 退出池生命史

这件事的重要性在于，它说明连接池不是“只要建出来就尽量一直留着”。恰恰相反，HikariCP 非常明确地接受一个事实：

- 有些连接应该继续活
- 有些连接到了某个时刻就该被请出场

所以驱逐并不是边角逻辑，而是后半链另一条正式出口。

从生命史角度看，这甚至和借出一样重要：
- 借出决定“谁能被继续用”
- 驱逐决定“谁该退出”

没有这条分支，池就会越来越容易把坏连接、老连接、脏连接继续交给后面的调用方。

## 到了这里，连接后半段已经不可能再被理解成“用完放回去”了

现在再回头看最开始那个直觉：

- 用完之后 `close()`
- 连接就放回池里

看到这里，这个理解已经明显不够用了。

更准确的说法应该是：

- `close()` 只是后半链入口
- 真正重要的是后面三件事：
  1. 状态有没有被清干净
  2. 命运有没有被重新判断
  3. 最后是继续活，还是该退出

也就是说，对 HikariCP 来说，连接用完之后最重要的问题从来不是“回没回池”，而是：

**它回池之前，配不配继续作为下一轮可交付连接活下去。**

## 这篇真正立住的，不是 `close()` 这个动作，而是“连接命运判断”这条后半链

如果只从表面看，这篇很容易被讲成：

- close 会触发归还
- 归还前会 reset
- 有异常就驱逐

这种讲法当然不算错，但还是太像行为清单。

从前面整卷和本卷前一篇借出链归纳回来，更稳妥的理解方式应该是：

1. 借出链在问“这个候选连接能不能安全交付”
2. 后半链在问“这条用过的连接还配不配继续活着”
3. 清理、判断、归还、驱逐四步，共同构成了连接生命史的后半段

也就是说，这篇真正补上的，不是 `close()` 的方法细节，而是：

**HikariCP 的后半链，本质上是在判断连接的命运。**

## 这篇之后，HikariCP 最自然的继续方向是什么

到这里，HikariCP 主干卷已经把连接生命史的前半段和后半段都立住了：

- 借出链
- 归还 / 驱逐链

如果继续往下写，最自然的下一步就是：

- **ConcurrentBag 无锁并发设计**

因为到这里，读者最自然会继续追问：

- 那么池里这些候选对象到底是怎么被并发存、并发借、并发归还的
- ThreadLocal、本地缓存、共享扫描和 handoffQueue 又是怎样协同工作的

也就是说，下一篇应该顺着借还两条主线，再往下压到存储层本身。
