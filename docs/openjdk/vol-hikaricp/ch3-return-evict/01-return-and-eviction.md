# 03. 为什么 HikariCP 里的 `close()` 不等于关闭连接，而是在决定这条连接还能不能继续活着

> **前置依赖**: [02 — 一次 getConnection() 的借出链](../ch2-borrow-path/01-getconnection-borrow-path.md)：借出链交付的是代理连接，不是裸 JDBC Connection
> → **后续**: [04 — ConcurrentBag 为什么要做成三段借还结构](../ch4-concurrentbag/01-lock-free-bag-design.md)
> 关联域：05-housekeeper(后台维护)、06-validation(验证)、07-leak-detection(泄漏检测)

## 困惑：连接明明已经“用完了”，为什么 HikariCP 却还要做这么多事？

在普通 JDBC 直觉里，连接的后半段好像很简单：

```java
Connection connection = dataSource.getConnection();
// do sql
connection.close();
```

如果没有连接池，这个心智模型基本成立。`close()` 大多数时候真的意味着：

- 当前业务线程不再使用这条连接
- 驱动层释放连接相关资源
- 底层物理连接被关闭

但一旦进入 HikariCP，这个模型就立刻不够用了。因为在池化世界里，`close()` 不再只是“结束资源”，它还必须回答一连串更难的问题：

- 这条连接现在还能不能继续活着，供下一次借出使用
- 如果还能活，它身上留下的事务和连接状态怎么被清掉
- 如果不该继续活，它是在什么地方被真正驱逐
- 如果调用期间发生异常，应该把它当成一次普通 SQL 失败，还是一条连接级故障
- 如果连接已被标记驱逐，归还时是直接放回池，还是走关闭退出
- 如果泄漏检测任务已经挂上了，归还时谁负责取消

也就是说，连接在 HikariCP 里不是“用完即死”的一次性资源，而是一条被长期管理的生命体。借出是它生命史的前半段，归还与驱逐则是后半段：先解除对调用方的占用，再清理状态，再决定命运，最后要么回池复用，要么真正退场。

所以这一篇真正要回答的问题不是“`close()` 内部按顺序调了哪些方法”，而是：

**为什么在 HikariCP 里，连接用完之后不会直接结束，而必须先进入一条决定它命运的归还与驱逐链？**

## 一、三个直觉方案为什么都不理想

### 方案一：`close()` 就是关闭底层 JDBC 连接

```java
public void close() throws SQLException {
    delegate.close();
}
```

#### 为什么不行：池化世界里，这会把“复用”直接杀死

如果每次 `close()` 都真的关闭物理连接，那么前面借出链做的事情几乎全废了：

- 池内维护不再有复用意义
- `ConcurrentBag` 只是在管理一批一次性对象
- keepalive、maxLifetime、HouseKeeper 都失去前提
- 每次业务请求最终还是退化成“借一次、建一次、关一次”

#### 为什么不行：调用方不该决定物理连接的生死

在 HikariCP 里，调用方只能决定“我这轮用完了”，但不能直接决定“这条物理连接现在就该死”。连接是否继续活着，必须交还给池统一判断。

### 方案二：归还就是把连接原样放回池里

```java
public void close() {
    pool.add(this.connection);
}
```

#### 为什么不行：原样放回意味着把上一轮请求的脏状态交给下一轮

如果连接只是原样塞回池里，问题马上出现：

- 未提交事务怎么办
- `autoCommit` 被改过怎么办
- `readOnly`、隔离级别、`catalog`、`schema` 被改过怎么办
- `warnings`、打开的 statements、dirtyBits 怎么处理

连接池的复用前提，从来不是“对象还能拿到”，而是“状态已经被清回公共可用形态”。

#### 为什么不行：回池前必须重新获得“公共资源资格”

连接在借出期间是业务线程的私人物品；回池前，必须通过重置、回滚、取消泄漏任务等步骤，重新变成一个下一个线程也能安全使用的公共候选。

### 方案三：异常驱逐只是尾巴里的补丁

```java
catch (SQLException e) {
    throw e;
}
```

#### 为什么不行：异常不只是业务失败，它可能是在宣告“这条连接不配继续活着”

有些异常只是 SQL 执行失败，有些异常却意味着底层连接已经断开、协议状态已经坏掉、后续继续复用风险极高。如果不在归还链里做连接级判断，这条坏连接就可能被重新放回池，交给下一个调用者。

#### 为什么不行：驱逐判断其实是在回答“还能不能继续留在池里”

`checkException()` 之所以重要，不是因为它在异常路径里出现，而是因为它站在连接生命史的岔路口上：这次故障到底只属于当前调用，还是应该影响连接的未来命运。

## 核心设计（一句话顿悟）

**HikariCP 的 `close()` 不是“结束连接”，而是把一条已借出的私有连接重新带回池的控制范围，然后决定它是回池复用，还是被驱逐退场。**

## 总图：归还与驱逐链的完整路径

```text
ProxyConnection.close()
  → cancelLeakTask()                     [取消泄漏任务]
  → closeStatements()                    [清理打开的 Statement]
  → rollback?                            [事务状态门]
  → resetConnectionState(...)            [连接状态重置门]
  → clearWarnings()                      [连接清洁门]
  → delegate = ClosedConnection          [调用方视角关闭]
  → poolEntry.recycle()                  [回到池视角]
    → hikariPool.recycle(this)
      → isMarkedEvicted() ?              [命运门]
        → closeConnection(...)           [真正退场]
        → or connectionBag.requite(...)  [重新入池]

异常路径：
SQLException
  → checkException(...)                  [连接级故障判断]
    → 需要驱逐? evict(...) / markEvicted()
    → 不需驱逐? 保持连接继续可回池
```

这张图最关键的价值，在于把两件常被混淆的事情拆开：

- `close()` 对调用方的语义是“你已经不能再用这条连接了”
- `close()` 对连接池的语义却是“现在轮到池来判断这条连接接下来该活还是该死”

## 二、第一层：为什么 `ProxyConnection.close()` 是归还链入口，而不是终点

### 2.1 调用方调的是 `close()`，真正接住的是代理连接

`ProxyConnection.java:240`：

```java
public final void close() throws SQLException
```

这一步延续了 Ch2 的结论：调用方拿到的是代理连接，不是裸连接。所以 `close()` 被调用时，首先进入的是代理层逻辑，而不是直接进入驱动层的物理关闭。

### 2.2 代理层的任务不是“关闭物理连接”，而是重新接管控制权

归还链第一步最重要的语义变化是：控制权从调用方手里回到池手里。调用方只是在宣告“我不用了”，后续这条连接如何清理、如何重置、如何决定命运，都归池接管。

### 2.3 为什么归还链必须从代理开始，而不能从裸连接开始

如果一开始就把裸连接交给业务线程，那 `close()` 就很难被拦截成“回池”。代理的意义正在这里：它让 HikariCP 能把调用方的“关闭动作”翻译成池内部的“归还与驱逐动作”。

### 2.4 为什么“调用方视角关闭”和“池视角关闭”必须拆开

这是理解整条归还链最关键的一个认知转换。

对调用方来说，`close()` 之后这条连接就应该立刻不可再用；否则调用方还可能继续误操作同一个代理对象。

但对池来说，`close()` 之后才刚刚开始：

- 还没取消泄漏任务
- 还没回滚事务
- 还没重置连接状态
- 还没决定是回池还是驱逐

所以“调用方视角已经关闭”和“池视角已经处理完成”不是同一时刻。代理层的价值，就是把这两个时刻拆开：先让调用方这边结束，再让池内部继续处理后半链。

### 2.5 路标：归还链的入口先解决“谁接住 close()”，还没开始决定命运

到这里，只是确定了 `close()` 进入的是代理层；真正决定这条连接继续活还是退出，还在后面。而“调用方关闭”与“池内处理”这两个时间点被拆开，也正是后面所有清理和命运判断能成立的前提。

## 三、第二层：取消泄漏任务，为什么归还第一件事不是回池而是先撤销告警雷管

### 3.1 泄漏任务在借出时挂上，所以归还时必须先取消

`ProxyConnection.java:200`：

```java
void cancelLeakTask()
```

借出链里，`createProxyConnection(leakTaskFactory.schedule(poolEntry))` 会给这次借出挂上一个泄漏检测任务。归还时第一件事必须把这个任务撤掉，否则即便连接已经被正确归还，后台仍可能把它误报成泄漏。

### 3.2 为什么泄漏任务取消要早，而不是回池后再取消

因为一旦连接先回池、又很快被别的线程借走，旧的泄漏任务如果还没取消，就会把上一轮借出的上下文和下一轮借出的现实混在一起。取消动作必须尽早完成，切断上一轮借出与当前连接对象的关联。

### 3.3 泄漏检测的存在说明：池不仅关心连接对象，还关心“这条连接曾被谁拿走多久”

这件事很重要。HikariCP 管理的不只是对象池，还有“借出行为”的可观察性。`cancelLeakTask()` 看起来像个小动作，实际上是在结束一段借出行为的监控生命周期。

### 3.4 为什么“先取消泄漏任务”而不是“最后再取消”

这个顺序非常微妙。如果先做完所有状态清理、甚至已经把连接重新放回池里，最后才回头取消泄漏任务，那么在极端并发情况下，连接可能已经进入下一轮借出，而上一轮的泄漏任务却还没撤干净。这样一来，一条连接的两轮借出生命周期就会发生时间上的重叠污染。

也就是说，泄漏任务取消不只是“别误报”这么简单，它还是在做借出生命周期的时间切割：上一轮借出到这里正式结束，后面的动作全部属于归还链，而不再属于借出链。

### 3.5 路标：取消泄漏任务，是在结束“借出行为”的监控生命周期

真正的连接命运判断还没开始，但借出行为的那段计时和告警逻辑，必须先被收口。只有把上一轮借出彻底切干净，归还链后面的清理与命运判断才不会和借出链时间线搅在一起。

## 四、第三层：清理打开的 Statement，为什么 `close()` 先碰的是语句资源而不是连接本体

### 4.1 代理先关心的是“调用期间还挂着什么附属资源”

`ProxyConnection.java:222-225` 提示了一个非常现实的问题：如果连接 `close()` 时还有未清理的 statements，代理层需要先处理这批附属资源。

### 4.2 为什么 Statement 清理失败会触发连接驱逐

源码里有这样一段日志与驱逐逻辑：

```java
LOGGER.warn("{} - Connection {} marked as broken because of an exception closing open statements during Connection.close()", ...);
poolEntry.evict("(exception closing Statements during Connection.close())");
```

这说明 HikariCP 的判断非常明确：如果连“关闭本轮借出期间产生的语句资源”都发生异常，那么它更倾向于认为这条连接已经不够可信，应该被标记驱逐，而不是冒险再放回池。

### 4.3 为什么这一步会先于连接状态重置

因为如果附属资源都还没收干净，直接去重置主连接状态就像还没清桌面就直接锁门。语句资源的异常经常意味着这条连接整体状态已经不稳定，先判断它还能不能继续信任，比急着回池更重要。

### 4.4 路标：语句资源清理是在问“外围现场清完了吗”

这一步还没进入连接本体状态重置，但它已经在替后面几层做准备：只有外围语句资源先收干净，事务清理和状态重置才有稳定落点。换句话说，这一层是后面三层递进链条的起点：

- 先收外围资源
- 再清事务痕迹
- 再清连接配置状态
- 最后做命运裁决

## 五、第四层：事务状态门，为什么 `rollback()` 经常是归还链上的第一刀

### 5.1 如果本轮调用留下了未提交事务，回池前必须先清

`ProxyConnection.java:251` 附近有调试日志：

```java
LOGGER.debug("{} - Executed rollback on connection {} due to dirty commit state on close().", ...);
```

它说明归还链关心的不只是“这条连接是不是还能活”，还关心“它回池时是不是干净”。只要本轮调用把事务状态弄脏了，回池前就要先 rollback。

### 5.2 为什么 rollback 不是多余保险，而是公共资源卫生要求

因为下一轮借出拿到的应该是一条公共连接，而不是上一轮请求半途留下的事务上下文。对池化连接来说，回滚不是“帮调用方补锅”，而是在恢复公共资源卫生。

### 5.3 rollback 失败说明的就不只是业务问题，而可能是连接已坏

如果一条连接连最基本的事务回滚都做不稳，那它是否还值得继续留在池里，就要被重新怀疑。也正因为如此，事务清理与异常驱逐在归还链里天然靠得很近。

### 5.4 为什么 HikariCP 宁可在归还时付出一点清理成本，也不把风险留给下一位调用者

这是归还链一个很鲜明的价值取向：宁可在当前 `close()` 时多做一点工作，也不要把不确定性推迟给下一位借出线程。

如果把事务清理、状态恢复这些动作都延后到“下一次借出前再看情况处理”，短期内也许能让 `close()` 更轻，但代价是：

- 借出链会变得更重
- 问题暴露点会后移
- 下一位调用者会接收到更多历史尾巴

HikariCP 选择的是相反方向：尽量把这一轮留下的问题在这一轮归还时就收干净。

### 5.5 路标：事务状态门解决的是“私有事务世界有没有退出干净”

只有把私有事务痕迹清掉，连接才有资格继续往“回池复用”方向走。也正因为 HikariCP 选择在归还时收尾，而不是把问题推给下一轮借出，所以 rollback 这一步才显得如此靠前。

这也让下一层的目标更明确：事务门解决“有没有留下正在进行的事”，状态重置门解决“有没有留下被改过的配置”。两层不是重复，而是前后递进。

## 六、第五层：`resetConnectionState()` 为什么是归还链最像“清场”的一步

### 6.1 连接借出期间改过的状态，不能直接留给下一个线程

`ProxyConnection.java:255`：

```java
poolEntry.resetConnectionState(this, dirtyBits);
```

这一步的意义非常直接：把借出期间被修改过的连接状态重置回池的标准基线。

### 6.2 dirtyBits 的存在说明：不是所有状态都每次重置，而是按脏位决定

这是 HikariCP 很典型的工程取向：它不把重置写成“无脑全量恢复”，而是通过 dirtyBits 追踪借出期间到底改过什么，然后只恢复那些真的变脏的部分。

### 6.3 为什么状态重置必须发生在回池前，而不是下一次借出前

因为“回池候选”的定义就要求它已经是公共可用资源。不能把一个半脏半净的连接先塞回池，再指望下一个借出线程替你收拾残局。

### 6.4 为什么 `clearWarnings()` 这种小动作也要放在归还链里

很多人看到 `clearWarnings()` 会觉得这只是 JDBC 的边角动作，但它恰好说明了 HikariCP 的态度：一条准备回池的连接，不能只做到“勉强还能用”，而是要尽量回到一个干净、稳定、低惊讶的公共状态。

warning 本身未必会直接导致连接驱逐，但如果连 warning 都不清，下一位调用者看到的就不再是“自己的连接现场”，而是上一位调用者遗留的连接现场。

### 6.5 路标：`resetConnectionState()` 在回答“连接配置状态是不是也已经清回公共形态”

如果事务清理解决的是“有没有留下未提交工作”，状态重置解决的就是“连接配置层面还脏不脏”；而 `clearWarnings()` 这类动作，则是在补齐“公共资源观感”这一层。三者合起来，才算真正把一条私有连接清回公共世界。

也正因为前三层已经依次清了外围资源、事务痕迹和连接配置，后面的 `checkException()` 才更像真正的命运裁决：到那里要回答的不再是“哪里还脏”，而是“即便已经清理过，这条连接还值不值得继续活着”。

## 七、第六层：`checkException()` 为什么不是异常尾巴，而是命运判断门

### 7.1 归还链上的异常，最重要的不是抛不抛，而是这条连接还能不能活

`ProxyConnection.java:151`：

```java
final SQLException checkException(SQLException sqle)
```

这个方法的根本意义，不是包装异常，而是在判断这次故障是否已经上升到“连接级别”。

### 7.2 为什么要把异常分类成“业务失败”与“连接失败”

如果一次 SQL 报错只是业务约束失败、语法失败、数据失败，这并不一定意味着连接本身坏了；但如果异常显示连接断开、网络中断、协议损坏，那就不该让它继续回池。

### 7.3 `checkException()` 实际上是在做连接生命史裁决

它在回答：

- 这次异常只影响当前调用吗
- 还是已经说明这条连接不配继续待在池里

所以这不是小尾巴，而是命运门。

### 7.4 为什么 `checkException()` 放在代理层而不是池中心最后统一处理

因为最早接触到异常上下文的往往就是代理层。这个位置最接近业务调用现场，最容易看见：

- 这次异常发生在什么操作上
- 当时连接正处于什么借出上下文里
- 是否已经足以怀疑连接级故障

如果把这一步完全延后到池中心统一判断，很多贴近现场的上下文就已经丢了。代理层先做初步裁决，池中心再承接后续命运流转，这是更自然的责任分层。

### 7.5 路标：异常路径并不附属，它是在决定“这条连接还能不能继续活着”

到这里，归还链已经不只是清理动作链，而是正式进入命运判断链。`checkException()` 的位置也说明：命运判断不是只在后台发生，它可以在离业务现场最近的那一层就开始。

## 八、第七层：`PoolEntry.recycle()` 为什么不是“放回池子”，而是把命运再次交给 HikariPool

### 8.1 `ProxyConnection.close()` 的末尾不会自己决定回池还是关闭

`ProxyConnection.java:268`：

```java
poolEntry.recycle();
```

代理层到了这里，并不会直接做 `connectionBag.requite()`。它先把连接交回 `PoolEntry`，再由 `PoolEntry` 交回 `HikariPool`。

### 8.2 `PoolEntry.recycle()` 只是转交，不是终审

`PoolEntry.java:77-81`：

```java
void recycle()
{
   if (connection != null) {
      hikariPool.recycle(this);
   }
}
```

这段代码很短，但意义很大：代理层并不自己决定“现在回池还是驱逐”，而是把决定权重新交给池中心。

### 8.3 为什么终审必须回到 `HikariPool`

因为连接命运不只是这条连接自己的事，还要看整个池的策略：

- 它有没有被标记驱逐
- 池是否还开放
- 当前生命周期策略是不是要求它退场
- 后台线程是否已经对它做过标记

这些都不该由代理层单独拍板。

### 8.4 为什么 `PoolEntry` 要站在代理层和池中心之间

`PoolEntry` 的价值不是“多包一层对象”，而是给连接一个稳定的池内身份。代理层关心的是调用方语义，池中心关心的是生命周期和管理结构，`PoolEntry` 则把这两边绑定到同一个池内条目上。

也正因为如此，`recycle()` 不能直接变成一句 `connectionBag.requite()`。如果这样写，代理层就会绕开池中心的终审能力，生命周期判断也会被截断。

### 8.5 路标：`recycle()` 是把“调用方已结束”转译成“池中心接手终审”

真正的命运分叉，还在 `HikariPool.recycle(this)` 里。`PoolEntry` 正是这个转译点：它让代理层不必理解全部池策略，却仍能把连接安全地交还给池中心。

## 九、第八层：`HikariPool.recycle()` 为什么同时连着“回池复用”和“真正关闭”两条路

### 9.1 回池和驱逐不是两条完全分开的链，而是在 recycle 处汇合再分叉

`HikariPool` 侧会重新看这条连接的状态。如果它已经被标记驱逐，就不会再让它回池，而会转入真正关闭路径。

### 9.2 被标记驱逐的连接，归还时不再是“归还”，而是“带着归还动作退出”

这点很关键：对调用方来说都是 `close()`，但对池来说，两种 `close()` 后果完全不同：

- 普通连接：清理后回池
- 被驱逐连接：清理后退出

### 9.3 为什么命运分叉要发生在 recycle 之后，而不是借出时一次性决定完

因为借出后到归还前，连接状态可能继续变化：

- 借出期间被异常标记驱逐
- 借出期间触发 eviction
- 借出期间出现连接级故障

所以最终命运判断必须在归还完成前再看一遍，而不是只看借出时那一刻。

### 9.4 为什么 `isMarkedEvicted()` 的最终落点经常出现在归还时

很多驱逐动作并不是在业务线程手里那一刻就立刻完成真正关闭，而是先打标记，再等这条连接回到池中心时统一处理。这种设计的好处是：

- 不需要让每个发现问题的地方都各自负责完整退场
- 避免业务线程和后台线程同时抢着做物理关闭
- 让真正退场始终回到池中心的一致路径上

所以“被标记驱逐”和“真正关闭”不是同一时刻，这恰好体现了 HikariCP 在生命周期管理上的分层。

### 9.5 路标：recycle 之后的分叉，决定了“这条连接是回池继续活，还是归还后顺势退场”

到这里，归还链和驱逐链开始真正合并成同一张图。被标记驱逐的连接，也许在借出期间就已经注定不能继续活，但它的真正退场，仍要沿着统一归还路径收口。

## 十、第九层：`connectionBag.requite()` 为什么不是简单 `add()`，而是重新开放公共借出资格

### 10.1 真正回池时，发生的是状态转换，不是容器插入

`ConcurrentBag.java:187`：

```java
public void requite(final T bagEntry)
```

归还真正关键的动作，是把条目状态重新设回 `STATE_NOT_IN_USE`，而不是“加回某个列表”。

### 10.2 `requite()` 的本质是重新授予“候选资格”

一条连接在借出期间是 `IN_USE`，只有在归还链完成清理后，它才配重新变成 `NOT_IN_USE`。所以 `requite()` 的含义不是“塞回池”，而是“恢复成可再次借出的候选”。

### 10.3 为什么归还路径还要考虑 handoff 等待线程

如果此刻正有线程在 `handoffQueue` 等待可用连接，那么归还链不仅是在回池，也可能是在直接把这条连接移交给等待中的借出线程。也就是说，归还链和借出链在 `ConcurrentBag` 这一层是直接耦合的。

这件事非常能说明 HikariCP 的运行时风格：借出和归还并不是先后完全隔离的两段故事，而是可能在同一时刻、同一条连接上首尾相接。一个线程刚 `close()`，另一个线程就可能立刻在等待路径上接到这条连接。对连接池来说，这意味着归还动作必须足够干净、足够早地完成关键重置；否则下一位调用者接到的就不是“刚归还的热连接”，而是“还带着前一位状态尾巴的半成品”。

### 10.4 为什么 handoff 机制进一步证明“回池”不是静态存放动作

如果归还只是一句“add 回列表”，那就不会存在 handoff 这种直接移交路径。handoff 的存在说明：Bag 层从一开始就不是在管理一个静态容器，而是在管理一批持续流动的候选资格。连接可以回到公共池，也可以在归还瞬间直接跨给等待中的借出线程；真正稳定不变的不是它放在哪个列表里，而是它是否已经重新获得了公共借出资格。

### 10.5 `reserve()` / `unreserve()` 为什么和归还链属于同一世界

`ConcurrentBag.java:306` 和 `ConcurrentBag.java:318` 的 `reserve()` / `unreserve()` 看起来不像归还主线的一部分，但它们和 `requite()` 一起揭示了同一个事实：Bag 真正管理的从来不是“集合里的对象数”，而是“每个条目此刻是否还可被借、是否已被保留、是否该被移除”。

也正因为 Bag 管的是状态，归还动作才不可能退化成一句容器 `add()`。从借出到归还，条目的候选资格始终是通过状态转换而不是结构位置决定的。

### 10.5 路标：回池复用的本质不是回容器，而是重获候选身份

理解了 `requite()`，就能理解为什么 Ch4 必须单独讲：池真正管理的不是列表，而是状态。`reserve()` / `unreserve()` 则进一步说明，这套状态机不是借出链的偶然技巧，而是整个池的根基础设施。

## 十一、第十层：真正关闭路径为什么必须回到 `closeConnection()`

### 11.1 被驱逐的连接最终还是要走真正物理关闭

`HikariPool.java:457`：

```java
void closeConnection(final PoolEntry poolEntry, final String closureReason)
```

这一步才是物理连接真正退场的地方。

### 11.2 为什么真正关闭不放在代理层直接做

因为“真正关闭”不仅是调一下驱动 `close()`，还包括：

- 从池的管理结构中移除
- 记录关闭原因
- 与池中心的生命周期策略保持一致

这些都要求关闭动作回到 `HikariPool` 统一完成。

### 11.3 `softEvictConnection()` 为什么叫 soft evict

`HikariPool.java:626`：

```java
private boolean softEvictConnection(final PoolEntry poolEntry, final String reason, final boolean owner)
```

这里的 “soft” 不是“温和一点驱逐”的修辞，而是分层机制本身：**先打标，再沿统一链路退场。**

也就是说，soft evict 不是否认真正驱逐，而是在把“发现这条连接不该继续活”与“真正把它物理关闭并移出池”拆成两个阶段：

- 第一阶段：先把命运裁决做出来（标记应该退场）
- 第二阶段：再根据它当前是否仍被持有、是否已经归还，沿统一路径进入 `closeConnection()`

这样做的价值是很具体的：

- 不需要每个发现问题的地方都自己完成整套物理退场
- 避免业务线程和后台线程在同一条连接上抢执行终结动作
- 让真正退场始终回到池中心的统一路径上

所以 soft evict 的关键，不是“温和”，而是“分层收口”。这也是它和本文主线完全一致的地方：连接命运可以先被判定，真正死亡则统一收口。

### 11.4 为什么真正关闭必须和“关闭原因”绑在一起

`closeConnection(poolEntry, closureReason)` 里最容易被忽略的是 `closureReason`。这不是日志修饰品，而是在给一条连接的退场留下可追踪的死因：

- 是被用户主动驱逐
- 是 passed maxLifetime
- 是 passed idleTimeout
- 是被判定 dead connection
- 还是归还链上的异常收口

对长期运行的池来说，连接不只是会死，还要知道“是怎么死的”。否则后续排障只能看到池在掉连接，却看不懂掉的是哪一类连接。

### 11.5 路标：真正关闭路径是在说“连接的生命，最后在哪里结束”

如果前面的步骤都在问“还能不能继续活”，那 `closeConnection()` 就是在执行最后判决。而 `closureReason` 让这个判决不仅发生了，还留下了可追溯的历史。

## 十二、失败路径：如果归还与驱逐链少掉某一门，会坏在哪里

### 12.1 没有取消泄漏任务，正常归还会被误报成泄漏

源码锚点：`ProxyConnection.java:200`

后果：监控噪声激增，真正泄漏与已归还连接混在一起。

如何避免：归还动作一开始就取消对应的泄漏任务，不让旧借出上下文残留到回池之后。

### 12.2 没有 rollback/状态重置，下一轮拿到的是上一轮的脏连接

源码锚点：`ProxyConnection.java:251`、`ProxyConnection.java:255`

后果：跨请求事务污染、连接属性污染、问题极难排查。

如何避免：把事务清理和状态重置都放在回池前完成，而不是把脏连接先塞回池。

### 12.3 没有 `checkException()`，坏连接会伪装成普通归还连接

源码锚点：`ProxyConnection.java:151`

后果：本应退场的连接重新回池，下一位调用者替上一位踩雷。

如何避免：异常路径必须显式做连接级判断，而不是把所有 `SQLException` 都当成业务层问题抛掉了事。

### 12.4 没有 recycle 分叉，驱逐和复用会被混成同一种 close

源码锚点：`PoolEntry.java:77`

后果：被标记驱逐的连接仍可能被正常回池，生命周期策略彻底失效。

如何避免：把命运终审放回 `HikariPool.recycle()`，不要让代理层单独决定回池或关闭。

### 12.5 没有 `requite()` 的状态回切，连接会“消失在池外”

源码锚点：`ConcurrentBag.java:187`

后果：连接既没真关闭，也没恢复成 `NOT_IN_USE`，池可用连接数会慢慢掉光。

如何避免：归还链最后必须把状态切回公共候选态，确保这条连接重新进入可借出世界。

### 12.6 没有 `closeConnection()` 统一退场点，连接死亡会四处分散

源码锚点：`HikariPool.java:457`

后果：真正物理关闭散落在多个位置，池中心失去对连接退场的一致管理。

如何避免：把真正关闭统一收口到池中心，由 `closeConnection()` 负责最终退场。

### 12.7 没有 `closureReason`，连接会死得不明不白

源码锚点：`HikariPool.java:457`

后果：池虽然在掉连接，但排障时很难分辨到底是空闲超时、寿命到期、主动驱逐、死连接回收还是归还链上的异常收口。

如何避免：让每次真正退场都带着明确原因进入 `closeConnection()`，把连接死亡历史也纳入池的可观察范围。

## 十三、收网：为什么 `close()` 真正做的不是“关闭”，而是“重新判命”

| 章节 | 核心收获 |
|------|---------|
| 困惑开场 | 调用方以为自己在“关闭连接”，池其实才刚开始接手判命 |
| 三个方案 | 真关物理连接、原样回池、忽略异常驱逐都不成立 |
| 代理入口 | 归还链先回答“谁来接住 close()”，并拆开“调用方关闭”与“池内处理” |
| 泄漏任务 | 先结束借出行为监控，再谈回池 |
| Statement 清理 | 先清外围资源，再碰连接本体 |
| 事务状态门 | rollback 负责把连接从私有事务世界带回公共世界 |
| 状态重置门 | dirtyBits 驱动按需恢复连接公共形态 |
| 命运门 | `checkException()` 判断这条连接还能不能活 |
| recycle 分叉 | 归还与驱逐在池中心汇合后再分路 |
| requite/handoff | 真正回池的本质是恢复候选资格，甚至可能直接把连接交给等待线程 |
| closeConnection | 真正死亡统一收口到池中心，并带着 closureReason 留下死因 |
| 失败路径 | 归还链最怕的不是慢，而是带着脏状态或坏命运重新回池 |

现在再回头看标题“为什么 `close()` 不等于关闭连接”，答案已经清楚了：

- 对调用方，`close()` 的语义是“你不能再用它了”
- 对池，`close()` 的语义却是“现在轮到我来判断它还能不能继续活”

所以归还链的核心价值，不是把连接放回去，而是先把它从“业务线程的私人物品”重新清成“池内公共候选”；如果清不干净，或者命运判断认定它不该再活，就顺势把它导向驱逐与真正关闭。

换句话说，`close()` 在 HikariCP 里真正做的不是“关闭连接”，而是**重新判命**：是继续活着留在池里，还是在这次归还中正式退场。

如果把这一篇和 Ch2 连起来看，借出链回答的是“候选怎样被安全交给调用方”，归还链回答的则是“调用方放手之后，连接怎样重新回到池的控制范围内”。两篇合起来，连接从借出到归还这条完整闭环才真正成立。

也正因为闭环已经出现，读者才会自然意识到：这套系统的真正难点从来不是 `getConnection()` 或 `close()` 这两个表面 API，而是 API 背后那套持续流动的状态机。借出时是 `NOT_IN_USE → IN_USE`，归还时则要么回到 `NOT_IN_USE`，要么转向驱逐与移除。到这里，“连接池不是容器，而是状态机”这句总判断就不再只是观点，而是已经在源码级链路里落地了。

再往前多走一步看，这也是 HikariCP 为什么会被认为“快”的一个更底层原因：它并不是单靠某个微优化变快，而是把借出、归还、驱逐、复用这些常见路径都提前收敛进一套稳定状态机里。状态越稳定，额外判断越少；额外判断越少，热路径才越短。于是所谓性能，最后又回到了结构质量上。
