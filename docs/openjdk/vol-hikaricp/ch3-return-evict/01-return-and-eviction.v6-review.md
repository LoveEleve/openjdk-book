## 三、六层深审

### 1. 主题层

优点：

- 标题、困惑开场和收网高度一致，始终围绕“close() 不等于真正关闭连接”
- 核心冲突很鲜明：调用方视角已关闭，池视角才开始判命
- 这组张力已经成为全篇最有辨识度的主轴

问题：

- 个别中段仍然带一点“展开清单”的味道，虽然信息完整，但主线张力有时会被技术点稀释

建议：

- 后续如果再压结构，可继续围绕“调用方关闭 vs 池内判命”这组冲突来统一中段节名

### 2. 结构层

优点：

- 现在已经具备较完整的递进感：
  - 先收外围资源
  - 再清事务痕迹
  - 再清连接状态
  - 最后做命运裁决
- `softEvictConnection()` 的分层机制也已被明确解释，不再只是术语点到为止

问题：

- 二级节、三级节数量依然偏多，仍带有“深补后切得很细”的痕迹
- 和 Ch1、Ch2 一样，还不是 vol-02 那种最自然、最稳的节边界状态

建议：

- 暂不建议继续在本篇内部反复切分节名；更适合等 Ch4-Ch5 落地后统一做一轮卷内结构收束

### 3. 事实层

优点：

- 关键源码描述与锚点当前保持一致
- `ProxyConnection.close()`、`checkException()`、`PoolEntry.recycle()`、`requite()`、`closeConnection()`、`softEvictConnection()` 的分工都没有发现硬事实错误

风险点：

- 如果后续继续大幅扩写 `checkException()` 的异常分类细节，需要重新核具体异常分支源码，避免从总判断滑向未经核实的细节结论

### 4. 解释层

优点：

- 现在已经不只是“按顺序解释 close() 里调用了哪些方法”，而是在解释“这些步骤为什么要按这个顺序出现”
- `softEvictConnection()` 已经从“温和驱逐”的模糊比喻，修正为“先打标、再沿统一链路退场”的分层机制说明，这一点很关键

问题：

- 少数地方仍然偏总结，比如对 `PoolEntry` 的身份角色解释，还能再绑定一层运行时场景

建议：

- 后续如果继续打磨，可再增加一小段“为什么代理层不能绕过 PoolEntry 直接 requite”的对照场景

### 5. 失败路径层

优点：

- 已覆盖泄漏任务、事务污染、异常误判、回池分叉、状态回切、统一退场点、closureReason 七类故障面
- 失败路径和正文主线一致，已经不是独立附录，而是正文的反面镜像

问题：

- 个别失败路径仍可再压缩成更统一的模板，但不影响当前达标判断

建议：

- 后续卷写作时，优先直接按“源码控制点 → 后果 → 避免动作”固定模板写，减少后补整形成本
