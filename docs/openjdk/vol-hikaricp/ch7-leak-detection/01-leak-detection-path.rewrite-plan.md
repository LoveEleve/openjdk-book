## 一句话困惑

为什么一条连接一旦借出去迟迟不还，HikariCP 不是立刻知道，而是要借助 `ProxyLeakTask` 这种延迟检测机制？它到底在借出时埋了什么、归还时又取消了什么？

## 一句话顿悟

HikariCP 的泄漏检测本质上不是“池里凭空发现泄漏”，而是：**在借出时给这条连接挂一个定时告警任务，只要它超过阈值还没回到后半链，就把借出当时的调用栈和对象身份翻出来。**

## 读者理解路径

1. 从“为什么泄漏检测不能靠池里轮询就发现”切入。
2. 建立最小总图：`borrow -> schedule leak task -> connection in use -> close cancels task -> timeout triggers warning`。
3. 解释为什么泄漏检测入口在借出链，而不是归还链或后台 HouseKeeper。
4. 解释 `ProxyLeakTask` / `ProxyLeakTaskFactory` 为什么是整条诊断链的核心。
5. 解释“泄漏检测”并不是回收连接，而是定位“谁把它借走后忘了还”。
6. 最后收束：泄漏检测是连接生命史的诊断分支，而不是普通超时检查。

## 失败方案推演

### 失败方案一：池里定时扫一下谁没回来就行了

这个想法看起来很自然，因为池本来就在管理连接。

问题在于，池当然能看到“谁还在 in-use”，但它如果想告诉你“到底是谁借走没还”，就不能只靠当前状态，还必须保留：
- 借出时机
- 借出时的调用栈
- 关联的代理连接

也就是说，泄漏检测不是静态盘点，而是要在借出时就埋好诊断线索。

### 失败方案二：连接泄漏检测就是超时检查的一种别名

超时和泄漏看起来很像：
- 都和时间有关
- 都说明某个连接长时间没有回来

但它们解决的问题不同：
- 超时更像借出失败时的调用方等待边界
- 泄漏检测更像“已经借出去的连接，谁持有太久没还”

所以泄漏检测不是借出超时的重复，而是借出后的诊断支线。

### 失败方案三：发现泄漏就说明 HikariCP 会自动帮你恢复

这个误解也很危险。

HikariCP 的泄漏检测首先做的是：
- 告警
- 定位调用栈
- 提醒这条连接借出太久

它不是自动修复系统的魔法。真正的根因仍然可能在：
- 应用代码没按时 close
- 事务边界异常
- 外部调用把连接长时间持有

所以泄漏检测首先是诊断能力，不是恢复能力。

## 必须澄清的误解

1. 泄漏检测不是池内轮询，而是借出时埋诊断任务。
2. 它不是“超时检查的另一个名字”，而是借出后的诊断分支。
3. `close()` 取消泄漏任务这一点，和借出时创建泄漏任务一样关键。
4. 泄漏检测主要解决“谁借了不还”，不是“池替你自动修复一切”。
5. 本篇讲的是诊断链，不是指标/JMX 总览。
