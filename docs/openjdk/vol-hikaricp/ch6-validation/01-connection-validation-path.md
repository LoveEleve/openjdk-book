# 为什么 borrow 成功了，连接却还不能立刻交给调用方：HikariCP 的连接验证主线

> 本文基于 HikariCP 7.0.2 当前源码。本文只讲“借出前的可交付性判断”：为什么在 HikariCP 里，一条连接即使已经从 `ConcurrentBag` 里借出来了，也还要继续经过驱逐判断、活性判断、可能的 `beginRequest()`，最后才会被包装成代理连接交给调用方。本文不重讲 HouseKeeper、keepalive、泄漏检测和指标监控，而是把视角收在“候选对象怎样变成可交付连接”这一刻上。

## 为什么 `borrow()` 已经成功了，池却还不能立刻把连接交出去

在前面几篇里，我们已经把连接生命史的主骨架搭起来了：

- `HikariConfig` 定义连接这一生的策略边界
- `HikariDataSource` 是应用进入池世界的入口
- `HikariPool` 是运行时中心
- 借出链决定候选对象怎样变成可交付连接
- 归还链决定一条用过的连接是继续活着还是退出
- HouseKeeper 则在后台继续管理连接的余生

如果只从这个大图看，借出链里最醒目的动作往往是：

- `ConcurrentBag.borrow()`

于是很容易形成一个直觉：
- 能借到对象，说明池里已经找到了可用连接
- 找到了可用连接，那不就该直接交给调用方了吗？

这个直觉的问题在于，它把“有候选对象”误当成了“已经通过交付资格审查”。

在 HikariCP 里，这两者并不是一回事。

因为一条连接即使此刻还放在池里、还能被借出来，也并不自动说明：

- 它没有被标记驱逐
- 它没有在空闲期里悄悄死掉
- 它不需要做额外的请求边界准备
- 它现在就适合被安全交给新调用方

也就是说，`borrow()` 成功说明的是：
- 池里给你找到了一个候选连接

但 HikariCP 真正还要继续回答的是：
- **这个候选连接，现在是否值得继续活着并被交付？**

所以，本文真正要回答的问题不是“连接验证有哪些配置项”，而是：

**为什么在 HikariCP 里，借到对象不等于交付成功，而必须再走一整段可交付性判断链？**

## 先看失败方案：为什么不能把连接验证理解成“可选 ping”

### 失败方案一：`borrow()` 成功了，说明连接当然可用

这是最自然的第一反应。

因为从池存储层看，`borrow()` 至少已经说明了一件事：
- 有对象从 `NOT_IN_USE` 切到了 `IN_USE`

如果只停在这个层次，这个结论好像也没什么问题。

但它漏掉了一个非常关键的事实：
- 池状态和连接状态不是一回事

也就是说，一个连接可能在池内部结构上仍然是“可借的候选对象”，但在物理连接语义上已经不适合继续交付。

例如：
- 它已经被标记驱逐
- 它在空闲期里已经死掉
- 它需要在交付前再执行请求边界动作

所以 `borrow()` 解决的是“有没有候选者”，不是“候选者现在能不能直接上场”。

### 失败方案二：最安全的做法就是每次借出都完整验证一次

这个思路也很直观，因为它看起来最稳：
- 每次借出前都做一次完整活性检测
- 坏连接就不会混进去了

问题在于，连接验证本身也是成本。

对于连接池来说，这意味着一个更尖锐的平衡：
- 如果每次都严格全量检测，借出链会变重
- 如果一点都不检测，又可能把坏连接交出去

所以 HikariCP 这里并不是在问“要不要验证”，而是在问：

- **在哪些情况下必须验证**
- **在哪些情况下可以安全跳过验证**

这就是 `aliveBypassWindow` 这类设计真正有意义的地方。它不是偷懒，而是在高频借出路径上做“正确性和成本”的平衡。

### 失败方案三：验证只是附属细节，真正主线还是借出和归还

如果只把验证看成借出链上的一个小插曲，很容易低估它的位置。

因为从连接生命史角度看，验证其实是在做一件非常核心的事：

- 它决定这条连接是继续活着，还是在借出前这一刻就应该被淘汰

也就是说，它不是附属细节，而是：
- 借出链上的命运判断点

如果没有这一层，池就只能“谁先借到谁就拿走”；有了这一层，池才能说“不是谁借到谁都配被交付”。

## 候选连接到可交付连接的最小总图

如果把 HikariCP 的连接验证主线先压缩成最小模型，它可以写成下面这样：

```text
ConcurrentBag.borrow()
   -> evict check
   -> alive check / bypass
   -> beginRequest (optional)
   -> createProxyConnection(...)
   -> returned to caller
```

如果再换一种更容易理解的拆法，这条线可以分成三段：

```text
[候选阶段]
borrow() gives a candidate

   ->

[过筛阶段]
evict / alive / request boundary checks

   ->

[交付阶段]
proxy connection returned to caller
```

这张图最重要的价值，不是让读者背方法名，而是先把三个问题分开：

### 一、候选阶段
回答：对象是怎么先被借出来的？

### 二、过筛阶段
回答：为什么候选对象还不能直接交付？

### 三、交付阶段
回答：什么情况下，它才真正算当前调用方可安全使用的连接？

只要先把这三段分开，验证为什么这么重要，就不再像“多做一步检查”。

## 一、第一道门：是不是已经被标记驱逐了

一条候选连接被借出来之后，第一件要问的事，并不是“马上交付”，而是：

- 它是不是其实已经不该继续活着了？

这就是驱逐判断会最先出现的原因。

在 HikariCP 的借出链里，这个判断非常靠前：

证据：`com/zaxxer/hikari/pool/HikariPool.java:166`

这说明什么？说明对池来说，候选对象的“可借”状态并不自动覆盖它的“可继续存活”状态。

也就是说，池内部存在两层不同问题：
- 结构上能不能借到
- 生命史上还配不配继续活着

只要它已经被标记驱逐，就算这次 `borrow()` 把它拿到了，它也不应该再被交付出去。

所以驱逐判断不是异常尾声，而是验证主线的第一道门。

## 二、第二道门：它是不是已经悄悄死掉了

即使一条连接没有被显式标记驱逐，也不代表它现在仍然可靠。

因为对连接池来说，还有一种更隐蔽的风险：
- 连接看起来还在池里
- 但底层其实已经死掉了

这就是 `isConnectionDead(...)` 这类判断存在的原因。

而在 HikariCP 当前实现里，活性检查并不是每次都无脑执行，它会先看一个窗口：

- `aliveBypassWindowMs`

证据：`com/zaxxer/hikari/pool/HikariPool.java:62`
证据：`com/zaxxer/hikari/pool/HikariPool.java:166`

这两处放在一起，很能说明问题：

- 如果连接刚被归还不久，就可以先跳过验证
- 如果已经过了旁路窗口，就需要认真判断它是不是已经死了

所以 HikariCP 在这里并不是“要不要验证”的二元决策，而是在做三层判断：

1. 是否已经被驱逐
2. 是否还在旁路窗口内
3. 如果不在旁路窗口内，是否真的已经失活

也正因为如此，`aliveBypassWindow` 不是简单优化参数，而是借出链在高频路径上做成本与正确性平衡的关键节点。

## 三、`PoolBase.isConnectionDead()`：为什么真正的验证落点不在池表面，而在池基础层

一旦候选连接需要做活性检查，真正的落点并不在外层 API，而是在池基础层：

- `PoolBase.isConnectionDead()`

这个位置很重要，因为它说明连接验证并不是一个“接口层的小补丁”，而是池基础能力的一部分。

方法级锚点也很明确：
- `PoolBase.isConnectionDead(...)`: `com/zaxxer/hikari/pool/PoolBase.java:157`
- 先设置 `networkTimeout`：`PoolBase.java:160`
- 如果 `isUseJdbc4Validation` 为真，就走 `connection.isValid(...)`：`PoolBase.java:164`
- 否则执行 `connectionTestQuery`：`PoolBase.java:168`、`173`
- 最后再把 `networkTimeout` 还原：`PoolBase.java:177`

也就是说，对 HikariCP 来说，验证不是某个配置加上去的外挂，而是连接生命史本来就必须拥有的一段判断能力。

从结构上看，这一步回答的是：

- 当前这条连接还能不能继续承担下一轮借出责任

所以它和驱逐判断并列在同一个层次上：
- 都在决定“这条候选连接是否值得继续活着并被交付”

## 四、`beginRequest()`：为什么在交付前还要有最后一道请求边界动作

即使驱逐和活性检查都通过了，借出链也还没结束。

如果启用了 request boundaries，HikariCP 还会在真正交付前执行：
- `beginRequest()`

证据：`com/zaxxer/hikari/pool/HikariPool.java:174`

这一点之所以重要，不在于这个调用本身很复杂，而在于它提醒我们：

- 借出成功不只是“对象拿到了”
- 还要让这条连接在当前请求边界上进入正确状态

也就是说，连接交付给调用方之前，不只是“池确认它没坏”，还要确保它已经站在一个适合开始服务新请求的边界上。

所以 `beginRequest()` 的位置非常耐人寻味：
- 它既不属于前面的候选获取
- 也不属于最后的代理交付
- 它就卡在“通过筛选后、正式交付前”这一道门上

这说明 HikariCP 对交付时刻的控制，比“验证通过就交出去”还要更细一层。

## 五、为什么最后必须是代理交付，而不是把底层连接直接扔出去

即使前面的过筛全都通过了，真正的交付动作也还不是“把底层连接扔出去”。

最后一层真正决定交付完成的，是：
- `createProxyConnection(...)`

证据：`com/zaxxer/hikari/pool/HikariPool.java:179`

这一步的重要性在于，它再次确保：

- 调用方拿到的不是裸连接
- 池的控制权不会在交付那一刻断掉

因为只有通过代理连接，后面很多事情才能继续被池接住：

- close 重新走回归还链
- 状态重置重新回到池控制中
- 异常和驱逐判断仍然可以继续作用于这条连接

所以从借出主线看，真正的完成时刻不是“候选对象通过验证”，而是：

**候选对象已经被包装成池可继续控制的代理连接，并安全交到了调用方手里。**

## 到了这里，连接验证已经不可能再被理解成“顺手 ping 一下”了

现在再回头看很多人对连接验证的直觉：

- 借之前 maybe ping 一下
- 通过就交出去

看到这里，这个理解已经明显太浅了。

更准确的说法应该是：

- 验证不是附加动作
- 它是候选连接到可交付连接之间的一整道安全门

也就是说，HikariCP 真正关心的不是“有没有做一次检查”，而是：

- 这个候选对象有没有通过完整的交付资格审查

这也是为什么验证主线会同时牵扯：
- 驱逐状态
- alive 检查
- bypass 窗口
- request boundary
- 代理交付

所以，这一篇真正补上的，不是几个参数或几个 if，而是：

**借出链中的可交付性判断，是一条完整的过筛链。**

## 这篇真正立住的，不是“连接测试”，而是“可交付性判断”这个概念

如果只从表面看，这篇很容易被讲成：

- 借之前要检查连接
- 不活就丢掉
- 活着就给出去

这种讲法当然不算错，但还是太像连接测试配置说明。

从前面整卷主线归纳回来，更稳妥的理解方式应该是：

1. borrow 只给出候选对象
2. 候选对象还要继续过筛
3. 驱逐、活性、请求边界、代理交付共同构成交付资格审查
4. 所以 HikariCP 的连接验证，本质上是在判断“它值不值得继续被交付”

也就是说，这篇真正补上的，不是一个 ping 步骤，而是：

**连接验证其实是在保护借出链的正确性交付。**

## 这篇之后，HikariCP 最自然的继续方向是什么

到这里，HikariCP 主干层已经从：
- 总骨架
- 借出链
- 归还/驱逐链
- 并发协作
- 生命周期后台维护

继续补到了：
- 借出前的可交付性判断

如果继续往下写，最自然的下一步就是：
- **连接泄漏检测**

因为到这里，连接的借、还、活、筛都已经讲清楚了；接下来最自然的问题就是：

- 如果一条借出去的连接迟迟不归还，池是怎么发现这件事的
- 这条生命史怎么被诊断、怎么被告警
