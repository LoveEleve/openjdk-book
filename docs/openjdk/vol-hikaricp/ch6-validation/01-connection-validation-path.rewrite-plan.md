## 一句话困惑

为什么 HikariCP 在借出连接时，不是“Bag 里有一个对象就直接给出去”，而还要额外判断它是不是被驱逐了、是不是还活着、是否可以跳过验证、是否要调用 `beginRequest()`？

## 一句话顿悟

HikariCP 借出的不是“池里碰巧拿到的对象”，而是**一条经过可交付性判断的候选连接：它必须证明自己没有被驱逐、没有悄悄死掉、并且在当前边界下值得继续交给调用方。**

## 读者理解路径

1. 从“为什么 borrow 成功不等于可以立刻交付”切入。
2. 建立最小总图：`borrow -> evict check -> alive check / bypass -> beginRequest (optional) -> proxy handoff`。
3. 解释 `aliveBypassWindow` 为什么存在，为什么 500ms 旁路不等于偷懒。
4. 解释 `isConnectionDead()` 为什么不是简单 ping，而是连接验证策略的真正落点。
5. 解释 `beginRequest()` 为什么放在交付前最后一段。
6. 收束到：连接验证不是“额外检查”，而是候选对象到可交付对象之间的安全门。

## 失败方案推演

### 失败方案一：能从 Bag 里借到对象，就说明连接可用

这是最自然的误解，因为 `borrow()` 已经意味着：
- 这个对象从池内可用状态切到了 in-use

但这只能说明：
- 有候选对象

并不说明：
- 候选对象当前还活着
- 它还没被标记驱逐
- 它值得继续交付

所以 borrow 成功只是进入候选阶段，不是通过交付阶段。

### 失败方案二：每次借出都全量做一次活性检测最安全

这看起来最稳，因为可以避免把坏连接交出去。

问题在于，连接验证本身也有成本。如果每次都无脑全量检查，会把高频借出路径拖重。

所以 HikariCP 不是“要不要验证”二选一，而是在做一个平衡：
- 既不能把坏连接交出去
- 也不能让验证把所有借出都拖慢

### 失败方案三：验证只是连接池的附属细节，不构成独立主线

这个理解会低估连接验证在 HikariCP 里的地位。

因为连接借出链前面讲的是“拿到候选对象”，后面讲的是“交付代理连接”，而验证正好卡在中间，决定：
- 这条候选连接是继续活着
- 还是就在这里被淘汰

它其实是连接命运判断在借出时刻的即时执行点。

## 必须澄清的误解

1. `borrow()` 成功不等于连接已经可交付。
2. 连接验证不是附属 ping，而是借出安全门。
3. `aliveBypassWindow` 不是偷懒，而是性能与正确性平衡策略。
4. `beginRequest()` 不是可有可无的尾巴，而是交付前最后一道请求边界动作。
5. 本篇讲的是借出前的可交付性判断，不是 keepalive/HouseKeeper 的后台维护。
