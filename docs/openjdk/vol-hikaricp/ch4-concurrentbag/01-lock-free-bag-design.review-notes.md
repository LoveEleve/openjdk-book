# HikariCP Ch4-01 ConcurrentBag 无锁并发设计 — review notes

## 第一轮：事实审

### 目标
核对：
- `ConcurrentBag` 是否被准确定位为借还协作协议，而不是普通容器
- `ThreadLocal` / `sharedList` / `handoffQueue` / 状态机相关描述是否与源码一致
- `file:line` 引用是否真实存在

### 当前需核对的关键锚点
- `ConcurrentBag` 类定义
- `borrow()`
- `requite()`
- `reserve()` / `unreserve()`
- ThreadLocal 本地缓存
- `sharedList`
- `handoffQueue`
- `IConcurrentBagEntry` 状态定义

### 初步判断
- 当前主线与 Ch4 规划一致：本地命中 -> 共享扫描 -> handoff 移交
- 没有把 `ConcurrentBag` 写成普通集合类，这是对的
- 当前最大事实风险在于：状态机（`NOT_IN_USE/IN_USE/RESERVED/REMOVED`）和 `requite()` 的方法级锚点还没有补齐

## 第二轮：因果审

### 目标
检查正文中所有“为什么 BlockingQueue 不够”“为什么三层必须并存”“为什么它是在管理协作而不是存放”这类判断，是否由源码结构支撑。

### 当前因果链
1. `BlockingQueue` 不能同时表达本地命中、共享可见和等待移交三层协作
2. `ThreadLocal` 不是附属缓存，而是快路径的一部分
3. `sharedList` 不是全局真相，而是第二层可见性结构
4. `handoffQueue` 是等待线程和归还线程之间的移交层
5. 状态机比容器本身更重要，因为它决定对象在借/还/保留/移除中的安全性

### 当前风险
- 这些结论方向是对的，但需要用 `borrow()` / `requite()` / `reserve()` 的具体路径来压实，不然容易显得像并发设计经验总结
- “无锁”这个词必须谨慎，不能写得像完全无协调；应持续保持“减少全局竞争、分层协作”这条语气

## 第三轮：结构审

### 目标
检查结构是否遵守“困惑 -> 失败方案 -> 总图 -> 并发协作拆解 -> 收网”的方法论，而不是退化成数据结构介绍。

### 当前结构评价
当前结构是：
1. 困惑开场
2. 失败方案
3. 最小总图
4. `ConcurrentBag` 在解决什么
5. `borrow()`
6. 三层结构并存原因
7. 状态机
8. 为什么减少争用
9. 收网总结
10. 下篇桥接

### 当前结构优点
- 没有退化成类图或字段说明书
- 先立“协作协议”总概念，再讲 ThreadLocal/shared/handoff 三层
- 与前后两篇借出/归还主线衔接很自然

### 当前结构风险
- 如果后续补源码时三层结构写得太散，会把“协作协议”主概念冲淡
- 状态机一节目前权重较轻，若不补硬锚点会削弱本篇的技术重心

### 当前读者收益

- 为什么 `ConcurrentBag` 不是普通队列
