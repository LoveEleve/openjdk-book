# 为什么 HikariCP 还要单独做一套 metrics：连接生命史的持续观测面

> 本文基于 HikariCP 7.0.2 当前源码。本文不把 metrics 写成一个监控接入手册，也不把它写成“有几种实现”的清单，而是专门解释：为什么在借出、归还、驱逐、后台维护、泄漏检测和 JMX 控制面都已经存在之后，HikariCP 还必须再单独建立一套持续量化的观测面。本文关注的不是图表怎么接，而是：连接生命史里哪些关键阶段被量化、为什么要统一抽象、又为什么 JMX 和 metrics 不能互相替代。

## 为什么连接池已经会跑、会报警、会被 JMX 看见了，却还不够

前面几篇已经把 HikariCP 讲成了一个很完整的运行时系统：

- 配置定义了连接生命史的边界
- 池中心负责借出、归还和驱逐
- ConcurrentBag 负责高并发借还协作
- HouseKeeper 负责连接余生的后台维护
- 泄漏检测能把借出去太久不还的连接追出来
- JMX 还能把池暴露成一个可运行时观察和控制的系统

如果只看这些能力，连接池似乎已经具备了：
- 运行能力
- 诊断能力
- 管理能力

那为什么还要再单独做一套 metrics？

这恰恰说明了日志、JMX 和 metrics 三者不是同一种东西。

- **日志** 擅长记录离散事件
- **JMX** 擅长暴露状态和有限控制
- **metrics** 擅长把运行中的关键变化持续量化成外部系统能采集、聚合、告警的时间序列信号

也就是说，日志能告诉你“刚才发生了什么”，JMX 能告诉你“现在状态怎样”，而 metrics 更关心：

- 一段时间里连接等待在变长还是变短
- 使用时长分布在变差还是变好
- 超时次数是不是持续上升
- 池的活跃/空闲状态是不是长期偏移了某个边界

所以 metrics 在 HikariCP 里不是“再多加一套观测接口”，而是把连接生命史从“可以事后看”“可以此刻看”，进一步推进到了“可以持续量化地看”。

本文真正要回答的问题不是“怎么接 Micrometer”或者“Prometheus 有哪些指标名”，而是：

**为什么对 HikariCP 来说，连接生命史不只要能被管理和诊断，还必须能被持续量化地观察？**

## 先看失败方案：为什么不能把 metrics 理解成“顺手多几个数字”

### 失败方案一：有日志和 JMX 就够了，不需要单独的 metrics

这是最自然的第一反应。

因为前面两条线看起来已经很强：
- 有问题时，日志会报
- 想看状态时，JMX 能看

看起来好像已经具备了“排障”和“观察”的全部能力。

问题在于，这两者都不擅长回答同一个问题：

- **一段时间里，这个池的运行趋势在怎么变化？**

日志是事件性的：
- 某次初始化失败了
- 某条连接泄漏了
- 某次生命周期边界被触发了

JMX 是瞬时性的：
- 此刻有多少活跃连接
- 此刻有多少等待线程
- 此刻配置长什么样

但线上最关键的很多判断，其实依赖的是时间序列：
- 获取连接的等待时间是不是持续变高
- 连接使用时间是否拉长
- 超时是不是偶发，还是在连续堆积
- 池状态是不是在慢慢偏到危险边界

也就是说，日志和 JMX 虽然都重要，但它们天然不能完全替代持续量化观测。

### 失败方案二：metrics 就是多加几个计数器，没什么主线可讲

这个理解特别容易让一篇源码文直接塌成“指标清单”。

因为表面上看，metrics 好像确实只是：
- 记录几个耗时
- 加几个计数
- 暴露几个 gauge

问题在于，HikariCP 量化的并不是任意数字，而恰恰是连接生命史里最关键的几个阶段：

- 连接创建有多慢
- 借出等待有多慢
- 连接使用持续了多久
- 超时发生了多少次
- 当前池状态快照是什么

这些都不是随便挑的，而是在回答：

**连接生命史里，哪几个阶段最值得被持续量化。**

所以 metrics 的主线不是“数字多不多”，而是“它到底在量化连接生命史的哪些关键节点”。

### 失败方案三：Dropwizard、Micrometer、Prometheus 三套实现才是重点

第一次看到 HikariCP 的 metrics 目录时，很容易被不同实现吸引：
- Dropwizard
- Micrometer
- Prometheus

看起来好像“选哪个接法”就是主题本身。

这个理解会把读者很快带偏。

因为从源码主线看，真正重要的不是“最后接哪个平台”，而是：

- 池内部先如何定义统一的观测点
- 再由不同实现把这些观测点翻译给不同外部系统

也就是说：
- 具体平台实现是外壳
- 统一观测抽象才是主线

如果一上来就沉进平台差异，这一篇就会从源码机制文变成接入文档。

## HikariCP 观测面的最小总图

如果把 HikariCP 的 metrics 主线先压缩成最小模型，它可以写成下面这样：

```text
pool events / pool state
   -> metrics tracker abstraction
   -> pool stats snapshot
   -> external metrics implementation
```

如果再换一种更容易理解的拆法，这条线可以分成三段职责：

```text
[生命史事件]
creation / borrow wait / usage / timeout

   ->

[统一观测抽象]
IMetricsTracker / MetricsTrackerFactory

   ->

[状态快照与外部输出]
PoolStats + Dropwizard/Micrometer/Prometheus
```

这张图最重要的价值，不是让读者先记住几个类名，而是先把三个问题分开：

### 一、生命史事件
回答：连接池里到底哪些阶段最值得被持续量化？

### 二、统一观测抽象
回答：为什么要先定义一套中立指标接口，而不是直接绑死某个平台？

### 三、状态快照与外部输出
回答：池当前状态怎样被定期采样，并通过不同实现暴露给外部系统？

只要先把这三段分开，metrics 就不再像“顺手多加的数字”。

## 一、连接生命史里最值得被量化的，不是“所有东西”，而是几个关键阶段

只要从生命史视角回头看，HikariCP 最值得量化的就不是“所有动作”，而是那些直接决定池健康度的关键阶段：

- 连接创建用了多久
- 借出等待了多久
- 一条连接被持有了多久
- 获取连接超时发生了多少次
- 当前活跃/空闲/等待状态是什么

这些指标之所以值钱，不是因为它们“好看”，而是因为它们分别对应连接生命史中的关键压力点。

而这些点不是概念上随便挑的，在 `HikariPool` 里都有明确记录入口：
- 借出成功：`recordBorrowStats(...)`：`com/zaxxer/hikari/pool/HikariPool.java:171`
- 借出超时：`recordBorrowTimeoutStats(...)`：`com/zaxxer/hikari/pool/HikariPool.java:183`
- 连接使用完成：`recordConnectionUsage(...)`：`com/zaxxer/hikari/pool/HikariPool.java:436`

- 创建太慢，说明前端压力可能顶不住
- 借出等待变长，说明借出链开始吃紧
- 使用时长拉长，说明归还链被拖慢
- 超时变多，说明前面几条链已经失衡
- 状态快照偏移，说明池整体运行结构可能正在变化

所以 metrics 量化的不是参数，而是生命史里的受压阶段。

## 二、为什么 `PoolStats` 不能每次现算，而要有自己的分辨率

只要谈“池现在有多少活跃连接、多少空闲连接、多少等待线程”，最自然的想法就是：

- 想看就现算一次不就行了？

这个想法的问题在于，连接池本身就是高频路径。如果每次观测都直接去全量扫描内部状态，观测本身就可能开始反咬运行时。

这就是 `PoolStats` 这种结构存在的原因。

它的意义不是“包装一下状态”，而是：

- `PoolStats` 自己用 `timeoutMs` 和 `reloadAt` 控制采样分辨率：`com/zaxxer/hikari/metrics/PoolStats.java:30`、`40`、`100`
- `HikariPool` 里对 `PoolStats` 的更新入口也很明确：`com/zaxxer/hikari/pool/HikariPool.java:675`

**给池状态观察建立一个分辨率边界，让观测本身也被纳入性能成本控制。**

也就是说，metrics 在 HikariCP 里并不是“越实时越好”，而是在做一层很成熟的折中：
- 状态要足够有用
- 但不能为了观察它而把池本身拖慢

所以 `PoolStats` 不是附属 bean，而是观测面本身的一部分。

## 三、为什么需要 `IMetricsTracker` / Factory 这种统一抽象

如果 HikariCP 只打算服务一个固定监控平台，那最简单的办法就是：
- 在池里直接写死这个平台的调用

但它没有这么做。

这说明源码主线里更重要的问题不是“把指标发给谁”，而是：

- 先把连接生命史里值得量化的点抽象出来
- 再让外部平台各自实现这一套观测协议

这就是 `IMetricsTracker` 和 `MetricsTrackerFactory` 这类抽象真正值钱的地方。

对应的硬锚点包括：
- `IMetricsTracker`: `com/zaxxer/hikari/metrics/IMetricsTracker.java:22`
- `MetricsTrackerFactory`: `com/zaxxer/hikari/metrics/MetricsTrackerFactory.java:19`
- `PoolStats`: `com/zaxxer/hikari/metrics/PoolStats.java:28`

也就是说，它们不是“多包一层接口”，而是在回答一个非常关键的设计问题：

**连接池的观测点应该先独立于监控平台存在。**

这样一来，Dropwizard、Micrometer、Prometheus 等实现，都只是在接同一套观测抽象，而不是把池内部主线绑死在某个监控栈上。

## 四、为什么三种实现不是三条主线，而是一条主线的三种外壳

看到 HikariCP 里同时存在：
- Dropwizard
- Micrometer
- Prometheus

很多人会自然以为：
- 这三套实现各自都值得独立大讲一篇

如果从“怎么接平台”角度看，当然能这么拆。

但从源码主线角度看，它们真正有价值的地方不在“各自细节”，而在于它们共同证明了一件事：

- HikariCP 的观测面不是某个平台特供的
- 它先定义了统一的生命史观测点
- 然后让不同平台各自把它们外化

所以，这三套实现对本篇来说更像三种外壳，而不是三条并行主线。

真正的主线还是：
- 连接生命史里哪些阶段被量化
- 池状态怎样被采样
- 这些采样怎样经由统一抽象被送出去

## 到了这里，metrics 已经不可能再被理解成“几个数字”了

现在再回头看最开始那个误解：

- metrics 不就是再多加几个数字吗？

看到这里，这个理解已经明显不够用了。

更准确的说法应该是：

- metrics 不是随机挑几个数字
- 它是在持续量化连接生命史里的关键阶段

也就是说，HikariCP 关心的不是“数字多不多”，而是：

- 这些数字能不能稳定映射出借出、使用、超时、池状态这些关键阶段的运行趋势

所以 metrics 真正补上的，不是统计附件，而是：

**连接生命史的一层持续观测面。**

## 这篇真正立住的，不是几个监控实现，而是“可量化观测面”这个概念

如果只从表面看，这篇很容易被讲成：

- 有个 `IMetricsTracker`
- 有个 `PoolStats`
- 还能接 Dropwizard/Micrometer/Prometheus

这种讲法当然不算错，但还是太像集成说明。

从前面整卷主线归纳回来，更稳妥的理解方式应该是：

1. 连接生命史里有些阶段必须被持续量化
2. 池状态不能每次都全量现算，所以要有受控分辨率的快照面
3. 统一观测抽象先于具体平台实现存在
4. 所以 HikariCP 的 metrics，不是在加数字，而是在补一层持续可量化的观测面

也就是说，这篇真正补上的，不是一个监控适配器体系，而是：

**HikariCP 怎么把连接生命史变成持续可采集、可聚合、可告警的时间序列信号。**

## 这篇之后，HikariCP 完整卷最自然的继续方向是什么

到这里，HikariCP 的诊断与可观测层已经补上了三条线：

- 借出后的诊断生命史（泄漏检测）
- 运行时控制面（JMX）
- 持续量化观测面（metrics）

如果继续往下写，最自然的方向就不再是主干补篇，而会更像：

- 卷级整理
- 或按需补具体平台接线（如 Micrometer / Actuator）

也就是说，到这里，HikariCP 这一卷已经非常接近阶段性收口点了。
