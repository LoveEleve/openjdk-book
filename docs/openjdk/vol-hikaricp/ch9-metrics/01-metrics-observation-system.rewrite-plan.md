## 一句话困惑

为什么连接池不仅要有借还、维护、验证、泄漏检测和 JMX，还要再单独做一套 metrics 体系？它到底在量化什么，又为什么不直接靠日志/JMX 代替？

## 一句话顿悟

HikariCP 的指标体系，不是在重复 JMX，而是在做另一件事：**把连接生命史中的关键事件和池状态，持续量化成外部系统可采集、可聚合、可告警的时间序列信号。**

## 读者理解路径

1. 从“为什么 JMX 还不够，还要 metrics”切入。
2. 建立最小总图：`pool events/state -> MetricsTracker -> PoolStats -> external registry`。
3. 解释指标为什么不是“顺手加几个计数器”，而是连接生命史的观测面。
4. 解释五类典型指标：创建、获取等待、使用时长、超时次数、池状态快照。
5. 解释 `PoolStats` 为什么要有轮询分辨率，而不是每次实时遍历池状态。
6. 解释 Dropwizard / Micrometer / Prometheus 三种实现为什么都是外壳，核心在统一观测抽象。
7. 收束到：指标体系是在给连接生命史补一层持续可量化的观测面。

## 失败方案推演

### 失败方案一：有日志和 JMX 就够了，不需要单独的 metrics

这是最自然的直觉。

因为前面我们已经有：
- 日志（泄漏告警、驱逐、初始化日志等）
- JMX（运行时状态和有限控制）

看起来观测手段已经不少。

问题在于，日志和 JMX 解决的都不是“持续量化采样”这个问题：
- 日志偏事件
- JMX 偏状态与管理
- metrics 偏持续量化与时间序列观测

所以它们不是替代关系，而是不同观察面。

### 失败方案二：metrics 就是多加几个计数器，没什么主线可讲

这个理解会让整篇掉成小工具说明。

因为 HikariCP 的 metrics 不只是“加几个 counter/gauge”，而是在问：
- 连接借出时，等待了多久
- 连接使用了多久
- 连接创建花了多久
- 连接超时发生了几次
- 当前池的运行状态快照是什么

也就是说，它量化的是连接生命史里的关键阶段，而不是孤立数值。

### 失败方案三：不同实现（Dropwizard/Micrometer/Prometheus）才是重点

这很容易让人陷进具体接线细节。

但对源码主线来说，真正重要的不是“接哪个监控平台”，而是：
- HikariCP 如何先抽象出统一的 metrics 观测点
- 再由不同实现把这些观测点投给不同外部系统

所以平台实现是外壳，统一观测抽象才是主线。

## 必须澄清的误解

1. metrics 不是日志和 JMX 的重复，而是持续量化观测面。
2. HikariCP 指标量化的是连接生命史关键阶段，不是几个随意挑出来的数字。
3. `PoolStats` 不是普通 bean，它是在平衡池状态采样成本和精度。
4. Dropwizard / Micrometer / Prometheus 不是三条主线，而是统一指标抽象的不同落地实现。
5. 本篇讲的是指标体系主线，不是监控平台接线教程。
