# HikariCP Ch9-01 指标监控体系 — review notes

## 第一轮：事实审

### 目标
核对：
- `IMetricsTracker`、`MetricsTrackerFactory`、`PoolStats`、不同实现类的角色归属是否准确
- `file:line` 引用是否真实存在
- 是否把“可观测面”写成超出源码可支撑范围的统一平台故事

### 当前需核对的关键锚点
- `IMetricsTracker`
- `MetricsTrackerFactory`
- `PoolStats`
- HikariPool 中与 record borrow / timeout / usage / creation 相关锚点
- Dropwizard / Micrometer / Prometheus 代表实现类

### 初步判断
- 当前主线与 Ch9 规划一致：生命史事件 -> 统一观测抽象 -> 状态快照 -> 外部实现
- 没有把本篇写成平台接入教程，这是对的
- 当前最大事实风险在于：还没有把 HikariPool 中“真正记录哪些指标”的方法级锚点补足，正文目前更多是指标体系层面的结构解释

## 第二轮：因果审

### 目标
检查正文中所有“为什么 JMX 不够”“为什么 PoolStats 不能每次现算”“为什么平台实现是外壳”这类判断，是否由源码结构支撑。

### 当前因果链
1. 日志 / JMX / metrics 三者解决的是不同观察问题
2. metrics 真正量化的是连接生命史里的关键阶段
3. `PoolStats` 是在平衡状态采样成本和精度
4. 统一观测抽象先于具体平台实现存在

### 当前风险
- 这些判断方向是对的，但如果不补 `HikariPool` 里记录 borrow timeout / usage / creation 等锚点，会显得像观测哲学总结
- `PoolStats` 的“分辨率边界”很值钱，但要靠实现锚点压实，否则容易偏抽象

## 第三轮：结构审

### 目标
检查结构是否遵守“困惑 -> 失败方案 -> 总图 -> 观测面拆解 -> 收网”的方法论，而不是退化成 metrics 清单。

### 当前结构评价
当前结构是：
1. 困惑开场
2. 失败方案
3. 最小总图
4. 生命史里哪些阶段最值得量化
5. `PoolStats`
6. `IMetricsTracker` / Factory
7. 三种外壳实现
8. 收网总结
9. 下篇桥接

### 当前结构优点
- 没有退化成接口清单
- “可量化观测面”是单一主概念，结构稳
- 和前文 JMX / 泄漏检测形成互补，不重复

### 当前结构风险
- `PoolStats` 与 `HikariPool` 的具体联系还没被压硬，容易让这一节漂成抽象层
- 三种实现如果后续补源码不注意取舍，容易又滑回平台细节散讲

## 第四轮：读者审

### 目标
检查读者是否能从“几个监控数字”切到“连接生命史被持续量化”这个视角。

### 当前读者收益
读完后，读者至少应能回答：
- 为什么 metrics 不是日志和 JMX 的重复
- 为什么 HikariCP 量化的是生命史关键阶段
- 为什么平台实现不是主线，统一观测抽象才是主线

### 当前读者风险
- 如果缺少 HikariPool 侧 record 锚点，读者会接受结构框架，但未必能感受到这些指标真的是从借、用、超时这些节点长出来的
- `PoolStats` 一节最容易因为证据不够而显得抽象

## 第五轮：边界审

### 目标
检查本篇是否提前透支 Micrometer / Actuator 接线补篇，或是否漏掉本篇必须收住的边界。

### 当前边界控制
本篇明确不深讲：
- Spring Boot Actuator 整合

- 如果为了讲观测而重讲借出/归还/泄漏/JMX 全主线，会让本篇失焦

## 当前结论

这篇已经完成一次性深审收口，当前主问题已从“结构是否成立”收敛为“观测面是否有足够方法级锚点”。本轮补强后，这个缺口已经被明显压实：
- `recordBorrowStats(...)`: `HikariPool.java:171`
- `recordBorrowTimeoutStats(...)`: `HikariPool.java:183`
- `recordConnectionUsage(...)`: `HikariPool.java:436`
- `PoolStats` 采样分辨率控制：`PoolStats.java:30`、`40`、`100`
- `HikariPool` 创建 `PoolStats`：`HikariPool.java:675`
- 统一观测抽象：`IMetricsTracker.java:22`、`MetricsTrackerFactory.java:19`、`PoolStats.java:28`

这让“metrics 是连接生命史的持续观测面”这条主论断，不再只是观测层概念，而有了清晰的实现托底。
