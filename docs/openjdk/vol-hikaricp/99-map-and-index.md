# HikariCP 卷总图 / 总索引

> 这不是新的正文专题，而是整卷导航图。它解决的不是“某个机制怎么实现”，而是：**如果你现在带着某个问题进来，应该先读哪几篇；如果你想回看某条主线，它在整卷里是怎么分布的。**

## 一、整卷主图：一条连接在池里的一生

如果把整卷压缩成一张总图，它其实讲的是一条 JDBC 连接在池中的一生：

```text
被配置出来
  -> 被装进池
    -> 被借出
      -> 被使用
        -> 被归还 or 被驱逐
          -> 在池里继续活着
            -> 被验证
              -> 被告警
                -> 被控制
                  -> 被量化观察
```

对应篇章：
- 被配置出来 / 被装进池：`Ch1`
- 被借出：`Ch2`
- 被归还 or 被驱逐：`Ch3`
- 在池里继续活着：`Ch5`
- 并发协作支撑借还：`Ch4`
- 被验证：`Ch6`
- 被告警：`Ch7`
- 被控制：`Ch8`
- 被量化观察：`Ch9`

## 二、如果你是第一次看这卷，建议主线顺序

1. `Ch1` 连接池核心架构
2. `Ch2` 连接获取完整流程
3. `Ch3` 连接归还与连接驱逐
4. `Ch4` ConcurrentBag 无锁并发设计
5. `Ch5` 连接生命周期管理 / HouseKeeper
6. `Ch6` 连接验证机制
7. `Ch7` 连接泄漏检测
8. `Ch8` JMX 与运行时管理
9. `Ch9` 指标监控体系

这个顺序的好处是：
- 先立总骨架
- 再立借还前后半链
- 再补并发存储层
- 最后补验证、诊断、控制和观测面

## 五、篇章之间最关键的桥

- `Ch1 -> Ch2`
  - 总骨架立住后，先看连接怎么被借出去

- `Ch2 -> Ch3`
  - 借出链之后，自然就是归还 / 驱逐后半链

- `Ch2/Ch3 -> Ch4`
  - 借还讲完，再问底层对象是怎么并发协作存取的

- `Ch3 -> Ch5`
  - 归还后连接并没死，接着看它在池里如何继续活着

- `Ch5 -> Ch6`
  - 连接继续活着时，借出前为什么还要验证

- `Ch6 -> Ch7`
  - 借出前可交付性判断讲完，再看借出去之后迟迟不还怎么被诊断

- `Ch7 -> Ch8 -> Ch9`
  - 先有诊断支线，再补控制面和持续量化观测面

## 六、最容易读散的地方

### 1. 只看 `ConcurrentBag`
会觉得很强，但不知道它在整个连接生命史里到底服务哪一段。

### 2. 先看 `JMX` / `metrics`
会知道怎么看池，却不知道你看到的到底对应借、还、活、退哪一段。

### 3. 把 `HouseKeeper` 当成定时任务，把 `leak detection` 当成附属告警
这样会错过“连接余生”和“借出后的诊断生命史”这两条很关键的主线。

## 七、跨卷位置

本卷是四卷体系的第一阶段入口：

- 本卷覆盖：HikariCP 连接池核心（连接生命史管理链）
- 对照卷：`vol-druid` — 以本卷为对照基准，展开 Filter/SQL 解析/监控等扩展
- 无关卷：`vol-mybatis` / `vol-mybatis-plus` — 连接池与 ORM 正交，无交叉引用
