### 2.2 依赖方向分析

1. **vol-druid → vol-hikaricp**：依赖成立。Druid 卷以 HikariCP 为对照基准，每篇正文都明确对比两者设计差异。这是设计意图明确的跨卷对照，不是无意的交叉引用。

2. **vol-mybatis-plus → vol-mybatis**：依赖成立。MyBatis-Plus 卷明确声明"已读 vol-mybatis"为阅读前提，且在卷级审查笔记、导读中都有显式说明。

3. **vol-hikaricp ⇎ vol-mybatis / vol-mybatis-plus**：无依赖成立。连接池卷与 ORM 卷之间不存在引用，这符合两者在技术栈中的正交关系。

4. **vol-druid ⇎ vol-mybatis / vol-mybatis-plus**：无依赖成立。同上。

### 2.3 潜在问题

- **vol-hikaricp 缺少卷级审查笔记**：其他三卷都有 `vol-xxx-review-notes.md`，唯独 HikariCP 没有。这会成为跨卷审查的盲区。
- **vol-hikaricp 和 vol-druid 缺少 `.note.md`**：MyBatis 和 MyBatis-Plus 都采用 4 件套（含 `.note.md`），但两个连接池卷只有 3 件套。格式不一致导致跨卷检索时，`.note.md` 中的"本篇主张"无法跨卷对齐。

### 3.2 分层对齐分析

**数据源层（2 卷，18 篇）：**
- HikariCP 和 Druid 都覆盖了连接池的核心机制，但 DRUID 多了 Filter/SQL 解析/监控安全等扩展层。
- 两卷的架构设计意图不同：HikariCP 是"极简连接池"，Druid 是"带监控和 SQL 分析的连接池"。
- 跨卷对照集中在连接池核心机制（借出、归还、验证、维护），这些是两卷的重叠区域。

**ORM 层（2 卷，19 篇）：**
- MyBatis 是 MyBatis-Plus 的基础，MP 的所有增强都建立在 MyBatis 原生体系之上。
- 两卷的架构分层高度一致（都是 A/B/C/D 四层），展现了方法论的一致性。
- 跨卷依赖清晰：MP 卷以 MyBatis 卷为阅读前提。

**数据源层与 ORM 层之间：**
- 无直接引用关系。这是合理的——连接池是 JDBC 层的资源管理，ORM 是 SQL 生成和执行层的抽象，两者正交。
- 但在实际运行中，MyBatis 通过 `DataSource` 接口获取连接，Druid/HikariCP 通过 `DataSource` 接口提供连接。这个"接口契约"层面的关系在四卷中都没有被单独描述。

## 五、边界审 — 跨卷边界与重叠

### 5.1 边界清晰区域

| 边界 | 左卷 | 右卷 | 边界是否清晰 |
|------|------|------|:------------:|
| 连接池核心机制 | vol-hikaricp | vol-druid | 清晰。两卷都从不同角度覆盖，但设计意图不同，互不冲突。 |
| 监控与扩展 | vol-hikaricp（无） | vol-druid（大量） | 清晰。HikariCP 几乎没有监控扩展，Druid 以此为特色。 |
| ORM 核心 | vol-mybatis | vol-mybatis-plus | 清晰。MP 卷明确声明以 MyBatis 卷为前置。 |
| 数据源层 ↔ ORM 层 | 连接池卷 | ORM 卷 | 清晰。通过 `DataSource` 接口解耦，互不引用。 |

### 5.2 重叠区域

| 区域 | 涉及卷 | 重叠程度 | 分析 |
|------|--------|:--------:|------|
| 连接验证 | vol-hikaricp Ch6, vol-druid D-7 | 高 | 两卷都覆盖了连接验证，但设计差异大，对照阅读有意义。 |
| 连接生命周期 | vol-hikaricp 主干层, vol-druid D-1/D-5 | 高 | 两卷都覆盖了创建、借出、归还、销毁，但实现机制不同。 |
| Boot 装配 | vol-druid D-9, vol-mybatis S-2, vol-mybatis-plus MP-7 | 中 | 三卷都覆盖了 Spring Boot 自动装配，但装配对象不同。 |
| 插件/拦截 | vol-mybatis M-6, vol-mybatis-plus MP-5 | 中 | MyBatis 原生插件链 vs MP 的增强总线，两者有继承关系。 |

### 5.3 遗漏区域

| 区域 | 说明 |
|------|------|
| DataSource 接口契约 | 四卷都没有单独描述 `DataSource` / `Connection` 的 JDBC 接口契约，以及连接池与 ORM 之间如何通过该契约解耦。 |
| 事务管理器 | 虽然 vol-mybatis 的 S-1 覆盖了 `SqlSessionTemplate` + Spring 事务，但没有单独篇章描述 `PlatformTransactionManager` / `DataSourceTransactionManager` 与连接池的关系。 |
| 连接池选择策略 | 在 Spring Boot 环境中，如何选择 HikariCP vs Druid vs 其他连接池？四卷都没有覆盖。 |
| 统一性能基准 | 四卷各自有性能相关的描述，但没有跨卷统一的性能基准测试或对比报告。 |

## 八、结论

四卷跨卷审查完成。核心结论：

1. **跨卷引用关系清晰**：vol-druid 对照 vol-hikaricp，vol-mybatis-plus 依赖 vol-mybatis。两个正交领域（数据源层 vs ORM 层）之间无交叉引用，边界合理。

2. **格式不一致**：HikariCP 和 Druid 卷采用 3 件套（缺 `.note.md`），MyBatis 和 MyBatis-Plus 卷采用 4 件套。建议统一为 4 件套。

3. **卷级审查笔记缺失**：vol-hikaricp 缺少卷级审查笔记，其他三卷都有。

4. **跨卷阅读路径可优化**：各卷的导读可以补充跨卷阅读路径说明，让读者知道本卷在四卷体系中的位置。

5. **无严重矛盾或冲突**：四卷在术语、概念、架构上保持一致，没有发现跨卷矛盾。
