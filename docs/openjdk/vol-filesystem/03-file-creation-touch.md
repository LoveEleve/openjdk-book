## 现在真正该问的，不再是“一个文件怎样被 inode 指针树索引”，而是“这个文件在还不存在的时候，内核到底怎样让它第一次进入磁盘世界”

上一篇我们已经把 inode 和间接块讲清楚了。你知道一个文件并不是连续磁盘区，而是由 inode 这个身份证和 `i_block[15]` 这棵分级指针树把散落块重新串成逻辑整体；目录也被重新解释成“内容是目录项数组的普通文件”。

可这一切都默认文件已经存在：名字已经能解析到 inode，inode 已经在 inode table 里，目录项也已经写在父目录的数据块里。

新的问题马上就变得非常尖锐：**第一个文件到底怎么诞生？**

用户态里你不过是敲了一下：

```c
open("a.txt", O_CREAT|O_WRONLY, 0644);
```

或者更偷懒一点，直接：

```bash
touch a.txt
```

从表面上看，这个文件还是 0 字节，似乎没写任何真正内容。可如果文件系统什么都不做，它就不会“存在”。所以创建文件这件事的本质，恰恰不是“写文件数据”，而是先把一套最小但关键的索引关系真正落地：

- 这个名字在父目录里是否已经存在？
- 如果不存在，新的 inode 号从哪来？
- 哪个 Block Group 被选来承接这个 inode？
- inode bitmap 和组计数器怎么改？
- 父目录的目录项数组里，怎样插入一条 `name -> inode` 记录？
- 为什么一个 0 字节文件明明没有数据块，却已经算“存在”了？

所以本篇最重要的顿悟是：**创建文件首先不是写内容，而是把“名字 → inode”这层索引关系，以及“inode 已被占用”这层账本事实，正式写进磁盘与缓存系统。**

先把总图记住：

```text
创建前半段：
  先做路径解析
  确认父目录存在、目标名字不存在

VFS 分叉：
  最后一个分量若不存在且带 O_CREAT
  从 lookup 跳到 create

文件系统落地：
  ext2_new_inode 选组、占 inode bitmap、更新组计数、初始化 inode
  ext2_add_link 把新名字写进父目录目录项数组

最终结果：
  0 字节文件已存在
  但 i_block[15] 仍全 0
  数据块分配留到第一次真正 write 再发生
```

这一篇最重要的一句话是：**`touch a.txt` 创建的不是“文件内容”，而是“名字和 inode 之间的一条正式绑定关系”，以及这条绑定背后那几本必须同步更新的账本。**

## 一、如果创建文件不先确认名字不存在，文件系统连“到底是打开旧文件还是诞生新文件”都分不清

### 1. 最朴素的错误方案：看到 `O_CREAT` 就直接分配一个新 inode，再把名字写进去

从“先把文件造出来”这个角度看，这似乎很自然。调用者都说了 `O_CREAT`，那我就先拿一个空闲 inode，把目录项写进去，文件不就有了吗？

问题在于，`O_CREAT` 的含义从来不是“无条件新建”。它真正的语义是：**如果名字不存在，那就创建；如果名字已经存在，那就按是否带 `O_EXCL`、是否只是普通打开等规则决定后续行为。**

也就是说，创建逻辑必须建立在“先判断这个名字当前是不是已经有合法绑定”之上。否则你根本分不清自己是在创建新文件，还是应当打开旧文件，甚至有可能破坏现有目录项与 inode 关系。

### 2. 第二个失败方案：那就先分配 inode，再查目录，如果名字已存在就把 inode 丢掉

这看起来似乎能补上语义：先抢个 inode 号，再去目录里查名，若名字已存在就回滚。

可这会把“判断是否需要创建”与“修改磁盘账本”顺序彻底搞反。分配 inode 本身就要改 inode bitmap、group 计数和内存 inode 状态，这些都不是零成本。若只是为了判断名字存不存在就先动账本，失败回滚不仅麻烦，还容易扩大临界区与错误处理复杂度。

更糟的是，`O_CREAT|O_EXCL` 这样的语义要求“确认不存在并创建”这一过程尽可能原子且顺序清晰。先查名，再决定是否进入 create，是 VFS 与文件系统能合作守住语义的关键。

### 3. Linux 的答案：路径解析先行，最后一个名字分量先走 `lookup`，确定 `-ENOENT` 之后才有资格谈 create

这就是文件创建路径的第一层顿悟。它和前面很多章节一样，都是先把“问题语义判清楚”，再让底层分配动作登场。

VFS 不会一看到 `O_CREAT` 就立刻把自己砸进磁盘分配世界，而是先沿路径做普通解析：父目录在不在、各层 dentry 和 inode 能否顺利找到、最后一个名字项当前到底是什么状态。只有最后分量明确是“目标不存在”，且调用标志允许创建时，后半段 `create` 路径才正式成立。

换句话说，**创建文件不是从“分配 inode”开始，而是从“先确认这不是一个已有对象”开始。** 若要把这一节补成更硬的源码正文，最关键的证据位应回到 `fs/namei.c` 与 `fs/ext2/namei.c` 的路径解析、`lookup`/`create` 分叉相关路径：它们共同支撑“先裁定名字语义，确认 `-ENOENT` 后才有资格进入 create”这句判断。

## 二、路径解析：`touch a.txt` 的前半段，其实是在翻父目录这本门牌册，确认新名字还没登记过

### 1. 为什么路径解析不是创建文件的配角，而是前置语义裁判

很多人一提文件创建，会立刻跳到 inode bitmap 和目录项插入，仿佛名字解析只是无聊前戏。其实恰恰相反：路径解析是在替后面所有落盘动作做语义裁判。

它必须回答：父目录存在吗？中间路径有没有挂载穿越？最后这个名字在当前目录项数组里是不是已经绑定到某个 inode？如果这一关没过，后面的“新建”根本没有资格发生。

所以从教学顺序看，路径解析不是为了凑完整，而是为了强调一个非常重要的事实：**文件系统里的所有磁盘动作，首先都受名字语义约束。**

### 2. `link_path_walk`、`lookup_fast`、`lookup_slow` 这些层次在解决什么问题

从最宏观的人话看，这几层不是在做不同种类的“找名字”，而是在尽量把“查路径”做成先快后慢的分层过程。

- 如果 dentry cache 里已经有现成答案，最好直接命中，别每次都重新进具体文件系统目录页里扫目录项。
- 只有当缓存不够用、名字状态不明确或需要真正回到目录内容时，才进入更慢的查找路径。
- 最终，具体文件系统的 `lookup` 才回答“在这个父目录的数据块里，到底有没有这条名字记录”。

这很像前面内存卷反复出现的设计哲学：先走靠近调用者、便宜、缓存化的路径，兜不住了再进更重的真实世界。路径解析的快慢分层，本质上也是这种结构。

### 3. 为什么 `ext2_lookup` 本质上是在扫目录这个特殊文件的内容

到了具体文件系统层，这件事就很漂亮地接回了上一篇的目录本质。所谓“找名字”并不是目录树自己带着某种神秘索引魔法，而是系统把父目录 inode 当成普通文件，读它的数据块内容，再在那些 `ext2_dir_entry_2` 条目里逐个找 `name` 是否匹配。

这意味着 `lookup` 根本不是脱离磁盘布局的特殊仪式，而是一次“读目录文件内容并解释成目录项数组”的普通文件系统操作。正因为目录是文件，所以名字解析才最终落回“扫目录项数组”这件很朴素的事。

### 4. 本节最该记住的结论：创建文件前半段，真正干的是“沿路径找到父目录，再在父目录门牌册里确认这个名字还不存在”

所以一句最短人话是：**`touch` 真正的第一步不是造文件，而是翻父目录的门牌册，确认这张门牌还空着。**

## 三、`O_CREAT` 分叉：VFS 真正做的不是自己改位图，而是把“名字语义已经裁定完毕”这个结果交给具体文件系统去落磁盘账

### 1. 为什么 VFS 自己不能直接创建 inode

到这里路径语义已经清楚了：名字不存在，允许创建。很自然的下一个误解是：那 VFS 既然已经知道要创建，干脆自己统一分配一个 inode，再统一写目录项不就完了。

这做不到，因为 VFS 根本不知道 on-disk 格式。它知道“需要一个新文件对象”，却不知道 inode table 在哪、inode bitmap 长什么样、group descriptor 如何更新、目录项如何在 ext2 目录文件里插入，或者别的文件系统会不会用完全不同的数据结构、日志事务甚至 extent tree。

所以 VFS 只能统一表达语义，不能统一执行业务落盘。

### 2. `vfs_create()` 的意义：把高层名字规则和低层磁盘账本解耦

这就是 `vfs_create()` 真正优雅的地方。它不像一个“实际建文件的人”，更像一个统一受理窗口：前面路径解析已经裁定“这个名字应该走新建分支”，现在把“给我一个新 inode，再把名字绑上去”这个抽象请求下发给具体文件系统。

Ext2、Ext4、XFS 甚至别的非本地文件系统，都可以复用同一套 `open(O_CREAT)` 的高层语义；差异发生在各自的 `i_op->create()` 落盘路径里。这样语义统一了，磁盘实现却保持自治。

### 3. `ext2_create()` 为什么像一个小型事务的总入口

一旦进入 Ext2 的 create 路径，系统真正要完成的事情至少有两大块：

- 先把一个新 inode 号合法地分配出来，并把 inode 元数据初始化好。
- 再把名字写入父目录项数组，让这个 inode 真正能被路径世界看到。

注意这两件事必须最终同时成立才叫“文件创建成功”。如果只分配了 inode 但目录项没写进去，那只是一个半成品；如果目录项先写了但 inode 还没真正初始化好，也会破坏一致性。

所以 `ext2_create()` 最该被理解成“把这两本账绑起来推进的入口”，而不是“单独做某一件事的函数”。

### 4. 本节最该记住的结论：`O_CREAT` 分叉后的核心，不是 VFS 统一创建文件，而是 VFS 统一决定“该创建了”，再让具体文件系统用自己的账本规则去完成创建

所以一句最短人话是：**VFS 负责判案，具体文件系统负责立账。**

## 四、`ext2_new_inode()`：新文件诞生时，真正先被改动的并不是目录名字，而是“哪个组还有空证件、哪张证件号先被占掉”这本身份账

### 1. 为什么 inode 分配必须先于目录项落盘

这点非常关键，因为目录项里真正记录的是 inode 号。没有 inode 号，就谈不上“名字指向谁”。所以创建文件的第一本账，不可能是目录项，而只能是 inode 身份账。

这意味着系统必须先找到一个合法空闲 inode 号，把它从“未使用”状态变成“现在已经属于一个新文件”，并完成最基本的元数据初始化。只有这样，后面目录项才有了可写入的目标编号。

### 2. 选组为什么不是“随便挑个还有空 inode 的 BG”

如果只是为了分配成功，似乎任何一个还剩空闲 inode 的 Block Group 都可以。可 Ext2 仍然会在这里做更细的策略判断：目录与普通文件的选组倾向不同，普通文件尽量贴近父目录，目录则更倾向于分散。

这是非常有工程味的决定。它说明 inode 分配不是只追求“今天把号发出去”，而要考虑后续布局局部性和目录树扩展。普通文件靠近父目录，查找和相关数据布局通常更友好；目录若全挤一处，则后面整个子树的名字空间和元数据压力会过热。

所以选组其实已经在替未来的目录与数据访问做局部性铺垫。

### 3. inode bitmap 为什么是创建时最先被写脏的核心账本

一旦组选定，真正的“身份占位”动作发生在 inode bitmap 上。那一个 bit 从 0 翻成 1，意味着这张“空白证件号”正式被占掉了。这可能是整条创建路径里最值得你牢牢记住的一瞬间，因为它把一个抽象“即将存在的文件”，第一次变成了磁盘账本里的事实。

从这里开始，inode 号不再只是一个可能性，而变成了一项系统已经承认的资源占用。之后哪怕目录项写入失败，也要按失败路径认真回滚，而不是假装事情从未发生过。

### 4. 为什么 group descriptor 计数器也必须同步更新

如果只改 bitmap 而不改组统计，系统后面看见的空闲 inode 数就会和事实脱节。下一次选组和分配时，它对“这个组还剩多少空位”的判断就会越来越不准。

这正是 group descriptor 计数器存在的意义：位图负责精确真假账，计数器负责高层概览账。它们就像一份明细表和一份汇总表，必须同步才能保证后续调度和定位策略的判断还可信。

### 5. 为什么一个空文件的 inode 会把 `i_block[15]` 先全部清零

因为到这一刻为止，系统只是确认“这个身份存在了”，还没有任何数据块内容需要索引。一个 0 字节新文件的逻辑本质，就是：**有名字，有 inode，有属性，但还没有数据块。**

这再次强调了本篇最大的顿悟：创建文件首先建立的是索引和身份，不是内容。`touch a.txt` 成功时，文件已经存在，但它的数据树还完全是空的。

### 6. 本节最该记住的结论：`ext2_new_inode()` 真正完成的是“选一个合适行政区，从 inode bitmap 领走一张空白证件号，并把它初始化成一个合法但尚无内容的新身份”

所以一句最短人话是：**创建文件的第一本账，是 inode 身份账。**

## 五、`ext2_add_link()`：文件真正对外“存在”的瞬间，不是 inode 分配成功，而是父目录那本门牌册里终于多了一行名字

### 1. 为什么“有 inode 了”仍然不等于“用户已经能看见这个文件”

这点特别容易想当然。系统刚分配完 inode 时，内核内部已经知道有这么一个新身份存在；但用户态路径解析世界仍然完全看不见它。因为名字世界依赖的是目录项，而不是 inode table 本身。

如果父目录数据块里还没有写入 `a.txt -> ino` 这条记录，那么下次 `lookup("a.txt")` 仍然会回答“不存在”。也就是说，inode 是存在条件之一，但不是对外可见条件。证据位上，这层最值得回到 `fs/ext2/ialloc.c` 中 `ext2_new_inode()` 一类路径与 `fs/ext2/dir.c`/`fs/ext2/namei.c` 中目录项插入相关实现去看：它们共同支撑“先有身份账，再有门牌账，最后才有对外可见性”这条主线。

### 2. 为什么目录项插入本质上是在修改父目录这个普通文件的内容

这又一次把上一章的“目录就是特殊文件”拉回现实。`ext2_add_link()` 并不是在更新某个独立目录数据库，而是在父目录文件的数据块里找到一段合适空间，写入一条新的 `ext2_dir_entry_2`。

这意味着文件创建并不只改“新文件自己的账”，还会改“父目录文件的内容”。一个看似无害的 `touch`，至少已经脏了两个方向：新 inode 自己，以及父目录的数据页。

### 3. 为什么目录项常常表现为“切现有 rec_len、塞进洞里”，而不是每次都重写整个目录

因为目录项是变长记录。只要父目录某个数据块里有足够长的空洞，或者某条已有记录后的剩余对齐空间足够，就可以在局部切下一块给新条目。这样做大大降低了每次创建文件都重写整个目录文件的成本。

这体现的又是同一种系统哲学：**只做局部最小必要修改。** 目录越大，这一点越重要。

### 4. 为什么 `d_instantiate` 像一个“内核名字世界的提交点”

当目录项已经成功写入，新的名字和 inode 号关系在磁盘/缓存账本上成立后，VFS 侧的 dentry 也才有资格与这个 inode 正式绑定。可以把这看成名字缓存世界里的提交时刻：从这一刻起，路径解析不仅理论上应该能找到该文件，内核的 dentry/inode 关系也进入一致状态。

这一步的意义在于把“磁盘账本已经记账”和“VFS 名字缓存已经承认这条关系”接起来，避免用户态下一次看到的世界和底层账本脱节。

### 5. 为什么回滚逻辑本身也说明目录项才是真正提交点

如果 inode 分配成功了，但目录项插入失败，那么系统会走失败回滚：减少链接计数，丢弃这个新 inode，让它重新回到未完成状态，不留下半成品。

这说明在设计者眼里，**文件是否真正创建成功，不是看 inode 有没有短暂出现，而是看“名字 → inode”的外部可见关系有没有最终建立。** 只有这条关系成立，文件才对世界可见。

### 6. 本节最该记住的结论：文件真正诞生的提交点，是父目录门牌册里那条新目录项被成功写进去

所以一句最短人话是：**inode 像房产证，目录项像门牌登记；证件办下来还不够，门牌册上出现你的名字，外界才真正知道你住进来了。**

## 六、把本篇收成一张图：`touch` 改的不是文件内容，而是三本账——名字账、身份账和汇总账

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：`touch a.txt` 明明 0 字节，为什么还要改磁盘。答案首先否定了“创建文件 = 写内容”这个直觉。Ext2 创建一个空文件时，真正优先落地的是索引关系，而不是数据块。

路径解析先沿 VFS 与目录项世界确认：父目录存在，目标名字当前不存在。`O_CREAT` 于是把高层名字语义从 `lookup` 分叉到 `create`，但 VFS 并不亲自改磁盘账，而是把这件事交给 `ext2_create()`。

`ext2_new_inode()` 先做身份账：选一个合适的 Block Group，在 inode bitmap 上占掉一个空位，更新 group 和全局计数，初始化一个还没有数据块的新 inode。随后 `ext2_add_link()` 再做名字账：在父目录这个特殊文件的数据块里插入一条 `name -> inode` 记录，让路径世界能真正看见它。只有这两步都成功，`dentry` 与 inode 的绑定才算在 VFS 世界里提交完成。

因此，一个 0 字节文件虽然没有任何数据块，却已经通过三类账本获得存在性：

- inode bitmap 说明“这个身份号被占用了”；
- group descriptor / 统计计数说明“空闲额度变了”；
- 父目录目录项说明“这个名字现在指向这个 inode”。

把这一切压成最短总图，就是：

```text
先判语义：
  路径解析确认父目录存在、目标名字不存在

再建身份：
  ext2_new_inode 选组、占 inode bitmap、更新计数、初始化 inode

再登记名字：
  ext2_add_link 在父目录目录项数组中写入 name -> ino

最后提交可见性：
  dentry 与 inode 绑定
  0 字节文件正式可见
```

所以本篇最该记住的一句话是：**文件创建最核心的动作不是“写内容”，而是把名字、inode 和账本状态三者统一成一条正式存在的索引关系。**

## 七、几个最容易说错的地方

### `touch a.txt` 是不是基本不改磁盘，因为文件还是空的？

不是。它会至少改 inode 位图、相关计数器和父目录目录项，空文件也需要被正式登记进名字与 inode 世界。

### 创建文件是不是一上来就先分配数据块？

通常不是。0 字节新文件可以只有 inode 和目录项，没有任何数据块分配。

### 路径解析是不是创建文件前的无关样板代码？

不是。它是名字语义裁判，决定当前到底该打开旧文件、报已存在，还是走创建分支。

### inode 分配成功是不是就意味着文件已经“存在”了？

还不够。只有目录项把名字绑定到 inode 后，文件才对路径解析世界真正可见。

### 目录项插入是不是和 inode 创建无关的另一步小修小补？

不是。它是创建路径的提交点之一，没有它，新 inode 只是内部半成品。

### 空文件是不是“什么账都没占”，只是一个抽象名字？

不对。它已经占用了 inode 号，也修改了目录和组统计，只是尚未占用数据块。

## 收束：看懂文件创建之后，你才会真正明白“一个文件诞生”首先是索引关系的建立，而不是内容写入的开始

回到开头那个问题：一个还不存在的文件，内核怎样把它第一次登记进磁盘世界？现在答案已经完整闭环了。它不会先去写数据块，而是先沿路径世界确认名字不存在，再让具体文件系统分配 inode 身份、改 inode 位图与计数器，最后把名字写进父目录这本门牌册里。0 字节文件之所以已经算存在，不是因为它有内容，而是因为名字和 inode 的绑定关系已经正式落盘并在 VFS 世界提交。

也正因为如此，你会发现文件系统里最初的“存在”从来不是内容意义上的，而是索引意义上的：先有名字、身份和账本，后面才有真正的数据块写入、页缓存脏页、writeback 和读写路径。理解了这件事，后面的写流程就不再像“又一次系统调用”，而更像是在一个已注册对象上，第一次把真实字节内容塞进去。

这就是为什么说：**文件创建首先是“建立索引”，不是“写入内容”；空文件也已经是完整对象，因为它在名字世界和元数据世界里都已正式存在。**

## 八、误解清单、证据清单与边界清单

### 误解清单

- `touch a.txt` 不等于“基本不改磁盘”；空文件也必须正式改动 inode 位图、组统计和父目录目录项。
- `O_CREAT` 不等于一上来就先分配 inode；创建路径首先要先裁定名字语义是否允许新建。
- inode 分配成功不等于文件已经对外存在；目录项还没写入前，路径世界仍然看不见它。
- 0 字节新文件不等于“什么都没占”；它只是还没占数据块，不代表没有身份账和门牌账。
- 目录项插入不是无关紧要的末梢动作；它是名字世界真正提交可见性的关键一步。

### 证据清单

- 路径语义裁判：`fs/namei.c` 与 `fs/ext2/namei.c` 的路径解析、`lookup`/`create` 分叉相关路径，支撑“先确认 `-ENOENT`，再有资格 create”的判断。
- 身份账：`fs/ext2/ialloc.c` 中 `ext2_new_inode()` 一类路径，支撑选组、占 inode bitmap、更新计数、初始化新 inode 的主线。
- 门牌账：`fs/ext2/dir.c`/`fs/ext2/namei.c` 中 `ext2_add_link()` 与目录项插入路径，支撑“父目录门牌册里多一行名字后文件才真正可见”。
- 提交点：`d_instantiate` 与相关 dentry/inode 绑定路径，支撑“磁盘账本成立后，VFS 名字缓存也要正式承认这条关系”的判断。
- 失败回滚：create 失败后的链接计数与 inode 回滚路径，支撑“inode 先短暂出现不等于文件真正创建成功”的主线。

### 边界清单

- 本文讨论的是 Ext2 创建路径的稳定心智模型；路径解析层次、锁顺序、Orlov 选组和错误回滚细节会随内核版本与实现演进变化。
- “存在”在文件系统里首先是索引与名字可见性的语义，不等于内容已经存在或数据块已经分配。
- VFS 统一的是高层名字规则，不替具体文件系统决定位图、inode table 和目录项落盘细节。
- 0 字节文件是完整对象，但不是完整数据对象；内容树仍会等到第一次真正写入才开始生长。
- 本文先讲对象诞生；第一个字节怎样进入 page cache、怎样挂脏账和后续 writeback，要到下一篇再闭环。
