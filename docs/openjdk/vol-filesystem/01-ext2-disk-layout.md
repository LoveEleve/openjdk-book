## 现在真正该问的，不再是“用户态怎样拿到页”，而是“这些页之外，磁盘上的字节流被格式化之后，内核凭什么知道哪个扇区属于哪个文件”

内存这一卷到上一章已经收束了：你已经看见从 `malloc()`、栈、ptmalloc 一路往下，最后怎样接到 Buddy、页表、缺页、回收和 OOM。那条线解决的是：**程序在运行时，字节怎样暂时活在内存里。**

可程序不只活在内存。只要数据要跨进程、跨重启、跨断电继续存在，它迟早得掉到磁盘上。问题也随之骤变：在内存里，地址和页表帮你找东西；到了磁盘，你面对的是一大片原始块设备空间。格式化之前，那只是线性扇区；格式化之后，文件系统凭什么知道：

- 哪些块已经被文件占了，哪些还空着？
- inode 号给定时，它的元数据到底躺在磁盘哪里？
- 一个目录项说“这个文件是 inode 12345”，系统为什么不用全盘扫描就能找到它？
- 为什么某些区域坏了还有希望从备份恢复，而不是整个文件系统瞬间失忆？

这就是文件系统卷第 1 篇真正要回答的核心困惑。

很多初学者会把“文件系统”想成某种很抽象的软件逻辑，好像不过是在磁盘上写点目录和文件名。但真正一旦落到块设备上，事情的第一原则其实和前面内存卷非常像：**想高效管理，就必须先把空间组织成位置可计算的布局，而不是等到查找时才全盘扫一遍。**

所以本篇最重要的顿悟是：**Ext2 的第一件大事不是“存文件”，而是先把整块磁盘切成若干 Block Group，再在每个分组里放好总规、目录、位图、户籍册和数据区。** 文件系统之所以能定位、分配和恢复，地基都在这张布局图里。

先把总图记住：

```text
磁盘入口：
  Boot Sector 负责最前面的引导与分区入口语义

主体组织：
  磁盘被切成多个等大 Block Group

每个 Block Group 内部大致分段：
  SuperBlock
  Group Descriptor Table
  Block Bitmap
  Inode Bitmap
  Inode Table
  Data Blocks

全局意义：
  SuperBlock 记录整座“城市”的总参数
  GDT 记录每个区的关键设施坐标
  位图负责空闲账本
  inode table 负责文件元数据户籍册
  data blocks 才是真正放文件内容的地方
```

这一篇最重要的一句话是：**文件系统并不是“把文件顺着磁盘一行行排开”，而是先把磁盘规划成一座有行政区、总规、位图账本和元数据户籍册的城市，这样任何一个 inode 或 block 的位置才都能被公式算出来。**

## 一、如果格式化之后磁盘仍只是“一整块线性空间”，那么创建文件、找空闲块和恢复故障都会退化成全盘普查

### 1. 最朴素的失败世界：磁盘就是一个从 0 到 N 的块数组，文件系统把文件顺次塞进去

先从最直觉的错误模型开始。假设磁盘格式化之后，文件系统什么复杂布局也不做，只把整块设备看成一条线性 block 数组。创建文件时，从前往后找空闲块，把名字、元数据和内容某种方式顺着塞进去。

这个模型在玩具系统里也许还能凑合，但一旦文件数量、目录层级、并发操作和崩溃恢复进入现实，它就会迅速失控。因为系统迟早要回答下面这些问题：

- 一个 inode 在哪？
- 某个文件的数据块从哪开始？
- 哪个块空闲？
- 哪个 inode 空闲？
- 某一段损坏时，备份信息在哪？

如果磁盘上没有被预先规划出“专门记这些账”的区域，那么这些问题很多都只能通过大范围扫描去解决。那意味着每次分配和定位的成本都会随着磁盘规模越来越难看，恢复时更是噩梦。

### 2. 第二个失败方案：那就做一份全局大目录，把全盘所有元数据都集中放一起

如果意识到“完全线性”太蠢，一个更像样的想法是：把所有元数据集中到磁盘前部，后面全部当数据区。这样 inode、位图和目录信息似乎就比较容易集中管理。

这比纯线性排文件前进了一步，但它仍然把自己困进了几个问题里。第一，所有分配和更新都更容易扎堆在少数热点区域，扩展性和并发局部性差。第二，任何前部元数据区域损坏，影响面巨大。第三，磁盘很大时，元数据和数据区相距可能很远，本地性很差。文件刚分配完 inode，真正写数据又要跑去很远的数据区。

也就是说，“全局集中”虽然让概念图简单，却让现实的定位、并发与故障域都变得笨重。

### 3. Ext2 的核心选择：把磁盘切成多个 Block Group，让每个区自带自己的账本和户籍设施

这就是 Block Group 设计最重要的价值。Ext2 并没有把整块磁盘当成一个巨大、扁平的资源池，也没有把所有元数据都挤在前面，而是把主体空间切成多个等大的组。每个组里都配有自己的 block bitmap、inode bitmap、inode table，以及属于该组的数据块区。

这样做的根本好处，是把“全盘一锅账”拆成了“分区自治的小账本”。分配空闲块时，不一定要盯着全盘一个总位图；分配 inode 时，也有组内自己的户籍册；数据和元数据更有机会保持组内接近，局部性更好。更重要的是，损坏和维护成本也更容易局部化。

所以如果只记一句关于 Block Group 的人话，可以这样记：**它让文件系统从“全盘一张表”变成“每个行政区都有自己的空地账本、人口账本和户籍册”。** 若要把这一节补成更硬的源码正文，最关键的证据位应回到 `include/linux/ext2_fs.h` 中 Block Group 相关布局定义，以及 `fs/ext2/super.c` 中挂载与读取全局布局参数的路径：它们共同支撑“Block Group 不是概念分块，而是定位、分配和恢复都依赖的真实地形划分”。

## 二、六段式布局：Ext2 真正优雅的地方，不是段名多，而是每一段都在替“位置可计算”这件事服务

### 1. 为什么“分组”还不够，组内仍然要固定分段

到这里你已经知道磁盘主体被切成多个 Block Group，但若组内布局仍然混乱，系统依然无法快速推导“我现在该去这个组里的哪个位置找哪个设施”。

所以 Ext2 的第二个关键动作，是让组内结构也尽量规则化。不同段不只是为了分类整齐，而是为了让各种定位公式成立：给定 inode 号、组号、块号和位图位置，系统应该能依靠少量全局参数直接算出目标磁盘位置，而不是进入“组内再扫描一遍”的第二层混乱。

### 2. Boot Sector：为什么文件系统自己的故事还没开始，最前面却先让出一小块地

磁盘最前面的 boot sector 提醒你：文件系统不是活在真空里。它首先存在于分区、引导和块设备入口语义之下。对 Ext2 来说，这块区域并不等于文件系统自己的业务主体，但它解释了为什么“磁盘上的第一个逻辑扇区”不能简单理解成“文件数据从这里开始”。

从教学角度看，这一步很重要，因为它能帮你分清两层东西：**引导/分区入口语义**和**文件系统自己的磁盘布局语义**。前者是整块设备的开场白，后者才是 Ext2 真正开始治理空间的地方。

### 3. SuperBlock：整座城市的总规为什么必须有一个全局入口

如果 Block Group 像行政区，那 SuperBlock 就像城市总规。它不处理每一块具体数据，而是告诉整个系统：这座文件系统多大、块多大、每组有多少 block 和 inode、总共有多少 inode、多少块被保留、这是不是真正的 Ext2、上次状态是否干净等。

换句话说，它回答的是“如何解释这块磁盘”的元问题。没有 SuperBlock，内核甚至不知道接下来该按 1KB、2KB 还是 4KB 的 block 视角去理解设备，更不知道组边界和 inode 编号公式如何成立。

这就是为什么挂载一个文件系统时，系统首先非常在意能不能正确读取 SuperBlock。因为它不是某个细节结构，而是整张布局图的解释器。

### 4. GDT：为什么光有总规还不够，还要每个组有一份“设施目录”

有了 SuperBlock，系统知道了全局几何与规则；但当它真的想定位某个组的位图和 inode table 时，仍需要一份更贴近组级设施的目录。这就是 Group Descriptor Table 的价值。

如果说 SuperBlock 回答的是“整座城怎么规划”，那 GDT 回答的就是“每个区的空地账本、人口账本和户籍册分别从哪里起”。它把组级关键设施的位置明确列出来，系统不必靠猜，更不必扫描。

所以 GDT 是从“全局理解规则”走向“开始在某区具体办事”的第一道桥梁。证据位上，这层最值得回到 `include/linux/ext2_fs.h` 中组描述符定义，以及 `fs/ext2/super.c`/相关挂载路径中解释和定位 GDT 的实现：它们共同支撑“SuperBlock 管总规，GDT 管每个区的关键设施坐标”这句判断。

### 5. 位图与 inode table：为什么文件系统必须把“空不空”和“是谁”分开记账

Block bitmap 的任务是回答“哪些数据块还空着”；inode bitmap 回答“哪些 inode 号还没被占用”；inode table 则进一步回答“某个 inode 号的元数据本体放在哪”。

这三者看似都在记元数据，实际上承担的是不同职责：

- 位图关心资源是否已被占用。
- inode table 关心已分配资源的具体身份信息。
- 数据块区才关心真实字节内容。

把这些角色分开，是位置可计算和分配快速化的关键。如果把“空不空”和“内容是什么”揉在一个模糊结构里，系统将很难既快速找空位，又快速定位已有对象。

### 6. 本节最该记住的结论：六段式布局的本质不是“教科书六个名词”，而是“每一段都承担一类可计算职责，合起来让文件系统摆脱全盘扫描”

所以请把六段式理解成一套职责分工，而不是段名列表：**有入口、有总规、有区目录、有两类空闲账本、有户籍册，最后才是数据本体。** 这样一来，位置才有可能被算出来，而不是靠扫出来。

## 三、SuperBlock：真正让内核敢说“这是一块 Ext2 文件系统”的，不是文件名后缀，而是这张总规里写死的几何、身份和恢复规则

### 1. 为什么挂载时第一件事不是找目录，而是先验证身份和几何

很多人从用户态角度理解文件系统，会先想到目录树、文件名和路径。但对内核来说，挂载一块设备时最先要做的不是“列目录”，而是确认这块设备到底是不是自己认识的文件系统、块大小和组大小该怎样解释、接下来所有定位公式是否成立。

也就是说，文件系统的第一步不是业务语义，而是格式身份校验与几何解释。SuperBlock 正是承载这件事的核心结构。

### 2. `s_magic` 为什么这么重要

`0xEF53` 之类 magic 值听起来像一个很小的细节，实际上它承担的是身份验证的最短路径。挂载时内核不可能盲信任何块设备都能按 Ext2 解释；它需要一个非常直接的签名，来避免后续把错误格式当成正确总规，从而把整张地图读歪。

所以 magic 值的价值，不在于神秘，而在于让“你到底是不是 Ext2”这件事能在极早阶段被快速确认或否认。

### 3. 块大小、每组 block 数、每组 inode 数为什么都必须出现在总规里

这几项字段听起来像普通参数，实际上决定了几乎所有后续定位公式。块大小一变，位图大小、inode table 展开方式、组容量边界和组内地址计算都会跟着变。每组多少 inode、多少 block，也决定了 inode 号和块号如何落到具体 group 和组内偏移。

换句话说，这些参数不是“挂载后可有可无的信息”，而是整个文件系统空间坐标系的刻度尺。没有它们，GDT、位图、inode table 的相对与绝对位置都无法被正确解释。若要补这一节的实现证据位，最关键的落点应回到 superblock 字段定义与 `fs/ext2/super.c` 中把这些字段读入内存并构成全局几何解释的路径：它们共同支撑“没有这些总规参数，后面的定位公式根本无从成立”这句判断。

### 4. root 保留块和挂载计数为什么又把“运营现实”带回来了

SuperBlock 里最有工程味的地方之一，是它不只记录抽象几何，还记录运营策略。比如保留块让 root 或关键维护路径在普通用户空间耗尽前仍有一点活动余地；挂载计数与状态位又服务于 fsck 与恢复节奏，提醒系统这块文件系统是不是长期处在需要更严格检查的状态。

这说明 SuperBlock 不是单纯的静态格式说明书，它同时还是一个“格式解释 + 运行健康状态”的复合总规。

### 5. 为什么备份策略是 SuperBlock 设计不可分割的一部分

如果 SuperBlock 是整张文件系统地图的解释器，那它一旦损坏，系统就会在“怎么读这块盘”这件事上当场失语。所以只保留一份正本风险太大。

Ext2 通过在特定 Block Group 中保留备份，让“总规损坏 = 整个文件系统失忆”这件事不那么绝对。备份不是额外小优化，而是总规本身生存能力的一部分。它不是帮你恢复某个文件，而是在帮整张城市规划图别一下子化为乌有。

### 6. 本节最该记住的结论：SuperBlock 既定义几何坐标，也定义身份与恢复前提；它是文件系统地图的解释器和心脏

所以一句最短人话是：**SuperBlock 不是“元数据中的一块”，而是“其余所有元数据如何被解释”的起点。** 没它，后面一切都失去参照系。

## 四、GDT 与 inode / block 位图：Ext2 之所以能快速定位和快速分配，不是因为“存得巧”，而是因为区目录和位图账本让查找变成公式与位运算

### 1. 为什么 inode 号能被直接换算到某个 Block Group

前面我们一直在说“位置可计算”，这里终于可以把这件事落成人话。只要 SuperBlock 告诉你每组有多少 inode，inode 号就不再是抽象编号，而能直接换算到“它属于第几个 group、是该 group 里的第几个 inode 槽位”。

也就是说，inode 号不是某种全盘随机 ID，而是一把可回推地理位置的索引钥匙。你不需要从磁盘头扫到尾找 inode 12345，而是先算出它落在哪个组，再通过该组的 inode table 起点和 inode 大小算出具体落盘位置。

### 2. GDT 为什么像“区办公室”而不是“总规备份”

因为 GDT 不再解释全盘规则，而是在某个组级别告诉你：block bitmap 在哪，inode bitmap 在哪，inode table 从哪开始。这是一份更贴近执行现场的目录。

有了它，系统从“我知道这张盘怎么解释”走到“我现在要去这个组里办事时，先去哪里找空地账本和户籍册”。它和 SuperBlock 是总规与区办的分工，而不是重复劳动。

### 3. 位图为什么比链表更适合做块和 inode 的空闲记账

如果 block 或 inode 的空闲状态用链表记，每个对象都得支付指针开销，还要面对碎片化和链表遍历问题。位图的优势在于极其省空间：1 bit 就能表达一个 block 或 inode 是否空闲；同时，“找下一个空位”这件事又能被实现成高效的按位扫描。

这让空闲记账同时兼顾了密度和随机访问能力。你不必为每个资源再养一个重型元数据节点，也不必在一大堆散对象里查谁空着。对文件系统这种按块和按 inode 管理的大规模资源池来说，位图是非常自然的选择。

### 4. 这套设计也暴露了文件系统的一条长期矛盾：位图很省，但从前往后扫也会带来布局偏好与长期碎片问题

位图的好处非常明显，但它并不自动保证最优分布。若分配策略总偏向某些方向，长时间运行后的块布局仍可能逐渐变得不够理想。这也是为什么后续 inode 直接/间接块、局部性和更现代文件系统布局策略会持续进化。

所以你不该把位图理解成“完美分配器”，而是“在空间成本和分配效率之间非常优秀的一层基础账本”。

### 5. 本节最该记住的结论：inode 定位靠组号公式 + 区目录，空闲资源分配靠位图；两者共同把“找对象”和“找空位”都从扫描退化成有界计算

所以一句最短人话是：**Ext2 的高效，来自两套不同账本的配合——GDT 让你知道去哪里找设施，位图让你知道设施里哪里还空着。**

## 五、Block Group 的真正价值：不是“把磁盘分几块”这么表面，而是同时在照顾局部性、并发分配和故障域收缩

### 1. 为什么“分组”是文件系统版的“把大问题拆成本地问题”

把磁盘切成 Block Group 后，很多原本必须从全局处理的问题都被压成了组内局部问题：本组哪个 block 空，本组哪个 inode 空，本组 inode table 在哪，本组数据块优先落哪。

这和前面内存卷里大量思想非常像：Buddy 不把全世界空闲页只放一锅，页缓存按 `address_space` 组织，cgroup 把主机内存拆成部门账。Ext2 的分组也是同一哲学：**只要全局管理太贵，就先拆成本地自治单元。**

### 2. 为什么局部性在这里比看上去更重要

如果 inode、位图和数据块在组内彼此接近，创建文件、找空位、读 inode、写数据时更有机会少做远距离跳转。这在机械磁盘时代尤其重要，即便今天底层设备形态变化，局部性仍然影响缓存与访问模式。

所以 Block Group 不只是行政便利，也是性能布局：它试图让“同一个文件或同一批相关元数据”更可能在相近地带活动，而不是天女散花地分散全盘。

### 3. 为什么“每组有自己的账本”也天然更利于并发与故障边界控制

多个线程、多个进程同时创建文件或分配资源时，如果所有人都盯着一份全局位图和单一 inode 区，冲突会更集中。分组之后，不同组上的分配路径有了更强的天然切分基础。

同时，如果某组局部损坏，影响面更容易局部化，不至于像“所有元数据都堆在一个中心区”那样一坏就全盘受伤。这并不等于文件系统就会轻松恢复，但它至少让损坏和救援不必从一开始就是全局灾难。

### 4. 本节最该记住的结论：Block Group 是 Ext2 同时服务于“位置可计算、局部性更好、竞争更分散、故障更局部”的核心折中单元

所以请把 Block Group 理解成整卷后面几篇都会反复回来的“文件系统基本行政区”。后面的 inode、创建、写数据和挂载权限，都会围着这张分区地图转。

## 六、把本篇收成一张图：Ext2 真正先做的不是“存文件”，而是“把磁盘规划成任何元数据和数据都能被算出来的位置体系”

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：格式化一块空盘后，文件系统怎么知道哪个扇区属于哪个文件。答案首先是否定了“线性摆放文件”与“全局元数据大集中”这两种天真模型。Ext2 先把磁盘主体切成多个 Block Group，再让每个组内部拥有固定职责的分段：SuperBlock 负责解释整张地图，GDT 负责列出每个区的关键设施位置，block/inode 位图负责空闲账本，inode table 负责元数据户籍册，data blocks 才真正承载文件字节内容。

这样一来，inode 号不再是只能扫描找的抽象编号，而能先计算组号，再结合组描述符和 inode table 起点推导出落盘位置；空闲块和空闲 inode 也不必挨个问，而可以在位图上按位寻找。Block Group 则把这一切从全盘级问题拆成了本地问题，顺手照顾了局部性、并发分配和故障域收缩。

把这一切压成最短总图，就是：

```text
入口层：
  Boot Sector 说明这块设备不是直接从文件系统正文开始

总规层：
  SuperBlock 定义身份、几何和恢复前提

区目录层：
  GDT 给出每个 Block Group 的关键设施坐标

账本层：
  Block Bitmap / Inode Bitmap 记录哪里还空

户籍层：
  Inode Table 记录文件元数据本体

数据层：
  Data Blocks 才是真正放内容的地方
```

所以本篇最该记住的一句话是：**Ext2 的第一原则不是“文件怎么排”，而是“磁盘上的任何关键位置都必须可算、可定位、可局部管理”；六段式 Block Group 结构正是这条原则的落地。**

## 七、几个最容易说错的地方

### 格式化之后，文件系统是不是就只是“空目录 + 空数据区”？

不是。格式化最先长出来的是整套布局结构：总规、区目录、位图、inode 表和数据区，而不是只有“以后放文件的空地方”。

### SuperBlock 是不是只记录总容量和块大小？

远不止。它还承担身份校验、保留块、挂载状态、恢复前提和备份策略等关键语义。

### GDT 是不是 SuperBlock 的重复副本？

不是。SuperBlock 讲全局规则，GDT 讲每个 Block Group 里关键设施具体在哪，是总规与区办的分工关系。

### 位图是不是只是一种“实现细节”，换成链表也差不多？

不对。位图直接决定了空闲资源记账的空间效率和查找方式，是 Block Group 可快速分配的核心基础之一。

### Block Group 是不是只是为了“分几块看着整齐”？

不是。它同时服务于位置可计算、局部性、并发分配和故障域收缩。

### 文件系统是不是从一开始就关心“文件内容放哪”，元数据布局只是附带的？

恰好相反。没有前面的元数据布局，系统连“内容放哪”和“怎么找到它”都无从谈起。

## 收束：看懂 Ext2 磁盘布局之后，你才会真正明白“文件系统”首先是一套空间治理学，而不是一组 API

回到开头那个问题：字节流怎么落到磁盘，文件系统又凭什么知道哪个扇区属于哪个文件？现在答案已经完整闭环了。它不是靠临时扫描、也不是靠把一切堆到磁盘前面，而是先用 Block Group 把磁盘切成多个可自治的行政区，再在每个区里放好总规、区目录、空闲账本、户籍册和数据区。正因为这张布局图先存在，inode 号、块号、空闲位和恢复路径才都有了可计算坐标。

也正因为如此，你会发现“文件系统”这件事从来不是先写几个系统调用接口，再想办法把数据存进去。它首先是一套空间治理学：怎么把原始块设备切出边界、定义单位、压缩记账成本、保证定位公式成立，并把故障与并发都控制在可管理的范围里。只有这一步成立，后面的 inode、目录、创建、读写、日志和挂载权限世界才有落脚点。

这就是为什么说：**文件系统的第一个难题不是“存文件”，而是“先把磁盘变成一张任何对象都能被算出来的地图”。** Ext2 的布局之所以值得单独讲一篇，正是因为后面所有文件系统行为，都是在这张地图上发生的。

## 八、误解清单、证据清单与边界清单

### 误解清单

- 格式化之后不等于只有“空目录 + 空数据区”；最先长出来的是整套布局结构和账本设施。
- SuperBlock 不只是容量和块大小说明书；它还承载身份校验、恢复前提、保留块和几何参数。
- GDT 不是 SuperBlock 的重复副本；它是组级设施目录，把全局总规落到每个 Block Group 的办事坐标上。
- 位图不是可替换成任何容器的细枝末节；它直接决定空闲资源记账方式与定位效率。
- Block Group 不只是“分几块看着整齐”；它服务于位置可计算、局部性、并发分配和故障域收缩。

### 证据清单

- 全局总规：`include/linux/ext2_fs.h` 与 `fs/ext2/super.c` 中 superblock 相关定义和读取路径，支撑“先解释整张地图，后续定位公式才成立”的主线。
- 行政分区：Block Group 相关布局定义与挂载解释路径，支撑“把全盘一锅账拆成每组自治小账本”的判断。
- 设施目录：组描述符定义与 GDT 解析路径，支撑“每个区的 block bitmap、inode bitmap、inode table 坐标如何被快速定位”。
- 空闲账本：block bitmap / inode bitmap 相关定义与使用路径，支撑“哪些资源空着、哪些已被占用”这两本最基础的分配账。
- 户籍册：inode table 位置与 inode 号到组号/表内偏移的计算关系，支撑“给定 inode 号如何不扫盘直接算出落点”的判断。

### 边界清单

- 本文讨论的是 Ext2 常见磁盘布局心智模型；块大小、sparse super、组描述符扩展和 mkfs 选项会随工具链和格式版本变化。
- 引导/分区入口语义和文件系统自己的布局语义是两层不同问题；Boot Sector 的存在主要是为了分清这两层。
- Block Group 讲的是空间治理地基，不自动等于后续 inode 索引、目录项语义或日志恢复细节；这些要在后续篇章继续展开。
- “位置可计算”不等于实现简单；它是通过固定布局、位图账本和组级设施目录换来的工程秩序。
- 本文先讲“磁盘怎么变成地图”；下一篇才真正进入“地图上的文件内容怎样被 inode 索引起来”。
