## 现在真正该问的，不再是“文件怎么存在”，而是“第一个字节写进去时，内核到底先碰了哪几层，又为什么 `write()` 成功了数据仍可能掉”

上一篇我们已经把文件创建打穿了。你知道 `touch a.txt` 的本质不是写内容，而是让名字、inode 和目录项三本账正式连起来：父目录里出现了 `a.txt -> ino`，inode 位图被占了一个号，group 统计也随之更新。一个 0 字节文件于是开始存在，但它还没有真正的数据块。

这时一个非常自然、也非常容易想错的问题就来了：**当程序第一次对它执行 `write(fd, "x", 1)` 时，那 1 个字节到底发生了什么？**

很多人会下意识觉得：既然我在写文件，而且系统调用也返回成功，那数据应该已经“写到磁盘上”了。这个直觉在现代缓存文件系统里通常是不成立的。

真正的写路径远比这复杂：

- VFS 先决定走哪条通用写主循环；
- 文件系统在真正 copy 字节前，先要搞清这个逻辑文件偏移对应哪一个物理块，必要时还得现场分配新块；
- 字节通常先被拷进 page cache，而不是直接流向磁盘控制器；
- 系统会同时把页缓存页、缓冲块、inode 这几层“以后需要回写”的账本记脏；
- `write()` 这时往往就可以返回了，而真正 submit 到块层、等待设备完成则留给 writeback 路径异步推进；
- 如果你不停猛写，前台线程还可能被 `balance_dirty_pages` 主动限速，不让脏页把内存水位冲穿。

所以本篇最重要的顿悟是：**对普通 buffered write 来说，`write()` 成功最常见的含义并不是“磁头已经落盘”，而是“内核已经接管了这些字节，并把它们安全挂进 page cache 与脏页账本”。**

先把总图记住：

```text
用户态入口：
  sys_write / vfs_write 接住请求

通用写主循环：
  generic_perform_write 按页或 folio 分段处理

文件系统关键职责：
  write_begin 前先确认逻辑块 → 物理块映射
  必要时分配新块并更新 inode 指针链

数据落点：
  字节先拷进 page cache
  相关 folio / buffer_head / inode 被标脏

真正落盘：
  后台 writeback 线程稍后提交 IO
  或者 fsync / 内存压力逼它提前完成
```

这一篇最重要的一句话是：**Ext2 写路径真正做的是“先把块号与缓存状态定下来，再把字节接进 page cache，最后把持久化责任留给后面的脏页与回写系统”。**

## 一、如果 `write()` 每次都同步等磁盘完成，语义当然简单，但文件系统和应用吞吐都会被自己拖死

### 1. 最朴素的错误世界：用户每写一次，内核立刻同步找到块、写盘、等设备确认，再返回

从最直观的正确性出发，这当然是最容易理解的写语义。你写一个字节，内核就立刻把它放到正确物理块，等设备彻底完成，系统调用再告诉你“好，成功了”。这样应用不用猜“数据现在到底在哪”，系统也没有所谓脏页积压的问题。

问题在于，它会把设备延迟直接绑定到每次用户态 write 调用上。小写很多时，系统会被大量细碎同步 IO 拖得非常痛，CPU 和磁盘之间也建立不起任何像样的批量与流水线。你等于是为了最朴素的“立刻完成”语义，把 page cache、writeback、延迟合并和后台回写这些现代文件系统赖以生存的性能手段全部废掉了。

这就像每次顾客往账本上添一笔，都要求会计立刻跑去银行柜台办一次完整转账，再回来回答“好了”。它当然精确，但会计厅会先被自己来回跑死。

### 2. 第二个失败方案：那就完全异步，只管把字节丢给内核，不做任何块映射和脏账记账

如果意识到同步落盘太贵，另一个极端就是“先把字节收下再说”。只要用户缓冲区内容被复制了，内核先别急着管这些字节最终属于哪个物理块、哪个 inode 脏了、哪张页后续要刷，等以后某个后台线程再慢慢猜。

这也不行。因为一旦把“块映射”“页缓存驻留”和“脏页责任”都推迟，系统后面会失去最基本的定位前提：到底哪张 page cache 页被改了，哪段文件逻辑块需要落盘，哪些 inode 应进入 writeback 队列，哪些块还需要先被分配出来。

所以 buffered write 虽然不要求立刻把数据送到设备，但并不意味着什么都可以晚点再说。恰恰相反，它需要**先把未来回写所依赖的定位账本和脏账本记清楚**，这样后面的异步持久化才不会变成瞎忙。

### 3. Linux 的答案：先在 write 路径里确定逻辑块落点与缓存归宿，随后再把持久化延后

这就是 Linux 写路径的核心取舍。它既不走“每次同步落盘”的重税路线，也不走“只复制字节、其余以后再猜”的拖延路线，而是把事情拆成两段：

- 前台 `write()` 先负责把逻辑文件偏移接入到明确的缓存页与磁盘块归宿上，并记好脏账；
- 真正的设备 IO 则交给后面的 writeback 机制异步推进。

于是 `write()` 的成功语义变成：**数据已经被内核可靠接手，并挂入正确的缓存/账本体系。** 这比“已经持久化”弱，但远比“随便先收下再说”强。后面 page cache、dirty pages、`fsync()` 和 writeback 的所有故事，都是在这个语义之上成立的。

## 二、`sys_write` 到 `generic_perform_write`：文件系统真正共享的不是“怎么找块号”，而是“把一个大写请求拆成页级循环并逐段推进”这套骨架

### 1. 为什么 Ext2 不需要自己重写一整套用户态写循环

你可能会以为，既然每个文件系统的磁盘格式不同，那每个文件系统连 `write()` 的主循环都得从头自己写。事实上，这样会带来大量重复：边界检查、把用户数据拆成页级片段、反复推进当前位置、处理部分成功等，都不是 ext2 特有问题，而是大多数 page-cache-backed 本地文件系统共同面对的通用写语义。

这正是 VFS 和 `generic_perform_write()` 这条公共骨架存在的原因。通用层负责把“用户请求写 N 个字节”转化为“按页/folio 逐段推进”的循环，而具体文件系统只需要在关键钩子上回答自己最懂的问题：我要把这一段写到哪里，块映射和回写时机该怎么处理。

### 2. `generic_perform_write()` 的核心价值：它把“写一个大缓冲区”降解成“若干次页级写事务”

从调用者看，`write(fd, buf, 8192)` 是一次连续写请求；从内核缓存世界看，它更像对若干 page cache 页面或 folio 的局部更新。因为 page cache 和文件偏移本来就按页组织，写路径自然也要按页推进。

所以 `generic_perform_write()` 真正做的不是“直接写磁盘”，而是把一个大请求拆成若干次小型页级事务：每次先让文件系统准备目标页和块映射，再把用户缓冲区这一段复制进去，最后做对应页的结束处理和脏账记账。

这一步非常重要，因为它把“用户的线性字节流”重新落回了前面你已经熟悉的 page cache 世界。文件系统不是在直接和原始用户缓冲区谈判，而是在逐页接管内容。若要把这一节补成更硬的源码正文，最关键的证据位应回到 VFS 通用写骨架与 `mm/filemap.c` 相关路径：它们共同支撑“`generic_perform_write()` 把大写请求拆成逐页事务，而文件系统只在关键钩子上回答块映射和提交细节”这句判断。

### 3. 为什么 `write_begin` / `write_end` 这种钩子分界特别合理

写前半段要解决“我能不能在这个位置安全修改 cache 页、底下块号是什么、必要时要不要先分块”；写后半段则更像“刚才那段字节已经拷进来了，现在该把哪些层级标脏、文件大小是否要更新、页状态是否要提交”。

这两个时刻的关注点完全不同，所以把它们分成 begin/end 两段比做成一个巨大钩子更清晰。begin 偏准备与定位，end 偏记账与提交缓存视图。

所以这并不是 API 形式主义，而是在把写路径的两个关键阶段显式拆开。

### 4. 本节最该记住的结论：大多数本地文件系统共享“页级写循环”这条通用骨架，真正的差异藏在块映射和提交细节钩子里

一句最短人话是：**VFS 和 `generic_perform_write()` 负责把“大写请求”拆成“逐页小事务”，文件系统只在关键节点回答“这页背后是谁、该怎么记账”。**

## 三、`ext2_write_begin` 与 `ext2_get_block`：Ext2 的写路径真正坚持的是“先把逻辑块翻译成物理块，必要时当场分配，再允许你改缓存”

### 1. 为什么空文件第一次写时，问题首先不是“拷哪个字节”，而是“这个逻辑块到底还没有家”

对一个刚 `touch` 出来的 0 字节文件来说，inode 和目录项都已经存在，但 `i_block[15]` 仍可能全是 0。也就是说，名字已经注册了，身份证也办好了，但“住址链”还没真正指向任何数据块。

这时你执行第一次 `write()`，最先遇到的麻烦不是“把 1 个字节写到页缓存哪一页”，而是“这个文件逻辑块背后到底对应哪个磁盘块”。如果连底层块号都没有，page cache/buffer_head 也无从知道自己到底代表的是哪段磁盘空间。

所以 Ext2 的写路径有一个非常鲜明的立场：**真正 copy 字节前，逻辑块必须先找到或分配好物理块。** 证据位上，这层最值得回到 `fs/ext2/inode.c` 中 `ext2_write_begin()`、`ext2_get_block()` 与块位图/间接块更新相关路径去看：它们共同支撑“Ext2 在写时先把逻辑块落到真实物理块上，再允许你改缓存”这句判断。

### 2. 为什么 Ext2 选择在写入时立即分块，而不是先记个逻辑欠条

Ext2 的典型路径是 allocate-on-write：用户一写到某个还没有物理块的文件逻辑位置，就在 `write_begin` 阶段通过 `ext2_get_block(create=1)` 把块号真正定下来，必要时现场从 block bitmap 领一个新块，再更新 inode 的指针树。

这样做的最大好处，是地址关系很早就稳定。页缓存里的这段脏数据从一开始就知道自己最终要落到哪个磁盘块，buffer_head 和 inode 账本也更容易形成一致。

代价是碎片和灵活性。你如果对同一文件做很多零碎小写，Ext2 可能很早就把物理块一个个定死，失去后续把许多脏页合并成更连续 extent 的机会。这正是 ext4 delayed allocation 想要改掉的地方。

### 3. `ext2_get_block` 为什么是 inode 指针树第一次真正为“写”服务的现场

前一篇我们讲过 `i_block[15]` 如何索引已有数据。到了写路径，这套指针树第一次从“查已有块”升级成了“必要时边查边长新枝”。

如果目标逻辑块原本已有映射，`ext2_get_block` 只是把现成物理块号交出来；如果没有，就要沿 inode 的索引树确定该在直接块、一级间接还是更深层级补新块，必要时还得先给间接块本身分配空间。

这意味着写路径不是纯消费 inode 索引结构，而是在第一次写入某些逻辑区间时主动扩张这棵树。创建文件给你的是空白身份证，第一次写才让这张身份证开始真正拥有住址链。

### 4. block bitmap 为什么在这一刻正式登场

这也是第一篇和第三篇埋下的账本终于会师的地方。创建文件时改的是 inode bitmap；第一次真正写新数据块时，block bitmap 才第一次被迫承认：“好，这个 block 以后归这个文件了。”

所以如果把创建文件理解成“拿到身份证”，那第一次写更像“开始领房子和地址”。没有这一步，文件存在归存在，内容依然无处可落。

### 5. 本节最该记住的结论：Ext2 写路径在 copy 字节前先完成“块号落座”，好处是地址早稳定，代价是更容易较早锁定碎片布局

一句最短人话是：**Ext2 的缓冲写不是“先写缓存以后再想块号”，而是“先把块号落实，再让缓存承接字节”。**

## 四、copy + dirty：对普通 buffered write 来说，真正的“已写入”时刻是字节进了 page cache 且三层脏账都记好了，而不是磁盘中断回来那一刻

### 1. 为什么 CPU 并不是在直接把用户缓冲区字节推给磁盘控制器

很多人对 `write()` 的直觉仍停留在“字节一路流向磁盘”。这在裸设备直通思维里或许好想象，但对常规 page-cache-backed 写路径来说并不准确。CPU 最先做的事，是把用户态缓冲区中的内容拷进内核已经准备好的 page cache 页或 folio。

这一步完成后，字节已经离开用户空间，进入文件系统和页缓存共同负责的缓存现实。但它们离设备还很远。

### 2. 为什么 folio、buffer_head 和 inode 三层都必须被标脏

只把 page cache 页标脏还不够，只把 inode 标脏也不够。它们承担的视角不同。

- folio/page 脏，表示“这一页缓存内容被用户改过了”。
- buffer_head 脏，表示“在这页里，哪些具体磁盘块片段需要刷”。
- inode 脏，表示“这个文件对象现在有待写回的数据或元数据，需要进入更高层 writeback 账本”。

这三层就像局部账、分项账和总账。只有一起记明白，后面的 writeback 才既知道哪页内容变了，也知道这个文件本身正处在需要回写的队列里。若要补这一节的实现锚点，最关键的落点应回到页缓存脏页标记、buffer_head 脏标记以及 inode 进入 writeback 账本的相关路径：它们共同支撑“不是只脏一层，而是 folio/buffer_head/inode 三层协同立账”的判断。

### 3. 为什么 `write()` 的成功点会被放在这里

一旦字节已从用户缓冲区复制进 page cache，且相关脏账已经成功记账，系统通常就认为自己已经“接管”了这次写入。用户态缓冲区可以被复用、修改或释放，因为后续落盘责任已经转移到内核。

这时设备是否真的完成写回，不再属于当前普通 `write()` 的最强保证。真正要求“数据已经持久化到稳定后备”时，调用者应当用 `fsync()`、`fdatasync()` 等更强接口明确发问。

这也就是为什么很多掉电场景会打醒初学者：`write()` 返回 1，不代表磁盘上真的已经有那 1 个字节。它只代表内核说“这笔账我接手了”。

### 4. 为什么说 page cache 是“已写入”和“已持久化”之间最重要的中间现实

你可以把 page cache 看成写路径里的缓冲现实世界。用户态和磁盘之间并没有直接手拉手，page cache 正是在中间托住语义、吞吐和异步写回可能性的那一层。没有它，系统要么每次同步慢到爆炸，要么缺乏足够的中间账本组织能力。

所以“数据先进入 page cache，再异步落盘”不是某种实现小技巧，而是现代 buffered write 语义成立的核心。

### 5. 本节最该记住的结论：普通 `write()` 成功通常表示“字节进了 page cache 且脏账立好了”，而不是“设备已经完成持久化”

一句最短人话是：**`write()` 最常见的成功语义，是内核成功接手了数据，不是磁盘已经认领了结果。**

## 五、`balance_dirty_pages` 与 `wb_workfn`：没有前台限速和后台 writeback 的配合，脏页要么把内存吃爆，要么让每次写都同步痛死

### 1. 为什么“只异步不控量”会把内核自己拖进泥潭

page cache 让 `write()` 可以先快返回，这是好事。但如果系统只会接收脏页、不管积压速度，前台写者完全可能比后台设备快很多。这样脏页越来越多，最终不是把内存吃满，就是让回收和写回体系被巨量待处理页拖得抖动严重。

所以异步不是“你只管写，系统永远能在后面慢慢追上”。它必须配套一套水位与限速逻辑，让前台感知到“你已经写得远快于后端现实了”。

### 2. 为什么“每次写后都强制同步刷一波”又走回了另一个极端

反过来，如果你害怕脏页积压太多，于是决定在每次写后都强行触发同步刷盘，那么 buffered write 的主要价值也就没了。前台线程会被设备延迟拖住，page cache 只剩下短暂的中转意义。

这说明真正好的策略，既不能完全放任脏页狂长，也不能把异步写回退回成同步落盘。

### 3. Linux 的折中：前台写路径管制造与适度自限，后台 writeback 线程管持续排水

这就是第 7 篇内存卷 writeback 哲学在文件写路径里的直接体现。文件系统写入时，前台线程把字节写进 page cache 并标脏；后台 `wb_workfn` 等 writeback 路径则在合适时机调用 `writepages` 把这些脏页真正送往设备。

当前台脏页制造速率超过后端排水能力时，`balance_dirty_pages` 一类逻辑会开始让当前线程适度 sleep 或减速，让整台机器别被脏页洪水冲垮。于是写路径最终变成一套“前台入账、后台出账、必要时前台协同减速”的平衡系统。

### 4. ext2 写路径和 ext4 delayed allocation 为什么在这里分叉

这也是一个非常值得对照的点。Ext2 在 `write_begin` 时就把真实物理块定下来，所以 page cache 中的脏页从一开始就知道自己最终对应哪块磁盘位置；而 ext4 delayed allocation 则把“先接收脏页”和“最后挑一块连续物理位置”尽量拉开，让后者更有机会按全局脏页分布做更漂亮的连续 extent 分配。

Ext4 因此更容易减少碎片和提升连续写质量，但也意味着 `write()` 成功时，连最终块号都可能尚未彻底落定。于是“成功”和“真正持久化”之间的距离被拉得更远。

### 5. 本节最该记住的结论：写路径的现代平衡不是“写完即落盘”，而是“前台先把数据与账本接住，后台持续排水，当前台太快时再反过来给它踩刹车”

所以一句最短人话是：**普通文件写不是直写磁盘，而是一场 page cache 蓄水、后台 writeback 排水、前台脏页限速共同维持的平衡术。** 证据位上，这层最值得回到 `mm/page-writeback.c` 与相关后台回写/脏页限速路径去看：它们共同支撑“前台并不是一直自己等磁盘，而是在后台 writeback 和 `balance_dirty_pages` 的控制链里与后端吞吐做平衡”这句判断。

## 六、把本篇收成一张图：`write()` 成功真正代表的，是“字节、块号和脏账都已进入内核秩序”，而不是“设备已完成承诺”

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：文件已经诞生，但第一个字节到底怎样真正写进去。答案首先不是“用户缓冲区直接打到磁盘”，而是先走 VFS 与 `generic_perform_write()` 这套页级写骨架。通用层把大写请求拆成逐页事务，文件系统则通过 `write_begin`/`get_block` 回答底层块号问题。

Ext2 的鲜明特征是 allocate-on-write：逻辑块第一次写入时，`ext2_get_block(create=1)` 就会沿 inode 指针树找到或现场分配真实物理块，block bitmap 也在这里第一次被改动。块号确定后，用户字节才被 copy 进 page cache 页；随后 folio、buffer_head 和 inode 三层脏账同时被记上。对普通 buffered write 来说，这时 `write()` 往往就已经可以返回——因为内核已经接手了数据与责任。

真正的持久化则由后面的 writeback 路径推进：后台 `wb_workfn` 调用 `writepages` 把脏页送到底层设备，而 `balance_dirty_pages` 则在前台写得过快时适度限速，避免脏页把内存和回写系统一起拖垮。Ext4 delayed allocation 进一步表明：不同文件系统甚至会把“块号何时真正落定”也拉到更靠后的位置，以换取更少碎片和更大连续 extent。

把这一切压成最短总图，就是：

```text
入口层：
  sys_write / vfs_write 接住请求

通用骨架：
  generic_perform_write 按页推进

文件系统职责：
  write_begin 前先定逻辑块 → 物理块
  必要时修改 block bitmap 与 inode 指针树

缓存与账本：
  字节先进 page cache
  folio / buffer_head / inode 同时标脏

真正落盘：
  后台 writeback 提交 IO
  前台必要时被脏页限速拖住
```

所以本篇最该记住的一句话是：**`write()` 返回成功，最常见的含义不是“数据已持久化”，而是“数据、块号和脏账本都已经纳入内核的写缓存秩序”；设备何时真正落盘，是后面的 writeback 世界在继续兑现。**

## 七、几个最容易说错的地方

### `write()` 成功是不是就代表磁盘已经把数据写好了？

通常不是。更常见的情况是数据已经进入 page cache 并记脏，真正持久化还在后面的 writeback 路径里。

### ext2 第一次写空文件时是不是只改 page cache，不改磁盘账本？

不是。必要时它会先分配真实数据块，修改 block bitmap，并更新 inode 的块索引结构。

### `generic_perform_write()` 是不是 ext2 特有的写逻辑？

不是。它是很多本地文件系统共享的通用写骨架，ext2 只在关键钩子上提供自己的块映射与提交逻辑。

### page cache 脏了是不是只需要标一层 dirty？

不够。fol io/page、buffer_head 和 inode 三层脏语义承担不同视角，后续 writeback 需要它们协同。

### ext4 delayed allocation 是不是只是“写得更晚一点”这么简单？

不是。它本质上是在把“先接数据”与“最后挑物理块”解耦，以换取更连续的 extent 和更少碎片。

### `fsync()` 是不是可有可无，只是让写更保险一点？

不是。若你真正关心持久化语义，`fsync()` 之类接口是在普通 `write()` 只承诺“内核已接手数据”之后，继续追问“设备是否已经完成”的关键手段。

## 收束：看懂写路径之后，你才会真正明白“文件里出现了一个字节”在 Linux 里往往先是缓存事实，再是持久化事实

回到开头那个问题：第一次往文件里写字节时，内核到底先碰了哪几层，又为什么 `write()` 成功了数据仍可能掉？现在答案已经完整闭环了。写路径先在 VFS 通用骨架里把请求拆成页级事务，再由 ext2 在 `write_begin` 阶段搞定块号与必要的块分配，随后把用户字节拷进 page cache，并把相关 folio、buffer_head 和 inode 三层一起记脏。只有这样，内核才有资格说“这笔写入我已经接手”。

也正因为如此，你会发现文件系统里的“已写入”其实分成了两个世界：缓存事实和持久化事实。前者发生在 page cache 与脏账本，后者发生在 writeback 和块设备。普通 `write()` 更多是在完成第一件事，而不是第二件事。真正理解这层分裂之后，你再看 `fsync()`、掉电丢数据、脏页限速和 ext4 delayed allocation，就不会再把它们误解成“奇怪的额外复杂度”，而会看成缓存文件系统必须承担的性能与一致性平衡。

这就是为什么说：**文件写入的第一现场不是磁盘，而是 page cache；磁盘是后续履约地点，而不是普通 `write()` 的默认完成点。**

## 八、误解清单、证据清单与边界清单

### 误解清单

- `write()` 成功不等于磁盘已经写完；普通 buffered write 最常见的现实是“内核已接手并记脏”。
- Ext2 第一次写空文件不只是改 page cache；必要时它会先分配真实数据块并更新 inode 指针树。
- `generic_perform_write()` 不是 ext2 私有逻辑；它是很多本地文件系统共享的通用页级写骨架。
- page cache 脏了不等于只脏一层；folio/page、buffer_head 和 inode 三层承担不同账本视角。
- ext4 delayed allocation 不是“晚一点再写”这么简单；它本质上把“先接数据”和“最后挑物理块”解耦，以换更连续布局和更少碎片。

### 证据清单

- 通用写骨架：VFS 通用写路径与 `mm/filemap.c` 相关实现，支撑“把大写请求拆成逐页事务”的主线。
- 文件系统块映射：`fs/ext2/inode.c` 中 `ext2_write_begin()`、`ext2_get_block()` 及块位图/间接块更新路径，支撑“先定块号再改缓存”的 Ext2 立场。
- 三层脏账：页缓存脏页标记、buffer_head 脏标记以及 inode 进入 writeback 账本的路径，支撑“folio/buffer_head/inode 三层协同记账”的判断。
- 后台排水：`mm/page-writeback.c` 与相关 writeback worker 路径，支撑“真正落盘是后续履约阶段”的主线。
- 前台限速：`balance_dirty_pages` 与脏页限速相关路径，支撑“前台写得太快时，系统如何把后端吞吐现实反传回来”的控制链。

### 边界清单

- 本文讨论的是 Ext2 buffered write 的稳定心智模型；VFS 骨架、folio/buffer_head 细节、阈值和 ext4 分配器行为会随内核演进变化。
- 写路径里“已写入”与“已持久化”是两种不同语义；真正 durability 仍要结合 `fsync()`、文件系统和设备缓存理解。
- `generic_perform_write()` 讲的是通用骨架，不等于所有文件系统在块映射与提交策略上都一样。
- ext4 delayed allocation 放在本文是为了做对照，不意味着 Ext2/Ext4 在块号落定时机上只是参数差异。
- 本文先讲写入如何进入缓存现实；下一篇读路径会从另一面讲“磁盘现实怎样再被搬成缓存现实”。
