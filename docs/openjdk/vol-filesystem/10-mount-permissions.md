# 挂载与权限管理：`mount /dev/sda1 /mnt` 真正做的，不是“把分区显示出来”，而是把盘上的结构翻译成 VFS 世界的一棵可遍历树，再在每次访问时逐层做门禁判定

## 现在真正该问的，不再是“磁盘内部结构怎样自洽”，而是“这些结构怎样通过一次 `mount` 进入系统调用可见的世界，并在每次 open/read/write 时变成一套门禁系统”

到上一章为止，文件系统卷已经把磁盘内部世界几乎走通了：从 Ext2 的块组布局、inode 索引树、文件创建、读写、删除，到 ext4 的 JBD2、Btrfs/ZFS 的 COW 路线，你已经看见了一套盘上结构如何自己组织、更新和恢复。

可这些故事还有最后一层非常关键的回接没讲：**这些盘上的结构到底怎样被接进 Linux 的 VFS 命名空间，让用户看到 `/mnt` 这条路径，并通过它一路 `ls`、`open`、`read` 到某个文件？**

也就是说，磁盘世界再完整，如果没有一条从块设备结构翻译到 `struct super_block`、`struct inode`、`dentry` 和 mount namespace 的通道，它仍只是“盘上的数据”，不是“系统里的一棵树”。

而一旦这棵树被接进来了，另一个问题立刻跟上：**谁可以走进这棵树里的哪扇门？** 这就把我们带到权限系统：经典 rwx 位、capability 旁路、ACL 细粒度授权，为什么要叠在一起而不是只看一个 `chmod 755`。

所以本篇最重要的顿悟是：**挂载解决的是“盘上结构如何变成 VFS 世界里一棵活树”，权限解决的是“树接进来之后，哪个进程能走到哪一层”。**

先把总图记住：

```text
挂载：
  sys_mount / vfs_kern_mount 选择文件系统类型
  具体文件系统读盘上 superblock
  构造内存中的 struct super_block
  读取 root inode
  构造 root dentry
  把这棵树挂进命名空间

访问控制：
  路径遍历到 inode 后
  先看 mode bits(owner/group/other)
  再考虑 capability 特权旁路
  若存在 POSIX ACL，再做更细粒度裁决
```

这一篇最重要的一句话是：**挂载真正完成的标志，不是“设备打开了”，而是“磁盘格式已经被翻译成 `super_block + root inode + root dentry` 并接入 VFS 路径树”；权限判定真正看的，也从来不只是一个 `755`。**

## 一、如果没有挂载这一步，磁盘上的文件系统即使结构完整，也只是“能被解释的原始块”，还不是命名空间里的一棵树

### 1. 最朴素的误解：`mount` 只是让目录里“显示出”另一个分区内容

很多人从命令行直觉出发，会把 `mount /dev/sda1 /mnt` 理解成一种 UI 行为：之前 `/mnt` 目录是空的，mount 之后“那里显示出了分区内容”。

这种说法抓住了表象，却完全忽略了底层最关键的变化。因为分区内容并不是早就以“目录树”的形式躺在内存里等着显示，而只是盘上的 superblock、inode table、数据块和其他元数据结构。它们必须先被某个文件系统驱动读出来、解释成内存中的 VFS 对象，才能变成可路径遍历的根。

也就是说，mount 不是“显示已有树”，而是**把盘上结构第一次翻译成 VFS 世界的一棵可活用的树。**

### 2. 第二个失败理解：那 VFS 自己读一遍磁盘 superblock，不就能统一挂任何文件系统了？

如果只看 VFS 抽象层，似乎它知道 superblock、inode、dentry 这些通用运行时对象，那么它直接读盘，应该也能统一挂载任何文件系统。

这很快就会撞墙。因为 VFS 知道运行时树长什么样，但它并不知道 Ext2、Ext4、XFS、Btrfs 在盘上如何编码块大小、superblock 位置、根 inode 号、日志/校验结构和特定操作集。它无法仅凭抽象接口就猜出磁盘格式。

所以挂载天然必须分层：**VFS 负责统一挂载框架，具体文件系统负责把自己的盘上字节解释成这套统一框架能消费的运行时对象。**

### 3. Linux 的答案：先选文件系统类型，再由该类型的 mount/fill_super 回调把盘上格式翻译成 VFS 世界

这就是 `sys_mount` 到 `vfs_kern_mount` 这一层最重要的结构意义。VFS 不亲自决定某块设备上的 superblock 长什么样，也不亲自猜根目录 inode 在哪；它只负责：

- 找到你说的文件系统类型；
- 建立一个挂载实例；
- 调用该文件系统自己的 mount / fill_super 路径；
- 等它把盘上世界翻译成 `super_block` 与 root dentry 之后，再把它接进命名空间。

所以如果只记一句关于挂载的最短人话，可以这样说：**VFS 提供挂载舞台，具体文件系统提供翻译器。**

## 二、`sys_mount` → `vfs_kern_mount`：挂载链路真正先做的不是读目录，而是确定“我现在到底要让谁来解释这块盘”

### 1. 为什么挂载的第一问题是“类型是谁”，而不是“根目录在哪”

从用户视角看，挂载后最在意的是“/mnt 下面会出现什么”。可对内核来说，在还不知道这块设备是 ext2、ext4、xfs 还是别的之前，谈根目录位置纯属空中楼阁。

因为“根目录 inode 在哪”“superblock 在哪”“块大小是多少”“挂载选项如何解释”，全都依赖于文件系统类型本身。挂载首先是选择解释规则，再谈读取具体对象。

### 2. `vfs_kern_mount` 的角色为什么像总装线而不是工匠本身

这个名字很容易让人误解成“VFS 在内核里直接挂设备”。更准确的理解是，它更像总装线：负责组织挂载实例、调用文件系统类型对象提供的回调，并在成功后拿到一个可用的 `vfsmount`/挂载对象与超级块关系。

真正做“翻译盘上结构”细活的，还是 ext2、xfs、btrfs 等文件系统自己的代码。VFS 更像负责把各家工匠都接到统一流水线上的总装厂。

### 3. 为什么说这里已经在做“块设备世界”与“命名空间世界”的第一次翻译

块设备世界关心的是某个 `/dev/sda1` 这种设备入口；命名空间世界关心的是 `/mnt` 这类路径树接点。挂载把这两者第一次接起来：一个是要被解释的原始设备来源，一个是解释成功后要插入系统路径树的位置。

所以 mount 不是单纯对设备做事，也不是单纯对目录做事，而是在拉起一座桥：**左手抓设备，右手抓命名空间挂点，中间靠文件系统驱动把盘上世界翻译成树。**

### 4. 本节最该记住的结论：挂载链路的第一阶段，是“先决定谁有资格解释这块盘”，再由它构造后面的树

一句最短人话是：**在 root dentry 出现之前，mount 最先做的并不是找文件，而是先找翻译器。**

## 三、`ext2_fill_super`：这一步真正完成的不是“把 superblock 读进来”，而是把一组磁盘参数、操作集和根对象拼成一个活的 `struct super_block`

### 1. 为什么“读到 superblock 字节”距离“文件系统已挂好”还差得很远

第一篇我们讲过磁盘 superblock：它是总规、几何参数和恢复前提的入口。可现在你必须再进一步理解：**盘上的 superblock 字节本身并不是 VFS 世界里的 super_block 对象。**

只有当具体文件系统把这些字节读进来、校验 magic、解释块大小、初始化运行时私有信息、挂上 `s_op` 等操作集，再把根 inode 也找出来时，VFS 才真正得到一个可工作的 `struct super_block`。

也就是说，fill_super 不是“read once and done”，而是“把盘上总规翻译成运行时总控对象”的完整装配阶段。

### 2. 为什么 `s_magic`、块大小和 group 信息在这里才第一次变成“运行时事实”

在盘上，这些只是字节；到了 `ext2_fill_super`，它们开始变成 VFS 和 ext2 驱动之后所有决策的真实参数：块多大、组多少、inode 每组多少、根 inode 该怎么取、哪些操作集该挂到 `sb` 上。

这说明挂载不仅是“把已有对象读出来”，还是“把纯存储格式参数提升成运行时行为配置”。同样的盘，如果这一步解释错了，后面整个路径树都会搭歪。

### 3. 为什么 `sb->s_op` 这种操作集挂接也是 superblock 成为“活对象”的关键一环

只读参数还不够。一个活的文件系统实例还必须知道自己之后怎样写 inode、怎样回收、怎样统计、怎样同步。也就是说，它得有行为，不只是状态。

这就是 `super_block` 与简单“盘上 superblock 镜像”的差别：前者是一个带操作集和运行时私有数据的活对象，后者只是字节格式说明书。挂载真正完成前，内核必须让它从说明书长成一个能响应 VFS 请求的对象。

### 4. 本节最该记住的结论：`fill_super` 的本质是“把盘上的总规字节翻译并组装成一个带行为的运行时超级块实例”

一句最短人话是：**盘上 superblock 是图纸，内存里的 `struct super_block` 才是已经装配好的机器。**

## 四、root inode 与 root dentry：文件系统真正可遍历的起点，不是“读到了 inode#2”，而是“这个 inode 已经被接成了命名空间里的根路牌”

### 1. 为什么单有 root inode 仍不足以让 `/mnt` 可走

第二篇我们已经知道 inode 是内容身份证，目录是特殊文件。但就路径遍历而言，inode 只回答“这个对象是什么”；它还不回答“这个对象在当前名字树里挂在哪”。

这也就是为什么挂载不能只停在“读出根 inode”。若没有 dentry，路径遍历系统就没有名字入口去指向它，VFS 世界里的 `/mnt` 依然不会突然变成一棵新树的门口。

### 2. `d_make_root` 这种动作为什么是本篇最该记住的提交点之一

可以把它理解成和第三篇文件创建里的 `d_instantiate` 有相似味道：都是把一个 inode 真正接进名字世界。创建文件时，是把普通文件名和 inode 绑定；挂载根目录时，则是把整个文件系统的 root inode 绑定成 root dentry。

一旦 `sb->s_root` 成立，这个 superblock 才第一次拥有“从哪进入这棵树”的正式入口。没有这一步，superblock 仍像一台没有门牌的建筑：结构全在，入口未公开。

### 3. 为什么说 `/mnt` 之所以突然可见，本质上是“另一棵根树被 graft 进了当前命名空间树”

用户态看到的是：原先普通目录 `/mnt`，mount 后变成另一个文件系统的入口。内核里真正发生的，是当前命名空间把新超级块的 `s_root` 接到了这个挂点上。换句话说，不是“/mnt 被填充了内容”，而是“/mnt 变成了另一个 root dentry 的路由口”。

这也解释了为什么 mount namespace 会显得那么重要：挂载不是静态修改磁盘，而是在运行时重接路径树。不同命名空间完全可以因此看到不同的树接法。

### 4. 本节最该记住的结论：挂载真正完成的标志，不是设备可读、也不是 root inode 找到了，而是 `sb->s_root` 已经作为 dentry 被接进 VFS 路径树

一句最短人话是：**根 inode 只是城市档案，root dentry 才是挂在城门口的路牌。**

## 五、权限判定：`chmod 755` 只是第一层门禁，真正的放行或拒绝还要继续看进程身份、capability 和 ACL

### 1. 为什么“看 owner/group/other 三组 rwx 位”只解释了最经典的那个表面模型

教科书权限模型往往到 `rwxr-xr-x` 就打住了，好像 VFS 访问控制本质上就是按 owner/group/other 三档位匹配。这个模型在入门上很有价值，但如果只停在这里，你会立刻解释不通很多现实：

- 为什么 root 能绕过大量普通 DAC 限制？
- 为什么同一个组里想只给 Alice 单独多一点权限，用 `chmod` 表达不了？
- 为什么路径遍历、读目录和打开文件有时权限要求又不完全一样？

这说明 mode bits 只是经典 DAC 世界的第一层，而不是全部。

### 2. 传统 rwx 判定究竟解决了什么

mode bits 的核心价值是提供一个最普遍、最轻量的三层门禁：对象 owner 看 owner 位，匹配组看 group 位，其他人看 other 位。绝大多数普通文件权限问题，都可以先在这里被判掉。

它的优点是简单、紧凑、盘上 inode 自带、路径遍历时开销低。也正因为如此，它始终是第一道门，而不是被 ACL 或 capability 完全取代。

### 3. capability 为什么说明“root 特权”本质上已经从 uid=0 的神话里被拆出来了

现代 Linux 不再满足于“谁是 root 就无所不能”这种粗暴二元世界。capability 框架把传统特权切成一组可独立授予和检查的能力。像 `CAP_DAC_OVERRIDE`、`CAP_DAC_READ_SEARCH` 这种能力，本质上是在说：**这个进程可以在某些 DAC（离散访问控制）检查上走旁路。**

这意味着“绕过 rwx 三位限制”并不是 inode 上有什么特殊位，而是进程凭据里带着另一层更高权限语言。这就是为什么 capability 应该被理解成“门禁总控卡”，而不是“另一个 chmod”。

### 4. ACL 为什么说明“三组位”的表达力天生有限

一旦你希望“只给 alice 一个命名用户权限，但不想让整个 group 一起获权”，经典三组位就失语了。ACL 的价值正在于此：它把原本广播式的三档门禁，扩成了可命名用户/组的白名单体系，同时通过 `MASK` 这类上限保持与传统语义兼容。

这意味着权限世界也和文件系统演化主线类似：最简单的固定字段解决最广泛的共性，但细粒度场景迟早要引入一层外挂语义。前面第六篇讲过 xattr/ACL 的物理外挂，这里则把它的判定语义接回来了。

### 5. 为什么说权限判断最终是“进程凭据 × inode 元数据 × ACL/capability”的交叉裁决

这句话非常值得牢记。没有哪个单层足够决定最终结果：

- inode mode bits 提供基础门禁；
- 进程的 fsuid/fsgid 决定你先落在哪一档；
- capability 可能在某些场景给你旁路资格；
- ACL 又在需要时补上细粒度例外规则。

所以权限不是“看一眼 755”，而是一场交叉匹配。只有这样你才能真正理解为什么同一个文件在不同身份、不同命名空间和不同安全配置下，判定结果会不同。

### 6. 本节最该记住的结论：mode bits 是第一层，capability 是特权旁路层，ACL 是细粒度例外层，三者叠起来才是现代 VFS 世界里的完整门禁

一句最短人话是：**`chmod 755` 只是门锁面板，capability 是万能卡，ACL 是白名单补丁。**

## 六、把本篇收成一张图：挂载解决的是“如何把盘变成树”，权限解决的是“谁能沿这棵树继续往里走”

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：盘上的 ext2/ext4/Btrfs/ZFS 结构到底怎样通过一次 `mount` 进入系统调用可见的世界。答案首先不在“显示分区内容”，而在挂载链路按层分工：VFS 先选择文件系统类型，再调用对应驱动的 mount/fill_super 路径，把盘上的 superblock、块大小、组信息和 root inode 翻译成内存里的 `struct super_block`、操作集和 `sb->s_root`。只有当 root inode 已经长成 root dentry 并被接进命名空间树时，文件系统才真正对 `/mnt` 这类路径可见。

接着，树接进来并不意味着谁都能随便走。访问控制以 inode mode bits 作为第一层通用门禁，再叠加 capability 的特权旁路和 POSIX ACL 的细粒度例外规则。于是 `chmod 755` 不再是全部真相，而只是第一道过滤。进程身份、ACL 白名单和特权能力共同决定这扇门最终是开是关。

把这一切压成最短总图，就是：

```text
接树：
  mount 选定文件系统类型
  fill_super 把盘上总规翻译成运行时 super_block
  root inode → root dentry
  sb->s_root 接进命名空间树

判门：
  mode bits 提供基础 DAC
  capability 提供特权旁路
  ACL 提供细粒度命名授权
```

所以本篇最该记住的一句话是：**挂载的本质，是把块设备上的文件系统结构翻译并接成 VFS 世界的一棵活树；权限的本质，是在你真正沿着这棵树走动时，再按 inode、凭据、ACL 和 capability 层层裁决你能走到哪。**

## 七、几个最容易说错的地方

### `mount` 是不是只是“把分区显示在目录里”？

不是。它真正做的是把磁盘格式翻译成内存里的 super_block、inode 和 dentry 关系，再挂接进命名空间树。

### VFS 是不是自己就能统一解释所有磁盘 superblock？

不能。VFS 只提供统一框架，具体 on-disk 格式必须由 ext2/ext4/xfs/btrfs 等文件系统自己的回调解释。

### root inode 读出来是不是就等于挂载完成？

还不够。真正的完成标志是 `sb->s_root` 已经作为 root dentry 存在，并能被路径遍历入口使用。

### 权限判断是不是就是“看 chmod 755”这么简单？

不是。mode bits 只是第一层，后面还有进程身份匹配、capability 旁路和 ACL 细粒度授权。

### root 能访问是不是因为 inode 上有“root 特权位”？

不是。更多是 capability 框架在 DAC 之上提供了旁路能力，而不是 inode 本体里有什么特殊 root 开关。

### ACL 是不是完全取代了传统 rwx 三组位？

不是。传统 mode bits 仍是基础门禁，ACL 更像在其之上叠加细粒度命名授权与 mask 约束。

## 收束：看懂挂载与权限之后，你才会真正明白“文件系统进入系统世界”和“用户能否走进文件世界”其实是两套彼此咬合但完全不同的问题

回到开头那个问题：这些磁盘上的结构，最后是怎样被读进 `struct super_block`、挂到 dentry 树上，并接入整棵 VFS 路径世界的？现在答案已经完整闭环了。挂载链路先确定谁来解释这块盘，再由具体文件系统驱动把磁盘上的 superblock、root inode 和操作集翻译成内存里的活对象，最终通过 `sb->s_root` 接进当前命名空间。于是盘上的结构第一次不再只是块，而变成了系统里真正可遍历的路径树。

而一旦这棵树被接进来，第二个问题就立刻站起来：谁能往树里走？这时 mode bits、capability 和 ACL 才开始接力，把“文件系统可见”进一步区分成“对哪些进程可进入、可读、可写、可执行”。也就是说，挂载解决的是存在性和接入，权限解决的是访问资格和边界。

这就是为什么说：**文件系统不是 mount 完就结束，真正的系统现实是“先接树，再判门”。** 只有把这两件事分开，你才能看懂本地文件系统和远程文件系统、权限和命名空间、inode 语义和进程凭据是怎样在 VFS 里真正咬合起来的。

## 下一篇桥接

到这里，本地块设备文件系统已经完整接进了 VFS 世界。下一步最自然的问题就是：**如果文件系统根本不在本地磁盘，而是在另一台服务器上，客户端怎么还能像操作本地 inode 一样去 `lookup`、`open`、`read`，而背后其实是在和远端协议交互**？

下一篇 `11-nfs-network-fs.md` 会把这条网络文件系统主线补上：NFS 客户端如何把远端导出的目录投影成本地 dentry/inode 视图，file handle 为什么会变成 opaque token，网络往返怎样重新改写缓存、一致性和权限判断，以及为什么“看起来像本地文件系统”往往只是 VFS 给你的幻觉。那一篇要回答的，不再是“本地盘怎样接树”，而是“远端树怎样被投影成本地树”。
