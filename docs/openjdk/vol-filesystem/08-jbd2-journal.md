## 现在真正该问的，不再是“ext4 比 ext2 多了日志”这么一句话，而是“日志到底是怎么把半写状态变成要么整包承认、要么整包作废的”

上一章我们已经从横向上看过文件系统演化图：Ext2 的核心痛点之一，是元数据更新没有事务日志保护；ext4 则通过 extent、delayed allocation 和 JBD2 去修这根老刺。可如果只停在“ext4 有 journal，ext2 没有”这个层面，JBD2 仍然像个黑箱。

真正继续追问下去，你会发现痛点并不抽象，而是非常具体：在 Ext2 里，一次 `unlink`、创建文件、分配新块或者扩容文件，往往同时要改多本账——目录项、inode、位图、group descriptor、块树。这些账本分散在不同磁盘块里，若机器恰好在中途掉电，就可能出现极其难看的半成品状态：

- 名字没了，但 inode 还活着；
- inode 长大了，但位图没记；
- 位图说块已占用，但 inode 树还没真正指过去；
- 目录项、inode、位图各自写了一半，恢复时只能靠 fsck 全盘猜哪一半该认。

这就是本篇真正要解决的核心困惑：**JBD2 到底如何把这些本来会分散落盘的元数据修改重新打包，做到崩溃后不是“猜猜哪几本账应该算数”，而是“只要事务完整提交就整包认，不完整就整包丢”。**

所以本篇最重要的顿悟是：**JBD2 真正保证的不是“用户数据总已落盘”，而是“元数据修改以事务为单位变成可判定生效或作废的一包”，恢复时只需要识别整包是否封箱，而不必再全盘猜账。**

先把总图记住：

```text
JBD2 三层对象：
  journal_t = 整个日志系统与环形日志空间
  transaction_t = 一批准备一起提交的元数据修改
  handle_t = 上层一次操作拿到的记账票据

上层改元数据时：
  start(handle)
  get_write_access(声明要改哪个 metadata buffer)
  真正修改 buffer
  dirty_metadata(把新版本挂进事务)
  stop(handle)

后台提交时：
  descriptor block 先列清单
  再写本事务的 metadata 副本
  最后写 commit block 作为“整包成立”的锚点

崩溃恢复时：
  没有完整 commit 的事务一律不认
  只有完整提交的事务才会 replay
```

这一篇最重要的一句话是：**JBD2 的价值不在“多写一遍磁盘”，而在于它替 ext4 建了一套事务账本，让目录项、inode、位图这些原本会分散写入的元数据修改，终于拥有了统一的提交边界。**

## 一、如果 ext2 的多本账仍然各写各的，崩溃恢复就永远只能靠事后全盘盘点和猜测

### 1. 最朴素的失败世界：目录项、inode、位图谁先改完算谁的，崩溃时靠 fsck 事后缝合

Ext2 的老世界本质上就是这样。一次文件系统操作会涉及多个元数据块：目录项所在目录页、inode table、inode bitmap、block bitmap，甚至间接块和 group descriptor。平时这些更新看起来都能顺利完成，可一旦电源在中途被拔掉，磁盘上留下的就可能是一组彼此不一致的半成品。

这时内核已经没有一个“原始事务意图账本”告诉它：这几步本来应该是一组。它只能在下次挂载时依赖 fsck 全盘扫描，尝试从结果推回“哪些 inode 没人认了、哪些位图不对、哪些目录项挂空了”。

也就是说，恢复不是从“提交记录”出发，而是从“残骸现场”反推真相。磁盘越大、元数据越多、半成品越复杂，这件事就越痛。

### 2. 第二个失败方案：那就简单“先写日志，再写真实元数据”，日志里也不必区分事务边界

如果意识到缺少事务账本才是问题，一个很自然但不够彻底的改进是：凡是改元数据，先把副本写一遍到某处日志区，然后再去原地覆盖真正元数据。这样至少崩溃后有一份“最近改过什么”的痕迹。

问题在于，光有“最近改过什么”还不够。你仍然得回答：**这些日志记录里，哪几块本来属于同一次原子更新？机器断电时，这一批到底算不算完成？**

如果日志本身不提供清晰事务边界，那恢复时仍然会面临相似痛苦：看到一串散乱日志副本，却不知道该认前半、认后半，还是全都不认。你只是把现场从主文件系统搬到了日志区，没有真正给系统一个“整包成败”的判定锚点。

### 3. JBD2 的核心答案：不是“先写一份副本”这么简单，而是“把一批修改打成一个有明确起止和提交锚点的事务包”

这就是 JBD2 最关键的思想转折。它不是简单追加一个“日志副本区”，而是在运行时明确维护 transaction 概念：一批元数据修改会被归入同一个 running transaction，由 commit 线程统一写成有结构、可恢复、可判定是否完整的一包记录。

于是 ext4 不再像 ext2 那样让目录项、inode、位图和其他元数据各自孤零零落盘，而是先在内存里把“这几本账属于一组”这件事立起来，再让后台提交系统按事务写 journal。恢复时系统不用全盘猜“哪些修改本来应该一起成功”，因为事务包自己已经把这个关系写明了。若要把这一节补成更硬的源码证据，第一组锚点应放在 `fs/jbd2/transaction.c`、`fs/jbd2/journal.c` 一类围绕事务创建、状态切换与提交调度的核心路径上：这些文件说明 JBD2 并不是只有“日志块长什么样”，而是真的维护了 running/committing/checkpoint 等事务生命周期与统一提交边界。

## 二、`journal_t`、`transaction_t`、`handle_t`：JBD2 之所以能既服务大事务又不把上层接口写成一团，是因为它把“整套日志系统”“一次提交”和“一次业务调用”明确拆成了三层对象

### 1. 为什么一个系统调用的修改粒度，不适合直接等于一次 commit 粒度

假如你把每次上层小操作都强制变成一次独立 commit，那么 journal I/O 会非常碎：创建一个小文件、改一位 bitmap、调一个 inode 时间戳，统统单独走一轮完整提交。这样虽然概念简单，却会把日志系统写成低吞吐、高手续费的同步流水线。

反过来，如果让所有上层逻辑直接共享一个巨大 transaction，而没有任何更细粒度票据对象，上层代码又会非常痛苦：每次只想改几个 metadata buffer，却得自己操心整包事务状态和空间预留。

所以 JBD2 不能只有一种对象层级，它必须同时照顾“上层调用很细”和“底层提交最好攒批”这两个现实。

### 2. `journal_t` 为什么应该被理解成“整套财务系统”，而不是“一次事务”

`journal_t` 最适合的人话角色，是日志系统整体实例：它知道 journal 空间在哪里、环形区域怎么推进、当前有哪些 transaction 在 running / committing、后台 `kjournald2` 线程如何调度、恢复时从哪开始扫描。

也就是说，`journal_t` 不是某次操作的上下文，而是这整套日志金融系统本身。没有它，后面所有事务包和 handle 都没地方安家。

### 3. `transaction_t` 解决的是“把很多 handle 的修改合并进同一批 commit”

transaction 这层是 JBD2 最值得牢牢记住的中间层。它的存在说明：一批 metadata 修改会被收集在一起，最终以一个 commit 边界整体判定成功或失败。多个 handle 可以把自己改过的 buffer 都挂进同一个 running transaction，等这个 transaction 满了、时间到了或被触发提交时，再统一写入 journal。

这让 ext4 得以避免“每个小动作都独立提交”的高昂成本，同时也让“这几本账属于同一包”具备可恢复意义。

### 4. `handle_t` 为什么又不可缺少

上层 ext4 代码在某个具体操作里，真正关心的是：我这次准备改几个 metadata buffer，我是否已经向 JBD2 声明了这件事，我改完后怎样把这些 buffer 挂进当前事务。它不需要也不应该直接操心整个 running transaction 生命周期。

于是 `handle_t` 正好扮演这张“记账票据”：**这是业务代码与 JBD2 交互的最小接口对象。** 它说明“我这次要参与 journal 的哪几个修改”，又不强迫业务代码直接管理日志系统全局。往更实的证据位落，这层关系通常可以顺着 `fs/ext4/*.c` 中上层操作调用 `jbd2_journal_start()`、再经 `jbd2_journal_get_write_access()`、`jbd2_journal_dirty_metadata()`、`jbd2_journal_stop()` 这一串接口回到 `fs/jbd2` 的事务实现去看。也就是说，`handle_t` 不是讲义上的概念图，而是真正把 ext4 具体元数据修改挂进 JBD2 事务纪律的那张票据。

### 5. 本节最该记住的结论：JBD2 通过 journal / transaction / handle 三层拆分，把“整个日志系统”“一次提交包”和“单次业务操作”清晰分开

所以一句最短人话是：**`journal_t` 像整套财务系统，`transaction_t` 像本次一起走审批的一包账，`handle_t` 像业务代码手里的一张报销单。**

## 三、`jbd2_journal_start` → `get_write_access` → `dirty_metadata` → `stop`：JBD2 真正强制上层遵守的，不是“怎么改数据”，而是“改元数据前先声明、改完后再正式入账”的事务纪律

### 1. 为什么元数据不能像普通内存一样随手改完再说

如果没有日志纪律，上层 ext4 代码完全可以像 ext2 那样：拿到 buffer_head，改 `bh->b_data`，标脏，结束。这样路径很短，但 JBD2 就失去了最关键的信息：**这个 buffer 的旧状态在事务开始前是什么，我何时得知它将被本事务修改，它何时才算属于这次事务的新版本。**

所以日志系统不是围观者，它必须在真正修改发生之前就介入。

### 2. `get_write_access` 为什么必须先于实际修改

这一步最核心的人话是：**先通知 JBD2“我要动这个 metadata buffer”，再真的动它。**

因为只有这样，JBD2 才能在旧状态仍然清晰时，把必要的前置条件准备好，保证未来恢复时知道这块在事务里处于什么位置。若你先改了，再告诉日志系统，很多“修改前现场”就已经失去了。

这和数据库 WAL 的核心纪律非常像：先登记变更资格，后实施变更本身。

### 3. `dirty_metadata` 为什么又必须晚于实际修改

如果说 `get_write_access` 是“我准备改”，那么 `dirty_metadata` 就是在说“我已经改完了，这个 metadata buffer 的新版本现在属于当前 running transaction”。

这不能和前一步混成一个动作，因为业务代码和日志系统都需要一个明确时点：之前 buffer 还只是“被登记为可写”，之后它才真正成为“事务内的新内容”。把两者分开，既有利于恢复语义，也有利于上层逻辑在修改前后保持清晰边界。

### 4. `jbd2_journal_stop` 为什么不是简单的“函数返回收尾”

stop 不只是“我这次 handle 用完了”，它还可能触发更大范围的后果：当前 transaction 的计数减少、预留资源释放、必要时唤醒提交线程。也就是说，它是把业务操作从“正在参与事务”过渡到“本次局部修改已经全部挂账完成”的正式出口。

这说明 JBD2 并不是一个透明背景库，而是在强制上层代码遵守一套元数据修改礼仪。你不是随手改内存，而是在事务规则下申请、修改、入账、退出。

### 5. 本节最该记住的结论：JBD2 通过 start/access/dirty/stop 这套协议，把元数据修改从“自由散改”变成“先声明、后修改、再入账”的事务纪律

一句最短人话是：**JBD2 真正管的不是你改了什么逻辑，而是你改 metadata 时必须按它的账本纪律办事。**

## 四、commit：descriptor、metadata copies、commit block 三段式提交里，真正决定“这包事务是不是存在”的不是前面的数据，而是最后那张封箱签

### 1. 为什么只把 metadata 副本顺序写进 journal 仍然不够

哪怕前面已经有 transaction 概念和 handle 协议，如果后台提交时只是把一批 metadata buffer 副本顺序写入 journal，恢复仍然会碰到一个大问题：崩溃发生在中途时，我怎么知道这一批到底写全没有？

看到前几块 journal payload 并不意味着事务已成立。它们也可能只是一个尚未完成的半包。恢复若盲目重放，会重新制造半写状态；完全不认，又会浪费已经安全落盘的大量记录。

所以提交结构必须再往前走一步，让事务拥有一个“整包到底算不算数”的最终锚点。

### 2. 为什么 descriptor block 必须先出现

descriptor 的核心意义，不只是“列出这批事务包含哪些 metadata block”，更是在恢复时告诉系统：接下来 journal 里的这些 payload 分别打算对应主文件系统里的哪些真实块位置。

也就是说，它像一张装箱单。没有装箱单，你即便看到一堆 journal payload，也不知道将来该把它们重放回哪几个原始元数据块。

所以 descriptor 不是附件，而是 transaction replay 所依赖的结构清单。若要把这一层讲成更有证据位的源码正文，关键落点应放在 `fs/jbd2/commit.c` 中围绕 descriptor/payload 组织事务写出的路径，以及 `fs/jbd2/recovery.c` 中扫描 descriptor 并据此决定如何 replay 的路径。它们共同支撑“descriptor 不只是日志附件，而是恢复系统理解事务内容布局的清单”这句判断。

### 3. 为什么 commit block 必须最后出现，而且它是整个事务的原子锚点

这就是 JBD2 最精彩的一刀。

只有在 descriptor 和所有 payload 都已经稳定写入 journal 之后，系统才允许写出最后的 commit block。于是恢复时逻辑会非常干净：**只要 commit block 没出现，就当这包事务从未完成；一旦它出现，就把前面整包都视为完整、可重放。**

这让“崩溃刚好发生在中途怎么办”这个问题有了极其清晰的答案。恢复不是模糊猜测，而是看封箱签在不在。

所以 commit block 不是普通尾巴，而是整个事务存在性的唯一官方盖章。更进一步的证据位，应落在 `fs/jbd2/commit.c` 与 `fs/jbd2/recovery.c` 对 commit record 生成、落盘与识别的那几组路径上：正是这些实现细节把“没有完整 commit 就整包不认，有了 commit 才有资格重放”从概念口号变成了真正的恢复判定规则。

### 4. 为什么说 JBD2 解决的是“多本账一起认账”的问题，而不是“每块数据更快了”

你应该已经能看到全貌了：descriptor 负责列清单，payload 负责装内容，commit block 负责做成败锚点。它们三者加起来，才让目录项、inode、位图这些原本会分散写出的修改，在 journal 世界里重新结成一个事务包。

于是 JBD2 真正优化的不是数据传输速度本身，而是崩溃时的语义可判定性。它把“半写状态”从主文件系统里赶出去，收缩到“journal 里只认有没有 commit block”这一个问题。

### 5. 本节最该记住的结论：JBD2 之所以能让恢复从猜测变成判定，关键就在 descriptor 先列清单，commit block 最后封箱

一句最短人话是：**commit block 不是普通结束标志，而是“只有看到它，前面那批 journal 记录才被法律承认”的封箱签。**

## 五、recovery / replay：JBD2 让恢复从“全盘猜哪里半写了”收缩成“只检查最近哪些事务拿到了封箱签”

### 1. 为什么 ext2 的 fsck 会越到大盘越痛

在没有日志的世界里，崩溃恢复只能回到全盘元数据现场：目录项、inode、位图、间接块树都得重新互相对账。盘越大、文件越多、元数据越复杂，这种事后清查就越慢、越重、越容易让挂载恢复时间变得难以接受。

也就是说，Ext2 恢复痛的不是“没法恢复”，而是“恢复范围几乎是整盘”。

### 2. JBD2 为什么能把恢复范围压缩到 journal

因为 journal 已经替你记下了最近“哪些元数据修改本来打算作为一笔事务共同成立”。恢复时，系统不再需要满盘巡逻去猜谁写了一半，而只需要检查 journal 这段最近活动区域：哪些事务有完整 commit，哪些只是半截。

一旦事务完整，按 descriptor 清单把 metadata 副本 replay 回主文件系统；若事务没有 commit，则整包丢弃，当作从未发生。这样恢复复杂度就从“扫描整盘元数据世界”压成了“扫描最近的日志段”。

### 3. revoke 为什么说明恢复并不只是“看见 commit 就全都写回去”这么机械

现实世界里，同一块元数据位置可能在后续事务里被重新分配、废弃或撤销重放意图。如果恢复只看 commit，不理解后续事务对旧块的否定，那么 replay 可能把本不该重新写回的老内容又盖回去。这里最重要的源码证据，应继续落在 `fs/jbd2/recovery.c` 与 revoke 相关路径上：它们提醒你，JBD2 的恢复语义不是“见到日志就全抄回去”，而是“在 commit 成立前提下，再结合 revoke 这类否定记录判断哪些旧元数据副本不该被 replay”。

这就是 revoke 记录存在的意义：它在告诉恢复逻辑，“即便你在早前日志里见过某块副本，这次也别再按老意图重放它了”。这又一次证明 JBD2 不只是“写几份副本”，而是有完整事务生命周期语义的恢复系统。

### 4. 为什么说 JBD2 把恢复从“逻辑推理题”变成了“日志审计题”

Ext2 的 fsck 更像刑侦：看一地现场痕迹，逆推出哪些账本该如何自洽。JBD2 的恢复更像审计：查看 journal，判断哪几包拿到 commit，哪几包被 revoke，按账本有规则地 replay。

这并不意味着恢复就完全简单了，但它确实把问题从“在全盘里找真相”大幅收缩成“在最近事务日志里做判定”。这就是 ext4 crash recovery 体验能与 ext2 拉开代差的根本。

### 5. 本节最该记住的结论：JBD2 recovery 真正快的原因不是代码优化，而是恢复问题被从“全盘猜账”缩成了“日志里审计最近事务是否完整”

一句最短人话是：**有日志之后，恢复主要看最近哪些事务拿到了封箱签；没有日志时，恢复得去全城查账。**

## 六、三种 journal 模式：日志存在不等于数据永远最安全，真正变化的是“元数据和数据内容谁被强保护、谁只是顺带约束”

### 1. 为什么“ext4 有日志”仍然不等于“普通 write 天然安全持久”

很多人第一次接触 ext4 时，会把“有 journal”误解成“那我只要 `write()` 成功，断电后文件内容也一定完好”。这非常危险。

JBD2 默认最核心保护的是元数据事务一致性，也就是目录项、inode、位图等账本别乱。至于普通文件数据内容本身，在不同 journal 模式下保护边界并不相同。你不能把“文件系统不会乱账”直接等价成“用户数据每次写都已持久化且永不出现旧内容窗口”。

### 2. `data=writeback`、`ordered`、`journal` 真正区分的是什么

这三种模式并不是“安全 / 更安全 / 最安全”这么粗糙，而是在划数据与元数据的耦合边界。

- `writeback` 只 journal 元数据，对相关数据块何时落盘不做严格先后约束；元数据可以先提交，数据可能还没安全到位。
- `ordered` 仍然主要 journal 元数据，但会要求相关数据块先于对应元数据 commit 落盘，避免“新元数据指向旧垃圾内容”这种最刺眼的不一致。
- `journal` 最重，数据和元数据都先进入 journal，再走后续流程，因此代价也最高。

所以日志模式真正改的，不只是“写多少”，而是“元数据 commit 对普通数据内容承担多强约束”。

### 3. 为什么默认往往是 `ordered`

因为它提供了一个非常实用的折中：不要求像 full data journaling 那样把普通数据也双写进日志，成本不会过高；但又尽量避免最糟糕的“文件大小和 inode 已经更新了，数据块里却还是旧垃圾”场面。

也就是说，默认模式在大多数通用场景里优先守住“文件系统不乱账，用户最肉眼可见的错误别出现”，而不是追求最极端的数据持久化保险。

### 4. 本节最该记住的结论：JBD2 默认最核心保护的是元数据一致性，普通文件数据是否也被强保护，要看 journal 模式和显式持久化接口

一句最短人话是：**ext4 有日志，不等于每次 write 的用户数据都天然等于事务已提交；日志最先守的是账本，数据内容保护程度还要看模式与 `fsync()`。**

## 七、把本篇收成一张图：JBD2 真正做的，不是“多写一份日志”，而是替 Ext4 建了一套可以判定成败、可以只重放完整事务、可以把崩溃恢复问题从全盘缩到日志段的事务机器

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：ext2 里目录项、inode、位图等多本账各写各的，掉电时半成品状态为什么这么难救；ext4 所谓“有日志”又到底把哪件事改变了。答案首先不在“写多一份副本”，而在 JBD2 把元数据修改重新组织成了可判定成败的 transaction。

`journal_t` 提供整套日志世界，`transaction_t` 把许多 handle 的修改攒成一次 commit，`handle_t` 则让具体 ext4 代码可以按“start → get_write_access → dirty_metadata → stop”这套纪律登记和提交元数据修改。后台 `kjournald2` 再把这批事务写成 descriptor → payload → commit block 的三段式日志记录，其中 commit block 充当唯一的封箱签：没有它，这包事务视为未完成；有了它，recovery 才有资格整包重放。

于是崩溃恢复终于从 ext2 的“全盘猜账”变成 ext4 的“日志审计”：扫描 journal，看哪些事务完整提交、哪些被 revoke、哪些应该 replay。恢复范围也从整盘元数据世界收缩成最近那段 journal。最后，不同 journal 模式又进一步提醒你：日志最核心守的是元数据一致性，普通文件数据是否也被强保护，则取决于模式与显式持久化要求。

把这一切压成最短总图，就是：

```text
对象层：
  journal_t 管整套日志系统
  transaction_t 管一次提交包
  handle_t 管一次业务调用票据

纪律层：
  先声明可写 metadata
  改完再把新版本挂进事务

提交层：
  descriptor 列清单
  payload 存副本
  commit block 封箱

恢复层：
  只认有完整 commit 的事务
  日志恢复替代全盘猜账

模式层：
  元数据永远最先被保护
  数据保护边界依赖 journal 模式
```

所以本篇最该记住的一句话是：**JBD2 的本质不是“日志文件存在”，而是“元数据修改终于拥有了统一事务边界和封箱签”；这让 ext4 在崩溃后不必再去整盘猜，直接只认那些已经被正式提交的事务包。**

## 八、几个最容易说错的地方

### JBD2 是不是就是“先把所有内容写到日志，再写到原位置”？

不够准确。它更关键的是事务边界、提交顺序和恢复判定，而不是“多一份拷贝”这么粗。

### `handle_t` 是不是就等于一次完整 commit？

不是。多个 handle 可以并入同一个 running transaction，一起提交，handle 更像单次业务调用手里的记账票据。

### commit block 是不是只是日志尾巴里的一个普通块？

不是。它是事务是否被恢复系统承认的唯一锚点，没有它整包都应视为未提交。

### ext4 有日志是不是就说明普通 `write()` 返回后数据一定落盘了？

不是。日志最核心保证的是元数据事务一致性；普通数据内容是否强保护，还要看 journal 模式和 `fsync()` 之类显式持久化要求。

### recovery 是不是看到 journal 里有记录就全都 replay？

不是。只有有完整 commit 的事务才会被重放，revoke 等信息还会进一步影响哪些记录应被跳过。

### JBD2 是不是主要为了让正常写入更快？

不是。它最根本的价值在于让崩溃恢复从全盘推理收缩成日志审计，性能收益更多体现在恢复可控性和元数据更新组织上。

## 收束：看懂 JBD2 之后，你才会真正明白“有日志”这件事的本质，不是多写一份，而是终于能在掉电后说清楚哪几本账算数、哪几本账作废

回到开头那个问题：日志到底怎样把半成品状态变成“要么整成、要么整包作废”？现在答案已经完整闭环了。JBD2 不是简单把 ext2 的元数据再备份一份，而是为 ext4 建立了一整套事务对象、操作纪律、提交结构和恢复规则。目录项、inode、位图等原本会分散写出的修改，先被绑进同一 transaction，再由 descriptor 和 commit block 明确画出这包事务的边界与生效点。崩溃后，恢复不再需要全盘猜哪里半写，而只需审计 journal 中哪些事务真的拿到了封箱签。

也正因为如此，你会发现“日志”在文件系统里并不是一个附加配置项，而是一种新的世界观：更新不再只是“改完就算”，而是“先收编成事务、再有条件承认”。理解了这一点，ext4 为什么能把 ext2 最痛的崩溃恢复问题压下来，才真正有了机制上的解释，而不是停留在“它有日志所以更安全”这种空话上。

这就是为什么说：**JBD2 最重要的成果，不是让磁盘多了一份记录，而是让崩溃后的世界终于有一把能判断“哪些修改正式发生过”的法槌。**

## 九、误解清单、证据清单与边界清单

### 误解清单

- JBD2 不是“多写一份元数据副本”这么简单；它真正关键的是事务边界、提交锚点和恢复判定规则。
- `handle_t` 不等于一次完整 commit；它更像单次业务调用参与事务的票据，多张 handle 可以并入同一个 running transaction。
- ext4 开了 journal 不等于普通文件数据天然立即持久化；JBD2 最核心守的是元数据事务一致性。
- recovery 不是“看到 journal 里有块就都 replay”；没有完整 commit 的事务必须整包丢弃，revoke 还会进一步否定部分旧记录。
- `ordered` 模式也不等于“用户数据进了 journal”；它更接近“在提交相关元数据前，先约束对应数据块写出顺序”。

### 证据清单

- 事务生命周期：`fs/jbd2/transaction.c`、`fs/jbd2/journal.c` 中围绕 running/committing/checkpoint 事务状态的路径，支撑“JBD2 真在维护事务系统，而不是只写一串日志块”。
- 业务票据入口：`fs/ext4/*.c` 调用 `jbd2_journal_start()`、`jbd2_journal_get_write_access()`、`jbd2_journal_dirty_metadata()`、`jbd2_journal_stop()` 的路径，支撑 `handle_t` 作为上层元数据修改票据的角色。
- 提交结构：`fs/jbd2/commit.c` 中 descriptor/payload/commit block 组织与写出的路径，支撑“三段式提交”和 commit 作为封箱签的判断。
- 恢复与 revoke：`fs/jbd2/recovery.c` 中扫描 commit、descriptor 与 revoke 的路径，支撑“只认完整 commit，且不是无脑全 replay”的恢复语义。
- ext4 模式边界：`fs/ext4/*.c` 与挂载模式相关路径，配合文档/实现共同说明 `ordered`、`writeback`、`journal` 三种模式在“数据是否进日志、顺序如何约束”上的差别。

### 边界清单

- 本文讨论的是 ext4/JBD2 常见实现心智模型；具体函数拆分、线程调度、checkpoint/revoke 细节与锁顺序会随内核版本变化。
- JBD2 最核心保证的是元数据事务一致性；普通文件数据的持久化边界仍要结合 journal 模式、块设备缓存和 `fsync()` 语义一起判断。
- `ordered`、`writeback`、`journal` 的差别不能只靠名字猜；不同挂载选项、数据路径和实现演进会影响细节表现。
- recovery 能压缩恢复范围，不等于崩溃后业务语义零损失；应用层仍可能需要面对最后几次写入是否真正 durable 的问题。
- 把 JBD2 和 WAL 类比有助于理解“先记账、再承认”，但 ext4/JBD2 不是通用数据库事务系统，锁粒度、隔离语义和对象模型都不同。
