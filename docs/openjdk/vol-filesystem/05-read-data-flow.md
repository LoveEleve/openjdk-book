## 现在真正该问的，不再是“写路径怎样把字节先变成脏页”，而是“读路径怎样先把磁盘现实变成缓存现实，然后才把字节交给用户”

上一篇我们已经把写路径打穿了。你知道 `write()` 返回成功通常并不意味着磁盘已经落盘，而只是说明：

- Ext2 已经在需要时把逻辑块映射到真实物理块；
- 用户字节已拷进 page cache；
- folio、buffer_head 和 inode 三层都已经记脏；
- 真正的持久化被留给后面的 writeback 世界。

这条链路的核心是：**先把写入变成缓存现实，再延迟持久化。**

读路径则刚好相反。用户态执行 `read(fd, buf, 4096)` 时，真正要解决的不是“如何把一个已经在内核手里的页再拷给用户”，而是更前面的一步：**目标那 4KB 文件内容现在到底是不是已经存在于 page cache 里？如果还没有，内核得先沿 inode 的块索引树把它从磁盘搬成缓存现实，然后你才有东西可拷。**

这就让读路径天然分成三种完全不同的体感状态：

- 页缓存命中：数据已经在内存里，几乎没有块设备 I/O。
- 页缓存未命中：必须真正走 inode → block → bio，把页从磁盘带回来。
- 预读命中：当前页自己也许之前不在，但因为系统上一次顺手多读了几页，它现在恰好已经躺在 cache 里等你了。

所以本篇最重要的顿悟是：**`read()` 的核心不是 copy，而是先确保“目标 folio 已经存在于 page cache”；真正决定延迟高低的，是这一步落在哪种状态。**

先把总图记住：

```text
统一入口：
  read_iter 最终大多汇到 filemap_read 这条通用读骨架

快路径：
  目标 folio 已在 page cache
  直接 copy 给用户

慢路径：
  page cache 未命中
  文件系统沿 inode 索引树找物理块
  块层把页读回 page cache
  再 copy 给用户

提前量：
  顺序访问会触发同步/异步预读
  让“下一页”尽量在真的被访问前就先进入 cache
```

这一篇最重要的一句话是：**普通文件读的第一现场也不是磁盘，而是 page cache；磁盘只在缓存现实还没建立时，才作为后备事实被重新搬进来。**

## 一、如果每次 `read()` 都直接打磁盘，文件系统会把自己最常见的顺序读和重复读优势亲手全扔掉

### 1. 最朴素的错误世界：用户每次 `read()`，内核都直接去磁盘读对应块，再拷给用户

从逻辑上看，这当然可以工作。用户说要读文件某段字节，内核就定位物理块、发起设备读，把拿回来的数据直接拷给用户缓冲区，任务完成。

可一旦把真实工作负载放进去，这套模型会非常痛苦。因为大量文件读取本来就具有重复性和顺序性：同一程序会反复读相同配置文件、动态库、热数据页；顺序扫描又会一页接一页往前走。若每次都坚持“先打设备再说”，你就等于主动拒绝利用这些访问模式，把所有读都当成第一次陌生读取。

这会让设备 I/O 次数、上下文切换和整体延迟都被不必要地放大。磁盘明明已经替你交出过这些字节，你却假装从未见过它们。

### 2. 第二个失败方案：那就只靠页缓存留住历史，但完全不做预读，永远等用户真的碰到下一页再处理

如果意识到重复读值得缓存，很容易接受“命中过去的页就别打磁盘”这一步。但如果你只停在这里，仍然会低估顺序读的机会。

因为顺序读时，当前页刚被访问，下一页、下下一页在非常短时间内被触碰的概率很高。你若完全被动地等每一页都各自触发一次缺页/未命中处理，那虽然少了重复读取，却仍没把连续性带来的批量优势吃干净。

这说明读路径不只需要“记住过去”，还需要适度“猜测未来”。这正是预读存在的理由。

### 3. Linux 的答案：先把 `read()` 统一折叠成“确保目标 folio 在 page cache 里”，然后再根据命中、未命中和访问模式分流

所以 Linux 读路径真正的统一问题不是“怎么从磁盘读”，而是：**目标 folio 现在是否已经在 page cache 里，如果没有，用什么最合适的方式把它弄进来。**

这个视角非常重要，因为它把复杂读路径重新收束成一个单一目标。命中时，后端磁盘世界根本不用说话；未命中时，文件系统与块层才开始介入；顺序读时，又会在“确保当前页存在”的同时顺手把未来几页带上。

也就是说，读路径不是“每次读文件都去设备要数据”，而是“每次先检查缓存现实是否已经成立，只有没成立时才回到磁盘现实”。若要把这一节补成更硬的源码正文，最关键的证据位应回到 `mm/filemap.c` 中 `filemap_read()`、`filemap_get_pages()` 一类路径：它们共同支撑“普通 read 的第一现场不是块设备，而是先确认目标 folio 能不能从 page cache 世界里拿到”这句判断。

## 二、`sys_read` 到 `filemap_read`：和写路径一样，真正共享的不是磁盘格式，而是“把用户请求拆成按 folio 逐段推进”的通用骨架

### 1. 为什么 Ext2 也不需要自己重写整套读主循环

和写路径类似，读路径里有大量和具体磁盘格式无关的共性工作：迭代用户请求、处理偏移、在 cache 命中时做 copy_to_user、决定何时触发 readahead、管理 folio 引用和循环终止条件。这些事情对 ext2、ext4 和很多本地文件系统来说都很相似。

所以文件系统真正特有的部分，不在“怎样循环读 8KB 请求”，而在“某一页未命中时，这页的磁盘块究竟怎么找、怎么读回来”。这使得通用读骨架和文件系统特定块映射职责天然适合分层。

### 2. `filemap_read()` 真正关心的不是“块设备有没有数据”，而是“这一轮用户请求对应的那些 folio 现在能不能从 page cache 拿到”

这和很多人对 `read()` 的第一直觉正好相反。内核读路径的第一现场不是块设备，而是 page cache。`filemap_read()` 的中心动作可以粗暴理解成两步：

- 先想办法拿到当前逻辑偏移对应的 page cache folio；
- 拿到之后，再把其内容拷给用户迭代器。

这意味着 filemap 世界把“设备现实”和“用户 copy”中间夹了一层非常明确的 cache 判定与 folio 获取逻辑。读路径的绝大部分复杂性，其实都发生在“拿 folio”这一步。证据位上，这层最值得回到 `mm/filemap.c` 的通用读骨架，以及 `fs/ext2/file.c`/`fs/ext2/inode.c` 中 `read_folio`、`ext2_get_block()` 与块映射路径去看：它们共同支撑“通用骨架负责逐 folio 推进，文件系统只在未命中时补磁盘现实”这句判断。

### 3. 为什么说 `filemap_get_pages()` 这种阶段才是真正的分水岭

对用户来说，都是一次 `read()`；对内核来说，`filemap_get_pages()` 一类阶段几乎决定了这次读属于哪种体感世界：

- 现成命中：快。
- 未命中，需要触发 `read_folio`：慢。
- 未命中但顺手带到的预读页已经在路上或已到 cache：比硬未命中好很多。

所以读路径真正的性能转折点，不在最后 `copy_folio_to_iter()`，而在前面“这一页如何进入、等待或命中 page cache”。

### 4. 本节最该记住的结论：通用读骨架负责把“读一个大缓冲区”拆成“逐 folio 取缓存页再 copy”，文件系统只在未命中时补上磁盘路径

一句最短人话是：**`read()` 的统一骨架是“先找 folio，再 copy”，而不是“先打设备，再想缓存”。**

## 三、页缓存命中：文件读最快的时候，不是磁盘很快，而是磁盘这次根本没被问到

### 1. 为什么 page cache 命中才是普通读路径真正想要的常态

很多人讲文件系统性能时，一开口就谈磁盘、NVMe、I/O 延迟。但对绝大多数普通本地读路径来说，真正理想的状态其实是：**这次根本别碰设备。**

只要目标 folio 已经在 page cache，读路径就不必再经历块映射、bio、设备队列和完成中断。它要做的主要工作退化成：拿到 folio、做必要校验、把内容拷给用户。和未命中相比，这通常是两个世界。

这也是为什么 page cache 被称为读路径主舞台之一。磁盘再快，也难和“这次压根不需要磁盘”相比。

### 2. 命中意味着什么

命中并不只是“有一份内容在内存里”。更准确地说，它意味着：

- 当前偏移对应的 folio 已经在 page cache 索引中；
- 该 folio 内容状态足以供本次读取使用；
- 当前线程无需为设备 IO 等待，只需围绕内存页进行后续工作。

从用户体感看，命中会让 `read()` 更像一次内存拷贝；从内核机制看，它则意味着前面几篇讲过的页缓存、xarray 和 readahead 全都成功地把设备访问挡在了后台。

### 3. 为什么“第二次读快很多”经常归根到底只是因为第一次已经替你把 folio 搬进来了

这点看似简单，却非常值得反复强调。很多性能现象并不神秘：第一次读慢，是因为它必须把磁盘现实转成缓存现实；第二次读快，是因为这次你直接活在缓存现实里了。

也正因此，page cache 命中不仅仅是“少一次 I/O”，而是在把一次完整的设备路径彻底从请求临界路径上移走。

### 4. 本节最该记住的结论：读路径最快的状态不是“设备快”，而是“这次根本不用和设备说话”

所以一句最短人话是：**page cache 命中之所以快，不是因为磁盘突然变快了，而是因为磁盘这次没有参与。**

## 四、页缓存未命中：第一次真正读文件的关键，不是 copy，而是沿 inode 指针树把正确物理块找出来，再把它读成一个缓存页

### 1. 为什么未命中时问题会重新退回到“磁盘上哪块才是我要的这页内容”

一旦 page cache 里没有对应 folio，系统就不能再偷懒地只做内存 copy 了。它必须重新回到磁盘布局与 inode 索引世界，回答：**当前这个文件逻辑偏移，对应哪一个逻辑块，再对应哪一个物理块，最后怎样把那 4KB 真正搬进新的 folio。**

这就让上一章讲过的 `i_block[15]` 和间接块路径，从“结构知识”变成了真正的运行时读取路径。

### 2. `ext2_read_folio()` 为什么像读路径里的“接单人”

在未命中场景下，通用 filemap 层会要求具体文件系统把目标 folio 填满。对 ext2 来说，这个职责落在 `read_folio` 类钩子上。它的任务不是决定用户要不要这页，而是回答“好，我现在负责把这页真正装满内容”。

要做到这一点，它必须借助 ext2 的块映射逻辑，也就是再次调用 `ext2_get_block()` 一类路径。只是这一次不是为了分配新块，而是为了从文件逻辑块推到既有物理块位置。

### 3. 为什么 `ext2_get_block()` 在读路径里和写路径里扮演的是同一个“翻译器”，但语义不同

这很值得对照回收上一章。写路径里它面对的是“如果没有块，是否要 create=1 并现场分配”；读路径里更常见的问题则是“块早就存在，我只要把逻辑块号翻译成物理块号，绝不能顺手改账本”。

也就是说，函数名可能相近，索引树还是同一棵，但写和读对它提出的请求不同：

- 写：必要时扩树、分块、改位图。
- 读：只做翻译，找出已有块号，别创造新现实。

这提醒你，同一套 inode 索引结构并不是只在创建和写路径上有意义，它也是所有文件数据读取的地基。

### 4. 为什么“从磁盘搬回页”最终还是要落到 page cache，而不是直接 DMA 到用户缓冲区就完事

这又回到了本篇的第一性原则。普通 buffered read 的目标不是“给这次调用凑到数据就算了”，而是把文件页带进 page cache，让后续访问可以命中，让多个进程共享读缓存，让 readahead 和 writeback 体系有共同工作对象。

所以设备读回来的内容首先填进 folio/page cache。之后这次 `read()` 再把它 copy 给用户，未来别的读取也能继续复用这张 folio。这比每次都搞一次“设备 -> 用户缓冲区”的一次性直送，服务的世界要大得多。

### 5. 本节最该记住的结论：页缓存未命中时，读路径真正慢的地方是“沿 inode 索引树找块 + 让块层把内容装进 page cache”，而不是最后那次 copy_to_user

一句最短人话是：**未命中时，`read()` 的核心不是拷字节，而是先把页从磁盘世界搬成缓存世界。**

## 五、预读：第一次读一页时，内核真正聪明的地方不是只读这一页，而是顺手猜你下一页大概率也快到了

### 1. 为什么“每页都独立 miss 一次”会把顺序读打得很亏

假设程序在顺序扫描文件：第 0 页未命中，内核读回来；接着第 1 页未命中，再读；第 2 页再 miss，再读……这种模式即使 page cache 正常工作，也还是把顺序读变成了一串细碎、重复起步的设备访问和缺页准备动作。

这太浪费顺序性了。因为一旦当前页刚被访问，后续几页很快也被访问的概率极高。系统若还假装完全不知道未来，只在每页真正踩到时才做准备，就等于白白放弃了大量局部连续访问信息。

### 2. 同步预读和异步预读为什么是两层不同的加速时机

第一次真正缺某页时，系统可能需要同步把当前页乃至附近少量页带回来，这是“为了不让当前读失败”的最低保障。而一旦检测到顺序模式成立，后续更积极的异步预读又会登场：在当前读还能继续服务用户时，后台先把后面的页悄悄拉进 cache。

所以预读并不是一个单一按钮，而是分成“当前必须补救的同步前推”和“为了未来命中的异步提前”。这让系统既能保证当前页尽快可用，又能逐渐把后续读体验变成 cache 命中。

### 3. 为什么预读和本篇主线天然闭环

你现在应该能看见闭环了：

- 写路径先把数据做成 page cache 里的脏页；
- 读路径优先希望命中 page cache；
- 命不中时，读路径先把页搬进 page cache；
- 顺序读时，预读又努力让“下一次未命中”提前变成“下一次命中”。

也就是说，page cache 并不是写独享或读独享的结构，而是整个本地文件系统读写路径共享的中间现实世界。预读的全部意义，就是让未来的读尽量少离开这个世界。

### 4. 本节最该记住的结论：预读真正做的，不是“多读几页”这么简单，而是把顺序读的未来访问尽量提前转化成 page cache 命中

所以一句最短人话是：**预读的目标，不是多搬几页，而是减少未来再次触发未命中的次数。** 证据位上，这层最值得回到页缓存通用读路径与 readahead 相关实现去看：它们共同支撑“预读不是多读几页这么粗，而是把顺序访问的未来页提前转化成 cache 命中”的判断。

## 六、把本篇收成一张图：`read()` 的真正主线，不是“从磁盘到用户缓冲区”，而是“先确保文件页成为缓存现实，再决定这次是不是需要真正触盘”

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：第一次读一个还没进 page cache 的文件页时，内核怎样沿 inode 的块索引把它从磁盘搬回来。答案首先说明，普通 read 的第一现场并不是块设备，而是 `filemap_read()` 这条 page-cache-first 的通用骨架。它先尝试拿到当前偏移对应的 folio，拿到之后才 copy 给用户。

若 folio 已命中，读路径就几乎退化成一次内存 copy；磁盘没有发言机会。若未命中，文件系统才通过 `read_folio` 与 `ext2_get_block()` 重新回到 inode 索引树和物理块定位世界，块层把目标内容读回 page cache，当前读请求随后再从 cache 里取数据。顺序读场景下，同步/异步预读又会继续努力把未来页提前带进 cache，让下一次访问尽量落到命中而不是未命中。

把这一切压成最短总图，就是：

```text
入口层：
  sys_read / vfs_read → filemap_read

第一判断：
  目标 folio 是否已在 page cache

命中：
  直接 copy 给用户
  0 次块设备 I/O

未命中：
  ext2_read_folio / ext2_get_block 找物理块
  块层把页读回 page cache
  再 copy 给用户

提前量：
  readahead 把未来顺序页提前变成 cache 命中
```

所以本篇最该记住的一句话是：**读路径真正快不快，首先取决于 page cache 现实是否已经建立；命中时磁盘不参与，未命中时系统的全部工作都在于尽快把目标页搬进这个缓存世界。**

## 七、几个最容易说错的地方

### `read()` 是不是天然比 `write()` 更“直接打磁盘”？

不是。普通 buffered read 同样首先围绕 page cache 组织，未命中才回到磁盘现实。

### 页缓存命中时，文件系统是不是仍然要顺着 inode 指针树走一遍？

通常不需要。命中说明目标 folio 已经存在于 page cache，读路径主要工作退化为取 folio 并 copy 给用户。

### 未命中时最慢的地方是不是 `copy_to_user`？

通常不是。真正重的是沿 inode 索引树找块、发起块设备读取、等待页进入 page cache。

### 读路径里的 `ext2_get_block()` 是不是会像写路径那样顺手分配新块？

不应该。读路径的职责是翻译已有块，不是创造新现实；写路径才会在 `create=1` 语义下分配新块。

### 预读是不是“可有可无，多读几页而已”？

不是。它是在主动把未来顺序访问转化成 page cache 命中，直接决定连续读的体感延迟和 I/O 组织方式。

### page cache 是不是只对写路径有意义？

不是。读路径同样以它为主舞台，命中、未命中和预读命中三态都围着它组织。

## 收束：看懂读路径之后，你才会真正明白“读一个文件”首先是一次缓存判定，再次才是一次磁盘访问

回到开头那个问题：第一次 `read()` 一个从未命中过 page cache 的文件页时，内核怎样沿 inode 的块索引把它从磁盘搬回来？现在答案已经完整闭环了。普通读路径首先在 `filemap_read()` 和 page cache 世界里判断目标 folio 是否存在；命中时，当前读更像一次内存 copy；未命中时，Ext2 才借助 `read_folio` 和 `ext2_get_block()` 沿 inode 指针树找到物理块，由块层把内容读进 page cache，然后再交给用户。顺序读时，预读又继续把“未来的磁盘访问”提前转换成“未来的缓存命中”。

也正因为如此，你会发现文件系统里的“读取文件”并不是每次都从磁盘开场，而是每次都先问一句：**这页是不是已经是缓存现实？** 只有答案是否时，磁盘世界才重新登场。理解了这条主线，你再看重复读为什么快、顺序读为什么越读越顺、第一次打开冷文件为什么慢，就会发现这些现象其实都只是 page cache 三态切换的不同表情。

这就是为什么说：**文件读路径的核心不是“搬数据”，而是“尽量别每次都重新搬数据”。** page cache 命中才是常态目标，磁盘访问只是为了把这种常态重新建立起来。

## 八、误解清单、证据清单与边界清单

### 误解清单

- `read()` 不等于天然直打磁盘；普通 buffered read 同样首先围绕 page cache 组织。
- page cache 命中时，不需要再顺着 inode 指针树重走一遍块映射现实；真正慢的是未命中场景。
- 未命中最重的通常不是最后一次 copy_to_user，而是“找块 + 发块设备读取 + 等页进入 page cache”。
- 读路径里的 `ext2_get_block()` 不应该像写路径那样顺手创建新块；读是在解释已有现实，不是在发明新现实。
- 预读不是可有可无的“多读几页”；它直接决定顺序读有多少机会提前变成 cache 命中。

### 证据清单

- 通用读骨架：`mm/filemap.c` 中 `filemap_read()`、`filemap_get_pages()` 一类路径，支撑“先拿 folio、再 copy”的 page-cache-first 主线。
- 文件系统未命中补货：`fs/ext2/file.c`/`fs/ext2/inode.c` 中 `read_folio`、`ext2_get_block()` 与相关块映射路径，支撑“未命中时先沿 inode 索引树把页搬进缓存世界”的判断。
- 块层现实：页从 inode 索引树映到块设备读取的路径，支撑“真正慢的是设备与等待，不是最后那次 copy”。
- 预读状态：页缓存通用读路径与 readahead 相关实现，支撑“顺序访问的未来页如何提前变成 cache 命中”的判断。
- page cache 作为中间现实：命中、未命中、预读命中三态共同支撑“磁盘只在缓存现实尚未建立时才重新登场”的主线。

### 边界清单

- 本文讨论的是 Ext2 buffered read 的稳定心智模型；`filemap_read`、folio、buffer_head、readahead 触发点与具体文件系统读页路径会随内核演进变化。
- page cache-first 讲的是普通 buffered read 路径，不等于所有文件读取都必须如此；Direct I/O、特殊文件和设备文件会走别的路线。
- 预读是利用顺序性下注，不是对所有工作负载都稳赚；随机访问时它同样可能收手或下注失败。
- 本文重点是“怎样把页先变成缓存现实”，不展开 writeback/脏页退场；那是前后文里另一条主线。
- 读路径里的性能体感强依赖命中态、未命中态和预读态切换，不能被简化成“磁盘快慢”一个变量。
