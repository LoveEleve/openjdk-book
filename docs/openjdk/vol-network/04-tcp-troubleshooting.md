## 现在真正该问的，不再是“算法上该怎样工作”，而是“当现实不按教材走时，`TIME_WAIT`、`CLOSE_WAIT`、重传、零窗口和粘包这些现象到底在替哪一层机制报警”

上一章我们已经把 TCP 传输期的理论边界讲清楚了。你知道发送方真正可发的 inflight 数据不是看一个窗口，而是 `min(rwnd, cwnd)`；MSS 和 MTU 又决定了“一个段装多少”与“链路允许多大包”不是同一回事；CUBIC、BBR 等拥塞算法则在持续猜测“这条路到底还能飞多少数据”。

再往前一章，你也已经明白 TCP 连接本身是一台状态机：三次握手在同步序列空间和连接存在性，四次挥手与 TIME_WAIT 在收尾和隔离旧报文，RST 和超时则代表不同类型的失败现实。

可一到线上，工程师面对的并不是“窗口和状态机很优雅”这种教科书结论，而是一堆模糊投诉：

- 为什么机器上全是 `TIME_WAIT`？
- 为什么 `CLOSE_WAIT` 一直不掉？
- 为什么某个 RPC 偶尔平白多出几十毫秒？
- 为什么 `recv()` 一次读到了两条消息，或者只读到半条？
- 为什么客户端有时秒失败，有时一直超时？
- 为什么 `ss` 里明明 state 正常，但 RTT 和重传仍然在涨？

本篇真正要做的，就是把这些看似零散的“线上症状”重新拆回 TCP 机器内部：**状态机、关闭语义、发送合并、延迟确认、字节流边界、建连防护和抓包/统计证据。**

所以本篇最重要的顿悟是：**TCP 排障的第一原则不是看见现象就改 sysctl，而是先问：这个症状到底是在替状态机、窗口、计时器、字节流语义还是队列资源发警报。**

先把总图记住：

```text
生命周期症状：
  TIME_WAIT / CLOSE_WAIT 属于状态机尾端问题

关闭语义症状：
  close / shutdown / SO_LINGER 决定是优雅收尾还是强制复位

交互延迟症状：
  Nagle + delayed ACK 会把小消息延迟放大

应用层边界症状：
  TCP 只提供字节流, 粘包/半包必须由协议自己解

建连异常症状：
  backlog / SYN Cookies / TFO / RST / firewall 决定连接为什么连不上

证据链：
  ss 看状态与 socket 指标
  nstat 看内核累计计数
  tcpdump 看 Seq/Ack/Window/重传的真实时间线
```

这一篇最重要的一句话是：**排障真正要做的，不是背参数，而是把“线上抱怨”翻译回 TCP 的状态、窗口、计时器和字节流语义，再用工具把猜测钉成证据链。**

## 一、如果你不先把现象归类到“状态机、计时器、窗口、消息边界”这几类问题里，调参几乎一定是在蒙

### 1. 最朴素的错误排障方式：看到连接多就调 TIME_WAIT，看到延迟高就关 Nagle，看到重传就怪网络

这几乎是很多线上事故的第一反应。问题在于，这些现象并不是同一层级的问题：`TIME_WAIT` 可能只是主动关闭很多连接的正常协议卫生；延迟突增可能是 Nagle/延迟 ACK，也可能是应用处理慢、路径 RTT 飙升或零窗口；重传既可能来自真实丢包，也可能和乱序、队列阻塞、网卡 offload 观察口径有关。

如果你不先判断现象在 TCP 哪一层冒头，就很容易用一把锤子砸错地方。比如你以为 `CLOSE_WAIT` 是内核清不掉，其实往往是应用没 `close()`；你以为“粘包”是 TCP 有 bug，其实是应用把字节流错当消息队列。

### 2. 更好的起点：先问“这是状态问题、关闭问题、延迟问题、消息边界问题，还是建连/丢包证据问题”

真正有效的排障，第一步往往不是命令，而是分类。因为分类能决定你接下来优先看哪组证据：

- 如果是状态数量异常，先去状态机语义里找；
- 如果是优雅关闭和资源泄漏，先去 `close`/`shutdown`/`SO_LINGER` 的含义里找；
- 如果是小包延迟，先去 Nagle/延迟 ACK 组合里找；
- 如果是“收不到完整消息”，先把 TCP 当字节流，不要先怪网络；
- 如果是“连不上/很慢/总重传”，就准备好 `ss`、`nstat`、`tcpdump` 三层证据。

也就是说，**排障不是收集所有命令输出，而是先把问题放回协议语义图上的某个区域。**

### 3. 本节最该记住的结论：TCP 排障的第一步不是调参，而是把症状翻译回协议的哪台子机器在报警

一句最短人话是：**先识别哪一层在喊疼，再决定该看哪个指标。**

## 二、`TIME_WAIT` 与 `CLOSE_WAIT`：它们都表示“连接还没彻底消失”，但一个是在做协议卫生，一个往往在提示应用没收尾

### 1. 为什么看到大量 `TIME_WAIT` 不能直接得出“系统出 bug 了”

`TIME_WAIT` 最常见的误读，就是把它当成无用垃圾状态，仿佛连接既然已经关了，就不该继续占着表项或端口。

可前一章我们已经讲过，它承担的是两项真实职责：

- 如果最后 ACK 丢了，主动关闭方还能重发；
- 让旧四元组相关的延迟报文在新连接可能复用之前自然老去。

所以一个系统里 `TIME_WAIT` 多，首先说明的是“这里存在大量主动关闭的连接”，而不是“内核忘了清”。只有当它和端口耗尽、短连接风暴、复用策略和资源水位一起出现问题时，才会从正常协议卫生升级成容量问题。

### 2. 为什么 `CLOSE_WAIT` 和 `TIME_WAIT` 的排障方向几乎相反

`CLOSE_WAIT` 的含义是：对端已经发来了 FIN，本地协议栈也 ACK 了，但本地应用还没走完自己的关闭动作。这里的关键词不是“网络”，而是“应用层迟迟没把本端这半边关掉”。

因此大量 `CLOSE_WAIT` 常常首先意味着代码路径漏 `close()`、连接池归还逻辑没走、业务线程卡住、半关闭后的应用收尾没完成，而不是“TCP 自己 stuck 住了”。

所以这两个状态虽然都表现为“连接看起来没消失”，可语义和处置方向几乎相反：

- `TIME_WAIT` 常是主动关闭方正常的协议后坐力；
- `CLOSE_WAIT` 常是本地应用收尾不及时。

若要把这一节补成更硬的证据位，最合适回到当前 socket 视角的 `ss -ti`、状态累计视角的 `nstat` / `/proc/net/snmp`，再配合抓包时间线去看：它们共同支撑“状态多本身不是罪名，关键在于这些状态是否和端口耗尽、应用未 close、重传或异常时间线绑定”这句判断。

### 3. 为什么“状态多”本身不是结论，关键在于它是否和系统资源或行为异常绑定

几万 `TIME_WAIT` 如果机器端口范围够大、短连接就是业务常态、资源没压垮，也许只是流量模式的自然结果。相反，几百个 `CLOSE_WAIT` 如果一直不掉，哪怕数量不大，也可能已经暴露了应用逻辑 bug。

这再次说明：状态本身不是罪名，状态出现的位置和持续方式才决定它是不是症状。

### 4. 本节最该记住的结论：`TIME_WAIT` 常是协议卫生，`CLOSE_WAIT` 常先查应用收尾，别把两者当同一类“连接没关干净”

一句最短人话是：**一个在替协议擦地，一个在催应用收拾会议室。**

## 三、`close`、`shutdown` 与 `SO_LINGER`：很多“连接怎么没优雅关闭”其实不是 TCP 不会关，而是应用根本没说清自己想关的是“整个 fd”还是“一个方向”

### 1. 为什么 `shutdown(SHUT_WR)` 和 `close()` 不该被混着用语义理解

`close()` 在 socket 世界里不仅涉及协议关闭，还涉及文件描述符引用计数。一个 fd 被复制、传递或被多个上层持有时，单次 `close()` 未必立刻等于“socket 进入最终关闭语义”。

`shutdown(SHUT_WR)` 则非常明确：本地发送方向到此为止，但我仍准备继续读对方后续数据。它是协议方向语义，不是对象引用语义。

所以当应用说“我要优雅半关闭，只写 EOF 让对方知道我说完了，但还要继续接收”，真正贴切的操作是 `shutdown(SHUT_WR)`；把它一股脑理解成 `close()`，经常会误判状态机为何走到 `FIN_WAIT` 或 `CLOSE_WAIT`。

### 2. `SO_LINGER=0` 为什么经常被误当成“更快的正常关闭”

看上去它确实会让 `close()` 很快结束，但这并不等于“更优雅”。当 `l_onoff=1, l_linger=0` 时，socket 关闭更像一种主动放弃：未发出的数据可能被丢弃，并通过 RST 告诉对方“这条连接别按正常 FIN 路线收尾了”。

所以它并不是温柔地加快挥手，而是在很多场景下直接改了关闭性质。把它当成性能优化按钮，会很容易把资源问题暂时藏起来，却把数据完整性或协议礼仪打烂。

### 3. 为什么生产里常说“`CLOSE_WAIT` 本质上是应用 bug”

因为到 `CLOSE_WAIT` 时，内核已经把“对方不再发送”这件事明确传给本地应用了。接下来若应用迟迟不 `close()` 或不完成自己的写方向收尾，这不是网络路径再怎么努力能替它补上的，而是上层逻辑没有结束对象生命周期。

这时候你继续调 socket 参数，常常是在绕着根因兜圈子。真正要查的是：哪个代码路径拿着 fd 没收、哪个线程卡住、哪个连接池归还失败。

### 4. 本节最该记住的结论：关闭连接首先是应用语义问题，`close` 管引用，`shutdown` 管方向，`SO_LINGER=0` 更像强制复位而不是优雅收尾

一句最短人话是：**别拿关门、关一半门和直接砸门当成一回事。**

## 四、Nagle + Delayed ACK：很多“小消息偶尔多等几十毫秒”的锅，不在带宽，而在双方都在“好心省包”时意外凑成了互等

### 1. 为什么带宽很空时，RPC 仍然可能莫名其妙变慢

这正是 Nagle/Delayed ACK 组合让人头疼的地方。应用明明每次只写几十字节，网络也不拥塞，CPU 也不忙，但就是偶尔出现一小截额外延迟。

这里的问题并不是“路不够宽”，而是发送方和接收方都在帮自己省操作：发送方想等等看能不能多攒一点小段再发，接收方想等等看能不能捎带 ACK 或少发一个纯确认。两边各自都很合理，可一旦交互模式是短小 request/response，就可能形成“你等我 ACK、我等下一个数据”的微型僵局。

### 2. 为什么 `TCP_NODELAY` 不是一把万能药

很多人一看到延迟抖动就想全局打开 `TCP_NODELAY`。这在低延迟小消息 RPC 场景里经常有效，但它本质上是在用更多更碎的小包去换更少等待。若业务更偏批量吞吐、包效率和聚合，盲目全关 Nagle 可能只是把延迟问题换成包数量与协议开销问题。

所以真正要先问的是：**我这个流量模式，主要痛的是小交互尾延迟，还是更在乎吞吐和包效率？**

### 3. 为什么 Delayed ACK 也不能被简单骂成“坏设计”

站在接收端看，立即为每个小段都回一个 ACK 也会制造很多纯确认包。Delayed ACK 的存在，就是在减少这种额外包负担。它的问题不在于它错，而在于你当前的业务交互模式恰好和 Nagle 组合出了互等。

这再次体现了排障的核心姿势：**先看交互模式和协议语义，再决定要不要动一个默认优化。**

### 4. 本节最该记住的结论：Nagle 和 Delayed ACK 单看都在省事，组合起来却可能在小消息交互场景中制造额外等待；是否关闭取决于你的流量模式

一句最短人话是：**两边都想省包时，第一条小消息可能就会多等一下。**

## 五、粘包：这不是 TCP 的 bug，而是应用把“有序字节流”误当成了“天然带消息边界的消息队列”

### 1. 为什么发送端两次 `send()`，接收端一次 `recv()` 读到一起并不奇怪

前面的三章已经把这个事实埋得足够深：TCP 的抽象对象是字节流，而不是消息。发送端两次写入的数据在网络上可能被合并成一个 segment，也可能分成多段；接收端一次 `recv()` 拿到多少字节，取决于当下内核缓冲里已到达并可交付的连续字节数，而不是发送端调用了几次 send。

所以所谓“粘包”，其实是应用层对 TCP 抽象边界的误解暴露出来了。

### 2. 为什么“半包”与“粘包”其实是同一件事的两个面

“粘包”说的是两条应用消息被一起读出来；“半包”说的是一条应用消息被拆成多次读出来。它们看起来相反，本质上是同一事实的两个面：**TCP 不保留应用消息边界。**

所以不要把它们当作两个不同问题，更不要去网络层找根因。真正要修的是应用协议如何显式标记消息边界。

### 3. 为什么解决方案永远在应用协议层

你可以用定长、分隔符、长度前缀、自描述编码等方式定义消息边界，但无论哪种方案，工作都必须由应用协议完成。内核不会也不应该替你猜“这一段字节什么时候算一条完整消息”。

这就像水管里的水。你不能要求水管自己帮你划分每一杯的边界，得靠量杯、刻度或隔板。

### 4. 本节最该记住的结论：TCP 负责连续可靠字节流，消息边界完全是应用协议的责任

一句最短人话是：**“粘包”其实是“你没有给字节流定义包边界”。**

## 六、SYN Cookies、TFO、RST、backlog：建连异常里最危险的误区，是把“握手没成”都当成同一种失败

### 1. 为什么“没连上”这个描述几乎没信息量

一个连接没建立起来，可能是：

- 对端端口没监听，立即回 RST；
- 防火墙静默丢弃，导致超时；
- 服务端半连接队列压力过大；
- backlog 满了但握手还在内核里推进；
- 开启了 SYN Cookies；
- TFO 在某些路径下提前带数据或被策略禁用。

这些场景在用户口头上都可能被说成“连不上”，但底层现实完全不同。排障如果不先拆开这几类失败，就会一直在黑箱里瞎调。

### 2. 为什么 backlog 和 `accept()` 的关系最容易被想错

很多人会以为应用不调用 `accept()`，三次握手就不能完成。更准确的说法是：三次握手主要发生在内核协议栈里；`accept()` 是从已完成连接队列里把 child socket 取给应用。应用取太慢当然会造成积压，backlog 满了也会影响新连接进入，但这不等于“不 accept 就无法握手”。

这区别非常关键，因为它决定你排查的对象到底是“握手本身没完成”，还是“握手完成了但应用没及时把连接取走”。

### 3. SYN Cookies 为什么是防御性降级，而不是常态神技

SYN Flood 时，服务端如果为每个半连接都长期保留完整 `request_sock` 状态，很容易被半连接耗尽资源。SYN Cookies 的思路是：在资源紧张时，不急着为每个 SYN 分配完整状态，而把必要验证信息编码进 SYN+ACK 序列空间里，等第三次 ACK 回来再验证并正式建连接。

这能提升抗打能力，但它本质上是一种防御性降级，会牺牲部分状态和选项处理的灵活性。把它理解成“永远打开更好”的常规优化是危险的。

### 4. TFO 为什么说明“连握手和应用数据都可能被尝试折叠”

TCP Fast Open 的目标，是把“先握手再传第一批应用数据”这两个动作在特定前提下更紧地压在一起。它的吸引力在于减少一次应用等待，但同时又会带来重放、策略、安全和兼容性上的权衡。

所以别把 TFO 只看成“更快的三次握手”，它是在拿更复杂的状态和安全边界换更低的连接首包延迟。

### 5. 本节最该记住的结论：建连异常里，“立即拒绝、静默超时、半连接保护、已完成队列积压、快速打开尝试”是不同类型问题，不能被一句“连不上”糊成一团

一句最短人话是：**“没连上”只是表面，真正要查的是：对方是明确说不、根本没回、来不及排队，还是在用防御策略硬撑。**

## 七、证据链：`ss`、`nstat`、`tcpdump` 这三层工具之所以关键，不是因为命令多，而是因为它们分别站在“当前 socket 视角、内核累计视角、包时间线视角”看同一个问题

### 1. 为什么只看一个指标几乎总会误导你

只看 ping、不看 socket；只看 `retrans`、不看抓包；只看抓包、不看内核状态……这些都很容易把你带偏。因为 TCP 问题常常同时横跨三种现实：

- 某个具体连接当前状态如何；
- 全机或全栈长期累计发生了多少重传、丢弃、RST、窗口压缩；
- 线上包的真实时间顺序到底是什么。

没有任何一个单独视角能把这三层都覆盖。

### 2. `ss -ti` 在回答什么

`ss` 更像当前 socket 的体检单。state、send/recv queue、rtt、rto、cwnd、delivery rate、retrans、skmem 等信息都让你知道：**此刻这条连接自己觉得自己怎么样。**

如果 `recv-q` 长、`send-q` 堆、cwnd 小、rtt 飙高或 state 异常，这能迅速帮助你判断是状态机尾部、窗口边界还是发送侧节奏出了问题。

### 3. `nstat` / `/proc/net/snmp` 在回答什么

这些更像协议栈总账。它不会告诉你某一条连接发生了什么，但会告诉你整个主机在一段时间里累计看到了多少重传、拥塞事件、RST、失败连接、接收错误等。它能帮你判断问题是孤立个案，还是一类系统性症状正在大面积发生。

### 4. `tcpdump` 在回答什么

抓包的独特价值在于时间线。只有它能真正展示某一条或几条连接上 Seq/Ack、dup ACK、SACK、窗口通告、SYN/FIN/RST 是按什么顺序出现的。你会看到“到底是先零窗口、后重传”，还是“先丢段、后 RTT 漫长退避”，还是“中间设备直接回了 RST”。

这让 `tcpdump` 成为把猜测变成现场证词的关键工具。证据位上，这一节最该强调的不是某个神奇命令，而是三层口径各自站位：`ss` 盯当前 socket 状态和局部窗口现实，`nstat`/`/proc/net/snmp` 盯整机累计协议总账，`tcpdump` 盯单条连接的真实时间顺序。只有把这三层叠起来，你才不会把“当前状态看起来正常”误判成“整条时间线没问题”。

### 5. 为什么这三层必须交叉验证

因为 TCP 症状太容易长得像。RTT 高可能是路径拥塞，也可能是接收端慢、应用不读、Delayed ACK、甚至抓包位置不同带来的误解。只有 `ss` 告诉你当前 socket 状态、`nstat` 告诉你系统累计背景、`tcpdump` 给你真实事件序列，这三条线对上了，你才真正敢下结论。

### 6. 本节最该记住的结论：TCP 排障真正有效时，从来不是“跑了个命令”，而是把当前连接、系统总账和真实包时间线拼成同一条证据链

一句最短人话是：**`ss` 看现在，`nstat` 看长期，`tcpdump` 看真相发生顺序。**

## 八、把本篇收成一张图：线上 TCP 症状不是参数表，而是一张把状态机、关闭语义、小包交互、消息边界和证据链重新拼回协议本体的诊断地图

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：为什么线上会同时出现 `TIME_WAIT`、`CLOSE_WAIT`、偶发几十毫秒延迟、“粘包”、SYN 异常和重传抖动，而大家却常常只会说一句“TCP 很慢”。答案首先不在参数表，而在把症状重新放回 TCP 机器内部。

`TIME_WAIT` 和 `CLOSE_WAIT` 都是连接没有彻底消失，但前者多半属于主动关闭方的协议卫生，后者常常暴露本地应用没有完成收尾。`close`、`shutdown` 和 `SO_LINGER` 又把“如何关”细分成引用释放、半关闭和强制复位三种完全不同的语义。Nagle 与延迟 ACK 说明带宽很空并不等于没有延迟，双方都想省包时小消息也可能互等。所谓“粘包”则把根因直接拉回应用层：TCP 从来就不是消息边界协议。

建连异常更进一步提醒你，“连不上”不是一种失败，而可能是 backlog、SYN Cookies、TFO、RST 或静默丢包路径的不同表象。最终，只有 `ss`、`nstat` 和 `tcpdump` 三层证据链拼起来，状态机、窗口、计时器和包时间线才会真正闭环。

把这一切压成最短总图，就是：

```text
状态层：
  TIME_WAIT / CLOSE_WAIT 指向不同的生命周期问题

关闭层：
  close / shutdown / linger 决定收尾方式

交互层：
  Nagle + delayed ACK 解释小包延迟

语义层：
  TCP 只给字节流，不给消息边界

建连层：
  backlog / SYN Cookies / TFO / RST 决定不同连不上路径

证据层：
  ss 看当前 socket
  nstat 看累计协议账本
  tcpdump 看真实时间线
```

所以本篇最该记住的一句话是：**TCP 排障真正有效的关键，不是背参数，而是把表面症状翻译回“这是哪一层语义在尖叫”，再用 socket 视角、协议总账和抓包时间线把它钉死。**

## 九、几个最容易说错的地方

### `TIME_WAIT` 多是不是一定说明系统出问题了？

不一定。它常常只是主动关闭很多连接的协议后坐力，只有与端口耗尽或容量问题叠加时才成为故障信号。

### `CLOSE_WAIT` 是不是“网络不好”的表现？

通常不是。它更常提示本地应用收到对端 FIN 后没有及时完成自己的关闭动作。

### `SO_LINGER=0` 是不是更优雅的快速关闭？

不是。它更接近强制复位，可能丢弃未发送数据并让对端看到 RST/`ECONNRESET`。

### “粘包”是不是 TCP 的 bug？

不是。TCP 只提供字节流，不负责应用消息边界；边界设计永远是上层协议的责任。

### `TCP_NODELAY` 是不是延迟高时就应该永远打开？

不一定。它是在更多小包开销和更低交互延迟之间做取舍，得看流量模式。

### 只抓个包是不是就足够排查 TCP 问题？

不够。真正靠谱的排障通常要把 `ss` 当前视角、`nstat` 累计视角和 `tcpdump` 时间线视角一起对起来。

## 收束：看懂 TCP 生产排障之后，你才会真正明白“线上现象”从来不是教材之外的意外，而是教材里那台状态机、窗口机和字节流机器在现实世界里的回声

回到开头那个问题：线上看到大量 `TIME_WAIT`、`CLOSE_WAIT`，客户端说“TCP 很慢”，服务端说“偶尔收不到完整消息”，这些现象其实是不是同一个协议的不同表情？现在答案已经完整闭环了。它们确实都来自同一台 TCP 机器，只是分别从状态机收尾、关闭语义、小包交互、消息边界和建连保护这些层面漏了出来。

也正因为如此，你会发现所谓“TCP 很慢”这种抱怨本身几乎没有信息量。真正重要的是先把它拆回：到底是状态尾巴在拉长、应用没收 fd、小消息互等、字节流被误用、SYN 队列吃紧，还是路径上真的出现了重传和拥塞。只有把这些问题重新放回 `rwnd/cwnd/ACK/Seq/Flags/定时器` 那张协议图里，再用 `ss`、`nstat`、`tcpdump` 把证据钉住，排障才不是碰运气。

这就是为什么说：**生产排障不是教材的反例，而是教材在现实里给你出的综合题。** 状态机、窗口、字节流和计时器本来就在那，只是线上把它们从抽象规则变成了会疼的现象。

## 十、误解清单、证据清单与边界清单

### 误解清单

- `TIME_WAIT` 多不自动等于系统出问题；它常常只是主动关闭方正常的协议后坐力。
- `CLOSE_WAIT` 通常不首先怪网络；它更常提示本地应用没有及时完成自己的关闭动作。
- `SO_LINGER=0` 不等于更优雅的快速关闭；它更接近强制复位，可能直接让对端看到 RST。
- “粘包”不是 TCP bug；它是应用把字节流误当成消息边界协议的后果。
- 只抓个包或只看一个计数器都不够；真正靠谱的排障要把 `ss`、`nstat`、`tcpdump` 三层口径对起来。

### 证据清单

- 当前 socket 视角：`ss -ti` 提供 state、send/recv queue、rtt、rto、cwnd、retrans、skmem 等，支撑“现在这条连接自己觉得自己怎么样”。
- 协议总账视角：`nstat` / `/proc/net/snmp` 提供重传、RST、失败连接、拥塞事件等累计计数，支撑“这是个案还是系统性症状”的判断。
- 时间线视角：`tcpdump` 提供 Seq/Ack、dup ACK、SACK、窗口通告、SYN/FIN/RST 的真实先后顺序，支撑“到底先发生了什么”的判断。
- 状态机告警：`TIME_WAIT`/`CLOSE_WAIT` 与前文状态机主线相互印证，支撑“状态多本身不是结论，关键在于它和资源或应用收尾是否绑定”的判断。
- 建连防护：backlog、SYN Cookies、TFO、RST 与防火墙路径共同支撑“连不上不是一种失败，而是多种路径分叉后的不同表象”。

### 边界清单

- 本文讨论的是 TCP 生产排障稳定心智模型；默认超时、SYN Cookie 触发条件、Delayed ACK 细节和 `ss` 输出字段会随内核与发行版变化。
- 线上的“TCP 很慢”本身没有信息量；必须先映射回状态、窗口、计时器、字节流或建连队列哪一层在报警。
- `ss`、`nstat`、`tcpdump` 三层视角各有盲区，单独使用都容易误判；它们的价值在于交叉验证。
- 关闭语义、Nagle/Delayed ACK、字节流边界和建连防护本来就不是一个维度的问题，不能混成一类“网络慢”处理。
- 本文先讲症状怎么翻译回协议机理；下一篇内核收包路径才真正回答“这些症状沿哪条流水线被放大”。
