## 现在真正该问的，不再是“包怎么进来”，而是“用户态明明只调了一个 `send()`，为什么数据却要先在本机内核里排队、算路、找下一跳、过 qdisc，最后才轮到网卡发光发电”

上一章我们沿着收包方向走完了整个旅程：网卡先 DMA 把帧卸进 RX ring，硬中断只负责按铃，NAPI/softirq 才批量提货，GRO 在协议栈前做合并，IP 层决定本机交付还是转发，TCP 最终把字节排进 socket 接收队列，再通过 `sk_data_ready` 和 epoll callback 让用户态醒来。

那条路径的核心收束是：**真正把“网线上来了一帧”翻译成“应用可以读到字节”的，不是某个单一函数，而是一条从 DMA 到 socket readiness 的流水线。**

发包路径则是这条流水线的镜像，但并不只是反向播放。因为发送侧有几个收包侧没有的特殊难点：

- 应用随时可能一次塞进来很多字节，但 TCP 不一定允许你现在就全发；
- `rwnd`、`cwnd`、Nagle、MSS/MTU 都会在发送侧同时施加边界；
- IP 路由和邻居子系统必须在真正出设备前把下一跳和目标 MAC 决定好；
- 本机设备出口还会再经过 qdisc 与驱动 TX ring 这些“本地出城队列”；
- 网卡是否支持 TSO/GSO、应用是否使用 `sendfile()`/`splice()`，又会决定 CPU 到底为每个段干了多少复制和分段工作。

这就是本篇真正要回答的核心困惑：**`send()` 返回到底意味着什么，TCP 是在哪一层真正把数据“接管”下来的，又是在哪一层才终于把它变成网卡可发送的物理现实。**

所以本篇最重要的顿悟是：**普通 `send()` 成功的语义，通常不是“对端已经收到”，甚至不是“网卡已经发出”，而是“本机 TCP 栈已经接管这批数据，并把它挂进了一条仍要经过窗口控制、路由、ARP、qdisc 和驱动的发送流水线”。**

先把总图记住：

```text
用户态入口：
  send/write/writev 把字节交给 socket

TCP 层：
  tcp_sendmsg 把字节排进发送缓冲和 write queue
  tcp_write_xmit 决定当前哪些 skb 真能放行

IP/邻居层：
  ip_queue_xmit 选路
  neigh_resolve_output / ARP 找下一跳 MAC

设备层：
  dev_queue_xmit 进入 qdisc
  驱动 ndo_start_xmit 把 skb 变成 TX descriptors
  NIC DMA 取数并真正发到链路上

优化层：
  TSO/GSO 让“大 skb”与“线上小段”分工
  sendfile/splice 尽量减少用户态显式拷贝
```

这一篇最重要的一句话是：**内核发包真正困难的地方，不是把字节搬出去，而是决定“现在允许发多少、走哪条路、发给谁的 MAC、先在本机排队多久，以及在哪一层把大块数据拆成线上真正的小段”。**

## 一、如果 `send()` 每次都要求立刻把数据同步送到网卡甚至等对端 ACK，用户态线程会被网络时钟拖死

### 1. 最朴素的错误世界：应用调用一次 `send()`，内核立刻构帧、立刻发包、最好还顺便等对端收到再返回

从“我 send 了，就该送出去”这个直觉出发，这似乎最符合用户心智。应用交了一段缓冲区，内核最好马上把它变成线上流量，甚至收到 ACK 再说成功。

可这会把用户线程完全绑死在网络时钟上。链路是否拥塞、对端是否及时 ACK、ARP 是否刚好过期、设备队列是否忙，这些本来就不受应用控制的现实，会直接变成 `send()` 的阻塞成本。只要网络稍有抖动，用户态调用就会被硬生生拖成长尾。

更糟的是，小写入会变成大量细碎同步动作，CPU、协议栈和设备都很难做批量与流水线优化。

### 2. 第二个失败世界：那就完全只拷到一个全局大缓冲池里，后面谁爱发谁发，应用永远立刻成功

这看起来像另一个极端解法：为了不拖住应用，send 只要把数据拷进本机某个大池子就立刻返回，后面什么时候发出去、发不发得出去都先不管。

这同样不成立。因为发送能力终究受 `rwnd`、`cwnd`、socket 缓冲、qdisc、TX ring 等资源限制。若 send 对这些边界一无所知，只无限兜底，系统很快会被发送缓冲、重传队列和设备排队拖爆。你只是把网络时钟从应用线程身上移走了，却没有建立任何靠谱的限流和排队秩序。

### 3. Linux 的答案：先把数据接进 socket 发送缓冲与 TCP write queue，再让后续层按窗口、路由和设备能力逐步放行

这就是 Linux 发包路径的核心取舍。`send()` 不等于“立刻上网线”，也不等于“无限收条子不记账”，而是先把用户数据交给一个受控的发送流水线入口：socket 发送缓冲和 TCP write queue。

应用和网络由此被部分解耦。应用可以先把数据提交给本机 TCP 栈，只要本机发送缓冲还有空间；后续真正何时发、能发多少，则再由 TCP 窗口、IP 路由、邻居解析、qdisc 和驱动来层层决定。

这也解释了为什么 `send()` 的成功语义只是一种“本机接管成功”，而不是终点承诺。若要把这一节补成更硬的源码正文，最关键的证据位应回到 `net/ipv4/tcp.c` 中 `tcp_sendmsg()` 和发送缓冲/write queue 相关路径：它们共同支撑“`send()` 首先是把字节纳入本机 TCP 的待发送体系，而不是直接交给网卡”的判断。

## 二、`tcp_sendmsg()`：发送路径真正开始的地方，不是 IP，也不是网卡，而是 socket 发送队列和发送缓冲的内核记账世界

### 1. 为什么用户数据首先要进入 socket 发送缓冲

TCP 不是收到一段用户态字节就立刻把它们整批推出去，而是要考虑拥塞窗口、接收窗口、分段粒度和重传。如果应用写得比网络快，本机必须有一个地方暂时把这些待发送字节接住。这就是 socket 发送缓冲存在的现实意义。

它相当于一个本机侧的“待发仓库”：应用把货交给仓库，仓库再按网络节奏逐步出货。没有这一层，应用就会被迫与 RTT 和 ACK 周期同步，吞吐和可编程性都会很差。

### 2. 为什么 `tcp_sendmsg()` 不能只做一次简单 `copy_from_user`

从表面上看，它确实要把用户缓冲区数据搬进内核；但更深一层，它还在决定这些字节如何被组织成写队列中的 skb、当前是否应该触发 push、是否要受 Nagle/TCP_CORK 等策略影响，以及发送缓冲账本还剩多少空间。

所以 `tcp_sendmsg()` 真正做的不是“拷贝完就完”，而是**把应用字节编排进 TCP 的待发送世界。** 这一步既涉及内存复制，也涉及发送语义组织。

### 3. 为什么发送缓冲不足时阻塞 socket 和非阻塞 socket 体验完全不同

这也是发包路径在应用可见语义上的关键点。若发送缓冲已经顶到上限，而应用又继续写：

- 阻塞 socket 会等可用空间重新出现；
- 非阻塞 socket 则更倾向于返回 `EAGAIN/EWOULDBLOCK`。

也就是说，应用是否被拖住，并不是仅由网络状态决定，还取决于它对 socket 的编程模式。这一点会直接影响上层 I/O 模型和事件循环设计。

### 4. 为什么说 `tcp_sendmsg()` 是“发包”的第一现场，却还远没到“真正发出”的时刻

这非常值得反复强调。到这里为止，数据只是进入了 TCP 栈自己管理的发送世界：写队列、sk_wmem、可能的 segment 组织和发送条件判断。它还没经过路由、没找下一跳 MAC、没进 qdisc、没进驱动 TX ring，更没上物理链路。

所以不要把 `send()` 返回时刻错认成“包已经发了”，顶多说“这批字节已经合法进入了 TCP 的发货系统”。

### 5. 本节最该记住的结论：`tcp_sendmsg()` 的核心不是立刻发，而是把用户数据纳入一个受发送缓冲、分段策略和窗口控制约束的待发送体系

一句最短人话是：**`send()` 首先是在把货交给 TCP 仓库，不是在把货交给网卡。**

## 三、`tcp_write_xmit()` 与 `ip_queue_xmit()`：真正决定“现在能放行多少”的，是窗口和 inflight；真正决定“放行后往哪走”的，才是路由和 IP 层

### 1. 为什么 TCP write queue 不可能一上来就全部出队

上一章你已经知道，发送方真正可让同时在途的数据上界是 `min(rwnd, cwnd)`。这意味着就算 write queue 里堆着很多待发送字节，TCP 也不能因为它们已经排好队就一次性全发。它还得问：

- 对端现在还愿意接多少？
- 当前路径估计还能承受多少 inflight 数据？
- 已发未确认的部分目前又占了多少？

所以 TCP write queue 像一个待发总仓，`tcp_write_xmit()` 才是出货闸门。没有这个闸门，上一章讲的流控和拥塞控制就全失效了。证据位上，这层最值得回到 `tcp_output.c`/相关发送路径中 `tcp_write_xmit()` 一类逻辑去看：它们共同支撑“write queue 里有货不等于现在都能出仓，真正能放行多少还得过 rwnd/cwnd/inflight 这道门”的判断。

### 2. 为什么 `snd_wnd` / `cwnd` / inflight 这些量在这里第一次真正落地成“放行还是不放行”

上一章它们更多还是概念模型；在 `tcp_write_xmit()` 一类发送逻辑里，它们终于变成现实中的门槛判断。某个 skb 是否能被推进到真正发包路径，不是看应用写没写，而是看这些窗口和已在途数据状态是否允许再多放一辆车上路。

这也说明 TCP 的“拥塞控制/流控”不是理论附加，而是发包路径的核心刹车器。

### 3. 为什么 `ip_queue_xmit()` 的角色和 `tcp_write_xmit()` 完全不同

一旦 TCP 决定“这批数据现在可以发”，接下来问题就从“发不发得出”切换成“发出去后往哪走”。`ip_queue_xmit()` 站的正是这个位置：它不再关心序列号和拥塞窗口，而是关心目的 IP、路由表、出接口、本地出站 Netfilter 和后续链路封装入口。

所以千万别把 TCP 和 IP 发送路径揉成一团。前者决定的是“允许出仓的节奏”，后者决定的是“出仓之后走哪条路线”。

### 4. 为什么这里再次印证了“协议栈的每层只做自己那一层决定”

`tcp_write_xmit()` 不负责路由，`ip_queue_xmit()` 不负责判断 `cwnd` 是否够，链路层更不会知道应用刚才 write 了几次。每一层都只在自己的边界上追加一个新的裁决：

- TCP 说你现在能发多少；
- IP 说发了以后该往哪；
- 邻居子系统说往那边时下一跳 MAC 是谁；
- qdisc 说本机出口该怎么排。

这正是网络卷开头那条逐层翻译哲学在发送方向上的再次落地。

### 5. 本节最该记住的结论：发包路径里，TCP 负责“是否放行”，IP 负责“放行后去哪”，两者都是闸门但不是同一个问题

一句最短人话是：**TCP 管发货额度，IP 管发货路线。**

## 四、邻居子系统与 ARP：真正让一个待发 skb 从“知道下一跳 IP”变成“具备 Ethernet 头里该填哪个 MAC 的能力”的，是这座最后的桥

### 1. 为什么发包路径到这里还不能直接调用网卡

即使路由已经告诉你“从 eth0 发，下一跳是 192.168.1.1”，网卡和交换机在二层仍然不认这个 IP。它们看的是目的 MAC。若没有这个 MAC，Ethernet 帧头就不完整，发也无从发起。

所以发包路径到了链路入口前，还得再过一道桥：从 next-hop IP 找到 next-hop MAC。这就是邻居子系统和 ARP 的职责。

### 2. 为什么 ARP 未命中时 skb 会被暂存，而不是立即失败

这一点和第一篇里讲过的 ARP 语义在发送路径上完全闭环。若邻居状态是 `NUD_INCOMPLETE`，系统会发 ARP Request，并把当前待发 skb 暂时挂到邻居等待机制里。这样一来，TCP 不用因为“MAC 还没解析出来”就立刻把这次发送判失败；它可以把链路地址解析问题交给下层统一处理。

所以 ARP 未命中常常对应的是“首包延迟”，而不是“首包消失”。只有解析超时、队列满或邻居不可达时，问题才升级成真正失败。

### 3. 为什么这一步特别能说明 TCP/UDP/ICMP 都共享同一套链路解析现实

TCP 并不单独拥有 ARP 逻辑，UDP 也不单独拥有。因为“下一跳 IP 如何变成链路地址”本来就属于所有 IP 负载共享的最后一跳问题。邻居子系统正是为这种共享性存在的。

这也就是为什么网络栈要分层：上层协议不必各自重写一套“小区找门牌”流程。

### 4. 本节最该记住的结论：邻居子系统和 ARP 不是发送路径的小尾巴，而是 IP 路由结果能真正落成二层帧目的地址的最后桥梁

一句最短人话是：**路由告诉你去哪栋楼，ARP 才告诉你这栋楼门牌号。**

## 五、`dev_queue_xmit()`、qdisc 与驱动 TX ring：就算 TCP 和路由都点头了，本机出口仍然不是一条无阻塞直道，而是一套要排队、要整形、要交给硬件 DMA 的本地发车系统

### 1. 为什么协议栈准备好了 skb，不代表可以直接塞给网卡

如果系统里只有一个 socket、一个流、一个网卡，直接交给驱动似乎很自然。现实里却常常有很多 socket 和很多流同时争用同一设备出口。若谁准备好就立刻发，设备队列和时延会迅速变得不可控，更别提优先级、整形、公平性和 bufferbloat 问题。

所以在“协议栈已经准备好发”与“网卡真正开始 DMA 发送”之间，本机还必须有一层自己的出口秩序。这就是 `dev_queue_xmit()` 和 qdisc 的存在理由。

### 2. qdisc 真正解决的不是“协议正确性”，而是“本机出口的公平、顺序和排队语义”

TCP 的窗口控制站在端到端视角，qdisc 则站在本机设备视角。它要决定：

- 多个流共享同一出口时谁先上；
- 是否做简单 FIFO，还是按流公平、优先级、整形等策略调度；
- 本机出口队列要不要过深，怎样避免 bufferbloat。

这说明 qdisc 不是 TCP 的重复实现，而是**本机出口层面的排队政策。** 若要补这一节的实现证据位，最关键的落点应回到 `net/core/dev.c` 中 `dev_queue_xmit()`、qdisc 进入与驱动发车相关路径：它们共同支撑“协议允许发并不等于本机出口不用再排队，本地发车系统仍有自己的治理层”这句判断。

### 3. 为什么驱动的 `ndo_start_xmit()` 是另一个世界的入口

一旦 skb 穿过 qdisc 和 `dev_queue_xmit()`，它才真正从通用网络核心世界进入设备驱动世界。驱动要把 skb 变成 TX descriptors，交给 NIC 去 DMA 读取数据并上线。这时关注点从序列号、ACK、路由表切换成了：

- TX ring 还有没有空位；
- 这张 skb 是否需要硬件 offload；
- 发送完成后怎样回收 descriptor 和 skb。

所以 `ndo_start_xmit()` 像发包路径里的最后一道海关：过去了，才算真的要变成电/光信号。

### 4. 为什么 BQL 等机制再次说明“队列并不是越大越好”

很多人会本能觉得，出口队列大一点总更安全，免得网卡吃不饱。可队列太大反而可能把延迟藏进本机设备出口，形成典型 bufferbloat：上层看起来还在流畅 send，实际上包都排在本地很久了。

所以现代发送路径越来越强调：**不是要无限排队，而是要把队列放在最该放的位置、最该控制的深度。** BQL 这类机制正是在提醒你，本机队列本身也是延迟控制的一部分。

### 5. 本节最该记住的结论：`dev_queue_xmit()` 和 qdisc 代表的是“协议允许发”之后，本机出口仍要再做一次排队治理；驱动和 TX ring 则把这个逻辑世界真正翻成硬件发车动作

一句最短人话是：**TCP 点头了，不代表网卡马上就走；中间还有本机收费站和装车道。**

## 六、TSO/GSO 与 `sendfile()` / `splice()`：真正的性能优化，不是改掉 TCP/IP 语义，而是把“分段”和“复制”尽量推到更合适的位置去做，或者直接少做一次

### 1. 为什么 CPU 不一定真要为每个线上 TCP 段单独构造一个小 skb

上一章讲过 MSS 决定线上 segment 粒度，这不等于上层在很早时就必须把每个 segment 都完全拆出来。若应用写了很大一段连续数据，而后面还有 TSO/GSO 能力，系统完全可以先保留更大的 skb，并把“最终切成很多符合 MSS 的小段”这件事推迟到更靠近设备或由硬件完成。

这就是 TSO/GSO 的真正价值：**它们改的是“分段发生的位置”，不是“TCP 还要不要分段”这条协议事实。**

### 2. TSO 和 GSO 为什么不能混成一个概念

TSO 更偏向把“大 skb 的最终切段工作”交给网卡硬件；GSO 则是在内核里提供一套通用的软件分段回退机制。二者都服务同一个目的：让上层不必过早把每个小段都拆出来，但它们分担工作的层次不同。

这就像物流中心先把大周转箱推到装车区，最后是在硬件分拣机上拆，还是在人工最后一道口上拆，路线不同，但都不改变最终上路的单车尺寸必须合规。

### 3. 为什么 `sendfile()` / `splice()` 不是“没有任何拷贝”的神话按钮

这类接口最核心的收益，是减少用户态显式中转：文件页尽量不必先读进用户缓冲区，再被应用写回 socket，而是让内核直接把页缓存和 socket 发送路径接起来。

可这不等于整条系统路径里没有任何内存搬运。页缓存是否命中、文件系统和 socket 路径支持如何、TLS/offload/驱动能力怎样，都会决定最终还能剩多少拷贝、多少引用传递。

所以更准确的说法是：**它们尽量减少用户态往返和一次显式复制，而不是保证“全路径绝对零拷贝”。**

### 4. 本节最该记住的结论：发送路径优化的关键，不是改变协议，而是把“分段”和“复制”这两笔最重的 CPU 活，尽量后移、下放或省掉一层

一句最短人话是：**真正高效的发送，不是少走语义，而是少做重复体力活。** 证据位上，这层最合适回到 TSO/GSO、`sendfile()`、`splice()` 与相关发送优化路径去看：它们共同支撑“优化并没有改掉 TCP/IP 语义，而是在分段发生的位置和用户态复制次数上动刀”这句判断。

## 七、把本篇收成一张图：发包不是“用户一写就上线”，而是“先把数据交给 TCP 仓库，再让窗口、路由、ARP、本机出口排队和硬件能力一层层点头”

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：`send()` 返回之后，数据为什么还可能只在内核队列里，而没有真正到网卡。答案首先说明，普通 `send()` 的第一现场不是设备，而是 `tcp_sendmsg()` 和 socket 发送缓冲：应用先把字节交给本机 TCP 仓库。之后 `tcp_write_xmit()` 再依据 `snd_wnd`、`cwnd` 和 inflight 状态决定当前哪些 skb 真的可以放行。

一旦放行，`ip_queue_xmit()` 与路由表决定该往哪条出路走；邻居子系统再把 next-hop IP 变成 next-hop MAC。即便这些都完成了，skb 还要再经过 `dev_queue_xmit()` 和 qdisc，把多个 socket/流的本机出口排队问题处理完，最后才由驱动 `ndo_start_xmit()` 填 TX ring，让网卡 DMA 取数并上线。TSO/GSO 继续决定“最终小段是在硬件还是软件口子上拆”，`sendfile()`/`splice()` 则尽量减少用户态往返和一次显式复制。

把这一切压成最短总图，就是：

```text
用户态：
  send / write / writev

TCP 入口：
  tcp_sendmsg → write queue / send buffer

放行层：
  tcp_write_xmit 按 rwnd/cwnd 决定何时出仓

路由与链路层：
  ip_queue_xmit → route / Netfilter / ARP

设备出口：
  dev_queue_xmit → qdisc → ndo_start_xmit → TX ring → NIC DMA

优化层：
  TSO/GSO 调整分段位置
  sendfile/splice 减少用户态复制
```

所以本篇最该记住的一句话是：**`send()` 的成功语义通常只是“本机 TCP 栈已经接管了这批数据”；真正把它变成线上流量，还要再经过窗口、路由、邻居、本机排队和硬件发车这几道门。**

## 八、几个最容易说错的地方

### `send()` 返回是不是就说明网卡已经把包发出去了？

通常不是。它更常说明数据已经进入本机 TCP 发送路径并被接管，后面还要经过多层排队和放行。

### 发送缓冲区是不是只是一个性能优化缓存？

不只是。它也是应用与网络时钟解耦、阻塞/非阻塞语义成立以及发送路径限流的关键一环。

### `cwnd`/`rwnd` 决定了能发多少，是不是就不需要 qdisc 了？

不是。前者解决端到端和接收方边界，qdisc 解决本机设备出口多流争用与排队治理，是不同层问题。

### ARP 未命中时，发送路径是不是会立刻失败？

通常不会。邻居子系统会先尝试解析并暂存待发 skb，只有解析失败或队列/超时等条件触发时才转成真正失败。

### TSO/GSO 是不是改变了 TCP MSS 语义？

不是。它们改变的是分段发生的位置，不改变线上 segment 必须满足 MSS/MTU 约束的事实。

### `sendfile()` 是不是保证全路径绝对零拷贝？

不是。它的核心收益是减少一次用户态往返和显式复制，具体还有多少拷贝取决于缓存、协议和硬件路径。

## 收束：看懂内核发包路径之后，你才会真正明白“发送数据”在 Linux 里首先不是上线，而是排进一条等待被逐层放行的物流链

回到开头那个问题：用户态 `send()` 之后的数据到底如何从 socket 发送队列、TCP/IP、qdisc、驱动 TX ring 一路走到网卡，并最终变成电/光信号？现在答案已经完整闭环了。`send()` 先把数据交给本机 TCP 栈，TCP 再根据窗口与 inflight 状态决定何时放行，IP 和路由决定走哪条路，ARP/邻居子系统补齐本地链路门牌，qdisc 和驱动把包推进本机出口与 TX ring，最后由 NIC DMA 和硬件发送出去。每一层都只回答自己那一层的“现在能不能继续往前走”。

也正因为如此，你会发现发送路径上的很多线上现象——`send()` 成功但对端还没收、发送缓冲区积压、ARP 首包延迟、qdisc backlog、TSO 关掉后 CPU 飙高——并不是随机问题，而是这条物流链某个环节在放大现实约束。理解了发包路径，你就不再只会说“应用发不出去”，而会继续追问：**它是卡在 TCP 仓库、窗口放行、路由/ARP、本机出口排队，还是硬件发车这一站。**

这就是为什么说：**发包的本质不是 copy，而是分层放行。** 真正的发送能力，从来不是由应用一头说了算，而是要等这一长串环节都点头。

## 八、误解清单、证据清单与边界清单

### 误解清单

- `send()` 返回不等于网卡已经把包发出去了；它更常意味着本机 TCP 栈已经接管了这批数据。
- 发送缓冲区不只是性能缓存；它也是应用与网络时钟解耦和阻塞/非阻塞语义成立的关键一层。
- `cwnd`/`rwnd` 不会替代 qdisc；前者管端到端/接收方边界，后者管本机出口多流排队和整形。
- ARP 未命中不等于发送路径立刻失败；邻居子系统通常会先尝试解析并暂存待发 skb。
- `sendfile()`/`splice()` 不是保证全路径绝对零拷贝；它们更核心的收益是减少一次用户态往返和显式复制。

### 证据清单

- 发送入口：`net/ipv4/tcp.c` 中 `tcp_sendmsg()` 与发送缓冲/write queue 相关路径，支撑“`send()` 首先把字节交给本机 TCP 仓库”的判断。
- 放行闸门：`tcp_output.c`/相关发送路径中的 `tcp_write_xmit()` 逻辑，支撑“真正能出仓多少取决于 rwnd/cwnd/inflight”的判断。
- 路由与邻居：`ip_queue_xmit()`、邻居解析与 ARP/next-hop 路径，支撑“放行之后还得先找路、找 MAC”的主线。
- 本机出口：`net/core/dev.c` 中 `dev_queue_xmit()`、qdisc 和驱动 TX 相关路径，支撑“协议允许发并不等于本机出口不用再排队”的判断。
- 优化层：TSO/GSO、`sendfile()`/`splice()` 与相关路径，支撑“优化是在分段位置和复制次数上动刀，而不是改掉协议语义”这句判断。

### 边界清单

- 本文讨论的是 Linux 常见内核发包心智模型；qdisc 默认策略、offload 能力、BQL、零拷贝路径和驱动细节会随网卡、驱动和内核版本变化。
- `send()` 的成功语义首先是“本机接管”，不是对端收到、更不是 durable/可靠交付证明。
- TCP 窗口、路由、邻居、本机出口和驱动各管一层现实，不能把任一层简化成“最后只是发包”。
- TSO/GSO、`sendfile()`/`splice()` 的收益高度依赖协议路径和硬件能力，不适合被宣传成无条件神技。
- 本文先讲“包怎么走”；下一篇 I/O 模型才真正回答“应用怎么等、在哪里等、谁承担等待成本”。
