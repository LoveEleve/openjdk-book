## 现在真正该问的，不再是“线程在数据未就绪时怎么等”，而是“为什么 select/poll 明明已经会睡眠了，到了 1 万个 fd 场景里仍然得每轮重扫，而 epoll 又是怎样把这件事从‘每次重查’改成‘有变化时增量记账’的”

上一章我们已经把 I/O 模型的本质说清楚了：阻塞 I/O 把等待交给内核调度器，非阻塞 I/O 把等待退回用户态；select/poll 让你一次等待很多 fd，但每轮都要重新提交整张名单、重新遍历一遍；信号驱动和异步 I/O 则分别在 readiness 通知和 completion 通知两条线分叉。

到这里，select/poll 的局限已经非常明确：**它们的问题不是不会睡，而是“睡醒后、下一轮调用时，整批监听关系还得从头再报一遍，再从头扫一遍”。**

这就把我们带到 epoll 真正的核心困惑：

- 为什么 epoll 并不是“更快的 poll”这么简单？
- 它到底怎样把“关注哪些 fd”和“这次哪些 fd 已经就绪”拆成两套长期/短期结构？
- 为什么 `epoll_wait()` 可以只消费当前 ready list，而不是每次都重查整张名单？
- LT 和 ET 到底改变的是“socket 行为”，还是“事件重复呈现语义”？
- Reactor 模式究竟和 epoll 的关系是什么，为什么很多高并发框架都把 epoll 当底座，而又必须在其上自己组织 handler、线程和业务状态机？
- io_uring 为什么看起来像是“下一代 epoll”，但其实回答的问题并不完全一样？

所以本篇最重要的顿悟是：**epoll 真正的突破不是把单次扫描写得更快，而是把“我长期关心哪些 fd”作为内核状态留下来，再让“这次谁就绪了”在事件到来瞬间增量加入 ready list；`epoll_wait()` 只来领现成结果。**

先把总图记住：

```text
select/poll 世界：
  每轮调用重新交一整份 fd 名单
  内核每轮重新遍历和检查

epoll 世界：
  interest list 长期保存在内核中
  数据到达时通过回调把对应 epitem 挂入 ready list
  epoll_wait 只消费当前 ready list

LT/ET：
  不是两种 socket
  而是事件如何重复呈现给应用的两种报告策略

Reactor：
  在 epoll 提供的 ready list 之上组织事件循环与 handler 分发

io_uring：
  把问题从“谁准备好了”进一步推进到“哪次 I/O 已经完成”
```

这一篇最重要的一句话是：**epoll 的关键不在红黑树，而在“监听关系持久化 + 就绪事件增量生产 + `epoll_wait` 只取 ready list”这一整套等待组织方式。**

## 一、如果每轮都重新把 1 万个 fd 交给内核，再让内核重扫 1 万个 fd，哪怕只有 3 个有数据，你也已经为剩下 9997 个“什么都没发生”的对象白付了成本

### 1. select/poll 真正浪费在哪里

上一章已经讲过，select/poll 的主要问题并不是“它们不会睡”——睡眠本身已经把 CPU 空转成本压下去很多了。真正贵的地方是：**每轮调用前后，它们都得围着整个 fd 集合做一次从头组织和从头检查。**

连接数少时，这种成本不显眼；一旦监控的 fd 数量进入几千、几万级，而每轮其实只有极少数 fd 真正就绪，你的绝大多数 CPU 时间就会被“确认那 9997 个还没事”吞掉。

### 2. 最朴素但错误的优化想法：那就在用户态记住上一次的名单，下次别重新传

这看起来很自然：既然每轮都传名单很浪费，那用户态不如记住监听关系，下次只把变化部分交给内核。

问题是，如果内核本身不保存这份监听关系，它下一轮照样得重新构造等待关系；如果它保存了，你实际上就已经开始走向 epoll 思想了。也就是说，这条“半优化想法”最终会逼你承认：**监听关系应该成为内核里的长期状态，而不是每次 wait 的临时输入。**

### 3. epoll 的根本回答：把“名单本身”变成内核长期保存的对象

这正是 epoll 和 select/poll 最本质的分歧。epoll 不是在每轮 wait 时重新接收一份完整兴趣集合，而是先通过 `epoll_ctl` 把“我长期关心这些 fd 的这些事件”注册进内核，让它变成一个持久的 interest list。

这样一来，等待阶段就不必再从用户态完整重传“全名单”，内核也不必每轮重新为这份名单从零建立等待关系。监听关系只在 ADD/MOD/DEL 时变化，而不是在每次 wait 时重建。

### 4. 为什么这还不足以解释 epoll 的全部优势

很多人知道“epoll 监听关系常驻内核”，就以为问题已经解决了。其实这只是第一步。如果 epoll 只是把全名单存起来，但 `epoll_wait()` 每次仍然线性扫一遍名单，那你只是省了传参，没省掉等待的根成本。

真正让 epoll 性能模型变样的，还在第二步：**就绪事件不是 wait 时全量扫描出来的，而是在事件发生时通过回调增量地推入 ready list。** 这才是从“每次检查所有人”变成“谁有变化谁自己举手”的关键。若要把这一节补成更硬的源码正文，最关键的证据位应回到 `fs/eventpoll.c` 中 `eventpoll`/`epitem` 的 interest list 管理和 `ep_poll_callback` 的 ready list 挂接路径：它们共同支撑“epoll 真正省下的不是单次扫描常数，而是把 ready 事件生产时机前移到了事件发生瞬间”这句判断。

### 5. 本节最该记住的结论：epoll 真正第一刀砍掉的，不是扫描算法，而是“每轮重建监听关系”这层浪费

一句最短人话是：**select/poll 每次都交临时名单，epoll 先把名单长期存档。**

## 二、`eventpoll` 与 `epitem`：epoll 之所以能既记住你关心哪些 fd，又只在 wait 时返回少数就绪项，是因为它内部从一开始就把“通讯录”和“来电列表”拆成了两套结构

### 1. 为什么一个结构同时承担“注册管理”和“就绪消费”会天然别扭

假设 epoll 只有一份单一容器，同时用它来表示“所有被关注的 fd”和“当前这次可返回的事件”。那么你会立刻遇到矛盾：

- 注册管理需要支持 ADD/MOD/DEL、去重、查重和持久保存；
- 就绪消费则需要支持快速把当前 ready 项取出来、重复控制、唤醒等待者。

这两类问题的访问模式完全不同。硬塞进一套结构里，常常会让其中一边非常难看。

### 2. `eventpoll` 里的 interest list 和 ready list 为什么必须分家

这就是 epoll 最值得看清的一点。内核里的 `eventpoll` 不是一根单链表，而是同时维护：

- 一套“我现在长期监视哪些 fd、它们关注什么事件”的索引世界；
- 一条“当前已经 ready，可以被 `epoll_wait()` 消费”的就绪链表。

这两者关系非常像：通讯录和来电记录。通讯录长期在那，不因本次是否来电而消失；来电记录只保留当前有变动者，消费后又可能清空或等待下次事件重新挂入。

### 3. `epitem` 的角色是什么

一个被 epoll 监视的 fd，并不是只在内核里留个整数就完事。它需要一份“监视项对象”来把 file 指针、用户注册的事件掩码、用户态附带的 data、以及和 wait queue 的回调关系都挂到一起。这个对象就是 `epitem` 这类中间实体的意义。

你可以把它理解成：**不是 fd 自己知道自己在被谁盯，而是 epoll 为每个被盯对象准备了一张长期档案卡。** 只有这样，后面事件到来时，内核才能顺手知道该把哪张卡扔进 ready list。

### 4. 为什么说 ready list 才是 `epoll_wait()` 近乎“只领现成结果”的根本前提

当某个 fd 变得可读/可写，系统不需要等 `epoll_wait()` 再去全量检查；它会在事件发生时，把对应 `epitem` 挂进 ready list。于是 `epoll_wait()` 运行时面对的就不再是“全部关注对象”，而是“已经就绪对象的现成名单”。

这就是 epoll 真正绕开 O(N) wait 扫描的关键：**不是 wait 变聪明，而是生产 ready 事件的时机前移到了事件发生瞬间。**

### 5. 本节最该记住的结论：epoll 之所以像“只处理有事的人”，是因为它从结构设计上就把“长期关注名单”和“当前就绪名单”彻底拆开了

一句最短人话是：**interest list 是长期通讯录，ready list 是本轮来电列表。**

## 三、`epoll_create1` / `epoll_ctl` / `epoll_wait`：三组系统调用真正对应的是“建总台、长期登记、现场领单”，而不是三种同级别的“事件等待函数”

### 1. 为什么 `epoll_create1` 不是“立刻开始等待事件”

很多初学者会把 `epoll_create1()` 看成“开始用 epoll 的入口”，仿佛调用后就已经接近等待阶段。更准确的理解是：它只是帮你创建了一座事件总台，内核因此拥有一个 `eventpoll` 实例，可以开始收纳长期监听关系和就绪链表。

也就是说，创建 epoll fd 不等于有了任何兴趣对象，更不等于已经开始等待事件。它只是建了一个“你以后可以把很多 fd 登记进来的容器”。

### 2. `epoll_ctl` 为什么是 epoll 的核心，而不只是“添加 fd 的小工具函数”

上一节已经讲过，epoll 的根思想是把监听关系长期保存进内核。真正执行这件事的就是 `epoll_ctl`。ADD 把新 fd 和感兴趣事件注册进去，MOD 更新它的兴趣掩码，DEL 则把它从通讯录和可能的 ready 关系里都清掉。

因此 `epoll_ctl` 不是“杂务接口”，而是 epoll 的灵魂入口：没有它，epoll 就退化成一个空壳 wait 容器，根本没有长期 interest list 这一设计价值。

### 3. 为什么 `epoll_wait` 本质上是在消费 ready list，而不是发起一次新的全局轮询

这一步和 select/poll 的思维方式完全不同。`epoll_wait()` 不再说“帮我现在去看这 10000 个 fd 里谁准备好了”，而更像说：“把你已经知道 ready 的那批先给我，如果现在还空，就睡着等下一个 ready 事件到来时叫醒我。”

注意这句差别极其关键。它意味着 `epoll_wait()` 是消费者，不再是主要生产者。ready 事件的生产被回调提前做掉了，它只是按需领取结果。

### 4. 为什么说 epoll 生命周期天然对应“建总台 → 做订阅 → 收通知”

如果把三个调用重新翻成人话，它们其实非常清晰：

- `epoll_create1`：建事件总台；
- `epoll_ctl`：做长期订阅登记；
- `epoll_wait`：收本轮已就绪通知。

这样看时，你就很难再把 epoll 理解成“另一个 poll”。poll 每轮重提名单，epoll 则先长期建台和登记，再按 ready list 收通知。模型完全不同。

### 5. 本节最该记住的结论：epoll 三个系统调用分别对应“建总台、长期登记、按 ready list 领结果”，其价值重点在 `epoll_ctl` 建立的持久监听关系和 `epoll_wait` 的消费语义

一句最短人话是：**epoll 不是一轮轮点名，而是先订阅，再等通知。**

## 四、`ep_poll_callback`：epoll 真正省下 O(N) 的地方，不在 wait 里查得更快，而在数据到达那一刻就顺手把“谁 ready 了”记好了

### 1. 为什么“事件生产时就登记 ready”比“等待时才全量检查”高明得多

select/poll 的痛点在于，事件有没有发生，很多时候要等 wait 阶段再全量盘点。epoll 的思路则完全相反：既然 socket 在收包、发包、错误和挂断时本来就会走自己的唤醒链，何不在那个时刻顺手把相应 `epitem` 放进 ready list？

这样 wait 阶段就不再承担“发现谁 ready”的主责，而只是“拿走已经 ready 的项目”。

这就是 `ep_poll_callback` 路径真正的价值：**ready 事件由事件到达时增量生产，而不是由等待者事后全量发现。**

### 2. 为什么这再次把 epoll 和 socket 等待队列紧紧绑在一起

前面 I/O 模型篇已经讲过，socket readiness 最终会沿着 `sk_data_ready`、wait queue 等链路传播。epoll 并没有另起炉灶，而是把自己接进了这条既有通知链：当底层对象状态变化时，它顺手收到通知，再把对应监视项排进自己的 ready list。

这说明 epoll 并不是绕过 socket readiness 机制，而是在其之上再搭一层“多对象就绪聚合器”。

### 3. 为什么 epoll 不能被误解成“所有操作都 O(1)”

这也是经常被宣传口号搞糊涂的地方。epoll 的核心优势是**避免每次 wait 对所有未就绪 fd 做 O(N) 检查**，而不是宣称“任何场景下所有动作都常数时间”。

- ADD/MOD/DEL 仍要维护内核中的兴趣关系；
- 大量事件同时 ready 时，把这些事件拷给用户态本身就和事件数成正比；
- 某些回调、去重和锁竞争也有自己的代价。

所以更准确的说法是：epoll 把“每轮无意义检查全体 fd”的成本大幅压掉了，而不是把一切都神化成 O(1)。

### 4. 本节最该记住的结论：epoll 的真正性能来源是“ready 事件在发生时就被放进 ready list”，而不是 wait 阶段 magically 查得飞快

一句最短人话是：**epoll 不是等的时候更聪明，而是平时就把账记好了。**

## 五、LT 与 ET：它们真正改变的不是 socket 本身，而是“同一份 readiness 该重复提醒几次”；ET 把“把当前缓冲区彻底读/写到 EAGAIN”为止的纪律强行交给了应用

### 1. 为什么 LT / ET 容易被误解成“两种 socket 模式”

很多人会说“LT socket”和“ET socket”，仿佛这是两类不同对象。更准确的理解是：**socket 还是那个 socket，变的是 epoll 怎样报告它的 readiness。**

LT（level triggered）更像“只要条件还满足，我后续 wait 还会继续告诉你”；ET（edge triggered）更像“我只在状态从无到有变化那一刻提醒你一次，后面怎么清空这波 ready 由你自己负责”。

### 2. 为什么 LT 更容易写对

因为 LT 具有天然容错性。你这次只读了一半数据，下次 `epoll_wait()` 只要该 fd 仍可读，它还会继续把这个事件告诉你。也就是说，应用即使一次没把缓冲区清空，也不容易永久丢掉后续通知。

所以 LT 非常适合初学者和许多业务场景：它把“漏读一部分”的后果降到了最低。

### 3. 为什么 ET 必须和非阻塞、循环读/写到 `EAGAIN` 搭配

ET 最大的危险就在于：它只告诉你“状态变化发生了”，不保证后续仍然会重复提醒。如果你在回调里只读一点就返回，而缓冲区里其实还有数据，但状态没有再次发生“从无到有”的边沿，你可能就再也等不到新的提醒。

这就是为什么 ET 模式几乎总要配合：

- fd 设成非阻塞；
- 收到事件后循环 `read/recv` 或 `write/send`；
- 一直做到返回 `EAGAIN`，把当前 ready 状态彻底排空。

ET 真正不是“更快的 LT”，而是“把更多就绪消费纪律强制下放给应用”。

### 4. 为什么 ET 的收益不在“神奇减少系统调用”，而在“尽量减少重复就绪通知”

如果某个 fd 长时间保持可读，LT 会在后续 wait 中不断提示它仍然可读；ET 则尽量只在边沿来一次提醒，剩下交给应用自己把这波数据吃干净。收益来自减少重复通知和重复用户态事件分发，而不是改变 socket 自身的数据面。

所以 ET 值不值，取决于你是否愿意为更严格的 handler 纪律，换较少的重复事件风暴。

### 5. 本节最该记住的结论：LT/ET 的真正差异，不在速度宣传，而在“ready 事实如何重复呈现给应用”，以及“应用是否有纪律一次把这波 ready 吃到 EAGAIN 为止”

一句最短人话是：**LT 会反复提醒你门还开着，ET 只在门刚打开时按一次铃。**

## 六、Reactor：epoll 本身只是一台就绪事件聚合器；真正让高并发服务跑起来的，是用户态怎样围绕它组织事件循环、handler 分发和线程拓扑

### 1. 为什么拿到 ready events 还远远不够

epoll 只会告诉你：“这几个 fd 现在可读/可写/出错了。” 可高并发服务器真正要解决的是：接下来谁负责 accept、谁负责 read、谁负责 write、哪个 handler 只做轻活、哪个任务该扔给 worker、哪个连接状态还没完整建立。

这些都不是 epoll 自己管的，而是用户态架构必须在它之上继续组织的问题。

### 2. Reactor 真正提供的是什么抽象

Reactor 模式最核心的价值，是把“等待事件”和“事件到来后如何分发给业务处理逻辑”稳定组织成一台循环机器。epoll_wait 只是产生一批 ready events；Reactor 再根据事件类型、fd 绑定的 handler 和线程拓扑，决定接下来谁去 accept、谁去读、谁去写、谁去清理错误。

也就是说，**epoll 是内核事件源，Reactor 是用户态把事件变成业务动作的总调度台。**

### 3. 为什么 Reactor 线程里不能塞重业务

因为它不仅承担“等事件”这件事，还承担“尽快消化并分发本轮所有 ready fd”这件事。若某个 handler 在 Reactor 线程里执行很久，后面的 fd 虽然已经 ready，也得排着等，最终把 readiness 延迟和尾延迟一起放大。

这就是为什么很多成熟框架都把 Reactor 和 worker 分开：I/O 线程尽量短平快，只做网络收发和状态推进；重业务交给线程池或其他执行器。

### 4. 为什么主从 Reactor 拓扑经常出现

因为 accept 本身是一个特殊入口，它决定新连接怎样分发给后续 I/O 线程。把 accept 和每个连接的 read/write 混在同一个单线程 Reactor 中虽然简单，但在多核和大量连接场景里会受限。于是就有了主 Reactor 专管接入、从 Reactor 分担连接 I/O 的常见结构。

这不是 epoll 强制的，而是高并发用户态围绕 epoll 自然长出的架构演化。证据位上，这层最值得强调的不是某个单独内核函数，而是边界本身：`fs/eventpoll.c` 负责“谁 ready 了”，真正的 Reactor 线程拓扑、handler 分发、主从 Reactor 划分属于用户态框架层。这组边界本身，就是本节最关键的实现证据。

### 5. 本节最该记住的结论：epoll 只负责“谁 ready 了”，Reactor 才负责“ready 之后整个程序怎样继续有秩序地向前走”

一句最短人话是：**epoll 是事件雷达，Reactor 才是调度大厅。**

## 七、io_uring：它看起来像“下一代 epoll”，真正变化的不是把 ready list 做得更极致，而是把关注点从“谁可做”进一步推进成“这次操作已经完成”

### 1. 为什么 epoll 再高效，也仍然只是在告诉你“现在可以去做”

epoll 的核心语义始终是 readiness。你拿到 `EPOLLIN` 后，还得自己去 `read()`；拿到 `EPOLLOUT` 后，也只是说明当前有机会继续 `write()`。也就是说，用户态仍要在收到通知后再发起真正 I/O。

这在很多场景下已经非常好，但也不是所有场景的终点。自然有人会继续追问：**能不能连“发起那次 read/write”也提前交给内核，最后我只来收结果？**

### 2. io_uring 的真正分叉点：共享提交队列和完成队列

这就是 io_uring 与 epoll 的核心区别。它不只在意“哪些 fd ready 了”，而是允许用户把具体 I/O 操作先描述成 SQE 放进提交队列，内核去执行；完成后再把 CQE 写进完成队列。用户最终收割的是“这次操作做完了没有、结果是什么”，而不是“现在理论上可以开始做”。

所以 io_uring 更接近把 readiness 世界往 completion 世界再推一层。

### 3. 为什么它不是“epoll 的简单替代品”

因为它们面向的问题边界并不完全一样。epoll 擅长聚合大量 readiness 事件；io_uring 擅长把操作提交和完成回执组织进共享 ring。很多系统仍会同时使用或在不同路径组合两者，而不是二选一完全替换。

另外，“共享 ring”并不自动等于“零系统调用、零拷贝、万事俱优”。提交方式、固定 buffer、操作种类和协议路径都会影响实际收益。若要补这一节的证据位，最合适回到 `io_uring/*` 的提交队列/完成队列路径和官方设计语义去看：它们共同支撑“io_uring 回答的是 completion，而不是简单把 epoll 再做快一点”这句判断。

### 4. 本节最该记住的结论：io_uring 真正推进的，是把“你来问谁 ready 了”进一步变成“你先提交我要做什么，内核做完后给你结果”

一句最短人话是：**epoll 说“这活现在能干了”，io_uring 更像“这活我替你干完了，结果在这里”。**

## 八、把本篇收成一张图：epoll 的根本革命不是把扫描写快，而是把“监听关系持久化”和“就绪事件增量生产”这两件事同时做对，然后由 Reactor 把它们变成真正的用户态并发秩序

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：1 万个 fd 里只有 3 个就绪时，为什么不必每轮扫描全部 fd。答案首先不在某个更快的遍历算法，而在数据结构和生产时机的变化：epoll 先通过 `epoll_ctl` 把 interest list 长期保存在内核中，再通过 `ep_poll_callback` 在事件发生时把对应 epitem 增量挂进 ready list。于是 `epoll_wait` 不再是全局轮询器，而是 ready list 的消费者。

LT 和 ET 又在 ready 事件呈现方式上分叉：默认 LT 适合更容错的重复提醒，ET 则用更严格的“读/写到 `EAGAIN` 为止”纪律换更少重复通知。Reactor 模式把 epoll 提供的 ready events 组织成真正的事件循环和 handler 分发机器，使 I/O 线程、worker 和连接状态机得以协作。io_uring 则代表另一条语义推进：从 readiness 通知继续走向 completion 回执。

把这一切压成最短总图，就是：

```text
interest list：
  长期保存在内核中

ready list：
  由事件到来时的回调增量生产

epoll_wait：
  只消费当前 ready 集合

LT / ET：
  决定 ready 事实重复呈现还是只在边沿报告

Reactor：
  把 ready events 变成用户态事件循环与 handler 分发

io_uring：
  从“谁 ready”推进到“哪次操作已完成”
```

所以本篇最该记住的一句话是：**epoll 真正省掉的不是某次 wait 的常数，而是“每轮都重新登记并重扫整批 fd”这层浪费；Reactor 再把这种内核级增量事件模型接成用户态的并发秩序。**

## 九、几个最容易说错的地方

### epoll 的优势是不是因为红黑树查找变成了 O(1)？

不准确。红黑树更多解决注册管理；真正的性能关键是监听关系持久化和 ready list 的增量生产。

### `epoll_wait()` 是不是每次也会像 poll 一样重新扫所有 fd？

不是。它主要消费当前 ready list；事件发现工作在更多时候已经由回调在事件发生时提前做了。

### LT 和 ET 是不是两种完全不同的 socket？

不是。socket 还是那个 socket，变化的是 epoll 如何重复报告 readiness 事件。

### ET 一定比 LT 更快吗？

不一定。它减少重复通知，但把更严格的“读/写到 EAGAIN”为止的纪律压给了应用，写错就容易丢通知机会。

### Reactor 是不是 epoll 的内核实现名字？

不是。epoll 是内核多路复用机制，Reactor 是建立在它之上的用户态事件循环和 handler 分发模式。

### io_uring 是不是 epoll 的完全替代？

不是。它的核心语义更偏 completion，而不是 readiness，适用边界与组合方式都不同。

## 收束：看懂 epoll 与 Reactor 之后，你才会真正明白“高并发等待”最值钱的不是让线程会睡，而是让“谁有变化”这件事尽可能在变化发生时就被增量记账，并只把已准备好的对象交给应用

回到开头那个问题：为什么 1 万个 socket 中只有 3 个有数据时，不必每轮扫描全部 fd？现在答案已经完整闭环了。因为 epoll 不再把“哪些 fd 值得看”当成每轮都要重新提交和重查的临时问题，而是先把 interest list 作为内核长期状态保存，再让事件在数据到达时通过回调自己进入 ready list。于是 `epoll_wait()` 只是把这批 ready 对象交给用户态，而不是再次从 10000 个里捞 3 个。

也正因为如此，你会发现 epoll 真正重写的不是函数接口，而是等待组织方式。LT 和 ET 再往上控制 ready 事件怎样重复呈现，Reactor 把 ready 事件进一步组织成用户态调度秩序，io_uring 则继续把问题从“可做”推进到“已完成”。这些看似不同的机制，其实都在回答同一个问题：**高并发程序怎样把“等待”从一件线性扫描和盲目轮询的苦差，变成一件增量、就绪、可批量消费的流水线。**

这就是为什么说：**epoll 的真正革命，不是某个复杂度口号，而是“监听关系持久化 + ready 事件增量生产”这两个设计一起到位。** 一旦这个核心站住，后面再看百万连接、Reactor 线程拓扑和 io_uring，就不再是散技术点，而是一整条等待模型进化史。

## 十、误解清单、证据清单与边界清单

### 误解清单

- epoll 不等于“更快的 poll”这么简单；真正关键是监听关系持久化和 ready 事件增量生产。
- 红黑树不是 epoll 性能神话的全部；它更多解决注册管理，不代表所有操作都 O(1)。
- `epoll_wait()` 不等于每次重新扫全名单；它主要在消费当前 ready list。
- LT/ET 不是两种不同 socket；变化的是 readiness 事件怎样重复呈现给应用。
- Reactor 不是 epoll 的内核名字；它是建立在 epoll 之上的用户态事件循环与分发秩序。

### 证据清单

- 总台与档案卡：`fs/eventpoll.c` 中 `eventpoll`/`epitem`、interest list 管理路径，支撑“长期通讯录”这层结构。
- 增量就绪生产：`fs/eventpoll.c` 中 `ep_poll_callback` 与 ready list 挂接路径，支撑“ready 事件在发生时就被记账”的主线。
- 系统调用分工：`epoll_create1`/`epoll_ctl`/`epoll_wait` 对应的建总台、长期登记、现场领单语义，支撑“三组接口不是同级等待函数”的判断。
- LT/ET 行为边界：`fs/eventpoll.c` 中事件重复呈现、`EPOLLONESHOT`/`EPOLLEXCLUSIVE` 等语义，支撑“变化的是报告策略，不是 socket 本体”的判断。
- io_uring 分叉：`io_uring/*` 中提交队列/完成队列语义，支撑“从 readiness 继续推进到 completion”的区别。

### 边界清单

- 本文讨论的是 Linux epoll/Reactor/io_uring 的稳定心智模型；`fs/eventpoll.c`、`io_uring/*` 字段、锁顺序和优化选项会随内核版本变化。
- epoll 擅长组织 readiness，不自动替代用户态的 handler、状态机和线程拓扑设计；Reactor 仍需应用自己写对。
- LT/ET 选择是语义与工程纪律的取舍，不是简单的“谁更快”口号。
- io_uring 的收益依赖操作种类、buffer 策略和协议路径，不应被宣传成对 epoll 的无条件完全替代。
- 本文先讲等待组织；下一篇才真正回答“会等之后，为什么总账仍然先爆”。
