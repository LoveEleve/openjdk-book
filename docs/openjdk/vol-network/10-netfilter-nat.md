## 现在真正该问的，不再是“本机能撑多少连接”，而是“这些连接一旦穿过容器、网桥、转发和公网出口，谁在中途决定它们该被放行、丢弃、改目的地址、改源地址，还要记住这次改写以便回包回得来”

上一章我们已经把本机容量账本讲清楚了。你知道百万连接从来不只是 epoll 的问题，而是 socket、缓冲区、队列、fd、CPU、NIC 和应用对象管理这些总账的最小值。也就是说，哪怕一台主机上的 TCP 协议和 I/O 等待模型都已经解释清楚了，现实网络仍然可能在“这台主机不只是终点，还在帮别人转发、改地址和做多租户隔离”这一步再长出一整层复杂度。

这就把我们带到 Netfilter 和 NAT。很多人对它们的第一印象是：哦，iptables 规则表；或者：NAT 就是改一下 IP 和端口。

这两个理解都抓住了一点皮毛，但都低估了真正的系统性难点。因为一旦一台 Linux 主机既是本机应用终点、又是转发节点、又可能承载 Docker/Kubernetes 网桥、又要处理公网/内网的地址改写，它面对的就不只是“这一包要不要放”，还要回答：

- 这包应该在协议栈的哪一层位置被检查或改写？
- 先路由再改，还是先改再路由？
- 只改这一个包够不够，还是必须给整条双向连接记一笔状态账？
- 外网回包进来时，系统怎么知道该把它翻回原始内网端点？
- 两个 NAT 后面的端点想直连时，为什么有时 STUN 能帮上忙，有时却不得不靠 TURN 中继？

所以本篇最重要的顿悟是：**Netfilter 的核心不是一组规则，NAT 的核心也不是改一下包头，而是“在正确的 hook 上做决策，并让 conntrack 为同一条双向流长期保留状态语义”。**

先把总图记住：

```text
Netfilter：
  包在协议栈里经过若干关键 hook
  各模块按表/链/优先级在这些位置做决策

iptables：
  用户态只是把 match + target 规则装进这些 hook 世界

conntrack：
  为一条双向流建立状态账本
  让后续包不必每次重新做“这条 NAT 映射是谁”这种推理

NAT：
  SNAT 改源地址/端口
  DNAT 改目的地址/端口
  回包之所以能回来, 靠的是连接跟踪里保存的双向映射关系

NAT 穿透：
  STUN 帮你看见自己在外网眼里的映射
  TURN 在直连失败时中继
  ICE 负责把各种候选路径排出来逐一试通
```

这一篇最重要的一句话是：**NAT 真正改变的不是“某一个包的地址”，而是“整条双向流在系统眼里的身份与回程路径”；如果没有 conntrack 这本状态账，它很快就会在回包阶段失忆。**

## 一、如果所有包都只在一个统一位置被一组规则处理，路由、地址改写和本机/转发语义很快就会彼此打架

### 1. 最朴素的错误世界：无论包从哪里来、要到哪里去，一律在某个统一入口按顺序套规则

从使用者直觉看，这似乎很方便：所有包都来一张大规则表，按顺序判断 ACCEPT、DROP、DNAT、SNAT、MARK……统一治理，多直观。

问题在于，不同来源和去向的包其实处在协议栈不同阶段：

- 入站包在路由前你甚至还不知道它最终要不要本机接收；
- 本机主动发出的包根本不会经过入站路径；
- DNAT 若改的是目的地址，通常要在最终路由决定前做；
- SNAT 常常又得等出口基本选定后再做才有意义。

如果你把这些场景都强压到一个“统一检查点”，很快就会发现：有些规则太早了、路由还没决定；有些规则太晚了，路由已经按错误目的地下了结论。本机路径和转发路径也会互相污染。

所以包处理绝不是“一张大表在一个位置执行”能说清的。

### 2. 第二个失败世界：那就先全部路由完，再让 NAT/过滤统一处理

这比第一种想法更像样一点，因为至少你承认路由很重要。但它仍然会在 DNAT 场景里出问题。举个最经典的例子：外部客户端访问一个公网 IP:port，这包进来后如果最终应该被 DNAT 改写到内网服务地址，那么最终路由必须依据改写后的目标地址做决定，而不是先按改写前的地址去路由。

所以“先全部路由，再统一做 NAT”同样走不通。路由和地址改写是互相牵制的，它们的执行点必须被精确切开。

### 3. Linux 的答案：把包经过协议栈的关键位置切成多个 hook，让不同动作在正确时机介入

这就是 Netfilter 最值得先记住的根设计。它并不强求所有包走同一决策点，而是把协议栈拆成几个非常关键的位置：路由前、本机入站、转发、本机出站、路由后。不同类型的规则和模块可以按这些钩子与优先级插入。

于是你终于可以让“改目的地址”发生在它应该影响路由之前，让“改源地址”发生在出口阶段，让“本机收包”和“转发包”走不同决策链。包的命运不再是一锅端，而是按流向和阶段分层裁决。若要把这一节补成更硬的源码正文，第一组证据位应落在 `net/netfilter/*` 中围绕 hook 注册、表/链挂接与优先级调度的路径上：它们共同支撑“PREROUTING 不是术语表上的名字，而是一个真实存在、可在路由前插入动作的时间点”这句判断。

### 4. 为什么说五个 hook 真正提供的是“包命运的时间轴”

很多教程背五个 hook 名字时像在背术语表。更有用的理解是：它们其实给了你一条时间轴。你以后读任何防火墙、NAT、Docker、Kubernetes Service 或透明代理规则时，都要先问一句：**这个动作应该发生在包命运的哪一个时刻？**

一旦你用时间轴思维来看，DNAT 在 PREROUTING、SNAT 常在 POSTROUTING、INPUT/FORWARD/OUTPUT 这些分支的存在都会变得顺理成章。

### 5. 本节最该记住的结论：Netfilter 的第一性价值不是“能写规则”，而是把包处理拆成了若干时序正确的介入点

一句最短人话是：**先切对时间轴，规则才有意义。**

## 二、表、链与规则：iptables 真正做的不是修改内核逻辑，而是把“什么条件匹配、匹配后做什么”装配到正确 hook 的正确优先级上

### 1. 为什么用户态 `iptables -A ...` 不是在“编程 Linux 网络栈”

很多人第一次接触 iptables，会觉得自己好像在直接操作内核网络代码。更准确的理解是：用户态只是在往 Netfilter 已经提供的框架里灌规则对象。内核网络栈的主流程没有被你重写，你只是给它的若干挂点安装了一批 match/target 组合。

这就像你不是在改机场安检系统本身，而是在现有安检闸口加了一套“什么旅客、什么条件、放行还是拦下”的细则。

### 2. 为什么表必须分工，而不能把所有 target 混在一起

`raw`、`mangle`、`nat`、`filter` 这些名字经常被当成“几张不同目的的规则表”。真正关键的是：不同 target 和副作用需要出现在不同阶段。

- `raw` 可能在连接跟踪之前就决定某包是否完全绕过状态机；
- `mangle` 更像在改标记或某些包属性，为后续策略路由/分类做铺垫；
- `nat` 必须出现在地址改写真正有意义的时机；
- `filter` 才是最常见的放行/丢弃裁决区。

所以“分表”不是用户体验设计，而是为了让不同副作用在协议栈时间轴上不互相踩脚。

### 3. 为什么不能把所有流量都概括成一条固定“raw→mangle→nat→filter”流水线

这是一个特别容易被简化错的地方。不同 hook 会遇到不同的表和优先级，不是每个包在任何场景下都必然把所有表按同一顺序走一遍。真正的执行次序得结合：

- 包现在处在哪个 hook；
- 哪些表在这个 hook 上注册了规则；
- 这些规则的优先级与副作用是什么。

所以一旦脱离具体 hook 谈表顺序，很容易说得太粗，最后排障或设计规则时就会踩坑。

### 4. 本节最该记住的结论：iptables 的本质不是“一张全局规则表”，而是“把 match/target 模块挂到不同 hook 和优先级上，让它们在正确时刻生效”

一句最短人话是：**规则不是写在哪都行，得先站对闸口。**

## 三、conntrack：没有状态账本，NAT 只能改出去的这一包，却不知道回来的那一包该还给谁

### 1. 最容易被低估的事实：NAT 不是单向改头，而是双向连接语义的持续翻译

假设一个内网客户端 `10.0.0.2:40000` 访问外网服务器，出口主机把它 SNAT 成 `1.2.3.4:50000`。出去这一包当然能改，可一旦服务器回包回来，系统又怎么知道 `1.2.3.4:50000` 其实该翻译回 `10.0.0.2:40000`？

如果你只是“看见包就把地址改一下”，那回程时立刻失忆。因为回包的五元组已经不是原样，它站在当前主机视角只看见公网地址和端口，根本不知道它属于哪一条过去做过改写的连接。

这说明 NAT 绝不是“改本包字段”这么简单，它必须是**围绕一条双向流长期记账**的动作。

### 2. conntrack 真正记的不是“某包做过什么”，而是“这条流的原始方向与应答方向 tuple 关系”

这就是连接跟踪最核心的价值。它不是给每个包贴孤立标签，而是为一个流建立一份状态对象，把原始方向和回复方向的 tuple 关系保存下来。这样后续包不必重新猜 NAT 映射，系统只要按当前包去命中 conntrack，就知道该把它归到哪条已有流上，并沿着已记录的映射关系处理。源码证据上，最值得补的落点应放在 `net/netfilter/nf_conntrack*.c` 一组路径：它们共同体现了“首包建状态、后续包按已有状态命中”这条事实，而不是每个包都重新独立推理一遍 NAT 关系。

于是你获得的不是一次性地址改写，而是一种持续可逆的会话翻译。

### 3. 为什么只在首包上做 NAT 决策是合理的

一条新流第一次出现时，系统必须决定这条连接的 NAT 映射：源地址怎么改、目的地址怎么改、端口是否要重新选、冲突怎么避免。这一步只要成功落到账本，后面的包就都能复用这份状态，不必每次重新选地址和端口。

这就是为什么 NAT 经常被描述成“在新连接首包上决定映射，后续包按已有 conntrack 状态走”。不是因为后续包不再改头，而是因为**改写策略已经不是逐包临时算，而是逐流复用状态。**

### 4. 为什么 conntrack 表满了会变成“新连接进不来”的容量问题

上一章讲过百万连接本质是资源会计学。到了 NAT 世界，conntrack 表就是额外的一本大账。只要每条被跟踪的流都占一项状态对象，这张表迟早会受到总量和老化速度限制。表满时，后果不是“旧连接随机坏掉”这么简单，而是很多新流根本没有地方建状态，连 NAT 决策和后续放行都无从谈起。

所以 Netfilter/NAT 扩展问题从来不只是规则多不多，也常常是状态账本够不够。

### 5. 本节最该记住的结论：conntrack 把 NAT 从“改一个包头”提升成了“给一条双向流建立持续可逆的地址翻译账本”

一句最短人话是：**没有 conntrack，NAT 只会发出去，不会认回来。**

## 四、SNAT、DNAT 与 NAPT：真正决定它们差别的，不是名字，而是“改谁的地址/端口”以及“这件事必须发生在路由前还是路由后”

### 1. 为什么 DNAT 要比 SNAT 更早影响包命运

DNAT 改的是目的地址和/或端口。一个外部客户端打到公网 VIP，如果最终该去内网服务，那么路由必须基于“改完之后的目标”去选下一跳。若你等路由都做完了再改目的地址，包可能已经被错误地当成本机流量或错误出口处理。

所以 DNAT 典型地要求在路由决定前就介入，才能让后续本机/转发选择真正围绕新目标展开。

### 2. 为什么 SNAT 往往更适合在出口阶段

SNAT 改的是源地址和/或端口，它通常服务于“内网多个主机共享一个公网出口地址”这类场景。此时系统往往已经知道包要从哪个出口发出，再把源地址改成该出口应呈现的公网身份才更自然。

如果太早做 SNAT，可能会让后续某些策略和路由判断提前失去原始源语义。于是它常出现在更靠后、接近实际离开本机的时机。

### 3. 为什么说 NAPT/PAT 才是大多数家庭/云主机 NAT 的常态

单纯改地址不够时，端口也得一起参与。多个内网主机同时出网，若都共享一个公网地址，就必须靠不同公网端口把它们区分开。这样同样是 `1.2.3.4`，外界仍能依靠端口知道回包该落回哪条 conntrack 映射。

也就是说，现代 NAT 更多不是“地址一对一替身”，而是“地址 + 端口联合重写”这套更细粒度的会话映射机制。

### 4. 为什么 NAT 会让端到端语义开始变别扭

一旦中途主机在改 tuple，端点看到的自己和对方，就不再总等于网络上真正流经路径的地址。入站连接要考虑 DNAT 映射、端口暴露、filter 放行、回程路由；出站连接又要看 SNAT 端口池和 conntrack 状态。这些都在告诉你：**NAT 用的是“中间人重写身份”的办法在换地址稀缺与拓扑自由，但端到端简单性会跟着流失。**

这也是为什么 NAT 穿透会成为独立的大问题，而不是“既然都能改地址，那直连总能想办法吧”。

### 5. 本节最该记住的结论：SNAT、DNAT、NAPT 的差异不在名词，而在“改哪个 tuple 字段”“影响哪一段路由/转发决策”以及“后续回程如何靠 conntrack 找回原始端点”

一句最短人话是：**DNAT 改你要去找谁，SNAT 改别人看到你是谁，NAPT 让很多人共用一个外部身份还不至于串号。**

## 五、STUN / TURN / ICE：它们存在不是因为 NAT “偶尔麻烦”，而是因为 NAT 从设计上就让“陌生入站流量怎么找到内侧主机”这件事变得天然不确定

### 1. 为什么仅靠交换私网 IP 没法让两个 NAT 后端点直连

两个主机若都躲在各自家庭路由器后面，彼此交换 `192.168.x.x` 这种地址并没有意义。那些地址在对方网络中根本不可路由。即便它们都知道自己的“外网映射地址”，也不代表对方发来的陌生入站包就会被 NAT 放进来。

这就是 NAT 穿透最残酷的现实：**你看到自己在外界眼里的样子，不等于外界现在就能顺利打进来。**

### 2. STUN 为什么只够你“看见映射”，不保证你“能被打通”

STUN 的价值是让客户端询问一个公共服务器：“你看到我从外面长什么样？” 于是端点至少知道了自己当前映射出来的公网 IP:port 候选。

这很有用，因为没有这一步，你连自己在外界的候选身份都不知道。可它只解决了“自我认知”，没解决“对端陌生流量一定能打进来”。一旦 NAT 策略更严格，比如对称 NAT、端口限制或防火墙策略，这个候选仍可能只是一个别人看得见却摸不着的影子。

### 3. 为什么 ICE 不直接替你选一条路，而是先收集很多候选再逐一试通

因为真正能通的路径依赖双方 NAT 类型、网络策略和当前映射。没有哪条单一公式能一眼看出“这俩端点一定该走 host candidate、srflx 还是 relay”。所以 ICE 的核心策略是：**先把所有可行候选列出来，再对候选 pair 做连通性检查，选最优可用路径。**

这说明 NAT 穿透不是一次 deterministic 计算，而是一场“候选收集 + 试通筛选”的协商过程。

### 4. TURN 为什么是“最贵但最稳”的兜底

一旦直连候选都失败，唯一稳定答案就是让双方都先把流量送到一个中继服务器，由它转发。这就是 TURN 的位置。它的代价非常明显：服务器带宽、额外 RTT、中继成本都上升。但它的好处也同样直接：**不再依赖双方 NAT 愿不愿意为对方打洞。**

所以 TURN 不是“退化的 STUN”，而是完全不同的一层兜底思路：放弃端到端直连幻想，换中继确定性。

### 5. 本节最该记住的结论：STUN 负责让你看见自己映射成什么，ICE 负责试哪条候选能通，TURN 负责在直连失败时彻底放弃穿透改走中继

一句最短人话是：**STUN 是照镜子，ICE 是排赛道，TURN 是实在跑不通就改坐摆渡车。**

## 六、把本篇收成一张图：Netfilter 真正把“包经过一台 Linux 主机”重写成了一条“分阶段决策 + 状态账本 + 地址翻译”的流水线，NAT 只是其中最显眼但绝不是最孤立的一环

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：访问 Docker 端口或内网服务时，包为什么会被放行、转发、改写，还能让回包回到正确客户端。答案首先不是“某张表改一下 IP”，而是包在协议栈里本来就要经过若干关键闸口：PREROUTING、INPUT、FORWARD、OUTPUT、POSTROUTING。不同规则和 target 只有站对时机，才不会和路由、本机交付或转发决策打架。

iptables 只是把 match/target 规则装进这套 hook 世界，而真正让 NAT 持续成立的，是 conntrack：它把首包上选出来的地址/端口映射记成一笔双向状态账，让后续包和回包都沿着同一翻译关系走。于是 DNAT、SNAT、NAPT 才不是一次性改头，而是整条双向流身份被重写。

再往上，NAT 穿透又把这个故事延伸到公网端到端世界：一旦中途设备愿意改 tuple，直连语义就不再天然成立。STUN 负责看见映射，ICE 负责组合候选并试通，TURN 在直连失败时兜底中继。这说明 NAT 的真正复杂性，不在规则本身，而在它把“地址是谁、谁能主动找谁”这件事变成了一套状态机和博弈过程。这里最该补的边界提醒是：STUN 只能告诉端点“外界看见我的映射是什么”，它并不承诺任意陌生对端都能顺着这个映射打进来；真正能否穿透，还取决于 NAT 类型、映射保持策略、过滤策略和双端同时试通时机。也正因为如此，讲 NAT 穿透时必须把 STUN/TURN/ICE 分成“看映射、排候选、兜底中继”三层，而不能把它们混成一套万能直连法术。

把这一切压成最短总图，就是：

```text
hook 世界：
  包命运在不同阶段被不同模块决定

规则世界：
  iptables 把 match/target 装进对应 hook

状态世界：
  conntrack 把首包决策扩展成整条双向流的长期账本

改写世界：
  DNAT / SNAT / NAPT 重写地址与端口身份

穿透世界：
  STUN 看映射
  ICE 试候选
  TURN 做中继兜底
```

所以本篇最该记住的一句话是：**Netfilter 的本质不是“写几条规则”，而是“在正确的时序位置对包做决策，再用 conntrack 把这次决策变成整条连接后续都能沿用的状态现实”；NAT 的复杂性，正在于它把一个原本应该端到端直接成立的地址世界，改造成了中间人长期翻译的世界。**

## 七、几个最容易说错的地方

### Netfilter 是不是就等于 iptables？

不是。Netfilter 是内核里的 hook/状态/处理框架，iptables 只是用户态把规则装进这套框架的一种接口和工具。

### NAT 是不是只改一个包头字段那么简单？

不对。它真正依赖的是 conntrack 为整条双向流保存映射关系，否则回包阶段很快就会失忆。

### PREROUTING、POSTROUTING 只是规则分组习惯名吗？

不是。它们对应包命运时间轴上的不同位置，DNAT/SNAT 能否正确生效高度依赖时序是否站对。

### 只要 STUN 拿到了公网地址，P2P 就一定能直连？

不一定。STUN 只解决“看见映射”，不保证 NAT 会接受任意陌生入站流量。

### TURN 是不是一种“低级的 STUN”？

不是。TURN 不是在帮你发现映射，而是在直连失败时直接承担中继路径，语义和成本都不同。

### conntrack 表满是不是只是某条规则太多？

不是。它往往意味着状态账本资源本身耗尽，会影响新连接建立和 NAT/防火墙决策，不只是“规则执行变慢”。

## 收束：看懂 Netfilter 与 NAT 之后，你才会真正明白“一个包经过 Linux 主机”从来不只是转发，而是一场带状态账本的多阶段审判与身份改写

回到开头那个问题：数据包经过 Linux 主机时，谁决定放行、丢弃、改目的地址，谁又记住这次改写让回包能正确返回？现在答案已经完整闭环了。包会沿着 Netfilter 的几个关键 hook 穿过不同决策点，iptables 等规则接口只是把 match/target 装进这些闸口；真正让 NAT 能长期成立的，是 conntrack 在首包上建立的双向状态账。没有这本账，DNAT/SNAT 只会是一次性的头部魔术，第二个方向的包一来系统就会失忆。

也正因为如此，你会发现容器网络、端口映射、Service 转发和 NAT 穿透之所以容易让人头大，不是因为规则表太长，而是因为它们把“谁是谁、该往哪去、回头怎么回来”这三件原本更直接的事，全都重写成了依赖中间状态机的路径。理解了 hook 时序、conntrack 账本和 NAT 的双向身份翻译之后，后面的 TLS、容器网络和多租户隔离问题，才终于不再像一堆散配置，而会变成同一条协议时间轴上的不同干预点。

这就是为什么说：**NAT 不是简单的地址魔法，而是一种有代价的中间人秩序。** 规则写错会马上出错，状态账本撑不住会整体失忆，穿透失败则说明中间人不肯放你们直接见面。

## 八、误解清单、证据清单与边界清单

### 误解清单

- Netfilter 不等于 iptables；前者是内核里的 hook/状态处理框架，后者只是其一类用户态装配接口。
- NAT 不是“改一下包头字段”这么简单；真正让它持续成立的是 conntrack 为双向流保存的映射账本。
- PREROUTING/POSTROUTING 不是规则分组习惯名；它们对应包命运时间轴上的真实时刻，时序站错会直接改错路由语义。
- conntrack 表满不只是“规则有点慢”；它意味着新流连状态对象都建不起来，会直接影响 NAT 与放行决策。
- STUN 不等于直连保证；它只解决“看见映射”，不解决“对端一定打得进来”。

### 证据清单

- hook 与时序：`net/netfilter/*` 中围绕 PREROUTING/INPUT/FORWARD/OUTPUT/POSTROUTING 注册与优先级调度的路径，支撑“包处理先切时间轴再谈规则”的判断。
- conntrack 主线：`net/netfilter/nf_conntrack*.c` 一组路径，支撑“首包建状态、后续包按状态命中”的双向流账本语义。
- NAT 改写：`net/netfilter/*nat*.c` 中 DNAT/SNAT/NAPT 相关路径，支撑“改写不是逐包魔术，而是基于连接状态复用映射”的实现逻辑。
- 表/链/规则装配：iptables/nft 用户态与 `net/netfilter/*` 的装配关系，支撑“用户态不是在重写网络栈，而是在既有 hook 世界里灌规则对象”。
- STUN/TURN/ICE 边界：协议实现与 RFC 路线共同支撑“STUN 看映射、ICE 排候选、TURN 做中继兜底”的三层分工。

### 边界清单

- 本文讲的是 Linux Netfilter/conntrack/NAT 的稳定心智模型；具体 nftables 与 iptables 用户态差异、helper、超时、hash table 与模块参数会随内核和发行版变化。
- NAT 的正确性不只取决于规则，还取决于路由、反向路径、conntrack 容量、老化策略和中间网络拓扑。
- `nf_conntrack` 表满是系统级容量问题，不应简化成“把规则写少一点”这种单变量答案。
- STUN/TURN/ICE 讲的是穿透策略边界，不是对所有 NAT/防火墙组合都能成功直连的保证书。
- 本文不覆盖 Kubernetes kube-proxy、eBPF service mesh 或更复杂多租户策略的全部实现细节；这里只建立基础的 hook + 状态账本 + 地址改写主线。
