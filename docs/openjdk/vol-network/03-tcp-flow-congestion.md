## 现在真正该问的，不再是“连接怎样成立”，而是“连接建立之后，发送方为什么不能把 1GB 一股脑全塞进网络，而必须在对端缓冲和路径拥塞这两道门之间小心试探”

上一章我们已经把 TCP 的状态机和握手挥手讲清楚了。你知道连接并不是“发几个包就行”，而是双方通过 Seq/Ack、Flags 和状态迁移逐步对齐的一份动态契约。SYN、SYN+ACK、ACK 确认的是初始序列空间和连接存在性；FIN、TIME_WAIT 和 RST 则在收尾和异常路径里继续维持协议卫生。

可连接一旦进入 `ESTABLISHED`，真正的大戏才刚开始。此时双方已经建立好了字节流关系，新的问题不再是“能不能连”，而是：**到底一次还能发多少、为什么不能无限快、为什么一个很大的应用消息会被拆成多个 segment、为什么有时网络空得很但发送方仍会慢下来、又为什么有时对端读得飞快但连接依然被拥塞控制卡住。**

这就是本篇真正要回答的核心困惑。

很多人初学 TCP 时，会以为“窗口”就是一个统一的速度旋钮。其实不是。真正决定当前还能不能发的，至少有三件事在同时约束：

- 接收方还吃得下多少，也就是 `rwnd`；
- 路径当前大致还能承受多少在途数据，也就是 `cwnd`；
- 单个段最多能装多少应用数据，也就是由 MSS/MTU 决定的分段粒度。

所以本篇最重要的顿悟是：**TCP 传输能力不是一个数字决定的，而是“接收能力 × 网络承载能力 × 分段粒度”共同作用的结果，其中真正可发的 inflight 数据上界首先是 `min(rwnd, cwnd)`。**

先把总图记住：

```text
接收方限制：
  rwnd = 对端还能接多少

网络路径限制：
  cwnd = 发送方估计路径还能承受多少 inflight 数据

分段粒度限制：
  MSS = 一个 TCP segment 能装多少应用数据
  MTU = 一跳链路允许的最大 IP 包大小

算法世界：
  Reno = 丢包驱动的基线增长/回退
  CUBIC = 面向高 BDP 路径的时间曲线增长
  BBR = 用带宽和最小 RTT 建模，而不是等丢包才承认拥塞
```

这一篇最重要的一句话是：**TCP 连接建立之后，发送方到底还能不能继续发，不是由“我手里还有数据”决定的，而是由接收方窗口、拥塞窗口和分段边界共同把门。**

## 一、如果没有接收窗口，发送方只按自己节奏灌数据，慢接收端会先被自己的缓冲区拖死

### 1. 最朴素的失败世界：只要网络还能走，发送方就一直发，接收方自己慢慢处理

从发送端视角看，这似乎很合理：我有数据，线路也通，那就尽量多发；对端应用处理得慢，是它自己的事。可 TCP 要解决的是端到端字节流，而不是“我只管扔出去”。

如果发送方完全看不见接收方缓冲区状态，慢接收端很快就会被灌爆。它应用层也许读得慢，socket 接收缓冲区越积越多，最终不是丢数据，就是把内存压力和流量控制变成无序灾难。网络明明没堵，接收端自己却先崩。

这说明：**连接里第一层速度边界并不是网络，而是对端到底还接不接得下。**

### 2. 为什么“我给你发快点，你自己慢慢缓存”不是一个普适答案

你可能会想，那就让接收端多给点缓冲区嘛。问题是缓冲区不是无限的，应用消费速度也不是总能稳定追上。更关键的是，TCP 不只是做“尽量多缓存”，它要做的是可持续的字节流交付。如果接收方被迫长期靠暴力缓存抗住上游，内存与延迟都会恶化。

所以 TCP 不会把“接收方顶不住”这个现实藏起来，而是明确要求接收方把自己当前可接受的额度通告给发送方。这就是 `rwnd` 的意义。

### 3. `rwnd` 本质上是什么

接收窗口可以理解成接收方发给发送方的一张信用额度单：**我当前接收缓冲区还剩多少空间，你在未确认数据总量上别超过这个额度。**

于是发送方不能只看自己还有多少待发送字节，而必须看：当前已发未确认的 inflight 数据加上即将发送的数据，会不会超过对端通告的接收窗口。只有在 ACK 到来、窗口右移或接收方重新扩大窗口时，发送方才有资格继续多发。

这让 TCP 连接在数据传输阶段保持了一种非常明确的“信用发货”关系。发送方不是随便塞货，而是在接收方信用额度之内推进。

### 4. 为什么 ACK 到来不仅是“你前面的收到了”，还是“发送窗口可以往前滑了”

ACK 的价值不只是确认过去。它还在重塑未来。当前面若干字节被确认之后，发送方手里“已发未确认”的那一段窗口左边缘会向前收缩，于是窗口右边就又空出新额度。这就是滑动窗口的真正含义：不是一个固定框，而是随着确认持续右移的可发送区间。

所以 ACK 在 TCP 里同时承担两种角色：

- 告诉你过去哪部分已经安全抵达；
- 允许你未来再释放多少新数据。

若要把这一节补成更硬的源码正文，最关键的证据位应回到发送窗口推进、ACK 处理与 `tcp_info` / `ss -i` 可观测字段上：它们共同支撑“ACK 不只是确认过去，还在重塑未来窗口”这句判断。

### 5. `rwnd=0` 为什么不是连接坏了，而是“对端暂时别再送货”

当接收窗口降为 0，很多初学者会误以为连接出了错。更准确的理解是：接收方在明确告诉你，“我的收货区满了，现在不要正常发货了”。连接本身仍可能健康，只是数据平面进入临时暂停状态。

这时发送方通常不会永远沉默，而会通过零窗口探测包定期确认对端窗口是否恢复。这样一来，“停发”也不是死状态，而是一种等待对端重新给出信用额度的控制模式。

### 6. 本节最该记住的结论：`rwnd` 不是性能优化附加项，而是 TCP 为了不把慢接收端灌爆而内建的信用额度系统

一句最短人话是：**`rwnd` 解决的不是网络堵不堵，而是对端吃不吃得下。**

## 二、MSS 与 MTU：TCP 分段和 IP 分片不是一回事，真正健康的网络更希望端点一开始就把段切到合适大小，而不是把过大的 IP 包扔给中间网络去碎尸

### 1. 为什么应用一次写 1501 字节，不等于线上只会看到一个“1501 字节包”

应用看到的是连续字节流，它根本不关心 segment 边界。但传输层不能这么想。链路有 MTU 上限，TCP 自己头部和 IP 头部也占空间，所以应用写 1501 字节时，很可能会被拆成两个 TCP segment，而不是在链路上出现一个“1501B 纯数据包”。

这说明“应用消息大小”和“网络上传输的段大小”本来就是两回事。把两者混为一谈，是理解粘包、拆包和 MTU 问题的常见误区。

### 2. 为什么 MSS 必须存在

如果 TCP 不主动分段，而总把应用字节尽量塞进单个包，那么一旦生成的 IP 包大于链路可承受 MTU，就会依赖网络层分片。这个策略既不稳，也让发送端对真正的包边界失去控制。

MSS 的作用，就是在 TCP 层提前划出“每个段最多可装多少应用数据”。这样端点自己就能把字节流切成适合当前路径的 segment，而不是把一个过大的整体包甩给 IP 层和中间网络去拆。

### 3. 为什么“尽量避免 IP 分片”几乎是工程共识

IP 分片最大的问题，不在于它一定不能工作，而在于它把一个上层报文切成多个彼此依赖的片段，任何一片丢失都可能让整个上层报文重组失败。中间设备、NAT、隧道和防火墙对分片的处理也可能更复杂、更不一致。

所以工程上更好的思路是：**尽量在发送端就把 TCP segment 切到合适大小，让 IP 包天然适配路径 MTU。** 这比“先造个大包，再期待网络帮你拆”健壮得多。

### 4. 为什么 MSS 和 MTU 不能混着说

MTU 是某一跳链路层允许的最大 IP 包大小；MSS 是单个 TCP segment 能装的应用负载上限。前者是下层基础设施限制，后者是上传输层基于这个限制和头部开销推导出来的“安全装货量”。

你可以把它们理解成货车总重上限和单个货箱净装载量：不是一个概念，但强相关。

### 5. 为什么 PMTUD 又说明这件事不是“固定 1460 字节永远正确”

很多教程里都会举以太网 MTU 1500 → MSS 1460 的经典例子，这对入门很有帮助，但也很容易让人误以为 1460 是永恒真理。实际上，路径上隧道、额外头部、不同链路 MTU 都会影响可用大小。PMTUD 的意义就是让端点逐步发现路径真实可承受的 MTU 边界，从而选择更合适的 MSS。

所以 MSS 不是定值，而是发送端根据路径环境和协商结果得出的工作上限。证据位上，这层最值得回到 `tcp_info` / `ss -i` 可观测口径与路径 MTU/分段相关实现去看：它们共同支撑“MTU 是链路上限，MSS 是端点基于这个上限推导出的安全装货量”这句判断。

### 6. 本节最该记住的结论：MSS 让 TCP 自己决定一段装多少，MTU 则是链路对一个 IP 包的硬边界；健康网络更想靠前者避免后者触发分片

一句最短人话是：**应用写多大不重要，重要的是 TCP 最终切多大；端点自己把段切好，比让 IP 在半路拆包更可靠。**

## 三、`cwnd`：就算接收方吃得下、段大小也切对了，发送方仍不能无限发，因为网络路径本身也会被 inflight 数据压垮

### 1. 为什么“对端还能收，我就继续发”仍然不够

即便 `rwnd` 很大，对端应用和接收缓冲都很从容，发送方也不能简单推断“那我现在可以把路打满”。因为接收方愿意收，并不意味着中间路径有能力同时承载无限多还没被确认的数据。队列、链路速率、共享瓶颈和路由设备缓存都在告诉你：路径本身也是一种有限资源。

所以 TCP 还需要第二道窗口：不是接收端授予的，而是发送方自己对“网络当前大概还扛得住多少 inflight 数据”的估计。这就是 `cwnd`。

### 2. 为什么 `cwnd` 不是物理量，而是发送方手里的一个不断修正的估计

网络不会主动告诉你“我的容量是 123456 字节”。发送方只能通过 ACK、丢包、RTT 变化、交付速率等信号去猜。于是拥塞窗口从本质上说，不是测量得到的常量，而是一个不断试探、不断修正的控制变量。

这点非常关键，因为它决定了拥塞控制算法为什么看起来总像在“试探边界”：它不知道答案，只能边走边估。

### 3. 为什么真正可发数据上限是 `min(rwnd, cwnd)`

到这里三层约束第一次合流了。接收方可能只剩 32KB 窗口，而路径可以吃 1MB inflight；那发送方也只能发 32KB。反过来，接收方缓冲区很大，路径当前却被估计只能承受 64KB inflight，那也只能发 64KB。

所以 TCP 的速度上限从来不是看单一窗口，而是同时看“对端能吃多少”和“路径敢不敢送多少”。真正控制当前飞行数据量的，就是这两个窗口里更小的那个。

### 4. 为什么 ACK 又在这里同时承担“信用回收”和“路径探测反馈”双重职责

前面你已经看到 ACK 会释放接收窗口。现在它还要承担另一层含义：发送方会从 ACK 节奏里读取路径反馈，估算当前是否还能继续增大 `cwnd`。也就是说，同样一个 ACK，在流控语义里是“你可以再占我多少缓冲”，在拥塞控制语义里又是“这条路径刚才还能运转到这个 inflight 规模”。

这就是为什么 TCP 的反馈信号常常一举多得，也为什么状态机会显得格外精妙。

### 5. 本节最该记住的结论：`cwnd` 是发送方对网络还能承受多少 inflight 数据的估计，而真正可发上限一定要和 `rwnd` 再做一次取最小值

一句最短人话是：**`rwnd` 是对端说“我还能吃多少”，`cwnd` 是你自己猜“路上还能飞多少”，真正能发的是两者更小值。**

## 四、Reno 基线：拥塞控制最朴素但极有代表性的思想，就是先大胆试探，看到丢包或超时再收缩，永远靠反馈而不是先验去学路径边界

### 1. 为什么连接刚建立时 TCP 不会直接把 `cwnd` 开到很大

因为它没有先验。路径带宽多大、队列多深、共享流量有多少，这些发送方都不知道。若一开始就把 inflight 数据开得很大，很可能在最早几个 RTT 就把瓶颈队列顶满，引发剧烈丢包和排队。

于是 Reno 一类基线算法的出发点非常朴素：**先保守起步，得到正反馈再逐步放大。**

### 2. 为什么“慢启动”名字会误导人

慢启动听起来像一个增长很慢的阶段，但它真正常见的直觉反而是“相对直接打满链路，它算谨慎；可一旦开始收到 ACK，窗口其实会增长得很快”。这是因为每收到 ACK 就给窗口加一点，按 RTT 看往往会表现成近似指数扩张。

所以它的“慢”不是指数学速度慢，而是相对于“完全不知道边界却一上来就把油门踩到底”而言更谨慎。

### 3. `ssthresh` 为什么存在

只靠慢启动一直涨下去并不现实。随着窗口增大，你终究会越来越接近路径边界。`ssthresh` 的意义，就是给发送方一个阶段切换点：在较小窗口时允许更激进地探路，接近某个历史风险区后改成更温和的拥塞避免增长。

这说明 Reno 不只是“窗口大了就继续加”，而是在“探索期”和“保守期”之间切换策略。

### 4. 为什么 3 个 duplicate ACK 会被当成特殊信号

超时当然说明出事了，但它来得太晚。若接收方连续发来重复 ACK，往往意味着后续一些段已经到了，只是中间某段缺失导致累计确认卡住。这个时候发送方不必傻等整个 RTO 计时器爆炸，就已经得到足够证据：中间那段大概率丢了。

这正是快速重传的意义：利用 duplicate ACK 在超时之前先止损。它不是魔法判断，而是一种“下游还能回我 ACK，说明链路没完全死，只是某段掉了”的经验推断。

### 5. 为什么 Reno 的价值不在“它今天还最强”，而在“它把丢包驱动窗口调节这条主线讲得最清楚”

很多现代系统默认不再用最原始的 Reno，但 Reno 仍然是理解拥塞控制的最好基线。因为它把几个最重要的问题讲得极清楚：

- 不知道路径容量，所以得先试；
- 试得过猛会丢包，所以要回退；
- 回退不能总等超时，所以 duplicate ACK 也很关键；
- 窗口增长应分阶段，不是一根线到底。

### 6. 本节最该记住的结论：Reno 的核心不是某个具体参数，而是“靠 ACK 增长、靠丢包与超时缩减”的反馈控制哲学

一句最短人话是：**Reno 是“先探、再收、再探”的第一份清晰样板。**

## 五、CUBIC 与 BBR：现代拥塞控制真正分叉的，不是“谁更快”，而是“到底把什么信号当成路径容量的主要证据”

### 1. 为什么高带宽长 RTT 链路会逼着 Reno 的线性世界开始显得保守甚至迟钝

当路径带宽很高、RTT 很长时，按 RTT 一点点加窗口会让恢复显得很慢。历史峰值已经很高，你却还得小步线性往回试探，很容易让链路长时间利用不满。

这就是为什么后来的拥塞控制开始尝试新的增长模型：既然丢包仍是重要信号，那能不能让恢复过程更贴合大 BDP 链路现实，而不是只按“每 RTT 加一个 MSS”这么朴素地走。

### 2. CUBIC 真正改写的，是“窗口如何从丢包后的低点重新爬回历史峰值”这段曲线

CUBIC 记住上一次丢包前的窗口高点，然后用时间驱动的三次曲线围绕这个点恢复和再探测。它在接近历史峰值时放慢，在超过历史峰值后再继续向上伸。这样比纯线性恢复更适合大带宽、高延迟环境。

所以 CUBIC 的重点不是“完全不看丢包”，而是**仍承认丢包是重要信号，只是把丢包后的窗口恢复曲线设计得更适合现代高速路径。**

### 3. BBR 真正改写的，则是“为什么非要等丢包了我才知道路满了”

BBR 的出发点更激进。它认为丢包并不是唯一值得依赖的容量信号，甚至在 buffer 很深的路径里，等丢包才减速往往已经意味着队列排长、延迟变差。于是 BBR 转而更重视两个估计：瓶颈带宽和传播 RTT。

通过持续估算 delivery rate 和最小 RTT，它试图逼近一条更像 BDP 的发送模型：别等队列挤爆才说拥塞，而是看到吞吐不再涨、RTT 却在往上拖时，就承认路径已经接近饱和。

这相当于把“拥塞证据”从“包掉了没”部分改写成“我的路径模型现在怎么看”。

### 4. 为什么不能把 BBR 简化成“比 CUBIC 新，所以一定更好”

因为两者依赖的主要信号和公平性假设不同。CUBIC 对丢包敏感、路径兼容性广，在很多 Linux 场景里非常实用；BBR 在一些长肥管道和 bufferbloat 场景下很吸引人，但也可能和其他流、公平性、队列管理和实现版本产生新的博弈。

所以比较它们，不能只看年代或单场景吞吐，而得看网络环境、竞争流特征和你到底更想把哪类延迟/吞吐问题压下去。

### 5. 本节最该记住的结论：CUBIC 和 BBR 代表的是两种不同的核心信号哲学——前者仍围绕丢包后恢复曲线，后者更像带宽/RTT 模型驱动

一句最短人话是：**CUBIC 更像“撞到墙后怎样更聪明地重新加速”，BBR 更像“尽量别等撞墙，而是靠测路况提前估容量”。** 若要补这节的证据位，最合适回到 Linux 拥塞控制相关实现与 `ss -i` / `tcp_info` 可见字段去看：它们共同支撑“CUBIC 仍围绕丢包后恢复曲线，BBR 更偏向带宽/RTT 模型”这条信号哲学分叉。

## 六、把本篇收成一张图：TCP 传输阶段真正持续在解的题，不是“能不能发”，而是“还能安全再飞多少字节、多大的段，以及这些边界该由谁来收紧”

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：连接建立后，发送方为什么不能把 1GB 一股脑全塞进网络。答案首先不是“TCP 比较保守”这么简单，而是因为它同时受三组约束：接收方缓冲还能吃多少 (`rwnd`)、路径当前估计还能承受多少 inflight 数据 (`cwnd`)、单个 TCP segment 该按多大粒度切 (`MSS`/`MTU`)。

`rwnd` 是接收方给出的信用额度，防止慢接收端被灌爆；MSS/MTU 又把“应用写多少字节”和“网络上实际出现多少个 segment、每个有多大”这件事拆开，帮助端点主动规避 IP 分片；`cwnd` 则让发送方即使面对一个很能吃的接收端，也不敢无限制把路径压满。

在算法层面，Reno 给出了最经典的反馈控制哲学：先试探，再根据丢包或超时回退；CUBIC 改写了大窗口恢复曲线，BBR 则进一步试图把主要容量证据从“等丢包”转向“带宽/RTT 建模”。它们都在围绕同一个问题打转：**发送方怎样在没有先验答案的前提下，持续猜测还能安全飞多少数据。**

把这一切压成最短总图，就是：

```text
接收边界：
  rwnd 决定对端此刻还能收多少

路径边界：
  cwnd 决定发送方敢让多少数据同时在途

分段边界：
  MSS 决定一个 TCP 段装多少应用数据
  MTU 决定一跳 IP 包最多多大

控制哲学：
  Reno = ACK 增长，丢包/超时回退
  CUBIC = 丢包后按时间曲线恢复
  BBR = 按带宽/RTT 模型估计路径容量
```

所以本篇最该记住的一句话是：**TCP 连接建立后真正持续在做的，不是“把数据尽快发完”，而是让发送方不断在“对端还吃得下多少”“路上还飞得动多少”“一段到底装多大”这三层现实之间重新对齐自己下一步的发送节奏。**

## 七、几个最容易说错的地方

### 发送速度是不是只由拥塞窗口 `cwnd` 决定？

不是。真正的未确认在途数据上界首先是 `min(rwnd, cwnd)`，接收方窗口和网络拥塞窗口同时参与约束。

### `rwnd` 小是不是就说明网络拥塞了？

不一定。它更多说明接收方缓冲或应用消费速度跟不上，是接收端信用问题，不一定是路径拥塞问题。

### MSS 和 MTU 是不是一个东西？

不是。MTU 是链路可承载的最大 IP 包大小，MSS 是单个 TCP segment 能装的应用数据上限。

### IP 分片是不是和 TCP 分段差不多，只是发生层次不同？

不对。它们发生层次不同、代价模型也不同；工程上通常更希望靠 TCP 分段避免不得已的 IP 分片。

### 慢启动是不是增长很慢？

名字容易误导。它相对“直接打满链路”更谨慎，但窗口在 ACK 驱动下常会非常快地放大。

### BBR 是不是一定全面优于 CUBIC？

不是。它们依赖的主信号和公平性取舍不同，适用优势也受链路、队列和竞争流环境影响。

## 收束：看懂流控与拥塞控制之后，你才会真正明白“发送数据”并不是把字节推出去，而是持续维持一条关于能力边界的动态共识

回到开头那个问题：连接建立后，发送方为什么不能把 1GB 一股脑全塞进网络？现在答案已经完整闭环了。因为 TCP 不是简单把数据推出去，而是要持续维持一条动态共识：接收方此刻还能承受多少（`rwnd`）、路径当前大约还能飞多少（`cwnd`）、单个 segment 该切多大（`MSS`/`MTU`）。只有在这三层边界同时允许的范围内，发送方才有资格继续推进未确认字节流。

也正因为如此，你会发现传输阶段真正复杂的地方不在“收发包”本身，而在于反馈控制：ACK 不只是确认过去，还在释放未来窗口；丢包和超时不只是错误，还在重塑发送节奏；CUBIC 和 BBR 争论的也不是“谁更炫”，而是“到底把什么看成最可信的路径容量证据”。理解了这一点，后面所有重传、RTT 抖动、bufferbloat、吞吐瓶颈和线上调优问题，才终于有了共同语言。

这就是为什么说：**TCP 传输阶段的本质，不是发包，而是让“还能继续发多少”这件事始终跟着接收端、路径和分段现实一起收缩或扩张。**

## 八、误解清单、证据清单与边界清单

### 误解清单

- 发送速度不只由 `cwnd` 决定；真正的在途上界首先是 `min(rwnd, cwnd)`。
- `rwnd` 小不自动等于网络拥塞；它更多先说明接收端缓冲或应用消费速度顶不住。
- MSS 和 MTU 不是一个概念；一个是 TCP 装货量，一个是链路层对 IP 包的硬边界。
- IP 分片不等于 TCP 分段；工程上通常更希望靠端点分段避免被动分片。
- BBR 不等于一定全面优于 CUBIC；它们依赖的主信号、公平性和适用场景本来就不同。

### 证据清单

- 接收窗口：`rwnd` 与 ACK 相关可观测字段、`ss -i` / `tcp_info` 一类口径，支撑“对端还能吃多少”的信用额度语义。
- 拥塞窗口：`cwnd`、inflight、ACK 驱动增长与退避相关实现/可观测字段，支撑“发送方自己猜路上还能飞多少”的主线。
- 分段边界：MSS/MTU/PMTUD 相关实现与可见字段，支撑“链路上限”和“单段净装载量”的分工。
- ACK 双重角色：确认过去和释放未来窗口的相关路径与指标，支撑“ACK 同时在重塑未来发送额度”的判断。
- 算法分叉：Linux 拥塞控制实现与 `ss -i` / `tcp_info` 可见字段，支撑“CUBIC 围绕丢包恢复曲线，BBR 围绕带宽/RTT 建模”的哲学差异。

### 边界清单

- 本文讨论的是 TCP 传输阶段稳定心智模型；初始窗口、RTO、SACK、RACK/TLP、默认算法和实现细节会随内核版本变化。
- `rwnd`/`cwnd`/MSS 讲的是主边界，不等于所有线上体感都只由这三项单独决定；路径 RTT、应用行为和队列现实同样重要。
- CUBIC/BBR 的比较不是新旧之争，而是信号选择和环境适配差异，不能被简化成“谁更先进就永远更好”。
- MSS 常见示例值有助于入门，但路径 MTU 与隧道/额外头部会让真实边界变化。
- 本文先讲机制；下一篇生产排障才真正回答“这些边界在线上为什么会漏成会疼的症状”。
