## JDK 装在一个"箱子"里

你有没有想过：JDK 装完，那几千个类文件到底放在哪？

打开 `jdk/lib/`，你找不到 `java/lang/String.class`——它不在任何 `.class` 目录里，而在一个叫 **`lib/modules`** 的文件里。这个文件就是 JDK 的"箱子"：**整个 JDK 的运行时类库，按模块组织，压缩进一个文件**。JVM 启动时把它内存映射进来，按需读类——这就是域 41（ZIP & JIMAGE）的主角。

这一篇把箱子翻个底朝天：先看里面有什么（jimage），再自己组一个迷你箱子（jlink），最后画一张依赖图（jdeps）。

## 1. 箱子里面有什么：jimage

### 看目录

```
$ jimage list <jdk>/lib/modules
jimage: /opt/codev/TencentKona/lib/modules

Module: java.base
    META-INF/services/java.nio.file.spi.FileSystemProvider
    com/sun/crypto/provider/AESCipher$AES128_CBC_NoPadding.class
    ...
Module: java.compiler
    javax/tools/Tool.class
    ...
```

实测完整输出 70 个模块、27,100 条资源路径。`java.base` 一条线就 6,434 条——String、Object、集合框架全在这。

### 看箱子本身的结构

`jimage info` 打印镜像头：

```
 Major Version:  1
 Minor Version:  0
 Flags:          0
 Resource Count: 29345
 Table Length:   29345
 Offsets Size:   117380
 Redirects Size: 117380
 Locations Size: 605863
 Strings Size:   642825
 Index Size:     1483476
```

这里藏着一个有意思的坑：**info 说 Resource Count 29,345，list 却只列出 27,100 条**——哪个对？用第三个命令裁决：`jimage extract` 把整个箱子解包出来数文件：

```
$ jimage extract --dir /tmp/jimage-extract <jdk>/lib/modules
$ find /tmp/jimage-extract -type f | wc -l
27100
```

**27,100 个文件，和 list 完全一致**。所以 info 的 Resource Count（29,345）数的是**索引表条目**，不是可提取的资源——注意 `Table Length` 也是 29,345，`Offsets Size` 117,380 ÷ 4 也是 29,345，三处同数；而 list 和 extract 两边都证实真实资源是 27,100。这个"两个命令数字打架，第三个命令裁决"的过程，本身就是域 41 的教材：**镜像 = 哈希索引 + 压缩资源区，索引条目比资源多**。

### 镜像 ≠ JAR

解包出来的目录里，`java.base/java/lang/String.class` 躺在原地，和编译产物一模一样。但注意 jimage 和 JAR 是两种完全不同的东西：

- **JAR/ZIP**：打包格式，压缩的目录+文件，靠中央目录索引；`java -jar` 加载的是它。
- **jimage**：JVM 启动专用格式，整个文件**常驻内存映射**，按哈希表 O(1) 定位资源——JVM 运行期根本不扫目录，直接查表。

`jimage` 工具是观察这个内部格式的唯一直接窗口。写域 41 时，"镜像 ≠ JAR"是开场白，"哈希索引 + 空洞"是结构题。

## 2. 自己组一个最小 JDK：jlink

箱子能拆，也能**自己造一个小的**。`jlink` 按模块裁剪，组装出只含指定模块的运行时镜像：

```
$ jlink --add-modules java.base,java.logging \
        --strip-debug --no-man-pages --no-header-files \
        --output /tmp/jre-mini
$ du -shL /tmp/jre-mini /opt/codev/TencentKona
45M     /tmp/jre-mini
323M    /opt/codev/TencentKona
$ /tmp/jre-mini/bin/java -version
openjdk version "17.0.8.1" 2023-08-25 LTS
```

**45MB vs 323MB，砍掉 86%**——一个能跑 `java -version`、能加载 java.base 和 java.logging 的最小 JVM。注意命令里 `du` 加了 `-L`：`/opt/codev/TencentKona` 是指向真实 JDK 的软链，不带 `-L` 只会数出 0。它和你日常用的 JDK 是同一个箱子格式（jlink 造出来的就是 jimage 镜像），只是里面只装了 2 个模块：

```
$ /tmp/jre-mini/bin/java --list-modules
java.base@17.0.8.1
java.logging@17.0.8.1
```

对照完整 JDK 的 `java --list-modules`——70 个模块。这就是**运行期 vs 镜像期**的两个视图：`java --list-modules` 是运行期问 JVM，`jimage list` 是镜像期翻箱子，同一份内容两个入口（域 40 vs 域 41）。

jlink 还有 `--list-plugins` 看裁剪插件（实测含压缩 `--compress`、去重 `--dedup-legal-notices`、排除文件 `--exclude-*`、剥离调试信息 `--strip-debug` 等）。最小运行时的价值：生产镜像瘦身、容器镜像定制、隔离环境。注意它的边界：**装进去的模块是终身的**——最小运行时缺模块没法现场补，裁剪前先想清楚依赖（这正是下一节 jdeps 的用武之地）。

## 3. 依赖图：jdeps 与 jdeprscan

### 一个 jar 依赖什么

裁剪之前得先知道依赖。`jdeps` 分析字节码里的模块引用：

```
$ jdeps math-game.jar
math-game.jar -> java.base
   demo                                               -> java.io
   demo                                               -> java.lang
   demo                                               -> java.util
   demo                                               -> java.util.concurrent
```

math-game.jar 的全部依赖收敛到 **java.base 一个模块**（用了 io/lang/util 四个包）。更狠的是 `--print-module-deps`——直接输出可喂给 jlink 的模块名：

```
$ jdeps --print-module-deps math-game.jar
java.base
```

**`jdeps --print-module-deps` 的输出，就是 `jlink --add-modules` 的参数**——依赖分析的"读"端和镜像组装的"写"端闭环了。这就是模块化工具链的主线：分析（jdeps）→ 裁剪（jlink）→ 验证（jimage/java --list-modules）。写域 07（模块系统）时，这个闭环是标准插图。

### 废弃 API 扫描

`jdeprscan` 查 jar 里用了哪些废弃 API：

```
$ jdeprscan math-game.jar
Jar file math-game.jar:
```

空报告——这个 jar 干净。jdeprscan 的价值在旧代码库：`java.util.Date`、`Vector` 这些废弃符号一网打尽，是升级 JDK 前的体检工具（域 48 工具链素材）。

## 4. 对照：三工具一箱

| 工具 | 角色 | 实测产出 | 写作域 |
|---|---|---|---|
| `jimage` | 读镜像 | 70 模块/27,100 资源/解包 27,100 文件 | 41 |
| `jlink` | 写镜像 | 45MB 最小运行时（-86%） | 41/40 |
| `jdeps` | 读依赖 | math-game → java.base 单模块 | 07 |
| `jdeprscan` | 扫废弃 API | 空报告 | 48 |
| `java --list-modules` | 运行期视图 | 70 模块 vs 2 模块 | 40 |

和 async-profiler 那类运行期工具没有直接对照——模块/镜像工具是纯 JDK **构建期**主题，它们服务的对象是"JDK 这个产品本身"。

## 生产注意

- **jlink 裁剪不可逆**：最小运行时缺模块不能现场补，生产前用 `jdeps --print-module-deps` 把依赖摸全。
- **jimage 是只读的**：工具只能看和拆，不能改；改镜像的唯一方式是重新 jlink。
- **`--list-modules` vs `jimage list` 别混**：前者是运行期 JVM 视角，后者是文件格式视角，两个入口同一样内容。

## 复现说明：数字来自哪，变了又意味着什么

本篇全部输出来自 2026-08-11 对 TencentKona JDK 17.0.8.1 的实测。

- **结构稳定**：jimage 的哈希索引结构（Table Length = 槽位）、list/extract 计数一致、jdeps 输出格式——任何 JDK 17 都一样。
- **数值可变**：资源总数（27,100 是这台 JDK 的）、模块数（70）、大小比（45MB vs 323MB 依赖编译选项）——不同发行版/版本不同。
- **复现要点**：`jimage`/`jlink`/`jdeps` 都是无副作用只读命令（jlink 只写 --output 目录），随时可重跑验证。

## 跨域桥

- **镜像格式**（域 41）：`lib/modules` = 哈希索引 + 压缩资源区；jimage 是唯一直接窗口；"Resource Count 与 list 计数不一致"是索引条目 vs 真实资源的实证（extract 裁决）。
- **模块系统**（域 07）：jdeps 依赖图是模块引用关系的实证；`--print-module-deps` → `--add-modules` 闭环是工具链主线。
- **启动加载**（域 11/40）：镜像期（jimage list）vs 运行期（java --list-modules）两个视图；CDS 归档与 jimage 是"共享/映射"思想的同族。
- **工具链**（域 48）：jimage/jlink/jdeps/jdeprscan 四件套 = JDK 构建期工具的代表。

工具卷七篇到此收尾。从 JFR 的事件流到 jimage 的镜像结构，你已经见过一个 JVM 的两面：运行时怎么被观察，产品本身怎么被拆装。下一步，带着这些"亲眼所见"，回到源码去写每个机制背后的实现。
