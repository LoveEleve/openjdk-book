# 06. JMX 与火焰图 — 观察 JVM 的两类眼睛

> 本篇 MBean 属性与 perf 产物抓自 2026-08-11 的实测（JMX 数据来自 Demo PID 3775707，perf 全链路来自 math-game PID 3029544，JDK 17.0.8.1），不是编的。

## 两类眼睛：问出来的和采样出来的

前几篇的观测方式其实可以分成两类。

一类是**问**：jcmd 问 JVM 答，jconsole 问 JMX 答，MBean 树上的每个属性都是 JVM 主动报上来的——你得到的是"它愿意告诉你的"。

另一类是**采样**：perf 不问 JVM，它挂在 CPU 上，每隔固定周期看一眼"现在谁在跑"——你得到的是"内核看到的"。

两类眼睛看到的世界不一样，互补：JMX 给你**状态**（线程几个、堆多大、GC 几次），采样给你**分布**（CPU 时间花在哪、栈长什么样）。这一篇把两副眼睛都装上：先看 JMX 的窗口 jconsole，再看内核采样器 perf 和火焰图。

## 1. JMX 的窗口：MBean 树

### 一棵 26 个节点的树

JDK 自带 jconsole。本机连上目标进程（`jconsole <pid>`），MBeans 页签里就是一棵树——实测（本地连接器直读，同树同数据）是 26 个 MBean：

```
java.lang:type=Runtime / Threading / OperatingSystem / Compilation / ClassLoading / Memory
java.lang:name=G1 Young Generation,type=GarbageCollector / G1 Old Generation
java.lang:name=G1 Eden/Survivor/Old Gen,type=MemoryPool / Metaspace / Compressed Class Space
java.lang:name=CodeHeap 'profiled/non-profiled/non-nmethods',type=MemoryPool ×3
java.nio:name=direct/mapped/mapped-'non-volatile memory',type=BufferPool ×3
java.util.logging:type=Logging
com.sun.management:type=DiagnosticCommand / HotSpotDiagnostic
jdk.management.jfr:type=FlightRecorder
```

**这棵树就是域 33（JMX）的"目录"**——JMX 的所有接口都在这里挂名。点开 `java.lang:type=Threading`，属性就是体检报告：

```
PeakThreadCount            = 14
DaemonThreadCount          = 10
ThreadCount                = 14
TotalStartedThreadCount    = 14
ThreadContentionMonitoringEnabled = false
ObjectMonitorUsageSupported      = true
```

线程数、守护线程数、峰值——`ThreadCount 14 / Peak 14` 说明这台 JVM 线程数没波动过。`ObjectMonitorUsageSupported = true` 表示可以查每个 monitor 的占用明细（域 19 的 JMX 侧入口）。

`GarbageCollector` 节点直接给累计值：

```
java.lang:name=G1 Young Generation,type=GarbageCollector
  CollectionCount = 3752
  CollectionTime  = 3468
```

3752 次 young GC、累计 3468 毫秒——**不用算，JMX 记着账**。jstat 的 YGC 列（域 02）读的就是同一笔账（PerfData 侧），两处数字应该一致——这就是"同一事实两个接口"的对照。

### JMX 是什么：一个服务器 + 一个注册表

树下面的机制一句话：**MBean 服务器（MBeanServer）+ 注册表**。每个 MBean 是一个"管理对象"（比如 `Threading` 背后的 `sun.management.ThreadImpl`，实现在 `src/java.management/share/classes/sun/management/`），注册到服务器上，客户端通过 `ObjectName`（就是 `java.lang:type=Threading` 这个字符串）定位。jconsole 只是标准客户端之一。

**同一棵树，多个消费方**。实测 Arthas `jvm` 命令的输出，读的就是这棵树上的 MBean：

```
VM-VENDOR              Tencent
VM-VERSION             17.0.8.1+2-LTS
LOADED-CLASS-COUNT     6622
UNLOADED-CLASS-COUNT   0
```

`LOADED-CLASS-COUNT` 就是 `java.lang:type=ClassLoading` 的 `LoadedClassCount` 属性——**jconsole 点开看，Arthas 命令读，同一份数据**。JMC 的 MBean 浏览器、VisualVM、甚至你自己写的 JMX 客户端，都是这棵树的消费方。写域 33 时，"MBean 树 = 接口清单"这个等式就是文章的骨架。

### 本机怎么连

实测的本地连接是两条命令的事：

```
$ jcmd <pid> ManagementAgent.start_local
$ jcmd <pid> ManagementAgent.status
Agent: enabled
Connection Type: local
Protocol       : rmi
URL            : service:jmx:rmi://127.0.0.1/stub/rO0ABXNyAC5qYXZheC5t...
Properties     :
  com.sun.management.jmxremote.ssl = true [default]
  com.sun.management.config.file = management.properties [default]
  com.sun.management.jmxremote.local.only = true [default]
```

`start_local` 开一个**仅本机**的 JMX 连接器（jconsole 本地进程直接双击就连上）；注意 Properties 里的默认值：`ssl = true`、`local.only = true`——**远程 JMX 默认带 SSL 且拒绝远程连接**，这是域 33 的安全底座，生产开远程 JMX 必须先显式配认证（`jmxremote.password`）和加密。

## 2. 内核视角：perf

JMX 是 JVM 报数。perf 不问 JVM——它是内核的采样器，挂在 CPU 的周期中断上，每隔固定时间记录"此刻正在执行哪条指令、属于哪个线程的哪一层栈"。

```
$ perf record -g -p <pid>          # 采样，默认按频率采样
$ perf script > perf.stacks        # 导出文本栈
```

实测（math-game 进程）产出 56,718 个样本、`perf script` 展开 363,540 行——**平均每个样本约 6 层栈帧**。这就是"CPU 时间花在哪"的原始数据：**没有 JVM 参与，全是内核记录的**。

关键差异在视角：

| | perf | JFR 采样 | async-profiler |
|---|---|---|---|
| 采样者 | Linux 内核 | JVM 内部 | JVM 内封装内核 |
| 看到什么 | 内核态+用户态全部 | JVM 事件+Java 栈 | 两者结合 |
| 依赖 | root/perf 权限 | 无 | 同 perf 或 JDK 自带 |

这个"三层"关系是理解采样架构的主线（域 18/32 写作骨架）：**async-profiler 的 CPU 引擎就是 perf_event_open 的封装**（异步剖析器项目笔记 AP-2 篇 2 学过 perf_event_open + mmap ring buffer），它把内核能力包装成 JVM 采样器；JFR 则是 JVM 自己的采样器（不碰内核）。工具之下还是工具。

还有一个采样特有的坑（域 18 的主菜）：**JVM 栈采样只在安全点发生**——JFR 和 async-profiler 抓 Java 栈时，线程必须停在安全点才能取帧，所以采样分布天然偏向安全点附近（safepoint bias）。perf 没有这个问题（内核直接读 PC），但看到的是机器码地址，Java 方法名要 JIT 符号表才能还原——各有各的盲区。

## 3. 火焰图：栈折叠与聚合

56,718 个样本没法直接看。Brendan Gregg 的火焰图脚本把原始数据变成一张图，原理只有两步——**折叠 + 聚合**。亲手跑一遍（`/opt/tools/FlameGraph/` 是脚本仓库）：

```
$ perf script > perf.stacks                    # 原始样本
$ stackcollapse-perf.pl perf.stacks > perf.folded   # ① 折叠
$ flamegraph.pl perf.folded > flamegraph.html   # ② 聚合绘图
```

第一步"折叠"把每个样本的栈从"多行帧"压成"一行分号串"（实测 56,718 样本 → 5,483 条唯一栈）；第二步"聚合"把相同前缀的栈合并计数，画成矩形。**火焰图每个矩形的宽度 = 该路径在采样中的占比**——这就是"CPU 时间分布"的图形化。

实测产物：

```
C1_CompilerThre;__GI___pthread_disable_asynccancel 1
C1_CompilerThre;__condvar_cancel_waiting 1
...
```

打开生成的 HTML，一条从底部到顶部的"山脊"就是一条热路径，宽度即占比。JMC 自带 Flame Graph 视图也能直接从 JFR 采样渲染（不用装脚本），但脚本版的价值在于**暴露了"折叠"这一步**——async-profiler 内部的 Trie 树就是它的 C++ 实现（每个节点一个方法、相同前缀共享），两个实现互相印证，是"聚合算法"主题的最佳教材（域 32 素材）。

## 4. 对照与素材地图

| 对照轴 | 一侧 | 另一侧 | 写作域 |
|---|---|---|---|
| JMX 双消费 | jconsole / JMC MBean 浏览器（树） | Arthas `jvm` / `dashboard`（命令） | 33 |
| 采样三视角 | perf（内核） | async-profiler / JFR（JVM 侧） | 18/32 |
| 聚合双实现 | FlameGraph 脚本（栈折叠） | async-profiler Trie 树 | 32 |
| 规则引擎 | JMC Automated Analysis（74 条规则） | JFR 事件 → JVM 域 | 25/19 等 |

最后一行值得单独说：JMC 的自动分析不是黑盒提示——74 条规则，每条都是"规则 → 事件 → 域"的链条（规划库 KP 06 节全量清单）。比如规则 `LongGcPause` 盯的是 GC 停顿类事件（`GCPhasePause` 等，域 25），`BiasedLockingRevocation` 盯的是偏向锁撤销事件（域 19）。写工具侧文章时，"JMC 用哪条规则盯哪个域"就是现成的健康维度清单。

## 生产注意

- **JMX 远程**：默认 `ssl=true` + `local.only=true`，生产开远程必须显式配认证文件和加密参数；只在本机调试就 `start_local`，别开端口。
- **perf 权限**：需要 root 或 `perf_event_paranoid` 放开（实测本环境 paranoid=2 可跑用户进程）。容器里权限不足时，用 async-profiler 的 fdtransfer 机制或直接上 JFR 采样。
- **perf 与 JIT 符号**：Java 方法名需要 JIT 符号表（`-XX:+PreserveFramePointer` 或 perfmap），否则火焰图里全是裸地址——这也是"perf 看 Java 总差一步"的原因。
- **采样别开太久**：perf 周期采样产生的原始数据按 MB 计（实测 56,718 样本就是 28MB 文本），按需开、开完即收。

## 复现说明：数字来自哪，变了又意味着什么

本篇 JMX 数据来自 2026-08-11 对 Demo（PID 3775707）的本地连接器直读（MBean 属性如 ThreadCount=14、CollectionCount=3752 是那次运行的值）；perf 数据来自对 math-game（PID 3029544）的一段采样（56,718 样本、5,483 条唯一栈）。

- **结构稳定**：MBean 树形（这台默认配置的 JDK 17 是 26 个，换 GC/开关会增减）、MBean 属性名、`start_local` 输出格式、火焰图"折叠+聚合"两步法——任何环境都成立。
- **数值可变**：ThreadCount、CollectionCount、样本数、栈分布——换一次运行就是另一组数；甚至同一进程隔 10 分钟再采，火焰图形状都会变（热点转移）。
- **复现要点**：perf 要 root/paranoid 放开；JMX 本地连接先 `start_local` 再连；火焰图脚本在 `/opt/tools/FlameGraph/`。

## 跨域桥

- **JMX**（域 33）：MBean 树 26 节点 = 接口清单实证；`sun.management` 实现在 `src/java.management/share/classes/sun/management/`；Arthas `jvm` 是同一棵树的双消费方。
- **采样架构**（域 18/32）：perf（内核）→ async-profiler（封装）→ JFR（JVM 内）三层关系；safepoint bias 是 JVM 侧采样的固有盲区。
- **聚合算法**（域 32）：FlameGraph 栈折叠 ↔ async-profiler Trie 树，两个实现互相印证。
- **规则引擎**（域 25/19 等）：JMC 74 条规则 = "规则→事件→域"链条（KP 06 全量）。
