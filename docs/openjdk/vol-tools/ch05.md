# 05. 钻到 JVM 肚子里看对象 — jhsdb 与 Serviceability Agent

> **前置依赖**：[03 — 堆分析](openjdk/vol-tools/ch03.md)：认识对象与堆；[02 — jcmd](openjdk/vol-tools/ch02.md)：看过标准工具的"黑盒"输出

>
> 本篇所有输出抓自 2026-08-11 对 Demo 进程（PID 3757059 / 3775707，JDK 17.0.8.1）的实测，不是编的。

## 前四篇都是"黑盒"，这一篇是"白盒"

回想一下前面用的工具。jcmd 问 JVM："堆多大？线程在哪？"——JVM 自己回答。jmap 问："给我统计一下对象。"——JVM 自己数好给你。JFR 问："把发生的事记下来。"——JVM 自己记。

**全是黑盒**：你永远只拿到 JVM 愿意给你的答案，看不到它内部真实的数据结构长什么样。

这一篇换一个玩法：**不问了，直接读**。JVM 的整个运行时——对象头、Klass、堆分区、计数器——都躺在它自己的内存里。有一组工具能绕过 JVM 的一切接口，直接按内存布局把那些结构读出来，像读一本摊开的书。它叫 **SA（Serviceability Agent，可服务性代理）**，JDK 内置，入口命令是 `jhsdb`。

它怎么做到的？在 Linux 上，SA 通过 `ptrace` 附加目标进程，然后直接读 `/proc/<pid>/mem`——目标 JVM 的地址空间就是一张大地图，SA 按 HotSpot 的 C++ 数据结构布局（哪个偏移是 mark word、哪个偏移是 klass 指针）逐字节解读。**这就是"从外部读 JVM 内存"**：目标 JVM 完全不知情，甚至它已经死了（crash 后的 core dump）SA 也能读。

这一篇用三个探索任务，把 SA 的能力过一遍：看类结构、看堆布局、看 PerfData 计数器。

## 1. 看类结构：Inspect 一个 Klass

### 先找到类地址

clhsdb 是 SA 的命令行界面。连着 Demo 进程，先问它"Demo$BusyTask 这个类在哪"：

```
$ jhsdb clhsdb --pid <pid>
hsdb> class Demo$BusyTask
Demo$BusyTask @0x00007f94d4007a08
```

得到一个内存地址。注意这个地址**不是对象**，是 **Klass**——类的内部表示（域 06 的主角：C++ 里描述"这是一个什么类"的数据结构）。

### 再解剖它

```
hsdb> inspect 0x00007f94d4007a08
Type is InstanceKlass (size of 464)
juint Klass::_super_check_offset: 56
Klass* Klass::_secondary_super_cache: Klass @ null
Array<Klass*>* Klass::_secondary_supers: Array<Klass*> @ 0x00007f9518412580
Klass* Klass::_primary_supers[0]: Klass @ 0x00007f94d3000d68
OopHandle Klass::_java_mirror: OopHandle @ 0x00007f94d4007a78
jint Klass::_modifier_flags: 8
Klass* Klass::_super: Klass @ 0x00007f94d3000d68
jint Klass::_layout_helper: 16
Symbol* Klass::_name: Symbol @ 0x00007f956c334aa0
AccessFlags Klass::_access_flags: 536870944
markWord Klass::_prototype_header: 1
Klass* Klass::_next_sibling: Klass @ 0x00007f94d30d0478
int Klass::_vtable_len: 6
ClassLoaderData* Klass::_class_loader_data: ClassLoaderData @ 0x00007f956c21d730
Array<Method*>* InstanceKlass::_methods: Array<Method*> @ 0x00007f95184125a0
ConstantPool* InstanceKlass::_constants: ConstantPool @ 0x00007f9518412358
...
```

这是**一个类在内存里的完整解剖图**——InstanceKlass（普通 Java 类的 Klass 形态）464 字节，字段逐个摊开。挑四个最能说明问题的读：

- **`_super_check_offset: 56`**：快速子类型检查用的"去哪查父类"偏移——`instanceof`/`checkcast` 的快路径全靠它。HotSpot 源码注释（`src/hotspot/share/oops/klass.hpp`）说这组字段（连同 `_secondary_super_cache`/`_secondary_supers`/`_primary_supers`）"all help make fast subtype checks"：primary super 查 `_primary_supers[depth()]`，secondary 走缓存。
- **`_super: Klass @ 0x00007f94d3000d68`** 和 **`_primary_supers[0]` 是同一个地址**：BusyTask 的直接父类（Object）。顺着这个指针就能走出整条**继承链**——类继承关系在内存里的样子；类加载器关系则是另一个字段 `_class_loader_data` 管的事（域 07 的两个维度别混）。
- **`markWord Klass::_prototype_header: 1`**：原型对象头。值 1 的二进制是 `...0001`，最低位是**偏向锁标记位**——Klass 记着"新对象出生时对象头应该长什么样"，对象分配时从这里拷贝。写域 06/19 时，"偏向锁位在对象头第 0 位"这句话，这里有实物。
- **`_methods` / `_constants` / `_class_loader_data`**：方法表、常量池、类加载器数据——一个类的"五脏"各指一处内存。

注意最后一行 `InstanceKlass (size of 464)`——**这个输出本身就是域 46 的活教材**：SA 能逐字段展开，靠的是和 HotSpot 编译时一致的结构布局（vmStructs 那套机制）。

## 2. 看堆布局：universe

SA 还能直接问"堆怎么分的"。clhsdb 里敲 `universe`：

```
hsdb> universe
Heap Parameters:
garbage-first heap [0x0000000446000000, 0x0000000800000000] region size 8192K
G1 Heap:
   regions  = 1908
   capacity = 16005464064 (15264.0MB)
   used     = 1263234840 (1204.7MB)
   7.89% used
G1 Young Generation:
Eden Space:
   regions  = 149
   capacity = 1837105152 (1752.0MB)
   used     = 1249902592 (1192.0MB)
   68.04% used
Survivor Space:
   regions  = 0
   capacity = 8388608 (8.0MB)
   used     = 966936 (0.92MB)
   11.53% used
G1 Old Generation:
   regions  = 3
   capacity = 1082130432 (1032.0MB)
   used     = 12365312 (11.79MB)
   1.14% used
```

和 jcmd 的 `GC.heap_info`（域 02 看过）一比，差异立现：`GC.heap_info` 给"total/used"两个数，universe 给**整个分区的家底**——Eden 149 个 region、Survivor 0 个、Old 3 个；而且注意 Eden 占了 1752MB 容量里 1192MB（68%）——因为年轻代正在疯狂分配（我们那个 AllocTask）。`[0x0000000446000000, 0x0000000800000000)` 是堆的虚拟地址区间，上界又是 32GB 边界（压缩指针）。

**这是域 09（内存核心）最直接的素材**：G1 的"分区布局"概念，不是图，是这一页输出。

## 3. 看 PerfData：jsnap

第三个任务看计数器。JVM 内部有一批 PerfData 计数器（域 38），`jhsdb jsnap --all` 直接倒出来——192 行。最值钱的是 `sun.rt._sync_*` 锁计数器：

```
sun.rt._sync_Inflations=5 event(s)
sun.rt._sync_Deflations=3 event(s)
sun.rt._sync_ContendedLockAttempts=0 event(s)
sun.rt._sync_FutileWakeups=0 event(s)
sun.rt._sync_Parks=6 event(s)
sun.rt._sync_Notifications=5 event(s)
sun.rt._sync_MonExtant=2 event(s)
```

这 7 个计数器是**锁子系统（域 19）的体检报告**：Inflations=5（5 次锁升级成 monitor）、Parks=6（6 次 park 停等）、ContendedLockAttempts=0（0 次锁竞争——我们的 Demo 不抢锁，符合预期）。写域 19 时，"锁竞争到底多不多"不是拍脑袋——`ContendedLockAttempts` 一个数就是答案。jstat 也是读 PerfData（域 02 提过），但 jsnap 是**全量直读**，jstat 只投影了其中 12 个视图。

## 4. 对照：SA 三件套 vs JDK 工具

jhsdb 还带了 jmap/jstack/jinfo 的 SA 版。同一台机器对照实测：

| 功能 | JDK 工具 | SA 版（jhsdb） | 差异 |
|---|---|---|---|
| 堆参数 | `jcmd GC.heap_info`（5 行） | `jhsdb jmap --heap`（49 行配置） | JDK 17 里 `jmap -heap` 直接报错并把你指去 SA："Error: -heap option used… **Use jhsdb jmap instead**"——JDK 自己承认这条路由没了 |
| 线程栈 | `jstack` / `jcmd Thread.print` | `jhsdb jstack --locks` | SA 直读内存，不依赖 attach API |
| 标志 | `jinfo -flags` / `jcmd VM.flags` | `jhsdb jinfo --flags` | SA 版只出显式标志摘要 |

核心差异一句话：**JDK 工具问 JVM，SA 工具读 JVM**。这带来一个杀手锏场景：JVM 卡死或崩溃时，JDK 工具可能根本连不上（attach 依赖 JVM 活着响应），而 SA 能读 core dump——**进程死了，分析照做**。这是域 46 的主打场景。

还有个反向教训（实测踩的坑）：SA 在线连活进程时，`scanoops` 扫全堆（15GB）会慢到超时；`class` 命令的类名带 `$` 时要小心 shell 转义；进程退出后再 attach 报 `cannot open binary file`——**SA 的报错在诚实告诉你它读不到内存了**。

## 5. 三路读 JVM 内部

SA 不是唯一能读 JVM 内部的路。三条路对照（域 46/28 写作的对照框架）：

| 路线 | 代表 | 原理 | 场景 |
|---|---|---|---|
| 官方白盒 | SA（jhsdb） | 读 /proc/pid/mem + 结构布局 | 在线/离线读结构 |
| 运行时自解析 | async-profiler 的 vmStructs | 从 VM 里读出结构偏移 | 采样时顺带解析帧 |
| 问 JVM 自己 | JVMTI / jcmd | JVM 主动上报 | 标准诊断 |

对象头就是三条路都能看的例子：hsdb Inspect 是官方视角，vmStructs 是运行时自解析（async-profiler 展开 `[inlined]` 帧时用），JFR 的采样栈是 JVM 上报。**同一个数据结构，三种读取方式**——写域 06（对象模型）时，这个"三路对照"就是文章骨架。

## 生产注意

- **权限**：SA 用 ptrace 附加，目标进程必须同用户（或 root），容器里还要注意权限配置。
- **在线干扰**：SA 附加会暂停目标进程做解析（`scanoops` 全堆扫描实测会卡），在线慎用重操作。
- **杀手锏**：core dump 分析——`jhsdb jmap --core core --exe java`，进程死了也能查堆。域 46 的主场。
- **gui 模式**：`jhsdb hsdb --pid` 的图形界面（Object Histogram / Inspect 对象头 / 线程栈）在桌面环境下更直观，操作步骤见附录 G5/G6。

## 复现说明：数字来自哪，变了又意味着什么

本篇的 clhsdb 输出来自 2026-08-11 对 Demo（PID 3757059）的实测（该进程存活约 10 分钟，正好够一轮 SA 会话），jsnap/jhsdb 三件套来自 PID 3775707。

- **结构稳定**：InstanceKlass 的字段清单（`_super_check_offset`/`_java_mirror`/`_vtable_len` 等）、universe 的分区结构、`sun.rt._sync_*` 计数器族——任何 JDK 17 进程都一样，字段名即结构（域 06 素材）。
- **数值可变**：类地址（每次运行不同）、分区大小、计数器值（Inflations=5 是那次运行的累计）——换一次运行就是另一组数。
- **复现要点**：`class` 命令的类名写 `Demo$BusyTask` 时注意 `$` 转义；inspect 必须先用 `class` 拿到地址；进程死后一切命令都会失败——SA 会话要在进程活着时做完。

## 跨域桥

- **SA 架构**（域 46）：jhsdb 全家桶（hsdb GUI / clhsdb CLI / jsnap / SA 版 jmap/jstack/jinfo）共用同一套"读内存 + 结构布局解析"机制；`jmap -heap` 在 JDK 17 已失效（实测报错直接指向 `jhsdb jmap`）。
- **对象模型**（域 06）：InstanceKlass 464 字节的字段解剖、mark word 原型头（偏向锁位）、klass 指针——对象布局文章的直接素材。
- **堆布局**（域 09）：universe 的 G1 分区输出是"分区概念"的实物。
- **锁**（域 19）：`sun.rt._sync_*` 计数器 ↔ JMC LockInstances 页 ↔ JFR JavaMonitorEnter 事件，锁的三份体检报告。
- **PerfData**（域 38）：jsnap 全量直读 ↔ jstat 投影视图。
