## 上一篇给 JVM 装了监控仪,这一篇打开工具箱

上一篇我们用 JFR 给 JVM 装了台监控仪——它不打扰进程，默默把 30 秒里发生的一切录下来，事后慢慢回放。

但监控仪解决不了所有问题。很多时候你想要的不是"事后回放"，而是**现在就问它一句**：堆用了多少？线程卡在哪？编译开了多少？系统属性里那个参数是什么？——要快，要准，要能当场改。

JVM 给自己准备了一把这样的手术刀：**jcmd**。它不插管、不开刀、不重启进程，直接跟 JVM 本体对话。这一篇把它从头到尾过一遍——你会发现它根本不是什么"内存命令"或"GC 命令"，而是一个**命令框架**：49 个子命令，每个都是 JVM 内部一个"诊断命令类"的客户端。理解了这一层，jcmd 对你来说就不再是背命令，而是读目录。

## 1. 先问它自己：你支持什么

### 找到进程

任何诊断的第一步是找到目标进程。`jps -l` 列出所有 JVM，带全类名：

```
$ jps -l
3871634 Demo
3029544 target/math-game.jar
```

第一列是 PID，第二列是主类（无包名的类就叫 `Demo`，jar 包就显示 jar 路径）。同一台机器上还会有一堆别的 JVM——JMC、IDE、微服务，全都在列。

**49 个子命令**，加一个 `help` 自己。它们不是随便堆的，按前缀分是九组，每一组对准 JVM 的一块：

| 前缀 | 数量 | 管什么 | 关联域 |
|---|---|---|---|
| `VM.*` | 20 | 虚拟机本体：标志、信息、事件、元空间、CDS、NMT、字符串表… | 03/20/10/11/34/07 |
| `GC.*` | 6 | 堆、直方图、转储、触发 GC | 25/37 |
| `Compiler.*` | 9 | JIT：代码缓存、编译队列、编译指令 | 13/16 |
| `JFR.*` | 5 | 飞行记录器控制（上一篇的主场） | 32 |
| `ManagementAgent.*` | 4 | JMX 远程管理代理 | 33 |
| `JVMTI.*` | 2 | JVMTI 接口：加载 agent、数据转储 | 28/47 |
| `Thread.print` | 1 | 全线程转储 | 17/24 |
| `System.trim_native_heap` | 1 | 修剪本机堆（malloc_trim） | 34 |
| `help` | 1 | 查任何子命令的参数 | 35 |

注意到没有——**jcmd 自己什么都不会做**。它只是把"帮我调 GC 命令""帮我打印线程"这些话翻译给 JVM，真正干活的是 JVM 里注册的一堆 `DiagnosticCommand` 类。框架代码在 `src/hotspot/share/services/diagnosticCommand.cpp`，JFR 的命令在 `src/hotspot/share/jfr/dcmd/jfrDcmds.cpp`，NMT 的在 `src/hotspot/share/services/nmtDCmd.cpp`；客户端 `jcmd` 本身只是 `src/jdk.jcmd/share/classes/sun/tools/jcmd/JCmd.java` 里几百行 Java。这就是域 35 的全部骨架：**命令注解 → 参数解析 → 进 JVM 执行 → 输出回传**。

这个架构值得记住，因为它是"JVM 内置的 Arthas"——能力范围（类、线程、堆、编译）和 Arthas 高度重合，但 jcmd 是 JVM 自带的、零侵入的；Arthas 是外部字节码增强的、更强的。两个命令框架，同一个思想（注解驱动），两套实现。写域 35 时这是主线对照。

## 2. 输出怎么读 — 六个典型输出

命令清单只是目录。真正要紧的是**输出怎么读**——写作要引用真实输出，先亲手抓六个最常用的。

### VM.flags：这台 JVM 的完整配置

```
$ jcmd <pid> VM.flags
3725467:
-XX:CICompilerCount=15 -XX:ConcGCThreads=6 -XX:+FlightRecorder
-XX:G1ConcRefinementThreads=23 -XX:G1EagerReclaimRemSetThreshold=64
-XX:G1HeapRegionSize=8388608 -XX:InitialHeapSize=1006632960
-XX:MaxHeapSize=16005464064 -XX:MaxNewSize=9596567552
-XX:ReservedCodeCacheSize=251658240 -XX:+SegmentedCodeCache
-XX:+UseCompressedClassPointers -XX:+UseCompressedOops -XX:+UseG1GC
```

一行输出，整台 JVM 的"生效配置"。要读出三层：

第一，**这不是你启动时写的那几条**。这台 Demo 启动时一个 `-XX` 都没写，而这份输出有 22 个标志——因为 VM 会根据机器自动补全所有没写的（ergonomics）。比如这台机器物理内存 59.6GiB：`InitialHeapSize=1006632960`（960MB）≈ 物理内存的 1/64，`MaxHeapSize=16005464064`（14.9GB）≈ 物理内存的 1/4——这是 JDK 的默认堆比例（初始 1/64、最大 1/4），你没写，它就给你算好。写域 03（标志系统）时，VM.flags 就是"哪些是显式设置、哪些是派生值"的实证来源。

第二，**值本身就能看出这台 JVM 的形态**：`+UseG1GC`（用 G1）、`+SegmentedCodeCache`（代码缓存三段式，域 16）、`+UseCompressedOops`（压缩指针，堆没超 32GB）——每个 +XX 都是一扇窗。

第三，**它读的是运行期实况**。配合 `VM.set_flag`，可以当场改可写标志（`MinHeapFreeRatio 10` 这类），不用重启——这是"运行期改配置"的唯一官方通道，后面 Arthas 的 `vmoption` 也是同样的能力。

### GC.heap_info：一眼看堆

```
$ jcmd <pid> GC.heap_info
3725467:
 garbage-first heap   total 2473984K, used 126149K [0x0000000446000000, 0x0000000800000000)
  region size 8192K, 15 young (122880K), 1 survivors (8192K)
 Metaspace       used 5100K, committed 5312K, reserved 1114112K
  class space    used 568K, committed 704K, reserved 1048576K
```

五行，堆的全貌。三处要会看：

- 第一行是**堆本体**：G1 堆当前提交 2.36GB、用了 123MB，方括号是堆的虚拟地址区间——上界 `0x8000000000` 是 32GB 边界，因为压缩指针只能寻址这么多，`+UseCompressedOops` 不是白开的。
- 第二行是**年轻代**：region 8MB，15 个 young region（120MB），1 个 survivor。注意这是**当前时刻**的年轻代——G1 的年轻代大小是动态的，这一行是快照。
- 后两行是 **Metaspace**：used/committed/reserved 三态——保留 1GB、只提交了 5MB。这就是 Metaspace"虚拟空间大、按需提交"的活证据（域 10 素材）。

### Thread.print：全线程转储

```
$ jcmd <pid> Thread.print
3725467:
2026-08-11 19:52:45
Full thread dump OpenJDK 64-Bit Server VM (17.0.8.1+2-LTS mixed mode, sharing):
...
"busy-1" #25 prio=5 os_prio=0 cpu=192317.67ms elapsed=196.43s
         tid=0x00007f1a0c2272d0 nid=0x38d8ae runnable  [0x00007f1972efd000]
   java.lang.Thread.State: RUNNABLE
	at java.util.Random.next(java.base@17.0.8.1/Random.java:209)
	at java.util.Random.nextDouble(java.base@17.0.8.1/Random.java:463)
	at Demo$BusyTask.run(Demo.java:14)
	at java.lang.Thread.run(java.base@17.0.8.1/Thread.java:833)
```

线程头一行信息密度极高：`"busy-1" #25 prio=5 os_prio=0 cpu=192317.67ms elapsed=196.43s tid=0x... nid=0x38d8ae runnable`。逐个拆：

- `cpu=192317.67ms`：这个线程累计吃了 192 秒 CPU——实测这份转储里 busy-1、busy-2、alloc-1 三个线程各约 192 秒，进程才活了 196 秒：**每个线程都独占了一整核**。CPU 高不高，这列一眼出结果。
- `tid=0x00007f1a0c2272d0`：Java 线程内部地址；`nid=0x38d8ae`：原生线程号（十六进制，十进制 3725486——用 `ps -L -p <pid>` 能对上一对一）。
- `runnable` + `Thread.State: RUNNABLE`：线程状态，和锁信息段配合读（`- waiting on <0x...>` / `- locked <0x...>` 是锁竞争现场，域 19 素材）。

抓线程转储有个注意点：**它需要安全点**（所有线程停在已知位置），所以 Thread.print 有短暂停顿——生产上别高频抓（域 18 相关）。

### Compiler.codecache：JIT 的仓库

```
$ jcmd <pid> Compiler.codecache
3725467:
CodeHeap 'non-profiled nmethods': size=118880Kb used=217Kb max_used=217Kb free=118663Kb
CodeHeap 'profiled nmethods': size=118876Kb used=1154Kb max_used=1154Kb free=117722Kb
CodeHeap 'non-nmethods': size=8004Kb used=1164Kb max_used=1747Kb free=6839Kb
total_blobs=1204 nmethods=755 adapters=363
compilation: enabled
              stopped_count=0, restarted_count=0
```

三块代码堆：C2 产物（non-profiled）、C1 产物+预热方法（profiled）、运行时桩（non-nmethods）。`total_blobs=1204 = nmethods 755 + adapters 363 + 其他`——755 个已编译方法就是这台 JVM 的"JIT 稳态"。当 used 逼近 size 时会看到 "CodeCache is full"——这是检查这个的唯一命令入口。

### VM.events：最近发生了什么

```
$ jcmd <pid> VM.events
3725467:
Compilation events (20 events):
Event: 196.282 Thread 0x00007f1a0c216f00 1502       4       java.util.HashMap::containsKey (14 bytes)
Event: 196.284 Thread 0x00007f1a0c216f00 nmethod 1502 0x00007f19fd0d2710 code [0x00007f19fd0d28c0, 0x00007f19fd0d2bc8]
Event: 196.284 Thread 0x00007f1a0c216f00 1498       4       java.lang.String::substring (58 bytes)
...
Deoptimization events (20 events):
Classes unloaded (0 events):
VM Operations (20 events):
```

四段环形缓冲：编译事件、反优化事件、类卸载、**VM 操作**。编译事件行有三个关键字段：时间戳（196.282 = 启动后毫秒）、编译层级（`4` = C2 全优化，`1` = C1）、方法名+字节码大小。第二行 `nmethod` 表示编译完成，给出机器码地址区间。VM 操作段和上一篇 JMC 的 VM Operations 页、JFR 的 `ExecuteVMOperation` 事件是**同一件事的三个视图**（域 20 素材闭环）。注意它是环形缓冲——只留最近 20 条，全量历史请找 JFR。

### VM.metaspace 与 VM.log：两个"隐藏能力"

`VM.metaspace` 打印元空间内部：实测 75 个类加载器、2448 个类，其中 **1116 个来自共享归档**（`1116 shared`——CDS 的痕迹，域 11 呼应）；往下是 chunk 的 capacity/committed/used/waste 明细——这是唯一能看到 Metaspace 内部 chunk 分配的命令。

`VM.log` 是运行期配置统一日志框架（ULF）的入口——`-Xlog` 只能在启动时配置，VM.log 让**运行中的 JVM 也能开日志**：

```
$ jcmd <pid> VM.log output=gc.log what=gc+heap     # 打开 gc+heap 标签的日志
$ jcmd <pid> VM.log list          # 看当前配置
$ jcmd <pid> VM.log disable       # 全关
```

"无需重启即可开日志"——排查现场问题时的救命能力（域 04）。注意 `what` 的值是 tag 组合，用 `+` 连接（`gc+heap`），写错会得到提示 "No tag set matches selection"——这个报错本身就是在教你 tag 语法。

### jstat：把快照连成趋势

jcmd 是单点快照。要看**趋势**，用 jstat——它读的是 PerfData 计数器（域 38），每秒钟采样一次：

```
$ jstat -gcutil <pid> 1000 3
  S0     S1     E      O      M     CCS    YGC     YGCT     FGC    FGCT     CGC    CGCT       GCT
  0.00  15.81  58.17   1.31  97.34  88.05   8199     7.679     3     0.023     0     0.000     7.702
  0.00   9.28  33.17   1.31  97.34  88.05   8219     7.697     3     0.023     0     0.000     7.721
  0.00   2.71  20.67   1.31  97.34  88.05   8239     7.717     3     0.023     0     0.000     7.740
```

三行之间发生了什么？E（Eden 占用）58% → 33% → 20%，YGC 8199 → 8219 → 8239——**每秒钟 20 次 young GC**，Eden 每 50 毫秒清空一次。这是"分配风暴"的速度感：不是概念，是计数器在跳。12 个选项里 `-gcutil` 最常用（各代使用率百分比），`-gc` 是绝对值，`-class`/`-compiler` 看类和编译。

## 3. 对照：jcmd vs Arthas vs JFR

同一个问题，三个工具三种打开方式：

| 问题 | jcmd | Arthas | JFR |
|---|---|---|---|
| 线程现在卡在哪 | `Thread.print`（安全点定格） | `thread -n 3`（CPU 采样 Top） | Threads 页（全程时间线） |
| 看/改标志 | `VM.flags` / `VM.set_flag` | `vmoption`（带 ORIGIN 列） | JMC 参数页（只读） |
| 堆状态 | `GC.heap_info`（快照） | `memory`（含 codeheap 明细） | Memory 页（曲线） |
| 一段时间内发生了什么 | `VM.events`（最近 20 条） | `dashboard`（周期刷新） | 事件流（全量可回放） |

Arthas 的 `vmoption` 输出比 `VM.flags` 多一列 **ORIGIN**——每个标志标明来源是 DEFAULT（默认值）还是 ERGONOMIC（自动推导）：

```
 KEY                 VALUE               ORIGIN              WRITEABLE
 HeapDumpBeforeFull  false               DEFAULT             true
 SoftMaxHeapSize     16005464064         ERGONOMIC           true
```

`SoftMaxHeapSize 16005464064` 标着 ERGONOMIC——正是上一篇 VM.flags 里那个 14.9GB 的来历（1/4 物理内存自动推导）。两把尺子量同一个数，互相印证（域 03 素材）。

## 生产注意：零开销与一个停顿

- **零侵入**：读类、读标志、读堆信息这些命令，JVM 侧只是拷贝数据，没有采样开销——生产上随便用。
- **一个例外**：`Thread.print` 需要所有线程到安全点才能抓栈，会有短暂停顿（毫秒级，但存在）——高并发线上慎用高频抓取。
- **重操作**：`GC.heap_dump`、`GC.class_histogram` 会触发 GC 或遍历堆，属于"重"命令，诊断窗口用，别当日常。

## 复现说明：数字来自哪，变了又意味着什么

本篇所有输出都是 2026-08-11 的实测抓取（PID 3725467 与 3775707，JDK 17.0.8.1，Demo 负载）。如果你自己跑：

- **结构稳定**：子命令清单（JDK 17 就是这 49 个）、输出格式、量级关系（young GC 每秒十几次、cpu 列和 nid 列的含义）——任何 JVM 都一样。
- **数值可变**：`GC.heap_info` 的 used、`jstat` 的 YGC 计数、`VM.events` 的时间戳——换一次运行就是另一组数。它们是"这台 JVM 此刻的体检值"，不是定律。
- **判断方法不变**：CPU 高的线程看 `cpu=` 列、分配风暴看 jstat 的 E 列下跌速度、编译看 `nmethod` 事件的层级——**方法比数字更值得复制**。

## 跨域桥

- **命令框架**（域 35）：jcmd 的每个子命令背后是一个 `DiagnosticCommand` 类——框架在 `src/hotspot/share/services/diagnosticCommand.cpp`，JFR 命令在 `src/hotspot/share/jfr/dcmd/jfrDcmds.cpp`，NMT 在 `src/hotspot/share/services/nmtDCmd.cpp`，客户端在 `src/jdk.jcmd/share/classes/sun/tools/jcmd/JCmd.java`。
- **标志系统**（域 03）：`VM.flags` 是生效值全貌，`VM.set_flag` 是运行期唯一改法，Arthas `vmoption` 的 ORIGIN 列补了"来源"维度——三处交叉引用写标志文章。
- **GC 观察**（域 25/26）：`GC.heap_info` 快照 + jstat 趋势 + JFR 事件流 = 三段时间分辨率，写 GC 时按需取用。
- **VM 操作**（域 20）：`VM.events` ↔ JMC VM Operation 页 ↔ JFR `ExecuteVMOperation`，三视图闭环。
