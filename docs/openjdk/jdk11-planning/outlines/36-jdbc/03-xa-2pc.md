# 03. XA 与 2PC — 分布式事务的理论地基(面试向)

> 🟡 Working | 域 36 JDBC 第 3 篇(面试向)| Layer 3
> 读者处境: 面试"分布式事务"——2PC 是理论支撑;XAResource 的接口语义与流程,以及为什么 Seata AT 不走 XA。

### 1. "XAResource 是什么？" — 分布式事务的参与者接口

场景: 两个库要原子提交——JDBC 侧怎么表达"参与者"?

- 规范: `javax.transaction.xa.XAResource`(X/Open XA 标准,java.transaction.xa 模块,JDK11 共 5 个文件,纯接口)
- 核心方法: `start(Xid, flags)`(开启分支事务)/`end`/`prepare(Xid)`(**投票**)/`commit(Xid, onePhase)`/`rollback`/`recover`
- 常量: TMONEPHASE(一阶段优化)/TMJOIN/TMSUSPEND、XA_OK/XA_RDONLY
- 实现位置: **不在 JDK**——数据库驱动(MysqlXAConnection)与事务管理器(Atomikos/Spring JtaTransactionManager)实现
- 关键设计 (斜体): *XAResource 是"参与者契约"——事务管理器(协调者)通过它对每个分支发指令;JDK 只定义接口(签名+常量),实现全在驱动/中间件——面试讲"JDK 只出协议,实现归厂商"有深度*
- 面试: "Xid 是什么?"——全局事务标识(formatId + 全局/分支 id)

### 2. "2PC 怎么执行？" — 两阶段提交流程

场景: 协调者(事务管理器)怎么让两个库原子提交?

- **阶段一(准备/投票)**: 协调者向所有参与者发 `prepare(Xid)`——每个库执行 SQL 但不提交,**锁住资源**并回复"可提交"(XA_OK)/"要回滚"(XA_RB*)
- **阶段二(提交/回滚)**: 全部 prepare 成功 → 向所有参与者发 `commit`;任一失败 → 全部 `rollback`
- 一阶段优化: 只有一个参与者时 `commit(xid, TMONEPHASE)`(跳过 prepare)
- 关键设计 (斜体): *2PC 的"原子性"靠两阶段协议达成: 阶段一"确认都能提交",阶段二"统一行动";面试画时序图(协调者+2 参与者,prepare→commit)是基本功*
- 面试: "为什么需要 prepare 阶段"——避免"最后一个库提交失败"造成部分提交;prepare 是投票锁

### 3. "2PC 的经典问题" — 阻塞与协调者故障

场景: 面试"2PC 有什么缺点"——三大问题

- **同步阻塞**: prepare 后参与者**持有资源锁**直到阶段二——长事务/慢库拖住全局
- **协调者单点**: 协调者崩溃且未恢复 → 参与者无法决定提交/回滚(锁死)
- **脑裂/网络分区**: 阶段二消息丢失 → 参与者状态不确定
- 关键设计 (斜体): *"2PC 是强一致但脆弱"——它保证原子性,代价是阻塞与协调者依赖;面试答"2PC 阻塞 + 单点"就有深度;现代替代: 3PC(引入超时)/TCC/本地消息表/Seata AT*
- 面试: "2PC vs 3PC"——3PC 加超时与预提交,减少阻塞窗口(但仍非完全可靠)

### 4. "与 Seata 的对比" — 生产选型

场景: 生产分布式事务——XA 还是 Seata?

- **Seata AT 模式**: 不依赖 XA 接口——业务 SQL 后记录**回滚日志(undo log)**,提交时"分支提交";最终一致性(异步补偿)
- **Seata XA 模式**: 用 XA 接口(依赖数据库 XA 支持)
- 对比: XA 强一致(同步/锁/慢);AT 最终一致(异步/无锁窗口/快);TCC 业务补偿(手动)
- 关键设计 (斜体): *选型: 强一致场景(资金对账)用 XA/Seata-XA;高并发场景用 AT/TCC——"一致性强度 vs 吞吐"的经典权衡;面试"Seata AT 为什么比 XA 快"——不用全局锁+异步分支*
- 面试: "2PC 理论的现代工程化"——XA(标准)、Seata AT/TCC(变体)——理论支撑→工程落地
