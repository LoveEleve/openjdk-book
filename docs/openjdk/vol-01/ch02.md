# 第2章：JavaMain —— 跨进 JNI_CreateJavaVM

> **前置依赖**：[ch01 Launcher Chain](openjdk/vol-01/ch01)：dlopen + dlsym 拿到三个函数指针、pthread_create 创建新线程
> → **后续**：[ch03 JNI_CreateJavaVM](openjdk/vol-01/ch03)：Atomic::xchg 守卫 → JNI_CreateJavaVM_inner → Threads::create_vm

## 0. 问题——为什么需要 JavaMain？

上一章结束在 `pthread_create(ThreadJavaMain)`——新线程的入口是 `ThreadJavaMain`，但它只是一个签名适配器，把 `void* args` 转成 `int` 返回值。真正做事的是 `JavaMain(args)`。

问题是：为什么要 165 行代码？如果新线程只是调 `ifn->CreateJavaVM(...)` 创建 JVM 然后结束，10 行就够了。答案是：**创建 JVM 只是前半段——JVM 活了之后，还要加载主类、构建 `String[] args`、找到 `main()` 方法、调用它，最后在所有退出路径上做资源清理**。

`JavaMain` 是启动器链的**最后一个 C 函数**——从这里跨出去，就是 HotSpot C++ 的世界。165 行代码分 10 个阶段，分界线在第 2 阶段：

| 阶段 | 做什么 | 关键操作 |
|:--:|------|---------|
| 1 | 参数解包 | `void* _args` → `JavaMainArgs` 各字段 |
| 2 | **创建 JVM** | `InitializeJVM` → `ifn->CreateJavaVM()` |
| 3 | 特殊模式处理 | `-version`/`--list-modules`/`-XshowSettings` |
| 4 | 没给参数 | 打印帮助 → `LEAVE()` |
| 5 | 追踪日志 | 打印 `InitializeJVM` 耗时 |
| 6 | 加载主类 | `LoadMainClass(env, mode, what)` |
| 7 | 构建参数 | `CreateApplicationArgs` → `String[] args` |
| 8 | dry-run | `--dry-run` 模式，不实际执行 |
| 9 | PostJVM 初始化 | AWT 事件线程等平台初始化 |
| 10 | 调用 main() | `GetStaticMethodID` + `CallStaticVoidMethod` |

## JavaMain() 全貌

`JavaMain` 在 `java.c:413-578`，165 行。先看完整源码：

```c
/* === src/java.base/share/native/libjli/java.c === */

JavaMain(void *_args) {
    /* ═══════ 阶段1：参数解包 ═══════ */
    JavaMainArgs *args = (JavaMainArgs *) _args;
    int argc = args->argc;
    char **argv = args->argv;
    int mode = args->mode;
    char *what = args->what;
    InvocationFunctions ifn = args->ifn;

    JavaVM *vm = 0;
    JNIEnv *env = 0;
    jclass mainClass = NULL;
    jclass appClass = NULL;
    jmethodID mainID;
    jobjectArray mainArgs;
    int ret = 0;
    jlong start = 0, end = 0;

    /* ═══════ 阶段2：创建 JVM ═══════ */
    RegisterThread();
    start = CounterGet();
    if (!InitializeJVM(&vm, &env, &ifn)) {
        JLI_ReportErrorMessage(JVM_ERROR1);
        exit(1);
    }

    /* ═══════ 阶段3：特殊模式快速通道 ═══════ */
    if (showSettings != NULL) {
        ShowSettings(env, showSettings);
        CHECK_EXCEPTION_LEAVE(1);
    }
    if (showResolvedModules) {
        ShowResolvedModules(env);
        CHECK_EXCEPTION_LEAVE(1);
    }
    if (listModules) {
        ListModules(env);
        CHECK_EXCEPTION_LEAVE(1);
        LEAVE();
    }
    if (describeModule != NULL) {
        DescribeModule(env, describeModule);
        CHECK_EXCEPTION_LEAVE(1);
        LEAVE();
    }
    if (printVersion || showVersion) {
        PrintJavaVersion(env, showVersion);
        CHECK_EXCEPTION_LEAVE(0);
        if (printVersion) {
            LEAVE();
        }
    }
    if (validateModules) {
        LEAVE();
    }

    /* ═══════ 阶段4：没给参数 → 打印帮助 ═══════ */
    if (printXUsage || printUsage || what == 0 || mode == LM_UNKNOWN) {
        PrintUsage(env, printXUsage);
        CHECK_EXCEPTION_LEAVE(1);
        LEAVE();
    }

    FreeKnownVMs();

    /* ═══════ 阶段5：追踪日志 ═══════ */
    if (JLI_IsTraceLauncher()) {
        end = CounterGet();
        JLI_TraceLauncher("%ld micro seconds to InitializeJVM\n",
                          (long)(jint)Counter2Micros(end - start));
    }

    ret = 1;

    /* ═══════ 阶段6：加载主类 ═══════ */
    mainClass = LoadMainClass(env, mode, what);
    CHECK_EXCEPTION_NULL_LEAVE(mainClass);
    appClass = GetApplicationClass(env);
    NULL_CHECK_RETURN_VALUE(appClass, -1);

    /* ═══════ 阶段7：构建 String[] args ═══════ */
    mainArgs = CreateApplicationArgs(env, argv, argc);
    CHECK_EXCEPTION_NULL_LEAVE(mainArgs);

    /* ═══════ 阶段8：dry-run 快速通道 ═══════ */
    if (dryRun) {
        ret = 0;
        LEAVE();
    }

    /* ═══════ 阶段9：PostJVM 初始化 ═══════ */
    PostJVMInit(env, appClass, vm);
    CHECK_EXCEPTION_LEAVE(1);

    /* ═══════ 阶段10：查找并调用 main() ═══════ */
    mainID = (*env)->GetStaticMethodID(env, mainClass, "main",
                                       "([Ljava/lang/String;)V");
    CHECK_EXCEPTION_NULL_LEAVE(mainID);
    (*env)->CallStaticVoidMethod(env, mainClass, mainID, mainArgs);
    ret = (*env)->ExceptionOccurred(env) == NULL ? 0 : 1;
    LEAVE();
}
```

165 行，10 个阶段。分界线在第 2 阶段——`InitializeJVM` 返回前 JVM 不存在，返回后 JVM 已经活了。

## 阶段1：参数解包

第一章结尾的 `ContinueInNewThread` 把五个值打包进 `JavaMainArgs` 结构体，通过 `pthread_create` 的 `void* args` 参数传进来。这里解包回各自的变量：

```c
JavaMainArgs *args = (JavaMainArgs *) _args;
int argc = args->argc;
char **argv = args->argv;
int mode = args->mode;
char *what = args->what;
InvocationFunctions ifn = args->ifn;
```

`JavaMainArgs` 的定义：

```c
typedef struct {
    int    argc;
    char **argv;
    int    mode;
    char  *what;
    InvocationFunctions ifn;
} JavaMainArgs;
```

以 HelloWorld 为例，这些字段的值：

| 字段 | 值 | 说明 |
|------|-----|------|
| `argc` | `1` | 只剩 `"HelloWorld"` 一个参数（`-cp` 和 `/data/workspace/demo` 已被 `ParseArguments` 消费） |
| `argv` | `{"HelloWorld"}` | 剩余的非选项参数 |
| `mode` | `LM_CLASS` | 启动模式：通过类名启动 |
| `what` | `"HelloWorld"` | 要执行的类名 |
| `ifn` | `{CreateJavaVM, GetDefaultJavaVMInitArgs, GetCreatedJavaVMs}` | 三个函数指针，初始化为 0 |

`RegisterThread()` 在 Linux 上是空函数——只有一行注释 `stubbed out for windows and *nixes`，不执行任何操作。

## 阶段2：InitializeJVM —— 创建 JVM

这是本章的核心。`InitializeJVM` 在 `java.c:1524-1549`：

```c
InitializeJVM(JavaVM **pvm, JNIEnv **penv, InvocationFunctions *ifn) {
    JavaVMInitArgs args;
    jint r;

    memset(&args, 0, sizeof(args));
    args.version = JNI_VERSION_1_2;
    args.nOptions = numOptions;
    args.options = options;
    args.ignoreUnrecognized = JNI_FALSE;

    if (JLI_IsTraceLauncher()) {
        int i = 0;
        printf("JavaVM args:\n    ");
        printf("version 0x%08lx, ", (long) args.version);
        printf("ignoreUnrecognized is %s, ",
               args.ignoreUnrecognized ? "JNI_TRUE" : "JNI_FALSE");
        printf("nOptions is %ld\n", (long) args.nOptions);
        for (i = 0; i < numOptions; i++)
            printf("    option[%2d] = '%s'\n",
                   i, args.options[i].optionString);
    }

    r = ifn->CreateJavaVM(pvm, (void **) penv, &args);
    JLI_MemFree(options);
    return r == JNI_OK;
}
```

15 行，做三件事：

**1. 组装 JavaVMInitArgs。** JNI 规范定义了 `JavaVMInitArgs` 结构体——告诉 JVM 用什么版本启动、传哪些选项：

```c
memset(&args, 0, sizeof(args));
args.version = JNI_VERSION_1_2;       // 0x00010002，JNI 1.2 版本号
args.nOptions = numOptions;           // 启动选项的个数
args.options = options;               // 选项数组指针
args.ignoreUnrecognized = JNI_FALSE;  // 不忽略未知选项——错了就报错
```

`memset(&args, 0, sizeof(args))` 不是可有可无——`args` 是栈上的局部变量，不初始化的话里面的 padding 字节是随机的。JNI 实现会检查 `args.version` 的值来判断调用方支持的 JNI 协议版本——如果 padding 恰好在 `version` 字段的高位字节（4 字节对齐之间的空隙），随机的值会让 JNI 误判版本号。C 的安全实践：任何要传给外部接口的结构体，先全部清零再逐字段赋值。

`options` 是一个全局数组，由 `JLI_Launch`（ch01）的 Step 7-10 通过 `AddOption()` 逐步填充。填充不在 `JavaMain` 的 10 个阶段里——它发生得更早，在 `pthread_create` 之前。所以 `InitializeJVM` 里直接使用 `numOptions` 和 `options` 两个全局变量，不需要传参：
- `-D` 系统属性（`sun.java.command`、`sun.java.launcher` 等）
- 用户命令行上的 JVM 参数（`-Xmx256m` 等）
- 编译期参数（`jargv`，如果有）

`JNI_VERSION_1_2` 是历史遗留——JNI 1.2 及以上版本使用相同结构体，实际运行的是 JDK 11 的完整 JNI 实现。

**2. 追踪日志。** `JLI_IsTraceLauncher()` 在没开追踪时不进这个 `if`，日常等于空操作。

**3. 调用 CreateJavaVM。** 这是第一章 `dlsym` 解析出的第一个函数指针——`ifn->CreateJavaVM`。它在 `jni.cpp:4098` 指向 `JNI_CreateJavaVM`：

```c
_JNI_IMPORT_OR_EXPORT_ jint JNICALL JNI_CreateJavaVM(JavaVM **vm, void **penv, void *args) {
    jint result = JNI_ERR;
    result = JNI_CreateJavaVM_inner(vm, penv, args);
    return result;
}
```

`JNI_CreateJavaVM` 是 JVM 的入口。它返回两个指针——通过 `pvm` 和 `penv` 这两个 `out` 参数写回调用方：

- **`JavaVM**`**：JVM 实例的**接口句柄**。它不是 JVM 对象本身（JVM 内部是一个巨大的 C++ 对象图），而是一个包装结构体——只含一个字段 `const JNIInvokeInterface_ *functions`，指向真正的函数指针表。函数表里是 5 个全局 JVM 操作（`DestroyJavaVM`、`AttachCurrentThread`、`DetachCurrentThread`、`GetEnv`、`AttachCurrentThreadAsDaemon`），前 3 个槽位是 NULL 保留。`LEAVE()` 宏里调用的 `(*vm)->DestroyJavaVM(vm)` 就是通过这个指针——`(*vm)` 解引用拿到 `JavaVM_` 结构体，`DestroyJavaVM(vm)` 调 C++ 内联包装方法，内部转发到 `functions->DestroyJavaVM(this)`。
- **`JNIEnv**`**：当前线程的**JNI 环境句柄**。和 `JavaVM_` 同模——一个包装结构体，持有 `JNINativeInterface_ *functions` 指针（**228 个**函数指针）。它是**线程绑定的**——每个线程有自己的 `JNIEnv*`。阶段 6-10 的 JNI 调用（`GetStaticMethodID`、`CallStaticVoidMethod`）都通过 `env->XXX()` 的 C++ 内联包装转发到函数表。

两个指针的类型虽然不同，但底层结构同源——都是 `JNIEnv_` 结构体，通过 `JNIInvokeInterface_` 指针表桥接。区别是抽象层级：`JavaVM*` 操作 JVM 生命周期（创建/销毁线程），`JNIEnv*` 操作当前线程里的 Java 对象和方法。

`JNI_MemFree(options)` 的释放时机很关键——它紧跟在 `CreateJavaVM` 返回之后，在 `return` 之前。JVM 已经调用了 `args.options` 里的所有选项，不再需要这份数组。注意：释放的是**数组本身**（`options` 指针指向的内存），不是数组里 `JavaVMOption` 结构体的 `optionString` 字段——那些字符串指针仍然有效（它们指向的内存由 `JLI_StringDup` 分配、由 JVM 持有）。

`InitializeJVM` 返回后，JVM 已经是一个完整运行的虚拟机了。后续所有代码都是用 JNI 和它交互。

## 阶段3：特殊模式快速通道

`InitializeJVM` 之后有一串 `if`，对应各种 `java` 命令的特殊模式。它们的共同点：JVM 已经活了，做一件特定的事，然后退出。

| 命令行 | 标志 | 做什么 | 然后 |
|--------|------|--------|------|
| `java -XshowSettings` | `showSettings != NULL` | `ShowSettings(env)` 打印 JVM 配置 | 继续往下走 |
| `java --show-module-resolution` | `showResolvedModules` | `ShowResolvedModules(env)` 打印模块解析信息 | 继续往下走 |
| `java --list-modules` | `listModules` | `ListModules(env)` 列出所有可观察模块 | `LEAVE()` |
| `java --describe-module X` | `describeModule != NULL` | `DescribeModule(env, X)` 描述指定模块 | `LEAVE()` |
| `java -version` / `--version` | `printVersion \|\| showVersion` | `PrintJavaVersion(env)` 打印版本 | `LEAVE()` |
| `java --validate-modules` | `validateModules` | 什么都不做 | `LEAVE()` |
| `java -?` / `-help` / `-X` | `printXUsage \|\| printUsage \|\| what==0 \|\| mode==LM_UNKNOWN` | `PrintUsage(env)` 打印帮助 | `LEAVE()` |

这些模式都不走到 `LoadMainClass`，更不会 `CallStaticVoidMethod`。我们的 HelloWorld 不匹配任何一个，因此穿过这串 `if`，继续执行。

`CHECK_EXCEPTION_LEAVE(n)` 和 `LEAVE()` 都是 C 预处理器宏。它们的实际定义在 `java.c:378-409`：

```c
// java.c:378
#define LEAVE() \
    do { \
        if ((*vm)->DetachCurrentThread(vm) != JNI_OK) { \
            JLI_ReportErrorMessage(JVM_ERROR2); \
            ret = 1; \
        } \
        if (JNI_TRUE) { \
            (*vm)->DestroyJavaVM(vm); \
            return ret; \
        } \
    } while (JNI_FALSE)

// java.c:402
#define CHECK_EXCEPTION_LEAVE(CEL_return_value) \
    do { \
        if ((*env)->ExceptionOccurred(env)) { \
            JLI_ReportExceptionDescription(env); \
            ret = (CEL_return_value); \
            LEAVE(); \
        } \
    } while (JNI_FALSE)
```

两个宏都用 `do { ... } while (JNI_FALSE)` 包装——这是 C 语言宏的标准安全模式。如果不用 `do-while`，宏在多条语句的 `if/else` 里展开后会因为分号位置出错（`if (x) MACRO; else ...` 展开为 `if (x) stmt1; stmt2; else ...` 导致 `else` 没有匹配的 `if`）。

`CHECK_EXCEPTION_LEAVE` 的逻辑：先检查 `(*env)->ExceptionOccurred(env)`——JNI 有没有挂起的异常。有则打印异常描述、设 `ret = n`，然后走 `LEAVE()`。`LEAVE()` 做两件事（注意顺序）：先 `DetachCurrentThread` 解绑当前线程，成功与否都继续——然后无条件 `DestroyJavaVM` 销毁 JVM 然后在 `DestroyJavaVM` 体内 `return ret`。解绑失败只是打印错误（`ret = 1`），不影响 JVM 销毁——资源总要释放。

这就是为什么 `CHECK_EXCEPTION_LEAVE` 不直接 `return n`：`return` 只退函数不清理 JVM。所有退出必须走 `LEAVE()` 统一清理路径。

## 设计权衡

**为什么用宏 `LEAVE()` 而不是直接 `return`？** JavaMain 有 7 个退出点（`-version`、`--list-modules`、`-help`、`dry-run`、异常等），每个退出点都需要做相同的清理：`DetachCurrentThread`（解绑当前线程）和 `DestroyJavaVM`（销毁 JVM 实例）。如果每个 `return` 前面都手写这两行，迟早漏一个。`LEAVE()` 宏把清理逻辑集中到一个名字——任何路径想退出就写 `LEAVE()`，漏了 cleanup 的问题不存在。

**为什么特殊模式（`-version` 等）要在 `PostJVMInit` 之前处理？** `PostJVMInit` 会启动 AWT 事件线程等平台初始化——`java -version` 不需要这些。把快速通道放在最前面，`-version` 和 `--list-modules` 可以在 JVM 刚创建完、还没加载用户类之前就拿到结果并退出，启动延迟降到最低。

**为什么 ch02 只讲 5 个阶段就停？** 后 5 个阶段（`LoadMainClass` → `CallStaticVoidMethod`）全是 JNI 调用——它们看起来简单（`GetStaticMethodID` 一个函数调用），但背后依赖类加载器、类型系统、方法解析——这些都在 `JNI_CreateJavaVM` 内部。先深入 JVM 初始化，理解这些基础设施怎么建起来的，再回头看 JNI 调用才有意义。顺序不能倒。

## 本章总结

`JavaMain` 只做了一半——10 个阶段里我们走了前 5 个。核心是第 2 阶段：

```c
r = ifn->CreateJavaVM(pvm, (void**)penv, &args);
```

第一章 `dlopen` + `dlsym` 拿到的函数指针，在这一行被真正调用。`InitializeJVM` 传入了 `options`（JLI_Launch 各步填充的选项数组），JVM 创建成功后 `*vm` 和 `*penv` 指向可用的 JVM 实例和 JNI 环境。

`CHECK_EXCEPTION_LEAVE(n)` 检查 `env` 里有没有挂起的 JNI 异常——有则设置返回码 `n` 并清理退出。`LEAVE()` 做三件事：`DetachCurrentThread`（从 JVM 解绑当前线程）、`DestroyJavaVM`（销毁 JVM 实例）、返回。这解释了为什么特殊的 if 分支调 `LEAVE()` 后不会继续执行。

## 为什么停在这里

阶段 6-10——`LoadMainClass`、`GetStaticMethodID`、`CallStaticVoidMethod`——全是 JNI 调用，依赖 JVM 内部已经建好的类加载器和类型系统。不先搞懂 `JNI_CreateJavaVM` 内部做了什么（`Threads::create_vm` → `init_globals` → `universe_init` → 类加载器初始化 → 类型系统建立），这些 JNI 调用就是黑盒。

所以先深入 JVM 初始化流程，走完 `JNI_CreateJavaVM` → `JNI_CreateJavaVM_inner` → 整个 Vol 1 的核心，再回到 `JavaMain` 的后半段。

