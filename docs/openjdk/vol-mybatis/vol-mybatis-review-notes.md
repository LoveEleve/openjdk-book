## ② 因果审

跨篇主线成立：

- `M-1 -> M-2`：`Configuration` 元数据中心是 mapper 调用协议的前提。
- `M-2 -> M-3`：Mapper 方法进入 `SqlSession` 后，才谈得上事务与资源责任边界。
- `M-3 -> M-4`：会话/事务责任进一步落到执行链与 JDBC。
- `M-4 -> M-5`：执行链里的本地缓存与共享缓存被单独收束为一致性专题。
- `M-4 -> M-6`：执行链里已经出现的 `BoundSql` / 插件入口被单独收束为动态 SQL 与插件专题。
- `M-6 -> M-7`：参数绑定之后，进入类型语义与对象图装配语义。
- `M-7 -> M-8`：对象图装配之后，进一步讨论增量结果消费的协议边界。
- `M-8 -> M-9`：结果消费层收束后，回到 XML/注解/provider 双入口如何并流。
- `M-9 -> S-1`：MyBatis 核心注册主线进入 Spring 会话/事务桥。
- `S-1 -> S-2`：Boot 装配桥自动装起 `S-1` 已建立的责任桥。

未发现因果回环。`S-2` 也没有反向改写 `S-1`，而是建立在其之上。

## ③ 结构审

卷级结构目前为：

- A. MyBatis 核心主干层：`M-1 ~ M-5`
- B. MyBatis 机制补深层：`M-6 ~ M-9`
- C. Spring 集成层：`S-1`
- D. Boot 装配层：`S-2`

这个结构与方法论要求一致：先主干，再补深，再集成，再装配。

## ⑤ 边界审

边界总体清晰：

- `M-1` 只立配置启动协议，不重写 mapper 代理。
- `M-2` 只立接口调用协议，不重写会话生命周期。
- `M-3` 只立会话/事务责任，不吞掉执行器细节。
- `M-4` 只立执行协议，不把缓存、动态 SQL、类型系统完整展开。
- `M-5` 只讨论一致性边界，不把 `cursor_cache_oom` 展开成 Cursor 专题。
- `M-6` 只讨论动态 SQL 与插件协议，不吞掉类型系统。
- `M-7` 只讨论对象图装配，不把 Cursor 生命周期和 Spring 集成提前透支。
- `M-8` 只讨论增量消费协议，不把缓存或结果装配重写一遍。
- `M-9` 只讨论双入口并流，不展开 Spring 扫描与 Boot 装配。
- `S-1` 只讨论会话责任重分配，不重写 Boot 自动装配。
- `S-2` 只讨论装配桥，不重写 MyBatis 核心与 Spring 事务桥。

## ⑥ 依赖审

- 依赖方向总体单向：核心 -> 补深 -> Spring -> Boot。
- `S-1` 依赖 `M-3`（原生会话/事务边界）与 `M-9`（mapper 注册主线），这点合理。
- `S-2` 依赖 `S-1`，说明 Boot 装配桥不是新模型，而是自动装起既有责任桥。
- 未发现跨层回环或同一机制被两层抢主线的情况。

## 当前仍缺的卷级补层

按方法论，“完整卷”还应补生产层。本卷已识别但尚未开写的候选包括：

1. `cursor_cache_oom`：大结果集与嵌套结果映射的内存边界
2. `blocking_cache`：二级缓存阻塞锁与一致性排障
3. `BatchExecutor`：部分成功后整批回滚的异常收束边界
4. `ResultLoader` / `lazy_properties`：懒加载线程与生命周期边界

因此当前卷级结论只能是“主干与集成层阶段性收口”，不是“所有实践层面都已覆盖”。
