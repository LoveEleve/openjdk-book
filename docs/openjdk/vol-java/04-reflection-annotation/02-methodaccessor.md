## 反射慢的真相,在 MethodAccessor 里

"反射为什么慢"是面试必问——但大多数答案停在"反射有额外开销"的笼统层面。`method.invoke(obj, args)` 一行代码,实际走的是**三层 MethodAccessor 的动态切换**: 先 Delegating 转发、native 调 15 次、然后 JVM 现场生成字节码替换。字段访问则是另一条路——Unsafe 按偏移直读。

这篇把 invoke 的完整链路、膨胀阈值、字段访问器体系和反射性能的代价清单一次讲透。

## 1. "invoke 的完整链路" — Delegating → Native → Generated 三层

### 1.1 Method.invoke 的三步

`Method.invoke`(`Method.java:552-567`):

```java
// Method.java:552-567(截取核心,逐字)
public Object invoke(Object obj, Object... args)
    throws IllegalAccessException, IllegalArgumentException,
       InvocationTargetException
{
    if (!override) {
        Class<?> caller = Reflection.getCallerClass();
        checkAccess(caller, clazz,
                    Modifier.isStatic(modifiers) ? null : obj.getClass(),
                    modifiers);
    }
    MethodAccessor ma = methodAccessor;             // read volatile
    if (ma == null) {
        ma = acquireMethodAccessor();
    }
    return ma.invoke(obj, args);
}
```

三步: **① 可见性检查**(`!override` 时每次 checkAccess,`Method.java:556-561`)→ **② 读 volatile `methodAccessor`**(`Method.java:562`,未初始化走 `acquireMethodAccessor`@`Method.java:623`)→ **③ 交给 accessor 执行**(`Method.java:566`)。真正的调用逻辑全在 accessor 里。

### 1.2 三层结构

`acquireMethodAccessor` 最终走到 `ReflectionFactory.newMethodAccessor`(`ReflectionFactory.java:189`),默认路径(`ReflectionFactory.java:212-217`):

```java
// ReflectionFactory.java:212-217(截取核心,逐字)
NativeMethodAccessorImpl acc =
    new NativeMethodAccessorImpl(method);
DelegatingMethodAccessorImpl res =
    new DelegatingMethodAccessorImpl(acc);
acc.setParent(res);
return res;
```

产生三层结构:

```
Method.methodAccessor ──> DelegatingMethodAccessorImpl(纯转发)
                              └──> NativeMethodAccessorImpl(JNI native 调用)
                                     └──(超过阈值后)──> GeneratedMethodAccessor(生成字节码)
```

- **第一层 Delegating**(`DelegatingMethodAccessorImpl.java:33`):纯转发——`invoke` 就是把参数传给 delegate(`DelegatingMethodAccessorImpl.java:40-44`),`setDelegate`(`DelegatingMethodAccessorImpl.java:46`)可以换掉底层实现
- **第二层 Native**(`NativeMethodAccessorImpl`):走 **JNI native 调用**——有 JNI 边界开销(参数转换、JNI 封装)
- **第三层 Generated**:JVM **运行时生成的字节码类**,直接调用目标方法——无 JNI 边界

### 1.3 为什么垫一层 Delegating

关键在"**运行时换实现**": 启动时 native 慢但生成快(不用现场写字节码),热身后把 delegate 换成生成的字节码类。**委托层让切换对 `Method.invoke` 完全透明**——调用方拿到的 accessor 引用不变,底层实现悄悄换掉。

关键设计(斜体):*Delegating 垫层是"策略可替换"的经典结构——invoke 的调用方永远只面对 Delegating 一个入口,底层的 native/字节码切换是内部事务。面试答"反射调用是三层: 委托、native、生成字节码"是入门;能说出"委托层是为了运行时无感切换实现"才是真懂。*

跨层标注: [内部卷: 27-jni(JNI 调用边界与 call_stub);native 慢的根源: 参数 boxing 检查 + JNI 封装]

## 2. "多少次要膨胀" — inflationThreshold 与计数器

### 2.1 阈值:第 16 次起换实现

`NativeMethodAccessorImpl.invoke`(`NativeMethodAccessorImpl.java:45-60`)的膨胀判断:

```java
// NativeMethodAccessorImpl.java:45-60(截取核心,逐字)
public Object invoke(Object obj, Object[] args)
    throws IllegalArgumentException, InvocationTargetException
{
    // We can't inflate methods belonging to vm-anonymous classes because
    // that kind of class can't be referred to by name, hence can't be
    // found from the generated bytecode.
    if (++numInvocations > ReflectionFactory.inflationThreshold()
            && !ReflectUtil.isVMAnonymousClass(method.getDeclaringClass())) {
        MethodAccessorImpl acc = (MethodAccessorImpl)
            new MethodAccessorGenerator().
                generateMethod(method.getDeclaringClass(),
                               method.getName(),
                               method.getParameterTypes(),
                               method.getReturnType(),
                               method.getExceptionTypes(),
                               method.getModifiers());
        parent.setDelegate(acc);
    }
    ...
```

- 计数器 `numInvocations`(`NativeMethodAccessorImpl.java:37`)每次 invoke 递增
- 超过阈值(`inflationThreshold`,`ReflectionFactory.java:88` 的 **15**)→ `MethodAccessorGenerator.generateMethod` 现场生成字节码 → `parent.setDelegate(acc)`——**delegate 被换成生成的实现,之后每次调用都走字节码**
- **vm-anonymous 例外**:注释说明(`NativeMethodAccessorImpl.java:48-50`)——vm 匿名类(如 lambda 生成的类)无法被字节码按名引用,永远不膨胀

### 2.2 阈值可调与跳过路径

`ReflectionFactory` 的两个开关:

- `-Dsun.reflect.inflationThreshold=N`:调整阈值(读取在 `ReflectionFactory.java:707` 附近)
- `-Dsun.reflect.noInflation=true`:**完全跳过 native 期**(`ReflectionFactory.java:87` 的 `noInflation` 标志)——`newMethodAccessor` 直接走 `generateMethod`(`ReflectionFactory.java:205-207`),首次调用就是字节码

### 2.3 生成器:手工构造 class 文件

`MethodAccessorGenerator`(`jdk/internal/reflect/MethodAccessorGenerator.java:39`)的 `generateMethod`(`MethodAccessorGenerator.java:68`)/`generateConstructor`(87 行)用 `ByteVector`/`ConstantPool` 等工具**手工组装一个 class 文件的字节**(每个被反射的方法生成一个类,比如 `GeneratedMethodAccessor1`),加载后实例化替换 delegate。类比: 这就是 ASM 等字节码库做的事情,只不过 JDK 自己写了一份。

关键设计(斜体):*15 次的取舍是"生成成本 vs native 成本"的平衡: 反射调用少(≤15 次),native 的 JNI 开销可接受,不值得付生成成本;调用多,生成字节码的摊薄收益超过生成成本。注意"生成类只包含本方法"——每方法一个类,类加载本身有成本,这就是阈值存在的意义。*

## 3. "字段访问也是生成的吗" — FieldAccessor 与 Unsafe 直读

### 3.1 不是——字段走另一条路

方法调用有字节码生成路径,**字段访问没有**。`Field` 的 accessor(`Field.java:81-83` 的 `fieldAccessor`/`overrideFieldAccessor`)由 `ReflectionFactory.newFieldAccessor` 创建,实际工厂在 `UnsafeFieldAccessorFactory`(`UnsafeFieldAccessorFactory.java:31`):

```java
// UnsafeFieldAccessorFactory.java:32
static FieldAccessor newFieldAccessor(Field field, boolean override) {
```

### 3.2 访问器:清一色 Unsafe 直读

字段访问器(`jdk/internal/reflect/` 下,共 41 个文件)其实**只有 Unsafe 一族**: `FieldAccessorImpl` 是抽象基类,40 个 `Unsafe*FieldAccessorImpl` 子类分三组——实例字段(UnsafeIntegerFieldAccessorImpl 等,每类型一个)、静态字段(UnsafeStatic* 系列)、qualified 版本(UnsafeQualified*,处理模块强封装检查)。核心机制完全一致(`UnsafeFieldAccessorImpl.java:51` 实测):

```java
// UnsafeFieldAccessorImpl.java:51(截取核心,逐字)
fieldOffset = unsafe.objectFieldOffset(field);
```

**用 `objectFieldOffset` 拿到字段在对象里的偏移,按类型 `unsafe.getInt(obj, offset)` 直读内存**——没有 JNI 边界、没有访问检查。

**这就是字段访问比方法调用快的原因**: 方法要走 accessor 三层/生成字节码,字段直接算偏移 + 一次内存读。

### 3.3 setAccessible 与 override 分支

`Field.getFieldAccessor`(`Field.java:1081-1085`)按 `override` 标志选 accessor:

```java
// Field.java:1081-1085(截取核心,逐字)
private FieldAccessor getFieldAccessor(Object obj)
    throws IllegalAccessException
{
    boolean ov = override;
    FieldAccessor a = (ov) ? overrideFieldAccessor : fieldAccessor;
    return (a != null) ? a : acquireFieldAccessor(ov);
}
```

`setAccessible(true)` 后 `override=true` → 走 `overrideFieldAccessor` 分支——**跳过访问检查**。这就是"setAccessible 提高反射性能"的机制: 不仅省掉 invoke 里的 checkAccess,字段路径直接走 Unsafe 直读。

关键设计(斜体):*方法走"生成字节码"、字段走"Unsafe 偏移"——两条优化路线的取舍: 字节码生成慢启动快运行,Unsafe 偏移启动快但受模块强封装限制(域 32 展开)。面试答"为什么 setAccessible(true) 后反射变快": 方法省 checkAccess、字段换 override 分支直读——两个机制都说到才完整。*

## 4. "invoke 的代价清单" — 反射性能全景

### 4.1 四类成本

| 成本 | 说明 | 能否优化 |
|------|------|---------|
| ① 可见性检查 | `!override` 时每次 checkAccess(调用者/类/模块链) | setAccessible(true) 跳过 |
| ② 参数 boxing/数组展开 | Object[] args 的装箱拆箱、变长参数包装 | 无法避免(反射契约) |
| ③ 方法分派 | 生成前:JNI 边界;生成后:字节码直接 call | 阈值/膨胀机制 |
| ④ 异常包装 | 目标方法异常包成 InvocationTargetException | 无法避免(反射契约) |

### 4.2 优化三板斧

- **缓存 Method/Field 对象**:省掉"每次 getMethod 新建对象"(01 篇的 ②)
- **setAccessible(true)**:省掉 ① 的每次检查
- **批量调用摊薄膨胀成本**:热路径上一次反射调用上万次,膨胀成本被摊薄——框架里的反射调用几乎都超过 15 次阈值,实际走的是生成字节码路径

Spring 的 ResolvableType、MyBatis 的 MetaClass 都是这个思路: 缓存成员对象 + setAccessible + 高频调用吃膨胀红利。

关键设计(斜体):*"反射慢 vs 直接调用差多少"——生成字节码后差距在一个数量级内;真正慢的是 boxing、可见性检查、以及阈值前的 native 调用。面试答"反射慢"的四项成本清单 + 三板斧优化,就比"反射慢因为动态"高一档。*
