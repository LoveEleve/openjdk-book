# 泛型擦除、原始类型与数组协变：为什么编译时很严格，运行时却"啥都不剩"

> 基于 JDK 11 `java.util.ArrayList`、`java.lang.reflect.Array`、`java.lang.ArrayStoreException` 与 JLS 的类型擦除规则。本文讨论的是泛型的擦除机制、原始类型为什么会保留在那里，以及数组协变为什么需要运行时 `ArrayStoreException` 兜底。擦除规则属于 JLS 语言规范；`ArrayList` 内部用 `Object[]`、`Array.newInstance` 反射建组、`ArrayStoreException` 的运行时检查都是 JDK 11 可观测事实。

## 先看两个都叫"类型"，命运却完全相反的输入

你写了一个泛型容器：

```java
List<String> list = new ArrayList<>();
```

编译期它非常严格：往里面塞 `Integer` 会直接报错。可一旦编译完成，运行时的 `ArrayList` 里只是一个 `Object[]`（`ArrayList.java:136` 的 `transient Object[] elementData`），`String` 这个类型参数已经不见了。同一个 `List<String>`，编译时严格、运行时无痕。

再看数组：

```java
Object[] arr = new String[3];   // 编译期允许
arr[0] = 42;                    // 运行期抛 ArrayStoreException
```

这里反过来：赋值给 `Object[]` 编译期放行了，结果跑到运行期才爆异常。同样是"类型"，泛型选择在编译期严格、运行时擦除；数组选择在编译期宽松、运行时检查。

这两个现象背后是同一个设计矛盾：**Java 想在编译期给出强类型保证，又必须兼容"字节码里没有泛型"的遗产。** 于是它把两种不同的职责分别发给两个阶段。把它们混成"为什么编译这么严格/这么宽松"，就会同时误解泛型擦除和数组协变。

这里至少有三个失败方案。

第一种失败方案，是把"泛型擦除"理解成"泛型没用"。擦除不是说运行时彻底没有类型信息，而是说**字节码层面的容器不携带类型参数**；编译期的一切检查仍然有效，跨类型的错误在编译期就被拦住了。

第二种失败方案，是把"原始类型能编译过"当成"应该用"。`List list = new ArrayList();` 能跑，是因为擦除后它就是 `Object` 列表；但用原始类型等于自己把编译期检查关掉，把"类型安全"倒退成"全是 `Object`、塞进去全靠小心"。

第三种失败方案，是以为数组和泛型"道理一样"所以协变规则也该一样。数组天生协变（`String[]` 是 `Object[]` 的子类型），泛型天生不变（`List<String>` 不是 `List<Object>` 的子类型）。把两者搅在一起，会完全看不懂为什么要 `ArrayStoreException`、为什么不能写 `new T[]`。

所以这三个失败方案指向同一个顿悟：**Java 的类型系统把"编译期保证"和"运行时表示"拆开卖。泛型把安全押在编译期，运行期擦除为 Object；数组把安全押在运行时，编译期用协变换灵活。两条路线都要用运行时检查来兜底，只是兜底点不同。**

## 一、泛型擦除：编译期的安全检查在哪儿消失

### 字节码里没有 `<String>`

`ArrayList<String>` 编译后，`elementData` 是 `Object[]`，不是 `String[]`（`ArrayList.java:136`）。插入元素时，`add` 的签名擦除成 `add(Object)`，编译器在调用点做检查：你传的必须是 `Object`，而 `String` 满足，`Integer` 在编译期就过不了。

取出元素时，`get` 返回 `Object`，编译器在调用点插入一个隐式强转，把 `Object` 转回 `String`。所以 `String s = list.get(0)` 编译后其实是 `String s = (String) list.get(0)`。

这就是"擦除"的全部含义：**类型参数只活在编译期，用于做检查；进入字节码时被换成边界 `Object` 或边界类型。** 运行时没有 `List<String>` 与 `List<Integer>` 的区分，它们塞进同一个类加载器时是同一个类。

### 擦除为什么没有让安全性崩塌

有人会担心：既然运行时没类型参数，那 `cast` 不是可能失败吗？确实可能——但失败点是"取出来当 String 用"的那一行，而不是"塞进去"的那一行。你没法把一个 `Integer` 塞进 `List<String>`（编译期检查拦住），所以运行时取出来再做强转时，理论上只可能强转本来正确的 `String`。

真正会崩的情况，只有你用原始类型或 `@SuppressWarnings` 把检查关掉了——那时候运行时强转才可能失败。所以擦除本身不制造类型安全漏洞，漏洞来自"绕过编译期检查"的人。

## 二、原始类型：为什么它还在，又为什么该躲着走

### 原始类型是"擦除后的样子"，保留是为了兼容

`List`（不带泛型参数）叫原始类型，它就是 `List` 擦除后的样子：一个接收并返回 `Object` 的容器。JDK 保留它，是为了让泛型引入之前的旧代码（`new ArrayList()`）能继续编译运行。

编译器对原始类型的态度是：**允许你用它，但只要你用了，这个容器相关的泛型检查就全部失效。** 你往 `List` 里塞什么类型编译器都不拦，取出来时它是 `Object`，需要你手动强转。

### 混用原始类型和参数化类型的危险

真正危险的是混用：

```java
List<String> strings = new ArrayList<>();
List raw = strings;              // 允许，但绕过了检查
raw.add(42);                     // 编译期不报错
String s = strings.get(0);       // 运行期 ClassCastException: Integer 不能转 String
```

问题不在原始类型本身，而在用原始类型 **引用** 一个原本是参数化的对象，等于把编译期已经建立的安全边界重新撕开。这条边界不该被当作"更方便的写法"。

到这里，泛型的擦除机制和原始类型已经讲清了。接下来这一节讲的是和泛型"完全相反"的另一条设计路线——数组。它和泛型的选择几乎对称：一个在编译期死守，一个在运行时检查。

## 三、数组协变：为什么 `String[]` 能当 `Object[]`，然后又翻车

### 数组的协变是一笔"编译期宽松、运行时检查"的交易

数组是协变的：`String[]` 是 `Object[]` 的子类型，所以 `Object[] arr = new String[3]` 在编译期就被接受。泛型不是：`List<String>` 与 `List<Object>` 没有子类型关系，`List<Object> = List<String>` 编译期报错。

为什么数组敢协变而泛型不敢？因为数组记住了自己的**运行时组件类型**。你写的 `arr` 静态类型是 `Object[]`，但它运行时知道自己真的是 `String[]`。于是当你要往里放东西时，JVM 会检查这个元素能不能塞进"实际"的组件类型——塞不下就抛 `ArrayStoreException`。

```java
Object[] arr = new String[3];
arr[0] = 42;   // 运行时检查：实际组件类型是 String，42 不是 → ArrayStoreException
```

### 这个检查和泛型强转是同一种兜底的不同位置

如果把数组和泛型并排看：

```text
泛型
  → 编译期拦截跨类型赋值
  → 运行期把取出的 Object 强转回目标类型

数组
  → 编译期允许父类引用指向子类数组（协变）
  → 运行期检查塞入的元素是否符合实际组件类型
```

两条路线都在"编译期不可能全知"的地方补了运行时检查。泛型补的是"取出时的强转"，数组补的是"塞入时的组件检查"。明白这一点，就明白为什么 `new T[]` 写不了，也明白为什么 `ArrayList` 只能内部用 `Object[]` 在外面再强转到 `T`。

## 四、`new T[]` 为什么写不了：泛型创建数组撞上了运行时表示

### 矛盾的根源

`T` 在运行时不知道自己的确切类型（擦除了），而数组在运行时**必须**知道自己的组件类型（要用于 `ArrayStoreException` 检查）。于是"以 `T` 为组件类型建数组"这句话，在运行时无解——`T` 已经没了，怎么知道组件类型？

所以 JDK 的 `ArrayList` 不走 `new T[]`，而是在 `elementData` 存 `Object[]`，外面取时再强转（`ArrayList.java:136`）。

### 真要在运行时建泛型数组怎么办：`Array.newInstance`

JLS 禁的是 `new T[]` 这种语法，但你绕到反射层仍然能建——只要组件类型在运行时是已知的：

```java
// Array.java:76
Object arr = Array.newInstance(Integer.class, 3);
```

`Array.newInstance(Class<?> componentType, int length)` 接收一个运行时确定的组件类型，返回一个 `Object`（运行时才真正是 `Integer[]`）。它就是"运行时才知道组件类型"时建数组的合法入口，也是把"泛型擦除"和"数组需要组件类型"两个矛盾在特定场景下能对上的桥。

## 五个最容易混掉的边界：擦除不是"没用"，原始类型不是"更方便"，数组协变不是"漏洞"，new T[] 不是"编译器偷懒"，运行时检查两次不是同一处

第一，擦除不是"泛型没用"。它只是把类型参数的主场限定在编译期；反射时虽然看不到 `String`，但编译期的所有拦截照常生效。泛型把安全押在了你写代码的那一刻。

第二，原始类型不是"更方便的写法"。它是旧代码兼容的尾巴，一旦用它引用参数化对象，就把编译期检查关掉了；安全的假象远大于它带来的便利。

第三，数组协变不是"类型系统的漏洞"。它是"编译期宽松、运行时检查"的交易；`String[]` 假装成 `Object[]` 时，JVM 记住的是真实组件类型，塞错元素会抛 `ArrayStoreException`，安全并没丢失，只是兜底点不同。

第四，`new T[]` 写不了，不是编译器偷懒。它在运行时无解：`T` 已擦除，而数组必须知道组件类型。要运行时建，走 `Array.newInstance`，传入运行时已知的 `Class`。

第五，泛型的运行期强转和数组的 `ArrayStoreException` 不是同一处兜底。前者查"取出时是不是目标类型"，后者查"塞入时是不是实际组件类型"；两者都是编译期不可能全知后的补充，但位置完全不同。

把这五条边界记稳，泛型和数组就不会再被简化成"编译时严格 / 运行时不严"的一刀切。它们真正想讲的是：Java 的类型系统把保证拆碎了——泛型把安全放在编译期的签名检查，数组把安全放在运行期的组件检查，而擦除、原始类型、`new T[]` 的种种"奇怪"，都是这两套规则在字节码兼容约束下相遇的结果。

## 收网：编译期和运行时各守一段，泛型与数组只是选择不同

回到开头两个现象，现在能看清它们的共同设计了。

`List<String>` 编译时拦截一切跨类型，运行时 `elementData` 只是 `Object[]`；安全由编译期检查 + 取出时的隐式强转双重承担。`String[]` 被赋给 `Object[]` 编译期放行，安全性由运行时 `ArrayStoreException` 兜住。两者都不是"类型检查失效"，而是把检查放在了不同的环节。

把整篇压成一张总图：

```text
泛型
  → 编译期：List<String> 拦 Integer
  → 运行时：擦除为 Object[] / add(Object) / get 隐式强转
  → 原始类型：关掉检查的兼容尾巴
  → new T[]：T 已擦除，运行时不知道组件类型，走 Array.newInstance

数组
  → 编译期：String[] 是 Object[] 子类型（协变）
  → 运行时：检查塞入元素是否匹配真实组件类型
  → 不匹配抛 ArrayStoreException
```

所以当你再看到`泛型擦除`、`原始类型`、`数组协变`这些词时，真正该记住的是：Java 只在字节码里保留了最保守的表示，而把"你写的是不是对的"这句判断，一部分留给了编译期签名，一部分留给了运行时的强转和数组组件检查。两条规则各管一段，加起来才构成它表面上的"有时严格、有时宽松"。
