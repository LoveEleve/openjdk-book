# 方法重载、重写与桥接方法：为什么你写的两个方法，在编译器和 JVM 眼里可能不是同一个

> 基于 JDK 11 `java.lang.Comparable`、`java.lang.reflect.Method` 与 JLS 的方法分派规则。本文讨论的是重载（Overload）与重写（Override）的判别陷阱，以及泛型擦除后 javac 生成桥接方法（bridge method）的机制。方法重载的选择规则属于 JLS 语言规范，桥接方法的存在可以用 JDK 11 的 `Method.isBridge()` 观测，但桥接方法本身由 javac 生成、不是 JDK 运行时的 Java 源码。

> → **后续**：泛型擦除与原始类型

## 先看两个会让你觉得"编译器疯了"的场景

第一个场景出现在重载歧义上：

```java
void doIt(String s) { ... }
void doIt(Integer i) { ... }
```

调 `doIt(null)`，编译器上报错："ambiguous"。你心想，`null` 不是既能当 String 也能当 Integer 吗？为什么要我选。如果把其中一个 `Integer` 换成 `Object`，也就是 `doIt(String)` 和 `doIt(Object)`，`doIt(null)` 反倒不报错了——因为 JLS 会选更具体的 String。所以歧义并不是"多个方法都能接 null 就歧义"，而是"多个方法都能接 null、且没有任何一个比另一个更具体"时才歧义。

第二个场景出现在泛型实现上：

```java
class Box implements Comparable<Box> {
    public int compareTo(Box o) { ... }
}
```

你只写了一个方法，用 `javap -p` 一查，发现类里居然有两个 `compareTo`：一个是你写的 `compareTo(Box)`，另一个是 `compareTo(Object)`——你没写过它，它却躺在字节码里。

这两个现象表面上都在"方法"上做文章，背后却是两种完全不同的分派机制。把它们混成"重写/重载是一回事"，就会在面试和排障时同时翻车。

这里至少有三个失败方案。

第一种失败方案，是把"重载"和"重写"当成同一个概念的两个名字。实际它们站在完全不同的边界上：重载是同一类里的编译期选择，重写是继承体系里的运行期分派。把 `overload` 记成"方法名相同"、`override` 也记成"方法名相同"，就丢失了两者真正差异所在。

第二种失败方案，是用"返回值能否区分"去判断重载。很多人以为 `int f()` 和 `String f()` 可以共存，因为它们"返回类型不同"。但选项优先级里还说"返回值不参与重载的判别"——两个方法参数列表相同、只有返回值不同，编译器直接报错，因为它在调用点根本不知道该选哪个。

第三种失败方案，是以为"我只写了一个方法，类里就一定只有一个方法"。泛型擦除后 javac 会偷偷生成桥接方法，这正是 `compareTo(Box)` 的类里出现 `compareTo(Object)` 的原因。以为"没写过就不存在"，会在反射遍历 `getMethods()`、或看序列化/代理生成时百思不得其解。

所以这三个失败方案指向同一个顿悟：**重载对编译器负责"这一次调用选哪个签名"，重写对运行时负责"这一次调用进哪个实现"，桥接方法对字节码负责"泛型擦除后的签名兼容"——三者是三层不同的问题，各自有各自的规则。**

## 一、重载：编译期的静态选择，规则只在"签名"上

### 重载的本质是"同一名字、多份签名"

重载发生在同一个类（或同一条继承链上能见到的多个方法）里：方法名相同，参数列表不同。选择发生在编译期，编译器在调用点根据实参类型，在可见的重载集合里挑一个签名。

这里的两个硬规则：

- 参数列表（个数、类型、顺序）是重载判别的唯一依据
- 返回值不参与重载判别，所以 `int f()` 和 `String f()` 不能共存

### null 为什么造成"ambiguous"

`null` 对重载选择是一个特殊输入：它不需要转换，就能匹配任何引用类型。于是当两个方法都能接受 `null` 时，编译器需要判断哪一个"更具体"——也就是谁的参数类型是另一个的子类型。`doIt(String)` 与 `doIt(Object)` 之间，String 是 Object 的子类，编译器能建立偏序，选 String，不报错。`doIt(String)` 与 `doIt(Integer)` 之间，String 和 Integer 互不为子类，编译器无法建立偏序，于是报 ambiguous。

要记住的是：**歧义不是"两个都能接住"，而是"两个都不能证明自己比对方更该被选"。** 编译器不会违背模糊/具体关系去猜，宁可让你显式转型。

## 二、重写：继承体系里的运行期分派

### 重写不是"签名相同就行"

重写发生在子类里：方法名相同、参数列表相同、返回类型相同或协变。它不是"想覆盖就能覆盖"，有几个边界必须同时满足：

- 方法必须是非 `static`、非 `private`、非 `final` 的（`static` 是隐藏不是重写，`private` 对子类不可见，`final` 禁止覆盖）
- 覆盖方法的访问权限不能缩小（`protected` 不能被覆盖成 `private`）
- 覆盖方法不能抛出比原方法更宽泛的 checked 异常

### 运行时分的不是"签名"，而是"实现"

重写发生在运行期：调 `obj.method()` 时，JVM 根据 `obj` 的实际类型决定走进哪个实现。这正是多态的核心——你写的是父类引用，实际跑的是子类版本。

这也解释了为什么重载和重写经常被混掉：同一处 `obj.doIt(...)` 的代码，参数是编译期选签名的（重载），对象是谁决定实现（重写）。两个阶段一前一后、互相独立。

到这里，两层分派已经讲清了：重载是编译期、重写是运行期。接下来这一层和前两层都不一样，它发生在字节码层面，而且**不是你写的代码**——是 javac 替你生成的桥接方法。

## 三、桥接方法：泛型擦除后，javac 替你补上的"翻译层"

### 泛型接口擦除后会出现什么

看 JDK 11 的 `Comparable`：

```java
// Comparable.java:96
public interface Comparable<T> {
    public int compareTo(T o);
}
```

`T` 有界时擦除为边界类型，无界时擦除为 `Object`。所以 `Comparable<T>.compareTo(T)` 编译后签名为 `compareTo(Object)`。

你在实现类里写：

```java
class Box implements Comparable<Box> {
    public int compareTo(Box o) { ... }
}
```

这个方法的参数是 `Box`，不是 `Object`。于是出现一个事实错位：接口要求（擦除后的）`compareTo(Object)`，而你只提供了 `compareTo(Box)`。如果不做处理，反射和某些调用路径会认为你没有完整实现接口。

### javac 的答案：生成桥接方法

javac 在编译 `Box` 时会自动生成一个额外的方法，它的签名是接口擦除后的那个 `compareTo(Object)`：

```text
public int compareTo(Object o) {
    return compareTo((Box) o);   // 桥接：转发给真正实现
}
```

这个自动生成的方法就是桥接方法（bridge method）。它保证两点：第一，字节码层面"接口签名"真实存在，反射/序列化/代理能正确找到它；第二，它转发给子类真正的重写实现，不改变运行期的多态语义。

### 怎么"看到"它：JDK 11 的反射观测

JDK 11 的 `Method.isBridge()`（`java.lang.reflect.Method.java:577`）就是专门标记这些合成方法的入口：

- 真身方法是子类自己写的 `compareTo(Box)`
- 桥接方法是 javac 生成的 `compareTo(Object)`，`isBridge()` 返回 true

所以当你遍历某个类的 `getMethods()` 时，看到的"多出来的方法"不是 bug，而是 javac 为泛型擦除做的签名兼容补充。它也在协变返回类型（子类覆盖时把返回类型变窄）时出现，作用是让字节码层面的"父签名"和"子签名"同时成立。

## 五个最容易混掉的边界：重载不是重写，返回值不参与重载，static 没有重写只有隐藏，桥接不是你自己写的重载，isBridge 不是"坏方法"标记

第一，重载不是重写。重载是编译期在同一名字下选签名，重写是运行期在继承体系里选实现；前者看参数列表，后者看实际对象类型。

第二，返回值不参与重载判别。`int f()` 与 `String f()` 参数相同则不能共存，编译器在调用点无法决定选哪个，直接报错。

第三，`static` 方法没有"重写"，只有"隐藏"。子类声明同签名的 static 方法会隐藏父类方法，但调用哪个由静态类型决定，不进入运行期多态行为。

第四，桥接方法不是你写的重载。它是 javac 在泛型擦除后自动生成的签名翻译层，参数可能叫 `Object`，看起来像重载，实际只是把擦除签名转发给真身实现。

第五，`isBridge()` 不是"这个方法是坏的"标记。它表示这是一个由编译器生成的桥，用来协调泛型擦除与接口签名之间的一致；看到桥接方法代表代码经过了泛型实现，而不是有 bug。

把这五条边界记稳，方法分派就不会再被简化成"重载、重写都叫 override"的口语。它真正想讲的是三层分工：编译期选签名（重载）、运行期选实现（重写）、字节码层保签名兼容（桥接）。

## 收网：方法分派是三层各管一摊，不是一句"方法名相同"能概括的

回到开头那个 `null` 报错和那个凭空多出来的 `compareTo(Object)`。

`null` 报错说明：重载的选择发生在编译期，而且依赖"更具体"的偏序；编译器找不到明确更匹配的候选，宁可让你显式转型，也不替你在模糊关系里乱猜。

`compareTo(Object)` 凭空出现说明：泛型擦除后，接口签名的 `compareTo(Object)` 和实现类的 `compareTo(Box)` 必须在字节码层面同时存在，javac 只能生成桥接方法去翻译。

把整篇压成一张总图：

```text
重载（Overload）
  → 同一类内，同名不同参数
  → 编译期按实参选签名
  → 返回值不参与，null 可能 ambiguous

重写（Override）
  → 子类覆盖父类实例方法
  → 运行期按实际类型选实现
  → 非 static/private/final，访问权限与异常有约束

桥接方法（Bridge Method）
  → 泛型擦除后由 javac 生成
  → 把擦除签名转发给真身实现
  → 可用 Method.isBridge() 观测，不是“多出来的 bug”
```

所以当你在代码里"重载"或"重写"一个方法时，你其实同时在跟三条规则打交道：编译器怎么选签名、运行时怎么选实现、字节码怎么补签名兼容。理解它们各自的分工，才不会在 `null` 歧义、返回值报错、反射多出的方法这些地方反复栽跟头。
