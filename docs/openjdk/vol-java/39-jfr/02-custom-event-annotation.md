# 自定义事件与注解：为什么 JFR 事件真正要声明的，不只是字段，而是一份可被录制器和分析器理解的事件 Schema

> 本文基于 JDK 11 `jdk.jfr` 注解体系、`EventType`、`ValueDescriptor`、`EventFactory`。本文聚焦自定义事件类、注解元数据、事件 Schema 与动态事件；字节码注入放到下一篇。
> **前置依赖**：[JFR 全景与事件模型](01-jfr-overview-event-model.md)、[注解模型](../04-reflection-annotation/04-annotation.md)
> **后续**：[字节码增强机制](03-bytecode-instrumentation.md)

## 先看一个很容易写得过于草率的问题：继承了 `Event`，为什么还不等于你已经定义好了一个“好用的 JFR 事件”

上一篇已经把 JFR 的事件协议立住了：`begin/end/commit` 定义了一次事件如何被记录。但如果继续往前走一步，真正的问题马上出现：**录制器和分析工具怎么知道这条事件叫什么、该归到哪个类别、字段代表什么、默认是否启用、阈值如何解释？**

如果这些信息全靠使用者自己猜，那事件就退化成“某个 Java 类里塞了几个字段”。这显然不够。JFR 要的是一条正式事件流，而正式事件流里的每个事件，都必须先被描述成一份可被系统理解的 Schema：

- 字段叫什么；
- 字段类型是什么；
- 事件名字、分类、说明是什么；
- 哪些设置会影响它是否被记录；
- 分析工具该怎样把它展示给人看。

所以自定义 JFR 事件真正要写的，不只是“一个继承了 `Event` 的类”，而是**一份带有元数据的事件声明。** 类和字段给出数据形状，注解补齐录制器和分析器需要的那层语义。

## 一、为什么静态事件真正是“类 + 字段 + 注解”三件套：只有字段还不够，系统还需要知道这些字段是什么意思

### 先看最直接的形状

最常见的自定义事件写法当然还是从类出发：定义一个继承 `Event` 的类，再在里面放字段。这个步骤提供了两样东西：

- 事件有了一个独立类型；
- 事件负载有了具体的数据槽位。

但到这里为止，JFR 仍然只知道“这里有个事件类，里面有若干字段”。如果没有额外元数据，它很难知道：

- 这个事件该怎么展示；
- 字段该用什么名字呈现给人；
- 这个事件默认是否启用；
- 多久触发一次、达到什么阈值才值得记；
- 是否应该自动带上调用栈。

### 为什么注解不是装饰，而是事件声明的一部分

JDK 11 里，和事件声明最直接相关的几个注解入口包括：

- `@Label`：`Label.java:48`
- `@Description`：`Description.java:45`
- `@Name`：`Name.java:46`
- `@Category`：`Category.java:123`
- `@Enabled`：`Enabled.java:45`
- `@Period`：`Period.java:43`
- `@Threshold`：`Threshold.java:44`
- `@StackTrace`：`StackTrace.java:44`

这组注解已经说明，JFR 事件声明从一开始就不是“字段定义完就结束”。你真正交给 JFR 的，是：

- 一份数据结构；
- 一份事件元数据；
- 一组和录制行为直接相关的默认设置。

所以静态事件不是“继承 Event 即可”，而是**类、字段、注解共同组成的一份事件 Schema。**

## 二、为什么这些注解不只是 UI 标签：它们同时在定义“怎么展示”和“怎么记录”

### 先把两类元数据分开

很多人第一次看这些注解，会把它们统统理解成“为了 UI 友好”。这只对了一半。更准确地说，它们分成两类：

- **展示型元数据**：告诉分析工具“怎么让人看懂它”；
- **行为型元数据**：告诉录制器“在什么条件下记它”。

### 展示型元数据为什么很重要

像 `@Label`、`@Description`、`@Category`、`@Name` 这类信息，直接决定事件在工具里如何出现：

- 人看到的显示名是什么；
- 事件被分到哪个类别树下；
- 说明文本怎么展示；
- 名字是否沿用类名，还是显式指定一套更稳定的事件名。

这层元数据如果缺失，工具虽然仍能看到事件，但可读性和可发现性会显著下降。JFR 的目标不是“把数据悄悄写进文件就完”，而是让这些事件最终还能被人类和工具稳定分析。

### 行为型元数据为什么更关键

更容易被忽略的是另一半：`@Enabled`、`@Period`、`@Threshold`、`@StackTrace` 这类注解，已经不只是影响展示，而是在参与录制策略本身。

这意味着：

- 有些注解决定事件默认是否处于开启状态；
- 有些注解决定周期事件的频率语义；
- 有些注解决定低于阈值时根本不值得写；
- 有些注解决定记录时是否额外附带栈信息。

也就是说，JFR 注解不是“漂亮一点的文档注释”，而是**录制器和分析器共同消费的正式元数据。**

## 三、为什么 `EventType` 和 `ValueDescriptor` 才是运行时真正消费的事件 Schema：工具读的不是你的源码，而是这份元模型

### 先看运行时类型入口

JDK 11 里，`EventType` 定义在 `EventType.java:47`。关键方法包括：

- `getFields()`：`EventType.java:62`
- `getName()`：`99`
- `getLabel()`：`112`

这已经足够说明，JFR 在运行时并不是直接拿着某个 Java 源码文件去做分析，而是把事件类收束成了更稳定的事件类型模型：

- 事件名字；
- 事件标签；
- 字段描述列表。

### 为什么这一步比想象中更关键

因为真正写进录制文件、真正被分析工具和消费 API 读取的，不是“某个类本身长什么样”，而是它在运行时投影出来的 Schema。`EventType` 可以被理解成“事件类型的正式定义”，而每个字段则进一步通过 `ValueDescriptor` 这种描述对象被结构化表示出来。

这也就解释了一个非常重要的事实：**JFR 的消费者最终依赖的是事件元模型，而不是你的业务源码。**

所以当我们说“自定义事件要设计好”，真正要设计好的，恰恰是这份会投影成 `EventType` / `ValueDescriptor` 的 Schema。

## 四、为什么静态事件是默认路径：它让事件 Schema 在编译期就稳定下来

### 静态类的最大价值不是简单，而是稳定

一旦事件结构在编译期就能确定，静态类方案几乎总是最自然的：

- 字段是什么一目了然；
- 注解元数据和字段定义写在一起；
- 类型安全更强；
- 维护者不需要在运行时再拼装事件结构。

这意味着多数业务埋点、本地运行行为记录、性能热点事件，最适合的都还是静态事件类。

### 为什么这也让分析链更清晰

静态类方式下，事件声明本身就是一种稳定文档：代码、字段、标签、阈值、分类、是否采栈，都能直接在类定义处被看清。Schema 一旦稳定，录制配置、消费 API、分析工具展示也更容易围绕这份稳定约定工作。

所以静态继承之所以是默认路径，不是因为 JFR 没有更灵活的机制，而是因为**大多数事件结构本来就不该在运行时漂移。**

## 五、为什么 `EventFactory` 不是“更高级的写法”，而是给“运行时结构才确定”的场景准备的动态 Schema 工厂

### 先看动态入口长什么样

JDK 11 里，`EventFactory` 定义在 `EventFactory.java:80`。关键入口包括：

- `create(List<AnnotationElement>, List<ValueDescriptor>)`：`EventFactory.java:120`
- `newEvent()`：`188`

这说明 JFR 并没有把事件定义能力锁死在“必须写 Java 子类”这一条路上。只要你能在运行时提供：

- 事件级注解元素；
- 字段级描述列表；

它就能帮你生成一份新的动态事件类型，并允许你在后面实例化事件对象。

### 为什么这本质上是在运行时生成 Schema

注意这里最关键的不是“能 new 出一个事件”，而是：你必须先把描述事件所需的元数据和字段结构都准备好，工厂才能工作。也就是说，`EventFactory` 不是“省掉 Schema”，而是**把 Schema 的生成时机从编译期推迟到运行时。**

这使它非常适合那些事件结构本来就到运行时才确定的场景，比如：

- 热配置埋点；
- 规则引擎按规则动态决定要记哪些字段；
- 平台工具按用户输入临时拼装事件定义。

### 为什么它不该替代静态类成为默认方案

因为灵活性不是免费的。动态事件意味着：

- 类型安全下降；
- 可读性下降；
- 维护者更难从代码结构上直接看出完整事件定义；
- 事件 Schema 的变更更多发生在运行时而不是编译期。

所以它的定位不该是“更高级”，而是“在结构无法提前确定时的必要兜底”。多数场景里，静态事件仍然更清晰、更稳定、更容易被维护。

## 六、为什么 JFR 自定义事件真正要设计的，是一份能被录制器、配置模板和分析工具共同消费的 Schema

前面几节可以收回到同一个根问题：JFR 不是只想让你“记录点东西”，而是想让这件事能被整个生态链稳定理解。

- 录制器要知道默认是否启用、哪些阈值成立；
- 配置模板要知道事件名字和类别；
- 分析工具要知道字段该怎么展示；
- 消费 API 要知道怎样按字段和类型读取数据；
- 远程或离线分析时，系统不能依赖你业务源码仍然在场。

所以一条自定义事件真正的完成态，不是“代码能 `commit()` 成功”，而是：**这条事件已经被声明成一份完整、稳定、可消费的 Schema。** 这正是注解、`EventType`、`ValueDescriptor` 和 `EventFactory` 这些看似分散的东西最终会汇到一起的原因。

## 收网：自定义 JFR 事件真正要声明的，不只是字段，而是一份可以被记录系统识别、被工具展示、被配置筛选的事件 Schema

现在可以把整篇压成一条主线：

- 继承 `Event` 只解决了“它是一条事件”，没有解决“系统怎样理解它”；
- 静态事件真正是类、字段、注解三件套；
- 注解一半控制展示，一半直接参与录制行为；
- `EventType` / `ValueDescriptor` 才是运行时真正消费的元模型；
- `EventFactory` 则在结构运行时才确定时，负责动态生成事件 Schema；
- 大多数场景仍然应优先选择静态事件，让 Schema 在编译期稳定下来。

所以理解自定义 JFR 事件的正确角度，不是“怎么写一个继承了 `Event` 的类”，而是：**怎样把一段业务行为正式声明成一份可被 JFR 记录器、配置模板和分析工具共同理解的事件 Schema。** 一旦这层 Schema 立住，后面的字节码注入、录制配置和离线消费才有真正的共同基础。

下一篇自然就会追到这套模型更底的一层：事件类、字段和注解都已经声明好了，为什么 `commit()` 在源码里看起来却像空壳？JFR 到底在什么时候、通过什么机制把事件类改写成真正可写入录制缓冲的形态，这就是 `03-bytecode-instrumentation.md` 要接着回答的问题。
