# JFR 全景与事件模型：为什么它不是另一种 dump 工具，而是把运行行为持续压成低开销事件流

> 本文基于 JDK 11 `jdk.jfr.Event`、`Recording`、`FlightRecorder`、`RecordingState`。本文聚焦 JFR 的三物件模型、事件生命周期和低开销设计动机；注解与配置留到后续篇章。
> **前置依赖**：[ThreadLocal](../11-thread-threadlocal/02-threadlocal.md)、[原子与 CAS](../13-atomic/01-atomicinteger-cas.md)
> **后续**：[自定义事件与注解](02-custom-event-annotation.md)

## 先看一个最容易被混淆的问题：既然已经有 `jstack`、heap dump 和 profiler，为什么还需要 JFR

JVM 线上排查常见的三种信息来源，表面看都在“观察系统”，但它们记录的其实是三种不同形态的信息：

- `jstack`、heap dump 这类工具给你的是**某个瞬间的快照**；
- 常规 profiler 往往通过**周期性采样**偷看热点；
- JFR 记录的则是一段时间窗口里**发生过哪些值得保留的事件**。

这三者不是谁替代谁，而是在回答不同问题。快照擅长回答“现在是什么样”；采样擅长回答“最近经常在哪儿耗 CPU”；而 JFR 真正想保留的是“这段时间里系统到底发生过什么运行行为”。

这也就是为什么 JFR 不该被理解成“JDK 自带 profiler”或“另一种 dump 工具”。它的核心不是截某一刻，也不是定期偷看，而是把 JVM 和应用的重要行为压成一条持续事件流：等问题发生之后，你还能回头分析那段时间里到底发生了哪些事件。

所以这一篇真正要回答的，不是“JFR 能看什么”，而是：**它为什么要把可观测性建成一个低开销持续事件记录系统。**

## 一、为什么 `FlightRecorder`、`Recording`、`Event` 刚好组成了一套持续事件流系统

### 先看三物件各站在哪一层

JDK 11 里：

- `FlightRecorder` 定义在 `FlightRecorder.java:59`
- 获取全局入口 `getFlightRecorder()` 在 `FlightRecorder.java:176`
- `Recording` 定义在 `Recording.java:63`
- `Event` 定义在 `Event.java:91`
- `RecordingState` 枚举在 `RecordingState.java:33`

这几个类最容易被背成“JFR 里的几个对象”，但更重要的是看它们的分工层次：

- **`Event`**：一次具体事件的定义与提交协议；
- **`Recording`**：一段录制窗口，也就是“哪些事件、以什么设置、从什么时候录到什么时候”；
- **`FlightRecorder`**：整个 JVM 里的录制引擎门面和全局入口。

### 为什么它们合起来才叫“事件流系统”

如果只有 `Event`，你顶多能定义“发生了一件事”；如果只有 `Recording`，你只是有一个会话容器；如果只有 `FlightRecorder`，你只是在说 JVM 里存在一套录制引擎。真正让 JFR 成立的是三者叠在一起：

- 引擎长期驻留；
- 会话决定录制窗口；
- 事件在窗口内被持续提交。

也就是说，JFR 的本体不是某个单点 API，而是一套“引擎 + 会话 + 事件”的系统分层。

## 二、为什么 `Recording` 代表的是会话，而不是全局唯一开关：JFR 天生就是窗口化录制模型

### 先看 `Recording` 的动作入口

JDK 11 里，`Recording` 的关键入口包括：

- `start()`：`Recording.java:168`
- `stop()`：`209`
- `enable(String)`：`602`
- `disable(String)`：`623`
- `enable(Class<? extends Event>)`：`640`
- `disable(Class<? extends Event>)`：`658`

这些入口已经把 `Recording` 的身份说得很清楚：它不是“JFR 是否开启”的全局布尔值，而是一段带有自己生命周期和配置的录制会话。

### 为什么这一步很关键

如果 JFR 只有一个全局录制状态，那它会非常僵硬：你很难同时做短时问题排查和长期低频记录，也很难按不同事件集、不同时长、不同输出策略并存观察。

而会话模型意味着：

- 录制可以 start / stop；
- 录制可以针对不同事件集单独 enable / disable；
- 多个观察窗口理论上可以并存；
- “我现在录什么、录多久、何时结束”是会话级别决策。

这说明 JFR 从设计上就不是一次性命令，而是面向时间窗口的记录系统。

## 三、为什么 `Event.begin()` / `end()` / `commit()` 是最小事件协议：JFR 记录的不是对象创建，而是一次经过判定后被提交的事件

### 先看 `Event` 公开协议长什么样

JDK 11 里，`Event` 暴露的关键方法是：

- `begin()`：`Event.java:102`
- `end()`：`110`
- `commit()`：`121`
- `shouldCommit()`：`144`

这几个方法最容易被看成普通工具方法，但从协议角度看，它们其实定义了 JFR 事件生命周期的最小闭环。

### 为什么“创建事件对象”不等于“事件已被记录”

这是理解 JFR 的第一道门。一个事件对象就算被 new 出来了，也不代表它已经进入记录系统。真正决定“这件事要不要进飞行记录”的，是提交协议：

- `begin()` 标出事件开始；
- `end()` 标出事件结束；
- `commit()` 才把它交给录制系统；
- `shouldCommit()` 则允许在提交前先问一句：值得写吗？

这也就解释了为什么 JFR 和日志模型很不一样。日志通常是一句代码直接输出，而 JFR 是把“定义事件”“测量事件”“决定是否提交”“真正提交写入”拆成了不同步骤。

### 为什么 `begin/end` 不是装饰动作

它们不只是为了 API 对称好看。JFR 事件很多都带持续时间语义：一个请求、一次锁竞争、一段 IO、一轮方法执行，这些都不是瞬时点，而是区间。`begin/end` 让事件本身能表达这个区间，`commit()` 则在区间信息已经齐备之后再做真正提交。

所以 JFR 记录的不是静态对象，而是**一段经过时间边界标注、并经过提交判定的运行行为。**

## 四、为什么 `shouldCommit()` 比想象中更核心：JFR 的低开销先从“写之前先判断值不值得写”开始

### 先看它和 `commit()` 的关系

JDK 11 的 `Event` 在 Javadoc 中已经明确暗示了一个非常重要的使用模式：在真正做昂贵字段填充或提交之前，可以先调用 `shouldCommit()`，如果结果是 false，就尽早放弃后续工作。

这说明 JFR 不是“先做完所有事，再决定要不要记”。它的设计反过来：**先把启用判断和阈值判断前置，再决定值不值得继续做更多写入准备。**

### 为什么这就是它的第一层成本纪律

JFR 要想能长期挂在线上，就不能要求每个埋点在未启用时也做完整字段构造、字符串拼接、复杂对象准备。否则即使最终不写文件，事件代码本身也已经付出了太大成本。

所以 `shouldCommit()` 的意义不是小优化，而是整个 JFR 成本模型的一部分：

- 事件未启用，尽快退出；
- 事件已启用但阈值不满足，尽快退出；
- 只有真的需要记录时，才值得继续补齐字段并提交。

这也是为什么 JFR 能把“长期开着”这件事做得比很多重型采样和日志方案更现实。

## 五、为什么 JFR 的低开销设计首先体现在“未启用几乎零成本”：它不是总在付费,而是按需进入写入路径

### 先看最容易被忽略的一点

旧稿已经抓到一个关键事实：`Event.java` 公开层面的方法很多都像空壳或极薄门面。这里最值得关注的不是“它为什么看起来空”，而是这种形态本身就透露了成本设计的方向：**未启用时，事件路径应该尽可能退化成极小判断甚至 no-op。**

### 为什么这比“启用后优化得很快”更基础

很多工具都强调“启用后很高效”，但对于长期在线系统来说，更关键的问题往往是：不用的时候你要花多少钱。JFR 的第一层答案正是：

- 没有相关录制会话启用时，事件代码应尽量什么都不做；
- 只有进入录制窗口且满足规则时，才真正进入写入路径；
- 真正的写入又通过环形缓冲、结构化记录和内部优化去压缩成本。

所以“未启用几乎零成本”不是附加卖点，而是 JFR 能成立的必要条件。

## 六、为什么事件流和快照/日志/采样互补：JFR 真正独特的是“给你一段可复盘的时间窗口”

### 和快照相比，它保留的是历史过程

快照工具只能告诉你“那一刻是什么样”，却很难保留变化过程。JFR 的事件流则能回答：在问题发生前后，这段时间里 GC、锁竞争、方法执行、线程调度、IO 等行为是怎样演进的。

### 和日志相比，它天然是结构化可控记录

日志也能记历史，但日志常常有字符串拼接、格式约定不统一、噪声大、难做统一事件类型约束等问题。JFR 从一开始就把记录单位定义成结构化事件，并且把启用、阈值、录制窗口纳入统一控制模型。

### 和采样相比，它不是“周期性偷看”，而是“事件发生时再写”

采样天然会错过未被采中的瞬态行为，而事件流的语义是：只要某类行为被定义成事件并被启用，它发生时就能被记录。它不依赖“恰好采到”，而依赖“事件本身是否值得记”。

所以 JFR 的独特价值，不是更像谁，而是它给了生产排查一种新的信息形态：**一段时间窗口里的结构化事件历史。**

## 五个最容易混掉的边界：JFR 不是快照，Recording 不是全局开关，new Event 不是已记录，shouldCommit 不是 commit，低开销也不是零成本

第一，JFR 不是快照。它保留的是一段时间窗口里的结构化事件历史，适合回看行为如何演进，而不是只回答某一个瞬间的堆栈或堆状态。

第二，`Recording` 不是全局开关。它代表一段有生命周期、有事件设置、有起止边界的录制会话；“JFR 开了”必须进一步说明是哪一个会话、记录哪些事件、从何时到何时。

第三，new 一个 `Event` 不是已记录。对象创建只建立事件实例，`begin/end` 负责时间边界，`commit()` 才把完整事件交给录制系统；事件对象存在和事件进入记录流是两件事。

第四，`shouldCommit()` 不是 `commit()`。前者是提交前的成本判断，让未启用或不满足条件的事件尽早退出；后者才是真正提交动作，不能把“值得写”误解成“已经写入”。

第五，低开销也不是零成本。JFR 的目标是未启用时尽量接近 no-op、启用后按规则进入高效写入路径，但事件定义、判断、缓冲和实际记录仍然存在成本，低开销不等于可以无条件滥加埋点。

把这五条边界记稳，JFR 就不会再被简化成“另一个 dump”或“永远免费开的 profiler”。它真正想讲的是：用引擎管理会话，用事件协议记录行为，用提交判定控制成本，再保留一段可供事后复盘的运行历史。

## 收网：JFR 不是另一种 dump 工具，而是把 JVM 运行行为持续压成可低开销写入、可事后分析的事件流

现在可以把整篇压成一条主线：

- 快照、采样、事件流是三种不同信息形态；
- `FlightRecorder`、`Recording`、`Event` 分别承担引擎、会话和事件协议角色；
- `Recording` 代表一段录制窗口，而不是全局唯一开关；
- `begin/end/commit` 定义了一次事件的最小提交协议；
- `shouldCommit()` 把“值不值得写”前置到真正写入之前；
- JFR 的低开销首先建立在未启用时几乎零成本，启用后再按规则进入写入路径。

所以理解 JFR 的正确角度，不是“JDK 自带了个 profiler”，而是：**JDK 自带了一套低开销持续事件记录系统。** 它关心的不是某个瞬时快照，而是一段时间窗口里，JVM 和应用究竟发生过哪些值得事后复盘的运行行为。
