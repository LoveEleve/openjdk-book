# 32-unsafe/01 重写规划

> 状态：重写前计划
> 适用规范：`docs/openjdk/WRITING-GUIDELINES.md`
> 版本边界：JDK 11 `sun.misc.Unsafe` 与 `jdk.internal.misc.Unsafe`。本文聚焦双入口、`getUnsafe()` 访问门槛、能力域分层与“不安全”语义；DirectBuffer 与堆外回收放到下一篇。
> 目标：把“Unsafe 全景与能力边界”改写成一篇围绕“Unsafe 不是一个普通高阶工具类，而是让 JDK 和极少数框架越过 Java 默认类型/内存/线程安全边界的一组底层原语，因此真正重要的问题不是 API 多不多，而是谁能拿到它、拿到后到底绕过了什么保护”展开的机制文章。

## 1. 读者困惑

- 为什么 `Unsafe` 明明能 import，却普通业务代码通常拿不到实例？
- `sun.misc.Unsafe` 和 `jdk.internal.misc.Unsafe` 到底是什么关系，为什么会有两层入口？
- 为什么它叫 Unsafe，它到底“越过”了 Java 的哪些默认保护？
- `Unsafe` 的能力边界怎么分，为什么 CAS、堆外内存、字段偏移和 park/unpark 会同时出现在这里？
- 为什么 JDK 自己大量用它，却又不鼓励业务代码直接依赖？

## 2. 一句话顿悟

**`Unsafe` 的本质不是“高级工具类”，而是一组故意绕过 Java 默认安全边界的底层原语：它让调用者能按偏移读对象、手动管理堆外地址、做原子更新、直接阻塞/唤醒线程。也正因为这些能力破坏了类型安全、内存安全和线程安全的默认兜底，所以真正的门槛不是能不能 import 到类，而是谁有资格通过 `getUnsafe()` 拿到这把钥匙。**

## 4. 理解路径

### 第一节：从“为什么 import 到类却拿不到实例”开场

用读者最常见的第一撞墙点开场：类能看到，但 `getUnsafe()` 拒绝你。先立住总问题：Unsafe 的门槛是运行时资格校验，不是源码可见性。

### 第二节：双入口为什么是“兼容壳 + 内部真实实现”

证据：
- `sun.misc.Unsafe.java:56/65`
- `sun.misc.Unsafe.java:96`
- `jdk.internal.misc.Unsafe.java:53/88`

主线：
- `sun.misc.Unsafe` 留作兼容入口，内部再委托到 `jdk.internal.misc.Unsafe`。
- 这解释了为什么业务看到的类与 JDK 内部真实实现不是完全同一个层次。

### 第三节：`getUnsafe()` 为什么是 Unsafe 的真正大门

证据：
- `sun.misc.Unsafe.java:96`
- 旧稿中的 `module-info.java:28/31` 线索

主线：
- 类可见不等于实例可得。
- 模块导出只是“你看得到类”；真正的实例门槛由 `getUnsafe()` 的 caller 校验控制。
- 这说明访问控制点在运行时资格，而不是 import 语法层面。

### 第四节：为什么对象偏移、堆外内存、CAS、park/unpark 会集中在同一类里

证据：
- `Unsafe.java:639`：`objectFieldOffset`
- `Unsafe.java:712/755`：数组基址与步长
- `Unsafe.java:461/607/570/584`：堆外内存与 copy
- 后续篇再深入 CAS/park 具体实现

主线：
- 这些能力的共同点不是“性能高”，而是都在直接触碰 JVM 的底层表示与调度原语。
- 一旦能算偏移、操作裸地址、做原子替换、直接 park 线程，就已经绕开了 Java 默认抽象层。

### 第五节：为什么它叫 Unsafe——Java 默认的三类保护在这里都会失效

主线：
- 类型安全：可绕过构造与字段封装，破坏对象不变量。
- 内存安全：可申请/释放堆外地址，GC 不再托底。
- 线程安全：可见性、顺序性与 CAS 失败路径由调用者自己负责。
- 这要回扣“为什么 JDK 要把它锁起来”。

### 第六节：为什么 JDK 自己大量使用它，却不等于业务代码应该直接使用它

主线：
- JDK 用 Unsafe 是为了构建更高层、更安全的公共抽象。
- 业务代码通常应优先使用原子类、并发容器、NIO buffer 等封装结果。
- 这不是“禁止”，而是分层设计：危险原语应尽量被收敛在底层设施里。

## 5. 失败方案清单

1. 把 `Unsafe` 当成普通性能优化工具，直接在业务层随手调用。
2. 认为能 import `sun.misc.Unsafe` 就等于能安全拿到实例。
3. 只把 Unsafe 理解成 CAS 工具，忽略它对对象布局和堆外地址的直接控制。
4. 以为堆外内存和对象偏移操作仍会被 GC / 类型系统自动兜底。
5. 看到 JDK 使用 Unsafe，就默认业务代码也应直接依赖它。

## 6. 误解清单

1. Unsafe 只是一个“更快”的反射工具类。
2. `sun.misc.Unsafe` 和 `jdk.internal.misc.Unsafe` 是两套互不相关实现。
3. 模块导出与否决定了能不能使用 Unsafe。
4. 只要代码不崩，按偏移写字段就是安全的。
5. JDK 内部常用的 API 就天然适合业务直接调用。
