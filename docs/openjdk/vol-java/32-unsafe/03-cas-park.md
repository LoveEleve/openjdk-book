# CAS 原语与线程控制：为什么 Unsafe 给并发大厦提供的不是成品，而是三块地基

> 本文基于 JDK 11 `sun.misc.Unsafe` 与 `jdk.internal.misc.Unsafe` 的 CAS、`getAndAdd*`、`park/unpark`、fence 原语。本文聚焦无锁更新模板、线程停放许可语义与内存有序性；AQS 和原子类的更高层实现已在前文，不重复展开。本文讨论的是 JDK 11 `Unsafe` 并发原语边界，不把这里的 CAS 模板、许可模型和 fence 语义外推成所有并发库或所有硬件平台都必须按同一形式暴露的统一规范。
> **前置依赖**：[Unsafe 全景](01-unsafe-overview.md)、[原子与 CAS](../13-atomic/01-atomicinteger-cas.md)
> **后续**：回到并发大厦的更高层应用

## 先看一个常见误解：有了 CAS，不等于并发问题已经被解决了

很多人第一次接触 Unsafe 的并发能力时，最容易记住的是 CAS：比较、交换、原子成功或失败。于是会很自然地把它理解成“并发最核心的问题已经搞定了”。但只要回想一下前面的 AQS、原子类、线程池、并发容器，就会发现事情远没这么简单。

并发从来不只是在某个位置上“改一个值”。它至少还要回答另外两类问题：

- 线程什么时候该停下来，什么时候又该被唤醒；
- 多个读写操作按什么顺序被其他线程看见。

这也就是 Unsafe 在并发里真正提供的三块地基：

- CAS：决定一个位置怎样被原子更新；
- `park/unpark`：决定线程怎样挂起和恢复；
- fence：决定这些读写在内存里按什么顺序生效。

所以这一篇的主线不是“列出几个并发 API”，而是把这三块地基重新收在一张图上，看它们为什么刚好够支起 JDK 并发体系。

## 一、为什么 CAS 是原子更新的最小地基：它只解决“这一步写入是否原子成功”

### 先看最直接的入口

JDK 11 里，`sun.misc.Unsafe` 对外暴露的 CAS 入口包括：

- `compareAndSwapObject(...)` 在 `sun/misc/Unsafe.java:859`
- `compareAndSwapInt(...)` 在 `875`
- `compareAndSwapLong(...)` 在 `891`

内部真实实现则落到 `jdk.internal.misc.Unsafe`：

- `compareAndSetObject(...)` 在 `jdk/internal/misc/Unsafe.java:1300`
- `compareAndSetInt(...)` 在 `1361`
- `compareAndSetLong(...)` 在 `1908`

这些入口的共同语义非常朴素：如果当前位置的值仍然等于期望值，就把它原子地替换成新值；否则什么也不写，返回失败。

### 为什么这一步这么重要，又为什么它还远远不够

CAS 真正值钱的地方，是它把“先读、再判断、再写”这三个动作压成了一个底层原子步骤。这样，无锁算法才能在不直接占用互斥锁的前提下，尝试乐观更新共享状态。

但它的边界也同样清楚：CAS 只回答“这一写有没有在竞争下成功提交”。它并不替你决定失败后怎么办，也不替你处理线程是否该阻塞，更不替你自动定义整套内存可见性协议。

所以 CAS 是地基，而不是完整建筑。上层原子类和无锁结构之所以存在，就是在围绕这个最小地基继续补完整个并发协议。

## 二、为什么 `getAndAdd` 本质上是 CAS 自旋模板：很多“现成原子操作”其实只是循环地尝试提交

### 先看几个代表性入口

JDK 11 里：

- `sun.misc.Unsafe.getAndAddInt(...)` 在 `sun/misc/Unsafe.java:1105`
- `getAndAddLong(...)` 在 `1121`
- `getAndSetInt(...)` 在 `1137`

内部实现则能更直接看出模板：

- `jdk.internal.misc.Unsafe.getAndAddInt(...)` 在 `2334`
- `getAndAddLong(...)` 在 `2372`
- `getAndSetInt(...)` 在 `2569`
- `weakCompareAndSetInt(...)` 在 `1406`
- `weakCompareAndSetLong(...)` 在 `1953`

旧稿已经抓到了最关键的事实：这些看起来像“现成高级原子操作”的东西，本质上并不是神奇新原语，而是标准自旋模板的封装。

### 为什么它们的骨架总是一样

核心流程几乎可以压成同一张卡片：

1. 先读当前值；
2. 基于旧值算出新值；
3. 用 CAS 尝试提交；
4. 如果失败，就重读再来一轮。

这就是 `AtomicInteger.getAndIncrement()`、各种无锁计数器、并发容器局部更新路径背后的共同骨架。所谓“无锁”，不是说永远一次成功，而是说**失败时靠重试推进，而不是立即把线程挂到互斥等待里。**

### 为什么 weak CAS 明明可能“假失败”，却反而很适合放进循环里

很多人看到 weak CAS 会疑惑：既然它可能在值没变时也返回失败，那还有什么用？答案恰恰在外层循环。因为自旋模板本来就默认“失败要重来”，所以只要失败不会破坏状态，weak CAS 完全可以作为内部提交动作。

也就是说，weak CAS 的可用性不是建立在“它从不失败”，而是建立在“调用方已经准备好用循环吃掉失败”。

## 三、为什么 ABA 会成为 CAS 的经典盲区：值相等不等于历史没变

### 先看 CAS 的盲区到底是什么

CAS 只会比较“当前值是不是还等于我刚才看到的那个期望值”。它不记录这段时间里这个位置经历过什么历史。

这就会出现经典 ABA：

- 线程 1 看到值是 A；
- 线程 2 把它改成 B，又改回 A；
- 线程 1 再做 CAS 时，会误以为“这个位置从来没被别人碰过”。

### 为什么有些场景几乎不在乎，有些场景却会出大问题

如果你只是更新一个纯计数值，很多时候 ABA 并不会真的破坏业务含义；但如果你在操作的是链表、栈、队列这类引用结构，“值又变回原样”并不代表结构语义没变。指针可能已经指向了另一个生命周期、另一个节点上下文，历史差异被彻底吞掉了。

这也解释了为什么 ABA 不是“CAS 不可靠”的泛泛口号，而是 **CAS 只看当前快照、不看中间历史** 带来的天然局限。解决方向也因此很自然：把版本号、标记位或其他历史信息一起纳入比较对象里，而不只比对裸值本身。

## 四、为什么 `park/unpark` 不是 `wait/notify` 的换皮：它解决的是线程许可，而不是对象监视器等待

### 先看最底层入口

JDK 11 里：

- `sun.misc.Unsafe.unpark(Object thread)` 在 `sun/misc/Unsafe.java:1050`
- `park(boolean isAbsolute, long time)` 在 `1066`

内部实现则是 native 入口：

- `jdk.internal.misc.Unsafe.unpark(...)` 在 `jdk/internal/misc/Unsafe.java:2280`
- `park(...)` 在 `2294`

这组 API 非常值得和 `wait/notify` 对照着理解，因为它们代表的是另一套完全不同的阻塞模型。

### 为什么它的核心是“线程许可”，而不是“某个对象上的等待队列”

`wait/notify` 依赖的是对象监视器：你得先围绕某把锁建立等待关系，然后在那把锁对应的等待集上唤醒线程。`park/unpark` 则不是这样。它直接面向线程本身发放或消费一份许可：

- 目标是某个具体线程；
- 不要求你先持有某个监视器；
- `unpark` 可以先发生，许可会保留下来，下一次 `park` 直接消费掉。

这正是 `LockSupport` 与 AQS 能做精细线程控制的关键原因。它们不需要把所有等待协议都塞进对象监视器模型里，而是能直接对具体线程做定向停放与恢复。

### 为什么这对同步器设计意义巨大

只要线程可以被单独停放、单独发放许可，上层同步器就能自己决定：哪个线程该排队、哪个线程该被唤醒、唤醒后先抢什么状态、失败后是否继续排队。这比对象监视器那种更粗粒度的等待模型灵活得多。

所以 `park/unpark` 的价值不是“另一个阻塞 API”，而是它把线程调度控制权直接交给了上层同步器框架。

## 五、为什么 CAS 和 park 还不够：并发协议里还缺一块“读写顺序边界”的地基

### 先看 fence 入口

JDK 11 里：

- `sun.misc.Unsafe.loadFence()` 在 `sun/misc/Unsafe.java:1187`
- `storeFence()` 在 `1204`
- `fullFence()` 在 `1218`

内部实现对应：

- `jdk.internal.misc.Unsafe.loadFence()` 在 `jdk/internal/misc/Unsafe.java:3288`
- `storeFence()` 在 `3303`
- `fullFence()` 在 `3315`

这些方法最容易被忽略，因为它们不像 CAS 那样直接“改了一个值”，也不像 `park` 那样直接“停了一个线程”。但从并发正确性看，它们补的是另一块同样不可缺的地基：**读写顺序边界。**

### 为什么原子更新并不自动等于完整可见性协议

哪怕某一次 CAS 本身是原子的，也不意味着你围绕它前后做的所有读写，都已经按你脑子里想的顺序被别的线程看见。并发协议经常不仅要控制“某个点能不能原子更新”，还要控制“哪些读不能越过这一步，哪些写不能被重排到另一侧去”。

fence 存在的意义，就是把这种顺序约束显式化：

- load fence 约束读侧顺序；
- store fence 约束写侧顺序；
- full fence 同时补齐更强的顺序边界。

这也说明，Unsafe 的并发原语如果只讲 CAS，会天然少掉一大块。并发正确性从来都是原子性、阻塞控制和有序性三者一起成立。

## 六、五个最容易混掉的边界：CAS 不是并发全解，getAndAdd 不是神奇新原语，weak CAS 不是没用，park 不是 wait 换皮，fence 也不是可有可无的细枝末节

在收网之前，先把这一篇最容易记错的五条边界压实。

第一，CAS 不是并发问题的全解。它只负责回答“这一次比较并交换是否原子成功”，并不会替你处理失败后的重试策略、线程是否该阻塞、以及整套协议前后读写该怎样配合。

第二，`getAndAdd`、`getAndSet` 这类操作也不是硬件突然多送你的高级原语。它们本质上仍然是“读旧值 → 算新值 → CAS 提交 → 失败重试”的自旋模板，只是 JDK 把这个模板提前封装成了现成能力。

第三，weak CAS 也不是“因为可能假失败，所以没什么价值”。恰恰相反，只要外层本来就准备好循环重试，它就非常适合做内部提交动作；因为调用方本来就不会把一次失败当作最终结论。

第四，`park/unpark` 更不是 `wait/notify` 的换皮版本。它改变的不是方法名，而是等待模型本身：等待关系不再依附某个对象监视器，而是直接围绕线程许可展开。正因为如此，AQS 才能精细控制“唤醒谁、什么时候唤醒、唤醒后先抢什么状态”。

第五，fence 也不是并发语义里的可有可无细枝末节。哪怕某一次 CAS 本身是原子的，围绕它前后的读写也依然可能发生重排；fence 补的正是这块顺序边界。少了它，并发协议就很容易在“看起来值改对了”但“别人看见顺序不对”这类问题上出错。

把这五条边界记稳，Unsafe 并发原语这一篇就不会重新塌回“几个底层 API 清单”这种表面印象。它真正想讲的是：JDK 并发体系之所以能成立，不是因为 Unsafe 直接给了锁和队列，而是因为它先给了三块更底层的控制杠杆。

## 收网：Unsafe 在并发里真正交给 JDK 的，不是锁和队列，而是“改值、停线程、控顺序”三块地基

现在可以把整篇压成一张总图：

- CAS 决定一个共享位置怎样被原子提交；
- `getAndAdd`、`getAndSet` 这类高级操作，本质上是 CAS 自旋模板的封装；
- ABA 暴露了 CAS 只看当前值、不看历史的盲区；
- `park/unpark` 用线程许可模型，把挂起/唤醒控制权交给上层同步器；
- fence 则补齐并发协议里的可见性与顺序边界。

所以 Unsafe 在并发里的作用，从来不是“直接给你一个现成同步器”，而是把三块最底层的控制杠杆暴露出来：

- 怎么原子改值；
- 怎么停放线程；
- 怎么控制读写顺序。

AQS、原子类、线程池、并发容器这些前面已经拆过的上层结构，本质上就是围绕这三块地基继续向上搭起来的。也正因为如此，Unsafe 既不是普通业务层该直接拥抱的 API，却又是理解 JDK 并发内核几乎绕不开的一层。

`32-unsafe` 到这里也收官了：第一篇把“越界原语集合”的边界立住，第二篇解释了堆外内存如何被包装和回收，最后这一篇则把并发大厦底层真正踩着的三块地基串了起来。下一步自然可以切回后续更高层的主题继续推进。
