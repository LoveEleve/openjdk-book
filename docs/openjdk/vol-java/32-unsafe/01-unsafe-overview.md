# Unsafe 全景与能力边界：为什么它不是工具类，而是越过 Java 默认安全边界的一把钥匙

> 本文基于 JDK 11 `sun.misc.Unsafe` 与 `jdk.internal.misc.Unsafe`。本文聚焦双入口、`getUnsafe()` 访问门槛、能力域分层与“不安全”语义；DirectBuffer 与堆外回收放到下一篇。本文讨论的是 JDK 11 `Unsafe` 能力边界，不把这里的兼容壳分层、运行时资格校验和原语集合方式外推成所有底层内存接口都必须遵守的统一规范。
> **前置依赖**：[原子与 CAS](../13-atomic/01-atomicinteger-cas.md)、[AQS 核心](../12-lock-sync/01-aqs-core.md)
> **后续**：[堆外内存与 DirectBuffer](02-offheap-directbuffer.md)

## 先看第一个最容易撞墙的事实：类明明能看到，实例却不是你想拿就能拿

很多人第一次接触 `Unsafe`，往往先看到的是它那张几乎无所不能的 API 地图：可以按偏移读对象字段、可以手动申请堆外内存、可以做 CAS、可以 park/unpark 线程。然后紧接着就会产生一个自然想法：既然类都能 import 到，那直接拿来用不就好了？

真正的第一道门槛恰恰在这里。`Unsafe` 的问题从来不是“有没有这个类”，而是：**谁有资格拿到实例，谁被允许越过 Java 默认安全边界。**

这也是为什么这一篇不能把它写成普通工具类介绍。`Unsafe` 真正危险的地方，不在于 API 名字看着底层，而在于它允许调用者绕开 Java 原本替你兜住的那几层保护：对象封装、类型安全、GC 托底、线程同步语义。

所以这一篇要先讲清的，不是“有哪些方法”，而是：为什么 JDK 要把这把钥匙锁起来，以及拿到它之后到底越过了什么边界。

## 一、为什么 `Unsafe` 的门槛不在 import，而在运行时资格校验

### 先看公开入口做了什么

JDK 11 的 `sun.misc.Unsafe` 定义在 `sun/misc/Unsafe.java:56`。公开入口 `getUnsafe()` 在 `sun/misc/Unsafe.java:96`，旧稿已经抓到这一点：它不会因为你能看到类就无条件把实例交给你，而是会检查调用者是否属于受信任的 system domain；不满足条件就直接拒绝。

这说明一件非常关键的事：`Unsafe` 的控制点不是“你能不能写下这个类名”，而是“运行时是否认可你有资格拿这把钥匙”。

### 为什么这和模块导出不是一回事

旧稿里也已经点到了 `jdk.unsupported/module-info.java` 的 `exports` / `opens` 线索。这个细节很重要，因为它能帮读者分清两个层次：

- 模块导出解决的是“类符号是否可见”；
- `getUnsafe()` 校验解决的是“实例是否可得”。

也就是说，类可见性和能力可用性在这里是被故意拆开的。JDK 并没有把“看得到类”自动等同于“允许你越界操作内存和对象布局”。

这正是 Unsafe 的第一层设计意图：**它不是语法上隐藏，而是运行时把真正的能力关口收紧。**

## 二、为什么会有 `sun.misc.Unsafe` 和 `jdk.internal.misc.Unsafe` 两层入口：前者是兼容壳，后者是内部真实实现

### 先看两个类的关系

JDK 11 里：

- `sun.misc.Unsafe` 在 `sun/misc/Unsafe.java:56`
- 其中持有 `theInternalUnsafe`，位置在 `sun/misc/Unsafe.java:65`
- `jdk.internal.misc.Unsafe` 定义在 `jdk/internal/misc/Unsafe.java:53`
- 内部自己的 `getUnsafe()` 在 `jdk/internal/misc/Unsafe.java:88`

这已经把层次关系说得很明白：`sun.misc.Unsafe` 并不是一套完全独立实现，它更多是面向兼容层暴露出来的一层壳，真正的底层能力最终落在 `jdk.internal.misc.Unsafe` 这边。

### 为什么 JDK 要这么分层

因为历史上很多代码、框架甚至 JDK 自身都和 `sun.misc.Unsafe` 发生过耦合，完全消失它的名字成本极高；但与此同时，JDK 又不希望把底层实现长期冻结在旧包名与旧边界上。所以最现实的做法就是：保留兼容入口，同时把真实实现和内部演进空间放到更明确的内部层次里。

这也解释了为什么读 `Unsafe` 源码时，不能把这两个类简单看成“重复实现”。它们更像是：

- `sun.misc.Unsafe` 负责兼容暴露；
- `jdk.internal.misc.Unsafe` 负责内部真实能力。

## 三、为什么对象偏移、堆外内存、CAS、park/unpark 会集中出现在同一个类里：它们都在直接触碰 JVM 底层表示

### 先看几组代表性入口

旧稿已经抓到几类关键方法：

- `objectFieldOffset(...)` 在 `sun/misc/Unsafe.java:639`
- `arrayBaseOffset(...)` / `arrayIndexScale(...)` 在 `712` / `755`
- `allocateMemory(...)` / `freeMemory(...)` 在 `461` / `607`
- `copyMemory(...)` 在 `570` / `584`

而内部实现层也有对应入口：

- `allocateMemory(...)` 在 `jdk/internal/misc/Unsafe.java:607`
- `copyMemory(...)` 在 `779` / `798`
- `freeMemory(...)` 在 `899`
- `objectFieldOffset(...)` 在 `948`
- `arrayBaseOffset(...)` / `arrayIndexScale(...)` 在 `1055` / `1111`

### 为什么这些能力本质上是一类东西

表面上看，对象字段偏移、堆外地址、CAS、线程 park/unpark 似乎属于完全不同话题：一个像对象模型、一个像内存管理、一个像并发原子更新、一个像调度原语。但它们在 Unsafe 里会聚到一起，原因并不是“都比较高性能”，而是它们都在做同一类越界动作：**直接绕开 Java 上层抽象，去碰 JVM 的底层表示与运行时原语。**

一旦你能：

- 计算对象字段在内存里的偏移；
- 直接操作一段不受 GC 常规管理的裸地址；
- 发起底层 CAS；
- 直接 park / unpark 线程；

那你其实已经不再通过普通 Java 语义与运行时打交道了，而是在直接触碰它的地基层。

所以 Unsafe 更像“越过默认抽象层之后的一组原语集合”，而不是几个恰好放在一起的性能小工具。

## 四、为什么它叫 Unsafe：Java 默认替你兜底的三类安全承诺，在这里都会失效

### 类型安全为什么会失效

Java 平时最重要的一层保护，就是对象应该按自己的构造规则和字段封装被访问。但一旦进入 Unsafe 世界，调用者可以按偏移直接读写字段，可以绕开类本来想维护的不变量。你写进去的值，也许在字节层面没问题，但在对象语义层面已经坏掉了。

这就是类型安全被打穿的地方：对象不再只能通过它公开的方法和约束被修改。

### 内存安全为什么会失效

`allocateMemory(...)` / `freeMemory(...)` 这类 API 最直白地说明了 Unsafe 的第二重危险：它允许 Java 代码自己管理堆外地址空间。申请多少、什么时候释放、有没有越界写、地址是否悬空，GC 都不会像管理普通对象那样自动替你兜住。

所以一旦这里出错，问题级别就不再只是“某个业务对象状态错了”，而可能直接上升到进程级故障、内存泄漏甚至 JVM 崩溃。

### 线程安全为什么会失效

Unsafe 的并发原语也一样。CAS、volatile 语义、park/unpark 这些东西让你能搭出高性能并发结构，但它们并不会自动替你完成协议设计。可见性要不要保证、重试路径怎么收口、唤醒顺序会不会出竞态，这些责任都落回调用者自己身上。

也就是说，Unsafe 并不是“自动更线程安全”，而是让你直接接触线程安全背后的原始杠杆。

## 五、为什么 JDK 自己大量使用它，却不等于业务代码应该直接依赖它

### JDK 用 Unsafe，是为了把危险原语封装成更高层抽象

前面并发域已经反复看到：原子类、AQS、ConcurrentHashMap、NIO buffer 这些能力的深处，经常都站着 Unsafe。但这并不意味着应用层应该直接复制这种使用方式。恰恰相反，JDK 使用 Unsafe 的意义之一，就是把这些危险而强大的原语包装成大多数开发者可以安全使用的上层 API。

换句话说，Unsafe 是标准库在地基层用的，不是为了让每个业务模块都自己去浇地基。

### 为什么分层在这里尤其重要

如果业务代码直接把 Unsafe 当成普通优化手段，就很容易跳过原本已经存在的安全抽象，自己承担对象布局、地址管理、同步协议、兼容边界这些底层责任。短期看也许能拿到一点能力或性能，长期看却常常把可维护性、可移植性和升级兼容性一起押上去。

所以更合理的原则不是“绝不接触 Unsafe”，而是：**除非你就在构建底层设施，否则优先使用标准库已经替你封装好的那一层。**

## 六、五个最容易混掉的边界：Unsafe 不是工具箱，类可见不等于实例可得，内部双入口不是重复实现，能做 CAS 不等于天然线程安全，JDK 自用也不等于业务直用

在收网之前，先把这一篇最容易记错的五条边界压实。

第一，`Unsafe` 不是普通工具箱。它和常见 util 类最大的不同，不是 API 更多，而是每一组能力都在主动绕开 Java 默认替你兜住的安全边界：对象封装、类型检查、GC 托底、同步语义，都可能被你亲手接管。

第二，类可见也不等于实例可得。`import sun.misc.Unsafe` 只能说明编译器认识这个符号；真正能不能拿到那把钥匙，取决于 `getUnsafe()` 在运行时愿不愿意把实例交给当前调用者。

第三，`sun.misc.Unsafe` 和 `jdk.internal.misc.Unsafe` 也不是两份重复实现。前者更多承担兼容壳角色，后者才是内部真实能力集合；把它们看成双副本，会直接看丢 JDK 在兼容与内部演进之间做的分层。

第四，能做 CAS、volatile 语义和 park/unpark 也不等于你天然就得到了线程安全。Unsafe 给你的只是原始杠杆，不会替你把可见性、重试、竞争失败和唤醒协议设计好；这些协议一旦写错，问题一样会非常底层而且难查。

第五，JDK 自己大量使用 Unsafe，更不等于业务代码就该直接照抄。JDK 使用它，往往是为了把危险原语再封装成更稳定的上层抽象；业务层如果直接越过这些抽象去碰地基层，承担的会是可移植性、可维护性和升级兼容性的整包代价。

把这五条边界记稳，Unsafe 这一篇就不会重新塌回“一个很猛的隐藏 API 清单”这种表面印象。它真正想讲的是：Unsafe 把原本被 Java 隔开的底层原语重新暴露了出来，而这份能力本身就是代价。

## 收网：Unsafe 真正可怕的地方，不是 API 多强，而是它允许你跨过 Java 默认替你守住的边界

现在可以把整篇压成一条总线：

- `Unsafe` 的门槛不在类是否可见，而在 `getUnsafe()` 的运行时资格校验；
- `sun.misc.Unsafe` 更像兼容壳，`jdk.internal.misc.Unsafe` 才是内部真实实现；
- 对象偏移、堆外地址、CAS、park/unpark 之所以会聚在一起，是因为它们都在直接接触 JVM 底层表示；
- 它之所以叫 Unsafe，是因为类型安全、内存安全、线程安全三层默认兜底都会在这里失效；
- JDK 自用它，是为了搭更高层抽象，不是为了鼓励业务层普遍直连。

所以理解 Unsafe 的正确角度，不是“Java 里有个很猛的隐藏工具类”，而是：**JVM 提供了一组越界原语，JDK 用它们造出并发、NIO、原子类这些上层设施，而你只有在确实需要进入地基层时，才应该认真面对它带来的全部代价。**

下一篇自然就会接住这里最直观、也最容易让人误判的一块能力：既然 Unsafe 能直接申请不受 GC 常规托管的地址空间，那 `DirectByteBuffer` 到底是怎么把堆外内存包成一个 Java 对象的，谁来记账，谁来回收，这就是 `02-offheap-directbuffer.md` 要接着回答的问题。
