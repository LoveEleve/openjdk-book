# 字节流与装饰器模式：为什么类很多，核心却只在 EOF、叠加职责和批量缓冲

> 本文基于 JDK 11 `InputStream`、`FilterInputStream`、`BufferedInputStream` 及常见内存/管道字节流。本文聚焦 `read()` / `read(byte[],off,len)`、EOF 表示、装饰器链、缓冲补充机制与典型流种类；字符解码与 NIO 通道分离到后续篇章。本文讨论的是 JDK 11 `java.io` 字节流抽象，不把这里的默认实现和包装方式外推成所有 IO 框架都必须遵守的统一规范。
> **前置依赖**：[阻塞与等待语义对照](../10-concurrent-collections/05-blocking-queues.md)
> **后续**：[字符流与字节桥接](02-reader-writer.md)

## 先看一个最容易把字节流体系误会成“类太多所以很乱”的直觉

第一次翻开 `java.io` 时，很多人都会被类名数量吓一跳：`InputStream`、`FileInputStream`、`BufferedInputStream`、`DataInputStream`、`ByteArrayInputStream`、`PipedInputStream`……看起来像是层层叠叠的一大坨老 API。于是很容易得出一个表面判断：字节流体系之所以难，是因为类太多、层次太深。

真正难的地方其实不在类多，而在于它一直在围绕三条非常基础的边界做抽象：

- **怎么表示“真的没有更多字节了”**；
- **怎么把底层读取、缓冲、结构化解析这些职责运行时叠加起来**；
- **怎么把频繁的小读变成更少的大块系统调用，再在内存里慢慢消费**。

所以这一篇不打算把 InputStream 家族做成百科，而是用这三条主线把它们重新收回来：EOF 语义决定了 `read()` 为什么长成现在这样；装饰器模式决定了 IO 功能为什么不是靠继承爆炸；缓冲则解释了为什么“读一个字节”背后常常不是“做一次系统调用”。

## 一、为什么 `read()` 返回的是 int：EOF 和有效字节必须同时被编码进返回值

### 先看最直觉但根本装不下语义的失败方案

如果你第一次设计一个字节流 API，很自然会觉得：既然读的是字节，那 `read()` 返回 `byte` 不就好了？问题是，一旦把“没有更多数据了”这件事也算进去，`byte` 立刻就不够用了。

原因非常具体：有效字节本来要覆盖 `0..255`，而 EOF 又需要一个额外值来表达“源已经结束”。如果返回类型只有 `byte`，那你就会立刻撞上经典冲突：`0xFF` 本身就是合法数据，但 `-1` 又常被拿来表示 EOF，二者在 8 位有符号 byte 语义里根本无法无歧义共存。

所以 `InputStream.read()` 返回 `int` 不是历史包袱，而是一个非常直接的语义要求：**返回值既要容纳完整的 0..255 字节值，又要额外容纳一个 EOF 哨兵。**

### 这就是为什么“按返回值循环”是字节流使用的第一原理

JDK 11 的 `InputStream` 定义在 `InputStream.java:50`。它所有后续变体再复杂，这个返回语义都没有变：只要你在处理单字节读取，真正安全的驱动方式就是“按返回值是否为 -1 继续循环”。

也就是说，字节流的第一原则不是“读一个 byte”，而是“**每次问一次：这是一个合法字节，还是已经没有更多数据**”。后面所有批量读取、缓冲、桥接，本质上都还是建立在这层 EOF 语义之上。

## 二、为什么默认批量 read 仍然不能替代业务循环：InputStream 只能提供保底语义，不能替你假设数据边界

### 先看“既然有 `read(byte[], off, len)`，是不是一次就能拿满”这个误解

很多人从单字节读取走到批量读取时，会自然产生一种乐观预期：既然我都给了一个 byte 数组，指定了长度，那 API 就应该一次帮我读满。这种想法对某些具体流、某些具体场景看起来常常“碰巧成立”，于是很容易被误当成普遍契约。

JDK 11 的 `InputStream` 里：

- `read(byte[])` 位于 `InputStream.java:204`
- `read(byte[], int, int)` 位于 `265`

默认实现当然会尽量帮你多读，但关键是：**这只是抽象基类的保底策略，不是对所有具体流都能外推的业务边界承诺。** 文件、网络、管道、内存流，底层节奏都可能不同；更重要的是，即使底层流愿意尽量多读，业务消息边界也不必然等于这次 read 调用的长度需求。

所以可靠的 IO 代码仍然要按返回值驱动循环，而不是假设“一次调用就凑齐了我想要的业务块”。这一点和上一节的 EOF 原理其实完全同一脉：字节流 API 只保证“我这次实际给了你多少字节”，不会替你推导“这是不是你业务上完整的一帧”。

### 为什么 JDK 还会额外提供 `readAllBytes()` / `transferTo()`

JDK 11 也提供了：

- `readAllBytes()`（`InputStream.java:113` / `332`）
- `transferTo()`（`142` / `699`）

这不是在推翻前面的原则，而是在告诉你：如果你的语义本来就是“把剩下所有字节一次性读完”或“把剩下所有字节整体转发到输出端”，那就别再自己手写样板循环了。换句话说，**JDK 可以封装常见循环，但不会替你改变底层 read 的语义边界。**

## 三、为什么 IO 体系不用继承穷举组合，而是走装饰器：职责叠加比类爆炸更重要

### 先看如果全靠继承会发生什么

假设你想把“从文件读取”“带缓冲”“再支持结构化读取”这些能力组合起来。如果全靠继承，你很快就会得到一长串令人绝望的类排列：BufferedFileInputStream、DataBufferedFileInputStream、BufferedSocketInputStream……每多一种职责，就要为所有底层源重新组合一遍。

这就是典型的类爆炸。更麻烦的是，IO 职责很多时候不是编译期静态决定的，而是运行时按场景临时叠加：有时你只想要缓冲层，有时你还要再加结构化解码，有时底层源又从文件换成内存。

### FilterInputStream 正好说明了“包装已有流再叠一层职责”这条路线

JDK 11 里：

- `FilterInputStream` 定义在 `FilterInputStream.java:46`
- 它持有的被包装流字段 `in` 位于 `:50`

这已经把设计思路说透了：它不是靠再造一种新的“超级输入流”子类去包办一切，而是承认有一条底层流存在，然后在外面再包一层新的行为。缓冲、数据类型读取、解压缩等职责都可以沿着这条路线继续叠加。

所以 `new BufferedInputStream(new FileInputStream(f))` 不是语法巧合，而是这套体系的根：**底层字节来源先定下来，功能职责再通过包装层逐步加上去。**

这一层真正要记住的是，InputStream 家族“类很多”不是因为设计乱，而是因为它把“数据源”和“增强职责”刻意拆开，让它们在运行时自由组合。

## 四、为什么 BufferedInputStream 会快：它优化的不是 Java 循环，而是系统调用边界

### 先看“逐字节读很慢”慢在了哪里

很多人第一次听说缓冲流更快，会下意识觉得“也许是 Java 代码循环得更高效”。真正拖慢逐字节读取的，通常根本不是 `for` 循环，而是**每次都跨到底层流甚至系统调用边界**。只要你的数据源不是纯内存，一次 `read()` 很可能意味着更多层的边界切换。

这就是 `BufferedInputStream` 要解决的问题。它在 JDK 11 中：

- 类定义在 `BufferedInputStream.java:52`
- 默认缓冲大小 `DEFAULT_BUFFER_SIZE` 位于 `54`
- 关键字段包括 `buf`（`85`）、`count`（`96`）、`pos`（`113`）

这些字段合起来表达的是一件非常朴素的事：先一次性把一大块底层字节装进内存缓冲区，后面再在内存里慢慢拿。

### `fill()` 才是它真正值钱的地方

`fill()` 位于 `BufferedInputStream.java:219`。而单字节 `read()` 在 `269`，会优先看当前 `pos` 和 `count` 是否还有缓冲数据；只有缓冲耗尽时，才再次 `fill()` 去找底层流补货。

所以缓冲流的本质不是“读一个字节更快”，而是：

```text
少量底层大读
  → 多量内存小读
```

这正是它快的原因。系统调用少了，Java 代码里那点数组索引循环根本不再是问题主角。

### `read1()` 说明它优化的是“怎么少过边界”，而不是“所有字节都必须先进缓冲”

更有意思的是 `read1()`，位于 `BufferedInputStream.java:282`。它在某些条件下会直接把底层流读进目标数组，而不强制中转到内部 `buf`。这进一步说明：BufferedInputStream 的核心并不是“任何数据都先进一层数组”，而是“**尽量减少不必要的底层边界往返**”。

所以缓冲的本质一定要记成这句话：**它是在批量化系统调用，不是在给 Java 循环做语法糖。**

## 五、为什么内存流和管道流也在同一套体系里：字节流抽象的核心是“数据管道”，不是“文件”

### 先拆掉“流就是文件或网络”的狭义印象

很多人提到 InputStream，脑子里第一反应都是文件和 socket。可字节流这套抽象之所以能稳定存在这么多年，恰恰是因为它描述的不是某种具体设备，而是“**有一端在提供字节，另一端按顺序消费字节**”这类统一的数据管道关系。

这也是为什么纯内存的 `ByteArrayInputStream`、线程间传输用的 `PipedInputStream` / `PipedOutputStream`，都能自然落进同一套 API 里。它们的底层介质不同，但对上层调用者来说，驱动方式依旧是：按 read 语义取字节，按 EOF 语义判断是否结束，必要时再通过包装层叠加缓冲和解析职责。

### 这恰好把前三条主线收成一个统一抽象

到这里，字节流体系看起来就不再杂乱了：

- EOF 语义解释了为什么 `read()` 是 int；
- 装饰器解释了为什么职责叠加不靠继承爆炸；
- 缓冲解释了为什么同样是 read，性能差异可以非常大；
- 内存流和管道流则说明“流”描述的是统一管道抽象，而不是某个固定外设。

所以字节流真正统一的，不是它们都叫 InputStream，而是它们都在回答：**字节从哪里来、怎么被一段段读走、什么时候算真正结束。**

## 六、四个最容易混掉的边界：read 不是返回 byte，批量 read 不是读满承诺，缓冲不是 Java 小优化，流也不等于文件

在收网之前，先把这一篇最容易记错的四条边界压实。

第一，`read()` 不是“读取一个 byte 并返回 byte”。它返回 `int`，本质上是在同时回答两个问题：这次拿到的是不是合法字节值，以及底层是不是已经真的结束。少了这个额外状态位，`0xFF` 和 EOF 根本没法无歧义共存。

第二，`read(byte[], off, len)` 也不是“只要给了数组就帮你一次读满”。它能做的是尽量把当前能给的字节交给你，而不是替你推断业务边界已经完整到齐。真正完整的一帧、一条消息、一个文件块，仍然得由调用方按返回值循环去确认。

第三，缓冲流也不是“Java 层数组循环更快”的小优化。它真正值钱的地方在于把大量细碎的小 read 合并成更少的底层大读，让昂贵的系统调用边界少被穿越几次。内存里的数组索引只是后果，不是主因。

第四，流也不等于文件。文件、内存字节数组、线程间管道都可以落进同一套 InputStream 抽象里，因为这套体系真正统一的不是设备类型，而是“有一段顺序字节正在被消费”的管道关系。

把这四条边界记稳，字节流体系就不会重新塌回“老 API 类太多”这种表面印象。它真正想解决的，其实一直是三件很朴素的事：EOF 怎么表达，职责怎么叠加，底层边界怎么批量化。

## 收网：类很多不是本质，真正的本质是 EOF、职责叠加和系统调用批量化

回到开头那个错觉，现在已经能看清为什么 InputStream 家族并不是真的“类太多所以很乱”。类多只是表象，真正把这套体系串起来的，其实只有三条边界。

第一，EOF 必须和有效字节值共存，所以 `read()` 必须返回能同时表达 0..255 和 -1 的 `int`。第二，文件读取、缓冲、结构化解析这些职责不能靠继承穷举组合，否则类会爆炸，于是 JDK 选择用 `FilterInputStream` 这条包装链在运行时叠加职责。第三，逐字节读取真正慢的不是 Java 代码，而是底层系统调用边界，因此 `BufferedInputStream` 要做的核心事就是先批量补货，再在内存里慢慢消费。

把整篇压成一张总图，就是：

```text
字节流抽象
  → read() 返回 int 承载字节值 + EOF
  → 具体数据源可来自文件、内存、线程管道
  → 运行时通过装饰器叠加缓冲/解析职责
  → 缓冲层把“频繁小读”变成“更少的大块底层读取”
```

如果说这一篇解决的是“字节流为什么长成现在这样”，下一篇就会继续沿着这条边界往上走：一旦数据不再只是 0..255 的字节，而是字符、编码和文本，`InputStreamReader`、`Reader/Writer`、`StreamDecoder` 这些桥接层又是怎样把“字节管道”接成“字符管道”的。
