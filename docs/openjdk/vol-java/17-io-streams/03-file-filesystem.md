# File 与平台文件系统：为什么它先是一段路径，而不是已经打开的文件

> 本文基于 JDK 11 `File`、`java.io.FileSystem`、`java.io.UnixFileSystem`、`FileDescriptor`。本文聚焦 `File` 的路径抽象、FileSystem 委托、exists/create/delete/list/mkdirs 等行为，以及 fd 作为 OS 句柄影子的资源边界；NIO Path/Files 生态仅点到为止。本文讨论的是 JDK 11 `java.io` 旧文件体系，不把这里的路径委托方式和 Unix 示例实现外推成所有平台、所有文件 API 都必须遵守的统一规范。
> **前置依赖**：[字节流与装饰器模式](01-byte-streams.md)、[Throwable 与 IO 异常边界](../06-exceptions/01-throwable-structure.md)
> **后续**：域 18 序列化

## 先看一个最常见、也最容易把 `File` 误会成“已经存在的文件对象”的直觉

很多人第一次写 `new File("a.txt")` 时，脑子里隐含的模型其实非常像“我现在拿到了一个文件对象”。这也是为什么后续看到 `exists()`、`length()`、`createNewFile()` 时，会自然觉得这些操作像是在对象自己身上“问一问”或“做一做”。

真正的问题是：`File` 从一开始就不是“已经打开的文件”，甚至也不是“已经确认存在的文件实体”。它首先只是一段**路径抽象**——一串还要交给平台文件系统去解释的文本。只要这层边界没看清，后面关于 `createNewFile()` 为什么能原子、为什么删除目录常失败、为什么不关流会把 fd 用光，都会被误讲成“Java 文件对象的怪脾气”。

所以这篇的主线不是罗列 `File` 的常用方法，而是先把这三条边界立住：

- `File` 本身主要在描述路径；
- 真正触盘的事情都委托给平台 `FileSystem`；
- 真正稀缺的外部资源不是 File 对象，而是 `FileDescriptor` 背后的 fd 句柄。

## 一、为什么 `new File(...)` 不会先碰磁盘：File 的第一身份是路径抽象

### 先拆掉“构造 File 就是在打开文件”的误解

如果 `File` 真代表一个“活的文件对象”，那它的构造过程至少得确认路径是否存在、是文件还是目录、当前有没有权限打开它。但现实是，`new File(...)` 往往在这些事一概未知时也能顺利返回。这说明构造阶段做的根本不是“打开文件”，而只是把路径表达先准备好。

JDK 11 中：

- `File` 定义在 `File.java:148`
- 平台文件系统单例 `fs` 位于 `File.java:155`
- `getPath()` 在 `516`
- `getAbsoluteFile()` 在 `576`

这些入口已经足够说明：File 对象内部首要持有的是路径表示，而不是已经打开的 OS 句柄。绝对路径解析、相对路径拼接、规范化之类动作，主要都还是路径层的计算，而不是磁盘层的 I/O。

### 为什么这件事会直接影响你对后续 API 的理解

一旦接受“File 先是路径”，很多原本看起来奇怪的行为就都顺了：

- `new File("not-exist")` 为什么不会因为文件不存在就失败；
- `getPath()` / `getAbsoluteFile()` 为什么不需要真的去读文件内容；
- 同一个 File 既可能最后指向普通文件，也可能指向目录，甚至可能永远只是一条不存在的路径。

这也意味着，File 的很多方法不是在操作“这个对象里的文件”，而是在拿着这段路径去向底层文件系统提问或发命令。

## 二、为什么真正触盘的都要走 FileSystem：Java API 统一，平台语义下沉

### 先看为什么 File 不能自己知道“存不存在、多长、能不能独占创建”

路径只是字符串或路径片段的组合；“这个路径现在在不在磁盘上”“它对应的文件长度是多少”“能不能原子创建而不与别人冲突”这些都不是路径文本能自己回答的。这些问题天生要问操作系统和平台文件系统。

这就是 `java.io.FileSystem` 存在的原因。JDK 11 中：

- `FileSystem` 抽象类定义在 `FileSystem.java:34`
- `normalize`（`52`）
- `prefixLength`（`58`）
- `resolve`（`65` / `99`）

它把路径解释和具体触盘行为都抽成了一层平台委托接口。Java 层 `File` 统一提供 API 入口，而真正怎么落地、怎么问 OS、怎么处理平台差异，都下沉到具体 FileSystem 实现。

### 为什么 exists / length / createNewFile 都只是委托入口

这在 `File` 的几组方法上最明显：

- `exists()`（`File.java:823`）
- `length()`（`989`）
- `createNewFile()`（`1029`）

它们看起来像是 File 对象自己的能力，实际真正触盘的动作都交给了 `fs`。以 Unix 平台示例来看：

- `UnixFileSystem` 定义在 `UnixFileSystem.java:34`
- `getBooleanAttributes0()` 在 `250`
- `getLength()` 在 `261`
- `createFileExclusively()` 在 `266`

这说明 `exists`、`length`、`createNewFile` 在 Java 层只是统一入口；真正判断属性、读取长度、执行原子创建的，是平台侧实现。

### 为什么 `createNewFile()` 的原子性不能靠“先 exists 再创建”凑出来

这也是一个特别容易被误会的地方。很多人看到 `createNewFile()` 的语义是“存在则失败”，会直觉地把它想成：Java 先帮你调一次 `exists()`，如果不存在再创建。问题在于，这两步之间天然会有竞态窗口——你检查完不存在，别人立刻就可能先建出来。

JDK 11 之所以能提供这条语义，不是靠 Java 层拼 if 判断，而是因为底层直接走了 `createFileExclusively` 这样的独占创建路径。也就是说，**原子性来自平台原语，不来自 Java 自己先问再做。**

这一层很关键，因为它把“File 是路径、真正动作在 FileSystem”这条主线真正钉死了。

## 三、为什么目录 API 容易让人误会：它们看起来像高级操作，实际仍然保持了非常克制的语义边界

### `listFiles()` 为什么不是更底层的目录协议

目录操作尤其容易被误会成“Java 应该帮我做更多”。比如很多人直觉会觉得 `listFiles()` 比 `list()` 更底层、更接近系统调用。实际在 JDK 11 里：

- `list()` 在 `File.java:1137`
- `listFiles()` 在 `1257`

它们的关系更像是：先拿到目录项名列表，再把这些名字重新包装成一组 `File` 对象。也就是说，`listFiles()` 不是“另一个更底层的目录系统调用”，而是在 list 结果之上多包了一层“继续当作路径对象使用”的便利封装。

这再次呼应了前面的主线：`File` 的价值首先是路径抽象，所以很多目录 API 最终也还是在围绕“路径字符串 + 后续委托”组织，而不是跳出这套模型另起炉灶。

### 为什么 `mkdirs()` 和 `delete()` 特别容易暴露“你脑补了递归语义”这个坑

- `mkdirs()` 位于 `File.java:1390`
- `delete()` 位于 `1056`

`mkdirs()` 的语义相对符合大多数人直觉：缺失父目录就逐级创建。但 `delete()` 特别容易踩坑，因为很多人会本能觉得“删目录就该顺手把里面也删了”。JDK 这里恰恰非常克制：它只负责删除文件或空目录，不替你做整棵目录树的递归遍历清理。

这说明 File API 的很多危险点，不是实现奇怪，而是**调用者自己脑补了比 API 明确承诺更多的语义**。目录非空删不掉，并不一定先说明权限有问题，而很可能只是因为 Java 根本没答应帮你递归清空。

## 四、为什么 FileDescriptor 才是真正稀缺的资源影子：不关流泄漏的不是 File，而是 fd

### 先看为什么路径对象和打开句柄根本不是同一层资源

只要 `File` 还是路径抽象，就意味着真正和操作系统资源上限挂钩的，不会是这段路径字符串本身，而是“你后来把这条路径拿去 open 之后，系统给了你什么句柄”。这正是 `FileDescriptor` 要表达的层。

JDK 11 中：

- `FileDescriptor` 定义在 `FileDescriptor.java:48`
- 内部 fd 字段在 `50`
- 标准输入/输出/错误三个预置描述符在 `150` / `158` / `167`
- `valid()` 在 `176`

这说明 FileDescriptor 更像是 OS 资源句柄在 Java 里的影子。你真正会耗尽的不是 File 对象数量，而是进程能打开的 fd 上限。

### 为什么“关闭流”是在释放操作系统资源，而不是做对象礼貌动作

很多初学者把 close 理解成“良好习惯”，仿佛不关也只是 Java 对象晚点被 GC 而已。真正的问题在于：流对象最终大多都会围绕 FileDescriptor 和底层 open/close 工作。你不 close，泄漏的不是一个普通 Java 引用，而是一个进程级稀缺句柄。

因此“不关流会怎样”这道题真正该答的是：**不是 File 对象会堆积，而是底层 fd 资源会耗尽。** 这和前面字节流、字符流都能自然接上，因为无论你怎么包装、怎么桥接，底层只要真打开了外部资源，最后都得落回描述符这一层去释放。

## 五、四个最容易混掉的边界：File 不是已打开文件，createNewFile 不是 exists+create，delete 不是递归清理，泄漏的也不是 File 对象

在收网之前，先把这一篇最容易记错的四条边界压实。

第一，`File` 不是“已经打开的文件对象”。它首先只是一段路径表示：可能存在，也可能不存在；可能最后指向普通文件，也可能指向目录。构造 `File` 更多是在准备路径语义，而不是在占用外部资源。

第二，`createNewFile()` 也不是 Java 先 `exists()` 再创建的语法糖。它真正值钱的地方恰恰在于避免这两步之间的竞态窗口；如果只是先检查再创建，就根本没有资格承诺“存在则失败”的原子语义。

第三，`delete()` 更不是“帮你把目录树顺手清干净”的递归清理器。对很多调用者来说，这个误解特别危险，因为它会让人把目录非空删除失败误判成别的问题。其实 API 很克制：它默认不替你脑补整棵树的遍历和删除语义。

第四，资源泄漏的也不是 `File` 这段路径对象本身。真正会被进程上限卡住的，是后续打开流或通道后拿到的 `FileDescriptor`/fd。路径对象可以存在很多个而没有问题，真正昂贵的是已经向操作系统登记过的那个打开句柄。

把这四条边界记稳，`File` 体系就不会重新塌回“文件对象 API 有点怪”这种表面印象。它真正想表达的是三层分工：路径先被描述，平台再去解释，真正稀缺的外部资源最后由描述符层承载。

## 收网：File 是路径抽象，FileSystem 决定平台语义，FileDescriptor 才是 OS 资源影子

回到开头那个最容易误导人的直觉，现在已经能看清为什么 `File` 看起来像“文件对象”，实际却经常和你想的不一样了。因为它从一开始就不是“已经打开的文件”或“已经验证存在的实体”，而首先是一段待解释的路径。只有当你调用 `exists()`、`length()`、`createNewFile()`、`delete()`、`list()` 这些方法时，它才把这段路径交给 `FileSystem` 去问平台、做真正触盘动作。

这也把整篇的三层边界彻底收住了：

- `File` 负责路径抽象；
- `FileSystem` / `UnixFileSystem` 负责把路径解释成平台行为；
- `FileDescriptor` 负责承载真正会耗尽的 OS 句柄资源。

把整篇压成一张总图，就是：

```text
File
  → 路径表示
  → 构造时通常不触盘

FileSystem
  → 规范化/拼接路径
  → exists/length/create/delete/list 等真实平台动作

FileDescriptor
  → 打开后的 OS 句柄影子
  → 真正稀缺的外部资源
```

如果说前两篇讲的是“字节怎么流、字符怎么桥”，这一篇真正讲清的就是：**文件路径本身和真正外部资源不是一回事；路径解释、平台差异和句柄资源管理，才是 File 体系最容易被误会的三层边界。** 下一站进入域 18 时，我们就不再停留在“文件与流”上，而会看另一件更容易被误解的事：对象为什么能被整体写出去、再整体读回来，序列化到底在保存什么，又丢掉了什么。
