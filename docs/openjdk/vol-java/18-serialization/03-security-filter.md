# 反序列化安全：危险不在某个 bug，而在于数据能直接驱动对象恢复链

> 本文基于 JDK 11 `ObjectInputFilter`、`ObjectInputStream` 及默认反序列化流程。讨论范围聚焦反序列化攻击面、gadget 链机制、JDK9+ 过滤器、模式串限制与生产白名单实践；不展开具体第三方 gadget 链源码。本文讨论的是 JDK 11 自带反序列化防线，不把这里的过滤器接口、模式串能力和默认恢复路径外推成所有对象恢复框架都必须遵守的统一规范。
> **前置依赖**：[序列化协议与流程](01-protocol-flow.md)、[serialVersionUID 与自定义序列化](02-serialversion-custom.md)
> **后续**：域 19 Buffer 与 Channel

## 先看一个最容易把反序列化漏洞误讲成“某个库写错了”的错觉

很多人第一次听到“反序列化漏洞能直接 RCE”时，都会本能觉得：一定是某个框架、某个库、某个类本身写得很离谱，才会把一段字节流读成代码执行。这个判断只说对了一半。某些 gadget 库当然会放大问题，但真正更根本的危险，并不从某个单独 bug 开始，而是从反序列化机制本身的默认能力开始：**外部数据可以决定要恢复什么类、触发哪些钩子、构造怎样的对象图。**

只要你把这件事和上一章串起来，问题就会突然变得非常清楚：默认反序列化会按流里的类描述去恢复对象，恢复过程中还会自动跑 `readObject`、`readResolve` 等钩子。也就是说，`readObject()` 从来不是“被动读字节”这么简单，它是在**执行一条由数据驱动的对象创建与恢复链**。

这就是为什么反序列化安全不能靠“某个类没问题”来自证清白。只要不可信输入能进入 `ObjectInputStream`，而你的类路径上又恰好存在可被串起来的 gadget，对手就不需要往 JVM 塞新字节码，它只需要让你的程序帮它把一串“合法类的合法行为”按恶意顺序跑完。

所以这篇真正要讲的，是三件事：

- 反序列化危险为什么是机制级的，而不是偶发 bug；
- `ObjectInputFilter` 到底在恢复链上拦什么、怎么拦；
- 为什么生产实践里的正确答案几乎总是分层防线，而不是只拉一张黑名单。

## 一、为什么一段字节流能变成代码执行：危险来自“数据驱动对象恢复”本身

### 先看反序列化默认会替你做哪些事

上一章已经讲过，`ObjectInputStream.readObject0()` 会按流里的 type code 和类描述逐步恢复对象。JDK 11 中，关键入口是：

- `ObjectInputStream.java:1619`：`readObject0`
- `ObjectInputStream.java:1687`：普通对象读路径继续走向 `readOrdinaryObject`
- 再加上上一章已经建立过的 `readObject/readResolve` 钩子自动调用链

这意味着，只要你愿意把字节流交给默认反序列化流程，运行时就会主动替你做这些动作：

- 按数据声明的类名去找类；
- 构造对象壳体；
- 填充字段；
- 在合适时机自动调用恢复钩子。

这已经不是“读数据”那么温和，而是**让外部数据驱动了一套对象恢复执行流程**。

### 为什么 gadget 链不是“某个类单独作恶”，而是多个合法行为被恶意串起来

所谓 gadget 链，危险恰恰不在于某个类自己看起来就像恶意载荷，而在于攻击者能把多个类的合法副作用串成一条链。一个类在 `readObject` 里做集合重建，一个类在 hashCode/compareTo/transform 里又会触发别的调用，一个类最终能把参数喂进反射或命令执行。这些类单看都可能是完全正常的依赖库；可一旦顺序被不可信数据驱动起来，就会形成一条从“恢复对象图”到“执行危险调用”的路径。

这就是为什么删掉某一个已知 gadget 类库，并不自动等于“反序列化已经安全”——它最多只是切断了某一条已知链。真正的问题仍然在：**程序依旧允许不可信数据主导对象恢复流程。**

### 所以反序列化漏洞的两个前提为什么几乎总是天然满足

只要系统同时满足两件事，攻击面就成立：

1. 有不可信字节流能进入 `readObject`；
2. 类路径上存在足够丰富的可恢复类和潜在 gadget。

在大型 Java 应用里，这两个前提往往并不稀缺：网络入口、缓存、消息、文件导入都可能成为字节流入口；而类路径上则经常挂着大量框架、集合、反射、表达式或第三方库。也就是说，这不是“某些小众项目才会碰上”的漏洞模型，而是一种非常普遍的默认风险面。

## 二、ObjectInputFilter 为什么不是“安全替代”，而是给默认恢复链补上的护栏

### 先看它为什么要拦在恢复路径上，而不是事后补救

一旦对象已经被造出来、钩子已经开始执行，再想事后补救往往就太晚了。真正有意义的防线必须插在“**对象还没被接受进恢复流程**”的时候。JDK 9+ 引入 `ObjectInputFilter`，本质上就是在做这件事。

JDK 11 中：

- `ObjectInputFilter` 接口定义在 `ObjectInputFilter.java:103-119`
- `FilterInfo` 在 `126-176`
- 三态 `Status` 在 `184-197`

它最关键的方法是 `checkInput(FilterInfo)`。这已经说明过滤器的职责不是“读完了帮你检查”，而是**在反序列化沿途逐点裁决：这个类、这个数组、这个对象图深度、这个引用数量、这个流长度，现在还要不要继续让它往下恢复。**

### 为什么三态比布尔值更合理

`ALLOWED` / `REJECTED` 当然容易理解，真正容易被低估的是 `UNDECIDED`。它的意义在于：一个过滤器不必什么都管，它只需要对自己有把握的维度做裁决，其余问题交给后续过滤器或全局策略继续判断。

这使过滤器真正能被组合：你可以有一个只看类模式的规则、一个只看深度和数组长度的规则、一个只看特定业务 DTO 包的规则。它们不是互相覆盖，而是通过 `UNDECIDED` 形成一条更细粒度的护栏链。

所以 `ObjectInputFilter` 不是一个“单开关”，而是一套允许类、深度、大小、引用数等不同维度并行防守的裁决接口。

## 三、为什么模式串和四类 limit 正好对应两大攻击面：类模式防 RCE，资源限制防 DoS

### 先看为什么“只配类黑白名单”还不够

很多人一看到过滤器，第一反应就是“那我把危险类禁掉不就好了”。这当然是必要的一层，但远远不够。因为攻击不只有代码执行一种。就算你完全不利用 gadget 链，只要给 JVM 喂一个极深的对象图、一个巨大的数组声明、一个海量引用风暴，也足以把进程内存、栈深或 CPU 拖死。

这就是为什么 `ObjectInputFilter` 既支持类模式匹配，也支持多种规模限制。两类护栏分别在防完全不同的攻击面：

- **类模式**：防止不该进入恢复链的类被接受，主要对付 gadget / RCE 路径；
- **四类 limit**：防止资源炸弹，主要对付 DoS。

### 四类限制为什么不是随便凑出来的

JDK 11 中：

- 全局过滤器初始化路径在 `ObjectInputFilter.java:257-282`
- `setSerialFilter()` 在 `306`
- `createFilter()` 在 `383`
- `parseLimit()` 在 `575-594`
- 真正执行匹配与限制的逻辑在 `Global.checkInput()`（`615-656`）

这几类 limit 分别是：

- `maxdepth`：对象图深度上限
- `maxrefs`：引用数量上限
- `maxbytes`：已读流字节上限
- `maxarray`：数组长度上限

它们分别对应的真实风险也非常清晰：

- 深度炸弹会冲栈或制造极深恢复链；
- 巨型数组会直接吃内存；
- 海量小对象和句柄会拖爆引用表与 GC；
- 超大字节流会拉高带宽和对象恢复成本。

这说明这些 limit 不是“顺手加几个参数”，而是一套非常有针对性的 DoS 护栏。

## 四、为什么黑名单不够，白名单才是默认立场

### 先看黑名单为什么天然落后于 gadget 发现速度

黑名单的思路是：把已知危险类、危险包、危险库列出来，匹配到就拒绝。问题在于 gadget 链的世界不是一个固定清单。今天是 CommonsCollections，明天可能是别的表达式引擎、别的框架组件、别的反射桥接类。只要类路径够大，攻击者就会继续寻找新的合法组合。

所以黑名单天然是追着问题跑：你永远只能列出“已经被发现危险”的那部分，而不能证明“剩下的全都安全”。

### 白名单为什么更符合最小攻击面原则

白名单的思路恰好相反：只允许业务明确需要恢复的那一小撮类和包进入恢复链，其他一律不碰。这样一来，系统不再默认相信整个类路径都可以安全参与对象恢复，而是把攻击面主动压到最小。

这也是为什么生产实践里真正靠谱的顺序往往是：

1. 能不用 Java 原生反序列化就尽量不用；
2. 必须用时，优先白名单；
3. 再配上四类规模限制；
4. 再考虑黑名单作为补充防线，而不是主防线。

所以“黑名单还是白名单”不是风格选择，而是**默认信任范围到底放多大**的问题。

## 五、资源炸弹为什么和 RCE 同样重要：有时对手根本不想执行代码，只想把你的 JVM 拖死

### 先看为什么“没法 RCE 就安全了”是错觉

很多人一谈反序列化安全，注意力会全被远程代码执行吸走。可实际攻击里，资源耗尽往往更容易实现：不需要拼一条精妙 gadget 链，只要构造一个合法但极端的对象图、数组或引用数量，就能把 JVM 拖到 OOM、StackOverflowError 或长时间 Full GC。

这也是为什么类白名单虽然重要，却不能单独担当全部防线。它主要是在约束“哪些类能进来”，却不直接限制“这个对象图到底有多深、多大、多密”。

### 为什么 `filterCheck` 连“这次没新类”也照样要跑

JDK 11 中：

- `filterCheck` 入口在 `ObjectInputStream.java:1329`
- 过滤失败抛异常在 `1368-1369`
- 即使是处理句柄等“当前没有新类对象”的分支，也会在某些路径继续做无类维度检查，例如旧稿已指出的 `readHandle` 相关调用点。

这正说明过滤器从一开始就不只是类裁决器，而是一整套对象恢复预算控制器：哪怕这一步没有引入新类，也可能让总深度、总引用数、总字节数继续上涨，所以限制仍要生效。

这一层把安全问题真正从“类安全”扩展成了“**恢复过程的整体资源安全**”。

## 六、为什么生产实践一定是分层防线：禁用、白名单、限制、监控缺一不可

### 先看“装一个过滤器就万事大吉”的误解

ObjectInputFilter 很重要，但它不是魔法护身符。只要你继续允许不可信 Java 序列化流进入系统，过滤器做的也只是把“默认无边界恢复”改造成“有限制的恢复”。如果规则过宽、白名单失控、limit 过大或监控缺失，风险仍然会以别的方式出现。

### 真正靠谱的顺序是什么

生产上更可靠的顺序通常是：

- **第一层：能不用就不用**。不可信输入场景优先选纯数据协议，而不是 Java 原生对象恢复；
- **第二层：必须用时先白名单**。只允许业务 DTO 和极少数基础类型进入恢复链；
- **第三层：四类资源限制补齐**。深度、引用数、字节数、数组长度都要按业务量级设边界；
- **第四层：精简类路径**。少带一个潜在 gadget 库，就少一大片可组合材料；
- **第五层：异常与 reject 监控**。`InvalidClassException`、`StreamCorruptedException`、filter REJECTED 的频次暴涨，往往就是攻击或误配置信号。

这说明真正的安全答案从来不是单点修补，而是把默认“任何类都可恢复、对象图无限展开、资源无限消耗”的便利路径，层层改造成有边界的恢复流程。

## 七、五个最容易混掉的边界：反序列化不是读数据，gadget 不是单类后门，过滤器不是万能替代，黑名单不是默认答案，没法 RCE 也不等于安全

在收网之前，先把这一篇最容易记错的五条边界压实。

第一，反序列化不是“把字节读成对象值”这么温和。默认 `readObject` 路径会按流里的类描述去恢复对象、填充字段、触发钩子，所以它本质上是在执行一条由外部数据驱动的恢复链，而不是被动搬运数据。

第二，gadget 链也不是“某个类自己藏了后门”。更常见的现实是：多个正常类各自做着正常副作用，一旦被恶意数据按特定顺序串起来，就形成了危险调用路径。只盯单个知名库，会直接低估风险面的来源。

第三，`ObjectInputFilter` 更不是“有了它就可以放心接收不可信 Java 序列化流”的万能替代。它做的是加护栏，而不是抹掉机制本身的危险：规则过宽、白名单失控、limit 太大，都会让风险换一种形式继续存在。

第四，黑名单也不是默认答案。它只能追着已知危险类和已知链条跑，天然落后于新 gadget 组合的发现速度。真正符合最小攻击面的思路，是先从白名单收缩恢复范围，再让黑名单只做补充拦截。

第五，就算攻击者没法走到 RCE，也不等于系统安全。对象图深度炸弹、巨型数组、海量引用和超长流一样可以把 JVM 拖进 OOM、栈溢出或长时间 GC。反序列化安全真正要防的，从来就不只是“有没有执行代码”，还包括“恢复过程会不会把资源打爆”。

把这五条边界记稳，反序列化安全就不会重新塌回“某个库有没有洞”这种过窄印象。它真正要解决的是：默认对象恢复机制太愿意相信输入，而过滤器与生产白名单的任务，就是把这条默认便利路径重新收回到可控边界里。

## 收网：反序列化的危险不在某个类，而在“数据能驱动对象恢复链”；过滤器的价值则在于把这条链重新加上边界

回到开头那个错觉，现在已经能看清为什么反序列化安全从来不只是“某个库有洞”。真正危险的，是 Java 默认机制愿意替外部数据做太多事：按流里的类描述加载类、建对象、填字段、跑钩子。只要类路径上存在可以被串起来的合法副作用，这条“数据驱动对象恢复”链就可能被扭成 gadget 链。

而 `ObjectInputFilter` 的意义，不是让这个机制 magically 无害，而是在恢复路径上明确加护栏：

- 类模式决定哪些类根本不准进来；
- `maxdepth/maxrefs/maxbytes/maxarray` 决定这条恢复链最多能走多深、多胖、多重；
- 三态裁决让多层规则可以叠加，而不是互相覆盖。

把整篇压成一张总图，就是：

```text
默认反序列化
  → 按数据驱动类恢复与钩子调用
  → 风险 = gadget RCE + 资源 DoS

ObjectInputFilter
  → 类模式：拦不该恢复的类
  → limit：拦过深、过大、过多、过长的对象图
  → 三态裁决：让多层护栏并存

生产防线
  → 最好禁用
  → 必须用则白名单 + limit + 精简类路径 + 监控
```

如果说前两篇讲的是“协议怎么写、兼容怎么控”，这一篇真正补上的就是：**为什么默认便利路径本身就是攻击面，以及怎样把这条路径重新收回到你能承受的边界里。** 到这里，序列化这一域也算真正闭环了。
