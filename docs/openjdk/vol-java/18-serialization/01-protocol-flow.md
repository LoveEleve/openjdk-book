# 序列化协议与流程：为什么 `writeObject` 写出去的不是对象本身，而是一套对象图协议

> 本文基于 JDK 11 `ObjectOutputStream`、`ObjectInputStream`、`ObjectStreamConstants`、`ObjectStreamClass`。讨论范围聚焦流头、TC_/SC_ 标记、`writeObject0/readObject0` 分派、HandleTable 引用跟踪，以及默认字段序列化边界；`serialVersionUID`、自定义序列化与反序列化安全放到后续篇章。本文讨论的是 JDK 11 默认 Java 序列化协议，不把这里的协议码、句柄表和对象恢复方式外推成所有对象持久化框架都必须遵守的统一规范。
> **前置依赖**：[引用原子与对象图心智](../13-atomic/03-reference-updater.md)、[类加载与类型恢复边界](../07-classloader/01-delegation-model.md)
> **后续**：[serialVersionUID 与自定义序列化](02-serialversion-custom.md)

## 先看一个最容易把 Java 序列化误讲成“对象直接变字节”的场景

很多人第一次讲 `ObjectOutputStream.writeObject(obj)`，都会顺口说“把对象写成字节流”。这句话在非常粗的层面不算错，但如果真按这个理解往下想，很快就会撞墙：对象里有循环引用怎么办？两个字段都指向同一个共享子对象怎么办？异常时读侧怎么知道下一个字节该按字符串、数组还是普通对象解释？如果只是“把对象打平成一串字节”，这些问题根本没有答案。

这正是 Java 默认序列化最重要、也最容易被忽略的一点：**写出去的不是对象内存本身，而是一套能描述对象图、类型信息、共享引用关系和恢复顺序的二进制协议。**

所谓“对象图协议”，意思至少包括三件事：

- 它得先声明“我是什么协议、哪个版本”；
- 它得让读侧在不知道 Java 运行时对象的前提下，靠流内标记继续往下分派；
- 它得能在遇到共享引用和环时，不把同一个对象无限递归展开，而是改写成“第一次完整写、后续只写句柄”。

所以这一篇不把 `writeObject` 当成“黑箱 magic”，而是把它拆成一条更清楚的主线：为什么流头、TC_ 标记、类描述符和 HandleTable 会一起出现，才能让 `ObjectOutputStream` 写出去的是一套可恢复对象图的协议，而不是对象的扁平拷贝。

## 一、为什么序列化流一开始就要写 `STREAM_MAGIC` 和版本：协议身份必须先自报家门

### 先拆掉“读方反正会知道这是序列化流”的误解

如果你已经站在 Java 代码里写 `new ObjectInputStream(...)`，很容易产生一个错觉：读方当然知道接下来要读的是 Java 序列化内容，还需要什么额外身份声明？真正的问题在于，字节流本身并不会替你说话。只要没有魔数和版本，读方拿到一串字节就无法快速确认：这到底是不是 Java 序列化流，还是别的格式误喂进来了；就算是，它的版本是不是还能按当前实现规则解释。

所以任何严肃的二进制协议，都会先在流头声明“我是我”。Java 序列化也不例外。

### `writeStreamHeader` 为什么是整个协议的第一步

JDK 11 中，流头写入就在 `ObjectOutputStream.writeStreamHeader()`：

- `ObjectOutputStream.java:634-637`

它会先写两段短整型：

- `STREAM_MAGIC`（`ObjectStreamConstants.java:39`）
- `STREAM_VERSION`（`ObjectStreamConstants.java:44`）

`STREAM_MAGIC = 0xaced` 的意义非常直接：给这条字节流盖一个“我是 Java 序列化流”的签名章。版本号则进一步保证：读方不是只认得这个格式，还得认得当前这版格式。

这也说明序列化不是“对象自己怎么写都行”，而是先得进入一个可识别、可拒绝、可兼容判断的协议空间。

### 为什么这一步和 class/zip/jimage 的魔数设计是同一类思想

这条设计并不特殊。class 文件、zip、jimage 等等二进制格式，也都是先靠固定头标识协议身份，再靠版本或结构约束决定后续是否能安全解析。所以 `STREAM_MAGIC + STREAM_VERSION` 的价值不是“老格式遗留”，而是二进制协议最朴素也最必要的第一层边界：**先确定我是谁，再决定你能不能继续读。**

## 二、为什么流里需要 TC_/SC_ 标记：读侧不可能凭空知道下一个对象是什么类型

### 先看“对象直接平铺字段”这个失败方案为什么行不通

假设你真的按“对象直接变字节”去设计，那么读侧会立刻卡住：下一个字节序列到底代表 null、字符串、数组、普通对象，还是类描述符？如果没有显式类型码，反序列化方根本无法知道接下来该按哪一套规则解释数据。

这就是 `TC_` 标记存在的原因。JDK 11 在 `ObjectStreamConstants.java:57-130` 中定义了一系列类型码，例如：

- `TC_NULL`
- `TC_REFERENCE`
- `TC_CLASSDESC`
- `TC_OBJECT`
- `TC_STRING`
- `TC_ARRAY`
- `TC_ENUM`

它们的意义不是“帮文档起个名字”，而是在真正告诉读侧：**现在轮到按哪一套协议分支继续往下读。**

### 为什么这会让序列化流成为“自描述协议”

有了 TC_ 标记，读侧不需要事先知道“接下来一定是某某类”，而是可以顺着流里的 type code 一边读一边分派。这就是序列化流“自描述”的真正含义：类型信息不是只活在 Java 编译期，而是被显式写进了流里。

### SC_ 标志又在补什么层次的信息

只有“这是一段对象”还不够。对类描述本身，读侧还需要知道这个类是普通 `Serializable`、还是 `Externalizable`、是否声明了自定义 `writeObject` 数据块、是不是枚举。这就是 `SC_` 标志位存在的原因（`ObjectStreamConstants.java:150-176`）。

因此，自描述协议至少分两层：

- `TC_` 先告诉你“接下来是什么大类条目”；
- `SC_` 再告诉你“这个类描述具备哪些附加序列化能力”。

这也是为什么 Java 序列化流虽然胖，但它换来的正是：**读侧不需要外部 schema 文件，也能沿着流内元信息继续往下解释。**

## 三、为什么写按 Java 类型分派、读按协议码分派：两边各自握着不同的真相

### 写侧拥有运行时对象，所以它按 Java 类型路由

`ObjectOutputStream.writeObject()` 最终会走到 `writeObject0()`，JDK 11 关键路由在：

- `ObjectOutputStream.java:1102-1116`
- `ObjectOutputStream.java:1161-1177`

写侧手里明明白白拿着一个 Java 对象，所以它最自然的决策方式，就是按运行时类型来判断：这是 null？是字符串？是数组？是枚举？还是普通可序列化对象？然后再写出相应的 TC_ 标记和内容体。

也就是说，写侧的出发点是“**我知道自己手里是什么 Java 东西，所以我决定该写什么协议码**”。

### 读侧手里只有字节，所以它只能先按 TC_ 反推类型分支

反序列化恰好相反。`ObjectInputStream.readObject0()` 的分派核心在：

- `ObjectInputStream.java:1646-1687`

读侧在开始时并没有一个现成 Java 对象，它手里只有字节流，所以它必须先看下一个 TC_ 标记，再决定进入 `readNull`、`readHandle`、`readClassDesc`、`readString`、`readArray`、`readEnum` 还是 `readOrdinaryObject`。这就是为什么读侧分派必须是 `switch(tc)`，而不是“我猜下一个应该是什么类型”。

### 为什么这两套路由不是重复，而是镜像互补

写侧按 Java 类型决定写什么；读侧按协议码决定怎么读回来。两者不是在做同一件事，而是在 protocol 两端各自完成最自然的职责。这种镜像关系本身就说明：Java 默认序列化根本不是“内存对象直接倒出来”，而是一条明确设计过的读写对称协议。

## 四、为什么循环引用和共享引用不会把序列化写死：HandleTable 让“同一个对象只完整写一次”

### 先看没有句柄表会发生什么

这一步是整篇最重要的心智之一。假设对象 A 持有 B，B 又持有 A。如果写侧每次见到对象引用都立刻递归展开完整内容，那么写 A → 遇到 B → 写 B → 又遇到 A → 再写 A……这条链会无限递归，直到栈炸掉。就算没有环，只要两个地方共享同一个子对象，如果你每次都完整展开，也会把“共享同一性”写丢——读回来后变成两个互不相等的副本。

所以序列化协议绝不能只是“见对象就写对象”。它必须先回答：这个对象之前写过没有？如果写过，就不要再展开，而是引用回去。

### 为什么关键顺序是“先登记句柄，再写字段”

JDK 11 在 `ObjectOutputStream` 里专门维护了 `HandleTable`：

- `handles` 字段在 `ObjectOutputStream.java:176`
- `HandleTable` 实现主体在 `2239-2296`

它的作用非常直接：第一次遇到对象时给它分配句柄号，后续再次遇到时就能直接写 `TC_REFERENCE`。而最要命的细节是，写普通对象时这个登记动作必须发生在字段真正展开之前。`writeOrdinaryObject` 的关键顺序就在：

- `ObjectOutputStream.java:1404-1430`

也就是：先写 `TC_OBJECT`、类描述，再 `handles.assign(obj)`，然后才开始写字段数据。这样一来，如果字段内部再次绕回这个对象，`writeObject0` 一进来就能命中 `handles.lookup(obj)`，直接走 `writeHandle()`：

- `ObjectOutputStream.java:1194-1197`
- `baseWireHandle` 在 `ObjectStreamConstants.java:140`

这一点如果顺序反了——先写字段、后登记句柄——循环引用根本来不及被切断。

### 读侧为什么也要“先建壳再登记”

反序列化侧同样遵守镜像原则：一旦确定要读一个新对象，就要先创建可放字段的壳体并登记句柄，再继续读它的字段内容。JDK 11 里：

- `readHandle` 在 `ObjectInputStream.java:1797`
- `readOrdinaryObject` 在 `2194`
- 读侧先登记句柄的关键动作在 `2219`

这样，字段里一旦再次遇到 `TC_REFERENCE` 指回这个对象，读侧就能直接回表拿到同一个对象实例，而不是再次 new 一个副本。

这一层真正要记住的是：**句柄表不是压缩优化，而是对象图协议能保住共享同一性和环结构的基础设施。**

## 五、为什么默认只写非 static、非 transient 字段：协议保存的是实例可重建状态，不是所有内存痕迹

### 先看“对象里有什么就写什么”这个朴素想法为什么过头了

很多人第一次理解默认序列化时，会下意识觉得“对象里有哪些字段，就都写出去”。可一旦这么想，马上就会撞上两个问题：

- static 字段本来属于类级共享状态，不属于单个实例；
- transient 字段恰恰通常是那些你不希望进入持久化协议的临时、敏感或派生状态。

所以默认协议不可能是“全部内存状态照单全收”。

### Java 默认协议保留的是“实例可恢复字段”

JDK 11 的 `Serializable` 注释已经把边界说得很清楚：

- `Serializable.java:91-92`

默认机制恢复的是非 static、非 transient 字段。也就是说，默认协议关心的是“这个实例怎样被重建成等价的对象状态”，而不是“JVM 里当前所有可见位模式都要照抄出去”。

这也解释了为什么 `transient` 在实践里经常用来跳过缓存、句柄、密码明文、派生字段等内容——不是因为它们不重要，而是因为它们不属于默认协议应该托管的实例状态。

## 六、为什么反序列化不会按你的普通构造链重走：它要先造出能承接字段恢复的对象壳体

### 先看“readObject 等于 new 一个对象再调用构造器”这个误解

如果反序列化真的完全按普通 `new` 路径重走，那类层次里所有构造逻辑、校验、副作用都会一起再执行一遍，这既不总是可行，也不一定符合协议恢复的需求。反序列化的第一优先级并不是“像手写 new 一样构造”，而是“**先得到一个能承接后续字段填充的对象壳体**”。

### 为什么它只会回到第一个非序列化父类的无参构造器

JDK 11 的 `ObjectStreamClass` 在这点上讲得很明确：

- 说明性 Javadoc 在 `ObjectStreamClass.java:890-891`
- `getSerializableConstructor()` 在 `1396-1403`

它关心的是“第一个非序列化父类的可访问无参构造器”。原因很直接：序列化类自己的实例状态将由协议字段恢复来填充，而不是靠它自己的普通构造逻辑重新推导。只有当回到某个非序列化父类时，才需要借助构造器把更底层对象壳体合法立起来。

这条边界非常重要，因为它把“协议恢复对象图”和“业务构造逻辑执行”清楚分开了。也正因为如此，很多构造器里做副作用初始化的类，一旦进入序列化领域，就会暴露出预期差。

## 七、五个最容易混掉的边界：序列化不是内存转储，TC_REFERENCE 不是压缩花活，默认字段不是全部字段，反序列化不是普通 new，句柄也不是可有可无

在收网之前，先把这一篇最容易记错的五条边界压实。

第一，`writeObject` 不是把对象内存直接倒成字节。它写的是一套带流头、类型码、类描述和引用句柄的协议；少了这些元信息，读侧根本没法知道接下来该按什么规则继续解释字节。

第二，`TC_REFERENCE` 也不是一个“写小一点”的压缩技巧。它真正值钱的地方，是保住对象图里的共享同一性和循环结构。没有它，同一个子对象会被写成多个副本，环结构更会直接把递归写死。

第三，默认序列化也不是“对象里有什么字段就全抄出去”。协议默认关心的是实例可恢复状态，因此 static 不进来，transient 也会被明确排除。把这件事理解错，就会对缓存字段、敏感字段和派生字段的行为产生错觉。

第四，反序列化更不是普通 `new` 的另一种语法皮肤。它首先要做的，是先造出一个能承接字段恢复的对象壳体，而不是完整重放你的业务构造链。只要把这一步和普通构造逻辑混在一起，后面很多“为什么构造器没按我想的执行”的问题就会全部变模糊。

第五，句柄表也不是可有可无的实现细节。它是整个对象图协议能成立的基础设施：写侧靠它避免重复展开，读侧靠它复用同一个实例。没有这张表，Java 默认序列化最多只能表达一棵无共享、无环的树，而不是一般对象图。

把这五条边界记稳，默认序列化就不会重新塌回“对象变字节”的扁平印象。它真正做的是把对象图、类型信息和恢复顺序明确写成一份可读写对称的协议，而不是把 JVM 里的内存布局偷渡到另一端。

## 收网：默认序列化写出去的不是对象本身，而是一套可恢复对象图的协议

现在回到开头那个误解，就能看清为什么“writeObject 把对象写成字节”这句话只说对了最表面的一层。真正写出去的不是对象内存本身，而是：

- 先用 `STREAM_MAGIC` / `STREAM_VERSION` 声明这条流的协议身份；
- 再用 `TC_` / `SC_` 标记把每个条目的类型和能力写清；
- 再通过写侧按 Java 类型分派、读侧按 type code 分派，把协议两端对齐；
- 最后用 HandleTable 保住“同一个对象只完整写一次、后续只写句柄”的对象图语义。

把整篇压成一张总图，就是：

```text
writeObject
  → 写流头（magic/version）
  → 写 type code / class desc
  → 新对象先登记句柄再写字段
  → 再遇到旧对象只写 TC_REFERENCE

readObject
  → 校验流头
  → 按 TC_ 分派读法
  → 新对象先建壳并登记句柄
  → 读字段时命中句柄就复用同一对象
```

如果说这一篇解决的是“默认协议到底在写什么”，那下一篇就要继续往协议演进处走：类一旦改字段、改结构、想自定义写法，为什么 `serialVersionUID` 会变成兼容性的第一道闸门？`writeObject/readObject/readResolve` 又是怎样把默认协议改写成带版本和自定义恢复逻辑的协议扩展层。
