# volatile 为什么不保证原子性？

> 适用：Java 技术专家 / 高级工程师面试
> 关联正文：`40-java-lang/05-jmm-volatile-final`、`13-atomic/01-atomicinteger-cas`
> 版本边界：下文对 volatile 语义的引用基于 JDK 11 的 `java.util.concurrent` 包文档（`package-info.java:251-255`），不同版本可能不同。

## 题目

`volatile` 保证可见性，为什么 `volatile int x; x++` 还是错的？它到底保证了什么、不保证什么？

## 常见答法

> volatile 保证可见性，不保证原子性，所以 `x++` 会丢更新。

这个答法只说对了结论，但很多人没讲透"原子性"到底指的是什么、`x++` 为什么不是原子的。只背"volatile 不保证原子"，面试官一追问"那它保证原子的是什么？"就容易卡住。

## 追问一：`volatile int x; x++` 这行代码在 CPU/字节码层面是什么？

> 答：它不是一条指令，而是"读旧值 → 算新值 → 写回新值"三步。

对。`x++` 看起来是一个操作，实际包含三步：从内存读 `x`、加上 1、把新值写回 `x`。volatile 只保证"读"和"写"各自的可见性，不保证"读 + 改 + 写"这三步是一个不可分割的整体。

所以两个线程可能同时执行 `x++`，都在第一步读到同一个旧值（比如 5），各自算成 6，再都写回 6——最终结果是 6 而不是 7。这不是"看不到另一个线程写的新值"，而是"两个线程都基于同一个旧值做了读-改-写，后写回的人把前一个覆盖了"。

## 追问二：那 volatile 保证的"可见性"到底体现在哪？

> 答：一个线程对 volatile 字段的写，happens-before 另一个线程对同一字段的后续读。

对。JDK 11 的并发包文档明确写了这条规则：对 volatile 字段的一次写 happens-before 对同一字段的每一次后续读（`package-info.java:251-252`）。并且 volatile 字段的读写"在内存一致性效果上接近进入/退出监视器，但不涉及互斥锁"（`package-info.java:254-255`）。

这句话点出了 volatile 的边界：**它给了你"写 happens-before 后续读"这一跳的顺序保证，但没给你"互斥"——它不阻止多个线程同时走同一段读-改-写。**

## 追问三：那要保证 `x++` 不丢更新，该用 `synchronized` 还是 `AtomicInteger`？

> 答：要么把读-改-写放进同步块，要么用原子类的 CAS 循环。

`synchronized` 用互斥锁把"读 + 改 + 写"变成临界区内的原子动作；`AtomicInteger` 用 CAS 循环让"只有在我读到的值还是预期的值时，我才写回"成为原子判定。两条路都能解决，但场景不同：

- 需要和别的 `synchronized` 块协调、或涉及多个变量的复合更新：用锁
- 只想让单个整数的读-改-写原子、且竞争不激烈：用 `AtomicInteger`

这里真正的分界是：**volatile 只保证单次读写的可见性，单靠它保护不了复合更新；复合更新要么交给锁、要么交给 CAS，而 CAS 本身还要叠在一个 volatile 字段上。**

## 源码证据

- volatile 写 happens-before 后续读（`package-info.java:251-252`）：可见性保证的正式表述
- volatile 读写"接近监视器但不互斥"（`:254-255`）：点出 volatile 与锁的本质区别
- 对照 `AtomicInteger`：它在 `volatile int value` 之上再套 CAS 循环，补的是原子不是可见性

## 一句话顿悟

**volatile 保证的是"一次读或一次写"在 happens-before 链上的可见性，不是"读 + 改 + 写"作为一个整体的原子性。** 面试官真正想听的不是你会背"volatile 不保证原子"，而是你能说出 `x++` 三步拆分、以及为什么可见性升级成原子性必须靠锁或 CAS。
