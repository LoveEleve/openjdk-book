# String 的 hashCode 为什么乘 31？

> 适用：Java 技术专家 / 高级工程师面试
> 关联正文：`01-string/02-equals-hashcode-compare`
> 版本边界：下文引用的 `StringLatin1.java`、`StringUTF16.java` 行号均为 JDK 11 源码，不同版本可能不同。

## 题目

String 的 hashCode 计算方法是 `h = 31 * h + char`，为什么乘数是 31 而不是 37、17、或别的质数？

## 常见答法

> 31 是一个质数，可以减少哈希碰撞。而且 31 可以写成 `(i << 5) - i`，JVM 可以优化成位运算。

这个答法方向对，但"质数"和"可优化"这两个理由都不是 31 独有的。37 也是质数，`(i << 5) + (i << 2) + i` 也能优化。真正的问题不是"31 是不是质数"，而是"**在有效分布和计算性能之间，为什么 31 比 17、37 更优**"。

## 追问一：为什么乘数必须是奇数？用偶数会怎样？

> 答：偶数乘法会导致低位归零，因为偶数乘法相当于移位，低位信息会丢失。

对。如果乘数是偶数，比如 32，`h * 32` 相当于 `h << 5`，低 5 位直接被清零。哈希值只取决于高位的字符，低 5 位永远不变，冲突会急剧增加。

所以乘数必须是奇数。但光奇数不够，还必须是**质数**——因为质数乘法在模运算下保留更多的分布特性。31 是质数，而且不大不小，正好。

## 追问二：为什么是 31 不是 37、不是 17？

> 答：31 在分布和性能上取了一个折中。17 太小，碰撞概率相对高；37 的乘法 `(i << 5) + (i << 2) + i` 需要三条指令；31 的 `(i << 5) - i` 只要两条。

JDK 11 的 `StringLatin1.hashCode()`（`StringLatin1.java:193-196`）和 `StringUTF16.hashCode()`（`StringUTF16.java:346`）都用的 31。31 的二进制是 `11111`，`31 * i` 可以拆成 `(i << 5) - i`——一次移位加一次减法，比 37 的 `(i << 5) + (i << 2) + i` 少一次加法。

在大量字符串的 hashCode 计算中，少一次整数运算的累积效果是显著的。而且经验验证表明，31 在常见字符串分布下产生的碰撞率与 37 基本相同，但性能更好。

## 追问三：那 31 的乘法会不会溢出？

> 答：会，但溢出不影响——Java 的 int 溢出是归零，等效于模 2^32 运算，不影响哈希分布。

对。`h = 31 * h + char` 中的 `31 * h` 可能超过 `Integer.MAX_VALUE`，溢出后自动归零，相当于在 `2^32` 空间做模运算。这是有意的，不是"bug"——哈希值本来就不需要精确的数学结果，只需要在 `2^32` 空间内分布均匀即可。

## 源码证据

- `StringLatin1.hashCode(byte[])`（`StringLatin1.java:193-196`）：`h = 31 * h + (v & 0xff)`，Latin-1 编码的哈希计算
- `StringUTF16.hashCode(byte[])`（`StringUTF16.java:346`）：UTF-16 编码的哈希计算，乘数同样是 31
- 31 的二进制 `11111`，`31 * i = (i << 5) - i`：JVM 可优化为一次移位加一次减法

## 一句话顿悟

**31 不是"随便选的质数"，而是"分布和性能折中后的最优解"——它既是奇数质数保证低位信息不丢失，`(i << 5) - i` 又只需要两条指令，比 37、17 在碰撞率和计算成本上更均衡。** 面试官真正想听的不是你会背"31 是质数"，而是你知道为什么是奇数、为什么是质数、以及为什么是 31 不是 37 不是 17。
