# ConcurrentHashMap 的 `get()` 为什么不需要加锁？

> 适用：Java 技术专家 / 高级工程师面试
> 关联正文：`10-concurrent-collections/01-chm-storage-rw`
> 版本边界：下文引用的 `ConcurrentHashMap.java` 行号均为 JDK 11 源码，不同版本可能不同。

## 题目

ConcurrentHashMap 的 `get()` 方法为什么不需要加锁？它怎么保证读线程不会读到写了一半的数据？

## 常见答法

> 因为 Node 的 val 和 next 是 volatile 的，读线程能直接看到最新值。

这个答法方向对，但太笼统。volatile 只保证"写 happens-before 读"这一跳，并没有解释为什么读线程在遍历链表时不会被写线程的并发修改搞乱。真正的问题不是"能不能看到最新值"，而是"**读线程在一个其他线程正在修改的链表上遍历时，结构会不会被破坏**"。

## 追问一：那读线程正在遍历链表时，写线程在链尾插了一个新节点，能读到吗？

> 答：不一定能读到，但结构不会坏。

这个答案很关键。"不一定能读到"是因为 `get()` 是弱一致性，不保证读到刚刚插入的节点。但"结构不会坏"是因为 CHM 节点类的 `val` 和 `next` 用 volatile 修饰（`ConcurrentHashMap.java:625-629`），写线程通过 `setTabAt`（`:768`）把新节点发布出去时，用的是 release 语义的匹配；读线程通过 `tabAt`（`:759`）读桶入口时，用的是 acquire 语义。所以读线程看到的 `next` 链指针，要么是完整的旧链，要么是已经接上新节点的链，**不会出现"指向一个写了一半的节点"这种中间态。**

## 追问二：那如果读线程撞上了扩容，桶里放的是 ForwardingNode 呢？

> 答：get() 会跟着 ForwardingNode 的 nextTable 去新表里继续找。

对。JDK 11 的 `get()` 在定位桶时，如果发现桶入口的 hash 是负值（`MOVED`、`TREEBIN`、`RESERVED`），就调用那个节点的 `find()` 方法去处理。对于 `ForwardingNode`，它的 `find()` 会去 `nextTable` 上继续查找。

所以 `get()` 不用加锁，也是因为它**不需要阻止扩容**——它不需要等扩容结束，也不需要让写线程停下来，它只需要知道"当前这个桶去哪找"就够了。

## 追问三：那什么时候 `get()` 才需要加锁？

> 答：不需要。CHM 的 get() 从设计上就承诺不加锁。

这个答案是"CHM 的 get() 不加锁"不是"CHM 不加锁"。写路径（put、remove、resize）在冲突时仍然会锁桶首节点。读路径之所以可以不加锁，是因为它依赖了三层发布协议：

1. `volatile Node<K,V>[] table`（`:778`）：读线程看到的是当前有效的表引用
2. `tabAt`（`:759`）用 acquire 语义读桶入口，`setTabAt`（`:768`）用 release 语义写桶入口——桶位的发布是有序的
3. 节点的 `val` 和 `next` 是 volatile 的（`:625-629`）：链表的连接和值的更新对读线程可见

这三层加在一起，让读线程在**不加锁**的前提下，能安全地走完"定位桶 → 遍历链表 → 确认 key → 读 val"的整条路径。

## 源码证据

- `get()` 入口（`:934`）：无锁，全程无 synchronized 或 lock
- `tabAt()`（`:759`）：acquire 读桶入口
- `setTabAt()`（`:768`）：release 写桶入口
- `ForwardingNode.find()`：扩容期间把读路径导向新表
- `Node.val` / `Node.next` 为 volatile（`:625-629`）：链表指针和值的可见性保证

## 一句话顿悟

**CHM 的 `get()` 不加锁，不是因为"volatile 就够了"，而是因为一条完整的发布协议把桶引用、桶入口、节点指针和节点值四级都安排成了"读线程要么看到旧值，要么看到已发布完成的新值，绝不存在中间态"。** 面试官真正想听的不是你会背"volatile 保证可见性"，而是你知道这一层两层三层分别保证什么、以及扩容时读线程为什么不需要停下来等。
