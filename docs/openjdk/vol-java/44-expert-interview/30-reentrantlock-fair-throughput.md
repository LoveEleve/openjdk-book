# 为什么 `ReentrantLock` 的公平锁吞吐通常更低？

> 适用：Java 技术专家 / 高级工程师面试
> 关联正文：`12-juc/01-aqs-reentrantlock`
> 版本边界：下文引用的 `ReentrantLock.java`、`AbstractQueuedSynchronizer.java` 行号均为 JDK 11 源码，不同版本可能不同。

## 题目

为什么很多人都说 `ReentrantLock` 的公平锁更“讲秩序”，但吞吐通常不如非公平锁？慢到底慢在哪？

## 常见答法

> 因为公平锁要排队，非公平锁可以插队，所以公平锁更慢。

这个答法方向对，但太口号化。**真正的差别不只是“能不能插队”，而是公平锁在每次竞争获取时都要先检查队列前驱，尽量把锁交给排在最前面的等待线程；非公平锁则允许刚到的线程直接 CAS 抢锁。** 这会带来更多排队唤醒、线程切换和缓存局部性损失，所以吞吐通常更低。

## 追问一：源码里“公平”和“非公平”到底差在哪？

> 答：差在 `tryAcquire` 里要不要先看 `hasQueuedPredecessors()`。

`ReentrantLock` 的非公平路径 `nonfairTryAcquire(...)`（`ReentrantLock.java:126-143`）在锁空闲时，直接 `compareAndSetState(0, acquires)` 抢锁，不先看等待队列。

而公平锁 `FairSync.tryAcquire(...)`（`ReentrantLock.java:213-221`）在 `state == 0` 时，先判断 `!hasQueuedPredecessors()`，也就是确认自己前面没人排队，才去 CAS 抢锁。

所以两者的本质区别不是 API 层面的“公平/不公平”标签，而是：**非公平锁优先减少一次排队；公平锁优先维护队列顺序。**

## 追问二：为什么“维护队列顺序”会伤吞吐？

> 答：因为它更容易把本来可以直接拿锁的线程送进等待/唤醒流程。

假设锁刚释放，当前 CPU 上正好有一个新来的线程在运行。非公平锁可以让它直接 CAS 抢到锁，省掉一次挂起/唤醒切换；公平锁却要先看队列里有没有前驱，只要队列头还有人排着，就必须老老实实让前面的线程来。

问题在于：**队列头那个线程未必此刻就在 CPU 上。** 为了讲顺序，系统可能需要把它唤醒、调度回来、再让它获取锁。这种“为了公平而强制交棒”的过程，通常比“谁先抢到谁上”付出更多上下文切换和调度成本。

## 追问三：那公平锁是不是就没有价值？

> 答：不是。它牺牲吞吐，换的是更可预测的等待顺序和更低的饥饿风险。

非公平锁的好处是吞吐通常更高，尤其在短临界区、高竞争场景下更明显；但代价是某些线程可能反复抢不过“刚到的线程”。公平锁则尽量按队列顺序发放锁，等待时间分布更稳定，不容易让某个线程长期挨饿。

所以选型本质是：**你要的是系统整体吞吐，还是等待顺序的可预测性。** 大多数业务代码默认用非公平锁更划算；只有在确实关心饥饿或等待顺序时，公平锁才值得那部分吞吐损失。

## 源码证据

- `nonfairTryAcquire(...)`（`ReentrantLock.java:126-143`）：锁空闲时直接 CAS 抢
- `NonfairSync.tryAcquire(...)`（`ReentrantLock.java:198-200`）：非公平路径入口
- `FairSync.tryAcquire(...)`（`ReentrantLock.java:213-221`）：先检查 `hasQueuedPredecessors()` 再 CAS
- `hasQueuedPredecessors()`（`AbstractQueuedSynchronizer.java`）：公平判定依赖 AQS 队列前驱检查

## 一句话顿悟

**`ReentrantLock` 公平锁吞吐更低，不是因为“公平”这两个字抽象上更贵，而是因为它在每次竞争获取时都更尊重等待队列，减少了插队，却增加了排队唤醒和线程切换成本。** 面试官真正想听的不是你会背"公平锁更慢"，而是你知道慢在 `hasQueuedPredecessors()` 背后的调度路径选择。
