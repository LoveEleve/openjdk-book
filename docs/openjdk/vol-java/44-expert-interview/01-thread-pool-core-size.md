# 线程池核心线程数到底该怎么定？

> 适用：Java 技术专家 / 高级工程师面试
> 关联正文：`14-threadpool/01-ctl-worker`、`05-executors-selection`
> 版本边界：下文引用的 `ThreadPoolExecutor.java:1342-1355`、`:1533-1551`、`:1042` 均为 JDK 11 源码行号，不同版本可能不同。

## 题目

一个线程池，核心线程数设多少？最大线程数设多少？队列用有界还是无界？

## 常见答法

> CPU 密集型：N + 1（N = CPU 核数）；IO 密集型：2N。队列用无界 LinkedBlockingQueue，避免拒绝。

这是面试界流传最广、也最容易被追问到卡住的一句话。它的问题不在于"数据不对"，而在于**它把"线程数"当成了独立的调优变量，忽略了队列、maxPoolSize、keepAliveTime、任务类型这四个变量与 corePoolSize 的联动关系。**

## 追问一：N+1 中的"1"是给谁的？

> 答：补偿页缺失或 GC 等系统损耗。

这个答案只能算及格。N+1 的"1"不是给 GC 的，而是给**计算线程偶尔被调度走、缺页中断、或其他系统抖动**留的缓冲。如果线程一直在跑纯计算，N 个线程就已经把 CPU 占满了，第 N+1 个线程并不会增加吞吐，只会增加上下文切换。所以 N+1 不是什么"公式"，而是一个"在充分压测前的保守起点"。

而且这个公式的前提是：**任务全是 CPU 密集、且没有阻塞、没有 IO、没有锁等待**。一旦任务中有任何阻塞点，N+1 就不成立了。

## 追问二：那 IO 密集型为什么是 2N？

> 答：因为 IO 密集时线程大部分时间在等 IO，可以多开一些线程让 CPU 在等待期间干别的活。

这条逻辑对，但"2N"这个乘数是怎么来的？在 IO 等待时间占比为 50% 时，2N 刚好能让 CPU 一直有活干。如果 IO 占比是 90%，2N 远远不够；如果 IO 占比是 10%，2N 就太多了。

所以 2N 不是公式，而是"假设 IO 等待时间和 CPU 计算时间差不多"这个假设下的一个特例。真实场景里，IO 占比各不相同，正确的做法是：**用压测或 APM 先拿到阻塞时间比，再用公式 `线程数 = N × (1 + 等待时间 / 计算时间)` 推导起点，再用压测调优。**

## 追问三：那 corePoolSize 和 maxPoolSize 到底谁先起作用？

> 答：核心线程优先，然后队列，然后非核心线程，最后拒绝。

这个顺序本身没错，但很多人只背了顺序，却不知道这个顺序的后果：**当 corePoolSize 设得偏大时，队列缓冲几乎不起作用，压力直接去到非核心线程创建；当 corePoolSize 等于 maxPoolSize 时（如 newFixedThreadPool），队列满了就等于拒绝——没有"扩非核心线程"这个阶段。** 所以 corePoolSize 不是独立参数，它决定了"队列缓冲窗口"的大小。

## 源码证据

- `ThreadPoolExecutor.execute()` 的四步决策链（`ThreadPoolExecutor.java:1342-1355`）：先试 core，再试 queue，再试 max，最后 reject
- `setCorePoolSize` 缩小 core 时只杀空闲 worker，不杀在跑的任务（`ThreadPoolExecutor.java:1533-1551`）
- `getTask()` 里 `timed` 标志决定走 `poll` 还是 `take`，`timed` 又由 `allowCoreThreadTimeOut` 和 `workerCount > corePoolSize` 共同决定（`ThreadPoolExecutor.java:1042`）

这些源码事实说明：**corePoolSize 不是"并发上限"，而是一个"常驻 worker 基线 + 队列缓冲窗口的边界"。** 调大 core 不会自动让系统变快，调小 core 也不会自动让系统变慢——它只是改变"任务优先走哪条路"的阈值。

## 一句话顿悟

**算线程数不是目标，控制"任务在队列里等多久、占多少线程、被拒绝时退回得有多快"才是。corePoolSize 只是这条链上的第一个阈值，不是"并发度"的承诺。** 面试官真正想听的不是你会背 N+1，而是你知道这个公式的假设在哪里、什么时候会失效、以及怎么用源码和压测去验证它。
