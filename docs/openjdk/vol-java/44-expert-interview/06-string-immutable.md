# String 为什么是不可变的？

> 适用：Java 技术专家 / 高级工程师面试
> 关联正文：`01-string/01-storage-immutable`
> 版本边界：下文引用的 `String.java` 行号均为 JDK 11 源码，不同版本可能不同。

## 题目

String 为什么被设计成不可变的？不可变到底保护了什么？

## 常见答法

> 因为 String 被声明为 final class，且内部的 char[] / byte[] 被 final 修饰，所以不可变。

这个答法只答了"怎么做到的"，没答"为什么这么设计"。真正的问题不是"String 怎么做到不可变"，而是"**JDK 的设计者为什么愿意付出不可变带来的所有拼接成本，也要把 String 设计成不可变的**"。回答这个，需要从四个维度来说。

## 追问一：不可变跟常量池有什么关系？

> 答：不可变保证常量池里的字符串不会被意外修改。

这是最直接的安全维度。字符串常量池让多个引用可以共享同一个字符串对象。如果 String 是可变的，一个引用改了字符串内容，所有指向同一个常量的引用都会受影响，这会直接摧毁常量池共享的安全前提。

所以不可变的第一条价值是：**让常量池共享成为可能**——多个引用指向同一个字符串对象是安全的，因为谁都不能改它。

## 追问二：不可变跟 hashCode 的缓存有什么关系？

> 答：因为不可变，hashCode 可以缓存，不用每次算。

对。JDK 11 的 `String.hashCode()`（`String.java:1501`）有一个 `hash` 字段做缓存：第一次调用时计算一次并缓存，之后直接返回缓存的 `hash`。如果 String 是可变的，改完内容后 hashCode 必须重新计算，那缓存就没有意义了。

String 是 HashMap 最常用的 key，它的 hashCode 缓存对 HashMap 的 put/get 性能有直接贡献。不可变让这个缓存成立，也让 String 最适合做 HashMap 的 key。

## 追问三：不可变对线程安全的影响是什么？

> 答：不可变对象天然线程安全，不需要同步。

这是最简单但最容易被忽略的维度。String 的 byte[] 是 `private final`（`String.java:140`），构造完成后就没人能改它。所以多个线程可以同时读同一个 String，不需要加锁，也没有竞态。这个特性在参数传递、日志、配置、类加载等场景里，让 String 成为"最安全的共享对象"。

## 追问四：那不可变付出的代价是什么？JDK 怎么解决？

> 答：每次拼接都创建新对象，代价是 O(n) 复制。JDK 用 StringBuilder 和编译期优化来解决。

对。这就是不可变的代价——每次 `+` 拼接、`substring`、`replace` 都创建新对象。JDK 的应对方式有三条：

1. 编译期常量折叠：`"a" + "b" + "c"` 直接变成 `"abc"`，零运行时开销
2. 变量拼接时 javac 自动生成 `StringBuilder` 链
3. 可变的 `StringBuilder` / `StringBuffer` 作为替代品，让开发者在不要求不可变的场景下自己选

所以不可变不是"无代价的"，而是"JDK 帮你把最常见的代价摊掉了，剩下的代价由你选 StringBuilder 来承担"。

## 源码证据

- `String` 是 `final class`（`:125`）——不能被继承
- `byte[] value` 是 `private final`（`:140`）——内部数组引用不可改，且不暴露给外部
- `byte coder` 是 `private final`（`:153`）——编码标志位也不可变
- `hashCode()` 缓存 `hash` 字段（`:1501`）——不可变让缓存成立

## 一句话顿悟

**String 不可变不是一个"实现细节"，而是一个"设计决策"——它同时让常量池共享、hash 缓存、线程安全三类受益成为可能，并把拼接的代价交给了 StringBuilder 和编译期优化去承担。** 面试官真正想听的不是你会背"String 是 final 的"，而是你知道不可变不是一个"顺带的事"，而是为了换回那三个受益，有意为之。
