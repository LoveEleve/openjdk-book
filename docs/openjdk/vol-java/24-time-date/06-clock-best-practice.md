# Clock 与时间最佳实践：为什么 `now()` 也是依赖，而不是一个应该被到处写死的常量入口

> 本文基于 JDK 11 `Clock` 及 `Instant/LocalDate/LocalDateTime/OffsetDateTime/ZonedDateTime` 的 `now(Clock)` 入口。本文聚焦时间源抽象、固定/偏移/tick 时钟与工程实践；系统调用与 OS 时钟来源只作边界说明。本文讨论的是 JDK 11 `java.time` 的时间源抽象与工程实践，不把这里的 Clock 工厂、UTC/偏移/地区分层和注入方式外推成所有时间库都必须遵守的统一规范。
> **前置依赖**：[组合时间类型](05-zoned-offset.md)、[格式化与解析](04-formatter-parse.md)
> **后续**：域 32 Unsafe 与本地内存

## 先看一个最容易被忽略的依赖：很多代码里的“现在”其实是硬编码进去的

业务代码里最常见的一类时间写法，就是直接在逻辑深处调用：

- `System.currentTimeMillis()`
- `Instant.now()`
- `LocalDate.now()`
- `LocalDateTime.now()`

表面看，这些写法只是“拿一下当前时间”，似乎无可厚非。但一旦代码进入测试、跨时区部署、回放历史数据、或者需要稳定断言的场景，问题马上出现：你以为自己依赖的是业务规则，实际上还偷偷依赖了**当前机器、当前时区、当前执行瞬间**。

也就是说，`now()` 从来不是空气。它本身就是一份外部依赖，只是平时被写成了静态调用，看起来不像依赖而已。

这正是 `Clock` 的价值所在。它做的不是“把系统时间再包一层”，而是把“现在从哪来”这件事显式化，让业务代码可以把当前时间源当作一个可注入、可替换、可冻结的对象来使用。

## 一、为什么 `Clock` 抽象的不是“时间值”，而是“当前时间源”

### 先看它的核心入口

JDK 11 里：

- `Clock` 类定义在 `Clock.java:140`
- 抽象方法 `instant()` 在 `Clock.java:444`
- 通用毫秒入口 `millis()` 在 `431`
- 系统时钟工厂 `systemUTC()` / `systemDefaultZone()` / `system(ZoneId)` 在 `160` / `183` / `202`

这组 API 连起来看，Clock 的本体其实非常朴素：它不是一个“时间值对象”，而是一个“给我当前 instant”的时间源抽象。

### 为什么这一步很关键

一旦“当前时间”被抽象成对象依赖，而不是硬编码静态调用，时间就从“只能现场获取”变成了“可以由外部提供”。这会直接改变代码的控制权：

- 业务逻辑不必自己决定“现在从哪来”；
- 测试可以决定“现在固定在哪一刻”；
- 基础设施可以决定“统一使用 UTC 还是某个 zone 视图”；
- 同一段业务逻辑可以在不同时间源策略下复用。

所以 Clock 的关键不是多了几个工厂方法，而是它把“当前时间来源”从隐式全局状态，变成了显式依赖。

## 二、为什么 `now(clock)` 才是真正的依赖注入落点：时间值对象并不要求你只能读系统时间

### 先看时间类型如何接住 Clock

旧稿已经抓到了两个很关键的入口：

- `LocalDate.now(clock)` 在 `LocalDate.java:227`
- `Instant.now(clock)` 在 `Instant.java:287`

这条设计思路并不只存在于这两个类型里，而是贯穿整个 `java.time` 体系：时间值对象并不要求你只能依赖全局系统时间，它们普遍提供了接收 `Clock` 的 `now(clock)` 入口。

### 为什么这比“手动传 long 时间戳”更自然

当然，你也可以在更高层先取一次时间戳，再把它作为参数一路传下去。但 `now(clock)` 的优势在于，它把时间源控制直接纳入时间 API 自身：你仍然是在构造 `Instant`、`LocalDate`、`ZonedDateTime` 这些语义明确的值对象，只是“现在”不再被硬编码成系统默认来源。

这意味着依赖注入没有破坏时间类型体系，反而和它自然对接上了。业务逻辑拿到的仍是正确语义的时间对象，只是这些对象的“当前值”来自一个可控制的 clock。

## 三、为什么 `fixed`、`offset`、`tick` 不是一些零散工厂，而是三种不同的时间源控制策略

### `fixed`：把时间冻结，换来可重复测试

JDK 11 里，`Clock.fixed(...)` 在 `Clock.java:348`。它解决的问题非常直接：当你的测试需要断言“当前时间等于某个确定值”时，真实系统时钟只会制造抖动，而不会带来任何价值。

这时最重要的不是“时间继续流动”，而是“同一段逻辑多次跑得到同样结果”。`fixed` 就是在把时间冻结成一个确定 instant，让测试断言脱离执行时机。

### `offset`：在已有时间源上整体平移

`Clock.offset(...)` 在 `Clock.java:374`。它不是冻结时间，而是在已有 clock 基础上整体加减一个 `Duration`。这种策略适合模拟“快进”“回拨”之类场景：基础时间源仍然存在，但你希望站在它之前或之后一段距离去观察逻辑。

所以 offset 的重点不是提供“另一个 now”，而是为已有时间源增加一个系统性偏移视角。

### `tick`：用精度换稳定可见时间

`tickMillis` / `tickSeconds` / `tickMinutes` 在 `Clock.java:231` / `255` / `278`，通用 `tick(...)` 在 `313`。它们的核心不是让时钟更精确，恰恰相反，是**主动降低可见时间精度**，把读取结果截断到某个粒度边界。

这带来的好处是：

- 同一个 tick 内多次读取可能得到相同值；
- 某些低频刷新、缓存键或测试场景会更稳定。

代价也同样明确：你失去了更细粒度的时间变化。所以 tick 适合“我不需要每纳秒都变”的场景，不适合高精度超时控制或精细耗时统计。

## 四、为什么“直接调系统时间”会让测试和生产边界混在一起

### 测试需要的是可控时间，不是“真实现在”

在单元测试里，很多逻辑真正想验证的是：

- 过期判断是否正确；
- 时间窗口是否命中；
- 重试是否按预期推进；
- 展示时间是否按指定 zone 格式化。

这些断言需要的是稳定、可复现的时间输入，而不是和真实系统时间强绑定。直接写死 `Instant.now()` 会把测试的成败交给执行瞬间，结果往往是：断言脆弱、边界难测、偶发失败难复现。

### 生产需要的是统一纪律，不是每处各自决定“现在”

到了生产环境，问题又变成另一种形态：不同模块如果到处自行读取当前时间，就很难统一时间源策略、统一时区视图，也更难在需要时切换为可观察、可回放的时间控制方式。

所以 Clock 的价值不是只在测试里才出现。测试只是最早暴露问题的地方，本质上它解决的是“当前时间由谁控制”的系统设计问题。

## 五、为什么“存 UTC、传偏移、显地区”是整个时间域最稳的工程收束

### 存储层：先保唯一时间点

前面几篇已经把这个结论铺得很清楚：真正适合作为存储底座的，是唯一时间点语义。所以存储层优先考虑 `Instant` 或 UTC 语义，本质上是在优先保存“事实发生在哪一刻”，而不是先保存展示视角。

### 传输层：既要可恢复事实时间，又要格式标准化

跨系统传输时，光有本地字符串不够，光有地区名也未必总够。更稳的策略是传标准化的、可恢复唯一时间点的表示。很多场景里，ISO-8601 带偏移文本或 `OffsetDateTime` 语义，是比裸本地时间更可靠的交换边界。

### 展示层：最后再投影到用户地区规则

用户真正关心的通常不是 UTC 自身，而是“我所在地区看到的是几点”。这时才把存储层的时间点重新投影成 `ZonedDateTime`，再交给 `DateTimeFormatter` 按本地规则输出。这样，展示语义就不会反过来污染存储与传输语义。

把这三层压缩成一句工程纪律，就是：**存 UTC，传偏移，显地区。**

## 六、为什么“只存本地时间字符串”是最差实践之一：它把前面五篇刚建立的语义边界一次性全打碎了

只存一段本地时间字符串，看起来最直观，实际上问题最多。因为它同时丢掉了：

- 唯一时间点信息；
- 偏移信息；
- 地区规则来源；
- Gap/Overlap 下的消歧能力。

也就是说，一旦只有“2026-03-29 02:30:00”这样的本地文本，你甚至不一定知道它是否存在、是否唯一、是否能稳定还原成事实时间。

这正是本域前五篇一层层建立起来的边界：

- `Instant` 负责唯一时间点；
- `OffsetDateTime` 负责带偏移的事实时间；
- `ZonedDateTime` 负责地区规则语义；
- `DateTimeFormatter` 负责把它们稳定转成文本；
- `Clock` 负责把“现在从哪来”也纳入可控范围。

如果最后又退回“存本地字符串”，等于把整套语义体系重新揉回一团。

## 七、五个最容易混掉的边界：now 不是空气，Clock 不是时间值，fixed 不只是测试技巧，tick 不是性能开关，UTC/偏移/地区也不是同一层东西

在收网之前，先把这一篇最容易记错的五条边界压实。

第一，`now()` 不是空气。每一次直接调用 `Instant.now()`、`LocalDateTime.now()`，都等于把当前机器、当前瞬间、当前默认时区的时间源硬编码进了业务逻辑，只是这种依赖平时不显眼而已。

第二，`Clock` 也不是另一个时间值类型。它抽象的不是“时间本身”，而是“现在从哪来”这件事；你真正拿来做比较、存储和展示的仍然应该是 `Instant`、`LocalDate`、`ZonedDateTime` 这些值对象。

第三，`fixed` 也不只是测试小技巧。它本质上是在把“当前时间”变成一个稳定输入，从而让依赖 now 的逻辑可复现、可断言、可回放。测试场景只是最直观的落点，它解决的是整个时间源控制权问题。

第四，`tick` 也不是单纯的性能开关。它主动降低可见时间分辨率，换来更稳定、更粗粒度的读数语义；所以它改变的不只是实现成本，也改变了调用者看到的时间行为。

第五，UTC、偏移、地区规则更不是同一层东西。存储层优先保存唯一时间点，传输层常带偏移恢复事实时间，展示层才再投影回地区规则。把这三层揉成“一个本地字符串”去存，会把前面整域刚拆开的语义一次性重新搅乱。

把这五条边界记稳，Clock 这一篇就不会重新塌回“时间 API 的一个工具类”这种表面印象。它真正补上的，是整个时间体系最后一块隐形地基：不只时间值要分清语义，连“当前时间从哪来”也要被显式管理。

## 收网：`Clock` 让时间 API 最后缺的那一块也显式化了——不仅时间值要分清语义，连“现在从哪来”也要分清

现在可以把整个 `24-time-date` 域压成一张收官图：

- `LocalDate` / `LocalTime` / `Instant` 先拆开日期、本地时刻、时间点；
- `Duration` / `Period` 再拆开时间线跨度与日历跨度；
- `ZoneRules` 把时区从字符串变成规则系统；
- `DateTimeFormatter` 把格式器做成可共享的不可变执行计划；
- `OffsetDateTime` / `ZonedDateTime` 解决本地时间如何落到时间线；
- `Clock` 最后把“当前时间源”也变成显式依赖。

所以这篇真正收住的，不只是一个 `Clock` API，而是整个时间体系的工程纪律：

- 语义先分层；
- 时间点先确定；
- 文本输出放在边界层；
- 当前时间源不要硬编码；
- 存储、传输、展示各自用对自己的时间类型。

这也是为什么 `now()` 不该被看成一个无害的小工具调用。它和时区、偏移、格式化一样，都是时间语义的一部分。只不过 `Clock` 让这部分第一次变得可以被显式管理。

时间域到这里收官。下一步自然转向另一类“看起来像 Java 标准库，但其实直接踩在 JVM 与 OS 边界上”的主题：`Unsafe`、堆外内存与直接缓冲区。这就是后续域要继续展开的问题。
