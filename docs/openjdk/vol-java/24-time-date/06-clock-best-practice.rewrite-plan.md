# 24-time-date/06 重写规划

> 状态：重写前计划
> 适用规范：`docs/openjdk/WRITING-GUIDELINES.md`
> 版本边界：JDK 11 `Clock` 及 `Instant/LocalDate/LocalDateTime/OffsetDateTime/ZonedDateTime` 的 `now(Clock)` 入口。本文聚焦时间源抽象、固定/偏移/tick 时钟与工程实践；系统调用与 OS 时钟来源只作边界说明。
> 目标：把“Clock 与时间最佳实践”改写成一篇围绕“`now()` 不是天然常量，而是业务代码对‘当前时间源’的一次隐式依赖；`Clock` 的价值在于把这份依赖显式化、可注入、可替换、可测试”展开的机制文章。

## 1. 读者困惑

- 为什么很多业务代码不该到处直接写 `System.currentTimeMillis()` 或 `LocalDateTime.now()`？
- `Clock` 到底抽象了什么，它只是对系统时间的薄封装吗？
- `Clock.fixed(...)`、`offset(...)`、`tick(...)` 分别解决什么问题？
- 为什么同样是“当前时间”，生产展示和测试断言对时间源的要求完全不同？
- 时间最佳实践为什么总强调“存 UTC、传偏移、显地区”？

## 2. 一句话顿悟

**时间里的 `now()` 也是依赖。直接调用系统时间，相当于把“当前时间源”硬编码进业务逻辑；`Clock` 做的不是多包装一层 API，而是把这份依赖变成一个可注入对象，让“现在从哪来”这件事可以被替换、被冻结、偏移、取整，并通过 `now(clock)` 入口传进所有时间值类型。**

## 4. 理解路径

### 第一节：从“为什么业务代码到处直接调 now 会让测试失控”开场

用最常见痛点开场：同一测试里两次 `now()` 结果不稳定、过期逻辑难断言、跨时区环境结果漂移。先立住总问题：现在时间源被隐式硬编码了。

### 第二节：Clock 为什么是在抽象“当前时间源”

证据：
- `Clock.java:140`：类定义
- `Clock.java:444`：`instant()`
- `Clock.java:431`：`millis()`
- `Clock.java:160/183/202`：系统时钟工厂

主线：
- Clock 的本体是“给我当前 instant”。
- `systemUTC` / `systemDefaultZone` / `system(zone)` 只是不同视角的系统时钟入口。
- 这把“现在从哪来”从静态调用变成了对象依赖。

### 第三节：为什么 `now(clock)` 是真正的依赖注入落点

证据：
- 旧稿里的 `Instant.java:287`、`LocalDate.java:227`
- 需在正文中强调 `LocalDate/Instant/...` 都提供 `now(Clock)` 入口

主线：
- 时间值类型并不要求你只能依赖全局系统时间。
- 通过 `now(clock)`，业务代码可以把当前时间来源统一外置。
- 这解决的是可测试性和环境一致性，而不是语法偏好。

### 第四节：fixed / offset / tick 为什么是三种不同的替换策略

证据：
- `Clock.java:348`：`fixed`
- `Clock.java:374`：`offset`
- `Clock.java:231/255/278/313`：`tick*` / `tick`

主线：
- `fixed` 适合确定性测试：时间冻结。
- `offset` 适合在已有时钟基础上整体平移。
- `tick` 适合降低可见精度，换稳定读取；代价是精度损失。
- 三者不是“更多 now 写法”，而是三种不同的时间源控制策略。

### 第五节：为什么“存 UTC、传偏移、显地区”是整个时间域的工程收束

主线：
- 存储层关心唯一时间点 → `Instant` / UTC。
- 传输层关心事实时间可恢复与标准文本 → `OffsetDateTime` / ISO-8601。
- 展示层关心用户地区语义 → `ZonedDateTime` + `DateTimeFormatter`。
- 这正好把前五篇所有语义边界收成一套工程纪律。

### 第六节：为什么不要只存“本地时间字符串”

主线：
- 没有 offset/zone 的本地字符串无法唯一还原时间点。
- Gap/Overlap 会进一步放大这类歧义。
- 这是最差实践的根因，不只是风格问题。

## 5. 失败方案清单

1. 在业务代码深处直接多次调用 `System.currentTimeMillis()` / `now()`。
2. 用真实系统时间驱动单元测试断言。
3. 用 tick 时钟做需要最高精度的超时控制。
4. 只保存本地时间字符串，期待之后总能还原真实时间点。
5. 在展示层直接复用存储层时间表示，不做地区转换。

## 6. 误解清单

1. `Clock` 只是 `System.currentTimeMillis()` 的面向对象包装。
2. 测试里只要 sleep 一下，就不需要 `Clock.fixed(...)`。
3. `tick` 只是性能优化，不改变可见语义。
4. 统一存本地时间比存 UTC 更直观，所以更安全。
5. 传输里只要字符串长得像日期，就足够跨系统交换。
