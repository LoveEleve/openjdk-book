# 核心值类型：为什么 java.time 要先把日期、本地时间、时间点拆成不同对象

> 本文基于 JDK 11 `LocalDate`、`LocalTime`、`Instant`。本文聚焦三类核心值类型的字段布局、工厂方法、不变式与语义边界；时区、格式化与运算放到后续篇章。本文讨论的是 JDK 11 `java.time` 核心值类型设计，不把这里的类型拆分方式和不可变策略外推成所有日期时间 API 都必须遵守的统一规范。
> **前置依赖**：[值对象与不可变性基础](../03-object-system/01-object-contract-references.md)、[编码与文本表示](../01-string/04-encoding-unicode.md)
> **后续**：时间运算

## 先看一个最常见、也最容易被旧 API 误导的时间建模错误

很多系统里其实同时存在三种完全不同的时间概念：

- 用户生日、账期、节假日——只关心“哪一天”；
- 每天 09:30 开盘、23:00 跑批——只关心“一天里的什么时刻”；
- 日志时间戳、消息发送时刻、数据库提交点——关心的是全局唯一时间点。

旧 API 时代，大家常常把这些东西都塞进 `Date`、`Calendar` 这种大而全的类型里，再靠注释、约定和转换逻辑去弥补语义上的混乱。结果就是：本来就不该混在一起的概念，被迫挤进同一个对象模型里，时区、可变性、格式化、副作用一起搅成一团。

这正是 `java.time` 的起点。它的最大改进不是“API 更现代”，而是先做了一件更基础的事：**把日期、本地时刻、时间点这些本来就不同的语义先拆开，再让每种语义都用不可变值类型去承载。**

所以这篇不会先讲“怎么调用 now/of/parse”，而是先讲这三个核心值类型为什么必须分家：`LocalDate` 负责日期，`LocalTime` 负责一天里的墙上时间，`Instant` 才负责 UTC 纪元上的唯一时间点。只有这层语义拆分先立住，后面 Duration、ZoneId、Formatter、Clock 才有落脚点。

## 一、为什么 `LocalDate` 只管日期：它根本不试图表达“这一刻”

### 先看它到底存了什么

JDK 11 的 `LocalDate` 用三个 final 字段保存日期：

- `year`（`LocalDate.java:175`）
- `month`（`179`）
- `day`（`183`）

边界常量在：

- `MIN`（`LocalDate.java:146`）
- `MAX`（`151`）

构造入口则走工厂方法，例如 `of(...)` 在 `LocalDate.java:267`。这套结构已经说明得非常明确：LocalDate 的世界里没有时区、没有几点几分、没有 epoch 秒，只有日历日期本身。

### 为什么这不是“功能少”，而是“语义更干净”

生日、账期、节假日、结算日这些值，本来就不该隐含“一天中的具体时刻”或“全球唯一时间点”。如果你硬让它们背上时区和钟点语义，很多错误反而更容易发生：看似多了信息，实际是在混入不该存在的解释空间。

所以 LocalDate 的价值不在于它“只有三字段”，而在于它明确拒绝承载自己本不该表达的东西。它只回答“哪一天”，别的问题留给别的类型去表达。

这也是类型设计最重要的第一条线索：**越核心的值对象，越不该通过“多塞一点字段以防万一”来求全。**

## 二、为什么 `LocalTime` 只管“一天里的时刻”：它不是时间点,只是墙上时间

### 先看它的字段本体

JDK 11 的 `LocalTime` 用四个字段表示一天中的时刻：

- `hour`（`LocalTime.java:221`）
- `minute`（`225`）
- `second`（`229`）
- `nano`（`233`）

这说明它关注的是“今天钟表上显示到哪一格了”，而不是“这在全世界唯一对应哪一瞬间”。

### 为什么营业时间适合它，日志时间戳却不适合它

比如“每天 09:30 开盘”这种业务规则，本来就只依赖一天内部的时刻结构，不依赖是 2026-03-01 还是 2026-03-02。LocalTime 表达这种语义非常合适。

但你如果拿 `LocalTime` 去表达“这条日志是何时发生的”，就会立刻丢失最关键的信息：到底是哪一天、哪个时区下的 09:30？它最多只是一天中的某个墙上时刻，而不是一个能跨机器、跨时区、跨日期唯一定位的时间点。

所以 LocalTime 的边界非常清楚：**它描述的是钟表上的时刻，不是历史时间线上的坐标。**

## 三、为什么 `Instant` 才是真正的时间点：UTC 纪元上的唯一坐标不能靠本地日期/时间凑出来

### 先看它的存储模型

JDK 11 的 `Instant` 用两个字段表示时间点：

- `seconds`（`Instant.java:253`）
- `nanos`（`258`）

其中 `EPOCH` 常量在 `Instant.java:213`，工厂入口 `ofEpochSecond(...)` 在 `303`。这套模型的关键意义是：它把“时间点”直接放回了 UTC 纪元坐标系，而不是放在某个本地日历/钟表视角里。

### 为什么它和 `LocalDate` / `LocalTime` 不是同一层问题

`Instant` 表示的是“全世界统一时间线上的哪个点”；`LocalDate` 和 `LocalTime` 表示的是“本地日历看到的是哪一天、钟表看到的是几点”。二者互转时一定要经过时区，就是因为：**同一个 Instant，在不同 Zone 下可能落到不同的日期和本地时间。**

这说明“日期 + 时间”并不会自然等于“时间点”。只要没有时区偏移语义，这个组合仍然只是局部视角，不能自动映射回一条全球统一时间线。

### 为什么 `Instant` 的纳秒字段不等于系统一定有纳秒精度

很多人看到 `Instant` 里有 `nanos`，会顺手把它理解成“比旧 `Date` 更高精度，所以系统时钟就真能纳秒级测量”。这又是一个很常见的误会。`Instant` 的 `nanos` 首先是**表示精度模型**的一部分：它允许一个时间点携带比毫秒更细的分量。但这并不自动承诺底层硬件时钟、操作系统调用或当前环境真的能提供纳秒级稳定精度。

也就是说，类型能表示得更细，不等于现实世界就能测得同样细。把“表示能力”和“实际时钟精度”分开，是使用 Instant 时必须保留的边界感。

## 四、为什么这三个类型必须分开：不是 API 喜欢碎片化，而是时间语义本来就不该混在一起

### 先看如果继续用一个大而全类型会发生什么

如果继续延续旧 API 的“一个对象尽量全包”思路，你就会不断在对象里塞：日期、时刻、时区、纪元含义、可变运算、格式化辅助……表面上像是功能完整，实际每次使用时都得先问一句：我现在需要的是其中哪一层语义？其余字段会不会误导调用者？

这正是旧时代 `Date` / `Calendar` 容易让人犯错的根源：**概念没有被类型本身强约束，只能靠调用者记忆上下文。**

### 类型拆分本质上是在把错误前置到编译期和建模期

当你选择 `LocalDate`、`LocalTime`、`Instant` 这些更窄的值类型时，很多错误会被更早暴露：

- 你没法拿 `LocalTime` 假装这是全球唯一时间点而不显式补别的信息；
- 你没法拿 `Instant` 直接表示“每天 09:30”这类本地规则而不再做转换；
- 你没法把“生日”和“日志时间戳”继续塞进同一种“差不多”的时间对象里。

所以 java.time 的真正价值是：**把时间语义分裂的问题，前置到类型选择这一步，而不是留给运行时注释和约定去补。**

## 五、为什么不可变是这套类型体系的默认姿势：值对象只有稳定，才值得共享和复用

### 先看不可变不是锦上添花，而是地基

这几个核心类型之所以都强调 final 字段、工厂方法和无 setter，不是因为“函数式风格更优雅”，而是因为时间值天然更适合作为**值对象**存在：一旦一个日期/时刻/时间点被构造出来，它就应该是稳定的、可复用的、可安全共享的。

这带来的直接收益包括：

- 线程安全更自然，不需要为了读一个日期值再额外同步；
- 值语义更清晰，对象本身可以放心在多个层次间传递；
- API 设计可以把“修改时间”统一表达成“返回一个新值”，而不是原地变形旧值。

### 为什么这也解释了它和旧 API 的根本分野

旧 API 的很多麻烦，不只是时区和语义混乱，还有可变对象在多线程和复用场景下带来的副作用。`java.time` 在这里的思路非常一致：先把语义拆开，再把每种语义装进不可变值类型。这样，时间 API 就不只是“叫法更现代”，而是从根基上换了一种建模哲学。

## 六、五个最容易混掉的边界：LocalDate 不是一天中的某刻，LocalTime 不是时间点，Instant 不是本地日历，纳秒字段不等于时钟精度，不可变也不只是线程安全彩蛋

在收网之前，先把这一篇最容易记错的五条边界压实。

第一，`LocalDate` 不是“某一天零点”的变体。它根本不试图表达一天中的任何时刻，更不会偷偷替你选一个时区里的午夜。它只负责日历日期，这正是它能把生日、账期、节假日这类语义守干净的原因。

第二，`LocalTime` 也不是时间点。它只说明钟表上的时刻，不说明是哪一天、哪个时区下的这个时刻。把它直接拿去表示日志事件发生时间，本质上就是把“墙上时间”误当成“全局坐标”。

第三，`Instant` 反过来也不是本地日历对象。它表达的是 UTC 时间线上的唯一位置，所以一旦你要把它解释成“今天几点”或“哪一天”，就必须显式引入时区视角。离开 Zone 去谈 Instant 的本地语义，本来就没有答案。

第四，`Instant` 里的纳秒字段也不等于系统时钟天然就有纳秒级真精度。它首先是表示模型足够细，可以承载更细分量；至于底层时钟能不能真的提供这种精度、稳定性和分辨率，是另一层平台事实。

第五，不可变更不是“顺手带来的线程安全加分项”这么轻。它是这整套值类型设计的地基：只有值稳定，`LocalDate`、`LocalTime`、`Instant` 才值得被缓存、共享、跨线程传递，并且让所有“修改”统一变成“返回一个新值”的风格。

把这五条边界记稳，java.time 的核心值类型就不会重新塌回“把旧 Date 拆成几个现代类”这种表面印象。它真正先做的，是把不同时间语义拆开，再用不可变值对象把这些语义各自钉死。

## 收网：java.time 真正先做的，不是多给你几个类，而是先把日期、本地时间、时间点拆成不同不可变值类型

回到开头那个建模错误，现在已经能看清为什么 `java.time` 的第一步不是“把 Date 改得更好用”，而是直接拆类型。因为生日、每日营业时间、日志时间戳本来就不是同一种东西：一个只需要日历日期，一个只需要一天内时刻，一个则必须是 UTC 时间线上的唯一坐标。继续把它们塞进同一种宽泛对象里，错误只会不断往后拖。

这也把整篇的主线完全收住了：

- `LocalDate` 只表达日期；
- `LocalTime` 只表达一天中的本地时刻；
- `Instant` 才表达真正的时间点；
- 不可变设计让这些值可以安全共享、稳定传递；
- 更细的表示精度不等于底层时钟就真有同样精度。

把整篇压成一张总图，就是：

```text
日期语义
  → LocalDate

墙上时间语义
  → LocalTime

全球唯一时间点语义
  → Instant

三者都走不可变值对象路线
  → final 字段
  → 工厂校验
  → 线程安全共享
```

如果说这一篇解决的是“为什么时间语义必须先拆开”，下一篇就会继续沿着这条线往下走：一旦值类型已经拆好了，`Duration` 和 `Period` 又为什么还要分开？它们都像“时间长度”，却为什么一个按秒和纳秒计，一个按年/月/日计，这就是 `02-duration-period.md` 要继续回答的问题。
