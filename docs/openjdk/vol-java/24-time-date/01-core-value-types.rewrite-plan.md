# 24-time-date/01 重写规划

> 状态：重写前计划
> 适用规范：`docs/openjdk/WRITING-GUIDELINES.md`
> 版本边界：JDK 11 `LocalDate`、`LocalTime`、`Instant`。本文聚焦三类核心值类型的字段布局、工厂方法、不变式与语义边界；时区、格式化与运算放到后续篇章。
> 目标：把“核心值类型”改写成一篇围绕“为什么 java.time 不再用一个 Date/Calendar 包打天下，而是先把日期、本地时间、时间点拆成不同不可变值类型”的机制文章。

## 1. 读者困惑

- 为什么 `java.time` 要把 `LocalDate`、`LocalTime`、`Instant` 拆成多个类型，而不是继续用一个统一日期时间对象？
- `LocalDate` / `LocalTime` / `Instant` 各自到底在表达什么，为什么不能混着用？
- 这些值类型为什么都强调不可变，它的工程收益到底是什么？
- `Instant` 明明有纳秒字段，为什么还不能简单等同于“系统时钟真有纳秒精度”？
- 为什么 `LocalDateTime` 或 `LocalTime` 单独都不是“全球唯一时间点”？

## 2. 一句话顿悟

**java.time 的核心改进不是“API 更新”，而是先把时间语义拆开：`LocalDate` 只表示日期，`LocalTime` 只表示一天内的墙上时间，`Instant` 才表示 UTC 纪元上的唯一时间点。每个类型都尽量用 final 字段和工厂校验维持不可变与不变量，这样才能把“日期”“本地时刻”“时间点”这些本来就不该混在一起的概念彻底隔离。**

## 3. 旧稿优点与问题

### 保留

- 已覆盖 `LocalDate`、`LocalTime`、`Instant` 的核心字段和工厂入口。
- 已指出 `Instant` 与本地日期/时间互转必须经过时区，这是关键边界。
- 已把旧 API 的可变性与语义混乱作为对照，方向是对的。

### 必须重写

- 旧稿偏“类一段段介绍”，需要先建立总问题：为什么新 API 要把时间语义拆开。
- 三个值类型要放在同一条“语义分层 + 不可变设计”主线上，不宜各自孤立背字段。
- 旧 API 对照要更明确落到“为什么 Date/Calendar/SimpleDateFormat 容易混语义或线程不安全”。
- 需要更清晰地把“不可变”从口号落到线程安全、复用与值语义收益上。

## 4. 理解路径

### 第一节：从“为什么一个 Date 不够”开场

用最常见混淆开场：生日日期、一天中的营业时间、日志里的全球时间戳，这三类东西语义完全不同，却常被一个 Date/Calendar 混着表达。先立总问题：java.time 先拆语义，再谈 API。

### 第二节：LocalDate 为什么只保留“日历日期”这层语义

证据：
- `LocalDate.java:146/151`：`MIN` / `MAX`
- `LocalDate.java:175/179/183`：`year/month/day`
- `LocalDate.java:267`：`of(...)`

主线：
- 只表达年/月/日，不携带时区与一天中的时间。
- 工厂方法负责校验不变量，字段 final 保证不可变。
- 这是“生日/账期/自然日”这类值的正确归宿。

### 第三节：LocalTime 为什么只表达“一天里的时刻”

证据：
- `LocalTime.java:221/225/229/233`：`hour/minute/second/nano`
- 对应工厂入口（旧稿已提，可在重写时按需补精确位置）

主线：
- 它只描述 24 小时内的墙上时间，不包含日期与时区。
- 因而它非常适合营业时间、每日触发时刻等场景，但天然不能代表一个全球唯一时间点。

### 第四节：Instant 为什么才是真正的“时间点”

证据：
- `Instant.java:213`：`EPOCH`
- `Instant.java:253/258`：`seconds/nanos`
- `Instant.java:303`：`ofEpochSecond(...)`

主线：
- `Instant` 的本体是 epoch 秒 + 纳秒调整量。
- 它表达的是 UTC 基准上的唯一时间点，而不是本地时间感觉。
- 纳秒字段是表示精度，不是对硬件时钟精度的自动承诺。

### 第五节：为什么三者必须分开，而不能靠一个统一类型凑合

主线：
- `LocalDate`、`LocalTime` 缺少时区上下文，不能单独映射到唯一时间点。
- `Instant` 反过来又不适合直接表达“某地日历上的某一天”或“某天里的 09:30”。
- 这说明类型拆分不是 API 设计师的洁癖，而是语义边界本来就不同。

### 第六节：为什么不可变是这套设计的默认姿势

主线：
- final 字段 + 工厂校验让值对象一旦构造完成就不会变形。
- 这带来线程安全、缓存复用和“值语义”上的稳定性。
- 对照旧 API 的可变性，解释为什么 `java.time` 天然更适合多线程共享。

## 5. 失败方案清单

1. 用一个统一日期时间对象同时表达生日、营业时间和日志时间点。
2. 把 `LocalTime` 或 `LocalDateTime` 当作全局唯一时间点使用。
3. 看到 `Instant` 的纳秒字段就以为底层时钟一定有纳秒精度。
4. 依赖可变日期对象在多线程间共享并修改。
5. 把时区转换问题拖到最后，先混用本地日期/时间和时间点。

## 6. 误解清单

1. `java.time` 的改进主要是类名更现代。
2. `LocalDate`、`LocalTime`、`Instant` 只是拆得更碎，用哪个都差不多。
3. 不可变只是线程安全加分项，对语义设计影响不大。
4. `Instant` 一定比旧 `Date` 更精确地反映底层时钟。
5. 只要有一个日期和一个时间，就自然构成唯一时间点。
