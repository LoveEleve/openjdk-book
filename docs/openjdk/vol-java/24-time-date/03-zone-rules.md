# 时区体系：为什么 `Asia/Shanghai` 不等于 `+08:00`

> 本文基于 JDK 11 `ZoneId`、`ZoneOffset`、`ZoneRules`、`ZoneOffsetTransition`、`ZonedDateTime`。本文聚焦时区标识、固定偏移、规则查询、Gap/Overlap 歧义与规则数据来源；格式化与解析放到后续篇章。本文讨论的是 JDK 11 `java.time` 时区规则体系，不把这里的区域 ID、规则查询路径和 tzdb provider 方式外推成所有日期时间库都必须遵守的统一规范。
> **前置依赖**：[核心值类型](01-core-value-types.md)、[时间运算](02-duration-period.md)
> **后续**：格式化与解析

## 先看最常见的误解：把时区当成一个字符串，或者当成一个固定偏移值

很多系统在设计时间字段时，会下意识把“时区”理解成一段附加信息：要么存个区域名，比如 `Asia/Shanghai`，要么存个偏移，比如 `+08:00`。表面看两者都像是在回答“这是哪个时区”，但实际上它们根本不是同一种东西。

- `+08:00` 说的是：相对 UTC 快 8 小时；
- `Asia/Shanghai` 说的是：去查上海这套地区规则，在你关心的那个时刻，它到底该偏移多少。

也就是说，一个是已经算出来的结果，一个是拿去查规则的入口。把这两者混为一谈，就会在夏令时、历史规则变更、跨地区部署这些场景里迅速出错。

所以这一篇真正要解决的不是“怎么写一个时区字符串”，而是：为什么时区不是字符串替换，而是一套**随时间变化的规则查询系统**。

## 一、为什么 `ZoneId` 只是规则入口：它先告诉你“查哪套规则”

### 先看 `ZoneId` 提供了什么

JDK 11 里：

- `ZoneId.systemDefault()` 在 `ZoneId.java:271`
- `ZoneId.of(String)` 在 `ZoneId.java:355`
- `getId()` 在 `ZoneId.java:487`
- `getRules()` 在 `ZoneId.java:562`

这已经足够说明 `ZoneId` 的角色：它首先是一个标识符对象。你可以用它表示“系统默认时区”“某个区域 ID”“某个偏移形式的 ID”，但它本身还不是最终偏移结果。

### 为什么它不是“拿来就能算”的偏移值

如果一个 ID 代表的是固定偏移，比如 `+08:00`，那它可以直接规约成固定秒数；但如果一个 ID 代表的是区域，比如 `Asia/Shanghai`，真正有意义的是它背后那套规则。你只有把“哪一刻”这个输入也交进去，才能得到当时的有效偏移。

所以 `ZoneId` 的价值不在“字符串长什么样”，而在于它把“时区”从一个写死的常量，变成了一个可查询规则系统的入口。

## 二、为什么 `ZoneOffset` 只是某一刻已经算出来的偏移：它不携带地区历史

### 先看它表达的是什么

旧稿里已经抓到了 `ZoneOffset` 的核心字段与边界：

- `UTC` 在 `ZoneOffset.java:151`
- `MIN` / `MAX` 在 `155` / `159`
- `totalSeconds` 在 `164`

这说明 `ZoneOffset` 的本体非常直接：它只是相对 UTC 的一个固定秒数。

### 为什么它适合表达结果，不适合表达整套地区语义

当你已经知道某一刻的最终偏移，比如“这条时间戳对应 UTC+08:00”，那 `ZoneOffset` 就足够了。它适合参与时间数学，也适合落到序列化和传输层。

但如果你想表达“这是上海时间”或者“这是纽约时间”，单个固定偏移就不够了。因为这些地区真正重要的是：在不同历史时期、不同日期、不同政策版本下，偏移可能会变化。固定偏移能表达当下结果，却不能表达整套地区规则。

这就是 `ZoneId` 和 `ZoneOffset` 的根本差异：**前者是规则入口，后者是某一刻的计算结果。**

## 三、为什么 `ZoneRules` 才是真正的时区引擎：偏移不是常量，而是时间的函数

### 先看规则引擎的关键入口

JDK 11 的 `ZoneRules` 定义在 `ZoneRules.java:110`，关键方法包括：

- `getOffset(Instant)`（`ZoneRules.java:490`）
- `getValidOffsets(LocalDateTime)`（`597`）
- `getTransition(LocalDateTime)`（`640`）
- `getStandardOffset(Instant)`（`761`）
- `isDaylightSavings(Instant)`（`814`）

这些入口合在一起，说明了一件事：时区规则不是一个静态整数，而是一张会根据输入时间点或本地时间做查询的规则表。

### 为什么“某个地区偏移多少”必须把时间也当输入

如果你问“纽约时区偏移多少”，这个问题本身其实不完整。因为不同时刻的纽约，偏移可能不同；甚至同一个地区在不同年份，规则也可能变化。真正完整的问题必须是：**在某个具体时刻，这个地区的有效偏移是多少？**

`ZoneRules.getOffset(Instant)` 的存在，就是把这个事实写进 API：偏移不是地区属性的固定常量，而是“地区规则 + 时间输入”共同决定的结果。

### 为什么夏令时不能靠手写公式凑出来

`getStandardOffset(Instant)` 和 `isDaylightSavings(Instant)` 进一步说明，标准偏移与实际偏移是分开的。夏令时不是“统一加一小时”这么简单的硬编码技巧，而是规则数据驱动的结果。

这也是生产系统里一个非常重要的边界：**DST 不是数学常量，而是规则数据。** 只要规则数据变了，某些历史时间的换算结果也可能随之变化。

## 四、为什么 Gap / Overlap 会让本地时间失去唯一性：本地时钟看到的 02:30 可能不存在,也可能出现两次

### 先看问题出在哪

当你从 `Instant` 出发去看本地时间时，通常没什么歧义：一个全球唯一时间点，在某个时区下总能映射出一个本地日期时间。

但反过来，如果你从 `LocalDateTime` 出发，试图问“这在某个时区下对应哪个真实时间点”，问题就复杂了。因为本地时间本身没有偏移信息，而规则切换会造成两类经典情况：

- `Gap`：时钟向前跳，某段本地时间根本不存在；
- `Overlap`：时钟向后拨，某段本地时间会对应两个不同偏移。

这也是为什么 `ZoneRules` 需要提供：

- `getValidOffsets(LocalDateTime)`（`ZoneRules.java:597`）
- `getTransition(LocalDateTime)`（`640`）

它必须先判断：这个本地时间到底有几个合法偏移，还是根本没有合法偏移。

### 为什么 `ofLocal` 和 `ofInstant` 的难度不同

`ZonedDateTime` 这里把两条路径分得很清楚：

- `ofLocal(...)` 在 `ZonedDateTime.java:366`
- `ofInstant(...)` 在 `406`

`ofInstant` 是从唯一时间点出发去查地区显示结果，通常不存在“到底是哪一刻”的歧义；`ofLocal` 则是从本地日期时间出发去找真实时间点，必须面对 Gap / Overlap 的规则分叉。

这也正是 `ZoneOffsetTransition` 这种类型存在的意义，类定义在 `ZoneOffsetTransition.java:99`：它不是额外概念堆砌，而是在承接“规则切换导致本地时间映射断裂或重叠”这个真实问题。

### 为什么这会直接影响存储设计

很多人觉得“存 `LocalDateTime` 加一个地区名，不就够了吗？”现在已经能看出，这并不总够。因为在 Overlap 场景下，同一个本地时间加同一个区域名，可能对应两个真实时间点；在 Gap 场景下，它甚至可能根本不对应任何真实时间点。

所以只保存“本地时间 + 区域名”，还不足以在所有场景下唯一还原事实时间。只要业务对唯一性敏感，就必须额外考虑偏移、时间点或歧义处理策略。

## 五、为什么规则数据必须和代码分离：时区不是写死在类里的,而是随 tzdata 演化的

### 先看规则从哪来

旧稿里已经抓到了默认 provider 的关键线索：`TzdbZoneRulesProvider` 在 `jdk/time/zone/TzdbZoneRulesProvider.java:86`。这说明 JDK 并不是把所有时区逻辑硬编码进 `ZoneId` 或 `ZoneRules` 类本身，而是通过 provider 加载打包的 tzdb 规则数据。

这和前面的分层完全一致：

- `ZoneId` 负责标识“查哪套规则”；
- `ZoneRules` 负责执行查询；
- provider 负责把规则数据提供出来。

### 为什么这对生产环境尤其关键

只要时区规则来自外部数据，而不是死写在业务代码里，就意味着：

- JDK 升级可能带来新的 tzdata；
- 某些历史时间的换算结果可能随规则版本变化；
- 跨时区系统在升级基础环境时，必须回归关键历史时间与边界时间。

这不是“时区知识点补充”，而是整个设计成立的前提。因为真实世界的时区本来就会变化，所以规则系统也必须允许随数据更新。

## 六、五个最容易混掉的边界：ZoneId 不是偏移值，ZoneOffset 不是地区规则，ZoneRules 不是静态常量，LocalDateTime 不天然唯一，tzdata 也不是永远不变

在收网之前，先把这一篇最容易记错的五条边界压实。

第一，`ZoneId` 不是最终偏移值。它更像一把钥匙，负责告诉系统“去查哪套地区规则”；只有把具体时刻也带上，这把钥匙才会真正开出某一刻的偏移结果。

第二，`ZoneOffset` 反过来也不是完整地区语义。它只表示某一刻已经算出来的固定偏移秒数，很适合表达结果，却不携带地区历史、未来调整和夏令时切换规则。

第三，`ZoneRules` 更不是一个静态常量表。它本质上是在回答“给定这个时刻/这个本地时间，此地区现在该用什么偏移”，所以偏移不是地区名自带的固定属性，而是时间的函数。

第四，`LocalDateTime + ZoneId` 也不天然唯一。遇到 Overlap，同一个本地时间在同一地区下可能对应两个真实时间点；遇到 Gap，它甚至可能根本不对应任何真实时间点。所以“本地时间 + 区域名”只能算规则查询输入，不自动等于唯一事实时间。

第五，tzdata 也不是一劳永逸的背景数据。只要规则数据会更新，某些历史时间的换算结果就可能随 JDK 或时区数据库版本变化而变化。时区系统从来不是写死一次就能永远稳定的常量集合。

把这五条边界记稳，时区这一篇就不会重新塌回“字符串 + 偏移”的表面印象。它真正讲的是一套规则查询系统：名字只负责指路，偏移只是阶段结果，真正决定答案的是背后那张随时间变化的规则表。

## 收网：时区真正有价值的不是名字，而是名字背后那张随时间变化的规则表

现在可以把整篇压成一条主线：

- `ZoneId` 负责标识你要查哪套时区规则；
- `ZoneOffset` 只是某一刻已经算出来的固定偏移秒数；
- `ZoneRules` 才是真正根据时间点或本地时间求偏移的引擎；
- Gap / Overlap 说明本地时间并不天然唯一；
- provider + tzdata 说明规则必须和代码分离，并允许演化。

所以 `Asia/Shanghai` 不等于 `+08:00`，并不是因为前者“写得更正式”，而是因为它代表的是一套地区规则，而不是一个固定数学结果。时区一旦进入真实世界，就不再是字符串拼接问题，而是规则查询问题。
