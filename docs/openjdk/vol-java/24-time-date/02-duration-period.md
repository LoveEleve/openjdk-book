# 时间运算：为什么“加一天”有时是 86400 秒，有时只是日历翻到明天

> 本文基于 JDK 11 `LocalDate`、`Duration`、`Period`、`TemporalAmount`。本文聚焦时间线时长与日历跨度的语义差异、plus/minus/between、TemporalAmount 应用与溢出边界；时区与 DST 放到下一篇。本文讨论的是 JDK 11 `java.time` 时间量语义，不把这里的 Duration/Period 划分方式和越界策略外推成所有时间 API 都必须遵守的统一规范。
> **前置依赖**：[核心值类型](01-core-value-types.md)
> **后续**：时区体系

## 先看一个几乎每个业务系统都会撞上的问题：同样叫“加一天”，你到底在加什么

表面上看，下面几种写法都像是在表达“加一天”：

- `date.plusDays(1)`
- `Duration.ofDays(1)`
- `Period.ofDays(1)`

如果只看方法名，确实很容易把它们当成三种差不多的 API 风格。但只要业务一复杂，这种“差不多”马上就会出错。

比如：

- 超时控制里“24 小时后失效”，关心的是固定物理时长；
- 账期里“明天到期”，关心的是日历翻过一天；
- 年龄、月结、账单周期里“一个月后”，关心的是年月日在日历上的推进。

这些问题看上去都在“加时间”，但它们根本不在同一个坐标系里。一个问的是时间线向前走了多少秒，一个问的是日历翻了多少格。`java.time` 在这里最重要的纪律就是：**先选语义，再选类型。**

所以这一篇真正要回答的不是“plus/minus 怎么调”，而是：为什么 `Duration` 和 `Period` 不能互换，为什么 `LocalDate.plusDays(1)` 也不是偷偷创建一个 `Duration` 来做加法。

## 一、为什么 `LocalDate.plusDays` 不是“加 86400 秒”：它首先遵守的是日历规则

### 先看它做的到底是什么运算

JDK 11 里，`LocalDate.plusDays(long)` 在 `LocalDate.java:1371`。它的思路不是“把当前日期转成某个时间点，加若干秒再转回来”，而是先在日期语义内部做运算：

- 小跨度先走当前月内的快路径；
- 再处理跨月、跨年的边界；
- 跨度更大时，转成 `epochDay` 做整数运算，再由日期工厂重建结果。

其中大跨度路径会经过 `Math.addExact(toEpochDay(), daysToAdd)`，位置在 `LocalDate.java:1397`。闰年规则则由 `isLeapYear()` 这类逻辑支撑，位置在 `LocalDate.java:854`。

这说明 `plusDays` 的本质不是“按秒推进时间线”，而是**在日历坐标系里推进日期**。它关心的是月长、闰年、跨月、跨年这些规则，而不是某个固定秒数。

### 为什么这一步不能偷懒成 Duration

如果 `LocalDate.plusDays(1)` 的本质只是“加 86400 秒”，那它首先就得有“当前日期对应哪个时间点”这个前提。但纯 `LocalDate` 根本没有时区，也没有一天中的时刻，它本来就不是时间点。你没法在不额外引入别的信息时，直接把它放进一条全球统一时间线里。

所以 `plusDays` 走自己的日历算法，不是实现细节偏好，而是语义上别无选择：**日期只能按日期规则算，不能假装自己是秒数。**

## 二、为什么 `Duration` 表示的是固定时间线距离：它回答的是“过去了多久”

### 先看它怎么存

JDK 11 的 `Duration` 定义在 `Duration.java:133`。它的核心字段是：

- `seconds`（`Duration.java:161`）
- `nanos`（`166`）

工厂方法包括：

- `ofDays(...)`（`Duration.java:180`）
- `ofSeconds(...)`（`223` / `246`）

`between(...)` 在 `Duration.java:486`，`plus(Duration)` 在 `689`，把它应用到某个时间对象上的 `addTo(...)` 在 `1100`。

这套结构已经把 Duration 的身份写死了：它不是日历跨度，而是秒与纳秒构成的固定时间线距离。

### 为什么 `Duration.ofDays(1)` 不是“日历上的一天”

`Duration.ofDays(1)` 的含义非常朴素：就是 86400 秒。它不管这个“1 天”落在 2 月、3 月、闰年，还是某个夏令时切换窗口里；它表达的只是固定物理时长。

这让 Duration 特别适合：

- 超时控制；
- 耗时统计；
- 重试退避；
- 任意需要固定秒数/纳秒距离的场景。

但它也因此天然不适合回答“明天”“下个月”“一年后生日”这类问题。那些问题依赖的是日历规则，不是秒数距离。

### `between` 为什么也要跟着语义走

很多人看到 `between`，会下意识觉得它只是“算个差值”。但 `Duration.between(start, end)` 算出的不是“两个日期在人类日历上的相差几天几月”，而是**两个 Temporal 在时间线上的距离**，最终归一到秒和纳秒。

这意味着：你一旦选了 Duration，就已经在回答“过去了多少物理时间”，而不是“日历翻了多少格”。

## 三、为什么 `Period` 表示的是日历跨度：它回答的是“日历走了多少年/月/日”

### 先看它怎么存

JDK 11 的 `Period` 定义在 `Period.java:133`。它的核心不是秒数，而是年、月、日三个日历单位。典型入口包括：

- `ofDays(...)`（`Period.java:218`）
- `between(LocalDate, LocalDate)`（`386`）
- `addTo(...)`（`894`）

这说明 Period 关心的不是“时间线过去了多少秒”，而是“在日历意义上推进了多少年、多少月、多少天”。

### 为什么它适合账期、年龄、月结，不适合精确超时

如果业务问题是：

- 两个自然日之间相差多久；
- 一个人满了多少岁多少月；
- 账单周期推进一个月；
- 合同从某日顺延若干天/月/年；

那么你需要的不是固定秒数，而是日历单位本身。Period 在这里才是正确表达。

反过来，如果你拿 Period 去做“30 秒超时”“24 小时后重试”，语义就已经偏了。因为它并不承诺自己是一段固定物理时长，而是一段按日历单位解释的跨度。

### 为什么 `Period.ofDays(1)` 和 `Duration.ofDays(1)` 长得像，却不该混用

这两个 API 最容易误导人。它们都写着 `ofDays(1)`，但实际在回答不同问题：

- `Duration.ofDays(1)`：固定 86400 秒；
- `Period.ofDays(1)`：日历上的一天。

也就是说，一个是在时间线上切出固定长度，另一个是在日历格子上向前走一格。表面词汇一样，语义完全不同。

## 四、为什么 `TemporalAmount` 能统一它们的用法，却不能抹平它们的语义差异

### 先看接口统一了什么

`TemporalAmount` 接口定义在 `TemporalAmount.java:99`，它提供的核心协议包括：

- `get(...)`（`TemporalAmount.java:117`）
- `getUnits()`（`134`）
- `addTo(...)`（`176`）
- `subtractFrom(...)`（`218`）

这让 `Duration` 和 `Period` 都能以“某种时间量”的身份，被应用到支持的 `Temporal` 对象上。

### 为什么这只是应用协议统一，不是语义统一

统一接口解决的是“怎么把一个时间量应用到目标对象”这个工程问题，不是“所有时间量本质一样”这个语义问题。

所以你看到 `temporal.plus(amount)` 时，真正决定结果的仍然是两件事：

- `amount` 到底是 `Duration` 还是 `Period`；
- 目标对象到底是 `Instant`、`LocalDate`，还是别的时间类型。

接口给了统一入口，但并没有帮你消灭类型差异。恰恰相反，它要求你在用统一入口之前，先把语义选对。

## 五、为什么 java.time 在时间运算上宁可抛异常，也不愿静默回绕

### 先看它的态度

时间值不是随便一个 long 加一加就完事。日期和时间都有明确边界，超出合法范围后，结果就不再是“另一个勉强可用的值”，而是根本不存在的时间语义。

这也是为什么 `LocalDate.plusDays` 的大跨度路径会走 `Math.addExact`（`LocalDate.java:1397`），而 `Duration` 的一些构造与运算路径里也会用到 `Math.multiplyExact` 一类检查。它们的共同态度是：**宁可立刻抛异常，也不静默制造错误时间。**

### 为什么这是时间 API 必须有的纪律

整数回绕有时还能被当作底层实现细节容忍，但时间对象一旦静默回绕，错误就会直接变成业务事实：账期错了、过期时间错了、审计时间错了，而且很可能直到生产环境才被发现。

所以 java.time 这里的设计不是“过于严格”，而是有意识地把错误前置暴露。时间值越接近业务边界，就越不能容忍默默错下去。

## 六、五个最容易混掉的边界：Duration 不是 Period 的高精度版，Period 不是 Duration 的日历别名，plusDays 不是偷偷造 Duration，TemporalAmount 不是语义统一器，越界也不是容错回绕

在收网之前，先把这一篇最容易记错的五条边界压实。

第一，`Duration` 不是 `Period` 的高精度版。它关心的是秒和纳秒构成的固定时间线距离，回答的是“过去了多久”；不是把 `Period` 的日历语义换成更细粒度而已。

第二，`Period` 也不是 `Duration` 的“按天写法”。它真正表达的是日历上的年、月、日跨度，回答的是“日历翻了多少格”。一旦你需要账期、年龄、月结这些语义，拿固定秒数去替代它，本质上就是把坐标系选错了。

第三，`LocalDate.plusDays(1)` 更不是偷偷创建一个 `Duration.ofDays(1)` 来做加法。`LocalDate` 自己根本不是时间点，也没有时区和一天中的时刻，所以它只能按日历规则在自己的坐标系里推进，而不是假装能先转成秒数再加回来。

第四，`TemporalAmount` 也不是“统一接口之后语义差异就没了”。它统一的是应用方式：你可以把某种时间量交给 `plus/addTo` 去作用在目标对象上；但这个 amount 到底是固定物理时长，还是日历跨度，仍然完全取决于它具体是 `Duration` 还是 `Period`。

第五，时间越界时抛异常也不是“太严格”。它是在明确拒绝制造一个根本不存在或已经失真的时间值。对时间这类紧贴业务边界的数据来说，静默回绕往往不是容错，而是把错误埋得更深。

把这五条边界记稳，时间运算这一篇就不会重新塌回“几个 plus/minus API 的选择题”这种表面印象。它真正想讲的是：时间对象已经拆开之后，运算仍然要继续守住坐标系——时间线归时间线，日历归日历。

## 收网：时间运算不是先选 API，而是先选“你到底在量什么”

现在可以把整篇压成一句最核心的话：`Duration` 和 `Period` 不是两种差不多的写法，而是两种不同坐标系里的时间量。

- `LocalDate.plusDays(1)` 先遵守的是日历规则；
- `Duration` 表达的是固定秒/纳秒距离；
- `Period` 表达的是年/月/日的日历跨度；
- `TemporalAmount` 统一了应用方式，但没有消灭语义差异；
- 时间越界时抛异常，是为了阻止错误时间继续流入业务。

如果说上一篇解决的是“为什么日期、本地时间、时间点必须拆开”，这一篇解决的就是：**即使都已经是时间对象了，运算时也仍然要先分清你在量的是时间线，还是日历。**

下一步自然就会遇到更棘手的一层：一旦时间进入真实世界，时区规则会让“本地时间”进一步失去直觉性。同样是 02:30，有的地区那天根本不存在，有的时刻会出现两次。这就是 `03-zone-rules.md` 要接着回答的问题。
