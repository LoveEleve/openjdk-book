# JDK 11 新特性与移除项：为什么它像一次"清扫 + 开新路"的边界版本

> 基于 JDK 11 源码树中可验证的模块与类型（`jdk.jfr` 的 `FlightRecorder`（`FlightRecorder.java:59`）、`jdk.jcmd` 的诊断工具模块），并对照 JEP 记录。本文讨论的是 JDK 11 为什么值得单独作为一个"版本边界"：一批新能力上线、一批旧模块被清走。需要先声明一个边界：当前可用的源码树是裁剪过的（约 11 个模块），`java.net.http` 等不在其中；因此 HttpClient 等特性的证据只能落到 JEP 记录和 JDK 11 发布说明层面，不能伪造源码行号。

## 先看一个"升级后突然编译不过/运行报错"的典型现象

一个 JDK 8 时代的项目要升级 JDK 11。编译时出现一堆 `package javax.xml.bind does not exist`、`package org.omg.CORBA does not exist`。开发者的第一反应是"是不是依赖没配好"。真相是：**这些包不是丢在某个 JAR 里，而是 JDK 11 把整个 Java EE 模块和 CORBA 从 JDK 里清走了。**

另一个现象：项目想在 JDK 11 下跑，于是去搜"JDK 11 新特性"，看到一长串 JEP 列表（HttpClient、ZGC、JFR 开源、Nestmates……），越看越懵，不知道该关心哪些、该评估哪些。列表背得再熟，也不知道自己的代码到底碰没碰到边界。

这两个现象背后是同一个认知缺口：**JDK 11 不只是一次"加功能"的版本，它更是一次"重新划边界"的版本。一边开新路（HttpClient、JFR、模块约束），一边清旧账（Java EE、CORBA、老 API）；升级评估的核心不是背特性列表，而是核对"我的代码用了什么，在新边界里还在不在"。**

这里至少有三个失败方案。

第一种失败方案，是把新特性当成"反正都是 JDK 自带的，升级就有"。JDK 11 引入的很多能力是**模块化之后才成立**的边界，比如强封装、`InaccessibleObjectException`、反射受限。不关心模块边界，只当"升级自动获得新功能"，就可能在升级后撞上访问被拒。

第二种失败方案，是把"JDK 11"当成一个单一事实源，直接套用 JDK 8 或 JDK 17 的知识。JDK 11 是模块化后的重要承接点，但它既不是 Java EE 时代的终点，也不是 LTS 之后的全部变化。写 JDK 11 特性，必须和前后版本对照着看，不能拿任何单一大版本当"统一事实"。

第三种失败方案，是把"移除项"只当新闻看，不落到自己的代码。`javax.xml.bind` 没了、Nashorn 被标记弃用、某些 `Thread` 方法语义收紧……升级前最该做的是在类路径、依赖、反射调用、JNI 里扫一遍这些会不会被碰到。不扫而直接升，代码哪天就断在某个老 API 上。

所以这三个失败方案指向同一个顿悟：**JDK 11 的最大价值是"边界被重新定义"——新能力上线、旧模块被清、模块化的访问约束全面生效。对这种版本，真正的评估动作不是背 JEP 列表，而是按"我用了什么 → 它在新边界里在不在 → 不在该怎么办"三问对一遍。**

## 一、新能力：四条线上的"开新路"

### 语言与类型系统

JDK 11 在语言层最重要的一项收口是 JEP 323（Local-Variable Syntax for Lambda Parameters）：lambda 参数也允许用 `var` 声明，风格和局部变量统一。整体而言，这类语言变化的共同特点是"编译期就可见"，升级时编译器会第一时间暴露不兼容，相对容易发现。

### 运行时与 JVM

JDK 11 最重要的运行时变化之一是 JFR 从闭源转向开源并纳入 OpenJDK 主线——源码树里现在可以看到 `jdk.jfr` 模块和 `FlightRecorder`（`FlightRecorder.java:59`）。对排障来说，这等于把"低开销事件流"变成一个所有 JDK 用户都能用的标准能力，而不是特定发行版专享。此外，诊断工具模块 `jdk.jcmd` 也随 JDK 11 分发，`jmap`/`jstack`/`jcmd` 作为标准工具可用。

### 网络与协议

JDK 11 正式引入 HttpClient（JEP 321），支持 HTTP/1.1、HTTP/2 和 WebSocket，提供同步与异步两种用法。**这里要再次强调边界**：当前源码树裁剪掉了 `java.net.http` 模块，因此有关 HttpClient 的断言只能基于 JEP 记录与 JDK 11 发布说明，本文章节不伪造该模块的行号。对升级评估而言，它的意义是：以前"必须引第三方 HTTP 客户端"的场景，在 JDK 11 有了官方选项。

### 安全与 GC

JDK 11 引入实验性的 ZGC（JEP 333）和 Epsilon 无操作回收器（JEP 318），并把 TLS 1.3、ChaCha20 等安全能力纳入标准库。这些都属于"有边界的新能力"：ZGC 标记为实验性的，意味着它面向特定延迟目标而不适合默认生产替换；Epsilon 更是"故意不回收"的回收器，只在特定场景有用。

## 二、移除与弃用：清走的是"不再属于 Java"的东西

### 模块级移除

JDK 11 最具决定性的清理是移除 Java EE 与 CORBA 模块（JEP 320）。`javax.xml.bind`（JAXB）、`javax.jws`（JAX-WS）、`org.omg.*`（CORBA）等整体从 JDK 移除。这不是"不再内置"，而是"连类都找不到"。对用了这些包的项目，唯一出路是在外部依赖里显式引入对应独立库。

### API 级变化

- `Nashorn` JavaScript 引擎在 JDK 11 被标记弃用（JEP 335），并在后续版本移除
- 一些老 API 的行为或可用性在模块化约束下变严：反射跨强封装模块的访问被 `InaccessibleObjectException` 拦截

### 为什么这构成"版本边界"

"移除"不是无损升级。一段在 JDK 8 能编译的代码，在 JDK 11 可能编译失败（包不存在）或运行失败（访问被拒）。因此版本边界不是一个"知识问题"，而是一个"需要核对代码实际使用"的问题——这正是本系列反复强调的：先分清"这是我该看的版本事实"，再谈"我能推导什么"。

到这里，新能力和移除项两个方向都过了一遍。接下来单独深讲 JFR——它是"开新路"里最值得单独评估的一项，因为它的价值在 JDK 11 发生了从"非标准"到"标准"的质变，需要单独一节讲清，而不是和新能力混在一起带过。

## 三、为什么 JFR 在 JDK 11 才是真正的"标准观测能力"

### 从工具到模块

JDK 8 及更早，Flight Recorder 主要存在于某些商业发行版。JDK 11 把 `jdk.jfr` 模块正式纳入 OpenJDK 主线，源码树里的 `FlightRecorder`（`FlightRecorder.java:59`）和 `jdk.jfr` 模块（`module-info.java:38`）就是证据。这意味着：

- 低开销事件流变成所有 JDK 11 用户的默认能力
- `jcmd JFR.start/JFR.dump/JFR.stop` 这类诊断命令随标准工具可用
- 自定义事件、录制配置、消费者 API 都属于 JDK 标准 API

### 对升级评估的含义

对长期在 JDK 8 上运行、想升级到 JDK 11 的团队来说，JFR 的开源是从"没有标准低开销观测"到"有标准低开销观测"的一次能力跃迁。这个跃迁值得单独评估，而不是当作"多了一个 JEP"顺带提一句。

## 五个最容易混掉的边界：新特性不是升级自动获得，"JDK 11 事实"不能从 8 或 17 推导，移除项不是新闻而是代码核对点，JFR 开源不是"多一个命令"是能力跃迁，源码树裁剪不代表发布缺特性

第一，新特性不是升级自动获得。模块化边界的强封装、反射受限等，都是 JDK 11 必须主动适配的变化；升级后出现 `InaccessibleObjectException`，不是因为"少配了什么依赖"，而是边界变了。

第二，"JDK 11 事实"不能从 8 或 17 推导。它是模块化后的承接点，也是 Java EE 移除的起点；写 11 的特性、边界和移除项，必须和 8、17 对照着看，不能拿单一版本当统一事实。

第三，移除项不是新闻而是代码核对点。`javax.xml.bind`、CORBA 整体移除、Nashorn 弃用，这些不只是"看个新闻"，而是升级前必须扫自己代码库用到没有的检查清单。

第四，JFR 开源不是"多一个命令"，而是从"商业发行版专享"到"标准能力"的跃迁。JDK 8 上无法依赖的标准低开销观测，在 JDK 11 属于默认能力。

第五，当前源码树裁剪了部分模块（如 `java.net.http`），不代表 JDK 11 发布缺这些特性——而是本仓库仅仅保存了其中 11 个模块。写 JEP 级特性时不伪造行号，是这条边界的底线。

把这五条边界记稳，JDK 11 就不再是一串需要背的 JEP 编号。它真正想讲的是：这是模块化之后的分水岭，新能力（HttpClient、JFR、模块约束）与旧清理（Java EE、CORBA、Nashorn 弃用）同时发生；升级评估的第一步，是判断自己的代码站在边界哪一侧。

## 收网：JDK 11 的意义是"边界被重新定义"，不是"多了一批功能"

回到开头那个"编译不过"的现象，现在能看清它为什么不是依赖问题、而是版本边界问题了。

`javax.xml.bind` 不存在，是因为 JDK 11 把 Java EE 模块整体移除；`InaccessibleObjectException` 出现，是因为模块化强封装开始生效。这些都不是"少了某个配置"，而是"你写的代码和 JDK 11 的新边界不一致"。

把整篇压成一张总图：

```text
JDK 11 = 清扫 + 开新路

开新路
  → HttpClient（JEP 321）：HTTP/2、WebSocket
  → JFR 开源：jdk.jfr 模块进入 OpenJDK 主线
  → 模块约束：强封装、InaccessibleObjectException
  → 实验性 GC：ZGC / Epsilon

清旧账
  → Java EE 模块移除：JAXB / JAX-WS / CORBA
  → Nashorn 弃用（JEP 335）
  → 老 API 在模块化下行为收紧

升级评估三问
  → 我用到了什么
  → 它在新边界里在不在
  → 不在该怎么办
```

所以当你在评估"要不要升 JDK 11"或者"已经升了出问题"时，真正该做的不是把 JEP 列表背一遍，而是拿着这三问去扫自己代码：**我用到的 API 在新边界里还在不在？如果被移除或被过度封装挡住了，是该换标准替代、引入独立依赖，还是保持旧版本运行？** 这才是"版本边界"四个字落在工程上的意义。
