# ForkJoinPool work-stealing：为什么分治池不能让所有线程抢同一个队列

> 本文基于 JDK 11 `ForkJoinPool`。讨论范围聚焦 `WorkQueue`、`base/top/array`、`ctl`、`signalWork`、`scan`、`poll` / `push` / `pop`、commonPool 与工作窃取主线；ForkJoinTask 任务状态机与 API 放到下一篇。本文讨论的是 JDK 11 Java 层实现路径，不把这里的 WorkQueue 组织方式和 commonPool 默认角色外推成所有分治执行器都必须照搬的统一规范。
> **前置依赖**：[CompletableFuture 基础](01-cf-basics.md)、[ThreadPoolExecutor 对照](../14-threadpool/01-ctl-worker.md)
> **后续**：[ForkJoinTask 与分治](04-forkjointask.md)

## 先看一个最容易把分治并行写成“共享队列线程池”的错误直觉

如果你已经熟悉普通线程池，很容易自然地把所有并发执行器都想成“多个工作线程 + 一个共享任务队列”。这个模型在 `ThreadPoolExecutor` 上完全说得通：任务通常是外部提交进来，worker 再从共享队列里一个个领活。

但一旦任务本身会在执行过程中继续裂变出更多子任务，这个模型就会迅速露出问题。设想一个递归分治过程：当前任务刚拆成左右两半，左右又继续拆，新的子任务并不是偶尔产生，而是像树一样在 worker 内部持续涌出。如果你把每次 `fork` 出来的子任务都塞进一个全局共享队列，那么所有 worker——包括正在拆任务的那个 worker——都会围着同一个热点队列争抢 push/poll，局部性丢掉了，共享竞争却被放大了。

这正是 `ForkJoinPool` 选择另一条路线的原因：**它不让所有线程总盯着同一个共享队列，而是先给每个 worker 一条自己的本地双端队列，自己先吃自己拆出来的活；只有空闲线程才去别人那里偷任务。**

所以这篇真正要讲的，不是“FJP 也有线程池和队列”，而是：为什么分治并行池必须把“任务产生地”和“任务窃取地”分开建模，才能同时兼顾缓存局部性和全局负载均衡。

## 一、为什么分治任务不能都进一个共享队列：共享热点会吞掉分治本该有的局部性

### 先看共享队列模型在分治场景里的失败方式

共享阻塞队列的好处是简单：谁有空谁去拿，谁提交谁就塞进去。但分治任务和普通外部任务有一个本质不同：它们会在执行过程中继续由 worker 自己大量产生新任务。也就是说，任务流不是“外部提交者 → 队列 → 工人”这一条线，而是“工人执行 → 工人再生子任务 → 继续执行/被别人偷走”的循环。

如果这些子任务每次都要回到一个全局共享队列，那么刚刚把任务拆出来的 worker 也得和所有别的线程一起争抢这条队列。这样不仅会制造一个中央热点，还会让本来最适合继续处理这些局部子任务的那个线程，失去就地延续执行的优势。

换句话说，共享队列模型最大的问题不是“不能并发”，而是它把所有任务都当成同一种外来工作，**看不见任务和生成它的 worker 之间天然存在的局部关系。**

### ForkJoinPool 要保护的，其实是“刚拆出来的任务离我最近”这个事实

分治任务有一个很重要的现实：一个 worker 刚把任务 A 拆成 A1 和 A2，这两个子任务往往最接近它刚刚处理的数据局部性和调用上下文。让这个 worker 先继续处理它们，通常比把它们立刻扔给别的线程更合算。

所以 FJP 的第一原则不是“先公平分活”，而是“**先保住本地连续执行，只有空闲线程才来救场**”。这也是为什么它需要本地队列，而不是先把所有子任务推回共享池里。

## 二、WorkQueue 为什么必须是双端队列：owner 和窃取者面对的是两种完全不同的需求

### 先看它的三个核心字段

JDK 11 的 `WorkQueue` 定义在 `ForkJoinPool.java:777`，最关键的字段是：

- `base`（`ForkJoinPool.java:780`）
- `top`（`ForkJoinPool.java:781`）
- `array`（任务环形数组）

这不是普通 FIFO 队列的头尾同构，而是一条明确区分“本地 owner 从哪头动”和“外来偷任务的人从哪头动”的双端队列。

源码前部的大段类注释在 `227-248` 一带已经把这套语义说得很清楚：owner 的 push / pop 主要围绕 top 端；窃取者的 poll 则从 base 端拿任务。也就是说，**同一条队列天然分裂成了两个角色入口。**

### 为什么 owner 要 LIFO，本地优先吃顶端任务

owner 把新 fork 出来的任务 push 到 top，再优先从 top 端 pop，等价于一种本地 LIFO 策略。它的好处不是“栈结构更酷”，而是：刚刚拆出来的子任务通常最接近当前执行上下文，本地线程顺着它们继续做，缓存局部性和递归连续性都更好。

这和前一节的总问题正好闭环：分治池首先想保住的，是“谁刚生产了这些活，谁最适合先把它们继续做掉”。LIFO 恰好在策略上支持这一点。

### 为什么窃取者反而要从 base 端 FIFO 地偷

外来偷任务的线程需求完全不同。它不是刚拆出任务的 owner，不需要保持最近局部性；它更需要的是尽量少和 owner 在同一个端点上打架。所以它从 base 端 poll，比从 top 端去和 owner 抢更合理。

同时，base 端的任务通常更“老”，更像还没被 owner 继续深入处理的分支，把这些较早任务搬走，往往也更有助于平衡整棵分治树的工作分布。

所以双端队列不是实现花活，而是把两类竞争需求显式分离：

```text
owner
  → top 端
  → LIFO
  → 保局部性、保递归连续性

stealer
  → base 端
  → FIFO
  → 少和 owner 冲突、搬走较老任务
```

这一层一定要讲透，因为它是 FJP 和普通共享队列线程池最根本的结构分歧。

## 三、为什么本地优先 + 工作窃取能同时兼顾局部性和全局均衡

### 先看“本地优先”到底体现在哪

ForkJoinPool 的执行不是一上来就随机窃取，而是**owner 先尽量处理自己队列里的任务**。相关方法如 `nextLocalTask`（`ForkJoinPool.java:943`）和 `topLevelExec`（`1016`）正是在体现这条思路：本地还有活，就先干本地活，别急着四处乱看。

这条策略非常关键，因为它确保 worker 不会轻易把自己刚生产、最有局部性的任务让出去。只有当本地真的空了，它才需要把视线投向全局去找别人的工作。

### 工作窃取真正解决的是“有些人闲了，有些人还忙”

有了本地队列之后，新问题自然变成：如果某个 worker 很快把自己的活做完了，而别的 worker 还背着一大串子任务怎么办？答案不是重新把所有队列合并，而是工作窃取：**闲下来的 worker 去别人队列的 base 端偷一份任务回来。**

这样，系统既没有一开始就让所有线程围着共享队列抢，也不会因为每个人只看自己地盘而出现严重负载不均。局部性优先解决“最近任务谁来做最划算”，窃取机制解决“全局算力别闲着”。

这一层真正要留下的是：ForkJoinPool 的设计不是在本地优先和全局均衡之间二选一，而是把它们安排成了先后顺序——**先局部连续执行，再在必要时用窃取补平衡。**

## 四、ctl 为什么不是“更大的线程计数器”，而是池级调度控制字

### 先看为什么 FJP 关心的不是单纯线程数

在线程池那一域里，我们已经见过 `ThreadPoolExecutor` 用 `ctl` 把 runState 和 workerCount 绑在一起。ForkJoinPool 也有自己的 `ctl`，位于 `ForkJoinPool.java:1312`，但它关心的问题又不一样。

FJP 的难点并不只是“总共有多少 worker”，而是：

- 当前有多少 worker 正在活跃干活；
- 有多少已经失活、挂到等待结构上；
- 新任务到来时该唤醒谁；
- 什么时候需要补偿、什么时候可以继续收缩。

也就是说，FJP 的池级控制更偏向“活跃/等待调度”，而不是简单的固定线程数管理。

### 为什么要用 64 位 ctl 去同时携带多个控制子域

相关注释和掩码说明在 `ForkJoinPool.java:734-739`、`1260-1263` 一带。你不需要记住每一位具体怎么排，但一定要理解：**ctl 在这里承担的是一个原子快照的职责，用来把‘池里当前这些活跃/等待控制事实’捆成一次可 CAS 观察和更新的整体。**

这就和上一域的 TPE 又形成了对照：TPE 的 ctl 是“状态 + 工人数”的联合事实；FJP 的 ctl 更像“池级调度控制字”，服务于活跃 worker、等待栈和唤醒逻辑。

这一层要讲成角色差异，而不是位运算细节表。

## 五、没活干时 worker 为什么不是简单阻塞在一个队列上：它要先扫描、再失活、再等 signalWork

### 先看普通线程池为什么可以简单阻塞，而 FJP 不行

在普通线程池里，worker 没活干时阻塞在共享 `BlockingQueue.take()` 上，非常自然。因为任务来源集中、队列入口集中，“没活”基本就意味着“共享池里真没活”。

ForkJoinPool 不是这样。每个 worker 都有自己的本地队列，所以“我这儿没活”并不等于“系统里没活”。因此一个 worker 空下来后，不能马上认定自己该长期沉睡，它得先去看别人是不是还有可以偷的工作。

### 这就是 scan / 失活 / signalWork 这条链存在的原因

类注释 `468-486` 一带已经明确说明了 scan 的角色：worker 顶层循环里会扫描可用 WorkQueue，寻找非空队列并尝试窃取。只有在多轮扫描都找不到工作后，它才会逐步进入失活/等待结构，而不是像普通线程池那样直接对着一个共享队列阻塞。

当新任务到来、某个队列重新出现可执行工作时，`signalWork`（`ForkJoinPool.java:852`）再负责把合适的等待 worker 叫醒，让它重新参与扫描和执行。

所以 FJP 的空闲恢复机制可以压成这样：

```text
本地没活
  → 先扫别人有没有活
  → 扫不到再失活等待
  → 新活到来时 signalWork 唤醒
  → 醒来后继续扫描/执行
```

这和普通线程池最大的差异在于：**FJP 的空闲 worker 不是在等“共享队列给它喂活”，而是在等“整个池里重新出现可偷的活”。**

## 六、commonPool 为什么会成为 CompletableFuture Async 和并行流的默认后端

### 先看 commonPool 的角色

`commonPool()` 位于 `ForkJoinPool.java:2395`，`getCommonPoolParallelism()` 位于 `2563`。它不是某个业务私有池，而是一座全局共享的分治执行后端。很多 JDK 内置异步机制——包括前面讲过的 `CompletableFuture` Async 默认执行器、并行流等——都会把细粒度异步任务往这座池子上放。

### 为什么它比普通共享队列池更适合做默认后端

原因并不是“ForkJoinPool 一定更快”，而是它特别适合承接这类特点明显的任务：

- 任务粒度细；
- 任务可能继续派生子任务；
- 任务之间更适合走本地连续执行 + 空闲再窃取，而不是所有线程都排一个共享队列。

这和前两篇 CompletableFuture 的 Completion 传播正好接上：大量 Async 节点本质上也是细粒度异步任务，如果它们都压回一个共享阻塞队列，调度和竞争特征会和 FJP 的设计目标冲突。commonPool 因此成为一个自然默认后端。

当然，这不意味着它适合所有阻塞任务；但这部分边界要留到后续应用和执行器专题里继续展开。本文先立住结构性的原因：**FJP 的本地双端队列 + 窃取模型，更适合承接细粒度、可继续裂变的异步工作。**

## 七、五个最容易混掉的边界：FJP 不是共享队列池，双端不是花活，窃取不是常态，ctl 不是线程计数器，commonPool 不是万能池

在收网之前，先把这一篇最容易记错的五条边界压实。

第一，ForkJoinPool 不是把 `ThreadPoolExecutor` 换个名字再套一层。普通线程池最自然的心智是“外部任务进共享队列，worker 去领活”；FJP 面对的却是“worker 在执行中继续裂变子任务”，所以它首先要保护的是任务生成地和任务消费地之间的局部关系。

第二，WorkQueue 的双端结构也不是实现花活。top 和 base 之所以分开，不是为了把一个普通队列写复杂，而是为了把 owner 的本地连续执行和 stealer 的外部搬运明确拆到两个端口上，减少冲突并保住局部性。

第三，工作窃取也不是系统默认总在做的事情。真正的常态是本地优先：worker 先尽量把自己刚拆出来的活继续做下去；只有本地空了，窃取才成为救场手段。如果把“偷任务”理解成 FJP 的日常主路径，就会把整个设计主次看反。

第四，`ctl` 更不是“ForkJoinPool 版本的线程数量计数器”。它真正关心的是池级调度事实：谁活跃、谁等待、谁需要被重新叫醒。把它只看成一个大整数，会直接看丢 FJP 在活跃/失活切换上的控制意图。

第五，`commonPool` 也不是“JDK 默认给你的万能异步池”。它之所以适合作为很多细粒度 async 节点和并行流的默认后端，是因为这些任务模型和本地双端队列 + 工作窃取的调度方式相匹配；这不等于所有阻塞、长耗时、外部依赖重的任务都该无脑往里扔。

把这五条边界记稳，ForkJoinPool 才不会重新塌回“一个更高性能的线程池”这种扁平印象。它真正提供的是另一种执行哲学：不是让所有线程排队领同一种活，而是先让任务在本地连续生长，只有空闲线程才去别处把较老分支偷回来补平衡。

## 收网：ForkJoinPool 不是“另一个线程池”，而是“先保住本地任务连续执行，再靠窃取补平衡”的执行引擎

现在回到开头那个错误直觉，就能看清为什么“所有线程抢同一个队列”不适合分治池了。分治任务最有价值的不是谁先拿到活，而是刚拆出来的子任务应该优先由本地 worker 连续处理，以保住局部性；只有空闲线程才应该从别人那里窃取较老任务，把负载重新拉平。

这也是 WorkQueue 必须做成双端的原因：owner 从 top 端 LIFO 地吃自己最近拆出的活，stealer 从 base 端 FIFO 地搬走别人较老的活。池级 `ctl` 则继续负责在“谁还活跃、谁已等待、来活后该叫醒谁”这些调度事实之间维持原子一致。worker 没活时也不是立刻睡死，而是先扫描、再失活、再等 `signalWork` 把它叫回来。

把整篇压成一张总图，就是：

```text
ForkJoinPool
  → 每个 worker 一条本地 WorkQueue
  → owner: top 端 LIFO
  → stealer: base 端 FIFO
  → 本地优先保局部性
  → 空闲窃取保全局均衡
  → ctl 负责池级活跃/等待调度控制
```

如果说前两篇 CompletableFuture 讲的是“结果和依赖怎样流动”，这一篇真正补上的就是：**这些细粒度异步步骤最终落到怎样一种执行引擎上，才能不把所有线程重新压回一个共享热点队列。**
