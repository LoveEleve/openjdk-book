# 09-map-hash/02 重写规划

> 状态：重写前计划
> 适用规范：`docs/openjdk/WRITING-GUIDELINES.md`
> 版本边界：JDK 11 `HashMap`。本文聚焦 `resize()`、`loadFactor/threshold`、`TREEIFY_THRESHOLD/UNTREEIFY_THRESHOLD/MIN_TREEIFY_CAPACITY`、`treeifyBin()` 与 `TreeNode.split()`。不展开红黑树旋转细节和 `ConcurrentHashMap` 的完整机制。
> 目标：把“扩容与树化”改写成一篇围绕“为什么 JDK 8+ 的 HashMap 扩容几乎不重算桶位、以及为什么桶长到 8 也不一定马上变树”的机制文章，并顺带把 JDK7 环链事故与 JDK8 尾插修复讲成结构性对比。

## 1. 读者困惑

- `++size > threshold` 之后，HashMap 扩容到底在搬什么？
- 为什么元素新位置只可能是“原下标”或“原下标 + oldCap”？
- `(e.hash & oldCap) == 0` 到底在判断什么位？
- 为什么说 JDK 8 扩容几乎不需要重算 hash？
- 负载因子为什么默认是 0.75，而不是 1.0 或 0.5？
- 链表长度到 8 为什么还不一定树化？为什么又要有 6 和 64 这两个配套阈值？
- “JDK7 扩容会死循环，JDK8 修了”到底是修了哪种链表迁移方式？

## 2. 一句话顿悟

**JDK 8+ HashMap 扩容的精髓，是利用“容量翻倍只多出一位”的事实，把桶内元素按那一位拆成 lo/hi 两组，直接决定留原位还是搬到 `原下标 + oldCap`；树化阈值体系则是在“链表太长就该兜底”和“表还太小先扩容更划算”之间做平衡。**

## 3. 旧稿优点与问题

### 保留

- 已覆盖 `resize` 的倍增、`(e.hash & oldCap) == 0` 高低位拆分、负载因子 0.75、三个树化阈值、JDK7 环链与 JDK8 尾插改进。
- 已提到泊松分布注释与树化概率背景。
- 已自然承接 `LinkedHashMap` / `TreeMap`。

### 必须重写

- 旧稿像“知识点清单”，需要先建立主问题：为什么 JDK8 扩容不再做教学版“全量重算桶位”。
- `resize` 应围绕“旧桶只分成 lo/hi 两半”讲透，而不是单独讲 `newCap`、`newThr`、拆链三件事。
- 树化段要强调“链长到阈值 ≠ 立刻上树”，并把 `MIN_TREEIFY_CAPACITY` 放在与扩容的权衡关系里解释。
- JDK7 死循环与 JDK8 修复应明确落到“头插反转 vs 尾插保序”的迁移差异，而不是只做历史结论。
- 负载因子和泊松分布要服务于“为什么 8 是罕见但必须兜底”的主线，而不是孤立数学点。

## 4. 理解路径

### 第一节：从“扩容为什么没重算全量下标”切入

先承接上一篇：HashMap 定位桶用 `(n - 1) & hash`。当容量翻倍，为什么 JDK 11 不重新取模所有节点，而只看 `e.hash & oldCap`？这是整篇主悬念。

### 第二节：`resize` 的第一层动作——容量与阈值翻倍

证据：
- `HashMap.java:664-698`：`resize` 前半段
- `HashMap.java:683-685`：`newCap = oldCap << 1` / `newThr = oldThr << 1`
- `HashMap.java:690-696`：首次默认容量与阈值计算

主线：
- 扩容不是每次都从默认 16 开始，首次和后续是两条路径。
- 真正关键是“oldCap 左移一位”，这为后面“只多出一位”埋下条件。

### 第三节：为什么新位置只可能是原位或原位 + oldCap

证据：
- `HashMap.java:703-744`：链桶搬迁全段
- `HashMap.java:717-738`：`(e.hash & oldCap) == 0` 拆 lo/hi 链

主线：
- 旧容量是 2 的幂，翻倍后新 mask 只比旧 mask 多一位。
- 因此旧桶中的节点，新下标只取决于“新增那一位”是 0 还是 1。
- 0 → 留原下标；1 → 原下标 + oldCap。

这是全文最核心的顿悟点。

### 第四节：JDK8 扩容为什么“几乎不重算 hash”

主线：
- 哈希值早就存在 `Node.hash` 里，不用重新调用 `key.hashCode()`。
- 扩容决策只看 `hash` 与 `oldCap` 的按位与结果。
- 这让迁移更像“按新高位拆桶”，而不是“每个节点重新完整寻址”。

同时指出：严格说仍然会重新写入新表，但不需要重新算用户 hash，也不需要重新遍历比较所有位。

### 第五节：为什么要尾插保序——这和 JDK7 环链事故直接相关

证据：
- `HashMap.java:711-739`：`loTail/hiTail` 尾插
- 旧稿历史事实：JDK7 头插导致链表反转，多线程 resize 可形成环

主线：
- JDK8 在 lo/hi 两条链里都用尾插，保持相对顺序。
- 这不仅让扩容行为更稳定，也修掉了 JDK7 头插反转在并发 resize 下形成环链的经典事故机制。
- 但必须明确：修了环链 ≠ HashMap 线程安全。

### 第六节：负载因子 0.75 和泊松分布为什么一起出现

证据：
- `HashMap.java:58-77`：类注释里 load factor 含义
- `HashMap.java:69-78`：0.75 取舍说明
- `HashMap.java:181-199`：桶内节点数泊松分布与 8 的概率
- `HashMap.java:247-249`：`DEFAULT_LOAD_FACTOR`

主线：
- 负载因子太大，桶更拥挤，查找成本上升；太小，空间浪费严重。
- 0.75 是时间/空间折中，不是数学常数。
- 泊松分布注释的意义不是考试数学，而是说明：正常分布下长链极少见，所以树化是兜底，不是常规主路径。

### 第七节：为什么 8 / 6 / 64 这三个阈值要配套出现

证据：
- `HashMap.java:258-274`：三个阈值常量
- `HashMap.java:639-640`：达到链长阈值时调用 `treeifyBin`
- `HashMap.java:751-769`：`treeifyBin` 先看容量
- `HashMap.java:2203-2247`：树桶 `split` 后可能 `untreeify`

主线：
- `TREEIFY_THRESHOLD = 8`：链足够长，冲突已异常，值得考虑树化。
- `MIN_TREEIFY_CAPACITY = 64`：表太小时优先扩容，让元素散开，往往比上树更划算。
- `UNTREEIFY_THRESHOLD = 6`：拆桶或缩小时给树退回链表留缓冲，避免 8↔7↔8 这种来回抖动。

### 第八节：树桶扩容时为什么也按 lo/hi 拆，只是多了“可能退树”

证据：
- `HashMap.java:2193-2247`：`TreeNode.split`

主线：
- 树桶扩容同样按 bit 拆成 lo/hi 两边。
- 拆完后若某边节点数不够，就 `untreeify` 回链表；够多才保留树。
- 这说明“树化”不是一劳永逸状态，而是随桶密度动态切换。

### 第九节：收束到 JDK7 vs JDK8 的真正差异

主线：
- JDK7：头插迁移，链表反转，并发 resize 可能环链。
- JDK8+：尾插保序 + 高低位拆分，修掉环链风险。
- 但仍无同步，仍可能数据竞争、覆盖、丢失更新，因此生产并发场景仍应使用 `ConcurrentHashMap`。

## 5. 失败方案清单

1. 把扩容理解成“每个元素重新 `hash % newCap`”。
2. 看见 `(e.hash & oldCap) == 0` 却不知道它检测的是新增高位。
3. 以为链长到 8 就必然立刻树化。
4. 忽略 `MIN_TREEIFY_CAPACITY`，把所有长链都当成树化案例。
5. 以为 JDK8 修了死循环就等于 HashMap 线程安全。
6. 用默认容量装超大数据，却不预估容量和负载因子，导致反复扩容。
7. 把泊松分布注释当作无关数学装饰，错过它对阈值设计的解释作用。

## 6. 误解清单

1. 扩容时必须重新调用每个 key 的 `hashCode()`。
2. `oldCap` 只是旧容量数字，与新桶位无直接关系。
3. 树化是常规主路径；正常分布下其实极少进入。
4. `UNTREEIFY_THRESHOLD = 6` 是随便拍的数字。
5. JDK7/JDK8 差异只在性能，不影响正确性风险。
6. 0.75 是经验值，没有结构性理由。
