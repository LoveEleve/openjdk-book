# 09-map-hash/01 重写规划

> 状态：重写前计划
> 适用规范：`docs/openjdk/WRITING-GUIDELINES.md`
> 版本边界：JDK 11 `HashMap`。本文聚焦 `hash()` 扰动、2 的幂寻址、`Node` 桶结构、`putVal` / `getNode` 主流程，以及树化阈值在第一篇中的定位；扩容与树化细节放到下一篇展开。
> 目标：把“HashMap 的存储与哈希”改写成一篇围绕“为什么 HashMap 不是一个简单的 `hashCode % n` 数组，而是一套低成本分布修复 + 幂次寻址 + 多形态桶结构”的机制文章。

## 1. 读者困惑

- 为什么 `HashMap` 不直接拿 `key.hashCode()` 取模，而还要做一次扰动？
- 容量为什么必须是 2 的幂？这和 `(n - 1) & hash` 到底有什么关系？
- `HashMap` 底层到底是数组、链表还是红黑树？为什么三种答案都有人说？
- `put` 的时候先比较什么，什么时候覆盖，什么时候挂链，什么时候树化？
- `null` key 为什么能放进来？
- 为什么说 `HashMap` 的正确性高度依赖 `equals` / `hashCode` 契约？
- 第一篇里为什么要先提树化阈值，但又不把树化和扩容细节展开完？

## 2. 一句话顿悟

**HashMap 的本体不是“数组 + hashCode”这么简单，而是：先用扰动函数把高位信息压进低位，再借助 2 的幂容量把位与运算变成快速寻址，然后把同一桶里的冲突节点按数量和表容量在链表与树之间切换。平均 O(1)` 的背后，是一整套围绕“让碰撞尽量少、碰撞后也别太惨”的工程折中。**

## 4. 理解路径

### 第一节：先建立总问题——HashMap 为什么不是 `hash % n` 的教学模型

从常见教学版出发：数组 + 哈希函数 + 冲突链表，看似够了；再指出 JDK 11 真实实现为什么复杂得多：低位偏斜、容量取幂、极端碰撞、树化和扩容路径都要考虑。

### 第二节：桶里真正存的是什么

证据：
- `HashMap.java:277-291`：`Node<K,V>`
- `HashMap.java:392` 等待后续若需要 table 字段行号，再读取补齐
- `HashMap.java:147-156` / `158-180`：类注释里说明 bin、TreeNode、Poisson 分布背景

主线：
- 第一层结构是 `Node[] table`；每个槽位是一个桶入口。
- 桶里平时放 `Node` 链，节点多时可能转成 `TreeNode` 树。
- 因此“HashMap 底层是数组/链表/红黑树”三种说法都各说到了一部分，但完整答案是“数组 + 桶节点，多形态冲突结构”。

### 第三节：扰动函数为什么一定要存在

证据：
- `HashMap.java:323-340`：`hash(Object key)` 上方完整注释与实现

主线：
- 寻址只看低位，所以高位好的 `hashCode` 如果低位分布差，仍会扎堆碰撞。
- `(h >>> 16) ^ h` 的目的就是用极低成本把高位信息折到低位。
- `null` key 返回 0，因此自然落到 0 号桶。

### 第四节：2 的幂容量为什么和扰动函数是一对组合拳

证据：
- 需要补读 `tableSizeFor` 精确源码区域
- `HashMap.java:235-249`：默认容量与负载因子
- `HashMap.java:565-566` / `624-626`：`(n - 1) & hash`

主线：
- 2 的幂容量让 `% n` 可退化成位与，降低寻址成本。
- 但这样只会读取低位，所以必须先靠扰动函数改善低位分布。
- 这两步不是独立技巧，而是一前一后配合的设计。

### 第五节：`putVal` 到底怎么决策

证据：
- `HashMap.java:607-661`：`put` 与 `putVal`
- `HashMap.java:673-744`：`resize` 中首次分配与扩容入口（本篇只点到扩容触发，不展开拆桶）
- `HashMap.java:751-769`：`treeifyBin`（本篇只点到“何时尝试树化”）

主线：
- 路径不是“先链表后红黑树”的单线故事，而是：
  1. table 为空则先初始化；
  2. 桶空直接落点；
  3. 桶首相同 key 则覆盖；
  4. 树桶走树插入；
  5. 链桶遍历到尾后挂新节点；
  6. 链过长才尝试树化；
  7. size 超阈值再扩容。
- 让读者先建立 put 的分支图，下一篇再接“为什么扩容不是全量重算”。

### 第六节：`getNode` 为什么和 `putVal` 是镜像关系

证据：
- `HashMap.java:563-580`：`getNode`

主线：
- 同样先算 hash、定位桶、先看首节点，再分树或链。
- “首节点直接比较”不是偶然优化，而是因为桶空或单节点桶是常态。

### 第七节：为什么键契约会直接影响正确性

证据：
- `HashMap.java:307-316`：`Node.equals`
- `HashMap.java:567-576` / `630-645`：key 比较条件

主线：
- HashMap 认同一个 key，要先 hash 相同，再 `equals` 成立。
- `equals` 相等但 `hashCode` 不等，会直接落不同桶，导致“看似相等却找不到”。
- 可变 key 修改后，重新计算 hash 会定位到别的桶位置，旧映射就像“丢了”。
- `null` key 特殊但一致：hash=0，走固定桶。

### 第八节：树化阈值在第一篇只立路标

证据：
- `HashMap.java:258-274`：`TREEIFY_THRESHOLD` / `UNTREEIFY_THRESHOLD` / `MIN_TREEIFY_CAPACITY`
- `HashMap.java:639-640`：达到阈值时调用 `treeifyBin`
- `HashMap.java:753-754`：容量不足时先 `resize()` 而不是树化

主线：
- 这一篇只回答“什么时候会触发树化检查”。
- 真正的树化、拆桶、`(e.hash & oldCap) == 0` 和 JDK 8 扩容路径留给下一篇。
- 让读者先知道：桶过长并不必然立刻变树，表太小时优先扩容。

## 5. 失败方案清单

1. 把 HashMap 理解成“数组 + `hashCode % n`”的简化模型，并拿它解释 JDK 11 行为。
2. 以为 `hash()` 的扰动只是多余的花活。
3. 以为容量取 2 的幂只是历史传统，与位运算寻址无关。
4. 认为 HashMap 底层永远是链表，或永远是红黑树。
5. 误把树化阈值 8 理解成“链表长度 8 就一定树化”。
6. 用可变对象做 key 后再修改其参与 `equals/hashCode` 的字段。
7. 违反 `equals` / `hashCode` 契约却期待 HashMap 正常工作。

## 6. 误解清单

1. `ConcurrentModificationException` 是 HashMap 正确性保障的一部分；它只是调试友好的 fail-fast。
2. `null` key 是特例 hack，不属于正常寻址逻辑；实际上它只是 hash=0 的一个稳定路径。
3. `put` 总是先遍历完整桶链，再判断是否覆盖。
4. 树化是解决碰撞的默认路径；实际正常情况下大多数桶根本不会树化。
5. `hash()` 的高位混入低位会彻底消除碰撞；它只是低成本改善分布。
6. 平均 O(1)` 意味着所有路径都接近常数；极端碰撞下仍可能退化，只是 JDK 11 比旧版本更平滑。
