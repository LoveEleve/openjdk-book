# Executors 工厂与选型：方便的代价，往往是把边界藏起来

> 本文基于 JDK 11 `Executors`、`ThreadPoolExecutor` 与 `ScheduledThreadPoolExecutor`。讨论重点是 `newFixedThreadPool`、`newSingleThreadExecutor`、`newCachedThreadPool`、`newScheduledThreadPool`、`newWorkStealingPool` 的参数映射和生产边界；ForkJoinPool 细节留到后续异步/并行专题。本文讨论的是 JDK 11 工厂方法的默认参数组合，不把这些默认值外推成所有业务、所有版本都应照搬的最佳实践。
> **前置依赖**：[ctl 与 Worker](01-ctl-worker.md)、[FutureTask 与定时调度](04-futuretask-scheduled.md)
> **后续**：域 15 异步编程

## 先看一个最常见、也最容易把线程池选型当成“API 风格偏好”的误会

`Executors.newFixedThreadPool(8)` 看起来非常舒服：一行工厂方法，连构造参数都不用记。很多人第一次用线程池时，也正是因为这种“开箱即用”的感觉，直接把工厂方法当成默认答案。问题在于，线程池最危险的边界，从来都不是 API 长短，而是**你有没有清楚知道自己到底选了什么队列、什么线程上限、什么回收策略、什么拒绝语义。**

工厂方法最容易让人放松的地方，恰恰是它把这些边界条件替你打包藏好了。你看到的是“固定线程池”“缓存线程池”“单线程池”这些好记的名字，看不到的却是：有的默认给你无界队列，有的默认给你几乎无上限线程膨胀，有的默认让任务按时间排序，有的甚至根本不是 `ThreadPoolExecutor` 这一条路线。

所以这一篇真正要讲的，不是背工厂名字，而是把这些工厂方法重新翻译回上一域已经建立好的那套线程池语言：**它到底替你选了什么 `core / max / queue / keepAlive / handler` 组合，以及这些默认组合在什么任务模型下会变成优势，什么情况下又会直接埋雷。**

## 一、为什么工厂方法越方便，越容易把最危险的边界藏起来

### 先推演“我只想少写几行代码”这个最自然的动机

很多人选 `Executors` 的起点都不是性能，而是省心：既然 JDK 都给了固定池、缓存池、定时池这些工厂，那我直接挑一个和场景名字最像的，不就够了吗？这个动机本身完全合理。问题在于，线程池从来不是一个“名字差不多就行”的组件，因为它的风险大多来自隐藏边界，而不是显眼 API。

比如你以为自己选的是“固定线程数”，实际上你同时还选了“无界排队”；你以为自己选的是“缓存线程，空闲会回收”，实际上你同时还选了“几乎不设线程数量上限”。这些隐藏选择才是真正决定系统在高峰、积压和退场时会怎么表现的因素。

这也解释了为什么很多生产规范不是简单粗暴地说“Executors 错了”，而是更强调：**方便没错，但一旦边界条件对你很重要，就不能让它们继续藏在工厂里。**

## 二、newFixedThreadPool 为什么最容易藏住“无界排队”这颗雷

### 先看它表面上最吸引人的地方

`newFixedThreadPool(int nThreads)` 位于 `Executors.java:91`。表面看，这个名字给人的心理承诺非常直接：线程数固定，系统并发能力看起来也就稳住了。很多人因此会误以为它天然更安全，因为“线程数不会继续膨胀”。

但这只是看到了一半。固定线程数确实限制了同时工作的 worker 数量，可另一半代价是：**多出来的任务会持续往队列里堆。** 也就是说，你固定住的只是并发执行数，不是系统总负担。

### 为什么真正危险的地方是无界队列，而不是线程数固定

fixed thread pool 背后真正藏着的，是 `corePoolSize == maximumPoolSize == nThreads` 加上一条无界 `LinkedBlockingQueue`。这意味着：

- 线程数不会再超过 nThreads
- 但任务一旦来得比处理得快，后续活不会通过增线程分担，而是继续排进队列

这时风险就从“线程数失控”换成了“任务积压失控”。如果你的任务处理速度长期赶不上提交速度，系统不会立刻显式失败，而是先把越来越多的任务吞进队列。延迟、内存占用、请求超时、GC 压力，最后都可能沿着这条隐藏路径一起爆出来。

所以 fixed 真正固定住的不是系统负载，而只是 worker 上限。这个边界如果不被看见，就特别容易让人产生虚假的安全感。

## 三、newCachedThreadPool 为什么最危险的又完全是另一头：它把压力直接转成线程膨胀

### 先看它为什么在轻载、突发短任务时看起来很好用

`newCachedThreadPool()` 位于 `Executors.java:217`。它的名字也很诱人：线程能缓存、空闲还能自动回收，看起来像一种弹性很强的默认选择。对于大量短小、突发、很快就完成的任务，这种模式确实很顺手，因为它几乎不靠队列缓存，而是尽量把任务直接交给现成线程，没线程就临时补，空闲一段时间再收掉。

### 问题是：它几乎不帮你限制线程增长

cached thread pool 背后的参数组合本质上是：

- `corePoolSize = 0`
- `maximumPoolSize = Integer.MAX_VALUE`
- `keepAliveTime = 60s`
- `SynchronousQueue` 直接交接，不缓存普通排队任务

关键点在于这条队列语义。`SynchronousQueue` 不给你一个“先排队缓冲”的垫层，所以任务一旦没有空闲线程立刻接手，就更倾向于触发新线程创建。于是系统压力不会表现成“队列越来越长”，而会表现成“线程越来越多”。

如果任务都很短，线程很快回收，这没问题；但如果任务本身很慢、外部 IO 长时间阻塞，或者流量高峰远超预期，这个“几乎无上限”就会被迅速放大成线程膨胀、上下文切换增加、内存和调度压力暴涨。

所以 cached thread pool 的隐藏边界，和 fixed 恰好相反：**fixed 藏的是无界排队，cached 藏的是近乎无界扩线程。**

## 四、single / scheduled / work-stealing 为什么都不是 fixed / cached 的简单变体

### single 不是“把 fixed 改成 1”这么简单

`newSingleThreadExecutor()` 位于 `Executors.java:174`。表面上它当然很像 `newFixedThreadPool(1)`，但它真正强调的是“**单线程串行执行语义应该被稳定固定下来**”。因此它不仅在线程数上等价于 1，还通过包装限制了调用方轻易把这个执行器重新配置成多线程池的可能。

也就是说，single 的重点不是“参数值恰好等于 1”，而是“我承诺这是一条串行执行通道”。这和“你自己恰好 new 了一个 core=max=1 的 TPE，但未来可能还会动它”在工程语义上并不完全一样。

### scheduled 不是普通线程池加一个 delay 参数

`newScheduledThreadPool(int corePoolSize)` 位于 `Executors.java:288`（带 ThreadFactory 版本在 `303`）。它背后选用的根本不是普通阻塞队列，而是我们上一篇已经拆过的 `ScheduledThreadPoolExecutor + DelayedWorkQueue` 体系。

这意味着它关注的核心不再只是“谁先提交”，而是“谁先到期”。如果你把它当成普通线程池再额外睡一下，就会完全错过定时调度真正的资源管理逻辑：时间排序进了队列，不是线程先被占住等待。

### work-stealing 根本不是 ThreadPoolExecutor 家族

`newWorkStealingPool(int parallelism)` 位于 `Executors.java:112`，无参版本在 `128`。它返回的也不是 `ThreadPoolExecutor`，而是 `ForkJoinPool` 路线。也就是说，你如果把它也当成“另一个 TPE 参数套餐”，就已经在模型上错了。

这类工厂对应的是可分解并行任务、工作窃取与 ForkJoin 生态，不是前面这几篇围绕 core/max/queue/reject 建起来的 TPE 语义链。它确实仍然叫“线程池”，但已经是另一套执行模型。

这一节真正想让读者留下的结论是：**工厂名看起来都像“线程池模板”，但它们背后对应的执行语义并不在同一层次。**

## 五、为什么生产常常更愿意直接 new ThreadPoolExecutor：不是为了显摆，而是为了把边界摊开

### 真正缺的不是自由，而是可见性

当系统进入生产阶段，最重要的通常不是“默认值能跑”，而是“队列容量、线程上限、回收策略、拒绝语义到底是什么”。这时工厂方法最大的缺点不是不够灵活，而是把边界隐藏得太深，导致调用方很容易只记住了名字，却忘了套餐里到底附带了什么条件。

直接构造 `ThreadPoolExecutor` 的价值，恰恰在于把这些条件摊开：

- 队列是否有界
- 最大线程数是否可控
- keepAlive 是否真的符合业务负载形态
- 拒绝策略是否匹配系统的退化承诺
- 线程工厂是否给了可观测的线程命名与异常处理

也就是说，生产上常直接 new TPE，不是因为工厂方法“有毒”，而是因为**一旦边界必须被显式管理，隐藏套餐就不再是优点。**

### “别用 Executors”真正该怎么理解

这句话如果讲得太绝对，会误导读者以为工厂方法一律错误。更准确的理解应该是：

- 教学、脚手架、临时工具、小范围明确场景下，工厂方法完全可以用
- 一旦系统边界、容量、拒绝、命名和监控都重要，就不该继续让这些参数隐身

所以不是“Executors 不能用”，而是“**不能在不看清默认参数的前提下盲用它。**”

## 六、为什么参数调优不能靠一条万能公式：线程数、队列和拒绝本来就是联动的

### 先拆掉“CPU 核数 + 1”就够了的幻想

线程池调优最容易被讲成几条口诀：CPU 密集约等于核心数，IO 密集乘一个系数，队列看经验值。问题在于，这些公式最多只能作为起点，不能替代任务模型本身。

因为线程池参数从来不是孤立按钮。你调大 `corePoolSize`，会改变排队前的执行并发；你改队列容量，会改变扩线程和拒绝触发时机；你改 `maximumPoolSize`，会改变高峰期到底是更多线程吸收压力，还是更早进入排队或拒绝。它们天然就是联动的。

### 真正可用的调优顺序应该回到任务模型和观测数据

更靠谱的调优逻辑一般是：

1. 先看任务是什么：CPU 密集、IO 密集、突发短任务、长尾阻塞、定时任务还是可分解并行任务；
2. 再决定是否要显式有界队列、需要多大峰值弹性、能接受哪种拒绝语义；
3. 最后用压测和生产观测看活跃线程数、队列深度、任务等待时间、拒绝次数、CPU 和 GC，再回调参数。

所以本篇最后一定要把线程池参数讲成“任务模型的约束映射”，而不是“背几个流行公式”。

## 七、四个最容易混掉的边界：fixed 不是总量上限，cached 不是免费弹性，scheduled 不是普通池加 delay，work-stealing 不是另一种 TPE 套餐

在收官前，先把这一篇最容易被名字误导的四条边界压实。

第一，`newFixedThreadPool` 不是系统总量上限，只是工作线程数量上限。线程数固定，不代表排队任务数量也被固定；如果背后还是无界 `LinkedBlockingQueue`，压力只会换一种形态躲进队列里。

第二，`newCachedThreadPool` 也不是“自动伸缩所以天然安全”的代名词。它确实能回收空闲线程，但它更重要的另一面是：在没有普通排队缓冲的情况下，压力会优先转成线程增长。回收能力解决的是闲时收缩，不是忙时膨胀上限。

第三，`newScheduledThreadPool` 不是普通线程池多一个 delay 参数这么简单。它真正换掉的是工作队列和任务语义：线程不再只看谁先提交，而是要看谁先到期。如果把它误解成“普通池里让线程 sleep 一下”，就会把时间排序这件最关键的机制直接抹掉。

第四，`newWorkStealingPool` 更不能被当成“另一个 ThreadPoolExecutor 默认套餐”。它走的是 ForkJoinPool 路线，面对的是可拆分并行任务和工作窃取模型；这和前四篇围绕 `core / max / queue / reject` 建起来的 TPE 语义链根本不是同一层东西。

把这四条边界记住，Executors 这一篇就不会重新塌回“几个好记工厂名字的对比表”。它真正要交付的，是名字背后那套被打包隐藏的执行边界：压力到底先变成排队、扩线程、时间排序，还是直接切到另一套并行模型。

## 八、域 14 收官：从状态机、工人、退场、结果，到最后的选型落地

### 这一篇要把前四篇真正收回来

到这里，线程池域的五篇内容其实形成了一条很完整的链：

- 开篇先把线程池地基立住：联合状态机、`ctl` 和 Worker 这个可管理的工人实体；
- 接着把任务提交主线展开：core → queue → max → reject 这条资源决策链怎样路由新任务；
- 再往下把退场和满载边界讲清：旧任务怎么善后，新任务怎么被拒绝、背压或牺牲；
- 然后把结果与时间补齐：异常、取消、等待和定时排序为什么必须继续绑定在任务对象与延迟队列上；
- 到这一篇，才把前面所有机制翻译成最终选型：你到底该用哪种参数组合，哪些“省事工厂”在你的边界下是不是还能省心。

### 线程池选型真正选的，从来不是一个名字

所以到最后，线程池并不是“选 fixed 还是 cached”这么表面的决策，而是在选：

- 我想把压力先变成排队，还是先变成扩线程？
- 我接受无界排队，还是接受更早拒绝？
- 我需要的是串行、定时、直接交接，还是可分解并行？
- 我能不能接受隐藏套餐，还是必须把边界显式摊开？

这才是 `Executors` 这一篇真正要留下的收束。

## 收网：方便本身没错，但在线程池里，边界透明往往比少写几行更重要

回到开头那个误会，现在已经能看清为什么工厂方法的便利既真实、又危险了。真实在于：它确实替你快速拼好了一个能跑的线程池套餐。危险在于：线程池最敏感的那些边界——队列是不是无界、线程会不会膨胀、任务何时被拒绝、是否属于 TPE 还是 ForkJoin 路线——也一起被包装名字藏了起来。

这就是为什么 `newFixedThreadPool` 真正危险的不是“线程固定”，而是它暗含无界队列；`newCachedThreadPool` 真正危险的不是“会缓存”，而是它几乎不设线程上限；`newScheduledThreadPool` 真正特别的不是工厂名，而是它背后另走了一套 DelayedWorkQueue 的时间排序体系；`newWorkStealingPool` 更是直接切换到 ForkJoin 模型。

把整篇压成一张总图，就是：

```text
Executors 工厂
  → 不是新机制
  → 是把线程池参数套餐直接打包给你

fixed
  → 线程数固定
  → 无界队列风险隐藏

cached
  → 直接交接
  → 线程膨胀风险隐藏

single / scheduled / work-stealing
  → 各自对应串行、定时、ForkJoin 路线

生产选型
  → 先看任务模型
  → 再把 core / max / queue / keepAlive / reject 摊开
  → 用压测和观测验证
```

如果前四篇讲的是线程池的内部机制，这一篇真正补上的就是最后那一步：**把机制翻译成选型，不再被“名字听起来合适”这种表面感觉牵着走。**
