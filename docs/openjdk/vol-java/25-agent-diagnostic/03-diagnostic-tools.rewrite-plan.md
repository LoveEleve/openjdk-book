# 25-agent-diagnostic/03 重写规划

> 状态：重写前计划
> 适用规范：`docs/openjdk/WRITING-GUIDELINES.md`
> 版本边界：JDK 11 `jcmd`、`jstack`、`jmap`、`jstat`、`jps` 工具入口。本文聚焦工具族分工、典型排查路径与生产组合原则；JFR/JMX 只作为协同工具点到为止。
> 目标：把“诊断工具族与生产规范”改写成一篇围绕“JDK 诊断工具不是几个名字相近的命令，而是一组按信息形态分工的工具链：有的负责快照，有的负责趋势，有的负责统一命令入口；真正重要的不是记命令大全，而是先判断你现在缺的是哪一类信息”展开的机制文章。

## 1. 读者困惑

- 线上出问题时，为什么不是随便挑一个 `j*` 工具就行？
- `jcmd`、`jstack`、`jmap`、`jstat` 到底分别解决哪类问题？
- 为什么 `jcmd` 看起来像“万能入口”，却不等于其他工具都没意义了？
- 线程卡顿、高 CPU、内存膨胀、GC 抖动这些问题，为什么观测手段完全不同？
- 为什么生产排查总强调“快照 + 趋势 + 回放”，而不是只靠单次 dump？

## 2. 一句话顿悟

**JDK 诊断工具的关键不是命令多少，而是信息分工：`jstack` 解决线程快照，`jmap` 解决堆分布与 dump，`jstat` 解决 GC/类加载趋势，`jcmd` 提供统一命令入口，`jps` 帮你先确认目标。工具之间不是互相替代，而是在回答不同形态的问题：此刻线程在干什么、最近 GC 一直怎样、堆里到底堆了什么、以及目标 JVM 现在支持哪些命令。**

## 3. 旧稿优点与问题

### 保留

- 已抓到 `jcmd` / `jstack` / `jmap` / `jstat` / `jps` 的入口类与典型用途。
- 已把 `jcmd` 放回 Attach 通道统一入口，这是重要结论。
- 已给出“快照 + 趋势 + 回放”的组合思路，适合做本域收官。

### 必须重写

- 旧稿偏工具清单，需要先立住总问题：你现在缺的是哪种信息，而不是该背哪条命令。
- `jcmd` 和其他工具的关系要讲成“统一入口 vs 专用前端”的分工，而不是万能替代。
- SOP 要围绕信息形态组织，而不是只列命令顺序。
- JFR/JMX 作为协同工具要服务于“回放/远程管理”两种补位角色，不宜喧宾夺主。

## 4. 理解路径

### 第一节：从“线上出问题时先拿什么看”开场

用最真实的场景开场：线程满 CPU、堆涨、GC 抖、延迟尖峰。先立住总问题：先确定你缺的是线程快照、堆快照、GC 趋势，还是持续事件回放。

### 第二节：为什么 `jcmd` 是统一入口,却不是所有观测维度的语义替代

证据：
- `JCmd.java:51/52/114`

主线：
- `jcmd` 通过 Attach 接上目标 JVM，再下发命令。
- 它像总控台，能统一触发多类诊断命令。
- 但“统一入口”不等于“统一观测语义”；你仍然要先知道自己在看什么问题。

### 第三节：为什么 `jstack` 解决的是“这一刻线程都在干什么”

证据：
- `JStack.java:41/43/117`

主线：
- `jstack` 的本体是线程快照，不是趋势工具。
- 高 CPU / 死锁 / 卡顿排查要靠多次采样对比，而不是单次结果神化。
- 解释 `top -Hp` → 十六进制 nid → 栈帧定位这条常见链路。

### 第四节：为什么 `jmap` / `jstat` 分别回答“堆里是什么”和“最近一直怎样”

证据：
- `JMap.java:47/49`
- `Jstat.java:41/44`

主线：
- `jmap` 偏快照：直方图、heap dump、对象分布。
- `jstat` 偏趋势：GC 次数、代际变化、类加载统计。
- 这说明“内存问题”本身也要拆成静态分布和时间趋势两层。

### 第五节：为什么 `jps` 看似简单，却是排查链的稳定起点

证据：
- `Jps.java:38/42`

主线：
- 生产排查首先要确认目标 JVM、参数、版本和 PID。
- 错进程、错容器、错用户是最浪费时间的排查事故。
- `jps/jcmd -l` 这类动作本质上是在校准目标。

### 第六节：为什么生产排查要组合“快照 + 趋势 + 回放”

主线：
- `jstack/jmap` 解决此刻截面。
- `jstat` 解决最近一段时间的运行趋势。
- `JFR` 解决“刚才到底发生了什么”的持续事件回放。
- `JMX` 解决远程可观测与管理接口。
- 这样才能把单点 dump 的局限补齐。

## 5. 失败方案清单

1. 线上出问题先盲目执行某个熟悉命令，而不判断缺的是哪类信息。
2. 把 `jcmd` 当成所有工具的语义替代，忽略具体命令维度。
3. 只看一次 `jstack` 或一次 heap dump，就下结论。
4. 把 GC 抖动问题当成纯堆分布问题，不看 `jstat` 趋势。
5. 不先确认 PID / 目标进程，就直接开始 dump 和分析。

## 6. 误解清单

1. `jcmd` 出现后，`jstack/jmap/jstat` 就没有独立价值了。
2. 高 CPU 问题只要拿一份线程 dump 就一定够。
3. `jmap` 能看堆，所以它也能解释 GC 时间趋势。
4. `jstat` 看到 GC 频繁，就不需要再看对象分布。
5. 所有线上问题都应该先做 heap dump。
