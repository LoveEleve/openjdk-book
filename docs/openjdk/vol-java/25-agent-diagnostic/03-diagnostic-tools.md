# 诊断工具族与生产规范：为什么 JDK 诊断不是背命令大全，而是先判断你缺的是哪类信息

> 本文基于 JDK 11 `jcmd`、`jstack`、`jmap`、`jstat`、`jps` 工具入口。本文聚焦工具族分工、典型排查路径与生产组合原则；JFR/JMX 只作为协同工具点到为止。本文讨论的是 JDK 11 自带诊断工具族分工，不把这里的命令入口、输出形态和协同策略外推成所有 JVM 诊断生态都必须遵守的统一规范。
> **前置依赖**：[Attach 机制](01-attach-mechanism.md)、[Instrumentation 与字节码增强](02-instrumentation.md)
> **后续**：按写作顺序进入后续域

## 先看最常见的误区：线上排查不是先想“我会哪个命令”，而是先想“我现在缺的是什么信息”

很多人第一次接触 JDK 诊断工具时，脑子里会形成一个“工具名清单”：`jstack` 看线程，`jmap` 看堆，`jstat` 看 GC，`jcmd` 很万能，`jps` 看进程。背下来当然有帮助，但真正到了线上事故现场，这种记忆很容易失效，因为你面对的不是一张选择题，而是一个模糊症状：

- CPU 为什么突然飙高？
- 服务为什么卡住不返回？
- 内存为什么一直涨？
- GC 为什么突然抖成这样？
- 刚才那 30 秒里到底发生了什么？

这些问题真正缺失的信息形态并不一样。有的缺线程快照，有的缺堆分布，有的缺一段时间里的 GC 趋势，还有的缺持续事件回放。JDK 工具族的价值，恰恰就在于它们不是同义词，而是按信息类型分工。

所以这一篇的主线不该是“命令大全”，而应该是：**先判断你现在缺的是哪类信息，再决定拿哪件工具。**

## 一、为什么 `jcmd` 是统一入口，却不是所有诊断语义的替代品

### 先看它的入口位置

JDK 11 里，`JCmd` 定义在 `JCmd.java:51`，主入口在 `JCmd.java:52`。旧稿已经抓到一个非常关键的调用点：它会通过 `VirtualMachine.attach(pid)` 去连接目标 JVM，位置在 `JCmd.java:114`。

这说明 `jcmd` 不是“直接知道所有 JVM 内部状态”的神奇客户端，它依然建立在前两篇讲过的 Attach 通道之上。真正的能力仍然来自目标 JVM 端愿意暴露的命令集合。

### 为什么它更像总控台，而不是一切工具的语义替代

`jcmd` 很容易让人产生一种错觉：既然它几乎什么都能下发，那是不是以后只记住 `jcmd` 就行了？这只对了一半。

- 对的一半是：它确实是统一入口，线程、GC、JFR、类直方图、heap dump 等很多能力都能从这里触发；
- 不对的一半是：**入口统一，不等于观测语义统一。**

你依然要先知道自己现在需要的是线程快照、堆快照、趋势统计，还是持续事件录制。`jcmd` 解决的是“从哪儿下命令”，不是“所有问题本质一样”。

所以理解 `jcmd` 的正确角度，不是“万能命令”，而是“统一控制台”。

## 二、为什么 `jstack` 解决的是“这一刻线程都在干什么”：它是快照工具，不是趋势工具

### 先看它怎么连进 JVM

JDK 11 里，`JStack` 定义在 `JStack.java:41`，主入口在 `43`，连接目标 JVM 的动作在 `JStack.java:117`。这说明它和 `jcmd` 一样，本质上也是 Attach 通道上的一个专用前端。

### 为什么它最适合回答“卡住、高 CPU、死锁”这类线程问题

`jstack` 的核心价值不是“输出很多文字”，而是把**这一刻**线程状态、锁等待关系和当前栈帧截下来。它最擅长回答的问题是：

- 哪些线程正在 `RUNNABLE`，它们在跑什么代码；
- 哪些线程 `BLOCKED`，卡在谁的锁上；
- 哪些线程 `WAITING/TIMED_WAITING`，是在等条件、sleep、park 还是 IO；
- 有没有 Java 级死锁。

### 为什么线程问题通常要多次采样，而不是迷信一次 dump

快照工具的天然局限是：它只告诉你这一刻发生了什么。一次线程 dump 当然可能直接命中问题，但很多时候真正有价值的是连续多次采样对比：某个热点线程是不是一直卡在同一段代码、同一个锁竞争是否持续存在、某些工作线程是不是整体都在 park。

所以 `jstack` 最重要的边界不是“它能不能看线程”，而是“它看的是此刻截面，不是时间趋势”。

### 为什么高 CPU 定位经常是 `top -Hp` 配合 `jstack`

旧稿里已经给出一个很实用的生产路径：

1. 先用 `top -Hp <pid>` 找高 CPU 线程；
2. 把线程号转成十六进制；
3. 再到 `jstack` 输出里找对应 `nid=0x...` 的 Java 栈。

这条链路之所以稳定，就是因为它把 OS 线程视角和 JVM 栈视角接到了一起：一个告诉你“哪个线程在烧 CPU”，另一个告诉你“它在跑哪段 Java 代码”。

## 三、为什么 `jmap` 和 `jstat` 都和内存/GC 有关，却回答的是两类完全不同的问题

### `jmap` 看的是“堆里现在是什么”

JDK 11 里，`JMap` 定义在 `JMap.java:47`，主入口在 `49`。它代表的是内存问题里的快照视角：直方图、heap dump、对象分布，这些东西都在回答一个问题——**此刻堆里到底堆了什么。**

这类信息特别适合：

- 看对象类型分布是否异常；
- 判断是否存在可疑大对象或明显泄漏方向；
- 为进一步离线分析准备 heap dump。

### `jstat` 看的是“最近一直怎样”

`Jstat` 定义在 `Jstat.java:41`，主入口在 `44`。它和 `jmap` 最大的不同，不在“都和 GC 有关”，而在它提供的是趋势视角：一段时间内的 GC 次数、代际变化、类加载统计、回收节奏。

这意味着 `jstat` 最适合回答的问题是：

- GC 最近是不是突然变频繁；
- Young / Old 区变化是否异常；
- 类加载 / 卸载节奏有没有奇怪抖动；
- 这不是某一个瞬间，而是一段时间的运行模式。

### 为什么“内存问题”本身也必须拆成快照和趋势两层

很多排查之所以绕路，就是因为把这两层混成一层：看到 GC 抖，就直接去 dump 堆；看到堆里对象多，就直接推断 GC 一定有问题。实际上，`jmap` 和 `jstat` 分别回答的是：

- 堆里目前是什么分布；
- 系统最近怎么在回收和波动。

两者缺一不可。没有分布，你不知道谁占了堆；没有趋势，你不知道系统是不是一直在恶化、只是偶发波动，还是进入了某种新的运行模式。

## 四、为什么 `jps` 看起来最简单，却经常是排查链里最省时间的一步

### 先看它的入口

JDK 11 里，`Jps` 定义在 `Jps.java:38`，主入口在 `42`。它看似只是“列个进程”，但在线上排查里，这一步的意义远比很多人想得大。

### 为什么先确认目标进程，本质上是在防止一切后续动作跑偏

生产环境里最浪费时间的一类事故，不是工具不会用，而是压根盯错了目标：

- 连错 PID；
- 进了错容器；
- 以为是这台 JVM，实际是旁边那个；
- 参数、版本、启动方式和你脑子里预期根本不一致。

所以 `jps`，或者更广义地说用 `jcmd -l` 这类动作去先校准目标，本质上是在给整个排查链做坐标校准。没有这一步，后面所有 dump、histogram、GC 统计都可能是认真分析了错误对象。

## 五、为什么生产排查必须组合“快照 + 趋势 + 回放”：单次 dump 天然只能回答一部分问题

### 先把几类工具重新放回信息形态里

如果把这一域重新压缩成信息类型，会发现分工非常清楚：

- `jstack` / `jmap` 偏快照；
- `jstat` 偏趋势；
- `jcmd` 偏统一入口；
- `jps` 偏目标校准。

而真正完整的生产排查，往往还会再补两块：

- `JFR` 负责持续事件回放，回答“刚才那段时间到底发生了什么”；
- `JMX` 负责远程管理与监控接口，回答“能否持续观测、远程操作和暴露指标”。

### 为什么这才是更稳的 SOP

旧稿里已经给出了一条很实用的顺序，我把它收束成更明确的诊断逻辑：

1. 先确认目标：`jps` / `jcmd -l`；
2. 再拿线程快照：`jstack`，而且通常要连续采样；
3. 然后看 GC 趋势：`jstat`；
4. 再看堆分布或 dump：`jmap`；
5. 如果需要补时间维度，再上 `JFR`；
6. 如果需要远程持续暴露，再结合 `JMX`。

这条 SOP 的关键不在命令顺序本身，而在信息层次：

- 快照解决“现在怎么了”；
- 趋势解决“最近一直怎样”；
- 回放解决“刚才发生了什么”；
- 远程接口解决“怎么持续看和控”。

所以生产诊断从来不是“有一个最强工具”，而是多种信息形态的拼接。

## 七、五个最容易混掉的边界：jcmd 不是万能语义替代，jstack 不是趋势工具，jmap 不是 GC 走势，jstat 不是堆快照，jps 也不是可有可无的小命令

在收网之前，先把这一篇最容易记错的五条边界压实。

第一，`jcmd` 不是万能语义替代。它统一的是命令入口，不是问题本质；就算都能从 `jcmd` 里触发，你仍然得先判断自己缺的是线程快照、堆分布、GC 趋势，还是持续事件回放。

第二，`jstack` 也不是趋势工具。它最擅长的是回答“这一刻线程在干什么”，所以高 CPU、死锁、卡顿都应该把它当作快照来理解；真正要看是否持续异常，往往还得靠连续采样或别的趋势维度补位。

第三，`jmap` 更不是 GC 走势工具。它告诉你的是“现在堆里堆了什么、谁占得多”，而不是“最近一段时间回收频率怎样、代际波动怎样”。没有这条边界，就很容易把快照分布和回收趋势混在一起。

第四，`jstat` 反过来也不是堆快照。它提供的是一段时间内的 GC/类加载节奏与统计趋势，很适合回答“最近一直怎样”，却不会告诉你堆里某一刻究竟堆了哪些对象类型。

第五，`jps` 也不是可有可无的小命令。它看似简单，实际上承担的是最容易被忽视的“目标校准”职责：先确认你盯对了 JVM、对了 PID、对了启动参数和容器环境，不然后面所有快照、趋势和 dump 都可能是认真分析了错误对象。

把这五条边界记稳，JDK 诊断工具这一篇就不会重新塌回“背命令大全”这种表面印象。它真正想讲的是：工具族之所以值得拆开，不是因为名字多，而是因为它们各自承担的观测语义本来就不同。

## 收网：JDK 诊断工具真正的价值，不在名字多少，而在它们按信息类型分工，逼你先把问题问清楚

现在可以把整篇压成一条主线：

- 诊断先要判断你缺的是哪类信息，而不是先挑一条熟悉命令；
- `jcmd` 提供统一控制台，但不抹平具体观测语义；
- `jstack` 回答线程此刻在干什么；
- `jmap` 回答堆里现在堆了什么；
- `jstat` 回答最近一段时间 GC / 类加载一直怎样；
- `jps` 帮你先把目标 JVM 校准对；
- 真正的生产排查要把快照、趋势和回放组合起来。

所以理解 JDK 诊断工具族的正确方式，不是“背五六个命令名”，而是：**先把问题拆成线程、堆、GC 趋势、时间回放这些信息维度，再让工具各自回答自己最擅长的那一类。** 一旦这个分工建立起来，`jcmd`、`jstack`、`jmap`、`jstat` 就不再是零散命令，而是一条完整的诊断工具链。
