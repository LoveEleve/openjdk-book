# 内存泄漏与 CPU 飙高定位：线程转储和堆转储到底在回答什么问题

> 基于 JDK 11 的 `java.management`（`ThreadMXBean`）模块，以及 JDK 自带的 `jstack`/`jmap`/`jcmd`/`top` 工具。本文讨论的是两类最常见的线上问题——内存泄漏和 CPU 飙高——各自的定位思路，以及线程转储（thread dump）和堆转储（heap dump）在这两条路径里分别扮演什么角色。`ThreadMXBean.dumpAllThreads()`（`ThreadMXBean.java:103-104`）、`findDeadlockedThreads()`（`:111`）、`getThreadInfo(id)`（`:206`）是 JDK 11 可观测 API；`jstack`/`jmap` 等工具的行为是 JDK 工具实现，不同版本输出格式可能有差异。
> **前置依赖**：[G1 GC 日志解读](../42-production-practice/02-g1-gc-log.md)
> → **后续**：按扩展计划进入 JDK 诊断工具链或线程池治理

## 先看两个最容易被"工具选择"带偏的线上事故

第一起是内存缓慢上涨：服务稳定运行两三天后，堆占用一步步爬高，重启后恢复正常，几天后又是同一走势。很多人第一反应是"赶紧 dump 堆"，然后对着几百 MB 的快照不知所措，因为堆里全是看起来正常但就是清不掉的业务对象。

第二起是 CPU 突飙到满核：某个时间点起，CPU 冲上 100% 并持续，接口变慢。很多人第一反应是"抓个线程 dump 看看"，但线上同时有几十个线程，随便抓一次 dump 往往只是某一点的静态切片，热点方法不一定就在那几帧里。

这两起事故真正的问题不在"堆有问题"或"线程有问题"，而在**定位顺序**：内存泄漏要回答的是"谁一直拿着引用不放"，CPU 飙高要回答的是"哪个线程在哪个方法上转圈"。工具只是答案的载体，选错工具、抓错时机，得到的就是一堆无用的快照。

这里至少有三个失败方案。

第一种失败方案，是内存泄漏一上来就全堆 dump。堆转储适合回答"当前有哪些对象占着多少空间、谁引用着它们"，但它是一次性静态快照。如果泄漏是"每过一会儿多一批新对象"的走势，单次 dump 看不到增长趋势，得配合多次 dump 或 `jmap -histo` 看对象计数变化。

第二种失败方案，是 CPU 飙高随手抓一次线程 dump 就下结论。`jstack` 给的是瞬间的线程栈快照；热点方法如果在几个采样点之间高频跳动，单次 dump 可能抓不准。更可靠的做法是连续抓几次、比较哪里反复出现，或者在确认后的线程上用其他方式核对。

第三种失败方案，是把两个问题混用同一套诊断思路。内存泄漏的终点是"堆里谁占大头"（堆转储），CPU 飙高的终点是"哪个线程在哪转圈"（线程转储）。如果 CPU 高却先抓堆 dump，或者内存泄漏却只反复抓线程 dump，方向就从起点就错了。

所以这三个失败方案指向同一个顿悟：**内存泄漏和 CPU 飙高是两条不同的定位主线——一条跟着"活对象的引用链"走，一条跟着"执行中的线程栈"走。先按现象选对方向，再选对那一刻的工具和时机，dump 才有意义；方向反了，dump 越仔细，越浪费时间。**

## 一、内存泄漏：堆转储回答"谁占着不走"，多快照回答"趋势"

### 先从现象判断是不是泄漏

"内存缓慢上涨、重启后恢复"是最典型的强泄漏信号。此时先别急着 dump，先确认是泄漏还是短暂的高峰：连续观察几段时间的堆占用趋势，或者用 `jmap -histo` 看对象数量是否单调增长。如果趋势是"只涨不降"或者"涨到某个水位后 GC 清不掉"，才进入真正的 heap dump 阶段。

### 堆 dump 要回答什么

堆转储（heap dump）回答的核心问题是：**当前时刻，哪些对象占着最多空间，它们被谁引用着。** 分析堆 dump 时，焦点应该放在：

- Dominator tree（支配树）：找到"只要这个对象活着，一大块对象都跟着活"的根
- 大对象列表：占用最高的对象是什么
- 引用路径：这些大对象是被谁一路引用到根的（通常是某个容器、缓存、ThreadLocal、或类加载器）

其中最经典的泄漏根因是类加载器：一个类加载器不被释放，它加载的所有类、所有静态字段里的对象就都变成"仍在引用中"。这类问题的堆 dump 里会出现大量同一类加载器名下的重复类对象。

### 多次快照比单次快照更有效

如果对象是"随着请求逐渐累积"的，一次 dump 无法区分"正常缓存"和"异常泄漏"。正确的做法是：在低峰和高峰分别抓一次 heap dump，对比对象数量和类型变化。某个类型对象数量在两个快照间显著增长，并且增长与请求量正相关，才是真正的泄漏候选。

## 二、CPU 飙高：线程转储回答"哪个线程在哪转圈"

### 从 OS 层定位到线程

CPU 飙高定位的第一步不在 JVM 工具里，而在操作系统：用 `top` 看到是哪个进程 CPU 高，再用 `top -H` 或 `ps` 按线程看是哪些线程在烧 CPU。这一步的关键是拿到"线程的 native 线程号（tid）"，因为 JVM 工具（`jstack`）里给出的是 Java 线程 ID，而 OS 层看到的是 native 线程 ID——两者需要通过 `printf "%x" PID` 把十进制转十六进制和 Java 线程 ID 对上。

### jstack 侧要对上号

`jstack <pid>` 输出的每一段是一段线程栈。定位 CPU 高烧点时，要把 OS 侧 `top -H` 发现的高 CPU 线程号，转成十六进制后，在 dump 里找到对应 Java 线程；然后再看它的栈顶——是业务代码在循环、是锁等待、还是 GC 线程本身。

这一步经常被人跳过：不核对线程号就翻 dump，最后在错误的线程栈上浪费大量时间。

### 连续采样比单次准确

CPU 热点在采样点之间可能快速移动。一次 `jstack` 只能代表"这一刻"的栈。正确做法通常是：隔一小段时间连续抓 3-5 次 `jstack`，比较哪些方法反复出现在同一线程栈顶。反复出现的才是稳定的热点；只在一次里出现、后面立刻变的，更可能是随机路过。

到这里，两条主线（内存泄漏和 CPU 飙高）的定位工具和时机已经讲清了。接下来这一节看看另一种可能性：不依赖外部工具，直接在应用内用 `ThreadMXBean` 拿线程栈信息。

## 三、`ThreadMXBean`：不依赖外部工具的程序化诊断入口

### 在应用里也能拿到这些信息

很多时候线上不允许临时上 `jstack`，或者希望把诊断能力内建到监控里。JDK 11 的 `java.management` 模块提供了程序化入口，不需要外部工具：

- `ThreadMXBean.dumpAllThreads(boolean lockedMonitors, boolean lockedSynchronizers)`（`ThreadMXBean.java:103-104`）：拿全量线程栈，效果接近 `jstack`
- `ThreadMXBean.findDeadlockedThreads()`（`:111`）：检测等待循环导致死锁的线程
- `ThreadMXBean.getThreadInfo(long id)`（`:206`）：按线程 ID 拿单个线程信息

这些 API 的意义在于：你可以把"周期性抓线程栈"做成应用内的监控逻辑，在告警触发时自动采集，而不是等人手动登录机器再敲命令。

### 什么时候用程序化、什么时候用外部工具

外部工具（`jstack`/`jmap`）的优点是不改代码、随时可用；缺点是依赖人工、时机靠人抓。程序化 API 的优点是可以嵌入告警、自动采集，缺点是你要预先内置这些逻辑，且 `dumpAllThreads` 这类调用本身也有一定开销，不能高频触发。

## 四、两个工具的边界：线程转储 vs 堆转储

### 一张表理清分工

| 问题 | 该先看 | 工具 |
|------|--------|------|
| 内存缓慢上涨、GC 清不掉 | 堆里谁占大头、被谁引用 | heap dump / `jmap -histo` |
| CPU 飙满、接口变慢 | 哪个线程在哪个栈顶上转 | thread dump / `jstack` |
| 接口卡死、疑似死锁 | 有无线程僵在锁等待链 | `jstack` + `findDeadlockedThreads` |
| 启动后系统才变慢 | 类加载器/缓存是否泄漏 | heap dump + 多次对拍 |

### 为什么不能互换

线程转储看不到"对象占用"：它只告诉你线程在干什么，不告诉你堆里谁在膨胀。堆转储看不到"谁的 CPU 高"：它只给你当前对象布局，不提供执行热点。两者是 JVM 的两个不同截面——一个管"活着的东西在哪"，一个管"正在跑的东西在哪"。把问题按"是内存还是 CPU"归类，再选对应的 dump，才不会走错方向。

## 五个最容易混掉的边界：内存问题看堆不看线程，CPU 问题看线程不看堆，单次 dump 不能当结论，工具线程号要对上 Java 线程号，程序化诊断也是选项

第一，内存问题看堆不看线程。堆转储回答"谁占着不走、谁引用着它"，线程转储对这种问题几乎帮不上忙；CPU 问题反过来看线程不看堆，堆快照给不了执行热点。

第二，单次 dump 不能当结论。内存泄漏要看多次快照的趋势，CPU 热点要连续采样对比；一次静态快照只能证明"这一刻长这样"，不能证明"一直是这个模式"。

第三，工具线程号要对上 Java 线程号。`top -H` 给的是 native 线程号，`jstack` 给的是 Java 线程 ID，两者要经过进制转换和对照，否则很容易在 dump 里找错线程。

第四，`ThreadMXBean` 是程序化诊断入口不是摆设。`dumpAllThreads`、`findDeadlockedThreads`、`getThreadInfo` 能把抓取逻辑内建进监控，让告警自动采集，而不是等人手动上机。

第五，jstack/jmap 工具的输出来自 JVM 工具实现，不同版本输出格式可能有差异；同一套诊断思路，在 JDK 8 和 JDK 11 上工具命令、输出字段要对应当前版本，不能拿旧格式硬套。

把这五条边界记稳，内存泄漏与 CPU 飙高的定位就不会再被"一上来就 dump"带偏。它真正想讲的是：先按现象判断是内存问题还是 CPU 问题，再选对的快照类型和时机；内存跟引用链走，CPU 跟线程栈走，两个方向一旦选错，dump 再多也只是在错误截面里找答案。

## 收网：定位的第一步不是打开工具，而是确认该看哪个截面

回到开头两起事故，现在能看清它们各自的正确顺序了。

内存缓慢上涨：先确认趋势（连续观察/`jmap -histo`），再做 heap dump，重点看支配树、大对象、类加载器；必要时低峰/高峰各抓一次对比增长。

CPU 突飙：先用 `top -H` 定位高 CPU 线程，转十六进制对到 `jstack` 里的 Java 线程，连续采样几个点找出稳定热点，再落到具体方法。

把整篇压成一张总图：

```text
内存泄漏
  → 现象：堆缓慢上涨，GC 清不掉
  → 先看趋势，再抓 heap dump
  → 重点：支配树 / 大对象 / 类加载器
  → 多次快照对比增长

CPU 飙高
  → 现象：接口变慢，CPU 冲满
  → 先 top -H 找线程，转十六进制对上 jstack
  → 连续采样几个点，找稳定热点
  → 落到具体方法或锁或 GC

程序化诊断
  → ThreadMXBean.dumpAllThreads / findDeadlockedThreads / getThreadInfo
  → 内建到监控，告警自动采集

工具边界
  → 无引用的 dump 快照：只在错误的时间点看错误截面
```

所以当你在线上遇到"变慢、变卡、内存上涨"时，真正该问的不是"要不要 jstack 还是 jmap"，而是：**这个现象是内存问题还是 CPU 问题？我该看的是活对象的引用链，还是执行中的线程栈？** 想清楚截面再动手，工具才会为你提供答案；想不清就 dump，工具只会再给你一堆需要继续猜的数据。
