# JDK 诊断工具链：jps、jstack、jmap、jstat、jcmd 到底该在什么时候用

> 基于 JDK 11 `jdk.jcmd` 模块的工具入口：`sun.tools.jcmd.JCmd`（`JCmd.java:51`）、`sun.tools.jstack.JStack`（`JStack.java:41`）、`sun.tools.jmap.JMap`（`JMap.java:47`）、`sun.tools.jps.Jps`、`sun.tools.jstat` 包。本文讨论的是这些工具各自回答什么问题、在什么阶段该用哪一个，以及 `jcmd` 作为统一入口和 JFR 的关系。工具的具体命令语法属于 JDK 工具实现，不同版本可能有差异；本文给的是 JDK 11 的通用分工，不是命令手册。

## 先看一个看似"工具很多、随便用用就行"的实际误区

很多人在线上遇到问题时，顺手就敲 `jstack` 或 `jmap`，哪个"听起来对"就用哪个。`jstack` 拉线程栈、`jmap` 看堆，反复几个来回，耗时又长，最后往往发现：工具确实能跑，但抓到的信息并不是当时最需要的那个截面。

问题的根源不是"工具不够用"，而是**没有先判断诊断阶段**。诊断一个线上问题，通常要经过"找到目标进程 → 看进程状态 → 看线程/内存/GC → 深入某一点"几个阶段，每个阶段有它最合适的工具。把工具当一道一道随便点的菜，就会用了半天还在原地的信息里打转。

这里至少有三个失败方案。

第一种失败方案，是不知道哪个工具"先用"。比如直接对 `/proc` 里找不到、或者已经被中断的 PID 敲 jstack，报错后才想起来该先确认进程还在不在。合适的第一步其实往往是最不起眼的 `jps` 或 `jcmd -l`——列出当前 JVM 和 main 参数。

第二种失败方案，是把 GC 相关分析全压给 `jmap`。`jmap -heap` 给的是某时刻的堆信息，`jstat` 才是看 GC 趋势和停顿的持续观测工具。想看"堆长期怎么走"，该用 `jstat`；想看"这一瞬间堆里什么东西占了多少"，才用 `jmap`。

第三种失败方案，是把 `jcmd` 当成"另一个最强大命令"，却不清楚它其实是一组子命令的统一入口。`jcmd <pid> help` 能列出系统支持的所有子命令，包括 JFR、Thread.print、GC.class_histogram 等；把它只当单条命令用，会浪费这个统一入口最大的价值。

所以这三个失败方案指向同一个顿悟：**诊断工具不是六个平行按钮，而是一条按阶段排列的路径。先用 jps/jcmd 确认目标和入口，再用 jstack/jstat 看线程和趋势，最后用 jmap/jcmd 深挖堆或对象。每换一个工具，都是在回答上一个工具提出的下一层问题。**

## 一、`jps` 与 `jcmd -l`：先确认目标是谁

### 它们回答"当前有哪些 JVM"

`jps` 列出当前机器上的 JVM 进程以及它们各自的进程号。`jcmd -l` 除了列出进程，还会带上每个 JVM 的主类或 main 参数。对多服务同机部署的环境，这一步能帮你确认"我要操作的是哪一个 PID"，避免对一个无关进程误用诊断命令。

### 为什么要先走这一步

后面所有工具（jstack/jmap/jstat/jcmd）都要求一个正确的 PID。先 `jps` 或 `jcmd -l` 确认 PID 和进程身份，是整条诊断链的第一步。跳过这步直接对猜测的 PID 操作，可能在错误进程上浪费时间，甚至对系统进程误发命令。

## 二、`jstack`：看线程的某一刻，重点在"主线程栈顶"

### 它回答"某个线程此刻在干嘛"

`jstack`（`JStack.java:41`）抓取 JVM 的线程栈快照，给出每个 Java 线程当时在执行哪组方法、处于什么状态。它适合回答：有没有线程僵在锁上、某个线程栈顶是不是热点方法、有没有明显的死锁等待环。

### 它的边界

`jstack` 是一次性的静态切片，看不到趋势。上一篇文章已经强调过：CPU 热点要连续采样几次对比，不能靠单次下结论。另外它的抓取动作本身也有开销，生产环境高频触发会引入额外负担。

## 三、`jstat`：看 GC 和类加载的趋势，是"持续观测"工具

### 它回答"堆和 GC 在一段时间内怎么走"

`jstat -gcutil <pid> <interval>` 按固定间隔输出 GC 使用率、次数和耗时。它是四个工具里最适合"持续盯趋势"的：想要"老年代占用是不是单调上涨""GC 停顿是不是越来越频繁"，看 `jstat` 比反复抓 `jmap` 更直接。

### 它和 `jmap` 的分工

可以把两者想成"趋势 vs 快照"：

- `jstat`：持续观测，回答"这段时间 GC 怎么走、堆使用率怎么变"
- `jmap`：单点快照，回答"这一刻堆里谁占大头、能不能导出 heap dump"

看趋势用 `jstat`，确认具体对象和引用路径时才切到 `jmap`。

## 四、`jmap`：看堆快照和对象分布，是"深挖"工具

### 它回答"这一刻堆里有什么"

`jmap`（`JMap.java:47`）主要两类用途：`jmap -histo` 按类统计对象数量和占用，`jmap -dump` 导出 heap dump 供离线分析。它回答的是"当前时刻哪些对象最多、谁占着空间"。

### 它的边界

`jmap -dump` 和 `-histo` 在较大堆上可能触发明显的临时开销甚至短暂停顿，生产环境要评估时机。更稳妥的深挖做法有时是 `jcmd <pid> GC.heap_dump -filename=...`，它和 `jmap -dump` 走同一层诊断入口，但通过 jcmd 的子命令形式更容易和其他诊断统一管理。

到这里，jps 到 jmap 这条"确认目标 → 看线程 → 看趋势 → 深挖堆"的路径已经走完了。最后一节看 jcmd——它不是一个独立工具，而是把前面这些能力统一到了同一个入口下。

## 五、`jcmd`：统一入口，能做的事远不止一条命令

### 它是一组子命令的壳，不是单条命令

`jcmd <pid> help` 会列出当前 JVM 支持的所有子命令。JDK 11 里常见的包括：

- `Thread.print`：打印线程栈（对应 jstack 的核心能力）
- `GC.class_histogram`：类直方图（对应 jmap -histo）
- `GC.heap_dump`：导出堆转储
- `GC.run` / `GC.run_finalization`：手动触发 GC 相关动作
- `JFR.start` / `JFR.dump` / `JFR.stop`：JFR 录制控制

这意味着许多过去要用不同工具分开敲的动作，现在都可以统一到 `jcmd <pid> <子命令>` 上。统一入口的价值在于：诊断动作集中在一个语法下，脚本化、自动化都更容易。

### `jcmd` 与诊断 API 的关系

`jcmd` 部分子命令（如 `GC.heap_dump`、`Thread.print`）底层通过 JVM 的诊断接口导出数据，和 `ThreadMXBean`、`HotSpotDiagnosticMXBean` 等程序化 API 走的是不同入口——前者是外部工具，后者是应用内 API。`jcmd` 适合人工/脚本即时诊断，程序化 API 适合把抓取逻辑内建到监控里。

## 六个最容易混掉的边界：jps 没有信号而是列表，jstack 是快照不是趋势，jstat 是趋势不是快照，jmap 是深挖不是日常轮询，jcmd 是统一入口不是单命令，工具输出格式随版本变

第一，`jps` 不是"发送信号"的工具，而是列出当前 JVM 的目录工具。它本身不做诊断，只帮你确认该对哪个 PID 操作。

第二，`jstack` 是快照不是趋势。它给出某一刻的线程栈，CPU 热点需要连续采样对比；单次快照只证明"那一刻长这样"。

第三，`jstat` 是趋势不是快照。它给出按间隔采样的 GC/堆使用数据，适合看走势；想看"这一瞬堆里谁占大头"，它给不了，要切 `jmap`。

第四，`jmap` 是深挖不是日常轮询。它做 heap dump 或 histo 时有瞬时开销，适合在确认有问题后单点使用，不适合高频定时扫描。

第五，`jcmd` 是统一入口不是单条命令。`jcmd <pid> help` 列出所有子命令；Thread.print、GC.class_histogram、JFR 控制等都能从这里统一发起。

第六，工具输出格式随版本变。JDK 8 与 JDK 11 的 `jstat`/`jmap` 输出字段、列名可能有差异；跨版本对照时要按当前版本工具的实际输出理解，不能拿旧命令手册硬套。

把这六个边界记稳，JDK 诊断工具就不会再被当成六个平行按钮。它真正想讲的是：工具服务的不是"要不要敲一个好看的命令"，而是"当前诊断阶段需要哪一层信息"——先确认目标（jps）、看线程（jstack）、看趋势（jstat）、深挖堆（jmap）、统一入口（jcmd），每一站都是上一站问题的下一层。

## 收网：诊断工具是路径，不是按钮

回到开头那个"随手敲工具"的误区，现在能看清为什么它会失败了。

如果你没有先确认 PID 就敲 `jstack`，可能在错误进程上浪费时间；如果你想要的是"老年代是不是一直涨"却用了 `jmap`，看到的只是瞬间快照；如果你不知道 `jcmd` 是一组子命令的入口，就会错过 JFR、Thread.print、GC.class_histogram 这些统一发起的动作。

把整篇压成一张总图：

```text
jps / jcmd -l
  → 列出 JVM，确认操作目标 PID

jstack
  → 线程栈快照
  → 看有没有线程僵、栈顶是不是热点
  → 单次快照，热点要连续采样

jstat
  → GC / 堆使用趋势
  → 看老年代是不是涨、GC 停顿是不是变多

jmap
  → 堆直方图 / heap dump
  → 看时刻对象分布，深挖引用
  → jcmd <pid> GC.heap_dump 可统一发起

jcmd
  → 统一入口
  → help 列子命令：Thread.print / GC.class_histogram / JFR.start 等
```

所以当你在线上打开终端时，真正该问的不是"先敲 jstack 还是先敲 jmap"，而是：**我现在处在诊断的哪一层？是要确认目标、看线程、看 GC 趋势、还是深挖堆？** 顺着这条路径走，每换一个工具都是在回答上一站遗留的问题；直接跳层，往往只是在错误的信息里继续打转。
