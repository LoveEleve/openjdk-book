# ConcurrentSkipListMap 跳表：为什么并发有序 Map 不选红黑树

> 本文基于 JDK 11 `java.util.concurrent.ConcurrentSkipListMap`。讨论范围聚焦底层有序链表、`Index`/`HeadIndex` 多层索引、`findPredecessor`/`doGet`/`doPut` 主路径、marker 删除协议，以及范围查询的弱一致边界。`ConcurrentSkipListSet` 只在文末作为包装收束，不展开独立实现细节。
> **前置依赖**：[ConcurrentHashMap 扩容与计数](02-resize-count.md)、[TreeMap 与有序 Map 基础](../09-map-hash/03-linkedhashmap-treemap.md)
> **后续**：[CopyOnWrite 与无锁队列](04-copyonwrite-concurrentqueue.md)

## 先看一个最自然、也最容易把有序并发做成大锁的直觉

当业务需要“有序”时，很多人第一个想到的是 `TreeMap`；当业务再加上“并发”时，最顺手的补丁就是在外面包一把锁。表面看，这似乎已经满足了需求：有序性有了，线程安全也有了。但只要场景稍微像样一点，这个方案就会很快露出代价。

例如做一个延迟任务调度表，线程们会同时做三类事：插入新任务、按最小时间戳取出最早任务、按时间窗口扫一段范围。只要外层是一把大锁，查最早任务也要和插入竞争，范围扫描更会把后面的更新请求一起堵住。它不是“不能工作”，而是会把有序访问和并发访问粗暴压成一个串行瓶颈。

那为什么 JDK 不走另一条路：既然 `TreeMap` 本来就是红黑树，直接做一棵并发红黑树不就好了？问题在于，并发有序结构最难的不只是“查找复杂度”，而是修改时影响范围能不能控制在局部。红黑树插入和删除后，常常还要做旋转、重着色和平衡修复，结构影响会沿父子关系向上扩散。你当然可以为它设计复杂同步协议，但它很难像局部链表重连那样，把并发修改限制在相邻指针范围内。

这正是 `ConcurrentSkipListMap` 的出发点：**保留有序查询能力，但把底层结构换成更适合局部 CAS 修改的跳表。** 整篇文章只回答一个主问题：并发有序 Map 为什么更愿意选“底层有序链表 + 上层稀疏索引”，而不是并发红黑树。

## 一、跳表不是树的别名，而是“链表本体 + 稀疏导航层”

### 先把结构图定住

如果只记一句“跳表有很多层”，后面读 `ConcurrentSkipListMap` 源码时很容易迷路。真正应该先建立的，是它的角色分工：**所有真实键值都存在底层有序链表，上层索引只负责帮你更快接近目标位置。**

JDK 11 里，最顶层入口是 `head`：

```java
// ConcurrentSkipListMap.java:340
private transient Index<K,V> head;
```

底层真实数据节点是 `Node`：

```java
// ConcurrentSkipListMap.java:359-363
static final class Node<K,V> {
    Node<K,V> next;
    Node(K key, V value, Node<K,V> next) {
```

上层导航节点是 `Index`：

```java
// ConcurrentSkipListMap.java:373-377
static final class Index<K,V> {
    final Node<K,V> node;
    final Index<K,V> down;
    Index<K,V> right;
```

把这三者连起来，结构图就很清楚了：

```text
head
  → 最高层索引链：尽量向 right 走
      ↓ 走不动就 down
  → 下一层索引链：继续向 right 逼近
      ↓ 再 down
  → 底层全量有序链表：所有真实 key/value 都在这里
```

所以跳表不是“随机化版树”，也不是“树和链表混合体”这种模糊说法。更准确地说，它是一条全量有序链表，上面叠了若干层越来越稀疏的快捷索引。查找时先靠索引快速逼近目标区间，再落到底层链表收口。

### 为什么这种形态天生更适合并发

这时再回头看“为什么不直接做并发红黑树”，答案就开始清楚了。红黑树的问题不在于查找不够快；问题在于修改一旦触发平衡修复，结构变化往往不是某两个相邻引用之间的小改动，而可能沿着父子链继续蔓延。你要保证并发线程都能看懂这场结构变化，代价会很高。

跳表则不同。它的本体是链表，索引层也还是链表。插入和删除的核心动作，最终都可以落回“把某个节点插进前驱和后继之间”或者“把某个节点从相邻链中摘掉”。也就是说，它把有序结构维护问题尽量局部化成了相邻指针重连。

JDK 类注释在开头就把这种取向说得很直白：它强调的是对频繁遍历的索引链表使用更便宜的算法（`ConcurrentSkipListMap.java:120-123` 一带），而不是为了一棵严格平衡树去维护更复杂的全局结构。

这一层只记住一句话：**跳表之所以被选中，不是因为它比红黑树“更强”，而是因为它更容易把并发修改控制成局部链路操作。**

## 二、查找为什么能只靠“向右走，走不动就向下落”

### 先看有序查找真正依赖的动作

一旦结构图立住，查找主线反而比树更直观。跳表不要求你在脑子里维护左右子树和旋转规则，它只做两种移动：

- 如果右边索引还没超过目标 key，就继续向右
- 如果再向右就会越界，就下降到下一层

这个策略在 `findPredecessor` 里最明显。方法入口在 `ConcurrentSkipListMap.java:464`。它从 `head` 开始，一层层做“右移或下落”的判断，直到找到目标 key 在底层链表中的前驱位置。

这里比较大小时统一走 `cpr`（`ConcurrentSkipListMap.java:391`），把比较器和自然顺序都收口到同一个入口。真正的重点不在于 API 名字，而在于查找策略本身：**上层索引负责缩小范围，底层链表负责最终命中。**

### `doGet` 为什么仍然是“索引导航 + 底层收口”

`doGet` 入口在 `ConcurrentSkipListMap.java:536`。它不是另一套全新算法，而是沿着同样的思路展开：先在索引层向右/向下逼近目标，再在底层链表完成最后比对。

这样设计有两个直接好处。第一，查找的主要行程被索引层大幅压缩，平均情况下仍能保持 `O(log n)` 的期望复杂度。第二，也是更重要的一点，查找线程读到的结构都是链式局部关系：右边是谁、下一层是谁、底层后继是谁。它不需要理解一棵平衡树在旋转过程中的中间姿态。

这里给一个路标：这一节不是为了证明“跳表也有 `O(log n)`，所以和树一样好”。那只是复杂度口径上的结论。更值得记住的是，**跳表把“快查找”建立在多层局部导航上，而不是建立在全局平衡修复上。** 后面讲并发插删时，这个区别才会真正体现出价值。

## 三、插入为什么不需要全局锁：因为真正改动的是局部相邻指针

### 先排除“大锁保护有序插入”的直觉

对有序结构做插入时，最自然的保护方式还是大锁：锁住整张表，找到插入位置，改完再放锁。这个方案当然简单，但它把“局部有序插入”夸张成了“全局禁止别人前进”。范围查询、最小值读取、别的 key 的插入，统统得为这一条链路停下来。

`ConcurrentSkipListMap` 选择的是另一条路线。`doPut` 入口在 `ConcurrentSkipListMap.java:595`。它先在索引层下降，最终落到底层链表的前驱位置，然后尝试把新节点 CAS 到前驱和后继之间：

- 初始化底层或定位前驱
- 在底层链表上尝试插入新 `Node`
- 如果插入成功，再根据随机层高为它补建若干 `Index`
- 必要时通过 `head` 再向上长出新层

底层插入的关键动作出现在 `ConcurrentSkipListMap.java:653` 一带，后续加索引的主线则在 `665-676` 和 `addIndices`（`ConcurrentSkipListMap.java:701+`）附近。

### 为什么先插底层，再补索引层

这是跳表实现里一个很值得记的顺序。很多人初看会以为“索引层不是更高更快吗，那是不是应该先把高层建好？” 实际恰好相反。真正的数据本体是底层有序链表，所以**只有当底层节点已经稳定进入有序链，给它补索引才有意义。**

这也解释了为什么运行时主线不应该被“随机层高”抢走焦点。层高当然重要，它决定索引稀疏度和期望复杂度；但从并发插入的角度看，更关键的是：插入首先是一场底层相邻指针的局部链接，然后才是附加导航层的逐层补全。

也正因为如此，插入线程真正需要争用的往往只是它眼前那几个相邻节点，而不是整张表的全局结构。失败了就重试前驱定位和局部 CAS，成功了就继续补索引。这种局部失败重试，比平衡树那种可能触发全路径修复的修改，更容易和并发环境相处。

## 四、为什么删除不能一步 CAS 完成：marker 是为了让别的线程看懂“它正在退出”

### 先看最朴素、也最容易出问题的删除方案

如果只从单线程链表出发，删除一个节点最直觉的想法就是：前驱直接把 `next` 改到目标节点的后继，整个删除一步完成。问题在于并发跳表不是单线程链表。别的线程此刻可能正好读到了目标节点，或者正要沿着它继续前进，或者也在尝试对同一段链路做修改。单步越过虽然看上去最省事，却没有给其他线程留下足够清晰的中间状态，让它们知道“这个节点不是正常存在，而是正在被摘除”。

JDK 11 的类注释专门把删除协议写成了三步（`ConcurrentSkipListMap.java:199-207`）：

1. 先把待删节点逻辑删除
2. CAS 把它的 `next` 指向一个 marker 节点
3. 再让前驱越过待删节点和 marker

注释里的图已经很直观：

```text
... -> b -> n -> marker -> f -> ...
```

这里的 marker 不是“学术版 ABA 标记位”的照搬，而是工程上一个显式可识别的过渡节点。它的职责非常具体：**告诉后来线程，这个节点已经不再是稳定成员，但前驱清理动作可能还没完全做完。**

### `unlinkNode` 和帮助清理说明了什么

真正执行这套协议的辅助逻辑在 `unlinkNode`（`ConcurrentSkipListMap.java:413-423`）里。你会看到，它不是简单“如果能删就删”，而是先在必要时补 marker，再推进前驱越过被删节点。

更关键的是，这套协议不是只让发起删除的线程自己收尾。`findNode`（`ConcurrentSkipListMap.java:503-517`）在查找过程中如果碰到已经删除或带 marker 的节点，也会顺手帮忙清理。这正是跳表并发实现里非常典型的一种思路：**删除不是一锤子买卖，而是一个别的线程也能识别、也能协助推进完成的退出协议。**

这和上一篇 CHM 的 `ForwardingNode` 有点像：都不是为了多发明一个内部节点类型，而是为了让后来线程在看到“半路上的状态变化”时，不必发懵或停机等待，而能知道自己该继续找、该帮忙清理，还是该转向下一跳。

### marker 真正修复了哪种失败方案

所以 marker 的价值，不是让源码显得复杂，而是修复了前面那个朴素失败方案：删除如果只想一步 CAS 越过去，其他线程很难知道自己看到的是“稳定链表”还是“刚被别人抽走半截的链表”。有了 marker，这次删除就变成了可观察、可识别、可协助完成的多步协议。

这一层一定要记住，因为它恰好体现了并发跳表的设计哲学：**允许中间态存在，但中间态必须能被其他线程看懂。**

## 五、范围查询为什么能工作，但只给弱一致视图

### 有序能力从哪里来

并发跳表之所以值得存在，不只是因为它线程安全，更因为它保留了有序结构最有价值的那批能力：

- `firstKey` / `lastKey`
- `ceilingEntry` / `floorEntry`
- `subMap` / `headMap` / `tailMap`

这些 API 之所以能成立，不是因为索引层很炫，而是因为**底层链表始终按 key 有序。** 索引层只是帮你更快逼近位置；真正保证“最左边是谁”“某个 key 的前后边界在哪”的，仍然是底层有序链路。

像 `findFirst`（`ConcurrentSkipListMap.java:829`）和 `findFirstEntry`（`ConcurrentSkipListMap.java:845`）这种方法，本质上都是在这套有序底层之上寻找边界入口。

### 为什么它不承诺全局一致快照

但这里马上有一个容易误判的地方：有序，不等于快照一致。很多人一看到范围 API，就会下意识期待“既然顺序是稳定的，那我遍历一段范围时看到的应该也是同一个时刻的静态画面”。并发跳表并不提供这种承诺。

原因很直接：它并没有在范围遍历前先把整个结构冻住。别的线程仍可能在你遍历过程中插入新键、删除旧键、清理 marker、补索引层。于是你得到的是一个**顺序不乱、结构不坏、但允许与并发修改交错的弱一致视图**。

这里的取舍其实和前两篇完全同一脉络。CHM 为了高吞吐量，接受了 `size()` 弱一致；并发跳表为了保留有序导航能力且不引入全局大锁，也接受了范围视图不是线性一致快照的代价。

更准确地说，它承诺的是：

- 你走过的键序不会乱掉
- 并发插删不会把结构搞坏
- 但你不该把遍历结果理解成某个冻结瞬间的完整快照

这一层的顿悟是：**`ConcurrentSkipListMap` 保障的是可并发前进的有序视图，而不是静态快照语义。**

## 六、`ConcurrentSkipListSet` 不是另一套结构，只是把 value 固定住的包装

### 为什么这里值得顺手收一下

讲完 `ConcurrentSkipListMap` 后，很多人会顺手再问一句：那并发有序 Set 呢？JDK 的答案并没有再发明一套新结构，而是复用同一个底座。`ConcurrentSkipListSet` 本质上就是一个把 value 固定成占位值的并发跳表 map 包装。

对应证据很直接：

- 类定义：`ConcurrentSkipListSet.java:95`
- 注释写明 value 用 `Boolean.TRUE`：`ConcurrentSkipListSet.java:102`
- 默认构造直接 new 一个 map：`ConcurrentSkipListSet.java:113`

这件事的意义不在于多讲一个 API，而在于帮助读者把心智统一起来：并发有序 Set 和并发有序 Map 不是两条分裂路线，底层都是同一套跳表协议。

## 五个最容易混掉的边界：跳表不是树换壳，索引不是数据本体，局部 CAS 不是零重试，marker 不是垃圾节点，范围有序也不是快照一致

第一，跳表不是树换壳。它的核心不是“把红黑树随机化”，而是把真实数据放到底层有序链表，再用稀疏索引层做导航；如果把它理解成另一种树，就会错过它为什么更适合局部并发修改。

第二，索引不是数据本体。`Index` 和 `HeadIndex` 负责加速 right/down 导航，真正的 key/value 归属仍然在底层 `Node` 链表；这也是为什么插入必须先把底层链表接好，再补索引层。

第三，局部 CAS 不是零重试。跳表避免的是全局大锁和大范围结构修复，不是保证每次修改都一次成功；并发线程仍可能在同一段相邻链路上竞争，失败后需要重新定位前驱并重试局部链接。

第四，marker 不是垃圾节点。它不是“迟早会被 GC 的多余对象”，而是删除协议里的显式中间态，专门用来告诉后来线程：这个节点正在退出，请协助越过或清理，而不要把它当稳定成员继续依赖。

第五，范围有序也不是快照一致。`subMap`、`headMap`、`tailMap` 和边界查找保留了顺序语义，但遍历过程中别的线程仍可并发插删；你看到的是可继续前进的有序弱一致视图，不是某个冻结时刻的静态画面。

把这五条边界记稳，ConcurrentSkipListMap 就不会再被误解成“有序版 CHM”或“并发版 TreeMap”。它真正想讲的是：为了保留有序导航又不把同步范围扩散到整张结构，JDK 11 选择了链表本体、稀疏索引、局部 CAS 和可被协助完成的删除协议。

## 收网：跳表真正替代的不是树，而是“大范围同步”

回到开头那个问题：并发有序 Map 为什么不选红黑树？现在已经可以给出一个比“实现简单”更准确的答案了。

第一，跳表把数据本体放在底层有序链表，把“快查找”交给上层稀疏索引；它不是随机树，而是链表本体加导航层。第二，插入和删除的核心动作都能局部化成相邻指针 CAS 和失败重试，不必像平衡树那样频繁触发更大范围的结构修复。第三，删除协议通过 marker 把中间态显式暴露出来，让别的线程能识别并帮助清理；第四，范围 API 仍然成立，因为底层顺序始终被维护，但它给的是弱一致可并发视图，而不是冻结快照。

把这些点压成一张总图，就是：

```text
并发有序需求
  → 不想用全局锁包 TreeMap
  → 选择底层有序链表作为真实数据面
  → 用多层 Index 加速 right/down 查找
  → 插入走局部 CAS 链接
  → 删除走 marker 三步协议
  → 范围查询保留有序性，但接受弱一致视图
```

所以，`ConcurrentSkipListMap` 真正替代的不是“树”这个名词，而是那种为了维持全局平衡而更容易扩大同步范围的思路。JDK 11 选跳表，是因为它更擅长把有序结构维护拆成线程们可以局部推进、失败后重试、必要时互相帮助清理的小动作。
