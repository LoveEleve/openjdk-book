# TransferQueue 与并发集合选型：入队成功为什么不等于交付成功

> 本文基于 JDK 11 `TransferQueue`、`LinkedTransferQueue`，并串联本域已经重写的 CHM、SkipList、CopyOnWrite/CLQ 与 BlockingQueue。讨论重点是 `put` 与 `transfer` 的语义差异、数据节点/请求节点配对、`xfer`/`awaitMatch` 主线，以及并发集合和线程池工作队列的选型边界。完整 sweep 清理和所有实现分支不在主线逐行展开。
> **前置依赖**：[阻塞队列家族](05-blocking-queues.md)、[ConcurrentHashMap 存储与读写](01-chm-storage-rw.md)
> **后续**：域 14 线程池与任务执行

## 先看一个“任务已经入队，但业务仍然不敢算交付”的场景

假设一个系统把任务放进并发队列后立刻向上游返回“提交成功”。这个返回到底意味着什么？是任务已经被某个消费者线程拿走了，还是只是暂时躺在队列里，等未来某个消费者有空再处理？这两个答案在低负载时看起来没区别，一到故障排查或流量高峰就会完全分叉。

如果业务只需要“队列接住了这个任务”，普通 `BlockingQueue.put()` 足够：只要队列没有超过容量，元素成功进入队列，生产者就可以返回。可如果业务关心的是“现在已经有接收者接手了”，那 `put()` 的成功就不够强。它可能只代表任务落地，并不代表消费者已经出现。

这不是 API 细节，而是两种不同的交付承诺：

```text
入队确认：元素已经进入某个队列
交付确认：元素已经被某个消费者线程接手
```

`TransferQueue` 正是为第二种问题补上的一层语义。它并不只是给 `BlockingQueue` 多添几个方法，而是把“生产者愿意等到什么程度”明确写出来：愿意入队就走 `put`，必须等接收者就走 `transfer`，只接受当前已经有人等着接就走 `tryTransfer`。

这一篇既是 `10-concurrent-collections` 的收官，也是整个并发集合选型的收束。前面几篇分别解决了映射、有序、快照、无锁推进、空满等待；现在要把它们统一成一个原则：**先确定你要的语义，再谈哪种锁、哪种 CAS、哪种实现更合适。**

## 一、TransferQueue 比 BlockingQueue 多出来的，正是“交付确认”

### `put` 和 `transfer` 到底差在哪

`TransferQueue` 在 JDK 11 中定义为 `BlockingQueue` 的子接口（`TransferQueue.java:68`）。它新增的核心方法不是为了让 API 看起来更丰富，而是为了表达“队列接住”和“消费者接手”之间的距离：

- `tryTransfer(E e)`（`TransferQueue.java:86`）：当前没有等待消费者就立即失败
- `transfer(E e)`（`TransferQueue.java:105`）：没有消费者就等待，直到完成交接
- 定时 `tryTransfer(E e, timeout, unit)`（`TransferQueue.java:134`）：在有限时间内等待交接
- `hasWaitingConsumer()`（`TransferQueue.java:145`）与 `getWaitingConsumerCount()`（`TransferQueue.java:160`）：观察当前是否已有消费者在等待

把它们和 `BlockingQueue.put()` 放在一起，就能看到返回条件的层级：

```text
put
  → 元素成功进入队列即可返回

transfer
  → 必须等某个消费者接手后才返回

tryTransfer
  → 当前没有等待消费者就立即返回失败

定时 tryTransfer
  → 在规定时间内等交接，超时仍未匹配就返回失败
```

这几个方法不是不同写法的同义词，而是不同强度的交付合同。`put` 更像“我把货放到中转站了”；`transfer` 更像“我必须看见接货人，才算这次交付完成”。

### 为什么不能只用 `put` 再额外检查一次队列

朴素方案是先 `put`，再观察 `size()` 或重新查一下队列，期待由此判断消费者有没有接手。问题是这两个动作之间没有形成同一个原子语义：你看到的 size 可能已经被别的线程改变，元素也可能刚被取走、刚被插入，单独的检查无法证明“这一次 put 对应的消费者确实完成了交接”。

`TransferQueue` 的价值就是把“放入”和“配对”放进同一个内部协议里，让发送方不必用外部观察拼凑交付确认。

这一层只要记住一句话：**`put` 的成功边界是入队，`transfer` 的成功边界是被接收。** 这条边界决定了后面所有方法和选型差异。

## 二、LinkedTransferQueue 的角色图：数据节点和请求节点如何相遇

### 它不是普通链队列加一个阻塞方法

`LinkedTransferQueue` 的类定义在 `LinkedTransferQueue.java:91`。如果只把它理解成“更高级的 `LinkedBlockingQueue`”，会漏掉真正的结构变化：它的队列里不仅可以排放带数据的节点，也可以排放代表“我正在等数据”的请求节点。

JDK 11 的节点定义在 `LinkedTransferQueue.java:445-449` 附近，关键字段包括：

```java
static final class Node {
    volatile Object item;
    volatile Node next;
    volatile Thread waiter;
```

这里的 `item` 不只是“队列元素内容”，它还承担模式区分：节点可能是一个发送方带来的数据，也可能是一个接收方留下的空请求。`next` 连接等待队列，`waiter` 记录需要在匹配后被唤醒的线程。

因此，LTQ 的角色图应该先这样画：

```text
发送方
  → 数据节点(data)

接收方
  → 请求节点(request)

队列遍历
  → 找到相反模式的节点
  → CAS 尝试配对
  → 配对成功：数据交给接收者，等待线程唤醒
  → 配对失败：按调用模式入队、返回或继续等待
```

这个模型和普通阻塞队列的“元素存进一个槽位”不同。普通队列的消费者是在未来某个时刻来取已有元素；LTQ 还允许消费者先把自己的请求挂在那里，等发送方出现时直接完成配对。

### 为什么数据节点和请求节点必须同时存在

如果只允许数据节点排队，消费者只能不断检查“前面有没有货”；如果只允许请求节点排队，发送方又不知道该把数据交给谁。两类节点同时存在，才能把“生产者先到”和“消费者先到”这两种时序统一成同一条配对协议。

这也解释了为什么 LTQ 的实现比普通队列更复杂：它不只是维护元素的先后顺序，还要维护两种相反意图的节点，判断它们什么时候可以完成一次交接。

## 三、`xfer` 为什么能把 `put`、`transfer` 和 `tryTransfer` 收成一个状态机

### 先看统一入口

LTQ 把公共方法的差异集中到 `xfer`（`LinkedTransferQueue.java:662`）中，而不是让每个方法各自维护一套“匹配、入队、等待、取消”的逻辑。`awaitMatch` 位于 `LinkedTransferQueue.java:703`，负责在已经挂起等待的情况下处理继续等待、超时、取消和匹配完成。

从调用者视角看，`xfer` 至少需要区分两个维度：

- 我是发送方还是接收方？
- 我愿意等多久？

源码中 `haveData` 就承担第一个维度；`how` 则编码第二个维度，包括立即尝试、异步入队、同步等待和定时等待。公共方法映射集中在 `LinkedTransferQueue.java:1268-1381` 一带。

把这个状态机压成一张图：

```text
xfer(e, haveData, how, nanos)
  ├── haveData=true：发送数据
  └── haveData=false：请求数据

how
  ├── NOW：当前匹配不到就返回
  ├── ASYNC：入队后不等匹配完成
  ├── SYNC：一直等到匹配
  └── TIMED：等到匹配或超时
```

于是各 API 的语义就不再是零散规则：

- `put` 使用数据节点的异步模式，进入队列即可继续
- `transfer` 使用数据节点的同步模式，必须等消费者匹配
- `tryTransfer` 使用立即模式，没有等待消费者就失败
- 定时版在同步交付上再加一条时间边界
- `take` 则以接收方模式进入同一套匹配协议

### 为什么统一状态机比每个方法各写一份更可靠

如果 `put`、`transfer`、`tryTransfer` 分别实现自己的链入和等待逻辑，最容易出现的不是功能缺失，而是边界分叉：某个方法取消等待后没有正确清理节点，另一个方法超时后又留下不同形态的残留；数据节点与请求节点的匹配规则也可能出现微妙差异。

统一 `xfer` 的设计让这些操作共享一套节点配对和等待清理协议，公共 API 只负责选择不同的模式参数。这样做的代价是 `xfer` 本身更复杂，但它把“语义差异”和“底层并发结构”分离开了。

这一层的路标是：**LTQ 的核心不是某个单独的 `transfer()` 方法，而是一个能表达发送/接收、立即/异步/同步/定时的统一状态机。**

## 四、为什么交付确认会改变系统背压

### `put` 返回时，生产者到底确认了什么

`put` 的语义是元素成功进入队列。只要队列接受了它，生产者就可以返回；消费者什么时候取、取之前会排多久，不在 `put` 的返回条件里。这个语义适合“先缓存，稍后处理”的流水线，因为生产者不需要被消费者速度直接卡住。

`transfer` 则故意取消了这层缓冲自由。发送方调用 `transfer(e)` 后，即使节点已经进入了内部等待链，也不能因此返回；它必须等另一个线程以接收方模式匹配到它，交接完成后才能返回。

所以两者对系统背压的影响完全不同：

```text
put
  → 队列可以吸收生产消费速度差
  → 发送方更容易继续推进
  → 代价是任务可能积压

transfer
  → 没有接收者就把发送方挡住
  → 生产速度直接受到消费速度约束
  → 代价是发送方等待、吞吐受交接者影响
```

这不是“transfer 更安全、put 更弱”这么简单，而是两种不同的系统节奏。`put` 把速度差暂存在队列里；`transfer` 不允许速度差被悄悄缓存。

### 为什么还要 `tryTransfer` 和定时版

如果业务要求交付确认，但又不能无限等待，就需要另外两种强度：

- `tryTransfer`：只在此刻已经有等待消费者时完成交接，否则立即失败
- 定时版：允许一段有限等待窗口，窗口结束仍未匹配就返回失败

这两种方法把“严格交付”和“不可无限阻塞”同时保留下来。否则调用方只能在 `transfer` 的无限等待和 `put` 的过早返回之间二选一。

## 五、并发集合选型：先选语义，再选并发策略和实现代价

### 为什么不能只问“哪个容器最快”

并发集合没有一张脱离场景的性能排行榜。不同容器解决的是不同问题：哈希映射、顺序映射、稳定快照、无锁生产消费、有界等待、直接交接、时间到期。你如果先问“哪个无锁、哪个吞吐高”，很可能是在用性能指标替代需求语义。

更可靠的选型顺序应该是：

```text
第一问：我要保存什么语义？映射、集合、队列还是交接？
第二问：我要不要顺序、范围、容量、快照或时间条件？
第三问：并发代价接受什么？锁、CAS、复制、节点、弱一致？
第四问：失败时应该返回、阻塞、超时还是拒绝？
```

### 把本域几类结构放回同一张图

| 需求 | 代表结构 | 核心承诺 | 主要代价 |
|---|---|---|---|
| 无序高并发映射 | `ConcurrentHashMap` | 单操作并发安全、读路径轻 | 弱一致视图、复合操作仍需组合 API |
| 有序并发映射 | `ConcurrentSkipListMap` | 顺序与范围查询 | 索引层与局部 CAS 的复杂度 |
| 读多写少稳定快照 | `CopyOnWriteArrayList` | 迭代器站在旧数组快照上 | 每次写复制 `O(n)` |
| 无阻塞生产消费 | `ConcurrentLinkedQueue` | 节点局部 CAS 推进 | 遍历弱一致、没有空满阻塞 |
| 有界缓冲与等待 | `ArrayBlockingQueue` | 固定容量、空满条件等待 | 一把锁串行化头尾修改 |
| 链式缓冲与头尾并行 | `LinkedBlockingQueue` | 双锁分离、空满等待 | 节点与跨锁计数协调 |
| 不要缓冲只要交接 | `SynchronousQueue` | 生产者消费者直接配对 | 没有接收者就无法完成交付 |
| 需要交付确认 | `LinkedTransferQueue` | `transfer` 等到消费者接手 | 交付等待会把背压传回发送方 |
| 到期才能消费 | `DelayQueue` | 时间条件满足后取出 | 取出顺序受 delay 约束 |

这张表真正要表达的不是“谁更高级”，而是每个容器对调用者做了什么承诺。特别是最后三列附近的结构，差异已经从“数据放在哪里”升级成“线程什么时候允许继续”。

## 六、线程池为什么把队列选择变成调度策略

### workQueue 不是被动存储，而是 execute 路径的一部分

`ThreadPoolExecutor` 持有 `BlockingQueue<Runnable> workQueue`（`ThreadPoolExecutor.java:447`），构造器从 `ThreadPoolExecutor.java:1174-1186` 一带接收它。这个字段看起来只是一个任务容器，实际上它会直接参与线程池的调度决策：任务来了以后，是创建线程、排队，还是触发拒绝。

因此，线程池队列不能只按“容量大不大”选。它实际上在决定线程池的饱和行为。

### 无界队列为什么会压住 maximumPoolSize

如果使用近似无界的 `LinkedBlockingQueue`，任务通常会优先进入队列。只要队列还能接收，线程池就倾向于继续排队，而不是快速创建超过核心线程数的工作线程。这样做适合希望平滑排队的模型，但也可能让 `maximumPoolSize` 很久没有机会发挥，积压则转化成延迟和内存压力。

### 有界队列为什么会把拒绝策略拉进来

使用有界 `ArrayBlockingQueue` 或有界 `LinkedBlockingQueue` 时，队列容量是明确的。核心线程用满、队列也满以后，线程池才会进入继续创建非核心线程或执行拒绝策略的分支。此时队列大小不再只是存储参数，而是系统允许积压多少任务、何时把压力反馈给调用者的控制阀。

### SynchronousQueue 为什么更早推动线程扩展或拒绝

如果使用 `SynchronousQueue`，任务没有中间落点，提交线程必须找到直接接手的工作线程。找不到时，线程池更快进入创建新线程或拒绝的路径。这个选择适合希望任务尽快交给工作线程、不希望在队列里隐式积压的场景，但也意味着线程创建和拒绝压力会更早显现。

所以线程池队列的选择，本质上是在三种行为之间做取舍：

```text
无界/大容量队列
  → 更愿意排队
  → 延迟和内存积压更可能被隐藏

有界队列
  → 明确积压上限
  → 满载后进入扩线程或拒绝

SynchronousQueue
  → 不允许任务落地排队
  → 更早要求接收线程、扩容或拒绝
```

## 收网：并发集合选型的第一原则是语义，不是“无锁”标签

回到开头的问题：为什么 `TransferQueue` 还要在 `BlockingQueue` 之上增加一层？因为“元素已经入队”和“元素已经交到消费者手里”是两种不同的业务事实。`put`、`transfer`、`tryTransfer` 和定时版方法，正是在为这几种不同事实提供不同返回边界。

再把整个 `10-concurrent-collections` 域串起来，主线也就完整了：

```text
我要存 key/value
  → ConcurrentHashMap

我要有序 key/value 和范围查询
  → ConcurrentSkipListMap

我要读多写少、遍历稳定
  → CopyOnWriteArrayList

我要无阻塞生产消费
  → ConcurrentLinkedQueue

我要空满等待和容量流控
  → ArrayBlockingQueue / LinkedBlockingQueue

我要生产者必须等消费者接手
  → SynchronousQueue / LinkedTransferQueue
```

这张图背后的选型顺序只有四步：先确认语义，再确认顺序/容量/快照/交付条件，再评估锁、CAS、复制和内存代价，最后决定失败时应该返回、阻塞、超时还是拒绝。

并发集合的价值，是把共享状态下的常见并发协议封装起来；它并没有让共享状态本身变得免费。能用线程局部数据、消息所有权转移或无共享设计解决的问题，仍然应该优先避免共享。
