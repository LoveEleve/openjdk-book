# ConcurrentHashMap 扩容与计数：为什么它不能只靠一个线程搬家、一个整数计数

> 本文基于 JDK 11 `java.util.concurrent.ConcurrentHashMap`。讨论范围聚焦 `sizeCtl`、`initTable`、`addCount`、`helpTransfer`、`transfer`、`ForwardingNode`、`baseCount`、`counterCells` 与 `sumCount`。树化细节、跳表与其他并发容器留到后续篇章。本文提到的 `size()` 弱一致与分片计数，指的是 JDK 11 当前实现策略，不应外推为所有 map 的统一语义。
> **前置依赖**：[ConcurrentHashMap 存储与读写](01-chm-storage-rw.md)、[LongAdder 与分片计数](../13-atomic/02-striped64-longadder.md)
> **后续**：[ConcurrentSkipListMap 跳表](03-skiplist.md)

## 先看两个最顺手、也最容易把并发打崩的朴素方案

上一篇已经把 `ConcurrentHashMap` 的读写主线立住了：读路径尽量不加锁，空桶写尽量用 CAS，只有桶内真正发生冲突时才锁首节点。但只把 `put` 和 `get` 跑通，还不够说明这张表能在高并发下长期活下去。真正会把它拖死的，往往是另外两件事：表满了要扩容时怎么办，以及元素个数要怎么统计。

最顺手的扩容方案，是让某个线程停下来把旧表所有桶一次性搬到新表，其他线程在这段时间里等它干完。单线程 `HashMap` 就是这么想问题的，因为它不需要关心别的线程此刻是否也在往表里写数据。但并发场景里，这种独占扩容会立刻放大成停顿：越是写入高峰，越容易有线程撞上“我要扩容，所以大家先别动”。

最顺手的计数方案，是给整张表放一个全局 `size`，每次插入或删除都对它做一次 CAS 或原子加减。这个方案在低竞争时没毛病，可一旦很多线程同时写入，它们就会反复在同一个内存位置上碰撞。数据本身可能分散在不同桶里，计数却被强行压回同一个热点上。

所以这一篇要回答的其实是两个同类问题：**当成本开始全局化时，CHM 怎么把它重新拆散给并发线程分摊？** 扩容上，它不想让一个线程独占搬家；计数上，它不想让所有线程争抢一个整数。围绕这个目标，JDK 11 把两条机制都做成了“协调 + 分片 + 汇总”的协议。

## 一、`sizeCtl` 不是普通阈值，而是扩容与初始化的协调旗

### 先别把它当成单一字段说明书

如果直接看源码字段定义，`sizeCtl` 很像一个普通的容量控制参数：

```java
// ConcurrentHashMap.java:800
private transient volatile int sizeCtl;
```

但它真正扮演的角色，比“下一次扩容阈值”复杂得多。CHM 不想再为“是否正在初始化”“是否正在扩容”“扩容阈值是多少”“协作扩容代数是什么”分别发明一组零散同步状态，所以把这些责任都压到了 `sizeCtl` 这面协调旗上。

在不同阶段，它的含义不同：

- 正数：当前像阈值，告诉表什么时候该扩容
- `-1`：当前有人正在做初始化
- 小于 `-1`：当前有人正在做扩容，而且这个负值里还编码了扩容代数与参与者信息

这也是为什么只死记“`sizeCtl` 有哪些取值区间”并不能真正理解 CHM。更重要的结论是：**CHM 需要一个所有线程都能抢、都能观察、都能据此决定自己下一步动作的全局协调入口。** `sizeCtl` 承担的就是这份工作。

### 初始化为什么也先抢这面旗

这面旗最早在表初始化时就开始工作。`initTable()` 入口在 `ConcurrentHashMap.java:2281` 附近。它的思路不是“谁先来谁都能顺手 new 一个数组”，而是先看 `sizeCtl`，只有抢到初始化资格的线程才分配表，其余线程发现已经有人在做，就不要重复开工。

源码里最关键的动作是：

- `sizeCtl < 0`：说明别人已经在初始化或扩容
- CAS 把 `sizeCtl` 抢成 `-1`：宣告“初始化由我负责”
- 初始化完成后，把 `sizeCtl` 改成新的扩容阈值

初始化完成后的阈值在 JDK 11 中被设成 `n - (n >>> 2)`（`ConcurrentHashMap.java:1526`），也就是 0.75 装载因子对应的扩容门槛。这里先记住一个路标：**同一个字段在初始化前后角色会切换，但它始终承担的是“协调谁先动、下一阶段何时触发”的责任。**

### 为什么扩容还要给 `sizeCtl` 编码“代数”

如果扩容只会有一个线程做一次，那负数状态本来不用设计得这么复杂。但 CHM 的目标恰恰是让多个线程协作扩容，因此它必须解决另一个问题：当前加入协作的线程，到底是在帮哪一轮扩容，还是误闯进了别的阶段？

这就是 `resizeStamp`、`RESIZE_STAMP_BITS` 和 `RESIZE_STAMP_SHIFT` 的意义所在（`ConcurrentHashMap.java:575-586`、`2276-2277`）。它们不是给读者制造位运算障碍，而是为了让 `sizeCtl` 不只是“负数表示扩容中”这么粗糙，而是能进一步标识“这是哪一代扩容、目前有多少协作者在这代扩容里活动”。

这一层只要记住一句话：**`sizeCtl` 之所以复杂，不是因为作者想炫技，而是因为 CHM 想把初始化和扩容都做成并发协调协议，而不是某个线程的私有流程。**

## 二、扩容为什么要做成“写线程顺手帮忙搬家”

### 先回到上一篇埋下的那个 `MOVED`

上一篇的 `putVal` 里，有一个最容易让人出戏的分支：线程明明在写某个 key，却突然撞上 `helpTransfer(tab, f)`。如果只把这件事记成“CHM 扩容会协助”，读者通常仍然不明白：为什么写线程要被拉去干搬桶这种事？

真正的答案是，CHM 不想把扩容变成一个巨大的串行阶段。写线程本来就在推动表增长；当它发现表已经逼近阈值，或者发现眼前这个桶已经处在迁移态时，与其让它站在门口干等，不如让它顺手参与把新表搭起来、把旧桶搬过去。这样，全局成本就被分摊给了那些正在写表、最有可能受扩容影响的线程。

这个判断是在 `addCount()` 里串起来的。`addCount` 入口在 `ConcurrentHashMap.java:2316`。它做的不只是“把计数加一”，还会在总量接近阈值时检查：当前是不是该扩容了？如果该扩容，那么是我发起，还是我加入别人的扩容。

### `addCount` 为什么是扩容入口，而不是 `putVal` 自己包办

直觉上，好像 `putVal` 更像扩容触发点，因为它才是真正插入元素的方法。但 CHM 选择把“写入成功后要不要扩容”的逻辑放进 `addCount`，本质上是把“结构修改”与“规模变化”这两件事拆开。`putVal` 负责把桶结构改对；`addCount` 负责根据最新总量判断当前表是否该升级到下一容量。

在 `addCount` 里，关键判断出现在 `ConcurrentHashMap.java:2335-2347` 附近。只要发现当前总量已经跨过 `sizeCtl` 所代表的阈值，就会进入扩容路径：

- 如果还没人发起，这个线程可以转去启动 `transfer`
- 如果已经有人在搬，这个线程可以加入 `helpTransfer`

这条链特别值得记，因为它体现了 CHM 一直坚持的设计立场：**把高并发下不可避免的全局成本，拆成“参与者顺手帮忙推进”的局部动作。** 它没有安排一个专职后台搬运工线程，也没有要求所有后来写线程在门口空转等待。

## 三、`transferIndex` 解决的不是“从哪开始搬”，而是“谁搬哪一段”

### 协作扩容最怕什么

一旦决定让多个线程一起搬桶，新的难点立刻出现了：如果大家都从 0 号桶扫到末尾，线程之间就会反复撞在同一段区间上，不但没有协作，反而在重复劳动。CHM 要解决的不是简单的“迁移算法”，而是“多线程怎样分工搬迁”。

这也是 `transferIndex` 的职责：

```java
// ConcurrentHashMap.java:805
private transient volatile int transferIndex;
```

它记录的不是“当前搬到哪一个桶”这么直白的含义，而是**还没被认领的迁移区间上界**。当一个线程准备参与迁移时，它不会从头到尾自己扫，而是先通过 CAS 从 `transferIndex` 认领一段工作区间。认领成功后，这一段就归它负责，其他线程继续从剩余区间认领自己的片段。

### 为什么连搬迁步长都要考虑 CPU 数量

`transfer` 入口在 `ConcurrentHashMap.java:2416`。它一开始就会根据 `NCPU` 和当前表长度计算 `stride`（`ConcurrentHashMap.java:2418`、`597`）。这一点很能说明 CHM 的工程味：协作不是越细越好，也不是越粗越好。分片太大，会让单个线程长时间霸占一大段工作；分片太小，又会让大家频繁争抢任务边界，协作成本高过收益。

所以 `stride` 实际上是在回答：**一次认领多大一块区间，既能让线程并行推进，又不会让任务分发本身变成新的热点。**

到这里为止，扩容已经不再像单线程哈希表那样只是“旧桶拆成新桶”。在 CHM 里，它更像一个小型并行调度协议：

```text
需要扩容
  → 有线程发起 transfer
  → nextTable 分配出来
  → transferIndex 指向待认领区间
  → 各写线程认领一段 stride
  → 各自搬桶并回写迁移标记
```

这张图后面还差最后一个关键角色：旧桶搬走后，后来经过这个位置的线程怎么知道该往哪找。

## 四、`ForwardingNode` 不是占位符，而是迁移期间的路标牌

### 为什么搬完旧桶后不能直接留空

如果一个线程已经把旧桶数据迁走了，最简单的做法似乎是把旧桶清空，让大家以后都看新表。问题在于，其他线程此刻可能还握着旧表引用，或者刚刚通过旧表下标算到了这个桶位。如果这里只留下 `null`，后来者无法区分“这个桶本来就是空的”和“这个桶的数据已经搬去新表了”。

所以 CHM 在每个旧桶迁移完成后，不是简单写空，而是写入一个专门的转发表节点：

```java
// ConcurrentHashMap.java:2223-2227
static final class ForwardingNode<K,V> extends Node<K,V> {
    final Node<K,V>[] nextTable;
    ForwardingNode(Node<K,V>[] tab) {
        this.nextTable = tab;
```

`ForwardingNode` 最关键的意义，是把“旧表上的这个桶已经退休”这件事编码成一个可被读写线程共同识别的状态信号。它携带 `nextTable`，所以后来者不必猜，只要顺着这个路标继续走，就能在新表上接着查找或协助迁移。

### 迁移期读线程为什么不用停下来等

这也把上一篇的一个问题彻底闭环了：为什么 `get()` 遇到负 hash 特殊节点时，可以不加锁继续走下去？因为 `ForwardingNode` 提供的不是一个模糊信号，而是一个带着明确去向的新表入口。

在 `ForwardingNode.find` 中（`ConcurrentHashMap.java:2232-2244` 一带），查找逻辑会沿着 `nextTable` 继续执行，必要时还能继续穿过多层转发表节点。于是扩容中的读线程并不需要停在门口等“世界稳定下来”，而是能直接被导向新表。

这件事的工程价值很大。扩容如果要求“先冻结所有读者，等搬完再恢复”，吞吐量会被严重拖垮。CHM 选择的路线是另一种：**允许新旧表短暂共存，但用 `ForwardingNode` 保证后来线程总能找到下一跳。**

### 旧桶什么时候真正退场

在 `transfer` 收尾时，最后阶段会把 `nextTable` 提升为新的 `table`，再把 `sizeCtl` 设成新容量下的下一轮阈值（`ConcurrentHashMap.java:2458-2460`）。这意味着旧表不会永远存在；它只是扩容协议中的过渡舞台。

这里有一个很重要的理解顺序：不要把“旧桶放 `ForwardingNode`”想成最终结构，而要把它看成迁移中的交通标识。它存在的价值，恰恰是为了让系统在不停机的情况下完成从旧表到新表的切换。

## 五、为什么计数不能只靠一个全局 `size`

### 扩容协作解决了“搬家热点”，计数还剩“写热点”

即使扩容已经做成协作协议，CHM 仍然会被另一种全局热点拖慢：所有线程都要去更新同一个计数器。你可以把这理解成一种结构上的反讽——数据已经被分散到不同桶里并发写了，结果元素总数的统计又把所有线程重新集中到一个内存位置互撞。

JDK 11 的 CHM 不愿意承受这种单点争用，所以计数也走了“两级路径”。相关字段分别是：

- `baseCount`（`ConcurrentHashMap.java:790`）
- `counterCells`（`ConcurrentHashMap.java:815`）
- `CounterCell`（`ConcurrentHashMap.java:2555`）

这三者的关系可以先压成一句话：**低竞争时，尽量走一个便宜的全局基数；高竞争时，把线程打散到多个分片格子里。**

### 为什么 `baseCount` 没有被彻底废弃

看到 `CounterCell` 后，很多读者会下意识以为：“那以后就都写分片格子了，`baseCount` 只是历史包袱。” 实际不是这样。CHM 的思路恰恰是先走最便宜的路径，如果竞争真的开始明显，再升级到分片。

这就是 `addCount` 前半段在做的事（`ConcurrentHashMap.java:2316-2332`）：

- 先尝试 CAS 更新 `baseCount`
- 如果 CAS 失败，或者已经检测到竞争明显，再转入 `fullAddCount`
- `fullAddCount` 会把线程散到不同 `CounterCell`

也就是说，CHM 不想一开始就为每次写入都背上分片数组和额外寻址的成本。它先假设当前竞争可能不高，如果事实证明单点已经开始成为热点，再逐步扩成分片计数结构。这跟前面扩容的思路高度一致：**先走成本最低的路径，只有在冲突真的出现时才升级机制。**

### `CounterCell` 解决的不是正确性，而是争用位置太集中

`CounterCell` 的存在理由，不是“没有它就算不准”，而是“没有它，太多人会在同一个 CAS 点上打架”。每个线程被散列到某个 cell 后，就不再都去撞 `baseCount`，而是在不同分片上局部累加。最后真正要读总量时，再把这些分片加总起来。

所以这里的设计取舍非常清楚：

```text
单个全局计数器
  → 更新路径简单
  → 高并发下 CAS 热点严重

baseCount + CounterCell[]
  → 低竞争时仍然便宜
  → 高竞争时把写热点拆散
  → 读取总量时需要汇总
```

这也是为什么你会觉得它和 `LongAdder` 很像：它们解决的是同一类问题——不是“怎么加一”，而是“很多线程同时加一时，怎样避免都撞同一个位置”。

## 六、`size()` 为什么是弱一致：因为汇总时不会冻结世界

### 先承认它没有试图做一件事

很多人第一次听说 CHM 的 `size()` 只是近似值，会本能觉得这像个缺点。但如果你把前面整篇逻辑连起来，这反而是顺理成章的结果。CHM 前面在扩容上不愿意 stop-the-world，在计数上不愿意集中争用；如果此刻又要求 `size()` 每次都返回一个冻结全局写线程之后算出来的精确值，那前面的吞吐量努力就会被重新抵消掉。

JDK 11 里，`size()` 在 `ConcurrentHashMap.java:909-910` 通过 `sumCount()` 完成，`mappingCount()` 在 `ConcurrentHashMap.java:2167` 也是同一条主线。`sumCount()` 本身只是把当前可见的 `baseCount` 和各个 `CounterCell` 里的值做一次求和（`ConcurrentHashMap.java:2560-2564`）。

关键点在于：汇总过程中，并没有要求所有写线程先停下。也就是说，当你在读分片 A 时，别的线程可能刚好在更新分片 B；当你刚加完 `baseCount` 时，别的线程又可能已经把新的增量打进某个 cell 里。于是这个结果天然更像“当下近似快照”，而不是事务提交点上的精确总数。

### 为什么这不是 bug，而是设计代价

如果把 `size()` 的语义理解成“线性一致精确值”，那 CHM 的这套计数实现当然显得不够强。但 CHM 追求的不是这个目标。它追求的是在大量并发更新时，更新路径尽量轻、尽量少冲突，而读取总量则接受弱一致代价。

所以更准确的表述应该是：**CHM 选择把精确一致性交给吞吐量让路。** 更新时，线程们不用都去抢同一个热点；读总量时，调用者得到的是一个通常足够有用、但不该被当作严格事务边界的结果。

这也是为什么业务上“先看 `size()`，再据此做强控制逻辑”常常是不稳妥的。`size()` 更适合监控、估算、统计场景，而不是精确约束并发流程的唯一依据。

## 五个最容易混掉的边界：sizeCtl 不是单阈值，协作扩容不是后台线程，ForwardingNode 不是空桶标记，CounterCell 不是精度补丁，size() 也不是事务快照

第一，`sizeCtl` 不是单阈值。它在不同阶段承担的是不同协议角色：初始化资格、扩容协作状态、下一轮阈值都可能编码在这里；如果只把它看成“装载因子阈值变量”，就看不懂为什么初始化和扩容都先去抢它。

第二，协作扩容不是后台线程专职搬家。CHM 没有把迁移外包给一个永远独立的搬运者，而是让正在写表、最可能受到扩容影响的线程顺手发起或加入 `transfer`；扩容成本因此被摊给并发参与者，而不是集中制造一次长停顿。

第三，`ForwardingNode` 不是空桶标记。它不是在说“这里没东西”，而是在说“这里的东西已经搬去 `nextTable`，请顺着我继续找”；如果把它和普通 `null` 桶混为一谈，迁移期读写路径就会被误解成结构空洞。

第四，`CounterCell` 不是精度补丁。没有它，CHM 依然可以算对数量；它真正解决的是高并发下所有线程都去撞同一个计数热点的问题。分片计数改善的是更新吞吐，不是事后修补正确性。

第五，`size()` 也不是事务快照。`sumCount()` 汇总时不会冻结所有写线程，所以结果天然是某个并发时刻的近似可见值；它适合监控、估算和统计，不适合充当强控制逻辑里的精确边界条件。

把这五条边界记稳，ConcurrentHashMap 的扩容与计数就不会再被看成两坨独立技巧。它真正想讲的是同一套设计取向：凡是会把并发成本集中到一个线程或一个内存点上的地方，都尽量改造成“协调状态 + 分片参与 + 最后汇总”的协议。

## 收网：扩容靠协作搬家，计数靠分片累加

回到开头两个朴素方案，现在已经能看清它们为什么都不适合并发哈希表了。

第一种失败方案是独占扩容：让一个线程把所有桶搬完，其他线程等着。这会把高并发写场景压成大停顿。CHM 的解法是：用 `sizeCtl` 协调阶段，用 `transferIndex` 分片任务，用 `ForwardingNode` 给后来线程指路，让写线程在需要时顺手加入迁移。

第二种失败方案是单点计数：让所有线程都去改一个全局 `size`。这会把数据层面的分散写入重新压缩成一个计数热点。CHM 的解法是：低竞争时先 CAS `baseCount`，高竞争时分流到 `CounterCell`，最后需要总量时再汇总。

把这两条主线合在一起，本文真正要留下的图是：

```text
表太满了
  → sizeCtl 协调当前阶段
  → 写线程可发起或加入扩容
  → transferIndex 分片搬桶
  → ForwardingNode 把后来线程导向 nextTable
  → 最终 nextTable 接管为新 table

写线程太多了
  → 先尝试 baseCount
  → 冲突重了再分流到 CounterCell
  → size() / mappingCount() 最后汇总
```

这也把上一篇的 `MOVED` 完整闭环了：它不是一个神秘常量，而是“这个桶已经进入迁移协议”的明确信号。看到它的线程，不是只能等待，而是可以被拉进扩容协作链里。
