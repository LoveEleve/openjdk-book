# CopyOnWrite 与无锁队列：为什么一个愿意复制整组数组，另一个坚持局部 CAS

> 本文基于 JDK 11 `CopyOnWriteArrayList`、`CopyOnWriteArraySet` 与 `ConcurrentLinkedQueue`。讨论范围聚焦 COW 的 `array`/`getArray`/`setArray`/`add`/迭代器快照，以及 CLQ 的 `Node`、`offer`、`poll`、`peek`、`updateHead` 和弱一致遍历。阻塞队列、背压和线程挂起语义不在本文展开。
> **前置依赖**：[ConcurrentSkipListMap 跳表](03-skiplist.md)、[CAS 与原子更新基础](../13-atomic/01-atomicinteger-cas.md)
> **后续**：[阻塞队列家族](05-blocking-queues.md)

## 先看两个都想“别挡住读者”，但代价完全不同的场景

并发容器里最容易让人混淆的一件事，是把“读友好”想成同一种优化方向。好像只要目标都是“别让读者被写者拖慢”，大家就应该走同一套实现路线。`CopyOnWriteArrayList` 和 `ConcurrentLinkedQueue` 恰好说明，现实并不是这样。它们都在努力减少读侧或消费侧被阻塞的机会，但对“读到什么”和“写方该付什么代价”的回答几乎正好相反。

第一类场景是监听器列表、白名单、插件链、只偶尔更新的路由快照。这里读者最在意的不是“永远最新”，而是“我开始遍历这一份名单后，中途别突然有人把底层结构改花”。换句话说，它宁可接受自己读到的是稍旧快照，也希望这份快照在整个读取过程中稳定不动。

第二类场景是持续生产消费：日志事件不断入队，网络任务不断出队，消息不断被多个线程接力处理。这里最无法接受的反而是全表复制和长时间锁持有。消费者不需要一份静态快照，它更需要队列能一直往前推进，让生产者和消费者尽量少互相拖住。

这就是本文真正的总问题：**同样追求“读侧尽量轻”，为什么一个容器愿意在每次写时复制整组数组，另一个容器却宁愿在链表节点上反复做局部 CAS？**

## 一、CopyOnWriteArrayList 为什么愿意为稳定快照付出整组复制代价

### 先把它服务的读者想清楚

如果一个容器的主要使用方式是“拿到当前名单，然后完整遍历一遍”，那读者最怕的不是旧，而是不稳。比如事件通知系统在广播监听器时，如果遍历到一半底层数组被原地插入、删除、平移，调用方就得额外面对游标错位、并发修改异常、甚至一轮通知里有人收到两次、有人一次都收不到的风险。

`CopyOnWriteArrayList` 针对的正是这种读者心理：**我可以接受读到旧版本，但不能接受正在读的那一版被原地改动。**

这也是为什么它把核心状态压成了一个 `volatile` 数组引用：

```java
// CopyOnWriteArrayList.java:105
private transient volatile Object[] array;
```

读路径拿数据时，不是跟写线程共享一份可变数组结构，而是先取到某个已经发布好的数组引用。`getArray()` 和 `setArray()`（`CopyOnWriteArrayList.java:111`、`118`）把这个“读当前数组”和“发布新数组”的入口明确收口了。

### 为什么 `get()` 可以无锁前进

`get(int index)` 在 `CopyOnWriteArrayList.java:397`。它没有先去抢写锁，也不需要像 fail-fast 容器那样额外检查结构版本。原因很简单：它面对的是某个已经发布出去的数组快照。只要写线程不去原地改这个旧数组，读线程按下标取值时就不会看到“写了一半的数组”。

也就是说，COW 读无锁不是靠运气，也不是靠“写线程通常很少所以问题不大”，而是靠一个更直接的前提：**读者所依赖的那份数组，在它手里期间根本不会被原地改动。**

这就把 COW 的核心承诺说清了：你读到的也许不是最新数组，但一定是一份完整数组。

### 为什么 `add()` 必须复制整个数组

这一承诺的代价，全部压到了写线程身上。`add(E e)` 在 `CopyOnWriteArrayList.java:428`。它的主线不是“拿到锁后原地 append”，而是：

1. 读取当前数组
2. 复制出一个长度更大的新数组
3. 在新数组尾部写入新元素
4. 通过 `setArray` 一次性发布新数组

这个顺序很关键。只要旧数组一旦被任何写线程原地改动，前面“读线程可以站在一份稳定数组上无锁前进”的承诺就破了。所以 COW 根本不能选“修改旧数组再补同步”的路线；它必须让旧数组彻底只读，把变化都放进新副本里，最后再整体切换引用。

这里给一个路标：这不是“为了线程安全多拷贝一下”的小优化，而是整个容器语义的根。**CopyOnWrite 不是附加技巧，它就是这类容器之所以能提供稳定快照读的原因。**

## 二、为什么 COW 不适合写多：复制成本不是副作用，而是写方主账单

### 先别把它误会成“线程安全万能列表”

很多人第一次接触 COW，会先被“读无锁、迭代稳定、不抛并发修改异常”这几个优点吸引，然后下意识把它想成一种高级列表，仿佛只要并发就该优先考虑它。这个理解最大的问题，是把它的代价当成了小缺点，而不是主成本。

前面已经看到，COW 每次真正的结构写入都要复制整组数组。这意味着它的写成本天然是 `O(n)`：元素越多，复制越贵；写越频繁，复制和垃圾回收越密集。对于几十个监听器、几百个白名单条目，这个代价往往还能接受；但如果把它拿去承载高频日志流、任务队列、消息堆积列表，它就会立刻变成一种自找麻烦的选择。

也就是说，COW 并不是“线程安全列表，再附带一点写开销”，而是“**明确偏向读者，让写者为稳定快照付费**”的容器。

### 为什么 `CopyOnWriteArraySet` 只是同一路线的包装

`CopyOnWriteArraySet` 正好能帮读者把这件事看得更清楚。它不是另一套并发结构，只是用列表做底层，再加一层 Set 语义包装：

- 类定义在 `CopyOnWriteArraySet.java:104`
- 底层字段是 `CopyOnWriteArrayList<E> al`（`CopyOnWriteArraySet.java:108`）
- 默认构造直接 new 这个列表（`CopyOnWriteArraySet.java:113`）

这说明 COW 其实是一整条家族路线：**如果你的主要诉求是“读者看到稳定快照，写者不多，且集合规模不大”，那列表和集合都可以用同一种写时复制哲学来实现。**

这里也顺便把选型边界说清：一旦写频率上来，或者集合规模上来，COW 的复制成本就不再是可以忽略的代价，而会直接反噬吞吐量和内存分配压力。

## 三、ConcurrentLinkedQueue 为什么不能复制整组数据，也不愿意上大锁

### 持续生产消费场景根本不允许 COW 式写法

队列和监听器名单最大的不一样，在于它不是“偶尔改一次，平时反复读同一份内容”，而是元素持续进来、又持续被拿走。生产者不断写，消费者不断删，整个结构始终处在前进过程中。此时如果还想用“复制整组内容，再一次性发布”的策略，代价会非常荒唐：每入队一个元素都复制整条队列，每出队一个元素也复制整条队列，几乎等于主动把吞吐量打穿。

那给队列套一把锁呢？当然能工作，但生产者和消费者会被串成一条线：有人入队时，别人不能出队；有人出队时，别人不能入队；并发优势被大幅抵消。

`ConcurrentLinkedQueue` 选择的是第三条路：**把队列实现成链式节点结构，让生产者和消费者主要在局部节点关系上做 CAS 推进，而不是在整个容器层面做复制或大锁串行化。**

### 节点结构说明了它到底在保护什么

CLQ 的核心节点在 `ConcurrentLinkedQueue.java:184-186`：

```java
// ConcurrentLinkedQueue.java:184-186
static final class Node<E> {
    volatile E item;
    volatile Node<E> next;
```

这两个字段已经把主线暴露出来了。`item` 表示当前节点里是否还承载真实元素；`next` 决定队列链路怎样继续往后推进。并发入队出队真正要保护的，不是一个抽象“队列对象”，而是这些局部节点关系：谁连向谁，哪个节点的 item 还有效，哪个空节点已经可以被后续线程跳过。

这就是为什么 CLQ 的正确性不依赖“整队冻结”，而依赖“局部状态可被并发线程识别并推进”。

## 四、为什么 `offer()` 的真正线性化点是 `next` 的 CAS，而不是 `tail` 立刻变准

### 先排除“尾指针必须永远最准确”的直觉

很多人第一次看无锁队列，最容易卡住的地方是：如果 `tail` 不是每次都立即指向最新尾节点，队列怎么还能正确？这个疑问非常自然，因为在普通串行链表里，我们往往把“尾指针准确”当成结构完整的一部分。

CLQ 恰好把这件事拆开了。`offer(E e)` 在 `ConcurrentLinkedQueue.java:354`。真正决定新元素是否已经入队成功的，不是 `tail` 字段有没有立刻追上来，而是某个前驱节点的 `next` 有没有成功 CAS 到新节点。只要这一跳成功，新元素就已经成为队列链的一部分，后来线程总能沿着链路找到它。

换句话说，**决定正确性的是链表真实结构有没有往前长，而不是辅助指针有没有第一时间追平。**

### `tail` 为什么更像加速器，而不是唯一真相

这也解释了为什么 CLQ 可以容忍 `tail` 暂时落后。它主要是为了帮助后来线程更快接近队尾，减少从较旧节点反复向后追链的成本。即使 `tail` 一时没跟上，只要真实的 `next` 链已经接好了，队列本身就没有坏。后来某个线程再顺手把 `tail` 推近，只是补性能，不是在补正确性。

这一点和很多并发容器的设计哲学是相通的：先保证真正的数据结构已经向前推进，再用惰性更新去修正那些“能帮助后续更快找到位置”的辅助指针。对 CLQ 来说，真正的入队线性化点是 `next` 的 CAS，不是 `tail` 的立刻准确。

这一层一定要记住，否则很容易把 `tail` 的惰性推进误判成实现瑕疵。它其实是无锁队列典型折中：**允许辅助指针短暂滞后，以换取更少的争用和更简单的局部推进协议。**

## 五、为什么 `poll()` 和 `peek()` 也能无锁推进：先让节点“空掉”，再逐步收头

### 出队不等于马上把整段链表物理拆掉

如果只从单线程队列出发，出队最直觉的动作是：头节点指向下一个节点，被取走的那个节点就彻底从结构里消失。但并发无锁队列里，别的线程可能正好还抓着当前头节点，或者正沿着它往后走。于是 CLQ 并不会要求每次出队都把链路瞬间整理成最干净的样子。

`poll()` 在 `ConcurrentLinkedQueue.java:383`。它的关键动作之一，是先通过 `casItem`（定义在 `ConcurrentLinkedQueue.java:205`）把当前节点里的 `item` 置空。这样一来，其他线程即使仍然经过这个节点，也能识别出：这个节点的元素已经被消费掉了，不应再把它当成有效队列元素。

接着，`updateHead`（`ConcurrentLinkedQueue.java:290`）会把头指针逐步往前推进，让这些已经空掉的旧头节点慢慢退场。

### 这说明 CLQ 也在使用“可识别中间态”

这条线特别像上一篇跳表里的 marker 删除协议。它们都没有要求所有结构变化必须一步完成，也没有要求别的线程在中间态出现时原地停住。相反，它们做的是：**允许中间态存在，但中间态必须让后来线程看得懂，并且还能继续帮助结构向前收缩。**

对 CLQ 来说，这个中间态就是“节点还在链上，但 `item` 已经为空”。这样的节点不是 bug，也不是脏数据，而是消费协议中的过渡状态。后来线程遇到它，可以跳过，可以顺手推进头指针，而不是被迫加锁清场。

同样地，`peek()`（`ConcurrentLinkedQueue.java:404`）也会在查找可见头元素时顺带配合 `updateHead` 做头部清理。这说明 CLQ 的消费语义不是“一个线程单独负责完整收尾”，而是“多个线程在前进过程中共同把旧节点往后淘汰”。

## 六、为什么一个遍历像快照，一个遍历像实时弱一致视图

### COW 迭代器为什么天然是快照

`CopyOnWriteArrayList.iterator()` 在 `CopyOnWriteArrayList.java:1023`。它最核心的语义不是“给你一个能并发工作的游标”，而是“把你绑定到创建迭代器那一刻拿到的数组快照上”。既然后续写线程不会原地改这份旧数组，那这个迭代器自然就能稳定地遍历到底。

这意味着两件事同时成立：

- 它不会被后来写操作打断成半截
- 它也不会自动看到后来刚刚加入的新元素

这不是局限，而是快照读的本义：稳定优先于最新。

### CLQ 遍历为什么只能是弱一致

CLQ 则完全不同。它的遍历面对的是一条持续变化的链：有人正在 offer 新节点，有人正在 poll 旧节点，有些节点 item 已空、但链还没完全收缩。这个前提下，若还要求遍历必须返回“某个冻结瞬间的完整快照”，代价就会迅速逼近全局锁或全量复制。

CLQ 并没有选择那条路。它给出的是弱一致视图：你可能看到一部分新元素，可能看不到刚刚删除的元素，但遍历不会像普通 fail-fast 容器那样因为结构变化就直接报废。

所以这里形成了一个特别清晰的对照：

```text
CopyOnWriteArrayList
  → 遍历绑定在创建时数组快照上
  → 读得稳定，但可能过时

ConcurrentLinkedQueue
  → 遍历跟着运行中的链表前进
  → 读到的是动态弱一致视图
```

这一节真正要记住的，不是“一个快照、一个弱一致”这两个术语，而是它们背后的代价来源：**一个靠整组复制隔离写影响，一个靠无锁局部推进接受遍历结果与并发修改交错。**

## 七、什么时候该选 COW，什么时候该选 CLQ

### 两者都不是“更高级的线程安全容器”

读到这里，最重要的不是再背几个 API，而是把选型边界真正收住。

如果你的场景是：

- 读远多于写
- 集合规模不大
- 读者更看重稳定快照而不是绝对最新
- 写者可以接受 `O(n)` 复制成本

那 COW 路线才成立。监听器列表、白名单、配置快照，都是这条路的典型用户。

如果你的场景是：

- 元素持续入队/出队
- 生产者和消费者都在高频并发推进
- 无法接受整组复制
- 更在意持续吞吐，而不是遍历时的静态快照

那 CLQ 这种无锁链队列才更匹配。

反过来，把它们用反了，问题也很典型：在高频写队列场景用 COW，会把系统拖进复制和 GC 压力；在需要稳定遍历名单的场景用 CLQ，会得到一个随时可能被并发修改穿插的动态视图。

## 五个最容易混掉的边界：快照不是最新，复制不是小代价，tail 不是唯一真相，空节点不是脏数据，弱一致遍历也不是随便读

第一，快照不是最新。`CopyOnWriteArrayList` 迭代器绑定的是创建那一刻的数组版本，它保证的是遍历期间结构稳定，不保证自动看见后来加入的新元素；把“稳定快照”误解成“实时视图”，就会错判它的语义。

第二，复制不是小代价。COW 的整组数组复制不是附带开销，而是它给读者提供无锁稳定视图的主账单；一旦写频率高、数组大，这个代价会直接体现在吞吐、分配和 GC 压力上。

第三，`tail` 不是唯一真相。对 `ConcurrentLinkedQueue` 来说，真正决定入队成功的是前驱节点 `next` 的 CAS，`tail` 只是帮助后来线程更快逼近队尾的辅助指针；它短暂落后并不等于队列结构损坏。

第四，空节点不是脏数据。CLQ 中 `item == null` 的节点常常是消费协议中的中间态，表示元素已经被取走，但链路收缩还在继续；后来线程应识别并帮助推进，而不是把它当成异常残留。

第五，弱一致遍历也不是随便读。CLQ 不承诺遍历得到冻结快照，但它仍然努力保证结构可继续前进、元素不会因并发修改把遍历直接打废；弱一致说的是与并发更新交错，不是说结果毫无规则。

把这五条边界记稳，CopyOnWrite 和 ConcurrentLinkedQueue 就不会再被误解成“两个都很适合读”的同类容器。它们真正想讲的是两种完全不同的偏袒：一个让写者为稳定快照买单，一个让生产者和消费者通过局部 CAS 持续把结构往前推。

## 收网：一个用复制隔离写影响，一个用局部 CAS 让结构持续前进

回到开头那个问题：为什么一个愿意复制整组数组，另一个坚持局部 CAS？现在已经可以给出一个完整答案。

第一，`CopyOnWriteArrayList` 服务的是“稳定快照读”场景。它用 `volatile` 数组引用承载当前版本，用写时复制保证旧数组永远不被原地改动，所以读者和迭代器可以站在某个完整版本上无锁前进。代价则全部压到写者：每次结构修改都要复制整组数组。

第二，`ConcurrentLinkedQueue` 服务的是“持续生产消费”场景。它不能接受全量复制，也不愿用大锁把生产者和消费者串行化，于是把正确性落在局部节点关系上：`next` 的 CAS 决定真实链路是否前进，`item` 置空表示元素已被消费，`updateHead` 和辅助指针惰性推进负责把结构慢慢收紧。

第三，这两种设计在遍历语义上自然分叉：COW 给你创建时快照，稳定但可能旧；CLQ 给你运行中弱一致视图，可持续前进但不承诺静态画面。

把这三点压成一张总图，就是：

```text
读多写少、要稳定名单
  → CopyOnWrite
  → 复制新数组
  → 一次性发布
  → 读者站在旧快照上继续读

持续生产消费、要持续吞吐
  → ConcurrentLinkedQueue
  → 节点局部 CAS 链接
  → item 置空 + 头尾惰性推进
  → 读者/消费者跟着运行中结构前进
```

所以，它们看起来都在做“读友好”，其实偏袒的对象完全不同：COW 偏袒的是“拿到一份稳定名单的读者”，CLQ 偏袒的是“希望结构一直往前流动的生产者和消费者”。

下一篇继续把“并发”再往前推一步：当生产者和消费者不只是想并发前进，还需要在队列空了或满了时阻塞等待，为什么就要进入 `BlockingQueue` 家族？单锁双条件、双锁双条件、零容量直接交接又分别是在解决什么问题？
