# StampedLock 与读写锁：为什么读多写少时，两个读者不该互相等

> 本文基于 JDK 11 `ReentrantReadWriteLock` 与 `StampedLock`。讨论重点是读写分离语义、高低 16 位计数、读锁/写锁互斥规则、StampedLock 的写/读/乐观读三模式、版本戳校验与锁转换；不展开内部完整等待队列细节。
> **前置依赖**：[AQS 核心](01-aqs-core.md)、[共享模式与并发工具族](04-shared-tools.md)
> **后续**：域 16 Stream 与函数式、域 14 线程池与任务执行

## 先看一个最常见、也最容易被“互斥锁直觉”拖慢的场景

假设你维护的是一张配置表、路由表或缓存索引。绝大多数请求只是来读，真正更新数据的写操作很少发生。此时如果还沿用普通互斥锁的思路，两个读者也得排队：前一个线程只是读一眼，后一个线程同样只是读一眼，却依旧要在门口等它把锁放掉。

这个等待从正确性上当然没错，但它把“本来完全可以并行的两个读”也压成了串行。读多写少场景里，这种保守往往才是真正的瓶颈来源。

于是问题自然分成了两层。第一层是：既然读操作彼此不修改状态，为什么不能让多个读者同时通过，只把写者单独挡住？这催生了读写锁。第二层则更激进：如果写非常非常少，读者是不是连共享读锁的获取成本都不一定值得付，能不能先不加锁把数据读出来，再事后验证这段时间里有没有写者动过它？这就走向了 `StampedLock` 的乐观读。

所以这篇的主线不是“再介绍两个锁类”，而是：**读路径优化本身也有分层——先从所有人互斥进化到读者并行，再进一步在写极少场景里尝试先读后验。**

## 一、ReentrantReadWriteLock 为什么要把一个 state 拆成高低 16 位：它要同时记读者和写者

### 先排除“读写锁就是两把彼此独立的锁”这个误解

很多人听到 `readLock()` 和 `writeLock()`，会下意识把它理解成：哦，那就是一个对象里包了两把完全独立的锁。这个直觉有一点表面帮助，但容易把真正关键的地方看丢。因为读锁和写锁的关系不是并列无关，而是**同一份共享状态的两种不同解释**。

JDK 11 的 `ReentrantReadWriteLock` 定义在 `ReentrantReadWriteLock.java:216`，内部同步核心是 `Sync`（`ReentrantReadWriteLock.java:253`）。最重要的设计，就藏在高低 16 位拆分里：

- `sharedCount(c)`（`ReentrantReadWriteLock.java:269`）取高 16 位
- `exclusiveCount(c)`（`ReentrantReadWriteLock.java:271`）取低 16 位

这意味着同一个 `int state`，被一刀切成了两块语义：

- 高 16 位：当前有多少读者
- 低 16 位：当前写者重入了多少层

这就是为什么它不是“两把独立锁”，而是“**一台同时记读者数量和写者占用层数的同一状态机**”。读锁和写锁只是同一 state 的两种入口视图。

### 为什么这种编码方式刚好适合读写分离

读多写少场景真正想表达的是三条规则：

- 读-读可以并行
- 读-写必须互斥
- 写-写必须互斥

如果你还把 state 想成单一二值占用位，那这三条规则根本无从编码。高低位拆分后，事情就清楚了：高位只要大于 0，说明已经有读者；低位只要大于 0，说明已经有写者。于是获取规则自然变成了状态判定：

- 读获取时，只要没有写者占着低位，读计数就能继续增
- 写获取时，必须同时看到高位没有读者、低位没有别的写者，才能独占成功

这一层最重要的不是背位运算，而是看懂：**读写锁之所以可能让两个读者并行，是因为它愿意在状态里同时记录“有多少读者”和“有没有写者”。**

## 二、为什么读锁可并行、写锁却必须独占：读者优化不是放弃互斥，而是把互斥留给真正冲突的地方

### 先看读锁为什么能共享通过

在 `ReentrantReadWriteLock` 里，读锁走共享获取路径。`tryAcquireShared` 位于 `ReentrantReadWriteLock.java:453-494`，`fullTryAcquireShared` 位于 `501`。它们真正做的事，并不是“让读者无条件冲进去”，而是先问：当前是不是有写者在持有低位计数；如果没有，读者数量可以继续在高位累加。

这说明“读读并行”并不等于“读锁不算锁”，而是说：**在没有写者破坏一致性的前提下，读者之间不必再互相阻挡。** 锁依然存在，只是它不再把所有访问粗暴压成单线程通过。

### 写锁为什么反而更严格

写锁走独占获取路径，`tryAcquire` 位于 `ReentrantReadWriteLock.java:382`。它之所以严格，是因为写操作要修改共享状态，一旦与其他读者或写者并发穿插，就可能让读者看到中间态，或者让多个写者互相覆盖。

所以写获取必须看到两件事同时成立：

- 当前没有别的写者占用
- 当前也没有读者还在看旧状态

这就是读写锁的真正平衡点：**它不是全面放松互斥，而是只把读者之间那部分本来没冲突的互斥拆掉。**

## 三、为什么写锁能降级成读锁，读锁却不该直接升级成写锁

### 先看“写完后我还想继续安全读取”这个真实需求

一个非常常见的场景是：线程先拿写锁修改共享结构，改完后还想基于最新状态继续读一段时间，但它又不希望自己刚释放写锁，别的写线程立刻插进来把这份状态再改掉。此时最自然的路径就是：先在仍然持有写锁时获取读锁，再释放写锁，让自己从独占写者平滑降成共享读者。

这就是所谓锁降级。它的目的不是炫技巧，而是缩短独占窗口，同时保持“我接下来读到的还是自己刚写完那一版”。

### 为什么反过来从读锁升级成写锁很危险

很多人会自然反问：那既然能降级，为什么不能直接从读锁升成写锁？问题在于读锁本来就是允许多个读者并存的。你如果在持有读锁时想升级成写锁，就会遇到经典死局：自己不肯先放掉读锁，其他读者也不肯先走，而写锁又要求“所有读者都清空”才能成功。

于是“读着读着想直接变成写者”这件事，在多读者并发场景下天然危险。也正因为如此，读锁升级通常不能像写锁降级那样被当成安全常规路径。

这一层真正要记住的是：**降级是在独占者主动让出一部分权力，升级却往往是在多个共享者中强行争取独占，这两件事的风险根本不对称。**

## 四、StampedLock 为什么进一步怀疑“连共享读锁都不一定值得上”

### RRWL 已经让读者并行了，为什么还不够

到这里，很多人会觉得：两个读者已经不用再互相等了，问题应该解决得差不多了。可在写极少、读极多的场景里，JDK 还想再往前推一步。原因是：即使读锁之间能并行，它们每次仍然要走加锁、计数、解锁这套同步路径。对于极高频、极轻量的读操作来说，这笔成本本身也可能变得显眼。

于是 `StampedLock` 提出更激进的问题：**如果当前根本没有写者在动数据，那读者是不是连共享读锁都不一定要上？能不能先无锁读取，再事后验证期间是否发生过写？**

这就是乐观读的出发点。它不是否认并发风险，而是试图把同步成本后移：先便宜地读，只有怀疑读期间混入了写者时，再退回到更重的安全路径重读。

### StampedLock 为什么根本没用 AQS

`StampedLock` 定义在 `StampedLock.java:229`，它没有复用 AQS，而是自己维护状态位和等待结构。本文不打穿内部排队细节，但一定要先立住一点：它不是 ReentrantReadWriteLock 再加一个乐观读方法那么简单，而是从状态设计上就把“版本戳”纳入了主语义。

关键状态位常量在 `StampedLock.java:368-376`，其中：

- `LG_READERS = 7`
- `WBIT`（`StampedLock.java:372`）：写锁位
- `RBITS` / `SBITS`（`StampedLock.java:373-376`）：读计数与版本相关位掩码

你不需要死记每一位，但必须知道：**它的状态里不只在记录有没有读者/写者，还在记录一个可以被乐观读拿来做事后校验的版本视图。**

## 五、乐观读为什么敢先不加锁：因为它读完后还要回来证明“期间没人写过”

### 先看最危险的失败方案：读完直接信，不做任何验证

如果把乐观读误解成“反正先不加锁，读完就用”，那它当然是不安全的。因为写者可能正好在你读取多个字段的中间插进来，导致你拿到一份前半段旧值、后半段新值的混合视图。

所以 `StampedLock` 的乐观读从来都不是“无锁且无证据”，而是“**先无锁读取，再验证期间有没有写者动过版本**”。没有后面的 `validate()`，前面的“乐观”就会变成单纯的赌命。

### `tryOptimisticRead()` 和 `validate()` 是怎么配合的

乐观读入口在 `StampedLock.java:629-631`：

```java
// StampedLock.java:629-631
public long tryOptimisticRead() {
    return (((s = state) & WBIT) == 0L) ? (s & SBITS) : 0L;
}
```

这说明乐观读真正拿到的不是“锁”，而是一份当时版本戳快照。只要当下没有写者持有写锁位，就返回当前版本相关位；如果此刻已经有写者在写，连乐观读资格都不给，直接返回 0。

读完数据后，再用 `validate()`（`StampedLock.java:646-648`）去比较：你手里的 stamp 对应版本，是否仍和当前状态版本一致。若一致，说明这段读取期间没有写者改变版本；若不一致，说明你刚才那次无锁读取不可信，必须退回到 `readLock()` 或更强路径重读。

这一层的关键结论是：**乐观读快，不是因为它省掉了正确性，而是因为它把正确性证明放到了读取之后。**

### 为什么这特别适合“写很少”的场景

乐观读的收益，完全建立在这样一个假设上：大多数时候，读期间真的没有写发生。只有在这种前提下，你才经常能“零锁开销读完 + validate 一次通过”。如果写很频繁，乐观读就会反复失败、反复回退重读，最后得不偿失。

所以它不是“更高级的读锁”，而是**在写极少假设成立时，用重试概率换掉读锁固定成本**。这条边界一定要讲清，否则读者很容易把乐观读误用到写热点场景里。

## 六、转换方法为什么重要：它们在帮你缩短独占窗口，而不是替你消灭竞争

### 先看一个很真实的尴尬场景

很多业务操作并不是一上来就知道自己要写。常见路径往往是：先读一眼判断条件，大多数时候条件不成立，只读即可；少数时候发现必须修改，再转去写。这时候如果总是一开始就上写锁，独占窗口会被白白拉长；如果先读后彻底解锁再重新写，又会在读写之间暴露窗口，让别的线程插进来改变状态。

这就是 `StampedLock` 转换方法存在的意义：在合适条件下，尽量把当前模式平滑换到目标模式，减少不必要的彻底放锁重来。

### `tryConvertToWriteLock` 为什么不是总能成功

`tryConvertToWriteLock()` 位于 `StampedLock.java:739`。它最有价值的，不是“提供了升级 API”，而是把“升级并不总能成功”这件事明明白白写进返回值：成功给你新的 stamp，失败直接返回 0。

这很重要，因为它提醒调用方：**转换不是承诺，而是机会。** 如果当前状态不允许平滑升级，比如此刻并不满足只有你一个读者等条件，那就得走老老实实释放旧 stamp、重新获取新模式的兜底路径。

同样地，`tryConvertToReadLock()`（`StampedLock.java:776`）和 `tryConvertToOptimisticRead()`（`817`）也都是在帮你尽量缩短重锁路径，而不是保证任何时候都能无缝换挡。

这一层真正的理解不是背 API 名字，而是看懂：**StampedLock 在给你一套“先用便宜模式观察，必要时再平滑升/降级”的工具箱。**

## 七、怎么把 RRWL 和 StampedLock 放回同一条“读路径优化分层”主线上

### 先别把它们讲成两个孤立先进工具

很多资料会分别介绍 `ReentrantReadWriteLock` 和 `StampedLock`，但读者读完后仍然不知道什么时候该选谁。更有帮助的方式，是把它们看成同一条读路径优化链上的两个层级。

第一层优化，是 ReentrantReadWriteLock：先把“所有访问都互斥”改成“读者之间别互相等，只有写者独占”。如果你的场景需要可重入、需要和 Lock/Condition 语义配合、需要相对清晰直接的读写规则，它通常已经够用。

第二层优化，是 StampedLock：在“读-读并行”之上再问一句——写既然很少，读是不是连共享读锁都不一定每次值得拿？如果你愿意接受 validate/回退重读逻辑，并且业务不需要重入和 Condition，这时乐观读才真正有价值。

### 选型真正看什么

把选择条件压成几句：

- 只要互斥或需要 Condition、多条件等待、可重入：先看 `ReentrantLock`
- 读多写少、需要清晰语义、能接受读写锁常规开销：看 `ReentrantReadWriteLock`
- 写极少、读极多、可接受乐观读校验和失败回退，而且不依赖重入/Condition：再考虑 `StampedLock`

所以不要把 `StampedLock` 当成“读多写少场景的默认更优解”。它只是这条优化链上更激进的一层，收益更高，前提也更苛刻。

## 五个最容易混掉的边界：读写锁不是两把独立锁，读并行不是无锁，降级不是升级镜像，乐观读不是无验证读，StampedLock 也不是 RRWL 升级版

第一，读写锁不是两把独立锁。`ReentrantReadWriteLock` 的读锁和写锁共享同一个 state，只是高低位语义不同；它们不是各玩各的两把锁，而是围绕同一份读写资格事实协同工作。

第二，读并行不是无锁。多个读者能同时通过，不等于它们完全脱离同步语义；读锁仍然要参与状态判断和计数，只是把读者之间原本不必要的互斥拆掉了。

第三，降级不是升级镜像。写锁降级成读锁，本质是独占者主动让出一部分权力并保持已写状态的可见连续性；读锁升级成写锁则常常要在多个共享读者中强行争独占，天然更危险，也不对称。

第四，乐观读不是无验证读。`tryOptimisticRead()` 给你的不是“现在可以放心乱读”的许可证，而是一份事后必须用 `validate()` 核对的版本快照；没有验证，乐观读就只是把中间态风险藏起来。

第五，`StampedLock` 也不是 RRWL 升级版。它提供的不是“同样语义但更快”的简单替换，而是一套以版本戳、乐观读和模式转换为核心的新取舍；你若需要重入、Condition 或更直接的 Lock 语义，RRWL 反而更合身。

把这五条边界记稳，读写锁和乐观读就不会再被误解成“读多写少时换个更高级的锁”这么简单。它们真正想讲的是一条逐层优化的读路径：先把读者之间不必要的互斥拆掉，再在写极少前提下把读锁固定成本后移到事后校验，并始终用清晰的回退路径守住正确性。

## 收网：读路径优化也有层级，先做到读者并行，再考虑先读后验

回到开头那个问题：为什么读多写少时，两个读者不该互相等？因为普通互斥锁把“可能冲突”和“根本不冲突”的访问一视同仁地压成了独占。读写锁做的第一步，就是把“读者之间并不修改共享状态”这件事编码进 state，让读-读并行成为可能。

而当你继续追问“那读锁本身是不是还可以再轻一点”时，StampedLock 才会出场。它不是让你无脑不加锁，而是把读路径再拆成两层：先乐观读取，再用版本戳证明期间是否无写发生；证明失败时，再退回真正的锁路径。

把整篇压成一张总图，就是：

```text
互斥锁
  → 所有人排队

ReentrantReadWriteLock
  → 读者并行
  → 写者独占
  → state 同时编码读写计数

StampedLock
  → 写锁 / 读锁 / 乐观读三模式
  → 先读后验
  → validate 失败再回退重读
```

所以，读写锁和乐观读真正解决的不是“锁更多了”，而是“读路径该不该为并不存在的冲突付同样代价”。这也是域 12 整个锁同步篇收束到最后，最值得留下的一条主线：**并发控制不是只有加锁或不加锁，而是在不同竞争模式下，选择让谁等、谁并行、谁先乐观试一把。**

到这里，锁与同步域就完整闭环了。下一站不再从同步器骨架出发，而会转向更上层的执行与数据处理模型：线程池如何消费这些同步结构，Stream 与并行流又怎样建立在已有并发基础设施之上。
