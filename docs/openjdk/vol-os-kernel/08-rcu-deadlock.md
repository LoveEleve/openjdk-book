# RCU、lockdep、活锁与 per-CPU：除了“你等我”，并发还有别的活法

> 主题：OS 内核｜第 8 篇
> 前置文章：`07-lock-family.md`
> 本篇后续：`09-interrupts-softirq.md`
> 版本说明：本文讨论 Linux 上稳定的并发治理心智模型；RCU grace period 的具体检测机制、lockdep 报告细节、抢占模型、per-CPU 访问宏以及 RCU 回调执行上下文会随内核版本、配置与 PREEMPT 模式变化。本文以“锁之外还有哪些路”作为主线，不把某一版本的函数名、位段布局或软中断实现细节当作跨版本常量。

## 读者真的必须排队吗

前一篇把锁家族铺开以后，读者很容易形成一个新直觉：并发控制无非是在各种锁之间做选择——要么睡，要么转；要么让读者等写者，要么让写者等读者；实在不行就让用户态先忙一轮，再进内核排队。

这个直觉已经比“只有一把 mutex”进步很多，但它还没触到内核并发设计最有意思的地方。因为一旦你的读者数量远远超过写者，比如路由查找、连接跟踪、只读配置快照、内核里很多几乎只读的索引结构，你很快就会冒出一个新问题：**读者难道真的也必须为“将来某个很偶发的写”付出锁成本吗？**

这篇就是在锁家族之后，继续把同步哲学往外推。它会回答四个层层递进的问题：

- 有没有一种方案，能让读者几乎完全不拿锁？
- 锁写错了，不等真死锁发生，能不能提前看出来？
- 有些程序没死锁却也没进展，这和死锁到底差在哪？
- 如果我们干脆把共享变成“不共享”，是不是就连锁都省了？

先记住本篇总图：

```text
传统锁：你等我，我等你放行
RCU：读者先走，写者等旧读者自然走完
lockdep：不是等事故发生，而是提前检查锁顺序图是否成环
活锁：线程都在动，但没人真正往前走
per-CPU：把共享拆成每核副本，很多锁直接消失
```

这一篇最关键的顿悟是：**同步不只是一句“谁先拿锁”。** 有时你可以把等待全部推给写者，有时你可以把共享本身拆掉，有时你甚至可以在真正卡死前先把危险顺序图抓出来。

## 一、RCU：不是“读者更快的锁”，而是“读者尽量别拿锁”

### 1. 失败方案：每个读者都老老实实加读锁

如果一个数据结构几乎一直被读，偶尔才被改，最自然的方案是 rwlock：读者并行，写者独占。这已经比普通互斥好多了。

但它仍然让每个读者先付出一笔协调成本：哪怕只是进来查一眼，也得带着“我现在在读”这个锁语义走一遍。读者越多，这个成本越常驻；写者想更新时，也得等所有现有读者散场。

当读流量比写流量大几个数量级时，连这点“读锁成本”都可能被嫌贵。于是 RCU 出场时，并不是在问“能不能让读锁更轻”，而是在问：**能不能把读锁这件事本身尽量拿掉。**

### 2. RCU 的哲学不是“你等我”，而是“我等你走”

RCU 的核心思想可以压缩成三步：

- 读者走自己的，不去阻塞别人。
- 写者不直接原地改旧对象，而是准备一个新版本。
- 新旧版本切换后，旧版本先别急着释放，要等所有可能还在读旧版本的读者自然走完。

```text
读者
  → 进入读临界区
  → 只管拿当前可见指针去读
  → 不和别的读者互斥，也尽量不阻塞写者

写者
  → 准备新副本
  → 原子替换共享指针
  → 旧副本暂时保留
  → 等旧读者都离开后再释放旧副本
```

所以 RCU 真正颠覆的不是某个 API，而是等待方向。锁的哲学多半是“我进来时，你先别动”；RCU 的哲学则是“我先把新世界挂上去，但旧世界先别拆，等旧读者自己看完走人”。

### 3. 为什么读者可以几乎无锁

RCU 读者之所以能非常轻，是因为它们通常不负责协调一致写入，也不负责阻止对象版本切换。它们只是在进入一个受保护的读时期后，拿到当前指针并据此读数据。

关键在于：写者承诺自己不会把旧对象立刻收走。这样，哪怕读者手里还捏着旧指针，也不会突然踩进悬空内存。也就是说，读者之所以不需要重锁保护，不是因为内存凭空永远不变，而是因为写者把“对象何时能真正死亡”的责任扛了过去。

### 4. Grace Period 的本质：不是等全系统静止，而是等“所有旧读者都不再可能拿着旧指针”

很多人第一次听到宽限期，会误以为 RCU 在等所有 CPU 全部停下来。其实不是。它真正等的是一个更精确的条件：**在旧指针还可能被谁持有这件事上，系统已经跨过了那个危险窗口。**

只要每个可能持有旧版本的执行上下文都经历过一次“我已经不在旧读临界区里了”的时刻，那么旧对象就可以安全释放。这个时刻在 RCU 世界里就是 quiescent state 背后的直觉含义。

所以 Grace Period 不是“暂停世界”，而是“确认旧世界已经没人还在里面逛”。

### 5. RCU 并没有消灭代价，只是把代价全部推给写路径和延迟释放

RCU 经常被误说成“无锁更快”。更准确的说法是：它把读路径做得极轻，但代价并没有消失。

这些代价主要落在：

- 写者要复制和替换，而不是原地修改。
- 旧对象要延迟释放，内存会暂时同时养着新旧两份。
- 系统要维护 Grace Period 的推进与回调处理。

这里最值得再强调一层的是“成本互换”到底换了什么。传统锁里，读者每次进门都先交一点门票，写者则在需要时清场；RCU 则反过来，把门票几乎全免给了读者，但要求写者在每次更新时承担更多家务：准备新版本、保留旧版本、等待所有旧读者自然离场、最后再异步清理现场。也就是说，RCU 并不是让同步消失，而是把“每次读都付一点”改成“每次写付很多，但读几乎不付”。只有当读远多于写时，这个账才值得。

所以 RCU 不是“免费并发”，而是“在读远多于写时，愿意为读者零开销花额外写成本和生命周期复杂度”。

## 二、lockdep：死锁最可怕的地方，不是它一定发生，而是它平时看起来像没事

### 1. 失败方案：等真正锁死再去抓栈

很多人排查死锁的第一反应是看现场：进程不动了，CPU 没进展了，再去抓栈、看谁拿着哪把锁。但死锁有个更讨厌的特点——它往往是时序依赖事故。你的代码可能跑十万次都没事，只有在某个极小窗口里才刚好撞出 ABBA。

于是“等事故发生再诊断”就很被动。你不仅要运气好才能复现，还得在事故现场信息还没被冲掉前抓住它。

### 2. lockdep 的聪明之处：不等死锁发生，先盯顺序图有没有成环

lockdep 最有工程味的地方就在于，它不执着于“此刻有没有真的卡死”，而是先把你获取锁的顺序关系记录下来，构成一张依赖图。

如果系统已经观察到 A 之后拿 B，又观察到 B 之后拿 A，那么哪怕这两次没有发生在同一次事故现场，依赖图里也已经出现了一个潜在环。环意味着：只要时机合适，这两条顺序迟早可能互相咬住。

```text
观察到顺序：A → B
又观察到顺序：B → A
  → 图中成环
  → 即使这次还没真的卡死，也应报警
```

所以 lockdep 的价值，不在于“替你复盘现场”，而在于把概率性事故提前翻译成确定性的结构违规。

### 3. 它检测的不是“线程停了”，而是“这套加锁关系本身已经危险了”

这就是为什么 lockdep 报告经常发生在系统还没真的死的时候。它看到的是锁类之间的关系模式，而不是当前线程是不是已经永远不动。换句话说，它在抓“未来会不会出事的骨架”，而不是等血已经流出来才给你看。

这非常像编译器对未定义行为的警告：程序眼下可能还跑着，但结构上你已经走到悬崖边。

### 4. `echo t > /proc/sysrq-trigger` 这类手段，更多是在事故已发生后帮你看现场

一旦系统真的进入死锁或疑似卡死，抓全任务栈仍然很重要。因为这时候你需要知道：谁持有了什么、谁在等什么、锁链条停在了哪一层。

所以 lockdep 和抓栈不是替代关系，而是前后两层：

- lockdep 负责提前识别“这套顺序有毒”。
- 栈回溯负责在事故真的发生时告诉你“毒是怎么扩散到现场的”。

## 三、活锁：线程都很忙，却谁也没把事情真正做完

### 1. 死锁是停住，活锁是一直动但白动

死锁容易想象：大家互相等，最后谁也不走。活锁更恶心，因为表面上线程都没停。它们在运行、在重试、在让步、在退避，但系统层面的有效进展接近于零。

这意味着活锁常常比死锁更难被一眼看出。死锁时你会看到任务挂着不动；活锁时你看到的是 CPU 很忙、线程很活跃，可业务还是没往前推。

### 2. 活锁经常来自“太礼貌的重试策略”

一个经典活锁场景是：两个线程都 trylock 失败，于是都决定“那我先退一步让别人来”；可它们退让和重试的节奏又完全一致，于是每一轮都同时退、同时抢、同时再失败。

这类问题说明，不是所有“避免阻塞”的策略都天然更好。有时候你以为自己在减少等待，实际上是在制造一种永不停息但始终没成果的同步舞蹈。

### 3. 为什么活锁比死锁更难自动检测

死锁容易留下静态证据：等待图不动了、锁依赖卡住了、任务栈状态稳定。活锁则在不断变化：线程状态在变，调用栈可能反复循环，CPU 利用率甚至很高。

所以活锁更像一种“进展失败”，而不是“状态冻结”。它往往要靠更高层的吞吐、重试次数、退避模式和时间分布去推断，而不只是靠“这个线程挂住没”。

### 4. 活锁提醒我们：不阻塞不等于高效

这也是 RCU、CAS 自旋、trylock 退避这些模式都必须谨慎的原因。只要你把“等待”换成“重试”“乐观尝试”或“主动让步”，就要小心另一种风险：也许线程都很努力，但努力的方向刚好互相抵消。

## 四、per-CPU：把共享变成“不共享”，很多锁问题就直接蒸发

### 1. 失败方案：所有统计、计数、局部缓存都放在同一份全局变量里

假设每个 CPU 都在高频更新同一个统计计数器。逻辑上这很自然：系统总计数不就该放一份吗？

但只要你真的这么做，马上就会同时触发两层成本：

- 锁或原子更新本身的协调成本。
- 上一篇讲过的缓存行热点与一致性流量。

很多场景下，真正需要的是“每个核先各记各的，最终再汇总”。如果这样已经满足语义，那坚持维护一份实时全局一致副本反而是在自找并发麻烦。

### 2. per-CPU 的思想比 RCU 更激进：连共享都先拆掉

RCU 仍然承认“我们共享同一份逻辑对象，只是读写时机不同”；per-CPU 更激进，它直接问：这东西真的有必要实时共享吗？

如果答案是否定的，那么最便宜的同步就是不共享。每个 CPU 有自己的副本，本核只改自己的，本地更新完全不需要和别人争抢。最后需要总量时，再集中汇总。

```text
每核独立副本
  → 本核更新零竞争
  → 不需要跨核抢同一缓存行
  → 需要全局视图时再汇总
```

所以 per-CPU 不是某种“优化细节”，它本质上是在改问题定义：从“怎样高效共享”改成“这件事能不能先别共享”。

### 3. 代价是实时一致视图变弱，汇总成本后移

当然，per-CPU 不是白赚。你省掉了更新期的共享成本，就意味着平时看到的是一堆分散副本；想拿到全局精确结果，必须额外汇总。若业务要求每次读取都看到一个精确、实时、全局统一的数，这种方式就未必适用。

所以 per-CPU 适合的是“局部频繁写、全局偶尔读”的模式。它用最终汇总成本，换取日常更新零争用。

### 4. 抢占为什么会和 per-CPU 绑在一起

如果你说“我在本 CPU 的副本上更新，所以不用锁”，那前提是这段更新期间你真的还停在这个 CPU 上，没有中途迁移到别的核去操作另一份副本。于是抢占和迁移控制就开始变得相关。

最容易出错的失败场景是：代码先取到“当前 CPU 的副本指针”，还没来得及更新，就因为可抢占被调度走；等它恢复运行时，已经落到另一颗 CPU 上了。此时你手里拿着的，可能还是旧 CPU 的那份副本引用，而你接下来的逻辑却默认“我还在本地”。这种错不一定会立刻崩溃，但它会悄悄破坏“每核独立记账”的前提，让局部更新跑到错误的柜子里去。

这也是为什么很多 per-CPU 访问模式会和 `preempt_disable`、`get_cpu_var` 这类保护语义绑在一起：不是因为 per-CPU 自己天然神秘，而是因为“本地副本”这个假设必须在执行上下文层面被守住。

## 五、经典软件互斥：没有硬件原子之前，人们也试过纯软件把门

### 1. 历史意义不在于今天还常用，而在于它解释了为什么硬件支持后来变成必需品

像 Dekker、Peterson 这些经典软件互斥算法，今天在工程里很少直接上场，但它们仍然值得讲，因为它们让人看到：在没有现代硬件原子支持时，软件曾经尝试只靠标志位和轮转协议去构造互斥。

### 2. 它们依赖的是一种今天已经不能随便假定的世界

这些算法往往隐含了一些很强的假设：读写可见性足够直接、访存顺序不会被轻易改乱、参与者数量和执行模型非常受控。可一旦你把它们放进多核缓存、一致性协议和弱内存模型的世界，就会发现这些前提再也不能轻信。

这正好反过来说明了为什么我们前面花那么多篇去讲缓存一致性、Store Buffer、原子操作和屏障：现代并发不是靠纯逻辑推理就能兜住的，它必须依赖硬件与软件共同给出的可见性契约。

## 六、把这几条路收成一张更大的图：锁不是同步的全部，等待也不是唯一代价

现在可以把这篇所有角色放回同一张图里。

如果传统锁太贵，第一种出路是 RCU：让读者几乎不管写者，代价由写者延后承担；第二种出路是 per-CPU：干脆把共享拆掉，让很多更新从根上不再需要锁。可只要系统里还有锁，顺序就还可能写错，死锁风险就还在，于是 lockdep 负责提前把危险关系图照出来。与此同时，你也不能因为线程还在跑就掉以轻心——活锁提醒我们，“一直在动”并不等于“真的有进展”。

```text
锁太重
  → RCU：读者不等，写者等旧读者走
  → per-CPU：先别共享，各核各记各的

锁仍然存在
  → lockdep：提前发现危险顺序环
  → 活锁分析：识别“忙但没进展”的失败模式
```

所以本篇最该记住的一句话是：**同步设计不只是选哪把锁，而是在决定“要不要共享、谁来等待、风险在什么时候暴露、以及错误能不能在事故前被看见”。**

## 七、几个最容易说错的地方

### RCU 是不是“更高级的读写锁”？

不够准确。它不是单纯让读锁更便宜，而是把等待方向彻底改了：读者几乎不等，写者负责延迟释放与生命周期治理。

### 只要有 lockdep，是不是死锁就不会发生？

也不是。lockdep 非常强大，但它依赖实际观测到的锁类关系与启用配置；它是极好的运行时验证器，不是数学意义上的宇宙级完备证明。

### 活锁是不是比死锁轻，因为线程至少还在跑？

不一定。活锁的业务效果可能同样糟糕，甚至更难定位，因为系统表面上“还活着”。

### per-CPU 是不是万能免锁方案？

不是。它只适合那些允许把共享拆成局部副本、并接受最终汇总或局部视图的场景。需要实时统一真相的状态，不能简单靠 per-CPU 糊过去。

## 收束：并发世界真正高级的地方，不是锁更多，而是开始学会少等、少共享、少靠运气

现在回到开头那个问题：读者真的必须排队吗？答案显然已经不是“当然”。当读者极多而写者极少时，RCU 让我们第一次看到：同步不一定非要让读者掏钱；当局部更新极多时，per-CPU 让我们看到：最好的锁有时是不共享；当系统复杂到多把锁纠缠时，lockdep 又说明：工程上真正高明的地方，不是等事故发生后再英雄式排查，而是尽量把概率性风险提前结构化暴露出来。

这篇的开场困惑也就闭环了：锁家族之后，内核并没有停在“睡还是转”的二选一，而是继续发展出“读者几乎无锁”“把共享拆掉”“在事故前就验证锁关系”这些更高级的生存策略。
