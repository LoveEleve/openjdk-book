# CFS 调度器：被打断之后，内核到底凭什么决定“下一个该谁跑”

> 主题：OS 内核｜第 10 篇
> 前置文章：`09-interrupts-softirq.md`
> 本篇后续：`11-process-fork-switch.md`
> 版本说明：本文讨论 Linux 调度器从 CFS 到 EEVDF 的稳定心智模型；`vruntime`、红黑树、负载均衡、cgroup CPU 控制与实时调度语义会随内核版本、PREEMPT 模式和具体调度类演进。本文以“公平如何被量化”为主线，不把某版本默认参数、固定时间片数值或某棵树上字段名字当作跨版本常量。

## 时钟中断敲门以后，内核凭什么说“你先下来，换他跑”

上一篇讲的是：设备和时钟可以强行打断当前执行，ISR 要尽快收尾，下半部再接手，时钟中断则不断推动系统节拍。可真正的大问题其实还在后面：**被打断以后，内核怎么决定接下来把 CPU 交给谁。**

这是调度器要回答的核心问题。

很多人第一次思考“公平调度”时，会下意识地给出一个非常像样的答案：大家平分 CPU，不就公平了吗？如果只有两个任务，每人一半；四个任务，每人四分之一；谁都别吃亏。

这个答案听起来很公正，却很快会被现实打脸。因为真实进程并不一样：

- 有的进程大部分时间在等 IO，偶尔醒来只想赶紧跑一下。
- 有的进程是纯 CPU 密集型，一旦给它 CPU，它能一直烧满。
- 有的任务被用户显式调低了 nice 值，希望少占点资源；也有些任务需要更高权重。
- 多核机器上，还要继续问：是该把任务均匀摊开，还是优先留在本核保缓存热度？

所以调度器真正面对的问题从来不是“大家各占多少时间”这么简单，而是：**如何在响应性、吞吐、公平、局部性和权重偏好之间，给出一个持续可计算的决策规则。**

先记住本篇总图：

```text
时钟中断或其他调度触发点到来
  → 更新当前任务已运行的代价
  → 把公平量化成可比较的虚拟时间
  → 从可运行任务集合中选“最该轮到”的那个
  → 多核上再考虑迁移代价与负载均衡
  → 容器限制和实时类在更高层改写这套默认公平
```

这一篇最关键的顿悟是：**公平不是“每人一半”，而是“按权重推进虚拟运行时间，谁用得少谁优先”。**

## 一、公平如果不能被量化，就只能沦为口号

### 1. 失败方案：简单轮转，每人一小段时间

最直觉的方案就是 Round Robin：就按顺序转圈，时间片一到就换人。这样谁都不会一直霸占 CPU，看上去也很公平。

问题在于，这种公平过于“机械”。如果一个交互型任务刚从睡眠里醒来，只想跑一下把输入处理掉，却总要排在一群 CPU-bound 任务后面轮一圈，它的响应性仍会很差。另一方面，如果一个任务被人为设置了更高权重，仅靠“排队轮流”也表达不出来这种偏好。

把这个失败再说具体一点：你在终端里敲一个字符，shell 进程被唤醒，只需要很短一段 CPU 去回显和处理；与此同时，后台编译任务早就在持续吃满 CPU。如果调度器只知道“大家轮流来”，那么这个刚醒的交互任务很容易被埋进长队里。结果不是吞吐出了大问题，而是用户体感先崩了——你会觉得机器“明明没死，却敲一下等半天”。

也就是说，简单轮转能解决“别一个人一直霸占”，却无法精细表达“谁最近已经跑很多了，谁虽然也在队列里但其实更该先响应”。

### 2. CFS 把“公平”改写成一块持续增长的记分牌

CFS 最聪明的地方，不是红黑树，而是它先把公平量化了。它不再只看“你现在是不是轮到”，而是给每个可运行实体都记一块表：你到目前为止，按你的权重折算后，已经用掉了多少 CPU。

这个量就是 `vruntime` 的教学直觉。

```text
实际运行时间增长
  → 按权重折算成 vruntime 增量
  → 跑得越多，vruntime 越靠后
  → 跑得越少，vruntime 越靠前
  → 于是“运行少的优先”被变成一个可比较的数
```

所以 CFS 真正做的事，是把“公平”从一句模糊原则，变成了一个能持续比较的动态指标。

### 3. 权重不是直接给更多时间，而是改变你“记分变快还是变慢”

这是很多人第一次学 CFS 时最容易想错的地方：权重高，不是说调度器给你发一个更大的固定时间片红包；更准确地说，是你每跑一段实际时间，在 `vruntime` 这块记分牌上增长得更慢。

于是高权重任务不会被迅速判定成“你已经跑够了”，它更容易持续保持在“还轮得到你”的区间里。低权重任务则相反，同样跑一会儿，账本长得更快，就更容易被排到后面。

所以 nice 值和 weight 并不是“直接写死优先级数字”，而是在改变公平账本的走表速度。

### 4. 交互型任务为什么会显得“被隐式优待”

很多交互型任务并不是因为被打了一个神秘高优标签才更灵敏。它们经常睡眠，真正占用 CPU 的时间短，于是 `vruntime` 累得慢。等它们再次被唤醒时，在“谁最近用得少”的比较里，自然更容易靠前。

这背后的体感非常具体：用户并不会关心某个后台编译任务是不是平均多跑了几毫秒，他先感受到的是“我敲了键、点了窗口、拖了滚动条，系统是不是立刻理我”。CFS 对睡眠后唤醒任务更友好的地方，正在于它把“最近没怎么跑”的任务更快拉回前面，从而让交互行为看起来更跟手。

这意味着：交互型体验好，并不一定来自特殊偏爱，而是来自 CFS 对“最近没怎么跑”的任务天然更友好。这正是 `vruntime` 模型比简单轮转更精妙的地方。

## 二、红黑树不是亮点，亮点是“用一棵可排序结构随时捞出最该运行的人”

### 1. 一旦公平可量化，下一步就是要高效地选最小值

既然调度器现在关心的是“谁的 `vruntime` 最小”，那它接下来的数据结构需求就非常清楚：我要维护一组可运行任务，并且能高效取出当前最小的那个。

如果每次都线性扫一遍，任务一多就会拖慢调度决策本身。于是 CFS 需要一棵能维持有序关系、又能高效插入、删除和取最小的结构。

### 2. 红黑树在这里的角色，不是“很高级”，而是“够稳、够快、够适合动态有序集合”

调度队列里的任务一直在变：有人睡了，有人醒了，有人用完了时间片又回树里，有人退出了。红黑树适合这种场景，不是因为它理论上最浪漫，而是因为它能在动态增删中始终维持有序，并让“找最小”这件事保持便宜。

所以别把关注点放成“调度器用了红黑树，好高级”。更本质的理解是：**一旦公平被量化成可比较值，调度器自然需要一个动态有序集合来随时拿出最该先跑的任务。** 红黑树只是这件事的工程实现。

### 3. 真正被调度的不是“进程抽象”，而是可运行实体

从教学上，可以先把它理解成“每个要竞争 CPU 的实体都有自己的 `vruntime` 和可运行位置”。线程和进程在调度层最终都被压成某种 schedulable entity，而不是靠“它是哪个应用”的人类语义来排队。

这一点会在下一篇 `task_struct`、fork 与上下文切换里继续展开：调度器此刻挑的是“谁该跑”，下一篇会解释“这个谁在内核里长什么样”。

## 三、时间片不是固定常数，而是在“响应”和“切换成本”之间摆钟

### 1. 失败方案：越短越公平

如果只从“让大家轮得更勤”出发，你会觉得时间片越短越公平。因为这样没人能长时间霸占，响应也似乎会更快。

可时间片一旦短到一定程度，另一个成本就冒出来了：上下文切换本身不是零代价。切得太勤，CPU 会把越来越多时间花在保存现场、切换地址空间、恢复寄存器、维护调度器账本上，而不是真正干业务。

所以“越短越公平”是一个非常典型但错误的单指标思维。

### 2. 调度周期和最小粒度，本质是在折中“每个人都别等太久”和“别全耗在换人上”

CFS 会用类似调度周期、最小粒度这样的参数去平衡这件事。直觉上可以这样理解：

- 任务不多时，希望一轮周期里大家都至少跑到一次，响应别太差。
- 任务很多时，若还严格按“每人都切很细”去照顾，切换成本会吃掉吞吐，于是需要设一个下界，别把分片切到过碎。

因此，时间片不是一张事先固定印好的车票，而是由当前可运行实体数量和系统希望维持的交互/吞吐平衡共同推出来的。

### 3. 新唤醒任务为什么不能“出生即插队”得太离谱

另一个常见问题是：一个刚醒来的任务如果总能立刻粗暴抢占当前任务，会让系统频繁抖动。可如果醒来后永远老老实实排大队，交互性又会变差。

所以调度器通常会在“醒来应有一定优势”和“别一醒就把系统切得满天飞”之间再设一道缓冲。这也是 `vruntime`、唤醒粒度之类机制要做的事：新醒任务不是没有机会，但也不是想抢就一定马上抢下来。

## 四、调度器演进：从“按优先级排队”走向“按公平账本排队”

### 1. O(N) 和 O(1) 时代真正暴露的问题，不只是复杂度

讲调度器演进时，很容易只盯着算法复杂度：O(N) 太慢，所以要 O(1)；O(1) 再不够，于是换 CFS。这个说法只说对一半。

更深的变化其实是调度哲学。早期方案更像在一堆静态优先级或启发式规则里打补丁：谁更急、谁更重要、谁该先上。这样可以运行，但很难把“公平”这个概念持续量化，更容易对交互型任务、睡眠任务或特殊行为产生意外惩罚。

### 2. CFS 把问题从“谁优先级更高”改成“谁最近用得更少”

这是调度器历史上最值得记住的转向。它不是完全不看权重，而是把权重放进了 `vruntime` 增长速率里，然后用“谁账本最靠前”作为主要决策基础。

这样一来，调度就不再只是静态等级比较，而变成了一个持续追踪“谁在最近这段时间里用得少、该补一点”的过程。

### 3. EEVDF 说明调度器还在继续朝“更精细地表达应该轮到谁”演进

即使 CFS 已经比早期调度器成熟很多，调度器的演进也没有停。像 EEVDF 这样的新方向，继续在“公平”和“何时该被服务”之间做更细致的数学表达。

对当前读者最重要的，不是背新缩写，而是看懂这条长期趋势：**调度器越来越少依赖粗糙启发式，越来越把‘该谁先跑’变成可持续比较的时间模型。**

## 五、多核负载均衡：不是平均分任务，而是在“平均”和“别搬太狠”之间做买卖

### 1. 失败方案：哪个核任务多，就立刻搬一个过去

多核调度最直觉的方案是平均主义：只要某颗 CPU 忙、另一颗空，就立刻迁一个任务过去，看上去最平衡。

这个方案的问题在于，它只看“每核任务数”，没看迁移成本。任务刚在某个核上跑热了缓存，突然搬走，新的核得重新热启动本地缓存；如果还跨 NUMA 节点，内存局部性也可能立刻变差。

所以负载均衡不是简单的数学平均问题，而是一个“值不值得搬”的代价决策问题。

### 2. 空闲 CPU 拉任务很合理，但不是所有不均衡都值得立刻修

NEWIDLE 这类触发很容易理解：某核都空了，当然应该尝试拉点活来干。但即便如此，内核也不会像流水线分豆子那样完全无脑平均。因为系统真正要优化的不是“图上看起来一样平”，而是整体吞吐、响应和局部性综合最好。

也就是说，调度器不是讨厌不平衡，而是讨厌“有价值的不平衡被放着不用”。若一个轻微失衡恰好换来了更好的 cache locality，它未必值得立刻纠正。

### 3. NUMA 把“搬不搬”这个问题再抬高一层

跨 NUMA 节点迁移，代价不只是某个核 L1/L2 热度归零，还可能把任务与自己原来更近的内存拆开。于是有些情况下，宁可接受负载分布不那么整齐，也不想为了看起来均衡而把任务搬去远端。

这说明多核负载均衡的真正目标从来不是“平均”，而是“在迁移成本也算进账本后，仍然划算的平均”。

## 六、CGroup CPU 与实时调度：默认公平不是唯一法律

### 1. CGroup CPU：容器限制说明“公平”还可以被人为重新分账

到这里你会发现，CFS 默认是在同一套普通调度世界里谈公平。可现实里，系统管理员和容器平台还会继续对这套公平做再分配：某个容器只能拿多少 CPU，某个组在竞争时权重更高，某个配额周期到了就必须先停一下。

所以 CGroup CPU 的意义，不是发明另一套调度器，而是在默认公平之上继续加一个“预算壳”。它让“谁该跑”不只受进程自身 `vruntime` 影响，还受自己所属资源组可用预算影响。

### 2. 实时调度说明有些任务根本不接受“你先排公平队”

CFS 追求的是长期加权公平，但实时任务关心的往往不是“平均分得是否公正”，而是“我该及时跑的时候是不是马上就能跑”。

这就是为什么 SCHED_FIFO、SCHED_RR、SCHED_DEADLINE 这类调度类必须存在。它们不是对 CFS 的小修小补，而是在说：**有些工作关心确定性优先于长期公平。**

所以实时调度与 CFS 的差别，不是“谁更高级”，而是优化目标不同：一个优先考虑公平，另一个优先考虑截止期或及时性。

## 七、把 CFS 收成一张图：它不是“时间片轮转升级版”，而是一台持续记账的公平机器

现在可以把这篇的角色放回一条完整链路里。

时钟中断和其他调度触发点不断给调度器机会，让它更新当前任务“已经用了多少”的账本。`vruntime` 把公平变成动态数值，红黑树让“最该轮到谁”能够被高效取出。调度周期和最小粒度防止系统在响应与切换成本之间走极端。多核负载均衡继续把“平均”和“别搬太狠”一起纳入考虑。CGroup CPU 和实时类则在更高层重新改写默认公平。

```text
调度触发点到来
  → 更新当前实体的已用账本
  → 在可运行集合里比较谁最“该被补”
  → 选出最靠前的那个
  → 多核上再考虑迁移值不值
  → 资源组和实时类继续覆盖默认规则
```

所以本篇最该记住的一句话是：**CFS 不是简单给每人切一块时间片，而是在持续维护一张“谁最近用得少、按权重还该补多少”的公平账本。**

## 八、几个最容易说错的地方

### 公平是不是就等于每个进程一半、一份、一样多？

不是。公平首先要看权重，其次还要看最近谁已经用得多、谁用得少。平分只是最粗糙的一种想象。

### 交互型任务更灵敏，是不是因为内核偷偷给它们打了神秘高优标签？

不一定。很多时候是因为它们经常睡眠，真正占用 CPU 少，于是 `vruntime` 自然更靠前。

### 多核负载均衡是不是越平均越好？

不是。迁移会破坏缓存和局部性，跨 NUMA 节点尤其昂贵。均衡的目标是吞吐和响应最优，不是图形上看起来整齐。

### 有了 CFS，还要实时调度和 cgroup，是不是说明 CFS 不公平？

不对。更准确地说，是系统里本来就同时存在“默认公平”“资源限制”“截止期/及时性”三类不同目标，单一调度策略不可能同时完美满足。

## 收束：调度器真正调的不是进程，而是“谁该为公平、多快、局部性和限制买单”

现在回到开头的问题：时钟中断敲门以后，内核凭什么说“你先下来，换他跑”？因为在 CFS 的世界里，这不再是拍脑袋的好恶判断，而是对一张持续更新的公平账本做决策：谁最近跑得少、谁权重更高、谁刚醒来更该被照顾、搬过去值不值、这个容器还有没有预算、这是不是根本不该和普通任务一起排队的实时工作。

这篇的开场困惑也就闭环了：调度器不是在简单轮流发时间片，而是在把“公平”真正变成一种可比较、可维护、可被覆盖的运行时秩序。
