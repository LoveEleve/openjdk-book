# 原子操作、CAS 与内存屏障：为什么“写完了”不等于别人已经看见

> 主题：OS 内核｜第 6 篇
> 前置文章：`05-mesi-false-sharing.md`
> 本篇后续：`07-lock-family.md`
> 版本说明：本文讨论 Linux/x86 常见原子操作与屏障心智模型；`LOCK` 前缀、`cmpxchg`、内存屏障映射、`READ_ONCE/WRITE_ONCE`、`smp_mb` 等行为会随架构、编译器、内核封装和 CPU 内存模型差异而变化。本文以机制解释为主，不把某一代处理器的精确 cycle 数、指令微码细节或汇编展开当作跨平台常量。

## `i++` 看起来像一步，硬件眼里却往往至少是三步

上一篇讲到，多核并不是所有核都盯着主存里同一份值，而是在缓存副本、一致性协议和写缓冲之上勉强维持一个“看起来同步”的表象。那篇留下的最大裂缝是：既然缓存行修改权会争抢，Store Buffer 又会让“本核已写”和“他核已见”分离，那软件到底拿什么去实现“不可分割”的更新？

最典型的问题就是这句大家再熟不过的代码：

```c
i++;
```

在单线程心智里，它像一个动作；在多核里，它往往至少拆成三个阶段：先读旧值，再算新值，再写回去。只要两个核在这个过程中交错，结果就可能丢更新。于是我们必须区分两件事：

- **原子性**：这次读改写会不会被别人从中间插进来。
- **顺序性**：我代码里写在前面的读写，别人观察时会不会还是这个顺序。

这篇要讲清的，就是这两件事分别靠什么守住，以及为什么“有原子指令”并不自动等于“顺序也没问题”。

先记住本篇总图：

```text
原子指令
  → 保证某次读改写不可被别的核拆开
CAS / xchg
  → 用通用原子原语拼出自旋更新模式
编译器屏障
  → 防止编译期把顺序偷偷改掉
CPU 屏障
  → 防止硬件运行期的缓冲和乱序破坏可见顺序
内存模型
  → 决定不同架构到底默认替你保留了多少顺序直觉
```

这一篇最关键的顿悟是：**原子性和顺序性不是同一个问题。** `LOCK` 或 CAS 解决的是“别把这一刀拆开”；屏障解决的是“这几刀在别人眼里必须按什么顺序看见”。

## 一、先别把 `i++` 当成语言魔法：为什么原子性必须由硬件兜底

### 1. 一个看似成立、实际上会丢更新的方案

假设两个核都对同一个计数器做 `i++`。如果你只按源码读，很容易脑补成：A 做一次加一，B 再做一次加一，最后结果自然加二。

真正的问题在于，这句语法糖背后不是一个不可再分的神秘动作，而是：

```text
读当前值
  → 在寄存器里加一
  → 把新值写回
```

如果核 A 和核 B 恰好都先读到了同一个旧值，随后各自加一、再各自写回，那么其中一次更新就会被覆盖掉。结果不是错在“加法不会算”，而是错在“这三步没有被当成一个整体保护起来”。

### 2. 原子操作的关键，不是更快，而是不给别人看见中间态

所谓原子性，不是“这条指令很短，所以很快做完”；真正重要的是：对其他观察者来说，这次更新要么还没发生，要么已经完成，中间那一半不能被别人撞见，更不能被别人把自己的更新插进来。

所以原子操作真正要回答的是：**我怎样让一整次读-改-写，在多核争抢下仍然像一个不可分割的动作。**

### 3. `LOCK` 前缀不是语法装饰，而是硬件层的“这次别插队”

在 x86 教学主线里，可以把 `LOCK` 前缀理解成对某类读改写指令的硬件宣告：这次更新不是普通写，请把它当成需要独占完成的动作。旧时代常用“锁总线”做直观说法，现代处理器更多是在缓存一致性层面抢下相关缓存行的独占修改权；但对读者最重要的稳定结论只有一个：**别的核不能在这次读改写中间塞进自己的写。**

```text
普通读改写
  → 读旧值
  → 算新值
  → 写回
  → 期间可能被别的核插队

带原子保障的读改写
  → 仍然有这些步骤
  → 但对外表现成不可拆开的整体
```

这也解释了为什么“语言里的一个表达式”并不自动具备原子性。真正给它底气的，不是语法形状，而是底层是否用了能获得硬件独占更新语义的指令。

### 4. 原子性是有成本的

如果普通访问都能随便打断、流水线和缓存层自由发挥，那么原子指令就必须额外收紧一些自由度：它可能要抢修改权、阻止别的核同时动这行，还常常伴随更重的序列化效果。

所以原子操作不是“白送的单线程写法升级包”。它是在告诉硬件：这一次你别再用最松的高吞吐方式糊过去，我宁可多付一些协调成本，也要换来一个不可分割的结果。

## 二、CAS：不是“自带循环”的黑箱，而是一种通用原子更新模式

### 1. 专用原子加法不够表达所有更新

如果你只是做计数器加一，专门的 atomic add 指令或封装已经很好用。但很多并发更新并不是简单加减：你可能想“只有当前值还是 old 时才改成 new”，或者“只有栈顶还是这个指针时才把它换成下一个节点”。

这类操作的共同点是：**你不是只想做一次写，而是想在‘当前值仍满足我刚才观察到的前提’时，原子地完成更新。**

### 2. CAS 的核心是“我按刚才看到的世界更新，如果世界变了，我认输重来”

Compare-And-Swap 的思想非常朴素：

- 先读一个旧值。
- 在本地算出你想写的新值。
- 真正写入时，不是无条件覆盖，而是先检查内存里现在还是不是你刚才看到的旧值。
- 如果还是，就原子写入；如果已经变了，说明别人抢先动过，你这次更新作废，重新来。

```text
读 old
  → 算 new
  → CAS(地址, old, new)
       ├── 当前值仍是 old：原子写入 new，成功
       └── 当前值已变：失败，重试
```

这让 CAS 成为一种极通用的原子原语。它本身不替你完成循环，但它给了你一种可重复尝试的安全比较-更新动作。

### 3. 自旋不是“锁住不动”，而是失败后不停重试

很多基于 CAS 的无锁或轻锁模式，都会出现一个让新手不舒服的形状：do-while 重试。那不是代码写得笨，而是这类更新本来就在承认一个事实：并发世界里，你观察到的旧值可能在下一秒已经作废。

所以自旋的本质不是“原地睡觉”，而是“我先试，如果别人比我快，我立刻按新局面重新试”。当竞争不激烈时，这种方式可能非常高效；竞争激烈时，它也可能疯狂烧 CPU。这正是下一篇锁家族要继续讨论的权衡：什么时候值得忙等，什么时候该睡眠让出 CPU。

### 4. ABA 说明“值看起来没变”不等于“世界真的没变过”

CAS 最经典的陷阱就是 ABA。某个位置的值先是 A，你读到它；随后它被别人改成 B，又改回 A。轮到你做 CAS 时，看见还是 A，就以为“什么都没变”，于是乐观提交。

可真实世界已经变过一轮了。对栈、队列、指针回收这类结构来说，这种“看起来还是 A，语义上却不是原来的那个 A”会很危险。

这也是为什么很多生产级无锁结构会引入版本号、tagged pointer 或更复杂的内存回收协议。CAS 解决了“这次更新别被拆开”，但它并不自动帮你识别“值相同、历史却不同”的问题。

## 三、先防编译器，再防 CPU：为什么屏障天然是两层问题

### 1. 失败方案：只盯 CPU 乱序，却忘了编译器也会改顺序

很多人学到内存屏障时，脑子里第一反应都是硬件：Store Buffer、乱序执行、缓存一致性。可如果你只盯着 CPU，会漏掉第一层敌人：编译器。

只要语义允许，编译器就会为了优化寄存器利用、指令调度和流水线表现，调整某些读写顺序，甚至合并、删除、缓存读值。对单线程来说这通常没问题；对并发共享变量来说，可能就会把你以为明确表达出的时序打散。

所以顺序问题从来不是“等程序跑上 CPU 才出现”。它在编译期就可能开始变形。

### 2. 编译器屏障的职责，是先守住你写出来的顺序意图

编译器屏障、`READ_ONCE/WRITE_ONCE` 这类工具，首先做的是告诉编译器：这里的读写有并发语义，不要随便当成普通局部变量优化掉，不要跨这个点重排，也不要把一次读写偷偷拆成多次更小动作。

这类工具不是在和缓存一致性打架，它们是在保住“源码中的顺序和一次性访问意图”别先被编译阶段破坏。

```text
源码顺序
  → 编译器优化可能先改一轮
  → 编译器屏障/ONCE 语义先把这一轮约束住
  → 之后还要继续面对 CPU 运行期乱序
```

### 3. `volatile` 为什么经常不够，也经常用过头

`volatile` 容易让人误以为“只要加上它，并发就安全了”。它的真实作用更接近：别把这次访问优化没了，别太随意缓存寄存器副本。它确实能部分约束编译器，但它并不能替你建立跨核原子更新，也不能自动解决 CPU 运行期的可见性顺序问题。

这里还要把它和 `READ_ONCE/WRITE_ONCE` 区分开。后者更强调“这一次读写就按一次来，不要偷偷撕裂、合并或重复”，它是在帮你守住单次访问的形状；可它同样不自动等于跨核顺序屏障。也就是说，`READ_ONCE/WRITE_ONCE` 解决的是“这一下别被编译器改坏”，屏障解决的才是“前后顺序别被系统重排”。

所以 `volatile` 最大的误导，不是它完全没用，而是它太容易让人误把“编译器层面别乱动”当成“并发层面已经安全”。这恰恰差着最难的一截。

## 四、CPU 屏障：当写已经离开源码，顺序问题才真正进入硬件现场

### 1. 仅防编译器，拦不住 Store Buffer

即使编译器完全按你的顺序生成了机器码，CPU 运行期仍然可能为了吞吐而重排可见效果。上一篇已经看到，Store Buffer 会让写先入账，本核先走；这意味着“我这条写在程序次序上已经做了”不等于“其他核此刻一定已经看见”。

所以 CPU 屏障的职责，正是用来在某些关键点告诉硬件：前面的读写不能再只停留在本核的乐观状态里，必须按照某种顺序约束真正对外收口。

### 2. 屏障不是“加一个神秘指令”，而是在修具体哪一类顺序裂缝

理解屏障时，最重要的不是先背 `mfence/lfence/sfence` 这些名字，而是先问：你到底在防哪种重排。

有的屏障是在说“前面的写必须先对外可见，后面的读才能开始当真”；有的是说“读和读之间别被调换”；还有的更多是在约束写和写、或读和写的顺序。

一个最经典的失败场景是消息传递：线程 A 先写数据，再写一个“ready”标志；线程 B 先看见 `ready`，再去读数据。直觉上，只要 `ready` 是原子变量，好像就够了。真正的问题是：如果缺少合适的顺序约束，B 完全可能先看见 `ready` 已更新，却还没看见 A 之前那批数据写入的最终可见结果。于是“标志先到了，数据却还没到”的反直觉结果就出现了。这个例子恰好说明：原子性只保证“那次写标志别被拆开”，却不自动保证“数据写在标志之前对别人可见”。

也就是说，屏障不是一个统一强度的“并发护身符”，而是针对不同顺序裂缝的修补工具。你要先知道哪堵墙漏风，才知道该补哪一块砖。

### 3. 为什么 StoreLoad 往往最贵

在很多教学语境里，StoreLoad 被看成最难伺候的一类顺序约束。原因不神秘：它往往要求当前核前面的写别只是“我自己记在缓冲里”，而要先推进到足够全局可见，然后后面的读再继续。这意味着它要管的不只是本核流水线内的次序，还可能牵动对外可见性的真正收口。

因此它常常比“只要求本核写按序出去”这种更贵。读者在这里不用死背具体 cycle 数，而要抓住根因：**凡是要求‘我先把前面的欠账对外结清，再开始看别人世界’的屏障，通常都不会便宜。**

### 4. Linux 的 `smp_mb/rmb/wmb` 本质上是在说“我要什么顺序”，而不是“我要哪条指令”

这也是内核封装这些接口的意义。大部分内核代码并不想把自己绑死在某一架构的指令名字上，它更想表达：这里我要完整的双向顺序、这里我只要读屏障、这里我只要写屏障。真正该落成 `mfence`、`dmb`、`barrier` 还是更轻的替代，则交给架构层去映射。

因此，屏障接口的核心不是“帮你少写汇编”，而是把问题提升到正确的抽象层：**你声明的是想要的顺序，架构实现的是达到这个顺序的最小代价。**

## 五、内存模型：为什么同一段无锁代码在 x86 上像对的，在 ARM 上却可能翻车

### 1. 失败方案：在一台机器上跑通，就以为顺序直觉是普世的

这是并发代码最常见、也最危险的错觉之一。开发者在 x86 机器上写了一段没有显式屏障的无锁代码，压测也过了，于是心里默认“这个顺序本来就成立”。一旦移到更弱的内存模型，问题才突然暴露。

这说明不是代码“突然变坏”，而是原来那台机器替你保留了更多顺序直觉，你却误以为这些顺序是语言或算法天然保证的。

### 2. x86 往往替软件多背了一部分顺序成本

从教学角度说，x86 的 TSO 往往比很多弱内存模型更接近程序员直觉。它并不是完全没有乱序问题，但它通常替软件保留了更多默认次序，让很多简单代码在没有太多显式屏障时也不至于立刻翻车。

这就是为什么很多工程师第一次接触 ARM/Power 等更弱模型时会震惊：原来自己以为“理所当然”的顺序，在别的架构上根本不是默认赠品。

### 3. 弱内存模型不是“做错了”，而是把更多责任交还给软件

弱模型的哲学不是说硬件不想保证正确，而是它不愿意默认替所有程序买下这么多顺序成本。于是更多顺序约束要由软件显式声明：这里需要 release，那里需要 acquire，这边需要 full barrier。

这也让“同一段无锁代码跨架构是否仍然正确”变成一个必须显式回答的问题，而不能靠经验侥幸。

### 4. 所以内核更强调用统一语义接口，而不是写死某一架构技巧

Linux 内核之所以强调 `smp_mb()` 这类抽象，不只是为了代码整洁，更是为了把“顺序需求”和“某架构恰巧足够强”这两件事分离。你声明需求，架构去兑现；不要反过来把某个架构默认赠送的顺序，当作全世界都欠你的保证。

## 六、把这些角色放回一条链：原子性是砖，顺序性是砂浆

现在可以把本篇的东西重新收成一条逻辑线。

当一次更新会被别的核插队时，首先要靠原子指令或原子原语保证“这次读改写别被拆开”；如果只是简单加减，专用原子更新可能已经够用；如果是更一般的“看旧值再换新值”，CAS 这种比较-交换模式就成了通用武器。

但原子性还不够。因为即便某次更新本身不可分割，编译器仍然可能改写顺序，CPU 运行期也仍可能通过缓冲和乱序让“本核已做”和“他核已见”分离。于是我们还要再补两层约束：编译器屏障守住源码语义，CPU 屏障守住运行期可见顺序；至于这些顺序默认保留多少，又由具体架构的内存模型决定。

```text
先解决：这次更新别被拆开
  → LOCK / xchg / cmpxchg

再解决：这些更新前后顺序别被改乱
  → 编译器屏障
  → CPU 屏障
  → 架构内存模型决定默认强弱
```

所以本篇最该记住的一句话是：**原子指令保证你手上的砖是一整块，屏障保证这些砖砌墙时别被悄悄调换顺序。**

## 七、几个最容易说错的地方

### `i++` 看起来是一句，所以是不是天然原子？

不是。它常常会拆成读、改、写多个阶段；有没有原子性，要看底层是否用了原子更新语义，而不是看源码是不是只写了一行。

### 有了 CAS，是不是就等于并发正确性解决了？

也不是。CAS 解决的是某次比较-更新的原子提交，不自动解决 ABA、饥饿、自旋退避和跨步骤顺序问题。

### `volatile` 能不能当成通用并发工具？

不能这么乐观。它更多是在约束编译器层面的访问行为，无法单独承担跨核原子性和运行期内存序保证。

### x86 屏障少，是不是说明 x86 基本不用考虑顺序问题？

不是。更准确的说法是：x86 默认替你保留了更多顺序直觉，但 Store Buffer、原子更新边界和跨核可见性问题依然存在；只是在很多场景下，你比在弱模型上少写一些显式约束。

## 收束：并发里的“安全更新”从来不是一个按钮，而是一整套分层协作

现在回到最开始的问题：为什么“写完了”不等于别人已经看见？因为从表达式到编译器、再到 CPU 执行和跨核可见，软件和硬件中间隔着好几层会为了性能偷改时序的机制。原子指令只是在其中一层保证“这一刀别被拆开”；真正想在多核世界里得到可依赖的并发语义，还必须把顺序问题一起钉住。

所以这篇的开场困惑已经闭环：`i++` 不是天然原子，CAS 不是万能并发咒语，`volatile` 不是跨核安全证明，屏障也不是多余仪式。它们共同在做的是一件更朴素但更难的事：让“我做了什么、别人什么时候看见、看见的顺序是什么”这三件事最终重新对齐。
