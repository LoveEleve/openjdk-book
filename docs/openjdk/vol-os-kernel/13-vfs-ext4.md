# VFS、inode、dentry 与 ext4：一个 `open()` 背后，内核怎样把几十种文件系统装进同一套接口

> 主题：OS 内核｜第 13 篇
> 前置文章：`04-page-cache-reclaim-oom.md`、`11-process-fork-switch.md`
> 本篇后续：`14-page-cache-io-path.md`
> 版本说明：本文讨论 Linux 文件系统抽象的稳定心智模型；VFS 四大对象、路径解析、dcache、ext4 extent 与 JBD2 的具体细节会随内核版本、文件系统实现和配置变化。本文以“统一抽象 → 元数据分工 → 磁盘索引 → 崩溃一致性”作为主线，不把某一版结构体字段、块大小或日志布局当作跨版本常量。

## `open("/data/a.txt")` 到底是怎么让 ext4、tmpfs、NFS 看起来都像“文件”的

从用户视角看，文件系统这件事其实非常奇怪。你对一个本地 ext4 文件、一个内存里的 tmpfs 文件、一个远端 NFS 上的文件，往往都能写出同样的代码：`open`、`read`、`write`、`close`。这就好像它们背后根本不是完全不同的系统，而只是“同一种文件”的不同口音。

可内核当然知道，事情没有这么简单。一个文件系统要回答的问题至少包括：

- 路径名怎么一步步解析成某个真正的对象？
- “文件名”和“文件本体”到底是不是一回事？
- 这个文件的数据块在磁盘上怎么找？
- 写到一半断电了，怎么保证元数据和数据不会落成半吊子状态？

如果每一种文件系统都要求应用重新学习一套 API，那 Linux 早就不可用了。于是 VFS 的第一层价值，并不是性能，而是**让几十种后端实现都能披着“文件”这个统一外衣和用户说话。**

先记住本篇总图：

```text
应用调用 open/read/write
  → 先落到 VFS 统一抽象层
  → VFS 用四大对象描述“文件系统、文件本体、名称映射、打开实例”
  → 路径解析通过 dentry 找到 inode
  → inode 再把你引到具体文件系统的数据索引结构
  → ext4 用 extent 组织连续块
  → JBD2 继续保证崩溃后一致性可判定
```

这一篇最关键的顿悟是：**Linux 统一的不是“磁盘布局”，而是“面向文件操作的对象模型”。** VFS 负责让接口看起来统一，具体文件系统再在这套模型背后各自实现自己的存储办法。证据位应回到 VFS 四大对象、路径解析、dcache、ext4 extent 与 JBD2 事务路径：它们共同支撑“统一接口、名字与本体分层、区间索引和崩溃一致性各司其职”的主线，而不是一句“open 背后会自动找到文件”就能带过。

## 一、VFS：内核先发明一套“文件对象语法”，再让各个文件系统自己去填实现

### 1. 失败方案：每个文件系统暴露自己的一套系统调用语义

最笨但很直觉的设计，是让 ext4、tmpfs、NFS、procfs 各自定义自己的操作入口。这样每个文件系统都能最直接地暴露自己内部最舒服的接口，不必为了统一抽象做额外适配。

这个方案的问题显而易见：应用层会被撕裂。你今天操作 ext4 学一套，明天挂个 NFS 又学一套，库、工具链和系统调用边界都要跟着分叉。文件系统越多，生态越碎。

所以 Linux 必须先做一件比“怎么存数据”更上层的事：先统一“文件这件事在内核里怎么被描述”。

### 2. VFS 的真正意义，不是隐藏一切差异，而是先统一最重要的那几个对象

VFS 之所以成立，不是因为它真的让所有文件系统看起来一模一样，而是因为它找到了它们之间足够大的最大公约数：

- 整个文件系统有自己的整体身份和状态。
- 文件本体有元数据、权限、大小和数据定位入口。
- 路径名解析需要一层名字到本体的映射。
- “打开这个文件”本身也是一个独立实例，它有当前偏移、打开标志等运行态状态。

这就是常说的四大对象心智模型：super block、inode、dentry、file。别急着背名字，先抓角色：**一个管整体，一个管本体，一个管名字，一个管打开后的会话。**

### 3. VFS 真正统一的是“对象 + 操作集”

这也是 VFS 最有工程味的地方。它不是试图把所有文件系统的内部逻辑都写死在一份通用代码里，而是先定义对象和操作位点：谁负责创建、谁负责查找、谁负责读写、谁负责重命名、谁负责 mmap。具体 ext4、tmpfs、NFS 再把自己的实现函数挂进去。

于是应用看到的是同一个 `open/read/write` 入口，内核内部却是“统一对象模型 + 每个文件系统自填操作表”的多态分发。

这和我们在很多其他子系统里看到的“统一接口 + 回调实现”是一致的：先统一语法，再允许实现差异。

## 二、inode 和 dentry：名字不是文件，本体才是文件

### 1. 失败方案：把文件名、权限、大小和数据位置都绑在同一个概念上

对普通用户来说，“`a.txt` 就是那个文件”几乎是自然直觉。可一旦你碰上硬链接、重命名、目录项缓存和路径解析，这个直觉立刻就会漏风。

因为文件名只是某个目录里的一段名字；文件本体的元数据、块位置、权限和时间戳，则是另一层东西。如果把这两层混成一个不可拆的概念，很多操作都会变得又笨又别扭。

### 2. inode 是“这个文件本体是谁”，dentry 是“这个名字在这里指向谁”

这就是 inode 和 dentry 分工的核心。inode 更接近“文件本体档案”：大小、权限、时间戳、数据索引入口、页缓存入口等都挂在它上面。dentry 则更像“目录里的这块名字牌子”：这个路径分量映射到哪个 inode，它的父目录是谁，这个名字最近是否已经被解析过。

```text
inode
  → 文件本体信息
  → 不关心你是通过哪个名字找到它的

dentry
  → 目录项名字映射
  → 关心“这个名字在这个父目录下指向哪个 inode”
```

所以“文件名不是文件”并不是文艺说法，而是内核对象模型里的真实分工。

### 3. 硬链接为什么能做到“两个名字一个文件”

只要把上面的分工想明白，硬链接就不神秘了。两个不同目录项名字，完全可以都指向同一个 inode。名字变了，甚至名字多了，本体都没变。

这也是为什么移动、重命名、硬链接这些操作很多时候动的是 dentry 关系，而不是文件数据本身。你改的是门牌，不是屋里家具。

### 4. dcache 的价值：不是缓存文件内容，而是缓存“走到这个文件怎么走”

前面第四篇讲过页缓存，那是缓存文件页内容。dcache 则是另一类完全不同的缓存：它缓存的是路径分量到 inode 的解析结果。

也就是说，dcache 优化的不是“读这个文件的数据快不快”，而是“下次再找这个名字别从磁盘目录里重新一层层翻”。这也是为什么一个系统里，页缓存和 dentry cache 可能都很大，但它们存的根本不是同一种东西。

所以当你排查“文件访问为什么慢”时，要先区分：慢的是内容没命中页缓存，还是名字解析没命中 dcache，别把两种缓存混成一谈。

## 三、ext4 extent：真正省元数据的秘诀，不是更会记每个块，而是别逐块记

### 1. 失败方案：大文件的每个数据块都单独记一个指针

如果一个大文件有成千上万个块，最朴素的记法就是：每个逻辑块对应一个物理块指针，像电话簿一样一条条记下来。这个办法最直接，但文件越大，元数据就越臃肿。大量顺序连续的数据，最终却被拆成了海量“第 N 块在哪”的重复记录。

这个问题在文件越连续时显得越荒唐：明明这 100MB 都挨在一起，你却还要一块一块抄一遍地址。

### 2. extent 的本质，是把“很多连续块”压缩成“一段区间”

ext4 的 extent 思路之所以重要，不在于它换了一棵更时髦的树，而在于它换了记录方式：连续的一大片物理块，不再按块逐个记，而是按区间记。

```text
不是记：块1在这，块2在这，块3在这……
而是记：从逻辑块 X 开始，对应一段连续的物理块区间，长度 N
```

于是，只要分配够连续，记录成本就会非常漂亮地压缩下来。

### 3. extent 的省，不是魔法，而是建立在“尽量让数据连续”这件事上

这也说明一个关键点：extent 并不是凭空比间接块更神奇，它是在“数据越连续，记录越省”的前提上获利。所以 ext4 不只是被动使用 extent 结构，它还会尽量争取连续分配、延迟分配、多块预留等策略，努力把这张区间表做得更稀疏、更划算。

也就是说，extent 的优势不是孤立存在的；它和分配器希望争取连续布局这件事是互相成就的。

### 4. 这也解释了为什么 ext4 对大文件和顺序写特别友好

一旦文件可以被表示成少量大 extent，查元数据更省，读写路径上的索引跳转也会更干净。真正拖垮它的，往往不是“大文件本身”，而是碎片化、随机化和连续性被破坏之后，extent 记录开始变细碎。

所以 ext4 的“快”并不是一句抽象评价，而是体现在：**它让连续数据的元数据表达成本大幅下降。** 证据位应检查 extent 树、分配路径与延迟分配/连续布局策略：它们支撑“区间索引与尽量连续的数据布局是互相成就的”这句判断，但不能被误读成 ext4 对任何碎片化 workload 都天然同样友好。

## 四、JBD2：崩溃一致性最怕的，不是丢一部分数据，而是没人知道系统停在了半步哪

### 1. 失败方案：直接改真实位置，断电时祈祷别停在最坏一步

如果文件系统更新元数据时只是按自己的顺序直接改真实位置，平时当然可以工作。最糟的是崩溃场景：你不知道系统到底改到了哪一步。文件大小也许已经变了，但目录项还没连好；位图可能更新了，inode 却没落地；或者数据写了一半，元数据先宣称“我已经好了”。

真正可怕的不是“没做完”，而是“没人说得清到底做了多少、下一次启动该信谁”。

### 2. JBD2 的核心，不是“多写一次”，而是先让半完成状态变得可判定

JBD2 的根本价值，不在“有日志”这三个字，而在它把一组更新先包装成一笔可识别、可提交、可重放或可丢弃的事务。这样一来，崩溃之后系统面对的就不再是混沌现场，而是一个可以判断“这笔更新到底算完成还是不算完成”的状态机。

```text
准备一组更新
  → 先把这组更新的日志信息写好
  → 形成“已提交”或“未提交”的可判定边界
  → 崩溃恢复时再决定：重放还是丢弃
```

也就是说，日志的真正价值不是把所有内容额外抄一份这么表面，而是让“半完成”变成“可以判定该怎么办”。

### 3. ordered / writeback / journal 三种模式，本质是在安全和写放大之间重新分账

一旦你接受“日志让系统更可恢复”，下一个问题就是：日志到底记到什么程度。不同模式的区别，其实就是在重写三件事的成本分配：

- 数据什么时候必须先落。
- 元数据何时宣称自己有效。
- 为了可恢复性，你愿意额外多写多少次。

所以这三种模式不是“谁先进”，而是谁在一致性保证与写放大之间取不同平衡点。

### 4. 日志也不是唯一道路，但所有道路都在解决同一个核心问题：崩溃后状态必须可判定

Soft updates 靠严格写序关系把依赖排好，LFS/F2FS 一类追加写思路则把“旧状态不改、新状态往后堆”当成另一条路。它们看起来实现完全不同，本质上却在回答同一个问题：**一旦系统在半路掉电，恢复逻辑能不能分辨哪些状态算真、哪些算废。**

这也是为什么我们在收束时不该只记 JBD2 的 API 名字，而应该记住“一致性路线的共同目标是让半完成状态可判定”。

## 五、把 `open("/data/a.txt")` 这件事重新走一遍：文件系统其实是四层接力

现在可以把整条文件系统线收回来。

应用发出 `open`，先遇到的是 VFS 统一对象模型。路径解析过程靠 dentry 把名字一步步导向 inode，inode 再把你带到真正的数据组织方式上。对 ext4 来说，大文件的块位置会尽量用 extent 这样的区间式索引去表达；一旦涉及元数据更新，JBD2 又继续保证“就算崩溃，也要让恢复逻辑知道这笔事到底算没算成”。

```text
open/read/write
  → VFS 统一接口
  → dentry 负责名字解析
  → inode 代表文件本体
  → ext4 extent 负责把数据块组织成可找的区间
  → JBD2 负责把元数据更新变成可恢复的事务
```

所以本篇最该记住的一句话是：**VFS 解决的是“怎么把不同文件系统说成一种语言”，inode/dentry 解决的是“名字与本体如何分工”，extent 解决的是“数据块怎么低成本索引”，JBD2 解决的是“崩溃后怎样还有话可说”。**

## 六、几个最容易说错的地方

### 文件名是不是就等于文件本身？

不是。名字更多落在 dentry 这一层，本体落在 inode 这一层。硬链接正是最直接的反例。

### dcache 和页缓存是不是一回事？

不是。dcache 缓存的是路径解析结果，页缓存缓存的是文件内容页。它们服务的是完全不同的成本点。

### ext4 快，是不是因为它“树结构更高级”？

不够准确。更关键的是 extent 让连续数据用区间而不是逐块指针表达，极大降低了元数据表达成本。

### 有日志，是不是就等于绝对不会丢数据？

不是。日志主要保证的是崩溃后一致性可恢复，不等于应用层所有“我以为已经持久化”的数据语义都自动成立。是否真正落盘，仍和回写、`fsync`、模式选择等边界有关。

## 收束：文件系统最聪明的地方，不是把数据放到盘上，而是把“名字、本体、布局和崩溃恢复”拆成了四层

现在回到最开始的问题：为什么一个 `open()` 能对 ext4、tmpfs、NFS 都说同一种语言？因为 Linux 并不是让所有文件系统长成一样，而是先用 VFS 发明了一套统一对象模型，再让每个后端在这套模型背后实现自己的存储与一致性策略。

这篇的开场困惑也就闭环了：应用看到的是统一文件 API，内核内部却在经历名字解析、本体定位、磁盘区间索引和崩溃一致性保障四层接力。

## 七、误解清单、证据清单与边界清单

### 误解清单

- VFS 统一的不是磁盘布局，而是面向文件操作的对象模型和操作位点。
- 文件名不等于文件本体；dentry 管的是名字映射，inode 管的是本体档案。
- dcache 不是页缓存；一个缓存路径解析结果，一个缓存文件内容页。
- ext4 的优势不只是“树结构高级”，更在于 extent 把连续数据的元数据表达压缩成区间。
- JBD2 不等于“绝对不丢数据”；它首先解决的是崩溃后状态可判定，而不是替应用自动完成全部持久化语义。

### 证据清单

- VFS 四大对象：super block、inode、dentry、file 与操作集路径，支撑“统一接口 + 各后端自填实现”的主线。
- 路径解析：dentry lookup、dcache 与 inode 定位路径，支撑“名字层”和“本体层”的分工。
- 数据组织：ext4 extent 树与分配路径，支撑“连续数据用区间表达，元数据成本更低”。
- 崩溃一致性：JBD2 事务、提交与重放/丢弃语义路径，支撑“半完成状态必须可判定”的判断。
- 跨后端统一：tmpfs/NFS/ext4 等在 VFS 对象模型上挂接的路径，支撑“统一语言不等于统一底层实现”。

### 边界清单

- 本文讨论的是 Linux 文件系统抽象与 ext4 的稳定心智模型，不把某一版结构体字段、块大小、日志布局或路径拆分写成跨版本常量。
- extent、延迟分配和连续布局策略能显著降低元数据成本，但碎片化 workload 与不同文件系统特征会改变最终收益。
- JBD2/日志模式解决的是崩溃后一致性可恢复，不自动等于应用感知上的“已经真正落盘”；回写与 `fsync` 边界仍然存在。
- dcache、页缓存、inode 与 file 属于不同层缓存/对象，不应在排障与性能分析时混成一张表。
- 下一篇会把“谁在代表文件说话”推进到“文件数据怎样真的流动起来，以及页缓存/零拷贝路径怎样介入”。
