# 虚拟化原理：为什么虚拟机不只是“被关起来的进程”，而是真的能跑另一套内核

> 主题：OS 内核｜第 17 篇
> 前置文章：`16-container-namespace-cgroup.md`、`02-paging-page-tables.md`、`03-mmap-vma-page-fault.md`
> 本篇后续：`18-ipc.md`
> 版本说明：本文讨论 x86/KVM 常见虚拟化心智模型；VMX/VMCS、EPT、IOMMU、virtio、SR-IOV 等具体细节会随处理器厂商、内核版本和设备能力变化。本文以“CPU、内存、I/O 三层如何一起假装‘客机独占硬件’”为主线，不把某代处理器的精确 VM-Exit 成本、EPT 层级细节或设备厂商特性当作跨平台常量。

## 容器已经能“像一台机器”，为什么虚拟机还需要另一整套复杂机制

上一章把容器讲透之后，一个很自然的问题就冒出来了：如果 Docker 已经能让进程看见自己的 PID、主机名、根文件系统和网卡，还能限制 CPU、内存和 I/O，那虚拟机到底还多做了什么？为什么它还需要 KVM、VMX、EPT、virtio、SR-IOV 这些听起来重得多的东西？

真正的分水岭，其实在内核这一层。容器虽然能改视角、改预算，但它和宿主共享的是同一套内核。你让容器里的进程觉得自己像 root、像 PID 1、像住在独立世界里，它仍然只是在同一套内核规则下活动。只要宿主内核出问题、被打穿、被升级，它们都一起受影响。

虚拟机不同。它不是“共享同一内核再改视角”，而是要在宿主之上真正跑起另一套内核。也就是说，现在被“骗”的不再只是一个普通进程，而是**整个客体操作系统**：它会以为自己在 ring 0、会管理“自己的物理内存”、会驱动“自己的设备”。

所以虚拟化真正困难的地方是：**CPU、内存和 I/O 都要配合演戏，而且戏还不能演穿帮。**

先记住本篇总图：

```text
CPU 层：
  客机内核看起来像在跑特权代码
  → 真正敏感动作被硬件抓出来交给 hypervisor

内存层：
  客机先把虚拟地址翻成“客物理地址”
  → 硬件再把客物理翻成宿主真物理

I/O 层：
  可以全靠 hypervisor 模拟
  也可以半虚拟化协商高效通道
  还可以把硬件虚拟功能直接交给客机
```

这一篇最关键的顿悟是：**容器骗的是进程，虚拟机骗的是整套操作系统。** 为了让客机内核也能被“骗得很自然”，CPU、页表和设备都必须增加专门的虚拟化舞台机制。

## 一、CPU 虚拟化：不是简单“让 guest 跑一跑”，而是给 CPU 增加一层“你看起来像特权，其实我还在上面盯着”

### 1. 失败方案：直接让客机内核像宿主内核一样运行在最高特权级

如果最朴素地想，既然客机要跑自己的操作系统，那不如就让它像宿主内核一样真正进入 ring 0，这样它该执行什么特权指令就执行什么。

这个方案的问题致命得几乎不需要展开：一旦客机真拥有和宿主同等的最终特权，它就不再是“客机”，而是另一套足以改硬件、改控制寄存器、改中断、改页表的宿主。虚拟化边界瞬间消失。

所以 CPU 层要解决的第一个核心问题不是“怎么跑得像内核”，而是“怎么让它觉得自己像内核，但真正最终控制权还在上层”。

### 2. VMX 的意义，不在多一个模式名，而在多一层“可被捕获的客体特权执行”

从教学上看，可以先把 VT-x / VMX 想成 CPU 新增了一套双舞台：

- 一个舞台给 hypervisor 真正控场。
- 一个舞台给 guest 看起来像在独占机器地表演。

也就是说，客体内核并不是普通用户进程那样跑在“明显较低特权”的世界里；它是在一个**看起来能执行很多特权动作、但关键动作仍会被硬件拦截回上层**的模式中运行。

这就是为什么 VMX 的本质不是“多一种特权级”，而是“多一层客体执行上下文 + 硬件可捕获的退出机制”。

### 3. VM-Exit 真正解决的是“敏感动作别悄悄做完，要在关键时刻把导演叫出来”

虚拟化最关键的桥，就是 VM-Exit。客机大多数时候可以顺畅往前跑，但一旦碰到某些敏感事件——控制寄存器、某些 I/O 指令、中断窗口、特定 MSR、EPT 违例等——CPU 不会直接放它随便做完，而是把执行权交回 hypervisor。

```text
guest 正在跑
  → 遇到某类敏感动作或异常条件
  → CPU 触发 VM-Exit
  → 回到 hypervisor 看该怎么处理
  → 处理完再 VM-Entry 回去继续演
```

所以虚拟化不是“软件偷偷模拟一切”，而是“硬件帮你在关键处吹哨，把导演叫上来”。没有这一层，hypervisor 很难既让客机自然执行，又在敏感边界上保持最终控制权。

### 4. VMCS 的价值，是让来回切换不必每次都临时到处找现场

一旦你接受“客机和 hypervisor 会频繁来回切换”，下一个问题就是：切换时谁来记住 host/guest 各自的现场？

VMCS 这类结构的意义，正是在于把 guest 与 host 的关键状态收拢成一个可管理的切换现场。这样 VM-Entry/VM-Exit 才不是“每次都靠软件手忙脚乱临时拼现场”，而是有明确舞台状态的上下文切换。

也就是说，VMCS 不是附属表格，而是这场双舞台演出能顺畅切场的脚本架。

## 二、EPT：客机以为自己管理的是物理内存，其实它管理的是“客体物理地址”

### 1. 失败方案：让 guest 页表直接指向宿主真物理地址

如果客机页表里直接记录宿主真实物理页地址，看起来似乎最省事：guest 自己做页表翻译，最后一步就直达真实内存。

但这会立刻打穿隔离边界。客机只要知道或猜到一些真实物理布局，就可能把别的虚拟机甚至宿主自己的内存页映射进来。于是“每个虚拟机好像独享一套内存”的幻觉瞬间破产。

所以内存虚拟化的核心，不是“让 guest 也能分页”，而是“让它只能管理自己那套假的物理世界”。

### 2. EPT 把“你以为的物理内存”和“真正的物理内存”拆成两层

这就是 EPT 最核心的心智模型：

- guest 先把自己的虚拟地址翻成它以为的“物理地址”，也就是客体物理地址（GPA）。
- 硬件再通过第二层页表把 GPA 翻成宿主真实物理地址（HPA）。

```text
GVA  --guest 页表-->  GPA
GPA  --EPT------->  HPA
```

所以虚拟机里的“物理地址”并不是真物理，只是 guest 自己以为的物理世界坐标。真正的底层资源分配权仍然握在 hypervisor 手里。

### 3. 两级翻译的本质，不是“多查一次表”这么简单，而是权限分离

很多人第一次接触 EPT 时，只把它理解成“再多查一级页表，所以更慢”。这当然是代价的一部分，但更重要的是它的结构意义：客机和 hypervisor 终于各管一层。

- guest 负责自己的虚拟内存语义和页表管理。
- hypervisor 负责把这些“客物理页框”真正绑到宿主物理页上。

也就是说，两级翻译的真正本质不是“多一级技术复杂度”，而是“客体的内存视图权”和“宿主的真实分配权”被彻底剥离了。

### 4. 这也解释了为什么 balloon、KSM、THP 会在虚拟化场景里重新出现

一旦 hypervisor 真正掌握 HPA 分配，它自然就会继续追问：这批真实物理页还能不能更省、更合并、更少 miss。

于是我们在前面几篇见过的内存话题又回来了：

- balloon 用来回收 guest 暂时不用的那部分。
- KSM 用来合并多个虚拟机里内容相同的页。
- THP/EPT 大页又会影响翻译效率和 TLB 行为。

这说明虚拟化不是一套与前文完全割裂的新世界，它只是在原有内存问题之上再叠了一层“guest 以为的物理世界”。

## 三、I/O 虚拟化：最贵的从来不是“发个包”本身，而是每次都让 hypervisor 做中间人

### 1. 失败方案：所有设备访问都 trap 出来，由 hypervisor 逐条模拟

全虚拟化最直观的办法就是：guest 以为自己在操作某个标准设备，实际上每次相关 I/O 都 trap 出来，让 hypervisor 解释并模拟结果。语义上很好懂，因为 guest 不需要知道自己在虚拟环境里。

可这个办法最大的痛点也很明显：每次 I/O 都把 hypervisor 拉进来做一次中转。尤其网络和块设备这种高频路径，一旦每个小动作都要 VM-Exit、模拟、再回来，开销会迅速堆高。

所以 I/O 虚拟化真正的难题不是“能不能模拟”，而是“怎么别让 hypervisor 在快路径上永远当中介”。

### 2. virtio：既然大家都知道你在虚拟化里，就别再假装这是台真设备了

virtio 的哲学非常直接：与其让 guest 继续假装自己面对一块老式真硬件，然后每次操作都 trap 出来模拟，不如双方坦白协商一种为虚拟化而设计的高效协议。

于是 guest 和 host 通过共享内存队列、kick 通知、完成中断等方式沟通。guest 不再把 I/O 动作包装成“我在真实硬件寄存器上敲了一下”，而是更诚实地说：“我把请求放进共享队列，请你按协议来取。”

```text
guest 把请求写入共享队列
  → 通知 host / vhost
  → host 处理实际 I/O
  → 完成后通知 guest
```

这就是为什么 virtio 常被称为半虚拟化：它不是在假装硬件，而是在承认彼此是虚拟化协作双方。

### 3. SR-IOV：另一条更激进的路，是让硬件自己会分身

如果说 virtio 是“坦白协商，尽量少做无谓模拟”，那 SR-IOV 更激进：它尽量让硬件自己在设备层切出多个虚拟功能，让虚拟机直接拿走其中一个接近真实设备的接口。

这样 hypervisor 在运行时快路径中的中介角色会进一步减轻，I/O 更接近裸机性能。

但代价也很真实：

- 硬件必须支持这种虚拟功能划分。
- 灵活性和热迁移能力常常受限。
- 资源数量不是无限的，VF 数目本身就是上限。

所以 SR-IOV 不是“更高级的 virtio”，而是另一种把复杂度更多前推到硬件里的权衡。

### 4. 三层路线的真正差别，不是快慢标签，而是谁来承担复杂度

可以把它们粗略理解成三条不同路线：

- 全虚拟化：guest 最无感，hypervisor 最累。
- virtio：双方协商协议，软件复杂度合理分摊。
- SR-IOV：硬件多做事，快路径最轻，但灵活性和资源弹性受约束。

这再次说明，虚拟化从来不是“有没有隔离”这一个问题，而是每一层都在权衡：为了让客机像真的，你愿意让谁承担更多模拟、翻译或硬件复杂度。

## 四、把 CPU、内存、I/O 三层收成一张图：虚拟机之所以像真机器，是因为每层都有专门的“演戏机制”

现在可以把这篇的三层线收回来。

CPU 层，VMX 让 guest 看起来像在跑特权代码，但关键动作会被硬件吹哨叫回 hypervisor；内存层，EPT 让 guest 以为自己管理“物理页”，而宿主仍牢牢掌握真物理分配；I/O 层，则在全虚拟化、virtio、SR-IOV 之间不断寻找“别让每次访问都把 hypervisor 拉来当中介”的平衡点。

```text
CPU：guest 能演内核，但敏感动作会被 VM-Exit 抓回
内存：guest 只管 GPA，hypervisor 真正掌 HPA
I/O：从软件模拟，到共享队列，再到硬件直通
```

所以本篇最该记住的一句话是：**虚拟机不是简单“共享内核的进程隔离”，而是在 CPU、页表和设备三层同时搭建出一个让另一套内核也信以为真的舞台。**

## 五、几个最容易说错的地方

### 虚拟机是不是只是“更重一点的容器”？

不是。容器共享同一套内核，只改视角和预算；虚拟机连客体内核都要真正跑起来，这要求 CPU、内存和设备层一起配合演戏。

### EPT 是不是只是“多查一级页表，所以慢一点”？

不够准确。更关键的是它把客体可管理的“物理世界”和宿主真正的物理分配权分开了。

### virtio 是不是“因为性能差才不得不加的补丁协议”？

相反，更准确地说，它是承认虚拟化现实后的一种高效协商：与其伪装成真设备，不如直接用为虚拟环境设计的队列协议。

### SR-IOV 是不是一定比 virtio 更高级？

不是。它更接近裸机，但也更依赖硬件能力、VF 数量和资源绑定，弹性与迁移能力未必更好。

## 收束：容器改的是世界观，虚拟机改的是舞台本身

现在回到开头的问题：虚拟机为什么不只是“被关起来的进程”？因为它要骗过的不只是一个进程，而是一整套客体操作系统。客体内核要相信自己在 ring 0，要相信自己管理着“物理页”，要相信自己驱动着网络和磁盘；而宿主又必须在这一切背后保留最终控制权。

这篇的开场困惑也就闭环了：容器是在同一内核里重新安排视角和预算，虚拟机则是在 CPU、内存与设备三层同时搭出一套足以承载另一内核的假舞台。
