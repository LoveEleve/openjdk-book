# 页缓存、回写、回收与 OOM：文件为什么慢一次快很多，内存不够时系统先放弃谁

## 为什么读文件第一次慢，第二次却像“白捡的一样”

同一个文件，第一次读往往明显慢；紧接着再读一次，却快得像数据早就在内存里等你。写文件也很奇怪：程序经常很快就返回了，但你心里又知道，磁盘不可能真的在那一瞬间把所有数据都稳稳写好。再往极端走，内存快耗尽时，系统有时会先回收缓存，有时会让进程卡住，有时会开始 swap，最糟时还会直接杀掉进程。

如果把这些现象拆开看，它们像五六个互不相关的子系统：页缓存、回写线程、LRU、swap、KSM、OOM Killer。但从读者视角真正需要的是一条连续主线：**文件页进来以后，系统怎样先拿它做加速，再把它当作弹药库，最后在内存压力下按层级处理它。**

先记住本篇总图：

```text
文件或 mmap 文件页第一次访问
  → 进页缓存
  → 后续读大概率直接命中内存
  → 写先改内存页并标脏
  → 回写线程择机落盘
  → 内存不足时先回收更容易放弃的页
  → 不够再换出匿名页、去重、最后 OOM
```

最关键的顿悟是：**页缓存既是加速器，也是可回收后备库。** 它让文件 IO 从“每次都碰磁盘”变成“尽量先碰内存”；而内存压力来时，系统第一时间又会想到“这些缓存里有哪些是可以先让出来的”。证据位应回到 `mm/filemap.c`、`mm/page-writeback.c`、`mm/vmscan.c`、`mm/ksm.c`、`mm/swapfile.c` 与 `mm/oom_kill.c` 一组路径：它们共同支撑“缓存、回写、回收、换出与 OOM 是一条连续压力阶梯”的主线，而不是彼此孤立的术语表。

## 一、页缓存：文件页先进内存，不是先进你的用户缓冲区

### 1. 一个最直觉但代价很高的方案

假设没有页缓存。每次 `read` 都直接向磁盘发请求，把数据读到用户缓冲区；每次 `write` 也直接同步写盘。这样语义看起来最朴素：读就是从盘读，写就是往盘写。

这个方案的问题在于，它把磁盘当成了每次 IO 的必经前台路径。只要应用重复读取同一批文件数据，你就得重复支付磁盘延迟；只要应用连续小写很多次，你就得把这些小写一笔不落地同步发给块层和设备。

这在机械盘时代非常痛，在 SSD 时代也远远不便宜。真正浪费的不是“磁盘慢”这句口号，而是：你一次次把本来可以复用、可以合并、可以延后处理的工作，硬生生放在了应用同步路径上。

### 2. 页缓存的核心，不是“多放一份副本”，而是“把文件页变成内存对象”

Linux 的做法，是把文件内容先看成一页一页的内存对象，再决定什么时候真的触碰磁盘。每个文件都会有自己的页缓存索引结构，按文件偏移把缓存页组织起来。这样，无论是 `read` 还是 `mmap` 触发的 file-backed 缺页，最终都不是直接从磁盘拿数据给调用者，而是先看看这页是否已经在页缓存里。

```text
访问文件数据
  → 先问页缓存：这个偏移对应的页在不在内存？
  → 在：直接拿内存页
  → 不在：从磁盘读入，挂进页缓存
  → 之后的再次访问：优先复用这页缓存
```

所以页缓存不是“磁盘数据的额外副本”那么简单。它实际上把文件 IO 的默认工作对象，从“磁盘扇区”换成了“内存页”。只有当页缓存缺页，或者脏页需要落盘时，系统才真正与磁盘交互。

### 3. 这也解释了为什么 `read` 和 `mmap` 文件映射会共享同一层

上一篇讲过，file-backed 缺页并不是凭空分配匿名页，而是要去接入文件内容。这里的关键就在于：这个“文件内容”并不是每个进程各有一份私有副本，而是可以共享同一层页缓存。

这意味着两件很重要的事：

- 同一文件页被反复 `read`，只要缓存还在，大概率都能复用。
- 同一文件页被映射进多个进程，也不必每个进程都重新向磁盘读一遍。

于是，页缓存成为 `read`、`write`、`mmap` 和回写之间的交汇点。没有它，上一篇里的 major fault 和本篇的文件 IO 其实是两条割裂链路；有了它，两者才合成一件事。

### 4. 预读为什么能让“顺序读看起来不像一次次随机读”

如果系统每次只在你真的读到那一页时才做 IO，顺序扫描大文件仍然会被很多次缺页或读请求打断。预读的意义，就是在看到你正在顺序前进后，提前把后面的页也拉进页缓存。

所以顺序读之所以快，不只是因为“当前页命中了缓存”，还因为内核试图把你的下一步也猜中。换句话说，页缓存不只是被动等命中，它还会主动押注：这人刚读完这一页，下一页大概率也要用。

这就是为什么顺序读的性能常常不像“重复做很多次独立 IO”，而更像“先把一串页装进内存，再在内存里流过去”。

## 二、写很快，是因为你常常只是把页写脏了，并没有立刻把盘写好

### 1. 写返回快，不代表数据已经安全落盘

很多应用第一次接触文件写时，都会默认“`write` 返回成功，数据就已经写到磁盘”。这在概念上很顺，但在实现上往往不成立。

更常见的情况是：应用把数据复制进内核维护的页缓存页，内核把这页标成脏页，然后先让应用返回。真正把脏页刷到磁盘，是之后回写线程或显式同步操作的工作。

```text
write
  → 修改页缓存里的对应页
  → 页被标记为 dirty
  → 应用可能先返回
  → 之后再由回写路径落盘
```

所以写快的根本原因，不是磁盘突然变快了，而是应用经常只是在改内存里的页缓存页。

### 2. 为什么系统宁可冒一点“断电窗口”，也要先写脏页到内存

如果每次小写都同步写盘，应用会被磁盘延迟牢牢绑在前台路径上。尤其是很多零散小写，若每次都立刻落盘，会产生大量昂贵而低效的写操作。

先写页缓存再批量回写，至少有三个收益：

- 可以把多次小写合并成更大的顺序写。
- 同一页上的重复修改只需要最终落一次盘。
- 应用前台路径更短，不必每次都等磁盘完成。

代价当然也很明确：数据在页缓存里脏着但还没落盘的这段时间，属于风险窗口。系统断电、设备掉线、某些故障场景都可能让你看到“应用早就返回成功，数据却没有真正持久化”。

这就是为什么 `fsync`、`fdatasync`、数据库 WAL 和很多持久化协议仍然如此重要。页缓存让普通写更快，但关键数据什么时候必须落盘，仍然要靠更明确的同步边界去保证。

### 3. 回写线程做的不是“把所有脏页立即清空”，而是维持节奏

如果脏页一直积累不回写，页缓存会越来越脏，最终拖垮可用内存和持久化风险。于是内核会用后台回写线程、脏页比例阈值和老化时间去维持节奏。

从教学上可以把它理解成两个水位：

- 水位还不高：后台悄悄回写，尽量不打断应用。
- 水位过高：前台写入者也可能被迫慢下来，直到部分脏页落盘。

这里最容易被低估的是：脏页不只是“还没落盘的数据”，它同时也是暂时不能像干净文件页那样随手丢弃的内存页。于是，脏页积累越多，系统手里的“便宜回收页”就越少；一边是应用还在快速写入，一边是回写跟不上，内存压力就会和持久化压力绑在一起。这样一来，问题就不再只是“磁盘慢一点”，而是“更多内存页被脏状态卡住，回收难度也上升”。

因此，写性能抖动并不只和磁盘硬件有关，还和脏页积累速度、回写速度以及阈值策略有关。很多“平时写很快，偶尔突然卡一下”的现象，本质上就是前台终于撞上了回写压力墙。

### 4. “慢读快写”其实是两套不同延迟被摆放的位置

读慢，是因为你第一次真的需要那页内容时，系统无法再拖，只能把数据拿回来。写快，是因为系统把真正的磁盘成本往后推，让应用先走。

所以文件 IO 的直观现象并不是“读天然慢、写天然快”，而是：

- 读更容易在第一次访问时把真实成本暴露出来。
- 写更容易先把成本藏在页缓存和后台回写里。

这也是为什么判断 IO 性能时，不能只看一次系统调用返回时间。你还得问：成本到底是在前台付了，还是被推迟到了后台某个时刻集中结算。

## 三、内存不够时，系统第一反应不是杀进程，而是先看哪些页最容易放弃

### 1. free 里的 cached 不是浪费，而是“最好先拿来救场的一层”

很多人看到系统空闲内存不多、cached 很大时会紧张，以为内存被浪费掉了。其实对 Linux 来说，页缓存本来就应该尽量利用空闲内存。只要这些缓存页在需要时能回收，它们就不是“僵死占用”，而是性能和弹性的双重储备。

换句话说，cached 大往往意味着系统之前把空闲内存拿去换取了文件访问性能；而一旦有新的内存需求上来，系统也会优先考虑从这些相对容易放弃的页里先腾地方。

### 2. 不是所有页都同样容易回收

内存压力下，系统最重要的判断不是“谁最老”，而是“谁放弃起来代价最低”。

文件页和匿名页在这里的命运就很不一样：

- 文件页通常有后备来源。干净文件页如果再需要，未来可以重读回来。
- 匿名页没有现成文件后备。你不能简单把一段堆数据丢了再说。

因此，在很多场景里，回收干净文件页比处理匿名页更便宜。它更像是清理一个随时可以重新借到的库存，而不是把用户现场唯一的一份草稿扔掉。

### 3. LRU 的核心不是“找最老的一页”，而是区分“可能是一过性访问”与“值得留下的页”

如果只用一条简单链表按最近最少使用回收，很容易把刚好被顺序扫描撞过一次的页误判成热点，或者把刚刚经历一次偶然访问的页留得太久。Linux 采用 active/inactive 之类的分代思路，本质上是在问：这页到底只是被碰过一次，还是已经证明自己值得继续留在内存里。

所以回收并不只是“年龄排序”，更像是一轮轮筛选：

```text
页进入回收视野
  → 先放在更容易被淘汰的一侧观察
  → 如果再次表现活跃，再提升保护级别
  → 内存压力真正来时，先从更容易放弃的一侧下手
```

这样做的目的，是降低“刚回收就又缺页回来”的抖动。如果系统刚把某页赶走，它马上又被访问，那说明先前的判断可能太激进了。对应用来说，这种现象常表现为一组页在“回收 → 再次缺页 → 再回收”之间来回震荡，CPU 花在回收和重建上的时间越来越多，真正业务反而跑不动。也正因此，回收策略不只是省内存，它还在努力避免把系统拖进 refault 风暴。

### 4. kswapd 和 direct reclaim 的差别，是“后台打扫”和“前台自己动手”

当水位开始下降，后台回收线程会先尝试异步把系统拉回安全区。这时应用不一定立刻感觉到疼。

但如果前台分配已经冲到更危险的位置，应用线程自己也可能被卷进回收路径，被迫停下来等系统先腾出足够页。这就是为什么有些内存压力问题会表现成请求突然卡住，而不是 CPU 满或 IO 满——线程可能不是在干业务，而是在替系统收拾房间。

所以“内存不够”不是一个单点事件，而是一条从后台预警到前台阻塞的压力阶梯。

## 四、除了回收，还有两种更激进的腾挪：KSM 和 swap

### 1. KSM：不是把页扔掉，而是先看看能不能合并同款

如果很多匿名页内容其实完全一样，例如同源虚拟机、大量重复库页或某些模板化用户态内容，系统还可以尝试先不回收、不换出，而是把相同内容合并成一份共享页，等未来谁写了再借 COW 分开。

这就是 KSM 的直觉：**既然内容一样，先别放这么多份。**

但它也不是免费午餐。你得扫描、比较页内容，还要承担未来写入时再次触发 COW 裂开的成本。所以 KSM 更适合“重复内容多、内存贵、额外 CPU 扫描值得”的场景，比如部分虚拟化环境，而不是所有普通业务默认都值得开。

### 2. swap：文件页能丢，匿名页不能凭空蒸发

当真正需要处理匿名页时，系统不能像处理干净文件页那样“先扔了再说”。因为匿名页往往没有可重读的原始后备。于是，系统需要一个更慢但能保命的后备去处：swap。

swap 的本质，不是“让内存变大”，而是“给匿名页一个临时的磁盘后备位置”。回收时把匿名页内容写出去，页表里留下足够让未来能找回它的信息；将来再次访问时，再触发缺页，把它读回来。

这意味着匿名页换出至少包含两笔潜在成本：

- 换出时要写。
- 换入时还要再读。

所以 swap 从来都不是优选路径，而是“文件页先不够用、匿名页又不能直接扔”时的保命后备。也正因为如此，很多延迟敏感系统会把 swappiness 压低，宁可多扔文件页，也不想把热匿名页频繁换进换出。

### 3. 为什么数据库常说“宁可回收文件页，也别把匿名工作集换出去”

数据库、缓存和内存型服务的匿名页，常常就是业务真正的热工作集。如果这些页被换出去，下一次访问它们时要付出的不是“读一份公共文件页回来”那么简单，而是整个业务现场被迫等随机 IO。

相比之下，文件页哪怕被回收，很多时候也只是未来多一次可预期的重读。因此，在这类负载里，swap 的代价往往比丢文件缓存更伤吞吐和尾延迟。

这也是为什么“有没有 swap”不该只用道德化口号来讨论，而应该问：你的匿名页到底是不是值得不惜代价也要尽量留在内存里。

## 五、最后一层：如果回收、合并、换出都不够，只能选一个进程牺牲

### 1. OOM 不是内核脾气差，而是承诺已经兑不出来了

当系统已经尝试过回收页缓存、后台和前台回收、必要时合并或换出匿名页，仍然拿不出足够物理页满足新的关键分配，请求又不能无限等待时，内核就只剩下最难看但最直接的手段：杀掉某个进程，释放它占用的资源。

所以 OOM 的本质不是“内核突然决定惩罚谁”，而是“先前所有承诺累积到这一刻，终于已经无法继续兑现”。

### 2. “杀谁”并不是随机的

OOM Killer 不是完全随机挑倒霉蛋。它会尽量评估：杀掉谁，最可能尽快回收出足够多的内存，同时代价相对可接受。

从直觉上看，以下因素通常很重要：

- 它当前实际占了多少可回收的内存。
- 它是不是被人为标记成更该活下来，或更该被优先牺牲。
- 杀掉它后，能不能真正释放出一大块压力，而不是杀了也没用。

这就是为什么 `/proc/PID/oom_score` 和 `oom_score_adj` 这种接口会存在。它们不是装饰，而是在告诉内核：这家伙如果必须牺牲，该排在多前或多后。

### 3. `oom_score_adj=-1000` 这类配置，本质上是在重新声明谁最不能死

对数据库、监控、协调器这类核心进程来说，“被系统随手杀掉”可能意味着更大的服务级事故。所以很多系统会明确下调它们的 OOM 分值，甚至设置到几乎不作为候选。

但这不代表问题消失了。你只是把风险重新分配给了别的进程。若系统整体承诺和工作集管理失控，总得有人为兑现失败买单。OOM 调优从来不是“让所有人都不被杀”，而是“决定最坏时先放弃谁”。

## 六、把文件页的一生串起来：从加速资产，到救火物资，到牺牲品筛选

现在可以把这一篇的所有角色放回同一条链上。

一次文件访问第一次发生时，数据常常先进入页缓存。之后的重复读取不必再走磁盘，写入也往往先落到页缓存页并标脏。回写线程再在合适时机把这些脏页真正推向磁盘，于是应用看到的是“写先返回，盘后补账”。

当内存开始紧张，系统先尝试回收更容易放弃的页，尤其是那些有后备、干净、重读代价可接受的文件页。若压力继续上升，它再通过更积极的手段压榨空间：观察冷热、后台回收、前台 direct reclaim、必要时 KSM 去重、swap 换出匿名页。只有这些路都不足以继续兑现内存承诺时，OOM 才作为最后一刀出现。

```text
文件页进来
  → 页缓存命中带来“第一次慢、之后快”
  → 写先把页弄脏，后台再回写
  → 内存不够时优先看哪些页最容易放弃
  → 不够再更激进：合并、换出、最后杀进程
```

因此，这篇最重要的总图不是某个结构体字段，而是这一句：**页缓存把文件 IO 变成了先用内存协调、再与磁盘结算的系统；而内存压力处理，则是在决定哪一批“先放在内存里协调”的内容现在必须让路。**

## 七、几个最容易说错的地方

### cached 很大，是不是说明内存被白白浪费了？

不是。很多 cached 本来就是为了把文件访问加速到内存级别准备的；只要它们在需要时可回收，就既是性能收益，也是弹性储备。线上排查时也不要只盯着 `free` 里那一列数字，而要连着看 `available`、`/proc/meminfo` 里的 `Cached`、`Dirty`、`Writeback`，再结合 `vmstat` 里的回收与换入换出迹象。真正该警惕的不是“cached 大”，而是“cached 里脏页很多、available 已经很低、回收和回写都在吃力”。

### `write` 返回成功，是不是说明数据已经稳稳在盘上了？

也不是。很多时候你只是把页缓存页写脏了，真正的落盘还要等后台回写或显式同步边界。

### swap 是不是把系统内存“扩容”了？

更准确地说，它给匿名页提供了更慢的后备位置，而不是让原本热的工作集凭空变快。换出换入都是真实成本，尤其对延迟敏感业务来说代价很重。

### OOM 是不是因为内核太激进地回收缓存？

不一定。OOM 更常见的根因，是整体承诺与可兑现资源长期失衡，或关键工作集与回收/换出策略不匹配。回收缓存只是前面更温和的一层，不是 OOM 的充分解释。

## 收束：`free` 看到的 cached，不只是“占着不用”的内存

现在回到开头那两个最常见的现象：为什么读同一个文件第二次快很多？为什么写看起来很快却又不一定立刻安全？答案都落在同一个地方——页缓存让文件页先变成内存对象，再决定什么时候真正与磁盘结算。

这也解释了为什么 cached 内存一方面是性能资产，一方面又是内存压力下最先被盯上的资源。它既能让你少碰磁盘，也意味着它在必要时可以被拿来救急。只有当这层余地被用尽，系统才会一路走向更昂贵的手段：更激进回收、swap、甚至 OOM。

所以这篇的开场困惑已经闭环：文件 IO 看上去“慢一次快很多”，不是磁盘忽然学会记忆，而是内核把文件页先养在了内存里；而内存不够时，内核也不会立刻暴怒杀进程，它会先沿着一整条越来越痛的阶梯，把还能挪、还能丢、还能换的东西处理一遍，最后才决定牺牲谁。

## 八、误解清单、证据清单与边界清单

### 误解清单

- cached 大不等于内存被白白浪费；页缓存本来就是性能资产，也是最先考虑回收的一层弹药库。
- `write` 返回成功不等于数据已经稳定落盘；很多时候只是页缓存页变脏了。
- `mmap`/`read`/page cache 不是几条互不相干的链路；它们在文件页与缺页路径上本就汇合。
- swap 不是免费扩容；它只是给匿名页提供更慢的后备位置。
- OOM 不是内核随手发脾气；它是前面缓存回收、回写、换出和更激进腾挪都不够后的最后手段。

### 证据清单

- 页缓存主线：`mm/filemap.c` 与文件页 fault/缓存命中路径，支撑“文件页先进页缓存，再决定何时碰磁盘”。
- 脏页与回写：`mm/page-writeback.c` 与回写线程/脏页阈值路径，支撑“写先标脏、后端再批量结算”。
- 回收：`mm/vmscan.c`、active/inactive/LRU 一类路径，支撑“先从更容易放弃的页下手”的事实。
- 激进腾挪：`mm/ksm.c`、swap 路径与匿名页换出逻辑，支撑“KSM 合并”和“匿名页不能像干净文件页那样直接丢弃”。
- OOM：`mm/oom_kill.c` 与评分/牺牲者选择路径，支撑“最后才杀进程，而不是一开始就动刀”。

### 边界清单

- 本文讲的是 Linux 页缓存、回写、回收与 OOM 的稳定心智模型，不把某一版 folio、LRU 世代、swap 或 OOM 评分细节写成长期契约。
- 文件页、匿名页、KSM、swap 与 OOM 的交互会受文件系统、块设备、内核版本、容器/cgroup 配置和工作负载形态显著影响。
- “先回收缓存、后考虑匿名页/换出/杀进程”是主线，不是每次都严格按同一可视化顺序发生的单一流水线。
- `fsync`、数据库 WAL、脏页阈值和写回节奏共同决定持久化体感；不能只看一次系统调用返回时间做结论。
- 下一篇将把视角从单核内存生命周期推进到多核缓存一致性，重点不再是“页去哪了”，而是“多个核同时碰一条缓存行会发生什么”。
