# 中断、softirq、tasklet 与 workqueue：谁有权让正在运行的代码立刻停下

> 主题：OS 内核｜第 9 篇
> 前置文章：`08-rcu-deadlock.md`
> 本篇后续：`10-cfs-scheduler.md`
> 版本说明：本文讨论 Linux/x86 上稳定的中断与延迟处理心智模型；IDT/APIC 细节、softirq/tasklet/workqueue 的实现边界、tickless 与 hrtimer 行为会随内核版本、架构、驱动模型和配置变化。本文以“打断链路与分工”为主线，不把某一版汇编入口、具体向量号布局或软中断实现细节当作跨版本契约。

## 网卡来了一个包，凭什么能让 CPU 立刻放下你手头的代码

到前一篇为止，我们一直在讲“多个执行体怎样协调访问共享数据”：锁、RCU、per-CPU、活锁、死锁，主角始终是多个并发主体之间怎么别把彼此搞坏。

这一篇把问题换了个方向：不是“大家怎么协调”，而是“谁有权打断你”。因为内核世界并不总允许一段代码悠闲地把自己跑完。网卡收到包、磁盘完成 DMA、定时器到期、APIC 发来时钟信号，这些事情不会先礼貌地问一句“现在方便吗”。它们可以在 CPU 正在执行别的路径时，强行插进来。

这就是中断最容易被低估的地方：**它不是普通函数调用，而是一种硬件级插队权。** CPU 不需要先同意，也没法说“我先忙完这段再理你”。

可如果每次中断都把所有活一次做完，系统又会立刻出现另一个麻烦：别的中断怎么办？当前进程还能不能继续？时钟滴答还能不能按时来？于是中断处理很快就逼出第二个核心问题：**插队之后，哪些事必须立刻做，哪些事应该延后做。**

先记住本篇总图：

```text
设备发出中断请求
  → 中断控制器把请求路由给某个 CPU
  → CPU 暂停当前执行，切到中断入口
  → 极短的上半部先收尾、确认、挂后续工作
  → 复杂工作转交下半部
  → 时钟中断又继续驱动 jiffies、hrtimer 和调度节拍
```

这一篇最关键的顿悟是：**中断处理的真正难点，不是“怎么打断”，而是“打断后哪些事绝不能拖，哪些事绝不能现在做”。**

## 一、先问最本质的问题：中断为什么不是普通回调，而是硬件对 CPU 的强制插队

### 1. 失败方案：设备有事时，CPU 自己轮询去问

最直觉的替代方案是轮询。CPU 隔一段时间就去问网卡、磁盘、定时器：“你们有新情况吗？”这样确实不用被打断，控制流也看起来更规整。

但轮询的问题是，你要么问得很勤，白白浪费大量 CPU；要么问得不勤，事件已经发生了却迟迟不能响应。对于低延迟设备事件，这两头都很糟。

于是中断出现的原因很朴素：当外设准备好了，就由它主动举手，告诉 CPU“现在轮到你理我”。CPU 不必一直盯着设备，设备也不用傻等下一轮被轮询。

### 2. 从设备到 CPU，中断是一条硬件通知链

从教学上看，可以先把这条链简化成：设备发出 IRQ，请求经中断控制器路由，最终落到某个 CPU。CPU 接到这个外部事件后，会暂停当前正常执行流，保存必要上下文，切入中断入口，再由内核根据中断向量找到对应处理逻辑。

```text
设备事件发生
  → 触发中断请求
  → 中断控制器决定送给哪颗 CPU
  → CPU 暂停当前上下文
  → 根据中断向量查找入口
  → 进入 ISR
```

所以中断的本质不是“某段代码想调用另一段代码”，而是“硬件世界要求 CPU 暂时换话题”。

### 3. 为什么中断门通常要先把同级普通中断挡在外面

如果 ISR 执行过程中，同级中断还可以层层嵌套地冲进来，那么递归深度、共享状态和栈压力都会迅速变得危险。于是中断入口常常会先建立一种非常保守的局部秩序：至少别让同类普通中断无限套娃。

这也是为什么读者会在很多解释里看到“中断期间会暂时屏蔽某些中断”这样的说法。它并不是在追求完美静态世界，而是在保护一件更现实的事：当前这个紧急插队别再被同类插队堆爆。

当然，这不等于系统进入了绝对原子区间。像 NMI 这种更高优先级、不可屏蔽的信号，仍可能继续打进来。也正因此，中断处理从来不是“现在世界彻底静止”，而只是“在尽量受控的插队条件下完成必要动作”。

## 二、ISR 为什么必须极短：中断真正可怕的不是打断，而是你被打断后赖着不走

### 1. 失败方案：既然都进了中断，那就干脆把所有活都做完

这是很多人第一次理解中断时最自然的想法：设备都打断我了，那我就顺势把整个工作流程一次处理到底，不用再拆来拆去。

问题在于，中断上下文不是普通工作线程。你在这里待得越久，当前 CPU 能正常响应别的事情的能力就越差；别的设备中断可能积压，时钟节拍可能延后，更别说很多中断上下文里根本不允许睡眠。

所以“都进来了就一口气做完”看似省事，实际上是在拿整个系统的响应性做赌注。

### 2. 上半部的职责，不是把事情做完，而是先把现场控制住

中断上半部，也就是通常说的 ISR，最重要的不是“完成业务逻辑”，而是“立刻做那些绝不能拖的最小动作”。比如确认中断源、做最必要的设备应答、把后续工作挂出去、避免中断风暴反复冲进来。

它更像是在说：

- 我知道这事来了。
- 我先把门口秩序稳住。
- 真正耗时的处理稍后再说。

所以 ISR 的核心价值是快速收尾和快速转交，而不是重活全吞。

### 3. ISR 里为什么通常不能睡眠

一旦你接受“中断是强制插队”，就能理解 ISR 里为什么对睡眠这么敏感。当前这条路径不是按进程语义、调度语义和普通线程栈语义慢慢推进的；它是被硬件临时拉出来救火的。

如果在这种上下文里随便睡下去，很多前提都会断裂：当前上下文并不是一个准备好在这里长期等待资源的普通线程；你也无法保证这条路径对应的共享状态、抢占计数和中断屏蔽状态还能让系统保持整洁。

最典型的失败场景是：ISR 里为了等某个资源，试图去拿一把可能睡眠的 mutex。这样一来，当前 CPU 一边还停留在“中断插队”的上下文里，一边却想走“普通任务排队睡眠”的语义路径。结果往往不是简单地等一会儿，而是直接破坏上下文假设：调度器和锁都默认这是一个能正常睡下去、将来再被唤醒的任务，但中断处理并不是这样设计出来的。也正因此，内核会把“在中断上下文里睡眠”视为硬错误，而不是仅仅“不推荐”。

所以“ISR 不能睡眠”不是风格约束，而是上下文性质决定的底线。

### 4. 中断处理最重要的工程原则：先恢复系统响应，再完成剩余业务

这句话几乎可以概括上下半部设计的全部哲学。你可以把 ISR 想成急诊分诊台：先登记、止血、挂号，真正复杂的治疗别堵在门口做。因为中断真正怕的不是“第一步慢一点”，而是“你一直占着门不让别人进”。

## 三、下半部：既然上半部不能久留，那剩下的活谁来做

### 1. 下半部不是一种实现，而是一类延后处理思想

上半部既然必须短，那很多真正耗时的处理自然要被推迟出去。这个“推迟出去”就是下半部思想的起点。

它并不是某一个固定 API，而是一类问题的共同答案：**这事和当前中断有关，但不必堵在中断最敏感的那一小段里完成。**

### 2. softirq：高频热点的快路径，但它快是拿语义舒适度换来的

softirq 适合高频、核心、需要很低额外调度成本的延后工作。网络收发这类热点就是典型。它的强项是快，但代价是执行约束也严：通常仍不能随便睡眠，且并发和重入语义都更硬核。

也就是说，softirq 不是“方便的延后工作线程”，而是“已经离开最短 ISR，但仍然属于高性能、低容忍度处理地带”的机制。

这也是为什么 RCU 回调会与它产生联系：两者都在利用一种“已经不在最前线 ISR 里，但又不想完全变成普通进程上下文”的中间地带。

### 3. tasklet：把并发危险收一点，但能力边界也跟着收窄

tasklet 的出现，可以先把它理解成对 softirq 使用复杂度的一种缓和。它保留了“延后到下半部做”的思路，但让同一个 tasklet 实例在并发执行语义上更可控，减少调用者自己承担的一部分并发负担。

代价是它并没有把你送回“普通线程世界”。换句话说，它比直接玩 softirq 好懂一点，但它也不是一个可以随心所欲阻塞和睡眠的普通工作线程。

### 4. workqueue：真正把事交给可睡眠的内核线程去慢慢做

如果剩下的工作真的会阻塞、会等资源、会花较长时间，那你就需要一种更“正常”的执行环境。这就是 workqueue 的价值：把工作排到内核线程上下文里去跑，让它拥有普通可睡眠任务的大部分待遇。

```text
ISR 先收尾
  → 若后续工作很轻且高频：偏向 softirq
  → 若希望更受控的延后执行：可用 tasklet 思路
  → 若后续工作会阻塞或较耗时：交给 workqueue
```

所以三种下半部的差别，本质上不是名字不同，而是：**你希望这件事继续留在“高性能但约束严”的世界，还是彻底下放到“慢一点但能睡”的世界。**

### 5. 选择下半部，本质上是在做“频率 × 耗时 × 可睡眠性”的乘法

中断后续处理到底选哪条路，最终还是得落到三个问题：

- 这事发生得有多频繁？
- 这活本身有多长？
- 它会不会阻塞、能不能睡？

高频、短、不能睡，越偏向轻量下半部；耗时、低频、需要阻塞，越应该往 workqueue 或其他线程化路径走。这个选择不是 API 偏好，而是响应性预算分配。

这里还要避免一个常见误解：tasklet、softirq、workqueue 不是单纯按“新旧版本”或“高级低级”排队的替代关系。它们真正分开的，是执行环境承诺。softirq 更像留在中断敏感地带继续冲刺，tasklet 则在这个地带上给你一点更收敛的并发语义，而 workqueue 是彻底切回普通线程世界，用更高延迟换可睡眠与更完整的调度语义。若只把它们看成三套名字不同的延迟队列，就会在最关键的“能不能阻塞、会不会拖住 CPU 响应”上选错工具。

## 四、时间管理：时钟中断不是“顺便报个时”，而是内核节拍的脉搏

### 1. 如果没有时钟中断，内核就很难知道“该轮到谁了”

到这里，我们已经能理解设备中断为何必须打断 CPU。但内核还有一类特别重要的中断，不是某个网卡或磁盘的专属事件，而是整个系统的节拍来源：时钟中断。

没有这类节拍，很多事情都失去统一参照：超时怎么推进，睡眠多久才该醒，调度器多久评估一次当前任务是否该让位，定时器何时触发。也就是说，时间管理不是“附属功能”，而是整个内核行为节奏的心跳。

### 2. jiffies：足够便宜的粗粒度全局滴答

jiffies 的价值在于简单粗暴：每来一次周期性时钟中断，全局节拍往前走一点。很多“知道大概多久了就够”的判断，并不需要纳秒级精度，只需要一个稳定推进的粗粒度时钟源。

所以 jiffies 不是“落后的老办法”，而是一种很省的公共时基。只要场景对精度要求不高，它依然非常实用。

### 3. hrtimer：当你不能接受“差几毫秒也无所谓”时

有些超时和定时场景不能靠粗滴答糊过去，比如更精细的定时唤醒、某些高精度事件调度。这时就需要 hrtimer 一类更高精度的时间管理机制。

它的意义不在于“更现代”，而在于它承认了一件事：不是所有时间问题都配用粗粒度节拍解决。越精细的时间语义，越需要更贵的管理结构和更精密的到期控制。

### 4. tickless：空闲时别为了“我还活着”而不停自我打断

还有另一种很有代表性的优化方向：当 CPU 根本空闲着时，为什么还要机械地周期性打断它，只为了让 jiffies 再走一下？如果近期没有别的定时事件，那这种固定节拍其实是在纯粹浪费能耗。

tickless 的核心就在这里：没必要一直按固定拍子敲鼓时，就让系统静下来，等真正有下一次到期事件时再唤醒。它不是改变时间语义，而是在空闲场景下减少不必要的“为了维持节拍而打断自己”。

### 5. 这也把下一篇调度器自然接了出来

因为只要谈到时钟节拍、到期事件和周期性中断，你就已经半只脚踏进调度器世界了。定时器中断不只是让内核知道“过了多久”，它还常常是调度器做时间片评估、推进 vruntime、触发重新决策的重要脉搏。

一个最直观的例子是：你有一个纯 CPU-bound 的进程，自己从不主动睡眠、也不做 IO。它之所以不会永远霸占 CPU，靠的并不是它自己突然良心发现，而是周期性的时钟事件不断给内核一个“现在该重新看看你是不是该让位了”的机会。也就是说，调度器之所以能定期夺回控制权，不只是因为它聪明，而是因为时钟中断一直在敲门。

所以时间管理这一节的意义，不是单独科普几个计时器名字，而是为下一篇回答“中断把当前执行打断之后，接下来该选谁跑”铺路。

## 五、把整条中断旅程收起来：从强制插队，到分层收尾，到系统节拍

现在可以把这篇的角色重新放回一条完整链路里。

设备事件发生后，硬件通过中断机制把请求路由给某颗 CPU。CPU 暂停当前执行流，切入中断入口。ISR 先做最小而必需的收尾动作，因为它必须尽快把系统从“被强制插队”的最敏感状态里拉出来。随后，较重的处理按频率、耗时和可睡眠性分流到不同下半部。与此同时，时钟中断则构成整个系统的公共节拍：有的场景用 jiffies 这样的粗滴答就够，有的要靠 hrtimer 提供更细控制，空闲时还会进一步走向 tickless 以减少无意义打断。

```text
硬件事件
  → 中断请求路由到 CPU
  → CPU 保存现场并切入 ISR
  → ISR 极短收尾
  → 后续工作分流到合适下半部
  → 时钟中断继续驱动全局时间与后续调度脉搏
```

所以本篇最该记住的一句话是：**中断系统真正高明的地方，不是“能打断 CPU”，而是“打断之后能迅速把紧急和不紧急的活重新分层”。**

## 六、几个最容易说错的地方

### 中断是不是就等于“立刻把所有相关工作都做完”？

不是。恰恰相反，真正好的 ISR 往往是尽快做完最必要的动作，然后把能延后的活交给下半部。

### 下半部是不是只是“晚一点执行”，所以三种机制差别不大？

也不是。它们最大的差别在于执行环境约束：是否高频、是否允许睡眠、并发语义是否复杂，这些都直接决定你该把活放到哪里。

### workqueue 是不是“更高级的 softirq”？

不够准确。它更像是“把工作交回可睡眠线程上下文”，代价和能力边界都与 softirq 不一样，不是简单高低级关系。

### 时钟中断是不是只是给 `time()` 提供数据？

远不止。它还是超时、唤醒、定时器到期以及后续调度决策的重要节拍来源。

## 收束：中断不是单纯的打断机制，它其实在重新安排全系统的优先级

现在回到开头那个问题：网卡到了一个包，凭什么能让 CPU 立刻放下你手头的代码？因为中断本质上就是硬件在告诉 CPU：现在有比你当前顺序执行更优先的事。可真正成熟的设计并不止于“打断”，而在于打断之后立刻重新分层：最紧急的先做，不能久留的马上转交，需要睡眠的交给线程化路径，时间节拍则继续为整个系统维持统一脉搏。

这篇的开场困惑也就闭环了：CPU 并不是总能把当前代码安安静静跑完；中断随时可能插队。而内核真正的本事，不只是接受插队，而是把插队后的善后工作组织成一套既保响应、又不把系统拖死的分工体系。
