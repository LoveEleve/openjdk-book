# 物理内存管理：Buddy、SLUB、NUMA 与 memblock 如何分工

> 主题：OS 内核｜第 1 篇
> 前置文章：无
> 本篇后续：`02-paging-page-tables.md`
> 版本说明：本文讨论 Linux 内核中稳定的物理内存管理模型；具体 zone、order 上限、SLUB 调试选项和架构行为会随内核版本、配置及硬件变化。文中的源码入口以 `mm/page_alloc.c`、`mm/slub.c`、`mm/memblock.c` 和 `include/linux/mmzone.h` 等为导航，不把未在当前工作树重新核验的行号当作版本契约。

## 开机以后，内核到底拿什么分配内存

一个进程调用 `malloc` 时，通常不会想到物理内存。它只看到一段可以读写的地址；地址背后是哪一根内存条、哪一个 NUMA 节点、哪一组物理页，似乎都被操作系统藏起来了。

但内核没有这个奢侈。驱动需要连续的页，文件系统需要缓存 inode，网络栈需要不断创建和销毁小对象，启动阶段还没有完整的内存管理系统，却已经要建立页表和保留内核镜像。它必须同时回答四个问题：

- 一次需要几页时，怎样从已经被切碎的物理内存中找到合适的块？
- 一个对象只有几十或几百字节时，怎样避免为它浪费整页？
- 多个 CPU 各自靠近不同内存时，怎样避免每次都从“最远的仓库”取货？
- Buddy 还没启动时，启动代码又向谁申请内存？

如果只用一种分配器回答所有问题，答案很快会变得笨重：它要么不擅长连续大块，要么浪费小对象的空间，要么在多核下争抢全局锁，要么根本无法覆盖启动早期。

Linux 的办法不是寻找一个万能分配器，而是把问题拆开：

```text
启动早期：memblock 先登记和分配
        ↓ 交接给
运行期页块：Buddy 管理 2^order 个物理页
        ↓ 提供页组
内核对象：SLAB/SLUB 把页组切成固定大小的对象槽
        ↑
分配决策：NUMA node / zone 选择“从哪里取”
```

这四个名字不是四个并列的“内存池”。它们处在不同层次：memblock 解决时间问题，Buddy 解决页块问题，SLUB 解决对象问题，NUMA 和 zone 解决位置与用途问题。先把这张分工图记住，后面每一段都只是在回答其中一个问题。

## 一、先解决大块：为什么 Buddy 不直接支持任意页数

### 1. 一个看似简单的方案

假设上层需求分别是 1 页、约 3 页和 64 页。这里要先把接口边界说清楚：Buddy 的页分配接口按 `order` 请求 `2^order` 页，并不直接接受“3 页”这种任意数量。于是，约 3 页的需求通常要按 order 2 申请一个 4 页块，再由上层决定如何使用多出来的页。最直接的替代方案，是维护一张可以接受任意长度的空闲区间表：每次扫描表，找到长度足够的连续区间，分配后把区间切开；释放时，再把相邻区间合并。

这个方案在纸面上很直观，真正运行起来却有两个麻烦。

第一，找到“足够大”的区间需要搜索。空闲区间越多，搜索越可能碰到长链表和复杂的合并逻辑。第二，任意大小的切分会留下很多不同尺寸的洞。即使总空闲量足够，也可能没有一段连续空间能满足大请求，这就是外部碎片。

内核需要的不是“所有大小都精确满足”，而是一个可以快速定位、又能长期恢复大块的规则。Buddy 的规则很克制：页块只按 2 的幂组织。

### 2. 只允许 2 的幂，反而更容易管理

把一个物理区域看成一棵二叉拆分树。树根是一块较大的连续区域；每次拆分，都把它分成两个同样大小的孩子。树的每个节点都有一个 order，表示它包含多少页的对数。

```text
order 3：一块 8 页
        ├── order 2：低地址的 4 页
        └── order 2：高地址的 4 页
                         ├── order 1：2 页
                         └── order 1：2 页
```

当上层需要约 3 页时，调用者先把需求向上取整为 order 2，也就是 4 页；Buddy 不会制造一个“3 页节点”。如果当前只有 order 3 的 8 页块，分配器先把它拆成两个 order 2 的 4 页块，返回其中一个，另一个回到 order 2 的空闲列表。释放时，如果这另一半也空闲，两块就可以重新合成 order 3，再继续向上合并。

例如，一个 order 3 的块要降到 order 0，必须经历 3 层分裂：order 3→2、order 2→1、order 1→0。每层都会把当前高阶块拆成一对低一阶 buddy，并把未返回的一半挂入对应的低阶 `free_area`；因此这不是“只改一个链表”的操作，而是沿途取出高阶块、逐层登记剩余半块，最后才把 order 0 的块交给调用者。

这个选择带来一个重要性质：一个 order 相同的块，只有一个可能的 buddy。它们的边界由块大小决定，不需要在所有空闲块中搜索“谁和我相邻”。Linux 的 `__find_buddy_pfn` 用页帧号和 order 对应的位做异或，计算出候选伙伴；`mm/page_alloc.c` 中的分配和释放路径再检查该伙伴是否真的空闲。

```text
请求 order n 的块
  → 从 order n 或更大的空闲列表取块
  → 若取到更大块：反复二分
  → 一半满足当前请求
  → 另一半进入更小 order 的空闲列表

释放 order n 的块
  → 计算同 order 的唯一 buddy
  → buddy 不空闲：当前块挂回 order n
  → buddy 空闲：摘下 buddy，合并为 order n+1
  → 继续向上检查
```

代码在这里的作用只是证明两件事：分裂会把未使用的一半重新放回更小阶的列表；释放会沿着 buddy 关系向上合并。真正需要记住的不是某个函数的局部写法，而是“分裂和合并互为逆操作”。

### 3. `free_area` 把查找范围缩小到一个格子

Buddy 不会把所有空闲块放进一条总链表。每个 zone 都按 order 维护空闲区域；源码中的 `struct free_area` 记录某个 order 下的空闲链表以及空闲块数量。实际内核还会按照迁移类型分开组织这些链表。

所以一次查找不是“扫描全部空闲内存”，而更接近：

```text
目标 zone
  → 目标 order
    → 目标 migratetype
      → 取对应 free_list 中的块
```

如果目标 order 没有空闲块，`__rmqueue_smallest` 会向更大的 order 寻找。以 order 3 的块满足 order 0 为例：它先从 order 3 的链表摘下一个块，把剩余的一半挂入 order 2；再把待分配的一半拆成两个 order 1，把剩余的一半挂入 order 1；最后拆成两个 order 0，把剩余的一半挂入 order 0。这里发生的是多个 order 的 `free_area` 状态变化，而不是只在目标链表里做一次摘取。若目标迁移类型也没有合适块，fallback 路径才会考虑跨类型借用。这个过程解释了为什么 Buddy 能在碎片化环境中保持相对稳定的管理成本：它牺牲了任意尺寸的精确性，换来了有界的组织规则。

### 4. “2 的幂”并没有消灭所有碎片

Buddy 主要治理外部碎片，但它也会产生内部浪费。请求 3 页，实际可能拿到 4 页；请求一个不适合页块粒度的区域，也会出现未使用空间。这个代价是明确的：用一点空间浪费，换取连续块的可恢复性和伙伴定位的简单性。

还有一种更棘手的情况：某些页不能移动。假设一个不可移动的内核页恰好钉在一大片物理内存中间，即使两侧有大量可移动页，系统也无法把它们重新拼成连续的大块。于是 Buddy 还需要知道“这块空闲空间未来能不能被移动”。

### 5. 迁移类型：不要让不可移动页把大块钉死

从源码行为看，Linux 会把空闲页按迁移类型分别组织，并在分配时优先尝试与请求匹配的类型；常见类别包括不可移动、可回收和可移动，具体类别和配置会随版本变化。基于这种行为，可以把它理解为一种减少碎片的策略：把可能长期固定的页尽量放在一起，把能够迁移或回收的页留出规整空间。这里的“减少”是设计效果的解释，不是源码对任何 workload 的保证。

```text
MIGRATE_UNMOVABLE    内核核心数据、部分内核栈和页表
MIGRATE_RECLAIMABLE  可以通过回收释放的对象或缓存
MIGRATE_MOVABLE      可以迁移的用户页等

分配：优先从请求对应的类型取
借用：目标类型耗尽后才跨类型取
后果：借用会降低后续内存规整的纯度
```

这是一个设计取舍，而不是绝对隔离。严格隔离会导致某类列表明明有空间却无法使用；允许借用则会让未来的 compaction 更困难。更准确地说，源码体现的是“优先按类型取、必要时再退让”的策略，而“这样更有利于后续规整”是对这套策略的设计解释。透明大页等需要大块连续内存的场景，通常正依赖这种可移动页更容易被聚拢的性质。

### 6. order 0 的热路径为什么还要有 PCP

即使 Buddy 的查找规则清晰，每次申请一页都访问 zone 的全局空闲链表，仍然会让多核系统频繁竞争 zone 锁。普通用户页和许多短生命周期分配都集中在最小阶，没必要让每一次小请求都触碰全局结构。

因此 Linux 还在 Buddy 之上放了 per-CPU pageset，也常简称 PCP。每个 CPU 暂存一批小页：

```text
申请单页
  → 当前 CPU 的 PCP 有页：直接取
  → PCP 为空：批量从 zone/Buddy 搬一批到本地
  → 后续请求：继续从本地取

释放单页
  → 先放入当前 CPU 的 PCP
  → 数量达到阈值：批量归还 Buddy
```

PCP 没有改变 Buddy 的所有权模型，它只是把大量细小操作批处理，减少全局锁和链表操作的频率。批量大小、high/low 水位和是否触发回收都由内核根据 zone 和配置决定，不能把某个版本中的固定数字当成普遍规律。

到这里，Buddy 已经能回答“大块页从哪里来”。但它不适合直接回答“一个几十字节的内核对象从哪里来”。如果让每个对象单独占一页，下一节的问题就会出现。

## 二、再解决小对象：为什么 Buddy 不能直接服务 `struct inode`

### 1. 页分配器擅长页，不擅长对象

内核经常创建固定类型的小对象：进程描述、inode、网络缓冲、文件描述等。对象的大小通常小于一页，而且创建与销毁很频繁。

如果每次创建对象都向 Buddy 申请一页，绝大部分页空间会闲置；如果让调用者自己在页中切槽，又会让每一种对象重复实现空闲槽管理、对齐、构造和回收。于是内核需要一个建立在页分配器之上的对象缓存层：Buddy 提供页组，SLAB/SLUB 把页组切成固定大小的槽。

```text
Buddy：我要一组连续页
        ↓
对象缓存：按 object_size 切出许多槽
        ↓
调用者：拿一个已对齐的对象槽
        ↓
释放：槽回缓存，缓存完全空闲后再还给 Buddy
```

这解决的不是外部碎片，而是内部碎片和重复分配成本。这里的“缓存”也不只是 CPU cache 的意思，而是内核为一种对象类型维护的可复用内存集合。

### 2. SLAB 的三种状态

经典 SLAB 为每种对象建立 `kmem_cache`，并用三类链表描述 slab 页组的状态：全满、部分使用和全空。分配优先从 partial slab 取槽；没有可用槽时，把 free slab 转为 partial；完全没有 slab 时，才向 Buddy 申请新的页组。

```text
kmem_cache_alloc
  → partial 有空槽：取一个
  → partial 为空、free 有 slab：初始化后转入 partial
  → 两者都没有：Buddy 提供页组，建立新 slab

kmem_cache_free
  → 槽回到 slab
  → slab 从 full 变 partial，或从 partial 变 free
  → 空闲 slab 达到回收条件：归还 Buddy
```

SLAB 还曾使用 coloring，让不同 slab 中相同位置的对象错开缓存行边界，以改善缓存行为。但这个设计也意味着更多元数据和状态管理。随着 CPU 数量、NUMA 节点和并发分配增加，集中式链表和锁逐渐成为热路径的负担。

### 3. SLUB 为什么把热路径搬到 CPU 身边

SLUB 不是另一个完全不同的分配思想，而是对对象缓存组织方式的重做。就源码行为而言，它减少经典 SLAB 那种更显式的集中状态管理，把空闲对象通过 freelist 串起来，并为每个 CPU 保留当前正在使用的 slab。把这理解成“为了缩短热路径、减少共享元数据接触”是合理的设计解释，但不应把这种解释直接当成源码里的字面承诺。

```text
当前 CPU 的 freelist 有对象
  → 直接弹出一个对象

当前 CPU 的 freelist 为空
  → 从 per-CPU partial 取一个 slab
  → 必要时从节点级 partial 获取
  → 再没有可用 slab，向 Buddy 申请页组
```

释放也尽量先回到本地路径。这样做的核心收益不是“完全没有锁”，而是让最常见的本地分配不必频繁争抢全局 partial 链表。跨 CPU 释放、远程节点分配、partial 数量控制和回收仍然需要协调；“无锁热路径”应理解为常见本地路径减少了锁竞争，而不是系统所有路径都没有同步。

SLUB 的代价也很明确：对象槽固定大小，不能消灭对象内部未使用的尾部空间；per-CPU 缓存会让内存短时间滞留在某个 CPU；为了本地性而保留的 slab 也未必立刻归还给 Buddy。因此观察内存占用时，不能只看业务对象数量，还要看 slab 缓存和回收状态。

这一层如果没有观测工具，读者很容易只记住“对象缓存会更快”，却不知道问题怎么落地排查。`/proc/slabinfo` 适合看某类缓存的对象数、slab 数和利用率；`slabtop` 适合快速找出当前最占内存的缓存；`kmemleak` 更像泄漏线索采集器，用来确认哪些对象分配后迟迟没有释放。它们回答的是三个不同问题：谁占得多、谁涨得快、谁像没回收。

### 4. 什么时候用对象缓存，什么时候回到页分配

对象缓存适合尺寸稳定、创建频繁、生命周期短或需要构造/析构处理的内核对象。页分配适合页表、DMA 缓冲、大块临时区域以及无法归入一种固定对象类型的请求。

这个层次关系很重要：SLUB 并没有取代 Buddy，它依赖 Buddy。SLUB 没有可用 slab 时仍然要向底层申请页组；slab 完全空闲并满足回收条件时，也会把页还回 Buddy。一个内核对象从 `kmem_cache_alloc` 开始，最终仍然受到物理页供应、迁移类型和 zone 水位影响。

## 三、内存不只是“多少”：NUMA 和 zone 决定从哪里取

### 1. 同样是空闲页，距离可能不同

在单插槽机器上，“找一页空闲内存”似乎只需要问总账本。但在 NUMA 机器上，每个节点拥有自己的处理器和本地内存。CPU 访问本地节点和远程节点的路径不同，延迟与带宽也可能不同。

因此分配请求有两个问题：空间够不够，以及应该从哪个节点拿。Buddy 解决第一个问题，NUMA 分配策略解决第二个问题。

```text
当前 CPU / 进程
  → preferred node：优先本地
  → 本地 zone：按用途和地址约束筛选
  → 本地不足：沿 zonelist 按距离尝试远端
  → 全部失败：进入慢路径，回收、规整或报告失败
```

节点之间的距离不是简单的“本地/远程”二值。就分配行为来说，内核会为节点准备候选列表，分配时先尝试近处，再根据策略回退。把这种行为概括成“本地优先”没有问题；但“这样一定更快”仍要结合线程迁移、内存绑定、交错策略和 cgroup 的实际情况判断，所以“进程绑在某个 CPU 上”并不自动等于“所有内存都在同一个节点”。

### 2. node、zone、page 是三个不同的视角

`node` 描述 NUMA 拓扑中的物理节点；`zone` 是节点内部按地址范围和用途划分的区域；`page` 是内核描述物理页的基本元数据单位。它们不是三种不同的内存。

```text
node
  └── zone
        └── free_area[order]
              └── free_list[migratetype]
                    └── page
```

`struct page` 记录页的状态、引用关系、映射关系以及与 LRU 等管理结构的连接。Buddy 管理的是这些 page 对应的空闲页块；页被对象缓存、页表或用户映射使用后，page 的状态和引用关系就不再只是“空闲/占用”两个值。

常见 zone 包括面向低地址 DMA 的区域、面向 64 位设备 DMA 的 DMA32 区域、内核直接映射常用的 NORMAL 区域，以及主要存在于 32 位内核历史模型中的 HIGHMEM。具体 zone 是否存在、边界如何确定，取决于架构、物理地址布局和内核配置；不能把某台机器的地址数字当作所有平台的硬编码事实。

ZONE_NORMAL 的直接映射是一个很有用的心智模型：内核可以通过线性关系把一部分物理地址转换到内核虚拟地址，而不是为每次访问重新建立一套独立映射。但这不等于所有物理内存都永远可以用同一种方式访问，也不等于用户进程直接看到了这段映射。下一篇会解释页表和地址翻译，补上“物理页如何变成虚拟地址”的另一半。

### 3. 本地优先也不是绝对规则

如果本地节点还有满足约束的空闲页，优先本地通常有利于访问延迟；但强行本地分配可能导致本地节点压力过高，或者让线程之间的带宽失衡。因此内核还需要在节点距离、zone 水位、GFP 约束、内存策略和回收状态之间做取舍。

排查 NUMA 问题时，`numactl --hardware` 可以帮助查看拓扑，`numastat` 可以观察节点分布。真正的问题通常不是“远程内存绝对错误”，而是远程访问是否出现在对延迟敏感的热路径，是否由线程迁移或错误的绑定策略造成，以及是否值得用交错分配换取更均衡的带宽。

## 四、启动早期：Buddy 还没上线，谁来分配

### 1. 不能让启动代码等待运行期分配器

内核启动时需要解析固件提供的内存布局、保留内核镜像和 initrd、建立早期页表，并为后续初始化准备数据结构。可是此时 zone、Buddy 空闲链表和 SLUB 对象缓存都还没有完成初始化。

这产生了一个时间上的先后矛盾：运行期分配器需要初始化结果，初始化过程本身又需要内存。解决办法不是提前把 Buddy 假装启动，而是使用一个更简单、目标更窄的临时分配器：memblock。

### 2. memblock 只维护“可用”和“保留”

memblock 的职责是登记内存区域并在启动早期做受约束的分配。为了教学理解，可以先把它看成两组核心信息：可用区域和保留区域。真实实现还包含区域计数、容量、遍历与分配辅助逻辑，但主线只需要先抓住这两个问题：哪些内存能用，哪些内存现在不能碰；调用方随后在尚未保留的区域中按对齐和方向分配。

```text
固件/架构代码提供内存布局
  → memblock_add：登记可用区域
  → memblock_reserve：保留内核镜像、initrd、页表等
  → memblock_alloc：从剩余区域取早期内存
  → mm_init 之后：未保留区域批量交给 Buddy
```

这里不应该把 memblock 理解成另一个长期运行的 Buddy。它不需要在启动阶段提供完整的回收、迁移、对象缓存和多核热路径；它只需要在“正式分配器尚未存在”的窗口里把边界守住。

### 3. 交接是 memblock 最重要的生命周期事件

当内存管理初始化进入后段，`memblock_free_all` 等路径会把未保留的内存交给页分配器。之后 Buddy 接管运行期的空闲页组织，SLUB 再建立对象缓存。memblock 里保留的区域不会因为交接而自动变成普通空闲页，它们仍然受到保留原因和生命周期的约束。

```text
启动：memblock 记录 memory / reserved
  ↓
早期分配：页表、内核镜像相关区域和启动数据
  ↓
内存管理初始化：建立 node、zone、page 和 Buddy 结构
  ↓
批量移交：未保留区域进入 Buddy 的 free_area
  ↓
运行期：SLUB 在 Buddy 提供的页组上服务对象
```

这条路径解释了一个常见排障问题：启动日志里看到的“可用内存”为什么不等于机器安装的全部内存。固件区域、内核镜像、initrd、ACPI 表、IOMMU 或架构保留区都可能进入 reserved。`memblock=debug` 和 debugfs 下的 memblock 信息可以帮助确认启动阶段哪些区域被登记、哪些区域被保留，但它们依赖内核配置和启动参数，并非每台系统默认都有。

## 五、把四套机制放回一条生命周期

现在可以重新走一遍“一个内存对象从哪里来”。

系统刚启动时，memblock 先登记可用物理区域，并保护不能被覆盖的区域。内核完成基础初始化后，把没有被保留的区域交给 Buddy；Buddy 按 node、zone、order 和迁移类型建立空闲结构。

运行期如果调用者需要一页，分配路径会优先考虑当前 CPU 的 PCP；如果需要更高 order 的连续页，则进入 zone 的 Buddy 路径，从相应 order 或更大 order 的 free list 取块并分裂。若调用者需要固定类型的小对象，SLUB 会优先从当前 CPU 的 freelist 取槽；没有槽时，它从 partial slab 补充；最终仍然要向 Buddy 申请新的页组。

释放时，SLUB 先把对象槽放回缓存；slab 完全空闲并满足回收条件后，页组才可能还给 Buddy。Buddy 收到页后检查 buddy 是否也空闲，若满足条件就向上合并。NUMA 策略贯穿分配选择，决定首先尝试哪个节点和哪些 zone，但它不改变 Buddy 的分裂合并规则。

```text
启动阶段
  固件内存布局 → memblock 登记/保留
                         ↓
运行期建立
  node → zone → free_area[order] → free_list[migratetype]
                         ↓
小页热路径              大块页路径
  PCP → Buddy            Buddy 分裂/合并
       ↘                ↙
        SLUB 页组与对象槽
                         ↓
释放
  对象回槽 → slab 空闲 → 页归还 Buddy → buddy 合并
```

因此，本文开头的四个问题有了四个不同答案：

- 大块连续页由 Buddy 管理，分裂与合并让外部碎片不会无限积累。
- 小对象由 SLAB/SLUB 管理，固定槽减少内部碎片和重复分配成本。
- 多节点机器由 NUMA 和 zone 组织，分配先考虑位置，再考虑空闲块。
- 启动早期由 memblock 过渡，等正式内存管理建立后再把未保留区域交给 Buddy。

最容易记错的地方也正是这里：这些机制不是互相替代。SLUB 不取代 Buddy，NUMA 不取代 zone，memblock 也不是永久运行的第二个页分配器。它们共同组成一条分层链路，每层只承担自己最擅长的决策。

## 六、几个不能混为一谈的边界

### Buddy 能保证“有空闲总量”就一定能满足大块请求吗？

不能。大块分配需要连续的、满足 order 的页块。系统可能还有很多零散空闲页，却没有足够大的连续块；迁移类型污染、不可移动页和内存规整失败都会让大块请求失败。Buddy 只是提高恢复大块的机会，并没有承诺任何时刻都能满足任意 order。

### SLUB 是不是完全没有锁？

不是。本地 freelist 可以减少常见热路径的锁竞争，但跨 CPU 释放、节点级 partial、对象调试、回收和远程访问仍然需要同步。更准确的说法是：SLUB 把最常见的本地分配尽量变成低协调成本路径。

### NUMA 本地优先是不是越严格越好？

也不是。本地内存通常更接近当前 CPU，但过度绑定可能造成某个节点耗尽、其他节点闲置；交错分配有时反而更适合吞吐型任务。NUMA 是分配策略，不是“远程内存永远错误”的规则。

### memblock 里的 reserved 会不会自然回收？

不会自动因为进入运行期就消失。某些保留区域在后续阶段可以被释放或移交，但必须由对应架构和初始化路径明确处理。排查内存缺口时，应先确认保留原因，而不是把所有 reserved 都当成泄漏。

## 收束：物理内存不是一块大水池

如果把物理内存想象成一块没有结构的大水池，Buddy、SLUB、NUMA 和 memblock 会显得像许多重复的名词。换一个角度，它更像一套分工明确的仓储系统：memblock 负责开业前的临时登记，Buddy 负责按规格拆装大箱，SLUB 负责把箱子切成高频取用的小格，NUMA 负责决定先去哪个仓库，zone 负责处理地址和设备的特殊约束。

这套设计的关键不是某个函数有多复杂，而是把不同粒度、不同时间阶段和不同硬件距离的成本分开。外部碎片交给 Buddy，内部碎片交给对象缓存；全局竞争交给 PCP 和 per-CPU freelist 缓解；启动阶段的循环依赖交给 memblock 绕开。

开篇的问题因此闭环了：内核并不是找到一个“万能内存分配器”，而是让不同角色在不同边界上接力。下一篇要继续追问：Buddy 给出的物理页可能并不连续，为什么进程却能看到连续、私有、看似完整的虚拟地址空间？
