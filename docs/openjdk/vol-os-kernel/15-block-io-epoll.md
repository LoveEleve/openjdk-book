# epoll、blk-mq、bio/request 与 Netfilter：高并发事件和落盘请求，内核到底怎么组织队伍

> 主题：OS 内核｜第 15 篇

> 本篇后续：`16-container-namespace-cgroup.md`
> 版本说明：本文讨论 Linux 事件多路复用、块设备分层与网络包过滤的稳定心智模型；epoll 内部结构、blk-mq 队列组织、I/O 调度器策略、Netfilter 5 链 4 表和 socket/sk_buff 骨架会随内核版本、设备类型和网络栈实现演进。本文以“轮询变订阅、语义与调度分层、数据包分阶段检查”作为主线，不把某版本源码字段、默认队列数或钩子注册细节当作跨版本常量。

## 为什么 select/poll 扛不住百万连接，而 epoll 却像是“谁有事谁按铃”

到上一章为止，我们已经把文件 I/O 路径讲到了页缓存与零拷贝：知道了数据怎么少拷贝、少绕路、少让 CPU 亲手搬运。但更底下还有两条非常关键的链路：

- 事件链：一个 fd 什么时候算“有事了”，为什么不能每次都把所有 fd 全扫一遍？
- 落盘链：页缓存里的脏页最终怎么变成块设备请求，为什么 HDD 还需要排序而 NVMe 常常不想让内核多管？

再加上网络包一路进出内核时，Netfilter 在哪几站插手、socket/sk_buff 怎么把分层封装组织起来，三个看似分散的问题其实都在回答同一类工程难题：**当事件、请求和数据量变得很大时，内核怎么避免“每次都从头数一遍”这种笨方法。**

先记住本篇总图：

```text
事件侧：
  轮询所有 fd → 成本随 fd 总数增长
  epoll 把它改成“先登记，有事再回调进就绪队列”

块设备侧：
  页缓存脏页 → bio 描述“要写什么”
  request 描述“怎么排队送”
  调度器决定要不要合并、排序、限深

网络侧：
  数据包进出内核
  → 在不同阶段经过 Netfilter 检查点
  → 最终在 socket/sk_buff 这套封装骨架上流转
```

这一篇最关键的顿悟是：**高并发下最贵的往往不是单次处理本身，而是你是不是每次都在对全体做无差别扫描。** epoll 用订阅取代轮询，blk-mq 用分层和多队列把请求拆散，Netfilter 用链和表把“在哪一步做什么”分清，这些本质上都在给内核的大流量现场减噪。证据位应回到 `fs/eventpoll.c`、bio/request/blk-mq 路径、Netfilter 钩子与 socket/sk_buff 分层：它们共同支撑“先分层登记，再在关键点定向触发”的统一工程味，而不是几个看似无关的子系统巧合长这样。

## 一、epoll：真正的 O(1) 不是魔法，而是“先登记，以后别每次重扫全场”

### 1. 失败方案：每次等待事件，都把所有 fd 从头检查一遍

select/poll 的直觉很朴素：你手里不是有一组 fd 吗？那每次等待时就把这组全看一遍，看看谁可读、谁可写、谁出错。

这个办法在 fd 很少时没有问题。真正的灾难出现在连接数非常大时：哪怕其中只有极少数 fd 真有事件，select/poll 还是得一遍遍扫完整个集合。

所以它们真正扛不住的，不是“单次检查逻辑复杂”，而是“检查成本和 fd 总数绑定得太死”。

### 2. epoll 的本质，不是“更高级的等待函数”，而是把轮询改成订阅

epoll 之所以能把复杂度从“与 fd 总数相关”改成“与真正有事件的 fd 数更接近”，靠的不是更快的遍历代码，而是换了思路：

- 注册阶段：先告诉内核，我以后关心这些 fd 上的哪些事件。
- 运行阶段：有事件时，由目标 fd 相关的回调把它丢进就绪队列。
- 等待阶段：`epoll_wait` 优先看就绪队列，而不是重扫全场。

```text
epoll_ctl(ADD)
  → 把 fd 登记进监控集合
  → 同时把“有事请通知我”的钩子挂上去

epoll_wait
  → 直接看就绪队列里现在有哪些 ready fd
  → 空则睡眠等唤醒
```

所以 epoll 的 O(1) 直觉，不在红黑树本身，而在“事件到达时就把结果推到你面前”，而不是“等你来问时再帮你挨个搜”。

### 3. 红黑树和就绪链表分别在解决不同问题

很多人会把 epoll 简化成“它内部有一棵红黑树”。这句话没错，但不够关键。更关键的是它内部至少有两种完全不同职责的数据结构：

- 一份“我关心哪些 fd”的已注册集合，需要支持动态增删查，这适合树或其他有序结构。
- 一份“现在已经 ready 的 fd”就绪集合，需要让等待者尽快拿到事件，这更像队列或链表语义。

也就是说，红黑树解决的是“把关心对象管理起来”，就绪链表解决的是“事件来了以后别再从头找”。两者一起才构成 epoll 的完整优势。

### 4. `ep_poll_callback` 这类回调才是 epoll 真正的灵魂

如果只登记 fd 却没有事件到达时的回调接力，epoll 仍然得在等待时自己去遍历判断。回调的意义就在于：真正拥有事件变化第一手消息的，是目标 fd 自己那一侧；既然如此，就应该在那一刻直接把“我现在 ready 了”上报给 epoll，而不是等 epoll 下次再来查。

所以 epoll 的精华可以浓缩成一句话：**不是等你轮询，而是事件自己来敲门。**

### 5. LT 与 ET 的差别，不是“谁更高级”，而是谁来承担“没处理完怎么办”的责任

Level Triggered 更像“只要这事还没处理完，我就继续提醒你”；Edge Triggered 更像“状态刚从无到有时提醒一次，后面你自己负责把缓冲区捞到 `EAGAIN` 为止”。

所以 ET 并不是神秘高性能开关。它只是把“别漏掉剩余数据”的责任更多压到应用自己那一层。若应用没把这层责任做好，性能未必更好，正确性还容易出坑。

## 二、块设备调度器：真正需要排序的，不是“写磁盘”这个概念，而是设备物理代价

### 1. 失败方案：页缓存一脏就按到达顺序原样往设备上扔

如果页缓存里的脏页一来就立刻变成请求、再按原顺序直接丢给设备，看起来最简单：谁先来谁先写。

问题在于，设备不是抽象“黑盒”。特别是传统 HDD，物理寻道和旋转延迟让请求顺序高度影响总吞吐。乱序小请求如果不做合并和排序，设备就会在大量无意义的移动上浪费时间。

所以“请求如何排队”不是细枝末节，而是设备物理特性直接决定的性能主战场。

### 2. I/O 调度器的本质，是在问“这些请求有没有必要先排一排再送”

从教学上看，I/O 调度器做的几件事可以收成两个关键词：

- 合并：相邻或接近的请求能不能拼成更大一笔。
- 排序：发送顺序要不要为了设备效率重新安排。

这就像仓库出货：如果两个包裹目的地挨着，你当然想同车一起发；如果跑道只有一条，你也想尽量按顺路方向组织起降。

### 3. HDD 需要调度器，常常不是因为 Linux“喜欢复杂”，而是因为机械寻道真的很贵

对机械硬盘来说，请求顺序直接影响磁头来回折返的代价。Deadline、电梯类、甚至更复杂的调度器，核心都是在努力避免“为了公平地谁先来谁先走，结果把设备跑成到处折返”。

因此，调度器在 HDD 上的价值首先是物理层面的：减少寻道和随机性，而不是单纯搞一个更漂亮的队列算法。

### 4. NVMe 上很多时候反而想让内核少插手

到了 NVMe/SSD 时代，情况变了。随机访问代价相比 HDD 小得多，设备内部并行度和自身调度能力也强得多。此时内核若还把请求拿来大动干戈地重新排序，收益可能已经不够高，反而增加额外软件延迟。

这就是为什么 `none` 之类轻调度策略会在 NVMe 上非常合理。它不是“内核偷懒”，而是承认设备物理模型变了：**当硬件自己比你更会并行地吞请求时，最好的调度器可能就是少干预。**

## 三、blk-mq 与 bio/request：上层只说“我要写哪些页”，下层再决定“怎么发车”

### 1. 失败方案：文件系统直接对驱动喊“把这些页写出去，顺序也由我说了算”

如果文件系统、页缓存和驱动全糊在一起，上层就会同时承担“数据语义描述”和“设备派发策略”两套责任。这不但难以复用，也让每层都很难单独演进。

Linux 块设备层之所以要分 bio、request，根本原因就在这里：先把“我要操作哪些页、哪个扇区范围”与“这些请求要怎么排队送硬件”拆开。

### 2. bio 更接近“语义单”，request 更接近“运输单”

从教学上可以先这样理解：

- bio 描述的是这次 I/O 要处理哪些页、哪段逻辑块范围，更接近“操作意图”。
- request 则是调度器和块层已经整理过、准备交给设备的一笔运输任务，更接近“发车计划”。

```text
页缓存/文件系统提出 I/O 需求
  → bio：要读/写哪些页、偏移在哪
  → 调度器视情况合并多个 bio
  → request：整理成更适合设备消费的一笔请求
```

所以两层分工不是多此一举，而是在分离“上层语义”和“下层派发”。

### 3. blk-mq 再往前走一步：既然多核下请求源很多，就别让所有核挤在一条总队列前面

老式单队列模型在多核高 IOPS 设备前会非常容易出现锁竞争：很多 CPU 同时往一条请求队列里塞活。

blk-mq 的关键洞察是：既然上层发请求的核心本来就很多，硬件队列也可能很多，那软件层也该把这件事拆成多队列，减少所有人挤一把总锁。

所以 blk-mq 真正解决的不是“请求描述怎么写”，而是“多核与多硬件队列时代，请求别再全堵到一个喉咙口”。

## 四、Netfilter：网络包之所以能被 NAT、过滤和跟踪，不是因为“有防火墙”，而是因为路径上被插了钩子

### 1. 失败方案：每个驱动、每个协议层自己决定要不要顺便做过滤和 NAT

如果没有统一的网络检查点框架，那么地址转换、过滤、连接跟踪这些逻辑就只能散落在各个设备驱动、协议栈分支或特殊路径里。这样规则系统很快就会碎掉，用户根本没法形成统一心智模型。

Netfilter 的价值，正是在包路径上提前约定了一组关键检查点。这样，大家先统一“在哪些时刻可以插手”，再在这些时刻挂不同类型的处理逻辑。

### 2. 5 链 4 表真正统一的，是“时机”和“操作类型”的解耦

从教学上看，链回答的是“包现在走到哪一步了”，表回答的是“我想在这个时机对它做什么”。

- 链：路由前、到本机、转发、从本机发出、路由后。
- 表：豁免跟踪、改包头、地址转换、过滤。

因此 Netfilter 的威力不在于名字多，而在于它把“什么时候插手”和“插手做什么”拆开组合。Docker 端口映射之类能力，也正是借这套组合关系落地的。

### 3. Netfilter 其实和前面的 epoll/块层有同一个设计味道：先定义钩子位置，再让逻辑挂进去

这也是本篇隐藏的统一主题。epoll 先定义“谁有资格在事件 ready 时通知我”，块层先定义“bio 到 request 的分界”，Netfilter 则先定义“包经过哪些检查点”。后面的策略、过滤、NAT、连接跟踪，全是在这些钩子点上追加逻辑。

所以它并不是一个孤立子系统，而是 Linux 一种非常典型的工程味：**先搭骨架，再把策略挂上去。**

## 五、socket / sock / sk_buff：网络数据之所以能层层封装，不是因为每层都复制一份，而是因为它们尽量共用同一块缓冲

### 1. 失败方案：TCP、IP、以太网每过一层都重新拷一遍包

如果每个协议层都把下层交上来的数据完整复制一份，再在前面加自己的头，那么网络栈很快就会沦为大型 memcpy 工厂。每多一层协议，就多一轮拷贝和缓存污染。

### 2. sk_buff 的聪明之处，不在于“很复杂”，而在于让各层尽量在同一块 buffer 上移动边界

从教学上可以先把 sk_buff 看成一只可伸缩的行李箱：底层是一块缓冲，协议层不会每层都重新打一只箱子，而是尽量在同一只箱子前后腾挪空间，加自己的头、改自己的边界。

所以 sk_buff 代表的并不是“网络包的一份静态结构体描述”，而是一种分层共用缓冲、减少重复复制的工程策略。它和上一章讲的零拷贝在精神上完全一致：能少搬一次就少搬一次。

### 3. socket / sock / sk_buff 的分层，也是在做“面向用户的抽象”与“面向协议栈的骨架”分工

用户看到的是 socket 这层 API 抽象；协议状态、队列和传输语义更多落在更靠里的 `sock`；真正包数据在协议层间传递时，又会依托 sk_buff 这套承载结构继续流动。

这和 VFS 四大对象其实很像：不是所有角色都揉成一个概念，而是把用户接口、协议状态和数据载体分层拆开。

## 六、把三条路径收成一张图：事件、落盘和网络都在想办法避免“每次都全量扫描一遍”

现在可以把本篇的三条线重新并到一起。

在事件侧，epoll 通过“先注册回调、事件到来直接进就绪队列”把 select/poll 的全量扫描改成订阅模型；在块设备侧，页缓存以下的 I/O 先用 bio 描述语义，再由 request 和调度器决定怎么送硬件，多队列进一步减少总队列争抢；在网络侧，Netfilter 把“在哪一步检查包、做什么改写”组织成钩子体系，socket/sk_buff 则继续用分层封装和共享缓冲降低复制与协调成本。

```text
事件：别每次重扫全部 fd
  → epoll 用订阅和就绪队列替代轮询

落盘：别让所有请求挤在同一条路上乱跑
  → bio 描述语义，request 负责发车，调度器按设备特性取舍

网络：别让所有改写逻辑散落在各层里
  → Netfilter 先统一检查点，socket/sk_buff 负责分层承载
```

所以本篇最该记住的一句话是：**epoll、blk-mq、Netfilter 看起来分属不同世界，骨子里却都在做同一件事——把“全量扫一遍”的笨办法改造成“先分层登记，再在关键点上定向触发”。** 这里最该补的一句边界提醒是：这种分层与回调化并不自动消灭成本，它只是把成本从“每次都重扫全体”换成“平时维护结构、关键点上定向协调”；选错设备假设或事件模型，代价仍会从别处冒出来。

## 七、几个最容易说错的地方

### epoll 的 O(1) 是不是因为红黑树查找特别快？

不够准确。红黑树主要解决的是“已注册集合怎么管理”，真正让 `epoll_wait` 不再和 fd 总数绑定的是回调 + 就绪链表的订阅模型。

### NVMe 不需要调度器，是不是说明调度器过时了？

不是。更准确地说，是设备物理特性变了：没有寻道、设备内部并行与调度能力更强时，内核重排序的收益下降了。

### bio 和 request 是不是只是同一件事的两个名字？

不是。bio 更像上层 I/O 语义单，request 更像调度和驱动准备发车的运输单。

### Netfilter 是不是就是 iptables 的另一种叫法？

不对。Netfilter 是内核里的检查点框架，iptables/nftables 是建立在这些检查点之上的规则表达与管理方式。

## 收束：高并发内核最怕的，不是工作很多，而是每次都用最笨的方法重新数一遍全体

现在回到开头那个问题：为什么 select/poll 扛不住百万连接，而 epoll 可以更稳？为什么脏页往下走之后还要分 bio、request 和调度器？为什么网络包非得过一组链和表？因为在大流量世界里，真正拖垮系统的常常不是“有很多事”，而是“每次来事都先把所有东西重新扫一遍、重新抢一遍、重新排一遍”。

这篇的开场困惑也就闭环了：事件、落盘、网络这三条链虽然看起来很不一样，但它们都在努力做同一件事——把粗暴全量处理变成分层登记、定向回调和按设备/场景特性取舍的组织系统。

## 八、误解清单、证据清单与边界清单

### 误解清单

- epoll 的优势不只是“红黑树快”；真正关键的是回调 + 就绪队列把轮询改成了订阅。
- NVMe 上调度器收益变小不等于调度器过时；它只是在承认设备物理模型变了。
- bio 和 request 不是两个名字描述同一张单子；一个偏 I/O 语义，一个偏发车计划。
- Netfilter 不是 iptables 的别名；前者是检查点骨架，后者是建立在骨架上的规则表达方式。
- socket/sk_buff 分层不是为了显得复杂，而是在尽量减少每层都重新拷一份包的冲动。

### 证据清单

- epoll：`fs/eventpoll.c`、interest set、就绪链表与回调路径，支撑“先登记、有事再通知”的订阅模型。
- 块层分工：bio、request、I/O 调度器与 blk-mq 多队列路径，支撑“语义单和运输单分离、单总队列被多队列拆散”。
- 设备特性：HDD 寻道与 SSD/NVMe 并行能力差异，支撑“调度器是否该多插手”必须看物理代价。
- Netfilter：5 链 4 表、钩子注册与路径分阶段检查，支撑“先定义时机，再挂策略”。
- 网络承载：socket/sock/sk_buff 与共享缓冲路径，支撑“分层封装不等于每层都复制一遍”。

### 边界清单

- 本文讨论的是 Linux 事件多路复用、块设备分层与网络包过滤的稳定心智模型，不把某版队列数、钩子细节或调度参数写成跨版本契约。
- epoll、blk-mq、Netfilter 共同体现的是“分层登记、定向触发”的工程味，不等于它们在所有场景下都比简单结构更便宜。
- HDD/SSD/NVMe、网卡卸载能力、协议栈配置与应用模型都会显著改变这些机制的收益与代价。
- “少全量扫描”不是唯一目标；公平性、可观测性、亲和性和错误恢复同样会决定最终设计选择。
