# 页缓存、mmap、Direct I/O 与零拷贝：文件数据从磁盘走到程序手里，到底绕了几圈

> 主题：OS 内核｜第 14 篇
> 前置文章：`04-page-cache-reclaim-oom.md`、`13-vfs-ext4.md`
> 本篇后续：`15-block-io-epoll.md`
> 版本说明：本文讨论 Linux 文件 I/O 路径的稳定心智模型；页缓存命中、预读、脏页回写、Direct I/O、mmap 文件映射、sendfile/splice 等语义会随内核版本、文件系统、块设备和网络栈实现变化。本文以“数据经过了几次拷贝”为主线，不把某版本函数名、页状态位或 DMA 细节当作跨版本常量。

## 读一个 100MB 文件，数据到底从磁盘到你手里拐了几次弯

前一篇讲清楚了文件系统怎样把“名字、本体、块布局和崩溃一致性”组织起来。但那还只是静态地图：知道文件是什么、块在哪里，并不等于知道数据真正流动时经过了什么路径。

真正让应用感到快慢差异的，常常不是 inode 号长什么样，而是这些问题：

- 第一次 `read` 为什么慢，第二次却常常快很多？
- `write` 明明已经返回了，为什么数据却还不一定在盘上？
- 数据库为什么常常执意绕开页缓存？
- `mmap` 为什么会少一次拷贝？
- `sendfile`/`splice` 所谓零拷贝，到底省掉了哪一段“搬运工”的劳动？

所以这一篇真正要回答的，不是“文件怎么表示”，而是：**文件数据在读、写、映射和发送过程中，到底经过了哪些中转站，哪些中转站是必要的，哪些又是在想办法被消掉。**

先记住本篇总图：

```text
普通 read
  → 磁盘到页缓存
  → 页缓存再复制到用户缓冲区

普通 write
  → 用户缓冲区复制进页缓存
  → 标脏，之后再回写磁盘

mmap
  → 文件页进入页缓存
  → 页缓存页直接映射进用户地址空间

Direct I/O
  → 尽量绕开页缓存，直接面向磁盘与用户缓冲

零拷贝
  → 尽量让数据留在内核 / DMA 路径上
  → 少经过 CPU 搬来搬去
```

这一篇最关键的顿悟是：**I/O 优化很多时候不是“让磁盘更快”，而是“让数据少拷几次、少绕几圈、少让 CPU 亲手搬运”。** 证据位应回到页缓存命中/缺页回填、脏页回写、Direct I/O、`mmap` 映射与 `sendfile`/`splice`/DMA 路径：它们共同支撑“优化核心在于少拷贝、少绕路、少让 CPU 当搬运工”的主线，而不是某个单独 API 名字天然更快。

## 一、页缓存读：第一次慢，是在把文件页请进内存；第二次快，是因为你读的已经不是磁盘了

### 1. 失败方案：每次 `read` 都直接向磁盘要一页数据

如果没有页缓存，`read` 的模型会非常直白：应用要多少字节，内核就去磁盘读多少回来，放进用户缓冲区，完事。

这个方案看似干净，但重复读取会非常愚蠢。只要同一个文件页短时间内被再读一次，系统又得重新付整套磁盘访问代价。也就是说，它完全没有记忆力。

而现实中的文件访问恰恰很依赖记忆：日志回看、热点配置、共享库、可执行文件页、常用数据文件，都会被反复碰。

### 2. 页缓存读的本质，不是“提前读很多”，而是“先问内存里有没有这页”

页缓存读路径最根本的一步，是先在文件对应的页缓存索引里找这页。如果已经有了，而且内容有效，那这次读取从一开始就不必去碰磁盘。

```text
read 请求到来
  → 先查页缓存里有没有这页
  → 有且内容有效：直接从内存这页拷给用户
  → 没有：触发磁盘读，把页装进缓存后再交给用户
```

所以“第一次慢、第二次快”并不是玄学，而是第一次在替后续访问付建仓成本，第二次则是在用现成仓货。

### 3. not present、uptodate、locked、dirty 这几种状态，其实在回答“这页现在能不能直接拿来用”

从教学上，不必死背具体标志位名字，先抓它们背后的问题分工：

- 不在缓存里：那就得去拿。
- 在缓存里且内容有效：那就直接用。
- 正在被 IO 或别人处理：那就得等。
- 页是脏的：对读来说仍然可能是最新有效内容，只是它还没落盘。

也就是说，这些状态不是为了让内核显得复杂，而是在不断回答一个非常实际的问题：**这次用户想读的那一页，现在是现货、缺货、在路上，还是店里刚改了账但还没报给总仓。**

### 4. 预读真正优化的，不是单次读取，而是“你接下来大概率还会继续往后读”

页缓存只能解释“第二次为什么快”，还不能解释“第一次顺序读一长段时为什么后来会越来越顺”。这时预读出场。

预读的关键不在于它神奇地知道未来，而在于它观察到一个很强的信号：你已经连续向前读了几页，那么下一页也大概率会要。于是系统开始提前把后面的页装进页缓存。

这让顺序读的代价从“每页都同步等一次磁盘”慢慢变成“磁盘在后台一段一段拉，前台尽量只在内存里流”。

### 5. 预读为什么常常是动态窗口，而不是写死 N 页

因为顺序性不是二元判断。你刚读了两页，不代表一定会一直线性扫完整个大文件；但你如果已经连续读了很多页，这个信号就越来越可靠。

于是预读窗口常会逐步扩大：先保守试探，再随着顺序行为被反复确认而放大。它优化的不是“所有读取”，而是“被证明越来越像顺序流的那批读取”。

## 二、页缓存写：`write()` 之所以快，往往只是因为你先把账写在内存里了

### 1. 失败方案：每次写都同步落盘，应用在前台等磁盘点头

如果把写语义理解成“调用返回时磁盘就必须已经稳定写好”，那应用每次小写都得老老实实等设备完成。这在 correctness 上最直白，但在性能上几乎是自杀。

特别是很多小块、连续、频繁写入的场景，真正的吞吐秘诀不在“每次写立刻结束”，而在“把这些零碎写合并起来再算总账”。

### 2. 普通写路径真正干的事，常常是“先把用户缓冲区内容抄进页缓存页，再记成脏页”

所以很多 `write()` 返回快，不是因为磁盘闪电般完成了持久化，而是因为 CPU 先把数据从用户缓冲区复制进页缓存页，然后把这页标成脏页。应用已经可以继续跑，落盘则交给后面的回写路径。

```text
write
  → 用户 buffer 复制到页缓存页
  → 页被标成 dirty
  → 应用先返回
  → 之后异步回写到磁盘
```

这也说明，普通 buffered write 和 read 一样，核心中转站都是页缓存。只不过读是在等“页进来”，写是在把“页改脏后以后再说”。

### 3. 延迟分配为什么能让 ext4 更容易拿到大 extent

前一篇讲 ext4 extent 时说过：连续布局越多，区间表达越省。延迟分配正是在帮它争取这个前提。

如果每次写一点点就立刻为它确定磁盘块位置，文件写入会更容易被零碎需求和当时局部空闲状态切碎。把分配决定稍微往后推，让系统在回写时一口气看到更大的脏数据范围，就更有机会分配出一段连续块，把 extent 做大。

所以 delalloc 不是单纯“懒一点再分配”，而是在为后面的布局质量和元数据压缩争取更好的决策时机。

### 4. 为什么 `fsync` 仍然如此重要

一旦理解写返回并不等于落盘，就会明白 `fsync` 的意义。它不是对页缓存模型的否定，而是给这套“先记在内存、后续再结算”的机制划出一条业务必须认真结清的边界。

所以 `fsync` 慢，不是它“做了多余的事”，而是它在替你把之前被推后的成本现在一次性结算。

## 三、Direct I/O：不是“更快的 I/O”，而是“别给我再来一份我根本不想要的缓存”

### 1. 失败方案：数据库既维护自己的 buffer pool，又让内核再缓存一遍同样的数据页

很多数据库或存储系统有自己极强的缓存管理能力：知道哪些页热、哪些页冷、何时预读、如何淘汰、如何控制刷盘。若这时内核还再给同一批数据建立一层页缓存，你得到的往往不是加倍收益，而是双份内存占用和双份状态协调。

这就是“双缓存浪费”的本质。真正烦人的不是“多一份副本”这么简单，而是：你多了一层并不按数据库工作负载认知来决策的缓存系统，它还会继续吃内存、参与回写和影响一致性行为。

### 2. Direct I/O 的重点不是反对缓存，而是把缓存控制权还给应用自己

`O_DIRECT` 这类路径的核心主张是：如果应用已经有自己的缓冲池与淘汰策略，那就别再强行让页缓存介入。数据尽量直接在用户缓冲和设备之间走，应用自己负责批量、对齐和局部性管理。

所以 Direct I/O 不是“永远比页缓存快”，而是“当应用比内核更懂自己的工作集时，别让系统替它做第二遍缓存决策”。

### 3. 这也解释了为什么 Direct I/O 有很多使用约束

因为你主动放弃了一部分内核通用优化：预读、写合并、页缓存复用、脏页批处理等。既然要自己掌权，就得自己承担更多约束，例如对齐要求、批量策略和更显式的 I/O 组织方式。

也就是说，Direct I/O 不是白拿性能，而是用“失去内核普适优化”的代价，换“应用独占缓存控制权”的好处。

## 四、mmap I/O：少掉的那一次拷贝，本质上是因为你直接摸到了页缓存页本身

### 1. read 的第二次拷贝到底花在哪

普通 `read` 路径里，即使页已经在页缓存，内核仍然还要把页缓存中的内容复制到用户提供的 buffer。因为用户缓冲区和页缓存页是两份不同的内存区域。

所以 read 的常见两段路可以概括成：

- 磁盘到页缓存。
- 页缓存到用户 buffer。

如果第一次已经缓存命中，那第一段可以省；但第二段只要你还在用普通 `read`，通常就还得做。

### 2. mmap 真正减少的，不是磁盘读，而是“页缓存再抄一份给你”这一步

`mmap` 的关键价值，在于它把文件页通过页表直接映射进用户地址空间。这样用户代码看到的并不是“从页缓存复制出来的另一份用户缓冲”，而就是那批页缓存页在自己地址空间里的映射视图。

```text
read
  → 页缓存命中后，仍要复制到用户 buffer

mmap
  → 页缓存页直接映射到用户页表
  → 用户直接访问这批页
```

这就是为什么 `mmap` 常被说成少一次 CPU 拷贝：不是因为磁盘凭空少读了，而是因为“页缓存到用户缓冲区”的那次复制不再需要。

### 3. 少一次拷贝，不等于没有新的管理代价

一旦用户直接映射到这些页，页缓存页就不再只是内核自己的内存对象了。映射关系、回收时机、写回同步语义、失效边界都会更敏感。

所以 `mmap` 不是单纯“更高性能的 read”，而是在“减少一次复制”和“增加一层映射生命周期复杂度”之间做交换。

## 五、零拷贝：真正被消掉的，是让 CPU 当搬运工的那一截劳动

### 1. 失败方案：磁盘读进来，再抄到用户态，再抄回内核态，最后再送网卡

以文件发送给 socket 为例，最朴素的实现就是：`read` 把文件读到用户缓冲，再 `write` 把用户缓冲送到 socket。这样每一层都清楚，编程模型也简单。

可这个路径非常绕：数据先从磁盘到页缓存，再从页缓存到用户，再从用户回到内核 socket buffer，最后才发给网卡。CPU 成了中间搬运工。

### 2. sendfile / splice 的真正优化，不是“文件传得更快”这句口号，而是别让数据进用户态兜一圈

sendfile 的核心思路是：既然用户进程根本不需要真正查看和修改这份数据，只是想把文件内容送给 socket，那为什么还要把数据搬进用户缓冲区再搬回内核？

于是零拷贝优化路径的核心就变成：尽量让数据留在内核页缓存 / 管道 / DMA 链路里流转，用户只发起控制，不亲手接货。

### 3. 为什么 DMA 在这里这么关键

只要数据还是 CPU 一段一段 `memcpy`，你最多只是减少了一部分复制次数，还没有把“谁在搬”这个问题彻底改掉。DMA 的价值就在于，它让设备和内存之间的搬运不必再全靠 CPU 扛肩膀。

所以很多零拷贝路径真正接近“零”，并不是因为路径中完全没有任何数据移动，而是因为**移动发生了，但尽量不再由 CPU 亲手做中间搬运。**

### 4. 零拷贝真正适合的是“数据中转”，不是“数据处理”

一旦应用必须真正解析、修改、重编码内容，数据终究还是得进到用户可操作的那一层。也就是说，零拷贝不是通用圣杯，它特别适合“我只是中转，不需要亲自拆箱”的场景，比如静态文件服务、管道转发等。

所以“零拷贝更快”只有在这类场景里才是强结论；若你最终还是要细改每个字节，那有些拷贝和触达就不可避免。

## 六、把五条 I/O 路径收成一张图：本质都是在问“CPU 到底亲手搬了几次”

现在可以把这一篇的路径重新收起来。

普通页缓存读让第一次访问先把数据请进页缓存，后续命中尽量不碰磁盘；普通写把数据先写进页缓存再标脏，落盘延后结算；Direct I/O 则是在说“别再给我第二份缓存”；`mmap` 通过页表映射省掉页缓存到用户缓冲的那次复制；而 sendfile/splice 继续把“用户态中转站”整段拿掉，让数据尽量留在内核和 DMA 路径上流过去。

```text
普通 read：磁盘 → 页缓存 → 用户 buffer
普通 write：用户 buffer → 页缓存 → 以后再落盘
Direct I/O：尽量绕开页缓存
mmap：页缓存页直接映到用户态
零拷贝：尽量不让 CPU 在用户态这层搬运数据
```

所以本篇最该记住的一句话是：**I/O 路径优化的核心，不只是命中磁盘还是命中缓存，而是数据到底经过了哪些中转站，以及这些中转站里 CPU 亲手搬了几次。** 这里最该补的一句边界提醒是：少拷贝不自动等于更快；页 fault、映射生命周期、设备队列、应用是否真的要改数据，以及文件系统/块设备能力，都可能让“理论上少一跳”的路径在现实里并不总是赢。

## 七、几个最容易说错的地方

### `read` 慢，是不是就只是磁盘太慢？

不够准确。你还要问：是不是没命中页缓存、预读没跟上、或者明明命中了却还在反复做用户态拷贝。

### `write` 返回成功，是不是就说明数据已经持久化？

不是。很多时候只是页缓存页已经被改脏，真正落盘还在后面。

### `O_DIRECT` 一定比页缓存路径更快吗？

不一定。它只是把缓存控制权交还给应用，适合那些自己比内核更懂工作集的场景，不是通用加速按钮。

### `mmap` 和 sendfile 都少拷贝，是不是可以互相替代？

不是。`mmap` 适合让用户直接访问页缓存页，sendfile/splice 更适合数据中转不进用户态。它们省掉的那一段劳动并不完全相同。

## 收束：文件 I/O 性能的真正秘密，不是磁盘突然变快，而是数据越来越少经过你手

现在回到最开始的问题：读一个 100MB 文件，数据到底拐了几次弯？答案取决于你选哪条路径。普通 read 往往让它先到页缓存、再抄给用户；普通 write 让它先脏在页缓存里；Direct I/O 试图绕开中间仓库；mmap 让你直接摸页缓存页；零拷贝则进一步把用户态这层中转站整段拿掉。

这篇的开场困惑也就闭环了：I/O 优化不只是“更快的磁盘”问题，而是在持续把数据从“多一次拷贝、多一个中转站、多一轮 CPU 亲手搬运”变成“少绕一次、少抄一份、少让 CPU 当搬运工”。

## 八、误解清单、证据清单与边界清单

### 误解清单

- `read`/`write` 的快慢不只取决于磁盘；页缓存命中、预读、脏页回写和用户态拷贝都在参与结算。
- `write` 返回成功不等于持久化完成；很多时候只是页缓存页已经被改脏。
- Direct I/O 不是通用加速按钮；它更像“把缓存控制权还给应用”，同时拿走了内核一层普适优化。
- `mmap` 不是“文件变成内存”这么简单；它省掉的是页缓存到用户缓冲的那次复制，同时引入映射生命周期复杂度。
- 零拷贝不等于完全没有数据移动；真正被尽量消掉的是 CPU 在用户态这层当搬运工的劳动。

### 证据清单

- 页缓存读写：页缓存命中、预读、脏页回写与 `fsync` 边界路径，支撑“第一次建仓、后续复用、写先记内存账”的主线。
- Direct I/O：`O_DIRECT`、对齐约束与文件系统/块设备路径，支撑“绕开页缓存是为了避免双缓存和重复决策”。
- `mmap`：文件页映射、fault 建页与页表接入路径，支撑“少一次复制但增加映射管理复杂度”。
- 零拷贝：`sendfile`/`splice`、页缓存到 socket/DMA 路径，支撑“用户态中转站被拿掉”的判断。
- 连续布局：delalloc、extent 与脏页批量回写路径，支撑“布局质量与 I/O 路径并不是彼此独立”的事实。

### 边界清单

- 本文讨论的是 Linux 文件 I/O 路径的稳定心智模型，不把某一版页状态位、DMA 细节或文件系统特化行为写成跨版本契约。
- 少一次拷贝、少一层缓存或少一轮中转不自动等于更快；页 fault、TLB、映射维护、设备模型和工作负载都可能改写收益。
- Direct I/O、`mmap`、零拷贝各自适用的前提不同，不应被叙述成可以互相随手替换的一组“高级 API”。
- `fsync`、WAL、写回节奏与应用持久化协议共同决定“何时算真正结账”，不能只看一次 `write` 返回时间。
