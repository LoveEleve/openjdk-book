# 容器原理：Namespace 让进程看见不同世界，Cgroup 让它别把世界吃光

> 主题：OS 内核｜第 16 篇
> 前置文章：`11-process-fork-switch.md`、`02-paging-page-tables.md`、`10-cfs-scheduler.md`
> 本篇后续：`17-virtualization.md`
> 版本说明：本文讨论 Linux 容器的稳定心智模型；七种 Namespace、cgroup v1/v2、overlay 文件系统、veth/bridge 和 `runc` 启动链细节会随内核、发行版和容器运行时演进。本文以“隔离视角 vs 限制资源”为主线，不把某一版本的目录布局、具体 controller 文件名或 Docker 内部实现细节当作跨版本常量。

## Docker 启动的不是“迷你操作系统”，而是一个被重新布置视角和预算的进程

很多人第一次接触容器时，会自然把它想成“比虚拟机更轻的一个小系统”。这个直觉有一半是对的：容器里的确能看到自己的进程树、自己的主机名、自己的根文件系统，甚至像是有了自己的一套网络接口和路由表。可另一半是错的：**它并没有独立内核。**

这正是容器最容易被误解的地方。它不是凭空创造了一个新操作系统，而是在同一内核上，把一个普通进程包装进一组更特殊的边界里：

- 有些边界负责改变它“看见什么”。
- 有些边界负责限制它“最多用多少”。
- 还有一些机制负责给它拼出一套看起来独立的文件和网络入口。

如果不把这几层拆开，容器就很容易被讲成玄学：仿佛一个 `docker run` 就突然召唤出一整个小宇宙。实际上，它做的事非常具体，只是组合得足够漂亮。

先记住本篇总图：

```text
普通进程
  → Namespace 改写它看到的世界
  → Cgroup 限制它能用的资源
  → overlay 给它拼一套看似独立的文件视图
  → veth/bridge 给它接一条单独的网络通道
  → 最终形成“像一台机器”的用户态体验
```

这一篇最关键的顿悟是：**容器不是新物种，它是一个进程加上一套视角隔离和资源预算规则。** Namespace 负责“你看见什么”，Cgroup 负责“你最多用多少”。

## 一、先把最容易混的两件事拆开：隔离视角，不等于限制资源

### 1. 失败方案：只做“看不见宿主”，就以为容器已经安全可用

假设我们只给一个进程戴上一副眼罩：让它看不见宿主上的其他 PID，看不见宿主真实主机名，看不见宿主的挂载树。这样它主观上就会觉得自己像是独占了一台机器。

这个方案在“体验上”已经很像容器了，但资源侧立刻露馅：它依然可以吃掉大量 CPU、内存、块设备带宽。如果不加限制，“看不见别人”并不会让它“用不坏别人”。

所以仅有隔离视角，不足以构成可托管的容器。

### 2. 反过来，只有资源限制，也造不出“像一台机器”的体验

如果你只用 cgroup 给一个普通进程加上 CPU、内存、I/O 配额，它确实不容易把宿主吃穿；但它仍然能看到宿主上的其他进程、共享同一主机名、同一网络接口、同一根文件系统视图。

这样做更像“给普通进程套上限额”，而不是“让它住进自己的小房间”。

所以容器真正成立，必须同时有两层：

- Namespace 让它看到的是局部世界。
- Cgroup 让它只能使用局部预算。

### 3. 这就是为什么“容器 = Namespace + Cgroup”不是口号，而是职责分工

很多资料会把这句总结写成一句口号，但它其实是非常实打实的工程分层。要理解容器，第一件事就是别把这两个角色混起来：

- Namespace 解决的是名字空间与可见性。
- Cgroup 解决的是消耗量与调度/回收行为。

如果前者是眼罩，后者就是饭卡和电表。你可以把自己关在一间看不见外面的房里，但如果没有电表和饭卡，你还是可能把整栋楼资源拖垮。

## 二、七种 Namespace：不是新建一套内核，而是让同一内核给不同进程展示不同世界

### 1. PID Namespace：容器里 `ps` 看到的世界为什么会变小

PID Namespace 最容易让人直观感受到“容器像一台独立机器”。因为它直接改变了进程树的可见性。容器内的进程可能看到自己有一个 PID 1，`ps` 看见的也只是容器这棵局部树，而不是宿主全局的所有任务。

这并不是因为内核真复制出了一整套新进程管理子系统，而是因为同一套任务结构在不同 Namespace 视角里暴露出了不同名字和可见范围。

### 2. UTS / NET / IPC / MNT：主机名、网络、IPC、挂载点分别被分层改写

容器体验之所以“像机器”，还来自其他几层视角一起被改写：

- UTS 让它能有自己的主机名。
- NET 让它能看到自己的网卡、路由和端口空间。
- IPC 让它的消息队列、共享内存、信号量空间不与宿主直接混在一起。
- MNT 让它拥有一棵看似完整而独立的挂载树。

这些东西分开看都只是局部小隔离，叠起来就形成了一种很强的错觉：这个进程仿佛真的活在自己的小系统里。

### 3. USER Namespace：最容易被忽略，却最像“权限翻译器”

很多人会以为“容器里是 root”就等于“宿主上也有 root 威力”。USER Namespace 正是在这里拆开这层直觉。它允许容器内部的 UID/GID 视角和宿主真实 UID/GID 映射关系分离。

也就是说，容器里的 root 更多是一种局部身份，不是自动拥有宿主上对所有资源为所欲为的全局权限。

这一步非常关键，因为它说明 Namespace 不只是“把东西藏起来”，有时还在重新翻译身份含义。

### 4. CGROUP Namespace：连“我属于哪个资源层级”这件事，也可以只给你看局部片段

到了这一层你会更清楚，“视角隔离”并不仅仅是进程、网络、挂载这些容易想到的东西。连 cgroup 路径本身的可见性，也可以被重新裁剪，让进程只看到自己的局部资源树，而不是宿主全局控制结构。

这进一步说明：Namespace 的本质从来不是“换掉真实世界”，而是“换掉你被允许看见的那部分世界”。

## 三、Cgroup v1：让进程别把宿主资源吃光，但一开始是“每个资源子系统各管各的”

### 1. 失败方案：所有限制都靠用户自觉，或者靠调度器一套默认公平通吃

上一篇讲过 CFS 可以按权重和公平账本调度 CPU。但默认公平不等于资源隔离。一个进程或一组进程若完全不受额外约束，仍可能在某些资源上过度占用。

所以 cgroup 出现的背景并不是“调度器不够好”，而是系统需要一种更显式的资源分组与额度控制手段。

### 2. v1 的核心思想：每类资源先有一个自己的 controller

cgroup v1 的强项是很直接：内存有内存 controller，CPU 有 CPU controller，块设备有 blkio，诸如此类。不同资源维度各自有一套控制文件和层级。

这让资源治理一开始很容易落地：你想限内存，就进 memory controller；想限 CPU，就配 CPU 相关参数。很多经典容器参数也正是在这套模型上被翻译出来的。

### 3. memory / cpu / blkio 为什么最常被拿来讲

因为它们几乎正对应了最容易失控、也最容易被租户明显感知的三类资源：

- 内存超了，可能直接 OOM 或严重回收抖动。
- CPU 超了，大家就会觉得慢。
- I/O 超了，磁盘和网络相关延迟都会开始排队。

因此这三者经常被当成 cgroup 的“第一批三剑客”，并不奇怪。

### 4. v1 的问题，不是“不能用”，而是每个资源树都各走各的以后，进程的身份关系会被切碎

这就是 cgroup v1 最深的结构性问题。因为每类 controller 都可能有自己的层级树，于是同一个进程在 CPU 这一棵树里挂在 A 节点，在 cpuset 那棵树里挂在 B 节点，在 memory 那棵树里又挂在 C 节点。每个子系统都自洽，但全局看起来像三套人事档案彼此不对齐。

这在简单场景还能忍，一旦容器层、编排层、资源策略层叠起来，冲突和理解成本就会迅速冒头。也正因此，v2 的统一层级不是锦上添花，而是在修 v1 这个深层裂缝。

## 四、Cgroup v2：真正统一的不是 API，而是“同一进程的所有资源限制应挂在同一棵树上”

### 1. 统一层级的意义，不在“语法好看”，而在“别让一个进程在三棵树里活成三个人”

v2 最关键的改进，不只是把文件名改得更整洁，而是把控制器统一挂在一棵层级树上。这样，一个进程的资源身份不再被分裂成多个互不对齐的从属关系。

也就是说，v2 修复的不是小毛病，而是“资源控制的身份模型”。

### 2. `cpu.max` 这类接口的背后，是统一语义而不是更多技巧

很多人会把 v2 理解成“新接口集合”。更值得理解的是：这些接口试图把“限制谁、怎么限制、这一层对子层开放哪些控制器”收进一套一致语义里，而不是继续让每个 controller 各玩各的。

统一层级的好处不只是管理方便，还在于冲突更少、推理更稳。当容器编排系统、监控和运行时都围绕同一棵树说话，资源世界终于更像是一个完整系统，而不是拼接棚。

### 3. 这也是为什么 v2 越来越成为容器世界的推荐默认面貌

不是因为 v1 不能干活，而是因为容器和编排系统越成熟，就越需要“资源身份一致”这种底层秩序。你不可能长期在一堆互相错位的控制树上优雅地构造大规模平台。

## 五、容器启动流程：`docker run` 不是“启动一个神秘盒子”，而是在同一个内核里依次布置视角、预算、文件和网络

### 1. 失败方案：把容器想成“一条命令直接召唤出一个完整小系统”

这会让容器显得特别神秘，好像某个守护进程一念之间就制造出一台新机器。实际发生的事要更具体得多：运行时只是按步骤调用现有内核机制，把同一个普通进程一步步送进新边界。

### 2. `runc` / container runtime 真正做的是“编排这些现成能力的组装顺序”

从教学上可以把容器启动链看成几件事依次落位：

- 先把进程放进新的 Namespace 视角里。
- 再给它挂上 cgroup 预算。
- 再给它准备一套看似完整的文件系统视图。
- 最后再把网络接口和默认入口点接进去。

这不是在创造一个新内核，而是在组织一组老能力的拼装顺序。

### 3. overlay 文件系统为什么是容器启动速度的关键拼图

镜像共享之所以高效，关键不在“镜像格式神奇”，而在于容器根文件系统通常不是每次都从零复制一整份。overlay 把基础镜像层当作只读共享层，多个容器可以一起踩在同一批 lower layers 上；真正需要修改文件时，再把对应内容拷到上层可写层去。

这就像前面讲过的 COW 在内存里的做法被搬到了文件层：**共享只读，修改时再复制。**

所以容器启动快，不只是进程快，也因为文件视图不是每次都重新“全复制造一套”，而是靠共享层和写时复制拼出来。

### 4. pivot_root / MNT Namespace / overlay 一起，才形成“我眼里这就是我的根文件系统”的错觉

只靠 overlay 还不够。容器之所以会真的把某棵目录树当成自己的 `/`，还得配合挂载视角隔离和根切换语义。这几层叠在一起，才把“共享同一内核、共享同一宿主磁盘上的层”伪装成“我有自己完整的一套根文件系统”。

也就是说，容器文件视图并不是单一技术点，而是 Namespace 与文件系统机制联手制造出来的局部世界。

### 5. veth + bridge：网络隔离也不是抽象“新网卡”，而是一对被接到桥上的线

网络这一层也是同样道理。容器里看到的独立网卡和 IP 空间，不是凭空生成，而是靠 NET Namespace 提供视角隔离，再用 veth pair 把容器这一端和宿主桥那一端接起来。

这说明容器启动链每一环都在做一件非常朴素但强大的事：把同一内核现有机制重新布线，最终让一个普通进程觉得自己住进了一套独立环境。

## 六、把容器收成一张图：它不是新内核，而是同一个进程被重新定义了视角、预算和舞台

现在可以把这一篇的角色重新放回一条完整链路里。

一个容器内的执行体，本质上仍是 Linux 进程。不同的是，这个进程启动前后，内核依次为它改写了几个关键维度：先用 Namespace 改写“你能看见什么”，再用 Cgroup 改写“你最多能拿多少”，再用 overlay 和挂载视图改写“你认为自己的根文件系统是什么”，再用 veth/bridge 把网络入口接进它看到的那个局部世界。

```text
普通进程
  → Namespace：看到的是局部世界
  → Cgroup：只能用局部预算
  → overlay + 挂载视图：以为自己有独立根文件系统
  → veth + bridge：以为自己有独立网卡和网络空间
  → 最终形成“像一台机器”的用户态体验
```

所以本篇最该记住的一句话是：**容器不是一台迷你虚拟机，而是一个进程在同一内核里被重新布置了视角、资源预算和舞台。**

## 七、几个最容易说错的地方

### Namespace 和 Cgroup 是不是都在做“隔离”？

不够准确。Namespace 更偏可见性隔离，Cgroup 更偏资源限制和资源统计；前者是眼罩，后者是预算。

### 容器里的 root 是不是就等于宿主上的 root？

不是。USER Namespace 恰恰在重写这层身份映射，让局部 root 不自动等于全局 root。

### 只要有 Namespace，是不是容器就已经完整成立了？

也不是。没有 Cgroup，你看不见别人，但仍可能把宿主资源吃穿；没有 overlay 和挂载视图，你也很难拥有完整的“这就是我的系统目录树”的体验。

### 容器和虚拟机的差别，是不是只是“一个轻一个重”？

太粗了。更关键的区别是：容器共享内核，只改视角和预算；虚拟机连内核本身也各自独立。这正是下一篇要展开的边界。

## 收束：容器真正高明的地方，不是造了一个新东西，而是把老机制拼成了一个看起来像新东西的世界

现在回到开头那个问题：Docker 到底把一个进程“关”进了什么样的小隔间？答案不是某个神秘盒子，而是一套非常具体的边界工程：看不见什么、最多用多少、根目录看起来是什么、网络入口怎么接进来。容器之所以迷人，不是因为内核凭空长出了一个新物种，而是因为它把 clone、Namespace、Cgroup、overlay、veth 这些本来就存在的机制组合成了一个强大得像新世界的用户体验。

这篇的开场困惑也就闭环了：容器不是迷你虚拟机，而是一个被同一内核重新安排了视角、预算与舞台的普通进程。
