# 锁家族：mutex、spinlock、rwlock、seqlock 与 futex 到底在替你挡什么灾

> 主题：OS 内核｜第 7 篇
> 前置文章：`06-atomic-barriers.md`
> 本篇后续：`08-rcu-deadlock.md`
> 版本说明：本文讨论 Linux 常见锁家族的稳定心智模型；mutex optimistic spinning、qspinlock 细节、rwlock 与 seqlock 策略、futex 语义与等待队列组织会随内核版本、抢占模型和架构演进。本文以“为什么要选这种等待方式”为主线，不把某个版本的结构体位段、固定 cycle 数或特定实现宏当作跨版本契约。

## 争一份数据时，等待者到底该睡，还是该抢着转

上一篇把积木准备好了：我们已经知道 `LOCK`、CAS 和屏障能给出原子性与顺序保证。但只靠这些原语，软件还没有真正得到一个好用的并发控制工具。因为在现实系统里，冲突不是一次性的——线程会反复争同一份状态，持锁时间长短不一，等待者有的能睡，有的根本不能睡，有的读很多写很少，有的用户态绝大多数时候还根本不该进内核。

于是，“怎么同步”就不再只是一个指令问题，而变成了一个等待策略问题：

- 持锁时间可能很短，值不值得让等待者睡一觉再醒？
- 持锁者若被调度走了，让别的线程原地空转会不会白烧 CPU？
- 读远多于写时，还要不要让所有读者都排队？
- 用户态绝大多数无竞争场景，难道也值得每次都陷入内核？

这就是锁家族存在的原因。它们不是很多“语法不同的互斥体”，而是在不同等待成本、并发形态和可中断语义下，对同一个问题给出的不同答案。

先记住本篇总图：

```text
长临界区、等待可能很久
  → mutex：睡眠等待，别白烧 CPU

极短临界区、睡眠成本反而更大
  → spinlock / qspinlock：原地忙等，抢到就走

读远多于写
  → rwlock：让多个读者并行
  → seqlock：让读者几乎无锁，但必要时重试

用户态无竞争是常态
  → futex：快路径留在用户态，慢路径再进内核
```

这一篇最关键的顿悟是：**锁的选择本质上是在决定“等待成本由谁承担、以什么方式承担”。** mutex 让调度器背锅，spinlock 让 CPU 背锅，rwlock 和 seqlock 在读写比例上做文章，futex 则努力把大多数无竞争情况挡在内核外面。证据位应回到 mutex/futex 等待队列、spinlock/qspinlock、rwlock/seqlock 和用户态原子快路径：它们共同支撑“锁家族本质上是在重新分配等待成本”的判断，而不是单纯 API 名称不同。

## 一、mutex：持锁时间可能不短时，别让等待者站在门口白耗着

### 1. 失败方案：所有锁一律自旋

一个最直觉的方案是：加锁失败就原地 while 循环，不停检查，直到别人释放。这样实现很统一，也不用睡眠、唤醒和调度队列。

这个方案在极短临界区里未必糟，但一旦持锁者会被调度走、临界区里可能睡眠、或者资源本身要等外部事件，等待者继续原地转就会变成纯浪费。线程什么都没推进，只是在替系统烧 CPU 和缓存带宽。

所以 mutex 的第一原则很朴素：**如果等待很可能不短，那就别让等待者站着空等。**

### 2. mutex 的核心不是“互斥”，而是“拿不到就睡”

从教学上看，mutex 最重要的不是它也能互斥，而是它和 spinlock 在等待策略上的根本分叉：拿不到锁时，等待者可以进入睡眠队列，让出 CPU；等持锁者释放后，再由唤醒路径把它叫回来继续竞争。

```text
尝试加锁
  ├── 没竞争：直接拿到
  └── 已被占用：加入等待队列 → 睡眠 → 未来被唤醒后再试
```

于是 mutex 真正依赖的不只是原子操作，还依赖调度器和等待队列。它把“等待”这个成本从 CPU 前台燃烧，转移成一次上下文切换和一次唤醒配合。

### 3. 睡眠不是白赚：它是在拿切换成本换 CPU 不空转

这也是为什么 mutex 并不天然优于 spinlock。它只是把代价换了个位置：

- 好处是等待者不再白占一个核空转。
- 代价是你得付睡眠、唤醒、调度切换的固定成本。

所以 mutex 特别适合“临界区可能不短、持锁者可能睡眠、等待者让出 CPU 更划算”的场景；而若临界区短到离谱，睡一觉的代价反而会比等锁本身还贵。

### 4. optimistic spinning 说明 mutex 也承认“有时睡太早不划算”

Linux 并没有教条到“只要是 mutex 就立刻睡”。optimistic spinning 之所以存在，正说明现实更复杂：如果持锁者正在跑，且很可能马上就释放，那么等待者立刻睡下去反而可能得不偿失。

这本质上是在 mutex 里偷偷借了一点 spin 的哲学：先乐观等一下，赌这次冲突非常短；只有当这场等待真的开始像长等待了，才转入睡眠路径。

这也提醒我们，锁家族并不是彼此绝缘的盒子。好的实现经常会跨边界借策略，因为真实系统里的等待长度不是写死的。

### 5. priority inheritance 说明 mutex 还在解决“谁挡了谁”的调度问题

mutex 还有另一个经常被忽视的使命：优先级反转。高优先级任务若在等一个低优先级持有的锁，而低优先级任务又迟迟得不到 CPU，就会出现“最该快的人反而被最慢的人挡住”的反常局面。

priority inheritance 的意义正在这里：不是为了让锁更快，而是为了在调度层面避免锁把系统优先级关系扭曲到不可接受。也就是说，mutex 不只是一个并发原语，它还是等待与调度交界处的一部分秩序维护。

## 二、spinlock：临界区短到连睡一觉都嫌亏时，只能原地抢

### 1. 睡眠路径也有固定成本

如果临界区只有几条指令，或者就在中断、底层热路径里，等待者一旦睡下去，光是切换出去再切换回来，就可能比真正持锁时间更长。

这时，mutex 的优点反过来会变成包袱：你为了不空转而付出的调度成本，比直接等几百个 cycles 还肉疼。

于是 spinlock 的场景就成立了：**如果锁很快就会释放，那原地抢比睡一觉更划算。**

### 2. spinlock 的关键不是“更底层”，而是“等待者持续占着 CPU”

spinlock 的等待方式与 mutex 完全相反。拿不到锁时，线程不睡，而是留在 CPU 上持续忙等，反复检查何时能接手。

```text
尝试加锁
  ├── 成功：进入临界区
  └── 失败：继续在本地循环观察，直到锁可用
```

这让 spinlock 在短临界区里极其高效，因为没有调度切换；但一旦持锁者迟迟不释放，等待者付出的就是真实的 CPU 时间。

### 3. 自旋锁最怕“持锁者不跑了”

这也是为什么自旋锁特别强调持锁路径要短、不要睡眠、不要被长时间抢占。等待者原地烧 CPU 的前提，是它相信前车马上就开。若持锁者自己停在那不动了，后面所有人都在无意义地冒烟。

所以“spinlock 适合短临界区”不是经验口号，而是它唯一能成立的基础假设。

### 4. ticket lock 与 qspinlock：公平不是免费的，缓存争用也不是免费的

让等待者自旋，并不代表实现方式只有一种。ticket lock 的好处是公平——先来先服务，大家按号码等。但它的问题也很明显：所有人盯着同一个位置看“轮到我没有”，这会把缓存行变成公共热点。

如果把上一章的伪共享记忆一起带过来，这个问题会更直观：虽然等待者逻辑上只是“看看号到了没”，并没有真正修改共享数据结构里的业务字段，但硬件看到的仍然是一群核在反复碰同一条锁缓存行。于是 MESI 会不停维护这条热点行的可见状态，等待者越多，缓存一致性流量越重，公平本身就开始变得昂贵。

qspinlock 的改进方向就在这里：让等待队列更像排队系统，而不是所有人围着同一扇门死盯。这样做不是为了让语义更高级，而是为了减少“所有等待者一起抢同一缓存行”的一致性流量。

于是，锁实现的优化核心并不只是“减少指令数”，而是“减少等待者之间彼此制造的缓存灾难”。这和上一篇的伪共享其实是一脉相承的：共享热点行本身就可能拖垮扩展性。

### 5. 为什么自旋锁通常不谈“递归友好”

mutex 常会显式跟踪 owner、等待队列和睡眠语义，自旋锁却更像一种最低延迟的占有声明。你再次进入同一把 spinlock，很多时候系统并不会温柔提醒你“你已经拿过了”，而是直接把自己卡死在原地。

这再次说明，自旋锁追求的不是语义舒适度，而是极短路径上的最低协调成本。它用更苛刻的使用前提，换来最短的热路径。

## 三、读多写少时，“互斥”还不够细：rwlock 和 seqlock 代表两条不同道路

### 1. 失败方案：所有读者也像写者一样排队

如果一个数据结构几乎一直在被读，偶尔才被改一次，而你还让每个读者都按完全互斥方式排队，那么很多本来可以并行的只读访问会白白被串行化。

于是“读多写少”这个场景会逼出新的问题：锁不能只回答“有没有互斥”，还得回答“读者之间到底要不要互相挡”。

### 2. rwlock：读者彼此不挡，但写者得等大家散场

rwlock 的思路很直接：读和读可以并行，写必须独占。也就是说，它把“大家只是来看一眼”与“我要动手改”分成了两个等级。

这让大量并发读场景受益很大，因为读者终于不用再像写者那样互斥。但代价也很明显：只要写者要进来，它就得等所有已经在场的读者散去；如果读流一直不断，写者还可能长时间饥饿。

因此 rwlock 并不是“更高级的 mutex”，而是拿写侧时延去换读侧并发。

### 3. seqlock：连读锁都懒得拿，读到不一致就重来

seqlock 则更激进。它发现某些场景里，读者真正想要的不是“我一定一次成功地读完”，而是“我尽量不被阻塞，如果正巧撞上写者，就重来一遍也行”。

于是它不要求读者真正持有一把排他意义上的锁。写者在更新前后改动序号；读者读开始前看一次，读完再看一次。如果发现中间变了，说明这次快照不可靠，就重读。

```text
读者开始
  → 记下序号
  → 读数据
  → 再看一次序号
  → 若序号变了或处于写中状态：整轮重读
```

这等于把“等待”换成了“乐观读取 + 失败重试”。只要写真的足够少，而读成本又不高，这种策略会让读路径极轻。

### 4. rwlock 与 seqlock 的本质区别，是你让谁付代价

两者都在优化读多写少，但手法完全不同：

- rwlock 让写者为正在读的读者买单。
- seqlock 让撞上写者的读者自己重读买单。

所以选择它们，不是简单看“读多不多”，而是要继续问：读者能不能容忍重试？写者能不能容忍被一群读者挡住？数据是不是小到重读成本可接受？

这也再次证明，锁家族从来不是函数名大全，而是一组“把等待和重试成本分配给不同角色”的策略集合。

## 四、用户态锁为什么不能每次都进内核：futex 的快慢路径分流

### 1. 失败方案：每次加锁失败与成功都走系统调用

如果用户态的每次 mutex 加解锁都立刻陷入内核，那么即使根本没有竞争，程序也要平白承担 syscall 和内核路径成本。这会让“绝大多数时候其实没人抢”的锁操作显得尤其愚蠢。

所以用户态锁最重要的洞察其实很简单：**无竞争才是常态，内核只该处理竞争。**

### 2. futex 的快路径：无竞争时，用户态自己就解决了

futex 的精髓就在于把快路径留在用户态。锁变量先在用户空间用原子操作尝试获取；如果成功，整个过程根本不需要进内核。

只有当发现真的发生竞争、必须等待时，线程才通过 futex 相关系统调用进入内核，把自己挂到等待队列里；释放方再唤醒它。

```text
用户态尝试 CAS 抢锁
  ├── 成功：直接走人，不进内核
  └── 失败：说明有竞争，进入 futex 慢路径等待
```

这让 futex 成为用户态锁的地基：它不是替你定义一整套锁语义，而是替你把“无竞争别来烦内核，有竞争再登记排队”这件事标准化了。

### 3. 这也是为什么 futex 不是“另一个锁类型”，而是一条用户态与内核的分工边界

从机制上讲，futex 最有价值的地方不是名字本身，而是分工：常态交给用户态原子变量，异常态交给内核等待队列。这种快慢路径分离，和前面页缓存、缺页、mutex optimistic spinning 的思想其实是一类东西——都在努力把最昂贵的路径留给真正不得不走的时候。

它也解释了为什么很多用户态锁看上去“非常快”，但一旦竞争突然上来，性能曲线会像换了一套实现。因为无竞争时你测到的是纯用户态原子操作；一旦争用出现，你测到的却变成了系统调用、排队、唤醒和调度器。也就是说，futex 不是把锁永远变快，而是把“贵的那部分”压缩到确实有冲突时才出现。

## 五、锁粒度演进：一把大锁容易想，很多小锁才有并发，但也最容易把自己绕死

### 1. 大锁的诱惑：简单、直白、难错

系统一开始最容易写对的办法，往往就是拿一把大锁把整片共享状态罩住。这样很省心：顺序清楚，不容易漏保护，也不太会出现多把锁交错获取的复杂关系。

问题是，并发度也会一起被罩死。你保护的是“大部分不会真冲突的工作”，却把它们一起串行化了。

### 2. 细粒度锁换来的并发，必须用更复杂的顺序纪律去买

当一把大锁变成按子系统拆、按对象拆、按字段热点拆，系统吞吐会提升，因为不相关的工作终于能并行了。但代价也跟着来：锁一多，获取顺序就变成一张图，而不是一条线。

于是死锁风险开始暴涨。A 先拿锁 1 再拿锁 2，B 先拿锁 2 再拿锁 1，这种 ABBA 问题几乎是细粒度演进的必经税。

### 3. 所以“更细粒度”从来不是无条件更先进

粒度更细，说明你把并发权利下放给了更多局部路径；同时也意味着你把顺序治理的责任分散到了更多人手上。系统不是自动更好，只是把“全局慢”换成了“局部快，但更容易因关系复杂而出事故”。

这也是为什么下一篇会把 RCU 和死锁检测接上来：当传统锁家族已经把“睡眠、自旋、读写优化、用户态快路径”都讲过一遍后，真正难的已经不是知道工具名，而是怎么在大系统里不把自己锁死。

## 六、把这些锁收成一张选择矩阵：你真正要选的不是 API，而是等待策略

现在可以把这一篇的角色重新放回一个选择问题里。

如果临界区可能长、等待者让出 CPU 更划算，用 mutex；如果临界区短得离谱，睡眠固定成本反而更亏，用 spinlock；如果读远多于写，rwlock 或 seqlock 开始登场，但前者让写者等读者，后者让读者重试来换无锁快读；若绝大多数锁操作根本无竞争，那就应该让用户态先用 futex 快路径自己解决，别动不动惊动内核。

```text
锁选择
  → 持锁会不会久？久：偏向睡眠
  → 临界区是不是极短？极短：偏向自旋
  → 读者是不是远多于写者？是：考虑 rwlock / seqlock
  → 无竞争是不是常态？是：让 futex 把快路径留在用户态
```

所以本篇最该记住的一句话是：**锁不是在选“语法上哪把更顺手”，而是在选“这次等待由 CPU、调度器、读者、写者还是用户态自己来付钱”。**

## 七、几个最容易说错的地方

### mutex 一定比 spinlock 更高级吗？

不是。它们只是把等待成本放在不同地方：mutex 让等待者睡，spinlock 让等待者忙等。高级与否取决于场景，不取决于名字。

### spinlock 只是“更快的锁”吗？

也不是。它快的前提是临界区真的很短、持锁者不会长时间跑不动；一旦前提不成立，它会非常浪费。

### rwlock 一定适合所有读多写少场景吗？

不一定。若写者不能接受被大量读者挡住，或者读者可以容忍重试，seqlock 反而可能更合适。

### futex 是不是一个“用户态 mutex 实现细节”，所以不用理解？

最好别这么想。它体现的是并发系统里非常重要的一条原则：无竞争别进内核，只有竞争才调用重量级协调机制。这条原则远不只属于锁。

## 收束：锁的世界没有银弹，只有谁来为等待买单

现在回到开头那个问题：争一份数据时，等待者到底该睡，还是该抢着转？答案从来不是“永远睡”或“永远转”，而是要看持锁时间、调度代价、读写比例、无竞争概率以及能否容忍重试。

也正因为如此，内核才会有一个锁家族，而不是一把万能锁。mutex、spinlock、rwlock、seqlock、futex 不是同义词集合，而是把等待、唤醒、缓存争用和顺序复杂度分配给不同角色的多种治理方案。

这篇的开场困惑也就闭环了：有了原子指令和屏障之后，真正的问题不再是“能不能同步”，而是“在什么场景下，用什么代价、让谁承担等待，才最值得”。

## 八、误解清单、证据清单与边界清单

### 误解清单

- mutex 不比 spinlock“更高级”；它们只是把等待成本放在不同地方。
- spinlock 不是更快的万能锁；一旦持锁路径不够短，它会非常浪费。
- rwlock 不是所有读多写少场景的默认答案；seqlock 可能更适合“读者能重试”的模型。
- futex 不是无关紧要的实现细节；它体现了“无竞争留在用户态，有竞争再进内核”的关键思想。
- 锁粒度越细不代表系统必然更好；并发提升常常用更高的顺序复杂度和死锁风险来买单。

### 证据清单

- mutex：等待队列、调度唤醒、optimistic spinning 与优先级继承路径，支撑“拿不到就睡、必要时短暂乐观自旋”。
- spinlock：qspinlock/ticket lock 与缓存行争用路径，支撑“极短临界区下忙等比睡眠更划算”。
- rwlock/seqlock：读多写少场景下的读并行与读者重试路径，支撑“代价到底让读者还是写者承担”的区别。
- futex：用户态原子快路径与内核慢路径等待队列，支撑“绝大多数无竞争锁操作不该惊动内核”。
- 锁粒度演进：多锁顺序、ABBA 问题与等待关系图，支撑“细粒度并发需要更强顺序宪法”。

### 边界清单

- 本文讨论的是 Linux 常见锁家族的稳定心智模型，不把某一版 qspinlock、mutex optimistic spinning 或 futex 位段细节写成长期契约。
- 锁的选择高度依赖临界区长度、抢占模型、读写比例、无竞争概率和是否允许睡眠，不能按名字做口号式选型。
- rwlock、seqlock、futex 等机制解决的是不同等待形态，不存在“一个锁统治所有热点”的现实。
- 细粒度锁把并发权限下放给更多局部路径，也把死锁、活锁和锁顺序错误风险同步放大。
