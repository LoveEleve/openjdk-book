## 连续地址空间，其实是一场成功的伪装

上一篇解决的是物理页从哪里来：Buddy 负责页块，SLUB 负责对象，NUMA 决定先从哪里取，memblock 顶住启动早期。但那篇还留下了一个更像魔术的问题：如果物理页本来就是碎片化分布的，为什么进程眼里却像拿到了一整条连续地址空间？

你在代码里写：

```c
*p = 42;
```

看起来只是把 42 写进某个地址。但 CPU 真正面对的问题并不是“把 42 写入内存”这么简单，而是：

- `p` 这个虚拟地址属于哪个进程？
- 它映射到哪一个物理页？
- 这页现在在不在内存里？
- 当前线程有没有写权限？
- 如果另一个 CPU 刚修改过这条映射，本核是不是还在用旧缓存？

如果没有一套统一的翻译机制，操作系统就只能把所有程序都暴露给真实物理地址。那样不仅无法隔离进程，也无法让零散物理页看起来像连续空间。分页的本质，就是让 CPU 每次访问都先经过一张“翻译地图”，再决定最终碰哪一页物理内存。

先记住本篇总图：

```text
虚拟地址
  → 查当前进程页表根
  → 逐级定位页表项
  → 读出物理页帧号和权限位
  → 拼出物理地址
  → 若 TLB 已缓存映射，可跳过大部分查表

同时，页表项不只回答“去哪一页”
  还回答“能不能读写执行”“这页是否访问过”“是否脏了”
```

这套机制最关键的顿悟是：**连续地址空间不是物理事实，而是页表翻译产物。** 进程看到的是连续虚拟页号，内核维护的是一组离散映射关系，CPU 再把两者在访问瞬间接起来。

## 一、先问最朴素的问题：为什么不能直接用一个超大数组映射所有地址

### 1. 最直觉的做法

假设一个进程拥有 4GB 虚拟地址空间，页大小是 4KB。那么最直接的想法是：准备一张巨大的数组，数组每一项对应一个虚拟页，项里记这页映射到哪个物理页。访问一个虚拟地址时，CPU 只要拿虚拟页号做下标，取出物理页号，再加上页内偏移，就完成翻译了。

这个方案有一个明显优点：查找路径简单，甚至接近一次索引就能拿到答案。

但它的问题也同样明显。一个 4GB 地址空间如果按 4KB 分页，会有大约一百万个虚拟页；即使每项只占 8 字节，一张完整页表也要消耗数 MB。更糟的是，大部分进程根本不会用满整个 4GB，更不会把每一段地址都映射成真实物理页。也就是说，你为了让“理论上可能存在”的地址可查，提前为大量根本不会出现的区域付出了页表内存。

分页真正要解决的不是“怎么查一次”，而是“怎样让未使用的地址空间不提前付费”。这就是多级页表出现的原因。

### 2. 多级页表：不是把整本电话簿印出来，而是按目录逐层翻

多级页表的核心思想很简单：不要提前为整段虚拟地址空间建一张完整大表，而是先建高层目录。只有当某一大段地址真的被用到时，才继续分配下一层页表页。

对于 x86-64 上常见的 48 位虚拟地址心智模型，可以先把地址理解成几段索引加一个页内偏移：

```text
虚拟地址
  → 顶层索引
  → 第二层索引
  → 第三层索引
  → 第四层索引
  → 4KB 页内偏移
```

每一级索引都只负责回答一个问题：往下走哪一个子表。真正给出物理页帧号和权限的，是最底层页表项。于是，一次地址翻译看起来更像在翻一本按章节、目录和子目录组织的手册，而不是查一张事先铺满所有条目的超级表。

从行为上看，CPU 会先从当前页表根出发，按虚拟地址中的几段索引逐级向下。只有走到最后一级表项，才拿到物理页帧号。于是，多级页表用更多层次换来了一个重要收益：未使用的大段地址空间根本不需要分配下层页表页。

### 3. 这里的“连续”只存在于虚拟页号

一段 100MB 的数组在用户看来是连续地址。对分页系统来说，这句话其实只表示“这一串虚拟页号相邻”。底层物理页完全可能来自不同的物理位置，甚至来自不同的 NUMA 节点。页表做的事，不是让物理页真的排成一条长带，而是让相邻虚拟页分别映射到各自的物理页后，仍然表现成连续地址空间。

```text
虚拟页 0x1000 → 物理页 A
虚拟页 0x1001 → 物理页 K
虚拟页 0x1002 → 物理页 C
虚拟页 0x1003 → 物理页 Q

对进程来说：地址连续
对内核来说：映射离散
```

这就是本篇必须先讲透的第一层：连续是编号连续，不是物理位置连续。只要页表项一条条接好，CPU 就会把它当作连续空间使用。

## 二、页表遍历：CPU 到底怎样从虚拟地址走到物理页

### 1. 一次解引用，先拆成“页号 + 偏移”

当程序写 `*p = 42`，CPU 并不会拿整个虚拟地址直接当物理地址用。它先把地址拆成两部分：高位用于逐级索引页表，低位作为页内偏移。页大小是 4KB 时，偏移部分需要 12 位，因为 4KB 就是 `2^12` 字节。

这意味着：只要最终找到物理页帧号，页内偏移就可以原样带过去。翻译真正要解决的是“这个虚拟页号现在对应哪一个物理页帧”。

### 2. 从页表根开始逐级向下

每个进程都有自己的页表根。CPU 当前运行某个进程时，会把这个进程的页表根地址装进硬件寄存器；随后每次遇到虚拟地址访问，MMU 都以这个根为起点逐级查表。

```text
当前进程的页表根
  → 顶层索引选中一个子表
  → 下一层索引再选中一个子表
  → 再下一层索引继续缩小范围
  → 最后一层页表项给出 PFN 和标志位
  → PFN + 页内偏移 = 物理地址
```

从教学上可以把它理解成“四次翻目录再找到正文”；若开启五级页表，原理不变，只是多了一层目录。这里重要的不是死背缩写，而是理解层次角色：高层负责裁剪地址范围，底层负责给出真正映射。

### 3. 多级页表用时间换空间

这个设计的代价也很直接：如果没有缓存帮助，一次地址翻译不是零成本的。CPU 可能要读取多级页表页，最后再去访问真正的数据页。这就是为什么页表常被说成“用时间换空间”：

- 换来的空间收益：未使用地址空间不需要提前分配整张大表。
- 付出的时间成本：地址首次访问时，要经历逐级页表遍历。

所以多级页表不是“更快的查找结构”，而是“更省空间的按需展开结构”。如果系统只有页表而没有后面的缓存机制，内存访问延迟会非常难看。TLB 的意义，就是把这笔重复翻译成本压回去。

### 4. 五级页表不是另一套机制，只是把同一套路再多上一层

很多读者第一次听到五级页表，会以为它代表了新的分页哲学。其实不是。它只是地址空间变大后，把同样的层级查表逻辑再扩展一层。四级页表和五级页表的区别，本质上不是“翻译方法变了”，而是“可覆盖的虚拟地址范围更大了”。

因此，本篇不把注意力放在某个具体位段数字上，而是放在稳定机制上：**页表遍历总是在做一件事——逐层缩小范围，直到拿到最终页表项。**

## 三、PTE 不只是地址：它同时承载权限、状态与异常入口

### 1. 只知道去哪一页，还不够

如果页表项只记录物理页帧号，CPU 最多只能知道“地址该落到哪里”。但真实系统还必须回答另外几个问题：这页是否已经装入内存？当前访问能否写入？用户态能不能碰？这页最近是否被访问过？执行代码时允不允许从这里取指令？

这些问题如果交给软件在访问后再检查，就太晚了。CPU 必须在真正读写内存前就知道答案。因此，页表项除了物理页帧号，还会带权限位和状态位。

### 2. Present、RW、User、NX：最先要抓住的四类位

理解分页时，最重要的是先抓住四类最常见位：

- `Present`：这条映射当前是否有效；无效时会触发缺页异常。
- `RW`：当前页是否允许写入；只读页上的写入可能触发写保护异常，也是 COW 的关键入口之一。
- `User/Supervisor`：用户态是否允许访问；很多内核地址对用户态天然不可见。
- `NX`：这页是否允许执行；它和只写不可执行策略一起构成常见执行防护基础。

这里最容易误解的是：权限位不是“内核事后参考一下的附加信息”，而是 MMU 在访问路径上立即执行的门禁。也正因为如此，它们成为缺页、写保护、用户态越权和不可执行保护的共同硬件入口。

### 3. Accessed 和 Dirty：内核判断“这页最近还值不值得留”的线索

页表项里还有一类位，不是用来立刻拒绝访问，而是为内核提供行为线索。最典型的就是 Accessed 和 Dirty。

- `Accessed` 表示这页最近被碰过。
- `Dirty` 表示这页被写过，页内容与后备存储相比已经变脏。

它们的重要性在于：内核做页回收、老化和回写时，不可能给每页维护一套昂贵的精细访存日志。页表位正好提供了一种硬件帮忙打点的办法。内核之后读取这些位，就能大致判断哪些页活跃、哪些页脏了、哪些页更适合先回收。

因此，PTE 不是单纯的“翻译结果”，而更像一张地址访问小档案：既告诉 CPU 去哪，也告诉内核这页最近经历了什么。

### 4. COW 的开关为什么落在写权限上

很多读者第一次接触写时拷贝，会把注意力放在“复制页”这件事上。更关键的其实是：**内核怎么知道现在该复制了。**

答案就落在页表写权限上。共享页在初始阶段可以被多个进程共同映射，但它们会被设置成不允许直接写。于是第一次写入时，CPU 先因为写保护触发异常；内核再检查这是不是一个合法的 COW 场景，若是，就分配新页、复制旧内容、修改页表，让本进程写向自己的私有页。

也就是说，COW 的触发点不是某个后台线程定时扫描，而是一次真实写入先撞上 PTE 的权限门。页表位因此不仅在做安全控制，也在做延迟分配与写时复制的控制分流。

## 四、如果每次都查多级页表，CPU 早就被翻译拖垮了

### 1. TLB 是页表的近路，不是另一份页表

到这里，一个新问题立刻出现：如果每次访存都要走一次多级页表遍历，CPU 为什么还能跑得这么快？

答案是 TLB。它缓存的不是普通数据，而是“虚拟页号到物理页帧号”的翻译结果。换句话说，TLB 记住的是某些页表遍历的最终答案。

```text
TLB 命中
  → 直接得到页帧号和关键权限
  → 跳过大部分页表遍历

TLB 未命中
  → 执行 page table walk
  → 得到翻译结果
  → 把结果放入 TLB
```

因此，TLB 不是另一张完整页表，而是对热映射的近路缓存。它让“第一次查表比较贵，后续重复访问便宜得多”成为可能。

### 2. 命中率为什么比单次延迟更重要

TLB 的条目数远小于理论虚拟页数，这意味着它不可能记住全部映射。真正决定性能的，是工作集是否足够局部，能让热点虚拟页长时间留在 TLB 里。

这也是为什么我们更关心 TLB 命中率，而不是某一次 miss 的绝对代价。命中率从 99% 掉到 95%，看起来只差几个百分点，实际意味着 miss 数量可能成倍增加，进而把大量时间重新花回页表遍历和后续访存上。对缓存友好的代码、紧凑的数据布局和合适的页大小，最终都会体现在 TLB 行为上。

如果想建立一个更直观的时序感，可以把一次 TLB miss 理解成两段成本叠加：先重新读取若干级页表页，拿到最终页表项；然后才去读真正的数据页。也就是说，miss 不是“多一次普通 cache miss”，而是“先重新翻地图，再去目的地”。这也是为什么它常常会把延迟放大得比直觉更明显。

### 3. TLB 一致性：为什么改了页表还不够

另一个很容易低估的问题，是跨 CPU 一致性。假设一个 CPU 修改了某条页表项，把某页改成只读，或者把某个映射拆掉；另一个 CPU 如果还保留着旧的 TLB 项，就可能继续按过期权限访问。

这就是 TLB shootdown 的背景。修改页表后，内核不能只改内存中的页表项，还必须让可能持有旧翻译缓存的 CPU 失效相关 TLB 项。

```text
修改页表
  → 找到正在使用该地址空间的 CPU
  → 发出 IPI 或其他失效通知
  → 目标 CPU 刷新对应 TLB 项或范围
  → 之后新访问才会重新查表
```

这里的成本很真实：页表更新不是免费改一个数字，它还可能牵动跨核通知和刷新。因此权限频繁变更、映射频繁拆建的系统，开销不只来自页表本身，也来自 TLB 一致性维护。

### 4. 内核全局映射为什么常常希望别被频繁刷掉

内核代码和常用内核映射会被各进程反复进入，比如系统调用、中断和异常路径。若进程切换时把这些高频内核映射的翻译也一起冲掉，TLB 会不断重学同样内容。因此，硬件和内核会提供一些办法，让某些全局映射尽量跨切换保留。

本质上，这仍然是在做同一件事：不要为“所有进程都反复会用到”的地址，每次都重新付翻译成本。后面讲高半区共享时，你会看到这套思路为什么与内核映射天然契合。

## 五、大页：不是为了省页表页，而是为了让 TLB 一次记住更大片范围

### 1. 4KB 页的灵活，换来更多翻译条目

小页的好处是灵活：内部浪费小，碎片更容易控制，缺页和回收的粒度也细。但它的代价是，覆盖大内存工作集时，需要更多页表项和更多 TLB 条目。

这时候大页的价值就体现出来了。2MB 页不是“更高级的页”，它只是让一条映射覆盖更多连续虚拟地址，也覆盖更多连续物理地址。这样，同样数量的 TLB 项，可以代表更大的内存范围。

```text
4KB 页：走到最后一级页表项，条目细，灵活但数量多
2MB 页：在更高一级就给出映射，不再继续细分 4KB 子页
1GB 页：更早停下，一条映射覆盖更大片范围，但约束也最强
```

从机制上说，大页之所以减少翻译成本，并不是“把普通页表项变大”这么简单，而是让 page table walk 在更高层就提前结束：原本还要继续向下找最后一级表项，现在上层条目自己就已经代表整块区域。于是，不仅 TLB 一项能覆盖更大范围，页表遍历本身也少走了几步。

所以大页优化的核心，不是让页表看起来更整齐，而是减少 TLB 压力，提高翻译缓存覆盖率。

### 2. 大页不是白赚：它要求更强的连续性和更粗的管理粒度

大页之所以能减少翻译条目，是因为它用更大粒度代表一整片区域。但这立刻带来两个约束。

第一，需要更大块的连续物理内存。第二，回收、迁移、拆分和权限管理的粒度也更粗。一旦你的工作集并不稳定，或者系统已经高度碎片化，大页分配和维护就可能变得昂贵。

这就是为什么大页从来不是“开了就更快”的通用结论。它在高局部性、大内存热集场景里可能很有价值；在对延迟毛刺敏感、内存碎片严重或生命周期混乱的场景里，也可能把问题放大。

### 3. THP 的真正代价：自动化背后的停顿与规整成本

透明大页最诱人的地方，是应用看起来“不用改代码”。但自动化并不意味着没有代价。内核为了把许多小页折叠成大页，或者为了给大页找出连续物理空间，可能要做规整、迁移和后台合并。

这时，读者要警惕一个常见误区：数据库或缓存系统关闭 THP，并不等于它们不想要更高 TLB 命中率；更常见的原因是，它们更害怕不可预测的分配延迟与抖动。于是问题变成了“吞吐潜力”和“尾延迟稳定性”之间的权衡，而不是“大页一定好”或者“一定坏”。

因此，大页这一节真正要记住的是：**它优化的是翻译覆盖率，代价则通常落在连续物理内存、后台规整和延迟稳定性上。**

## 六、每个进程都有自己的页表，那内核地址为什么还像是共享的

### 1. 进程私有，不等于整个地址空间全部私有

既然每个进程都有自己的页表，最自然的疑问是：系统调用进入内核时，内核代码难道还要临时切换到另一整套地址空间？如果真这样做，开销会非常高，而且异常和中断路径也会变得复杂。

Linux 的常见做法，是让进程页表里的用户态部分保持私有，而内核空间那一半映射在多个进程之间按模板共享。于是，切换进程时主要变化的是用户地址部分；内核常驻映射可以以相对稳定的方式出现在多个进程的页表中。

### 2. 高半区共享，解决的是“进入内核时别重新盖一座城”

从教学上可以先把地址空间理解成两块：

- 低半区主要放当前进程的用户态映射。
- 高半区主要放内核共享映射，如内核镜像、直接映射和若干内核专用区域。

```text
一个进程的地址空间
  ├── 低半区：本进程私有用户映射
  └── 高半区：多数进程共用的内核映射模板
```

这样做的好处很直接：线程从用户态陷入内核态时，不需要把内核代码和核心数据重新映射一遍。CPU 进入内核后，仍然能顺着当前地址空间中的共享高半区找到内核逻辑。

这里同样要避免说过头：高半区共享是常见心智模型，但具体布局、是否完整保留、KPTI 等安全机制引入的额外切换与隔离，会受架构和内核版本影响。本文只抓稳定主线：**进程页表并不是“所有部分都彼此完全不同”，内核映射通常会复用一份共享框架。**

### 3. 这也解释了为什么某些内核映射值得被 TLB 长期记住

高半区共享与 TLB 的关系很自然。既然这些映射在许多进程中都会被反复用到，那么尽量减少它们在切换中的失效，就能降低内核入口和常用内核路径的翻译重建成本。

所以，页表结构、TLB 策略和内核高半区布局不是三件独立的事。它们共同围绕一个目标：既让用户空间彼此隔离，又不要让每次进入内核都像切换到一块完全陌生的土地。

## 七、把整条链路收起来：一次 `*p = 42` 真正经历了什么

现在可以回到开头那个看似简单的写操作。

首先，CPU 看到的是虚拟地址，不是物理地址。它从当前进程的页表根出发，按地址中的几段索引逐级走向目标页表项。若 TLB 已经缓存了对应映射，这条近路会让大部分查表被跳过；若没有命中，就执行一次完整遍历。

拿到页表项后，CPU 不只是得到一个物理页帧号，还会同时检查 Present、写权限、用户权限和执行权限等位。若写入落在只读共享页上，这里可能触发写保护异常，把控制权交给内核进入 COW 路径；若页根本不存在，则可能触发缺页处理，由下一篇要讲的 VMA 和缺页异常机制继续接手。

如果这条映射被改动过，内核还要考虑其他 CPU 是否保留着旧 TLB 项；必要时要做 TLB shootdown，防止旧翻译继续生效。若工作集很大，系统还会考虑是否值得用大页提升 TLB 覆盖率；若线程进入内核，页表中的共享高半区让它不必临时为内核再拼一套新地图。

```text
虚拟地址访问
  → TLB 命中？命中则直接取翻译
  → 未命中则 page table walk
  → 读到 PTE：同时得到 PFN 与权限/状态
  → 权限允许：访问物理页
  → 权限不允许或映射缺失：进入异常路径
  → 页表有改动时：必要时同步其他 CPU 的 TLB
```

因此，本篇开头那句“连续地址空间是一场成功的伪装”，现在可以落地成更准确的话：

- 连续的是虚拟页编号，不是物理页排布。
- 页表负责把离散物理页接成连续抽象。
- PTE 决定这条抽象现在是否可访问、可写、可执行。
- TLB 负责让这套抽象在高频访问下仍然跑得动。
- 大页负责扩大单条翻译缓存的覆盖面。
- 高半区共享负责让每进程页表既能隔离用户空间，又能高效进入内核。

## 八、几个最容易说错的地方

### 页表是不是为了让内存连续分配？

不是。页表恰恰是为了让底层可以不连续。它把“连续虚拟地址”与“离散物理页”解耦，让内核不必先找到一大片物理连续内存，才能给进程提供一段连续空间。

### TLB 是不是普通数据缓存？

也不是。它缓存的是地址翻译结果，而不是用户数据本身。TLB 命中只能说明“这次不用重新翻地图”，不等于数据一定在 L1/L2 cache 里。

### 大页是不是一定比 4KB 页更好？

不是。它通常能提升翻译覆盖率，但会带来更高的连续性要求、更粗的管理粒度，以及可能的规整和延迟成本。是否值得，要看 workload 更在乎吞吐还是尾延迟。

### 进程切换是不是等于全部 TLB 内容都无条件清空？

不能这么绝对。具体刷新策略会受体系结构能力和内核实现影响，例如是否利用地址空间标签、是否保留某些全局映射、是否启用额外安全隔离。更稳妥的说法是：进程切换可能显著影响 TLB 有效内容，而内核会尽量减少不必要的失效成本。

## 收束：页表不是地图册，它更像实时边检系统

如果只把页表理解成“虚拟地址到物理地址的对照表”，会漏掉一半真相。它当然在做翻译，但它也是权限入口、异常分流点、活跃度线索来源，以及跨 CPU 一致性维护的基础。TLB 又把这套原本昂贵的翻译过程压缩成高频场景下可接受的成本；大页与高半区共享，则分别从覆盖率和复用角度继续为这套机制减负。

因此，分页真正建立的不是一张静态表，而是一套运行中的访问秩序：谁能看、谁能写、这页是否存在、改了映射后别的 CPU 怎么同步、哪些映射值得长期记住，全部都沿着这条路径发生。

开篇的问题也就回收了：进程看到的连续地址空间，并不是内核提前准备好的一整块连续物理内存，而是 CPU 每次访问时都依据页表和缓存机制实时拼出来的结果。

但这篇还刻意留了一个空白：页表解释了“地址怎么翻译”，却还没有回答“这条映射什么时候真正出现”。这正是为什么一个进程先拿到一大片虚拟地址时，RSS 不一定立刻上涨；只有真正访问、触发缺页并完成分配后，映射才会落到具体物理页上。
