# MESI、Store Buffer 与伪共享：为什么多核各写各的，也可能越跑越慢

> 主题：OS 内核｜第 5 篇
> 前置文章：`01-buddy-slab-physical-memory.md`
> 本篇后续：`06-atomic-barriers.md`
> 版本说明：本文讨论现代多核 CPU 上稳定的缓存一致性心智模型；MESI/MOESI 变体、缓存层次、包含性策略、Store Buffer 细节、内存模型术语和 `perf c2c` 观测表现会随处理器架构、微架构和工具版本变化。文中的硬件术语以 x86 常见实现为主线做教学解释，不把某一代处理器的具体容量、端口数或时序细节当作普遍常量。

## 为什么两个核各写各的变量，程序反而更慢了

很多人第一次学并发时，会天然把内存想成一张共享大表：变量 `x` 放在主存里，所有 CPU 都去读这一份；如果两个核同时操作同一个变量，才会出问题；如果它们各写各的变量，就应该互不干扰。

这个直觉在单核时代还勉强好用，到了多核缓存体系里就会马上失灵。真实情况是，每个核前面都有自己的缓存层。核 0 看到的 `x`，往往先是自己缓存里的一份副本；核 1 看到的，也可能是另一份副本。于是“同一个变量只有一个值”不再是硬件天然事实，而是缓存一致性协议努力维持出来的表象。

这件事一旦想通，很多看似诡异的现象就串起来了：

- 为什么两个核分别读写同一变量时，值的可见性不是瞬时的。
- 为什么写操作有时看起来已经执行了，其他核却还没看见。
- 为什么两个线程各写各的计数器，只因它们挨得太近，就会把性能打到地上。

先记住本篇总图：

```text
每个核先操作自己的缓存副本
  → MESI 决定副本之间如何“看起来一致”
  → Store Buffer 让写操作不必次次等全局确认
  → 代价是可见顺序和直觉顺序可能分离
  → 一致性的最小单位是缓存行，不是变量
  → 于是出现伪共享：逻辑无共享，硬件却在抢同一行
```

这一篇最核心的顿悟是：**多核下你以为在共享变量，硬件实际在共享的是缓存行；你以为写已经完成，很多时候它只是先进入了写缓冲。** 证据位应回到缓存一致性协议、store buffer、cache line 粒度与 `perf c2c`/HITM 观测路径：它们支撑“共享的是缓存行而不是源码变量”“写完成与他核可见之间可能有延迟”这两条主线，但不能把某一代微架构的具体时序当成普适常量。

## 一、先推翻一个直觉：多核并不是都盯着主存里同一份值在干活

### 1. 一个看起来合理、实际上根本跑不动的方案

最朴素的想法是：所有核的每次 load 和 store 都直接去主存。这样当然最“一致”——反正没有副本，大家看到的永远是主存里同一个值。

但这个方案等于放弃缓存。CPU 和主存之间的速度差距太大，如果每次读写都真的穿透到主存，多核的计算单元大部分时间只会在空等数据回来。现代处理器之所以能快，就是因为把热点数据先放在离核心更近的层次里。

所以，多核系统不可能靠“所有访问都直达主存”来保证一致。它必须允许每个核先读写自己的缓存副本，然后再想办法让这些副本在系统层面不互相撒谎。

### 2. 一致性协议解决的不是“要不要缓存”，而是“缓存副本怎么共存”

有了每核缓存，问题就从“数据怎么快一点”升级成“多份副本怎么别打架”。如果核 0 把一条缓存行里的数据改了，核 1 还拿着旧副本继续读，就会立刻出现一个新问题：哪份才算最新？

MESI 之类的一致性协议，做的就是这件事。它不关心你的变量名叫 `x` 还是 `counter`，它关心的是某一条缓存行当前在每个核眼里是什么身份：谁拥有修改权，谁的副本已经失效，谁还可以共享读取。

所以一致性协议不是“额外附加的优化”，而是“允许多核缓存继续存在的生存条件”。没有它，多核缓存不是加速器，而会变成制造错误结果的工厂。

## 二、MESI：缓存行不是一份数据，而是一个带身份的副本

### 1. 协议管理的是缓存行，不是变量

理解 MESI 的第一件事，是别把它想成“给变量加四种状态”。硬件不知道你的源码里哪里是一个变量，它只知道 cache line，也就是固定粒度的一段连续字节。很多架构里，这个粒度常常是 64B。

于是，真正被 MESI 管理的对象是“某个核里这条缓存行的副本”。它的状态大致反映两件事：

- 这条副本是不是有效。
- 这条副本和其他核、和主存之间是什么关系。

### 2. 四种状态，本质上是在回答“这份副本现在算不算权威”

从教学上可以把四种状态先理解成四个身份：

- `Modified`：这份副本被本核改过，主存还没跟上，本核此刻最像唯一权威。
- `Exclusive`：只有本核持有这份干净副本，内容与主存一致，但别人还没共享到。
- `Shared`：多个核都能读这份内容，大家看到的是同一版干净数据。
- `Invalid`：这份副本已经失效，再想用得重新取。

真正重要的不是背定义，而是理解它们背后的因果：只要一份副本允许被多个核同时安全读取，它就不能随意让某一核私自改写而不通知别人；反过来，只要某核想独占修改，它就必须让别人的旧副本失效。

### 3. 从 Shared 到 Modified，为什么写会突然变慢

读共享页很容易理解：大家都读同一版，问题不大。真正麻烦的是“本来大家都在读的这一行，现在某个核要写”。

这时，缓存行不能还保持 Shared。因为只要别人还保留着可读副本，本核写完以后，系统里就会同时存在新旧两版内容。于是写入方必须先发出某种“作废通知”，让其他核承认自己手里的这行已经不算数，随后当前核才能把这行升级成 Modified 并安全写入。

```text
原来：核0 和 核1 都持有 Shared 副本
核0 想写
  → 先让核1 的这一行作废
  → 确认别人不再持有可用旧副本
  → 核0 才能把本地行升级为 Modified
  → 然后真正修改
```

这就是很多写操作变慢的根源：它不只是在本核写一份数据，还要先协调“别人那几份别再当真”。

### 4. “同一个变量”在多核下其实是一个不断对账的错觉

到这里可以回看最开始那个问题：两个核同时 `x++`，为什么结果和时序不能只靠源码顺序理解？因为每个核在开始时看到的，都可能是自己缓存里的那份 `x`。想让“同一个 `x`”在全系统里维持一个能被大家接受的版本，就必须让每次写都经历获取修改权、使别人失效、再提交新值的过程。

这里还有一个特别容易让读者误判的陷阱：`x++` 在高级语言里看起来像一件事，在硬件上却往往至少包含“读旧值、加一、写回新值”几个阶段。也就是说，它并不会因为语法上只写了一次 `++`，就自动获得跨核原子性。你在源码里看到的是一个表达式，硬件真正执行的却是一连串可能被别的核打断、争抢缓存行修改权、甚至被缓冲延迟可见的动作。也正因为如此，下一篇才必须引入原子指令和屏障；否则我们只是知道“会打架”，却还没有任何可靠手段告诉硬件“这次别拆开算”。

所以，多核下“共享变量”并不是一个原始事实，而是一种经过协议维护后的错觉。这个错觉非常有用，但维持它是有成本的。

## 三、Store Buffer：为了别让每次写都卡在总线上，CPU 学会了先记账再结算

### 1. 如果每次写都等别人全部确认，流水线会被拖死

前一节已经看到，从 Shared 升级到 Modified 往往要让别的核失效确认。假如 CPU 每次执行 store 都必须原地等待这整个过程完成，再继续执行后续指令，那么写密集程序的流水线会频繁被远端确认拖住。

现代处理器不会愿意这样做。它更希望：当前这次写先记下来，本核先继续往后跑，至于这条写在系统里何时真正对别人可见，可以稍后再慢慢结算。

### 2. Store Buffer 干的就是“写先入账，本核先走”

Store Buffer 可以先把待写入的内容挂起来。对本核来说，程序好像已经执行过这条 store，可以继续往下发射和执行；对全系统来说，这条写还在往外传播、争取缓存行修改权或等待后续提交。

```text
本核执行写
  → 先进入 Store Buffer
  → 本核后续指令继续推进
  → 稍后再真正把结果提交到缓存一致性可见层
```

这让写操作在很多时候看起来没那么贵，因为 CPU 并不总是在前台傻等所有协调结束。

### 3. 为什么本核“已经写了”，别人却还没看见

Store Buffer 一出现，顺序直觉就开始松动。对当前核来说，它后面的某条读取甚至可能已经能通过 forwarding 看到自己刚写进去、还没完全全局可见的值；但对其他核来说，这条写也许还没真正离开缓冲、还没传播到它能看见的层次。

于是就出现了一个非常反直觉但非常重要的现象：**程序在本核看来已经写完，不等于其他核此刻也一定能看见这个结果。**

这并不是错误，而是硬件为了吞吐做出的妥协：一致性最终还是要维护，但“立即全局同步”不再是每条写的默认前台代价。

### 4. 这正是内存屏障要存在的根本原因

只要写可以先缓冲，读写的表面顺序和全局可见顺序就可能分离。于是软件在某些关键点上就需要一种手段，明确要求处理器“别再往后糊弄了，先把前面的写真正结算好”。

很多工程师第一次接触 x86 内存模型时，会得出一个危险但常见的半结论：既然 x86 比很多弱内存模型“更强”，那是不是基本不用操心顺序问题？这正是需要提前掐掉的失败方案。x86 的确帮你保留了不少直觉顺序，但它并没有承诺“你写完了，别人立刻就一定看见”；Store Buffer 仍然会把本核执行与他核可见拉开，跨核同步点仍然需要原子指令、锁语义或显式屏障来收口。也就是说，x86 只是替你少踩一部分坑，不是替你把坑全部填平。

这就是下一篇屏障和原子操作的根。屏障并不是凭空生出的语法仪式，而是因为硬件早就学会了为了性能而先欠账。

所以你可以把 Store Buffer 理解成一切后续内存序问题的起点：它救了吞吐，也制造了顺序直觉的裂缝。

## 四、伪共享：代码明明各写各的，为什么硬件却把它们判成同一场冲突

### 1. 真正共享的不是变量，而是缓存行

伪共享之所以隐蔽，就隐蔽在这里：程序逻辑上没有共享变量，硬件层面却仍然在共享同一条缓存行。

假设线程 A 只写 `counterA`，线程 B 只写 `counterB`。如果这两个字段恰好落在同一条 64B 缓存行里，那么对 MESI 来说，它们不是“两处独立数据”，而是“同一行里的两个偏移”。只要 A 改了自己的那个字段，整条行的状态就会变化；B 想改自己的字段，又得把整条行抢回去。

### 2. 伪共享不是争一个变量，而是抢一张桌子

可以把缓存行想成一张桌子。A 和 B 虽然写的是各自的纸，但纸都放在同一张桌上。只要一致性协议的最小保护单位是整张桌子，而不是纸上的单个字节，那么 A 一动笔，B 那边的整张桌子就可能失效；B 再写，又把桌子抢回去。

```text
核0 改字段 A
  → 获得整条缓存行的修改权
  → 其他核这条行失效

核1 改字段 B
  → 又要把同一条缓存行抢回来
  → 核0 那边失效

结果：逻辑各写各的，硬件却在反复乒乓同一行
```

这就是“伪共享”名字的由来：共享是假的，缓存行冲突是真的。

### 3. 为什么它会把扩核性能直接打垮

伪共享最可怕的地方，不是结果算错，而是结果完全正确、性能却突然塌掉。你会看到 CPU 很忙，多线程也都在跑，但吞吐不升反降。其根因不是锁竞争，也不是显式同步，而是缓存行在多个核之间来回失效、重取、再失效。

这类问题特别适合让人误判。因为从源码上看，每个线程确实在写自己的字段；从宏观监控上看，也未必马上出现明显的锁热点。真正的瓶颈藏在 cache-to-cache 的一致性来回拉扯里。

### 4. 伪共享的修复不是“换算法”，而常常只是让它们别坐同一张桌

因此，伪共享的经典修法并不神秘：把这些高频更新、会落在不同线程上的字段故意拉开，让它们不要落在同一条缓存行里。内核里会有 `____cacheline_aligned` 这样的宏，其他语言生态也有对应对齐或填充手段。

换句话说，修复伪共享并不总是在改并发算法本身，很多时候只是在尊重硬件的一条朴素事实：它按行维护一致性，不按变量维护一致性。

### 5. `perf c2c` 为什么能抓到它

伪共享最适合用 cache-to-cache 视角看，因为问题根本不在单核 cache miss，而在“这条数据总是要从别的核手里转过来”。像 `perf c2c` 这类工具关注的正是这种核间缓存传递、HITM 等现象。

HITM 之所以关键，是因为它几乎就在对你直说：这次命中不是从一份安静的共享副本里读出来的，而是要去碰另一核手里那份修改过、因此更像当前权威的缓存行。换句话说，当 HITM 很高时，你看到的往往不是普通局部性问题，而是缓存行正在多个核之间来回交接修改权。这正好与伪共享的主症状对上：程序逻辑没错，核也都在忙，但热点行总是处在“你刚改完、我又来抢”的乒乓里。

所以当你看到程序逻辑没有明显共享，却在多核扩展上异常差时，不要只盯锁，不要只盯 CPU 百分比，也要怀疑：是不是大家其实正坐在同一条缓存行上打架。

## 五、多级缓存架构：这些一致性麻烦不是漂在空气里，它们发生在分层缓存之上

### 1. 一致性问题并不是“缓存有了就自动解决”

到现在你已经能看出，多核缓存并不是单层平面。每个核前面至少会有更近的私有缓存，系统还会有更远但更大的共享层。也正因为有这种层次，一致性才不是“两个核和主存三点连线”这么简单，而是要在多个缓存层之间协调。

从教学角度，先抓住一个稳定心智模型就够了：

- 越靠近核心，容量越小、延迟越低。
- 越往外走，容量越大、共享范围越广。
- 一致性协议必须能跨这些层次追踪一条缓存行当前在哪些地方有效。

### 2. 为什么共享的最后一级缓存常常承担“对账站”角色

很多实现里，最后一级缓存对多核是一种公共交汇层。你可以先把它理解成大家最终要对账的公告栏：私有 L1/L2 让每个核先跑得飞快，共享更外层则让系统更容易知道某条行到底还被谁持有、失效该往哪边传播。

这里不必把某一代处理器的 inclusive、non-inclusive、victim cache 等细节全部提前背完。对当前主线来说，更重要的是理解：缓存层次越复杂，一致性越不可能靠“每次都广播问所有人”粗暴解决，它总要依托某种层级化组织。

### 3. 这也是为什么我们前面一直强调“硬件维护的是行，不是高级语言语义”

缓存层次、MESI、Store Buffer、伪共享，这几件事其实在回答同一个问题：当软件以变量和对象为单位思考时，硬件实际以缓存行、缓冲区和层级缓存为单位工作。只要两套粒度不重合，性能和可见性上的惊喜与惊吓就会源源不断冒出来。

## 六、把这几件事收成一张图：多核不是共享一份内存，而是在维护许多副本的秩序

现在可以把这一篇的角色重新放回一条逻辑线上。

首先，多核为了快，必须先让每个核拥有自己的缓存副本；否则每次都回主存，根本跑不动。接着，副本一多，就必须用 MESI 一类协议维持它们“看起来一致”。但协议本身又会让写操作不得不等待修改权协调，于是 Store Buffer 再出手，让写先缓冲、后结算。

写缓冲带来了吞吐，却也让“我已经写了”和“别人已经看见了”不再同步。与此同时，一致性协议保护的最小单位是缓存行，不是变量，于是即使两个线程逻辑上各写各的，只要它们恰好落在同一行里，就会引发伪共享。整个故事都发生在分层缓存架构之上，而不是抽象的一张共享大表里。

```text
每核私有缓存副本
  → 一致性协议维持全局表象
  → 写太贵，于是先进 Store Buffer
  → 可见顺序与执行顺序开始分离
  → 一致性按缓存行工作
  → 于是伪共享把“各写各的”也拖进冲突
```

所以这篇最重要的一句话是：**多核共享内存，并不是所有核同时盯着同一份值，而是硬件不断在多份副本之间维持一个可接受的秩序。**

## 七、几个最容易说错的地方

### 多核是不是所有核都直接看到主存里同一份最新值？

不是。它们通常先看到的是自己的缓存副本；“大家最终看到同一版”是协议努力维持出来的结果，不是起点事实。

### MESI 是不是在管理变量？

也不是。它管理的是缓存行副本。变量只是恰好落在某条行里的软件概念。

### 伪共享是不是说明程序有数据竞争，所以结果不对？

不一定。伪共享最讨厌的地方恰恰在于：结果可以完全正确，但性能会被一致性流量拖垮。

### Store Buffer 是不是说明写还没真正执行，所以程序可以当它不存在？

不能这么理解。对本核来说，这条写往往已经进入可被 forwarding 看见的状态；只是对其他核的全局可见性可能还滞后。这正是内存序和屏障问题的根。 

## 收束：并发程序真正共享的，常常不是变量，而是麻烦

现在回到最开始的问题：为什么两个核各写各的，程序反而更慢？因为硬件并不会按“源码里哪两个变量不同”来决定冲突边界。它按缓存行、一致性状态和写缓冲在工作。只要这些底层单位发生争用，即使高级语言层面看起来大家互不相干，性能仍然会被拖进同一场硬件对账战。

也正因为如此，多核并发的第一层困难并不是锁，而是你是否先接受了这样一个现实：共享内存从来不是“天然同步的一块区域”，而是由缓存协议、缓冲和层级架构勉强组织起来的合作现场。

这篇的开场困惑也就闭环了：多核不是“都读同一份内存，所以自然一致”，而是“每核先读自己的副本，再用协议修出一致表象”；伪共享不是“程序写错了”，而是“硬件维护一致性的粒度比你想象的大”。

## 八、误解清单、证据清单与边界清单

### 误解清单

- 多核不是所有核都直接盯着主存一份值；大部分时候先碰到的是各自缓存副本。
- MESI 管的不是源码变量，而是缓存行副本和它们的身份关系。
- Store Buffer 不是“写还没执行”；它更像“本核先记账、全局稍后结算”。
- 伪共享不一定导致结果错误，但非常容易让性能塌陷。
- HITM/cache-to-cache 热点不只是普通 miss，它常在说明缓存行正在跨核来回交接修改权。

### 证据清单

- 缓存一致性：MESI/MOESI 一类协议与 cache line 状态机，支撑“副本如何保持可接受的一致表象”。
- Store Buffer：写缓冲与 forwarding 路径，支撑“本核已写”和“他核已见”之间可能分离。
- 缓存行粒度：cache line 大小与副本管理粒度，支撑“硬件共享的是缓存行，不是源码变量”。
- 伪共享观测：`perf c2c`、HITM 与 cache-to-cache 事件，支撑“逻辑各写各的仍可能在同一行上打架”。
- 多级缓存：私有缓存与共享 LLC 的层次路径，支撑“一致性问题发生在分层缓存之上，而不是抽象单层主存”。

### 边界清单

- 本文用 x86 常见实现讲缓存一致性心智模型，不把某一代微架构、端口数、缓存容量或 cycle 数写成普遍常量。
- 一致性解决的是同一缓存行副本如何协调，不等于自动给软件建立跨地址顺序保证；这正是下一篇原子与屏障要接住的裂缝。
- 伪共享是否显著，会强烈依赖字段布局、写入频率、核数、NUMA 与工作负载形态。
- `perf c2c`、HITM 等工具能强力提示热点行，但仍需结合结构布局和算法语义解释，不能只凭单个指标神判。
