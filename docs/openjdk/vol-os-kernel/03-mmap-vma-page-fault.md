## 为什么 `mmap` 了 1GB，RSS 却几乎没动

很多人第一次做这个实验时都会愣一下：进程 `mmap` 一大段匿名内存，调用返回很快，虚拟地址也拿到了，但 `top` 里 RSS 并没有按 1GB 立刻上涨。只有你真的去读写那段内存，RSS 才开始一点点长出来。

如果只用“页表把虚拟地址翻译成物理地址”去解释，这个现象是不完整的。因为分页那一篇只讲清楚了：**一旦映射存在，CPU 怎样找到物理页。** 但这里真正的问题是：**这条映射是什么时候才算“真的存在到物理页上”的？**

这篇的主角，就是把“地址翻译”往前再推一层：

- `mmap` 返回时，到底创建了什么？
- 内核靠什么记住“这段地址未来该怎么处理”？
- 第一次访问一个尚未落地的地址时，为什么有时是正常分配，有时是磁盘读取，有时却直接段错误？
- `fork` 一个超大进程为什么能很快返回，难道内核真把全部内存复制了一遍？

先记住本篇总图：

```text
mmap
  → 建立一段“地址承诺”
  → VMA 记录这段承诺的区间、权限和来源
  → 真正访问时触发缺页
  → 内核按 VMA 决定：分配匿名页、接入文件页，还是判定非法访问
  → 若共享页被写，再进入 COW 路径做“写时复制”
```

这一整套机制最关键的顿悟是：**虚拟地址是承诺，物理页是兑现。** `mmap` 往往只发出了承诺，并没有立刻兑现；RSS 统计的主要是已经兑现到物理页上的那部分结果。

## 一、先别急着分物理页：为什么 `mmap` 只给地址，不给现成内存

### 1. 一个最笨也最直觉的办法

如果把内存映射理解成“用户一申请，内核就把对应物理页都备好”，很多事情都会显得简单：`mmap` 1GB 时立刻分配 1GB 物理页、清零、建页表，之后用户第一次访问就能直接用。

这个方案看起来很省事，因为真正访问时不用再缺页，也不用走额外路径。

但它的浪费同样惊人。大量程序会预留远超当前真实需求的地址空间；有的映射只是为了占位、对齐、增长弹性或者后续文件映射窗口；有的区域直到进程退出都没碰过。如果内核在 `mmap` 时就把所有物理页和最终页表都准备好，就等于为大量“可能永远不会被访问”的地址提前付费。

这正是虚拟内存里最不划算的一种付款方式：先把所有东西买齐，再等用户决定到底用不用。

### 2. `mmap` 做的是登记，不是现货发放

`mmap` 的真正动作更像是在土地局登记一块未来可用的地，而不是立刻把房子盖好。它做的是建立一段地址区间的语义承诺：这段地址属于当前进程、具有什么权限、背后是匿名内存还是文件、是共享还是私有。

```text
mmap 返回时
  → 进程得到一段虚拟地址区间
  → 内核记录这段区间的用途和规则
  → 但通常还没有为每一页准备好最终物理页
```

这就是 demand paging 的入口。真正昂贵的部分——分配物理页、装入文件页、建立最终 PTE——会尽量推迟到第一次访问时再做。

### 3. 匿名、文件、共享、私有：同样是映射，承诺内容并不一样

`mmap` 最容易被说得过于抽象。其实它至少要区分几类很不同的承诺：

- 匿名映射：背后没有文件，第一次触发时通常要分配匿名页。
- 文件映射：背后挂着文件，第一次真正访问时可能要把文件内容接入内存。
- `MAP_SHARED`：强调“多方看到的是同一份结果”，写入对共享者可见。
- `MAP_PRIVATE`：强调“初始内容可以共享，但私有写入不能污染别人”，这正是 COW 的落点。

共享和私有的区别，不能只停留在“能不能一起看”。它还会决定脏页结果落到哪里。`MAP_SHARED` 下，对文件映射页的修改更接近“大家共用同一本账本上的这一页”，因此修改有机会回到共享对象本身；`MAP_PRIVATE` 则更像“先拿一份共同底稿，谁改谁自己另抄一份”，所以私有写入不会直接改坏原文件视图，而会在后续进入 COW 路径。也正因为如此，两种映射即使初始内容一样，后续 RSS、脏页统计和共享可见性也会慢慢分叉。

同样是“这段地址以后可以访问”，匿名映射和文件映射的兑现方式不同；共享映射和私有映射的写入后果也完全不同。所以 `mmap` 本质上不是只返回一个地址，而是同时把一套未来行为规则挂在了这段地址上。

### 4. `brk` 和 `mmap` 的差别，也是在“承诺方式”上

很多语言运行时和分配器会同时用到 `brk` 和 `mmap`。从教学上看，它们的核心差别不是“谁更现代”，而是承诺方式不同。

`brk` 更像把传统堆顶往上推，形成一个整体连续增长区；`mmap` 更像随时在地址空间里划出一块独立区域。于是，大块对象用 `mmap` 时更容易单独释放回内核，而堆内的小块对象则更适合交给用户态分配器在自己的区域中再切分。

这不是说某个固定大小以下一定走 `brk`、以上一定走 `mmap`。真正的阈值和策略受 glibc、arena、碎片状态和配置影响。但读者至少要记住：**`mmap` 常被用来表达“我要一块独立映射”，而不是单纯“我要一些字节”。**

## 二、VMA：页表不记录语义，谁来记住这段地址到底承诺了什么

### 1. 只看页表，你根本不知道“这段地址该怎么处理”

上一篇讲过，页表负责翻译。可页表有一个天然短板：它只擅长回答“这个虚拟页当前映射到哪里、权限位是什么”。它并不天然知道这页背后对应的是哪个文件、这是一段匿名堆还是栈、当前访问落在承诺区域里还是纯属越界。

如果只靠页表，内核在遇到 Present=0 的地址时会非常尴尬。它最多知道“现在还没有物理页”，却不知道下一步应该：

- 给它补一页匿名零页？
- 去文件里找对应偏移的数据？
- 把共享只读页变成私有副本？
- 还是直接判它非法访问，发 `SIGSEGV`？

这些判断都不是纯硬件翻译能回答的，它们需要语义账本。VMA 正是这层账本。

### 2. VMA 记录的是一段区间的规则，不是一页一页的翻译

从教学上看，可以把 `vm_area_struct` 理解成“这段连续虚拟区间的合同”。它通常至少要记住几类信息：

- 这段地址的起止区间。
- 它允许读、写、执行中的哪些动作。
- 它是匿名映射还是文件映射。
- 它是共享还是私有。
- 真正发生缺页时，该调哪个处理逻辑继续往下走。

所以 VMA 的粒度不是“每一页”，而是“一段语义一致的地址区间”。只要这段区间的权限、来源和行为一致，就可以由一个 VMA 概括。

```text
页表：回答“这页现在映到哪了”
VMA：回答“这段地址如果被访问，应该按什么规则处理”
```

这个分层特别重要。页表是结果层，VMA 是规则层。缺页异常之所以能分流，不是因为硬件多聪明，而是因为硬件把异常抛上来之后，内核还能从 VMA 里查出语义。

### 3. 为什么进程地址空间里要按区间组织，而不是一页一页挂元数据

如果内核给每个虚拟页单独挂一份完整语义描述，也不是不能做。但那样既浪费内存，也让大量相邻、规则一致的页重复记录同一份信息。

实际进程里最常见的恰恰是大片规则一致的区间：代码段一整段只读可执行，数据段一整段可读可写，栈是一段可增长区域，匿名大块映射在一整段里共享同一种承诺。用区间描述它们，既更节省，也更符合后续 `mprotect`、`munmap`、拆分和合并的管理方式。

### 4. `/proc/PID/maps` 为什么像账本

当你看 `/proc/PID/maps`，每一行本质上都像是一个 VMA 的摘要：地址范围、权限、偏移、文件来源。它展示的不是页表逐页翻译结果，而是进程地址空间的语义分区。

这也是为什么 maps 和 RSS 不能混为一谈。maps 告诉你“承诺了哪些地块”；RSS 更像告诉你“这些地块里哪些已经真的盖了房、占了物理页”。

## 三、缺页异常：访问发生的那一刻，承诺才真正开始兑现

### 1. Present=0，不等于一定是错误

这是理解缺页机制最关键的一步。很多初学者看到页不存在，就会直觉地以为这肯定是非法访问。其实不是。

Present=0 只能说明：当前页表里还没有一条现成可用的物理映射。它没有告诉你“这是没建好”还是“本来就不该建”。要区分这两种情况，必须回到 VMA。

换句话说，缺页异常并不是单纯的失败信号，它更像一个问题上报：**这个地址现在没有现成映射，请内核根据语义规则决定下一步怎么办。**

### 2. 缺页路径真正问的是三件事

当访问撞上缺页，内核至少要依次回答三类问题：

```text
这个地址属于某个 VMA 吗？
  ├── 不属于：非法访问，段错误
  └── 属于：继续判断

这个 VMA 允许当前这类访问吗？
  ├── 不允许：权限错误，段错误或保护异常
  └── 允许：继续判断

这次应该怎么兑现？
  ├── 匿名映射：分配匿名页并建立映射
  ├── 文件映射：接入文件页，必要时触发 IO
  └── 共享/私有写保护：进入对应后续路径
```

所以“缺页异常”其实是很多路径的总入口，而不是单一路径。它既可能是正常的延迟分配，也可能是读取文件页，也可能是段错误。

### 3. Minor、Major、Invalid：不是三个词，而是三种完全不同的成本档位

从用户感知角度看，缺页最重要的不是名字，而是成本层次。

- Minor fault：通常说明数据已经在内存体系里，只差把映射补齐或接上，成本相对低。
- Major fault：通常意味着需要从更慢的地方把内容调回来，例如磁盘或 swap，成本可能高出很多。
- Invalid fault：说明这地址根本不在任何合法承诺区间里，结果不是分配，而是报错。

最容易混淆的是 file-backed 场景：同样访问一个文件映射页，有时只是 minor fault，有时却会变成 major fault。关键区别不在于“它是不是文件页”，而在于“文件内容此刻是不是已经在内存里”。如果页缓存里早就有对应内容，那么缺的只是把这页接进当前进程页表，成本更像补手续；如果页缓存里也没有，那就得真的去磁盘把货拉回来，成本才会上升为 major fault。也正因为这一层存在，缺页性能问题常常不能只盯着页表，还要继续往页缓存和 IO 路径追。

这三者最本质的区别在于：**它们不是同一种“慢”与“快”，而是“补手续”“调货”“直接拒绝”三种不同命运。**

### 4. RSS 为什么是访问后才涨，不是 `mmap` 后就涨

现在可以回到开头那个实验了。`mmap` 返回时，进程拿到的是 VMA 记录和地址承诺；当你还没访问时，很多页既没有匿名物理页，也没有最终 PTE，因此不会体现在 RSS 里。

只有当代码真的触碰某个页，缺页路径才会按 VMA 规则去兑现：要么分配匿名页，要么接入文件页，要么在非法条件下直接报错。RSS 上涨，恰恰是“这部分承诺已经落地成物理页”的结果。

这就是所谓 deferred allocation。它不是一个附属优化，而是虚拟内存整套经济模型成立的前提：地址先便宜地给你，物理页等你真用时再说。

## 四、COW：`fork` 为什么只复制承诺，不复制现金

### 1. 如果 `fork` 立刻复制全部物理页，会有多浪费

想象一个占用数 GB 地址空间的进程调用 `fork`。如果内核的策略是“既然子进程要一份副本，那就马上把全部物理页都复制过去”，这次系统调用会非常慢，内存带宽也会被打爆。

更糟的是，大量子进程会在 `fork` 之后立刻 `exec`，原来的用户态页根本马上就被新程序镜像替换掉。也就是说，你辛辛苦苦复制的大量页，很可能连一次真正的子进程用户态访问都没发生，就白复制了。

因此，立即复制物理页是一种看起来语义简单、实际上成本极差的方案。

### 2. `fork` 先复制页表关系，再把“未来是否复制”推迟到写入那一刻

COW 的做法恰好相反：先不复制页内容，只复制足够让子进程继续运行的地址空间结构。父子进程先共享原来的物理页，但把相关页表项改成只读或等价的受保护状态。这样，两边都还能读，但谁也不能直接写。

```text
fork
  → 子进程得到一份地址空间规则和页表关系
  → 父子暂时指向同一批物理页
  → 共享页先设为不可直接写

随后某一方第一次写
  → 触发写保护异常
  → 内核复制物理页
  → 写入方改用自己的私有副本
```

所以 COW 不是“复制时顺便写保护”，而是“用写保护把复制推迟到真正必要的时刻”。

### 3. COW 的判定不只看 PTE，也要看 VMA 语义

这里最重要的一点，是别把 COW 误解成“只要写保护异常就一定复制”。不是所有只读页都能合法进入 COW。

要决定这次写保护异常到底是：

- 合法的私有写入，需要复制；
- 共享映射下的别的合法路径；
- 还是根本不允许写，应该报错；

内核既要看硬件给出的页表状态，也要看 VMA 提供的语义规则。也就是说，**PTE 提供硬件入口，VMA 提供语义判词。** 两者缺一不可。

这也回答了完整性问题里那个很关键的分叉：匿名页的 COW 和文件私有映射的 COW，都可能走“写保护后私有化”这条主线，但它们背后的来源、回写关系和后续处理语义并不相同。正文先抓住稳定主线：都是先共享，再在第一次写时私有化；更细的匿名页/文件页分叉，留在后续页缓存与文件映射篇章继续展开。

### 4. `fork` 为什么快，不是因为复制变快，而是因为大多数复制被避免了

很多人会说“COW 让 `fork` 更快”，这句话其实还不够准确。更准确的说法是：COW 让 `fork` 在大多数常见场景里避免了立刻复制大量页，于是返回变快。

也就是说，它优化的不是“复制动作本身有多快”，而是“尽量少做本来可能完全没必要发生的复制”。一旦父子进程都大量写共享页，COW 的复制成本仍然会真实发生，只是发生得更晚、更按需。

因此，COW 不是把成本消灭了，而是把成本和真正的写入行为重新对齐。

## 五、承诺也不能无限乱开：overcommit 为什么要存在

### 1. 如果承诺不设上限，会发生什么

既然 `mmap` 可以先给地址、物理页以后再说，那内核是不是可以无穷无尽地承诺下去？从表面看，好像可以。因为在没访问前，很多映射并不真正占物理页。

但问题在于：一旦许多承诺被同时兑现，系统必须真的拿得出物理页、页缓存空间、swap 余量或者其他资源。如果承诺远超可兑现能力，最终就会在真正触发访问时集中爆雷。

于是，虚拟内存不能只讲“延迟分配多优雅”，还必须讲“延迟承诺不能乱开到失控”。这就是 overcommit 要解决的问题。

### 2. overcommit 的核心不是允许或禁止，而是选择谁承担风险

从教学上理解，overcommit 控制的是：内核愿意在多大程度上相信“这些承诺里不会所有都被同时兑现”。

- 更宽松的策略，给应用更大的地址空间弹性，但把风险推迟到未来真正访问时。
- 更严格的策略，在承诺阶段就更早拦截，减少未来爆雷概率，但也可能拒绝一些其实最终并不会真用满的请求。

所以 overcommit 不是单纯的“保守/激进”开关，而是决定**风险是在申请时暴露，还是在访问时暴露**。

### 3. 数据库为什么常常更偏向保守策略

缓存、数据库和需要稳定内存预期的系统，通常更怕“运行到一半才发现承诺无法兑现”。对它们来说，提前知道申请失败，往往比未来某个高峰时刻突然撞上内存耗尽更可控。

因此，这类系统常常倾向更保守的 overcommit 配置。原因不是它们不懂延迟分配的好处，而是它们更看重兑现阶段的确定性。虚拟内存的优雅，与生产系统的可预测性，并不总是同一个优化方向。

## 六、把这四件事放回同一条链上

现在可以把 `mmap`、VMA、缺页异常和 COW 收成一条完整链路。

首先，`mmap` 负责发出承诺：给进程一段地址区间，并说明这段区间将来按什么规则使用。VMA 负责把这份承诺记成语义账本：区间边界、权限、来源、共享还是私有。

接着，CPU 真正访问某页时，如果页表里还没有现成映射，就触发缺页异常。内核再根据 VMA 的账本判断：这页该分配匿名内存、接入文件内容、做共享映射、还是直接判非法访问。于是，一次“页不存在”事件，才终于从抽象地址变成真实物理页或真实错误。

如果这次访问还是发生在 `fork` 之后的共享只读页写入上，COW 再接手，把“本来可以共享的内容”推迟到写时才分家。最后，overcommit 则在更外围替整套承诺系统设预算，防止地址承诺与可兑现能力长期严重脱节。

```text
mmap
  → 建立地址承诺
  → VMA 记录规则
  → 首次访问触发缺页
  → 缺页按 VMA 分流：匿名 / 文件 / 非法
  → 若是共享只读页写入，再进入 COW 私有化
  → overcommit 在更外围限制承诺规模
```

所以，本篇最该留下的不是几个函数名，而是这一句：**虚拟内存真正厉害的地方，不是“有页表”，而是把承诺、账本、兑现和复制拆成了四个时刻。**

## 七、几个最容易混淆的地方

### `mmap` 返回成功，是不是就等于物理内存已经拿到手？

不是。很多情况下，它只代表地址承诺和 VMA 规则已经建立。物理页通常要等第一次真实访问时才兑现。

### 缺页异常是不是一定代表程序出错？

不是。很多缺页本来就是正常运行路径的一部分，尤其是匿名页按需分配、文件页按需调入和 COW 写保护触发。真正的错误是地址不在合法 VMA 里，或访问方式不被允许。

### `fork` 快，是不是因为复制物理页这件事变便宜了？

也不是。更准确地说，是很多本来可能发生的复制被推迟甚至被避免了。只要后续真的大量写，共享页的复制成本仍然会回来。

### RSS 涨了，是不是因为 `mmap` 更多了？

不能简单这么看。RSS 更接近“已经兑现到物理页上的那部分现实”；`mmap` 和 VMA 更像“承诺总额”。两者可能长期差很多。

## 收束：`mmap` 不是拿钱，像拿到一张可兑现支票

现在回到最开始那个实验：为什么 `mmap` 1GB 后 RSS 没立刻涨？因为你拿到的首先是一张支票，而不是一箱现金。支票上写着地址范围、权限、来源和兑现规则；真正兑不兑现、什么时候兑、用什么方式兑，要等你真的去银行窗口敲一下，也就是等真实访问触发缺页。

VMA 是这张支票的账本，缺页异常是窗口叫号系统，COW 是“多人先共用账面余额，谁先花谁再分户”，overcommit 则是银行决定能不能继续超额签发的风控规则。

所以这篇的开场困惑已经闭环：`mmap` 后 RSS 不涨，并不是什么统计异常，而是虚拟内存刻意把“先承诺、后兑现”这件事做到了机制里。也正因为如此，`fork` 才能快，地址空间才能便宜，文件映射才能按需接入，系统也才需要 overcommit 这种预算管理。
