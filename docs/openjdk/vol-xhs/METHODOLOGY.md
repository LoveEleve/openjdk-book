# vol-xhs 写作与分析方法论

> 适用范围：`docs/openjdk/vol-xhs/` 全部模块文档与后续重写任务。
> 目标：把 `my-xhs` 微服务平台的业务逻辑、工程问题、分布式问题、微服务问题，组织成可阅读、可验证、可交接的技术文章。

---

## 一、先定组织原则：按模块组织，不按问题类型组织

`vol-xhs` 的主组织维度是模块，不是“业务逻辑篇 / 分布式篇 / 工程篇 / 微服务篇”四条平行大线。

原因很简单：

读者真正想弄懂的，是“订单模块怎么工作”“库存模块为什么复杂”“搜索模块为什么出故障”，而不是脱离上下文地看一组抽象问题。

所以本卷统一采用：

- **横轴：模块/领域**
- **纵轴：四个分析视角**

也就是：

- 目录按模块划分：`00-overview-architecture` 到 `12-testing-release-ops`
- 每个模块内部，再从四个视角解剖：
  1. 业务逻辑
  2. 工程问题
  3. 分布式问题
  4. 微服务问题

这四个视角不是四套独立目录，而是每篇文章、每个模块都必须有意识覆盖的四组问题。

---

## 二、四个视角分别回答什么

### 1. 业务逻辑视角

业务逻辑回答的是：

- 谁在触发这个模块？
- 用户或上游服务想完成什么？
- 这个模块内部有哪些核心规则？
- 状态如何流转？
- 成功出口和失败出口分别是什么？

例如：

- 用户登录后，Token 如何签发、刷新、失效
- 用户加购后，购物车如何合并、覆盖、清空
- 用户下单后，订单如何创建、预扣库存、支付成功、关单、退款

业务逻辑不是接口列表，也不是 DTO 字段翻译。

必须写成：

- 场景
- 角色
- 状态机
- 规则
- 边界
- 失败路径

### 2. 工程问题视角

工程问题回答的是：

- 这套代码为什么能跑起来？
- 为什么之前跑不稳？
- 配置、日志、监控、测试、发布链路是怎么支撑业务的？
- 某个问题为什么不是“业务 bug”，而是工程落地问题？

重点包括：

- 配置中心与本地配置覆盖
- 启动参数与 profile
- Feign URL override
- SkyWalking 插件与 traceId 入 ES
- 启动脚本、重启脚本、巡检手册
- 测试分层、回归范围、发布验证

工程问题不是附录。对微服务系统来说，很多“业务问题”最后都死在工程细节上。

### 3. 分布式问题视角

分布式问题回答的是：

- 单机直觉在这里为什么失效？
- 多服务、多库、多缓存、多消息队列下，正确性靠什么维持？
- 一致性、幂等、重试、补偿、超时、死信分别怎么处理？

重点包括：

- 事务消息
- TCC / 三级扣减
- 幂等令牌 / 幂等窗口
- 分布式锁 / Lua 原子操作
- 延迟双删 / Canal / 最终一致性
- MQ 重试 / 死信 / 补偿任务

写分布式问题时，必须先讲朴素方案为什么不行。

例如：

- 为什么库存不能只在 MySQL 扣一次
- 为什么订单不能只靠本地事务保证一致性
- 为什么死信消息不能无限重试

### 4. 微服务问题视角

微服务问题回答的是：

- 这个模块为什么单独拆成服务？
- 它的边界是什么？
- 它和谁同步调用，和谁异步协作？
- 入口、编排、聚合、鉴权、容错是怎么分工的？

重点包括：

- 服务职责边界
- Feign 调用链
- MQ 订阅/发布关系
- Gateway 路由与过滤器链
- BFF 聚合
- 降级、限流、超时、重试
- 可观测性中的跨服务 trace

微服务问题的重点不是“用了 Spring Cloud”，而是“拆完之后复杂度转移到哪里了”。

## 三、模块文章的固定组织方式

每个模块都要遵守下面的主顺序：

1. **先写业务主线**
2. **再嵌入工程约束**
3. **再拆分布式代价**
4. **最后收束到微服务边界**

也就是说，文章不是平均切成四块，而是以业务主线作为骨架。

推荐顺序（总规范"场景→直觉→失败→设计→拆解→边界→桥接"七步的展开版本）：

1. 读者困惑
2. 业务场景
3. 直觉方案为什么不够
4. 角色与时序图
5. 主链路拆解
6. 源码证据
7. 工程落地问题
8. 分布式一致性问题
9. 微服务边界与依赖
10. 故障案例
11. 设计取舍与代价
12. 篇末桥接

注意：

- 业务模块以业务主线为骨架
- 横切模块以机制主线为骨架
- 但无论哪一类，都不能丢掉故障案例和工程实证

## 四、三步分离在 vol-xhs 中怎么落地

本卷继续遵守总方法论的三步分离：

1. 素材提取
2. 理解路径设计
3. 叙事写作

但在微服务场景里，素材提取要额外补四类证据。

### 第一步：素材提取

每篇写作前，至少提取下面这些卡片：

- 核心入口：Controller / Consumer / Job / Gateway route
- 核心服务：Service / Manager / Domain 逻辑
- 下游依赖：Feign、MQ、Redis、MySQL、ES、XXL-Job
- 状态机：订单状态、支付状态、库存状态、优惠券状态等
- 关键配置：application.yml、logback、bootstrap、Nacos 配置
- 失败路径：超时、回滚、重试、死信、空结果、脏读、重复提交
- 运行态证据：日志、traceId、Prometheus 指标、MQ 消费记录、数据库/缓存状态
- 已知故障：历史 bug、运行时事故、修复记录、验证结果

### 第二步：理解路径设计

先离开源码，回答：

- 读者在这个模块最容易困惑什么？
- 应该先讲哪个角色，后讲哪个角色？
- 哪些实现细节现在讲会打断主线？
- 哪个故障案例最能逼出设计动机？
- 哪个问题适合放到下一篇展开？

如果这些问题答不出来，不允许直接写正文。

### 第三步：叙事写作

按读者理解路径写，不按源码文件顺序写。

优先顺序永远是：

- 问题
- 冲突
- 失败方案
- 设计顿悟
- 机制拆解
- 证据
- 边界
- 桥接

---

## 五、证据分级：源码、语义、运行态三层证据

`vol-xhs` 不能只靠“看代码像是这样”下结论。

借鉴 `test-3` 的验证纪律，本卷统一使用三层证据法：

### L0：源码静态证据

能证明：

- 类、方法、配置、路由、注解、字段真实存在
- 调用链、依赖关系、状态流转在代码层面成立

典型材料：

- 文件路径（最低要求）
- `file:line`（关键结论尽量给到行号，但不编造）
- 配置片段
- 关键代码片段
- 路由定义
- MQ 消费者/生产者定义

### L1：框架/语义证据

能证明：

- 某个配置项到底如何被框架解释
- 某个注解/中间件行为是否符合直觉
- 某个版本行为是否有特殊语义

典型材料：

- Spring Boot / Spring Cloud 配置语义
- Nacos、RocketMQ、SkyWalking、ES 的官方或运行行为
- YAML / Properties / Logback 的解析规则

### L2：运行态证据

能证明：

- 这个机制在真实环境里真的生效了
- 这个故障在运行态真实出现过
- 这次修复在真实链路上被验证过

典型材料：

- 启动日志
- 端口检查
- traceId 跨服务链路
- Redis / MySQL / ES / MQ 的运行结果
- Prometheus 指标
- 故障现场日志

### 结论纪律

所有结论都要标清自己站在哪一层：

- 只做了源码核对：可以说“源码显示如此”
- 做了语义核对：可以说“按框架行为应如此”
- 做了运行态验证：才可以说“实测如此”

禁止把 L0/L1 的判断写成 L2 的口气。

---

## 六、每篇文章的固定交付件

每篇文章除正文外，必须同时具备以下交付件：

1. **一句话困惑**：读者到底在问什么
2. **一句话答案**：本篇最核心的人话结论是什么
3. **一张文字图**：角色、箭头、时序
4. **一个失败方案**：至少一个直觉方案及其失败原因
5. **一个故障案例**：现象、根因、修复、验证
6. **一个证据清单**：关键结论由哪些文件、日志、运行结果托底
7. **一个边界清单**：哪些结论只在当前实现/当前环境成立
8. **下一篇桥接句**：尚未解决的问题指向哪里

这些交付件可以嵌入正文自然段，也可以放在篇末附录，不要求固定模板标题；但内容必须全部存在。

没有这些交付件，正文通常还没真正闭环。

---

## 七、故障案例不是点缀，是强制结构件

在 `vol-xhs` 中，故障案例不是“有就写一点”，而是每篇必选要素。

每个案例最少要回答：

1. 故障现象是什么
2. 触发条件是什么
3. 是业务错误、工程错误、分布式错误还是微服务边界错误
4. 根因在哪个服务、哪段代码、哪个配置、哪个运行机制
5. 修复是怎么做的
6. 修复后如何验证
7. 还留下了什么边界或代价

推荐写法统一为：

- **现象**
- **根因**
- **修复**
- **验证**
- **余波**

故障写作时，禁止两种偷懒：

- 只写“某问题已修复”，不写为什么坏
- 只写“日志报错”，不写代码/配置根因

## 八、九透镜自查表

借鉴 `test-3` 的 L3 检查表，本卷每篇文档写完后都要过一次九透镜。

1. **性能**：这个链路最慢在哪里，缓存/限流/聚合是否影响延迟
2. **可扩展**：分片、无状态、消费者扩容、索引扩展性如何
3. **微服务**：同步/异步调用是否合理，是否存在边界漂移
4. **分布式**：一致性、补偿、重试、死信、锁、时序如何保障
5. **并发**：重复请求、竞态窗口、原子性缺口在哪里
6. **安全**：JWT/HMAC/AdminToken/InternalToken/数据脱敏如何落地
7. **弹性**：超时、降级、熔断、故障放行或 fail-closed 如何设计
8. **可观测**：trace、日志、指标、告警是否能证明问题
9. **一致性**：Redis、MySQL、ES、MQ 之间最终如何收敛

不是每篇都要平均写九段，但至少要在深审时确认：该篇最相关的透镜有没有被覆盖。

## 九、模块文章与横切文章的区别

### 1. 模块文章

例如：

- `01-user-account-auth`
- `03-product-sku-catalog`
- `04-cart-coupon-marketing`
- `05-inventory-order-payment`

写法要求：

- 以业务场景为入口
- 以主链路为骨架
- 用工程/分布式/微服务问题解释复杂度来源

### 2. 横切文章

例如：

- `09-data-model-storage`
- `10-async-task-transaction`
- `11-runtime-failure-review`
- `12-testing-release-ops`

写法要求：

- 以某类共同机制或共同问题为入口
- 用跨模块对照收束共性
- 但必须始终回到真实模块和真实案例，不能写成空泛总结

横切文章最容易写虚，所以必须强制引用真实模块中的实际案例。

## 十、写作顺序必须服从依赖，而不是平均推进

`vol-xhs` 不适合 13 个目录平均推进。

推荐顺序：

1. `00-overview-architecture`：先建全局地图
2. `03-product-sku-catalog`、`04-cart-coupon-marketing`、`05-inventory-order-payment`：先打穿交易主链
3. `01-user-account-auth`、`06-search-recommendation-home`：补入口与流量入口
4. `02-content-feed-interaction`、`07-im-notification-message`、`08-gateway-security-observability`：补内容、触达、基础设施
5. `09-data-model-storage`、`10-async-task-transaction`、`11-runtime-failure-review`、`12-testing-release-ops`：最后做横切收束

原因是：

- 交易主链最能暴露系统复杂度
- 后面的横切文章要复用前面真实案例
- 没有总图就写故障，容易只见树木不见森林

## 十一、写完后的深审清单

每篇正文完成后，至少过以下几轮：

### 1. 删码测试

删掉代码块后，文章还能不能成立。

### 2. 主线测试

只读小标题，能不能还原：

- 问题
- 失败方案
- 顿悟
- 机制
- 回收

### 3. 证据测试

每个关键结论是否都能落回：

- 真实源码
- 真实配置
- 真实日志
- 真实运行态结果

### 4. 故障测试

是否真的讲清了：

- 怎么坏的
- 为什么坏
- 怎么修的
- 怎么证明确实修好了

### 5. 四视角测试

是否至少覆盖了：

- 业务主线
- 工程落地
- 分布式代价
- 微服务边界

### 6. 边界测试

是否标明：

- 哪些是源码事实
- 哪些是设计推断
- 哪些是运行态实测
- 哪些仍未验证

### 7. 禁用词扫描

对正文主线运行禁用词检查（此处不再赘述、不再展开、类似地、同理、依此类推、篇幅所限、显然、容易看出、细节读者自行阅读源码）；命中后优先重写该节，不能用"只是过渡句"绕过检查。

---

## 十二、最后的判断标准

以后判断 `vol-xhs` 一篇文章写得好不好，优先看四件事：

1. 读者的问题有没有被真正抓住
2. 业务主线有没有讲清，而不是接口堆砌
3. 分布式和微服务复杂度有没有被解释出来，而不是只说“调用了某某服务”
4. 删掉代码后，这篇文章是否仍然成立

再补一句本卷的特殊标准：

**如果删掉故障案例后，文章对真实系统复杂度的解释明显变浅，说明这个案例写对了；如果删掉后毫无影响，说明它只是装饰。**

## 十三、与总方法论的关系

本文件不是替代：

- `docs/openjdk/WRITING-METHODOLOGY.md`
- `docs/openjdk/WRITING-GUIDELINES.md`

而是把它们在 `my-xhs` 这个 Spring Cloud 微服务系统里的执行方式具体化。

总方法论负责：

- 三步分离
- 理解路径优先
- 删码测试
- 失败方案
- 证据纪律

`vol-xhs` 方法论额外补充：

- 按模块组织
- 四视角解剖
- 三层证据法
- 故障案例强制化
- 运行态验证意识
- 横切专题与业务模块分写

读本卷前，先读总方法论；写本卷时，再按本文件落地。
