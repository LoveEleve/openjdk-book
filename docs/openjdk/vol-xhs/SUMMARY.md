# vol-xhs 全卷总览

> 适用范围：`docs/openjdk/vol-xhs/`
> 目标：把当前 `62` 篇模块正文收成一张能用于阅读导航、交接延续和项目表达的总图。

---

## 先给结论：这卷真正讲清的是一套“靠状态分层、异步收尾和多级证据链维持正确性”的微服务系统

如果只把 `my-xhs` 看成“15+ 个 Spring Boot 服务 + 一堆中间件”，这卷会显得像很多局部专题的堆叠：用户、商品、购物车、订单、支付、搜索、通知、网关、监控、部署、故障复盘，好像每一组都很重，但彼此之间只是松散相邻。

这不是这卷真正成立的方式。

把 `vol-xhs` 全部正文收回来之后，真正能压缩成一句人话的，是这样一个系统判断：

**`my-xhs`` 不是靠某个单一中心服务维持正确性，而是靠“主数据真相分域持有 + 交易时序由编排域拉齐 + 高频状态先落 Redis + 后半段靠消息与任务继续收尾 + 最终由测试/监控/故障复盘把证据拉回来”这整套机制共同维持正确性。**

换句话说，这卷写清楚的不是“每个服务都做了什么”，而是：

- 为什么这套系统不能按单机直觉理解；
- 为什么很多动作不能一次本地事务做完；
- 为什么“接口 200”在这里从来不等于“业务已经闭环”；
- 为什么工程脚本、配置中心、监控指标、死信与补偿任务，本身就是业务正确性的一部分。

如果要把它再往下压一层，可以得到这卷最核心的五个系统结论：

1. **业务真相是分域的。** 用户、商品、优惠券、库存、订单、支付、通知都各自持有不可互相替代的那部分状态。
2. **交易主链是编排出来的，不是单域内生长出来的。** 尤其是 `order`，它之所以最重，不是因为拥有最多数据，而是因为要把别域真相在同一个时刻拉成一条执行链。
3. **很多“看起来已经成功”的动作，其实只完成了第一层。** 下单成功不等于库存已确认，支付成功不等于订单已收口，通知推到在线用户不等于列表和红点已长期一致。
4. **异步系统不是“优化项”，而是主链完成后的正式执行层。** 事务消息、本地消息表、补偿 Topic、对账任务、死信、DLQ、定时重建，这些不是边角料，而是系统后半段的一部分。
5. **工程系统不是背景板，而是业务的一部分。** Gateway、Nacos、Redis Sentinel、启动脚本、Prometheus、SkyWalking、部署包、L2 验证纪律，全都在决定业务到底有没有以正确方式成立。

这就是这卷的总主题。后面的目录、分组和专题，都是在回答这五个判断分别落到哪一层、哪一段链路和哪一种故障上。

## 一、全卷最重要的主线：一条从“用户有身份”到“用户最终感知到结果”的业务链

如果要给这卷找一条真正的主业务线，它不是单独的“下单链”，也不是单独的“内容链”，而是一条更完整的用户视角链：

```text
用户获得身份
  → 看见内容和商品
    → 形成待购状态
      → 触发交易主链
        → 让钱和货重新对齐
          → 最终把结果扩散给用户自己和其他人
```

这条主线横穿了 `00` 到 `07`，其中每一组都在回答这条链上的一个关键问题。

### 1. `00-overview-architecture/`：先建立全局地图

这一组的价值，不是目录概览，而是先回答：

- 用户请求先打到哪里；
- 哪些服务是权威域，哪些是编排域或聚合域；
- 同步调用止于何处，异步扩散从哪里开始；
- 这套技术栈分别在接哪一类问题。

如果没有这一组，后面的每一篇都容易被误解成局部源码翻译；有了它，读者至少知道自己是在看同一张大图的哪一段。

### 2. `01-user-account-auth/`：用户先得成为“可被全系统识别的身份”

这一组从注册、JWT、权限到会话，把“用户”从数据库里的一行，变成了能经过 `Gateway → Redis → 下游服务` 流动的会话状态。

它真正讲清的是：

- 注册不是 `INSERT t_user`，而是被验证码、锁、唯一性和短事务压缩后的身份创建链；
- JWT 不是裸 Token，而是 Access / Refresh / HMAC Secret / Redis 黑名单 / Gateway 传播共同构成的会话；
- 权限模型不是“有 Token 就全通”，而是 JWT、角色、管理令牌、内部令牌和 HMAC 分层门禁；
- 单设备登录真正难的是旧会话何时、如何、由谁被收回。

这一组解决的是“你是谁、你现在是不是还被系统承认”的总前提。

### 3. `02-content-feed-interaction/`：内容不是一条记录，而是一条会继续扩散的行为链

这一组把“内容”从一篇笔记、一条评论、一个点赞按钮，重新拉回系统视角：

- 发布不是简单插库，而是“内容本体成立 + Feed 扩散继续推进”的双层链；
- Feed 不是时间线查询，而是推拉混合、游标分页、两层聚合和未读联动；
- 互动不是局部按钮，而是会继续影响计数、通知、推荐和后续展示的事件源；
- `analytics` 和 `counter` 两个模块专章又把这条互动链拆成了“关系真相层”和“计数展示层”；
- 审核当前仍然是 DFA 前置拦截为主，而不是完整的人审平台。

这一组解决的是“内容如何进入别人的世界”。

### 4. `03-product-sku-catalog/`：商品真相必须先拆成母体、变体和库存桥接

商品组真正做的，不是解释 SPU/SKU 定义，而是解释为什么商品真相不能放成一张表：

- `SPU` 持有商品共性真相；
- `SKU` 持有可交易变体真相；
- 真实库存不继续留在商品域，而让给 `inventory`；
- 详情页不只是 product 本地对象，而是骨架真相加上库存/计数等外部视图。

这一组先把“到底卖什么”和“到底按什么单位进入交易”钉死。

### 5. `04-cart-coupon-marketing/`：交易前置不是附属逻辑，而是把待购状态和价格语义先收住

这一组对应的是“用户准备买什么”和“准备按什么价格买”这两类前置问题：

- 购物车先以 Redis 三结构收敛成用户的权威待购集合，再异步落库；
- 优惠券有自己的模板、库存、用户券、核销、退回和对账生命周期；
- 当前没有独立 promotion engine，营销能力主要停留在“基础价格 + 单券折扣 + 订单收敛”的有限闭环；
- 所谓营销叠加，当前实际上只是单券驱动的价格收敛链。

这一组解决的是“交易发生前，用户的待购集合和价格候选是怎样被组织起来的”。

### 6. `05-inventory-order-payment/`：真正的交易主链

这是整卷最成熟、也最能暴露系统复杂度的一组。

它真正讲清的是：

- 库存为什么必须是预扣 → 确认 → 释放的三级状态机；
- 下单为什么是一场把地址、SKU、库存、优惠券和事务消息拉进同一条链的编排；
- 为什么必须用 RocketMQ 事务消息把订单本地事实和库存预扣可见性绑在一起；
- 支付链怎样独立维护“钱”的状态，再把它推回订单和库存；
- 履约和退款怎样继续推进“货”的状态，直到真正完成或收回。

这一组不是在讲某个服务内部实现，而是在讲一条交易怎样成立、怎样失败、怎样收尾。

### 7. `06-search-recommendation-home/`：流量入口如何把“用户没明确说出口的意图”组织出来

这一组看起来是“读路径”，实际上仍然在处理系统很重的业务问题：

- 搜索不是模糊查询，而是独立索引视图 + Search After + 高亮 + 热搜/历史副作用；
- 推荐不是热门榜，而是多路召回 + 粗排 + 精排 + 重排 + 行为回流的规则化 pipeline；
- 热搜不是累计次数，而是分钟桶 + 指数衰减 + 反作弊 + 置顶/屏蔽 + 快照双层榜单；
- `home` 不是薄 BFF，而是页面级读模型、并发聚合、降级语义和线程池资源控制层；
- 新补的 `search` / `home` 模块专章又把这一组从“专题链路”进一步落成了“模块职责 + 真实故障案例”。

这一组解决的是“用户为什么会在某个时刻看见这些内容，而不是别的内容”。

### 8. `07-im-notification-message/`：最终用户感知层

这组把“消息”拆成了三种完全不同的系统语义：

- IM：双边实时会话、有序消息、在线路由、离线补投；
- SSE 通知：业务事件提醒、在线即时可见；
- 聚合通知和未读红点：长期收敛视图；
- 跨实例专章又进一步说明，它们即使都叫“消息”，跨实例策略也不一样：IM 已经做了定向路由，SSE 仍是公共 Channel 下的轻量分发；
- 新补的 `im` / `notification` 模块专章又把“消息”拆回了两个完全不同的系统对象：会话事实与提醒视图。

这一组解决的是“系统最后怎样把结果还给用户”。

## 二、横切主线：这套系统不是靠一次成功，而是靠后半段收尾与长期收敛活着

如果说 `00`～`07` 主要回答“业务怎样跑”，那么 `08`～`12` 主要回答“为什么它跑着跑着不会立刻散掉”。

### 1. `08-gateway-security-observability/`：统一入口控制面

这一组把最北边那一层收得很清楚：

- Gateway 不是转发器，而是路由、JWT、HMAC、限流、trace 和流量元数据的统一入口控制面；
- JWT 和 HMAC 是双门禁，不是一个替代另一个；
- Sentinel route 级限流真正保护的是整个入口控制面；
- 可观测性不是工具清单，而是 trace / 日志 / metrics 三条证据线对齐；
- 新补的 `gateway` 模块专章又把这一组从“专题说明”推进成了“入口控制面职责 + 错误放行故障模型”。

这组的价值在于：它把“谁有资格进系统、进来以后带着哪些统一上下文”这一层讲清了。

### 2. `09-data-model-storage/`：数据到底落在了几种不同语义的状态平面上

这一组横切回答：

- MySQL 分片不是多建几张表，而是围绕 `user_id` 收敛交易主链，同时给 `orderNo` / `payment` 留旁路；
- Redis 不是缓存盒子，而是会话、缓存、脚本原子状态机和高可用入口的第二状态平面；
- ES 是查询投影视图，不是真相副本；
- MQ Topic 和 ConsumerGroup 构成的是不同语义的异步地图，而不是一条总线。

这组的价值，是把前面各条链反复出现的数据结构一次性讲透。

### 3. `10-async-task-transaction/`：真正完成主链后半段的执行系统

这组几乎就是“系统如何把做不起的一半继续做完”的专题：

- 异步事件不是发条消息，而是后半段执行系统；
- 事务消息负责第一跳原子性，本地消息表负责回查和补发，补偿消息负责残局继续收尾；
- 定时任务不是后台扫库，而是最终一致性最后一层执行器；
- 不同失败必须交给不同恢复层：重试、补偿 Topic、Feign 回查、表扫描、重建、DLQ、人工。

这组的价值，是把“系统为什么不要求一次做完所有事”解释清楚。

### 4. `11-runtime-failure-review/`：故障怎样暴露真实系统边界

这一组不是附录，而是把前面所有设计拉回现场：

- 端口冲突最危险的不是起不来，而是旧进程假恢复；
- 死信不是“重投一下”，而是自动恢复边界的明确信号；
- Feign timeout 不是一次 503，而是同步主链与补偿系统的分流点；
- 启动失败不是某行代码错了，而是条件装配、外部依赖、版本组合和脚本参数链一起断了。

这组的价值，在于说明设计边界只有在失败时才最清楚地显影。

### 5. `12-testing-release-ops/`：证明系统正确性的最后一层

### 6. `13-common-cross-cutting/`：支撑全卷的横切基础设施层

这一组把 `my-xhs-common` 里被各业务模块反复引用的横切能力一次性立住：Redis Lua 滑动窗口限流、接口/MQ 幂等、分布式锁、TCC Fence、三策略 ID 生成、读写分离与影子表路由、全链路 trace 与流量染色、`FeignInternalCallInterceptor` 内部调用令牌注入，以及多活（Zone）路由与数据源/Redis 热切换。它回答的是“为什么每个服务都自带一套相同的能力，而不是自己重复实现”。新补的 `common` 模块专章又进一步把这一组落成了“共享底座如何同时影响所有服务正确性”的平台级视角。

最后一组回答的是：“怎么证明前面说的这些东西不是纸上谈兵”。

- 测试策略不是多测，而是三层结论强度 + 15 层证据链 + 逐用例可归因；
- 启动脚本不是胶水，而是工程协议；
- 部署包不是 compose + sql，而是拓扑、配置导入、开机自恢复和验证协议；
- 监控告警不是平台安装，而是采集、规则、存储、通知和排障路径的对齐；
- 基于 compose 的远程 L2 清单又进一步把“能部署”和“当前在线”分开。

这组的价值，是把“如何证明系统真的按照你说的方式在工作”讲清楚。

## 三、这卷最重要的工程判断：正确性不是靠一层守住，而是靠多层一起收窄风险

如果要从全卷里抽出几条最能代表 `my-xhs` 的工程判断，我会选下面这些。

### 1. 先把轻的动作留在本地，重的后半段拆出去

这是全卷最普遍的一条设计取向：

- 注册先把前置资格收窄，再只用短事务写库；
- 内容发布先让内容本体成立，再让 Feed 扩散继续推进；
- 下单先把订单本地事实和事务消息绑住，再让库存预扣接管；
- 通知先把通知实体与未读视图收住，再决定在线推送；
- 推荐先返回可用结果，再靠行为回流改进下一轮。

也就是说，系统并不追求“一次把所有事做完”，而是追求“先把最小正确事实落稳，再让后半段有地方可继续做”。

### 2. 并发和幂等不是单点技巧，而是从入口到状态机一起设计

这一点几乎出现在每一组里：

- 注册：验证码 `GETDEL` + 用户名锁 + 唯一键兜底；
- 购物车：Lua 三结构原子写 + merge 幂等；
- 优惠券：Redis Lua 限领 + MQ syncSend + Outbox；
- 订单：幂等键 + 用户锁 + 事务消息 + 消费者幂等；
- IM：msgId 去重 + seqNo + 路由 TTL + 离线 ACK；
- 通知：msgId 去重 + 聚合窗口锁 + Redis 视图对账。

这卷真正讲透的是：幂等从来不是“加个注解就完了”，而是必须和状态机、消息链、缓存键和补偿链一起设计。

### 3. “真相”与“视图”必须明确区分

这是这卷里最常反复出现、也是最值得讲给别人听的一条架构判断：

- `SPU / SKU` 真相和库存视图不是一回事；
- ES 索引不是主数据真相；
- 通知列表和未读红点不是同一份状态；
- BFF 返回对象不是下游服务原始模型；
- 热搜榜不是原始搜索行为总次数；
- Grafana 看板不是业务真相，只是观测视图；
- Redis 在某些域是权威态，在另一些域只是高速投影视图。

也就是说，这套系统之所以复杂，很大程度上就是因为它不断在不同地方把“真相”和“给别人看的样子”分开了。

### 4. 很多最危险的错误都不是直接 500，而是“看起来成功”

这是这卷故障复盘与测试方法里反复回来的一个主题：

- 端口 OPEN 不代表新进程真的起来了；
- health 200 不代表新代码已生效；
- HTTP 200 不代表库存、MQ、计数、ES、通知都跟上了；
- Alertmanager ready 不代表告警已经送到人；
- Grafana 可打开不代表 series 在出数；
- UI 能看不代表 trace 和日志已经对齐；
- DLQ 重投请求成功不代表语义已经修好。

换句话说，这卷其实非常适合拿来讲一个面试里特别加分的系统判断：

**分布式系统最危险的不是失败，而是局部成功被误判成整体成功。**

## 四、从面试表达角度，这卷最值得讲的不是“用了哪些组件”，而是这些核心取舍

如果后面你要把这卷转成面试表达，最值得提炼的不是服务清单，而是下面这些“为什么不这样做”的答案。

### 1. 为什么库存要做三级扣减？

因为：

- 下单时直接扣会扣得太早；
- 支付成功后才第一次扣又会扣得太晚；
- 所以必须引入“已占位、待决算”的中间态。

### 2. 为什么订单要用事务消息？

因为：

- “先写订单再发消息”会出现订单已成立、库存世界却不知道；
- “先扣库存再写订单”又会出现库存已变而订单没落；
- 事务消息绑定的是“订单本地事实”和“库存预扣可见性”这一跳。

### 3. 为什么购物车用 Redis 为权威？

因为：

- 这是高频、短路径、强交互的准备态集合；
- 它比数据库更需要的是低延迟和原子局部更新；
- 但又不能只停在 Redis，所以再异步落 MySQL。

### 4. 为什么优惠券不用单纯数据库事务？

因为：

- 领券并发判断其实是“库存 + 限领次数”双状态原子收敛；
- Redis 更适合做这一跳；
- MySQL 和 MQ 再负责把结果收成可持久、可回查、可补偿的账本。

### 5. 为什么 BFF 必须存在？

因为：

- 商品详情、笔记详情、用户主页、Feed、购物车聚合都不是单域对象读取；
- 页面成立条件和字段降级语义本身就是后端问题；
- 如果全交给前端并发调下游，故障模型会完全失控。

### 6. 为什么 JWT 还要配 Redis 会话状态？

因为：

- 裸 JWT 解决不了单设备登录、主动注销、会话回收和并发刷新；
- 服务端状态又不能把每个请求都拖成在线查会话；
- 所以才是 JWT 负责携带身份，Redis 负责补会话控制。

### 7. 为什么通知和 IM 不能混成一个“消息系统”？

因为：

- 通知关心的是“用户该知道什么”；
- IM 关心的是“双方说了什么、顺序不能乱”；
- 前者能接受列表和红点作为离线视图，后者必须维护共享会话事实和离线补投。

### 8. 为什么测试要做 15 层验证？

因为：

- HTTP 200 只是第 1 层；
- 后面还有 Redis、MySQL、MQ、Gateway、SkyWalking、ES、Prometheus；
- 系统很多错误不是“接口失败”，而是“后面某层没跟上”。

这几条，正是全卷最像“系统设计答案”的地方。

## 七、如果只读这一份 SUMMARY，应该记住哪几句话

最后把全卷再压缩成几句最值得记住的话。

### 1. 这套系统最重的不是服务数量，而是时序责任被拆散了

`order` 之所以重，不是因为它拥有最多数据，而是因为它必须在正确时刻拉齐别域真相。

### 2. 这套系统最危险的不是直接失败，而是局部成功假装成整体成功

端口 OPEN、HTTP 200、health 200、Prometheus UP、DLQ 重投成功，都不自动代表业务已经真正闭环。

### 3. 这套系统最核心的设计不是“用了很多中间件”，而是“不同语义的状态必须落在不同层”

主数据、缓存权威、检索视图、消息意图、会话状态、页面视图、监控视图，全部被刻意拆开了。

### 4. 这套系统真正能跑稳，靠的不是一次性强一致，而是后半段执行系统长期收尾

事务消息、本地消息表、补偿 Topic、定时任务、对账、DLQ、人工边界，这些不是失败时才想起的补丁，而是主架构的一部分。

### 5. 这卷真正建立的是一套“可以继续深挖、可以继续交接、也可以直接拿去讲项目”的系统解释框架

它不是源码抄录，也不是组件清单，而是一张能回答：

- 业务为什么这么切；
- 工程为什么这么配；
- 分布式为什么只能这样收口；
- 微服务为什么把复杂度转移到了这些地方。

这就是 `vol-xhs` 当前已经完成的最重要工作。
