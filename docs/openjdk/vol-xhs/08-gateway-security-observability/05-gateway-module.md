# gateway：统一入口控制与安全边界层

> 对应模块：`my-xhs-gateway`
> 目标问题：为什么 gateway 不是薄转发层，而是整个系统的入口控制面？

## 一句话答案

`my-xhs-gateway` 不是 URL 转发器，而是统一入口控制面：路由、JWT、HMAC、内部调用令牌、限流、Sentinel、trace 生成与流量染色都在这里先收一道口。它真正负责的不是业务主数据，而是“谁有资格进系统、带着什么上下文进系统、进来以后要先过哪些门禁”。

## 1. 业务：它不持有业务真相，但持有入口真相

gateway 回答的是：

- 这个请求要去哪个服务
- 请求方身份是否可信
- 是用户调用、管理调用还是内部服务调用
- 限流、熔断和流量染色应该在入口怎么生效

这让它天然成为所有业务动作之前的第一层控制面。

## 2. 微服务：它位于所有服务之前，而不是平级参与业务编排

gateway 并不和 order、content、search 一样去持有某段业务状态；它更像这些服务共同共享的北向入口协议层。路由、认证和限流如果不先在这里统一，后面的服务就必须各自重复承担入口防线。

## 3. 分布式：它解决的是“统一门禁”和“上下文透传”

### 3.1 JWT / HMAC / 内部调用是三层不同门禁

- 用户请求通过 JWT 身份识别
- 高敏接口额外通过 HMAC 防重放/防篡改
- 服务间调用通过 `X-Internal-Call` 与内部 token 区分

这三层不是同一种认证机制的不同写法，而是不同调用场景的分层门禁。

### 3.2 trace 和流量染色从入口开始建立

Gateway 会生成或透传 `X-Trace-Id`，并把灰度、压测、AB 组等染色元数据塞进 Header，后续再由下游 HTTP / Feign / MQ 链继续传播。也就是说，trace 在这里不是日志装饰，而是跨服务请求上下文的起点。

## 4. 工程：这个模块最重的是控制语义，而不是路由配置量

### 4.1 Sentinel 和限流不是同一层东西

Gateway 既有 route 级 Sentinel 限流，也有 common 提供的 Redis Lua 滑动窗口限流。前者更像入口流量闸门，后者更像接口级业务限速。两者叠在一起，才形成“粗粒度挡洪峰 + 细粒度控热点”的入口保护。

### 4.2 入口层的失败会被全系统放大

业务服务里一个局部配置错，通常只影响一类接口；gateway 上的认证、路由或限流配置错，会直接影响所有后端服务。因此 gateway 的工程风险不在某个 Controller，而在“单点规则会不会误伤整张入口网”。

## 5. Bug：这轮重扫继续确认的真实边界

### 5.1 多 token 策略已经改成 fail-fast，避免静默绕过

之前已经补过相关问题：多个内部 token / 管理 token 读取或校验如果不 fail-fast，最危险的不是报错，而是静默退化到错误分支。现在这类入口校验已经按 fail-fast 处理，避免“看似兼容，实际漏拦”。

### 5.2 gateway 正确性更多是规则正确，而不是代码行数多少

入口层最典型的问题并不是业务计算错，而是：路由规则写错、白名单放大、Header 透传丢失、降级路径绕开门禁。这些问题往往不会在单个业务模块代码里显影，只会在全链路上暴露。

## 6. 真实故障案例：为什么入口层最危险的错误通常不是 500，而是“错误地放过去”

### 现象

系统表面上还能工作，请求也能打到下游，但后续排查时发现：某些本应拦截的调用被放行、本应要求 HMAC 的路径只校验了 JWT、或者内部调用 Header 没带上却仍然进入了业务服务。

### 根因

gateway 的很多错误不是“程序崩了”，而是“规则降级成了比预期更松的状态”。入口层一旦没有坚持 fail-fast，最坏结果不是报错，而是把本该挡住的请求放进系统。

### 修复前

- 更倾向兼容和兜底
- 某些缺失配置或缺失 token 可能静默回到宽松分支
- 风险在单次请求里不易察觉

### 修复后

- 入口校验按 fail-fast 处理
- 缺失关键 Header / token / 签名时直接拒绝
- 错误暴露在入口，而不是把问题带到业务深处

### 余波

这类故障说明 gateway 最重要的工程价值不是“把请求送过去”，而是“把不该进来的请求尽早挡在外面”。入口层宁可显式失败，也不能默默放松边界。
