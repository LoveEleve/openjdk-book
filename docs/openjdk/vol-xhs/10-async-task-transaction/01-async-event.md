# 01 Async Event：为什么这套系统的异步事件不是“发条 MQ 消息”就结束了

从 `09-data-model-storage/` 转到 `10-async-task-transaction/`，最容易带来的误解是：前面既然已经把 MySQL 分片、Redis 状态平面、ES 索引投影和 MQ 拓扑都拆开讲过了，那么“异步事件”这一篇是不是只需要把这些东西再串一次，最后下一个“系统大量依赖异步解耦”的结论就够了。

如果只是这么写，这一篇就会彻底失去价值。因为在 `my-xhs` 里，异步事件并不是“已经介绍过的 MQ 使用方式”的重复总结，而是另一层更贴近业务现实的机制：**系统为什么要把某些动作从同步主链里拆出去、拆出去以后靠什么保证不丢、不乱、不重复、还能在失败时被补回来。** RocketMQ、XXL-Job、本地消息表、Redis 幂等键、乐观锁、补偿表、DLQ，这些东西放在上一组看是存储或拓扑，放到这一组看则共同组成了一张“同步主链放不下的后半段执行系统”。

`my-xhs` 的很多核心能力都在靠这张执行系统活着。订单创建后，库存预扣和后续状态推进不能全压在用户那一次同步下单请求里，于是出现了本地消息表 + `ORDER_TRANSACTION_TOPIC`；支付成功后，订单状态更新不能只赌一条 MQ 或一条 Feign，于是出现了结果通知 + 回调 + 补偿任务三层链；搜索索引不能同步落 ES，就靠 Canal → MQ → Consumer 增量投影，再由 `IndexRebuildJob` 和 `IncrementalIndexSyncJob` 校偏；通知和未读数也不是“写库后立刻完事”，而是大量依赖异步分发、聚合窗口和对账任务收尾。也就是说，异步事件在这里不是技术选型点缀，而是系统复杂度真正被转移和收束的地方。

所以本篇真正要回答的，不是“系统哪里用了异步”，而是：**为什么这些事件必须异步、它们怎样从同步世界剥离出去、剥离出去后谁来兜底，以及失败时到底是补消息、补状态、补投影，还是补通知。** 只有这一层讲清，后面再写事务消息、补偿、定时任务时，读者才不会把所有异步动作都混成“MQ 重试一下”的同一种东西。

## 先给结论：`my-xhs` 的异步事件不是通知机制，而是同步主链的后半段执行系统

先别急着看代码，先把本篇最重要的人话答案钉住：`my-xhs` 里的异步事件，核心不是“服务之间发消息解耦”，而是把同步主链做不起、做不稳、或做了代价太大的后半段动作，挪进一套**可以重试、可以补偿、可以对账、可以迟到但不能随便丢**的执行系统里。

这条结论至少有三层含义。

第一，异步事件不是“额外通知”，而是业务主链的一部分。订单创建成功、支付成功、退款成功、库存回退、索引更新、通知分发，这些都不是可有可无的附属动作；只不过它们不一定适合同步压在用户请求线程里做完。第二，异步事件不是只有 MQ 一种承载物。本地消息表、补偿表、Redis 幂等键、XXL-Job/XXL-Job 触发的补发任务、RocketMQ 重试 / DLQ、甚至 Feign 回调，都在共同承担异步链。第三，异步事件也不是“最终总会成功”的魔法。它之所以能被系统接受，是因为作者同时设计了重试窗口、幂等约束、状态回查和人工介入边界，而不是因为 MQ 本身会自动修复一切。

如果忘掉这三层差别，你就会在后面的很多设计上产生非常典型的误判。你会以为本地消息表只是为了防 Broker 宕机；会以为补偿任务只是“兜个底”；会以为支付成功之后发条消息就够了；会以为进 DLQ 就等于系统能自己恢复。`my-xhs` 的真实实现恰恰证明这些都不成立。

## 直觉方案为什么不够：同步做完、发条消息通知一下、失败靠重试都不成立

### 失败方案一：把所有后续动作都塞进同步主链

这是最符合直觉的方案：用户点下单，订单服务在一个请求里把订单主表、明细、库存、优惠券、支付初始化、事件流、通知都一起搞定，然后 HTTP 200 返回。这样表面上最简单，成功和失败也都“同步可见”。

问题在于，`my-xhs` 的主链根本承受不起这种做法。只要把库存预扣、券核销、支付创建、事件流写入、通知发送、索引同步、后续状态推进全部塞进同步请求里，接口 RT 会迅速拉长，而且跨服务失败点会被暴露到用户入口：下单请求可能因为搜索索引、通知、远程支付依赖或 Broker 抖动而失败，即便订单主数据本身已经准备好了。

`OrderTransactionService.executeLocalTransaction()` 的实现已经说明作者在主动避免这种路径：本地事务只保证“订单主表 + 明细 + 本地消息表”三件事同库原子成功，再把后续动作交给异步链。也就是说，它故意只把最小同步闭环留在 MySQL 本地事务里。`my-xhs-order/src/main/java/com/myxhs/order/service/OrderTransactionService.java:41`

这说明本篇第一条最重要的理解不是“用了异步很先进”，而是：**同步主链被刻意缩短到只保核心写入，后半段动作必须另起一套执行系统。**

### 失败方案二：本地事务提交后直接 `send` MQ，就算异步化完成

第二个很常见的误解是：只要本地事务提交成功以后顺手发一条 MQ，异步问题就算解决了。这个方案比“全同步做完”前进一步，但仍然不够，因为它没有解决最危险的一种失败：**数据库已经提交成功，但 MQ 没发出去，或者发出去却没被后续消费者正确处理。**

`LocalMessageRetryJob` 的类注释直接点明了本地消息表存在的价值：即使 MQ Broker 整体宕机，本地消息表和订单表在同一 MySQL 事务里，只要 MySQL 不挂消息就不会丢，Broker 恢复后由定时任务扫描补发。`my-xhs-order/src/main/java/com/myxhs/order/job/LocalMessageRetryJob.java:31`

这句话其实已经说明，作者根本不相信“事务后直接 send 一下”能自然可靠。真正可靠的不是那次 `send` 调用，而是**消息先在本地事务里落库，再由异步 job 负责投递和补投**。如果没有这层本地消息表，订单主数据就会和消息投递之间留下一个不可修补的断点。

### 失败方案三：异步失败就靠 MQ 自动重试，系统自然会恢复

第三个误解则更像很多团队对异步系统的默认幻想：反正 MQ 有重试机制，消费失败总会再试几次；试几次不行进 DLQ，之后再重投一下，大多数问题总能回来。

Task13 的真实运行态验证已经把这个误解彻底打穿：团队是从一条真实 `ORDER_CREATED` 本地消息下手，把 payload 改成 malformed JSON，再让 `LocalMessageRetryJob` 重新补发到 `ORDER_TRANSACTION_TOPIC`，随后观察到库存消费者重试 6 次后进入 `%DLQ%inventory-order-transaction-consumer-group`；之后又真实执行了 DLQ 查询和重投。结果是：重投请求链路成功，但因为消息体本身还是坏的，消费结果继续是 `CR_LATER`。`docs/test-3/HANDOFF-TASK13.md:13`

这说明异步事件系统绝不是“失败→自动恢复”这么简单。重试与 DLQ 只能处理**可恢复失败**，不能修复**错误语义本身**。也就是说，异步系统的可靠性最终依赖的不是“重试次数够不够”，而是“失败原因是不是可通过再来一次解决”。

## 先画总图：`my-xhs` 的异步事件执行系统到底由哪些层组成

先把整体拓扑用文字图立住：

```text
同步主链
  -> 本地事务最小闭环
       订单主表 / 明细 / 本地消息表
       支付记录 / 业务主状态
       核心主数据提交

异步执行系统
  1. 本地消息 / 补偿表
     - t_local_message
     - 库存补偿表
     - 各类失败记录 Redis Set

  2. 投递通道
     - RocketMQ Topic
     - Feign 回调（补偿通道）

  3. 消费执行器
     - RocketMQ ConsumerGroup
     - XXL-Job 定时任务 / 重试任务 / 对账任务

  4. 失败恢复层
     - 指数退避重试
     - DLQ
     - 人工 / 运维介入
     - 全量重建 / 增量补偿
```

这张图里最关键的，不是名字多，而是“异步事件”在 `my-xhs` 里从来不是单层能力，而是一整套多级结构。

- 同步主链只负责把最小真相落稳。
- 本地消息 / 补偿表负责保证“事件意图”先被保存。
- MQ 与 Feign 是事件外送的通道，而不是成功本身。
- Consumer、XXL-Job、补偿任务和重建任务共同承担“把事件后半段做完”的职责。
- 重试、DLQ 和人工介入定义的是“做到哪一步还算系统自动恢复，做到哪一步必须出边界”。

只有先把这五层分开，后面很多设计取舍才说得清。

## 本地消息表为什么是异步事件的第一层：它保存的不是状态，而是“状态还没被外部世界消费的意图”

在 `my-xhs` 里，本地消息表的核心价值，不是因为它“和订单表在一个库”，而是因为它把一个本来只存在于程序调用栈里的事件意图，变成了可以被重试任务重新拾起来的持久对象。

`OrderTransactionService.executeLocalTransaction()` 的顺序非常值得注意：先写订单主表，再写事件流，再写明细，最后把 `LocalMessage` 一起插入。也就是说，这张表里的 payload 不是“补记一下日志”，而是和订单主数据一起提交的、后续将被发往 MQ 的正式事件体。`my-xhs-order/src/main/java/com/myxhs/order/service/OrderTransactionService.java:93`

这一步的关键设计点在于：**事件先变成数据库事实，再变成 MQ 事实。** 如果反过来先发 MQ、再指望数据库成功，那一致性问题会完全反过来爆炸。作者显然优先选择了“订单主数据和事件意图一起写入”，把“对外送出去”留给后面的异步执行层。

这也解释了为什么 LocalMessage 里会有 `status`、`retryCount`、`nextRetryTime` 这些字段。它不是简单 outbox 文本，而是带最小状态机的事件待办表：

- `0` = 待处理
- `2` = 失败待重试
- `3` = 本地死信

`LocalMessageRetryJob` 的逻辑完全围绕这套状态在跑。`my-xhs-order/src/main/java/com/myxhs/order/job/LocalMessageRetryJob.java:24`

## `LocalMessageRetryJob` 真正承接了什么：不是定时器，而是事务后半段的第一批执行器

很多人看到 XXL-Job 或本地消息补发任务时，会自然把它归到“运维任务”一类。但 `LocalMessageRetryJob` 在 `my-xhs` 里远远不是后台杂务，它其实是事务后半段的第一批执行器。

它每 30 秒扫描一次 `t_local_message` 中 `status=0/2` 且到达重试时间的消息，然后按 `operationType` 解析目标 Topic，再用 `rocketMQTemplate.syncSend()` 重新投递。若发送成功，就把记录标记成功；若失败，则按 `30s -> 60s -> 120s -> 240s -> 480s` 做指数退避，直到重试耗尽后标记 `status=3` 为本地死信。`my-xhs-order/src/main/java/com/myxhs/order/job/LocalMessageRetryJob.java:89`

这条设计至少有三层特别关键的地方。

第一，它明确接受“至少一次”语义。类注释直接说了：消费端必须保证幂等，因为本地消息表补发是 at-least-once，不是 exactly-once。也就是说，异步系统在这里不是去追求一次不差的完美投递，而是用“至少会被送达多次”来换“不容易丢”，再把幂等压力交给消费者。`my-xhs-order/src/main/java/com/myxhs/order/job/LocalMessageRetryJob.java:69`

第二，它区分了“本地死信”和“RocketMQ Consumer DLQ”。Task13 之所以特地强调“本次要验证的是 RocketMQ consumer DLQ，不是本地消息表死信”，正是因为作者意识到这两类失败不是同一个层次。前者是“消息还没可靠送出到下游消费链”，后者是“消息已经进了消费链，但消费者无论如何处理不了”。`docs/test-3/HANDOFF-TASK13.md:65`

第三，它把补发任务本身也暴露成了可观测对象。`deadLetterCount` 被注册为 Micrometer Gauge，说明本地消息死信不是纯内部状态，而是系统在监控和告警层需要直接看见的风险信号。`my-xhs-order/src/main/java/com/myxhs/order/job/LocalMessageRetryJob.java:53`

这就是为什么本篇必须把它写成“异步事件执行器”，而不是“有个定时任务做补发”。

## 异步事件为什么不只走 MQ：支付链的 Feign 回调与补偿任务说明“异步通道”本身就是多路的

如果把异步事件简单等同于 MQ，你马上就会在支付链里撞墙。`my-xhs-payment` 的补偿设计已经明确说明：支付结果并不只依赖 `PAY_RESULT_TOPIC` / `REFUND_RESULT_TOPIC` 一条路，而是同时保留了 Feign 主动通知和定时补偿任务。

`PaymentNotifyCompensateJob` 的类注释把场景写得非常清楚：支付成功后，本来应该通过 MQ 通知订单服务更新状态；但如果 Broker 宕机、订单服务消费失败、网络分区等问题让这条链没收敛，就由补偿任务扫描支付成功但超过 5 分钟仍未被订单侧确认的记录，再通过 Feign 去查询订单状态、必要时重新通知。`my-xhs-payment/src/main/java/com/myxhs/payment/job/PaymentNotifyCompensateJob.java:20`

这里最重要的设计判断是：作者显然没有把 MQ 当成唯一真理，而是把它看作**第一条后半段执行通道**。一旦这条通道失败，系统还愿意绕到另一条通道（Feign + Job）去继续收敛。这比“MQ 重试几次就算了”要积极得多，也更接近真正的最终一致性工程。

同样的思路也体现在退款补偿上。退款成功通知不是只有一条消息再赌消费者，而是被视作一条必须最终交付给订单状态机的业务事实。MQ、回调、Job 都只是不同阶段的执行者。

因此，在 `my-xhs` 里，“异步事件”更准确的定义不是“进入 MQ 就结束”，而是“脱离同步主链之后，系统为它配好的所有后续执行 / 回查 / 补偿手段”。

## `ORDER_COMPENSATION_TOPIC` 为什么说明补偿消息本身也是一种正式事件，而不是异常分支私货

`OrderCompensationConsumer` 很适合单独拿出来讲，因为它揭示了另一个常被忽略的现实：补偿消息不是系统边角料，而是被正式建模的一类异步事件。

这个消费者明确监听 `ORDER_COMPENSATION_TOPIC`，并且消费的不是某个模糊的字符串，而是 `CompensationMessage` 这种带 `action/orderId/timestamp` 语义的结构体。它还专门做了两层事情：

- 一级幂等：用 Redis `order:compensation:consumed:{msgId}` 去重
- 二级幂等：真正执行业务动作时，依赖 `closeTimeoutOrder` 或对应补偿方法内部的乐观锁 / 状态条件

`my-xhs-order/src/main/java/com/myxhs/order/consumer/OrderCompensationConsumer.java:20`

这说明作者对“补偿”这件事的理解并不是“失败了以后随便再搞一下”，而是把它变成了有 Topic、有结构、有去重、有重试、有 DLQ 预期的正式异步事件流。

这一点非常重要，因为它直接决定系统如何对待失败：不是在原来的同步代码里无限 `catch -> retry`，而是把失败动作提升成另一类正式消息，再交给另一套执行器去处理。对于复杂交易链来说，这种设计远比“方法里重试三次”更可维护。

## 真实故障案例：一条真实坏消息告诉我们，异步系统真正的边界不是“有没有重试”，而是“失败原因是否可恢复”

按照本卷方法论，这篇必须有真实故障案例，而且最好能逼出设计边界。对异步事件这篇来说，Task13 那条真实坏消息几乎就是最适合的案例。

团队不是构造了一条假消息，而是从真实订单的 `t_local_message` 里挑出一行 `ORDER_CREATED` 记录，把 payload 改成非法 JSON，再把 `status` 重置为待补发，让 `LocalMessageRetryJob` 用现有生产链路重新送。之后观察到的是完整闭环：

- 本地消息作为“待办事件意图”被重新拾起
- MQ 收到消息
- 下游库存消费者不断重试
- Consumer 仍无法解析消息体
- 最终消息进入 `%DLQ%inventory-order-transaction-consumer-group`
- 运维 / 诊断链可以真实查询 DLQ 并发起重投
- 但重投后仍然失败，因为坏的不是“链路”，而是“消息内容本身”

`docs/test-3/HANDOFF-TASK13.md:78`

这个案例特别适合放在异步事件篇，而不只是 MQ 篇。因为它揭示了异步系统最本质的一条边界：**事件一旦从同步主链拆出去，系统能做的是保留意图、重试执行、暴露死信、支持重投；但如果事件内容本身已经坏了，异步基础设施不会替你恢复语义正确性。**

换句话说，异步系统可以恢复执行机会，不能恢复错误语义。这个判断一旦立住，读者对后面补偿、DLQ、重试的理解就会稳很多。

## 证据清单：本篇关键结论分别站在哪一层

L0 源码静态证据：

- `OrderTransactionService.executeLocalTransaction()` 明确把订单主表、明细、本地消息表放在同一个本地事务里提交。`my-xhs-order/src/main/java/com/myxhs/order/service/OrderTransactionService.java:41`
- `LocalMessageRetryJob` 明确实现了本地消息表扫描、指数退避补发、本地死信标记与死信再次扫描。`my-xhs-order/src/main/java/com/myxhs/order/job/LocalMessageRetryJob.java:24`
- `OrderCompensationConsumer` 把补偿动作建模为独立 Topic + 结构化消息 + Redis 幂等 + RocketMQ 重试。`my-xhs-order/src/main/java/com/myxhs/order/consumer/OrderCompensationConsumer.java:20`
- `PaymentNotifyCompensateJob` 明确展示了“MQ 失败后转 Feign 回查 / 回调继续收敛”的补偿拓扑。`my-xhs-payment/src/main/java/com/myxhs/payment/job/PaymentNotifyCompensateJob.java:20`

L1 框架 / 语义证据：

- 本地消息表模式在这里承担的是“先把事件意图与主数据一并持久化”，再把实际投递延后到异步执行层，而不是把 MQ send 当作事务内动作。
- at-least-once 语义意味着消费者幂等不是锦上添花，而是异步系统的基本前提。`LocalMessageRetryJob` 已明确把这一点写进注释。`my-xhs-order/src/main/java/com/myxhs/order/job/LocalMessageRetryJob.java:69`
- “补偿”在 `my-xhs` 里不是异常分支私货，而是 Topic / Job / 回调共同参与的正式执行层。

L2 运行态证据：

- `docs/test-3/HANDOFF-TASK13.md` 已真实证明：本地消息表 → MQ → consumer retry → DLQ → 查询 / 重投 这整条异步链不是推演，而是运行态闭环。`docs/test-3/HANDOFF-TASK13.md:56`
- `docs/test-3/HANDOFF-TASK11.md` 已把补偿三动作 MQ 投递列为修复确认项，说明补偿消息链在历史回归中被真实验证过。`docs/test-3/HANDOFF-TASK11.md:85`

## 边界清单：哪些话现在能说，哪些还不能写满

第一，当前可以明确写出 `my-xhs` 大量依赖异步事件承接同步主链后半段，但不能把它写成“同步路径已经极简到只剩数据库提交”。不同链路同步部分长短不一，支付、通知、搜索仍各自保留了不同程度的同步逻辑。

第二，当前可以明确写出本地消息表 + MQ + 补偿任务已经构成真实执行系统，但不能写成“任何失败最终都会自动收敛”。坏 payload、消费者逻辑错误、外部依赖长期不可达，都可能把问题推到 DLQ 或人工介入边界。

第三，当前可以明确写出补偿消息在系统里被正式建模，但不能把它写成“所有异步失败都统一走补偿 Topic”。有些链路走重试，有些走本地死信，有些走 Job 重扫，有些走全量重建，恢复路径本身是分层的。

第四，当前可以明确写出本地消息表是交易异步事件的第一层保障，但不能把它写成“消息绝对不丢”。更准确的说法是：只要本地事务提交成功且 MySQL 健康，事件意图就先被持久化；但后续如何送达、能否消费、是否需要补偿，仍是异步执行层的事情。

## 收网：这篇 Async Event 真正建立了什么

到这里可以回收开头的问题了。`my-xhs` 的异步事件，不是“发条 MQ 消息解耦一下”的轻量技巧，而是一整套把同步主链做不起的后半段动作移出请求线程、再通过本地消息表、MQ、Consumer、补偿任务、重试、DLQ 和人工边界共同承接的执行系统。它真正复杂的地方，不在“是否异步”，而在“异步以后谁来执行、失败后谁来继续、什么时候可以自动恢复、什么时候必须承认边界”。

从业务逻辑视角看，它守住的是订单、支付、通知、搜索这些主链路后半段的持续推进；从工程视角看，它把本地事务、XXL-Job、RocketMQ、Feign 回调、Redis 幂等和补偿任务编织成多级执行层；从分布式视角看，它明确接受 at-least-once，转而用幂等、重试与死信边界控制代价；从微服务视角看，它让“同步接口返回成功”不再等于“业务已经全部做完”，而只等于“最小同步闭环已提交，后半段进入异步执行系统”。

更重要的是，本篇把一个特别容易被讲虚的事实钉住了：**异步系统最关键的从来不是“有没有 MQ”，而是“事件意图先被谁保存、后半段由谁推进、失败后还有没有下一层执行者”。**
