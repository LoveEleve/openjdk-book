# 01 Port Conflict：为什么“端口被占用”在这套系统里不是小事故，而是最容易误判的运行时故障

很多人第一次看到 `Port already in use` 或 `Address already in use`，直觉都会觉得这是一类很低级、很快就能处理的故障：把旧进程杀掉、重启服务、端口通了，事情就结束了。如果只从单机开发的角度看，这样理解当然没错。

但 `my-xhs` 的历史材料反复证明，在一个 15+ 微服务、带统一重启脚本、带 health 探活、带 SkyWalking / Sentinel / XXL-Job / Logstash / Prometheus 全栈运行面的系统里，端口冲突根本不只是“谁占了一个端口”的问题。它更危险的地方在于：**端口冲突非常容易被脚本健康检查、旧进程残留、历史 PID、同端口旧实例 health 200、以及“端口通就代表新代码生效了”这类运行时错觉一起掩盖。** 结果就是：你以为服务已经恢复，实际上恢复的是旧进程；你以为新版本已经上线，实际上线上还在跑旧 jar；你以为只是 analytics / coupon / search 某一个服务没起来，实际却是在整条交付链里留下了一个非常难追的“假恢复”状态。

这也是为什么这一篇不能只是罗列 `19003`、`19010`、`19016` 三个端口冲突案例，而必须把“端口冲突为什么会在这套系统里变成误判事故”讲透。因为前面的交接材料已经明确把三起历史事实写出来了：analytics `19003`、search `19016`、coupon `19010` 都曾因端口冲突导致启动失败；而更糟的是，后续 review 还发现 `restart-service.sh` 的健康检查存在假阳性，旧进程占着端口时，脚本仍可能误报新进程已经 UP。`docs/openjdk/vol-xhs/HANDOFF-XHS.md:161` `docs/review-1/02-findings/high/F-014-restart-script-health-check-false-positive.md:15`

所以本篇真正要回答的，不是“这三个端口曾被谁占用”，而是：**为什么端口冲突在 `my-xhs` 里会从一个看似简单的 bind 错误，演变成一类会误导运维、误导测试、误导交付判断的运行时故障。**

## 先给结论：端口冲突在这里最危险的不是服务起不来，而是“旧服务还活着，新服务起不来，但脚本说一切正常”

先别急着看脚本和端口号，先把本篇最重要的人话答案钉住：`my-xhs` 里的端口冲突，真正危险的点并不是某个微服务启动失败本身，而是它极容易制造一种比“直接挂掉”更难排查的状态——**旧实例还占着端口，新实例因端口冲突启动失败，但健康检查和重启脚本却把旧实例的健康结果错认成了新实例的成功。**

如果只是“服务完全起不来”，故障往往反而比较直白：端口不通、健康检查失败、日志报错，排查目标很快会收敛。但 `my-xhs` 这里的高风险场景是另一种：

- 某个旧 Java 进程还没完全退出
- 新进程启动时因端口被占直接 `APPLICATION FAILED TO START`
- `curl localhost:$PORT/actuator/health` 却打到了旧进程
- 脚本由此误判“模块 UP”
- 于是后续测试、回归甚至上线判断都建立在旧进程上

这正是 `F-014` 文档里明确记下来的现象：gateway 一次重启时，旧实例仍占 `19000`，新进程因为端口冲突启动失败，但脚本还是误报 `✅ gateway UP`。也就是说，端口冲突在这里不是单纯的资源争抢，而是一种会制造**假恢复**的运行时事故。`docs/review-1/02-findings/high/F-014-restart-script-health-check-false-positive.md:22`

这条结论特别重要，因为它会直接改变读者对后面三起历史冲突案例的理解方式：analytics / coupon / search 那三次不是“把冲突解决了就完事”，而是必须追问“当时恢复的是新实例还是旧实例、脚本和探活是否可靠、端口通是否真代表新代码生效”。

## 直觉方案为什么不够：杀掉旧进程、重新启动、看到端口 OPEN 还远远不够

### 失败方案一：只要 `ss` / `curl` 看到端口通，就说明服务已经恢复

这是最常见也最危险的直觉。很多排障动作会在看到 `19003 OPEN`、`19010 OPEN`、`19016 OPEN` 后就下意识认为服务已恢复。交接文档里也确实把服务恢复状态写成“端口全通”。但问题在于，**端口通只说明“有某个进程在监听”，并不等于“就是你刚刚启动的新进程”。**

如果旧实例还没死净，或者手工重启时 PID / 端口关系搞乱了，`OPEN` 只能证明端口上有 responder，而不能证明 responder 的代码版本、启动时间、参数、profile、依赖初始化状态都正确。`F-014` 的危险之处正在这里：health 端点是通的，但通的是旧实例，不是新实例。`docs/review-1/02-findings/high/F-014-restart-script-health-check-false-positive.md:15`

所以在 `my-xhs` 这种系统里，端口 OPEN 最多只能作为**弱证据**。强证据至少还要包含：端口监听 PID 是否等于新进程 PID、日志里是否真的出现新实例的 `Started ... in X seconds` 而不是 `APPLICATION FAILED TO START`、以及功能探活是否打到了新代码路径。

### 失败方案二：健康检查 200 就代表新服务就绪

这比单纯看端口更“高级”一点，但在 `my-xhs` 里同样不够。因为 review 已经明确指出：`restart-service.sh` 的健康检查只是简单 `curl http://localhost:$PORT/actuator/health`，并没有校验这个响应到底来自哪一个 PID。只要旧进程还占着端口，就会误把旧进程当成新进程。`docs/review-1/02-findings/high/F-014-restart-script-health-check-false-positive.md:19`

这意味着 health 200 在这里不是强语义的“新实例准备好了”，而只是“这个端口上有一个能返回 health 的进程”。如果运维或测试把 health 200 直接等价成“本次重启成功”，端口冲突就会被掩盖成“系统看起来一切正常”。

这也是为什么文档里把 health 探活本身当成风险源，而不是把它仅当成故障发现器。对 `my-xhs` 这种多服务、统一脚本管理的系统来说，**探活机制如果没有和真实 PID / 日志 / 业务链路一起验证，本身就可能成为误导来源。**

### 失败方案三：端口冲突只是单个服务的偶发问题，不会扩散成系统性风险

如果只看 analytics、coupon、search 三个端口号，容易觉得这些只是三个孤立事故：谁手工多起了一个进程，谁没杀干净而已。但历史材料实际上已经在提醒我们，端口冲突会扩散成至少三层系统性风险。

第一层是**交付风险**。新代码没有真正起来，旧代码还在服务，于是你验证到的不是你以为的版本。第二层是**回归测试风险**。测试脚本继续请求旧实例，回归结果就会混入历史行为。第三层是**运维脚本风险**。错误的 PID 被写回、后续 stop/restart 指向错误进程，问题会自我放大。`docs/review-1/02-findings/high/F-014-restart-script-health-check-false-positive.md:30`

所以这篇必须把端口冲突当成运行时交付故障来写，而不是单个微服务的偶发启动报错。

## 先画总图：`my-xhs` 里的端口冲突究竟是怎样变成“假恢复”的

先把这类故障的典型路径用文字图立住：

```text
旧实例仍存活
  -> 仍监听 19003 / 19010 / 19016 / 19000
  -> 新实例启动
       -> Tomcat/Netty bind 同端口失败
       -> APPLICATION FAILED TO START / Port already in use
  -> 重启脚本执行 health 检查
       -> curl 命中旧实例 /actuator/health
       -> 返回 200
       -> 误报新模块 UP
  -> 后续验证继续基于旧实例进行
       -> 端口 OPEN
       -> health 200
       -> 但新代码未生效
```

这张图里最关键的不是 bind 失败本身，而是它后面紧跟着的**错误观测链**。如果没有这一层错误观测，端口冲突只是普通启动失败；有了这一层，端口冲突就会演变成“明明没恢复，却被判定为已恢复”的假象。

这也是为什么本篇后面会反复强调：在 `my-xhs` 里，端口冲突排障不能止于“把端口抢回来”，还必须验证恢复证据链本身是不是可靠。

## 三起历史案例为什么值得放在一起讲：它们看似是三个端口，实则是同一类运行时故障模式

交接总文档已经把三起典型冲突列得很清楚：

- `F-036`：analytics 端口 `19003` 冲突启动失败
- `F-038`：search 端口 `19016` 冲突启动失败
- `F-039`：coupon 端口 `19010` 冲突启动失败

`docs/openjdk/vol-xhs/HANDOFF-XHS.md:161`

这三起案例单看像是不同模块的问题，但放在一起看，实际反映的是同一类运行时模式：**服务启动依赖固定端口，旧进程或异常残留一旦不干净，新的 JVM 就会直接在绑定阶段失败。**

而且这三起案例特别适合放在运行时故障组的开篇，不只是因为它们直观，还因为它们比逻辑 bug 更“系统基础设施化”：这类故障与具体业务代码几乎无关，但会直接决定 analytics、coupon、search 这些域到底有没有资格进入后续所有回归与验证。换句话说，它是比业务 bug 更靠近“环境正确性”的前置事故。

更关键的是，现在本机 `19003`、`19010`、`19016` 三个端口都已经实测 `OPEN`。这条 L2 证据可以支撑“当前状态已恢复”，但同样必须按方法论提醒：这只能证明当前有进程在监听，并不能单独反推“历史冲突的根因链条就是现在已经完全不可再现”。也就是说，恢复状态可以被写成现时事实，但故障成因与脚本风险仍必须单独复盘。

## `restart-service.sh` 为什么把一类普通端口冲突升级成高优先级故障

如果只有端口冲突，没有脚本假阳性，很多时候这类问题也许还停留在“中等麻烦”。真正把它升级成高优先级故障的，是统一重启脚本把“错误观测”标准化了。

`F-014` 文档已经把问题拆得很细：

1. 杀旧进程时只取第一个匹配 PID，可能留存多个同模块旧实例；
2. health 检查只看 `localhost:$PORT/actuator/health`，不校验响应是否来自新 PID；
3. 回写 pids 文件时同样可能写进旧进程；
4. 于是新进程明明因为端口冲突已经 `APPLICATION FAILED TO START`，脚本仍然会给出“UP”的结论。`docs/review-1/02-findings/high/F-014-restart-script-health-check-false-positive.md:17`

这说明在 `my-xhs` 里，端口冲突故障真正该被复盘的对象，不只是占端口的进程，还有**脚本如何放大这类故障**。因为统一脚本一旦有误导能力，错误状态就会比单次手工重启更容易被重复生产出来。

这也是为什么历史 handoff 里后来反复强调：重启一律用 `restart-service.sh`，并且 timeout 给足；但这条纪律本身还不够，review 又进一步揭示脚本自己的健康判断仍有漏洞。`docs/test-3/HANDOFF-TASK11.md:150`

也就是说，脚本既是规范化恢复器，也是故障放大器。对端口冲突来说，这一点必须讲透。

## 为什么“当前端口 OPEN”只能算恢复证据，不能替代根因证据

本机现在 `19003`、`19010`、`19016` 都能连通，这说明 analytics、coupon、search 当前监听已经恢复。作为运行态现状，这当然是有价值的证据。

但方法论要求我们必须把它放在正确层级：这条证据只能支撑“此刻服务端口是开的”，不能单独支撑“历史冲突已被彻底消除”或“重启链从此绝对可靠”。因为端口 OPEN 不会告诉你：

- 监听的是旧进程还是新进程
- 这次恢复是否仍经过了假阳性脚本路径
- 新进程是否真的携带了正确参数 / profile / 依赖初始化
- 下一次重启会不会再次踩中同样脚本缺陷

所以本篇里会同时保留两种口径：

- **L2 现时状态**：当前 19003/19010/19016 都 OPEN
- **L0/L1 根因与风险**：端口冲突 + 脚本假阳性路径曾真实发生，且恢复证据链仍有被误导的可能

这就是为什么“端口恢复”和“故障复盘”必须分开写。

## 真实故障案例：gateway 旧实例占端口，health 200 掩盖了 `APPLICATION FAILED TO START`

按照本卷方法论，每篇都要有一个能逼出设计问题的真实故障案例。对端口冲突篇来说，最典型的不是 analytics/search/coupon 哪一次单独抢端口，而是 `F-014` 里那次 gateway 重启假阳性，因为它把“端口冲突 + 错误观测”两层风险一次性暴露了出来。

案例过程非常清楚：

- 旧 gateway 实例仍占着 `19000`
- 新 gateway 进程启动时因端口冲突直接 `APPLICATION FAILED TO START`
- 脚本仍去 curl `localhost:19000/actuator/health`
- 返回 200，但这个 200 来自旧实例
- 脚本因此误报“新 gateway UP”

`docs/review-1/02-findings/high/F-014-restart-script-health-check-false-positive.md:22`

这类案例特别适合作为本篇主案例，因为它最能逼出“为什么端口冲突不是小事故”。如果只是 coupon / search / analytics 某次启动失败，团队还能靠重试或人工盯日志及时发现；但当错误观测链和旧实例残留叠在一起时，系统会进入一种最糟糕的状态：**故障已经发生，但恢复系统宣布成功。**

用方法论的五段式收它：

- 现象：新进程端口冲突启动失败，但脚本误报服务已就绪
- 根因：旧实例未完全退出、脚本只杀一个 PID、health 检查没校验新 PID、端口监听仍由旧实例持有
- 修复：脚本应全量清理匹配进程，校验新 PID 真正监听端口，并在日志中检查 `APPLICATION FAILED TO START`
- 验证：这条修法不是抽象建议，而是直接来自 F-014 文档中对 `restart-service.sh` 三个问题点的逐条修复建议：全量 kill、`ss -lntp` 核对监听 PID、检查启动日志失败关键词。`docs/review-1/02-findings/high/F-014-restart-script-health-check-false-positive.md:37`
- 余波：以后任何“重启后 health 200”的判断，都不能脱离日志与端口-PID 绑定关系单独成立

这正好说明端口冲突篇的重点，从来不是哪一个端口号，而是“错误恢复证据链会不会反过来误导人”。

## 为什么这类故障最适合放在运行时故障组开篇：它先于业务、先于一致性、先于链路

把端口冲突放在 `11-runtime-failure-review/` 的第一篇，还有一个很重要的原因：它是一类会在**业务逻辑尚未开始之前**就决定系统是否进入正确状态的故障。

库存、订单、支付、通知、搜索、推荐这些后面的复杂故障，都默认前提是服务本身已经按照新版本、正确参数、正确 profile 启动起来。端口冲突则会在这一切之前，把系统困在“旧实例还活、新实例已失败、状态却看似正常”的假世界里。也就是说，后面所有更复杂的排障，其实都建立在“你得先确认自己看到的是不是对的进程”这个前提上。

从这个角度看，端口冲突不是低级问题，而是最基础的运行时真相校验问题。它很适合作为运行时故障复盘组的入口。

## 证据清单：本篇关键结论分别站在哪一层

L0 源码 / 文档静态证据：

- `F-036`、`F-038`、`F-039` 已在交接总文档中明确记录为 analytics/search/coupon 的端口冲突启动失败案例。`docs/openjdk/vol-xhs/HANDOFF-XHS.md:161`
- `F-014` 文档已明确拆出 `restart-service.sh` 的三处关键风险：只杀一个匹配进程、只看 health 端口、PID 文件可能写错。`docs/review-1/02-findings/high/F-014-restart-script-health-check-false-positive.md:9`
- 多轮 handoff 已把 `restart-service.sh` 固化成标准重启入口，说明这不是偶发脚本，而是整个运行体系的一部分。`docs/test-3/HANDOFF-TASK11.md:150`

L1 框架 / 语义证据：

- “端口 OPEN”只能证明有进程监听，不证明新实例已就绪。
- “health 200”只能证明端口上有可响应进程，不证明响应来自新 PID。
- 统一重启脚本一旦缺少 PID / 端口 / 日志三方交叉验证，就可能把普通 bind 错误升级成假恢复事故。

L2 运行态证据：

- 当前本机 `19003`、`19010`、`19016` 均实测 `OPEN`，说明 analytics/coupon/search 当前端口已经恢复。
- `F-014` 文档已记录 2026-08-17 的真实复现场景：gateway 旧实例占 `19000`，新进程启动失败，但脚本仍误报 UP。`docs/review-1/02-findings/high/F-014-restart-script-health-check-false-positive.md:22`
- 历史恢复态文档也已明确写过服务恢复状态中 analytics、coupon、search 端口恢复可用。`docs/openjdk/vol-xhs/HANDOFF-XHS.md:169`

## 边界清单：哪些话现在能说，哪些还不能写满

第一，当前可以明确写出 analytics/coupon/search 都曾发生端口冲突启动失败，但不能把它写成“根因已经逐条精确定位到具体占用进程并永久根除”。现有材料更强的是恢复事实与脚本风险，而不是每次占用者的完整身份学。

第二，当前可以明确写出 `restart-service.sh` 的健康检查路径存在假阳性风险，但不能把它写成“脚本完全不可用”。更准确的说法是：脚本已经统一了很多重启细节，但在 PID / 端口 / 日志交叉验证上仍存在边界。

第三，当前可以明确写出本机三个冲突端口现在都是 OPEN，但不能把它写成“服务恢复 = 新代码必然已生效”。端口恢复只是一层现时证据，不是版本正确性的最终证明。

第四，当前可以明确写出端口冲突是运行时基础故障，但不能把它轻率写成“只要修脚本就解决一切”。脚本只是故障放大器之一，进程残留、手搓重启、历史 PID、外部探活方式都会共同影响这类事故。

## 收网：这篇 Port Conflict 真正建立了什么

到这里可以回收开头的问题了。`my-xhs` 的端口冲突不是“小服务没起来”的低级问题，而是一类非常容易制造假恢复、误导交付判断、并污染后续回归结论的运行时基础故障。它真正危险的地方，不是 bind 失败本身，而是旧实例残留、脚本探活、PID 记录和 health 结果可能一起把错误状态伪装成成功状态。

从业务逻辑视角看，它甚至还没进入业务，就已经决定后面的所有验证是不是在看正确的进程；从工程视角看，它暴露的是重启脚本、探活方式、端口-PID 绑定与日志校验之间的断裂；从分布式视角看，它说明多服务系统的“恢复证据”本身也必须被设计，而不是随手 curl 一下；从微服务视角看，它是比业务 bug 更基础的运行真相问题。

更重要的是，本篇把一个特别容易被低估的事实钉住了：**在 `my-xhs` 里，端口冲突最可怕的不是服务没起来，而是你以为它已经起来了。**
