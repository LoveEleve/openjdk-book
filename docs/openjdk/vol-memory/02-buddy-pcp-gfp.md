## 现在真正的问题不再是“页是谁”，而是系统怎么从一大堆页身份证里，当场拼出你要的那块连续内存

上一篇我们把物理页先对象化了：每个物理页都有自己的 `struct page`，状态、归属、引用、组织位置都挂在这张管理卡上。那一篇解决的是“页是什么”。

可光知道页是什么，还远远不够。真正让内核天天头大的，是另一类更现实的问题：驱动现在想要一页，文件系统现在想要几页，网络栈可能想要一串页，某个子系统甚至想要一段更大的连续物理块。**内核怎么在机器已经跑了半天、页早就到处被切碎、被占、被缓存、被映射之后，仍然又快又尽量稳地把这些请求发出去？**

这就是 Buddy 这一篇要回答的核心困惑。

如果把上一篇的 `struct page` 比作每个房间的身份证，那这一篇讨论的就是酒店前台真正的发房逻辑：客人来要单间、标间、套房时，前台不能每次都把整栋楼重新翻一遍，更不能等楼里全住乱了才想起怎么整理。它必须提前把空房按规格分好类，优先走最快的发房路径，压力大时再去清理和挪腾，同时还得知道哪些客人能等、哪些客人一秒都不能卡。

Linux 对物理页做的，也正是这样一套“发货系统”。它的主线不是一个算法名字那么简单，而是几层机制一起配合：

```text
空闲页组织：
  Buddy 把空闲页按 2^order 大小分桶
  让“找连续块”与“释放合并”都能快速完成

热路径加速：
  PCP 让每个 CPU 先用自己的小缓存
  避免大家每次都去争全局 zone 锁

碎片治理：
  迁移类型让可移动与不可移动页尽量分居
  给 compaction 和大块分配留活路

分配契约：
  GFP 告诉内核这次能不能睡、能不能回收、能不能碰紧急预留

压力闸门：
  watermark 把“还能正常分”“该后台回收了”“只剩救命钱”分成多级

旁路方案：
  kmalloc 偏向物理连续与热路径
  vmalloc 用虚拟连续绕开物理碎片现实
```

这一篇最该先记住的一句话是：**Linux 发内存时，真正难的从来不是“有没有页”，而是“怎样在高频请求里快速凑出连续块，同时把锁竞争、碎片化和系统失血控制住”。**

## 一、如果不想每次分配都全局搜索，空闲页就必须在平时先被组织好

### 1. 最笨的方案：来一个请求，就现场去整个物理内存里找一段连续空闲页

先从最朴素的直觉开始。假设驱动要 3 页、文件系统要 8 页、网络栈要 1 页。最直接的办法似乎是：那就等请求来了，再扫描整片物理内存，看哪里有一段连续空闲页，找到就发出去。

这个方案有一种“逻辑上总能做成”的诱惑。因为只要空闲页足够多，理论上扫描总能找到一段合适的连续空间。

问题在于，Linux 的分配不是偶尔来一次，而是高频、并发、到处都在来。你要是每来一个请求，都去全局扫物理页、判断哪些页空着、哪些页又刚被别人拿走、哪些连续区段还能用，那今天的内存分配就会从热路径直接退化成灾难现场。扫描本身贵，扫描期间还容易跟别的 CPU 抢同一批全局状态，连续性判断也不能靠想象完成。

更关键的是，请求大小还五花八门。你不能只会找 1 页，也得能找 2 页、4 页、8 页、16 页，甚至更大。若没有预组织，任何一个请求都变成“先在乱仓库里找货，再临时拼装”，速度和复杂度都会失控。

### 2. 第二个直觉方案：空闲页都丢进一个统一链表，需要大块时从里头抽连续页

如果觉得全局扫描太蠢，更进一步的想法往往是：那就至少把空闲页都维护在一个 free list 里，分配时从这个链表里找合适的页。

这比完全裸扫前进了一步，因为空闲与非空闲至少被区分开了。但它仍然不够。原因在于，一个“只知道谁空闲”的总链表，并不等于“知道哪几页能组成一个连续块”。

连续内存分配真正麻烦的，不是找任意空闲页，而是找**恰好连在一起**的一组空闲页。一个总链表只告诉你“这些页空着”，并不天然告诉你“哪两页是伙伴、哪四页原本属于同一更大块、这次拆了以后未来还能不能顺手拼回去”。如果没有更强的组织结构，大块请求一来，系统还是得额外花大量代价去判断连续关系。

### 3. Linux 的核心选择：空闲页不是平铺存放，而是按 2 的幂大小预先分组

所以 Linux 选的不是“来了再找”，也不是“统一放在一个大空闲池”，而是 Buddy 那个看起来老派、但极其工程化的答案：**把空闲页按 2 的幂大小预先组织起来。**

也就是说，空闲页世界不是一个平面仓库，而更像一组按箱规分层的货架：1 页一格，2 页一格，4 页一格，8 页一格……每一层都维护“当前有哪些这么大的连续空闲块”。你要 1 页，优先从最小格子拿；你要 8 页，就优先看 8 页格子有没有现货；没有时，再从更大格子拆。

这样一来，分配与释放都被改写了。分配不再是“全局搜索连续段”，而是“先看对应 order 有没有现货，没有就拆大块”；释放也不再是“随手丢回池子”，而是“看看我的伙伴是不是也空着，是就合并成更大块继续往上并”。

Buddy 的精髓，恰恰就在于它把连续块世界预先组织成一棵能拆也能并的层次结构。你今天觉得它只是“2 的幂分组”，后面越读越会发现：这一步几乎决定了 Linux 物理页分配为什么还能维持在可接受复杂度里。若要把这一节补成更硬的源码正文，最关键的证据位应回到 `mm/page_alloc.c` 中围绕 `free_area`、伙伴拆分/合并与按 `order` 管理空闲块的路径：它们共同支撑“Buddy 不是一堆空闲页，而是一组按 2 的幂规格分层存货的连续块货架”这句判断。

## 二、`free_area`：Buddy 真正存货的地方，不是“空闲页集合”，而是“按规格分层的连续块货架”

### 1. `free_area` 解决的不是“谁空闲”，而是“谁能按什么规格出货”

当我们说 Buddy 把空闲页按 `order` 分组时，不要把它想成一个模糊概念。更准确的心智模型是：**每个 zone 里，都有一组按块大小分层的空闲结构。**

这里最关键的不是某个结构体声明的语法，而是它背后的视角变化。过去你可能会想“空闲页是一批单页”；可到了 Buddy 这里，真正的一等公民不再只是单页，而是“1 页块、2 页块、4 页块、8 页块……”这些规格化连续块。

于是 `free_area` 真正维护的，不是“零散空页名册”，而是“当前有哪些 2^order 大小的连续空闲块”。你要什么规格，先看哪一层；拿不到，再向上借更大块来拆。

### 2. 为什么偏偏是 2 的幂，而不是 3 页、5 页、7 页这种任意规格

这正是 Buddy 最值得停下来咀嚼的地方。很多人知道它“按 2 的幂分组”，但没有继续问：**为什么非得这样分？**

核心原因有两个。

第一，任何请求都能被“向上取整到最近的 2 的幂，再一路拆下来”处理。比如你要 3 页，不必真的维护“3 页块”这种独立规格，而是去找一个 4 页块，拆成两个 2 页块，再继续把其中一边拆成单页，最终凑出需要的数量。这样所有请求都能借助有限层级的拆分逻辑完成，而不是为每种奇怪尺寸都单独养一套仓储规则。

第二，也是更精妙的一点：**伙伴关系因此变得唯一且可快速计算。** 一个 `order` 的块，只会有一个同级伙伴；只要双方都空闲，就能合并回上一级。这个“唯一伙伴”的性质，正是 Buddy 能把释放合并写成快速位运算的根基。如果块大小是任意规格，这种整洁的父子与兄弟关系就会很难维护，合并也会变得混乱。

所以 2 的幂不是拍脑袋选的，它同时满足了“易于拆分”和“易于回收合并”这两件事。

### 3. `PageBuddy` 与 order 信息为什么必须回写到页元数据里

你前一篇刚建立过 `struct page` 的心智模型，这里马上就能用上。Buddy 并不是在某个完全独立的小宇宙里运行；它仍然要借助每个页对象自己的元数据来表达“我现在属于哪个空闲块”。

这就是为什么一页回到 Buddy 体系时，系统不仅要把它挂进合适的 `free_area` 链表，还要在页元数据上留下标记和层级信息。否则，后面释放别的页想找伙伴、或者分配时想判断当前块的身份，就失去了统一落点。

换句话说，Buddy 虽然维护的是“连续块”世界，但它并不是把 `struct page` 抛开重来，而是建立在“页本体已经对象化”这个前提之上。连续块最终仍然要借助 page 元数据被识别、被拆开、被并回去。

### 4. 先别急着抠细枝末节，先记住 Buddy 的第一张总图

到这里主线其实只发生了三件事：

- 空闲页不能等请求来了再临时搜索，必须平时就先组织好。
- 这种组织不是“所有空闲页一锅炖”，而是按 `2^order` 规格分层维护。
- 每层都代表一种可直接出货的连续块规格，而 page 元数据又负责给这些块留下能回查的身份痕迹。

只要把这张图先记住，后面的分配、释放、碎片治理和水位控制就有了落脚点。

## 三、分配路径：Linux 真正擅长的不是“总能分到”，而是先把绝大多数请求挡在便宜路径里

### 1. 最重要的误解：`alloc_pages()` 不是一个“拿不到再说”的简单取货动作

很多人第一次看分配 API，会觉得 `alloc_pages(gfp, order)` 的语义非常直接：给我若干连续页，系统去拿，拿到就返回，拿不到就失败。

这当然是接口表面长相，但它完全没体现 Linux 在背后最在意的事情：**不是所有“拿页”的代价都一样。** 有些情况是现成块一把拿走，有些情况要先补 per-CPU 缓存，有些情况则意味着内存已经吃紧，系统得启动回收、压缩，甚至最后进入 OOM 决策。

所以从内核设计视角看，分配路径不是单条直线，而是一组按代价递进的通道。它最聪明的地方，不是最终一定能不能分到，而是尽可能把大多数请求留在最便宜的前两层，不让整个系统动不动就坠入慢路径泥潭。

### 2. 第一层：目标规格本来就有现货，直接拿走

最理想的情况，是目标 zone 的目标 `order` 本来就有空闲块。这时分配动作本质上只是：找到对应层级，把一块连续空闲块从链表里摘下来，交给调用方。

这条路径之所以便宜，不只是因为“步骤少”，更因为它几乎不需要额外治理动作。你没有去拆更大块，也没有惊动回收系统，更没有打断别的任务。它像仓库货架上正好有一整箱现货，前台扫一眼规格就能直接发货。

这也是 Buddy 全部设计最理想的兑现方式：提前组织好空闲块，所以请求来时可以直接命中现货层。

### 3. 第二层：目标规格没货，但更大规格有货，于是拆下来发

如果目标层没有现货，Buddy 不会立刻崩，而是会去更高的 `order` 看看有没有更大的连续块。只要有，就把它一路拆下来：8 页块可以拆成两个 4 页块，4 页块可以再拆成两个 2 页块……直到拆出你这次需要的规格。

这一步很关键，因为它说明 Buddy 的核心价值不只是“分层存货”，更是“上层现货可以向下拆分复用”。如果没有这条能力，所有层级都会彼此隔绝，你要 2 页时只能等 2 页层刚好有货，明明系统还有大量 8 页、16 页空闲块也帮不上忙，那会非常浪费。

从读者角度看，这里最该记住的是：**Buddy 不是在维护很多互相孤立的 free list，而是在维护一套可拆可并的规格树。** 分配时，拆分就是这棵树自上而下吐出小块的过程。

### 4. 第三层：本地现货与拆分都不顺时，才会真正碰到压力世界

如果目标层没货，向上找也不理想，或者当前 zone 与上下文限制把选择空间压得很窄，系统才会逐步走到更昂贵的世界：尝试其他候选 zone、唤醒后台回收、允许直接回收、必要时做 compaction，再不行才考虑 OOM。

这条路径一定要从“代价模型”来理解，而不是只背函数名。因为它真正表达的是：**内核宁可花大量心思设计前两层，也是不想把普通分配变成一次次系统级应激反应。** 走到慢路径，本身就是一种告警，说明当前不是普通取货，而是开始挤占库存、拆东墙补西墙，甚至要牺牲别人来活命了。

### 5. 所以分配路径的本质，不是三级流程图，而是“代价逐层递增”的防线体系

现在把这一节压成一句人话：

- 最便宜的是“对应规格直接有货”。
- 再贵一点的是“拆更大现货给你”。
- 明显开始紧张的是“得换 zone、补缓存、触发治理”。
- 最贵也最糟的是“回收、压缩、最终 OOM”。

只要你带着这个代价视角再去看 `alloc_pages()`，很多内核行为就都顺了：为什么要有 PCP，为什么要有水位线，为什么要细分 GFP 语义，为什么要尽量把不可移动页隔离开。它们全都在为同一件事服务：**守住快路径，别让普通分配一上来就把系统拖进慢路径。**

## 四、PCP：如果每次拿一页都去抢全局锁，再好的 Buddy 结构也会被多核机器磨碎

### 1. 失败方案：每个 CPU 每次分配单页，都直接去动 zone 的全局空闲结构

到这里你可能会觉得，Buddy 已经很优雅了：空闲块按规格分层，拿不到就拆，释放还能并。是不是问题已经解决了？

还没有。因为 Buddy 解决的是“如何组织连续块”，但并没有自动解决“多核并发怎么高频拿这些块”。在现代机器上，最常见的分配之一恰恰是单页或小块页分配，而且来自不同 CPU 的请求会非常密。要是每次都直接去操作 zone 上的全局空闲结构，那大家虽然逻辑上能分到页，却会在锁竞争上打成一团。

这就是第二层现实：**数据结构对不对是一回事，热点访问会不会把它的锁打爆又是另一回事。**

### 2. 为什么单页分配最容易把全局结构拖进热点锁竞争

因为大量内核路径要的并不是“偶尔一次 2MB 大块”，而是频繁的单页、少量页、短生命周期页。网络收发、页缓存活动、匿名页初次建立、各种临时缓冲，都可能把小页分配变成高频热点。

如果这些请求全都直接去动同一套 zone 级链表和锁，那么哪怕 Buddy 的逻辑本身是 O(1) 或接近 O(1)，系统也会被“太多人同时来碰同一把门锁”拖慢。也就是说，算法层面的常数好看，不等于多核下的并发常数也好看。

### 3. PCP 的核心思想：别让每次找零钱都开保险柜

于是 Linux 再加了一层非常经典的工程优化：**per-CPU pageset，也就是 PCP。**

它背后的想法极其朴素。既然很多分配是“每个 CPU 各自频繁拿少量页”，那就别让这些请求每次都去碰全局总仓库。相反，让每个 CPU 手里先揣一小盒常用零钱：平时单页、小批量页分配，先从自己的盒子里拿；盒子空了，再一次性去总仓库批量补货；盒子太满了，也不是每放回一页都惊动全局，而是攒到一定程度再批量回灌。

这就是 PCP 最核心的意义：**把“每次拿一页都锁全局”改成“每批次才锁一次全局”。**

### 4. PCP 真正优化的不是分配逻辑，而是锁开销的摊销方式

这点非常值得强调。很多人听到 PCP，会以为它是在“替代 Buddy”。其实不是。Buddy 仍然是底层空闲块组织方式；PCP 只是站在 Buddy 之上，为最热的单页、小页路径加了一层 per-CPU 前置缓存。

所以 PCP 优化的不是“页从哪来”，而是“每次拿页时要不要碰全局”。底下货还是 Buddy 管，只不过绝大多数常见请求先由本 CPU 的小缓存接住。只有当本地缓存见底或积压太多时，才和全局世界做一次批量同步。

这就是典型的内核工程思路：**不改变主结构的正确性，只在热点上做局部缓存和批量化，把锁成本摊薄。**

### 5. 为什么它天然适合多核时代

因为 per-CPU 数据最重要的优势，就是局部性和少争抢。一个 CPU 操作自己的 PCP，意味着很多普通分配可以不必和别的 CPU 正面抢同一把锁。只要本地盒子里有货，本核就像在自己的零钱盒里找钱，不用每次都排队去开保险柜。

而一旦需要补货，它也不是拿一页补一页，而是批量拿一把回来。释放时也一样：先放进自己盒子，攒多了再一起倒回总仓库。于是全局锁从“每次分配都碰”变成“每批次才碰一次”，争用密度直接降了一个量级。

### 6. 这里最该记住的不是 `high`、`batch` 的数值，而是 PCP 守住了 Buddy 的热路径可用性

`high`、`batch` 这些参数当然重要，但如果上来就抠阈值，容易把重点丢掉。更关键的人话是：**没有 PCP，多核时代的 Buddy 纵然结构优雅，也会因为全局热点太烫而失去实战效率。** PCP 并没有改变 Buddy 的物理页组织哲学，但它让这套哲学在现代并发机器上仍然跑得动。

所以后面你看到单页分配为什么常常很快，不要只把功劳记在 Buddy 身上；很大一部分“体感上的快”，其实来自 PCP 把绝大多数热请求提前截住了。证据位上，这层最值得回到 `mm/page_alloc.c` 中 per-CPU pageset、批量补货与批量回灌相关路径去看：它们共同支撑“PCP 不是替代 Buddy，而是在最热路径上把全局锁碰撞从每次分配一次，摊薄成每批次才碰一次”的判断。

## 五、释放与合并：Buddy 真正漂亮的地方，是它不仅会拆，还会把碎掉的小块往回长成大块

### 1. 失败方案：分配时只会拆，释放时把页随手扔回最小空闲池

如果一个分配器只解决“怎么把大块拆开满足请求”，而不认真处理“释放后怎么重新长回大块”，它最终一定会被碎片化打败。

最糟糕的释放思路就是：反正页用完了，那就把它丢回空闲集合，等下次需要再说。单页看起来回来了，系统账面上的空闲页数也许还不少，可真正的大块连续空间却会越来越稀缺。时间一长，你就会陷入一种很典型的窘境：机器上并非没有空闲页，但想找 2MB、4MB 这种更大连续块时，总是不够连着。

这说明“空闲总量”与“可用连续性”根本不是一回事。只会拆不会并的系统，最后一定被碎片吃掉未来。

### 2. Buddy 的释放不是“还一页”，而是“检查我和兄弟能不能重新拼回更大块”

Buddy 最漂亮的地方，就在于释放逻辑天然是分配逻辑的逆过程。

当一个块被释放回系统时，内核不会只说“好，它空了”。它还会马上追问：**和我同级、同规格、位置刚好互补的那个伙伴块，现在是不是也空着？** 如果是，那么这两个小块就没必要继续分开待着，而应该立刻并回上一级更大块。

并且这个过程不是只做一轮。刚并成 4 页块后，系统还会继续看：这个新的 4 页块有没有同级伙伴也空着？如果有，再并成 8 页块；再往上还能并，就继续往上。直到伙伴不空、规格不匹配，或者已经到达当前体系允许的上界为止。

也就是说，Buddy 释放时真正干的不是“把积木放回原位”，而是“沿着层级一路问，能不能把散掉的积木继续拼回更大的整块”。

### 3. 为什么伙伴关系能被快速判断，而不需要全局搜索

这又回到了前面“为什么非要 2 的幂分组”的根本原因。正因为每一级块大小和对齐关系都规整，系统才可以快速定位“我唯一可能的同级兄弟是谁”。

你不需要把这理解成某个魔法公式本身，而要理解它的意义：**连续块的兄弟关系在 Buddy 里不是搜索出来的，而是算出来的。** 这就是它和“把页扔回一个大空闲池，再慢慢看谁能拼起来”的本质差别。

有了这种唯一伙伴关系，释放合并就能写成非常稳定的循环：如果兄弟也空闲，就摘下来合并；合并后继续向上试；直到不能再并。没有这条性质，释放路径的复杂度和管理成本会难看很多。

### 4. 释放为什么决定了系统未来还有没有大块可分

很多人学 Buddy 时，注意力都放在分配，仿佛真正有技术含量的是“拿页那一刻”。其实从长期系统健康度看，释放同样关键。

因为今天一个大块被拆给了小请求，并不代表它永远只能维持碎片状态。只要未来释放得足够及时、伙伴关系没被破坏、不可移动页别把中间钉死，这些小块就有机会再生长回更大块。Buddy 对抗碎片化最基础的一条生命线，就在这里。

所以你可以把分配理解成“树往下拆”，把释放理解成“树往上长”。二者必须成对成立，Buddy 才不是单向消耗品，而是一套能长期维持连续性再生能力的体系。

## 六、迁移类型：光会拆和并还不够，因为有些页一旦卡住位置，就会变成碎片世界里的钢钉

### 1. 先看为什么“理论上能合并”常常在现实里失灵

你也许会想，既然 Buddy 释放时会不断往上并，那碎片问题是不是已经被自动解决了？

还没有。因为合并有一个隐藏前提：相关小块最终得有机会同时空下来。现实里最麻烦的恰恰是，有些页的生命周期特别长、位置又不能轻易挪动，一旦它们落在本来可以拼大块的关键位置上，就会像一颗颗钢钉，把连续空间永远钉断。

最典型的就是某些不可移动页。内核栈、页表、部分内核核心对象，不像普通用户页那样想搬就搬，也不像可回收缓存那样能轻松扔掉。它们在哪扎下来，哪里的连续性就可能长期受损。

### 2. 失败方案：所有空闲页混着用，谁先来就住哪

如果系统完全不区分“将来好不好挪”，那一开始看似很公平：不管是内核对象还是用户页，先来先住空闲位子。

问题在于，用户页未来也许能换出、能回收、能 compact；不可移动页却可能会原地站很久。你把两者完全混住，等以后真需要拼大块时，就会发现最糟糕的住客结构已经形成：本来能搬走的页和绝对搬不走的页穿插得很厉害，compaction 纵有本事，也很难腾出整块干净空地。

这时候 Buddy 自身并没有错，错的是你前面给它喂了一个“住户结构天然对大块不友好”的城市布局。

### 3. Linux 的补救：按可移动性把空闲页尽量分开养

所以 Linux 不满足于“所有空闲块统一管理”，而是进一步按迁移语义去做分类。你可以把它粗略理解为三大类：

- 不可移动的，典型如内核核心结构、页表、内核栈等。
- 可回收的，比如某些能够通过回收重新得到的缓存型对象。
- 可移动的，典型如很多用户页，未来更有机会被迁移或重新安置。

这样做的目的非常现实：**让未来容易搬走的页尽量住在一起，让注定不好搬的页别到处乱钉。** 只有这样，后续 compaction 才有真正的操作空间，Buddy 的大块再生能力也才有现实土壤。

### 4. `fallback` 的意义：分类不是绝对隔离，而是先尽量守规矩，实在不行再越线借房

当然，现实分配不可能永远完美对齐分类。某一类空闲块短缺时，系统不可能僵硬地说“没有就死等”，它还是得想办法活下去。于是就有了 fallback 这类策略：当前迁移类型的合适块不够时，按一定顺序去别的类型那边借。

这一步特别像城市管理中的“本来想按功能分区，但真到高峰期也只能临时混住”。它不是理想状态，而是一种务实让步。让步的代价也很清楚：短期救急，长期可能加重碎片治理难度。

所以 fallback 不该被理解成“分类没意义”，恰恰相反，它说明分类是有意义的，只是系统不能为守纯洁而当场饿死。工程里最常见的答案往往不是完美隔离，而是“先尽量对，再在压力下有限度越界”。

### 5. 这里最重要的一句人话：迁移类型是在替未来留后路

Buddy 负责今天怎么拆和并，迁移类型负责明天还有没有机会并回更大块。它不是一个额外装饰项，而是在告诉系统：**别只看这次能不能分出去，也要看这次分法会不会把未来的大块希望钉死。**

当你带着这个视角去看内存碎片化，就不会再把它误解成“空闲页太少”。很多时候机器明明还有页，却因为住户可移动性结构太差而失去连续大块能力。迁移类型就是 Linux 用来提前控制这种宿命的一层治理手段。

## 七、GFP：同样都是“给我分配内存”，但调用方其实在对内核说完全不同的话

### 1. 最大的误解：GFP 只是“从哪个 zone 里拿页”的简单标签

很多初学者第一次接触 `GFP_KERNEL`、`GFP_ATOMIC` 时，会把它们想成几个普通常量：选项不同，内核行为大概不同，仅此而已。

这远远低估了 GFP 的意义。GFP 真正表达的，不是一个无关紧要的“口味偏好”，而是**调用方在向内核声明自己当前的生存条件与容忍边界。**

同样是要一页内存，普通进程上下文和中断上下文面对的世界完全不同。前者可以睡眠，可以等回收，甚至能承受一定延迟；后者可能正处在不能阻塞、不能调度、不能把现场卡住的敏感位置。你如果让两者都用同一套分配语义，系统迟早会出事。

### 2. 失败方案：所有调用方都用同一个默认分配模式

这看起来非常省心。调用方别想太多，统一调用“给我页”，系统自己尽力而为。

问题在于，“尽力而为”在不同上下文里不是一个意思。对普通线程来说，尽力而为可以包含睡眠等待回收；对中断上下文来说，这种“好心”恰恰是致命的，因为你根本不能在那里睡眠。对实时路径来说，哪怕能睡，也未必能接受那种抖动。对内存回收相关路径来说，又可能需要额外权限才能动用特殊保留库存。

所以统一默认模式不是简单，而是把所有上下文差异强行抹平，最终迫使内核在最不该猜的时候瞎猜调用方能承受什么。

### 3. GFP 的本质：调用方把“我是谁、我能等多久、我能动哪些库存”提前说清楚

这才是 GFP 真正像契约的地方。

有的标志更关心“我想从哪类 zone 拿页”；有的标志表达“我能不能直接回收、能不能唤醒后台回收”；有的标志涉及“我是不是能触碰更低水位甚至紧急预留”；还有一些则体现“失败时怎么表现、要不要安静一些、可不可以反复尝试”。

你不需要把这里立刻变成宏名背诵大赛，更重要的是明白：**GFP 不是让分配器更花哨，而是让调用方先把自己的生存约束讲明白。** 只有这样，底层分配路径才能决定：这次是否可以进入慢路径，是否允许睡眠，是否能使用更激进的库存。

### 4. 为什么 `GFP_KERNEL` 和 `GFP_ATOMIC` 差别会大到影响系统生死

这两个名字最能帮你快速建立直觉。

`GFP_KERNEL` 背后的典型人话是：我现在在普通内核上下文里，可以承受一定等待，必要时你可以做回收、走更慢的治理路径，只要最终把页给我。

而 `GFP_ATOMIC` 背后的人话则更像：我现在不能睡、不能等太久、不能把现场交出去，所以你只能在非常受限的条件下迅速给答复；能立刻拿就拿，拿不到就尽快失败，别把我拖进需要阻塞的世界。

这就是为什么中断上下文若误用 `GFP_KERNEL`，问题会特别危险。不是说分配器突然坏了，而是调用方给出了一个根本不符合自己现场约束的契约，等于对内核说“你可以让我睡”，可它自己明明又处在不能睡的位置。这类错经常不是性能下降，而是直接稳定性事故。

### 5. 所以 GFP 是 Buddy 体系里最像“人话接口”的一层

Buddy、PCP、迁移类型、水位线，很多都在底下悄悄运转；GFP 则是最贴近调用方的一层。它像一个前台问卷：你现在是谁？能不能等？要不要惊动回收？你是不是处在特别敏感的位置？

只有把这些话说清楚，后面的分配器才不至于在错误上下文里做出“逻辑上努力、工程上找死”的决定。

因此本节你最该记住的不是宏的排列组合，而是：**GFP 是调用方与分配器之间的契约语言。** 调用方先声明边界，分配器再据此选择允许走哪些路。若要补这一节的实现证据位，最关键的落点应回到 `mm/page_alloc.c` 中 GFP 相关慢路径/快路径分派、回收准入与紧急保留库存判断路径去看：它们共同支撑“GFP 不是口味标签，而是在告诉分配器这次能不能睡、能不能等、能不能碰更深库存”的判断。

## 八、水位线：真正成熟的内存系统，不会等到最后一滴血见底才开始想办法

### 1. 失败方案：只有“还能分”和“彻底分不到”两种状态

如果一个系统只有两级判断——能分就分，分不到再说——那它表面上很简单，实际上会非常粗暴。

因为内存回收和碎片治理都不是瞬间完成的。你不能等库存彻底见底了，才突然大喊“快去回收、快去压缩”。那时候分配请求已经在前台排队，很多上下文根本承受不了这种临场大施工。

这就像水库管理不能只有“平时不管”和“完全见底报警”两种状态。没有提前量，等你意识到危险时，常常已经来不及了。

### 2. Linux 的思路：把库存健康度分成多层，让后台治理先于生死时刻启动

于是 Linux 给 zone 设计了多级水位线。你最该抓住的不是默认数值，而是这套分层语义：

- 有一条相对温和的阈值，低于它说明库存开始紧张，该让后台回收起来活动。
- 有一条更安全的回升目标，回收到这里就别继续折腾，避免过度治理。
- 还有一条最危险的底线，只有某些特别敏感、不能等的分配才允许触碰。

这就是为什么水位线通常会被讲成 LOW、HIGH、MIN 这样的多级体系。它的本质不是数字，而是“预警线、安全线、生死线”的分层管理。

### 3. `kswapd` 为什么要在“还没彻底没钱”时就被叫起来

这正是 LOW 这类水位的意义。后台回收线程不是等到前台已经没货可卖时才上班，而是在库存明显下滑、但还没到最危险状态时就先起来把局势往回拉。

这样做的好处是，很多普通分配请求甚至不会意识到后台已经在救火。它们仍可能沿着较便宜的路径拿到页，而不是每次都自己陷入直接回收。也就是说，**后台回收是在给前台分配争取“仍然像正常系统一样工作”的机会。**

如果没有这层提前治理，普通分配会更频繁地直接撞上慢路径，系统抖动会显著加重。

### 4. MIN 之所以危险，是因为那已经不再是正常营业库存，而是救命钱

理解水位时，一个很常见的误区是把所有空闲页都看成同一种“还可以分”的余额。实际上并不是。某些低水位以下的余量，更像是系统保留给特别紧急上下文的救命钱。

这就是为什么 `__GFP_HIGH`、`GFP_ATOMIC` 一类语义会和更低水位准入联系起来。它们不是“享受特权”这么简单，而是因为那类上下文本来就没有睡眠和慢慢等的空间。你不能让普通路径随意把这些保命库存吃光，否则真正到原子分配、中断分配需要时，系统就没有最后缓冲了。

所以水位线本质上也是一套权限管理：**不同调用方，不是都配拿同一层库存。**

### 5. 为什么水位线和 GFP 必须一起理解

因为水位回答的是“系统整体现在紧不紧”，而 GFP 回答的是“这次调用方有资格拿到多深的库存、能不能等系统慢慢恢复”。

单看任何一边都不完整。只有把两者放一起，你才会明白为什么同一时刻不同请求的命运会不一样：不是内核偏心，而是一个普通可阻塞请求本就该先让后台回收兜底，另一个原子上下文请求才有资格在更低水位仍被快速放行。

所以别把 watermark 当成一个抽象阈值系统，它其实和调用方生存权密切相关。它在替内核持续回答一句关键的人话：**现在还能不能按正常方式发货，还是该进入预警、限流、保命模式了。** 证据位上，这层最值得回到 `mm/page_alloc.c` 中 zone watermark、后台回收唤醒与低水位保命库存判定相关路径去看：它们共同支撑“水位线不是单纯数字，而是预警线/安全线/生死线的分层治理体系”这句判断。

## 九、`vmalloc` 与 `kmalloc`：当物理连续越来越难找时，Linux 不是放弃需求，而是换一个维度满足它

### 1. 先看这个现实：有时你要的是“看起来连续”，不一定真要“物理上也连续”

到了这里，Buddy 已经解释清楚了物理连续页怎么来、为什么来之不易。但新问题又会冒出来：如果某个子系统想要一大段连续地址，而物理内存早就被长期运行切得七零八落，怎么办？

这时候不能把“连续”这个词一概而论。很多需求真正执着的是“地址空间里我想顺着一大段连续地址访问”，并不一定强到必须要求底下也正好是一整段物理连续页。

这就给了 Linux 一个很实用的绕法：既然物理连续越来越贵，那就用页表把分散的物理页拼成一段虚拟上连续的地址给你。

### 2. `kmalloc` 更像拿现房，`vmalloc` 更像拿一条被虚拟走廊串起来的分散房间

这正是 `kmalloc` 与 `vmalloc` 对比最值得记住的地方。

`kmalloc` 更偏向于站在 Buddy 和 direct mapping 这条主线上工作。它拿到的内存更适合热路径访问，也更贴近“我要的这一小段在底下物理上也尽量规整”。因此它通常更快，也更适合高频场景。

`vmalloc` 则更像一种旁路：它不要求底下所有物理页本来就挨在一起，而是先在虚拟地址空间里找一整段连续区间，再把分散的物理页一页页映射进去。于是从调用方视角看，它得到的是一段连续虚拟地址；但底下真实物理页可以东一块西一块。

### 3. 失败方案：所有“大块连续”需求都硬压给 Buddy 去找物理连续块

这条路在小块、热路径、严格需要物理连续的场合当然成立，但如果你把所有大块需求都这么处理，就会很快撞上现实：长时间运行后的物理内存非常容易碎片化，大块连续物理空间是稀缺资源。你若事事都逼 Buddy 交整块大现房，不仅成功率难看，还会给系统带来更重的 compaction 和回收压力。

而有些使用场景根本不值得付这笔价。调用方只是想要“自己看上去像一大块连续地址”而已，底下是不是每一页都首尾相连，它并不真的关心。

所以 `vmalloc` 的意义，不是“另一个慢版本 `kmalloc`”，而是明确承认了一个现实：**有些连续性需求完全可以在虚拟地址层解决，没必要把珍贵的物理连续性白白烧掉。**

### 4. 为什么它通常更适合非热路径

因为你绕开 Buddy 的物理连续难题，并不是白拿好处。`vmalloc` 得一页页找物理页，再一页页建立页表映射，这意味着更高的管理和访问成本。它适合大块、低频、能接受额外开销的内核内存场景，却不适合天天在热点上高频来回跑。

这就是 Linux 的典型取舍：**热路径坚持更直接、更规整的物理分配逻辑；非热路径在物理现实太难看时，转而用虚拟连续来满足上层。**

### 5. 把这节与前面串起来：Buddy 在保物理连续，`vmalloc` 在承认物理连续不总值得死磕

于是这两者根本不是谁替代谁，而是两种连续性策略：

- Buddy/`kmalloc` 更像“我尽量真给你一块底下也规整的现房”。
- `vmalloc` 更像“底下没法给你一整层现房，那我给你拼一条虚拟长走廊”。

这也进一步说明了为什么前面迁移类型、水位线、PCP、GFP 都那么重要：只要你还想守住物理连续分配这条主路，系统就必须尽力避免它被碎片、锁争用和错误上下文拖崩；而 `vmalloc` 则是在明确告诉你，不是所有问题都值得继续拿物理连续性硬扛到底。

## 十、把本篇收成一张图：Buddy 真正守护的，不是一个分配算法名字，而是整条“正常发货链”

现在可以把这一篇彻底收回来。

我们一开始的问题是：内核怎么从一大堆页身份证里，快速拼出你要的那块连续内存？答案不是某条孤零零的函数调用链，而是一整套层层配合的发货体系。

最底下，Buddy 先把空闲页按 `2^order` 规格组织成可拆可并的连续块货架。这样分配时不必全局搜索，而是优先命中现货层，命不中再拆更大块；释放时又会沿着唯一伙伴关系往上合并，持续给大块再生留机会。

但光有 Buddy 结构还不够，多核机器会把单页高频分配变成锁热点，所以 PCP 再往前顶一层，让每个 CPU 先用自己的小缓存，把“每次都锁全局”摊成“每批次才锁一次全局”。

再往上，迁移类型在替未来做碎片治理准备。它不是只关心这次能不能分，而是尽量让好搬的页和不好搬的页别乱住，为未来 compaction 与大块再生保留余地。

GFP 则把调用方的现场约束翻译成契约语言：我能不能睡、能不能等、能不能走回收、能不能碰更低水位库存。它让分配器不必在错误时机自己猜调用方能承受什么。

watermark 再把整个库存状态分成预警线、安全线和生死线，让后台回收先于真正崩盘启动，并把最后的保命库存留给不能等的上下文。

最后，`vmalloc` 与 `kmalloc` 的对照提醒我们：Linux 并不是只会硬磕物理连续。值得守的场合，就尽量通过 Buddy 体系守住；不值得守的场合，就用虚拟连续绕开现实物理碎片。

把这一切压成最短总图，就是：

```text
空闲页世界：
  Buddy 按 2^order 规格分层存货
  分配靠拆，释放靠并

多核热路径：
  PCP 把全局锁竞争摊薄到批量同步

长期连续性：
  迁移类型减少不可移动页到处钉死空间

调用方契约：
  GFP 说明这次能不能睡、能不能回收、能碰哪层库存

库存治理：
  watermark 让后台回收提前介入，并保留紧急余量

旁路方案：
  kmalloc 偏主路、偏物理连续
  vmalloc 用虚拟连续换过物理碎片
```

所以本篇最该记住的一句话是：**Buddy 真正守护的，不只是“分配器能不能给你几页”，而是整条正常发货链能不能长期留在快路径：现货能直接发，小额请求别打爆全局锁，碎片别把未来钉死，错误上下文别乱闯慢路径，系统见底前就先自救。**

## 十一、几个最容易说错的地方

### Buddy 是不是只适合分配 2 的幂大小，别的请求就没法处理？

不是。调用方可以提出非 2 的幂需求，但底层通常会通过向上取整、拆更大块等方式满足。2 的幂是底层组织规则，不是上层所有请求的字面限制。

### 有了 Buddy，是不是就不再需要别的优化了？

不是。Buddy 解决的是连续块组织与拆并问题，但多核热点锁竞争还需要 PCP，长期碎片治理还需要迁移类型与 compaction，一样不能少。

### PCP 是不是在替代 Buddy？

不是。PCP 是 Buddy 之上的 per-CPU 热缓存层，优化的是热点并发路径，不是另起一套底层物理页组织规则。

### `GFP_ATOMIC` 是不是“更高级、更强力”的普通分配方式？

不对。它表达的是更苛刻的上下文限制：不能睡、不能长时间等，所以只能走更受限的路径。它不是日常优先选项，而是特定现场下的保命契约。

### watermark 是不是单纯的“空闲页数量阈值”？

不够准确。它本质上是一套库存治理与权限分层体系：什么时候该后台回收，什么时候算安全回升，哪些请求能碰更低层紧急库存，都和它相关。

### `vmalloc` 是不是“大块内存版本的 kmalloc”？

不是。`vmalloc` 的核心区别不是“大”，而是它用虚拟连续替代物理连续，因此管理和访问成本模型不同，更适合非热路径的大块地址需求。

## 收束：看懂 Buddy 之后，你才会明白 Linux 为什么总在拼命保住“正常分配像什么都没发生过”的幻觉

回到开头那个问题：内核怎么从无数页身份证里，快速组装出连续物理块？现在答案已经闭环了。它不是等请求来了再去整个物理内存里找空地，而是先用 Buddy 按规格组织空闲块；不是每次都让所有 CPU 抢总仓库，而是用 PCP 把高频小额请求截在本地；不是等碎片化把未来钉死了才后悔，而是用迁移类型尽量让可移动和不可移动页别乱住；不是把所有上下文都一视同仁，而是用 GFP 让调用方先声明生存边界；也不是等系统彻底见底才反应，而是靠水位线让后台回收提前上岗。

这整套设计最后形成的效果，其实很像一种刻意维持的幻觉：对绝大多数普通调用方来说，分配内存最好像什么都没发生过一样顺滑。可这种“顺滑”从来不是天生的，它是 Buddy、PCP、GFP、迁移类型和 watermark 共同把真正的混乱挡在后台后，才换出来的体感。

也正因为如此，后面你一旦进入页表、缺页和用户地址空间主题，就会更容易理解：进程之所以能把虚拟地址当成连续天地，不只是页表在做翻译，底下还得先有一套能把物理页正常发出去的体系替它托底。

## 十二、误解清单、证据清单与边界清单

### 误解清单

- Buddy 不是“有空闲页就行”的简单池子；它首先在管理按 `2^order` 分层的连续块库存。
- `free_area` 不是零散空页名册；它存的是不同规格的连续块货架。
- PCP 不等于替代 Buddy；它是在 Buddy 之上为热路径加的一层 per-CPU 小金库。
- GFP 不是一组无关紧要的口味标志；它是在告诉分配器这次能不能睡、能不能等、能不能碰保命库存。
- watermark 不是抽象阈值数字；它本质上是预警线、安全线和生死线的库存治理体系。

### 证据清单

- 连续块货架：`mm/page_alloc.c` 中 `free_area`、伙伴拆分/合并与按 `order` 管理空闲块的路径，支撑“Buddy 管的是连续块库存而不是一锅空闲页”。
- PCP 快路径：`mm/page_alloc.c` 中 per-CPU pageset、批量补货与回灌路径，支撑“最热小额请求先在 CPU 本地盒子里拿页”的判断。
- GFP 契约：`mm/page_alloc.c` 中 GFP 相关快慢路径分派、回收准入与紧急库存判断，支撑“调用方先声明上下文边界”的语义。
- 水位治理：`mm/page_alloc.c` 中 zone watermark、后台回收唤醒与低水位保命库存判定路径，支撑“预警线/安全线/生死线”的分层管理。
- 迁移类型与 fallback：`mm/page_alloc.c` 中迁移类型、fallback 与碎片治理相关路径，支撑“今天怎么住，决定明天还能不能拼回大块”的判断。

### 边界清单

- 本文讨论的是 Linux 常见物理页分配心智模型；`MAX_ORDER`、watermark 细节、迁移类型与 NUMA 回退会随内核版本和配置变化。
- Buddy/PCP 解决的是物理页供给现实，不自动等于后续虚拟地址翻译、页缓存或回收策略；这些在后续章节继续展开。
- GFP 语义很多且上下文强相关；本文强调契约思想，不把宏组合背诵变成重点。
- PCP、迁移类型和 watermark 都是在守住热路径；它们不保证在高压与碎片极端场景下永远还能维持便宜分配。
- `vmalloc`/`kmalloc` 的对照重点是“物理连续 vs 虚拟连续”的旁路策略，不等于谁绝对更先进。
