## 进入内存深水区之后，第一件要改掉的误解，是别再把“页”只当成 4KB 数据块

在上一卷里，我们已经多次碰到“页”这个词。Buddy 分配器按页发货，页表把虚拟地址指向页，页缓存把文件切成页，回收器把冷热页从 LRU 上摘下来，OOM 之前也在围着页做最后挣扎。可如果现在停下来问一句：**内核自己到底怎么认识某一页？** 很多人脑子里冒出来的第一反应，仍然是“靠页表吧”。

这正是进入内存深度主题后最先要纠正的地方。页表解决的是“某个虚拟地址眼里，这一页映射到哪里”；它回答的是地址翻译问题。可 Linux 内核还必须回答另一类更基础的问题：这页现在是不是空闲的？是不是脏的？是不是正在写回？是不是还被几个进程同时映射着？它属于哪个文件？它能不能被回收？它到底在 LRU、页缓存、swap、slab、伙伴链表中的哪一套生命周期里？

这些问题都不是页表能独自回答的。页表只看见映射关系，看不见整页的社会关系。真正让内核能管理物理页的，是另一套更底层的元数据系统：**每个物理页旁边，都有一张属于它自己的档案卡。** 这张卡在 Linux 里最经典的名字，就是 `struct page`。

所以这一篇真正要建立的心智模型不是“页有多大”，而是：**物理内存不是一大片沉默的 4KB 方块，而是一大堆附带元数据、状态位、引用关系和组织层次的对象。** 后面你再看 Buddy、缺页、页缓存、反向映射、回收和 swap，几乎都在围着这套对象系统转。

先把本篇总图记住：

```text
物理页本体：
  真正存放数据的 4KB/2MB/更大物理页帧

页元数据：
  struct page = 每个物理页对应的一张管理卡片
  记录状态、引用、映射归属、链表挂点等信息

页状态机：
  PG_locked / PG_dirty / PG_writeback / PG_referenced ...
  用 flags 上的按位编码表达生命周期

多页抽象：
  folio = 把“多个连续 page 组成一个管理单元”显式抬成类型

物理内存组织：
  PFN 负责编号
  Section 处理稀疏物理内存
  Node 处理 NUMA 拓扑
  Zone 处理用途与水位约束

访问方式：
  direct mapping 让内核能用线性偏移快速摸到绝大多数物理页
```

这一篇最重要的一句话是：**Linux 管理内存时，真正反复查询和修改的，不只是页表项，而是每个物理页那张长期陪伴它的元数据身份证。**

## 一、第一层困惑：为什么内核非得给“每个物理页”都建一份固定档案，而不是需要时临时算

### 1. 直觉方案一：页只是一块物理地址区间，需要时再靠地址推导状态

如果第一次设计操作系统内存管理，很容易冒出一个很省的想法：物理页既然就是“某个物理地址开始的 4KB”，那是不是没必要给每一页额外配一份常驻元数据？需要知道状态时，现场去别的地方查不就行了。比如要回收时，再去看谁映射它；要写回时，再去看它是不是文件页；要释放时，再去看引用有没有归零。

这个思路听起来很节省，因为它把元数据从“常驻档案”变成“按需侦探”。可一旦把 Linux 的真实工作负载放进去，它几乎立刻崩掉。

原因很简单：内核对页的判断不是偶尔发生，而是高频、并发、交叉发生。分配路径要判断这页是不是伙伴空闲页；页缓存要知道它是否 uptodate、dirty、writeback；回收路径要知道它是不是 file-backed、anonymous、unevictable；缺页处理要给新页建立引用和映射；写回完成后还要清状态、唤醒等待者；swap 进出又会给它加别的生命周期标签。你不可能让这些路径每次都跨很多结构去拼图式还原“这页是谁、现在怎样”。

也就是说，**页管理的第一性需求不是节省几个字节，而是让判断和修改都能快速落在同一个对象上。** 只要一个物理页会反复出现在分配、映射、IO、回收、换出这些路径里，它就必须有一份长期存在、随时可拿来改的元数据档案。

### 2. 直觉方案二：只有被映射的页才配元数据，空闲页不配

另一个更像样的想法是：既然不是每一页都时时刻刻活跃，那是不是只给“已使用的页”建对象，空闲页就先别管，等分配出去再创建元数据。这相当于把元数据从“全量编制”改成“动态建档”。

这条路的问题在于，空闲页本身也需要被管理。Buddy 之所以能快速分配连续物理页，正是因为空闲页已经在伙伴系统里按 order、迁移类型、链表节点组织好了。换句话说，空闲并不等于没有身份，而是“它现在处在 free list 这个生命周期中”。如果空闲页没有元数据，那分配器就失去最基础的组织骨架；每次要分配时都得重新扫描物理地址范围，先猜谁空闲，再临时拼连续块，这会把今天的常数级热点路径直接打回灾难现场。

更要命的是，页从“空闲”到“被文件缓存持有”再到“被映射”再到“脏页写回”再到“可回收”，中间不是几个孤立系统轮流接力，而是一条连续生命周期。元数据如果不能从空闲阶段就存在，这条链根本接不起来。

### 3. Linux 的答案：每个物理页从出生起就有一张管理卡，后面的所有机制都围着它打转

所以 Linux 选的不是“临时算”、也不是“用到再建”，而是更重但更稳的办法：**每个物理页都配一个长期存在的 `struct page` 描述符。**

你可以把它想成一家大酒店的客房管理。房间本体是物理页，真正住人的床和桌子在那里；但前台真正天天翻的，是每个房间对应的房卡记录：空房还是已入住，谁在住，需不需要保洁，能不能立刻重新出租，是不是已经预留给某类客人，等等。没有这张卡，酒店也能勉强营业，但所有操作都会从系统管理退化成靠人肉确认。

Linux 对物理页做的，就是这件事。它把“页”从一个纯地址区间，抬成了一个长期可管理的对象。后面你会看到，`struct page` 本身并不神秘；真正重要的是，它让后续几乎所有内存机制都有了共同的会合点。若要把这一节补成更硬的源码正文，最关键的证据位应回到 `include/linux/mm_types.h` 中 `struct page`/`folio` 相关定义与 `pfn_to_page()`、`page_to_pfn()` 这类互转关系依附的路径：它们共同支撑“每个物理页从一开始就被对象化建档，而不是临时推理”这句判断。

## 二、`struct page`：这 64 字节左右的小档案，为什么值得让整个内核长期背着走

### 1. 开场先别背字段，先抓住它要解决的矛盾

一听到 `struct page`，很多人会立刻去背字段：`flags`、`_refcount`、`mapping`、`lru`。这当然不是错，但如果你一上来就背字段，很容易错过它真正难的设计题：**内核既想让每一页都可管理，又不能让元数据本身把内存吃得太夸张。**

这里有个非常现实的账。假设物理内存是 1GB，以 4KB 页大小算，大约有 262144 个物理页。如果每页的元数据占 64 字节，那总元数据大约就是 16MB。这个体量已经不小了。你要是把每页元数据做成 128 字节，1GB 内存就要拿出约 32MB 只给描述符；机器越大，这笔税越线性上涨。

可另一边，字段又不能太寒酸。因为这张卡要支撑的不是单一模块，而是分配、引用计数、页缓存、匿名页、回收、IO、swap、锁、链表、反向映射等一整套协作网络。字段太少，很多路径就得把信息外置，结果又会回到“到处查、到处拼”的困境。

所以 `struct page` 真正体现的，是一种很典型的内核工程平衡：**它不是越小越好，也不是越全越好，而是在元数据体积、缓存友好性和机制承载力之间找平衡。**

### 2. 为什么人们总强调“64 字节左右”这个量级

围绕 `struct page`，一个经常被提起的量级是“64 字节左右”，很多资料也会把它和缓存行联系起来讲。这里最该抓住的，不是某个版本里精确的 `sizeof(struct page)` 数字，而是它背后的工程意味：**这份元数据被设计成足够小，才能让系统在全机规模上负担得起；同时又足够集中，才能在扫描和热路径里减少额外访存。**

为什么这个量级重要？因为内核不是偶尔摸一两张卡，而是会大批量扫描页。回收要扫，写回要扫，页缓存遍历要扫，LRU 老化要扫，NUMA 平衡和 compaction 也可能扫。只要 `struct page` 太大，扫描一次全局页元数据的缓存行为就会明显恶化，热路径也更容易被拖慢。

这里不要把“64B”理解成一个永恒不变的宗教数字，而要理解成：**内核希望每页元数据尽量短小、紧凑、可被高频读取。** 这也是为什么 `struct page` 这种结构哪怕看起来只是元数据，实际上也带着非常强的性能约束。证据位上，这层最适合回到 `include/linux/mm_types.h`、`include/linux/page-flags.h` 等头文件以及相关扫描路径去看：它们共同支撑“这张卡既要装下跨子系统状态，又不能胖到把全机扫描和热路径拖垮”的工程平衡。

### 3. 它最核心的不是字段名字，而是六类信息

如果离开具体头文件，把 `struct page` 抽象成人话，它至少长期承担了下面六类信息：

- 这页当前处在什么状态，比如锁住、脏、写回中、被访问过、不可回收。
- 这页还被谁持有，引用是否已经降到可以回收。
- 这页有没有被页表映射，以及映射关系处在什么程度。
- 这页属于哪个更大的归属对象，比如某个文件的 `address_space`，或者某套匿名内存关系。
- 这页在归属对象中的位置，比如文件偏移对应到哪一页。
- 这页此刻挂在哪类链表或容器里，方便 LRU、伙伴系统、页缓存等模块接管它。

一旦这样看，`struct page` 就不再像“字段汇总表”，而更像一个跨子系统的交叉路口：引用计数会改它，页缓存会改它，反向映射会借它，回收路径会审它，写回路径会锁它，Buddy 会把它挂回 free list。

### 4. 几个最值得先建立直觉的字段

现在再落到字段层，你会更容易知道它们为什么重要。

`flags` 负责表达这页现在处在什么状态机节点上。后面专门一节会展开，因为很多页生命周期转换，本质上就是在翻这些位。

`_refcount` 是“还有多少人抓着这页不放”的最基础判断。你可以把它理解成这页的生存票数。票数没归零，页就不能随便回收。很多看似不同的模块，最后都会在这里汇合。

`_mapcount` 则更偏“这页被页表映射了几层关系”。它和引用计数不是一回事。引用可以来自页缓存、内核持有、GUP pin、bio、swap cache，不一定都对应用户页表映射；而 `_mapcount` 更关心“有多少页表正在指向我”。这一差别到了 COW、反向映射、回收和换出时尤其关键。

`mapping` 让内核知道这页隶属于哪套上层归属关系。文件页时，它通常把页接回某个 `address_space`；匿名页时，它又会通过别的关系结构，让内核知道“这不是无主之地”。没有这个挂钩，页和文件缓存、反向映射、swap 的很多联系都断掉了。

`index` 可以粗暴理解为“我在归属对象里的页号”。比如文件页常常会用它表达“我是这个文件偏移量折算后的第几页”。

`lru` 一类链表挂点则提醒你：页不是静态档案，而是会不断在各种队列、链表、批量容器里移动。它必须自带挂钩，才能被系统快速编排。

### 5. `vmemmap` 这层含义也要记住：页元数据不是散在天边，而是系统性铺开的数组世界

当我们说“每个物理页有一个 `struct page`”，别把它想成系统到处零散 `malloc` 出来的一堆对象。更准确的心智模型是：**内核在内存模型初始化后，会为整片物理页世界建立一套系统化的描述符布局，`pfn_to_page()`、`page_to_pfn()` 这类转换让页号和描述符之间能高效互找。**

这很重要，因为它说明 `struct page` 不是某些模块的私有附属物，而是整个内存子系统的基础设施。你给一个 PFN，系统能很快摸到它的描述符；你拿到一个 page，也能很快还原它对应的页帧号。后面无论是 Buddy 按 PFN 算伙伴，还是回收路径按 page 看状态，这套互转关系都会反复出现。

到这里先停一下。主线其实只发生了两件事：第一，Linux 选择让每个物理页永久对象化；第二，`struct page` 之所以重要，不是因为它字段多，而是因为它承接了页在整个生命周期里的管理责任。

## 三、`PG_*` 标志位：页状态不是写成一堆分散布尔值，而是压进同一个位图里反复翻转

### 1. 直觉方案：给每种状态都配一个独立字段，读起来更直白

看到页有这么多状态时，最朴素的做法似乎是：那就一个状态一个布尔字段。锁住了就 `locked=true`，脏了就 `dirty=true`，写回中就 `writeback=true`，被引用过就 `referenced=true`。

从“源码可读性”角度看，这招很诱人。每个状态名字都露在外面，不需要位运算，初学者看起来也不绕。

但一到内核现场，这种设计很快就会暴露出两个问题。第一，空间膨胀。页状态并不少，如果每个状态都按独立字节甚至独立机器字存，`struct page` 会被迅速撑胖。第二，更关键的是并发修改和组合判断的成本。很多路径不是只关心一个状态，而是要快速问：这页是不是 dirty 但还没 writeback？是不是 referenced 过但还在 inactive LRU？是不是 locked，所以别人现在不能动？

如果状态散成很多字段，这类组合判断就会变成多次访存、多次条件拼接，甚至需要额外锁来保证观察的一致性。对于内核这种高频状态机，这是很贵的。

### 2. Linux 的做法：把大量页生命周期状态压缩进 `flags`

所以 Linux 的经典办法是：**把大量页状态压进 `flags` 这样的位集合里，用按位编码和原子位操作驱动页状态机。**

你不需要在这里死背每一位的编号，但最好尽快和几个高频角色混熟：

- `PG_locked`：这页暂时被锁住，别人不能随便并发改它。
- `PG_dirty`：这页内容已经被改脏，还没把变更写回稳定后备。
- `PG_writeback`：写回已经在路上了，别再把它当成普通干净页处理。
- `PG_uptodate`：页里的内容是有效的，不是还没读完或半残状态。
- `PG_referenced`：最近被访问过，回收策略会把这类信息当作冷热判断依据。
- `PG_reclaim`：它正落在回收相关流程里。
- `PG_swapbacked`：这类页有 swap 后备语义，常和匿名页世界联系更深。
- `PG_unevictable`、`PG_mlocked`：说明这页不该按普通可回收页那样处理。

当你把这些位看成“房门口的一整块状态牌”，很多现象就容易理解了。写文件页时，页先被弄脏；后台 flusher 把它送去写回时，会把写回位打开；完成后再把相应状态调整回来。回收器扫到一页，也是在看这块牌子上有哪些灯亮着，然后决定它能不能被摘走、需不需要延后、是不是要重新激活。

### 3. 为什么位图特别适合页这种对象

核心原因有三个。

第一是紧凑。位图让很多状态共享一块存储，不必为每个状态各付一大块元数据租金。`struct page` 本来就寸土寸金，位图非常合适。

第二是组合判断便宜。一个机器字里集中了多种状态，测试、设置、清除都可以围绕位操作展开。对高频路径来说，这比散落字段更利于做快速判断。

第三是状态机表达自然。页的很多生命周期转移，本质上就是某些位被置上、清下、同时检查。脏页开始回写、页被锁住再解锁、页被访问后给冷热算法记账，都很像在一块小黑板上反复改几笔，而不是在不同档案柜里来回更新。

### 4. 这里最容易犯的错：把 `flags` 当成“静态标签”，而不是“动态状态机”

初学者常把这些 `PG_*` 理解成“页的类别标签”，仿佛一页生下来就贴着某个固定属性。其实很多位根本不是静态分类，而是**在运行时频繁跳变的过程状态**。

最典型的是 dirty 和 writeback。dirty 不是“这类页天生是脏页”，而是“它此刻有尚未落盘的修改”；writeback 也不是永久身份，而是“它此刻正在被刷回”。referenced 也是一样，它更像回收系统记下的一次“最近有人碰过它”的痕迹。

这意味着你读任何与页状态有关的逻辑，都不能只问“这个位是什么意思”，还要问：**是谁在什么时候置它？谁在什么时候清它？其他路径看到这个位后会收敛到什么行为？** 一旦这样问，页状态图就会从静态名词表变成真正的运行时状态机。

### 5. 为什么这件事和后文所有主线都有关

Buddy 要知道一页是不是还能回空闲体系；页缓存要知道页是不是 uptodate、dirty、writeback；回收器要知道它是不是 referenced、unevictable；swap 路径要知道它处在哪套后备语义里；锁和等待也在围着这些状态位转。

所以 `flags` 不只是 `struct page` 里的一个字段，而是页生命周期中最频繁被观察和改写的入口之一。后文你再看任何“页为什么现在不能回收”“为什么这页还不能立刻释放”“为什么读者看到脏页、回写、回收这些词总连在一起”，都可以回到这里找感觉：**它们很多时候只是同一页在不同阶段翻了不同的状态位。**

## 四、`folio`：它不是把 `page` 改了个新名字，而是承认“很多场景真正管理的是一组页”

### 1. 先看老问题：明明经常成批处理页，为什么接口长期还假装自己总在处理单页

如果只看最早的页模型，世界似乎很简单：一个物理页对应一个 `struct page`，那大家都传 `struct page *` 不就好了。

问题在于，真实内核工作里，很多路径从来就不是真的“只对一个孤立 4KB 页做事”。页缓存会遇到更大的缓存单元，大页会让多个基础页结成一个管理整体，写回、锁、引用和状态判断也经常是对“一组连续页”一起做。可过去很多接口仍然表面上接收 `page`，然后在内部再去判断：这个 page 是不是某个 compound page 的一部分？我要不要先找到 head page？这次到底是在对单页做事，还是对一个多页单元做事？

这种写法能工作，但读代码的人会持续吃亏。因为“这到底是单页还是多页整体”并没有体现在类型里，而是藏在调用约定和运行时探测里。你得先有背景知识，才知道当前 API 实际在干什么。

### 2. 失败方案：继续让所有人传 `page`，靠约定和辅助函数隐式推断多页关系

这条老路的问题不只是可读性差。更深一层的问题是，它让很多本该显式的设计意图长期处于模糊地带。

比如锁。若一个较大的缓存单元本质上应该作为整体被锁住，那接口继续传单页，就会让人误以为锁粒度天然是“每页一把”。再比如引用和状态。很多时候真正想表达的是“这一整组页共享某个生命周期”，但单页 API 会逼着实现者不断在“局部 page”与“整体 head”之间来回折返。

这种模式看久了，你会发现老代码里充满了“先找 compound head”“再确认是不是 tail page”“把局部操作折回整体对象”的套路。它不是不能用，而是说明抽象层次已经落后于现实。

### 3. `folio` 的关键价值：把“多页是一个单元”从运行时事实，升级成接口层面的显式事实

`folio` 的出现，最该被理解成一次抽象纠偏。它承认：**很多内存管理场景里，真正自然的管理对象不是单个 base page，而是由多个页组成的一个整体。**

所以 `folio` 并不是“另起炉灶发明第二套页”，而是把这类整体对象显式提出来，让接口直接说人话。你看到 `folio_lock()`，脑子里就该明白：当前锁的是这个更高层的页单元，而不是随便哪个子页。你看到“这个 folio 有几页”，就知道这里在讨论的是成组页，而不是让你自己再去追 `compound_head`。

从教学角度看，`folio` 最大的好处甚至不是某个具体性能数字，而是**它把意图写进了类型本身**。以前很多“需要背景知识才能看懂”的 page API，现在至少开始把“我在处理一个更大的内存单元”明牌化了。

### 4. 为什么说它不仅是可读性改进，也是在给锁、状态和批量 IO 让路

一旦多页单元被显式承认，很多原本别扭的事情会自然很多。

首先是锁粒度。对一整个缓存单元或大页整体做 IO、回写、状态维护时，用一个整体对象当操作核心，通常比对每个子页各自打补丁更合适。你不一定要把它粗暴理解成“永远 O(1) 替代 O(N)”，但至少要意识到：**当对象边界更符合真实工作单元时，锁和状态同步就更容易围绕真实边界展开。**

其次是状态归属。很多状态和引用不应被误解成“每个子页各过各的”，而更像“这个更大单元整体处在某阶段”。`folio` 让这种表达更自然。

再者是批量 IO 和页缓存路径。文件读写和缓存管理越来越常碰到“这不是一个零散的单页故事”，显式多页抽象会让很多接口不必再假装所有操作都只对单页成立。

### 5. 这里最重要的学习姿势：把 `folio` 看成 Linux 终于承认自己的现实工作单元，而不是看成又多了个名词

很多人第一次接触 `folio` 会焦虑：是不是又要多背一套结构和 API。其实更好的理解方式是：它揭露了 Linux 早就存在的现实。过去内核并不是只处理单页，只是接口层经常装作自己只处理单页；`folio` 是把这个遮羞布掀开。

因此，本篇你真正该记住的不是 `folio` 的每个函数名，而是这句人话：**从某些内存子系统的视角看，“页”早就不是最自然的操作单位，`folio` 只是把那个更真实的单位正式写进了类型系统。** 若要补这一节的实现证据位，最关键的落点应回到 `include/linux/mm_types.h` 以及 `folio` 相关接口与 `compound_head`/大页单元交接的路径：它们共同支撑“`folio` 不是新名词装饰，而是把多页作为一个管理单元的现实明牌化”的判断。

这也是为什么它常被看成一次重要演进。它不是重新发明物理页，而是在承认“内核要管理的对象层次，已经不止 base page 一个尺度”。

## 五、PFN、Section、Node、Zone：给页建完档之后，还得回答“这页在整台机器上属于哪里”

### 1. 只给每页一张卡还不够，因为机器不是平的

到这里你已经知道，每个物理页都要有 `struct page`。但新问题马上又来了：如果整台机器有几十万、几百万、几千万页，仅仅“每页有卡”仍然不够。内核还必须高效回答：**某个物理地址对应哪一页？这些页分布在哪个 NUMA 节点？哪些页受 DMA 或高端内存之类用途限制？物理内存如果中间有空洞，该怎么组织？**

也就是说，`struct page` 解决的是“单页对象化”，但真正的全机内存管理还需要“群体组织”。

### 2. 最笨的办法：把全世界物理页当成一张完全连续的大表

你可以想象一种极简设计：物理内存从 0 开始线性排开，每 4KB 一个页号，然后所有页统一塞进一张连续总表里。这样做的确很直观，PFN 一算就出来，表项一偏移就找到页描述符。

这招的问题在于，它把现实机器想得太平了。真实物理内存可能存在空洞，热插拔场景可能让物理地址空间不是满的，NUMA 机器上不同 CPU 访问不同内存节点的代价也不一样，某些区域还承担特殊用途，比如 DMA、可移动页、内核直映射限制等等。

换句话说，一张“平面大表”虽然能编号，却不擅长表达多维组织约束。它无法优雅表达“这片地址根本没内存”“这批页属于另一个节点”“这类页最好别拿来放不可移动对象”。

### 3. PFN：先解决编号问题，让每个物理页有统一门牌号

所以 Linux 先把最基础的一层抽出来：**PFN，页帧号。**

它本质上就是物理地址按页大小折算后的编号。你可以把 PFN 理解成“这页在整台机器物理内存世界里的门牌号”。很多底层计算首先不是围绕虚拟地址，而是围绕 PFN 展开。比如伙伴系统判断伙伴位置、本地性相关计算、页和物理地址之间的还原，PFN 都经常是中间语言。

这一层很重要，因为它让“物理页是可编号的”这件事稳定下来。拿到 PFN，你可以进一步找到描述符；拿到描述符，也能反推出 PFN。页从此不只是“那块 4KB 东西”，还有一个标准化编号身份。

### 4. Section：先承认物理内存可能是稀疏的，不必把空洞也当真内存养着

但有 PFN 还不够，因为 PFN 空间本身也可能对应到并不连续、并不饱满的真实内存布局。于是内核又引入了类似 Section 这样的层次，去处理稀疏物理内存模型。

这层最该理解的，不是某个 `SECTION_SIZE_BITS` 具体值，而是它的设计动机：**别假设整个物理地址空间都实心填满了内存。** 如果某些区间根本不存在物理内存，或者未来可能热插拔，那系统最好有办法按块组织、按块识别，而不是傻乎乎为整片地址空间都准备等量元数据。

从这个角度看，Section 更像“把物理地址世界切成一段段行政区”，哪些区真的有居民，哪些区只是编号保留但地上没房子，系统要分得清。

### 5. Node：再叠一层 NUMA 视角，承认“不是所有物理页离所有 CPU 都一样近”

如果说 Section 处理的是“物理内存是不是连续存在”，那 Node 处理的就是“这些页对不同 CPU 来说是否同样近”。

NUMA 机器最核心的现实是，物理页并不只是统一大池子；它们挂在不同内存节点上，本地 CPU 访问本节点内存更快，跨节点访问更慢。所以内核做页分配、回收、平衡时，不能假装全机内存一律等价。Node 这层就是让系统知道：**这批页在拓扑上属于哪一个内存节点。**

一旦你记住这一点，很多后续设计都会顺手很多。为什么会有 per-node 的回收线程？为什么分配优先本地、失败再回退？为什么有些水位和统计是按节点记的？因为机器不是平的，Node 让这种“不平”正式进入内存管理逻辑。

### 6. Zone：最后再按用途约束分区，承认“并不是所有空闲页都能拿来干任何事”

到了 Zone 这一层，内核处理的是另一种现实：**即使两页都存在、都在线、都离当前 CPU 不远，它们也不一定适合拿来做同一类分配。**

某些页可能承担 DMA 兼容限制，某些页在 32 位时代和高端内存、直接映射能力绑得很深，某些页更适合放可移动对象，以降低碎片化并照顾后续 compaction 或大页分配。Zone 这种分区方式，本质上就是把“用途限制”和“水位管理”也嵌进页组织里。

这点非常关键，因为它提醒你：Buddy 分配器之后你看到的并不是“全机只有一个 free list”，而是不同 Zone、不同 order、不同迁移类型交错组成的更复杂分配世界。Zone 是那个把“用途约束”带进主线的层次。

### 7. 所以 PFN/Section/Node/Zone 不是四个散概念，而是四层不同问题的分工

把它们收成一句人话：

- PFN 回答“这页编号是多少”。
- Section 回答“这段物理地址世界里有没有真实内存，以及怎样按块组织稀疏性”。
- Node 回答“这页在 NUMA 拓扑上属于哪一边”。
- Zone 回答“这页在分配限制和水位策略上属于哪类池子”。

这四层叠在一起，才让内核能从“我知道每页有档案”，走到“我还能在整台机器的复杂地形里准确找到它，并按合适的策略对待它”。

到这里为止，主线也可以短暂停一下。现在你已经拿到一张真正可用的地图：每个物理页有 `struct page` 作为身份证，而整个物理页世界又通过 PFN、Section、Node、Zone 被组织成一套可定位、可分层、可受约束的结构。

## 六、direct mapping：为什么内核访问很多物理页时，看起来像在“直接摸内存”，而不是每次都重新搭地址桥

### 1. 最容易冒出的误解：既然内核最终也跑在虚拟地址里，它访问物理页时应该很绕

很多人在理解内核地址空间之前，会下意识觉得：用户态访问内存要靠页表翻译，内核既然也使用虚拟地址，那它访问一页物理内存时，多半也得经过很麻烦的一层映射搭桥。这个直觉不能说全错，但它忽略了 Linux 为了热路径效率做的一件关键事：**把大块物理内存预先线性映射进内核地址空间。**

这就是常说的 direct mapping。它背后的动机其实很朴素：如果内核天天都要碰物理页，而每次碰之前都先临时建立一层专门映射，那整个系统会被自己拖死。页缓存、网络缓冲、内核对象、块 IO、很多通用分配路径都需要高频接触页内容。对这些热路径来说，“先建桥再过河”太贵了。

### 2. 失败方案：每次要访问某个物理页时，临时造一个新的内核映射

这种方案并非完全不存在，它在某些特殊场景下确实会发生；但如果你把它当成常规道路，问题马上就来了。

第一，动态建映射意味着额外页表操作。第二，映射创建和销毁都可能带来同步、TLB 与管理成本。第三，很多热点路径接触物理页的频率太高，如果每次都走“临时借道”，那你还没开始处理真正业务，时间已经花在地址基础设施上了。

这就像酒店员工想去任何房间办事，都得先临时审批一条临时走廊。偶尔一次还能忍，天天这样整座楼都别想正常运转。

### 3. Linux 的做法：启动阶段就把大块物理内存铺进一个稳定的内核线性映射区

所以 Linux 在很多常见平台上会尽量建立一大片稳定的内核直接映射区域。这样一来，内核访问大量普通物理内存页时，不需要每次单独申请一段新的映射关系，而可以通过相对稳定的线性偏移快速拿到对应内核虚拟地址。

你可以把它理解成：**把“以后肯定会频繁走”的主干道，在系统刚站起来时就一次性修好。** 后面内核要碰这些页，大多数时候直接走现成通道，而不是临时搭桥。

这里最重要的理解不是某个架构上的具体宏值，而是这条工程原则：**页表开销被前置到初始化阶段，运行时的大量普通访问因此省掉了动态建映射的成本。**

### 4. 为什么 `kmalloc` 和 `vmalloc` 的体验差异，经常要回到这里理解

你后面会频繁听到一种说法：`kmalloc` 倾向于更快、更适合热路径，而 `vmalloc` 虚拟连续但通常更重。这个差异如果只背结果，意义不大；真正该记住的是，它和 direct mapping 背后的代价模型有关。

很多经 `kmalloc` 得到的内核内存，往往更贴近直接映射这套高频主路，因此普通访问与管理成本更低；而 `vmalloc` 的意义在于，当你更看重“给我一段虚拟连续地址”时，可以接受底层物理不连续，并承担额外页表管理代价。也就是说，它们不是简单的“一个快一个慢”，而是针对不同约束做的交换。

从读者视角看，真正要记住的是：**内核并不是完全不用映射，也不是任何情况都能直接摸物理页；而是它特地为最常见、最值得优化的大宗场景，准备了一条 direct mapping 快车道。**

### 5. direct mapping 对本篇的意义：它把“页是对象”这件事重新接回“页能被高频触达”

前面我们一直在讲页元数据、组织层次，如果没有 direct mapping，这一切会有点悬在空中，好像内核只是知道页是谁，但碰到它仍然很麻烦。

direct mapping 恰好把这件事补全了：页不仅有身份，而且在大量常见场景下，内核还能较低成本地真正摸到它、读它、写它、把它交给上层对象使用。于是“页对象化”和“页可高频操作化”才真正闭环。证据位上，这层最值得回到架构内核地址空间布局与 direct mapping 相关实现去看：它们共同支撑“不是每次访问物理页都临时搭桥，而是为大宗常见页访问预铺了一条线性快车道”的判断。

## 七、把本篇收成一张图：Linux 内存世界真正的底板，是“每页对象化 + 分层组织 + 直接可达”

现在可以把这一篇从头收回来。

我们一开始纠正的误解是：页表并不是内核理解物理页的全部。页表回答的是映射问题，而物理页真正被内核管理，依赖的是每页都有一张 `struct page` 档案卡。正因为有这张卡，内核才能把页的状态、引用、映射归属、链表位置、回收资格、IO 生命周期都持续挂在同一个对象上。

接着我们看到，页状态不是一堆分散的布尔值，而是通过 `flags` 上的 `PG_*` 位图形成动态状态机。脏、写回、被引用、可否回收，这些你后面反复见到的现象，很多都只是同一页在不同时间翻了不同位。

然后 `folio` 把另一个长期存在却一直模糊的现实正式抬上台面：很多场景真正管理的不是孤立单页，而是一组页构成的单元。它的意义不在于多背一个名词，而在于把真实工作单元显式写进类型和接口。

再往上，PFN、Section、Node、Zone 让物理页不只是“有档案”，还“有地理坐标”。页在全机范围内怎么编号、如何面对稀疏内存、属于哪个 NUMA 节点、落在哪种用途约束里，都在这四层里各归其位。

最后，direct mapping 把“页能被管理”进一步接到了“页能被高频触达”。内核不是每次都临时造一座映射桥，而是预先铺好一条大路，让绝大多数常见内存访问可以在较低成本下完成。

把这一切压成最短的总图，就是：

```text
每个物理页：
  不是裸 4KB 数据块
  而是“页本体 + struct page 元数据”共同组成的可管理对象

页运行时：
  通过 PG_* 位标志推进生命周期
  通过 refcount/mapcount 维护生死与映射关系

更大粒度：
  folio 让多页单元被显式表达

全机组织：
  PFN 编号
  Section 处理稀疏
  Node 处理 NUMA
  Zone 处理用途与水位

高频访问：
  direct mapping 让内核能较低成本摸到大量普通物理页
```

所以本篇最该记住的一句话是：**Linux 管理内存时，底板并不是某条分配函数链，而是先把每个物理页做成一个长期可管理对象，再把这些对象组织进全机地形，并给内核准备一条高频访问它们的直通路。**

## 八、几个最容易说错的地方

### `struct page` 是不是“页表项的另一种叫法”？

不是。页表项描述的是某个虚拟地址到物理页的映射关系；`struct page` 描述的是物理页这个对象本身的状态与归属。一个页可能被多个页表项映射，但仍只有自己那张核心管理卡。

### `refcount` 和 `mapcount` 是不是一回事？

不是。引用计数回答的是“还有多少地方抓着这页”；映射计数更偏向“多少页表映射着它”。很多内核持有、页缓存持有、pin 住的关系会影响前者，却不必等价到后者。

### `PG_*` 标志是不是静态分类标签？

不准确。很多位是动态过程状态，会随着读写、锁定、写回、回收而频繁变化。理解它们时要带上“谁置位、谁清位、别人看到后怎么反应”这三问。

### `folio` 是不是只是给 `page` 起了个新名字？

不是。它体现的是抽象层次变化：很多真实路径管理的是多页单元，`folio` 把这件事从隐式约定变成显式接口事实。

### direct mapping 是不是说明内核访问物理页永远不需要页表？

不是。更准确的说法是：内核会为大量常见物理内存提前建立稳定映射，因此运行时大量访问不必每次单独动态建映射。但这不等于所有地址场景都没有页表参与。

## 收束：先看懂这张身份证，后面才看得懂 Linux 为什么能把“页”不断接力给分配、映射、缓存与回收

回到开头那个问题：内核怎么认识每个物理页？现在答案已经完整闭环了。它不是靠页表临时猜，也不是靠某个单独模块私有记账，而是从系统一开始就给每个物理页配一张长期存在的 `struct page` 身份证。页的状态靠位图滚动，页的群体靠 PFN/Section/Node/Zone 组织，多页单元靠 `folio` 正式登场，而大量普通访问则靠 direct mapping 接回高频运行时。

这就是内存深度主题真正的起点。只有把这一层看清，后面你看到的 Buddy 分裂合并、页表映射、缺页分配、页缓存写回、反向映射回收、swap 换进换出，才不会再像一堆互不相干的子系统，而会像同一批页对象在不同制度下不断换场景。

## 九、误解清单、证据清单与边界清单

### 误解清单

- `struct page` 不等于页表项；前者描述物理页对象本身，后者描述某个虚拟地址到物理页的映射关系。
- 每页元数据不是“用到再建”的临时对象；空闲页也必须从一开始就有档案，才能被 Buddy 等系统组织。
- `PG_*` 标志不是静态分类标签；它们是跨子系统协作的动态状态位图。
- `folio` 不是给 `page` 换了个名字；它把多页单元作为真实工作对象显式抬进类型系统。
- direct mapping 不等于“内核以后完全不用页表”；它只是为大宗常见物理页访问预铺的稳定快车道。

### 证据清单

- 每页建档：`include/linux/mm_types.h` 中 `struct page`/`folio` 相关定义与 `pfn_to_page()`、`page_to_pfn()` 互转关系，支撑“每页从出生起就对象化”的主线。
- 状态位图：`include/linux/page-flags.h` 等相关头文件，支撑 `PG_*` 状态位如何把页生命周期编码到 `flags` 上。
- 多页单元：`folio` 相关接口与 `compound_head`/复合页交接路径，支撑“多页作为一个管理单元”从隐式事实变成显式抽象。
- 全机组织：PFN/Section/Node/Zone 相关定义与路径，支撑“页不仅有身份证，还被放进整机地形分层组织”的判断。
- direct mapping：架构内核地址空间布局与 direct mapping 相关实现，支撑“内核能较低成本高频触达大量普通物理页”的快车道现实。

### 边界清单

- 本文讨论的是 Linux 常见物理页元数据心智模型；字段布局、位号、direct mapping 范围与高端内存细节会随架构和版本变化。
- `struct page`/`folio` 的具体大小与字段组合是工程平衡结果，不能被简化成永恒不变的固定字节数教条。
- PFN/Section/Node/Zone 是四层不同问题分工，不应被误解成四个平行、可互换的名词表。
- direct mapping 覆盖的是大宗常见页访问，不代表任何场景都能靠一条固定线性映射解决。
- 本文先建立“页对象化”底板；后续分配、页表、缺页、回收、swap 都是在这张底板上继续长出来的机制。
