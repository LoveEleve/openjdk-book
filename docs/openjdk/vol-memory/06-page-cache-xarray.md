## 现在真正该问的，不是“文件缺页时会不会从页缓存拿数据”，而是“页缓存自己到底是怎样一套会找、会猜、会顺手多带、还允许你插嘴提示的系统”

上一篇我们已经在文件缺页那一节里反复碰到了页缓存。你已经知道，文件映射第一次读某页时，内核很多时候不会直接把它当作“给进程分一张新匿名页”，而是会回到页缓存世界：看看这页文件内容是不是已经在内存里，若不在，再安排从磁盘把它读进来，然后把这张页挂进地址空间视图。

可如果到这里就停住，页缓存仍然像个黑箱。好像所有问题都被一句“先看看 cache 里有没有”糊过去了。

真正继续追问下去，你会立刻遇到更难的问题：

- 一个大文件明明可以有成千上万页，页缓存到底按什么索引方式，才能按文件偏移迅速找到第 N 页？
- 为什么顺序读一个文件时，第一次慢，后面越来越顺，不像每页都重新经历一次完整缺页和 IO？
- 缺页时为什么内核有时不止映射当前页，而会顺手把旁边一批页也带上？
- 数据库明明也在读文件，为什么很多场景反而不想让页缓存再插一手？
- 用户态如果比内核更懂自己的访问模式，能不能告诉内核“这段我会顺序读”“这段我很随机”“这段用完就丢”？

这些问题的答案，才是本篇真正的主舞台。

所以本篇要建立的顿悟是：**页缓存不是“读过一次就记住”这么朴素的缓存，而是一整套围绕文件页号组织索引、围绕访问模式做预测、围绕缺页时机顺手铺路、并允许用户态给出策略提示的系统。**

先把总图记住：

```text
页缓存本体：
  每个文件的 address_space 挂着自己的页缓存索引

索引结构：
  按文件页号组织
  高并发读路径追求尽量少锁甚至无锁感知

预读系统：
  不是固定窗口
  而是根据顺序/随机访问动态放大或缩小

缺页顺手优化：
  fault-around 让一次缺页顺带映射相邻页

旁路方案：
  Direct I/O 允许某些应用绕开页缓存双缓存

用户态提示：
  madvise/fadvise/mlock/mprotect 等接口让应用表达意图
```

这一篇最重要的一句话是：**页缓存真正厉害的地方，不只是“把读过的页留在内存里”，而是它把“按页号找页”“猜你接下来还会读哪页”“顺手提前铺几步路”这几件事合成了一条高频读路径。**

## 一、如果页缓存里只有一堆散页，没有一套能按文件偏移迅速找页的索引，它根本撑不起文件读路径

### 1. 最笨的方案：文件读进来的页全都挂进一个线性链表，缺页时从头扫到尾找第 N 页

先从最朴素的错误设计开始。假设文件页被读入内存后，系统只是简单把它们挂在某个链表里。下一次进程读到文件偏移对应的第 N 页时，再从头扫一遍链表，看看目标页是不是已经缓存。

这在小玩具系统里还能工作，但在 Linux 这种现实世界里立刻就会崩。因为大文件可能有极大量页，热文件还可能被很多进程反复访问。你若每次都线性扫描，页缓存不仅救不了读路径，反而会把“查缓存有没有”本身变成高延迟负担。

这说明页缓存的第一性问题，并不是“能不能留住页”，而是**能不能按文件偏移迅速找到某一页是否已经在内存里。** 如果这一步做不好，后面的预读、缺页加速、页缓存命中全都成了空谈。

### 2. 第二个失败方案：那就做一棵老式索引树，但读路径每次都得拿重锁

如果意识到链表太蠢，更进一步的办法自然是做成树状索引。这样按页号查找至少有了对数级或分层式定位能力。

但如果这棵树每次读路径查找都要拿很重的锁，问题又回来了。因为页缓存读查找是极其高频的：缺页要查，普通 buffered read 也会查，预读路径还要查。要是每一次“看一眼 cache 里有没有”都得和写路径严重竞争，那页缓存仍然会在高并发场景下把自己拖成瓶颈。

所以文件页缓存的第二个核心难题，不只是“查得快”，还得是**读多写少的场景里，读者尽量别为了一眼查找就反复排队。**

### 3. Linux 的答案：每个 `address_space` 各自托管文件页，并用专门索引结构按页号管理它们

于是 Linux 很明确地把文件页缓存绑定到文件对象的更高层归属关系上：**每个文件的 `address_space` 代表这份文件页缓存世界的管理入口。**

这个设计非常关键，因为它告诉你：页缓存并不是整台机器上一锅炖的“大缓存池”，而是按文件或文件类对象的地址空间进行托管。你想找某个文件某个偏移对应的页，先回到这份 `address_space`，再在它底下的页缓存索引里按页号找货。

这一步把页缓存世界从“读过的页堆在一起”提升成了“每个文件都有自己的页号仓库”。而真正支撑这座仓库高效运转的，就是本节下一步要讲的 xarray。若要把这一节补成更硬的源码正文，最关键的证据位应回到 `include/linux/pagemap.h` 与 `mm/filemap.c` 中围绕 `address_space`、page cache 查询与文件页索引入口的路径：它们共同支撑“页缓存不是全机一锅炖，而是每个文件各自托管自己页号空间”的判断。

## 二、xarray：页缓存真正的升级点，不是换了个容器名，而是为“高频查找 + 并发读”这件事重新修了地基

### 1. 先别把 xarray 看成又一个名词，先看它为什么会替掉更老的索引结构

很多人第一次听到 xarray，会觉得这不过是 Linux 里又一种容器名词升级，好像只要知道“现在用这个，不用以前那个”就够了。

如果你这样学，很容易错过它在页缓存场景里的真正价值。xarray 并不是为了炫 API 更新，而是在回答一个非常实际的问题：**页缓存读路径太热、页太多、并发太强，老索引结构在内存密度和并发读体验上都开始不够理想。**

换句话说，它不是“学术替换”，而是“高频路径受不了了，所以数据结构得升级”。

### 2. 页缓存索引真正需要的，不是一般意义上的“能存键值对”，而是“按页号高密度地存，还要允许读者尽量轻装上阵”

文件页缓存的键天然就是文件页号或页偏移折算后的索引。值则是对应的 folio/page 缓存对象。看起来像个普通映射结构，但它有两个非常不普通的需求。

第一是密度。文件页很多，索引节点如果过于稀松、层次对象过多、每层都单独分配和维护，会在大缓存规模下制造可观的元数据与碎片成本。页缓存本来是为了省 IO，不该自己先把大量内存浪费在笨重索引上。

第二是并发读友好。查页缓存“有没有第 N 页”是极热路径，尤其在读多写少的场景下，你最不希望读者只是看一眼就被迫去和更新路径重度锁竞争。

所以 xarray 的价值，要从这两件事一起看：**它既要把页号索引存得更紧凑，又要让读者查找尽量轻。** 证据位上，这层最值得回到 `lib/xarray.c` 与 `mm/filemap.c` 中页缓存查询路径去看：前者提供高密度索引与并发友好的地基，后者把“按页号查找第 N 页是否已在缓存里”变成真正高频的文件读路径动作。这也是为什么页缓存对 xarray 的要求，不只是“能存键值对”，而是“能让最热查找动作轻到像地基”。

### 3. 为什么“RCU 读路径友好”在页缓存里价值特别大

前面讲 RCU 时你已经接受过一个思想：只要读远多于写，那让读者更轻、把同步重担更多压给写者，常常是好交易。

页缓存索引恰恰是这种场景。多数时候大家在做的是“查一下这页在不在”，而不是每次都插入新页或删除旧页。如果读路径可以在更轻的同步负担下完成，那缺页命中、顺序读命中、预读后命中这些高频操作的体感都会更好。

所以当 xarray 能让读路径更自然地享受 RCU 式并发好处时，它对页缓存的意义就远不只是“容器更现代”这么表面，而是**在最热的找页动作上持续减税。**

### 4. 为什么说它的升级结果，是让“查页缓存”这件事更像地基动作，而不是显眼动作

真正高质量的底层结构升级，往往不是让你在业务代码里频繁感觉到它，而是让某个高频动作变得足够便宜，以至于大家逐渐把它当背景噪声。

xarray 在页缓存里的理想效果就是这样：缺页查缓存、顺序读查缓存、fault-around 看相邻页、预读提交后再次命中查页……所有这些动作都依赖“先按页号看有没有货”。如果这一步足够高密度、足够并发友好，它就会退到背景，后面所有以页缓存为前提的加速才站得住。

### 5. 本节最该记住的结论：xarray 不是容器换名，而是页缓存在“按页号查找 + 并发读”这条最热路径上的基础设施升级

所以如果只记一句人话，就记这句：**页缓存选择 xarray，不是因为喜欢新结构，而是因为文件页缓存这件事本质上需要一个既能按页号高密度存放、又能让高频读查找尽量少负担的索引地基。**

这也就顺理成章把我们带到下一节：页能更快找到了，但光会“找到已有页”还不够，系统还想继续猜你下一步要找哪页。

## 三、预读：真正会做缓存的系统，不会傻等你每次都亲自把下一页敲门敲出来

### 1. 失败方案：永远只在当前访问确实缺页时，补这一页，绝不多做一步

如果只从 correctness 角度看，这套方案完全成立。程序访问第 N 页，没在页缓存里，就把第 N 页读进来；下一次访问第 N+1 页时，再重复同样流程。逻辑简单，猜错率为零，因为根本不猜。

问题在于，这种“绝不多做一步”的保守主义会把顺序读场景的性能浪费得很严重。因为程序明明在一页接一页往前走，系统却每次都装作不知道下一页大概率很快也会被访问，于是把一次本来可以批量摊薄的 IO 和缺页准备工作拆成一连串短促的小事件。

这会导致设备、页缓存和缺页路径都在做太多“重复起步动作”。

### 2. 为什么预读不该是固定窗口，而必须会随着访问模式变脸

既然顺序读值得猜，一个自然念头是：那我就固定每次多读 32 页、64 页不就好了。

这也不够聪明。因为访问模式不是永远顺序的。你有可能开始是顺序扫，后来突然随机跳；也可能先零散点读，过一会儿又变成线性扫描。固定窗口要么太保守，顺序读赚不够；要么太激进，随机读时白搬很多没人会碰的页。

这说明预读不是一个静态常量问题，而是一个动态判断问题：**系统要根据最近的访问轨迹，不断试探“我现在该不该更大胆地猜”，猜错时又要及时收手。**

### 3. Linux 的答案：让预读做成状态机，从小窗试探开始，再根据顺序性放大或缩小

于是 Linux 不是把 readahead 做成死板窗口，而是做成了一套状态机。它会带着一个关于当前窗口起点、大小、异步部分等信息的状态，观察你最近是在顺着往前走，还是乱跳。

刚开始时，系统不会一上来就自信爆棚，而往往先拿一个较小窗口试水。若后续访问表现出强顺序性，就逐步把窗口放大；若顺序信号变差或访问开始随机化，又把窗口缩回去。

这就是预读最该记住的工程精神：**先小猜，猜对了再加码，猜错了赶紧收。**

从系统设计角度看，这和很多自适应算法一脉相承——不是假设世界永远稳定，而是在运行中持续估计当前模式值不值得下注。

### 4. 为什么顺序读特别适合被“越猜越大胆”

因为顺序访问一旦成立，后续页大概率马上就会被用到。内核把这些页提前拉进页缓存，等程序真正访问时，缺页甚至 buffered read 的路径都可以更平滑。IO 也更容易合并成更像样的批量操作，而不是一页一页碎读。

所以顺序读能从预读里占到的便宜，不只是“少等几次磁盘”，更是把一连串原本分散的准备成本压成了更连续、更流水化的后台工作。

### 5. 为什么随机读又必须让状态机学会“别太自作聪明”

因为预读猜错的成本是真实存在的。你白读进来一批页，既占用页缓存空间，又可能挤掉真正热的数据，还浪费带宽和底层 IO 启动成本。

这就是为什么 readahead 必须有收缩逻辑。顺序信号一旦消失，系统就不能继续沉浸在“我猜你还会往下读”的自信里，而要重新回到谨慎模式。换句话说，**预读真正聪明的地方，不在敢猜，而在知道什么时候不该再猜。** 若要补这一节的实现证据位，最关键的落点应回到 `mm/readahead.c` 中 readahead 状态、窗口放大/收缩与顺序性判断相关路径：它们共同支撑“预读不是固定多读几页，而是一套会根据轨迹调整下注力度的状态机”。

### 6. 本节最该记住的结论：readahead 不是多读几页这么粗糙，而是一套根据访问模式持续放大或缩小下注力度的状态机

于是如果只记一句最短人话，那就是：**Linux 的预读不是固定窗口，而是“先小试、顺序时倍增、随机时收缩”的自适应下注系统。**

这也正是页缓存为什么不只是“被动记住过去”，而是在积极准备未来。

## 四、fault-around：既然你已经为了这一页付了一次缺页成本，顺手把旁边可能马上会碰到的门也打开，往往更划算

### 1. 先看保守做法的问题：一次 #PF 严格只映射当前页

哪怕页缓存和预读都已经在工作，你仍然可以坚持一种非常保守的缺页风格：本次缺页只处理当前这一页，哪怕相邻页已经在页缓存里，也先不映射，等程序下次真的踩到旁边页再重新走一次缺页入口。

这做法当然正确，但在顺序文件访问场景下经常太死板。因为你已经为这次缺页付出了异常入口、VMA 检查、页表建立这些固定成本。如果隔壁若干页其实都已经在页缓存里，下一步又大概率会被立刻访问，那把每一页都拆成一次独立 #PF，就像已经把门禁、管理员和值班台都叫起来了，却坚持每次只开一扇门。

### 2. 为什么 fault-around 只在文件缺页场景特别有意义

匿名页场景通常没有“隔壁很多现成页缓存页已经等着你”的背景；而文件缺页不同。文件顺序访问很容易让页缓存和预读提前准备好一段相邻页。此时当前缺页不只是“这一页不在页表里”，更像是“这一串邻近文件页其实很多都已经 ready，只差把页表门牌顺手挂上”。

于是 Linux 可以借机做一件很划算的事：**既然你为当前页触发了缺页，我顺手把相邻那批很可能马上访问的页也映进页表。**

这不是多读数据，而是“数据可能已在 cache，只是把地址空间到这些现成页的最后几步顺手铺完”。

### 3. 它真正节省的，不只是 IO，而是后续几十次本可避免的缺页入口开销

这一点特别重要。fault-around 的价值不在于神奇地减少了磁盘读，而在于如果相邻页已在页缓存里，它可以大幅减少“本来每页都要再进一次 #PF”的成本。

从宏观体感看，这就像你第一次把一扇门打开后，顺手把一整排即将经过的门也都解锁。程序继续顺序访问这些相邻页时，不再需要为每一页单独经历完整缺页入口。

所以它优化的是“地址空间映射补齐”的批量化，而不是页缓存内容本身的批量化。内容那边主要是 readahead 在忙，fault-around 则是把“已经准备好的内容”更积极地映到页表里。证据位上，这层最该回到 `mm/filemap.c` 中 fault-around 相关缺页路径去看：它们共同说明 fault-around 的价值不在于替代 readahead 拉内容，而在于在相邻页已现成可取时，减少后续每页再走一次 #PF 的开销。

### 4. 为什么它也不能无限激进

和预读一样，fault-around 猜错也有代价。你顺手映射了一批邻页，可若程序马上又跳到别处，这些页表建立动作就成了白忙一场，还会多占一些页表和 TLB 相关成本。

这就是为什么它通常更适合文件顺序缺页语境，而不是当作普遍铁律。它本质上也是一种“顺序访问大概率成立”的下注，只不过下注对象从“提前读数据”进一步延伸到“提前补页表映射”。

### 5. 本节最该记住的结论：fault-around 是把“预读好的相邻页”顺手提前映射进地址空间，省掉后续一串本可避免的 #PF

所以请把它和 readahead 的分工区分清楚：**readahead 偏向把内容提前拉进页缓存；fault-around 偏向把已经现成的相邻页顺手补上映射。** 两者配合时，文件顺序访问才会呈现那种“第一次可能慢一点，后面一路顺滑”的体感。

## 五、Direct I/O：页缓存不是永远值得信任的中间人，有些应用宁可自己管仓库，也不想让内核再存第二份货

### 1. 失败理解：页缓存既然这么聪明，那所有文件 IO 都让它过一遍肯定最好

到这里页缓存看起来几乎无所不能：索引快、预读会猜、fault-around 还会顺手补映射。于是很容易得出一个危险结论：那所有文件读写都交给页缓存中转，岂不是总赢。

这在很多通用应用里确实成立，但不是绝对真理。因为有一类应用自己已经做了非常重的缓存与预读系统，比如数据库、某些大数据引擎、专门的存储软件。对它们来说，内核页缓存再来一层，不一定是帮助，反而可能是重复劳动。

### 2. 为什么“双缓存”会从优化变成浪费

假设数据库已经有自己的 buffer pool，知道哪些页最热、何时淘汰、何时预读、如何批量刷写。此时如果内核仍把同一份文件数据再存进页缓存，相当于同一批货在中央仓库和餐厅后厨各放一份。

这会带来至少三类成本：

- 内存被一份数据占两次。
- 一致性语义更绕，上层和内核都得考虑谁的副本什么时候同步。
- 真正更懂业务局部性的那一层已经是应用自己，内核再按通用策略来一遍，不一定比应用判断更准。

于是对这些场景来说，页缓存不再像神助攻，反而像一个多出来的、不总知道你在想什么的中间人。

### 3. Direct I/O 的本质：我承认页缓存很强，但这批流量请你别插手

这就是 Direct I/O 最值得记住的人话。它不是“更底层、更硬核”的炫技模式，而是在明确告诉内核：**这次数据通路我自己有安排，别再帮我在页缓存里留一份，也别用通用预读和回写策略替我做决定。**

于是数据可以更直接地在设备和用户缓冲区之间流动，应用自己负责更多缓存、对齐、批处理和一致性细节。你绕开了页缓存，也就同时绕开了它的好处和它的双缓存代价。

### 4. 为什么这条路不是普适方案

因为页缓存之所以存在，本来就是在替大量普通程序兜住“你没有自己的缓存系统怎么办”这个现实。大多数应用既不想也不擅长自己管理复杂的文件页缓存语义。Direct I/O 把更多责任还给应用，本质上是用控制权换便利性。

所以它更适合那些本来就很强势、很懂自己工作负载、愿意自己扛更多复杂度的系统；对普通程序来说，页缓存大多数时候仍然是更划算的默认道路。

### 5. 本节最该记住的结论：Direct I/O 不是“更快的通用文件 IO”，而是“已有强缓存语义的应用主动拒绝页缓存当第二仓库”

因此，Direct I/O 最该被理解成一种边界声明：**当应用自己比内核更懂这批数据该怎么缓存和调度时，它会选择请页缓存暂时离场。**

这不是否定页缓存，而是在承认“通用最优”和“业务特化最优”有时不是同一个答案。

## 六、`madvise`、`fadvise`、`mlock`、`mprotect`：通用策略很强，但应用有时确实比内核更知道自己准备怎么读这段数据

### 1. 先看为什么“完全由内核猜”也不总够用

前面我们已经看到，页缓存会猜顺序性、会放大预读、会 fault-around。可内核再聪明，它看到的终究主要还是访问轨迹，而不一定知道应用接下来真正的意图。

比如一段数据，应用也许非常清楚自己接下来会顺序扫完；另一段数据，它也许知道只是随机点一下就不会再看；还有一段，它可能明确知道马上就会需要，希望尽快把内容 warm 起来。单靠内核自己从轨迹猜，未必总能及时又准确。

所以现实世界里还需要另一条补充渠道：**应用用 hint 的方式，把自己的阅读计划或内存使用意图告诉内核。**

### 2. 为什么这些接口更像“提示”而不是“绝对命令”

很多人刚接触 `madvise`/`fadvise` 一类接口时，会把它们想成“我命令内核这么做”。这种理解太重了。

更准确的说法是：它们在多数场景下更像建议、偏好或意图声明。应用把“我大概率顺序读”“这段随机”“这段不再需要”“这段请尽量常驻”这些信息告诉内核，内核再结合全局资源状态和自己的政策决定如何执行。

这点很重要，因为它说明控制权并没有完全交给应用。应用提供的是本地语境，内核仍保留全局调度权。

### 3. `madvise`/`fadvise` 在页缓存世界里最重要的意义：让应用参与预读与回收策略的塑形

就本篇主线而言，这类接口最值得关注的不是所有子命令，而是它们如何影响页缓存行为。顺序型 hint 可能让内核更激进地预读，随机型 hint 会提醒内核别太自作聪明地大规模下注，某些“我很快会用到”的 hint 又是在帮助页缓存提早准备。

而“我不用了”“可以冷却”“可以尽快回收”这类提示，则把应用对未来冷热变化的预判也提前告诉了系统。于是页缓存不再只是被动观察访问历史，还能听到一部分来自应用层的前瞻性提示。

### 4. `mlock` 和 `mprotect` 为什么也可以放进这组用户态控制视角里看

虽然 `mlock`、`mprotect` 的语义与预读不同，但它们本质上也都在表达“我希望这段内存在后续被怎样对待”。一个是在说“这段尽量别被换出”，另一个是在说“这段权限规则要变”。

它们提醒你：用户态并不是完全被动等内核猜。地址空间与页缓存系统虽然复杂，但应用也拥有一些合法、有限且有语义的插嘴口。理解这些接口，有助于你把“通用内核策略”和“应用特定意图”这两层区分开。

### 5. 本节最该记住的结论：页缓存策略并不只靠内核单向猜测，应用可以通过 hint 接口把自己对未来访问模式的了解喂回去

所以如果只记一句话，那就是：**内核的通用策略负责兜底，而 hint 接口则让真正更懂局部工作负载的应用，有机会提前告诉页缓存“这段该怎么被对待”。**

这也是为什么页缓存不是封闭黑箱，而是一套允许用户态适度塑形的系统。

## 七、把本篇收成一张图：页缓存真正做的，不只是“留下昨天读过的页”，而是“围绕明天可能还会读哪页”提前组织整条读路径

现在可以把这一篇彻底收回来。

我们一开始要解决的问题是：页缓存自己到底怎样组织，为什么“第二次读文件快很多”这件事并不只是缓存二字能解释完。答案首先落在 `address_space`：文件页缓存不是一锅乱炖，而是按文件自己的页号空间托管。要让这件事真正高效，底下就必须有一套适合高频按页号查找、同时又照顾并发读路径的数据结构，于是页缓存把 xarray 放到了索引地基的位置上。

但会找还不够，系统还得会猜。readahead 不是固定窗口，而是一套根据访问模式不断试探、放大和收缩的状态机。它努力把顺序读的未来几步提前准备出来，又在随机访问时及时收手，避免盲目搬货。

fault-around 则把这种“提前一步”的思路再向页表映射层延伸：既然已经为了当前页付出一次缺页成本，而相邻页又往往已经在页缓存里现成可取，那么顺手把它们的映射也补上，常常比等每一页各自再触发一次 #PF 更划算。

但页缓存不是任何场景都值得介入的万能中间人。对数据库这类自己已有强缓存体系的应用来说，Direct I/O 允许它们绕开页缓存双缓存现实，自行管理那批数据的命运。

最后，页缓存策略也不是只有内核单向猜。`madvise`、`fadvise`、`mlock`、`mprotect` 这类接口提醒我们：应用有时比内核更懂自己接下来准备怎么用一段数据，因此可以把 hint 喂回系统，帮助页缓存与地址空间策略更贴近真实工作负载。

把这一切压成最短总图，就是：

```text
组织层：
  address_space 托管文件页缓存
  xarray 负责按页号高频找页

预测层：
  readahead 根据顺序/随机模式自适应放大或收缩

顺手优化层：
  fault-around 让一次缺页顺带补上映射邻页

旁路层：
  Direct I/O 让强势应用拒绝页缓存当第二仓库

提示层：
  madvise/fadvise/mlock/mprotect 让应用表达自己的局部意图
```

所以本篇最该记住的一句话是：**页缓存真正强大的地方，不是简单记住过去，而是围绕“文件页号怎么高效找、你接下来大概率会读哪、这批数据到底值不值得让我插手”三件事，持续把读路径组织得更像一条提前铺好的流水线。**

## 八、几个最容易说错的地方

### 页缓存是不是就是“最近读过的页放内存里”这么简单？

不是。它至少还包含按页号索引、预读状态机、fault-around、用户态 hint 和绕过策略这些关键机制。

### xarray 是不是只是 radix tree 换了个名字？

不准确。对页缓存来说，它代表的是索引地基升级：更适合按页号高频查找，也更照顾并发读路径。

### readahead 是不是固定多读几页就行？

不是。访问模式会变，所以预读必须能根据顺序性和随机性动态放大或缩小窗口。

### fault-around 是不是等价于 readahead？

不是。readahead 更偏向提前把内容拉进页缓存；fault-around 更偏向把已经在 cache 里的相邻页顺手补上映射，减少后续 #PF。

### Direct I/O 是不是“所有程序都更快”的高级模式？

不是。它更适合那些已有强缓存/调度体系、愿意自己承担更多复杂度的应用，比如数据库。

### `madvise`/`fadvise` 是不是应用在命令内核必须这么做？

通常不是。更准确地说，它们多数是在提供 hint，让内核在全局策略里参考应用的局部意图。

## 收束：看懂页缓存之后，你才会真正理解“第二次读快很多”其实是索引、预测和顺手铺路共同换来的结果

回到开头那个问题：页缓存自己到底是怎样一套会找、会猜、会顺手多带、还允许你插嘴提示的系统？现在答案已经完整闭环了。它不是一个只会把昨天读过的页留在内存里的被动盒子，而是一套从 `address_space` 与 xarray 开始组织、靠预读状态机主动猜未来、靠 fault-around 顺手降低后续 #PF 密度、必要时允许强应用绕开、也允许用户态通过 hint 参与塑形的读路径系统。

也正因为如此，你会发现“文件第二次读快很多”并不是一个单一原因造成的体感。它可能是页缓存命中了、可能是预读已经把后续页带上了、可能是 fault-around 已经提前把映射铺好了，也可能是应用自己明确告诉内核“这段我会顺序扫”。这些机制叠在一起，才让文件读路径逐渐从“每次都去设备要数据”演化成“尽量在内存里提前把问题化整为零”。

这就是为什么说：**页缓存不是文件 IO 的附属小优化，而是 Linux 文件读性能真正长期站得住的主舞台之一。** 会不会找、猜得准不准、愿不愿意多做半步、何时该彻底别插手，这些决定了它到底是在帮忙，还是在添乱。

## 九、误解清单、证据清单与边界清单

### 误解清单

- 页缓存不是“最近读过的页放在内存里”这么简单；它同时包含按页号索引、预测、顺手补映射、绕过与 hint 等机制。
- xarray 不是只换了个容器名；在页缓存语境里，它承担的是最热查找路径的索引地基升级。
- readahead 不是固定窗口地多读几页；它是会随顺序性和随机性动态放大/缩小的状态机。
- fault-around 不等于 readahead；前者偏向把已在 cache 中的邻页顺手补上映射，后者偏向提前把内容拉进页缓存。
- Direct I/O 不是“总会更快”的高级模式；它更像强势应用声明“我不想让页缓存当第二仓库”。

### 证据清单

- 文件页托管入口：`include/linux/pagemap.h` 与 `mm/filemap.c` 中 `address_space`/页缓存查询路径，支撑“页缓存按文件页号空间托管”的结构。
- 索引地基：`lib/xarray.c` 与 `mm/filemap.c` 的页缓存查找路径，支撑“高频按页号找页 + 并发读友好”的 xarray 价值。
- 预测状态机：`mm/readahead.c` 中 readahead 状态、窗口放大/收缩与顺序性判断相关路径，支撑“预读是状态机而不是固定窗口”。
- 顺手补映射：`mm/filemap.c` 中 fault-around 相关缺页路径，支撑“减少后续 #PF 密度”的顺手优化语义。
- 用户态塑形：`madvise`/`fadvise`/`mlock`/`mprotect` 与 `Direct I/O` 相关路径，支撑“内核通用策略 + 应用局部意图 + 强应用旁路”的三层边界。

### 边界清单

- 本文讨论的是 Linux 常见页缓存心智模型；xarray、readahead、fault-around 与 DIO 细节会随内核版本和文件系统实现变化。
- 页缓存命中、预读命中和 fault-around 收益高度依赖访问局部性，不能抽象成“第二次读一定快”这种绝对句。
- Direct I/O 讲的是绕开页缓存双缓存，不等于自动获得更高吞吐；它把更多复杂度交还给应用。
- hint 接口多数表达的是意图与偏好，不是对内核的无条件命令；全局资源调度权仍在内核手里。
- 本文先讲读路径组织；页一旦被改脏，下一篇 writeback 才真正回答“怎样退场并落盘”。
