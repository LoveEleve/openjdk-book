## 现在真正的问题不再是“swap 能不能把页搬出去”，而是“连最后的仓库也快撑不住时，系统究竟该怎样面对一个已经答应出去的承诺”

上一篇我们把 swap 闭环补齐了。匿名页可以被搬到外部仓库，PTE 里留下 type 和 offset，未来访问时再按门牌把内容取回来；Swap Cache、cluster、预读和批量回收，则尽量把这条昂贵路径变得不那么随机、不那么浪费。

可 swap 不是无限仓库。物理内存有限，swap 也有限，页表、内核对象、不可回收页和设备映射还会继续占据资源。更现实的是，应用申请内存时，系统经常面对的并不是“现在手里有没有一页空闲物理内存”，而是一个未来承诺问题：**我现在答应你这片地址空间和这些写入，等你真正用到时，系统有没有足够的 RAM、swap 或可回收空间兑现？**

这就产生了本篇的核心困惑：

- 为什么一台只有 8GB RAM 的机器，程序申请 10GB 虚拟内存时不一定立刻失败？
- 系统如果允许很多“可能永远用不到”的内存承诺，未来真的用起来却发现兑付不了，怎么办？
- OOM 到来时为什么不是简单返回一个错误，而要杀掉某个进程？到底凭什么选它？
- 进程收到 `SIGKILL` 以后，如果它卡在不可中断 IO 或死锁里，物理页谁来释放？
- 为什么运维可以通过 `oom_score_adj` 保护某些关键服务，又能从 OOM 日志里判断谁才是真正的内存嫌疑人？

所以本篇要建立的顿悟是：**overcommit 管的是“现在是否敢答应未来的内存义务”，OOM Killer 管的是“承诺失守后如何选择性止损”，OOM Reaper 管的是“进程死了但资源还没及时释放时，如何把地址空间异步收走”。**

先把总图记住：

```text
承诺层：
  overcommit 决定系统愿意提前答应多少潜在内存

失守层：
  回收、swap 和分配重试都失败后进入 OOM

处决层：
  OOM Killer 计算候选进程的资源占用与人工偏移
  选择一个能释放较多资源、又不应被保护的对象

收尸层：
  OOM Reaper 不等进程正常退出
  直接尝试解除其地址空间映射、回收物理页

保护与诊断：
  oom_score_adj 表达运维偏好
  OOM 日志帮助定位匿名常驻、页表和地址空间占用
```

这一篇最重要的一句话是：**Linux 的内存耗尽处理不是一条“分配失败就崩”的直线，而是一套先管理承诺、再尝试回收、最后选择性止损并异步清场的防线体系。**

## 一、为什么 `malloc(10GB)` 在 8GB 机器上可能成功：因为申请地址空间和兑现所有物理页不是同一笔交易

### 1. 最容易产生的困惑：物理内存只有 8GB，系统凭什么敢答应 10GB

从物理资源角度看，这个问题似乎只有一个答案：答应就是骗人。机器只有 8GB RAM，怎么能给程序 10GB？

可用户态的内存申请往往只是建立一段虚拟地址空间承诺，程序可能只写其中一小部分，甚至拿到地址后从来不碰。若系统把“申请 10GB 地址”直接等价成“现在就必须准备 10GB 可写物理页”，那么大量合理程序都会在真正需要之前被过早拒绝。

堆预留、稀疏数组、地址空间布局、语言运行时保留区、内存映射窗口，都可能先申请一大片地址，随后只触碰其中一部分。操作系统如果完全不允许这种“先承诺、后兑现”，就会把虚拟内存的延迟分配优势一并砍掉。

### 2. 失败方案：所有申请都必须立即有等量物理页或 swap 作为抵押

这就是严格抵押式内存管理。每申请一页，就必须现在找到对应的 RAM 或 swap 承诺；没有足够抵押就立即返回失败。

它的好处是承诺非常保守，未来写入时不容易突然发现没有资源；但代价也明显：它把“可能永远不用的空间”当成“现在已经实际使用的空间”处理。大量只预留不触碰的地址会提前挤占承诺额度，让合理的大型映射和运行时预留变得困难。

这等于要求所有用户在搬进新房前，就先为每一间未来可能使用的房间付全额现金。安全，但会极大限制系统的利用率。

### 3. 第二个失败方案：既然严格太保守，那就永远答应，等真正不够时再说

另一个极端是完全乐观：申请多少都先答应，不在申请阶段做任何有意义的承诺约束。这样地址空间非常自由，程序也很容易拿到大范围预留。

问题在于，所有风险都被推迟到了真正写入或分配物理页的时刻。多个进程都相信系统会兑付，最终同时把承诺变成真实页面时，系统可能已经没有足够的 RAM、swap 或可回收对象。到这一步再处理，就不能简单对当前一个小请求返回“暂时不行”，因为承诺已经广泛发出，资源缺口也可能是全局性的。

于是系统必须选择某些进程止损，进入 OOM Killer。无限承诺换来了高利用率，却把未来的失败成本变成了选择性牺牲。

### 4. Linux 的答案：overcommit 是一套“现在允许承诺多少未来资源”的策略，而不是简单的内存大小检查

Linux 通过 overcommit 相关策略，把“地址空间申请”和“最终物理兑现”之间的承诺关系显式化。它并不是只问“现在有多少 free page”，而是评估当前已经承诺出去多少、未来可能需要多少、RAM 与 swap 能提供多大的承诺上限。

常见的三种策略可以先用人话理解：

- 启发式模式：大多数看起来合理的申请先答应，明显离谱的承诺才提前拒绝。
- 总是允许模式：申请阶段尽量不拒绝，把风险推迟到真正资源耗尽时交给 OOM。
- 严格模式：按照可兑现资源和配置的承诺上限审查申请，超过就当场拒绝。

它们不是单纯的“安全等级”，而是三种不同的资源经济学：现在更看重灵活利用，还是更看重未来每一笔承诺都有抵押。

### 5. `CommitLimit` 与 `Committed_AS` 要怎样理解

理解 overcommit 时，最容易被数字表面带偏。`CommitLimit` 可以理解为系统愿意承受的总承诺上限，具体由物理内存、swap、hugetlb 预留、overcommit ratio 等因素共同影响；`Committed_AS` 则更像当前已经发出去的承诺总账。

当新申请到来时，系统会比较“现有承诺 + 本次潜在承诺”与允许上限之间的关系。不同策略对这笔账的严格程度不同，但共同思想是：**内核不只看今天手里有多少钱，还要看已经答应了多少未来支出。**

这也是为什么一台机器的 `MemFree`、`MemAvailable` 和 `Committed_AS` 不能混为一谈。空闲页是当前库存，承诺账是未来义务，两者描述的是不同时间维度的风险。若要把这组判断落成更硬的证据位，最关键的实现支撑应回到 `mm/util.c` 中与 overcommit、`CommitLimit`、`Committed_AS` 相关的计算路径，以及 `/proc/meminfo` 对这些总账字段的导出逻辑：它们共同说明，承诺经济不是比喻，而是内核真的在维护的一本未来支出账。

### 6. 本节最该记住的结论：`malloc` 成功不代表 10GB 物理页已经就位，而是系统暂时接受了这笔未来承诺

所以如果只记一句话，就记这句：**overcommit 允许系统把“地址空间愿望”与“物理页立即兑现”分开；申请成功只是承诺被接受，不等于全部数据已经有 RAM 或 swap 逐页站岗。**

## 二、Overcommit 三策略：系统到底是“估着批信用”“无限额先刷”，还是“每笔都要求有抵押”

### 1. 启发式模式：只拒绝明显不合理的承诺，把虚拟内存的延迟兑现优势保留下来

启发式模式的核心不是数学上绝对精确地预测未来，而是承认一个现实：很多程序申请的内存最终不会全部变成实际写入。若系统每次都按最坏情况严格抵押，就会拒绝大量实际可运行的程序。

因此它更像银行根据收入和历史行为估计额度：大多数合理申请先批，只有明显超出系统可承受范围的承诺才提前返回 `ENOMEM`。这提升了地址空间使用灵活性，也保留了 mmap、运行时堆预留和稀疏访问的空间。

但它不是免费午餐。启发式判断永远不可能准确知道所有未来写入，承诺一旦同时兑现，仍可能把系统推到 OOM。它只是把“过早拒绝”与“未来止损”之间做了一个偏向可用性的选择。

### 2. 总是允许模式：把申请阶段的阻力降到最低，把兑现风险全部推到后面

总是允许模式更乐观。它把“现在先不要挡住申请”放在很高优先级，程序更容易获得大范围地址空间，适合某些明确知道自己工作集管理方式、愿意承担 OOM 风险的批处理或科学计算环境。

可这也意味着，管理员不能把“申请成功”理解成系统资源已经有了安全抵押。未来一旦大量页面真的被触碰，系统可能只能依靠回收、swap 和 OOM 来处理缺口。

### 3. 严格模式：把承诺审查提前，让失败更早、更可预期

严格模式则把未来可兑现性放在更高位置。系统按照配置的承诺上限，要求申请不要超过可接受范围。这样做的优点是失败更早、更接近申请现场，服务不容易运行很久后才突然在缺页或写入时进入 OOM。

代价是它可能拒绝一些实际上不会完全使用的预留空间。对于依赖大地址空间预留、延迟提交或稀疏工作集的程序，严格模式可能显得过于保守。

### 4. 为什么不存在“最好的通用策略”

因为三种模式面对的是不同的业务假设。一个批处理系统可能更看重高利用率，愿意承受少数作业被 OOM；一个关键服务平台可能更看重失败可预测性，希望申请阶段就有硬边界；一个通用发行版则需要兼容大量不同的程序行为，只能在灵活性和止损之间折中。

所以 overcommit 配置不能只按“越严格越安全”或“越宽松越高性能”理解。它实际上是在选择：风险更早暴露，还是更晚暴露；失败更局部，还是更全局；系统利用率和承诺确定性之间如何取舍。

### 5. 本节最该记住的结论：overcommit 是“承诺管理策略”，不是简单的内存开关

把三种模式压成三句人话：

- 启发式：大多数合理承诺先批，明显离谱的才拒绝。
- 总是允许：先尽量答应，未来兑付失败时再止损。
- 严格：每笔承诺都更早检查可兑现边界。

## 三、OOM Killer：当回收、swap 和重试都救不了当前分配，系统为什么不直接让整台机器一起倒下

### 1. OOM 的触发不是“free page 变成零”这么简单

很多人把 OOM 理解成 `MemFree=0`。这太粗糙了。系统可能还有少量空闲页，但受 zone、水位、GFP 上下文、连续性、不可移动页、cgroup 限制或回收能力影响，当前分配仍然无法完成。

真正进入 OOM 评估前，系统通常已经经历了多层尝试：Buddy 直接找现货，必要时走不同 zone，后台或直接回收尝试释放页，可能进一步写回、拆映射、swap，最后仍然无法满足当前承诺。OOM 是这些正常手段都不足后的止损路径，而不是看到某个单一计数器为零就立刻发生。

### 2. 失败方案：杀当前正在申请内存的进程，逻辑最简单，也最可能杀错人

如果当前进程申请失败，那就直接杀当前进程，似乎很直观：谁制造了需求，谁承担后果。

可当前分配者未必是最占内存的进程，也未必是最容易释放大量资源的进程。它可能只是一个小工具恰好在最坏时刻申请了一页，而真正把系统推向边缘的是另一个长期占据大量匿名内存的服务。只杀当前进程可能释放不了多少空间，甚至会让系统损失一个关键控制面服务。

因此 OOM 需要一套全局候选评估，而不能只看当前调用者。

### 3. Linux 的答案：先过滤不能杀的人，再用 badness 估计谁能释放更多资源

OOM Killer 会遍历候选任务，并跳过一部分不应作为普通牺牲品的对象，例如全局 init、当前线程组中的某些特殊关系、已经标记为正在处理 OOM 的任务，以及受到 OOM 约束保护的任务。

对剩余候选，系统会根据其地址空间常驻页、swap 中的页、页表等占用因素计算 badness，再结合 `oom_score_adj` 这类人工偏移，选择分数更高的对象。证据位上，这条主线最该回到 `mm/oom_kill.c` 中 badness 计算、候选过滤与受害者选择路径去看：正是这些实现把“谁更该牺牲”从直觉判断变成了资源占用、任务关系和人工偏好的综合评分，而不是简单地“谁触发谁去死”。

这套机制的基本价值是：**不要只问“谁现在触发了分配”，而要问“杀谁能释放更多资源，且对系统整体损害相对可控”。**

### 4. OOM badness 为什么重点看 RSS、swap 和页表

RSS 表示进程当前驻留在 RAM 中的页，这些页通常是发送 SIGKILL 后最直接能回收的资源。swap 计数则反映这个地址空间已经占据了外部后备，相关进程如果继续存活，未来可能还会把这些内容换回来；页表本身也占用内存，地址空间越大、映射越复杂，页表成本越高。

这些指标不是“进程价值”的完整衡量，而是“杀掉以后大致能释放多少内存资源”的近似。系统必须在极端压力下用一个可计算的评分，把复杂候选压成可比较的排序。

### 5. 为什么需要归一化与人工偏移

不同机器、不同内存规模下，原始页数不能直接作为通用分数。归一化让评分落进更容易比较的范围；人工偏移则承认自动公式不可能知道业务重要性。

一个监控进程可能占用不少内存，但对平台稳定性很关键；一个批处理任务即使占用同样内存，也可能是更合适的牺牲对象。`oom_score_adj` 就是把运维对业务价值的判断加入自动评分。

### 6. 为什么有时会优先处理子进程

一个父进程可能承担控制、监督或清理职责，子进程才是实际消耗大量内存的工作单元。若候选关系允许，优先杀掉占用资源的子进程，可能比直接杀整个控制进程更容易止血，也更有机会保留服务的管理能力。

这里的关键不是“所有 OOM 都必然先杀子”，而是 OOM 选择会考虑进程关系与释放收益，而非只按单个 PID 的表面大小排序。

### 7. 本节最该记住的结论：OOM Killer 不是随机杀进程，而是在承诺失守后做一次资源释放收益与业务偏好的折中排序

所以请把它记成一句最短人话：**OOM Killer 不是在寻找“谁犯了申请内存的错”，而是在寻找“谁被终止后能释放较多资源、又没有被系统或运维明确保护”。**

## 四、OOM Reaper：进程被判死不等于它已经把内存交出来，收尸必须从进程退出流程里独立出来

### 1. 失败方案：发出 `SIGKILL`，然后等进程自己退出、析构、释放所有内存

正常情况下，进程被杀后，退出路径会释放地址空间和相关资源。于是最简单的 OOM 设计似乎是：选好受害者，发 `SIGKILL`，接下来等它自然退出即可。

问题在于，内核可能杀掉一个卡在不可中断 IO、设备驱动或某种锁依赖中的进程。`SIGKILL` 表示它最终不能继续执行用户态，但不等于所有内核态阻塞都能立刻被打断。若系统一直等这个进程自己走完退出流程，最需要的物理页可能迟迟回不来，OOM 状态就会持续。

### 2. Linux 的答案：把“判决进程死亡”和“尽快收走它的地址空间”拆成两个并行职责

因此 Linux 引入 OOM Reaper。OOM Killer 负责选择受害者、标记它进入死亡处理；Reaper 则由独立工作路径异步尝试拿住这份 `mm`，遍历它的 VMA，解除用户地址空间映射，把能释放的物理页尽快归还系统。若要把这一节补成更硬的源码正文，最关键的证据位应落到 `mm/oom_reaper.c` 及相关回收路径上：它们共同支撑“判死”和“收尸”被故意拆成两条职责链，避免系统在最缺内存的时候还被迫长时间等待目标进程自己善后。

这是一种非常重要的职责分离：**SIGKILL 解决“这个进程不应继续成为资源消费者”，OOM Reaper 解决“它已经不配继续占着这些物理页”。**

两件事不必绑定在同一个阻塞退出流程里，系统才能在极端压力下尽快恢复一点可用内存。

### 3. 为什么 Reaper 会采用类似 `MADV_DONTNEED` 的地址空间清理思路

Reaper 的目标不是执行进程所有正常退出逻辑，也不是替应用做析构，而是尽快清理用户地址空间中的物理页。它可以沿 VMA 遍历，对映射范围做解除与释放，让页表、TLB 和物理页生命周期走一条专门的收割路径。

这种做法牺牲了“等进程自己优雅收尾”的可能性，但 OOM 已经是资源止损场景，优先级是快速回收可用内存，而不是保证应用级清理代码运行。

### 4. 如果目标进程卡在 D 状态，Reaper 也可能拿不到 `mmap_lock`

Reaper 并不是魔法。它要修改和遍历目标地址空间，仍然要遵守地址空间锁与并发规则。如果目标进程或其他路径长时间持有 `mmap_lock`，或者进程卡在不可中断状态导致相关操作无法推进，Reaper 可能暂时拿不到需要的锁。

因此实现会有重试和超时边界。它会给目标一定机会完成当前阻塞，但不能无限期等下去；否则“异步收尸”又会退化成“继续等待一个可能永远不醒的人”。

### 5. `TIF_MEMDIE` 这类标记为什么重要

被选中的任务需要被系统识别为“已经是 OOM 处理中对象”，避免它继续被反复纳入同一轮资源争抢或造成 OOM 选择重复震荡。分配路径看到这类标记后，可以采用更快失败或特殊处理语义，优先让系统尽快完成止损，而不是继续对它做普通重试。

### 6. 本节最该记住的结论：OOM Reaper 是把“进程死亡”和“物理页回收”解耦的异步收尸机制

所以如果只记一句话，就记这句：**被杀进程不一定能及时自己退出，但系统不能因此永远等着；OOM Reaper 直接尝试解除它的地址空间，把可回收物理页尽快拿回来。**

## 五、`oom_score_adj` 与 OOM 日志：自动评分负责估算资源，运维接口负责表达业务价值，日志负责告诉你现场到底谁在吃内存

### 1. 为什么只靠“占内存越多越该杀”仍然不够

OOM badness 的资源视角很合理，但它不知道业务。监控服务、数据库、SSH 守护进程可能非常关键，哪怕它们占用不少内存，也不该和可丢弃的批处理任务用同一种牺牲优先级。

反过来，一些实验任务、缓存服务或可重试的 worker，即使占用不小，也可能非常适合在压力下被优先牺牲。自动评分只能提供资源基准，必须有一个受控接口让管理员补充业务偏好。

### 2. `oom_score` 与 `oom_score_adj` 要分开看

`oom_score` 更像内核根据当前状态计算出的动态结果，随进程内存使用和系统环境变化；`oom_score_adj` 则是运维主动写入的偏移，表达“这个任务比自动公式判断的更该保护，或更适合牺牲”。

负向调整会降低受害概率，极端保护值可以让任务从普通候选中被排除；正向调整则把任务推向更容易被选中的方向。它不是让进程获得更多物理内存，而是在资源危机时改变选择排序。

### 3. 为什么保护关键进程不能只靠“希望它占用少一点”

关键服务一旦被 OOM 杀掉，平台可能失去登录、监控、数据库或控制面能力，后续即使有内存也很难恢复。依赖它“刚好比别的进程少占一点”来保命，风险很高。

因此关键进程应该通过明确的策略配置表达保护意图，并结合 cgroup、服务管理器和部署平台的资源边界一起设计。`oom_score_adj` 是一个具体工具，但不是替代完整资源隔离策略的万能保险。

### 4. OOM 日志为什么首先要看匿名常驻，而不是只看 `total-vm`

OOM 报告里常见的 `total-vm` 是进程虚拟地址空间总量，它可以很大，但不等于同等规模的物理内存已经驻留。真正更直接反映当前 RAM 压力的，通常是匿名常驻页、文件常驻页、共享内存常驻页、swap 使用和页表占用等分项。

匿名常驻往往是最值得优先关注的一项，因为它通常不能像干净文件缓存那样直接丢掉后靠文件重读恢复。它越大，说明进程拥有越多不可直接丢弃的私有工作集；文件常驻则需要结合是否活跃、是否脏、是否可重读来判断，不能只看一个总数。

### 5. 一条 OOM 日志应该怎样读

面对 `dmesg` 或内核日志，建议先建立三层问题：

第一，系统为什么走到 OOM：是全局内存不足、swap 枯竭、某个 cgroup 达到限制，还是高阶/特殊上下文分配无法满足？

第二，候选进程谁的匿名常驻、swap、页表和总地址空间最突出？不要只看 `total-vm`，要区分虚拟承诺与实际驻留。

第三，被杀进程的 `oom_score_adj` 是否改变了自动排序，是否存在保护值、容器边界或服务编排策略影响最终选择？

只有把这些问题连起来，OOM 日志才不是一行“Killed process”的结果，而是一张可以回放资源失守过程的现场记录。

### 6. 本节最该记住的结论：自动评分告诉你资源占用，人工偏移告诉你业务优先级，日志告诉你最终止损发生在哪里

所以可以把三者压成一句话：**`oom_score` 解释“系统算出来谁更危险”，`oom_score_adj` 表达“运维希望谁更该保护或牺牲”，OOM 日志则帮助你复盘“为什么这次危机最终落到了这里”。**

## 六、把本篇收成一张图：内存耗尽的最后防线，是“承诺管理 → 回收耗尽 → 选择性处决 → 异步收尸 → 现场诊断”

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：swap 也快撑不住时，系统为什么有时提前拒绝一笔内存申请，有时却先答应、最后杀掉某个进程。答案首先在 overcommit：它管理的不是当前 free page，而是未来可能需要兑现的总承诺。启发式、总是允许、严格模式，分别选择了灵活性、极度乐观和可预测边界之间不同的平衡。

当承诺最终兑现不了，系统不会只看当前申请者，而会在回收、swap、重试都失败后进入 OOM 选择。OOM Killer 过滤不能杀的对象，再根据 RSS、swap、页表等资源占用与 `oom_score_adj` 排序，选择一个能较大程度释放资源、又没有被保护的受害者。

发出 `SIGKILL` 还不够，因为进程可能卡住，资源不一定及时释放。OOM Reaper 把“判死”和“收尸”分离，异步尝试解除目标 `mm` 的用户映射，把物理页尽快归还；若锁或不可中断状态阻碍收割，它也有重试和强制路径边界。

最后，`oom_score_adj` 与 OOM 日志把自动机制接回运维现实。系统公式只知道资源占用，管理员还需要表达业务价值；日志则把虚拟地址空间、匿名常驻、文件常驻、swap、页表和最终受害者放回同一事故现场。

把这一切压成最短总图，就是：

```text
承诺：
  overcommit 决定申请阶段敢答应多少未来资源

耗尽：
  回收、swap、重试都无法满足当前分配

处决：
  OOM Killer 按资源释放收益与人工偏移选择受害者

收尸：
  OOM Reaper 不等进程完整退出
  直接尝试回收其地址空间物理页

保护与诊断：
  oom_score_adj 表达关键业务偏好
  OOM 日志还原谁占了什么、为何被选中
```

所以本篇最该记住的一句话是：**Linux 面对内存耗尽时，不是简单地把“申请失败”甩给调用方，而是先决定哪些承诺该被挡在门外，哪些已经发出的承诺需要选择性止损，再把被杀进程的资源尽快收回来，并留下足够线索让人复盘。**

## 七、几个最容易说错的地方

### `malloc(10GB)` 成功是不是代表机器已经为它准备了 10GB 物理内存？

不是。它可能只是建立了虚拟地址空间和一笔未来承诺，真正触碰页面时才逐步兑现。

### overcommit 越严格是不是一定越安全？

不一定。严格模式让失败更早、更可预测，但也可能拒绝大量最终不会完全使用的合理地址空间预留。

### OOM Killer 是不是总杀当前触发分配失败的进程？

不是。它通常会评估多个候选，当前分配者只是触发现场，不等于资源占用最大或最适合牺牲。

### `SIGKILL` 发出去后，物理页是不是马上全部释放？

不一定。目标进程可能卡在内核路径或持有关键锁，因此需要 OOM Reaper 尝试异步收割地址空间。

### `oom_score_adj=-1000` 是不是让进程获得无限内存？

不是。它只改变 OOM 选择排序或保护资格，不会增加物理内存、swap 或承诺上限。

### `total-vm` 最大的进程是不是一定是 OOM 真凶？

不是。虚拟地址空间可能包含大量尚未驻留的预留区域，判断应结合匿名 RSS、文件 RSS、swap、页表和实际 cgroup/系统边界。

## 收束：看懂 overcommit 与 OOM 之后，你才会真正明白“内存耗尽”是一次资源承诺体系的最终清算，而不是一个突然发生的单点错误

回到开头那个问题：当系统答应的内存承诺最终兑现不了，它如何决定先拒绝、再处决、最后收尸？现在答案已经完整闭环了。系统通过 overcommit 选择承诺边界；当回收和 swap 都不足以满足现实需求时，OOM Killer 不随机杀人，而是根据可释放资源、任务关系和人工偏好选择性止损；被杀进程如果不能及时自己退出，OOM Reaper 就独立尝试收回它的地址空间。

而真正的线上判断，也不能只盯着一行“Out of memory”。你需要区分虚拟承诺和实际驻留，比较匿名、文件、共享内存、swap 与页表占用，检查 `oom_score_adj` 和资源边界，才能知道系统为什么走到了这一步，以及下一个最应该保护或限制的对象是谁。

这就是为什么说：**OOM 不是内存管理突然失控的瞬间，而是系统在承诺、回收、换出和资源优先级都已经无法继续平衡之后，执行的一次有规则的止损结算。**

## 八、误解清单、证据清单与边界清单

### 误解清单

- `malloc(10GB)` 成功不等于 10GB 物理页已经就位；它更常是未来承诺被接受，而不是立刻兑现。
- overcommit 严格模式不自动等于“最好”；它只是把失败前移并提高可预测性，同时也会拒绝大量最终不会全部兑现的合理预留。
- OOM Killer 不一定杀当前触发失败的进程；真正决策看的是候选过滤、资源释放收益和人工偏移后的综合排序。
- `oom_score_adj` 不是无限内存豁免令；它只改变被保护或被牺牲的优先级，不创造资源。
- 发出 `SIGKILL` 不等于页马上全回来了；因此才需要 OOM Reaper 异步收尸。

### 证据清单

- 承诺账：`mm/util.c` 中 overcommit、`CommitLimit`、`Committed_AS` 相关路径，支撑“系统在管理未来承诺总账而不是只看当前空闲页”的判断。
- 受害者选择：`mm/oom_kill.c` 中候选过滤、badness 评分与受害者选择路径，支撑“不是谁触发谁去死，而是按资源与偏移综合评分”这条主线。
- 异步收尸：`mm/oom_reaper.c` 中 OOM Reaper 工作路径，支撑“判死”和“回收地址空间”被拆成两条职责链。
- 观测总账：`/proc/meminfo` 与 OOM 日志导出路径，支撑 `CommitLimit`、`Committed_AS` 和事故现场字段如何进入用户态。
- 运维偏好：`oom_score_adj` 相关接口与日志字段，支撑“自动评分 + 人工偏移 + 事故复盘”这套诊断结构。

### 边界清单

- 本文讨论的是 Linux 常见 overcommit/OOM/OOM Reaper 心智模型；公式、候选过滤、日志字段和 cgroup OOM 细节会随内核版本变化。
- OOM 是全局或局部资源止损机制，不是单个 API 的返回值语义；不同分配上下文和 cgroup 语境会改变触发与后果。
- `CommitLimit`/`Committed_AS` 讲的是未来承诺总账，不直接等同当前驻留页或进程真实占用。
- OOM 日志很关键，但不能只看 `total-vm` 这类虚拟地址数字；匿名常驻、文件页、swap、页表与 cgroup 边界要一起解释。
- `oom_score_adj` 能表达业务优先级，但不能替代 cgroup、资源配额和容量设计本身。
