## 现在真正该问的，不再是“数据怎么进页缓存”，而是“它被改脏以后，究竟谁来背着它走完从内存到磁盘的最后一段路”

上一篇我们已经把页缓存如何“进”讲清楚了。你知道文件页怎样按 `address_space` 和 xarray 被组织起来，系统如何通过 readahead 和 fault-around 让读路径越来越像提前铺好的流水线，也知道为什么有些强势应用会用 Direct I/O 绕开页缓存这位中间人。

可只讲“进”，还只讲了一半。因为页缓存不是只读世界。真正让系统更难受的，是一旦页被修改，事情就立刻从“怎样更快读到数据”转成“怎样把这些已被改脏的数据安全、有序、别太抖地送回后端存储”。

也就是说，`write()` 系统调用把数据拷进页缓存并返回，很多时候只是这条旅程的开始，而不是结束。对应用来说它像是“写成功了”；对内核来说，它更像是在说：**又多了一批欠着设备的债。**

这就把我们带到本篇真正的核心困惑：

- 页一旦被写脏，内核怎么知道“这页以后必须落盘”？
- 为什么系统不选择每次写都立刻同步落盘，而要先攒着？
- 如果前台写入比磁盘吞吐快得多，系统怎么决定先让后台写线程追、还是干脆让前台写线程停下来等？
- 写回线程为什么不是一个全局大工人，而是更像“每个设备各扫自家门前雪”？
- `memfd` 这种“看起来像文件、实际上没有真正落盘后备”的对象，又为什么还会落在页缓存和 writeback 这套思维方式里？

所以本篇要建立的顿悟是：**writeback 从来不是“写一次、落一次”的直通动作，而是一条把脏页标记、脏页积压、后台写回和前台限流拆开的流水线。**

先把总图记住：

```text
脏页产生：
  应用修改页缓存页
  页被标记为 dirty

触发层：
  脏页到一定比例先叫后台写回线程干活
  再继续涨则开始逼前台写线程减速或等待

执行层：
  flusher 线程按 backing device / 写回实体循环工作
  把脏页变成 IO 提交到底层设备

控制层：
  dirty throttling 不追求“立刻清空脏页”
  而追求“脏页量稳定在可控平衡区间”

特例层：
  memfd / shmem 这类无磁盘后备对象
  说明“文件语义”和“真实落盘介质”并不总是同一回事
```

这一篇最重要的一句话是：**writeback 真正要解决的，不是“会不会落盘”，而是“什么时候由谁落、前台要不要等、系统怎样在写得太快和落得太慢之间保持平衡”。**

## 一、如果每次 `write()` 都同步把数据推到底层设备，语义当然简单，但整个系统会为此付出巨大的延迟税

### 1. 最朴素的方案：应用每写一次，就立即把对应页同步刷到磁盘

这套方案在语义上非常直观：你写了，我就立刻把数据送到底层，写完再返回。这样应用不必猜数据是否还在缓存里，系统也不必长期背脏页债务，看起来干净利落。

可一旦把真实工作负载放进去，它马上就暴露出两个大问题。第一，设备 IO 启动本身有成本，如果每次小写都单独落一次盘，就等于把本来可以合并的大量操作硬拆成碎片。第二，前台线程会被后端设备延迟直接绑死，哪怕它只是顺手改了一点页缓存数据，也得站在原地等磁盘说“写完了你再走”。

这会让系统吞吐和延迟都很难看。小写会被设备延迟放大，批量性也被完全破坏，CPU 与磁盘之间根本建立不出流水线。

### 2. 第二个失败方案：那就完全异步攒着，永远不主动回写，等内存逼满再说

如果意识到同步落盘太贵，一个常见的反向极端就是：既然页缓存存在，那我就尽量把所有脏页都攒在内存里，等实在不行再说。这样前台写线程几乎感觉不到落盘延迟，似乎非常爽。

问题在于，这只是把痛苦从“每次都痛一点”改成“积累后突然痛很多”。如果后台没有持续、节制、及时地把脏页送走，脏页量会越来越大，回收压力变重，系统一旦开始追债，就会出现大抖动：前台写线程突然被迫等待，回收器、写回线程、设备队列一起进入应激状态。

更糟的是，脏页积压太多还会让故障恢复窗口变差、写回峰值更尖锐、设备缓存与文件系统日志压力更集中。也就是说，“无限期攒着”并不是聪明的异步，而只是把问题拖到以后集中爆炸。

### 3. Linux 的答案：先标脏，再攒批，再后台写，异步追不上时再限流前台

所以 Linux 既不走“写一页落一页”的同步极端，也不走“只管堆脏页，永远别催”的拖延极端，而是把整条出缓存路径拆成了几层职责明确的流水线：

- 前台写路径先把页标成 dirty，承认“这页现在欠着设备一笔账”。
- 系统让脏页积累到一定规模后，先叫后台写回线程起来干活。
- 如果后台追得上，前台通常还能继续顺畅写。
- 如果前台写得远快于后端设备吞吐，脏页继续上涨，系统才开始反过来限速前台，把债务增长压住。

这就是 writeback 主线最该先记住的人话：**能异步就尽量异步，异步追不上了才让前台为后端现实买单。**

## 二、标脏：writeback 的第一步从来不是“发 IO”，而是先把“这页以后必须还账”这件事记明白

### 1. 为什么“页被改过”这件事不能只靠调用方心里记着

应用调用 `write()` 时，当然知道自己改了什么数据；文件系统也知道这次写操作落在哪个 inode 和页范围里。可这种“知道”如果不被固化进内核长期可追踪的状态里，很快就会丢失。

因为写路径结束后，后面还有页缓存回收、后台写回、设备调度、内存压力控制等一长串异步参与者会登场。它们不可能靠回溯某次系统调用现场去判断“这页是不是改过”。

所以写回流水线的第一步，不是立刻把数据推出去，而是**把“这一页已经脏了，以后必须被写回或以其他方式处理”这件事明确记到账上。**

### 2. 为什么脏页状态必须同时体现在页对象和更高层索引世界里

这点和前几篇的主线一脉相承。页是对象化管理的，所以“脏”这个状态当然要能落在页对象自己身上。但对 writeback 来说，只知道某页自己脏了还不够；系统还得能够沿着文件页缓存的更高层结构，成批、按 inode、按 address_space、按设备地找到这些脏页。

这就是为什么脏页标记不是单一动作，而像是在同时更新几层视图：页对象知道自己变脏了，页缓存索引世界也能把“哪些位置脏了”高效标出来，全局统计又要知道当前脏页总量涨到了哪里。

换句话说，**“dirty”不是一个孤立标志，而是 writeback 世界里所有后续决策的起点坐标。**

### 3. 为什么 xarray tag 在这里如此关键

上一篇你刚接受过 xarray 作为页缓存索引地基的角色。到了 writeback 这里，它又承担了新的价值：不只是“按页号找页”，还要让系统高效看见“哪些页是脏的”。

如果没有这种更高层标记能力，后台写回想找脏页时就会很笨：要么整片索引都扫一遍，要么回退到粒度很粗的遍历。那样脏页一多，系统光是找“该写哪些页”就先把自己拖慢。

所以把 DIRTY 这类 tag 挂进页缓存索引结构，本质上是在给 writeback 未来的成批收割提前修路。你不是只知道“某页脏了”，而是让整个索引世界也能快速回答“脏页大致散在哪”。若要把这一节补成更硬的源码正文，最关键的证据位应回到 `mm/page-writeback.c` 中围绕 `folio_mark_dirty`、脏页计数与阈值判断的路径，以及页缓存索引上 dirty tag 的传播逻辑：它们共同支撑“脏页不是单一标志位，而是后续后台写回与限流决策的起点坐标”这句判断。

### 4. 为什么标脏之后立刻出现的不是“现在去写”，而是“现在开始统计压力”

这也是很多人容易误会的地方。页一变脏，不代表下一步立刻就是 submit_bio。更常见的下一步，其实是脏页计数与阈值判断开始发生作用：全局脏页多到什么程度了？某个写回域里是不是已经超过后台回写阈值？当前写者是否已经把系统推近必须限流的位置？

也就是说，标脏不是 writeback 的终点动作，而是触发后续“该不该惊动后台、该不该限制前台”的信号源。只有先把脏这件事稳稳记到账上，整个出缓存控制链路才有依据。

### 5. 本节最该记住的结论：writeback 的起点不是发 IO，而是把“欠债页”在页对象、页缓存索引和全局统计里都明确立账

所以请把“脏页”理解成一种正式负债状态，而不是随手一位标记。只有账立明白，系统才能继续决定：先后台追债，还是该让前台写者踩刹车。

## 三、双阈值：writeback 真正高明的地方，不是有阈值，而是把“后台开始追”和“前台必须等等”分成了两个层级

### 1. 失败方案：只有一个总阈值，低于它什么都不做，超过它所有人一起慌

如果只图实现简单，脏页控制最容易想到的办法就是搞一个总线：不到线，放任系统随便写；一过线，所有写者都开始被阻塞，后台也一并开工。

这当然比完全没控制强，但问题在于它太粗暴。因为后台写回线程启动、设备逐步追赶、前台写者明显感到痛苦，这三件事并不该发生在同一个瞬间。

若等到系统真的逼近危险区了才第一次叫后台起来做事，那后台还没来得及追上，前台就已经被迫站住了；而若稍微一脏就立刻阻塞前台，又会把系统搞得过于敏感，明明设备完全有机会从容消化这波写入，却被你提前掐住了吞吐。

### 2. Linux 的思路：先给后台一段追赶区间，追不上了再让前台承担设备现实

这就是双阈值设计最漂亮的地方。

系统不是只有“安全”和“爆炸”两个状态，而是至少区分出两层关键时刻：

- 第一层阈值到了，意味着“脏页积压已经值得后台开始认真干活”，但前台线程还不一定要痛。
- 第二层阈值到了，说明后台已经追得不够了，债务继续长下去会很危险，所以前台写者也必须开始减速甚至等待。

这一设计等于明确给后台写回线程留出一个安全作业区。脏页到第一层时，后台先追；若后台追得上，前台几乎不会觉得系统发生了什么。只有追不上、脏页继续逼近更危险线时，前台才会真正感到“设备跟不上了”。

### 3. 为什么这比“一把闸门”高明得多

因为它把 writeback 的痛苦尽可能向后台转移，并尽量延后前台可见损失。后台写回本来就该是吸收设备延迟、合并批量、平滑出流的第一道防线。前台线程最好只在确实没有别的选择时，才被迫停下来配合系统减速。

如果没有这种分层，系统要么反应太慢，等出大问题才一起慌；要么反应太早，前台吞吐无谓受损。双阈值的意义就在于：**后台优先救火，前台最后兜底。**

### 4. 这里最该记住的，不是 10% 和 20% 这些数字，而是“谁先承担现实压力”

具体比例、绝对字节数、设备域算法都可能随配置变化，但核心思维不变：第一层是叫后台起来追，第二层才是叫前台别再装看不见。阈值真正区分的不是数字档位，而是**压力传递顺序**。

所以双阈值的顿悟应该写成人话：**先让后台去追设备速度，后台追不上了，才让前台写者亲自为设备现实买单。**

### 5. 本节最该记住的结论：writeback 控制链不是“脏了就等”，而是“先后台追，追不上再前台等”

这条顺序会贯穿后面的 flusher 线程与 dirty throttling。没有它，你就读不懂为什么有时大量写入看起来完全不卡，有时却突然开始被限速。证据位上，这层最值得回到 `mm/page-writeback.c` 中后台阈值、前台阈值与 `balance_dirty_pages` 相关路径去看：正是这些实现把“先后台追，追不上再让前台等”从口号变成了真正的控制顺序。

## 四、flusher 线程：真正把脏页送到底层设备的，不是某个抽象“系统后台”，而是一群按设备/写回域各自追账的工人

### 1. 最容易想当然的设计：全系统只有一个统一写回线程，谁脏就归它管

如果从宏观看 writeback，很容易脑补出一个“系统有个后台线程，专门负责把脏页刷盘”的图景。这种想象简洁，但太粗。

因为现实设备世界并不均匀。不同块设备的吞吐、延迟、队列深度、背后文件系统行为都可能差异巨大。要是全系统只有一个统一大工人，它不是很容易被某个慢设备、某个大写回域、某个特别脏的工作集拖住，就是很难公平又高效地服务所有后端。

### 2. 为什么 writeback 必须更像“按责任区分治”，而不是“一人扫全城”

设想一块 NVMe 和一块慢机械盘同时有脏页积压。如果后台只有一个统一线程，它在调度上就容易陷入尴尬：到底优先追哪边？慢设备是否会拖住快设备的写回节奏？快设备是否会因为统一调度而无法把自己的能力吃满？

这说明 writeback 的自然分治单元，不该只是“全局脏页总量”，还得更贴近设备与写回实体。系统必须承认：**不同后端存储现实本来就不是一个速度世界。**

### 3. Linux 的做法：让每个 backing device / 写回域更像有自己独立的后台工人

于是 Linux 的 flusher 世界不是单线程神话，而更像每个设备或写回域都能有自己的一套追账循环。这样一来，后台写回就不必用一个统一节奏去套所有设备，而可以更贴近各自后端能力与脏页增长现实去追。

这件事非常关键，因为它把“双阈值给后台留追赶空间”这套思路真正落到了执行层：后台不是一个抽象黑箱，而是很多独立工人各管各的责任区。

于是慢设备主要和自己的脏页现实对账，快设备也不必完全陪着它一起慢下来。系统整体会更像多条并行追债流水线，而不是所有账都扔给同一个会被最慢客户拖死的催收员。

### 4. 为什么 `WB_SYNC_NONE` 和 `WB_SYNC_ALL` 这类语义能帮你理解写回的双面性

后台平时做的是尽量批量、尽量异步、尽量不打扰前台的追债工作，这更接近 `WB_SYNC_NONE` 那种语义：先把能送走的脏页往设备那边推，不一定要求前台站在原地等到世界完全干净。

而当你显式调用 `sync`、`fsync` 等需要更强落盘保证的接口时，系统目标就变了。现在不只是“后台先努力追一追”，而是“某个调用者此刻就要看到更严格的落盘结果”。于是等待语义也跟着变重。

这提醒你：writeback 不是只有一套速度目标，它还受调用语义约束。平时靠后台偷偷平滑掉的事，在同步保证场景下就得正面兑现。

### 5. 本节最该记住的结论：flusher 线程不是一个模糊后台，而是设备/写回域级别的独立追账执行者

所以如果只记一句话，就记这句：**writeback 真正落盘时，不是“系统后台统一刷一刷”，而是许多按设备或写回域划分的工人各自循环，把自己责任区里的脏页往底层设备送。** 若要补这一节的关键实现锚点，最适合回到 `fs/fs-writeback.c` 与相关 writeback worker 路径，结合 `bdi_writeback` 一类结构去看：它们共同支撑“后台不是一位模糊总工人，而是按设备/责任区分治追债”的判断。

这也正是为什么后面脏页限流可以做得更细：因为执行层本来就不是一个完全统一的大池子。

## 五、Dirty Throttling：系统真正要控制的，不是“前台还能不能写”，而是“脏页存量别和设备吞吐长期脱钩”

### 1. 失败方案：一旦发现写得太快，就简单粗暴地把前台线程大量 sleep 掉

这看起来很直接。既然后端磁盘写不过来，而前台又一直在制造脏页，那最省事的办法似乎就是：一看脏页多了，立刻把写线程们按住，让它们睡一会儿。

这种硬刹车当然能控制住最坏情况，但它太不平滑，也不够聪明。因为写入速度和设备追赶速度之间并不是非黑即白的关系，系统真正想要的往往不是“突然停住”，而是“把脏页存量拉回一个长期可控的平衡带”。

如果每次都靠粗暴睡死写线程，不仅延迟体验难看，还会导致吞吐大起大落，形成一种锯齿状抖动：先写疯，再猛刹，再放开，再写疯。

### 2. Linux 的目标：不是清空脏页，而是让脏页量稳定在一个平衡点附近

这就是 dirty throttling 最反直觉、也最值得记住的地方。系统并不追求“脏页越少越好”或“赶紧清零”，因为那样会过度牺牲缓存写合并与异步收益。

它真正想要的是：前台写速率、后台落盘速率和当前脏页存量三者之间形成一个相对稳态。脏页要有，但别无限涨；后台要追，但别一直追不上；前台要快，但别快到把系统推离控制区。

换句话说，dirty throttling 的目标更像巡航，而不是急刹。它追求的是稳定区间，不是瞬时极端。

### 3. 为什么这件事天然像一个控制器问题，而不是一个简单阈值问题

因为这里控制的不是单一事件，而是连续变化系统。前台写速率会变，后台设备吞吐会变，不同设备域的积压还会变。你若只靠一个“到了就停、低了就放”的硬阈值开关，很容易造成前后摆动太剧烈。

所以 writeback 才会引入更像 PID 风格的控制思想：根据当前脏页量相对平衡点偏高还是偏低，动态调整对写线程的实际限速力度。偏离越多，刹车越重；回到合理区间，又逐步放松。长期设备能力则通过平滑估算慢慢反馈进来。

这不是为了显得数学高级，而是因为文件写回本来就是一个必须持续微调的动态系统。

### 4. 为什么说它真正调和的是“前台写欲望”和“后端设备胃口”的节奏差

这一层特别适合写成人话。前台写线程只知道自己手里还有数据要塞进页缓存，它的“欲望速度”可能远高于设备真正能咽下去的速度。若完全照前台意愿走，脏页存量会爆；若完全照设备节奏卡死前台，缓存写带来的性能好处又白费了。

所以 dirty throttling 其实是在做节奏调解：**前台你可以快，但快到明显脱离后端可承受速度时，我就一点点加大阻尼，让你重新回到设备消化得了的区间。**

这也是为什么它更像巡航定速而不是红绿灯。红绿灯只有停和走，巡航系统则是在持续微调油门。

### 5. 本节最该记住的结论：dirty throttling 不是“把写线程卡住”这么简单，而是一套让脏页量、前台写速率和设备吞吐长期维持在可控平衡区间的动态控制机制

所以请把“限流”理解成“稳态调节”，而不是“紧急刹车”。真读懂了这一点，你才会明白为什么 Linux 写回系统经常看起来像是在温柔拖你一把，而不是总拿铁锤砸写线程。

## 六、`memfd`：它提醒你“文件语义”和“真实落盘后备”不是一回事，页缓存与 writeback 思维方式可以服务于不真正落盘的对象

### 1. 为什么 `memfd` 在这篇里值得单独讲

表面上看，本篇一直在讲脏页如何最终落到磁盘，而 `memfd` 恰恰是一种没有传统磁盘路径感的对象。那为什么要把它放进 writeback 世界里一起看？

因为它恰好能帮你打掉一个很常见的误解：**页缓存和文件语义，并不总等于“背后一定有个普通磁盘文件等着你写回”。**

`memfd` 看起来像文件：你有 fd，可以 `ftruncate`，可以 `mmap`，可以在进程间传来传去；但它又不像普通文件那样对应一个常规磁盘路径。它更像一种“借用文件接口包装出来的内存对象”。

### 2. 它真正说明的，是“用文件接口管理共享内存”这件事有多好用

有些场景里，你想要的是：

- 一块可以用 fd 传递的共享对象。
- 可以自然接入 `mmap`、权限、长度、生命周期这些成熟文件接口。
- 但你并不真的希望它变成一个落在文件系统路径上的持久文件。

`memfd` 恰好提供了这样一种折中：你享受文件接口与页缓存语义带来的管理便利，却不必把它理解成普通“磁盘文件”。

这非常适合某些临时共享内存、图形缓冲、进程间传递大块只在内存里活着的数据。

### 3. 为什么 seal 机制会成为它特别有意思的地方

一旦这种对象被多个参与方共享，另一个现实问题立刻出现：共享是有了，可我怎么让对方相信这份数据之后不会再被偷偷改掉？

seal 的存在，就是在给这种“文件接口 + 内存语义”的对象补上约束工具。你不只是把一块数据通过 fd 分享出去，还能在某些时刻宣布：长度别再改、内容别再改。这样共享方就不必永远活在“别人会不会又改了我还在看的这份东西”的不确定里。

这提醒你，writeback 世界里很多设计并不是单纯围绕磁盘，而是围绕“文件风格对象的生命周期和一致性管理”。若要补这组判断的证据位，最值得回到 `mm/memfd.c`、`shmem` 相关路径以及页缓存/文件接口交接处去看：它们共同说明 `memfd` 之所以值得放在 writeback 语境里，并不是因为它真的会走普通磁盘落盘，而是因为 Linux 复用的是文件式对象和页缓存管理语义。

### 4. 本节最该记住的结论：`memfd` 说明“文件式对象 + 页缓存式管理”可以服务于纯内存共享场景，而不一定对应真正落盘文件

所以把 `memfd` 放到本篇最后，非常合适。它像是在告诉你：前面整条 writeback/页缓存世界虽然大量围绕磁盘展开，但它背后的抽象其实比“磁盘文件”更宽。Linux 在很多地方真正复用的是“文件风格的对象管理与页缓存思维”，而不只是字面上的落盘路径。

## 七、把本篇收成一张图：脏页系统真正要维持的，不是“赶紧刷干净”，而是“别让前台写速率和后端设备现实彻底失联”

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：数据一旦被改进页缓存，谁负责把它安全送到底层设备，什么时候送，送太慢时谁来背锅。答案首先是否定了两个极端：既不能每次写都同步落盘，把所有设备延迟直接砸到前台线程脸上；也不能无限期攒着，让脏页债务最后集中爆炸。

Linux 选择的是一条分层流水线。前台写路径先把页明确标成 dirty，让“这页欠着设备一笔账”被正式立账；页对象、页缓存索引和全局统计都因此进入 writeback 世界。接着，系统通过双阈值把压力处理拆成两步：先给后台 flusher 线程一段追赶空间，后台追不上了，才开始让前台写线程减速或等待。

真正负责把脏页送到底层设备的，又不是一个模糊的全局后台，而是按设备/写回域各自工作的 flusher 循环。这样不同设备的速度现实不必被强行揉成一个节奏世界。再往上，dirty throttling 则像一个动态控制器，不追求把脏页立即清空，而是让脏页存量、前台写速率和设备吞吐长期稳定在平衡区间附近。

最后，`memfd` 提醒我们：页缓存和文件语义并不总等于“真正磁盘文件”。Linux 复用的很多是文件式对象与 writeback 思维方式，而不是永远对应一条普通落盘路径。

把这一切压成最短总图，就是：

```text
立账层：
  页被修改后先标 dirty
  页对象、页缓存索引和全局统计都知道它欠账了

触发层：
  第一层阈值先叫后台追
  第二层阈值再让前台写者等

执行层：
  flusher 按设备/写回域独立追债
  把脏页变成底层 IO

调节层：
  dirty throttling 让脏页量稳定在平衡带
  而不是忽大忽小地抽风

抽象边界：
  memfd 说明文件式对象管理不总等于传统落盘文件
```

所以本篇最该记住的一句话是：**writeback 真正守护的，不只是“脏页最后会不会落盘”，而是“前台写入、后台设备和页缓存债务三者之间能不能长期保持一种既高吞吐又不至于突然抽风的平衡关系”。**

## 八、几个最容易说错的地方

### `write()` 返回是不是就等于数据已经写到磁盘了？

通常不是。很多时候它只意味着数据已经安全进入页缓存并被标脏，真正落盘还在后面的 writeback 流水线里。

### 脏页一出现，系统是不是就会立刻把它刷掉？

不是。更常见的是先标脏、积累、让后台追，必要时再对前台限流。

### 双阈值是不是只是两个随便定的数字？

不准确。它们真正区分的是压力传递顺序：先后台追，追不上再前台等。

### flusher 线程是不是全系统只有一个？

不是。更合理的理解是按设备或写回域分治，让不同后端各自追自己责任区里的脏页。

### dirty throttling 是不是单纯“把写线程睡一会儿”？

不够准确。它更像一个动态控制器，目标是让脏页量和写入节奏稳定在平衡区间，而不是简单粗暴地刹车。

### `memfd` 是不是“普通磁盘文件的另一个别名”？

不是。它更像用文件接口包装出的内存对象，说明文件式语义与真实落盘后备并不总是同一回事。

## 收束：看懂 writeback 之后，你才会真正明白“写缓存”在 Linux 里其实是一种先欠账、再追账、最后再决定谁等谁的平衡术

回到开头那个问题：页一旦被改脏了，究竟谁来背着它走完从内存到磁盘的最后一段路？现在答案已经完整闭环了。它不是应用一写完就立刻同步完成，也不是后台无期限替你兜底，而是先通过 dirty 状态把债务立账，再让后台写回线程尽量在你没感觉到之前把账追上，只有在前台写得明显快过设备现实时，才通过 dirty throttling 把“你别再装看不见了”这个信号明确传回给写线程。

也正因为如此，你会发现“写缓存”在 Linux 里从来不是一句“异步写回”就能概括的。它真正复杂的地方在于：什么时候积累更划算，什么时候必须开始后台作业，什么时候该让前台协同减速，不同设备之间又如何互不拖累。这些层层分工叠在一起，才让页缓存既能吸收短期写突刺，又不至于在长期失衡时把整台机器拖进抖动与堵塞。

这就是为什么说：**writeback 的核心不是把脏页刷掉，而是把“欠债速度”和“还债速度”调到一个系统还能长期舒服活下去的关系里。**

## 九、误解清单、证据清单与边界清单

### 误解清单

- `write()` 返回不等于数据已经上盘；很多时候它只是数据进了页缓存并被正式立了脏账。
- 脏页出现不等于系统立刻刷盘；更常见的是先立账、再让后台追、必要时才限前台。
- 双阈值不是随便拍的两个数；它真正表达的是“后台先追、前台后等”的压力传递顺序。
- flusher 线程不是全机只有一个总工人；更合理的现实是按设备/写回域分治追债。
- `memfd` 不是普通磁盘文件别名；它证明的是文件式对象和页缓存管理语义可以服务纯内存共享场景。

### 证据清单

- 标脏与脏页总账：`mm/page-writeback.c` 中 `folio_mark_dirty`、脏页计数与阈值判断相关路径，支撑“立账先于发 IO”的判断。
- 双阈值与前后台分工：`mm/page-writeback.c` 中后台阈值、前台阈值与 `balance_dirty_pages` 路径，支撑“先后台追，追不上再前台等”的控制顺序。
- 后台工人分治：`fs/fs-writeback.c` 与 `bdi_writeback` 相关路径，支撑“writeback 按设备/责任区分治而不是全局一锅刷”的结构。
- 文件式纯内存对象：`mm/memfd.c` 与相关 `shmem` 路径，支撑 `memfd` 作为“文件接口 + 页缓存语义，但不等于普通落盘文件”的边界。
- 索引层脏页发现：页缓存/xarray dirty tag 与 writeback 索引路径，支撑“系统不是盲扫全量页，而是沿索引世界高效找到脏页”的判断。

### 边界清单

- 本文讨论的是 Linux 常见 writeback 心智模型；dirty 比例、限流公式、worker 组织与 memfd/shmem 细节会随内核和文件系统变化。
- writeback 讲的是“何时由谁追债”，不自动等于应用层 durability 语义；真正持久化边界仍要结合 `fsync()`、文件系统和设备缓存看。
- dirty throttling 是动态控制问题，不是固定 sleep 常量；不同设备与负载形状会让体感差异很大。
- memfd 放在本篇是为了说明“文件式管理不等于普通落盘文件”，不是说它和常规磁盘文件在后备语义上完全一样。
- 本文先讲正向追债链；页最终要被拆映射、换出或回收时，还需要下一篇反向映射能力配合。
