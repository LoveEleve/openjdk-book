## 现在真正该问的，不再是“系统 OOM 了为什么杀这个进程”，而是“它还没 OOM 时，我们到底该看哪些账本，才不会被看上去很大的自由空间或很夸张的 RSS 骗过去”

上一篇我们已经走到了内存管理链路的末端：overcommit 怎样决定承诺边界，OOM Killer 如何选择性止损，OOM Reaper 怎么把已经被判死的地址空间尽快收尸。那一篇讲的是系统已经失守之后如何善后。

可真正有经验的排障与调优，从来不愿意等到 OOM 那一刻才开始理解机器。因为等看到 `Killed process` 日志时，你已经站在事故现场最后一步了。

于是更现实的问题就变成：**在系统还没失守之前，到底该怎么看内存账本，才能提前知道压力是来自 page cache、匿名常驻、slab、页表、脏页积压、承诺账，还是某个容器的独立预算已经快爆了？**

这看似只是“会不会用 `free -h`、`top`、`cat /proc/meminfo`”的操作问题，实际上远比这复杂。因为 Linux 的很多内存指标都带有非常强的口径语义：

- `MemFree` 看的是当下完全空着的页，但系统真正还能再用多少，未必只看它。
- RSS 看的是一个进程账上挂了多少页，却不等于它“真实独占了多少物理内存”。
- 共享库、页缓存、slab、swap、脏页、huge page 各自来自不同子系统账本，不能一股脑相加。
- 容器环境里，你不仅要看主机总账，还得看这个 cgroup 自己的预算、事件和独立 OOM 压力。

所以本篇要建立的顿悟是：**内存监控不是去找一个“最权威的单数字”，而是先搞清楚每个数字到底在记什么账，再把系统总账、进程分账、参数旋钮和容器预算拼成同一张压力地图。**

先把总图记住：

```text
系统级可用量：
  不是 MemFree
  而更接近 MemAvailable = 空闲 + 可回收 - 水位预留

系统级总账：
  /proc/meminfo 把 LRU、回写、页缓存、slab、承诺、huge page 等子系统账本投影出来

进程级画像：
  RSS 是“账上挂了什么”
  PSS 是“按共享关系摊完后它实际占了多少”
  smaps 可以细到每个 VMA

调优开关：
  /proc/sys/vm 决定回收、脏页、承诺和 OOM 的触发边界

容器级预算：
  cgroup v2 把一台机器的总账拆成多个部门账
  每个容器有自己的上限、保护、事件和 OOM
```

这一篇最重要的一句话是：**内存观测的第一原则，不是盯住一个大数字，而是先搞清楚“这是余额、可动用资产、共享摊分账，还是部门预算账”，否则你看到的很可能只是表面繁荣或表面紧张。**

## 一、为什么 `MemFree` 经常看起来很小，但系统却没事；也为什么有时 `MemFree` 还不错，机器却已经在发抖

### 1. 最朴素的误解：只要 `MemFree` 大，系统就安全；`MemFree` 小，系统就快死了

这几乎是所有初学者都会踩的坑。因为“free”这个词太直白了：既然它表示空闲内存，那空闲越多不是越好吗？反过来，空闲快见底，机器不是应该马上出事吗？

这个逻辑放在没有页缓存、没有可回收 slab、没有水位预留、没有后台回收的简单模型里或许成立，但在 Linux 里远远不够。

系统为了性能，本来就会尽量把空闲页变成更有用的状态：文件页缓存、目录项与 inode 缓存、可回收 slab、预读带进来的页、缓冲区等。也就是说，一台健康机器的 `MemFree` 本来就可能不大，因为空闲页被系统主动拿去做缓存和各种加速了。

反过来，如果 `MemFree` 还有一些，但这些空闲页大多位于不合适的 zone、低于关键水位、或者周围可回收空间已经被预留吞掉，当前分配者仍可能感到很痛。于是单看 `MemFree`，既可能低估可用性，也可能高估安全感。

### 2. 第二个失败理解：那就把所有 page cache 和 reclaimable slab 全算成“可用”，得到一个超乐观数字

如果你已经知道 page cache 和某些 slab 在需要时可以回收，就很容易滑向另一个极端：那我把它们全都视为等价于空闲页，不就能得到真实可用量吗？

这仍然不对。因为这些页虽然“理论上可回收”，但并不意味着你可以无痛、瞬时、100% 地全拿回来。文件页缓存全收光会让读路径惨烈抖动；可回收 slab 也不是无条件立刻化成空白页。更现实的是，系统还要保留一部分水位预留，确保分配路径、原子分配和后台回收能继续转动。

所以“可回收”不是“等价于现金”，而更像“可以变现，但得打折，还要留底”。

### 3. Linux 的答案：`MemAvailable` 不是算“现在空了多少”，而是估“安全前提下还能再动用多少”

这就是 `MemAvailable` 真正聪明的地方。它不是单纯把所有看起来能回收的东西都加起来，而是试图回答一个更实用的问题：**如果现在又来一批正常分配，系统在不把水位打穿、不把缓存生态完全榨干的前提下，大概还能拿出多少页。**

它会从 `MemFree` 出发，但不会停在那里；又会把 page cache 和可回收 slab 的一部分视作潜在可用，但不是满额记入，而是会做保守折算；同时还要减去各种必须保留的预留。结果得出的不是“理想最大可回收值”，而是“更接近现实安全边界的可动用值”。

这也是为什么在线排障里，很多时候 `MemAvailable` 比 `MemFree` 更值得先看。前者更接近“你还能不能继续舒服活着”，后者只是在说“你现在口袋里有没有完全空着的现钱”。如果把这句判断往更硬的证据位落，关键落点应回到 `mm/page_alloc.c` 中 `si_mem_available()` 一类估算路径，以及 `/proc/meminfo` 的导出逻辑：前者说明 `MemAvailable` 不是简单相加空闲页，而是带着可回收折算和水位保留的保守估算；后者则把这份估算真正投影成用户态可读账本。

### 4. 为什么说 `MemAvailable` 本质上是一个“保守的可动用估算”，而不是精确真理

这点也很重要。它仍然是估算，不是上帝视角。因为未来访问模式、回收代价、脏页写回速度、设备负载都在变动。Linux 只能基于当前页缓存规模、slab 可回收性和水位预留关系给出一份保守判断。

但保守估算恰恰是实用价值所在。你在线上排障时不是想求解理论最优回收量，而是想知道：**这台机器是不是已经快把“还能舒服调度下去”的空间吃光了。** `MemAvailable` 就是在尽量回答这个问题。

### 5. 本节最该记住的结论：`MemFree` 只是现钱，`MemAvailable` 更像“现钱 + 可变现资产打折 - 必须保底的钱”

所以如果只记一句话，就记这句：**Linux 判断“还够不够活”时，更接近看 `MemAvailable`，而不是只盯着 `MemFree`。** 前者把可回收页和水位预留都带进了视野，后者只是在描述当下完全闲着的页有多少。

## 二、`/proc/meminfo`：它不是一串神秘字段，而是多个内存子系统各自账本在用户态的总报表

### 1. 为什么逐行死背 `meminfo` 意义不大

很多人面对 `/proc/meminfo` 的第一反应是背字段名：`Buffers`、`Cached`、`Active`、`Inactive`、`Dirty`、`AnonPages`、`PageTables`……这当然能帮你认识词面，但很容易陷入“认识每个词，却看不出哪一组在出问题”的尴尬状态。

因为 `meminfo` 真正的难点不是字段太多，而是它们来自不同子系统：有些是 LRU 状态投影，有些是 writeback 账本，有些是承诺经济总账，有些是 page cache 和 slab 的占用切片。你如果不先按来源和功能分组，就会把一整张体检报告看成毫无重点的化验单列表。

### 2. 更好的读法：先按子系统与问题类型分组，再回到具体字段

真正实战里，更有用的方式是先问：我现在在排查哪类问题？

- 如果担心 OOM 或承诺过高，先看 `CommitLimit`、`Committed_AS`、`SwapTotal`、`SwapFree`。
- 如果怀疑回收压力或工作集冷热问题，先看 `Active`、`Inactive`、`Active(file)`、`Inactive(anon)` 一类 LRU 投影字段。
- 如果怀疑写回跟不上，`Dirty`、`Writeback` 这类字段是关键。
- 如果担心某种“谁吃掉了内存”，就要去看 `AnonPages`、`Mapped`、`Slab`、`SReclaimable`、`SUnreclaim`、`KernelStack`、`PageTables`。

也就是说，**`meminfo` 不是“逐行看完”，而是“先锁定哪个子系统可能失衡，再看对应字段怎么讲同一个故事”。** 要把这一节补成更有源码锚点的正文，最合适的证据位不是穷举所有字段，而是指出 `/proc/meminfo` 这张总报表本身来自 `fs/proc/*` 与内存子系统导出接口的拼装：它把 LRU、writeback、slab、承诺账和 swap 这些来自不同内核子系统的统计投影到了同一个用户态入口，所以你才不能把它误会成单一机制的体温计。

### 3. 为什么 LRU 相关字段特别能把回收章节接回现实

像 `Active(file)`、`Inactive(file)`、`Active(anon)`、`Inactive(anon)`、`Unevictable`、`Mlocked` 这些字段，几乎就是你在第 9 篇学过的回收状态机的用户态倒影。它们让你第一次能从命令行直接看到“文件页和匿名页现在分别躺在哪一层”“有多少页根本不可回收”。

这也就是为什么说 `/proc` 是内核调试第一现场：前面的所有机制不是抽象故事，而是真的在这些字段里留下了实时投影。你不需要每次都去看 `mm/vmscan.c`，`meminfo` 已经把结果浓缩给你了。

### 4. `Dirty` / `Writeback` 等字段为什么又把 writeback 世界带回来了

如果 `Dirty` 长时间很高，说明有大量脏页还停留在页缓存账上；`Writeback` 高则意味着后台写回线程正在积极把这些债务往设备方向送。这些字段不只是“文件系统写得多”，而是在让你看到第 7 篇里那套 writeback 流水线此刻处在什么位置：是脏页积压了、后台正在追，还是追都追不过来。

所以不要把 `meminfo` 里的这些字段当作静态分类名词，它们其实是内核内部状态机的现场示波器。

### 5. `PageTables`、`KernelStack`、`Slab` 为什么经常是“谁把内存吃没了”排查的关键线索

很多线上问题不是“业务堆用太大”，而是页表膨胀、内核栈异常、不可回收 slab 泄漏、dentry/inode 缓存异常增长。这些问题如果只看总内存使用率，很容易都表现成一句“used 变高了”。

而 `meminfo` 的价值，就在于它能把“大头是谁”先拆出来。看到 `PageTables` 激增，你会想到海量小映射、巨量进程地址空间或页表压力；看到 `Slab`、`SUnreclaim` 很高，就会怀疑内核对象缓存或泄漏；`KernelStack` 异常则会把你引向线程数量和内核栈规模。

### 6. 本节最该记住的结论：`/proc/meminfo` 不是一个数字列表，而是 LRU、writeback、page cache、overcommit、内核对象等多套账本的总报表

因此最值得记住的人话是：**看 `meminfo` 时先问“我在怀疑哪个子系统”，再去看对应字段组合，而不是把几十行当作一锅乱粥逐条死背。**

## 三、RSS、PSS 与 `smaps`：进程级内存画像里，最大的坑不是“看不到数据”，而是“共享页如果按每进程全价记，会把责任账记重复”

### 1. 为什么 RSS 看起来直观，却经常会让你误判谁是真正的大户

RSS 很好懂：某个进程当前有多少页驻留在 RAM 里。但正因为它直观，很多人会把“RSS 大”直接等价成“这个进程独占了很多物理内存”。

问题在于，RSS 账本会把共享页在每个进程账上都记一遍。两进程共享 10MB 动态库，各自 RSS 里都可能记上这 10MB。你把全系统 RSS 一加，马上就会出现明显虚高。

所以 RSS 更像“这个进程眼下账上挂了哪些驻留页”，而不是“如果把全系统内存公平分摊，这个进程实际占了多少”。

### 2. PSS 为什么是更接近“真实责任分摊”的口径

PSS 的核心思想很朴素：私有页全算给你，共享页则按共享者人数平摊。这样一来，同一份共享库不会在每个进程头上都按全价重复记，而是被公平拆账。

这会让进程级内存责任画像更接近现实，也让“把多个进程占用加总起来”和“全机真实物理使用量”之间的关系更合理。对容量规划、容器账单、公平归责和找真正大户来说，PSS 往往比 RSS 更值得先看。

### 3. `smaps` 为什么会细到 VMA

上一章刚讲完 `mm_struct` 与 VMA，这里它们就立刻回到了实战。`smaps` 不是只给一个进程总计，而是沿着 VMA 一段一段输出：这段有多少 RSS、多少 PSS、多少私有脏页、多少共享干净页、多少 swap 等。

这意味着如果你不仅想知道“进程总共用了多少”，还想知道“究竟是堆、匿名映射、文件映射、共享内存还是某一段特殊 VMA 在吃”，`smaps` 才是真正能把问题切开的工具。

也就是说，**`smaps` 是把第 4 篇里那张地址空间地图重新翻译成了一份逐地块内存账单。**

### 4. 为什么 `smaps_rollup` 是线上排障非常实用的折中

完整 `smaps` 很细，但也可能非常大，尤其进程 VMA 多时阅读成本高。`smaps_rollup` 的价值，就在于它替你把所有 VMA 汇总成一份更轻量的总账：保留 PSS、Pss_Anon、Pss_File、Pss_Shmem 等关键口径，同时不必手工把几百上千段 VMA 相加。

所以线上第一次判断某进程是不是真的“占了很多”时，`smaps_rollup` 经常是比全量 `smaps` 更高性价比的起点。需要进一步追地块责任时，再回到完整 `smaps`。证据位上，这组判断最值得回落到 `fs/proc/*` 中生成 `smaps`/`smaps_rollup` 的路径，以及 `mm` 子系统对 RSS/PSS/私有脏页等口径的统计导出逻辑：正是这些接口把“进程总账”和“逐 VMA 地块账”分成了两种不同阅读颗粒度。

### 5. 为什么 USS / Private 视角也不能被忽略

PSS 很适合公平摊账，但如果你要问“这个进程一死，绝对只属于它的那部分内存能立刻少多少”，私有页口径又会更有价值。换句话说，PSS 擅长做共享责任分摊，USS/Private 擅长做“完全属于你自己的地盘”估算。

这提醒你，进程级内存画像没有单一银弹口径。问题不同，最合适的口径也不同：公平归责看 PSS，纯独占成本看 USS/Private，当前驻留规模看 RSS。

### 6. 本节最该记住的结论：RSS 是“账上挂了什么”，PSS 是“公平摊完后你实际占了多少”，`smaps` 则把这笔账拆回每个 VMA 地块

所以如果只记一句话，就记这句：**进程内存排查的最大误区不是没数据，而是拿错口径；RSS 常会把共享账记重，PSS 更适合找真实责任，`smaps` 更适合把责任落回具体 VMA。**

## 四、`/proc/sys/vm`：这些参数不是“神奇性能开关”，而是把内核各条压力传导线的触发边界暴露给了你

### 1. 为什么“调参数”之前必须先知道自己在改哪条数学边界

很多线上调优事故的根源，不是参数本身危险，而是把参数当魔法开关来拧。比如看到回收频繁就想随手改 `swappiness`，看到 OOM 就调 `min_free_kbytes`，看到写抖动就动 `dirty_ratio`。如果你没先理解这些参数对应的是哪条触发边界，结果很容易是把另一处平衡打坏。

因为这些 vm 参数不是抽象标签，而是前面十几篇机制的现场入口：有的在改水位保留区，有的在改脏页写回阈值，有的在改匿名/文件页回收偏好，有的在改 overcommit 承诺边界和 OOM 行为。

### 2. 为什么它们本质上都是“把平衡点搬前或搬后”

调大 `min_free_kbytes`，不是平白多出内存，而是让系统更早进入“别再把可用页吃这么干净”的保护区。调 `dirty_ratio`、`dirty_background_ratio`，不是改变设备速度，而是改变后台写回和前台限速从哪一刻开始介入。调 `swappiness` 不是凭空制造或消灭 swap，而是把匿名页与文件页牺牲顺序的偏好往一边推。

所以这些参数最该被理解成“触发点旋钮”，而不是“性能档位开关”。你在调的是系统何时开始紧张、何时开始回收、何时开始写回、何时开始限速。

### 3. 为什么 `vmstat` 与这些参数要一起看

参数告诉你边界在哪里，但只有结合现场统计你才知道系统是不是频繁撞线。比如 swapin/swapout 速率、回收活动、脏页积压、`pgscan`/`pgsteal` 一类指标，都会告诉你当前系统是不是已经在大量触发某条机制。

不看现场就只调参数，很像闭着眼改恒温器。你连屋里当前几度、温度变化趋势如何都不知道，谈不上知道自己是在把报警阈值调得更合理，还是把房间推得更极端。

### 4. 为什么参数“能调”不代表“应该频繁调”

默认值之所以存在，是因为内核已经做过大量通用平衡。线上只有当你能明确指出哪条机制对当前工作负载系统性不匹配时，调参数才有意义。否则，很多“我想让它少回收/少 swap/少写回”的愿望，最后只是把问题从一个子系统挤到另一个子系统。

因此调参最好被视为在已有观测结论上的定向修正，而不是排障第一反应。

### 5. 本节最该记住的结论：`/proc/sys/vm` 暴露的是触发边界，不是魔法按钮；调参前先定位是哪条压力传导线失衡

所以一句最短人话是：**这些参数调的是“什么时候开始紧张”和“紧张时先动谁”，而不是凭空让机器更大或更快。**

## 五、cgroup v2：容器里的内存不是“共享主机总账的一个视角”，而是内核真的在给每个部门单独记账、单独限额、单独 OOM

### 1. 为什么主机看起来还有内存，某个容器却已经 OOM

这类现象常把人搞糊涂：宿主机 `MemAvailable` 还不错，甚至 swap 也没吃满，某个容器却已经报 OOM 或被杀。若你只站在主机总账视角，会觉得很不可思议。

但 cgroup v2 的核心现实是：容器不是“共享总账但看起来像一组进程”那么简单。内核会为每个 memory cgroup 维护自己的账本、限制与事件线。某个容器可以先于全机总账失守，因为它自己的预算先被打穿了。

这就像公司总账户里还有钱，但某个部门自己的预算封顶已经到了。部门先停，不代表公司立刻破产。

### 2. 为什么 `memory.max`、`memory.high`、`memory.low`、`memory.min` 要分四档

如果只允许一个硬上限，容器控制会很粗糙：不到上限什么都不说，到了就猛烈回收甚至 OOM。现实里很多业务需要更细的行为边界：有的流量可以慢一点但不想死，有的缓存最好被保护，有的关键服务应获得硬保障。

所以 cgroup v2 把控制拆成了几层：

- `memory.max` 更像硬墙，超过后最终要回收、限速甚至 OOM。
- `memory.high` 更像“先给你明显压力”，用节流和回收提醒业务放慢。
- `memory.low` 表达尽量保护。
- `memory.min` 则是更强硬的底线保护语义。

这说明容器内存控制不是一个单数字封顶，而是一套部门预算与保护制度。

### 3. 为什么 `memory.events` 特别适合做线上早期告警

总量统计告诉你现在用了多少，但事件计数告诉你边界已经被碰了几次。高、max、oom、oom_kill 这些事件是“内核已经开始认真介入”的直接证据。

所以在容器环境里，光看当前 `memory.current` 或 rss 不够。很多时候更有价值的是知道：**这个容器最近是不是已经频繁撞 `memory.high`，是不是开始经历内核节流，是否已有局部 OOM 发生。** 这类事件能把“尚未死透但已经开始痛”的阶段提早暴露出来。若往证据位落，这层最关键的实现支撑应回到 `mm/memcontrol.c` 及 cgroup 相关导出路径：`memory.current`、`memory.events` 之所以值得信，不是因为名字听起来像预算表，而是因为内核真的在 memory cgroup 维度记账、限流和触发局部 OOM。

### 4. 为什么 per-cgroup LRU / reclaim / OOM 让容器隔离变成了内核的一等公民，而不是用户态约定

这也是 memory cgroup 真正厉害的地方。它不是在用户态做账本游戏，而是把前面章节讲过的回收、写回、匿名/文件页计数、OOM 决策等机制真正按 cgroup 维度再切了一遍。于是容器 A 的内存紧张先回收 A，自家超硬限先 OOM A，而不是把整机其他业务一起拖下水。

这意味着容器隔离不是“业务约定别超”，而是内核记账与回收体系已经把容器预算内建进决策链了。

### 5. 本节最该记住的结论：cgroup v2 把主机总账拆成多个部门账，每个部门都有自己的预算线、事件线和局部 OOM 路径

所以如果只记一句话，就记这句：**容器内存不是在偷看宿主机总账，而是在用自己那套由内核维护的分账本、分上限和分止损逻辑生活。**

## 六、把本篇收成一张图：会看内存，不是会背字段，而是知道每个口径在回答“总账、分账、共享账、承诺账还是预算账”中的哪一个问题

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：在线上还没 OOM 时，怎样从各类统计里提早看见压力往哪里聚集。答案首先告诉你别只看 `MemFree`，因为它只是现钱；真正更接近“还能舒服活下去”的，是 `MemAvailable` 这种把可回收资产和水位预留一起考虑进去的保守可动用估算。

接着，`/proc/meminfo` 把整个内存世界拆成了多套子系统账本：LRU 状态、writeback 状态、slab 和内核对象占用、承诺经济、大页与 swap。它不适合逐行死背，更适合按“我在怀疑哪个子系统”来分组阅读。

进程级画像进一步把总账拆成责任账。RSS 说的是“你账上挂了哪些页”，PSS 说的是“共享部分摊完之后你真实占了多少”，`smaps` 则把账单再落回每个 VMA 地块。于是共享库、匿名页、文件映射和私有脏页不再混成一团。

`/proc/sys/vm` 把回收、脏页、承诺和 OOM 的触发边界暴露成旋钮，提醒你调参其实是在改哪条压力传导线何时被触发。而 cgroup v2 则把这些主机总账进一步切成部门分账，让每个容器拥有自己的预算线、事件线和局部 OOM。

把这一切压成最短总图，就是：

```text
可用量口径：
  MemAvailable 比 MemFree 更接近安全可动用内存

系统总账：
  meminfo 是多个内存子系统的总报表

进程责任账：
  RSS 看挂账
  PSS 看公平摊分
  smaps 看 VMA 地块明细

触发旋钮：
  /proc/sys/vm 决定哪条机制何时开始介入

部门预算账：
  cgroup v2 让容器拥有自己的限制、事件和 OOM 路径
```

所以本篇最该记住的一句话是：**内存监控真正困难的地方，不是没有数字，而是数字太多、口径太杂；你必须先分清这是总账、责任账、共享摊分账、承诺账还是部门预算账，才有资格谈诊断和调优。**

## 七、几个最容易说错的地方

### `MemFree` 很大是不是就说明系统没压力？

不一定。它只表示完全空闲页，而不是综合考虑可回收资产和水位预留后的真实可动用空间。

### `MemFree` 很小是不是就说明快 OOM 了？

也不一定。健康系统常会把大量空闲页拿去做 page cache 和可回收缓存，更该结合 `MemAvailable`、回收和 writeback 现场一起判断。

### RSS 最大的进程是不是一定最值得优化或最该杀？

不一定。共享页会被重复记账，排查真实责任时更该结合 PSS、Private/USS 和具体 VMA 明细。

### `smaps` 太细是不是没有实战价值？

不是。它恰恰在“到底哪一段 VMA 吃了内存”这种问题上最有价值，只是第一次排查往往先从 `smaps_rollup` 这类汇总入口开始更省力。

### vm 参数是不是谁感觉不爽就都可以调一调？

不建议这样理解。它们对应具体机制的触发边界，调参前最好先通过统计确认是哪条压力传导线失衡。

### 容器 OOM 是不是一定意味着宿主机也快没内存了？

不是。memory cgroup 有自己的预算线和局部 OOM 路径，容器可以先于宿主机总账失守。

## 收束：看懂统计口径之后，你才会真正明白“内存诊断”从来不是找一个最重要的数字，而是把多层账本拼成同一张压力地图

回到开头那个问题：线上还没 OOM 时，怎样提前看见压力正在往哪里聚集？现在答案已经完整闭环了。你不能只盯 `MemFree`，也不能把 RSS 当成全部真相，更不能在容器环境里只看宿主机总账。你需要先分清可用量估算、系统总账、进程责任账、共享摊分账、参数触发边界和 cgroup 预算账各自在回答什么问题，再把它们叠成一张完整的压力地图。

也正因为如此，真正的内存排障和调优从来不是“看一个数大不大”。它是在问：现钱少是不是因为钱都被拿去做高价值缓存了？可回收资产是不是真的还能顺利变现？共享账是不是被 RSS 算重了？某个容器是不是已经先撞了自己的预算线？当前看到的脏页、slab、页表或匿名常驻，到底对应前面哪一条内核机制正在失衡？

这就是为什么说：**会看内存，不是会背字段名，而是会把字段放回机制与账本语义里解读。** 只有这样，统计才不是“结果陈列”，而是下一步用户态分配器、栈、堆和容器资源设计的行动线索。

## 八、误解清单、证据清单与边界清单

### 误解清单

- `MemFree` 不是“系统还安不安全”的总代表；它只是现钱，不代表安全可动用空间。
- `MemAvailable` 不是拍脑袋魔法数字；它是带着可回收折算和水位保留的保守估算，但也不是精确真理。
- `meminfo` 不是单一机制报表；它本来就是多个内存子系统总账拼在一起的总视图。
- RSS 最大的进程不自动等于最真实责任方；共享页会重复记账，PSS/`smaps` 往往更接近责任落点。
- 容器 OOM 不等于宿主机总账也快没内存了；memory cgroup 可以先撞自己的预算线。

### 证据清单

- `MemAvailable` 估算：`mm/page_alloc.c` 中 `si_mem_available()` 一类路径，支撑“不是简单相加空闲页，而是带折算和预留”的判断。
- 系统总账入口：`/proc/meminfo` 及 `fs/proc/*` 相关导出路径，支撑“多子系统账本在用户态汇总成一张报表”的结构。
- 进程责任账：`/proc/PID/smaps`、`smaps_rollup` 与相关导出路径，支撑 RSS/PSS/逐 VMA 地块账的两层阅读颗粒度。
- 调优旋钮：`/proc/sys/vm` 相关接口，支撑“这些参数不是神秘开关，而是回收、脏页、承诺和 OOM 触发边界”的判断。
- 容器预算账：`mm/memcontrol.c` 与 cgroup memory 导出路径，支撑 `memory.current`、`memory.events`、局部 OOM 和 memory.high 节流这套分账机制。

### 边界清单

- 本文讨论的是 Linux 常见内存观测口径；字段集合、估算方式、cgroup 细节会随内核版本和发行版变化。
- 单个统计口径都可能骗人；真正可靠的排障必须把系统总账、进程责任账和容器预算账交叉验证。
- `smaps`/`smaps_rollup` 很有价值，但读取成本和权限边界也要纳入线上取证策略。
- `/proc/sys/vm` 参数是机制边界，不是通用“调一调就会更快”的性能按钮。
- cgroup v2 讲的是分账与局部止损，不自动替代对宿主机全局回收、page cache 与 IO 压力的理解。
