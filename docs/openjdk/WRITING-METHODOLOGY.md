# 源码分析正文写作方法论

> 适用范围：`openjdk-book` 全部正文与后续重写任务。
> 核心目标：把已经验证的源码事实，组织成读者能够理解、复述、迁移的技术文章。

## 一、正文不是源码翻译

正文写作的输出不是：

- 源码文件的顺序翻译
- 类、字段、函数的清单
- 事实卡片的堆叠
- 代码块的连续粘贴

正文必须满足：即使删掉大部分代码，读者仍能复述机制、解释设计取舍，并知道它解决了什么问题。

## 二、写作前置依赖

正文开始前必须同时满足四类依赖：

### 1. 事实依赖

- 对应域已有范围规划与大纲
- 关键源码文件、函数、行号已重新验证
- 状态、线程、时序、字段和异常路径已有事实卡片
- 代码块来源明确，禁止凭记忆编造
- 版本差异、已知风险和未验证边界已记录

### 2. 机制依赖

- 这篇文章依赖的底层机制已有前置文章或明确的最小解释
- 前置机制不能只在正文中用一个名词带过
- 如果依赖尚未写成文章，必须在本篇提供足够的局部闭环，或调整写作顺序
- 不得引用尚未分析、尚未验证的后置域作为既成事实

### 3. 认知依赖

写作前必须回答：

1. 读者此刻真正困惑什么？
2. 哪些概念必须先出现，读者才能理解主线？
3. 哪些实现细节虽然正确，但现在会打断理解？
4. 本篇结束时，读者应该能解释什么现象？

### 4. 叙事依赖

- 先确定读者理解路径，再决定源码出场顺序
- 先问题、场景、障碍，再设计和代码证据
- 一篇必须形成闭环，不能只完成源码调用链的一半
- 篇与篇之间必须有明确的前置、后续和桥接关系

## 三、三步分离流程

### 第一步：素材提取

产物是事实卡片，不是正文。每张卡片至少记录：

- 场景/现象
- 角色与职责
- 入口与出口
- 关键调用链
- 状态与时序
- 关键字段/常量
- 设计取舍
- 失败路径与边界
- 源码文件、函数、行号
- 测试、实验或工具实证
- 版本差异

### 第二步：理解路径设计

先离开源码，以读者为中心设计文章：

- 开篇困惑是什么
- 最小心智模型是什么
- 哪个障碍先解释
- 哪个设计取舍后解释
- 哪段代码只作为证明
- 哪些细节移到后文或删除
- 结尾如何回收开篇悬念

这一阶段必须形成文章级结构和依赖声明，未完成不得写正文。

### 第三步：叙事写作

按理解路径写作，不按源码文件顺序写作：

1. 场景或问题
2. 直觉方案为何不够
3. 角色、数据流或状态机
4. 设计方案与取舍
5. 源码证据
6. 边界、失败与代价
7. 悬念回收和下一篇桥接

## 四、单篇文章的最小闭环

每篇至少包含：

### 1. 场景句

让读者知道这个机制在什么现象下出现。

### 2. 核心问题

明确读者要解决的疑问，而不是直接介绍类名。

### 3. 心智图

用文字图、时序图、状态图或数据流图说明：

- 角色
- 先后顺序
- 依赖关系
- 状态传播
- 成功与失败出口

### 4. 失败方案

至少推演一个直觉但不可行的方案：

- 它为什么看起来合理
- 它在哪里失败
- 当前设计绕过了什么代价

### 5. 源码证据

代码只能证明前文已经提出的判断。代码块要求：

- 来源真实
- 写作前重新 grep/sed 验证
- 单段尽量不超过 30 行
- 删除样板、无关日志和无关分支
- 代码后解释“这段证明了什么”

### 6. 边界与代价

至少说明一个：

- 失败路径
- 并发代价
- 内存/IO/延迟代价
- 兼容性约束
- 版本差异
- 未覆盖范围

### 7. 篇末桥接

篇末必须有：

- 本篇结论
- 开篇悬念回收
- 已解决的问题
- 尚未解决的问题
- 下一篇前置或后续桥接

## 五、写作语言规则

### 主语优先写角色

不要开头就写字段类型。优先使用：

> 角色 → 动机 → 障碍 → 手段 → 结果

例如：先说 VM 线程为什么需要让 Java 线程停下，再介绍状态字段，而不是先介绍字段是 volatile。

### 事实与解释分开

- “源码做了什么”必须有源码依据
- “为什么这么设计”必须标注为设计推断，或由注释、测试、提交历史支撑
- 不把合理猜测写成作者意图

### 不提前透支后文

- 不使用无法在当前文章内解释的核心名词
- 如果必须引用后续机制，只做导航式桥接，不把后文结论当作本篇前提
- 前向引用必须明确标注“后文展开”或改写当前结构

### 教学重复是必要的

核心结论至少出现两次：

- 第一次作为问题线索或中间判断
- 第二次在推导结束后收束

重复必须承担不同教学作用，不能机械复述。

### 篇幅与反偷懒约束

- 重大机制篇、主链路篇、总串联篇：叙述性正文原则上不少于 8000 字，目标 10000-15000 字。
- 中等专题篇：通常 5000-8000 字，但必须独立完成一个问题闭环。
- 困惑/事故场景开场建议不少于 600 字；失败方案推演建议不少于 1200 字；每个核心拆解层建议不少于 1500 字；误解澄清建议不少于 800 字；收网总结建议不少于 500 字。
- 篇幅不足时只能通过具体例子、失败方案、版本对比、误解纠正和文字化图表扩充，禁止空洞重复。

### 正文禁用词扫描

正文主线中出现以下词语时必须复查是否跳过了应讲内容：

- 此处不再赘述
- 不再展开
- 类似地
- 同理
- 依此类推
- 篇幅所限
- 显然
- 容易看出
- 细节读者自行阅读源码

## 六、篇章与全书依赖

每篇正文写作前建立依赖记录：

```text
本篇
├── 前置文章：读者必须先掌握的概念
├── 复用文章：只引用结论，不重复主线
├── 展开文章：本篇提供导航，后文深入
├── 横向关联：可用于知识脑图的交叉边
└── 后续文章：本篇结尾可自然引出的主题
```

依赖分为三种：

- **硬依赖**：没有前置概念无法理解本篇，必须先写
- **软依赖**：本篇可提供局部解释，也可先写
- **导航依赖**：只需要建立链接，不得把后文内容前置成既定事实

写作顺序按硬依赖拓扑排序；同层文章按读者认知负担、机制中心性和素材成熟度排序。

## 七、正文写作前检查单

- [ ] 目标读者和核心困惑明确
- [ ] 文章能在单篇内形成机制闭环
- [ ] 前置依赖已分类为硬/软/导航
- [ ] 大纲顺序按理解路径而非源码文件顺序
- [ ] 每个关键结论有事实卡片
- [ ] 每个源码行号已重新验证
- [ ] 代码块来源真实且长度受控
- [ ] 至少一个失败方案推演
- [ ] 至少一个设计取舍或代价
- [ ] 状态/线程/时序已画图或文字化
- [ ] 未引用未分析域的未经验证结论
- [ ] 篇末有悬念回收和下一篇桥接

## 八、正文完成后的深审

### 第一轮：事实审

查类名、函数名、路径、默认值、常量、数字和行号。

### 第二轮：因果审

查每个“因此、所以、为了、保证、避免”是否有证据，区分事实与推断。

### 第三轮：结构审

删掉源码顺序污染、重复段、前向引用和无法闭环的章节。

### 第四轮：读者审

不看代码块，只读叙述，确认读者仍能复述主流程。

### 第五轮：边界审

查失败、并发、生命周期、资源释放、版本差异和未覆盖空间。

### 第六轮：依赖审

查前置链接、后续链接、跨域引用和知识脑图节点是否真实存在且方向正确。

只有每轮都发现的问题已经修复，并且下一轮不再产生新的高风险问题，文章才算收敛。

## 九、额外目标：主动寻找可证实的源码缺陷

高质量源码分析不只是在既有设计上做解释；如果在阅读、写作或深审过程中能够发现真实的代码缺陷、边界漏洞、资源泄漏、竞态、错误注释、实现与契约不一致，且能建立完整证据链，这本身就是“真正读懂”的表现。

但这里必须遵守三条纪律：

1. **不为找 Bug 而猜 Bug。** 只有当源码、调用链、状态机、测试、日志或可复现实验共同支持时，才能把问题写成缺陷候选。
2. **先区分层级。** 发现的问题可能是：
   - 文中事实错误
   - 代码注释/文档错误
   - 实现边界缺失
   - 行为回归风险
   - 真正的功能/并发/内存 Bug
3. **先固化证据，再下结论。** 结论至少要能回答：场景是什么、触发条件是什么、错误表现是什么、源码为什么会走到这里、已有防线为什么失效。

### 发现 Bug 的最小证据链

当怀疑存在缺陷时，至少补齐以下材料：

- 触发场景
- 涉及角色/线程/资源
- 关键调用链
- 关键状态或索引变化
- `file:line` 证据
- 如果可能，给出最小复现、日志、断言或测试思路
- 影响面：正确性、并发、内存、性能、可维护性中的哪一类
- 为什么它不是“调用者误用”而是“实现本身缺口”

### 缺陷处理策略

- **文内修正**：如果只是正文说错了，直接修文章并记录。
- **文内标注风险**：如果是可疑实现边界但证据不足以定性为 Bug，在正文或 review-notes 中明确写成“风险/边界”，不能写成已确认缺陷。
- **形成 issue 候选**：如果证据完整、影响明确、具备复现线索，应在 review-notes 中单列“缺陷候选”，并建议整理为 issue。
- **正式提 issue**：只有在用户同意，或任务明确要求对外反馈时，才真正创建 issue。issue 内容应包含复现步骤、源码位置、预期/实际行为和影响说明。

### 深审中的额外检查点

在事实审、因果审和边界审之外，增加一条主动检查：

```text
这段实现除了“怎么工作”之外，是否存在
- 契约与实现不一致
- 资源释放时机缺口
- 索引/边界条件漏洞
- 并发竞态
- 错误恢复缺失
- 注释与实际行为相反
```

如果答案是“可能有”，必须继续追证，直到归类为：

- 已确认缺陷
- 高风险边界
- 证据不足，暂不定性

能发现并证明真实缺陷，是加分项，不是硬性 KPI；方法论鼓励这种能力，但禁止把猜测包装成发现。

## 十、四项强制复检

### 1. 删码测试

删除所有代码块后，文章仍应能讲清问题、失败方案、设计、主流程和边界。若文章塌陷，说明代码承担了叙事骨架。

### 2. 陌生人测试

假设读者会 Java，但不懂当前 JVM 机制，也不会替作者补全逻辑。检查读者是否会在某一节突然失去主线，或感觉作者默认其已经理解关键概念。

### 3. 反向提纲测试

只读小标题，应该能还原：

```text
问题 → 失败方案 → 顿悟 → 机制 → 回收
```

如果只能还原源码目录或类名列表，必须重排结构。

### 4. 禁用词扫描

对正文主线运行禁用词扫描；命中后优先重写该节，不能用“只是过渡句”绕过检查。

## 十、与知识脑图的连接

正文不是脑图节点的替代品。每篇文章同时产出结构化关系：

- `前置依赖`
- `核心机制`
- `调用关系`
- `状态转换`
- `数据流`
- `失败路径`
- `复用关系`
- `后续展开`
- `跨框架对照`

正文中的链接只表达已经验证的关系。不能为了图谱完整而制造未经源码证实的边。
