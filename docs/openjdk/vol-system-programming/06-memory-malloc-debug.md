## 现在真正该问的，不再是“malloc 背后有没有 arena”，而是“当 RSS 持续上涨、延迟变高、`mlock` 失败、`accept` 返回 `EMFILE`、线程看起来跑不动时，我该先看哪一本账，而不是先盯着一个单独的数字发呆”

上一章我们已经把一个非常容易误判的系统编程事实讲透了：`malloc(size)` 不是“立刻向内核申请一块内存”的简单系统调用，而是一个用户态分配器入口。它可能先在 arena、cache、空闲块体系里周转，必要时才通过 `brk`、`mmap` 等路径扩展地址空间。于是：

- `free()` 不等于 RSS 立刻下降；
- 多线程下 arena/cache 可能降低锁竞争，却放大保留内存与碎片感知；
- “线程安全的 malloc”也不意味着“异步信号里可安全重入”；
- 地址空间里的映射、物理驻留、用户态可复用空闲块，其实已经是三层不同账本。

到了真正排障时，这几层账本会和更多层纠缠在一起。凌晨三点你看到的表象，可能只是：

- `top` 里 RSS 越来越大；
- 服务延迟飙高，但 CPU 利用率并不离谱；
- 明明业务已经平静，进程体积却没明显缩回去；
- `mlock()` 失败，让你以为“系统还有很多空闲内存，为什么锁不住”；
- 新连接到第 1025 个就报错，或者线程突然像被钉在某些 CPU 上跑不动；
- 某个容器里进程莫名其妙被 OOM kill，但单看应用日志毫无头绪。

如果此时你只会盯一个 RSS 数字，或者只会问“是不是内存泄漏了”，大概率会被系统编程这门课狠狠干翻。因为内存排障从来不是看一个数，而是对齐多层现实：

- 虚拟地址空间里映射了什么；
- 这些映射里哪些页真的驻留在物理内存；
- 驻留页里哪些是共享、哪些是私有、哪些只是最近热过；
- 用户态分配器还握着多少可复用空间；
- 内核回收、cgroup/rlimit 和调度边界又把行为改成了什么样。

所以本篇最重要的顿悟是：**RSS 只是症状，不是结论。真正成熟的排障视角，必须把 `/proc/PID/maps` 的虚拟分区图、`smaps` 的驻留/共享信息、`malloc_info` 的分配器视角、`mlock`/`madvise` 的驻留策略、以及 nice/affinity/rlimit/cgroup 这类运行边界一起对齐。** 证据位应回到 `/proc/PID/maps`/`smaps`/`smaps_rollup`、`mm/mmap.c`、`madvise`/`mlock` 路径、glibc 分配器统计接口以及 rlimit/cgroup 暴露接口：它们共同支撑“多本账要对齐”的排障方法，而不是某个单独工具就能给出终局答案。

先把总图记住：

```text
虚拟地址空间：
  /proc/PID/maps 告诉你“房间怎么分”

物理驻留与共享：
  smaps/RSS/PSS/USS 告诉你“哪些房间现在真有家具、家具是谁共用”

分配器视角：
  malloc_info/mallinfo 只告诉你“仓库管理员手里还留着什么”

系统资源边界：
  mlock/rlimit/cgroup/affinity/nice 决定“你能锁多少、占多少、在哪些 CPU 跑、和谁争资源”

真正排障：
  不是信一个数字
  而是让这些账本互相对得上
```

这一篇最重要的一句话是：**内存问题之所以难，不是因为工具不够多，而是因为你常常在拿“虚拟映射账本”的数字，去回答“物理驻留”“分配器保留”甚至“调度竞争”的问题。**

## 一、如果把 `/proc/PID/maps` 当成“进程已经吃掉的内存清单”，你就会从第一步开始把虚拟地址、页表、缺页、共享页和实际驻留混成一锅，随后所有 RSS 结论都会越看越乱

### 1. 最朴素的错误世界：`cat /proc/PID/maps` 里看到一大段地址，就说明进程已经占用了同样大的物理内存

这是最常见、也最致命的入门误解。maps 每一行看起来都像一块实打实的内存区域：地址范围、权限、偏移、文件、匿名映射、`[heap]`、`[stack]`、共享库，看上去像极了“进程已经拥有的全部内存清单”。于是初学者自然会脑补：总面积差不多就是它已经吃下去的内存。

问题在于，maps 描述的首先是**虚拟地址空间映射关系**，不是“这些页此刻都已经变成独享驻留物理页”。一个映射存在，可能只是说明：

- 这段地址范围被保留了；
- 未来访问它时知道该按什么权限、从哪个文件或匿名来源建立页；
- 若是文件映射，将来缺页时知道到哪儿取内容；
- 若是匿名映射，将来缺页时知道怎么分配零页或私有页。

这和“当前已经驻留多少物理页”是两码事。你要是从第一步就把 maps 面积等同物理占用，后面再去看 RSS、PSS、page fault、COW、共享库时，整个心智模型都会拧巴。

### 2. maps 真正给你的，是“房子怎么分区、每个房间名义上做什么”的平面图

把 maps 看成平面图就顺了。它至少告诉你：

- 哪些范围是主程序的可执行代码段；
- 哪些范围是可写数据段；
- 哪一块被标成 `[heap]`；
- 哪些是共享库或文件映射；
- 哪些是匿名映射，可能来自大块分配、线程栈、JIT、TLS、guard page 等；
- 哪些是特殊内核辅助映射，如 `[vdso]`、`[vvar]`；
- 哪些线程栈或扩展区域在地址空间里各自占了位置。

这个信息极其重要，因为它回答的是：**进程的虚拟世界是怎么搭起来的。** 你若不知道这张图，就无法解释“为什么 malloc 大块不一定都进 `[heap]`”“为什么多线程程序 maps 里会多出很多匿名区”“为什么共享库映射面积很大但未必都算成你的独享压力”。

### 3. 为什么 `.text`、`.data`、`[heap]`、匿名映射、共享库和 `[stack]` 要分开看

因为它们代表的来源、缺页方式、共享关系和回收可能性都不同。

- `.text` 更偏文件后备、可执行、常常可共享；
- `.data`/`.bss` 更偏可写全局状态，私有修改后才成为你的责任；
- `[heap]` 常和传统 `brk` 扩展区关联，但绝不是所有动态内存唯一去处；
- 匿名映射可能承载大块对象、线程栈、JIT 区、守护页和各种运行时私有区域；
- 共享库往往看起来面积不小，但大量页可能在多个进程之间共享；
- `[stack]` 及其他线程栈区提示你：线程越多，地址空间与潜在驻留压力也会跟着变化。

所以看 maps 时最该避免的，就是把它当成一桶“通通叫内存”的东西。系统编程里，来源不同，账本就不同。

### 4. 为什么 `[heap]` 不是“所有 malloc 都在这里”的同义词

这是从第五篇必须回扣的一条线。既然 `malloc` 是用户态分配器接口，而分配器可能混用不同后端路径，那么你就不能把 `[heap]` 当成“malloc 世界的全部疆土”。很多场景下：

- 小中等对象可能更多停留在传统堆扩展区域；
- 大块请求可能直接体现在匿名 `mmap` 区；
- 线程栈、TLS 相关布局和运行时内部映射也会在 maps 中占地；
- 库、自定义分配器、JIT 或共享内存策略还可能引入额外匿名区。

于是一个非常重要的排障结论就出来了：**看到 `[heap]` 没明显增长，不代表 malloc 就没膨胀；看到匿名映射大，也不自动等于“内核泄漏”。** 你必须继续往下看 `smaps`、分配器统计和 workload 行为。

### 5. 为什么同一段 maps 看起来很大，却不代表当下工作集也一样大

因为虚拟映射只定义了“这里可以被怎样使用”，不定义“你此刻真正在用多少”。一个 1GB 的文件映射，一开始可能只是占了地址范围；真正访问了多少页、这些页是否常驻、是否被回收、是否被多个进程共享，都要结合缺页历史、回收行为和 smaps 类信息看。

这正是上一卷内存与 `mmap` 主题一直强调的那条线：VMA、页表、物理页、page cache、COW、回收，层层不是一个概念。把 maps 当驻留结果，就是把第一层平面图误当成整栋楼当前入住率。

### 6. 本节最该记住的结论：`/proc/PID/maps` 是虚拟地址空间的分区图，不是物理内存账单；它回答“有哪些房间、这些房间做什么”，不回答“房间里现在有多少家具、是谁的家具”

一句最短人话是：**maps 像房产证，不像仓库盘点单；房产证面积大，不代表屋里此刻真堆了同样多的货。**

## 二、`mmap`、`mlock`、`munmap`、`madvise` 这些接口最容易被误解成“我已经直接控制了物理内存”，可它们真正控制和影响的，是虚拟映射、驻留倾向、回收边界和访问策略，而不是对内核下命令说“给我无限常驻、按我想的方式预读/释放”

### 1. 最朴素的错误世界：`mmap(1GB)` 就立刻吃掉 1GB 物理内存，`mlock` 之后这 1GB 永远钉死，`madvise` 一下内核就会完全照做

如果这样理解，内存排障会变成一连串失望：

- 明明 `mmap` 了很多，为何 RSS 一开始没涨那么多；
- 明明 `mlock` 了，为何还会失败、而且不是只看“系统空闲内存够不够”这么简单；
- 明明 `madvise` 过了，为何回收、预读或冷热行为并不总按预期发生；
- 明明 `munmap` 了，为何观察到的进程整体压力还没按直觉立刻归零。

根源就在于：这些接口站在的层次不是“你直接指挥物理页”，而是“你在和内核协商地址空间、驻留和回收策略”。

### 2. `mmap` 建立的首先是 VMA 与缺页规则，不是一次性物理搬运

这和第二篇建立的 `mmap` 心智模型完全闭环。映射动作通常先确定：

- 这段虚拟地址属于你了；
- 它是匿名还是文件后备；
- 它的读写执行权限如何；
- 将来触碰它时该如何建立页。

也就是说，`mmap` 更像划定一块地并写明使用规则，而不是立刻把每平方米的家具都搬进去。真正的物理页消耗常常要等你首次访问、写入、触发 page fault 之后才兑现。因此 `mmap 1GB` 与“此刻 RSS 多了 1GB”之间根本没有简单等号。

### 3. `mlock` 为什么不是“只要我想，这批页就永远不能动”

因为锁页是稀缺能力，不是无限特权。`mlock()` 请求的是：尽量让这批页保持驻留，不被普通换出路径拿去腾挪。它会受到：

- `RLIMIT_MEMLOCK`；
- 进程权限；
- 当前系统可用资源；
- 整个系统/容器允许锁定页的边界；
- 页是否真的已经建立、范围是否符合要求。

这说明 `mlock` 的语义更接近“申请把一批家具固定在房间里，别轻易搬走”，而不是“我有权无上限占住整栋楼的仓储空间”。一旦你明白这是受限资源，`mlock` 失败就不该只盯“free 看起来还有多少”，而要联想到 rlimit、权限、容器和整体资源制度。

### 4. `madvise` 为什么最适合作为“策略提示”理解，而不是“命令式 API”

`madvise` 常常让人误会成“我告诉内核后，它就按我的业务意图执行了”。实际上，advice 这个名字本身已经提醒你：这更像建议与提示。你告诉内核：

- 这一段可能是顺序访问还是随机访问；
- 某些页近期可能不再重要；
- 某些范围接下来可能会被频繁触碰；
- 某些匿名页也许值得释放回初始状态。

但这些提示能带来什么实际效果，还要看内核版本、当前压力、页状态、文件系统与回收策略。也就是说，`madvise` 能改善内核判断，却不等于你已经拿到了 deterministic 的强保证。把它当作调优与回收协商接口，比把它当魔法按钮更接近现实。

### 5. `munmap` 为什么回答的是“地址空间关系结束”，而不等于“所有相关成本都瞬间消失到零”

解除映射的核心意义，是把这段虚拟地址关系切断。对用户态来说，之后再访问这段地址会出错；对内核来说，相应 VMA 关系需要被拆掉，关联驻留页和引用关系按规则释放或回收。

但你仍然要克制别把它理解成“总账单立刻归零”。例如：

- 其他共享者若仍在使用文件页，page cache 不会因你一个进程 `munmap` 而整体蒸发；
- 某些物理页是否马上回收、如何回收，仍受引用与回收路径影响；
- 更广义的进程 RSS、分配器保留、其他 VMA 增长，并不会因这一处 `munmap` 自动全都变好看。

### 6. 本节最该记住的结论：`mmap`/`mlock`/`madvise`/`munmap` 操作的是映射关系、驻留倾向和回收策略，而不是对物理内存下绝对命令；排障时必须把“虚拟建立”“物理驻留”“回收结果”拆开看

一句最短人话是：**`mmap` 是租房，`mlock` 是申请别搬家具，`madvise` 是给物业提建议，`munmap` 是退租；这四件事都不等于你直接改写整栋楼的物理容量。**

## 三、malloc 统计接口最容易让人陷入“既然有数字，那就有真相”的幻觉，可 `malloc_info`、`mallinfo` 之类看到的，只是分配器这一个仓库的库存，不是整个进程园区的总占用账单

### 1. 最朴素的错误世界：只要打印出 `malloc_info` 或 `mallinfo`，我就知道进程为什么占这么多内存了

这当然比什么都不看强，但依旧远远不够。因为这些接口回答的是：**glibc 这一层分配器自己怎么看手里的 arena、bin、空闲块和保留空间。** 它并不自动覆盖：

- 所有文件映射；
- 共享库映射；
- 线程栈；
- 其他运行时、JIT 或自定义分配器；
- 页缓存关联效应；
- 某些不走它这条路径的大对象布局。

所以它给你的是局部真相，不是终局真相。把局部真相当全貌，是内存排障第二常见陷阱。

### 2. 为什么 malloc 统计和 RSS 看起来常常“互相打脸”

因为它们站的账本层次不同。RSS 更关心：当前有多少页驻留在物理内存里，并记到这个进程头上。malloc 统计更关心：**分配器内部有哪些块正在用、哪些块空闲但仍被保留、哪些 arena 还握着地盘。**

于是下面这些组合都完全可能出现：

- RSS 很高，但 malloc 统计并不夸张，因为高的部分来自线程栈、文件映射、共享库、JIT 或其他匿名区；
- malloc 统计显示分配器手里有不少空闲保留块，但 RSS 下降不明显，因为这些页仍驻留、其他匿名映射也很重；
- RSS 看起来下来了，但业务层依旧泄漏对象，只是部分别的压力恰好减轻，把假象盖住了。

也就是说，malloc 统计和 RSS 不一致，不是工具坏了，而是它们根本不在回答同一个问题。

### 3. 为什么 `malloc_trim` 之类动作更适合做“验证实验”，而不是做单步定性结论

测试环境里调用 `malloc_trim()`，看到 RSS 降了一截，很多人立刻得出结论：“看，果然不是泄漏，只是分配器缓存。”

这结论常常过早。更稳的理解应该是：你刚刚验证了**至少有一部分内存是可被分配器整理并归还的**。这非常有价值，但它并不能独自排除：

- 真实对象泄漏仍同时存在；
- arena 空闲块与真正泄漏对象混在一起；
- workload 阶段性结束带来自然回落；
- 某些大块恰好被释放回 mmap 路径。

所以 trim 更像一个对账实验：它帮你分辨“保留可归还的部分”有多少，而不是直接替你宣判“这不是泄漏”。

### 4. 为什么线上排障里“工具覆盖范围 + 侵入性”同样要纳入判断

这一点特别容易被忽略。Valgrind、heap profiler、eBPF 分配跟踪、应用埋点、`malloc_info`、`smaps`，每种工具带来的：

- 观察粒度；
- 运行时开销；
- 覆盖范围；
- 是否需要重启或重编译；
- 是否会改变分配时序与竞争；

都不一样。于是成熟排障从来不是“先上最猛的工具”，而是先问：**我现在是线上高压进程，还是可复现实验环境；我要回答的是‘对象真泄漏了吗’，还是‘RSS 为什么不回落’，还是‘哪类映射正在变大’。**

这也是为什么完备性问题里会强调：凌晨三点先看 `smem`、`/proc/PID/maps`、`smaps` 这类低扰动证据，而不是一上来就 attach 重武器把现场打乱。

### 5. 本节最该记住的结论：`malloc_info`、`mallinfo`、`malloc_trim` 这类工具只描述分配器看到的那部分现实；它们对定位“保留空间、arena 空闲块、可归还部分”很有价值，但不能单独替代整个进程地址空间与 RSS 视角

一句最短人话是：**分配器库存表能告诉你仓库里堆了什么，但不能替你盘点整座园区的所有仓房、宿舍和停车场。**

## 四、伪泄漏排查真正困难的地方，不是“工具太少”，而是同一个 RSS 上升现象可能同时包含真实泄漏、分配器保留、工作集变热、共享页变化、cgroup 压力和回收时机错位；只看一条曲线，几乎注定会误判

### 1. 最朴素的错误世界：RSS 曲线向上，就是泄漏；负载结束后没掉回原点，就是更铁的泄漏证据

这是最常见的工程速断，但恰恰因为太顺嘴，所以最危险。RSS 上升可能意味着：

- 真实对象没释放；
- 分配器留着空闲块等下次复用；
- 大量匿名映射或线程栈新建后还没回落；
- 文件页/共享页关系变化让驻留统计看起来更重；
- 回收时机还没到，工作集刚被热起来；
- 容器/cgroup 压力把你推到某种更差局面；
- 你的负载模式从冷启动进入长期高水位阶段，本来就不该期待回到原点。

所以“曲线在涨”只能说明表象在变，不能说明因果已经清楚。

### 2. 为什么真正可靠的排障必须同时看 RSS、PSS/USS、maps/smaps、分配器统计和对象证据

因为每种证据都只剖开一层皮。

- RSS 告诉你当前进程头上的驻留重量；
- PSS/USS 更能帮你区分共享页摊薄后和纯私有负担；
- maps/smaps 告诉你究竟是哪类 VMA 在长；
- `malloc_info`/`mallinfo` 告诉你分配器自己保留了多少、空闲块长什么样；
- profiler、eBPF、Valgrind、应用埋点才更接近“对象有没有真的在持续留存”。

只有把这些证据叠起来，你才有机会回答：这是对象泄漏，还是分配器保留，还是共享/匿名映射结构在变，还是系统层压力与调度把表象放大了。

### 3. 为什么“同 workload 复测 + 低扰动干预”比一次性神判更稳

内存问题非常吃工作负载形状。一次偶发高峰、一次缓存预热、一次线程池扩容、一次日志轮转，都可能改变短期观察值。于是成熟排障更像做实验：

- 固定 workload 或尽量重放相似流量；
- 比较冷启动、热运行、负载回落后的多时间点证据；
- 做最小干预，例如只读 `/proc`、轻量采样、在测试环境跑 trim/heap profiler；
- 看现象能否稳定复现，而不是抓住一次截图就下判词。

这和做并发 bug 诊断很像：你不是在追求一句“我感觉像”，而是在构造证据链。

### 4. 为什么“开了阀门后水位下降”仍然不能单独证明此前没有漏水

这是大纲里的比喻，我建议直接记住。比如 trim、回收、负载下降后 RSS 下降了，这很好，说明有一部分是可排、可回落的。但它不能单独排除另一个事实：同时也许还有真实泄漏在缓慢叠加，只是之前被大块缓存/工作集噪音盖住了。

因此“能降”与“没有泄漏”之间没有必然推出关系。你仍要问：

- 降的是哪类 VMA；
- 分配器统计和对象跟踪是否同步变化；
- 业务层某类对象计数是否持续攀升；
- 不同流量阶段是否重复出现同样模式。

### 5. 本节最该记住的结论：伪泄漏判断不是在一条 RSS 曲线上做心理测试，而是把虚拟映射、物理驻留、分配器保留和对象生命周期证据叠在一起看；“可回落”不等于“没泄漏”，“未回落”也不自动等于“真泄漏”

一句最短人话是：**水位升高可能是漏水、暂存货、潮汐或排水延迟；不把水箱、仓库、阀门和天气一起看，只盯刻度尺一定会误判。**

## 五、nice、affinity、rlimit 和 cgroup 之所以要放进“内存排障”这篇，不是因为它们都属于内存接口，而是因为现实中的“进程变慢”“锁页失败”“accept 突然报错”“线程像跑不满”常常根本不是单一内存问题，而是资源边界与调度再分配的问题

### 1. 最朴素的错误世界：只要不是 OOM，性能和失败就跟调度/资源上限没关系；内存看起来够，就不该有 `mlock` 或 `EMFILE` 这类错误

这种想法之所以危险，是因为它把“资源够不够”错误地想成了一个全局、单维的问题。可 Linux 里的资源边界本来就是多层的：

- 你总共有多少物理内存，不代表你能锁住多少页；
- 系统还能开文件，不代表你的进程还能继续拿 fd；
- 机器有很多 CPU，不代表你的线程当前有资格在所有 CPU 上跑；
- 你进程自己的 nice/affinity/rlimit、容器 cgroup 和 systemd 配额，都会把“看起来资源很多”变成“对你来说已经没有了”。

这就是为什么很多所谓“内存问题”，最后根本是资源边界与调度视角没对齐。

### 2. `RLIMIT_NOFILE`、`RLIMIT_MEMLOCK`、`RLIMIT_NPROC` 为什么和系统编程主线是同一类问题

第一篇我们已经见过 fd 不等于底层对象本身；第五篇见过 `mlock` 受 rlimit 约束；到这里要把它们收成一条线：rlimit 其实是在给进程划经营额度。

- `RLIMIT_NOFILE` 约束的是你能同时持有多少个 fd；
- `RLIMIT_MEMLOCK` 约束的是你能要求多少锁定页；
- `RLIMIT_NPROC` 之类又把可创建的任务/进程数量拉进来；
- 超限后的失败，常常直接体现在系统调用返回的错误码上。

这意味着当你看到第 1025 个连接 accept 不进来、`mlock` 莫名失败、线程/子进程拉不起来时，第一反应不该是“内核坏了”或“机器明明还有资源”，而是先查：**这是不是对当前进程生效的那本额度账用完了。**

### 3. affinity 和 nice 为什么可能让“单机资源很多”却仍然表现出局部饥饿

假设你把一个多线程服务绑到很少的 CPU 上，或者把关键线程降了优先级，那么从整机看 CPU 也许很空，但对这个进程来说，可竞争资源其实被故意缩窄了。反过来，如果你粗暴抬高优先级或绑核，也可能：

- 抢走原本该给中断、softirq 或别的服务的时间；
- 让某些线程全挤在一个 NUMA 远端访问更差的布局里；
- 表面上“本进程更快”，整体尾延迟却更差。

这说明调度与绑核不是免费午餐，而是重新划分 CPU 竞争格局。把它纳入内存排障篇，是因为很多“变慢、卡顿、抖动、锁页失败后更慢”的现象，本质上都得靠资源格局来解释。

### 4. cgroup 和容器边界为什么会让“在宿主机上看起来很富裕”的资源，到了进程面前 suddenly 变得很贫穷

现代生产环境里，很多进程根本不直接面对整台机器，而是先被关进容器或 cgroup 预算里。于是：

- 宿主机总内存还够，不代表你所在 cgroup 的 memory budget 还够；
- 宿主机 fd 数量还多，不代表服务级 unit 的限制还多；
- 宿主机 CPU 很闲，不代表你的 cpuset 或 quota 没把你关小黑屋。

所以排障时必须问清“我是在哪个资源笼子里看这些数字”。否则很多图表会同时为真，却在你脑子里彼此矛盾。

### 5. 本节最该记住的结论：进程的实际可用资源，不由“整机还有多少”单独决定，而由 rlimit、affinity、nice、cgroup、systemd/容器约束共同决定；很多看似内存或性能问题的症状，实际是资源边界和调度再分配问题

一句最短人话是：**整座商场还有空位，不代表你这家店还有仓库额度、员工通行证和可用电梯。**

## 六、把本篇收成一张图：maps 负责告诉你“地址空间怎么分”，smaps/RSS/PSS 负责告诉你“哪些页真驻留”，malloc 统计告诉你“分配器自己握着什么”，而 rlimit/cgroup/调度则决定“这些账在现实里还能怎么继续演化”

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：为什么 RSS 变大时不能立刻说泄漏，为什么 `mlock` 失败时不能只看 free，为什么线程跑不动时也许该查 affinity/rlimit，为什么 `/proc/PID/maps` 看起来大不等于真的已经吃掉那么多物理内存。现在答案已经完整闭环了。

首先，`/proc/PID/maps` 描述的是虚拟地址空间的分区图：代码段、数据段、`[heap]`、匿名映射、共享库、线程栈和特殊内核映射，各自在地址空间里占位，但这不等于它们都已经转化为当前独享的驻留物理页。真正的驻留与共享关系，要继续去 `smaps`、RSS/PSS/USS 这层看。其次，`mmap`/`mlock`/`madvise`/`munmap` 站的是映射建立、驻留倾向和回收策略层，不是对物理内存发绝对命令。再往下一层，`malloc_info`、`mallinfo` 和 trim 一类工具只能告诉你分配器这一个仓库的保留、空闲和可归还部分，不能替代整个进程园区的总账。也正因为如此，判断“真泄漏还是伪泄漏”必须把对象证据、分配器统计、maps/smaps 和工作负载实验叠起来看，而不能拿一条 RSS 曲线做神判。

最后，现实中的排障永远不只发生在“内存”这个词里。`RLIMIT_NOFILE`、`RLIMIT_MEMLOCK`、`nice`、affinity、cgroup 和 systemd/容器预算共同决定了你这个进程能拿多少 fd、锁多少页、在哪些 CPU 上跑、被谁挤压。很多看起来像“内存还够却失败”“机器很闲却很慢”的怪现象，真正的答案都藏在这些资源边界里。

把这一切压成最短总图，就是：

```text
地址空间：
  maps 看分区

驻留与共享：
  smaps/RSS/PSS/USS 看物理现实

分配器：
  malloc_info/mallinfo 看 arena/空闲块/保留空间

泄漏判断：
  对齐对象证据 + 分配器视角 + VMA 增长 + workload 实验

资源边界：
  rlimit/cgroup/nice/affinity 决定进程到底能拿多少资源、在哪儿跑
```

所以本篇最该记住的一句话是：**内存排障不是盯着一个 RSS 数字猜故事，而是把虚拟映射、驻留页、分配器保留、系统回收和资源边界这些账本一页一页对起来。** 一旦这些账本能对齐，很多“看起来像泄漏”的恐慌会降下来，很多“为什么明明资源够还失败”的谜团也会自己开口。

## 七、几个最容易说错的地方

### `/proc/PID/maps` 的总面积，是不是就等于进程当前占用的物理内存？

不是。maps 描述虚拟映射关系，不直接等于当前驻留物理页总量。

### `[heap]` 变大，才说明 malloc 在增长；匿名映射变大就和 malloc 无关？

不能这样分。部分动态分配会落在 `[heap]`，部分也可能体现为匿名映射或其他区域。

### `mmap(1GB)` 后 RSS 没立刻涨到 1GB，是不是说明映射没成功？

不是。映射建立和物理驻留兑现是不同阶段，很多页要等首次访问后才真正建立。

### `mlock` 失败时，只要系统还有空闲内存，就一定是程序写错了？

不是。它还受权限、`RLIMIT_MEMLOCK`、容器/cgroup 和锁页总量等边界影响。

### `malloc_info` 或 `mallinfo` 打出来正常，就能排除内存问题？

不能。它们只覆盖分配器看到的那部分现实，不能替代整个地址空间与驻留视角。

### trim 之后 RSS 降了，是不是就能证明此前绝对不是泄漏？

不能单独这样下结论。它只能说明至少有一部分可回收保留空间被释放了。

### 整机 CPU 和内存都不高，进程就不该变慢或失败？

不是。affinity、nice、rlimit、cgroup 和容器预算都可能让单个进程先碰到自己的局部天花板。

## 收束：看懂进程地址空间与内存排障之后，你才会真正明白系统程序里的“内存问题”很少只是 `malloc/free` 两个函数的对错，而是多层账本同时在说话

回到开头那个问题：进程 RSS 上升、CPU 变慢、`mlock` 失败、线程跑不动时，到底怎么确认是地址空间、分配器、cgroup 还是调度问题？现在答案已经完整闭环了。先用 `/proc/PID/maps` 搭出虚拟地址空间平面图，再用 `smaps`、RSS/PSS/USS 看哪些页真驻留、哪些是共享或私有；再把 `malloc_info`、`mallinfo`、trim 和对象级证据接进来，区分分配器保留、工作集变化和真实泄漏；最后再检查 `RLIMIT_NOFILE`、`RLIMIT_MEMLOCK`、affinity、nice、cgroup 和容器预算，把“你这个进程到底有多少资源资格”这本账也补齐。

也正因为如此，系统编程里最糟糕的排障习惯之一，就是对着一个大数字想象故事：RSS 大了就说泄漏、free 了不掉就说内核不还、机器总体空闲就说进程不该慢。真正稳的做法是反过来：先分清这是哪一本账上的异常，再决定用哪类工具和实验去补证据链。

这就是为什么说：**内存排障的成熟度，不体现在你会不会背几个工具名，而体现在你能不能看见“虚拟地址、物理驻留、分配器保留、系统回收、资源额度”这几层现实根本不是一张表。** 只要这几层拆清了，下一步去理解多核共享内存下 cache line 怎样保持一致、atomic 为什么能在没有 mutex 的情况下仍建立顺序保证，就会自然得多。

## 八、误解清单、证据清单与边界清单

### 误解清单

- `/proc/PID/maps` 的总面积不等于当前物理驻留；它首先描述的是虚拟地址空间布局。
- `[heap]` 不是 malloc 世界的全部疆土；匿名映射、线程栈、共享库和其他 runtime 区域都可能参与内存表象。
- `mmap`/`mlock`/`madvise`/`munmap` 操作的不是“绝对物理命令”，而是映射关系、驻留倾向和回收协商。
- `malloc_info`/`mallinfo` 只能看见分配器手里的仓库，不等于整进程 RSS/PSS/USS 总账。
- RSS 上涨不是泄漏的直接同义词；分配器保留、工作集变热、共享页变化和资源边界都可能制造同样表象。

### 证据清单

- 地址空间与 VMA：`/proc/PID/maps`、`mm/mmap.c` 与缺页路径，支撑“先看分区图，再看驻留”的判断。
- 驻留与共享：`smaps`/`smaps_rollup`、RSS/PSS/USS 与匿名/文件页统计，支撑“物理现实和虚拟布局是两本账”。
- 驻留策略：`mlock`/`munlock`、`madvise`、回收与 trim 路径，支撑“锁页/提示/退租都不是绝对命令”。
- 分配器视角：glibc `malloc_info`、`mallinfo`、arena/tcache/trim 路径，支撑“分配器保留与 RSS 观感可能不一致”。
- 资源边界：rlimit、cgroup、affinity、nice 与容器暴露接口，支撑“进程实际可用资源不由整机空闲单独决定”。

### 边界清单

- 本文讨论的是 Linux 进程地址空间与排障的稳定心智模型，不把某一版 `/proc` 输出、glibc 统计字段或容器监控格式写成普适契约。
- RSS/PSS/USS、maps/smaps 与分配器统计回答的问题层次不同，不能用某一个数字替代其他账本。
- trim 成功、RSS 回落或 `malloc_info` 看起来正常，都只能构成局部证据，不能单独排除真实对象泄漏。
- `mlock`、`EMFILE`、性能抖动或 OOM kill 经常和 rlimit/cgroup/affinity/nice 一起作用，不能只按“内存够不够”做单变量解释。
- 后续进入 atomic/lock-free 时，重点会从“地址空间和驻留账本”推进到“同一块共享内存为何仍可能出现乱序与可见性问题”。
