## 现在真正该问的，不再是“线程之间怎样共享状态”，而是“如果一个异步事件可以在任何时刻打断任何线程，你凭什么还敢在 handler 里 `printf`、`malloc`、加锁，甚至顺手做完整清理”

上一章已经把一个非常重要、但又非常容易被偷换的概念拆开了：thread-safe、reentrant、async-signal-safe 不是同一回事。你已经知道：

- 一个函数可以线程安全，却仍然不适合在信号处理器里调用；
- TLS 能给每线程一份私有状态，但不能替代共享协议；
- 条件变量、mutex 和 join/detach 解决的是正常线程世界里的同步与生命周期问题；
- 1:1 线程模型让多个执行流真正并行，也意味着“任意线程在任意点被打断”这件事更真实。

到这里，系统编程会突然变得非常不讲情面。因为信号不是你自己排进任务队列的一段工作，它可能在：

- 某个线程正持有 `malloc` 内部锁时到来；
- 某个线程正卡在 stdio 缓冲刷新过程中到来；
- 某个线程正在持有应用自己的 mutex 时到来；
- 你根本没来得及挑好“一个合适的处理线程”时到来。

与此同时，服务程序又真的必须面对这些异步现实：

- 收到 `SIGTERM` 该优雅退出；
- 收到 `SIGHUP` 该考虑重载配置；
- 子进程退出要处理 `SIGCHLD`；
- 周期任务、超时控制、重试窗口需要定时器；
- 高频分配释放背后，`malloc` 会不会成为锁争用、碎片和 RSS 膨胀来源。

所以本篇最重要的顿悟是：**现代 Linux 程序之所以喜欢把信号“同步化”、把定时器“fd 化”，不是因为这更时髦，而是因为异步 handler 上下文太危险；与此同时，`malloc` 也不是一个“向内核要块内存”的薄壳，而是一整层带缓存、锁、arena 和地址空间策略的用户态运行时。** 证据位应分别回到 `kernel/signal.c`、线程 signal mask 与递送路径、`signalfd`/`timerfd` 实现路径，以及 glibc `malloc`/arena/tcache 与 `brk`/`mmap` 后端：它们支撑“同步化处理异步事件”和“分配器先在用户态周转”的判断，但具体默认值和策略会随内核/libc 版本变化。

先把总图记住：

```text
异步信号：
  先有 disposition
  再有 mask/pending/递送
  handler 上下文极度受限

现代工程化做法：
  pthread_sigmask 阻塞
  sigwait/signalfd 在普通线程里消费
  让主循环统一处理复杂逻辑

时间事件：
  timerfd 把“到点了”变成可读 fd
  epoll 可统一 socket/pipe/signal/timer

内存分配：
  malloc 先走用户态分配器
  必要时才向内核扩展区域
  多线程通过 arena/cache 降低竞争
  代价是碎片、保留内存和观察复杂度上升
```

这一篇最重要的一句话是：**异步信号的危险在于它会不打招呼地重入你的调用链，`malloc` 的复杂在于它把很多看不见的锁、缓存和地址空间行为藏在“只是一句 `malloc(size)`”背后；两者都要求你先想边界，再想 API。**

## 一、如果把信号当成“内核帮我回调一个函数”，你就会天然低估两件事：它不是按你的业务时机到来，也不是在安全、整洁、可加锁的普通线程上下文里到来

### 1. 最朴素的错误世界：收到 `SIGTERM` 时，内核像线程池一样帮我调一下 handler，我就在里面把日志打了、锁拿了、内存清了、状态全收尾

这个想法对初学者极有诱惑力。信号看起来很像“系统层面的事件回调”：出了事、收到了，就执行一段你注册的函数。既然是函数，里面当然可以干你平时在函数里干的一切。

恰恰这里最危险。信号处理器不是运行在某个你精心安排好的 worker 线程里，而是可能在任意线程、任意指令点突然插进来。它不会先问你：

- 当前线程是不是正持有某把锁；
- 当前库函数是不是处于半执行状态；
- 当前 stdio 缓冲是不是正在刷新；
- 当前分配器是不是正在修改 arena；
- 当前这次调用链是不是允许被打断后再重入复杂逻辑。

所以把信号看成“内核回调了一个普通函数”会让你天然过度自信，而真实语义更接近：**系统在最不讲礼貌的时刻，强行往你调用栈里塞了一小段极受限制的应急逻辑。**

### 2. sigaction 真正先定义的，不是“代码怎么跑”，而是“这个信号在这个进程里默认该被怎么对待”

信号世界第一层要建立的，不是 handler 代码，而是 disposition，也就是这个信号的处理动作语义。某个信号到来时，进程级上通常会处在下面几类选择之一：

- 使用默认动作；
- 直接忽略；
- 进入用户自定义 handler；
- 在需要时携带更多信息进入 `SA_SIGINFO` 风格处理。

这说明信号不是“哪个线程里随便写段逻辑就行”的本地细节，而是进程对外界异步事件的一种全局态度。你先决定要不要接、接了用哪种方式接，再谈具体线程里如何消化它。

### 3. signal mask 为什么再次说明“阻塞”和“忽略”不是一回事

很多人一看到 `SIG_BLOCK` 就本能理解成“这信号先别管了，等于不要了”。这会直接写错程序。

阻塞只是说：**当前线程现在不接这个信号。** 它不是把这个信号的语义抹掉。信号仍可能进入 pending 状态，等你未来解除阻塞后再递送。忽略才更接近“来了我就当没这回事”。

这个差别对工程实践极其关键。因为现代服务经常故意把某些信号先统一阻塞住，不让它们随机打断工作线程，然后交给专门线程用 `sigwait` 或 `signalfd` 在正常上下文里同步消费。要是把阻塞误会成忽略，你就解释不通为什么解除阻塞后信号还会来，也解释不通为什么值班线程能把那批待处理通知领走。

### 4. 标准信号与实时信号为什么又把“异步事件”分成了两种不同账本

这里只需要建立最小闭环。标准信号更像“某类事发生过”的提醒，它们常常不强调逐条完整排队；实时信号则更像带顺序、带更多排队语义、可能还能附带 payload 的通知。

这意味着你设计系统时不能偷懒地把所有信号都当成“可靠消息队列”。某些信号更适合表达“该停了”“孩子退出了”“终端断了”这类状态提醒，而不是每一件小事都希望内核替你完整排成消息流。信号首先是异步控制与通知机制，不是通用消息总线。

### 5. `SA_RESTART` 一类标志为什么再次提醒你：信号不是只影响 handler 那几行代码，而会把系统调用边界也卷进来

一旦信号到来，被打断的可能不只是用户态业务逻辑，还可能是一个阻塞中的系统调用。于是应用必须面对：

- 某些调用会被中断返回，要求你检查 `EINTR`；
- 某些调用在特定语义下可能被自动重启；
- 这两种行为差别会影响你的超时、重试和主循环设计。

所以信号的影响范围不止是“有没有一个 handler 跑起来”，而是整个调用栈与系统调用边界都可能被改变节奏。你如果只在 handler 里想问题，会低估它对全局控制流的冲击。

### 6. 本节最该记住的结论：信号不是普通回调；`sigaction` 先定义进程级处理态度，mask 再决定当前线程暂时接不接；阻塞是延后递送，不是忽略，异步打断还会把系统调用边界一并卷进来

一句最短人话是：**信号不是别人礼貌地敲门后等你开会讨论，它更像在你正忙时塞来一张必须按制度处理的紧急通知。**

## 二、线程里的信号最容易让人误解成“发给进程就等于所有线程都收到”，可真正关键的恰好是反过来：disposition 常是进程共享的，mask 却是每线程私有的，递送最终必须落到某个满足条件的线程身上

### 1. 最朴素的错误世界：`kill(pid, SIGTERM)` 发给的是进程，所以进程里每个线程都知道了；或者至少哪个线程处理无所谓

这两种想法都很糟糕。前者会误以为信号像广播一样在所有线程里同时展开；后者则会忽略“任意线程被异步打断”到底有多危险。

真实世界更麻烦也更精确。对同一进程里的线程来说：

- 信号的处理动作配置经常是进程级共享的；
- 但每个线程有自己的 signal mask；
- 一个发给进程的信号，最终并不是“让所有线程一起跑 handler”，而是要找一个满足递送条件、没有把该信号屏蔽掉的线程来承接。

所以线程世界里最危险的问题不只是“信号到了没有”，而是“到底让谁接”。

### 2. 为什么生产服务常让所有工作线程都先屏蔽某些信号，只留一个信号线程值班

因为这样才能把不可控的异步打断，尽量改造成可控的同步等待。典型思路是：

- 进程启动后，先在创建工作线程前统一规划 signal mask；
- 让普通 worker 线程都屏蔽掉 `SIGTERM`、`SIGHUP` 之类控制信号；
- 单独拉一个值班线程，用 `sigwait()` 或者 `signalfd` 等方式接这些信号；
- 值班线程收到后，再以普通线程语义通知主循环、设置停止标志、触发优雅退出或重载逻辑。

这样做的好处不是“少写 handler”，而是避免任何一个正在持锁、正在分配内存、正在写日志的业务线程，被异步地硬插入控制逻辑。也就是把“任意线程被信号砸中”的随机性，收束成“只有专门的人在固定窗口领通知”。

### 3. `kill`、`pthread_kill` 和更细粒度线程定向接口，为什么解决的是三个层次不同的问题

`kill(pid, sig)` 更像对整个进程这家公司发总通知；谁来处理，要看线程屏蔽关系与递送条件。

`pthread_kill(thread, sig)` 则更像指定某个员工本人收件。它不是改变 disposition，而是在现有处理语义下，明确把这次通知瞄准某个线程。

更底层、更精细的线程定向接口又进一步说明：线程不是“抽象得看不见”的东西，信号系统最终必须在内核层为某个具体可调度实体落地。也正因为如此，线程信号设计从来不是纯语法问题，而是“控制信号到底是否该随机进入业务线程”的架构问题。

### 4. 为什么“所有线程屏蔽 + 专用信号线程同步消费”其实和 epoll/事件循环哲学完全同构

第二篇已经建立了一个很强的模式：把原本分散、易丢节奏、容易轮询或乱打断的事情，变成一个统一主循环/等待循环里可消费的事件。信号同步化正是这个模式在异步控制事件上的应用。

- inotify 把文件变化变成事件；
- timerfd 把时间到期变成事件；
- signalfd 或 `sigwait` 把信号变成同步可消费事件。

你会发现，系统编程真正成熟的一条暗线就是：**尽量让复杂逻辑回到普通线程上下文里做，而不是让异步边界到处切碎控制流。**

### 5. `SIGCHLD`、`SIGTERM`、`SIGHUP` 这类控制信号为什么尤其适合同步化

因为它们后续往往都要引出复杂动作：

- `SIGCHLD` 之后你要循环 waitpid 回收子进程；
- `SIGTERM` 之后你要停止接收新请求、冲刷状态、关闭监听、等待 worker 收尾；
- `SIGHUP` 之后你可能要重读配置、重新打开日志、热更新部分运行参数。

这些都不是适合在异步 handler 里直接完成的动作。它们需要锁、日志、内存分配、文件 I/O、与别的线程协调，因此最好的归宿就是普通线程上下文。也就是说，这些信号的真正价值常常不是“用 handler 立刻干活”，而是“发一个必须尽快被主控制面处理的控制事件”。

### 6. 本节最该记住的结论：进程里的信号处理动作往往共享，但是否接收由每线程 mask 决定；发给进程的信号最终要落到某个线程，因此工程上常通过统一屏蔽与专用信号线程把异步递送改造成可控的同步消费

一句最短人话是：**公司总邮箱发来通知，不等于所有员工一起冲上去拆信；成熟做法是先定好谁值班、谁别被打扰。**

## 三、async-signal-safe 的真正残酷之处，不是“有几条 API 不能用”，而是它在逼你承认：handler 里几乎不能做任何像样的业务，只能留下最小事实，再把复杂处理搬回正常线程世界

### 1. 最朴素的错误世界：handler 很短就行，里面即使 `printf`、`malloc`、`pthread_mutex_lock` 一下，问题也不大

这类错误最危险的地方，在于它常常不是“每次都炸”，而是“平时好好的，压力一上来、时机一碰巧才死锁”。于是人特别容易自我安慰：我都运行几个月了，说明这样也没事。

可异步信号 bug 的本质正是**时机触发型**。只要某次信号恰好打断在：

- stdio 正持内部锁；
- 分配器正在整理 arena 或持有内部互斥；
- 你的业务线程正在拿着某把 mutex；
- 某个不可重入函数写到一半；

handler 再走进同样或相关路径，程序就可能把自己锁死。它不是“偶尔不幸”，而是模型上没有安全保证，只是你以前没撞中。

### 2. 为什么 `printf` 和 `write` 的差别再次成为系统编程里最值得反复记住的例子

因为这个例子足够反直觉，也足够说明问题。两者都能“输出一段文字”，但：

- `printf` 站在 stdio 层，可能碰到用户态缓冲、格式化、内部状态和锁；
- `write` 更接近内核系统调用边界，在 async-signal-safe 语义上往往才更有可靠位置。

所以区别根本不在“两个函数哪个功能更强”，而在“它们调用路径上藏着多少不能被异步重入的东西”。一旦你理解了这一点，就会自然明白为什么 `malloc`、`free`、`pthread_mutex_lock` 同样不该在 handler 里乱用：危险并不是名字不好听，而是**它们背后都有复杂状态机。**

### 3. 为什么“设置一个 `volatile sig_atomic_t` 标志”虽然朴素，却非常重要

因为它体现了 handler 的正确职责边界：不要在异步上下文里完成整个业务动作，只做最小、最确定、最少依赖共享复杂状态的通知。

例如：

- 把 `stop = 1` 设起来；
- 往事先准备好的 pipe/eventfd 写一个字节；
- 让主循环从 `epoll_wait()` 中被唤醒；
- 在正常线程上下文里再决定如何停服务、flush、join worker、关闭 fd。

这里千万别嫌“只是设个标志太弱”。恰恰是因为 handler 能安全做的事情非常少，这种极简设计才稳。它不是功能不够，而是把“异步事实已发生”与“我接下来怎样优雅收尾”硬切成两段，避免在错误的上下文里贪多。

### 4. signalfd 和 sigwait 为什么是把“极简 handler 原则”推进到工程化终点的典型手段

如果说设置标志位是在承认“handler 里别做复杂事”，那么 `sigwait`/`signalfd` 就更进一步：**干脆让复杂事完全不要发生在 handler 里。**

具体思路是：先把目标信号在线程层面屏蔽住，不让它随机异步打断任何业务线程；然后：

- 要么由专门线程同步 `sigwait`；
- 要么把 signalfd 丢进 epoll，由主循环像处理普通 fd 事件一样处理信号。

这样信号从“异步打断”退化成了“同步可消费事件”，处理它时你回到了：

- 可以拿锁；
- 可以写日志；
- 可以分配内存；
- 可以协调线程和子进程回收；
- 可以统一超时、网络与退出逻辑。

这就是为什么现代 Linux 网络/服务程序对 signalfd 有天然偏好。不是因为老 handler API 过时，而是因为大家越来越清楚：**复杂控制逻辑应该待在普通事件循环里，不该飘在异步悬崖边。**

### 5. 为什么“handler 里只做极小动作”也不代表你可以完全不懂 signal mask 与线程关系

因为如果屏蔽关系没规划好，信号还是会随机落到业务线程里；如果 pipe/signalfd/eventfd 的消费方没设计好，通知还是可能丢节奏；如果你不理解哪些信号会合并、哪些只是状态提醒，也可能在主循环里过度解读“收到了几次”。

也就是说，最小 handler 原则是必要条件，不是全部答案。你仍要把信号看成一个涉及 disposition、mask、递送线程、通知同步化和后续控制面的完整系统。

### 6. 本节最该记住的结论：async-signal-safe 不是“少用几个函数”这么简单，而是在逼你把 handler 缩到只留下最小事实；复杂业务动作应通过标志、pipe、`sigwait` 或 signalfd 回到普通线程上下文完成

一句最短人话是：**火警通道里只负责按铃和疏散，别在出口处开会、搬家具、重装天花板。**

## 四、定时器如果还停留在“闹钟一响就进 handler”这层理解，你就会错过 timerfd 最值钱的设计：把时间到期也变成一个可以和 socket、pipe、signalfd 一起统一消费的普通 fd 事件

### 1. 最朴素的错误世界：超时和周期任务反正就是定时器，定时器反正会发信号，那我在 handler 里做超时处理就行

这在单线程、小脚本或非常简单的工具程序里也许能工作，但一旦进入复杂服务主循环，就会把你重新扔回上一节那个异步悬崖边：

- 定时器到了，handler 异步打断任意线程；
- 你在 handler 里又想碰锁、日志、连接状态、任务队列；
- 网络 I/O、子进程回收、配置热更新和时间事件各自有各自的打断通道；
- 整个控制流被切得稀碎。

所以定时器真正该解决的问题，不只是“什么时候到点”，而是“到点这件事如何接入现有的等待与控制框架”。

### 2. `clock_gettime` 为什么先逼你分清“人类时间”和“经过了多久”

时间事件里最容易混掉的，是 `CLOCK_REALTIME` 和 `CLOCK_MONOTONIC` 这类语义边界。前者更接近墙上时钟、日历与现实世界时间；后者更接近用于测量经过时间的单调计数。

如果你做的是“10 秒后超时”“每 100ms 做一次检查”这种 elapsed-time 逻辑，却把它绑到会受校时跳变影响的人类时间上，程序在 NTP 调整、人工改时钟或系统时间漂移场景下就可能出现奇怪的提前/延后。于是定时器讨论从一开始就不是“哪个 API 顺手”，而是“你想表达的是墙钟时刻，还是经过时长”。

### 3. timerfd 为什么是把“时间到期”翻译成 fd 世界的一次关键统一

第二篇我们已经看到，epoll 的真正价值是统一等待语义，而不是只管网络。timerfd 则把“到点了”也塞进了这套世界：它让定时器过期表现成一个可读 fd。于是主循环可以像处理 socket、pipe、eventfd、inotify、signalfd 一样处理时间事件。

这带来三个直接好处：

- 超时控制不再需要异步 handler 去打断任意线程；
- 所有外部事件都可以在同一 epoll 循环里有序消费；
- 你可以在正常线程上下文里决定“收到超时后该关连接、重试、重载还是打日志”。

这正是“把异步事件同步化”的又一个经典例子。

### 4. 读取 timerfd 里的过期计数，为什么再次说明“事件到了”和“业务补偿如何做”不是一回事

timerfd 被读出的是累计过期次数，而不是“我已经替你把每一次错过的业务动作都补跑了”。这点很重要。假设程序因为调度、负载、stop-the-world 或别的长阻塞，错过了几个周期，timerfd 可以告诉你：这段时间发生了几次过期。

但它不会自动替你逐次补执行业务逻辑。你仍然要自己决定：

- 是只按“至少到点过一次”处理；
- 还是根据过期计数补做若干次推进；
- 还是干脆认为这段时间窗口已废弃，只更新下一次 deadline。

这说明 timerfd 解决的是“通知统一、可观测”，不是“业务语义替你做完”。

### 5. 为什么 timerfd 适合事件循环，却不该被神化成硬实时装置

因为它最终仍受：

- 调度延迟；
- 系统负载；
- 时钟分辨率；
- 线程什么时候真正被唤醒并跑到 `read(timerfd)`；
- 主循环里其他事件是否堵住了它。

所以 timerfd 对普通 Linux 服务程序非常优秀，但它表达的是“把时间事件纳入统一等待框架”，不是“纳秒级确定性执行”。把这层边界讲清，后面设计超时和周期任务时就不会误用它。

### 6. 本节最该记住的结论：timerfd 的真正价值，不是“Linux 又多了一个定时器 API”，而是把时间到期统一翻译成 fd 事件，让时间、网络、信号和管道都能回到同一事件循环里以普通线程语义处理

一句最短人话是：**timerfd 不是又一个闹钟，而是把闹钟接进总值班台。**

## 五、`malloc` 最容易被误解成“内核给我一块内存”的直接接口，可真正的系统编程边界恰好藏在这里：它先是 libc 分配器，再才可能是 `brk`/`mmap` 等内核路径；多线程下它还会引入 arena、缓存、锁竞争、碎片和 RSS 观测错觉

### 1. 最朴素的错误世界：`malloc(size)` 本质上就是一个系统调用，我要多少，内核就切多少给我

这个想法在 API 直觉上很自然，因为 `malloc` 看起来像“给我分配点内存”。可一旦这样理解，很多现象都解释不通：

- 为什么频繁小额 `malloc/free` 不会每次都陷入内核；
- 为什么某些内存明明 `free` 了，RSS 看起来却不立刻掉；
- 为什么多线程高并发下 `_int_malloc` 一类热点会吃 CPU；
- 为什么大块分配和小块分配路径表现差异那么大；
- 为什么“无泄漏”不等于进程地址空间和 RSS 立刻回到初始状态。

### 2. `malloc` 首先是用户态分配器接口，只有在自己兜不住时才去向内核扩展地盘

这才是正确心智模型。对 libc 分配器来说，很多请求会先在用户态已有的空闲块、bin、cache、arena 体系里解决。也就是说，`malloc` 很多时候先做的是：

- 看看现有空闲块能不能复用；
- 看看线程本地或 arena 级缓存里有没有合适对象；
- 只在不足时，才通过更底层机制向内核扩充可管理区域。

这就是为什么 `malloc` 不是 syscall 薄壳。它更像仓库管理员：小件先从现有货架里调货，货架不够才去申请扩仓。于是“分配内存”这件事从第一步开始就可能完全发生在用户态。

### 3. 为什么 `brk`/`sbrk` 与 `mmap` 只是分配器可能使用的后端，不该被你写成死板阈值口诀

很多人喜欢背“多大走 brk，多大走 mmap”之类口诀。这类记忆在某些实现和时期可能大致有参考价值，但如果你把它写成绝对规则，就会误导读者。因为实际选择会受很多因素影响：

- glibc 版本与实现策略；
- 动态阈值调整；
- 当前 arena 状态与历史分配模式；
- 是否已有可复用大块；
- 架构与配置差异。

正确说法应该是：现代分配器可能综合使用多种后端路径来扩展自己可管理的地址空间，`brk`/`mmap` 是常见后端，不同大小请求和历史状态会影响分配器怎么选。**理解边界比背静态阈值更重要。**

### 4. 多线程下为什么不能只靠“一把全局锁保护 malloc”糊过去

如果整个进程所有线程每次分配和释放都串行抢同一把大锁，那么在多核高并发程序里，分配器很快会变成热点。于是现代 libc 分配器会想办法降低这种全局竞争，比如引入：

- 多个 arena；
- 线程局部或近线程缓存；
- 更细粒度的 bin/arena 管理策略。

这些机制的共同目标是：**让不是同一批对象、不是同一线程热点的分配请求，尽量别都排到一条锁队列上。**

但别忘了，优化竞争往往意味着更多局部缓存、更多 arena、更复杂的回收与合并时机。这会换来：

- 内存保留增多；
- 空闲块更难立即集中回收；
- 某个线程释放的块不一定马上转化成另一个线程最容易复用的资源；
- 观测上看起来像“进程越来越胖”，即使逻辑上没有真正泄漏。

### 5. 为什么“free 了但 RSS 不掉”不能立刻等价成“内存泄漏”

因为分配器和内核之间也有账本边界。程序 `free()` 的常见意义，首先是“把这块对象归还给用户态分配器管理体系”，而不是“马上把对应物理页原封不动退回给内核”。是否继续保留给未来复用、是否合并、是否 trim、何时真正归还映射或收缩堆区，都取决于实现、当前工作集和碎片形态。

这也是为什么下一篇要专门讲 `/proc/PID/maps`、伪泄漏和内存排障。很多让人误判成“泄漏”的现象，其实是：

- arena 还留着；
- 空闲块分散；
- tcache 或近线程缓存保留着热点对象；
- 大量内存从业务角度可复用，但从 RSS 角度暂时没缩回去。

### 6. 为什么 `malloc` 会和本篇前半段的信号安全问题重新碰撞

因为分配器内部往往正是那种“平时你看不见，但异步重入时最致命”的复杂状态机。它可能涉及：

- arena 锁；
- 空闲链表/元数据更新；
- 线程缓存；
- 需要时向内核扩展地址空间。

于是“malloc 是线程安全的”只说明在正常线程并发路径下它努力协调了内部状态，不说明它可以在 signal handler 里被异步重入。信号如果打断了某线程中途的分配器路径，handler 再进 `malloc`/`free`，你就可能撞上前半篇反复强调的那条死线。

这也正是为什么本篇把信号、timerfd 和 malloc 放在同一章：它们表面上分属不同 API 家族，底层却都在考你同一个能力——**能不能看见隐藏在“简单调用”后面的上下文边界。**

### 7. 本节最该记住的结论：`malloc` 首先是用户态分配器，不是直接系统调用；多线程优化通过 arena/cache 降低锁竞争，却会把回收、碎片、RSS 和异步安全边界都变得更复杂

一句最短人话是：**`malloc` 表面像领一张纸，背后其实是整座仓库、排队规则和扩仓策略一起在运转。**

## 六、把本篇收成一张图：信号之所以危险，是因为它能在最坏时机插入；timerfd 之所以好用，是因为它把时间也拉回普通事件循环；malloc 之所以难排障，是因为它把用户态缓存、锁和地址空间策略都藏在了一个看似朴素的接口后面

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：服务收到 `SIGTERM` 时为什么不能在 handler 里随手 `printf`、拿锁、分配内存并完成所有清理；为什么现代程序喜欢用 `sigwait`/signalfd；为什么 timerfd 和 epoll 天生投缘；为什么 `malloc` 明明只是申请内存，却总和线程竞争、RSS 和异步安全牵扯在一起。现在答案已经完整闭环了。

首先，信号不是普通回调。`sigaction` 先定义进程级处理态度，signal mask 再决定各线程当前接不接，递送最终又必须落到某个满足条件的线程。因此成熟程序常常把控制信号统一屏蔽，再交给专用线程通过 `sigwait` 或 signalfd 在普通线程上下文里同步消费。这样做不是多此一举，而是为了避开异步 handler 的悬崖。

其次，async-signal-safe 不是“少记几条禁用 API”那么简单，而是要求你承认 handler 里几乎不能做像样的复杂业务。最稳的策略往往只是留下最小事实：设标志、写 pipe、唤醒主循环。后续真正的停止接收、冲刷日志、回收子进程、join worker、释放资源，都应该在普通线程语义里完成。timerfd 又把同样的工程哲学推进到了时间事件：把“到点了”也变成一个可读 fd，让网络、信号、管道和时间统一进入 epoll 主循环，而不是各自用异步打断切碎控制流。

最后，`malloc` 之所以值得放在这一章，是因为它再次暴露了“表面简单、背后复杂”的系统编程真相。`malloc` 首先是 libc 分配器接口，很多请求先在用户态缓存、arena 和空闲块体系中完成，必要时才通过 `brk`/`mmap` 等后端扩展地址空间。多线程优化减少了锁竞争，却也带来更复杂的内存保留、碎片和 RSS 观测问题；而一旦信号在错误时机重入分配器路径，所谓“线程安全”立刻不再能保护你。

把这一切压成最短总图，就是：

```text
信号：
  disposition + mask + pending + 递送线程
  复杂处理尽量同步化

handler：
  只留最小事实
  复杂清理移回普通线程/主循环

timerfd：
  时间到期 → fd 可读事件
  与 epoll/事件循环统一

malloc：
  用户态分配器优先
  必要时 brk/mmap 扩展
  arena/cache 降竞争
  代价是碎片、保留内存和异步边界更难看见
```

所以本篇最该记住的一句话是：**系统编程最容易咬人的地方，常常不是你显式写出来的并发逻辑，而是那些会在任意时刻打断你、或者在库内部悄悄持锁与缓存的运行时边界。** 一旦你学会把信号同步化、把时间事件 fd 化、把 `malloc` 当作用户态分配器而不是 syscall 壳子，很多服务程序的稳定性问题就会清楚得多。

## 七、几个最容易说错的地方

### 阻塞某个信号，是不是就等于忽略它？

不是。阻塞通常意味着暂缓递送，信号仍可能处于 pending 并在未来解除阻塞后被处理。

### 发给进程的信号，是不是所有线程都会一起处理？

不是。处理动作常是进程级共享，但递送最终会落到某个满足条件、未屏蔽该信号的线程。

### signal handler 里只要代码写得短，就可以 `printf`、`malloc`、拿 mutex 吗？

不能这样想。短不等于 async-signal-safe；关键在于调用路径会不会重入复杂内部状态。

### signalfd/timerfd 是不是只是把老 API 换个包装？

不只是。它们最关键的价值是把异步通知和时间到期统一翻译成普通 fd 事件，方便回到 epoll 主循环处理。

### timerfd 过期次数增加，是不是系统已经替我补做了每一次错过的业务动作？

不是。它报告的是累计过期事实，业务上要不要逐次补偿仍由应用决定。

### `malloc(size)` 是不是本质上总会立即触发一次系统调用？

不是。很多分配先在用户态分配器已有缓存、空闲块或 arena 中解决，只有不足时才向内核扩展。

### `free()` 之后 RSS 没掉，是不是就一定泄漏了？

不能直接下结论。可能只是分配器保留、碎片、arena/tcache 缓存或工作集尚未缩回内核。

## 收束：看懂信号、定时器与 malloc 之后，你才会真正明白系统程序最难管的不是“功能流程”，而是那些会在错误时机打断你、并把复杂状态藏在简单接口背后的运行时边界

回到开头那个问题：服务收到 `SIGTERM` 时既要停止接收、刷新数据，又不能在 handler 里乱碰 mutex、`printf`、`malloc`，到底该怎么办？现在答案已经完整闭环了。先用 `sigaction` 和 signal mask 建立正确的信号边界，再通过专用线程、`sigwait` 或 signalfd 把复杂处理搬回普通线程上下文；对时间事件，用 timerfd 把“到点了”也纳入 epoll 循环；对内存分配，把 `malloc` 看成用户态分配器和地址空间后端策略的组合，而不是一个薄薄的内核调用包装。

也正因为如此，系统编程里很多最顽固的生产 bug 往往不是“业务逻辑写错一行”，而是把上下文看错了：把异步 handler 当普通函数，把线程安全误当成信号安全，把 timer 事件散落在各种打断路径里，或者把分配器保留和碎片误判成泄漏。这些问题一旦进入高负载、多线程和长时间运行场景，就会特别咬人。

这就是为什么说：**异步边界管理，才是系统编程成熟度真正露底牌的地方。** 只要你能看见哪些事件必须同步化、哪些动作只能留在普通线程世界、哪些“简单接口”背后其实藏着锁和地址空间策略，后面读 `/proc/PID/maps`、判断伪泄漏、解释 RSS 膨胀和分析分配器行为时，视角就会稳得多。

## 八、误解清单、证据清单与边界清单

### 误解清单

- 信号不是普通回调；handler 运行在可能打断任意线程的危险上下文里。
- 阻塞某个信号不等于忽略它；很多场景只是延后递送，等值班线程或未来某时再消费。
- thread-safe 不等于 async-signal-safe；`printf`、`malloc`、拿锁这类路径在 handler 里都可能出大事。
- timerfd 不只是“另一个定时器 API”；它的真正价值是把时间到期拉回普通 fd 事件循环。
- `malloc` 不是 syscall 薄壳；arena、cache、`brk`/`mmap` 后端和异步重入边界都藏在后面。

### 证据清单

- 信号递送：`sigaction`、mask/pending、`kernel/signal.c` 与线程递送路径，支撑“进程级 disposition + 每线程 mask + 具体承接线程”的主线。
- 同步化处理：`sigwait`/`signalfd` 与 epoll 集成路径，支撑“复杂控制逻辑应回到普通线程上下文”。
- 时间事件：`timerfd`、时钟源、过期计数与 `epoll_wait` 集成路径，支撑“时间到期被 fd 化”的判断。
- 分配器：glibc `malloc`/arena/tcache、`brk`/`mmap` 后端与 trim 路径，支撑“先用户态周转，再必要时扩仓”的事实。
- 异步安全边界：async-signal-safe 函数集、stdio/分配器/锁路径，支撑“handler 里只能留下最小事实”的结论。

### 边界清单

- 本文讲的是 POSIX/Linux 信号、timerfd 与 glibc 风格 `malloc` 的稳定心智模型，不把某版 libc、内核或容器环境的默认行为写成长期契约。
- 标准信号、实时信号、`SA_RESTART` 与 signal mask 的具体表现会随目标系统和调用场景变化，排障时必须结合实际线程模型与阻塞点判断。
- signalfd/timerfd 让事件更易统一消费，但不自动替你设计优雅退出、补偿策略或业务超时语义。
- `malloc` 的 arena/tcache/trim 策略、RSS 回落速度和“看起来像泄漏”的表象，会受工作负载、线程池和版本差异强烈影响。
- 后续进入内存排障时，重点将从“异步边界怎样安全处理”推进到“地址空间与驻留账本怎样被读懂”。
