## 现在真正该问的，不再是“进程怎样 fork/exec/wait”，而是“如果多个执行流不再各自拥有独立地址空间，而是挤在同一个进程里共享 heap、fd 和全局变量，到底谁来保证它们不会把彼此的现实写乱”

上一章我们已经把多进程世界里最重要的边界讲透了。你知道：

- `fork()` 复制的是执行上下文，很多物理页借助 COW 延后复制；
- `execve()` 换掉的是当前进程的程序映像，不是额外再创建一个 PID；
- 父子进程各有 fd table，但表项可能仍指向同一个 open file description；
- `wait()`/`waitpid()` 回收的是退出状态，`SIGCHLD` 只是通知；
- daemon 化重新整理的是会话、终端、标准流和长期依附关系。

这些结论让你理解了：**进程隔离的代价是资源复制与切换，进程隔离的好处是很多状态天然不共享。**

可一旦你想要更轻的并发单位，问题就反过来了。线程最大的吸引力，恰恰来自“别再复制那么多东西”：

- 不再为每个任务复制一整个地址空间；
- 不再让父子进程通过 IPC 才能共享堆对象；
- 不再为“共享同一批 fd、缓存和配置”额外搭桥；
- 让同一进程里的多个执行流更直接地协作。

但线程也把新的危险一次性带了进来：

- 多个线程可以同时改同一块堆内存；
- 多个线程也可能共享同一个 fd 和 offset；
- 一个线程退出了，谁来领走它的返回值和栈等资源；
- 同一个函数也许“线程安全”，却仍然不适合在信号处理器里调用；
- 某些状态明明在同一进程里，却又必须做到“每线程一份”。

所以本篇最重要的顿悟是：**线程之所以轻，是因为它共享得多；线程之所以危险，也是因为它共享得多。线程编程真正要分清的，不是“有没有并发”这么粗，而是生命周期、共享状态、同步协议、TLS、线程安全和信号安全这几层边界分别由谁负责。**

先把总图记住：

```text
线程属于同一进程：
  共享地址空间
  共享大多数堆对象和全局变量
  共享很多打开文件对象与进程级属性

每个线程自己拥有：
  寄存器现场
  栈
  调度实体身份
  一部分线程局部状态

需要你显式补上的：
  join/detach 生命周期回收
  mutex/condition variable 同步协议
  TLS 私有副本边界
  thread-safe / reentrant / async-signal-safe 区分
```

这一篇最重要的一句话是：**进程把“隔离”当默认值，线程把“共享”当默认值；因此进程编程更常先想怎么传递状态，线程编程则必须先想哪些状态绝不能被同时乱改。**

## 一、如果把线程理解成“比进程更小的进程”，你就会误以为线程结束后资源会自动像普通函数返回那样消失、误以为每个线程天然拥有独立 fd 世界，最后在 join、detach 和共享对象生命周期上踩出一串隐蔽泄漏

### 1. 最朴素的错误世界：开一个线程，就像把某个函数丢到后台跑；跑完自然结束，主线程也自然什么都不用管

这是很多人第一次写 `pthread_create()` 时最容易形成的错觉。API 表面上确实像“启动一个函数”：给它一个入口函数和参数，新线程开始执行，主线程继续往下走。于是就很容易顺着写出这样的心智模型：线程不过是异步函数调用而已，函数执行完了，资源当然像普通栈帧那样自动清干净。

可线程不是普通函数调用。普通函数共享调用线程的栈、寄存器和生命周期；线程则拥有独立栈、独立寄存器现场和可被调度、可被等待的独立执行实体。你既然向系统申请了一份新的执行流，就也必须面对：

- 它什么时候真正结束；
- 谁来确认它结束；
- 谁来领取它的返回值；
- 哪些与该线程绑定的资源要在结束后被回收；
- 回收责任到底是在别的线程手里，还是交给运行时自动处理。

所以线程不是“会自动蒸发的后台函数”，而是“共享同一进程资源池、但拥有独立生命周期的执行体”。

### 2. `pthread_create` 真正创建的，不是一份小进程壳，而是一条共享同一进程现实的新执行流

回扣上一章的进程视角很有帮助。fork 之后，父子进程虽然一开始能看见相似地址空间内容，但最终还是两套逻辑独立的地址空间；线程则不同。`pthread_create()` 启动的新线程，从一开始就不打算把地址空间分家。它和创建者天然共享：

- 同一份进程地址空间；
- 同一批全局变量和大部分堆对象；
- 同一进程语义下的很多 fd 与打开文件对象；
- 诸如工作目录、资源限制、很多进程级属性。

与此同时，它又有自己的独立性：

- 自己的栈；
- 自己的寄存器现场和程序计数路径；
- 自己的线程 ID 和调度参与资格；
- 自己可能需要回收的结束状态。

这意味着线程编程从第一步就和进程编程做了截然不同的默认选择：**不是先隔离，再想怎么共享；而是先共享，再想怎么避免共享带来的冲突。**

### 3. 为什么 joinable 线程结束后“不处理”会积累资源，但它又不该被简单叫成进程式 zombie

joinable 线程结束后，运行主体可以已经不再继续执行，但与“别人还能否拿到它的退出结果、运行时能否彻底释放与它绑定的资源”相关的信息并不会凭空消失。系统/运行时需要为潜在的 `pthread_join()` 保留足够状态，让另一个线程能够确认它的结束、领取返回值并完成资源回收。

如果程序既不 `pthread_join()`，又不在合适时机把线程设成 detached，那么这些已结束但未被正常收尾的线程资源就会积累。这里的积累不像 zombie 进程那样主要体现在进程退出状态条目，而更像“你申请过的一份线程执行资源，还没有按协议完成最后收口”。

所以说“不 join 会不会出问题”，答案不是抽象的“可能不好”，而是：**会。因为 joinable 线程的生命周期最后一步不是“函数返回”，而是“被别的线程按约定领走”。**

### 4. `pthread_join` 与 `pthread_detach` 为什么其实是在回答同一个问题：谁负责收尾

一旦你把线程看成独立生命周期实体，这两个 API 的意义就会特别清楚。

`pthread_join()` 的意思是：我明确指定一个观察者线程来等待它结束，并在结束后取回结果、完成资源回收。它更像有主的领取。

`pthread_detach()` 的意思则是：我放弃事后 join 这条领取路径，让运行时在它结束后自动完成清理。它更像无主自动归档。

两者并不是“一个更高级、一个更低级”，而是两种不同的生命周期协议。关键在于别把协议混着用：

- 已经 detach 的线程不该再按 joinable 路径去 join；
- 计划靠 join 收尾的线程，就不能永远没人来 join；
- 创建线程时最好先想清楚它属于“我要拿结果的任务”，还是“只要它自己跑完就行的后台工作”。

### 5. 线程共享 fd 世界，为什么又把第一篇的 offset 竞态问题重新带回来了

很多人一转到线程，就会忽略第一篇关于 fd/open file description 的警告，好像“同一进程里的线程一起用一个 fd”是天然安全的。

不是。线程共享的往往不只是 fd 数字，更是它背后的打开文件对象语义。如果多个线程共同使用同一个会推进 offset 的 description，那么：

- 一个线程的 `read()` 可能改变另一个线程下一次读的位置；
- 一个线程 `close(fd)` 也可能影响别的线程是否还能安全使用该引用；
- `lseek + read/write` 这类两步位置协议在多线程下同样会有竞态；
- 想避免位置竞争，仍然要回到 `pread/pwrite` 或更明确的同步协议上。

这说明线程并没有替你解决第一篇的问题，反而让“共享对象被多个执行流同时碰”这件事更频繁、更直接了。

### 6. 为什么线程生命周期设计从一开始就该和“线程池还是一次性线程”绑定着想

如果你为每个任务现建线程、任务结束后再 join 或 detach，那么生命周期边界相对清晰；可一旦进入线程池世界，线程会活得比单个任务久得多，`pthread_join()` 通常只发生在线程池整体收尾时。此时你要区分：

- 线程生命周期；
- 线程上跑的任务生命周期；
- 任务结果怎么回收；
- 线程退出时机由谁决定。

这恰好说明 join/detach 讨论的不是“写法细节”，而是**你打算让谁为执行体善后**。线程池里不理解这条线，就很容易把任务结束误判成线程资源已经自然回收。

### 7. 本节最该记住的结论：线程不是“自动蒸发的后台函数”，而是共享同一进程现实、却有独立栈与独立结束状态的执行流；join 与 detach 决定的是谁负责把这份执行流的后事收干净

一句最短人话是：**线程跑完不等于后事自动办完；join 是有人去领，detach 是交给系统自动归档。**

## 二、mutex 和条件变量最容易被误解成“给某段代码加个锁就安全了”，可真正被保护的从来不是几行代码本身，而是“哪些状态必须同时成立、谁有资格改、谁该在什么条件下等待”的整套协议

### 1. 最朴素的错误世界：只要两个线程不会“同时执行同一行”，共享状态就安全了

这是初学同步最常见的偷懒想法。比如一个余额变量、一段队列、一个连接池标志位，看起来只要“加把锁”就能让程序变安全。于是代码写成：进入临界区、改几个字段、出来，就觉得完事了。

问题在于，线程 bug 通常不只来自“同一时刻撞上同一行代码”，而来自**你对共享状态成立条件的想象，和别的线程实际观察它的顺序不一致**。例如：

- 一个线程以为“队列非空”与“取出一个元素”之间没人会插手；
- 一个线程以为“余额足够”和“扣款”是同一原子事务；
- 一个线程以为自己看到“连接已经关闭”，别人就不会再拿这个连接继续写。

所以锁保护的不是语法片段，而是这些状态转换协议：谁检查、谁修改、检查与修改能不能被别人打断。

### 2. 为什么“两个线程都 `pthread_mutex_lock(&m)`”本身并不是死锁

完备性问题里专门强调了这一点，因为很多人会把“有等待”直接等同于“死锁”。如果两个线程都试图拿同一把 mutex，最常见的语义是：

- 一个线程先拿到锁进入临界区；
- 另一个线程在这把锁上等待；
- 前者解锁后，后者再继续。

这里有等待，但没有必然的循环等待，也没有资源环。它只是串行化访问。

所以不要把 mutex 的存在当成死锁来源本身。真正危险的是：**多个锁之间的顺序关系、等待条件与唤醒时机组合起来，形成了环。**

### 3. 典型死锁为什么不是“锁太多”，而是“不同线程对资源获取顺序没有共同宪法”

最经典的例子就是：

- 线程 A 先锁 `m1`，再想锁 `m2`；
- 线程 B 先锁 `m2`，再想锁 `m1`。

如果 A 拿着 `m1` 等 `m2`，B 拿着 `m2` 等 `m1`，两边都在等对方先放手，系统就进了循环等待。这里真正缺失的不是某个 API，而是全局协议：**多把锁出现时，大家到底按什么顺序拿。**

所以防死锁最有力的手段通常不是“祈祷运行时帮我处理”，而是：

- 给多把锁规定稳定顺序；
- 尽量缩短临界区，减少持锁时间；
- 必要时用 trylock/timedlock 打破“无限等待”；
- 重新设计共享状态，把“必须同时拿两把锁”的需求降下来。

### 4. 条件变量为什么再次证明“锁保护的是协议，不是动作”

条件变量最能暴露这一点。很多人第一次看到 `pthread_cond_wait()` 会想：“既然有人 signal 我了，那条件肯定成立了，我直接往下做就行。”

这正是错的地方。条件变量通知的不是“条件已经永恒成立”，而是“你有机会回来重新检查条件了”。因为在你被唤醒和你重新拿到锁之间，别的线程可能已经：

- 先一步消费掉了那个资源；
- 再次把状态改回“不满足”；
- 造成一次虚假唤醒，本来就没有新条件到来。

所以条件变量的典型写法必须是：拿锁、`while (!condition) wait`、被唤醒后再次检查、条件真的满足才继续。`if` 只检查一次，表达的是“我相信通知本身等于条件成立”，这在并发里经不起打。

### 5. 为什么“锁住共享对象”不等于“整个业务动作已经安全”

这点在系统程序里特别重要。比如一个线程拿锁检查“队列非空”，然后取出任务；另一个线程可能同时依赖“队列长度 + 关闭标志 + worker 退出条件”做决策。此时一把锁保护的不是单个字段，而是多个字段组合出的不变量。

因此你要问的不是“有没有锁”，而是：

- 锁覆盖了哪些共享字段；
- 哪些状态必须在同一把锁下读写；
- signal/broadcast 是否发生在正确的状态变更之后；
- 被唤醒者看到的是不是一致状态；
- 是否存在拿锁顺序不统一的路径。

这就是为什么成熟并发代码常常看起来不像“给每行危险代码套个壳”，而像“给整个共享协议定义法律”。

### 6. `pthread_mutex_trylock` 能做什么，不能做什么

它能做的一件重要事，是把“永远等下去”改成“拿不到就先退一步”，从而为死锁规避、降级路径、锁顺序纠正或旁路处理提供机会。比如一个线程发现第二把锁拿不到，就先放掉第一把，重新按统一顺序再来。

但别把它神化成“有 trylock 就没有死锁”。如果整体资源获取协议仍然混乱，trylock 只是让问题表现成忙等、饥饿或复杂重试，而不是自动变正确。它解决的是“阻塞等待形式”，不是“共享状态设计本身”。

### 7. 本节最该记住的结论：mutex、条件变量和 trylock 保护的不是代码行，而是共享状态协议；真正要统一的不是“谁能执行到这里”，而是“谁按什么顺序检查、修改、等待和唤醒”

一句最短人话是：**锁是规则执行器，不是自动正确机；条件变量给你的是复查机会，不是无条件通行证。**

## 三、TLS 最容易被误解成“既然每线程一份，那就不用再想并发了”，可它真正消除的只是某些共享写竞争，不会替你处理线程池复用、跨线程汇总、析构时机和共享对象内部一致性

### 1. 最朴素的错误世界：只要把全局变量改成 TLS，并发问题就自动没了

这类想法很有诱惑力。既然共享状态最危险，那就别共享了：给每个线程发一份自己的副本，大家各写各的，不就没有锁竞争了吗？

这个方向对一部分问题确实有效，比如：

- 每线程错误码；
- 每线程缓存区；
- 每线程统计临时计数；
- 每线程连接上下文指针；
- 每线程 allocator cache 一类局部状态。

但 TLS 解决的是“这份状态是不是必须被线程之间共享”这一层，不是“整个系统还剩不剩并发边界”。只要最终还要把各线程结果合并、把对象交给别的线程使用、把线程回收到线程池里复用，问题就会重新出现。

### 2. 为什么 `errno` 这类典型例子最适合帮助理解 TLS

`errno` 如果是整个进程只有一份全局变量，那么一个线程刚失败设了 `errno`，另一个线程立刻覆盖掉它，你就根本没法可靠地在每条执行路径里读取自己的错误结果。把它做成每线程独立副本之后，调用者看到的就是“我的最近一次错误”，而不会被别的线程串台。

这个例子说明 TLS 的真正价值是：**让某些逻辑上属于“当前线程上下文”的状态，不必为了传递它而层层增加函数参数，也不必为了保护它而加共享锁。**

### 3. 静态 TLS 和动态 TLS 为什么都在回答“私有状态放哪”，而不是“共享对象怎么变安全”

无论是编译期支持的 `__thread`/`_Thread_local`，还是 `pthread_key_create`/`pthread_setspecific` 这套动态 TLS 机制，本质都在帮你把“这份数据逻辑上属于某线程”落实到可访问的存储位置上。

它们有不同使用场景：

- 静态 TLS 更适合生命周期明确、类型固定的线程局部变量；
- 动态 TLS 更适合库代码在运行时给每线程挂一份私有上下文，还能在线程结束时跑析构动作。

但无论哪种形式，都不要误会成“共享对象因此安全了”。假设多个线程都各自有自己的缓存区，这很好；可如果它们最终都要写同一个日志文件、同一个全局 map、同一个统计汇总对象，那些共享对象仍要靠锁、原子或明确的所有权协议保护。

### 4. 为什么 TLS 能减少锁，却也可能带来新的生命周期和内存问题

每线程一份副本的好处，是把一些热点写竞争打散了；代价则是：

- 线程越多，总内存占用可能越大；
- 线程池里的线程会被复用，TLS 状态不会因为“上一个任务结束”就自动回到你想要的初始值；
- 线程退出时需要析构的 TLS 对象，其释放顺序和次数要按运行时规则理解；
- 你可能以为自己把状态“局部化”了，其实只是把状态残留到了长期存活的 worker 线程里。

这在服务端程序里特别常见：开发者把某请求上下文偷偷放进 TLS，结果线程池线程长期不退出，后续请求忘记清理旧值，于是逻辑互相污染。可见 TLS 只是换了一种地方存状态，不等于状态生命周期就 magically 对了。

### 5. 为什么 TLS 很适合“线程上下文”，却不适合表达“任务上下文”

这一点必须和线程池一起想。线程上下文的生命周期通常跟线程本身一致；任务上下文的生命周期却往往只是一次请求、一次 RPC、一次作业执行。在线程池里，一个线程可能先后执行无数个任务。如果把任务级状态塞进 TLS，却没有严格在任务边界重置，你就把“本该跟任务一起消失的状态”错误绑到了线程寿命上。

所以判断 TLS 该不该用时，一个关键问题是：**你手里的是每线程私有状态，还是每任务私有状态？** 前者通常合适，后者要非常警惕。

### 6. 本节最该记住的结论：TLS 解决的是“每线程一份”的私有状态存放问题，它能减少共享写竞争，但不会自动解决共享对象安全、线程池复用、生命周期重置和跨线程汇总问题

一句最短人话是：**TLS 给每个工人一本私有工作本，但总账本、交接班和下班清桌子，仍然要你自己定规矩。**

## 四、可重入、线程安全与信号安全常被混成“这个函数安全不安全”的一个标签，可它们描述的是三种完全不同的上下文：并发线程、同一执行流被打断重入、以及异步信号在任意时刻插进调用链

### 1. 最朴素的错误世界：一个函数既然“线程安全”，那不管在哪儿调都应该安全

这几乎是所有信号安全事故的认知根源。开发者看到某库号称 thread-safe，就自然把它理解成“多线程里随便调没事，那在 signal handler 里应该也没事”。

问题在于，线程安全讨论的场景是：多个线程在**正常调度语境**下并发访问某个函数或对象，库可以靠 mutex、TLS、原子变量等手段把竞态处理掉。

而信号处理器面对的是另一种世界：一个线程正在执行某段代码、可能正持有库内部锁、可能正处在分配器或 stdio 的中间状态，异步信号突然插进来，handler 又试图调用同一套非异步安全接口。此时你不是在面对“第二个线程按正常协议来了”，而是在面对“同一条执行链被不讲排队地打断后重入”。

### 2. 可重入为什么和线程安全不是一回事

可重入关注的是：**同一执行流在一个函数执行到一半时被打断，又再次进入这个函数，逻辑还能否成立。**

一个只用调用者提供的局部数据、不依赖共享静态缓冲、没有全局隐藏状态的函数，更容易是可重入的；反过来，如果函数内部反复使用同一块静态缓冲区、同一份全局游标，即使只有一个线程，也可能在重入时把自己状态写乱。

线程安全则允许用锁把并发调用串起来，因此一个函数可以是线程安全的，但未必是可重入的。因为锁能协调多个线程，却救不了“我在持锁过程中被信号打断，然后 handler 又来拿同一把锁”的局面。

### 3. 为什么 `printf` 与 `write` 的区别，最能打穿“线程安全不等于信号安全”

完备性问题里已经把例子点出来了：在 signal handler 里 `printf("caught SIGTERM\n")` 可能死锁，而 `write(STDOUT_FILENO, "caught\n", 7)` 往往是可接受的路径。

区别不在于它们都“能输出字符串”这件表层功能，而在于它们所处的语义层次不同：

- `printf` 可能牵涉 stdio 用户态缓冲、格式化、内部锁和更复杂的 libc 状态；
- `write` 则更接近一个受限、明确的系统调用边界，在 async-signal-safe 集合里通常才有稳定位置。

如果信号正好打断了某线程里的 `printf`/`malloc`/`pthread_mutex_lock` 内部路径，handler 再重入同类逻辑，就可能卡在已经被当前线程持有、却永远等不到释放的内部状态上。于是“明明还是这个线程，为什么还死锁”这个问题就通了：**因为它打断了自己，然后在不安全点又走回了自己没走完的路。**

### 4. 为什么 signal handler 的正确姿势通常是“先留下最小事实，再把复杂处理挪走”

这条思路和第二篇的 epoll/inotify 统一事件哲学、第三篇的 `SIGCHLD` 处理思路完全一致。既然异步 handler 上下文危险、能调用的函数集合极小，那最稳的方式通常是：

- 设置一个原子标志；
- 向一个 pipe/eventfd/signalfd 等安全通道写入最小通知；
- 让主循环或专用线程在正常上下文里完成日志、清理、重载配置、回收子进程等复杂动作。

这样做不是因为 handler “太弱”，而是因为它所处的执行时机太凶险。你应该把它看成急停按钮附近的最小应急动作区，而不是平时完整工作流的替代入口。

### 5. 为什么很多“线程安全”的库 API 仍然需要在信号篇重新审判一次

因为它们的 thread-safe 往往靠：

- 内部互斥锁；
- 分配器状态；
- 静态缓存或延迟初始化；
- stdio 缓冲；
- 全局注册表。

这些机制在普通线程并发里非常合理，可一旦放到异步 signal handler 里，就可能在“打断点不受控”这个前提下变成死锁或状态破坏源。所以本篇先把这三个词拆开，是为了下一篇讲信号时不再让“线程安全”这个大而化之的标签误导你。

### 6. 本节最该记住的结论：可重入、线程安全和 async-signal-safe 不是同义词；线程安全处理的是多线程正常并发，信号安全处理的是异步打断后的极小可用动作集，不能互相替代

一句最短人话是：**多人排队用工具是一回事，机器急停时伸手抢救又是另一回事；能排队，不代表能在急停瞬间乱插手。**

## 五、1:1、N:1、M:N 这些模型之所以重要，不是因为你要背名词，而是因为“线程为什么能并行、为什么一个阻塞系统调用会不会拖垮整个运行时、为什么协程不像内核线程那样天然吃满多核”全取决于用户执行单元和内核调度实体怎么映射

### 1. 最朴素的错误世界：线程既然比进程轻，那线程当然永远更划算；用户态协程既然更轻，那当然又永远比内核线程更划算

这种二元排序非常诱人：越轻越先进，越轻越高性能。可只要把“谁在调度、谁能并行、谁会被阻塞系统调用卡住”这几个问题摆出来，结论立刻复杂起来。

所谓轻重，从来不是单一维度。你可以在资源复制、切换开销、运行时管理复杂度、共享状态代价、阻塞语义和多核并行能力之间交换。不同模型轻的是不同地方，重的也是不同地方。

### 2. 1:1 为什么是 Linux 上 Pthreads 心智模型的核心

在 1:1 模型里，一个用户线程对应一个内核可调度实体。好处非常直接：

- 线程可以被内核独立调度到不同 CPU 上；
- 多核并行天然成立；
- 一个线程在阻塞系统调用里睡住，不必把整个进程的其他线程都一起冻住；
- 调试、性能分析和调度观测的语义相对统一。

代价则是内核需要为每条线程承担更多调度、栈和阻塞管理成本，用户态也必须面对更多真正并行带来的共享状态同步问题。可对现代通用 Linux 程序来说，这种代价通常比“并行能力和阻塞隔离”更值得。

### 3. N:1 为什么用户态切换很轻，却天然怕阻塞系统调用

如果很多用户线程/协程都复用在一个内核线程上，那么它们彼此切换可以非常便宜，运行时也能高度掌控调度策略。问题在于，从内核角度看，它们其实只是一条执行线上的不同用户态片段。

于是只要这条承载线程进了一个阻塞系统调用：

- 内核看到的是“这一条线程睡了”；
- 运行时没法让同一内核线程上的其他用户线程继续并行推进；
- 整个承载者上的所有用户执行单元都可能一起停住。

而且即使没有阻塞问题，只有一个内核调度实体，也意味着它无法天然跨多个 CPU 同时跑。你能做的是更便宜的协作式切换，不是凭空生出更多内核并行度。

### 4. M:N 为什么试图两头都要，却会把运行时复杂度大幅抬高

M:N 的诱惑在于折中：多个用户执行单元映射到多个内核线程，希望既拿到一部分用户态调度灵活性，又不完全失去多核并行和阻塞隔离。

这听起来很好，难点在于 runtime 需要承担更多职责：

- 哪些用户任务放到哪些内核线程上；
- 阻塞 I/O 怎么绕开或托管；
- work stealing、唤醒、负载均衡怎么做；
- 什么时候需要把用户态等待转换成内核态等待。

也就是说，M:N 不是免费午餐，而是“把一部分本来交给内核的复杂度，搬回运行时自己扛”。这在语言运行时里可以很有价值，但它已经超出“pthread 只是一个轻量 API”的范围了。

### 5. 为什么“线程比进程轻”这句话只说对了一半

对的一半在于：线程共享地址空间和许多进程级资源，确实减少了创建/复制/IPC 方面的一部分成本。

没说出的另一半是：

- 共享得越多，同步和缓存一致性问题越多；
- 一个线程写坏共享内存，可能把整个进程一起带下水；
- 锁争用、伪共享、内存分配器竞争、日志 fd 竞争都会在多线程里放大；
- 调试“偶发竞态”往往比调试多进程下的消息协议更棘手。

所以线程和进程从来不是“轻重排序”的单选题，而是“你愿意把复杂度放在隔离与通信，还是放在共享与同步”这道架构题。

### 6. 本节最该记住的结论：1:1、N:1、M:N 模型决定了用户执行单元能否真正并行、阻塞系统调用会不会拖住整组任务，以及复杂度主要由内核承担还是由运行时承担；“轻”不是绝对优点，而是成本搬家的结果

一句最短人话是：**线程和协程谁更轻，不先问“谁来调度、谁会被阻塞、谁能吃满多核”，这个问题就还没问对。**

## 六、把本篇收成一张图：线程之所以快，是因为共享地址空间和资源；线程之所以难，也是因为共享地址空间和资源；生命周期回收、同步协议、TLS 与安全边界，都是在给“默认共享”补法律

现在可以把这一篇彻底收回来。

一开始我们要解决的问题是：既然进程隔离很好，为什么还要线程；既然线程更轻，为什么 bug 反而更多。答案并不矛盾。线程的优势恰好来自它不再像进程那样复制和隔离那么多东西：同一进程里的多个线程天然共享地址空间、很多堆对象、很多 fd 与进程级属性，所以它们协作更直接、创建成本更低、跨线程交换数据也更省。

但正因为默认共享，线程程序必须自己补上进程原本替你天然提供的一些边界。`pthread_create()` 启动的是新的执行流，不是会自动蒸发的后台函数；`pthread_join()` 和 `pthread_detach()` 决定的是谁来为这条执行流收尾。mutex、条件变量和 trylock 也不是给几行代码贴止疼膏，而是在强制执行“谁有资格观察和修改哪组共享状态、等待者何时该苏醒并重新检查条件”的协议。TLS 让每线程私有状态有了落脚点，减少了部分共享写竞争，但不替你解决线程池复用、结果汇总和共享对象内部一致性。与此同时，可重入、线程安全和 async-signal-safe 这三个术语又把“安全”拆回了三种完全不同的上下文：正常多线程并发、同一执行流被打断重入、以及异步信号突袭。

把这一切压成最短总图，就是：

```text
生命周期：
  pthread_create → join 或 detach 收尾

共享状态：
  默认共享 heap/global/fd
  需要 mutex/cond/atomic 协议保护

私有状态：
  TLS 给每线程一份副本
  不等于共享对象自动安全

安全边界：
  thread-safe ≠ reentrant ≠ async-signal-safe

执行模型：
  1:1/N:1/M:N 决定并行、阻塞与调度复杂度
```

所以本篇最该记住的一句话是：**线程编程不是“把函数丢到后台并行跑”这么简单，而是选择了一个以共享为默认前提的世界；你得到的是更低复制成本和更直接协作，付出的则是必须亲手定义生命周期、同步协议、私有状态和安全边界。**

## 七、几个最容易说错的地方

### 线程是不是就是“更小的进程”？

不是。线程共享同一进程的大量资源，尤其是地址空间和许多进程级状态；它不是把进程简单缩小一号。

### 线程函数返回后，线程资源是不是一定自动全部回收？

不一定。joinable 线程通常仍需要被 `pthread_join()` 正常收尾；若不打算 join，应明确走 detach 协议。

### 两个线程都 `pthread_mutex_lock(&m)`，是不是就已经发生死锁？

不是。单锁等待通常只是串行化访问；真正的死锁更常见于多锁顺序不一致导致的循环等待。

### 条件变量被唤醒后，是不是就能直接往下执行，不用再判断条件？

不是。唤醒只表示“回来再看一次”，不能把通知本身当成条件已经稳定成立。

### TLS 能不能替代所有锁？

不能。TLS 只解决每线程私有状态存放与部分共享写竞争问题，跨线程汇总和共享对象一致性仍需额外协议。

### 线程安全是不是就等于信号安全？

不是。线程安全通常面对正常并发调用；信号安全面对的是异步打断后的极小可用动作集，约束严格得多。

### 线程一定比进程更高性能吗？

不能绝对化。线程减少了资源复制，却增加了同步、竞态、缓存一致性和故障隔离成本；要结合 workload 和模型看。

## 收束：看懂 Pthreads 之后，你才会真正明白“并发”不是简单地把执行流变多，而是决定哪些现实默认共享、哪些边界必须亲手补上

回到开头那个问题：如果多个执行流生活在同一个进程里，到底谁来保证它们不会把彼此现实写乱？现在答案已经完整闭环了。线程共享地址空间与大量资源，所以你得用 join/detach 管好执行流后事，用 mutex/condition variable 管好共享状态协议，用 TLS 安放每线程私有上下文，并把 thread-safe、reentrant、async-signal-safe 这几类“安全”严格拆开。最后再往下一层看，1:1、N:1、M:N 模型又解释了为什么有的执行单元天然能吃满多核，有的则会被阻塞系统调用整组拖住。

也正因为如此，线程编程里最危险的误解从来不是“不会调 API”，而是把一切问题都压缩成一句“加个锁就好”。很多 bug 不是没上锁，而是生命周期协议没定清、条件变量没按 while 复查、TLS 用来装错了上下文、把线程安全误当成信号安全，或者压根没想清楚共享对象的所有权与唤醒顺序。

这就是为什么说：**线程编程的第一课不是并行本身，而是共享边界管理。** 一旦你知道哪些状态天然共享、哪些状态必须每线程私有、哪些上下文根本不允许重入复杂库调用，后面信号、定时器、malloc 竞争和更细的异步安全问题就会顺得多。

下一篇 `05-signals-timers-malloc.md` 会把这条线接下去：`sigaction`、线程信号屏蔽与投递、`alarm`/`setitimer`/`timerfd` 的取舍、glibc `malloc` 在并发与异步上下文中的边界，以及为什么“异步安全”是系统编程里最容易在压力场景下反咬你的那道暗线。那一篇要回答的，不再只是“多个执行流如何共享”，而是“异步事件怎样在进程和线程之间打断、唤醒、分配资源，甚至制造最难调的竞态与死锁”。
