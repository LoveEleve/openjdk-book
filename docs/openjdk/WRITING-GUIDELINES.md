# 写作指南

本文档提炼自 ch11/07 的反复打磨过程，适用所有章节。

## 1. 依赖驱动排序——A 依赖 B，就先写 B

写任何内容前自问：读者理解这段话需要先知道什么？

- 如果需要的前置知识还未介绍 → 要么重排顺序（把 B 移到 A 前面），要么删掉对 B 的引用（在 A 里不提 B）
- "这个概念在后面会讲" → 说明当前结构有问题，需要重排

## 2. 从问题开始——先"为什么"再"是什么"

`class Foo { int bar; }` 不应出现在第一节。第一节应回答"它解决了什么问题"。

顺序：**为什么需要它 → 它做了什么 → 源码长什么样**

读者需要先有 mental model，代码才有意义。

## 3. 禁止前向引用

- "详情见 §5" ← 若 §5 已存在，这是好的跨节引用
- "这个概念在后面章节会讲" ← 说明当前节的结构错了，读者在这里看不懂是因为缺东西

## 4. 构造/运行时严格分离

如果一篇文章定位是"构造函数创建了什么"：

- 构造时做了什么 → 详细讲
- 运行时怎么用 → 点到为止，标注"细节在后续章节"
- 不要来回跳（"构造时分配了，运行时这样用，构造时还分配了……"）

## 5. 源码 + 解释 = 缺一不可

- 纯源码 → 看不懂逻辑
- 纯解释 → 找不到依据
- 正确做法：贴关键代码片段，行内注释逐行解释。模板代码和错误处理可省略

## 6. 一个概念改三轮讲不通 → 删除

如果一段内容反复调整还是讲不清楚，多半因为它依赖的概念还未建立。
两个处理方式：

- 删掉，到依赖建立后再写
- 保留但加阅读提示标注"首次可跳过，后续有空再细看"

## 7. 说人话

复杂概念先用人话解释一遍，再给源码和术语：

| 不要说 | 要说 |
|--------|------|
| `SuspendibleThreadSet::synchronize()` | HotSpot 自己做的阻塞/恢复机制，底层是 pthread_cond_wait |
| `swap_mark_bitmaps()` | 只交换两个指针，不拷贝数据 |
| `_age.cmpxchg(newAge, oldAge)` | 把 top 和 tag 打包在一个 size_t 里，一次 CAS 搞定 |

## 8. 每句陈述有源码依据

只要读者问"确定吗"，立刻查源码核实。常见错误包括：

- 字段初始值（`_finger = start()` 写成 `end`）
- 容量计算（`max_elems = N-2` 写成 `N-1`）
- 并发关系（"Mixed GC 和并发标记并发" → 源码确认不能并发）

## 9. 画流程图——时间线和数据流最直观

文字描述很容易绕晕（"⑦ 是在 mixed GC 的间隙跑的"），流程图画出来一目了然。

- 时间线图：标注每个阶段是 STW 还是并发
- 数据流图：谁读/写哪个字段，冲突在哪
