# 写作指南

本文档提炼自 ch09/07 的反复打磨过程，适用所有章节。

## 1. 去 AI 味——你写的是一本书，不是一份文档

读者翻开你的书，不是在读 Javadoc，不是在读 RFC，不是在读 AI 生成的问答对。他在读一个人写的故事。

**禁止的 AI 味模式：**

| 机器写的 | 人写的 |
|---------|--------|
| `## 0. 问题——为什么需要 X？` | 把问题融进叙事里，别标号，别加冒号模板 |
| `✅ 已就绪 / ❌ 缺失` | 别用符号，写句子："堆还没建，Metaspace 还没建" |
| 每段结尾 `→ 细节：[文件名](链接)` | 交叉引用独立成段，放在该放的位置，不要每段贴一次 |
| `| 场景 | 问题 | 解法 |` 三列表格开头 | 先讲一个具体场景——把读者拉进去——再自然带出其他场景 |
| `前置知识：` 后面列一串链接 | "上一章我们做了 X，这一章要用到它的 Y 部分"——把前置融进上下文 |

**鉴别标准**：默读一遍。如果听起来像是 AI 用模板生成的——那就是 AI 味。如果听起来像是一个懂这些东西的人在跟你聊天——那就是人味。

参考 ch01 的开头：
```
上一卷最后你亲手编译了一个 JDK。敲 java -version 的时候，从屏幕上看到三行输出，觉得挺自然
——JDK 嘛，一个命令启动一个 JVM，很正常。但如果你稍微想一下：这个 java 可执行文件才 23KB，
而 JVM 本体 libjvm.so 有 164MB。一个 23KB 的 C 程序，怎么启动一个 164MB 的 Java 虚拟机？
```
没编号、没表格、没符号。一个问题从好奇心里长出来，不是因为"§0 问题"模板要求的。

## 2. 依赖驱动排序——A 依赖 B，就先写 B

写任何内容前自问：读者理解这段话需要先知道什么？

- 如果需要的前置知识还未介绍 → 要么重排顺序（把 B 移到 A 前面），要么删掉对 B 的引用（在 A 里不提 B）
- "这个概念在后面会讲" → 说明当前结构有问题，需要重排

## 2. 从问题开始——先"为什么"再"是什么"

`class Foo { int bar; }` 不应出现在第一节。第一节应回答"它解决了什么问题"。

顺序：**为什么需要它 → 它做了什么 → 源码长什么样**

读者需要先有 mental model，代码才有意义。

## 3. 禁止前向引用

- "详情见 §5" ← 若 §5 已存在，这是好的跨节引用
- "这个概念在后面章节会讲" ← 说明当前节的结构错了，读者在这里看不懂是因为缺东西

## 4. 构造/运行时严格分离

如果一篇文章定位是"构造函数创建了什么"：

- 构造时做了什么 → 详细讲
- 运行时怎么用 → 点到为止，标注"细节在后续章节"
- 不要来回跳（"构造时分配了，运行时这样用，构造时还分配了……"）

## 5. 源码 + 解释 = 缺一不可

- 纯源码 → 看不懂逻辑
- 纯解释 → 找不到依据
- 正确做法：贴关键代码片段，行内注释逐行解释。模板代码和错误处理可省略

## 6. 一个概念改三轮讲不通 → 删除

如果一段内容反复调整还是讲不清楚，多半因为它依赖的概念还未建立。
两个处理方式：

- 删掉，到依赖建立后再写
- 保留但加阅读提示标注"首次可跳过，后续有空再细看"

## 7. 说人话

复杂概念先用人话解释一遍，再给源码和术语：

| 不要说 | 要说 |
|--------|------|
| `SuspendibleThreadSet::synchronize()` | HotSpot 自己做的阻塞/恢复机制，底层是 pthread_cond_wait |
| `swap_mark_bitmaps()` | 只交换两个指针，不拷贝数据 |
| `_age.cmpxchg(newAge, oldAge)` | 把 top 和 tag 打包在一个 size_t 里，一次 CAS 搞定 |

## 8. 每句陈述有源码依据

只要读者问"确定吗"，立刻查源码核实。常见错误包括：

- 字段初始值（`_finger = start()` 写成 `end`）
- 容量计算（`max_elems = N-2` 写成 `N-1`）
- 并发关系（"Mixed GC 和并发标记并发" → 源码确认不能并发）

## 9. 画流程图——时间线和数据流最直观

文字描述很容易绕晕（"⑦ 是在 mixed GC 的间隙跑的"），流程图画出来一目了然。

- 时间线图：标注每个阶段是 STW 还是并发
- 数据流图：谁读/写哪个字段，冲突在哪
