## 现在真正该问的，不再是"哪种容器更快"，而是"可见性、竞争位置、复制成本、队列边界和缓存一致性如何组合"

上一篇把线程池、连接池和锁的基础讲清楚了。现在要把视角推进到另一个关键层面：**共享数据结构在并发访问下如何保持正确性、可见性和吞吐之间的取舍。**

很多人以为并发容器的选型就是"有没有锁"：有锁就慢，无锁就快。但真实的选择远比这复杂。一个 CAS 无锁结构在高竞争下可能比有锁版本更糟；一个"读无锁"的 COW 在高频写时会带来巨大的复制成本。所以并发容器的选型不是看"有没有锁"，而是看：

- **可见性**：读线程能不能看到最新写入？
- **竞争位置**：锁在哪个粒度上竞争（全表、桶级、数组级）？
- **复制成本**：写操作是否需要复制整个数据结构？
- **队列边界**：背压和容量如何控制？
- **缓存一致性**：false sharing 和缓存行 bouncing 如何影响性能？

先把总图记住：

```text
HashMap + 外部锁:
  适合简单临界区/低并发, 但要谨慎锁粒度

ConcurrentHashMap:
  热点缓存/共享索引/并发读写 map

CopyOnWriteArrayList:
  配置/监听器/读远多于写

BlockingQueue:
  明确阻塞、容量和背压语义的生产消费模型

Disruptor/RingBuffer:
  固定对象/高吞吐事件流水线/低 GC 场景
```

这篇最该先记住的一句话是：**并发数据结构的目标不是去掉所有锁，而是把正确性、可见性和背压放在最适合工作负载的位置。**

## 一、HashMap 并发失效：未同步共享结构会怎样坏掉

### 1. 最朴素的错误世界：普通 HashMap 用在多线程场景"大多数时候没出错"

这个想法在"我的代码跑了很久没出问题"的假设下很常见，但多线程同时 `put` 一个普通 HashMap，最坏会发生什么？

### 2. HashMap 并发失效的最小图

```text
普通 HashMap:
  put/get/resize 没有并发保护

并发写入可能导致:
  丢失更新
  读到不一致中间状态
  旧实现中的 resize/transfer 结构破坏
  死循环/高 CPU/错误结果

结论:
  "大多数时候没出错" ≠ 正确
  未同步共享访问在内存模型上就是数据竞争
```

### 3. 为什么 JDK8 改成尾插和树化后，仍不能说"多线程 HashMap 没事了"

因为某些旧版死循环路径被修补，不代表整体线程安全。只要没有同步协议，仍可能丢数据、读到中间状态或触发未定义并发行为。错误容器的"偶尔正常"不是可接受设计。

### 4. 本节最该记住的结论：普通 HashMap 不是线程安全容器；"偶尔能跑"不是正确性证明，未同步共享访问在内存模型上就是数据竞争

一句最短人话是：**普通 HashMap 像没有调度员的仓库，多人同时改货架号和索引卡时，即使没有塌仓，也可能把货放错区。**

## 二、ConcurrentHashMap：桶级同步、volatile 与计数分流

### 1. 第二个朴素误解：CHM 几乎无锁读，所以永远 O(1)

CHM 的 `get()` 通常不显式加全局锁，但桶冲突、树化、扩容迁移、hash 分布和高竞争都会改变路径成本。而且 CHM 只保证容器操作语义，不自动让"读到的值"在业务层是瞬时全局一致快照。聚合操作和迭代通常是弱一致/快照近似，要按 API 语义使用。

### 2. ConcurrentHashMap 的最小图

```text
读路径:
  table volatile 引用
  → 定位桶
  → 节点字段/next/value 的可见性保证
  → 遇到迁移标记时跟随到新表

写路径:
  CAS 初始化桶/控制状态
  → 桶级 synchronized/锁保护链表或树更新
  → 扩容时迁移桶并设置 forwarding marker

size/count:
  通过分散计数单元减少全局竞争
```

### 3. 为什么"CHM 几乎无锁读"不等于"永远无锁、永远 O(1)"

因为桶冲突、树化、扩容迁移、hash 分布和高竞争都会改变路径成本。CHM 只保证容器操作语义，不自动让"读到的值"在业务层是瞬时全局一致快照。聚合操作和迭代通常是弱一致/快照近似，要按 API 语义使用。而且 CHM 实现随版本变化——Segment 时代与 CAS+synchronized 时代不可混写，阅读源码时要分清版本。

### 4. 本节最该记住的结论：CHM 依赖桶级同步和 volatile 可见性实现并发安全；读路径通常无锁但不是永远 O(1)，聚合操作是弱一致/快照近似

## 三、CopyOnWriteArrayList：读无锁，写复制全表

### 1. 第三个朴素误解：COW 是"读无锁"的，所以比所有有锁容器都快

COW 的读确实完全无锁/无阻塞，但每次写都复制整个数组，带来 CPU、内存和 GC 压力。它只适合读多写少且能接受写传播延迟的配置/监听器场景。高频写时复制成本会远超锁竞争。

### 2. CopyOnWriteArrayList 的最小图

```text
read:
  读取当前数组引用
  → 遍历稳定快照

write:
  复制旧数组
  → 在新数组上修改
  → volatile/可见性发布新引用

效果:
  读完全无锁/无阻塞
  写 O(n) 复制
  旧快照在读者结束前仍可用
```

### 3. 为什么 CopyOnWrite 不适合高频写

因为每次写都复制整个数组，带来 CPU、内存和 GC 压力。读者看到的是写入前或写入后的完整快照，而不是"最新实时共享对象"。它适合读多写少且能接受写传播延迟的配置/监听器场景。

### 4. 本节最该记住的结论：COW 的核心不是更快写，而是避免读锁竞争；适合读多写少的配置/监听器场景，不适合高频写

一句最短人话是：**COW 像公告栏每次改通知都重印一整张纸再换上；围观者始终看到完整公告，代价是改一次就重印一次。**

## 四、Disruptor：RingBuffer、Sequence 与缓存行友好

### 1. 第四个朴素误解：Disruptor 永远比 BlockingQueue 快一个数量级

Disruptor 的收益强依赖单生产者、批量、缓存友好和固定对象生命周期。如果工作负载充满随机访问、复杂对象分配、背压不稳定或多生产者激烈竞争，收益会变化。Disruptor 的正确性还依赖 sequence 协议和发布/消费约束，不只是"去掉锁"。

### 2. Disruptor 的最小图

```text
RingBuffer:
  预分配数组槽位
  → producer/consumer 通过 sequence 协调

SingleProducer:
  发布路径更短
  → 少一层竞争协调

MultiProducer:
  需要额外原子协调 sequence

消费者:
  根据 sequence barrier/依赖顺序消费

关注点:
  缓存行填充
  false sharing
  批量消费
```

### 3. 为什么 Disruptor 不是"永远比 BlockingQueue 快一个数量级"

因为收益强依赖单生产者、批量、缓存友好和固定对象生命周期。如果工作负载充满随机访问、复杂对象分配、背压不稳定或多生产者激烈竞争，收益会变化。

### 4. 本节最该记住的结论：Disruptor 把队列问题转化为预分配 RingBuffer、序号推进和缓存友好布局；但收益依赖特定 workload，不是万能方案

## 五、选型：不同并发容器在不同队列位置排队

### 1. 第五个朴素误解：无锁容器更高级，所以应该优先选无锁

CAS 重试、缓存抖动、自旋和回收协议都可能在高竞争下比锁更糟。真正要优化的是端到端吞吐、尾延迟和正确性，而不是追求"代码里没有 synchronized"。

### 2. 并发容器选型的最小图

```text
HashMap + 外部锁:
  适合简单临界区/低并发, 但要谨慎锁粒度

ConcurrentHashMap:
  热点缓存/共享索引/并发读写 map

CopyOnWriteArrayList:
  配置/监听器/读远多于写

BlockingQueue:
  明确阻塞、容量和背压语义的生产消费模型

Disruptor/RingBuffer:
  固定对象/高吞吐事件流水线/低 GC 场景
```

### 3. 为什么"无锁容器更高级"是危险观念

因为 CAS 重试、缓存抖动、自旋和回收协议都可能在高竞争下比锁更糟。真正要优化的是端到端吞吐、尾延迟和正确性，而不是追求"代码里没有 synchronized"。容器选择要回到线程池、连接池、数据库和下游容量一起看，脱离闭环单独选容器容易选错。

### 4. 本节最该记住的结论：容器选择要看读写比例、顺序要求、容量、背压和故障语义；"无锁更高级"是危险观念

## 六、把本篇收成一张图：并发容器的本质是在正确性、可见性和吞吐之间找最优平衡

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：100 个线程同时改一个 Map，为什么有的结构会死循环、丢数据，有的结构却能稳定运行。答案已经闭环了：普通 HashMap 没有同步协议，发生数据竞争就是错误；ConcurrentHashMap 依赖桶级同步和 volatile 可见性实现并发安全；CopyOnWriteArrayList 用写时复制避免读锁竞争；Disruptor 用预分配 RingBuffer 和序号推进把锁等待转移到 CAS 和缓存一致性。每种结构都有自己的正确性、可见性、复制成本和队列边界取舍。

把这一切压成最短总图，就是：

```text
HashMap + 外部锁:
  适合简单临界区/低并发, 但要谨慎锁粒度

ConcurrentHashMap:
  热点缓存/共享索引/并发读写 map

CopyOnWriteArrayList:
  配置/监听器/读远多于写

BlockingQueue:
  明确阻塞、容量和背压语义的生产消费模型

Disruptor/RingBuffer:
  固定对象/高吞吐事件流水线/低 GC 场景
```

所以本篇最该记住的一句话是：**并发数据结构的目标不是去掉所有锁，而是把正确性、可见性和背压放在最适合工作负载的位置。**

## 七、几个最容易说错的地方

### 普通 HashMap 用在多线程场景"大多数时候没出错"？

不是。未同步共享访问在内存模型上就是数据竞争，"偶尔正常"不是可接受设计。

### CHM 几乎无锁读，所以永远 O(1)？

不是。桶冲突、树化、扩容迁移都会改变路径成本，聚合操作是弱一致/快照近似。

### COW 是"读无锁"的，所以比所有有锁容器都快？

不是。读确实无锁，但每次写都复制整个数组，只适合读多写少的场景。

### Disruptor 永远比 BlockingQueue 快一个数量级？

不是。收益强依赖单生产者、批量、缓存友好和固定对象生命周期。

### 无锁容器更高级，所以应该优先选无锁？

不是。CAS 重试、缓存抖动、自旋都可能在高竞争下比锁更糟。

## 收束：并发数据结构不是去掉所有锁，而是把排队和同步放在最适合的位置

回到开头那个问题：100 个线程同时改一个 Map，为什么有的结构会死循环、丢数据，有的结构却能稳定运行。答案已经闭环了：因为每种结构都有自己的同步协议和取舍。普通 HashMap 没有同步协议，发生数据竞争就是错误；ConcurrentHashMap 依赖桶级同步和 volatile 可见性；CopyOnWriteArrayList 用写时复制避免读锁竞争；Disruptor 用预分配 RingBuffer 和序号推进。没有"万能容器"，只有"最适合工作负载的容器"。

这就是为什么说：**并发数据结构的目标不是去掉所有锁，而是把正确性、可见性和背压放在最适合工作负载的位置。** 只要这条主线站稳，下一篇进入同步原语时，你就不会再把 CountDownLatch、Semaphore、Barrier 看成"独立的工具"，而会自然去问：它们在单机和分布式场景下，分别在哪里排队、在哪里同步、在哪里失效。
