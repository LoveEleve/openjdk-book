## 现在真正该问的，不再是"系统能扛多少 QPS"，而是"哪些请求该拒绝、哪些该等待、哪些该降级、哪些必须停止重试"

前几篇把线程、线程池、并发容器和同步原语的基础讲清楚了。现在要把视角推进到另一个关键层面：**系统在峰值、突发热点或下游抖动时，如何让失败有序而不是级联雪崩。**

很多人以为流量治理就是"限流"：配一个阈值，超过就拒绝。但真实的选择远比这复杂。固定窗口有边界突刺，滑动窗口有桶统计成本，漏桶不允许突发，令牌桶可能把突发压给下游。而且限流只是流量治理的一环：熔断负责在下游不健康时主动断链，降级负责给被断掉的请求一个退路，隔离负责限制爆炸半径，超时和重试负责控制等待和恢复节奏。所以流量治理不是"选一个限流算法"，而是看：

- **哪些请求该立即拒绝**：超过容量边界的瞬时峰值？
- **哪些可以等待**：排队时间在可接受范围内？
- **哪些需要降级**：返回缓存、默认值或异步处理？
- **哪些必须停止重试**：避免把已经卡住的下游彻底打垮？

先把总图记住：

```text
入口限流:
  控制总体来水量, 防止瞬时峰值直接压到核心资源

应用层限流:
  按资源/调用方/热点维度做细粒度配额控制

熔断:
  下游不健康时主动断链, 避免继续占用资源

降级:
  断链后给出缓存/默认值/延迟处理等兜底方案

隔离 + 超时 + 重试:
  限制爆炸半径, 控制等待时长, 约束恢复节奏
```

这篇最该先记住的一句话是：**高并发系统的稳定性不是来自把每个请求都处理完，而是来自明确哪些请求该立即拒绝、哪些可以等待、哪些需要降级、哪些必须停止重试。**

## 一、容量边界：流量治理首先不是放大吞吐，而是承认瓶颈

### 1. 最朴素的错误世界：CPU 还没满，系统怎么就崩了

这个想法在"CPU 满了才算过载"的假设下很常见，但大促零点流量瞬间涌入时，入口层还能收请求，数据库连接池、下游 RPC、线程池和队列很快堆满。系统吞吐取决于最慢、最脆弱且最难扩展的那一层。

### 2. 容量边界的最小图

```text
请求到达
  → 网关/代理层先做粗粒度限流
  → 应用层按资源/调用方/接口做细粒度限流
  → 只有被放行的请求才能继续占用线程池、连接池、下游配额
  → 某层处理不过来
       → 排队增加
       → 超时变多
       → 线程占满
       → 上游继续等待/重试
       → 级联雪崩
```

### 3. 为什么不能靠"加机器""开更多线程"硬扛

因为很多瓶颈根本不在线性扩容路径上：数据库写能力、热点行锁、下游第三方 API 配额、缓存回源、网络排队都可能先达到上限；更多线程还会把等待放大成更长队列。流量治理要在请求抵达瓶颈前就做削峰、排队、拒绝和降级。

### 4. 本节最该记住的结论：系统吞吐取决于最慢、最脆弱且最难扩展的那一层；流量治理要在请求抵达瓶颈前就做削峰、排队、拒绝和降级

一句最短人话是：**流量治理像商场消防限流——楼外排队并不代表收银台、试衣间和电梯都能无限接人；真正重要的是别让最窄的通道先被踩塌。**

## 二、限流算法：你不是在选"最强算法"，而是在选怎样约束突发与精度

### 1. 第二个朴素误解：固定窗口、滑动窗口、漏桶、令牌桶排成优劣榜

真实问题是：你要限制平均速率、平滑输出、还是允许短时突发。不同算法在保护目标、突发容忍度、时延分布、实现复杂度和分布式一致性成本上都不一样。

### 2. 四类限流算法的最小图

```text
固定窗口:
  一个时间窗一个计数器
  到窗边界清零
  优点: 简单
  风险: 窗口交界处可能出现双倍突刺

滑动窗口:
  大窗切成多个小桶
  统计最近一段时间的总量
  优点: 比固定窗口更平滑
  代价: 需要维护多个桶/时间片

漏桶:
  请求先进入桶/队列
  按稳定速率流出
  优点: 输出平滑, 适合保护下游
  风险: 到达长期高于流出时, 等待或丢弃不可避免

令牌桶:
  以稳定速率产出令牌
  请求拿到令牌才放行
  优点: 允许在令牌积累后短时突发
  风险: 令牌配置不当会把突发压给下游
```

### 3. 为什么不能说"令牌桶一定优于漏桶"或"滑动窗口一定最精确"

因为不同算法在保护目标、突发容忍度、时延分布、实现复杂度和分布式一致性成本上都不一样；允许突发的令牌桶更适合入口吸收抖动，追求稳定输出的漏桶更适合贴近受保护资源。像 Sentinel 这类实现常用环形桶维护 pass/block/rt/exception 等统计，核心是降低统计更新和读取成本，而不是把"滑动窗口"神化成绝对最优。

### 4. 本节最该记住的结论：固定窗口的问题在于只知道本窗口，不知道边界前后的连续性；滑动窗口通过分桶降低边界突刺，但桶越细统计成本越高；没有绝对最优算法，只有最适合保护目标的算法

## 三、限流规则落地：从资源、入口到分布式计数，重点是限哪里而不是只会配阈值

### 1. 第三个朴素误解：限流就是配一个阈值

读者常见困惑不是不会背算法，而是"规则配上去了，为什么有时对某接口生效、有时只对某入口生效、重启后规则又丢了"。限流落地要先定义"被保护的资源"以及"从哪个维度统计"。

### 2. 限流规则落地的最小图

```text
Resource:
  一个方法、一个接口、一个下游调用、一个热点参数维度

Entry:
  请求进入资源
  → 经过统计链与规则链
  → 通过则继续执行
  → 被拦截则走 block handler / fallback

常见规则维度:
  直接:
    当前资源自己到阈值就限自己
  关联:
    关联资源繁忙时, 当前资源主动让路
  链路:
    同一资源从不同入口进入, 配不同阈值
```

### 3. 为什么"把 Redis 计数器一加"不等于分布式全局限流

因为你不仅在做计数，还在做全局时间窗、一致性、失败恢复和性能折中。网关故障、Redis 抖动或跨机房延迟都会改变限流的真实行为。而且远程计数把本地 O(1) 判断变成一次网络往返，这个性能拐点必须纳入方案评估。单机限流只对本实例视角成立；一旦多实例部署，每实例独立预算和全局共享预算会直接决定实现方式。

### 4. 本节最该记住的结论：资源模型、统计链和规则链把算法变成调用链中的判断点；单机限流和分布式限流不是一回事，需要区分"每实例独立预算"和"全局共享预算"

## 四、熔断与降级：下游已经不健康时，重点不是继续赌成功，而是停止放大故障

### 1. 第四个朴素误解：熔断和降级是同一回事

熔断和降级处理的是不同问题：熔断负责在异常或慢调用达到阈值后主动断链，降级负责给被断掉的请求一个可以接受的退路。把两者混写，会导致系统既没有及时断链，也没有准备可接受的回退路径。

### 2. 熔断状态机与降级策略的最小图

```text
熔断器状态机:
  closed:
    正常放行并统计慢调用/异常比例/异常数
  open:
    直接拒绝, 不再把请求送给不健康下游
  half-open:
    放少量探测请求
      成功 → 回到 closed
      失败 → 回到 open

降级策略:
  读降级 → 缓存/默认值/空结果
  写降级 → 异步落队列/延迟处理/稍后补偿
  功能降级 → 暂时关闭非核心链路
```

### 3. 为什么熔断不等于降级

因为熔断解决"要不要继续打这个下游"，降级解决"这次不打了，用户看到什么"。把两者混写，会导致系统既没有及时断链，也没有准备可接受的回退路径。熔断条件依赖时间窗与最小样本量——窗口过短会对偶发抖动过敏，窗口过长会对真实故障反应太慢。

### 4. 本节最该记住的结论：熔断是是否还要继续尝试访问下游，降级是不继续访问后下一个返回方案是什么；两者不是同一层概念

一句最短人话是：**熔断像电路里的断路器，检测到短路就先切断电源；降级像停电后的应急灯，不解决供电问题，但让人不至于立刻陷入黑暗。**

## 五、隔离、超时与重试：故障真正可怕的不是一次失败，而是失败被无限传播和放大

### 1. 第五个朴素误解：下游抖一下，上游统一开启三次重试就好

额外重试会把失败请求重新复制一遍，队列会把短时故障拖成长时间积压，而过长超时会让无效等待持续占据资源。很多系统不是被原始故障打垮，而是被自己的重试和排队打垮。

### 2. 隔离/超时/重试的最小图

```text
隔离:
  线程池隔离
    不同依赖/接口用不同执行资源
    好处: 故障边界清晰
    代价: 线程切换、队列和内存成本更高

  信号量隔离
    限制同时进入的请求数
    好处: 轻量
    代价: 不解决已占用线程的等待问题

超时预算:
  总 deadline
    → 拆给上游/中间层/下游
    → 越往下游预算越短
    → 不能每一层都各等一遍完整超时

重试:
  只对适合重试的失败做有限重试
  → 退避
  → 抖动
  → 限制重试比例
  → 避免和排队、熔断、全链路超时互相打架
```

### 3. 为什么很多系统不是被原始故障打垮，而是被自己的重试和排队打垮

因为额外重试会把失败请求重新复制一遍，队列会把短时故障拖成长时间积压，而过长超时会让无效等待持续占据资源。线程池、Future 和队列会把失败表现成大量等待线程，而不是立刻可见的错误。重试也必须和幂等性、失败类型、限流和熔断策略一起设计，否则最容易形成重试风暴。

### 4. 本节最该记住的结论：隔离决定故障能传播多远，超时决定等待能持续多久，重试决定失败后是否再次施压；三者必须和限流、熔断一起设计，否则重试风暴会把局部抖动放大成系统性雪崩

## 六、把本篇收成一张图：流量治理是把拒绝、等待、降级、探测和恢复放在正确的位置

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：秒杀流量到来时，为什么"机器还活着，数据库却先死了"。答案已经闭环了：系统吞吐取决于最慢、最脆弱且最难扩展的那一层，流量治理要在请求抵达瓶颈前就做削峰、排队、拒绝和降级。限流算法决定怎样约束突发与精度，规则落地决定限哪里而不是只会配阈值，熔断负责主动断链，降级负责兜底方案，隔离/超时/重试负责限制爆炸半径和恢复节奏。

把这一切压成最短总图，就是：

```text
入口限流:
  控制总体来水量, 防止瞬时峰值直接压到核心资源

应用层限流:
  按资源/调用方/热点维度做细粒度配额控制

熔断:
  下游不健康时主动断链, 避免继续占用资源

降级:
  断链后给出缓存/默认值/延迟处理等兜底方案

  限制爆炸半径, 控制等待时长, 约束恢复节奏
```

所以本篇最该记住的一句话是：**高并发系统的稳定性不是来自把每个请求都处理完，而是来自明确哪些请求该立即拒绝、哪些可以等待、哪些需要降级、哪些必须停止重试。**

## 七、几个最容易说错的地方

### 限流是在限制能力？

不是。它是在保护真正的瓶颈资源，让系统在过载时仍保持边界感。

### 熔断和降级差在哪？

熔断决定还要不要打下游，降级决定不打后怎么回复用户；两者不是同一层概念。

### 为什么重试会把系统打崩？

因为它会复制失败流量，与排队和超时一起放大过载。

### 令牌桶一定优于漏桶？

不是。允许突发的令牌桶更适合入口吸收抖动，追求稳定输出的漏桶更适合贴近受保护资源。

### 加机器就能解决过载？

不是。很多瓶颈根本不在线性扩容路径上：数据库写能力、热点行锁、下游 API 配额都可能先达到上限。

## 收束：流量治理不是证明前端能扛住更高 QPS，而是让系统在过载时仍保持边界感

回到开头那个问题：秒杀流量到来时，为什么"机器还活着，数据库却先死了"。答案已经闭环了：因为系统吞吐取决于最慢、最脆弱且最难扩展的那一层。流量治理要做的不是"把所有请求都接住"，而是明确哪些请求该立即拒绝、哪些可以等待、哪些需要降级、哪些必须停止重试。限流、熔断、降级、隔离、超时和重试不是独立的组件功能，而是一组协作边界，共同让系统在过载时仍保持边界感。

这就是为什么说：**高并发系统的稳定性不是来自把每个请求都处理完，而是来自明确哪些请求该立即拒绝、哪些可以等待、哪些需要降级、哪些必须停止重试。** 只要这条主线站稳，下一篇进入缓存时，你就不会再把"缓存命中很快"当作理所当然，而会自然去问：缓存没命中时为什么又会把数据库重新打穿，穿透、击穿和雪崩分别在哪里发生。
