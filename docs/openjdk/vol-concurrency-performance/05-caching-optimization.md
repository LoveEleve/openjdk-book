## 现在真正该问的，不再是"缓存命中有多快"，而是"失效时谁负责保护源站，更新时允许多旧"

前几篇把线程、并发容器、同步原语和流量治理的基础讲清楚了。现在要把视角推进到另一个关键层面：**缓存换来的读延迟背后，是一致性、淘汰、失效和故障的完整代价。**

很多人以为缓存就是"加了就快"：查一次缓存，命中就返回，没命中就查数据库然后回种。但真实的选择远比这复杂。缓存副本天然可能落后于源数据，本地缓存容量有限需要淘汰策略，Cache-Aside 的读写顺序可能留下并发窗口，穿透、击穿和雪崩的根因和防线完全不同。所以缓存优化不是"把命中率推到最高"，而是看：

- **命中时足够快**：多级缓存的读路径如何设计？
- **失效时不击穿**：穿透、击穿、雪崩分别用什么防线？
- **更新时说得清允许多旧**：Cache-Aside 的删除与更新、最终一致边界在哪里？
- **故障时不把源站当最后一个无限容量的缓存**：多级兜底和限流如何配合？

先把总图记住：

```text
缓存收益:
  用空间与副本管理换取更短读路径

缓存代价:
  淘汰、旧值、失效竞态、容量上限和故障恢复

稳定读链路:
  命中 → 快速返回
  miss → 合并回源
  更新 → 可靠失效/刷新
  故障 → 旧值/降级/限流/受控回源
```

这篇最该先记住的一句话是：**缓存优化的核心不是把命中率推到最高，而是让命中时足够快、失效时不击穿、更新时说得清允许多旧、故障时不把源站当最后一个无限容量的缓存。**

## 一、缓存边界：每一份副本都在用一致性换延迟

### 1. 最朴素的错误世界：缓存就是数据库的透明加速器

这个想法在"加了缓存就快"的假设下很常见，但缓存引入了独立的容量上限、淘汰决策、失效时序和故障恢复路径。从 CAP/BASE 的视角看，缓存副本往往是在可用性、分区容忍和读延迟与强一致之间做业务选择，而不是免费获得更高吞吐。

### 2. 多级缓存的最小图

```text
请求读取:
  浏览器/客户端缓存
    → CDN/边缘缓存
    → 反向代理缓存
    → 进程内本地缓存
    → Redis 等分布式缓存
    → 数据库/源服务

命中:
  在更靠前的层返回

未命中或失效:
  继续向后访问
  → 读取源数据
  → 按一致性策略回种副本
```

### 3. 为什么缓存不能被当作数据库的"透明加速器"

因为它引入了独立的容量上限、淘汰决策、失效时序和故障恢复路径。缓存层越靠近用户，通常越能减少网络和源站压力，但副本数量、失效传播路径和一致性成本也会增加。不是所有数据都适合缓存——实时性和正确性要求很高的数据可能需要读主库，体积大但访问稀疏的数据不值得占用热缓存。

### 4. 本节最该记住的结论：缓存用空间和副本管理换取更短读路径，但副本天然可能落后于源数据；不是所有数据都适合缓存

一句最短人话是：**多级缓存像城市周边的仓储网络——家门口的小仓库最快，但库存最少、补货最复杂；中央仓库更完整，却需要更长运输路径。**

## 二、本地缓存淘汰：Caffeine 为什么要防止一次扫描污染整个缓存

### 1. 第二个朴素误解：本地缓存容量越大越好，淘汰策略不重要

只按最近访问淘汰的 LRU 很容易受到扫描污染：一次全表扫描会让大量只访问一次的数据短暂变成"最近使用"，挤掉长期热点。频率信息可以帮助淘汰策略区分偶尔访问和反复访问。

### 2. W-TinyLFU 的最小图

```text
W-TinyLFU:
  新进入的数据
    → 先进入 Window 区

  Window 满
    → 选择候选者与 Main 区受害者比较访问频率
    → 候选者更有价值? 晋升
    → 否则淘汰候选者

频率统计:
  多组哈希映射到计数器
  → 用较少空间估计访问频率
  → 只用于淘汰决策, 不作为业务事实
```

### 3. 为什么不直接维护每个 key 的精确频率

因为精确统计会增加内存、更新和并发维护成本，而淘汰只需要相对排序。近似统计把资源留给缓存数据本身，用可接受的误差换取更好的空间效率。Count-Min Sketch 的误差边界适合淘汰判断，不适合精确报表。

### 4. 本节最该记住的结论：W-TinyLFU 将新数据的短期机会和长期频率分开处理，目标是降低扫描污染；近似统计用可接受的误差换取更好的空间效率

## 三、Cache-Aside：缓存和数据库怎样协作才不会互相覆盖

### 1. 第三个朴素误解：先删缓存还是先写数据库是一个二选一的面试题

线上真正危险的是并发读写交错：一个线程正在从数据库回种旧值，另一个线程已经完成了更新和失效。"更新数据库后删除缓存"通常比"更新后直接更新缓存"更容易保持简单边界，但删除并不自动等于强一致。

### 2. Cache-Aside 的最小图

```text
读:
  查缓存
  命中 → 返回
  未命中 → 查数据库
          → 按策略写入缓存
          → 返回

写:
  更新数据库
  → 删除缓存
  → 后续读 miss 时重新加载
```

### 3. 为什么"更新数据库后删除缓存"比"更新后直接更新缓存"更好

因为删除是幂等动作，不需要在缓存层复制完整的写入并发逻辑；直接更新缓存则可能出现多个写者乱序覆盖。但删除并不自动等于强一致，读回种、删除失败、消息延迟和多级缓存都会留下窗口。典型竞态是：读线程先 miss，写线程完成数据库更新并删除缓存，读线程随后把此前读到的旧值回种。

### 4. 本节最该记住的结论：Cache-Aside 把缓存当作旁路副本，应用显式负责读 miss 的回种和写操作后的失效；删除比更新更简单，但不能凭一个删除动作消除所有并发窗口

## 四、穿透、击穿与雪崩：缓存失效时，先判断是哪一种空

### 1. 第四个朴素误解：缓存失效了就是"缓存容量不够"

三类问题的共同结果是"请求回到了源站"，但根因和保护对象不同。穿透是不存在的数据反复进入源站，击穿是单个热点的并发加载，雪崩是大量副本同时失效。错误匹配方案只会增加复杂度而不减少回源。

### 2. 穿透/击穿/雪崩的最小图

```text
穿透:
  请求的数据不存在
  → 每次都 miss
  → 反复访问数据库
  防线:
    布隆过滤器先挡确定不存在的 key
    缓存空值并设置合适的短 TTL

击穿:
  一个热点 key 失效
  → 大量请求同时加载同一份数据
  防线:
    分布式锁或 SingleFlight 合并加载
    逻辑过期 + 后台刷新
    配合限流和超时保护源站

雪崩:
  大量 key 在相近时间失效
  → 大量回源同时发生
  防线:
    TTL 加随机扰动, 分散失效时间
    多级缓存/旧值兜底
    限流、熔断和分批刷新
```

### 3. 为什么三个经典问题不能共用一个固定答案

因为穿透是不存在的数据反复进入源站，击穿是单个热点的并发加载，雪崩是大量副本同时失效。它们分别需要过滤、合并和离散化。布隆过滤器的"否"可以排除不存在的 key，但"是"只代表可能存在；SingleFlight 更适合在同一进程内合并请求，跨实例时不能假设它自动具有全局效果。

### 4. 本节最该记住的结论：穿透需要布隆过滤器+空值缓存，击穿需要分布式锁或 SingleFlight 合并加载，雪崩需要 TTL 随机扰动+多级兜底；三者防线完全不同

## 五、多级缓存与热点：本地、Redis、消息和 TTL 怎样形成一条可恢复的读链路

### 1. 第五个朴素误解：两级缓存就是"L1 快、L2 稳"的简单叠加

每增加一层就增加一份副本和一条失效路径。真正的系统设计必须回答更新消息丢了怎么办、L1 旧值能留多久、L2 挂了是否回源、热点是否被分散以及恢复时如何避免二次洪峰。

### 2. 多级缓存的最小图

```text
读:
  查 L1 本地缓存
  miss → 查 L2 Redis
  miss → 查数据库/源服务
        → 回种 L2
        → 回种 L1

更新:
  源数据提交
  → 删除或更新 L2
  → 发布失效/更新消息
  → 各实例处理 L1
  → TTL 与对账任务作为兜底

故障:
  L2 不可用或热点过载
  → 旧 L1/本地兜底?
  → 限流/降级?
  → 是否允许回源?
```

### 3. 为什么两级缓存不是"L1 快、L2 稳"的简单叠加

因为每增加一层就增加一份副本和一条失效路径。更新消息丢了怎么办、L1 旧值能留多久、L2 挂了是否回源、热点是否被分散以及恢复时如何避免二次洪峰，这些问题都必须显式回答。消息更新 L2 后，L1 异步失效并不等于瞬时一致。

### 4. 本节最该记住的结论：多级缓存必须同时设计读路径、更新路径、过期路径和故障路径；不是多放一层，而是定义 L1/L2 的更新、失效、故障和恢复顺序

## 六、把本篇收成一张图：缓存命中只是成功的一半，失效路径才决定源站是否安全

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：读延迟降下来了，为什么用户仍看到旧状态，数据库还会突然被打满。答案已经闭环了：缓存用空间和副本管理换取更短读路径，但副本天然可能落后于源数据。淘汰策略决定本地缓存空间有限时谁留下，Cache-Aside 决定缓存和数据库怎样协作，穿透/击穿/雪崩的防线各不相同，多级缓存必须同时设计读、更新、过期和故障四条路径。

把这一切压成最短总图，就是：

```text
缓存收益:
  用空间与副本管理换取更短读路径

缓存代价:
  淘汰、旧值、失效竞态、容量上限和故障恢复

稳定读链路:
  命中 → 快速返回
  miss → 合并回源
  更新 → 可靠失效/刷新
  故障 → 旧值/降级/限流/受控回源
```

所以本篇最该记住的一句话是：**缓存优化的核心不是把命中率推到最高，而是让命中时足够快、失效时不击穿、更新时说得清允许多旧、故障时不把源站当最后一个无限容量的缓存。**

### 缓存就是数据库的透明加速器？

## 收束：缓存优化的核心不是命中率，而是失效路径才决定源站是否安全

回到开头那个问题：读延迟降下来了，为什么用户仍看到旧状态，数据库还会突然被打满。答案已经闭环了：缓存用空间和副本管理换取更短读路径，但副本天然可能落后于源数据。淘汰策略、Cache-Aside 一致性、穿透/击穿/雪崩防线和多级缓存协同，共同决定了缓存是否真正保护了源站。

这就是为什么说：**缓存优化的核心不是把命中率推到最高，而是让命中时足够快、失效时不击穿、更新时说得清允许多旧、故障时不把源站当最后一个无限容量的缓存。** 只要这条主线站稳，下一篇进入数据库并发时，你就不会再把"加锁"当作唯一手段，而会自然去问：读写分离、分库分表、乐观锁、悲观锁和死锁分别在哪里发生。
