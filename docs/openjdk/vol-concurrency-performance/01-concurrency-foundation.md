## 现在真正该问的，不再是“系统有多少个线程”，而是“线程在哪里排队、在等什么，以及为什么等待的位置决定了系统的吞吐边界”

很多系统在遇到性能瓶颈时的第一反应是：

- 加 CPU；
- 加线程；
- 加连接池。

但问题往往不是“资源不够”，而是“资源用在了错误的位置”。加核对 IO 密集型任务帮助有限，加线程只会增加上下文切换，加连接池可能把应用等待搬进数据库。

所以高并发优化的第一课，不是“调大线程数”，而是先搞清楚：**系统到底在哪里排队？**

- 在 CPU 上排队（CPU bound）？
- 在任务队列里排队（线程池满）？
- 在连接池前排队（数据库连接耗尽）？
- 在锁上排队（共享状态竞争）？

每个排队位置对应不同的优化手段。把排队位置搞错，优化就会做反。

先把总图记住：

```text
线程池:
  控制执行任务数量/任务队列

连接池:
  控制进入数据库/下游的并发

锁/原子:
  保护共享状态

池/锁/线程任一过载:
  → 其他层可能出现假满/排队/超时
  → 需要统一观测与容量建模
```

这篇最该先记住的一句话是：**高并发优化的本质不是把线程数调大，而是决定在哪里排队、在哪里背压、哪些资源必须串行，以及如何让队列不会无限增长。**

## 一、并发与并行：逻辑同时不等于物理同时

### 1. 最朴素的错误世界：系统的线程数越多，在同一时刻干的活也越多

这个想法在“线程 = 干活”的假设下很自然，但线程数增加不一定提高吞吐：

- 线程可能在等待 I/O、锁或下游；
- 线程数增加只会增加上下文切换；
- 加核受益的是 CPU bound 任务，不是等待 bound 任务。

### 2. 并发/并行与 Amdahl 的最小图

```text
concurrency:
  多个任务在时间窗口内推进
  → 单核也可通过时间片交错

parallelism:
  多核同时执行多个任务

Amdahl:
  speedup <= 1 / ((1-P) + P/N)
  → 串行部分限制总体上限

线程过多:
  runnable queue + context switch
  → 保存/恢复状态、缓存/TLB扰动
  → 不一定提高吞吐
```

### 3. 为什么线程池满不一定是 CPU 核数不够

因为线程可能在等待连接、锁、I/O 或下游。线程数增加只会增加排队和上下文切换。并行化前要知道 workload 是 CPU bound 还是等待 bound。而且上下文切换延迟不能用固定微秒数跨平台断言——同一套参数在不同 CPU、内核版本和负载下差异很大。

### 4. 本节最该记住的结论：并发是逻辑同时，并行是物理同时；Amdahl 定律指出串行部分限制加核收益；线程过多不一定提高吞吐，如果线程在等锁或 I/O，加线程只是增加上下文切换

一句最短人话是：**并发像多个订单同时在处理，只有并行才是多个工位同时加工；增加订单不等于增加工位。**

## 二、Java Thread 与 Virtual Thread：执行实体的不同成本

### 1. 第二个朴素误解：虚拟线程能创建很多，所以 CPU 密集任务也能无限并行

虚拟线程的价值在于减少阻塞任务的线程栈/调度成本，但 CPU 核数、锁、数据库连接和下游容量仍然是瓶颈。“百万虚拟线程”是模型能力，不是业务吞吐承诺。

### 2. 平台线程与虚拟线程的最小图

```text
platform thread:
  JVM thread ↔ OS schedulable thread
  → 独立栈/寄存器/调度实体
  → 可真正多核并行

Java thread states:
  NEW → RUNNABLE/BLOCKED/WAITING/TIMED_WAITING → TERMINATED
  RUNNABLE 不保证当前正在 CPU 上运行

virtual thread:
  用户态任务/continuation
  → 由少量 carrier/platform threads 承载
  → 阻塞可被 runtime 处理时让出 carrier
  → 仍受 pinning、CPU、内存和同步模型限制
```

### 3. 为什么虚拟线程能创建很多，却不能把 CPU 密集任务无限并行

因为它受 CPU 核数、锁、数据库连接和下游容量限制。虚拟线程解决了阻塞任务的栈和调度成本，但没有消灭瓶颈本身。

### 4. 本节最该记住的结论：平台线程由 OS 调度，虚拟线程由用户态承载；虚拟线程减少阻塞任务的栈/调度成本，但 CPU 核数、锁和下游容量仍是瓶颈

## 三、ThreadPoolExecutor：队列策略决定系统如何过载

### 1. 第三个朴素误解：`newFixedThreadPool` 是安全的，因为线程数固定

`newFixedThreadPool` 虽然线程数固定，但它的工作队列是无界的 `LinkedBlockingQueue`。如果任务提交速率持续超过处理速率，队列会无限增长，最终 OOM。

### 2. 线程池的最小状态机

```text
submit(task)
  → worker < corePoolSize?
      创建 worker
  → 否则 queue 未满?
      入队
  → 否则 worker < maximumPoolSize?
      创建额外 worker
  → 否则 rejection handler

队列:
  SynchronousQueue → 无容量, 直接交给 worker
  bounded queue → 有限背压
  unbounded queue → 可能隐藏内存/延迟无限增长

拒绝:
  Abort / CallerRuns / Discard / DiscardOldest
  → 不同的数据丢失/背压语义
```

### 3. 为什么“最大线程数”在使用无界队列时可能几乎不起作用

因为任务先进入队列，池不会轻易扩展到 maximum。队列策略实际上决定请求在何处排队。线程数公式只能作为初始估计，最终要按 CPU/等待比例、任务时长、下游容量和尾延迟压测。不存在所有业务通用的最佳值。

### 4. 本节最该记住的结论：线程池是“线程数 + 工作队列 + 拒绝策略”的联合状态机；无界队列可能隐藏无限增长，有界队列和拒绝策略才是真正的背压控制

一句最短人话是：**线程池像餐厅：先开固定桌位，再排队；队列无限长看起来不拒客，却会让客人和食材一起过期。**

## 四、连接池：数据库连接是稀缺资源和背压阀

### 1. 第四个朴素误解：线程池大了，连接池也该跟着一起放大

这个想法忽略了连接池的角色：它不只是复用连接，更是**限制进入数据库的并发量**。线程池放大但连接池不放大，大量线程会在连接池前排队；但连接池放大，数据库的锁、CPU、I/O 竞争也会增加。

### 2. 连接池的最小图

```text
request
  → borrow connection
  → 无空闲连接?
      等待/超时
  → 执行 SQL/事务
  → reset state
  → return connection

池太小:
  应用线程在池前排队

池太大:
  数据库锁/CPU/I/O/上下文竞争增加
  → QPS 未升, P99 变差
```

### 3. 为什么连接池大小不等于 QPS 上限

因为 QPS 还受事务时间、数据库并发、锁、I/O 和 SQL 成本影响。连接数调大可能只是把应用等待搬进数据库。HikariCP 等实现的内部优化不能替代容量模型。

### 4. 本节最该记住的结论：连接池限制进入数据库的并发，是应用与数据库之间的背压阀；池太小让应用线程排队，池太大把竞争搬进数据库

## 五、锁升级与 CAS：共享状态安全也有竞争成本

### 1. 第五个朴素误解：CAS 是无锁的，所以没有竞争成本

CAS 确实比重量级锁轻，但高竞争下 CAS 重试次数增加、缓存一致性流量上升，成本并不低。

### 2. 锁/CAS 的最小图

```text
synchronized/monitor:
  进入/退出对象监视器
  → 低竞争与高竞争可能走不同快速/阻塞路径

CAS:
  compare(expected, desired)
  → 成功更新
  → 失败重试/退避

高竞争:
  CAS 重试/缓存一致性流量上升
  锁膨胀/线程阻塞/调度成本上升
```

### 3. 为什么不能背“偏向锁→轻量锁→重量锁”当作所有现代 JDK 的固定实现

因为锁实现、偏向锁策略和 JVM 版本持续变化。性能取决于竞争、临界区、线程调度和数据布局。优化前需用锁/CPU/等待工具证明热点。

### 4. 本节最该记住的结论：CAS 不是无成本，高竞争下重试和缓存一致性流量上升；JVM 锁实现随版本变化，优化前必须用工具证明热点

## 六、把本篇收成一张图：高并发是在决定在哪里排队、在哪里背压

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：线程池满、连接池满、CPU 加核后仍然慢，真正排队在哪里。答案已经闭环了：排队可能在 CPU、任务队列、连接池前或锁上。每个排队位置对应不同的优化手段，把排队位置搞错，优化就会做反。

线程池是“线程数 + 队列 + 拒绝策略”的联合状态机。连接池是应用与数据库之间的背压阀。锁和 CAS 保护共享状态但引入竞争成本。高并发优化的本质不是把线程数调大，而是决定在哪里排队、在哪里背压、哪些资源必须串行，以及如何让队列不会无限增长。

把这一切压成最短总图，就是：

```text
线程池:
  控制执行任务数量/任务队列

连接池:
  控制进入数据库/下游的并发

锁/原子:
  保护共享状态

池/锁/线程任一过载:
  → 其他层可能出现假满/排队/超时
  → 需要统一观测与容量建模
```

所以本篇最该记住的一句话是：**高并发优化的本质不是把线程数调大，而是决定在哪里排队、在哪里背压、哪些资源必须串行，以及如何让队列不会无限增长。**

## 七、几个最容易说错的地方

### 线程数越多，在同一时刻干的活也越多？

不是。线程可能在等锁、I/O 或下游，增加线程只是增加上下文切换。

### 虚拟线程很多，所以 CPU 密集任务也能无限并行？

不是。虚拟线程减少阻塞的栈成本，但 CPU 核数、锁和下游容量仍是瓶颈。

### `newFixedThreadPool` 是安全的，因为线程数固定？

不是。它的无界工作队列可能让任务无限堆积，最终 OOM。

### 连接池大小应该和线程池一样大？

不是。连接池是限制进入数据库的并发量，放大连接池可能把竞争搬进数据库。

### CAS 是无锁的，所以没有竞争成本？

不是。高竞争下 CAS 重试次数增加，缓存一致性流量上升，成本并不低。

## 收束：高并发优化的第一课，不是调大线程数，而是先搞清楚系统到底在哪里排队

回到开头那个问题：线程池满、连接池满、CPU 加核后仍然慢，真正排队在哪里。答案已经闭环了：排队可能在 CPU、任务队列、连接池前或锁上。每个位置对应不同的优化手段。高并发优化的本质不是把线程数调大，而是决定在哪里排队、在哪里背压、哪些资源必须串行，以及如何让队列不会无限增长。

这就是为什么说：**高并发优化的本质不是把线程数调大，而是决定在哪里排队、在哪里背压、哪些资源必须串行，以及如何让队列不会无限增长。** 只要这条主线站稳，下一篇进入并发数据结构时，你就不会再把 ConcurrentHashMap、CopyOnWrite、Disruptor 和 BlockingQueue 看成“更快的数据结构”，而会自然去问：它们到底在哪一层减少了锁竞争，又把排队转移到了哪里。
