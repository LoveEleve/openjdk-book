## 先看真正的冲突：watch/trace 已经能看现场了，为什么还要 profiler

场景：前面几组文章里，Arthas 已经有了一整套非常强的“插桩式观察”能力：

- `thread` 能先缩到热点线程；
- `trace` 能看某个方法内部调用树；
- `watch` 能看参数、返回值、异常和 `cost`；
- `ognl` 甚至能直接读对象和静态成员。

于是一个很自然的直觉就会冒出来：

> 既然我都能织进去看现场了，为什么还需要 profiler / async-profiler 这条 native 采样链？

反过来，另一种同样危险的误解也会出现：

> 既然 profiler 能画全局火焰图，那是不是也能顺便看参数、返回值和单次调用现场？

这两种想法都把边界讲坏了。因为它们混淆了两类完全不同的问题：

- 插桩观察关心的是：**这一次调用里发生了什么**；
- 采样观察关心的是：**在整个观察窗口里，整体时间花在哪里**。

所以本篇真正要回答的不是：

> async-profiler 里有哪些 native 细节？

而是：

> **Arthas 已经能通过 ByteKit 在方法里插桩、用 OGNL 看对象、用 thread 看热点，那为什么它还需要 profiler / async-profiler 这条 native 采样链？反过来，既然 profiler 能画全局火焰图，为什么它又不能取代 trace/watch 这种插桩观察？**

先把全篇总图立住：

```text
thread -n / thread <id>
  → 瞬时线程视角

profiler
  → 时间窗口里的聚合热点视角

trace / watch
  → 已缩小目标后的方法内部 / 单次调用视角
```

这张图里最重要的一刀就是：

```text
采样负责缩范围
插桩负责解释细节
```

后面所有细节，都围绕这条边界展开。

## 一、先排除两个最直觉、也最容易把观察边界讲坏的方案

### 1. 全都靠插桩观察

一个最直觉的想法是：

> trace/watch 都这么强了，那 CPU、alloc、lock、wall 这些问题是不是也都靠插桩来解决？

这会立刻踩中成本边界。因为插桩的特点是：

- 你关心哪个方法，就得改哪个方法；
- 每次命中都要付出额外回调和表达式成本；
- 更适合少数目标、少量现场、明确入口。

如果把它拿去回答“整个进程这 30 秒里 CPU 都花哪了”这种问题，代价会和方法调用次数、织入范围一起膨胀。

所以插桩的强，不在于它能回答所有问题，而在于它能非常精确地解释**已经缩小后的**问题。

### 2. 全都靠采样观察

反过来，一个同样常见的误解是：

> profiler 都能把热点画成火焰图了，那参数、返回值、异常和调用现场是不是也能顺带看？

这也不行。因为采样的本质是：

- 按时间窗口抽样；
- 聚合调用栈命中频度；
- 给你一个统计意义上的整体热点分布。

它天然不保证：

- 某一次调用的参数是什么；
- 某一次调用抛了什么异常；
- 某一次返回值是不是错了。

所以 profiler 的强，不在于“什么都能看”，而在于它能低侵入地回答：**整体时间到底花在哪里。**

关键设计（斜体）：*插桩和采样不是同一把更细或更粗的尺子，而是两种本质不同的观察范式。*[模式: 单次现场 vs 窗口聚合] 如果强行只选其中一种：要么你会为了整体热点把大量方法都织入，每次命中都付出回调成本；要么你会拿火焰图去猜参数、返回值和异常，把“统计频度”误当成“这一次调用的事实”。

## 二、第一层：native 库加载问题为什么只是集成前提，不是采样问题本身

### 2.1 profiler 能不能反复 start/stop，首先受 native 加载身份影响

`ProfilerCommand.profilerInstance()`（`ProfilerCommand.java:551-590`）要先解决一个非常现实的问题：如果 stop 后再 start，同一个 `.so` 以相同路径被不同 ClassLoader 再次加载，可能触发：

```text
Native Library already loaded in another classloader
```

所以 Arthas 在 `ProfilerCommand.java:561-580` 里会把 native 库复制到临时文件，再调用 `AsyncProfiler.getInstance(libPath)`。

### 2.2 为什么这不能被误讲成“采样算法的一部分”

这条链很重要，但它解决的是：

- native 库加载身份；
- 多次 attach / stop / start 的可重复性；
- 类加载器边界下的 native 复用问题。

它并不回答：

- CPU 栈怎么采；
- wall-clock 事件怎么触发；
- alloc / lock 为什么能被记录。

关键设计（斜体）：*native 加载身份适配是 profiler 命令层的集成前提，不是采样算法本体。*[模式: 加载前提与能力本体分离]

所以这一步的意义，是保证 Arthas 能稳定“接上” async-profiler，而不是解释 async-profiler 本身怎么采样。

## 三、第二层：插桩观察和采样观察到底在回答什么不同问题

### 3.1 插桩回答的是“这一次调用里发生了什么”

前面 AR-2 的 `watch/trace` 已经建立了插桩观察链：

- `watch`：参数、返回值、异常、耗时；
- `trace`：方法内部调用点树；
- `tt`：一次调用现场的历史记录与重放。

它们的共同特点是：观察点直接钉在业务方法上，所以知道的是**单次调用语义**。

但代价也很明确：每次命中这个方法，都要付出织入和 listener 回调成本。

### 3.2 采样回答的是“整个窗口里时间主要花在哪里”

profiler 走的是另一条路：不修改业务方法，而是在采样时刻记录线程当前调用栈。

它回答的是：

- 整个观察窗口里，哪条调用路径最热；
- 哪类分配、锁竞争或阻塞事件最常出现。

所以它并不关心“这一次调用参数是什么”，而关心“这一段时间里哪条路径总被命中”。

关键设计（斜体）：*插桩看现场，采样看分布；前者精确，后者全局。*[模式: 调用级语义 vs 时间窗口聚合]

### 3.3 为什么这两种工具常常要按顺序组合

也正因为边界不同，线上排查经常会形成这样一条顺序：

```text
thread -n 先看热点线程
  → profiler 看整体热点路径
    → trace 下钻某个方法内部调用树
      → watch 看参数、返回值和异常
```

它们不是互相替代，而是在一步步把问题从“全局热区”收缩到“具体方法”和“具体这次调用”。

## 四、第三层：async-profiler 为什么能覆盖 JVM / Java / native 的整体热点

### 4.1 Arthas 自己不做这件事，但 async-profiler 本体就是为它设计的

Arthas 只把字符串交给 `one.profiler.AsyncProfiler`，真正的多来源采样能力在 async-profiler 本体里。当前源码路径里可以看到：

- CPU engine 的信号处理在 `async-profiler/src/cpuEngine.cpp`；
- wall-clock 模式在 `src/wallClock.cpp`；
- Linux perf 路径在 `src/perfEvents_linux.cpp`；
- JVM 入口和 JVMTI 相关能力在 `src/vmEntry.cpp`；
- alloc / lock 事件又会启用对应的 JVMTI 或 native 路径。

这说明 profiler 回答“整体热点”时，并不依赖单一实现，而是：**在 native / JVM / JVMTI 多条路径上拿到可聚合的调用栈与事件。**

### 4.2 为什么这正好是 Arthas 不该自己重复实现的东西

如果 Arthas 再自己做一遍：

- 它得重新处理 perf、信号、JVMTI、JFR、输出格式、平台边界；
- 还得重复面对 Linux / Mac、权限、类加载、native 栈展开这些问题。

所以“让 async-profiler 做采样本体，Arthas 做命令入口和结果包装”并不是偷懒，而是架构分工。

关键设计（斜体）：*Arthas 需要 profiler，不是因为它缺命令系统，而是因为整体热点这件事本来就属于 native 采样引擎的长项。*[模式: 命令层与引擎层分工]

## 五、第四层：火焰图为什么不是时间线，而 trace 树又为什么不是火焰图

### 1. 火焰图宽度回答的是频度，不是单次耗时顺序

火焰图最容易被读错的地方在于：横轴不是时间线，而是样本聚合宽度；纵轴表示栈深。

- 块越宽：该调用栈被采样命中的次数越多；
- 块越高：栈越深；
- 底部到顶部：调用者到被调用者。

所以它回答的是：

```text
这段观察窗口里，哪条路径最常被命中
```

而不是：

```text
某一次调用先做了什么、后做了什么
```

### 2. `--event` 不同，火焰图语义也会跟着变

CPU、alloc、lock、wall-clock 这些事件即使都能画成“火焰图形状”，含义也不同：

- CPU：CPU 时间热点；
- alloc：分配热点；
- lock：锁竞争热点；
- wall-clock：阻塞和等待路径。

同样的宽块，不同事件下不能按同一种语义读。

### 3. trace 树更接近“这一次调用里发生了什么”

而 `trace` 的树，回答的则是：

- 这一次调用内部又调用了谁；
- 调用点之间是什么关系；
- 单次路径上的耗时分布在哪里。

也就是说，火焰图和 trace 树不是“一个更漂亮、一个更朴素”的同类输出，而是两种时间语义完全不同的观察模型。

关键设计（斜体）：*火焰图看窗口内的聚合频度，trace 树看一次调用里的结构与耗时。*[模式: 聚合视图 vs 单次路径视图]

## 六、第五层：输出格式为什么本质上是消费方式差异

### 1. html / flamegraph 给人看整体热区

当你要快速回答“热区在哪”，html / flamegraph 非常适合，因为它把聚合热点压成一眼可扫的宽块结构。

### 2. collapsed 给其他火焰图或后处理工具继续消费

collapsed 文本不一定是终端最终读物，它更像一份中间结果，给别的工具继续处理。

### 3. Markdown 不是 async-profiler 原生格式

这一点在上一篇已经建立：Markdown 是 Arthas 在 `processStopMarkdown()` 中先拿 collapsed，再在命令层做二次聚合和渲染。它不是 async-profiler 原生输出能力。

所以输出格式不只是“展示皮肤不同”，本质上是在决定：

```text
谁是这份采样结果的最后消费者
```

关键设计（斜体）：*输出格式之分，本质上是消费方式之分。*[模式: 结果消费者边界]

## 收网：采样缩范围，插桩解释细节

现在把整条链收成一张图：

```text
thread -n / thread <id>
  → 找热点线程和瞬时栈
profiler
  → 看时间窗口里的整体热点
trace
  → 看某个方法内部调用树
watch
  → 看单次调用参数、返回值、异常
ognl
  → 直读对象与静态成员状态
```

把这张图压成一句话，就是：

**Arthas 需要 profiler / async-profiler，不是因为 watch/trace 不够强，而是因为插桩观察和采样观察本来就在回答不同问题：采样负责低侵入地缩小整体热点范围，插桩负责在已经缩小的问题上解释单次调用细节；二者不是替代关系，而是先后协作关系。**

到这里为止，主线其实只发生了四件事：

- native 加载问题只是集成前提，不是采样本体；
- 插桩和采样分别回答“单次现场”和“窗口分布”；
- async-profiler 擅长拿到 JVM/Java/native 的整体热点，而 Arthas 不该重做这件事；
- 火焰图、trace 树和 Markdown 本质上对应不同消费方式与时间语义。

这也解释了为什么线上排查经常先 profiler、再 trace/watch：**先用采样缩范围，再用插桩解释细节，才是两种观察范式最稳定的组合方式。**
