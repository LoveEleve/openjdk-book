> → **后续**：AR-2 Watch/Trace——Transformer 怎样把业务方法变成可观察的方法。
> 关联域：36-attach、47-instrumentation、Netty 事件循环。

## 先看一个最容易误判的现场：attach 明明成功了，为什么用户还是连不上

场景：上一章的问题已经解决——Arthas 确实通过 Attach API 进了目标 JVM，`AgentBootstrap`、`ArthasClassloader`、`ArthasBootstrap` 和 `SpyAPI` 这套寄生结构也已经住下来。可这时运维端最常见的真实感受却不是“好了，可以用了”，而是另一种更烦的现场：

- 终端根本连不上；
- 端口已经变了；
- tunnel 配了但会话没起来；
- 绑定到了 `0.0.0.0`，却因为密码问题被告警；
- `stop` 之后表面看会话结束了，但你又不敢确定增强、Spy 和类加载器引用到底撤没撤干净。

这类现场背后藏着一个非常容易想错的直觉：

```text
Arthas 已经进 JVM
  =
Arthas 服务已经可用
```

这恰恰是错的。

Arthas 进 JVM，只说明“寄生系统已经住下来”；它还远远不等于“已经开门营业”。真正能不能被用户连上、能不能受控暴露能力、失败时会不会留下半套服务、退出时能不能把增强和 Spy 清干净，都取决于另一条单独的生命周期链：

```text
bind() 负责开门
destroy() 负责撤门
```

所以本篇真正要回答的不是：

> Arthas 进来以后都配置了哪些端口和参数？

而是：

> **Arthas 住进 JVM 之后，怎样把自己安全地变成一个可连接、可认证、可失败回滚、可最终撤走的寄生服务？**

先把全篇总图立住：

```text
ArthasBootstrap 已经在 JVM 内存在
  → bind(configure)
    → 选端口 / 启 tunnel / 建认证 / 注册命令 / 监听终端
      → 确认服务真的可用
        → 最后才激活 SpyAPI
          → 用户会话与增强链开始运行
            → stop / shutdown
              → destroy()
                → 先关服务面，再摘增强面，最后清 Spy 与引用
```

这张图里最重要的两刀是：

```text
进 JVM ≠ 服务可用
bind 与 destroy 必须形成可逆生命周期
```

后面所有细节，都围绕这两条边界展开。

## 一、先排除一个最直觉、也最容易出事故的方案：进 JVM 了，服务就算已经起来了

### 1.1 为什么大家会自然这么想

上一章已经把“住下来”这件事讲清楚了：

- `AgentBootstrap` 接住 `loadAgent`
- `ArthasClassloader` 隔离 `arthas-core.jar`
- `ArthasBootstrap` 完成单例装配
- `SpyAPI` 被提升成所有增强代码共享的全局门面

于是很自然会产生一个错觉：

> 既然系统都已经装配好了，那用户当然应该已经可以连上 Arthas。

如果按这个直觉推下去，整条链会被错误地简化成：

```text
attach 成功
  → Arthas 在 JVM 里
    → 用户应该能连上
```

### 1.2 这个直觉为什么不成立

它解释不了最常见的线上现象：

- 端口可能冲突；
- 配置可能要求随机端口；
- tunnel 可能启动失败；
- 监听地址和认证策略可能不允许你直接暴露能力；
- 命令表可能还没注册完整；
- 终端监听器可能尚未真正 bind 成功；
- Spy 如果过早切到真实实现，还可能让业务增强链打进一个半启动系统。

也就是说，Arthas “在 JVM 里存在”与“Arthas 服务面已经准备好供用户接入”，根本不是同一个状态。

最需要先记住的一句话是：

**寄生成功，只代表 Arthas 已经住下来；服务可用，要求它再完成一整条开门链。**

### 1.3 为什么不能“端口先开起来，其他东西以后慢慢补”

一个直觉性的补救方案是：

> 先把端口开了，认证、命令、Spy 激活、统计、隧道这些后面慢慢补。

这也不行。因为服务面不是若干独立按钮，而是一条有顺序依赖的装配链：

- 端口开了但命令没注册，用户能连上却不能稳定执行命令；
- 认证没准备好就把监听暴露出去，会把高权限诊断能力裸露给不该看到的人；
- Spy 先切到真实实现，但后面的服务还没起来，增强链就可能打到一个半初始化状态；
- bind 半途失败如果不回滚，会留下下一次 attach 无法正确复用的脏状态。

所以本篇不把 `bind()` 当成“若干配置项的集合”，而把它当成一个更严格的问题：

**服务面必须被完整装起来，才算真正可用。**

## 二、第一层：`bind()` 为什么不是 setter 集合，而是一条装配流水线

### 2.1 真正的 bind 问题不是“怎么配”，而是“怎么按顺序成立”

`ArthasBootstrap` 的构造链在前一篇已经提到过，`bind(configure)` 的真正落点在 `ArthasBootstrap.java:175`。而 `bind()` 的主体从 `ArthasBootstrap.java:366` 开始。

它做的并不是“收集一下配置然后 new 两个对象”，而是把一组分散能力装成一套真正可连接的服务面：

- 选择或生成端口；
- 推断应用名并尝试启动 tunnel；
- 创建认证器和 ShellServer；
- 建立命令集合与外部命令 resolver；
- 注册 telnet/http 终端；
- 开始监听并检查 bind 是否真的成功；
- 最后才激活 Spy 和统计旁路。

如果把这条链压成一句话，就是：

```text
bind() = 把“已经住下来的 Arthas”变成“用户真的能连上的 Arthas”
```

### 2.2 为什么顺序不能乱

这里最值得先推演的失败方案就是：

> bind 不就是一堆初始化吗？顺序差一点应该也没关系。

顺序一乱，问题就会立刻暴露：

- 终端开始监听，但命令系统还没注册，用户连上来得到的是半空壳；
- 认证器还没装好，监听器却已经对外暴露；
- tunnel-client 已经开始对外注册，但本地服务面并不完整；
- Spy 提前切换到真实实现，业务字节码开始回调时，服务端和命令链还没准备好。

这也是为什么 bind 的主问题不是“每一步做什么”，而是“为什么这些步骤必须按现在的顺序做”。

关键设计（斜体）：*`bind()` 不是把参数填进几个对象，而是把一套寄生系统按依赖顺序装配成真正可连接的服务面。*[模式: 服务装配流水线] 顺序本身就是设计的一部分；少一步、早一步、晚一步，都会引出不同的半启动风险。

## 三、第二层：端口与 tunnel 如何回答“怎么被连上”

### 3.1 端口 0 为什么不是端口，而是“请在绑定阶段替我找资源”

`bind()` 的第一步之一就是处理端口。`ArthasBootstrap.java:375-383` 显示：当 `telnetPort` 或 `httpPort` 被配置成 `0` 时，Arthas 不会真的监听 TCP 端口 0，而是调用 `SocketUtils.findAvailableTcpPort()` 先找可用端口，再把结果回写到配置对象。

这意味着“端口 0”在这里根本不是一个网络协议层面的最终值，而是一种配置意图：

```text
我不预先占死端口
  → 绑定阶段再按机器现场挑一个真的可用端口
```

如果把这一步提前到更早的配置阶段，就会遇到一个经典问题：你当时看到的“空闲端口”，不等于真正开始监听时它仍然空闲。

关键设计（斜体）：*配置阶段可以表达资源意图，但真正的资源选择要尽量推迟到最终绑定点完成。*[模式: 延迟资源分配] 这样“端口 0”这种意图就不会提前固化成一个可能过时的假答案。

### 3.2 应用名为什么也属于连接面的一部分

`ArthasBootstrap.java:385-389` 会在没有显式 `appName` 时，从 `project.name` 或 `spring.application.name` 回退推断应用名。

这一步看起来像装饰，但它其实也属于连接面。因为一旦涉及 tunnel 或统计上报，远程侧需要的不只是“有一个会话”，还需要知道“这个会话对应哪个应用”。也就是说，连接能力不只是网络可达，还包括可识别性。

### 3.3 tunnel 为什么不是“另一种 attach”

如果配置了 `tunnelServer`，`bind()` 会在 `ArthasBootstrap.java:392-400` 创建并启动 `TunnelClient`：设置应用名、agentId、server URL，然后 `start()`，并等待连接结果。

这里最容易想错成：

> tunnel 是不是另一种把 Arthas 打进 JVM 的方式？

不是。attach 在上一章已经完成了；这里发生的事情，是 Arthas 已经在目标 JVM 内部，开始改写自己的**会话方向**：

```text
普通模式：用户主动连目标 JVM
隧道模式：目标 JVM 主动连 tunnel-server，用户再从中转入口取会话
```

也就是说，tunnel 解决的不是“怎么进 JVM”，而是“进 JVM 之后，在网络不友好的环境里，怎么仍然被连接上”。

关键设计（斜体）：*tunnel 改写的是服务连接方向，不是 agent 注入方式。*[模式: 反向连接 + 会话中转] 入站连接不容易放行时，就把问题改写成目标 JVM 主动建立出站连接。

### 3.4 为什么 tunnel 失败不应直接拖死整个 bind

`ArthasBootstrap.java:401-403` 里一个容易被忽略的细节是：tunnel-client 启动异常会被记录，但不会直接让整个 bind 失败。

这说明作者对 tunnel 的定位非常克制：它是连接面的增强能力，不是 Arthas 本地服务面能否起来的前提条件。如果 tunnel 挂了，就让它退化成“没有隧道”，而不是“整套本地 Arthas 服务都别起来了”。

这恰好符合前面的主线：**连接面可以有多种路径，但本地服务面的成立，不能完全绑死在某一条增强路径上。**

## 四、第三层：安全、命令边界与 ShellServer 为什么必须一起确定

### 4.1 为什么“先开门再补锁”是危险方案

如果把 bind 想成“先把端口开起来，安全以后再说”，最先出事故的就是认证和命令边界。

因为 Arthas 不是一个普通的信息展示页，而是一套高权限诊断系统：

- 能看线程；
- 能看类与字节码；
- 能增强方法；
- 能改变运行时观察方式；
- 能在某些场景下执行带强干预性的命令。

所以“先开门、以后再补锁”的方案在这里天然危险。

### 4.2 为什么监听到 `0.0.0.0` 时必须强制补密码

`ArthasBootstrap.java:405-430` 这一段里，最重要的安全分支是：当监听地址是 `0.0.0.0` 且没有显式密码时，Arthas 会生成随机密码并告警（`ArthasBootstrap.java:415-426`）。

这个设计回答的不是“用户体验要不要更方便”，而是更简单粗暴的问题：

> 你都把诊断端口暴露给整个网段了，凭什么还能默认不设认证？

所以认证不是 ShellServer 外面的一层补丁，而是在创建：

```java
new SecurityAuthenticatorImpl(...)
new ShellServerImpl(options)
```

这一步就已经一起被装进服务面了。

关键设计（斜体）：*认证不是服务起来之后补的一把锁，而是服务面本身的组成部分。*[模式: 接入边界前置] 只要服务是高权限诊断入口，认证与监听器就必须一起成立。

### 4.3 为什么 `disabledCommands` 要在命令表建立时就生效

`ArthasBootstrap.java:432-445` 处理 `disabledCommands` 时，不是“执行命令时临时拦一下”，而是直接把被禁用命令排除出 `BuiltinCommandPack` 的可注册集合。

这意味着命令边界并不是：

```text
命令已经存在
  → 执行时再决定要不要拒绝
```

而是：

```text
命令集合在注册阶段就被裁剪
  → 后续终端根本不把它当成可解析能力
```

这和认证其实属于同一条设计哲学：**不是等用户连上来后再临时打补丁，而是在服务被宣布“可用”之前，就先确定它到底开放哪些能力。**

### 4.4 为什么外部命令解析也属于 bind 主线

`loadExternalCommandResolver` 在 `ArthasBootstrap.java:520-524` 从 `commandLocations` 与 Arthas home 解析额外命令包。它看起来像扩展点，实际上也属于 bind 主线，因为“服务可用”不仅意味着端口在监听，还意味着命令面已经被完整装好。

也就是说，对用户来说，“能连上”从来不只意味着网络通，而意味着：

- 终端协议成立；
- 认证边界成立；
- 命令集合成立；
- 外部扩展也被纳入这套命令图谱。

## 五、第四层：为什么 `SpyAPI` 必须最后激活

### 5.1 这是一个非常容易被写成实现细节、但其实是失败安全机制的问题

现稿里最容易被低估的一点，是 `SpyAPI.init()` 在 `ArthasBootstrap.java:506-510` 出现在 bind 尾部。

如果只把它当成“顺序上靠后的一步”，就会错过它真正解决的风险：

> 如果真实 Spy 太早激活，而服务面还没完整起来，增强后的业务代码一旦回调过来，会打到什么状态的 Arthas？

### 5.2 为什么“先激活 Spy，再慢慢补服务”是危险方案

一个看似合理的方案是：

> Spy 是全局入口，那就早点激活，后面的命令、终端、统计、API 再慢慢补。

这会制造最糟糕的半启动状态：

- 业务增强链已经开始打到真实 Spy；
- 但服务端、命令表、监听器、API Handler 还没全起来；
- 一旦中途失败，就会留下“业务回调已经进入 Arthas，服务面却还没完整成立”的不一致状态。

所以 bind 尾部的顺序其实是在明确表达：

```text
服务面先完整成立
  → 再把 NOPSPY 切到真实 Spy
```

### 5.3 为什么统计旁路和 Spy 激活都被放在最后

绑定成功后，`ArthasBootstrap.java:481-510` 先创建 `SessionManager`、`HttpApiHandler`，再处理可选 MCP server，然后设置统计旁路 `UserStatUtil.arthasStart()`，最后才 `SpyAPI.init()`。

这里的含义是：只要还处在“服务链也许会继续失败”的阶段，Spy 就不该暴露为真实入口。只有当监听、命令、API 与其他支撑面都已经起来时，Spy 才能安全接管业务增强回调。

关键设计（斜体）：*Spy 不该证明“系统开始启动”，而应该证明“服务面已经完整可用”。*[模式: 延迟激活 + 失败安全] 在 bind 前半段失败时，业务代码碰到的仍然只是 NOP；只有真正开门成功后，真实 Spy 才接管入口。

## 六、第五层：bind 失败为什么必须整体回滚

### 6.1 为什么不能留下半套服务等下次覆盖

`ArthasBootstrap.java:513-517` 用 `try/catch` 包住整条服务装配链：如果端口、命令、终端或 API 初始化过程中出错，就先记录错误，再调用 `destroy()`，最后重新抛出异常。

这看起来像“常规清理”，但其实回答了一个很硬的失败方案：

> bind 半途失败，能不能保留已经创建好的那部分，下次 attach 再接着用？

不能。因为“已经创建好的那部分”本身就可能携带脏状态：

- 端口可能已经占上，但监听器没完整起来；
- tunnel 可能启动过，但本地服务面没成功；
- 命令表可能只注册了一半；
- Spy 可能还处在不该切换的边界状态。

所以 bind 的失败语义必须是：

```text
中途失败
  → 清掉已经创建的资源
    → 把系统退回到“尚未开门”的一致状态
      → 再把异常往外抛
```

### 6.2 为什么这还是 attach 成功判定的下游保证

上一章已经提到，`AgentBootstrap` 在桥接 ArthasBootstrap 后，还会用 `isBind()` 检查服务端是否真的起来。这条回指在 `AgentBootstrap.java:184-190`。

所以 bind 是否成功，不只是服务层自己的内部状态，它还反过来决定：

- 这次 attach 最终应不应该被报告成成功；
- 外部调用方能不能把“agent 进入 JVM”进一步升级成“Arthas 可用”。

也就是说，**attach 成功只是上游投递成功；bind 成功才是下游服务面成立。**

## 七、第六层：`destroy()` 为什么必须按 bind 的反方向撤离

### 7.1 destroy 真正要回答的不是“怎么清”，而是“为什么必须反向清”

一旦服务面被真正装起来，下一个最危险的问题就变成：

> stop 或 JVM 退出时，Arthas 怎么撤？

`destroy()` 的主体在 `ArthasBootstrap.java:838-888`。现稿里已经列出了很完整的步骤：关服务、停 tunnel、关线程池、摘 Transformer、清 Spy、关 worker group、移除 shutdown hook、停日志上下文。

但这串步骤最重要的不是背顺序，而是看清它的方向：

```text
bind 是从里向外把服务面装起来
destroy 就必须从外向里把服务面拆回去
```

### 7.2 为什么不能只关终端，不摘增强与 Spy 引用

一个危险的简化方案是：

> 用户都退出了，终端也关了，那 Arthas 应该就算结束了。

这在 Arthas 里完全不成立。因为终端只是最外层会话面；它后面还挂着：

- 命令执行线程池；
- tunnel-client；
- Transformer；
- ClassLoader 增强补丁；
- Spy 全局入口；
- ArthasClassloader 的可复用引用。

如果只关终端，不摘这些东西，就会留下真正麻烦的寄生残留。

### 7.3 为什么 `cleanUpSpyReference()` 是 destroy 链里最关键的安全阀

`destroy()` 在 `ArthasBootstrap.java:873-874` 调 `cleanUpSpyReference()`，而真正的清理逻辑在 `ArthasBootstrap.java:942-957`。它会把 Spy 切回 NOP，并通过反射清掉 `ArthasClassloader` 相关引用。

这一步的意义非常关键：哪怕业务字节码里还残留着对 `SpyAPI` 的调用，后续这些调用也不会继续打到一个已经撤走的 Arthas 实例，而是落回一个安全的空实现。

关键设计（斜体）：*destroy 不是“尽量把资源关掉”，而是要保证即使有残余调用继续发生，也只能落到安全的空路径。*[模式: 对称生命周期 + 空对象回退] 这就是为什么 Spy 的回退和类加载器引用清理必须在 destroy 链里占据关键位置。

### 7.4 为什么 `stop` 不是 `destroy()` 的同义词

`StopCommand.java:29-39` 还要补一个关键边界：`stop` 命令会先调用 `ArthasBootstrap.reset()` 恢复增强类，再调用 `destroy()`。

这说明：

- `destroy()` 是服务层撤离；
- `stop` 还多了一层命令语义：先恢复业务字节码，再撤服务面。

而 JVM shutdown hook 则是另一条路径：它直接进 destroy 链，不一定经过同样的命令交互语义。

这也是为什么 `stop` 和 `destroy()` 绝不能混成同义词：前者是用户命令层的“恢复 + 撤离”，后者是服务生命周期层的“反向拆解”。

## 收网：Arthas 不是“能启动一个服务”，而是“能可逆地寄生一套服务”

现在把整条链收成一张图：

```text
1. Arthas 已经住进目标 JVM
2. bind() 把端口、隧道、认证、命令、监听器装成完整服务面
3. 只有服务面完整成立后，SpyAPI 才从 NOP 切到真实实现
4. 中途任何一步失败，都必须 destroy() 回滚已创建资源
5. stop / shutdown 时，再由 destroy() 按 bind 的反方向撤离服务、增强、Spy 与引用
```

把这张图压成一句话，就是：

**Arthas 住进 JVM 之后，不只是“启动了几个端口”，而是把自己装配成一套可连接、可认证、可失败回滚、可最终撤走的寄生服务；`bind()` 负责把门装好，`destroy()` 负责把门按反方向拆掉。**

到这里为止，主线其实只发生了四件事：

- attach 成功还不等于服务可用；
- bind 负责把连接面、安全边界和命令面一起装起来；
- Spy 必须最后激活，避免半启动状态；
- destroy 必须和 bind 对称，才能保证寄生可逆。

这也解释了为什么 Arthas 的服务生命周期不该被误看成“启动/停止两个按钮”：

- tunnel 不是附加玩具，而是连接面的另一种方向；
- 认证和 `disabledCommands` 不是运维补丁，而是开门边界；
- `stop` 不是简单退出，而是“先恢复增强，再撤服务”；
- 即使残余业务调用还在发生，Spy 也必须已经退回到安全的 NOP 路径。

跨层标注：[OpenJDK 36-attach——attach 成功与 bind 成功是上下游两层成功条件]；[OpenJDK 47-instrumentation——Transformer 注册、retransform、removeTransformer 与增强恢复边界]；[Netty——终端监听的事件循环承载]；[空对象模式——Spy 由真实实现退回 NOP，保证残余回调安全降级]
