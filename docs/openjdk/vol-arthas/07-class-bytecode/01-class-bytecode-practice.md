# 18. 线上代码为什么和本地不一样？——类、ClassLoader、字节码与热替换的事实确认链

> 基于 `arthas` 当前类与字节码命令实现讨论；本文聚焦 `sc` / `classloader` / `sm` / `jad` / `redefine` / `reset` 的生产排查边界，不重复展开前面 Enhancer / Spy / Thread 的完整机制。
> **前置依赖**：[17 —— CPU 报警时，为什么不能一上来把所有信息都 dump 出来？](../03-thread-lock/04-thread-practice.md)：已经能从线程和栈把问题缩小到可疑业务类。
> → **后续**：更多运行时字节码与增强边界。
> 关联域：ClassLoader、Jad、Instrumentation redefine/retransform、Arthas reset。

## 先看一个最容易误判的现场：本地代码和线上行为不一致，为什么第一步不能直接 `jad`

场景：线上异常堆栈里出现了 `org.example.Service`。你本地代码明明已经改过，线上行为却完全不像你以为的那样。此时最自然的直觉是：

```text
赶紧 jad 一下看看当前代码
```

这个动作看起来很直接，但它默认了几件还没确认的事实：

- JVM 里真的只加载了一份 `org.example.Service`；
- 你看到的这个类就是目标 ClassLoader 版本；
- 你后面要追的方法签名也正是你以为的那个重载；
- 当前字节码没有被 agent 或 Arthas 增强改写。

也就是说，真正的危险不在“没有反编译”，而在**还没确认运行时事实，就急着把某一份字节码当成真相**。

所以本篇真正要回答的不是：

> `sc`、`sm`、`jad`、`redefine` 分别怎么用？

而是：

> **线上行为和本地源码不一致时，为什么不能一上来就 `jad` 或 `redefine`，而要先确认“当前 JVM 里到底加载了哪个类、哪个 ClassLoader、哪个方法签名、哪一版字节码”，最后才决定是否热替换？**

先把全篇总图立住：

```text
可疑业务类
  → sc / sc -d 先确认 JVM 里有没有它、由谁加载
    → classloader / hash 锁定目标版本
      → sm 确认方法签名与重载事实
        → jad 看当前真正生效的字节码
          → trace/watch 验证行为
            → 必要时 mc + redefine 临时止血
              → 若做过增强，再 reset 清理 Arthas 自己的织入层
```

这张图里最重要的一刀就是：

```text
先确认运行时事实
再决定是否热替换
```

后面所有细节，都围绕这条边界展开。

## 一、先排除几个最直觉、也最容易把线上事实看错的方案

### 1. 一上来直接 `jad`

最直觉的方案当然是：

```text
看起来像类代码问题
  → 直接 jad
```

这会很快把人带偏。因为 `jad` 看到的是**某个已经加载版本的字节码**，而不是自动替你回答：

- JVM 里是不是有多份同名类；
- 你看到的是不是业务当前那个 ClassLoader；
- 目标方法是不是那个重载；
- 这份字节码有没有被运行时增强过。

### 2. 忽略 ClassLoader 版本

另一个很常见的误判是：

> 类名对了，应该就够了。

这在线上多版本类共存的场景里非常危险。只要有多个 ClassLoader 同时加载同名类：

```text
org.example.Service
```

就已经不再对应一个唯一的 `Class`。忽略 ClassLoader，后面的 `jad`、`trace`、`watch`、`ognl` 都可能命中错误版本。

### 3. 直接 `redefine` 作为第一反应

如果行为不一致，另一个急躁的选择是：

```text
先 redefine 止血再说
```

但在你还没确认当前 JVM 里究竟跑的是哪一版类、哪一个方法、哪一种增强状态之前，redefine 很可能把错版本替换掉，或者直接因为结构不允许变更而失败。

### 4. 把 `reset` 当成 redefine 的回滚按钮

最后一个最容易讲错的地方是：

> 如果 redefine 出问题，再 reset 不就行了？

这不成立。`reset` 只负责撤销 Arthas 自己插入的增强；它不负责恢复你通过 `redefine` 换进去的新类定义。也就是说，这两者回滚的是两层完全不同的东西。

关键设计（斜体）：*类和字节码排查不是“先改，再看”，而是“先把运行时事实钉死，再决定要不要改”。*[模式: 事实确认优先]

## 二、第一层：`sc` 与 `classloader` 为什么先回答“当前 JVM 里到底是谁”

### 2.1 `sc` 查的是“已加载类事实”，不是磁盘清单

第一步通常是：

```text
sc org.example.Service
```

`SearchClassCommand` 在 `klass100/SearchClassCommand.java:37` 声明。它回答的是：

```text
这个类现在是否已经进入当前 JVM
```

而不是去扫磁盘上有哪些 jar 或源码文件。这条边界很重要，因为线上问题真正发生的地方，是已经加载进 JVM 的类世界，而不是你本地目录树。

### 2.2 为什么 `sc -d` 比单纯“找到类”更关键

继续执行：

```text
sc -d org.example.Service
```

这里最值得看的是：

- classLoader
- classLoaderHash
- 接口和父类
- 注解、保护域等运行时信息。

这一步的价值不是“展示更多字段”，而是确认：**你后面所有命令到底应该绑到哪一份运行时版本上。**

### 2.3 `classloader -c <hash>` 为什么不是切换 JVM

拿到 `classLoaderHash` 后：

```text
classloader -c <hash>
```

`ClassLoaderCommand.java:46` 声明了 `classloader` 命令；`-c` 在 `ClassLoaderCommand.java:100-103` 用于按 hash 指定/筛选某个 ClassLoader。

它的意义不是“切到另一个 JVM”，而是：

```text
把后续查找与操作
锁定到这一份 ClassLoader 实例所代表的类世界
```

关键设计（斜体）：*在多版本类共存现场，类名只是半张地图，ClassLoader 才是剩下那半张。*[模式: 运行时版本锁定]

## 三、第二层：`sm` 为什么要在 `jad` 之前确认方法事实

### 3.1 类存在，不代表方法就是你以为的那个方法

找到类之后，再执行：

```text
sm org.example.Service
```

`SearchMethodCommand` 在 `klass100/SearchMethodCommand.java:42` 声明。它回答的是：

- 方法是否真的存在；
- 重载方法的描述符是否符合预期；
- 你后面 trace/watch 的方法名是否写对；
- 方法是不是从父类继承而来。

### 3.2 为什么“类找到了”还不够

生产里经常出现一种错觉：

> 类名都找到了，后面直接 jad 或 trace 某个方法就行。

但方法层还可能有很多歧义：

- 命中的是另一个重载；
- 目标方法在父类；
- 构造器该写 `<init>`；
- 实际运行版本来自另一个 ClassLoader。

如果不先用 `sm` 把方法签名钉死，后面即便看到了一份字节码，也未必是你想要的那个方法事实。

关键设计（斜体）：*类名、ClassLoader、方法签名必须一起确认，少一个维度都可能把诊断带偏。*[模式: 分层定位]

---

## 四、第三层：`jad` 为什么看的是真正生效字节码，而不是源文件真相

### 4.1 `jad` 回答的是“JVM 此刻在运行什么”

当前几层事实都确认后，再看：

```text
jad org.example.Service
jad --source-only org.example.Service
jad -c <hash> --source-only org.example.Service
```

`JadCommand` 在 `klass100/JadCommand.java:40` 声明。它最重要的价值是：**看的不是你本地源码，也不是磁盘 class 文件，而是 JVM 当前已经加载并生效的字节码。**

### 4.2 为什么线上和本地不一致，至少有三种真相

`jad` 能帮你区分三类最常见的不一致：

1. 线上根本没部署你本地的新版本；
2. 同名类冲突，运行时加载了另一个 jar；
3. 类已经被 agent 或 Arthas 增强，当前字节码和磁盘 class 不同。

这也是为什么前面一定要先有 `sc -d` 和 `sm`：不先把类和方法版本锁住，`jad` 看到的就可能是错误对象的“真相”。

### 4.3 为什么 `jad` 不能替代代码评审

`jad` 看到的是当前生效字节码的反编译结果，不是原始源码真相：

- 注释丢失；
- 局部变量语义可能弱化；
- 泛型信息可能不完整；
- 某些结构已经被编译器或增强器改写。

所以它适合回答“JVM 此刻到底在运行什么”，不适合替代正常源码审阅。

关键设计（斜体）：*`jad` 不是源码阅读器，而是运行时事实探针。*[模式: 生效字节码取证]

## 五、第四层：`redefine` 为什么只能是最后一步止血

### 5.1 redefine 解决的是“已确认事实后的临时止血”

当前面这些事实都确认完了，才有资格考虑：

```text
mc /tmp/Fix.java -d /tmp
redefine /tmp/Fix.class
```

`mc` 由 `MemoryCompilerCommand.java:38` 声明，把 Java 源码编译成 class；`redefine` 由 `RedefineCommand.java:38` 声明，把 class 文件交给 Instrumentation 的 redefine 能力。

它的典型用途不是“替代发布”，而是：

```text
线上已经确认是某个方法体 bug
正常发版来不及
先临时止血
```

### 5.2 为什么它不是正常发布流程

redefine 的限制本来就很强：不能随意改已加载类的结构，例如：

- 新增字段；
- 增加方法；
- 改继承关系；
- 其他破坏签名/结构边界的修改。

JVM 可能直接拒绝这些变更。所以 redefine 天生就只适合作为“结构不变前提下的实现替换”。

### 5.3 为什么 redefine 前必须已经确认完运行时事实

如果你还没确认：

- 当前 JVM 里到底是哪一份类；
- 哪个 ClassLoader 在生效；
- 哪个方法签名有问题；
- 当前字节码是否已经被增强；

就去 redefine，本质上是在对一团事实不清的运行时状态做热替换。风险只会更大。

关键设计（斜体）：*redefine 不是用来“找问题”的，而是用来在问题已经被确认后临时止血。*[模式: 高风险最后升级]

## 六、第五层：`reset` 为什么只能回滚 Arthas 增强，不能回滚 redefine

### 6.1 增强回滚和类定义替换是两层完全不同的动作

`reset` 的语义是：

```text
reset
```

撤销 Arthas 自己织入的 `watch` / `trace` 等增强。

而 redefine 的语义是：

```text
用新的 class 定义替换 JVM 当前类定义
```

这两者改动的不是同一层：

- reset：处理 Arthas 自己的 Transformer / 增强缓存；
- redefine：处理用户提供的新类定义。

### 6.2 为什么很多人会误把 `reset` 当通用回滚按钮

因为它们在用户视角里都像“把线上字节码改了”。但实际上：

- 增强是 Arthas 自己织进去的观察逻辑；
- redefine 是你把业务类定义换掉了。

所以 reset 可以撤自己的增强，却没有义务也没有能力帮你恢复 redefine 之前的业务类定义。

关键设计（斜体）：*必须永远知道自己改的是“观察层”还是“业务定义层”。*[模式: 分层回退边界]

## 收网：先确认运行时事实，再决定是否热替换

现在把整条链收成一张图：

```text
线上行为和本地不一致
  → sc / sc -d 确认类是否存在、由谁加载
    → classloader / hash 锁定运行时版本
      → sm 确认方法签名
        → jad 看当前生效字节码
          → trace/watch 验证行为
            → 必要时 mc + redefine 临时止血
              → 若之前做过增强，再 reset 清理 Arthas 自己的织入层
```

把这张图压成一句话，就是：

**线上“代码不一致”问题不是一个“直接反编译或直接热替换”的问题，而是一个“先把运行时事实确认清楚，再决定是否止血替换”的问题：先确认类、ClassLoader、方法签名和当前生效字节码，最后才决定是否 redefine；而 `reset` 只负责撤销 Arthas 自己的增强，不负责回滚你的类定义替换。**

到这里为止，主线其实只发生了四件事：

- `sc` / `classloader` 先回答“JVM 里到底是谁”；
- `sm` 回答“方法是不是你以为的那个方法”；
- `jad` 回答“JVM 此刻真正运行的字节码是什么”；
- `redefine` 和 `reset` 分别处理不同层的修改与回退。

这也解释了为什么本地源码和线上行为不一致时，最危险的不是“看少了一个命令”，而是**在运行时事实还没钉死之前，就把某份字节码误当成真相，甚至急着热替换。**
