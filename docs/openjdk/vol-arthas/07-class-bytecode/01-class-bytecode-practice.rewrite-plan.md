# 01-class-bytecode-practice 重写规划

> 状态：重写前大纲
> 适用规范：`docs/openjdk/WRITING-GUIDELINES.md`
> 目标：把当前“sc / sm / jad / redefine / reset 命令顺序”重构成一篇围绕“线上代码为什么和本地不一样，以及你为什么不能一上来就反编译或热替换”的生产排查文

## 1. 选题判断

这篇值得独立成篇，但不能继续写成：

- 先 `sc`
- 再 `sm`
- 再 `jad`
- 再 `redefine`
- 最后 `reset`

这种命令口诀式文章。

更好的统一问题是：

**线上行为和本地源码不一致时，为什么不能一上来就 `jad` 或 `redefine`，而要先确认“当前 JVM 里到底加载了哪个类、哪个 ClassLoader、哪个方法签名、哪一版字节码”，最后才决定是否热替换？**

这样本篇就不再是“类与字节码命令用法说明”，而会被收束成一条运行时事实确认链：

- 先确认类是否真的已加载
- 再确认它属于哪个 ClassLoader 版本
- 再确认方法签名是不是你以为的那个方法
- 再确认当前 JVM 生效字节码到底长什么样
- 最后才决定是否 redefine，以及 reset 只回滚哪一层

## 2. 读者困惑

- 本地源码和线上行为不一致时，为什么第一步不是直接 `jad`？
- 为什么同名类在不同 ClassLoader 下会把诊断带偏？
- 为什么 `sm` 对生产排查和 `sc` / `jad` 一样重要？
- 为什么 `redefine` 只适合止血，而不是正常发布流程？
- 为什么 `reset` 不能回滚 `redefine`？

## 3. 一句话顿悟

**线上“代码不一致”问题通常不是一个“看源码”的问题，而是一个“运行时事实确认”问题：你必须先确认 JVM 里加载的是哪一个类版本、由谁加载、方法签名是否匹配、当前生效字节码到底是不是原始版本；只有这些事实都成立后，热替换才有资格成为最后一步，而不是第一反应。**

## 4. 版本边界

正文开头必须明确：

- 基于 `arthas` 当前类与字节码命令实现讨论
- 聚焦 `sc` / `classloader` / `sm` / `jad` / `redefine` / `reset` 的生产排查边界
- 不重复展开前面 Enhancer / Spy / Thread 的完整机制；这里只把它们当作上游证据来源
- 这里讲的是运行时类事实确认与临时止血路径，不等于正常开发发布流程

## 5. 旧稿主要问题

### 5.1 已有优点

- 已经抓到“线上 JVM 里到底加载了哪个类”这个真实切口
- `sc`、`classloader`、`sm`、`jad`、`redefine`、`reset` 的关键锚点都在
- 已经区分了增强回滚和 redefine 回滚不是同一层
- 生产顺序基本合理

### 5.2 必须修复的问题

- 当前骨架仍偏“命令顺序说明文”，主冲突还不够集中
- 失败方案推演不够厚：为什么不能直接 `jad`、为什么不能忽略 ClassLoader、为什么不能把 `reset` 当成 redefine 回滚，还没打透
- `classloader` 命令的意义还可以更明确地收回到“锁定运行时版本”这条主线
- `redefine` 的“止血而非发布”边界可以更有压迫感

## 6. 重写策略

本篇不按命令列表推进，而按运行时事实确认链组织：

1. 先建立冲突：线上代码和本地不一致，但第一反应不该是反编译或热替换
2. 先排除几个错误直觉：
   - 直接 `jad`
   - 忽略 ClassLoader
   - 直接 `redefine`
   - 以为 `reset` 能回滚 redefine
3. 再给总图：sc → classloader → sm → jad → watch/trace 验证 → redefine 止血 → reset 清理增强
4. 然后分层拆：
   - `sc` 确认类是否存在
   - `classloader` / hash 锁定版本
   - `sm` 确认方法签名
   - `jad` 看当前生效字节码
   - `redefine` 作为最后升级
   - `reset` 只处理 Arthas 自己的增强
5. 最后收束成“先确认运行时事实，再决定是否热替换”的排查哲学

## 7. 结构大纲（按理解路径）

### 第一节：事故开场——本地代码和线上行为不一致，为什么第一步不能直接 `jad`

目标：建立真实困惑，而不是从命令帮助开篇。

要回答：

- 线上异常堆栈出现业务类名，但运行行为和本地源码不一致
- 直接反编译很诱人，但还不知道 JVM 里到底加载了哪个版本
- 本篇真正要追的是：如何先把运行时事实钉死，再决定要不要改代码

预估字数：900-1100

### 第二节：先排除几个错误直觉——直接反编译、忽略 ClassLoader、直接热替换、拿 `reset` 当回滚

目标：做失败方案推演。

要回答：

- 为什么不能直接 `jad`
- 为什么同名类在不同 ClassLoader 下会让诊断偏到错误版本
- 为什么 `redefine` 不是正常发布流程
- 为什么 `reset` 只能撤 Arthas 增强，不能撤用户类定义替换

预估字数：1400-1700

### 第三节：第一层——`sc` 与 `classloader` 为什么先回答“当前 JVM 里是谁”

目标：把类存在性和加载者锁成第一层事实。

要回答：

- `sc` 回答的是“类是否进入当前 JVM”，不是扫磁盘 jar
- `sc -d` 提供的 classLoaderHash 为什么是后续所有命令的关键线索
- `classloader -c <hash>` 为什么不是切换 JVM，而是锁定运行时版本

### 第四节：第二层——`sm` 为什么要在 `jad` 之前确认方法事实

目标：把方法签名确认写成排查必须步骤。

要回答：

- 为什么“类存在”不等于“方法就是你以为的那个方法”
- 重载、继承、构造器、另一个 ClassLoader 版本怎样让命令命中错误目标
- `sm` 如何把后续 trace/watch/jad 绑定到正确方法签名

证据锚点：

### 第五节：第三层——`jad` 为什么看的是真正生效字节码，而不是源文件真相

目标：把反编译写成运行时事实证据，而不是代码审查工具。

要回答：

- `jad` 为什么是在看当前已加载字节码
- 三种“不一致”真相：线上没部署新版本、同名类冲突、已被 agent/Arthas 增强
- 为什么 `jad` 能回答“JVM 正在运行什么”，却不等于原始源码

### 第六节：第四层——`redefine` 为什么只能是最后一步止血

目标：把 redefine 写成高风险升级动作。

要回答：

- `mc` 与 `redefine` 如何组成临时热替换链
- 为什么结构性修改会被 JVM 拒绝
- 为什么它适合“先确认事实后临时止血”，而不是常规交付手段

### 第七节：第五层——`reset` 为什么只能回滚 Arthas 增强，不能回滚 redefine

目标：把两个“回退”层次拆开。

要回答：

- Enhancer 插入的 SpyAPI 调用为什么属于 Arthas 增强层

## 8. 必须展开的失败方案

至少要展开以下失败方案：

1. 一上来直接 `jad`
2. 忽略 ClassLoader 版本
3. 类存在就默认方法签名也对
4. 直接 `redefine` 作为第一反应
5. 把 `reset` 当成 redefine 的回滚按钮

## 9. 本篇必须明确澄清的误解

1. `sc` 查的是 JVM 已加载类，不是磁盘 jar 清单
2. 同名类在不同 ClassLoader 下不是同一个 `Class`
3. `sm` 是方法级事实确认，不是可有可无的辅助命令
4. `jad` 看的是当前生效字节码，不是原始源码真相
5. `redefine` 是止血动作，不是正常发布流程
6. `reset` 只处理 Arthas 自己织入的增强，不处理 redefine 的类定义替换
