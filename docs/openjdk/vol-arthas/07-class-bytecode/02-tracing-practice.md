## 先看真正的分叉：慢接口和偶发异常，为什么不能只靠一个命令

场景：同一个接口在线上可能同时出现几种完全不同的现象：

- 有时参数不对；
- 有时返回值怪异；
- 有时整段调用很慢；
- 有时只是偶发异常，等你连上命令时现场早就消失了；
- 有时你甚至不知道是谁把这个方法调进来的。

于是最自然的直觉就是：

> Arthas 既然有 watch、trace、stack、tt 这些命令，那总有一个可以把所有问题一次看完吧？

这正是最容易把线上排查搞乱的地方。因为这些命令虽然共享同一增强链和 Advice 事件源，但它们各自回答的是完全不同的证据缺口：

- `watch`：这一次调用里到底发生了什么；
- `trace`：这次调用内部时间花在哪一层；
- `stack`：是谁把它调进来的；
- `tt`：当时没人在现场，如何把那次调用先存下来，之后再看。

所以本篇真正要回答的不是：

> watch、trace、stack、tt 分别怎么用？

而是：

> **当一个接口“有时慢、有时报错、有时参数不对”时，为什么不能只靠 watch、或只靠 trace、或只靠 tt 解决，而必须在“单次调用现场”“方法内部调用树”“调用来源栈”“历史现场记录”这几种观察模型之间切换？**

先把全篇总图立住：

```text
先问自己缺哪种证据
  → 这一次调用现场不清：watch
  → 这次调用内部慢在哪不清：trace
  → 谁把它调进来的不清：stack
  → 当时没人在线，历史现场已经过去：tt
  → 想看趋势或行号，是同一事件源下的 monitor / line 分支
```

这张图里最重要的一刀就是：

```text
这些命令共享同一条增强链
但它们不是同一个工具的不同皮肤
而是四种不同的观察模型
```

后面所有细节，都围绕这条边界展开。

## 一、先排除几个最直觉、也最容易把问题看偏的方案

### 1. 用 watch 去解释方法内部慢在哪

watch 很强：它能看参数、返回值、异常、`cost`，还支持条件和对象展开。

但如果你真正想问的是：

```text
这个方法内部到底是哪一层慢？
```

那只盯着一次调用的 `params`、`returnObj` 和总耗时，仍然无法自然告诉你：

- 是数据库慢；
- 是 RPC 慢；
- 是锁竞争；
- 还是方法体内部某个循环异常。

也就是说，watch 更接近“这次现场发生了什么”，不擅长回答“内部结构里的时间分布”。

### 2. 用 trace 去恢复参数和返回值现场

反过来，trace 能给你一棵调用树，于是也很容易让人误会：

> 既然调用树都出来了，那参数和返回值顺手看一下也该能办到吧？

这同样不对。trace 的主职责是：

- 展开调用点；
- 统计耗时；
- 找到慢在哪个子调用层次。

它并不天然适合替你记录这一次调用的参数对象和返回对象细节。

### 3. 偶发问题总靠实时命令等它再发生

第三个常见误区是：

> 异常不是每次都有，那我就一直开着 watch/trace，等它再次发生。

这会很快碰到线上成本边界：

- 高频方法无限输出；
- 持续增强时间过长；
- 现场还没等到，命令本身已经给业务施加了不小干扰。

这正是 `tt` 要解决的：**不是一直在线等，而是先把现场录下来。**

关键设计（斜体）：*慢、错、偶发、来源不明，这四类问题缺的不是同一种证据，所以也不该被同一个命令硬解。*[模式: 证据缺口驱动的工具分流]

## 二、第一层：watch 为什么最适合回答“这一次调用里到底发生了什么”

### 2.1 watch 盯的是现场，不是结构

当你怀疑 `doBiz` 的入参、返回值或异常只在某些请求里出问题，最直接的入口通常是：

```text
watch org.example.Service doBiz
```

`WatchCommand` 在 `monitor200/WatchCommand.java:22` 声明。它天然适合回答：

- 这一次调用进来时参数是什么；
- 正常返回值是什么；
- 抛了什么异常；
- 这次调用总耗时多少。

也就是说，它看的是**单次调用现场**。

### 2.2 为什么线上第一下就应该限次、限深度

更稳妥的第一次尝试通常是：

```text
watch -x 3 -n 10 org.example.Service doBiz
```

- `-x 3`：控制对象展开深度；
- `-n 10`：限制输出次数。

这两个参数不是“命令附属品”，而是生产边界的一部分：如果你不先限制输出次数和对象展开深度，高频方法和复杂对象图会先把命令自己放大成负担。

### 2.3 为什么输出时机和条件表达式只是 watch 的约束器

watch 还能通过：

- `-b`：before；
- `-s`：success；
- `-e`：exception；
- `-f`：finish；
- `-e 'params[0] > 100'`：条件表达式；

来缩小记录范围。

但这些能力本质上都在服务同一个问题：**我要不要保留这一次调用现场，以及保留它的哪一面。**

关键设计（斜体）：*watch 的强项不是“能做很多种输出”，而是“围绕单次调用现场，精确控制什么时候记、记多少、展开多深”。*[模式: 单次现场模型 + 约束器]

## 三、第二层：trace 为什么最适合回答“这次调用内部慢在哪一层”

### 3.1 trace 盯的是方法体内部的耗时结构

当你知道接口慢，但还不知道慢在方法体里的哪一层时：

```text
trace org.example.Service doBiz
```

`TraceCommand` 在 `monitor200/TraceCommand.java:31` 声明。它回答的不是“参数是什么”，而是：

- 这个方法内部又调用了谁；
- 每个子调用花了多少时间；
- 时间主要堆在哪个分支。

也就是说，trace 关注的是**内部耗时结构**。

### 3.2 为什么它比 watch 更重

trace 不仅需要方法入口/返回事件，还要在方法内部调用点加 invoke 级追踪桩。这意味着：

- 回调点更多；
- 输出结构更复杂；
- 成本也更高。

所以 trace 更不适合“一上来全局打开”，而是应该在目标类、目标方法已经被缩小后再用。

### 3.3 为什么 trace 常常要级联下钻

如果 `trace org.example.Service doBiz` 已经把慢点缩小到 `DownstreamClient.call`，下一步常常不是继续盯原入口，而是再单独 trace 子方法：

```text
trace org.example.DownstreamClient call
```

这说明 trace 的典型节奏是：

```text
先拿到一棵树
  → 找最热子分支
    → 再把那个子方法变成新的入口继续下钻
```

关键设计（斜体）：*trace 的价值不在于“一次看完全部”，而在于把时间热点逐层压缩到更小的方法边界。*[模式: 调用树模型 + 级联下钻]

## 四、第三层：stack 为什么最适合回答“是谁把它调进来的”

### 4.1 stack 关注的是来源链，而不是内部调用树

有些方法本身并不慢，真正的问题是：

> 它是从哪条请求链路、哪个上游路径被调进来的？

这时更合适的是：

```text
stack org.example.Service doBiz
```

`StackCommand` 在 `monitor200/StackCommand.java:22` 声明。它不想把方法内部调用点展开成树，而是想把当前线程的业务调用来源栈切出来给你看。

### 4.2 为什么它比 trace 更直接地回答“调用来源”

trace 看到的是目标方法内部的子调用；stack 看到的是进入这个方法之前，线程一路是从哪几个业务栈帧过来的。

所以如果你的问题是：

- 到底是谁在调它；
- 哪条入口链路会把流量带到这里；

stack 通常比 trace 更直击要害。

### 4.3 为什么条件表达式能进一步缩小“谁的来源链”

像：

```text
stack -n 3 'params[0] == "pay"' org.example.Service doBiz
```

这样的用法，本质上是在说：**我不想看所有来源链，我只想看满足某类参数条件的那几次来源链。**

关键设计（斜体）：*stack 的强项不是“把整条栈原样打出来”，而是让你把“调用来源”从方法内部结构里单独剥离出来看。*[模式: 来源栈模型]

## 五、第四层：tt 为什么最适合回答“当时没人在现场怎么办”

### 5.1 tt 先解决“历史现场能不能留住”

如果异常一天只出现一两次，实时命令常常会面临同一个问题：等你连上去的时候，现场早就过去了。

这时：

```text
tt -t org.example.Service doBiz
```

更像是在建立一个历史现场录制器。`TimeTunnelCommand` 在 `monitor200/TimeTunnelCommand.java:39` 声明。后续你可以：

```text
tt -l
tt -i 1000
tt -s 'method.name == "doBiz" && params[0] == 123'
tt -i 1000 -w 'returnObj'
```

这里的核心问题已经不再是“当前这次调用在发生什么”，而是：**过去发生过的那次调用，还能不能被找回来。**

### 5.2 为什么它不能被当成无限历史数据库

tt 会受固定 ring stack 和记录容器边界影响，旧记录可能被覆盖。也就是说，它是“足够保存近期关键现场”的工具，不是永久历史仓库。

所以它适合：

- 偶发异常；
- 低频但关键的错误路径；
- 需要“先抓住，再慢慢分析”的现场。

### 5.3 为什么 `tt -p` 是真实调用，而不是无副作用重放

如果最终要重放：

```text
tt -p -i 1000
```

这不是“播放录像”，而是再次用历史 target 和参数去真实反射调用业务方法。它可能：

- 写数据库；
- 发送消息；
- 修改状态；
- 再次抛出业务异常。

关键设计（斜体）：*tt 的价值在于把“没赶上现场”补回来；它的风险在于重放时你并不是在看录像，而是在再次触发真实业务。*[模式: 历史现场模型 + 真实重放]

## 六、第五层：monitor 与 line 为什么只是同一增强链下的分支变体

这里先给一个路标：前面四节是主线。`monitor` 与 `line` 更像证明“同一增强事件源可以继续长出别的观察模型”的两个分支例子；赶时间可以先记结论——**增强层统一，消费模型分叉。**

### monitor：看趋势，不看单次现场

```text
monitor org.example.Service doBiz
```

它更关心一段时间里的调用次数、成功/异常和平均耗时，不追单次调用的完整现场。

### line：看当前执行到哪一行

```text
line org.example.Service doBiz
```

它更关心方法执行到了哪一行、该行附近有什么局部变量，而不是完整调用树或完整参数世界。

这两者都说明：同一套增强引擎、同一套 Advice 事件源，完全可以长出不同消费模型。

## 收网：先问自己缺哪种证据，再选对应观察模型

现在把整条链收成一张图：

```text
缺“这一次调用现场”
  → watch

缺“这次调用内部哪里慢”
  → trace

缺“是谁把它调进来的”
  → stack

缺“当时没在现场的历史证据”
  → tt
```

把这张图压成一句话，就是：

**watch、trace、stack、tt 不是同一命令的四个名字，而是同一增强链下四种完全不同的观察模型：watch 看单次现场，trace 看内部耗时结构，stack 看来源链，tt 看历史现场。真正稳定的排查路径，不是把它们一起打开，而是先问自己缺哪种证据，再选对应的观察模型。**

到这里为止，主线其实只发生了四件事：

- watch 不能替代 trace 的结构视角；
- trace 不能替代 watch 的单次现场；
- stack 回答的是“谁调进来”，不是“内部怎么慢”；
- tt 解决的是“当时没人在现场”，但不能伪装成无副作用录像。

这也解释了为什么慢接口和偶发异常不该只靠一个命令：**你缺的证据一变，最合适的观察模型也就跟着变。**
