# 02-tracing-practice 重写规划

> 状态：重写前大纲
> 适用规范：`docs/openjdk/WRITING-GUIDELINES.md`
> 目标：把当前“watch / trace / stack / tt 实战”重构成一篇围绕“慢接口和偶发异常为什么不能只靠一个命令，而必须在对象、线程、调用树和单次调用现场之间逐层切换”的生产排查文

## 1. 选题判断

这篇值得独立成篇，但不能继续写成：

- 先 `watch`
- 再 `trace`
- 再 `stack`
- 再 `tt`
- 最后给一个组合拳

这种命令串联式实战文章。

更好的统一问题是：

**当一个接口“有时慢、有时报错、有时参数不对”时，为什么不能只靠 watch、或只靠 trace、或只靠 tt 解决，而必须在“单次调用现场”“方法内部调用树”“调用来源栈”“历史现场记录”这几种观察模型之间切换？**

这样本篇就不再是“AR-2/AR-5 命令用法说明”，而会被收束成一条方法现场诊断链：

- watch 回答这一次调用现场
- trace 回答这次调用内部时间花在哪
- stack 回答是谁把它调进来的
- tt 回答当时没在现场怎么办
- 四者都从同一增强/Advice 体系出发，但面对的问题不同

## 2. 读者困惑

- 参数偶发错误时，为什么不直接 trace？
- 接口慢时，为什么 watch 还不够？
- 想知道谁调用了某方法，为什么 stack 比 trace 更直接？
- 偶发异常一天只出现一两次时，为什么 tt 比实时 watch 更适合？
- 这些命令明明都织入方法回调，为什么它们不能互相替代？

## 3. 一句话顿悟

**watch、trace、stack、tt 不是同一个“插桩观察功能”的四个名字，而是同一增强链下四种完全不同的观察模型：watch 看单次调用现场，trace 看方法内部调用树，stack 看业务调用来源，tt 先保存历史现场、再按需查询或重放。真正稳定的排查路径不是把它们一起打开，而是先分清你缺的是“当前现场”“内部耗时结构”“调用来源”还是“历史证据”。**

## 4. 版本边界

正文开头必须明确：

- 基于 `arthas` 当前 watch/trace/stack/tt 命令实现与前面 AR-2 / AR-5 机制篇讨论
- 聚焦线上慢接口与偶发异常的实践决策路径，不重复展开完整 Enhancer / Spy / Advice 引擎细节
- 不把下一步实践外的其他命令扩写成本篇主线
- 这里讲的是方法现场排查路径，不等于所有线上问题都必须依次执行四个命令

## 5. 旧稿主要问题

### 5.1 已有优点

- 已经抓到 watch / trace / stack / tt 是不同观察方式
- 每个命令的典型场景和关键参数都在
- `trace` 的树、`stack` 的 SpyAPI 边界、`tt -p` 的真实调用边界都讲到了
- 有一个合理的组合拳顺序

### 5.2 必须修复的问题

- 当前骨架仍偏“命令并列说明”，主冲突还不够集中
- 失败方案推演不够厚：为什么参数问题不能只用 trace，为什么慢接口不能只用 watch，为什么 tt 不能被当成无限历史数据库，还没打透
- `monitor` / `line` 的摆位可以更明确地收成“同一事件源的变体分支”，避免发散
- 结尾的组合拳还可以更明显地写成“缺什么证据，就选哪种观察模型”的决策链

## 6. 重写策略

本篇不按命令列表推进，而按“缺什么证据”组织：

1. 先建立冲突：慢接口和偶发异常不是同一类信息缺失
2. 先排除几个错误直觉：
   - 参数问题只靠 trace
   - 慢问题只靠 watch
   - 偶发问题一直盯着实时命令等它发生
3. 再给总图：watch / trace / stack / tt 四种观察模型
4. 然后分层拆：
   - watch 负责当前调用现场
   - trace 负责方法内部耗时结构
   - stack 负责调用来源
   - tt 负责历史现场保存与按需重放
   - monitor / line 作为同一增强链下的分支变体
5. 最后收束成“先问自己缺哪种证据，再选对应观察模型”的实践哲学

## 7. 结构大纲（按理解路径）

### 第一节：事故开场——慢接口和偶发异常，为什么不能只靠一个命令

目标：建立真实困惑，而不是直接列 watch/trace/tt。

要回答：

- 同一个接口可能有“参数错”“有时报异常”“整体慢”“不知道谁调进来”“问题过后现场消失”几类不同问题
- 本篇真正要追的是：这些问题分别缺什么证据

预估字数：900-1100

### 第二节：先排除几个错误直觉——只用 watch、只用 trace、一直等问题现场再次发生

目标：做失败方案推演。

要回答：

- 为什么 watch 不适合解释内部耗时结构
- 为什么 trace 不适合还原参数/返回值现场
- 为什么偶发异常不能总靠实时盯着命令等它再出现
- 真正需要的是多种观察模型按证据缺口切换

预估字数：1400-1700

### 第三节：第一层——watch 为什么最适合回答“这一次调用里到底发生了什么”

目标：把 watch 写成单次调用现场模型。

要回答：

- 参数、返回值、异常、耗时和对象展开各回答什么
- `-b/-s/-e/-f`、`-x`、`-n`、条件表达式为什么分别约束时机、深度、次数和记录范围
- 为什么高频方法必须限次、限深度

证据锚点：

- `WatchCommand.java:22,69`
- `WatchAdviceListener.java` 及前置文章桥接

预估字数：1700-2100

### 第四节：第二层——trace 为什么最适合回答“这次调用内部慢在哪一层”

目标：把 trace 写成方法内部耗时结构模型。

要回答：

- trace 关注的是子调用树与耗时分布
- 为什么它比 watch 更重
- `-n`、条件、级联下钻如何控制成本
- 为什么它不回答参数值，而回答调用树结构

证据锚点：

- `TraceCommand.java:31`
- `TraceAdviceListener` / `TraceTree` / `TraceView` 前置文章桥接

预估字数：1800-2200

### 第五节：第三层——stack 为什么最适合回答“是谁把它调进来的”

目标：把 stack 写成来源栈模型。

要回答：

- stack 关注的是业务调用来源，而不是方法内部树
- SpyAPI 边界裁剪为什么让它更接近业务栈
- 条件表达式如何缩小命中现场

证据锚点：

- `StackCommand.java:22`
- `ThreadUtil.findTheSpyAPIDepth()` 前置桥接

预估字数：1500-1800

### 第六节：第四层——tt 为什么最适合回答“当时没人在现场怎么办”

目标：把 tt 写成历史现场模型。

要回答：

- `tt -t` 记录什么，为什么不能当成无限历史数据库
- `tt -l` / `-i` / `-s` / `-w` 分别解决什么问题
- `tt -p` 为什么是一次真实业务调用，而不是无副作用回放
- 参数引用和 ring stack 边界为什么重要

证据锚点：

- `TimeTunnelCommand.java:39,121,146-149`
- `TimeTunnelAdviceListener` / `ArthasMethod` 前置桥接

预估字数：1900-2300

### 第七节：第五层——monitor 与 line 为什么只是同一增强链下的两个分支变体

目标：收束分支，避免正文发散。

要回答：

- monitor 为什么偏趋势聚合，不是单次现场
- line 为什么偏“执行到哪一行”和局部变量
- 它们如何证明“增强层统一，消费模型分叉”

预估字数：900-1200

### 第八节：收网——先问自己缺哪种证据，再选对应观察模型

目标：把全文收成一句话并桥接后续。

必须点名：

- watch 现场
- trace 结构
- stack 来源
- tt 历史
- monitor / line 分支
- 继续补齐其他专项命令

预估字数：800-1000

## 8. 必须展开的失败方案

至少要展开以下失败方案：

1. 用 watch 去解释内部耗时树
2. 用 trace 去恢复参数/返回值现场
3. 让高频方法无限 watch/trace
4. 把 tt 当成无限历史数据库或无副作用录像
5. 把 monitor / line 当成完全不同引擎，而不是同一增强链分支

## 9. 本篇必须明确澄清的误解

1. watch / trace / stack / tt 不是同一命令的四种名字
2. watch 看单次现场，不看调用树
3. trace 看内部调用树，不看完整参数世界
4. stack 回答调用来源，不等于性能树
5. tt 保存历史现场，但重放时仍会真实调用业务方法
6. monitor / line 仍然站在同一增强事件源上
