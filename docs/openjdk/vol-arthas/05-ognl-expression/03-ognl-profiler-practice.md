## 先看真正的分叉：对象状态不对，和 CPU 热点不清，为什么不能用同一把工具

场景：线上服务异常时，你经常面对的是两类完全不同的问题：

1. 某个对象的运行时状态不对，想直接读字段、看静态成员，或者确认某个单例现在到底是什么值；
2. CPU 100%，但单条线程栈看不出整体热点，想知道整体时间到底花在哪里。

它们看起来都属于“运行时观察”，于是最容易出现一个危险直觉：

> Arthas 里功能最强的命令，应该都能看；随便拿一个最猛的工具先上就行。

这正是线上排查最容易失手的地方。因为两类问题需要的证据形态完全不同：

- 对象问题追的是“这个对象现在是什么”；
- 热点问题追的是“过去这一段时间里，整体时间花在哪里”。

所以本篇真正要回答的不是：

> `ognl` 怎么用？profiler 怎么用？

而是：

> **线上异常出现时，为什么“对象状态不对”和“CPU 热点不清”不是同一个问题，不能用同一把工具硬解；而 Arthas 又怎样把 `thread`、`profiler`、`trace`、`watch`、`ognl` 这些能力按最小侵入和最大证据价值的顺序串起来？**

先把全篇总图立住：

```text
先判断问题类型
  → 对象状态问题：ognl / sc -d
  → 整体热点问题：thread 缩线程范围，再用 profiler 看聚合热点
    → 已缩到方法级：trace 看内部调用树
      → 需要单次调用现场：watch 看参数 / 返回值 / 异常
```

这张图里最重要的一刀就是：

```text
对象观察和采样观察不是一回事
工具选择应由“你要的证据形态”决定，而不是由“哪个功能看起来更强”决定
```

后面所有细节，都围绕这条边界展开。

## 一、先排除几个最直觉、也最容易扩大影响面的方案

### 1. 用 `ognl` 去解释整体 CPU 热点

`ognl` 的确很强：

- 能读静态成员；
- 能看对象字段；
- 能指定 ClassLoader；
- 还能直接调用方法。

于是很容易让人误会：

> 既然它能直接看到对象，那我是不是也能靠它推断 CPU 为什么高？

这通常答不上来。因为 CPU 热点是聚合问题：你想知道的是“过去这一段时间里，哪些调用栈反复被命中”。`ognl` 只能告诉你某个对象此刻的状态，不能自然还原整体时间分布。

### 2. 用 profiler 去看单次调用现场

反过来，看到 CPU 高也有人会想：

> profiler 都能画火焰图了，那参数、返回值、对象状态顺便也应该能看出来吧？

这同样不对。Profiler 的强项是：

- 跨线程；
- 跨时间窗口；
- 聚合热点。

它并不承诺给你某一次调用的 `params[0]`、`returnObj` 或对象内部字段。火焰图的宽块告诉你“哪里热”，不会告诉你“这一调用里某个参数到底是多少”。

### 3. 一上来就对全应用做 trace/watch

另一种常见误用是：

> 既然 trace/watch 最贴近方法执行真相，那直接从它们开始就好了。

这会过早提高观测强度：

- trace 会增强目标方法并追踪调用树；
- watch 会增强目标方法并执行表达式；
- 如果目标还没缩小，成本和噪声会一起放大。

关键设计（斜体）：*真正稳定的排查路径不是“先上最强工具”，而是“先用最小工具缩小范围，再用更强工具解释更小的问题”。*[模式: 证据递进 + 侵入性分级] 如果一开始就把 `ognl`、profiler、trace、watch 全开，你得到的不会是更完整的真相，而是四种不同粒度的证据同时互相打架：对象状态说明不了整体热点，火焰图又解释不了单次参数，trace/watch 还会过早提高侵入性。

## 二、第一层：`ognl` 适合回答“对象现在到底是什么”

### 2.1 当问题是对象状态，`ognl` 才是直接工具

如果你怀疑的是：

- 某个配置单例里的 Map 在变大；
- 某个静态字段已经偏离预期；
- 某个对象现场到底挂着什么值；

那更合适的入口通常是：

```text
ognl '@com.example.Config@INSTANCE'
ognl '@com.example.Config@INSTANCE.timeout'
```

`ognl` 命令定义在 `core/command/klass100/OgnlCommand.java:31-40`。它支持：

- `@类@静态成员`
- `@类@方法()`
- `-c <classLoaderHash>` 指定类加载器
- `-x` 控制结果对象展开深度

这说明它天然更接近“直接读对象 / 读静态成员 / 执行表达式”的能力。

### 2.2 为什么多版本类时必须先确认 ClassLoader

如果应用里同名类由多个 ClassLoader 加载，先用 `sc -d` 确认 classLoaderHash，再执行：

```text
ognl -c <classLoaderHash> '@com.example.Config@INSTANCE.timeout'
```

否则你以为自己读的是业务当前版本，实际可能命中另一份同名类。`ognl` 的强大能力和 ClassLoader 风险是绑在一起的。

### 2.3 为什么它天然更危险

`ognl` 最大的风险，不是语法难，而是它可以真实调用方法：

```text
ognl '@Service@reload()'
```

这不是模拟，而是真实业务执行。也就是说：

- 读字段、看对象相对安全；
- 一旦调用方法，就必须把它当成真实业务调用对待。

关键设计（斜体）：*`ognl` 的价值在于直接触达对象世界，它的风险也正是这种直接触达。*[模式: 反射式求值 + ClassLoader 感知]

所以 `ognl` 更适合作为“先读、少写、确认版本后再动手”的对象观察工具，而不是拿来解释整体热点。

## 三、第二层：profiler 适合回答“整体时间花在哪里”

### 3.1 当问题是整体热点，先别盯单个对象

如果你面对的是：

- CPU 100%；
- 多个线程轮着忙；
- `thread <id>` 看几个瞬时栈仍然拼不出全貌；

那更合适的入口通常是：

```text
profiler start --event cpu
...
profiler stop --format html -f /tmp/flame.html
```

它的目标不是还原单次调用现场，而是聚合“整体时间花在哪里”。

### 3.2 为什么火焰图回答的是聚合问题，而不是单次现场

Profiler 命令层本身并不实现采样引擎，而是把参数翻译给 async-profiler。火焰图的：

- 横轴：样本聚合宽度；
- 纵轴：栈深。

宽块代表该调用栈在窗口内被命中的比例更高，而不是“某一次调用花了多少时间”。

所以 profiler 最擅长的是：

```text
多线程 / 一段时间窗口 / 整体热点
```

而不是：

```text
单次调用 / 参数 / 返回值 / 当前对象内部状态
```

关键设计（斜体）：*Profiler 用采样聚合回答“哪里热”，不回答“这一次调用里对象是什么”。*[模式: 采样聚合]

### 3.3 为什么它常常位于 `thread` 之后、`trace/watch` 之前

在实践里，profiler 往往最适合放在中间层：

- 比 `thread` 更全局；
- 比 `trace/watch` 更低侵入；
- 比 `ognl` 更能回答整体热点。

也就是说，它不是所有问题的起点，也不是所有问题的终点，而是从“线程瞬时视角”向“方法现场视角”过渡的聚合层。

## 四、第三层：`thread`、`trace`、`watch` 怎样把两条观察路径继续缩小

### 1. `thread` 先把问题缩到线程级

当你还不知道热点在哪个线程时：

```text
thread -n 3
thread <id>
```

`thread` 的职责是：

- 先按线程排序；
- 再把候选线程变成具体栈证据。

它回答的是“谁在忙、谁在等、栈大致停在哪”。

### 2. `trace` 再把问题缩到方法内部调用树

如果线程栈已经把范围缩到某个业务方法，但你还不知道它内部到底慢在哪，就转到：

```text
trace <class> <method>
```

`trace` 的目标是把一次调用展开成方法内部调用树，回答“时间主要花在这个方法体里的哪个子调用点”。

### 3. `watch` 最后才进入单次调用现场

如果你已经知道目标方法，就是想看：

- 这一次调用的参数是什么；
- 返回值是什么；
- 有没有异常；
- `cost` 多大；

那才进入：

```text
watch -n 10 <class> <method>
```

`watch` 回答的是单次调用现场，和 profiler 的采样聚合是完全不同粒度的证据。

关键设计（斜体）：*从 `thread` 到 `profiler` 再到 `trace/watch`，不是命令堆叠，而是粒度逐步变细、侵入性逐步升高的证据收缩链。*[模式: 粒度递进 + 观测强度升级]

## 五、第四层：如何选择“最小工具”，而不是“最强工具”

### 对象状态问题

优先：

```text
sc -d / ognl
```

因为你真正需要的是：

- 当前类的版本和 ClassLoader；
- 对象或静态成员的运行时状态。

### 整体热点问题

优先：

```text
thread -n / profiler
```

因为你需要先知道：

- 哪些线程忙；
- 如果线程视角不够，再用采样聚合看整体热点。

### 方法内部问题

优先：

```text
trace / watch
```

但前提是目标已经缩到足够小。否则增强和输出成本会放大。

### 各工具的成本边界

- `ognl`：可能真实执行方法；
- `profiler`：会持续采样；
- `watch/trace`：会增强字节码；
- `thread`：成本相对低，但也只是线程级视角。

关键设计（斜体）：*最佳起手式不是功能最强的工具，而是能回答当前问题的最小工具。*[模式: 证据-成本匹配]

## 收网：对象观察、采样观察、方法现场，是三层不同证据

现在把整条链收成一张图：

```text
对象状态不对
  → ognl / sc -d

整体热点不清
  → thread -n / profiler

方法内部要解释
  → trace

单次调用现场要确认
  → watch
```

把这张图压成一句话，就是：

**线上异常排查时，`ognl`、`profiler`、`thread`、`trace`、`watch` 不是同类工具的不同皮肤，而是分别站在“对象状态”“整体热点”“线程级瞬时视角”“方法内部调用树”“单次调用现场”这几层不同证据面上；稳定的实践路径不是功能最强优先，而是先用最小代价缩小范围，再用更强工具精确解释。**

到这里为止，主线其实只发生了四件事：

- `ognl` 适合对象观察，不适合解释整体热点；
- profiler 适合聚合热点，不适合解释单次调用现场；
- `thread`、`trace`、`watch` 负责逐层缩小到线程、方法和调用级；
- 工具越强，侵入和副作用越大，所以必须按证据和成本递进使用。

这也解释了为什么“功能最强的命令”通常不是最佳命令：**真正可靠的是让工具和问题类型对齐，而不是让所有问题都去适配同一种观察方式。**
