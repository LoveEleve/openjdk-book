# 02-express-usage 重写规划

> 状态：重写前大纲
> 适用规范：`docs/openjdk/WRITING-GUIDELINES.md`
> 目标：把当前“watch / ognl / tt -s/-w 的表达式生效点”重构成一篇围绕“同一个 OGNL 引擎为什么在不同命令里承担不同职责，以及这些职责各自的副作用边界是什么”的机制文

## 1. 选题判断

这篇值得独立成篇，但不能继续写成：

- `isConditionMet()` 做什么
- `getExpressionResult()` 做什么
- `ognl` 命令怎么执行
- `tt -s` 怎么筛选
- `tt -w` 怎么取值

这种按调用点平铺的说明文。

更好的统一问题是：

**同样一套 OGNL 引擎，为什么在 `watch` 里它先是条件守卫、后是结果投影；在 `ognl` 命令里它又变成脱离 Advice 的独立执行器；在 `tt -s/-w` 里它还会在“批量筛选历史现场”和“单条历史取值”之间切换不同执行策略？这些差异为什么会直接决定副作用边界？**

这样本篇就不再是“表达式用法说明”，而会被收束成一条更硬的使用语义链：

- 条件判断和结果求值不是同一个动作
- Advice 根对象与 `cost` 绑定决定了 watch/tt 的上下文
- `ognl` 命令因为没有 Advice 根对象，所以天然更接近“任意执行器”
- 批量历史筛选和单条历史取值要在 ThreadLocal 池与一次性 Express 之间切换
- 副作用边界不是由语法决定，而是由“表达式何时、在哪个上下文、以什么方式被执行”决定

## 2. 读者困惑

- `watch -e 'params[0] > 100' 'params[0]' ...` 里为什么有两个表达式，它们为什么不是一次求值？
- `cost` 到底从哪来，为什么源码里实际是 `cost` 而帮助里可能写成 `#cost`？
- `ognl` 命令为什么不需要 Advice 根对象，却还能访问静态字段和执行方法？
- `tt -s` 和 `tt -w` 都是在历史现场上执行表达式，为什么一个走 ThreadLocal 池，一个走一次性带 ClassLoader 的 Express？
- 为什么同一套 OGNL 语法，在不同命令里副作用风险完全不同？

## 3. 一句话顿悟

**Arthas 里的表达式引擎不是一个“到处都一样用”的黑盒，而是被放在不同生效点上承担不同职责：在 `watch` 里，条件表达式先决定是否留下记录，结果表达式再决定输出什么；在 `ognl` 里，表达式脱离 Advice，直接变成一个拥有目标 ClassLoader 和方法调用能力的独立执行器；在 `tt -s/-w` 里，表达式则要在批量历史筛选和单条历史取值之间切换不同的上下文与缓存策略。**

## 4. 版本边界

正文开头必须明确：

- 基于 `arthas` 当前源码实现讨论
- 聚焦 watch / ognl / tt -s/-w 的表达式生效点与副作用边界
- 不重复展开上一章 ExpressFactory / OgnlExpress / WeakReference 等底层引擎机制；这里只把它们当作上游输入
- 不把下一篇 profiler 文章提前写成本篇主线；这里只桥接“从插桩观察切换到采样观察”
- 这里讲的是 Arthas 当前表达式消费路径，不等于所有 OGNL 或 EL 工具都这样划分条件、求值与上下文

## 6. 重写策略

本篇不按命令类别平铺，而按更强的问题链组织：

1. 先建立冲突：同一套 OGNL 语法，在不同命令里为什么会有完全不同的作用
2. 先排除几个错误直觉：
   - 条件和结果表达式可以合成一次求值
   - `ognl` 只是无副作用查询
   - `tt -s` 与 `tt -w` 在历史现场上执行表达式应该完全等价
3. 再给总图：watch 的守卫/投影、ognl 的独立执行器、tt 的批量筛选/单条取值
4. 然后分层拆：
   - 条件守卫与结果投影的两阶段语义
   - Advice 根对象与 `cost` 的绑定边界
   - `ognl` 命令为何天然更强、风险也更大
   - `tt -s` 与 `tt -w` 为何采用不同 Express 策略
5. 最后收束成“生效点决定副作用边界”的设计哲学

## 7. 结构大纲（按理解路径）

### 第一节：事故开场——同一套表达式语法，为什么在不同命令里会做完全不同的事

目标：建立真实困惑，而不是直接讲 `isConditionMet()`。

要回答：

- `watch` 里表达式像过滤器和输出器
- `ognl` 里表达式像独立执行器
- `tt -s/-w` 里表达式又像历史现场查询器
- 本篇真正要追的是：同一引擎在不同生效点上的职责差异

预估字数：900-1100

### 第二节：先排除几个错误直觉——一次求值、纯查询、历史现场统一处理

目标：做失败方案推演。

要回答：

- 为什么条件和结果表达式不能混成一次求值
- 为什么 `ognl` 不能被误当成只读查询工具
- 为什么 `tt -s` 和 `tt -w` 不能简单共享完全同一执行策略
- 真正需要的是“职责分离 + 上下文边界 + 风险分级”

## 8. 必须展开的失败方案

至少要展开以下失败方案：

1. 把条件和结果表达式合成一次求值
2. 把 `ognl` 当成只读查询工具
3. 把 `tt -s` 和 `tt -w` 当成同样的执行场景
4. 忽略 `cost` / Advice / ClassLoader 的绑定边界
5. 把表达式引擎当成零成本过滤器

## 9. 本篇必须明确澄清的误解

1. `-e` 条件和输出表达式不是同一次求值
2. `cost` 的实际绑定名和帮助文案可能不同，源码语义优先
3. Advice 属性与显式 bind 变量不是同一类名字
4. `ognl` 可以执行方法调用，不是天然只读
5. `tt -p` 之外，`tt -s/-w` 也受 ClassLoader 与上下文策略影响
6. 表达式生效点不同，副作用边界就不同
