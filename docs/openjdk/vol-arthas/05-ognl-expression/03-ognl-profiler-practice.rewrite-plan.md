# 03-ognl-profiler-practice 重写规划

> 状态：重写前大纲
> 适用规范：`docs/openjdk/WRITING-GUIDELINES.md`
> 目标：把当前“ognl / profiler / thread / trace / watch 组合拳”重构成一篇围绕“对象观察和采样观察为什么不能混用，以及它们怎样按最小代价组合成线上排查路径”的生产实践文

## 1. 选题判断

这篇值得独立成篇，但不能继续写成：

- `ognl` 怎么用
- `profiler` 怎么用
- `thread` / `trace` / `watch` 怎么接上
- 最后给一个工具对照表

这种并列工具清单式实践文。

更好的统一问题是：

**线上异常出现时，为什么“对象状态不对”和“CPU 热点不清”不是同一个问题，不能用同一把工具硬解；而 Arthas 又怎样把 `thread`、`profiler`、`trace`、`watch`、`ognl` 这些能力按最小侵入和最大证据价值的顺序串起来？**

这样本篇就不再是“工具组合拳介绍”，而会被收束成一条更硬的生产决策链：

- 先分清问题是在“对象现场”还是“整体热点”
- `ognl` 解决直接读对象/静态成员的问题
- `profiler` 解决聚合热点的问题
- `thread` / `trace` / `watch` 负责把范围继续缩小
- 工具越强，副作用和成本越高，所以要按最小代价递进

## 2. 读者困惑

- 为什么线上对象状态异常时，不该先开 profiler？
- 为什么 CPU 100% 时，仅靠 `thread <id>` 看几个瞬时栈不一定够？
- `ognl`、`watch`、`trace`、`profiler` 明明都能“观察运行时”，为什么它们不等价？
- 为什么 `ognl` 能直接读对象，却不适合解释整体 CPU 热点？
- 为什么 `profiler` 能画火焰图，却不适合直接看参数和返回值？

## 3. 一句话顿悟

**线上排查不是“哪个功能最强就先用哪个”，而是先分清你面对的是对象问题还是热点问题：`ognl` 适合直接读取运行时对象和静态成员，`profiler` 适合回答整体 CPU/alloc/lock 热点，`thread` / `trace` / `watch` 则负责把这两条路径继续缩小到线程、方法和单次调用现场。真正稳定的不是命令顺序，而是“先低侵入缩范围，再用更高成本工具精确解释”。**

## 4. 版本边界

正文开头必须明确：

- 基于 `arthas` 当前命令实现与前面 AR-2 / AR-3 / AR-5 / AR-6 机制篇讨论
- 聚焦线上故障时 OGNL 与 Profiler 这两类观察范式的分工与组合路径
- 不重复展开 `ognl` 引擎、`watch/trace` 字节码织入、async-profiler native 细节；这里只把它们当作已知能力
- 这里讲的是实践路径和成本边界，不等于所有故障都必须按固定顺序执行命令

## 5. 旧稿主要问题

### 5.1 已有优点

- `ognl` / `profiler` / `thread` / `trace` / `watch` 的组合路径基本合理
- 已经提醒了 `ognl` 的副作用和 profiler 的聚合视角边界
- 工具对照表和安全清单都有实践价值

### 5.2 必须修复的问题

## 6. 重写策略

本篇不按工具列表推进，而按更强的问题链组织：

1. 先建立冲突：对象状态异常和整体 CPU 热点是两类不同问题
2. 先排除几个错误直觉：
   - 用 `ognl` 解释整体热点
   - 用 `profiler` 直接看对象现场
   - 一上来就开 trace/watch/heapdump
3. 再给总图：thread 缩线程范围 → profiler 看整体热点 → trace/watch 下钻方法 → ognl 直读对象状态
4. 然后分层拆：
   - `ognl` 的场景和副作用边界
   - `profiler` 的聚合视角和火焰图边界
   - 线程、类加载器、字节码工具怎样把范围继续缩小
   - 不同工具的成本与适用问题
5. 最后收束成“对象观察 / 采样观察 / 方法现场”三层实践路径

## 7. 结构大纲（按理解路径）

### 第一节：事故开场——对象状态不对和 CPU 热点不清，为什么不能用同一把工具

目标：建立真实困惑，而不是直接列命令。

要回答：

- 线上异常通常分成“对象状态错了”和“整体热点不清”两类问题
- 它们看起来都属于“运行时观察”，但证据形态完全不同
- 本篇真正要追的是：工具如何按问题类型分工

预估字数：900-1100

### 第二节：先排除几个错误直觉——直接 `ognl` 看热点、直接 profiler 看对象、先开 trace/watch

目标：做失败方案推演。

要回答：

- 为什么 `ognl` 不适合回答整体 CPU 热点
- 为什么 profiler 不会告诉你单次调用的参数和返回值
- 为什么一上来就 trace/watch 会过早提高观测成本
- 真正需要的是按证据和侵入性逐步升级

要回答：

- 读取静态成员、实例字段、类加载器版本确认的典型路径
- `-c <classLoaderHash>` 为什么重要
- 方法调用为何必须当成真实业务调用
- 为什么 `ognl` 更适合作为“先读、少写”的对象观察工具

### 第四节：第二层——profiler 适合回答“整体时间花在哪里”

目标：把 profiler 写成采样聚合工具，而不是对象观察工具。

要回答：

- `profiler start/stop --format html` 的典型路径
- CPU / alloc / lock / wall-clock 事件分别在看什么
- 火焰图横轴、纵轴和“不是时间线”的边界
- 为什么 profiler 适合多线程整体热点，不适合单次调用现场

### 第五节：第三层——`thread`、`trace`、`watch` 怎样把两条观察路径继续缩小

目标：把线程视角、方法视角和单次调用视角写成递进链。

要回答：

- `thread -n` / `thread <id>` 为什么是瞬时线程视角
- `trace` 为什么是方法内部调用树
- `watch` 为什么是单次调用现场
- 为什么这些工具必须建立在已缩小目标之后再用

预估字数：1800-2200

### 第六节：第四层——如何选择最小工具，而不是最强工具

目标：把工具成本、收益和适用问题统一起来。

要回答：

- `ognl` 的副作用风险
- `profiler` 的持续采样成本
- `watch/trace` 的字节码增强成本
- `thread` 的线程快照与 CPU 窗口成本
- 为什么“功能最强”通常不是最佳起手式

预估字数：1500-1800

### 第七节：收网——对象观察、采样观察、方法现场三层路径

目标：把全文收成一句话并桥接后续。

必须点名：

- 对象状态 → `ognl`
- 整体热点 → `profiler`
- 线程与方法缩范围 → `thread` / `trace` / `watch`
- 低侵入优先，逐步升级

预估字数：800-1000

## 8. 必须展开的失败方案

至少要展开以下失败方案：

1. 用 `ognl` 去解释整体 CPU 热点
2. 用 profiler 去看单次调用参数、返回值
3. 一上来就对全应用做 trace/watch
4. 忽略类加载器版本，直接在多版本类上执行 `ognl`
5. 把方法调用型 `ognl` 当成无副作用查询

## 9. 本篇必须明确澄清的误解

1. `ognl` 不是安全只读浏览器
2. profiler 不是单次调用解释器
3. `thread`、`trace`、`watch` 不是互相替代，而是不同粒度观察层
4. 工具选择应由问题类型和侵入成本共同决定
5. 先缩小范围再增强/采样，比一上来最强工具更稳定
