# 02-cpu-sampling 重写规划

> 状态：重写前大纲
> 适用规范：`docs/openjdk/WRITING-GUIDELINES.md`
> 目标：把当前“ThreadSampler 双采样 / CPU 排序”重构成一篇围绕“线程 CPU 为什么不是一个瞬时可读字段，Arthas 又怎样在交互式命令里用两次采样近似出窗口热点”的机制文

## 1. 选题判断

这篇值得独立成篇，但不能继续写成：

- 第一次采样做什么
- 第二次采样做什么
- HotSpotThreadMBean 做什么
- TopN 怎么截断

这种按实现步骤顺排的说明文。

更好的统一问题是：

**`thread -n 3` 为什么不会立刻返回？线程 `%CPU` 又为什么不是像 `state` 一样直接从对象上读出来，而必须先采一次、等一段时间、再采一次，才能得到一个可排序的窗口热点近似值？**

这样本篇就不再是“ThreadSampler 导览”，而会被收束成一条更硬的采样链：

- `ThreadMXBean` 给的是累计 CPU 时间，不是瞬时百分比
- Arthas 只能用两次采样差值逼近窗口占用率
- 基线采样与结论采样职责不同
- TopN 只是排序后的深挖窗口，不是第一阶段就能直接知道的结果
- 内部线程支持是能力补充，不是与普通线程等价的精度承诺

## 2. 读者困惑

- 为什么 `thread -n 3` 要先等一会儿，而不是立刻返回？
- `%CPU` 为什么不能直接从 `Thread`、`ThreadVO` 或 `ThreadMXBean` 某个字段上读出来？
- 为什么必须做两次采样？
- 为什么第一次采样并不输出真正结论？
- 为什么内部线程也能进排行榜，但它们的精度边界又不完全一样？
- 为什么先取 TopN 再读锁/栈详情，不能反过来？

## 3. 一句话顿悟

**线程 CPU 不是一个瞬时字段，而是一个“累计 CPU 时间”计数器。Arthas 必须先读一次累计值建立基线，再等一个时间窗口，再读第二次累计值，用差值除以墙钟窗口，才得到近似的窗口 CPU 占用率；排序完成后，再对少数热点线程读取昂贵的深度详情。**

## 4. 版本边界

正文开头必须明确：

- 基于 `arthas` 当前源码与 `ThreadMXBean` / `HotspotThreadMBean` 行为讨论
- 聚焦普通线程 CPU 双采样与内部线程能力补充
- 不把下一篇阻塞锁统计提前写成本篇主线；这里只把深度 `ThreadInfo` 读取当作 TopN 之后的下游
- 这里讲的是 Arthas 当前实现的交互式近似采样，不等于操作系统 perf 级或 async-profiler 级 CPU 统计精度

## 5. 旧稿主要问题

### 5.1 已有优点

- 已经抓到“CPU 使用率没有一个瞬时字段”这个最关键事实
- 基线采样 / 第二次差值采样 / TopN 深挖 / 内部线程能力补充的关键锚点都在
- 已经注意到了内部线程与普通线程在对象身份 key 上的精度边界
- 已经解释了为什么排序先于深度 ThreadInfo 查询

### 5.2 必须修复的问题

- 当前骨架仍偏“双采样实现说明文”，冲突感还不够强
- 失败方案推演不够厚：为什么不能直接读一个百分比字段、为什么不能只采一次、为什么不能先取全量深度信息再排序，都还没打透
- 内部线程路径虽然解释了精度边界，但还没完全收回到“能力补充而非等价精度来源”这个主判断
- `200ms` 默认值虽然有解释，但还没很好地嵌入“交互速度 vs 统计平滑度”的主线

## 6. 重写策略

本篇不按代码执行顺序平铺，而按更强的问题链组织：

1. 先建立冲突：用户只想看“最忙的线程”，但 CPU 没有瞬时字段
2. 先排除几个错误直觉：
   - 直接读一个 `%CPU` 字段
   - 只采一次
   - 不等时间窗口
   - 先给全体线程都取深度 ThreadInfo 再排序
3. 再给总图：第一次基线采样 → 等待窗口 → 第二次差值采样 → 排序 → TopN 深挖
4. 然后分层拆：
   - 基线采样为什么只建立参照系
   - 差值采样为什么才能得到窗口热点
   - 内部线程为什么是补充视野而不是等价精度来源
   - TopN 为什么先便宜排序、后昂贵深挖
5. 最后收束成“线程是谁”和“线程刚才多忙”两阶段诊断链

## 7. 结构大纲（按理解路径）

### 第一节：事故开场——用户只想看最忙的线程，但 `%CPU` 根本不是一个现成字段

目标：建立真实困惑，而不是直接列 ThreadSampler 步骤。

要回答：

- `thread -n 3` 为什么要等待
- 用户想看的其实是“刚才这段时间谁最忙”
- `ThreadMXBean` 给的却是累计 CPU 时间，不是瞬时百分比
- 本篇真正要追的是：交互式命令如何从累计值逼近窗口热点

预估字数：900-1100

### 第二节：先排除几个错误直觉——直接读百分比、只采一次、全量深度信息先上

目标：做失败方案推演。

要回答：

- 为什么不能直接从 `ThreadVO` 或 `ThreadMXBean` 读到现成 `%CPU`
- 为什么只采一次只会得到“从线程出生到现在”的累计视角，而不是“刚才”
- 为什么如果先对全体线程做深度 ThreadInfo，再排序，成本会先爆掉

## 8. 必须展开的失败方案

至少要展开以下失败方案：

1. 直接读一个现成 `%CPU` 字段
2. 只采一次就下结论
3. 把累计 CPU 时间误当成“刚才最忙”
4. 先对全体线程取深度 ThreadInfo 再排序
5. 把内部线程结果误当成和普通线程完全等价的窗口差值精度

## 9. 本篇必须明确澄清的误解

1. `ThreadMXBean.getThreadCpuTime()` 返回的是累计 CPU 时间，不是瞬时百分比
2. 第一次采样不是失败结果，而是基线建立
3. 第二次按 delta 排序回答的是窗口热点，不是线程生涯总账
4. 多线程场景下线程 CPU 百分比之和可以超过 100%
5. 内部线程 id `-1` 是显示模型标识，不是可再次查询的 Java 线程 id
6. 内部线程支持是能力补充，不等于与普通线程同精度的双采样实现
