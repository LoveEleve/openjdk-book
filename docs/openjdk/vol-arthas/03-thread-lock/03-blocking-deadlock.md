## 先看一个最容易误判的现场：线程都卡住了，为什么 CPU 热点未必是真堵点

场景：接口全部超时，线程表里出现大量 `BLOCKED` 或 `WAITING`。上一篇你已经能用：

```text
thread -n 3
```

找出“刚才这段窗口里最忙的线程”。

但这时一个更容易被误用的直觉就会跳出来：

> 既然我已经知道谁最忙了，那最忙的线程应该就是真正把大家堵住的罪魁祸首。

这个直觉并不总成立。因为在锁争用现场里，真正的堵点可能是：

- 一个自己并不太忙的持锁线程；
- 它当前握着某把锁；
- 其他大量线程因此排队。

也就是说，CPU 热点和锁堵点回答的是两类完全不同的问题：

```text
CPU 热点：谁刚才最忙
锁堵点：谁握着哪把锁，让最多线程排队
```

所以本篇真正要回答的不是：

> `thread -b` 具体调了哪些 API？

而是：

> **接口全超时、线程表里全是 `BLOCKED/WAITING` 时，为什么 CPU 排名前几的线程未必是真堵点？Arthas 又怎样用一次全量深度快照，把“当前最热的争用锁”和“真正的死锁环”区分开？**

先把全篇总图立住：

```text
线程大量阻塞
  → 不能再靠轻量 CPU 快照判断堵点
    → 一次 dumpAllThreads() 拿到深度锁快照
      → 分别统计“谁在等哪把锁”和“谁当前持有哪把锁”
        → 找出“等待人数最多且当前确实有持有者”的锁
          → 把答案钉回持锁线程的具体栈帧
            → 若要确认是否形成死锁环，再交给 findDeadlockedThreads()
```

这张图里最重要的两刀是：

```text
thread -b 解决的是争用热点定位
findDeadlockedThreads() 解决的是循环等待确诊
```

后面所有细节，都围绕这条边界展开。

## 一、先排除几个最直觉、也最容易把“卡住”误判成“死锁”的方案

### 1.1 错觉一：只看 CPU 热点，就能找到真正堵点

上一篇 `thread -n` 回答的是“谁刚才最忙”。这对 CPU 抢占型问题非常有效，但到了锁争用现场，最忙线程不一定是堵点：

- 持锁线程可能自己 CPU 并不高；
- 可它手里的那把锁，却让几十个线程同时排队。

所以一旦问题从“忙”切换成“堵”，诊断入口就必须从 CPU 采样切换到锁拥有关系。

### 1.2 错觉二：只统计“有多少线程在等某把锁”，不看当前谁在持有

另一个直觉方案是：

> 既然要找堵点，那就统计哪把锁当前等待人数最多。

这还不够。因为快照里的等待关系本身可能有时序性：

- 线程在等待某把锁；
- 但当前深度快照里，未必能找到一个仍在持有它的线程；
- 如果没有当前明确持有者，你就不能把它直接解释成“最堵路的持锁线程”。

所以“最多等待人数”只是半张图，另一半必须补上：**当前是谁在持有这把锁。**

### 1.3 错觉三：只要线程都 `BLOCKED/WAITING`，那就是死锁

这也是现场最常见的语言误用。很多线程都卡住，可能只是：

- 一个慢持锁线程让大量请求排队；
- 条件等待、超时等待、线程池空转都叠在一起；
- 并不一定形成 A 等 B、B 等 A 这种循环等待。

所以“线程都卡住了”和“存在死锁环”不是同一个结论。

这也解释了为什么 Arthas 必须把：

- `thread -b` 当成锁争用热点定位工具；
- `findDeadlockedThreads()` 当成死锁确认工具。

## 二、第一层：为什么 `thread -b` 必须走一次全量深度快照

### 2.1 上一篇的轻量线程快照，为什么这次不够用了

前一篇的线程枚举链主要解决“谁存在、处于什么状态”。那份轻量快照足够支持：

- 线程列表；
- 状态统计；
- CPU 双采样。

但到了锁堵点问题，这些信息明显不够。你要知道的不只是“线程在等”，而是：

- 它在等哪把锁；
- 这把锁此刻谁持有；
- 持有线程的具体栈帧是什么；
- 还有多少别的线程也在等同一把锁。

所以 `thread -b` 必须切换到更重的一次性深度快照。

### 2.2 `dumpAllThreads()` 一次拿到的，不只是线程列表

入口在 `core/util/ThreadUtil.java:99-101` 的 `findMostBlockingLock()`：

```java
threadMXBean.dumpAllThreads(
    threadMXBean.isObjectMonitorUsageSupported(),
    threadMXBean.isSynchronizerUsageSupported())
```

这和上一章的 CPU 双采样完全不同。这里不是隔着时间窗口去看一个线程的活跃度，而是直接向 JVM 要一次**全量深度线程快照**：

- 线程栈；
- 当前等待锁；
- 已持有的 monitor；
- 已持有的 ownable synchronizer。

关键设计（斜体）：*一旦问题从“谁最忙”切换成“谁把路堵住了”，轻量快照就不够了，必须直接请求一次全量深度线程图景。*[模式: 深度快照] 这是故障定位专用路径，不该变成普通线程命令的默认成本。

### 2.3 为什么这条路径故意不做成默认行为

`dumpAllThreads()` 本身就很重：它要拿所有线程的栈和锁信息。线程很多、栈很深时，成本不会低。

所以 Arthas 没把它塞进普通线程列表路径，而是明确让 `thread -b` 走一条专门的“重查询”路径。换句话说，它在成本上已经承认：**锁堵点诊断不是轻量筛选，而是一笔专门为故障定位支付的开销。**

## 三、第二层：为什么等待关系和持有关系必须拆成两张表

### 3.1 `thread -b` 真正要拼的是两张视图

拿到 `ThreadInfo[]` 后，`findMostBlockingLock()` 维护两张 Map（`ThreadUtil.java:103-106`）：

```java
Map<Integer, Integer> blockCountPerLock;
Map<Integer, ThreadInfo> ownerThreadPerLock;
```

它们分别回答两个问题：

- 有多少线程在等某把锁；
- 这把锁当前是谁持有。

这两件事不能混在一张表里，因为它们来自不同来源，也承担不同语义。

### 3.2 第一张表：等待人数回答“哪里堵”

`info.getLockInfo()` 表示当前线程快照里关联到的等待锁。只要不为 null，就按 `lockInfo.getIdentityHashCode()` 给 `blockCountPerLock` 加一（`ThreadUtil.java:113-121`）。

这张表统计的是：

```text
本次快照里
有多少线程此刻正等在同一个锁对象上
```

它不回答“这把锁谁持有”，也不回答“它历史上争用过多少次”。

### 3.3 第二张表：持有者回答“谁把路堵住了”

线程当前持有的锁来自两类来源：

- `info.getLockedMonitors()`（`ThreadUtil.java:123-128`）
- `info.getLockedSynchronizers()`（`:130-135`）

它们共同把“某把锁当前被谁握在手里”记录到 `ownerThreadPerLock` 里。

也就是说：

- 等待表在描述“受害者分布”；
- 持有者表在描述“堵路者是谁”。

关键设计（斜体）：*锁争用诊断不能只看排队人数，也不能只看谁手上有锁；必须把等待关系和持有关系拆成两个视角，再在最后一步合并。*[模式: 直方图 + 反向索引]

## 四、第三层：为什么热点争用锁必须同时满足“等待人数最多”与“当前确实有人持有”

### 4.1 最热争用锁不是“随便选一个等待最多的锁”

选择逻辑在 `ThreadUtil.java:138-147`：

```java
if (entry.getValue() > maxBlockingCount
        && ownerThreadPerLock.get(entry.getKey()) != null) {
    mostBlockingLock = entry.getKey();
    maxBlockingCount = entry.getValue();
}
```

它有两个条件：

1. 等待数量超过当前最大值；
2. 该锁在持有者表里确实有当前持有者。

也就是说，Arthas 找的不是“等待人数多的锁”，而是：

```text
等待人数最多
并且当前的确能找到持有它的线程
```

### 4.2 为什么没有持有者的等待锁不该直接当答案

如果只按等待人数选，可能会把某些“看起来很多线程在等、但当前快照里没有明确持有者”的对象错当成主要堵点。

Arthas 在这里刻意收紧答案，是因为 `thread -b` 要返回的不是抽象统计，而是一个可操作的排查线索：

- 哪一个具体线程；
- 在哪一个具体锁帧；
- 当前挡住了多少线程。

没有持有者，这条线索就不完整。

### 4.3 为什么 `EMPTY_INFO` 不是错误，而是“这次快照没有合格答案”

如果没有满足条件的候选锁，方法返回 `EMPTY_INFO`（`ThreadUtil.java:149-152`）；`ThreadCommand.processBlockingThread()` 在 `ThreadCommand.java:175-181` 检查后再输出失败信息。

这不是“算法失败”，而是在明说：**本次快照没有找到一个既热又有明确当前持有者的争用点。**

关键设计（斜体）：*`thread -b` 不是随便给一个“看起来像答案”的锁，而是只在答案足够完整时才返回。*[模式: 热点筛选 + 持有者确认]

## 五、第四层：为什么 `identityHashCode` 只是快照期身份标签，而不是永久锁 ID

### 5.1 为什么这里必须按对象身份，而不是 `equals()`

锁争用回答的是：

```text
是不是同一个锁对象
```

而不是：

```text
这两个对象业务上 equals 是否相等
```

所以这里使用的是 `LockInfo.getIdentityHashCode()`。它的作用是把：

- 等待者看到的 `LockInfo`
- 持有者看到的 `MonitorInfo` / `LockInfo`

在同一次快照里对上号。

### 5.2 为什么它不能被误读成永久全局锁编号

这也意味着，identity hash 在这里的意义是有限的：它只服务于**这一次 dump 快照里的对象身份关联**。

它不是：

- 跨时间稳定的锁编号；
- 业务层能长期依赖的锁 ID；
- JVM 生命周期里的永久对象身份索引。

关键设计（斜体）：*这里的 identity hash 是快照期身份标签，不是业务可持久引用的锁编号。*[模式: 快照身份标签]

## 六、第五层：为什么 `thread -b` 是线索扫描，而 `findDeadlockedThreads()` 才是确诊工具

### 6.1 争用热点和死锁环不是同一个问题

Arthas 的 `jvm` 命令里会展示 `DEADLOCK-COUNT`，来源在 `JvmCommand.java:184-200`：

```java
threads.findDeadlockedThreads()
```

这个 API 关注的是：

```text
有没有线程形成循环等待
A 等 B，B 等 A，或者更长的等待环
```

而 `thread -b` 关注的是：

```text
当前哪把锁让最多线程在排队
并且当前能明确找到持有者
```

两者不是同一个维度。

### 6.2 为什么一个慢持锁线程可以堵住很多线程，却根本不构成死锁

这正是现场最常见的误判来源：

- 一个线程拿着锁执行得很慢；
- 其他几十个线程都在它后面排队；
- `thread -b` 会很快给你一个“最热争用点”；
- 但 `DEADLOCK-COUNT` 仍然可能是 0。

因为这里没有环，只是单点拥塞。

### 6.3 为什么死锁确认必须留给专门 API

反过来，真正的死锁环当然也属于“锁问题”，但你不能只靠“等待人数最多”去推断有没有形成环。

所以 Arthas 在这里做了一个非常清晰的职责拆分：

- `thread -b`：先做线索扫描，告诉你“最值得先看的堵点在哪”；
- `findDeadlockedThreads()`：再做精确判定，确认是否真的存在循环等待。

关键设计（斜体）：*争用热点筛选和死锁环确认，必须拆成两阶段工具，而不是让一个命令同时装作“扫描器”和“确诊器”。*[模式: 线索扫描 + 精确判定]

## 收网：锁诊断不是一个动作，而是“热点争用筛选 + 死锁环确认”的两阶段链

现在把整条链收成一张图：

```text
1. 发现大量 BLOCKED / WAITING，说明问题可能已从 CPU 转向锁争用
2. thread -b 先走一次 dumpAllThreads() 深度快照
3. 快照里分别建立“谁在等哪把锁”和“谁当前持有哪把锁”两张表
4. 只挑出“等待人数最多且当前有持有者”的锁，定位到具体持锁线程与栈帧
5. 如果还要确认是不是形成死锁环，再交给 findDeadlockedThreads()
```

把这张图压成一句话，就是：

**Arthas 处理锁问题时，并不是直接把“线程都卡住了”叫成死锁，而是先用 `thread -b` 在一次深度快照里筛出“最热争用锁”和持锁线程，再把真正的死锁确认交给 `findDeadlockedThreads()` 这种专门看循环等待的 API。**

到这里为止，主线其实只发生了四件事：

- CPU 热点和锁堵点是两类不同问题；
- `thread -b` 必须走一次全量深度快照，而不是复用轻量线程视图；
- 等待关系和持有关系必须拆成两张表，再合起来筛热点；
- 死锁确认不能靠“最多等待人数”推断，而要交给专门的循环等待检测 API。

这也解释了为什么 `thread -b` 和 `DEADLOCK-COUNT` 看起来都在处理“线程卡住”，却不该被混用：**前者是找最值得先查的堵路点，后者是确认 JVM 是否真的形成等待环。**

跨层标注：[JMX ThreadMXBean——`dumpAllThreads` 与 `findDeadlockedThreads`]；[锁拥有关系——monitor 与 ownable synchronizer 在快照中的两条来源]；[线程快照——锁诊断从轻量 ThreadVO 切换到深度 ThreadInfo]；[线索扫描与确诊分离——争用热点不等于死锁环]
