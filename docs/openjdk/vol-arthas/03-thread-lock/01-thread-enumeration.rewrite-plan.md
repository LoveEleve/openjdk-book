# 01-thread-enumeration 重写规划

> 状态：重写前大纲
> 适用规范：`docs/openjdk/WRITING-GUIDELINES.md`
> 目标：把当前“线程枚举 / ThreadVO / 状态统计”重构成一篇围绕“Arthas 为什么拿不到一张现成的线程总表，只能自己从 ThreadGroup 树构造一份可采样、可过滤、可渲染的线程快照”的机制文

## 1. 选题判断

这篇值得独立成篇，但不能继续写成：

- `ThreadUtil.getRoot()` 做什么
- `getThreads()` 怎么枚举
- `ThreadVO` 有哪些字段
- `ThreadCommand` 怎么统计状态
- `ViewRenderUtil` 怎么画颜色

这种按工具类和数据类平铺的说明文。

更好的统一问题是：

**Arthas 明明只是想回答“当前 JVM 里有哪些线程”，为什么却拿不到一张现成的全局线程表，而必须自己沿 `ThreadGroup` 树去枚举、重试、做快照、再在快照上做状态统计和后续采样？**

这样本篇就不再是“线程命令实现导览”，而会被收束成一条更硬的主线：

- JVM 没有现成的“线程总表”给 Arthas 直接读取
- Arthas 只能借 ThreadGroup 树做一次带并发容忍的快照构造
- 快照必须与活线程对象分离，才能支持后续采样、过滤、渲染
- 全量状态统计和条件过滤必须分开，才能既保留全局背景又支持局部视图

## 2. 读者困惑

- `thread --state BLOCKED` 这样的命令，Arthas 到底先从哪里拿到“所有线程”？
- JVM 为什么没有一张可以直接 `getAllThreads()` 的全局线程表？
- 为什么线程枚举还要做数组翻倍重试？
- 为什么不直接把活的 `Thread` 对象交给渲染层，而要先拷贝成 `ThreadVO`？
- 为什么状态统计和状态过滤要分成两件事？

## 3. 一句话顿悟

**Arthas 并不是在读取一张现成的线程总表，而是在当前 JVM 的 `ThreadGroup` 树上主动构造一份线程快照：先递归枚举出活线程，再把它们冻结成 `ThreadVO` 值对象，然后在这份快照上分别做“全量状态统计”和“条件过滤后展示”，为下一篇 CPU 双采样提供稳定输入。**

## 4. 版本边界

正文开头必须明确：

- 基于 `arthas` 当前源码与 JDK `ThreadGroup` / `ThreadMXBean` 行为讨论
- 聚焦“线程是谁”的枚举与快照问题，不提前展开下一篇 CPU 双采样算法
- 不把死锁、阻塞线程持有者分析、ThreadMXBean 细节扩写成本篇主线；这里只把它们当作 `ThreadCommand` 的分支消费者
- 这里讲的是 Arthas 当前 Java 层线程枚举策略，不等于 JVM 规范承诺必须这样实现

## 5. 旧稿主要问题

### 5.1 已有优点

- 已经抓到“JVM 没有一张所有线程表”这个关键事实
- `getRoot()` / `getThreads()` / `ThreadVO` / `processAllThreads()` 的关键锚点完整
- 已经指出状态统计与状态过滤不是同一集合
- 已经明确 ThreadVO 是快照，不是活线程对象

### 5.2 必须修复的问题

- 当前骨架仍偏“工具链说明文”，冲突感不够强
- 失败方案推演不够厚：为什么不能直接拿现成总表、为什么不能直接把 Thread 对象交给渲染层、为什么不能边过滤边统计，都还没打透
- 颜色和视图部分现在像渲染附录，还没收回到“快照如何变成人能读的排查入口”这条主线上
- 结尾虽然桥到了 CPU 双采样，但还没把“线程是谁”和“线程忙了多少”明确写成两阶段问题

## 6. 重写策略

本篇不按实现文件顺序推进，而按更强的问题链组织：

1. 先建立冲突：用户只想看线程列表，但 Arthas 手里并没有现成的线程总表
2. 先排除几个错误直觉：
   - JVM 肯定有一张全局线程表
   - 枚举一次数组就够了
   - 直接把 `Thread` 对象往后传就行
   - 状态统计和过滤可以一步做完
3. 再给总图：ThreadGroup 树 → 递归枚举 → 扩容重试 → ThreadVO 快照 → 全量状态统计 → 条件过滤 → 后续采样
4. 然后分层拆：
   - 为什么要先爬到根线程组
   - 为什么枚举是带并发变化容忍的快照构造
   - 为什么 ThreadVO 是值对象快照
   - 为什么全量统计和局部视图必须分离
   - 颜色和视图怎样把快照变成排查入口
5. 最后收束成“线程是谁”和“线程忙了多少”两阶段诊断链

## 7. 结构大纲（按理解路径）

### 第一节：事故开场——你只是想看线程列表，为什么 Arthas 手里却没有一张现成总表

目标：建立真实困惑，而不是直接列 `ThreadUtil` 方法。

要回答：

- `thread --state BLOCKED` 看起来像个简单查询
- 但 Arthas 首先得回答“当前 JVM 里到底有哪些线程”
- 本篇真正要追的不是“工具类怎么写”，而是“没有总表时，线程视图怎么被构造出来”

预估字数：900-1100

### 第二节：先排除几个错误直觉——现成总表、一次枚举到底、活对象直接下传、边统计边过滤

目标：做失败方案推演。

要回答：

- 为什么不能假设有 `getAllThreads()` 这样的稳定总表
- 为什么一次 `enumerate()` 不保证拿全线程
- 为什么不能把活的 `Thread` 对象直接交给渲染和采样层
- 为什么状态统计与条件过滤不能混成一步

预估字数：1400-1700

### 第三节：第一层——为什么要先爬到根线程组

目标：把 `ThreadGroup` 树写成枚举入口，而不是实现细节。

要回答：

- `ThreadUtil.getRoot()` 为什么不是猜根组名字，而是沿 `getParent()` 真实向上爬
- ThreadGroup 树为什么是 Arthas 在 Java 层能借到的线程组织结构
- 这一步真正解决的是“从哪里开始看全体线程”

证据锚点：

- `core/util/ThreadUtil.java:29-35`

预估字数：1200-1500

### 第四节：第二层——为什么线程枚举必须带扩容重试

目标：把 `getThreads()` 写成一次带并发容忍的快照构造。

要回答：

- `activeCount()` 为什么只是容量估计，而不是精确线程数
- `enumerate(threads, true)` 的递归枚举意味着什么
- 为什么“返回值等于数组容量”要被当成可能截断的信号
- 线程在枚举期间创建/结束，会给快照带来什么不确定性
- 这里的目标不是完美静止世界，而是构造一份够用的观察快照

证据锚点：

- `ThreadUtil.java:41-54`

预估字数：1700-2100

### 第五节：第三层——为什么 `ThreadVO` 必须是值对象快照，而不是活线程对象本身

目标：把 ThreadVO 写成“观察结果冻结层”。

要回答：

- `createThreadVO()` 复制了哪些字段
- 为什么这些字段足够支撑状态、渲染和后续采样填充
- 为什么活线程对象继续变化，会污染排序、过滤和输出层
- `cpu` / `deltaTime` / `time` 预留字段为什么说明下一篇会在快照上继续加工

### 第六节：第四层——为什么状态统计和状态过滤必须分成两件事

- `processAllThreads()` 为什么先对全量 ThreadVO 做状态聚合，再按 `--state` 过滤展示集合

## 8. 必须展开的失败方案

至少要展开以下失败方案：

1. 假设 JVM 有一张现成的稳定线程总表
2. 枚举时一次数组容量就足够
3. 直接把活 Thread 对象交给渲染和采样层
4. 边做状态统计边做 `--state` 过滤
5. 把颜色当成线程状态本身，而不是终端视图策略

## 9. 本篇必须明确澄清的误解

1. Arthas 不是在读取一张现成总表，而是在构造线程快照
2. `ThreadGroup.enumerate()` 的返回结果不是绝对稳定世界的全貌
3. `ThreadVO` 不是线程实体，而是观察结果值对象
4. 全量状态统计和当前过滤结果不是同一集合
5. CPU 不是枚举阶段直接读出来的固定字段，而是下一篇双采样的结果
6. 颜色映射属于可读性设计，不属于线程状态本体
