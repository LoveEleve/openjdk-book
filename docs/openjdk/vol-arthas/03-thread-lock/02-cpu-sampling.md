## 先看一个最容易被忽略的现场：你只是想看“最忙的线程”，为什么命令却不会立刻返回

场景：你执行：

```text
thread -n 3
```

Arthas 不会立刻把答案打给你，而是先等一小段时间。这段等待如果不知道原理，很容易被误会成“命令卡住了”。

但这里恰恰藏着本篇真正的问题：**线程 `%CPU` 根本不是一个像 `state` 那样现成挂在线程对象上的瞬时字段。**

`ThreadMXBean.getThreadCpuTime(id)` 给出的不是“此刻 CPU 百分比”，而是：

```text
线程从启动到现在为止累计消耗了多少 CPU 纳秒
```

所以用户真正想问的“谁刚才最忙”，在源码里必须先翻译成另一个数学问题：

```text
刚才这段时间里
累计 CPU 时间增加了多少？
```

也就是说，本篇真正要回答的不是：

> ThreadSampler 先做了什么、后做了什么？

而是：

> **`thread -n 3` 为什么不会立刻返回？线程 `%CPU` 又为什么不是像 `state` 一样直接从对象上读出来，而必须先采一次、等一段时间、再采一次，才能得到一个可排序的窗口热点近似值？**

先把全篇总图立住：

```text
已有线程快照 ThreadVO 列表
  → 第一次读取累计 CPU 时间，建立基线
    → 等待 sampleInterval
      → 第二次读取累计 CPU 时间
        → 用差值除以墙钟窗口，得到近似 CPU 百分比
          → 按窗口 delta 排序
            → 截出 Top N
              → 再对少数热点线程读取昂贵的深度 ThreadInfo
```

这张图里最重要的一刀就是：

```text
%CPU 不是现成字段
而是“累计 CPU 时间的两次读数差”除以“墙钟窗口差”之后的窗口近似值
```

后面所有细节，都围绕这条边界展开。

## 一、先排除几个最直觉、也最容易让 CPU 排名失真的方案

### 1.1 错觉一：直接从线程对象或 MXBean 上读一个现成 `%CPU`

最直觉的想法当然是：

> 线程都有 id、name、state 了，CPU 百分比也应该有个现成字段吧？

这恰恰是最根本的误解。`ThreadMXBean.getThreadCpuTime(id)` 返回的是**累计 CPU 时间**，不是一个已经归一化好的百分比；它告诉你的是“这个线程从出生到现在一共跑了多久 CPU”，而不是“刚才这 200ms 它占了多少 CPU”。

所以 Arthas 不是在读一个“现在值”，而是在利用两个累计值逼近一个窗口值。

### 1.2 错觉二：只采一次就可以知道谁最忙

如果只读一次累计 CPU 时间，能得到的只是：

```text
这个线程到现在总共用了多少 CPU
```

这回答不了用户真正关心的问题：

```text
刚才这段时间里，谁最忙
```

一个已经跑了很久、累计 CPU 很高但此刻很闲的线程，和一个刚刚突然爆发 CPU 的线程，在单次累计读数里会被混成一张“生涯总账”。

所以单次采样不是“不够精”，而是**问题本身就答错了**。

### 1.3 错觉三：先把所有线程的深度信息全取回来，再慢慢排序

另一个看似保险的做法是：

> 既然最终还要看 Top N 的锁信息、栈信息，不如先把所有线程的深度 `ThreadInfo` 都取回来，再统一排序。

这会把成本顺序彻底反过来：你明明只关心少数热点线程，却先对上千线程都做了昂贵的深度查询。这样诊断命令在真正开始有价值排序前，就已经把成本打满。

所以 Arthas 的正确顺序必须是：

```text
先用便宜的双采样把热点筛出来
再对少数候选线程做昂贵深挖
```

### 1.4 错觉四：内部线程和普通线程拿到的是完全一样精度的结果

Arthas 还会补充 GC、编译器、Watcher 等 JVM 内部线程的 CPU 视角，但这并不意味着它们天然和普通 Java 线程走的是完全相同精度的双采样路径。

这一点如果不先提醒，读者很容易把“能排到一起展示”误解成“采样语义完全相同”。后面会看到，内部线程路径更像能力补充而不是等价精度承诺。

## 二、第一层：第一次采样为什么只负责建立基线

### 2.1 第一次采样不是结论，而是参照系

`core/command/monitor200/ThreadSampler.java:34-77` 的 `sample(Collection<ThreadVO>)`，在第一次调用时 `lastCpuTimes` 为空，于是走基线分支：

1. 记录 `lastSampleTimeNanos = System.nanoTime()`（`:40`）；
2. 对每个 id 大于 0 的普通线程调用 `threadMXBean.getThreadCpuTime(id)`（`:41-45`）；
3. 把累计 CPU 纳秒数放进 `lastCpuTimes`；
4. 同时把累计 CPU 时间转换成毫秒写进 `ThreadVO.time`；
5. 按累计 `time` 降序排一次（`:61-75`）。

这一步最关键的不是它“采了一次样”，而是它明确没有声称自己已经知道“谁刚才最忙”。它做的只是：

```text
在 T1 时刻
给每个线程记下一个累计 CPU 时间基线
```

### 2.2 为什么第一次按累计 `time` 排序不等于真正的热点排序

第一次排序按的是累计 `time`，它只能告诉你：

- 到现在为止谁“生涯累计 CPU”更高；
- 不能告诉你刚才这段窗口里谁更热。

所以如果把第一次采样结果直接当成最终热点列表，就会把“线程从出生到现在有多忙”和“线程在最近窗口里有多忙”混为一谈。

关键设计（斜体）：*第一次采样的职责是建立参照系，不是输出结论。*[模式: 基线采样 + 延迟结论] 用户看到的那段等待不是命令迟缓，而是算法刻意先放下判断，等第二次采样补全窗口信息。

### 2.3 为什么调用方必须显式执行“采一次 → pause → 再采一次”

`ThreadCommand.java:165-169` 在 `processAllThreads()` 路径里明确这样调用：

```java
threadSampler.sample(resultThreads);
threadSampler.pause(sampleInterval);
List<ThreadVO> threadStats = threadSampler.sample(resultThreads);
```

默认采样间隔来自 `ThreadCommand.java:54` 的 `sampleInterval = 200`。

这说明 `ThreadSampler` 不是一个“我随手调一次就给你百分比”的黑盒，而是一种两阶段协议：

```text
第一次 sample
  → pause(窗口长度)
    → 第二次 sample
      → 才能下结论
```

## 三、第二层：第二次采样为什么才能把累计值变成窗口热点

### 3.1 真正的 CPU 百分比来自“累计值差”

第二次进入 `sample()` 后，ThreadSampler 记录新的墙钟时间（`ThreadSampler.java:79-80`），再读取当前普通线程的累计 CPU 时间（`:81-87`）。

真正有意义的量现在才出现：

```text
delta = time2 - time1
```

也就是：这个线程在两次采样之间新增消耗了多少 CPU 时间。

这是用户想问的“刚才这段时间里谁最忙”的唯一靠谱近似答案。

### 3.2 为什么还必须再除以墙钟窗口

光有 `delta` 还不够。两个线程在不同长度窗口里的 `delta` 不可直接比较，所以还要计算：

```java
sampleIntervalNanos = newSampleTimeNanos - lastSampleTimeNanos
```

对应 `ThreadSampler.java:116`。

最后百分比计算在 `:118-123`：

```java
Math.rint(delta * 10000.0 / sampleIntervalNanos) / 100.0
```

这里乘 `10000` 再除 `100`，只是为了四舍五入到两位小数；数学本质仍然是：

```text
窗口内 CPU 时间增量 / 窗口墙钟时间
```

关键设计（斜体）：*累计时间回答“从出生到现在用了多少”，差值时间才回答“刚才这个窗口用了多少”。*[模式: 差值采样 + 窗口归一化] Arthas 真正排序的是窗口内活动强度，而不是线程生涯总账。

### 3.3 为什么这仍然不是“绝对瞬时值”

这里必须主动收紧一个边界：即使做了两次采样，这个结果仍然是**窗口平均占用率**，不是硬件意义上的瞬时值。

也就是说，它回答的是：

- “在最近这 200ms 左右的窗口里，谁更忙”；
- 而不是“就在某个 CPU 时钟瞬间，谁正在执行”。

这也是为什么它适合交互式诊断，而不是冒充 perf 级采样器。

### 3.4 普通线程这条差值语义成立，依赖于两次采样复用同一批 `ThreadVO`

在 `processAllThreads()` 这种路径里，两次采样复用同一个 `resultThreads` 集合，因此基于 `ThreadVO` 对象身份的 `lastCpuTimes` key 能够对应起来，差值语义成立。

这也解释了为什么“对象身份”在这里不是偶然实现细节，而是采样链成立的一部分约束。

## 四、第三层：为什么 `200ms` 不是越短越好，也不是某种神奇常数

### 4.1 采样窗口越短，越接近局部状态，也越容易抖

如果把间隔调得很短：

- 结果更贴近局部瞬时状态；
- 但调度抖动、线程切换、计时误差的影响也会被放大；
- 交互式命令反而可能更容易出现“这次看起来像热点、下次又不像”的抖动体验。

### 4.2 采样窗口越长，越平滑，也越慢

如果把间隔调得很长：

- 结果更平滑；
- 但用户会更明显感觉到命令在等待；
- 对于想快速救火的交互式场景，反馈速度会变差。

### 4.3 为什么 `200ms` 更像折中，而不是 JVM 神奇常数

默认值 `200ms` 只是 Arthas 在“交互速度”和“统计平滑度”之间选的折中点，不是某个 JVM 层面的神奇常数。

它适合大多数交互式排查场景，但并不意味着：

- 你永远不该调短；
- 也不意味着调长一定更准。

关键设计（斜体）：*采样窗口不是正确答案的一部分，而是用户在“反馈速度”和“统计平滑度”之间选的诊断参数。*[模式: 交互式近似采样]

## 五、第四层：内部线程为什么能进结果，但精度边界不等同于普通线程

### 5.1 Arthas 为什么还要补一条内部线程视野

上一章的线程枚举主要来自 Java 层线程树，但真正的 CPU 热点并不总是业务线程：GC、编译器、Watcher 等 JVM 内部线程也可能是热点。

所以 `ThreadSampler` 还会尝试在 `getInternalThreadCpuTimes()`（`ThreadSampler.java:157-181`）里调用：

```java
ManagementFactoryHelper.getHotspotThreadMBean()
    .getInternalThreadCpuTimes()
```

也就是说，采样器不愿意把“业务线程快照”误当成“JVM 全部 CPU 消耗视野”。

### 5.2 为什么内部线程的 `ThreadVO` 只是显示模型

如果成功拿到内部线程 CPU 数据，它会按名字构造 `ThreadVO`，并把 id 记成 `-1`（`ThreadSampler.java:172-179`）。

这个 `-1` 不是一个真实可再次查询的 Java 线程 id，而只是：

```text
这是内部线程显示模型，不是普通 Java Thread 的 id
```

这一步已经主动提醒你：内部线程结果可以进入视野和排序，但它不等于完全复用了普通 Java 线程的全部采样语义。

### 5.3 为什么内部线程更容易退化成累计时间近似

当前实现里，第一次和第二次采样都会为内部线程重新创建新的 `ThreadVO`；而 `lastCpuTimes` 使用的是 `ThreadVO` 对象身份作为 key（`ThreadSampler.java:28,54-57,91-95,100-105`）。

这意味着第二次采样的新内部线程 VO，通常匹配不到第一次的旧 key，于是 `time1` 会回退到 `0`。结果就可能把内部线程的累计 CPU 时间当成这次 delta，而不是严格的窗口差值。

所以内部线程这条路径的定位必须收紧成：

**能力补充和视野补全，而不是和普通线程完全等价的双采样精度承诺。**

### 5.4 为什么获取失败后要直接降级关闭

如果 `HotspotThreadMBean` 获取失败，catch 分支会把 `hotspotThreadMBeanEnable` 设为 `false`，后续不再反复尝试。

这说明内部线程视野在设计上就是：

- 能拿到就补全；
- 拿不到就关闭这条可选能力；
- 但不能让它反过来拖垮主线程命令链。

关键设计（斜体）：*内部线程 CPU 视野是能力补充，不是主命令路径的生死依赖。*[模式: 能力探测 + 可关闭降级]

## 六、第五层：为什么 Top N 必须先便宜排序，再对少数线程取深度信息

### 6.1 `thread -n` 真正要做的是“先筛候选，再深挖”

`ThreadCommand.processTopBusyThreads()` 在 `ThreadCommand.java:184-219` 里：

1. 先 `ThreadUtil.getThreads()` 拿线程快照；
2. 做第一次采样；
3. 等待 `sampleInterval`；
4. 做第二次采样；
5. 让 ThreadSampler 按 delta 降序排序；
6. 通过 `subList(0, limit)` 截出 Top N。

也就是说，TopN 的真正含义不是“用户一开始就只看 3 个线程”，而是：

```text
先用便宜的 CPU 差值把全体线程排出候选顺序
  → 再对最值得看的少数线程做昂贵深挖
```

### 6.2 为什么深度 `ThreadInfo` 不该先于排序对全体线程执行

截断之后，Arthas 才读取深度 `ThreadInfo`：

```java
threadMXBean.getThreadInfo(tids, lockedMonitors, lockedSynchronizers)
```

然后把 `ThreadVO` 和 `ThreadInfo` 合并成 `BusyThreadInfo`（`ThreadCommand.java:212-219`）。

如果顺序反过来——先对全体线程取深度锁/栈详情，再排序——你会在还不知道谁值得看之前，就已经把最昂贵的信息采集成本付完了。

关键设计（斜体）：*先便宜排序，后昂贵深挖。*[模式: 候选集筛选 + 深度诊断] 这正是交互式诊断命令控制总体开销的关键。

## 收网：线程枚举回答“谁存在”，CPU 双采样回答“谁刚才最忙”

现在把整条链收成一张图：

```text
1. 先拿到 ThreadVO 线程快照
2. 第一次 sample 读取累计 CPU 时间，建立基线
3. 等待 sampleInterval
4. 第二次 sample 再读累计 CPU 时间
5. 用两次差值 / 墙钟窗口，得到近似窗口 CPU 百分比
6. 按 delta 排序，截出 Top N
7. 再对少数热点线程读取锁/栈等深度 ThreadInfo
8. 内部线程则作为 HotSpot 能力补充进入视野
```

把这张图压成一句话，就是：

**Arthas 不是在直接读取一个现成的 `%CPU` 字段，而是在已有线程快照上，通过“两次累计 CPU 时间读数 + 一个墙钟窗口差”逼近线程刚才这段时间的忙碌程度；排序完成后，再只对少数热点线程做昂贵深挖。**

到这里为止，主线其实只发生了四件事：

- `%CPU` 不是现成字段，而是窗口差值；
- 第一次采样建立基线，第二次采样才给结论；
- 内部线程是能力补充，不是与普通线程完全等价的精度来源；
- TopN 之后才值得花高成本读锁和栈详情。

这也解释了为什么 `thread -n 3` 会先等一下：**这段等待不是命令卡住了，而是 ThreadSampler 在为“刚才谁最忙”这个问题制造一个可计算的时间窗口。**

跨层标注：[JMX ThreadMXBean——累计线程 CPU 时间与深度 `ThreadInfo`]；[HotSpotThreadMBean——内部线程 CPU 视野补充]；[AR-3 线程快照——`ThreadVO` 作为双采样输入基底]；[交互式采样——窗口近似优先于绝对瞬时值]
