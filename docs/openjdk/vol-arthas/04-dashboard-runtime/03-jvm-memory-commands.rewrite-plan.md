# 03-jvm-memory-commands 重写规划

> 状态：重写前大纲
> 适用规范：`docs/openjdk/WRITING-GUIDELINES.md`
> 目标：把当前“jvm / memory / dashboard 数据边界”重构成一篇围绕“同一批 JVM 运行时数据为什么要被做成一次性快照命令和持续刷新面板两种消费方式，而不是互相完全复制”的机制文

## 1. 选题判断

这篇值得独立成篇，但不能继续写成：

- `jvm` 有哪些数据块
- `memory` 有哪些数据块
- dashboard 只显示其中哪些
- 最后给一个排查树

这种命令能力列表式说明文。

更好的统一问题是：

**既然 `jvm`、`memory` 和 Dashboard 都在看 JVM 运行时状态，为什么 Arthas 不把它们做成一个命令的三种皮肤，而是保留一次性快照命令、专项内存命令和持续刷新面板三种不同消费方式？**

这样本篇就不再是“命令清单导览”，而会被收束成一条更硬的消费边界链：

- 数据源可以共享
- 消费方式不能强行统一
- `jvm` 追求一次性完整盘点
- `memory` 追求内存池与缓冲细节
- Dashboard 追求持续趋势与高频可读性

## 2. 读者困惑

- Dashboard 里已经有 heap/GC/runtime 了，为什么还要单独有 `jvm` 和 `memory`？
- `jvm` 为什么看起来像一个“大杂烩”命令，却仍然有存在价值？
- `memory` 为什么不直接被 Dashboard 整块替代？
- 既然它们都在读 MXBean，为什么不干脆合并成一条统一输出？
- 同一份运行时数据，为什么要分成“持续趋势”、“完整盘点”、“专项细节”三种消费方式？

## 3. 一句话顿悟

**Arthas 并不是为 `jvm`、`memory` 和 Dashboard 分别维护三套监控实现，而是在复用同一批 MXBean / Thread / HTTP stats 来源的前提下，故意把消费方式拆开：`jvm` 负责一次性完整盘点，`memory` 负责内存池与堆外细节，Dashboard 负责只挑高频有价值的字段持续刷新。也就是说，数据源可以共享，输出节奏、覆盖面和视图重点不能强行统一。**

## 4. 版本边界

正文开头必须明确：

- 基于 `arthas` 当前源码实现讨论
- 聚焦 `jvm` / `memory` / Dashboard 三种消费方式的边界
- 不重复展开上一章 Dashboard 定时引擎；这里只把它当成持续刷新消费面的上游
- 不把后续实践篇的排查经验扩写成本篇主线；这里只把诊断决策树当作收尾桥接
- 这里讲的是 Arthas 当前命令编排边界，不等于所有诊断工具都必须把完整快照、专项视图和持续面板拆成三条命令

## 5. 旧稿主要问题

### 5.1 已有优点

- 已经抓到“Dashboard、jvm、memory：同一批数据的三种消费方式”这个关键边界
- `JvmCommand` 九个数据块、`MemoryCommand.memoryInfo()`、Dashboard 复用路径等锚点都在
- 已经注意到不同数据块算法口径不同
- 有一个实用的内存异常决策树

### 5.2 必须修复的问题

- 当前骨架仍偏“功能清单说明文”，主问题不够集中
- 失败方案推演不够厚：为什么不合并成一个命令、为什么 Dashboard 不整块复制 `jvm`、为什么 `memory` 不能只看 heap 总量，都还没打透
- `jvm` 九个数据块目前像列表介绍，缺少“为什么这些块属于一次性完整盘点”这一层统一判断
- `memory` 和 Dashboard 内存区的关系还可以更明确地写成“共享数据源，不共享消费层次”
- 决策树很好，但可以更自然地收束到“先趋势，再专项，再完整盘点”这条链路上

## 6. 重写策略

本篇不按命令清单推进，而按更强的问题链组织：

1. 先建立冲突：同样是 JVM 运行时状态，为什么不做成一个统一命令
2. 先排除几个错误直觉：
   - Dashboard 足够了，不需要 `jvm` / `memory`
   - `jvm` 足够全，可以取代 Dashboard
   - `memory` 只要看 heap 总量
3. 再给总图：共享数据源，三种不同消费方式
4. 然后分层拆：
   - `jvm` 为什么属于一次性完整盘点
   - `memory` 为什么属于专项内存细视图
   - Dashboard 为什么只取高频有价值字段持续刷新
   - 三者怎样共享来源但避免口径与输出结构混淆
5. 最后收束成“共享数据源，分化消费层”的设计哲学

## 7. 结构大纲（按理解路径）

### 第一节：事故开场——Dashboard 已经有 heap/GC/runtime 了，为什么还要 `jvm` 和 `memory`

目标：建立真实困惑，而不是直接列三条命令。

要回答：

- 用户很自然会觉得面板已经够用
- 但趋势观察、完整盘点、专项内存细节其实是三种不同问题
- 本篇真正要追的是“为什么同一批数据要被做成三种消费方式”

预估字数：900-1100

### 第二节：先排除几个错误直觉——一个命令包打天下、Dashboard 全复制、只看 heap 总量

目标：做失败方案推演。

要回答：

- 为什么不能把 `jvm` / `memory` / Dashboard 合并成一个超级命令
- 为什么 Dashboard 不该每 5 秒重绘 `jvm` 的全部盘点块
- 为什么内存异常不能只看 heap used / max 总量
- 真正需要的是：趋势面、完整盘点面、专项细节面分层

预估字数：1400-1700

### 第三节：第一层——`jvm` 为什么是一次性完整盘点，而不是持续趋势面板

目标：把 `JvmCommand` 九个数据块写成“全景盘点模型”。

要回答：

- 为什么 `jvm` 会一次性把 Runtime、ClassLoading、Compilation、GC、MemoryManagers、Memory、OS、Thread、FileDescriptor 这些维度都盘出来
- 为什么这些数据块有些依赖当前 MXBean 能力和可用性，不能简单理解成固定表头
- 为什么它适合一次性基线诊断，而不适合高频面板刷新

证据锚点：

- `monitor200/JvmCommand.java:24`
- `JvmCommand.java:39-200`

预估字数：1900-2300

### 第四节：第二层——`memory` 为什么是专项内存视图，而不是 Dashboard 内存块的放大版

目标：把 `MemoryCommand` 写成“内存池 / 堆外细节模型”。

要回答：

- `memoryInfo()` 为什么要同时汇总 HEAP、NON-HEAP、BUFFER-POOL
- 为什么 `used`、`committed`、`max` 不能混成一个“内存涨了”的粗判断
- 为什么 Dashboard 的内存块不能替代 `memory` 命令对 pool 级与堆外区的展开

证据锚点：

- `monitor200/MemoryCommand.java:30,42-103`

预估字数：1800-2200

### 第五节：第三层——为什么 Dashboard 只能挑一部分字段持续刷新，而不能整块复制 `jvm`

目标：把 Dashboard 写成“高频趋势面板”。

要回答：

- Dashboard 为什么只挑线程/CPU、内存、GC、Runtime 和可选 Tomcat
- 为什么 `jvm` 里的类加载、编译、内存管理器、文件描述符等块不适合每 5 秒重绘
- “完整盘点”和“趋势刷新”在输出结构与采集频率上为什么不能统一

证据锚点：

- `DashboardCommand.java` 采集路径（桥接回指）
- `DashboardView` 布局（桥接回指）

预估字数：1700-2100

### 第六节：第四层——同一批数据源为什么可以共享，但口径与消费语义又必须分离

目标：把共享与分离的边界写清楚。

要回答：

- `memory` 与 Dashboard 内存块共享 `MemoryCommand.memoryInfo()`，意味着什么
- GC 在 Dashboard 中是累计值趋势参照，在 `jvm` 中是完整盘点块，意味着什么
- `DEADLOCK-COUNT`、线程统计、FileDescriptor 等块为什么更适合 `jvm` 的一次性盘点
- 共享来源不等于共享输出语义

预估字数：1700-2100

### 第七节：第五层——一条内存/运行时异常的诊断决策树

目标：把三种消费方式收回到实际排查路径。

要回答：

- Dashboard 异常时先看趋势
- `memory` 负责池级 / 堆外细节
- `jvm` 负责把类加载、GC、文件句柄、死锁等背景一次性盘清
- 什么时候该继续 `heapdump --live`

要求：这节是收束，不是实践篇发散。

预估字数：1200-1500

### 第八节：收网——共享数据源，分化消费层

目标：把全文收成一句话并桥接下一篇。

必须点名：

- `jvm` 一次性全景盘点
- `memory` 专项内存细节
- Dashboard 持续趋势面板
- 共享数据源 / 分化消费语义
- 下一篇实践边界

预估字数：800-1000

## 8. 必须展开的失败方案

至少要展开以下失败方案：

1. 把 `jvm` / `memory` / Dashboard 合并成一个大命令
2. 让 Dashboard 每 5 秒完整重绘 `jvm` 全部数据块
3. 只看 heap used / max 就判断内存问题
4. 共享数据源就误以为三种命令语义完全等价
5. 把 Tomcat、GC、Runtime 全部强行解释成同一种窗口口径

## 9. 本篇必须明确澄清的误解

1. Dashboard 不是 `jvm` 的实时版
2. `jvm` 不是 Dashboard 的“完整版皮肤”
3. `memory` 不是只看 heap 总量的简单命令
4. 共享来源不等于共享输出结构和消费节奏
5. 累计值、窗口值、环境事实这三类指标可以同时存在于 Arthas，但不该被混成一种口径
6. Tomcat 区域与 JVM 内其他数据源并不是同一种采集协议
