## 一句话困惑

为什么生产环境里看起来最像“运维工作”的那些动作——限制来源、优雅关闭、健康检查、远端地址修正、JMX/Micrometer 指标、资源泄漏防守——最后追回源码时，总会重新落到 Tomcat 那几条运行时主线本身？

## 一句话顿悟

Tomcat 的安全与运维问题，并不是部署外壳上的附属主题，而是 **请求入口、执行链、类空间退场、生命周期收束这些结构在生产环境中的守护问题。**

## 读者理解路径

1. 从“为什么安全和运维不是独立附录，而是主线的生产投影”切入。
2. 建立最小总图：入口边界 -> 执行边界 -> 生命周期边界 -> 观测边界。
3. 解释来源地址、访问控制、Valve 等为什么本质上是入口边界治理。
4. 解释优雅关闭、健康检查、生命周期管理为什么是运行时收束治理。
5. 解释 JMX/Micrometer 观测为什么不是“顺手监控”，而是把前文主线变成可见指标。
6. 解释类加载泄漏、Session、长期运行边界为什么会变成运维风险而不仅是代码细节。
7. 最后收束：安全与运维不是和源码平行的一套知识，而是源码主线在生产环境里的延伸。

## 失败方案推演

### 失败方案一：安全就是上 WAF，运维就是看监控

这是最常见的分工式理解：
- 安全交给网关/WAF
- 运维交给监控平台
- Tomcat 本体只负责跑请求

问题在于，很多真正的生产边界并不在最外层，而在容器自己身上：
- 来源 IP 怎么被解释
- 健康状态何时对外可见
- 优雅关闭时请求怎么收尾
- 旧应用类空间退不退得掉

也就是说，安全和运维很多时候不是外围补丁，而是容器本体的结构性守护。

### 失败方案二：生产问题和源码主线无关，只看配置参数就够了

这和性能调优时的误解很像。看起来生产治理经常只剩几类配置：
- 访问日志
- RemoteIpValve
- 优雅关闭
- JMX / Micrometer 开关

但如果不回到前文主线，读者就不知道：
- 这些配置到底在保护哪一段运行时结构
- 它们为什么不是“可有可无的小功能”

### 失败方案三：观测只是额外附加能力

很多人把 JMX、Micrometer、访问日志当成“加上更好，不加也无所谓”的辅助能力。

这个判断不够稳。因为对于生产容器来说，可观测性本身就是把内部主线暴露成外部可判断信号的机制。没有这些信号，很多结构性问题根本无从被及时发现。

## 必须澄清的误解

1. 安全与运维不是主线之外的附属知识，而是主线的生产边界。
2. RemoteIpValve、健康检查、优雅关闭、JMX/Micrometer 都不是“小工具”，而是在保护或暴露前文主线。
3. 可观测性不是顺手加监控，而是把内部结构变成外部可见信号。
4. 本篇讲的是“怎么守住结构”，不是完整的事故排查手册。
