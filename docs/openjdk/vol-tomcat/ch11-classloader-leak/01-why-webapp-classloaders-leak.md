# 为什么应用停了，类空间却没退场：Tomcat 的类加载器泄漏与卸载失败主线

> 本文基于 Tomcat 10.1.34 当前源码。本文只讲 WebApp 类空间在“退场”阶段为什么会失败：请求已经不再进入、Context 已经停止、应用甚至已经重载，但整套类空间仍然可能因为线程、ThreadLocal、JDBC 驱动、缓存、RMI targets 等活引用链而被拖住。本文关注的主线是 `WebappClassLoaderBase.stop() -> clearReferences()` 以及它为什么既重要，又不可能成为万能兜底。

## 为什么应用都停了，老类和老实例却还可能挂在 JVM 里

从业务视角看，一个应用停下来往往很直观：

- Context 停止了
- 请求不再进来了
- 部署被替换了
- 新版本已经开始接流量

于是很容易自然产生一个想法：

既然应用都已经停了，那它原来的类、实例和状态，不就该顺势被 JVM 回收掉了吗？

这个想法之所以危险，是因为它混淆了两个完全不同的判断标准：

- **业务上看，应用是不是已经停了**
- **JVM 看，这套类空间是不是已经没有活引用了**

对 Tomcat 来说，真正决定一个 WebApp 能不能退场的，不是“请求还来不来”，而是：

- 还有没有线程在引用它的类
- 还有没有 ThreadLocal 把对象挂住
- 还有没有 JDBC 驱动、缓存、反射结构、RMI 目标把 ClassLoader 拖住

也就是说，应用停下来只代表：
- 它不再继续向前处理请求

却不代表：
- 它在 JVM 里的整套类世界已经成功退出

这也就是为什么在 Tomcat 场景里，类加载器泄漏会变成一个比普通 Java 应用更真实、更常见的问题。

因为 Tomcat 不是只启动一个应用然后跟着 JVM 一起结束，而是：

- 在同一个容器里长期托管多个 WebApp
- 允许应用停止、重载、替换
- 希望旧应用的类空间真正退场，为新应用让位

一旦旧类空间退不干净，问题就不再只是“某个对象还活着”，而会变成：

- 旧 WebApp 的类和静态状态残留
- Metaspace 逐步抬高
- 重载后出现新旧版本并存
- 最后演化成整应用无法卸载的类加载器泄漏

所以，本文真正要回答的问题不是“什么叫类加载器泄漏”，而是：

**为什么对 Tomcat 这种长期托管多应用的容器来说，应用停了并不等于类空间就退场了？**

## 先看失败方案：为什么不能把卸载失败理解成“GC 没及时收”

### 失败方案一：请求不来了，类自然就会被卸掉

这是最自然的直觉，因为很多人对类卸载的印象来自普通应用：

- 程序结束
- JVM 退出
- 一切都跟着结束

但 Tomcat 面对的不是这种“进程跟应用同生共死”的模型，而是：

- 容器继续活着
- 只有某个应用停了或重载了
- 旧应用的类空间要单独退出

这时候，JVM 判断能不能卸载类，看的不是“业务结束没结束”，而是：

- 这个 ClassLoader 还能不能被触达
- 这个 ClassLoader 加载出来的类对象还能不能被引用链追到

只要答案还是“能”，那就算请求早就不来了，整个 WebApp 类空间也可能继续活着。

所以这里最根本的问题不是“请求停止了没有”，而是“引用链断干净了没有”。

### 失败方案二：类加载器泄漏其实就是 ThreadLocal 泄漏

ThreadLocal 确实是最常见的源头之一，所以很多人一提类加载器泄漏，脑子里就只剩这一种模式：

- 线程没退
- ThreadLocal 没清
- 类加载器被挂住

这个理解抓住了一部分真实情况，但如果就停在这里，会把 Tomcat 当前清理链讲窄。

因为 Tomcat 明显不是只盯着 ThreadLocal 一种源头。它在 `WebappClassLoaderBase` 里主动考虑和尝试处理的残留源，还包括：

- JDBC 驱动
- 各类线程
- Timer 线程
- RMI targets
- `ObjectStreamClass` 缓存
- 其他跨类空间残留引用

这说明一个重要事实：

**类加载器泄漏不是某一种单点故障，而是“整套应用类空间仍被外界引用”这件事在多个方向上的不同表现。**

ThreadLocal 只是最有名的一种，不是全貌。

### 失败方案三：Tomcat 有 `clearReferences()`，所以容器会替应用全部擦干净

这也是非常危险的误解。

因为一看到 Tomcat 有主动清理逻辑，读者很容易产生一种安全感：

- 反正容器会在 stop 时清理
- 所以应用就算写得脏一点，Tomcat 也会兜底

问题在于，容器能不能替应用清理，取决于三个现实限制：

- 它能不能识别那条引用链
- 它有没有权限去断开那条链
- 断开这条链会不会引入更大的副作用

也就是说，`clearReferences()` 更像一种“尽力而为的退场清理”，不是“保证无泄漏的回收魔法”。

如果把它写成万能开关，就会严重误导读者对容器职责边界的判断。

## Tomcat 里类加载器卸载失败的最小总图

如果把这条后半段主线先压缩成最小模型，它可以写成下面这样：

```text
WebApp stops/reloads
   -> WebappClassLoaderBase.stop()
   -> clearReferences()
   -> try to cut residual references
   -> if references remain, classloader still retained
```

如果再换一种更容易理解的拆法，这条链可以分成三段职责：

```text
[应用类世界]
Servlet / Filter / Listener / app dependencies / static state

   ->

[残留引用链]
threads / ThreadLocals / JDBC drivers / caches / RMI targets

   ->

[容器清理动作]
stop() -> clearReferences() -> specialized cleanup methods
```

这张图最重要的价值，不是让读者先记方法名，而是先把三个问题分开：

### 一、应用类世界
回答：到底是什么东西要被卸载掉？

### 二、残留引用链
回答：为什么应用停了，这些类和对象还会继续活着？

### 三、容器清理动作
回答：Tomcat 在应用退场时具体试图清理什么、又为什么清不一定彻底？

只要这三层先分开，类加载器泄漏为什么会出现，就不再像一个玄学问题。

## 一、`stop()`：Tomcat 不是等着 GC 自己收，而是主动进入退场流程

只要进入多应用容器语境，就应该先放弃一个直觉：

- 应用停了，GC 自己总会收掉

Tomcat 当前实现并不是这么被动的。它在 `WebappClassLoaderBase` 上明确提供了一个生命周期入口：

证据：`org/apache/catalina/loader/WebappClassLoaderBase.java:1523`

这说明，对 Tomcat 来说，类加载器退场不是一个“等 JVM 自己看着办”的后处理细节，而是应用生命周期的一部分。

更准确地说，`stop()` 的意义不在于“简单标记这个加载器停了”，而在于：

**容器已经明确意识到，这个 WebApp 的类世界现在应该开始退场。**

也正因为如此，`stop()` 后面不会空着，而是紧跟着走向更关键的清理动作：`clearReferences()`。

## 二、`clearReferences()`：Tomcat 为什么要主动断引用链

`clearReferences()` 的定义位置：

证据：`org/apache/catalina/loader/WebappClassLoaderBase.java:1574`

只要看这个方法名，很多人第一反应会是：“Tomcat 要去清理引用。”

这个直觉没错，但还不够深。更准确的理解应该是：

**Tomcat 已经默认承认：只靠应用停掉、请求结束，并不足以保证类空间真正退出。**

所以它才必须主动进入一轮“退场清理”逻辑。

也就是说，`clearReferences()` 这个方法本身就已经是一种问题陈述：

- 旧应用类空间退不出去，这不是例外，而是容器必须正面处理的风险

因此，这里最重要的不是方法体里哪一行清了什么，而是整个方法存在本身就说明：

- 类加载器卸载失败在 Tomcat 场景里不是偶发噪声
- 容器必须为它准备专门的清场动作

## 三、为什么 Tomcat 要专门清 JDBC、线程、缓存、RMI targets

Tomcat 在 `clearReferences()` 后面，不是做一个统一“大扫除”，而是拆成多类专门清理动作。这种拆法本身就很能说明问题。

### 1. JDBC 驱动

证据：`org/apache/catalina/loader/WebappClassLoaderBase.java:1642`

JDBC 驱动之所以危险，不在于它“能访问数据库”，而在于它很容易通过驱动注册表、静态单例等方式把应用类空间挂住。

### 2. 线程与 Timer 线程

证据：`org/apache/catalina/loader/WebappClassLoaderBase.java:1678`
证据：`org/apache/catalina/loader/WebappClassLoaderBase.java:364`
证据：`org/apache/catalina/loader/WebappClassLoaderBase.java:1604`

线程泄漏之所以可怕，是因为线程本身就是活引用源。一旦线程还活着，它的上下文类加载器、ThreadLocal、任务对象、定时器链都可能把整个 WebApp 拖住。

这里还可以看到，Tomcat 并不是抽象地“顺便想到了 ThreadLocal”，而是明确保留了 `clearReferencesThreadLocals` 这一开关，并在 `clearReferences()` 里显式走 `checkThreadLocalsForLeaks()`。这再次说明：ThreadLocal 不是类加载器泄漏的全部，但它确实是容器明确重点照看的高风险源头之一。

### 3. `ObjectStreamClass` 缓存

证据：`org/apache/catalina/loader/WebappClassLoaderBase.java:2151`

这类缓存特别能说明问题：并不是只有“显眼的大对象”才会拖住类空间，连序列化元信息缓存这种平时完全不在业务视野里的东西，也可能成为残留引用的一部分。

### 4. RMI targets

证据：`org/apache/catalina/loader/WebappClassLoaderBase.java:2081`

这一类目标再次提醒我们：容器要处理的不是某一种固定泄漏，而是各种“跨出应用类空间边界后仍然残留的引用”。

把这些并列放在一起看，最重要的结论不是“Tomcat 有很多清理方法”，而是：

**Tomcat 已经明确把类加载器泄漏理解成一组多源头、多方向的残留引用问题。**

这也是为什么 ThreadLocal 只是常见样本，而不是全貌。

## 四、`modified()`：类加载隔离为什么天然连到重载

类加载器卸载失败不仅发生在“应用停掉之后”，它还天然连接到另一个容器能力：重载。

证据：`org/apache/catalina/loader/WebappClassLoaderBase.java:676`

`modified()` 这种入口的存在，本身就说明：Tomcat 不只是想把应用装起来和跑起来，它还要面对“应用变了之后怎么办”的问题。

而只要应用允许重载，类加载边界就不再只是“隔离可见性”这么简单，它还会变成：

- 新旧类空间如何切换
- 旧类空间能不能真正退出
- 旧实例和旧线程会不会把整个旧世界拖住

所以重载和泄漏本来就是同一条线的前后两端：

- `modified()` 关心“是不是该换新世界了”
- `clearReferences()` 关心“旧世界能不能真的退场”

也正因为如此，本篇不能只讲“隔离”，还必须顺手把“退场失败”这半段一起带出来。

## 五、为什么容器再努力，也不能保证替应用完全兜底

看到这里，很容易产生一种新的错觉：

- 既然 Tomcat 连 JDBC、线程、缓存、RMI targets 都考虑到了
- 那它是不是已经足够强大，能替应用彻底擦干净所有泄漏源？

答案仍然是否定的。

原因并不复杂：容器能做的清理，本质上总是受限于它能观察到、能定位到、能安全切断的那部分引用链。

一旦应用自己在别的地方：

- 留下跨类空间静态引用
- 把对象挂进容器无法控制的全局结构
- 开了不受控线程或第三方框架资源

Tomcat 即使知道“这里有风险”，也不一定能无副作用地强行清掉。

所以更准确的说法应该是：

- `clearReferences()` 很重要
- 但它是容器层的尽力清场
- 它不能替代应用自己遵守退场纪律

这也是为什么类加载器泄漏最终总会同时落到两个责任面上：

- 容器有没有尽力切断已知残留源
- 应用自己有没有留下超出容器可控范围的引用链

## 到了这里，类加载器泄漏已经不再像“JVM 小知识”，而像容器生命史的后半段

现在再回头看“为什么应用停了，类空间却没退场”这个问题，已经可以看得更清楚了。

Tomcat 遇到的不是“某个类偶然没回收”，而是：

- 应用作为一个独立类世界进入容器
- 运行中不断生成对象、线程、缓存、驱动、反射结构
- 退场时如果这些引用链没断干净，整个类世界就可能一起留在 JVM 里

所以类加载器泄漏并不是一个离主线很远的边角故障，而是：

**Tomcat 在多应用容器语境下，必须面对的生命周期后半段问题。**

这也解释了为什么前一篇要先讲类加载隔离，而这一篇要继续讲卸载失败。因为“类世界怎么建立”和“类世界怎么退场”本来就是同一条线的前后两半。

## 这篇真正立住的，是“退场失败”不是 GC 偶然抽风，而是引用链没断

如果只从表面看，类加载器泄漏很容易被讲成：

- 类没卸掉
- Metaspace 涨了
- JVM 有点怪

但从 Tomcat 当前实现归纳出来，更稳妥的理解方式应该是：

1. WebApp 停止不等于类空间自动退出
2. 类空间能否退出，取决于引用链是否真正断开
3. `stop()` / `clearReferences()` 说明 Tomcat 会主动做退场清理
4. 但容器的清理能力始终有限，无法替应用完全兜底

所以这篇真正补上的，不是几个清理方法，而是一种更关键的容器视角：

**Tomcat 管的不只是应用怎么活，也在尽力管理应用怎么退场。**
