## 一句话困惑

同样都是 Java 应用，为什么 Tomcat 不能像普通程序那样直接用一套类加载器把所有类都加载起来，而非要为每个 WebApp 维持一套独立的类加载世界？

## 一句话顿悟

Tomcat 不是只跑一个应用，而是在同一容器里托管多个 WebApp；因此类加载不再只是“怎么找到类”，而是**如何隔离应用、控制可见性、支持热部署、避免互相污染和帮助卸载**。

## 失败方案推演

### 失败方案一：Tomcat 直接用一套全局 ClassLoader 加载所有应用

这是普通 Java 应用最自然的直觉：
- 一个进程
- 一套类路径
- 一套类加载器
- 所有类都往里装

问题在于，Tomcat 面对的不是“一个程序”，而是“同一容器中的多个应用”。

如果所有 WebApp 都共享一套全局加载器，会立刻出现几个问题：
- 应用之间类名冲突怎么办
- 某个应用想带自己的依赖版本怎么办
- 一个应用的静态状态泄漏到另一个应用怎么办
- 某个应用重载时，旧类和旧实例怎么卸掉

所以对 Tomcat 来说，“一套全局加载器”从一开始就不是可行模型。

### 失败方案二：还是用传统双亲委派，一切按标准来就够了

另一个常见理解是：
- 好，那就每个应用一个 ClassLoader
- 但类加载规则仍按传统双亲委派来就行

这个理解也不够。

因为 Tomcat 面对的不是纯理论上的类查找，而是容器和应用之间复杂的可见性边界：
- 哪些类应该共享
- 哪些类应该被应用私有覆盖
- 哪些包应该由容器优先
- 哪些类必须对 WebApp 可见，但不能反过来污染容器

所以这里讨论的已经不是“委派模型教科书”，而是容器环境下的可见性与隔离策略。

### 失败方案三：类加载隔离只是部署细节，和请求主线没关系

这是另一个很容易低估的问题。因为类加载看起来不像请求链、Session、Mapper 那么“运行时”。

但实际上：
- Servlet 实例是谁创建的
- Filter/Listener/SCI 从哪套类空间里来
- Context 停止时旧实例为什么可能卸不掉
- 内存泄漏为什么会卡在 ClassLoader 上

这些问题最终都和类加载隔离直接相关。

所以它不是部署附属细节，而是 Tomcat 作为容器与普通嵌入式框架拉开差距的重要主线。

## 必须澄清的误解

1. Tomcat 的类加载问题不是“怎么找到类”，而是“怎么隔离应用并管理可见性”。
2. `WebappClassLoaderBase` 不是普通包装器，而是 WebApp 隔离机制的核心。
3. 打破传统直觉不是为了炫技，而是为了满足容器环境的现实需求。
4. 类加载隔离和热部署、卸载、泄漏是同一条线上的问题。
5. 本篇讲的是隔离与可见性主线，不是完整 JVM 类加载教程。
