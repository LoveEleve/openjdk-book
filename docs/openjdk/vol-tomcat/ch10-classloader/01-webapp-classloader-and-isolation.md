# 为什么 Tomcat 必须为每个 WebApp 维持一套独立类世界

> 本文基于 Tomcat 10.1.34 当前源码。本文只讲 `WebappClassLoaderBase` 这条主线：Tomcat 为什么不能像普通 Java 程序那样只靠一套统一 ClassLoader 把所有应用都装进去，而必须为每个 WebApp 维持自己的类空间、可见性边界与卸载路径。JVM 通用类加载原理、Spring Boot Loader 细节和生产排障会放在后续专题中分别展开。

## 为什么普通 Java 程序的类加载直觉，一到 Tomcat 这里就不够用了

如果只从普通 Java 应用的角度看，类加载问题通常不复杂。

最常见的直觉是：

- 一个进程
- 一套 classpath
- 一套 ClassLoader 体系
- 所有类都按这套结构被加载和解析

这种直觉在单体程序里大体成立，所以很多人第一次看 Tomcat 时，也会自然把它套过来：

- Tomcat 也是一个 Java 进程
- 那它大概也就是一套全局类加载器，把自己和应用一起装进去

这个理解的问题在于，它只适合“一个程序”的世界，不适合“一个容器同时托管多个应用”的世界。

Tomcat 面对的不是：
- 一个程序如何加载自己的类

而是：
- 多个 Web 应用如何共享容器、却又彼此隔离
- 哪些类必须容器共享
- 哪些类必须应用私有
- 一个应用停止或重载时，旧类和旧实例怎样真正退出

也就是说，在 Tomcat 这里，类加载不再只是“怎么找到类”，而变成了：

**如何为每个应用维护一套独立类世界，同时又让它和容器世界保持可控连接。**

所以，本文真正要回答的问题不是“Tomcat 用了哪个 ClassLoader 类”，而是：

**为什么 Tomcat 必须为每个 WebApp 维持一套独立类空间，而不能像普通 Java 程序那样用一套统一类加载器把一切都装进去？**

## 先看失败方案：为什么 Tomcat 不能共享一套全局类空间

### 失败方案一：一个 JVM 进程里，所有应用共用一套 ClassLoader 就够了

这是最符合普通应用直觉的方案。

毕竟 Tomcat 最终也是跑在一个 JVM 进程里，于是很容易产生这种想法：

- 反正 JVM 最后都是加载 Class
- 那容器和所有 WebApp 共用一套类加载器，不就最简单吗？

这个想法的问题在于，它会立刻撞上容器场景下最致命的几个矛盾：

- 两个应用带了不同版本的同名依赖怎么办
- 一个应用的静态单例、缓存、ThreadLocal 为什么不能污染另一个应用
- 一个应用卸载后，旧类为什么还可能被另一个全局加载器死死引用着
- 某个应用需要覆盖一部分容器可见类时，边界怎么控制

也就是说，全局一套类空间在“一个程序”里是简化，在“多个应用共享同一容器”里却会变成污染源。

所以 Tomcat 从一开始就不只是“加载类”，而是在解决“多应用共容器”的隔离问题。

### 失败方案二：每个应用一个 ClassLoader，但完全按传统双亲委派来就够了

当读者意识到“不能共用一套全局加载器”后，下一步常见直觉就是：

- 好，那每个应用一个 ClassLoader
- 但查找规则还是按传统双亲委派一路向上走

这个方案比第一种进了一步，但仍然不够。

因为 Tomcat 面对的问题，并不只是“每个应用分个箱子”，还包括：

- 哪些类必须由容器优先提供
- 哪些类应该允许 WebApp 自己覆盖
- 哪些类应当只在当前应用内可见
- 哪些对象一旦泄漏，会把整套应用类空间都拖住

换句话说，这里已经不是教科书里那种“父加载器优先还是子加载器优先”的纯模型讨论，而是容器环境下的可见性、隔离和卸载策略问题。

所以 `WebappClassLoaderBase` 这条线，绝不能被写成“Tomcat 版 ClassLoader 小技巧”。

### 失败方案三：类加载隔离只是部署细节，和运行时主线没什么关系

还有一个很容易低估的问题是：很多人会把类加载隔离看成部署或热部署场景下的小话题，觉得和请求主线、Session、async 这些“真正运行时”的主题没有直接关系。

这个判断同样不成立。

因为一旦往回看整个 Tomcat 卷，你会发现前面几条主线几乎都和类加载边界直接相连：

- Servlet 实例是在哪个类空间里被创建的
- Filter / Listener / SCI 是从哪套类空间里进入容器的
- Session 属性里挂的对象最终归哪套类空间所有
- 应用重载后旧实例为什么会卸不掉
- 类加载器泄漏为什么最后会变成整应用无法回收的问题

也就是说，类加载隔离不是部署尾声，而是**所有运行时主线的底层边界条件**。

## Tomcat 应用隔离的最小总图

如果把 Tomcat 的类加载隔离主线先压缩成最小模型，它大概可以写成这样：

```text
[容器公共类空间]
   <-> [WebappClassLoaderBase]
   <-> [单个 WebApp 私有类空间]
```

如果再换一种更容易理解的拆法，这条线可以分成三层职责：

```text
[共享容器世界]
Tomcat container classes

   ->

[隔离边界]
WebappClassLoaderBase

   ->

[应用私有世界]
Servlet / Filter / Listener / app dependencies
```

这张图最重要的价值，不是让读者先记类名，而是先把三个问题分开：

### 一、共享容器世界
回答：哪些类是多个应用共享的容器能力？

### 二、隔离边界
回答：谁负责决定“哪些类能进来、哪些类该隔开、哪些类该由谁先加载”？

### 三、应用私有世界
回答：为什么每个 WebApp 必须拥有自己的一套类空间？

只要先把这三层职责分开，后面为什么 `WebappClassLoaderBase` 不能被低估，就会清楚很多。

## 一、Tomcat 真正要隔离的，不是类名，而是“应用自己的运行世界”

第一次看 Tomcat 的类加载隔离时，最容易把问题想窄：

- 无非是不同应用别把同名类搞混了

这当然是其中一个问题，但远远不是全部。

Tomcat 真正要隔离的，其实是一个应用完整的运行世界。这里面不仅有：

- Servlet 类本身
- Filter 和 Listener
- 应用自己的业务依赖

还包括：

- 它们持有的静态状态
- 它们创建出的对象图
- 它们可能留下的 ThreadLocal / 缓存 / 反射引用

也就是说，Tomcat 不是在做一个“类查找优化器”，而是在为每个 WebApp 划一条尽量独立、可回收、可更新的生存边界。

所以这篇的关键不是“类加载器怎么找类”，而是：

**Tomcat 为什么必须把每个应用当成一整个类世界来管理。**

## 二、`WebappClassLoaderBase`：为什么它是隔离边界，而不是普通包装器

这条主线里最核心的角色当然是：

- `WebappClassLoaderBase`

证据：`org/apache/catalina/loader/WebappClassLoaderBase.java:120`

仅从名字看，它很容易被误读成“Tomcat 里某个特殊点的 ClassLoader 基类”。

但如果从容器场景看，它承担的其实不是“帮忙加载类”这么窄的职责，而是：

- 维持 WebApp 自己的类空间
- 划定它和容器类空间之间的可见性边界
- 承担后续重载、卸载和回收时的基础角色

换句话说，它不是类加载链上的一个普通节点，而是：

**Tomcat 用来把“共享容器世界”和“应用私有世界”隔开的核心边界。**

而且从当前实现看，它承担的也不只是“找类”这一件事。至少沿源码就能直接看到几类非常关键的方法入口：
- `findClass(...)`
- `loadClass(...)`
- `modified()`
- `stop()`
- `clearReferences()`

证据：`org/apache/catalina/loader/WebappClassLoaderBase.java:768`
证据：`org/apache/catalina/loader/WebappClassLoaderBase.java:1207`
证据：`org/apache/catalina/loader/WebappClassLoaderBase.java:676`
证据：`org/apache/catalina/loader/WebappClassLoaderBase.java:1523`
证据：`org/apache/catalina/loader/WebappClassLoaderBase.java:1574`

这些入口已经足够说明：Tomcat 不是只拿它来完成类解析，还拿它承担应用变更检测、停止和引用清理这类后半段职责。没有这一层，前面几篇里讲到的 Servlet、Filter、Session、SCI 等等，最终都可能会塌回一个模糊的全局类空间里。

## 三、为什么这里不能机械套用“传统双亲委派”四个字

只要说到容器里的类加载，很多人脑子里马上就会蹦出一个现成答案：双亲委派。

这个词本身当然不是错的，但如果把它当成这里的最终解释，就太浅了。

因为 Tomcat 这里真正关心的不是：

- 要不要讲双亲委派这四个字

而是：

- 哪些类必须由容器一侧稳定提供
- 哪些类可以由 WebApp 自己携带并优先决定
- 哪些场景下“传统直觉”反而会破坏应用隔离

所以这里最应该避免的，就是把整篇写成一篇通用 JVM 类加载教程，然后再顺手说一句“Tomcat 也差不多”。

Tomcat 不难理解的点，不是“它也有父子加载器”；Tomcat 真正难的点在于：

**它必须在共享与隔离之间做精细取舍。**

也正因为如此，`WebappClassLoaderBase` 值得单独成篇，而不是被扔进某个“类加载基础知识”附录里。

## 四、为什么类加载隔离天然牵连热部署、卸载与泄漏

一旦把 `WebappClassLoaderBase` 看成隔离边界，后面很多看似分散的问题就会自动串起来。

比如：

- 为什么某个应用 reload 之后，旧类有时还在
- 为什么某些静态集合、线程本地变量会拖住整个应用无法回收
- 为什么类加载器泄漏在容器里会变成大事故，而在普通单次启动程序里没那么明显

这些问题看起来像不同专题，但其实都指向同一件事：

**应用自己的类世界能不能真正退出。**

所以热部署、卸载、泄漏，不是额外附属话题，而是类加载隔离主线在“生命周期后半段”的自然延伸。

也正因为如此，本篇虽然不展开完整排障细节，但必须先把这层关系立住：

- 类加载隔离不是为了讲究结构优雅
- 它直接决定应用能不能安全共存、能不能平滑重载、能不能真正被卸掉

## 到了这里，Tomcat 和“普通内嵌 Web 框架”的差异终于彻底拉开了

看到这里，可以回头看前面几篇已经立住的主线：

- 启动与装配
- 请求进入
- 容器执行
- async/error
- Session
- Mapper
- Spring Boot 集成
- 规范边界

这些主线都很重要，但它们有一个共同前提：

**应用本身必须首先被当成一个相对独立的运行世界来托管。**

而这恰恰就是类加载隔离在 Tomcat 里的特殊价值。

也就是说，Tomcat 和很多普通“只内嵌一个应用”的 Web 运行时真正拉开差距的地方，不只是它有容器树、有 Valve、有 Session，而是：

- 它必须把多个应用放在同一容器里托管
- 还要尽量避免它们互相污染
- 并为后续重载与卸载保留退场能力

这就是为什么 `WebappClassLoaderBase` 不该被看成枝节，而应该被视作 Tomcat 作为“容器”区别于“单应用运行时”的关键线之一。

## 这篇真正立住的，不是一个 ClassLoader 类，而是“应用自己的类世界”这个概念

如果只从表面看，这篇很容易被误读成：

- Tomcat 里有个特殊的 ClassLoader
- 它负责加载 WebApp 的类
- 可能还有一些和双亲委派不一样的地方

这种理解当然不算错，但仍然太窄。

从当前源码和前面整卷主线综合起来，更稳妥的理解方式应该是：

1. Tomcat 托管的不是一个应用，而是多个 WebApp
2. 因此它必须把每个应用当成一个独立类世界来管理
3. `WebappClassLoaderBase` 是这条隔离边界的核心实现角色
4. 热部署、卸载、泄漏问题，都是这条隔离边界在后半段的表现

只有把这条线立住，后面再去看：

- 为什么某些依赖冲突只在容器里爆炸
- 为什么某些应用重载后会出现旧类残留
- 为什么类加载器泄漏会拖住整个 WebApp

这些问题才会真正落到统一的解释框架上。

## 这篇之后，Tomcat 完整卷最自然的继续方向是什么

到这里，Tomcat 完整卷的机制补深层又补上了一条关键主线：

- Servlet 生命周期是怎么被压成实例管理链的
- 多应用容器为什么必须建立独立类世界

如果继续往下写，最自然的方向有两个：

1. 顺着类加载这一条线继续往下补：
   - 类加载器泄漏
   - 热部署与卸载失败
   - 应用隔离失效的典型故障

2. 转入生产层：
   - 性能调优
   - 安全运维
   - 故障排查

如果按当前整卷路线图继续推进，后面最自然的方向有两种：

- 继续顺着类加载这一条线补“类加载器泄漏 / 热部署卸载失败”补篇
- 或者转入完整卷的生产层，先开“生产性能专题”

前者更连贯，后者更贴近整卷阶段推进；具体选哪条，取决于你是想先把类加载这一脉补深，还是先把完整卷往生产层推进。
