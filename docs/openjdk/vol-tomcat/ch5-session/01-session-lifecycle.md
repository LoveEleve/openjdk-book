# Session 为什么不是一个普通对象：Tomcat 里的生命周期、过期、持久化与复制

> 本文基于 Tomcat 10.1.34 当前源码。本文只讲 Session 生命周期主线：一个 Session 为什么不只是请求旁边的属性容器，而是由 `Manager` 管理、受请求访问驱动、会过期、会回收、在需要时还能被持久化或复制的状态载体。集群复制协议和存储实现细节会在后续专题继续展开。

## 为什么很多人一到 Session 就突然把系统想扁了

Tomcat 前几条主线，无论是启动装配、请求进入，还是 Catalina 内部执行闭环，看上去都天然像“系统级问题”：

- 有容器树
- 有协议层
- 有执行链
- 有异步与错误路径

可一到 Session，很多人立刻就会把思路缩回到业务代码层面。

因为在应用程序眼里，Session 很容易表现成一个非常熟悉、非常朴素的东西：

- 往里 `setAttribute()`
- 从里 `getAttribute()`
- 不用了就 `invalidate()`

这种用法太顺手了，顺手到人会自然产生一种幻觉：Session 不就是一个挂在请求旁边的状态 Map 吗？

可只要真的往 Tomcat 里追源码，这个理解很快就会崩掉。因为围着 Session 的，远远不止一个对象：

- 有 `StandardSession` 这样的实体类
- 有 `ManagerBase`、`StandardManager` 这样的生命周期控制者
- 有过期扫描和回收逻辑
- 有 `FileStore`、`JDBCStore` 这样的持久化落点
- 还有 `DeltaManager`、`BackupManager` 这种把状态跨节点传播出去的扩展路径

一旦把这些放在一起看，Session 就不再像一个普通对象，而更像一条完整的生命周期链：

- 请求访问它
- 管理器持有它
- 时间和状态驱动它过期
- 某些场景下还要把它保存下来，甚至复制到别的节点

所以，本文真正想回答的问题不是“Tomcat 的 Session API 有哪些方法”，而是：

**为什么在 Tomcat 里，Session 不是一个普通对象，而是一条贯穿请求生命周期、并在请求之外继续被管理的状态链？**

## 先看失败方案：为什么不能只把 Session 看成一个大号 Map

### 失败方案一：Session 就是一个挂属性的对象

这是应用开发最自然的直觉，因为在业务代码里，Session 几乎总是以“属性容器”的形式出现。

你看到的往往只是：

- `session.setAttribute("user", user)`
- `session.getAttribute("user")`
- `session.invalidate()`

所以很容易得出一个结论：Session 不就是一个带生命周期的 Map 吗？

这个结论的问题在于，它只能解释 **“请求正在使用 Session 时”** 发生了什么，却完全解释不了 **“请求不在访问 Session 时，谁还在继续管理它”**。

因为只要顺着 Tomcat 往下问几个问题，这个理解就开始撑不住了：

- Session 是谁创建出来的？
- 它是谁持有的？
- 为什么它会过期？
- 过期后是谁发现它、谁回收它？
- 为什么它还能被保存到文件或数据库里？
- 为什么在集群模式下它还能被复制到其他节点？

也就是说，业务看到的是 Session 的“表面接口”，Tomcat 管的是 Session 的“整条生命史”。

### 失败方案二：讲清 `StandardSession` 就等于讲清 Session 机制

当读者开始意识到 Session 不是普通 Map 时，下一步常见的误区是：那我就把 `StandardSession` 这个类讲明白，不就够了吗？

这比第一种理解进了一步，但仍然不够。原因是 `StandardSession` 确实定义了：

- Session ID
- 创建时间
- 最后访问时间
- 属性集合
- 有效性状态

可它仍然只是“被管理的实体”，而不是“管理它的一整套机制”。

如果只讲 `StandardSession`，你顶多能知道：

- 这个对象身上有哪些字段
- 某些 API 如何修改这些字段

但你仍然讲不清：

- 谁决定它该活多久
- 谁定期扫描它
- 谁在它失效后把它移除
- 谁决定它要不要持久化、要不要复制

所以只讲 `StandardSession`，会把生命周期主线又缩回成一个“对象结构讲解”。

### 失败方案三：过期、持久化、复制只是几个并列高级功能

从目录结构上看，这些东西很容易被拆成几个平行主题：

- `StandardManager.processExpires()` 处理过期
- `FileStore` / `JDBCStore` 处理持久化
- `DeltaManager` / `BackupManager` 处理复制

如果只是列目录，这么拆好像也没问题。

但从生命周期视角看，它们回答的其实是同一个更大的问题：

**当请求已经结束、对象不再被当前调用栈直接拿在手里时，这个 Session 接下来会怎么活、怎么死、怎么留下、怎么传播？**

所以这些内容不是毫无关联的“高级选修课”，而是 Session 生命周期在请求结束之后的延伸部分。

## Tomcat 里 Session 的最小总图

如果把 Session 主线先压缩成最小模型，它其实可以写成下面这样：

```text
Request access
   -> StandardSession
   -> ManagerBase / StandardManager
   -> expire / recycle
   -> persist / replicate (when needed)
```

如果换一种更好理解的拆法，这条链可以分成三层职责：

```text
[状态实体]
StandardSession

   ->

[生命周期控制]
ManagerBase / StandardManager

   ->

[请求之外的延伸]
expire / persist / replicate
```

这张图最重要的价值，不是让读者记类名，而是先把三个问题分开：

### 一、状态实体
回答：Session 本身长什么样，保存什么状态？

这一层主要由：
- `StandardSession`

承担。

### 二、生命周期控制
回答：谁在真正持有、分配、回收和扫描这些 Session？

这一层主要由：
- `ManagerBase`
- `StandardManager`

承担。

### 三、请求之外的延伸
回答：当请求已经结束，Session 为什么还会继续被过期、持久化、复制？

这一层主要由：
- 过期扫描
- `FileStore` / `JDBCStore`
- `DeltaManager` / `BackupManager`

承担。

只要这三层先分开，后面 Session 为什么不是“普通对象”，就会变得清楚很多。

## 一、`StandardSession`：它是状态实体，但不是完整机制

Session 主线最直观的入口当然是 `StandardSession`。

证据：`org/apache/catalina/session/StandardSession.java:80`

如果只看它的接口和字段，很容易觉得：

- 这就是一个代表 Session 的对象
- 里面放着 ID、时间戳、属性集合和有效位
- 业务代码通过它读写状态

这个判断不能算错，但还差最关键的一层：**它是被管理的状态实体，而不是完整机制本身。**

换句话说，`StandardSession` 更像“Session 生命史的承载者”，而不是“生命史的决定者”。

它负责保存：

- 当前 Session 的标识
- 创建和访问相关状态
- 属性数据
- 失效相关状态

但它不单独回答：

- 什么时候创建
- 什么时候扫描
- 什么时候过期
- 什么时候持久化
- 什么时候复制

这也是为什么不能把 Session 主题缩成一个类结构讲解。因为 `StandardSession` 只是“谁被管理”，真正决定“怎么被管理”的，是下一层 `Manager`。

## 二、`ManagerBase / StandardManager`：Session 生命史真正的控制者

如果说 `StandardSession` 是被管理的状态实体，那么真正控制它一生的是谁？

答案不在 `StandardSession` 自己身上，而在 `Manager` 体系。

其中至少有两个关键角色：

- `ManagerBase`
- `StandardManager`

证据：`org/apache/catalina/session/StandardManager.java:57`
证据：`org/apache/catalina/session/ManagerBase.java`

这里最重要的理解，不是简单背类名，而是先把角色关系立住：

- `StandardSession` 代表“一个具体会话”
- `Manager` 代表“谁在整体上拥有、组织和管理这些会话”

也就是说，`Manager` 不是一个顺手生产 Session 的工厂，而是整个 Session 生命周期的控制者。

它至少要负责几类问题：

- 当前有哪些 Session 仍然活着
- 哪些 Session 已经过期
- 什么时候要触发过期扫描
- 失效后如何清理
- 如果启用持久化或复制，如何把这些动作挂进主线

这就是为什么 Session 主题里，`Manager` 的重要性实际上不低于 `StandardSession` 本身。因为没有 `Manager`，就只剩下一堆孤立存在的 Session 对象；而有了 `Manager`，这些对象才会被组织成一套真正受控的生命周期系统。

## 三、过期与回收：Session 为什么会“死”

只要理解了 `Manager` 是生命周期控制者，下一步最自然的问题就是：Session 既然不是普通对象，那它什么时候会结束生命？

这就是过期与回收主线真正要回答的问题。

在应用代码视角里，大家最熟悉的“结束”动作往往是：

- 手工 `invalidate()`

但在 Tomcat 视角里，Session 的死亡远不止这一种来源。至少还有一条更系统的机制：**过期扫描**。

也就是说，Session 不一定非得等业务自己显式宣判失效。Tomcat 自己也会根据访问时间、有效状态等条件，定期去检查：

- 谁还活着
- 谁已经超时
- 谁应该被回收

这一点非常重要，因为它进一步说明：Session 的生命周期并不依附于某个具体请求。

- 请求访问它，只是它生命史中的一个片段
- 请求结束之后，它仍然可能继续存在一段时间
- 直到某次扫描或显式失效，才真正结束

所以“Session 会死”这件事，本身就是它有独立生命周期的证据。

也正因为如此，过期不是边角功能，而是 Session 主线的核心组成部分。没有过期，就没有完整生命周期；只有创建和访问，没有终止与清理，这条链就永远闭不了环。

## 四、持久化：为什么请求已经结束了，Session 还可能被保存下来

如果 Session 只是一次请求执行时顺手挂着的状态对象，那请求一结束，它就应该跟着栈帧一起消失。

但 Tomcat 里显然不是这样。因为在某些场景下，Session 不只是“继续活着”，它还会被保存到外部介质。

这就是持久化这条延伸主线的意义。

典型角色包括：

- `FileStore`
- `JDBCStore`

这里先把它们当作“生命周期会继续延伸到外部介质”的角色提示，不在本篇里提前展开实现细节。真正写到持久化专题时，再补足对应的精确 `file:line` 证据。

这里最重要的不是马上去区分文件版和数据库版的实现差异，而是先理解：

**持久化说明 Session 的生命史已经超出了单次 JVM 内存中的短时对象语义。**

也就是说，Tomcat 不只是问“这个 Session 现在能不能被请求访问”，它还会继续问：

- 如果容器关闭怎么办？
- 如果要恢复状态怎么办？
- 如果不想只依赖内存怎么办？

一旦这些问题出现，Session 就不再只是一个“堆内对象”，而开始变成一个需要保存、恢复、继续被托管的状态载体。

这也是为什么持久化不该被当成“可有可无的小扩展”。它本质上是在把 Session 的生命周期，从内存继续延伸到存储介质。

## 五、复制：为什么同一个 Session 还可能活到别的节点上

如果持久化是在问“这个状态能不能跨时间继续活着”，那么复制问的就是另一件更大的事：

**这个状态能不能跨节点继续活着？**

这就是集群复制路径里那些角色存在的意义，比如：

- `DeltaManager`
- `BackupManager`

这里同样先把它们当作“Session 生命周期会继续延伸到其他节点”的角色提示，不在本篇里提前展开集群协议和复制细节；真正进入集群专题时，再补足精确源码锚点。

从生命周期视角看，这一步特别值得注意，因为它进一步打破了“Session 是本请求附属对象”的幻觉。

在复制路径里，一个 Session 不只是：

- 被某次请求读写
- 被某个容器实例管理

它甚至还可能：

- 被传播到别的节点
- 在别的地方继续承担后续请求的状态载体职责

所以复制并不是单独的“集群专题功能”，它其实是 Session 生命周期在空间维度上的延伸。

也正因为如此，本篇虽然不展开复制协议细节，但必须先立住它在主线里的位置：它不是外挂，而是“Session 作为状态载体”这个事实在集群环境中的自然延伸。

## 到了这里，Session 已经不可能再被理解成“普通对象”了

现在可以回到开头那个最常见的误解：Session 是不是就是一个大号状态 Map？

看到这里，这个理解已经很难再成立。因为围绕 Session 的，不只是对象读写，还有一整条生命周期链：

- 请求访问它
- `StandardSession` 承载它
- `Manager` 管理它
- 过期扫描结束它
- 持久化把它延伸到存储介质
- 复制把它延伸到其他节点

也就是说，Session 的真正身份不是“一个对象上挂了一堆属性”，而是：

**一个贯穿请求生命周期、并在请求之外继续被管理、回收、保存、传播的状态载体。**

这也是为什么只讲 `StandardSession`、或只讲 `getAttribute/setAttribute`，都会把它讲扁。

## 这篇真正立住的，是 Session 的“生命史”而不是“属性表”

如果只从应用层看，Session 很容易被缩成一个属性容器：

- 存用户信息
- 存登录状态
- 存临时上下文

但从 Tomcat 源码归纳出来，更稳妥的理解方式是：

1. `StandardSession` 只是状态实体
2. `Manager` 才是生命周期控制者
3. 过期、持久化、复制是这条生命史在请求结束之后的延伸
4. 所以 Session 不能被理解成“请求旁边的普通对象”

只有把这条生命史立住，后面再讲集群复制、持久化策略、Spring Session 替代方案时，读者才知道这些内容不是附加装饰，而是在回答同一件事：

**这个状态对象如何继续活、如何被继续管理。**
