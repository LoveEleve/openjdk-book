# Tomcat Ch8-01 Servlet 规范与实现边界 — review notes

## 第一轮：事实审

### 目标
核对：
- 规范接口、Tomcat 实现类、Spring Boot 集成桥之间的角色归属是否准确
- `file:line` 引用是否真实存在
- 是否把“接口存在”误写成“规范条文已经被精确引用”

### 当前需核对的关键锚点
- `jakarta.servlet` / `jakarta.servlet.http` 下与生命周期、Filter、Session、Async、SCI 相关接口与注释
- Tomcat 侧：
  - `StandardWrapper`
  - `ApplicationFilterChain`
  - `ApplicationFilterFactory`
  - `AsyncContextImpl`
  - `StandardSession`
- Spring Boot 侧：
  - `TomcatStarter`
  - `ServletContextInitializer`

### 初步判断
- 当前主线结构是对的：规范层 -> 实现层 -> 使用层
- 文章没有把 Tomcat 主干重新讲一遍，而是明确在做“契约 vs 实现”的校准
- 最大事实风险在于：这一篇如果不补足 `jakarta.servlet` 侧更具体的接口/注释锚点，就会容易停留在“概念上区分了规范和实现”，而缺少真正硬证据

## 第二轮：因果审

### 目标
检查正文中所有“规范要求了什么 / Tomcat 选择了什么”这类判断，是否真正有契约与实现双侧支撑。

### 当前因果链
1. 生命周期：规范规定语义，Tomcat 决定当前的 `StandardWrapper` 落地路径
2. Filter / DispatcherType：规范给调用契约，Tomcat 给执行组织方式
3. async：规范给偏离同步主线的能力，Tomcat 给状态机与回流路径
4. Session：规范给跨请求状态语义，Tomcat 给生命史
5. SCI / Initializer：规范给扩展点，Tomcat 和 Spring Boot 各自把桥接补齐

### 当前风险
- 这五条链在结构上都成立，但要避免一句“规范要求”后面没有接口/注释锚点、只靠 Tomcat 实现反推
- 这篇一旦证据不足，就会退化成“作者主观区分规范和实现”

## 第三轮：结构审

### 目标
检查结构是否遵守“困惑 -> 失败方案 -> 总图 -> 对照拆解 -> 收网”的方法论，而不是变成规范条文摘要。

### 当前结构评价
当前结构是：
1. 困惑开场
2. 失败方案
3. 规范 / 实现 / 使用层总图
4. 生命周期
5. Filter / DispatcherType
6. async
7. Session
8. SCI / Initializer
9. 收网总结
10. 下篇桥接

### 当前结构优点
- 不是规范条文目录
- 不是 Tomcat 主干的重复摘要
- 每节都在回答“规范要求 vs Tomcat 落地”这两个问题

### 当前结构风险
- 如果后续补接口锚点时不注意节奏，容易变成“接口注释块 + Tomcat 注释块”的对照表，而失去叙事性
- `SCI / Initializer` 一节很容易把集成层重新吃回来，需要克制篇幅

## 第四轮：读者审

### 目标
检查读者是否真能从这篇里学会“契约视角”，而不是觉得只是回顾主干。

### 当前读者收益
读完后，读者至少应能回答：
- 为什么 Tomcat 不是规范本身
- 为什么不能把 Tomcat 当前实现直接等于 Servlet 规范
- 为什么规范层不是附录，而是对前面主干理解边界的校准

### 当前读者风险
- 如果读者没有紧跟前面 Tomcat 主干篇，这篇会显得较抽象
- 如果接口侧证据不够硬，读者会理解“应该区分”，但未必真正信服“这里哪些是规范、哪些是实现”

## 第五轮：边界审

### 目标

### 当前边界控制

- Tomcat 各主干链的完整运行细节
- 生产参数调优

### 当前边界风险

## 当前结论

这篇原先最大的缺口——**规范侧硬锚点不足**——已经被补上，当前已经进入可收口状态。

本轮补强后，规范层的关键契约都有了接口/注释侧证据支撑：
