## 一句话困惑

为什么线上看到的 Tomcat 性能问题，表面上总是“线程不够了”“连接打满了”“超时了”“吞吐掉了”，但真正往源码里追，最后又会回到 Connector、线程池、ProtocolHandler、Filter/Servlet 执行链、async 和类加载边界这些基础结构上？

## 一句话顿悟

Tomcat 的性能问题不是几组参数独立波动，而是 **请求主线、线程模型、队列策略、超时控制、异步分流和类加载边界共同作用后的运行时结构结果。**

## 读者理解路径

1. 从“为什么线上性能现象总是几个数字，但根因却在结构里”切入。
2. 建立最小总图：连接入口 -> 线程与队列 -> 请求执行链 -> 偏离路径 -> 资源退场。
3. 解释连接、线程、队列、超时为什么不是四个独立指标，而是同一条运行时主线的不同观察面。
4. 解释 async 为什么既可能缓解性能压力，也可能把问题转移到别的地方。
5. 解释类加载、Session、Filter/Servlet 等“看起来不像性能参数”的东西，为什么也会最后表现成吞吐和延迟问题。
6. 最后收束：生产性能调优不是背参数，而是回到源码主线识别瓶颈位置。

## 失败方案推演

### 失败方案一：性能调优就是调 `maxThreads`、`acceptCount`、`connectionTimeout`

这是最常见的运维直觉，因为线上最容易看到的就是配置项。

问题在于，参数只是表象控制杆，它并不自动告诉你：
- 当前瓶颈在连接接收、协议处理、执行链、异步等待还是资源退场
- 你调大一个参数，是在放大吞吐，还是只是在延后崩溃

所以本篇必须先把参数背后的结构层找出来。

### 失败方案二：线程不够就是线程池问题，连接打满就是连接层问题

这种切法看起来清楚，其实最容易误导。因为：
- 线程池耗尽，可能根因在下游阻塞、Servlet 执行太慢、async 设计不当
- 连接打满，也可能只是后面执行链太慢，导致前面请求积压

也就是说，线程、连接、队列这些指标不是孤岛，它们是同一条请求主线在不同位置上的堆积表现。

### 失败方案三：性能问题和类加载 / Session / Filter 这些主题没关系

很多人会把性能只理解成：
- 线程池
- 连接数
- 超时
- IO

但真实系统里：
- Session 过大或管理不当会拖慢请求处理
- Filter 链过长或做了重活会抬高延迟
- 类加载器泄漏和重载失败会把长期运行的性能问题累积成更大的稳定性问题

所以生产性能不是“只看网络层和线程池”，而是要把前面整卷的主线重新投影到线上观察面上。

## 必须澄清的误解

1. 性能参数不是性能问题本身，它们只是结构性问题的调节杆。
2. 线程、连接、队列、超时不是彼此独立的专题，而是同一条请求链上的不同观察面。
3. async 不是天然优化，它只是把压力重分布到别的边界。
4. Session、Filter、类加载这些“非参数主题”也会在长期运行中表现成性能与稳定性问题。
5. 本篇讲的是结构性性能理解，不是完整排障命令手册。
