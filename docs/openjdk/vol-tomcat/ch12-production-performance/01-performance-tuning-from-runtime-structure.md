# 为什么 Tomcat 的性能问题，本质上总会回到运行时结构本身

> 本文基于 Tomcat 10.1.34 当前源码。本文不做参数背诵，也不做命令清单，而是专门解释一件事：为什么线上看到的 Tomcat 性能问题，表面上总是“线程不够”“连接打满”“超时变多”“吞吐下降”，但真正往源码里追，最后几乎总会回到同一批运行时结构：连接入口、线程与队列、容器执行链、async/timeout 路径，以及资源退场边界。

## 为什么线上只看到几个数字，源码里却总是回到结构问题

线上讨论 Tomcat 性能时，最常见的切入点几乎总是几个数字：

- 连接数多少
- 线程池是不是打满
- 队列里排了多少任务
- timeout 有没有升高
- 响应时间是不是变长了

这些指标当然都重要，因为它们确实是线上最先跳出来的信号。

但只要真正往下追，就会发现一个很稳定的现象：

- 连接打满，最后会回到连接入口与执行链是否堵住
- 线程池耗尽，最后会回到请求主线里哪一段没有及时释放执行资源
- timeout 变多，最后会回到 async/阻塞/执行路径没有按预期收束
- 吞吐掉下去，最后会回到 Filter、Servlet、Session、类加载边界这些更底层的位置

也就是说，线上看到的是数字，源码里真正对应的却是一条条结构主线。

所以，如果把性能问题理解成“调几个参数”的游戏，就会不断遇到一种挫败感：

- 参数好像调了
- 症状有时缓了
- 但问题换个形式又回来

这是因为参数只是调节杆，不是根因本身。根因通常藏在系统结构里：

- 请求是怎么进入的
- 线程是在哪里被占住的
- 执行链是在哪一步拖慢的
- 偏离正常路径后，系统有没有真的把请求重新收束住
- 长期运行后，类空间和实例是不是在持续留下历史包袱

所以，本文真正要回答的问题不是“Tomcat 该怎么调优”，而是：

**为什么对 Tomcat 来说，生产性能问题最后总会回到运行时结构本身？**

## 先看失败方案：为什么不能把性能问题理解成几个独立参数

### 失败方案一：性能调优就是调 `maxThreads`、`acceptCount`、`connectionTimeout`

这是最常见的运维直觉，因为线上最容易触碰到的正是这些配置项。

表面上看，思路也很直接：

- 线程不够就加线程
- 连接不够就加连接
- timeout 太短就拉长

问题在于，这种思路只能解释“阀门能不能开大一点”，却解释不了：

- 为什么线程会被占住
- 为什么连接会排起来
- 为什么 timeout 会越来越多
- 为什么吞吐掉了以后，增加参数有时只是把故障延后

也就是说，参数可以改变外部表现，却不能自动告诉你问题卡在结构的哪一段。

所以把性能调优写成参数表，最大的问题不是“不实用”，而是它会掩盖掉真正的结构性瓶颈。

### 失败方案二：线程不够就是线程问题，连接打满就是连接问题

这是一种更隐蔽、但也更危险的误解。

因为线上症状很容易让人把每个指标单独成章：

- 连接打满 → 连接层问题
- 线程耗尽 → 线程池问题
- timeout 增多 → 超时配置问题

这个切法在观察上很方便，但在根因上往往是错位的。

例如：

- 线程池耗尽，可能是后面的 Filter/Servlet 太慢，导致执行链长时间不释放线程
- 连接打满，可能是前面请求进得来，但后面执行链出不去，最终把前端入口也压住
- timeout 变多，也可能是 async 把压力转移到了另一个边界，而不是 timeout 参数本身太激进

所以这些指标不是孤岛，而是同一条请求主线在不同位置上的堆积表现。

### 失败方案三：性能问题和 Session、类加载、Filter 这些主题没关系

很多人做性能分析时，会天然只盯：

- NIO
- 连接
- 线程池
- 协议栈

而把下游执行链、Session、类加载这些主题看成“功能层问题”，和性能没有直接关系。

这个判断也不对。

因为前面整卷已经说明：

- Filter 链是每个请求都必经的执行成本
- Servlet 实例生命周期决定请求拿到实例时会发生什么
- Session 不是普通对象，它可能把请求后的管理成本继续拖长
- 类加载隔离和卸载失败会把长期运行的稳定性问题逐步累积成性能/内存压力问题

也就是说，性能问题不是“只看前半段网络入口”，而是会把整卷里前面那些看似不直接是参数的主题，统统重新投影成线上指标。

## Tomcat 性能主线的最小总图

如果把 Tomcat 里最容易折射到性能现象的结构先压缩成最小模型，它可以写成下面这样：

```text
[连接入口]
Connector / ProtocolHandler / Endpoint

   ->

[执行资源]
threads / queues / request processors

   ->

[请求执行链]
Mapper -> Valve -> FilterChain -> Servlet

   ->

[偏离路径]
async / timeout / error

   ->

[长期运行边界]
Session / classloader / resource cleanup
```

这张图最重要的价值，不是让读者把所有前文再背一遍，而是先把生产环境里那些最常见的性能现象拆回结构位置：

### 一、连接入口
回答：请求到底能不能顺利进来？会不会在入口处积压？

### 二、执行资源
回答：线程、队列、处理器是不是已经被长期占住？

### 三、请求执行链
回答：请求一旦进入执行链，真正耗时在哪里累积？

### 四、偏离路径
回答：async/timeout/错误处理是在缓压，还是在把压力转移到别处？

### 五、长期运行边界
回答：系统长期跑下来，Session 与类空间是不是在不断给运行时增加额外负担？

只要先把这五层问题分开，生产调优就不再只是“盯参数表”，而会重新回到源码结构上。

## 一、连接、线程、队列其实是一条链，不是三个孤立指标

线上最容易先看到的是：

- 连接数高
- 工作线程打满
- 队列堆积

这三个现象太常见了，所以很多人习惯分别处理它们。但从 Tomcat 主干往回看，它们其实是一条链上的不同观察面。

请求首先要经过：

- `Connector`
- `ProtocolHandler`
- `Endpoint`

也就是前面 Ch2 已经立住的连接入口主线，例如：
- `NioEndpoint` 作为连接与事件入口：`org/apache/tomcat/util/net/NioEndpoint.java:71`
- `Http11Processor` 作为协议处理中心：`org/apache/coyote/http11/Http11Processor.java:70`

一旦请求进来之后，后面如果执行链长时间不释放资源，前面的入口压力就会不断向上传导：

- 请求进得快，执行得慢
- 执行线程长时间不归还
- 后续请求排队
- 入口侧继续堆积
- 最后表现成“连接打满”“线程不够”“队列爆了”这些症状

所以这三者不是三类独立故障，而更像同一条水管不同位置上的压力表。

也正因为如此，单独调大某一个参数，经常只能让表盘短时间好看一些，却不能真正把堵点拿掉。

## 二、执行链为什么会直接决定延迟和吞吐

请求一旦进入 Catalina，后面真正决定单次延迟和整体吞吐的，就是执行链本身：

- `Mapper`
- `Valve`
- `FilterChain`
- `Servlet`

前面 Ch3 已经把这条链的职责分开讲清楚了，例如：
- `StandardWrapperValve` 构造 `ApplicationFilterChain`：`org/apache/catalina/core/StandardWrapperValve.java:141`
- `ApplicationFilterChain` 最终推进 `doFilter(...)`：`jakarta/servlet/FilterChain.java:33`

到了生产性能视角，这条链要回答的问题就变了：

- 哪一层做了太多工作
- 哪个 Filter 链太长
- 哪个 Servlet 调用了太慢的下游
- 哪段执行把线程长时间占住

也就是说，性能问题在这里不再体现为“设计模式怎么走”，而体现为：

**每个请求在这条链上停了多久，线程被占了多久，后面的请求又因此等了多久。**

所以 Filter、Servlet、Valve 并不是“业务层的功能细节”，而是会直接投影成延迟分布、吞吐上限和线程占用时间的关键结构。

## 三、Session 为什么也会变成性能问题的一部分

如果只从业务代码看，Session 很容易像一个状态容器，不像性能问题的直接来源。

但从前面 Ch5 的生命史视角回头看，它完全可能成为性能结构的一部分：

- 属性读写本身带来额外工作
- 过期扫描和管理成本会进入长期运行开销
- 如果状态对象很重，复制和持久化就可能放大请求后半段成本

也就是说，Session 不一定每次都以“明显的慢点”出现，但它会让请求链和系统长期运行成本一起变重。

所以生产性能不是只盯请求入口和线程池，也要问：

- 请求链末端是不是在不断拖着更重的状态载体跑
- 系统是不是还在为大量 Session 状态继续付出管理成本

## 四、async / timeout：既可能缓压，也可能转移问题

async 是线上最容易被误读成“天然优化”的一条线。

因为从表面看，它确实能让请求不必一直死死占着同步调用链。

但前面 Ch4 已经说明，async 不是“请求 magically 更快”，而是：

- 请求偏离了原来的同步主线
- 状态机、容器协调、错误出口重新把它收束

对应的关键结构至少包括：
- `AsyncStateMachine`：`org/apache/coyote/AsyncStateMachine.java:129`
- `AsyncContextImpl`：`org/apache/catalina/core/AsyncContextImpl.java:442`

放到性能视角看，这意味着一件很重要的事：

**async 不是消灭压力，而是重新分布压力。**

如果使用得当，它可以：
- 缩短某些同步链路上的占用时间
- 让某些等待不再堵住原链条

但如果设计不当，它也可能：
- 把压力转移到别的线程或队列
- 拉长请求生命周期
- 让 timeout、错误回流、异步写回变得更多

所以生产调优里看到 async 时，不该先问“有没有开”，而该问：

- 它缓解了哪一段压力
- 又把压力转移到了哪里

## 五、为什么长期运行后，类加载与退场问题也会反过来拖性能

如果只看短时压测，很多人会觉得类加载和性能无关。但前面 Ch10/Ch11 已经说明，长期运行场景下，类空间退场失败会逐步累积成更大的稳定性与资源问题，例如：
- `WebappClassLoaderBase.clearReferences()`：`org/apache/catalina/loader/WebappClassLoaderBase.java:1574`
- `clearReferencesThreads()`：`org/apache/catalina/loader/WebappClassLoaderBase.java:1678`

这件事最后会怎样投影到性能上？

至少有几种很现实的路径：

- 旧类空间残留，Metaspace 持续抬高
- 旧线程、旧缓存、旧 ThreadLocal 持续挂住资源
- 容器重载/替换后的历史包袱不断叠加

这些问题一开始未必表现为“某个请求马上变慢”，但时间长了，它们会把：

- 内存压力
- 停顿风险
- 稳定性边界

一点点推向更差的位置，最后反过来影响吞吐和延迟。

所以对 Tomcat 来说，性能不只是“当前请求快不快”，还包括：

**这套系统长期跑下来，退场和清理是不是在不断留下历史债务。**

## 到了这里，参数就不再只是参数，而是结构瓶颈的外部旋钮

现在再回头看常见的生产参数：

- `maxThreads`
- `acceptCount`
- `connectionTimeout`
- async 相关配置

就会发现它们更像是外部旋钮，而不是问题本身。

因为每个旋钮背后，其实都连着一段运行时结构：

- 连接入口
- 线程与队列
- 执行链耗时
- 偏离路径收束
- 长期运行负担

所以更稳妥的性能调优方式，不是先问“该调哪个参数”，而是先问：

- 当前瓶颈究竟压在哪条结构链上
- 这个参数是在直接缓解瓶颈，还是只是在延后症状

也就是说，参数是结构问题的外部控制杆，而不是结构问题本身。

## 这篇真正立住的，是“性能问题最终都要回到主线结构上解释”

如果只从线上现象看，Tomcat 的性能问题很容易被讲成几类常见症状：

- 线程池不够
- 连接太多
- 超时变高
- 吞吐下滑

但从前面整卷源码主线归纳回来，更稳妥的理解方式应该是：

1. 入口结构决定请求能否顺利进来
2. 执行链决定线程会被占多久、延迟会堆多高
3. async/error 决定压力是被缓解还是被转移
4. Session 和类空间退场决定系统长期运行的额外负担

所以性能调优真正该做的，不是只背参数名，而是把线上症状重新投影回这些结构位置。
