## 一句话困惑

为什么 Tomcat 的线程池问题看起来像几个普通参数——`maxThreads`、队列、连接数——但一旦真的往源码里追，就会发现它其实牵扯 `Executor`、`TaskQueue`、`LimitLatch`、请求入口和执行链的整个承压结构？

## 一句话顿悟

Tomcat 的线程池不是一个普通工作池，而是请求主线的承压系统：**它决定请求能不能被接住、能排到哪里、何时开始真正执行，以及入口压力如何向后传播、再反过来拖住前面的连接入口。**

## 读者理解路径

2. 建立最小总图：`connection acceptance -> task handoff -> queueing -> worker execution -> backpressure`。

6. 最后收束：线程池/队列/连接并不是三个调优按钮，而是一套结构性承压系统。

## 失败方案推演

### 失败方案一：线程池就是 `maxThreads` 配大一点就行

这是最常见的运维直觉。因为一看到线程耗尽，最容易想到的就是：
- 线程不够
- 那就调大线程池

这个理解的问题在于，它只看到了“池子大小”，却没看到：
- 请求是怎么被交给线程池的
- 线程忙不过来时任务会先去哪
- 队列和连接入口之间怎么互相传压
- 哪些情况下加线程只是延后堆积，而不是消除堵点

### 失败方案二：队列只是缓存请求的地方，没什么特殊的

如果只从通用并发视角看，队列很容易被理解成：
- 线程忙不过来时，任务先排着

但对 Tomcat 来说，`TaskQueue` 不是普通“等一等”的位置，而是和线程增长、任务接纳策略、承压边界直接连在一起的。它并不只是存任务，而是在参与“当前到底该扩线程，还是继续排队”这种关键决策。

### 失败方案三：连接数和线程池是两套平行问题

这也是一个特别常见的误解。

表面上看：
- 连接数是连接器的事
- 线程池是执行器的事

但前面性能篇已经说明，线上最常见的问题恰恰是这两条线会互相传压：
- 后面执行链慢，线程不释放
- 线程池和队列堆积
- 前面连接继续进来
- 最终连接侧也表现出承压失衡

所以不能把连接和线程池硬切开看。

## 必须澄清的误解

1. Tomcat 的线程池不是普通参数表，而是请求主线承压结构的一部分。
2. `TaskQueue` 不是普通阻塞队列，它会影响线程增长与任务接纳策略。
3. `LimitLatch` 不是外围小工具，而是连接承压边界的一部分。
4. 线程、队列、连接是同一条承压链的不同观察面。
5. 本篇讲的是结构，不是调参清单。
