# Tomcat Ch19-01 线程池 / Executor 专题 — review notes

## 第一轮：事实审

### 目标
核对：
- `Executor`、`TaskQueue`、`LimitLatch` 是否被准确定位为承压结构中的不同节点
- `file:line` 引用是否真实存在
- 是否把“性能视角里的结构结论”误写成“已在本篇直接源码证明的断言”

### 当前需核对的关键锚点
- Tomcat 侧与线程池、队列、连接承压相关的关键类/方法：
  - `Executor`
  - `TaskQueue`
  - `LimitLatch`
  - 相关线程增长/接纳策略入口
- 与请求入口主线的连接点：
  - `NioEndpoint`
  - `Http11Processor`

### 初步判断
- 当前主线与 Ch19 规划一致：入口承压 -> 任务交接 -> 执行承压 -> 回压传播
- 没有把线程池写成纯参数表，这是对的
- 当前最大事实风险在于：还没有把 `TaskQueue` / `LimitLatch` 这些关键结构压到具体实现锚点，正文目前更多是承压结构层面的概念整理

## 第二轮：因果审

### 目标
检查正文里所有“线程/连接/队列是一条承压链”“队列参与决策”“入口和执行会互相拖住”这类判断，是否由源码结构支撑。

### 当前因果链
1. 线程池不是孤立并发工具，而是请求主线的执行承压节点
2. `TaskQueue` 不是普通缓存容器，而是在参与承压决策
3. `LimitLatch` 说明入口承压和执行承压会互相牵动
4. 线程、连接、队列问题本质上是同一条结构链在不同位置的失衡表现

### 当前风险
- 这些判断方向是对的，但要避免在没有 `TaskQueue` / `LimitLatch` 具体方法锚点时，把结论写得过实
- “回压传播”是一个非常好的组织概念，但必须持续保持它是从结构归纳出来的，而不是某个类名直接写着这个词

## 第三轮：结构审

### 目标
检查结构是否遵守“困惑 -> 失败方案 -> 总图 -> 承压结构拆解 -> 收网”的方法论，而不是退化成线程池参数手册。

### 当前结构评价
当前结构是：
1. 困惑开场
2. 失败方案
3. 最小总图
4. 线程池是承压节点
5. `TaskQueue`
6. `LimitLatch`
7. 执行链慢为什么会拖住入口
8. 收网总结
9. 卷级后续方向

### 当前结构优点

- 先立承压结构，再讲具体节点
- 与性能篇形成“现象 -> 结构”的双层关系

### 当前结构风险
- `TaskQueue` 和 `LimitLatch` 目前还是概念先行，后续收口时必须补硬锚点，不然容易显得像把前面性能篇再抽象一遍
