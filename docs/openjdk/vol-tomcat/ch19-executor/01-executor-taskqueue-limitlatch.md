# 为什么 Tomcat 的线程池不是参数表，而是请求主线的承压结构

> 本文基于 Tomcat 10.1.34 当前源码。本文不做 `maxThreads`、`acceptCount`、`connectionTimeout` 的参数手册，而是专门解释一件事：为什么线上看起来像“线程不够”“队列满了”“连接打住了”的问题，追到源码里最后会回到 `Executor`、`TaskQueue`、`LimitLatch` 和请求入口主线本身。也就是说，这篇讲的不是“怎么调池子”，而是“池子到底在承受什么”。

## 为什么线程池问题一上线，就总会被误解成“参数不够大”

Tomcat 上线后最常见的一类问题，几乎总会落到几个参数上：

- `maxThreads`
- `acceptCount`
- 连接数上限
- timeout

这些参数太显眼了，以至于只要线上一出现：

- 线程打满
- 请求排队
- 连接积压
- timeout 增多

最自然的第一反应就是：

- 池子不够大
- 队列不够长
- 连接数限制太小

这个反应不能说完全错，但它只看到了“表盘”，没有看到“表盘背后的机械结构”。

因为对于 Tomcat 来说，线程池从来不是一个孤立组件。它并不是像普通通用执行器那样，只负责接个任务、跑完就算；它在容器里承接的是请求主线本身的压力：

- 前面连接在进
- 中间任务在排
- 后面执行链在跑
- 慢的时候，压力会从后往前倒灌

也就是说，Tomcat 的线程池问题从来不只是“线程数不够”，而是：

**请求主线在不同位置上的压力，是怎么被接住、排队、继续推进，或者反过来拖住前端入口的。**

这也是为什么同样叫“线程池满了”，在不同系统里，根因可以完全不同：

- 有时是业务执行慢
- 有时是队列策略不对
- 有时是入口放量太快
- 有时是 async / timeout 把压力转移到了别处

所以，本文真正要回答的问题不是“Tomcat 线程池怎么配”，而是：

**为什么 Tomcat 的线程池、队列和连接入口，必须被理解成同一条承压结构，而不能被拆成几个孤立参数？**

## 先看失败方案：为什么不能把承压问题理解成几个独立旋钮

### 失败方案一：线程池不够大，就把 `maxThreads` 调大

这是最符合线上直觉的处理方式。

因为从监控上看，你最容易看到的就是：

- 活跃线程接近上限
- 请求耗时在涨
- 排队越来越明显

于是很容易下结论：

- 线程不够
- 那就把 `maxThreads` 调大

这个结论的问题在于，它只是在调“容器现在最多肯派多少工人”，却没有回答：

- 工人为什么一直不回来
- 工人没回来时任务先堆到哪
- 上游连接为什么还在继续压进来
- 调大线程之后，是不是只是把堵点延后了

也就是说，线程数只是承压链中的一个旋钮，不是整条链的解释。

### 失败方案二：队列只是等一等，不重要

很多人对队列的理解很朴素：

- 线程忙不过来
- 任务先排着
- 就这么简单

如果只在普通并发程序里，这种理解有时还说得过去。

但在 Tomcat 里，`TaskQueue` 并不只是个“先等等”的存放处。它会直接影响：

- 任务到底是继续排队
- 还是应该触发线程增长
- 承压是被暂时吸收了，还是在继续放大

也就是说，队列不是执行器边上的一个附属容器，而是承压结构里一个直接参与决策的节点。

### 失败方案三：连接压力和线程池压力是两回事

这也是特别常见的误解。

表面上看，两者好像确实不一样：

- 连接属于连接器
- 线程属于执行器

但从请求主线回头看，这二者其实是同一条压力链上的前后段：

- 前面连接进得快
- 后面执行链跑得慢
- 线程长时间不释放
- 队列开始堆积
- 入口侧继续承压

所以线上看到“连接打满”，未必是连接器本身先出事；很多时候只是后面的执行与承压结构已经把前面也拖住了。

这也就是为什么，在 Tomcat 里讲线程池问题，不能不把入口和执行链一起带进来。

## Tomcat 承压结构的最小总图

如果把这条承压主线先压缩成最小模型，它可以写成下面这样：

```text
incoming connections
   -> endpoint accepts
   -> tasks handed off
   -> queue / executor / workers
   -> request execution
   -> backpressure reflected upstream
```

如果再换一种更容易理解的拆法，这条链可以分成四段职责：

```text
[入口承压]
connections / endpoint acceptance

   ->

[任务交接]
handoff from connection handling to execution resources

   ->

[执行承压]
executor / queue / worker threads

   ->

[回压传播]
slow execution drags upstream layers
```

这张图最重要的价值，不是让读者背类名，而是先把四个问题分开：

### 一、入口承压
回答：请求和连接到底是怎样开始堆起来的？

### 二、任务交接
回答：连接事件在什么地方开始变成需要执行资源承接的任务？

### 三、执行承压
回答：线程、队列和执行器怎样共同吸收或放大压力？

### 四、回压传播
回答：为什么后面的慢，会反过来把前面的入口也拖住？

只要先把这四层分开，Tomcat 的线程池问题就不再像一串参数表，而会回到请求主线的结构本身。

## 一、Tomcat 的线程池首先不是“并发工具”，而是请求主线的承压节点

在普通应用里，线程池经常只是一个通用并发工具：
- 接任务
- 跑任务
- 跑完释放

但在 Tomcat 这里，它承担的不是泛化任务，而是：

- 请求进入之后的执行压力
- 执行链慢下来的堆积压力
- 队列排队与线程增长之间的平衡压力

也就是说，Tomcat 里的执行资源不是“有个池子方便并发”，而是：

**整条请求主线在执行侧如何被承住。**

所以本篇必须先改掉一个常见习惯：
- 不要把线程池当成主线之外的性能调优附件

更准确的说法应该是：
- 线程池就是 Tomcat 请求主线的执行承压结构之一

## 二、`TaskQueue`：为什么它不是一个普通“等一等”的地方

只要开始看执行承压结构，最容易被低估的就是队列。

因为很多人习惯把队列想成：
- 线程来不及跑
- 任务先放着

这个理解对 Tomcat 来说太浅了。

在容器场景里，队列并不只是缓存压力，而是在影响：

- 当前到底要继续排队
- 还是该让线程增长
- 还是说明后端执行链已经开始拖不动

也就是说，`TaskQueue` 在这里不是静态容器，而是承压决策结构的一部分。

这一点在源码里也不是抽象判断，而是直接写进了实现说明里：`TaskQueue` 明确声明自己是“专门为线程池执行器设计的队列”，并且在 `offer(...)` 里会根据当前池大小、最大线程数和 submittedCount 来决定是继续入队，还是返回 `false` 让线程池走扩线程路径。

证据：`org/apache/tomcat/util/threads/TaskQueue.java:27`
证据：`org/apache/tomcat/util/threads/TaskQueue.java:74`
证据：`org/apache/tomcat/util/threads/TaskQueue.java:88`

所以如果线上只看到“队列长了”，最稳的反应不是直接调队列长度，而是先问：

- 为什么线程没有及时释放
- 为什么任务会在这里堆住
- 这是不是后端执行链已经开始慢到反压前端了

## 三、`LimitLatch`：为什么连接承压和执行承压最后会互相拖住

Tomcat 最容易让人误判的地方之一，是入口压力和执行压力之间的关系。

表面上看：
- 连接是连接器的事
- 线程是执行器的事

可一旦系统承压，二者会很快被绑到一起。

`LimitLatch` 之所以值得单独看，不是因为它名字特别，而是因为它说明：

**Tomcat 对连接入口并不是无限制放行，而是在某些边界上主动设限，让前端压力和后端承压结构保持某种平衡。**

这点在实现上也非常直接：`LimitLatch` 自己就是一个“允许最多获取多少次、超过后进入 FIFO 等待”的共享闩锁，而 `countUpOrAwait()` / `countDown()` 正是承压边界的进入与释放动作。

证据：`org/apache/tomcat/util/threads/LimitLatch.java:27`
证据：`org/apache/tomcat/util/threads/LimitLatch.java:118`
证据：`org/apache/tomcat/util/threads/LimitLatch.java:129`

也就是说，连接入口并不是独立世界。它迟早会感受到后面执行资源的状态。

所以“连接多”和“线程满”经常不是两张不同图，而是同一条承压链在前后两端的不同表象。

## 四、为什么执行链慢了，前端入口迟早也会一起失真

只要把前面几篇串起来，就会发现一个非常稳定的传播路径：

- 请求先从入口进来
- 然后沿执行链往后跑
- 如果 Filter、Servlet、Session、async 路径任何一段变慢
- 线程就被占住
- 队列开始积压
- 前面的入口侧也就迟早开始表现出异常

也就是说，Tomcat 的承压从来不是局部的。

这也是为什么生产性能篇会强调：
- 线程、连接、队列是同一条链的不同观察面

而这一篇则继续把它压得更细：
- 入口不是简单接收连接
- 执行器不是简单跑任务
- 队列不是简单缓存任务
- 这些结构放在一起，才构成真正的承压系统

## 到了这里，线程池问题已经不能再被理解成“线程够不够”了

现在再回头看最常见的问法：

- 线程池是不是不够大？

看到这里，这个问题已经明显不够用了。

更准确的问法应该是：

- 压力到底先卡在入口、任务交接、队列还是执行链
- 线程为什么没释放
- 队列为什么会堆住
- 前端连接压力为什么会继续向后放大
- 当前的参数调整是在真正缓解结构瓶颈，还是只是在延后它

所以 Tomcat 的线程池问题，最终要回答的不是“线程数配多少”，而是：

**请求主线的执行承压结构，到底是在什么位置开始失衡。**

## 这篇真正立住的，不是几个并发参数，而是“承压结构”这个概念

如果只从表面看，这篇很容易被讲成：

- Executor 是什么
- 队列怎么配
- 连接怎么限
- 线程怎么调

这种讲法当然有用，但仍然太像参数手册。

从前面整卷主线归纳回来，更稳妥的理解方式应该是：

1. 请求入口、任务交接、线程执行、回压传播构成一整条承压结构
2. 线程池只是这条结构中的一个节点
3. 队列和连接也不是旁观者，而是在参与承压决策
4. 所以线上看到的线程、连接、队列问题，本质上都是结构失衡的不同投影

也就是说，这篇真正补上的，不是并发配置知识，而是一种更稳的诊断视角：

**Tomcat 的线程池问题，本质上不是参数问题，而是承压结构问题。**
