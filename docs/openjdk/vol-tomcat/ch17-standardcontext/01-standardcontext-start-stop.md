# 为什么一个 Web 应用在 Tomcat 里不是组件列表，而是一整套编排系统

> 本文基于 Tomcat 10.1.34 当前源码。本文只讲 `StandardContext` 这条线：一个 Web 应用在 Tomcat 里为什么不是“若干 Servlet、Filter、Listener 的集合”，而是一个由 `Context` 统一托管、按顺序启动、按顺序停止、还能把 Session、Loader、资源、子组件一起收起来的完整运行单元。本文不重复讲 `StandardWrapper`、类加载器泄漏、Boot 集成等专题，而把它们都放回 `Context` 这个应用级编排中心里看。

## 为什么“一个 Web 应用”在 Tomcat 里远不只是几个组件拼在一起

如果只从业务开发者的日常视角看，一个 Web 应用最显眼的东西往往就是这些：

- Servlet
- Filter
- Listener
- 再加一点配置

所以很容易自然形成一种直觉：

- Web 应用不就是这些组件的集合吗？
- Tomcat 只要把它们都注册进去，请求来的时候能调起来，就算完成任务了

这个直觉在“组件列表”层面并不完全错，但它严重低估了容器要承担的工作。

因为对 Tomcat 来说，一个真正运行中的 Web 应用不仅仅要“能被请求调用”，它还必须同时满足下面几件事：

- 有自己的类加载边界
- 有自己的 Session 管理器
- 有自己的资源视图
- 有自己的 Servlet / Filter / Listener / Wrapper 组织方式
- 有自己的启动与停止顺序
- 出问题或重载时，还要能尽量把自己整套东西收干净

也就是说，Tomcat 面对的不是“把一些组件堆进来”，而是：

**把一整个应用运行单元组织起来，并且在它需要退场时，再把它尽可能完整地收回去。**

这也是为什么在容器树里，`Context` 的意义远比“Host 下面的一层”更重。

它当然是请求路径上的一层节点，但它更深的职责是：

- 把这个 Web 应用的一切应用级部件装成一个整体
- 再把这个整体变成可启动、可停止、可重载、可清理的容器单元

所以，本文真正要回答的问题不是“`StandardContext` 有哪些字段和方法”，而是：

**为什么在 Tomcat 里，一个 Web 应用不能只被看成几个组件的清单，而必须被当成一整套需要统一编排和统一收束的运行系统？**

## 先看失败方案：为什么不能把 `Context` 理解成一层普通中间节点

### 失败方案一：一个 Web 应用就是若干 Servlet、Filter、Listener 的集合

这是最贴近日常业务代码的理解。

因为开发者真正接触到的通常是：

- 写几个 Servlet
- 配几个 Filter
- 注册几个 Listener
- 然后请求就能跑起来

于是很容易得出一个隐含结论：

- Web 应用本身就是这些组件的集合
- 容器不过是把这些组件拼起来而已

这个理解的问题在于，它只能描述“有哪些零件”，却描述不了“这些零件为什么能作为一个系统活起来”。

因为一旦真正进入容器实现，就会立刻碰到很多组件列表解释不了的问题：

- 哪个类加载器负责这套应用
- Session 是谁在持有和回收
- 静态资源与应用资源边界怎么定
- 启动时哪些必须先起来，哪些必须后起来
- 停止时哪些必须先停，哪些必须最后清

所以对 Tomcat 来说，应用从来不是清单，而是一个完整运行单元。

### 失败方案二：`Context` 只是 `Host` 和 `Wrapper` 之间的中间路由层

如果只从容器树结构看，`Context` 很像一个中间层：

- 上面是 `Host`
- 下面是 `Wrapper`

于是很容易把它理解成：

- 它只是继续把请求往下传一层
- 真正重要的是更下游的 Servlet/Filter 执行

这个理解的问题在于，它把 `Context` 只看成“请求经过的一层”，却没有看到它还在做更重的事：

- 持有 Loader
- 持有 Manager
- 持有应用级监听器和过滤器体系
- 组织 Wrapper 们
- 统一协调应用级子组件的启动和销毁

也就是说，`Context` 不只是执行链路上的中间层，而是整个应用级生态的托管者。

### 失败方案三：启动主线重要，停止和销毁只是收尾细节

这是很多源码分析最容易忽略的一点。

大家天然更爱看“怎么启动”，因为它更像主线；而“怎么停”“怎么销毁”经常被误认为只是收尾逻辑。

但对 Tomcat 这种长期运行容器来说，这种轻视是非常危险的。

因为一旦停得不对，后果并不只是“代码不够优雅”，而可能直接落成：

- 旧 Servlet 实例残留
- Session 管理器还活着
- 类加载器退不掉
- 线程和缓存继续挂着

也就是说，启动和停止不是主次关系，而是同一条应用生命史的前后两半。

## 一个 Web 应用在 Tomcat 里的最小总图

如果把 `StandardContext` 这条主线先压缩成最小模型，它可以写成下面这样：

```text
Context
   -> loaders / managers / resources / wrappers / listeners / filters
   -> start in order
   -> run as one unit
   -> stop / destroy in order
```

如果再换一种更容易理解的拆法，这条线可以分成四段职责：

```text
[应用级部件]
Loader / Manager / Resources / Wrappers / Listeners / Filters

   ->

[启动编排]
what must be ready before the app is considered started

   ->

[运行托管]
the app behaves as one managed unit

   ->

[停止与销毁]
what must be cleaned before the app is really gone
```

这张图最重要的价值，不是让读者背一串部件名，而是先把四个问题分开：

### 一、应用级部件
回答：Tomcat 要为一个 Web 应用统一托管哪些东西？

### 二、启动编排
回答：这些东西为什么不能乱序启动？

### 三、运行托管
回答：为什么请求主线里看到的只是这个应用单元的表层行为？

### 四、停止与销毁
回答：为什么应用退场时，必须把整套子系统一起收束？

只要先把这四段职责分开，`Context` 为什么不是一个普通中间层节点，就会清楚很多。

## 一、`StandardContext`：它首先是“应用级控制中心”，而不是“请求中转层”

`StandardContext` 的定义位置：

证据：`org/apache/catalina/core/StandardContext.java:146`

在前面的执行主线里，我们主要从请求路径上看它：
- `Host` 下面一层
- `Wrapper` 上面一层

但到了这一篇，必须把视角切回来：从请求路径看，它只是一个执行层级；从应用生命史看，它其实是整个应用级子系统的控制中心。

为什么这么说？因为一旦一个 Web 应用被放进 Tomcat，真正要被 `Context` 托管的从来不只是一组 Servlet，而是一整套会一起活、一起跑、一起退的东西：

- 类加载器
- Session 管理
- 资源视图
- Filter / Listener / Wrapper 注册体系
- 生命周期监听
- 应用级配置与状态

也就是说，`Context` 在这里更像一个“应用级容器中的总编排者”。

所以，不能把它讲成“请求传到这里再往下交”的中间层。那样会把它讲扁，读者会看不到应用级编排这个更重的职责。

## 二、为什么启动顺序不是实现细节，而是应用单元能不能成立的前提

只要 `Context` 真正托管的是一整个应用单元，下一步最自然的问题就是：

**这些应用级部件为什么不能随便乱序启动？**

原因很直接。因为这些子系统彼此之间存在依赖：

- 有些东西必须先准备好，后面的组件才能安全运行
- 有些组件一旦先启动，后面的世界还没就绪，就会立刻暴露出半初始化状态

也就是说，启动顺序在这里不是“实现偏好”，而是：

**应用单元能否真正进入一致运行态的前提。**

这也是为什么 `Context` 不是简单把一堆子对象都调一次 `start()` 就完事，而必须承担编排职责。它要保证的不是“每个零件都被启动过”，而是“这些零件在依赖关系成立的前提下共同进入可运行状态”。

所以，启动编排是应用级控制中心最核心的职责之一。

这条编排线在方法级上也能直接看到：
- `startInternal()`：`org/apache/catalina/core/StandardContext.java:4204`
- 其中会继续触发 `listenerStart()`、`filterStart()`、`loadOnStartup(...)`：`org/apache/catalina/core/StandardContext.java:3919`、`org/apache/catalina/core/StandardContext.java:3842`、`org/apache/catalina/core/StandardContext.java:4165`

## 三、运行时主线之所以看起来那么顺，是因为 `Context` 早就把应用单元托好了

前面的执行主线之所以看起来那么清爽：

- `Mapper -> Valve -> FilterChain -> Servlet`

并不是因为 Tomcat 只有这些东西，而恰恰是因为在请求到来之前，`Context` 已经把应用级部件整理成了一个可运行单元。

换句话说，请求主线之所以像一条顺滑流水线，是建立在下面这些更重的背景都已经稳定成立的基础上：

- 类加载边界已经就绪
- Session 管理器已经挂好
- 过滤器和监听器体系已经完成注册
- Wrapper 体系已经完成组织

所以从这个角度看，请求主线只是“运行中的表层现象”；而 `StandardContext` 则是在背后托住整台应用级机器。

也正因为如此，想真正理解嵌入式 Tomcat，不能只看请求怎么跑，还要看这一整个应用单元是怎么被托管起来的。

## 四、为什么停止和销毁和启动一样重要

只要承认 `Context` 托管的是一个完整应用单元，那么另一个结论也就自然成立了：

- 这个单元退出时，不能只是“请求停了”就算结束

因为请求停掉，只代表表层运行主线暂时没新流量了，并不代表：

- Servlet 实例已经被卸掉
- Session 状态已经被收干净
- 类加载器已经退场
- 监听器和线程引用已经断开

这就是为什么停止与销毁在 Tomcat 里绝不能被降级成“收尾细节”。

对应的硬锚点也很明确：`stopInternal()` 就是这条退场编排线的方法级入口。

证据：`org/apache/catalina/core/StandardContext.java:4612`

它们回答的是另一个和启动同等重要的问题：

**一个应用单元怎样才算真的退出了。**

也就是说，启动阶段要解决“如何让它活起来”，停止阶段要解决“如何让它真的退下去”。这两者缺一不可。

也正因为如此，`Context` 的重量一半来自启动编排，另一半来自退场收束。

## 五、为什么 `Context` 一层会同时牵住 Session、类加载和注册体系

看到这里，还可以更进一步理解一个容易让人困惑的现象：

为什么前面那些看起来分散的专题——
- Session
- 类加载
- Servlet/Filter/Listener 注册
- Wrapper 实例生命史

最后都能重新回到 `Context` 这一层？

原因其实很简单：它们本来就都是“应用级部件”。

- Session 不是请求入口问题，而是应用运行期状态问题
- 类加载不是协议处理问题，而是应用边界与退场问题
- 注册体系不是业务功能问题，而是应用组件如何进入容器的问题
- Wrapper 实例生命史也不是单纯 Servlet 细节，而是应用级执行单元的一部分

所以它们会重新汇合到 `Context`，不是偶然，而是因为 `Context` 本来就在管理“这个应用级单元怎么活、怎么跑、怎么退”。

也就是说，如果说前面的主干篇是在一条条拆运行主线，那这一篇就是在往回收：

**它把那些已经拆开的主线重新收回到同一个应用级编排中心。**

## 到了这里，Web 应用已经不能再被理解成“组件列表”了

现在再回头看最开始那个直觉：

- Web 应用不就是几个 Servlet、Filter、Listener 的集合吗？

看到这里，这种理解已经很难再成立。

更准确的说法应该是：

- 这些组件当然存在
- 但它们之所以能共同构成“一个应用”，不是因为名字被归到同一个目录下
- 而是因为 `StandardContext` 把它们统一托管成了一个能启动、能运行、能停止、能销毁的应用级单元

这也解释了为什么 `Context` 的复杂度会这么高。因为它处理的从来不是“组件列表展示”，而是“组件如何共同构成一台可运行、可退场的应用机器”。

## 这篇真正立住的，不是 `Context` 这个类，而是“应用运行单元”这个概念

如果只从类名看，这一篇很容易被讲成：

- `StandardContext` 是容器树里的一层
- 它下面挂着很多东西
- 生命周期也比较复杂

这种讲法当然不能说错，但它还是太像属性导览。

从前面整卷主线归纳回来，更稳妥的理解方式应该是：

1. `Context` 不是普通中间层，而是应用级控制中心
2. 它托管的不只是请求路径，还托管类加载、Session、注册体系、实例生命史等应用级部件
3. 启动和停止都必须被看成这台应用单元的整体编排
4. 所以 Web 应用在 Tomcat 里不是“组件清单”，而是一个完整的运行单元

也就是说，这篇真正补上的，不是一个大类的说明书，而是一种更准确的卷级视角：

**Tomcat 管理的不是零散组件，而是一整个 Web 应用运行单元。**

## 这篇之后，Tomcat 还剩下哪些值得继续补的线

到这里，Tomcat 完整卷里几个最重要的主干、集成、规范、补深和生产层主线，其实都已经被拉得很完整了。

如果继续往下补，比较自然的方向还有两个：

1. 继续补机制补深层：
   - Servlet / Filter / Listener 注册体系纵深
   - 线程池 / Executor 专题

2. 或者开始回头做卷级收口与整理：
   - 卷前导读
   - 总索引 / 总图
   - 篇间导航加强

如果按当前嵌入式主线继续推进，更自然的下一步是：

- **Servlet / Filter / Listener 注册体系纵深专题**

因为到这里，应用运行单元已经立住了，接下来最自然的问题就是：这些组件当初到底是怎么被系统性挂进来、并一起纳入 `Context` 托管体系的。
