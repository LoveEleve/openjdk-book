# Tomcat Ch17-01 StandardContext 启停主线 — review notes

## 第一轮：事实审

### 目标
核对：
- `StandardContext` 是否被准确定位为应用级生命周期编排中心
- `file:line` 引用是否真实存在
- 是否把“应用级控制中心”说得超出源码可支撑范围

### 当前需核对的关键锚点
- `org/apache/catalina/core/StandardContext.java`
- 若后续正文补强，再补：
  - `startInternal()`
  - `stopInternal()`
  - 与 Loader / Manager / Wrapper / Listener / Filter 注册相关关键方法

### 初步判断
- 当前主线与 Ch17 规划一致：`Context -> 应用级部件 -> 启动编排 -> 运行托管 -> 停止销毁`
- 没有把本篇写成 `StandardContext` 属性大全
- 当前最大事实风险在于：正文已经把 `StandardContext` 提升为“应用级控制中心”，但还没有方法级硬锚点来压实它如何具体编排这些子系统

## 第二轮：因果审

### 目标
检查正文中所有“为什么 Web 应用不是组件清单”“为什么停止与启动同等重要”这类判断，是否由源码结构支撑，而不是靠容器直觉硬推。

### 当前因果链
1. `Context` 不只是执行链的一层，而是应用级子系统的总托管者
2. 启动顺序重要，因为多个子系统之间有依赖关系
3. 停止/销毁同样重要，因为退场失败会留下 Servlet、Session、类空间等历史包袱
4. 前面分散的专题最后都会重新汇合到 `Context` 这一层

### 当前风险
- 这些判断方向是对的，但后续收口时必须补足 `StandardContext` 方法级或编排级锚点，否则容易显得像卷级抽象总结
- “前面所有东西都会回到 Context”这句最需要克制，要让它像“应用级部件在这一层被统一托管”，而不是像“所有问题最终都归 Context”这种泛化结论

## 第三轮：结构审

### 目标
检查结构是否遵守“困惑 -> 失败方案 -> 总图 -> 编排拆解 -> 收网”的方法论，而不是把多个前文主题机械重新聚合。

### 当前结构评价
当前结构是：
1. 困惑开场
2. 失败方案
3. 最小总图
4. `StandardContext` 为什么是应用级控制中心
5. 启动顺序为什么重要
6. 运行时主线之所以顺，是因为 `Context` 先托住应用单元
7. 停止和销毁为什么和启动一样重要
8. 为什么 Session / 类加载 / 注册体系会重新回到这一层
9. 收网总结
10. 下篇桥接

### 当前结构优点
- 没有退化成 `StandardContext` 方法名清单
- 把“应用运行单元”作为单一心智模型贯穿全文
- 和前文形成了卷级回收，而不是简单重复

### 当前结构风险
- 这篇天然带有“把前文重新汇总”的性质，如果后续不补硬锚点，容易显得像高层总结多于源码剖析
- `启动顺序`、`停止顺序`、`应用级部件` 三段如果都进一步膨胀，会让篇中部失去节奏感

- 为什么 `Context` 不是普通中间层
- 为什么启动和停止都属于应用单元编排问题
