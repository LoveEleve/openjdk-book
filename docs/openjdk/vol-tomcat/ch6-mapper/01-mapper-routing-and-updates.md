# 为什么 Tomcat 还要单独搞一套 Mapper：路由树、匹配规则与运行态更新

> 本文基于 Tomcat 10.1.34 当前源码。本文只讲 `Mapper` / `MapperListener` 这条主线：请求进入 Catalina 后，为什么不能直接沿容器树现找目标，而要依赖一棵专门的路由结构，以及这棵结构为什么还必须随着容器变化持续更新。Valve 链、FilterChain、Session 生命周期、async/error 控制流都不在本文主叙事中。

## 为什么已经有 `Engine -> Host -> Context -> Wrapper` 了，还要再造一个 Mapper

Tomcat 前面几篇已经把主线大致立住了：

- 启动时，容器树、Connector、Adapter、MapperListener 会被接成运行时系统
- 请求进入 Catalina 后，会继续经过 `Mapper -> Valve -> FilterChain -> Servlet`
- Session、async、error 又各自沿着这条主线往外延伸

看到这里，很多人都会自然冒出一个问题：

既然 Tomcat 本来就已经有一棵 `Engine -> Host -> Context -> Wrapper` 的容器树，那请求进入 Catalina 之后，为什么不直接顺着这棵树去找目标？为什么还要再单独搞一个 `Mapper`？

这个疑问非常自然，因为从表面看，容器树已经具备了所有“找目标”需要的层次：

- `Engine` 对应总入口
- `Host` 对应虚拟主机
- `Context` 对应 Web 应用
- `Wrapper` 对应最终 Servlet

乍一看，请求只要顺着这棵树一路往下找，不就能定位目标了吗？

问题在于，**容器树回答的是“系统如何组织”，而请求主线需要的是“高频路径如何快速、正确、持续地选中目标”。**

这两件事看起来相近，但并不相同。

容器树更像“系统的真实结构”；而请求主线在高频路径上需要的，是一个能把这套结构压成“可直接拿来匹配 Host/Context/Wrapper 的运行时路由结构”。

也正因为如此，Tomcat 里才会出现两类容易被混淆、但职责完全不同的角色：

- `Mapper`：负责请求到来时的目标选择入口
- `MapperListener`：负责容器变化时，把变化持续同步进路由结构

所以，本文真正要回答的问题不是“Tomcat 里有个 Mapper 类做了什么”，而是：

**为什么对 Tomcat 来说，容器树本身还不够，请求主线必须再拥有一棵可高频匹配、可运行时更新的路由树？**

## 先看失败方案：为什么不能让请求每次都沿容器树现找目标

### 失败方案一：请求来了，直接在容器树里逐层找

这是最自然的直觉方案。

既然 Tomcat 里已经有：

- `Engine`
- `Host`
- `Context`
- `Wrapper`

那请求到来以后，直接沿树走一遍不就行了吗？

这个想法的问题在于，它把“系统结构”和“高频匹配结构”混成了一件事。

请求主线并不是低频管理操作，而是系统里最频繁、最敏感的一条路径。它要解决的不只是“理论上能不能找到”，而是：

- 能不能高频匹配
- 能不能快速选中目标
- 能不能在多种 URL 规则下保证优先级正确
- 能不能在容器变化后仍然保持结构一致

也就是说，直接沿容器树现找目标，也许在概念上说得通，但对一个持续处理请求的运行时系统来说，这远远不够。

所以 `Mapper` 的存在，不是为了多造一层抽象，而是为了把“系统结构”压缩成“请求路径可用的匹配结构”。

### 失败方案二：Mapper 只是一个普通 URL 匹配工具类

当读者意识到“现找容器树”不够后，下一步常见误区就是：

- 好吧，那 Tomcat 就加了一个 `Mapper`
- 它不过是一个拿 host/uri 做匹配的小工具类

这个理解也不对。

原因是，如果 `Mapper` 只是静态工具，那它只能回答：

- 给我一个 host 和 uri
- 我返回一个结果

但 Tomcat 是运行中的系统，容器本身会变化：

- Context 会启动/停止
- Wrapper 映射会变化
- 容器树不是永远一动不动的静态配置

如果没有一套运行时同步机制，`Mapper` 就只能是一张启动时生成、随后慢慢过期的路由快照。

而 Tomcat 显然不是这么设计的。它不只需要一个“会匹配”的类，还需要一套“会随着系统变化持续更新”的路由体系。

所以 `Mapper` 不能脱离 `MapperListener` 单独理解。

### 失败方案三：四级匹配只是一些实现细节，随便提一下就够了

第一次看到 Tomcat 的路由匹配规则时，很多人会觉得不过就是几种 URL 模式：

- exact
- prefix
- extension
- default

这好像只是语法层的几条匹配规则，没必要专门当成主线讲。

但真正的问题在于：**请求为什么会命中这个 Wrapper，而不是另一个看起来也差不多能匹配的 Wrapper，本质上就取决于这套规则的层级顺序。**

如果把这块压成几条规则表，读者会知道“有四种匹配”，却不知道：

- 为什么要四层并存
- 为什么它们必须有优先级
- 为什么这套规则需要被塞进一个独立的运行时路由结构里

所以四级匹配不是小注释，它其实直接决定了“请求目标选择为什么是正确的”。

## Tomcat 路由主线的最小总图

如果把 `Mapper` 这条线先压缩成最小模型，它可以写成下面这样：

```text
容器树发生变化
   -> MapperListener 监听变化
   -> 更新 Mapper 路由结构
   -> 请求到来时 Mapper.map(host, uri)
   -> 得到 Host / Context / Wrapper 目标
```

如果再换一种更容易理解的拆法，这条链可以分成三段职责：

```text
[原始结构]
Engine / Host / Context / Wrapper

   ->

[运行态同步]
MapperListener

   ->

[高频匹配入口]
Mapper
```

这张图最重要的价值，不是让读者去背类名，而是先把三个问题分开：

### 一、原始结构
回答：系统本身是怎么组织的？

这一层是容器树本身：
- `Engine`
- `Host`
- `Context`
- `Wrapper`

### 二、运行态同步
回答：当容器结构变化时，谁负责把变化同步成可用的路由结构？

这一层主要由：
- `MapperListener`

承担。

### 三、高频匹配入口
回答：请求真的到来时，谁负责把 host/uri 快速压到正确目标上？

这一层主要由：
- `Mapper`

承担。

只要先把这三层职责分开，后面为什么要同时有容器树和路由树，就会清楚很多。

## 一、`Mapper`：它不是附属工具，而是请求主线的目标选择入口

在 Ch3 里，我们已经把 `Mapper` 放在 Catalina 执行闭环的第一跳。但到了这一篇，需要把这个定位再说得更明确一些：

`Mapper` 不是“前面帮忙查一下”的小工具，而是请求主线真正的目标选择入口。

它的定义位置是：

证据：`org/apache/catalina/mapper/Mapper.java:47`

单看这一个锚点，我们先不要过度推导内部细节，但至少可以稳稳立住两件事：

- Tomcat 把目标选择这件事专门抽成了一个独立结构
- 这个结构不是随手塞进某个 `Valve` 里的实现细节，而是自己独立存在的核心角色

也就是说，请求一旦进入 Catalina，并不会自动“顺着树掉下去”，而是会先经过一个专门的目标选择入口。

这也是为什么本篇要把 `Mapper` 放在最前面讲：因为后面的 `Valve` 链根本不是在真空里执行的，它们必须建立在“目标已经被选出来”的前提上。

换句话说：

- `Mapper` 解决“该去哪里”
- 后面的 `Valve` 链解决“到了那里之后怎么继续执行”

如果没有这个边界意识，就很容易把 `Mapper` 误写成“前置小工具”，而把所有重量都压到容器责任链上。那样一来，为什么目标会是这个 Host/Context/Wrapper，就失去了一个独立解释层。

## 二、四级匹配：为什么不能只靠一种 URL 匹配规则

一旦承认 `Mapper` 是高频请求的目标选择入口，下一个最自然的问题就是：它到底按什么规则找目标？

Tomcat 没有把 URL 匹配压缩成一种单一模式，而是准备了多层规则。当前规划里已经把它概括成四类：

- exact
- prefix
- extension
- default

这里最值得讲的，不是把这四种规则背出来，而是先理解：为什么一个运行中的容器系统不能只靠一种简单匹配模式。

原因很直接。真实 Web 应用里的路由，不会只有一种形态：

- 有的路径就是一个完全精确的 URL
- 有的路径需要目录级前缀匹配
- 有的请求是按扩展名命中的
- 还总得有一个兜底默认规则

所以 `Mapper` 要解决的不是“会不会匹配”，而是“多种可能都存在时，最后到底该选谁”。

这就意味着，四级匹配的意义不是“规则多一点更灵活”，而是：

**请求目标选择必须在多种合法候选里，稳定地得出一个正确结果。**

所以四级匹配不是附录，而是路由树存在意义的一部分。因为如果没有这套层次规则，`Mapper` 就不能承担“高频请求目标选择入口”这个角色。

## 三、`MapperListener`：路由树为什么不能是一张静态快照

如果只看到 `Mapper.map(...)`，读者很容易觉得：

- 好，Tomcat 就是在请求到来时查一下路由树
- 那这个路由树大概是启动时建好，然后一直用

问题在于，Tomcat 不是只会启动一次然后永远不变的静态系统。它的容器结构本身会发生运行时变化：

- Context 会启动/停止
- Wrapper 映射会增加/移除
- 容器树不是永远静态冻结的

如果 `Mapper` 只是启动时生成的一张静态快照，那它很快就会和真实容器结构脱节。

这就是 `MapperListener` 必须存在的原因。

它的定义位置是：

证据：`org/apache/catalina/mapper/MapperListener.java:47`

而在 Ch1 里我们已经看到，`StandardService` 不只持有 `Mapper`，还直接持有 `MapperListener`：

证据：`org/apache/catalina/core/StandardService.java:97`
证据：`org/apache/catalina/core/StandardService.java:103`
证据：`org/apache/catalina/core/StandardService.java:151`

这些锚点组合起来，至少能先立住一个很重要的事实：

- 路由结构不是静态工具表
- 它从启动期开始，就已经被纳入运行时装配与更新体系

这也是为什么 `MapperListener` 不能被降级成“旁路监听器”。它不是外围观察者，而是让路由树持续保持正确的运行态同步者。

没有它，`Mapper` 也许还会“会匹配”，但它匹配的就不再是最新的真实系统结构。

## 四、Tomcat 需要的不是“能找目标”，而是“高频、正确、持续地找目标”

到了这里，其实就能看清 `Mapper` 这条线最核心的价值了。

Tomcat 真正需要的，不只是：

- 有一棵容器树
- 有一个会做匹配的方法

而是三件事同时成立：

1. 系统真实结构存在
2. 这套结构能被持续同步成路由树
3. 请求到来时，这棵路由树能高频、正确地选出目标

也就是说，Tomcat 需要的不是“理论上总能找到一个 Servlet”，而是：

**在运行中的系统里，请求每次到来，都能快速、稳定、持续地找到当下真正正确的 Host/Context/Wrapper。**

这就是为什么容器树本身还不够，Tomcat 还要再搞出一个 `Mapper` 体系。

## 这篇真正立住的，不是几条匹配规则，而是“路由树”这个概念

如果只从 API 表面看，`Mapper` 很容易被讲成：

- 一个做 host/uri 映射的类
- 里面有几种匹配规则
- 路由树变化时有个监听器更新它

这种讲法当然不算错，但它还是太平。

从当前源码归纳出来，更稳妥的理解方式应该是：

1. 容器树是系统的真实结构
2. `MapperListener` 负责把结构变化同步成可用的路由树
3. `Mapper` 负责在请求高频路径上使用这棵树做目标选择
4. 四级匹配不是规则附录，而是这棵路由树正确选目标的基础

只有把这条链立住，后面再回头看：

- 为什么请求会命中这个 Wrapper
- 为什么不是另一个也能匹配的 Wrapper
- 为什么容器变化之后路由仍然保持正确

这些问题才会自然地落到一棵“运行时路由树”上，而不是零散散落在几个工具类和规则表里。

## 这篇之后，Tomcat 还剩下哪些值得继续深挖的方向

到这里，这篇已经把 `Mapper` 这条线最核心的结论立住了：

- 容器树是系统的真实结构
- `MapperListener` 负责把结构变化同步成可用路由树
- `Mapper` 负责在请求高频路径上使用这棵树做目标选择
- 四级匹配共同保证目标选择的正确性

如果继续沿 Tomcat 这条线往深处走，最自然的补篇方向有两个：

1. **四级匹配本身的规则细化**
   - exact
   - prefix
   - extension
   - default

2. **`MapperListener` 的动态更新主线**
   - Context / Wrapper 变化后，路由树如何保持最新

也就是说，本篇已经把“为什么需要一棵运行时路由树”讲清楚了；后续如果继续写，最自然的方向不再是重讲总骨架，而是把匹配规则和动态更新机制分别专题化。
