### 目标
核对：
- 类名、路径、角色归属是否准确
- `file:line` 引用是否真实存在
- 代码块是否来自真实源码，而不是凭记忆改写

### 当前需核对的关键锚点
- `org/apache/catalina/mapper/Mapper.java:47`
- `org/apache/catalina/mapper/MapperListener.java:47`
- `org/apache/catalina/core/StandardService.java:97`

- 若正文进一步展开匹配细节，还要补 `Mapper.map(...)` 等更精确锚点

### 初步判断
- 当前主线与 T-6 规划一致：`容器树 -> MapperListener 同步 -> Mapper 匹配入口`
- `Mapper` 被正确定位为高频请求路径上的目标选择结构，而不是普通工具类
- `MapperListener` 被正确定位为运行态同步者，而不是外围监听器

## 第二轮：因果审

### 目标
检查正文里所有“所以/说明/意味着”是否由源码支撑，而不是靠常识硬推。

### 当前因果链
1. 容器树本身不等于高频请求可用的路由结构
2. `Mapper` 之所以存在，是因为 Tomcat 需要高频、正确、持续地选目标
3. `MapperListener` 之所以存在，是因为路由树不能是一张静态快照
4. 四级匹配之所以重要，是因为目标选择正确性依赖它们的优先顺序

### 当前风险
- `Mapper` 目前只有类定义锚点，正文里虽然没有过度展开实现细节，但正式收口时要控制口气，避免用一个类定义就撑起过强结论
- 四级匹配当前主要是结构性说明，后续若真要把这一块写硬，应该拆专题并补更精确源码锚点

## 第三轮：结构审

### 目标
检查结构是否遵守“困惑 -> 失败方案 -> 总图 -> 分层拆解 -> 收网”的方法论，而不是变成路由规则清单。

### 当前结构评价
当前结构是：
1. 困惑开场
2. 失败方案
3. 最小总图
4. `Mapper`
5. 四级匹配
6. `MapperListener`
7. 收网总结
8. 是否继续 Tomcat 的收口判断

### 当前结构优点
- 没有退化成“Mapper API + 规则枚举”笔记
- 先立“为什么需要路由树”，再讲 `Mapper` 和 `MapperListener`
- 四级匹配被放在“为什么目标选择需要层次规则”的位置，而不是孤立表格

### 当前结构风险
- `Mapper` 与“四级匹配”之间如果后续再补源码时处理不好，容易出现实现细节突然增密的问题
- 最后一节“要不要继续写 Tomcat”目前是收口判断，功能上合理，但正式终稿时要注意语气不要太像项目总结而偏离正文体裁

## 第四轮：读者审

### 目标
检查第一次接触 Tomcat 路由体系的读者是否能跟住，而不是只看到一堆匹配规则名词。

### 当前读者收益
读完后，读者至少应能回答：
- 为什么有容器树还不够
- 为什么 `Mapper` 不是普通工具类
- 为什么 `MapperListener` 必须存在
- 为什么四级匹配是正确选目标的基础，而不是规则附录

### 当前读者风险
- `exact / prefix / extension / default` 这些名词如果后续精修时再加实现细节，可能突然抬高阅读门槛
- `Mapper` 当前被解释得比较清楚，但若没有更硬的具体匹配证据，读者仍可能觉得“道理上像是对的”

## 第五轮：边界审

### 目标
检查本篇是否提前透支后续主题，或是否漏掉本篇必须收住的边界。

### 当前边界控制
本篇明确不深讲：
- Valve 链与 FilterChain 执行细节

### 当前边界风险

- 如果为证明 `MapperListener` 太重要而展开过多容器生命周期事件细节，会提前吞掉专门的动态更新补篇
