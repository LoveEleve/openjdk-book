# 为什么 Tomcat 的故障排查，最后总是要回到那几条主线去找

> 本文基于 Tomcat 10.1.34 与 Spring Boot 3.5.16 当前源码。本文不做命令手册，也不做事故年鉴，而是专门解释一件事：为什么线上看起来千奇百怪的 Tomcat 问题——启动失败、连接打满、线程耗尽、timeout、类加载器泄漏、慢请求——最后往深了排，几乎都会重新落回前面整卷已经建立起来的几条运行时主线：启动链、入口链、执行链、偏离链、状态链和退场链。

## 为什么线上故障看起来很多，但真正该追的主线其实并不多

线上排 Tomcat 问题，最容易让人产生焦虑感的地方在于：故障表象太多了。

你可能会看到：

- 端口没起来
- 容器启动失败
- 连接数打满
- 线程池耗尽
- 某些请求超时
- 某些请求特别慢
- 某个应用重载后内存一直下不来
- Metaspace 持续抬高
- 错误页行为不符合预期

这些现象看起来彼此很不像：
- 有的像网络问题
- 有的像线程问题
- 有的像业务慢
- 有的像内存泄漏
- 有的又像配置错误

也正因为这种表象差异，很多排障一开始就很容易走偏：

- 看到异常先搜异常名
- 看到线程多就只盯线程池
- 看到连接高就只盯端口和连接器
- 看到超时就直接调 timeout
- 看到内存涨就先怀疑 GC

这些动作不能说完全没用，但它们很容易把人带进一种“现象驱动”的排障模式：

- 看到什么现象，就追什么局部关键词
- 结果每次都像在重新开一张新题
- 却很难形成稳定的定位框架

前面整卷做完之后，其实我们已经有了一个更稳的视角：

Tomcat 虽然故障现象很多，但它内部真正重要的主线并不多。至少可以收束成下面几类：

- **启动链**：系统怎么被装起来
- **入口链**：请求怎么进来
- **执行链**：请求怎么被真正执行
- **偏离链**：async / timeout / error 怎么重新收束
- **状态链**：Session 等长期状态怎么活着
- **退场链**：类空间、实例和引用怎么真正退出

所以，本文真正要回答的问题不是“Tomcat 常见故障有哪些”，而是：

**为什么对 Tomcat 来说，看起来五花八门的故障，最后总是要重新落回这几条主线上定位？**

## 先看失败方案：为什么不能靠关键词和症状直接硬猜

### 失败方案一：先看异常名，再全网搜索

这是最自然的排障起点。

- 日志报什么异常
- 就先搜什么异常
- 搜到类似 case 再套进去

这个方法最大的问题在于：它很容易把你困在“字面相似”里，而不是“结构位置”里。

同样一个异常名，可能只是最后冒出来的表层症状，但真正的问题可能早就发生在另一条主线上：

- 启动异常，根因可能是 Boot 集成桥某一步装配失败
- 连接异常，根因可能是执行链太慢导致入口侧堆积
- timeout 异常，根因可能是 async 设计不当而不是 timeout 参数本身

所以关键词搜索可以作为入口，但不能替代结构定位。

### 失败方案二：线程问题归线程，连接问题归连接，慢请求归业务

这是一种很常见的切法，因为它符合表面现象：

- 线程多了 → 线程问题
- 连接高了 → 连接问题
- 请求慢了 → 业务问题

问题在于，Tomcat 的很多问题本来就是跨链传播的。

例如：

- 连接打满，可能只是执行链释放太慢，把前端入口一起拖住
- 线程池耗尽，可能不是线程配置不够，而是后端阻塞导致执行链长期占住线程
- 慢请求看起来像 SQL 问题，但如果不把它放回 `Mapper -> Valve -> FilterChain -> Servlet` 这条链里，就不知道慢是卡在入口、过滤、业务、还是偏离路径

所以“按症状分科室”虽然直观，但很容易把同一条结构链切碎。

### 失败方案三：Tomcat 故障就是 Tomcat 自己的问题

这也是一个非常危险的误解。

因为真实线上问题里，经常会出现一种情况：

- 现象是在 Tomcat 层爆出来的
- 但根因其实是应用代码、第三方库、下游依赖、ThreadLocal、缓存、JDBC、类加载残留这些东西把容器某一段主线拖死了

也就是说，Tomcat 往往是“症状暴露面”，却不一定是“根因发生面”。

所以 Tomcat 排障的核心能力，不是把所有锅都记在容器头上，而是：

**先判断故障落在哪条主线，再判断那条主线上是容器实现自己出了问题，还是应用/依赖把这条线拖坏了。**

## Tomcat 故障排查的最小总图

如果把故障排查先压缩成最小模型，它可以写成下面这样：

```text
symptom
   -> locate runtime chain
   -> inspect the critical boundary on that chain
   -> decide whether root cause is container-side or app-side
```

如果换一种更便于实战的拆法，这条线可以分成六类结构位置：

```text
[启动链]
Tomcat / Factory / Starter / WebServer

[入口链]
Connector / ProtocolHandler / Endpoint / Processor

[执行链]
Mapper / Valve / FilterChain / Servlet

[偏离链]
AsyncStateMachine / AsyncContextImpl / ErrorReportValve

[状态链]
Session / Manager / expire / persist

[退场链]
WebappClassLoaderBase / clearReferences / old instances
```

这张图最重要的价值，不是让读者硬背排障分类，而是帮你在看到故障现象之后，先做第一步真正关键的判断：

**这个问题首先落在哪条链上？**

只要这一步判断错了，后面的命令、日志、线程栈、指标都可能越查越偏。

## 一、启动失败：先回启动链，不要一上来就盯异常名

只要容器起不来，第一反应应该先回启动链：

- Spring Boot 是怎么触发容器创建的
- Factory 有没有把结构组装出来
- Starter 有没有把应用注册进去
- TomcatWebServer 是在哪一步失败的

也就是说，启动失败最自然的定位框架应该是：

- **装配有没有完成**
- **容器有没有真正进入启动阶段**
- **应用注册有没有在容器初始化时炸掉**

前文已经把这条启动链压实过：
- `ServletWebServerApplicationContext.onRefresh()/createWebServer()`
- `TomcatServletWebServerFactory.getWebServer(...)`
- `TomcatStarter.onStartup(...)`
- `TomcatWebServer.initialize()/start()`

而不是先把异常名扔出去搜。

因为前面整卷已经建立过：
- `ServletWebServerApplicationContext`
- `TomcatServletWebServerFactory`
- `TomcatStarter`
- `TomcatWebServer`

这四层角色本来就在同一条启动与集成桥上。启动失败时，先按这条链逆着回去，比盯异常字符串更稳。

## 二、连接打满 / 线程耗尽：先看入口链和执行链是不是一起堵了

线上最常见的两个“看起来像基础设施”的问题是：

- 连接数打满
- 线程池耗尽

它们最危险的地方在于，表面症状很像资源不足，于是人很容易直接调：

- `maxConnections`
- `maxThreads`
- `acceptCount`

但前面性能篇已经说明，这几个问题大多数时候不是单独的“参数不够”，而是：

- 请求进得来
- 执行链走得慢
- 线程长时间占着不放
- 队列排起来
- 入口压力继续向上堆

也就是说，这类问题最稳的定位方式不是“入口层还是线程池层二选一”，而是：

**先同时回到入口链和执行链，看是不是执行链把入口链拖住了。**

前文对应的关键锚点至少包括：
- `NioEndpoint`：`org/apache/tomcat/util/net/NioEndpoint.java:71`
- `Http11Processor`：`org/apache/coyote/http11/Http11Processor.java:70`
- `StandardWrapperValve`：`org/apache/catalina/core/StandardWrapperValve.java:141`

如果这一步不做，就会不断出现一种假修复：

- 参数调大一点
- 表面症状缓一会儿
- 但真正堵点没消失

## 三、async / timeout / 错误页异常：先回偏离链，不要把它当普通慢请求

只要问题和下面这些现象有关：

- async dispatch 异常
- timeout 突然增多
- 某些请求不按正常路径收尾
- 错误页行为异常

第一反应就不该先把它当成普通慢请求，而应该直接回偏离链：

- `AsyncStateMachine`
- `AsyncContextImpl`
- `StandardHostValve.throwable(...)`
- `ErrorReportValve`

因为前面我们已经讲过，这一整段不是“主线之外的补丁逻辑”，而是 Tomcat 专门为偏离同步执行路径准备的一条重新收束链。

所以这类问题如果只放在：
- 业务慢
- timeout 参数太短
- 某个错误页没配好

这种局部解释里，通常都不够。

更稳的问法应该是：

**这个请求是不是已经偏离了正常执行链？偏离之后，容器在哪一段没有把它重新收好？**

前文对应的关键锚点至少包括：
- `AsyncStateMachine`：`org/apache/coyote/AsyncStateMachine.java:129`
- `AsyncContextImpl`：`org/apache/catalina/core/AsyncContextImpl.java:442`
- `StandardHostValve.throwable(...)`：`org/apache/catalina/core/StandardHostValve.java:231`

## 四、类加载器泄漏 / 重载残留：先回退场链，不要只盯 GC

只要现象带着这些特征：

- 应用重载后旧类还在
- Metaspace 逐渐抬高
- 旧线程、旧缓存、旧实例残留
- 停掉应用后资源不释放

第一反应就该直接回退场链：

- `WebappClassLoaderBase.stop()`
- `clearReferences()`
- 线程、ThreadLocal、JDBC 驱动、缓存、RMI targets 这些残留源

因为这类问题最容易被误解成：
- GC 不行
- JVM 有问题

但前面类加载器泄漏篇已经说明，根因通常不是 GC 本身，而是：

**应用类空间并没有真的和那些活引用链脱钩。**

所以只盯堆和 GC，很容易越查越偏。更稳的切入点应该是：

- 应用类空间为什么没退场
- Tomcat 当前清理动作已经做了什么
- 还剩哪些容器无法替应用兜底的引用链

前文对应的关键锚点至少包括：
- `WebappClassLoaderBase.stop()`：`org/apache/catalina/loader/WebappClassLoaderBase.java:1523`
- `clearReferences()`：`org/apache/catalina/loader/WebappClassLoaderBase.java:1574`

## 五、慢请求：不要直接把锅甩给 SQL 或下游接口

慢请求是最容易让人快速归因的症状之一。

一看到延迟高，很多人就会立刻想到：

- SQL 慢
- 远程调用慢
- 业务代码慢

这些当然都可能是真的，但如果就停在这里，排障就会少掉一个非常关键的层次：

**这个慢，到底是发生在执行链的哪一段？**

因为对 Tomcat 来说，请求慢并不是一个无结构的结果。它至少会穿过：

- `Mapper`
- `Valve`
- `FilterChain`
- `Servlet`
- 以及可能的 async/timeout 偏离链

所以更稳的排法不是一句“慢在 SQL”，而是先问：

- 是入口进得慢
- 还是执行链本身某一层拖得久
- 还是请求偏离主线后收不回来
- 还是 Session / 类空间 / 资源残留让系统整体越来越重

这样，慢请求才不会被草率缩成“应用代码慢”这一种解释。

## 到了这里，Tomcat 排障真正依赖的不是命令，而是“先分主线”的能力

看到这里，应该已经能看清一个很重要的事实：

真正稳定的 Tomcat 排障能力，并不是你会多少命令，而是你会不会先做一个结构判断：

- 这是启动链问题？
- 这是入口链问题？
- 这是执行链问题？
- 这是偏离链问题？
- 这是状态链问题？
- 这是退场链问题？

一旦这一步做对了，后面的日志、线程栈、指标、异常名、堆内对象，才会开始变得有意义。

如果这一步做错了，哪怕命令敲得再熟，也只是在错误的地图上越走越快。

所以故障排查真正该学的，不是命令本身，而是：

**如何把故障现象重新挂回那几条已经讲清楚的运行时主线上。**

## 这篇真正立住的，是“故障是主线的反面投影”

如果只从表面看，Tomcat 的故障现象很多、很乱、很像一堆互不相干的 case：

- 启动失败
- 连接打满
- 线程耗尽
- timeout
- 错误页异常
- 类加载器泄漏
- 慢请求

但从前面整卷主线重新看回来，更稳妥的理解方式应该是：

1. 故障现象虽然很多，但真正的结构主线很少
2. 排障第一步不是找命令，而是先找故障落在哪条主线
3. 前面整卷的主干、集成、规范、补深，最终都会在这一篇里重新变成定位框架

也就是说，这篇真正补上的，不是一本事故清单，而是一种更稳的排障视角：

**Tomcat 的故障，本质上是前面那些运行时主线在反面投影里的表现。**

## 到这里，Tomcat 完整卷第一阶段为什么已经可以阶段性收口

如果把整卷回头看一遍，到这里其实已经形成了一套非常完整的知识闭环：

- 主干层：系统怎么跑
- 集成层：系统怎么被装起来
- 规范层：哪些是契约，哪些是实现
- 机制补深层：实例生命史、类空间隔离与退场
- 生产层：性能、安全运维、故障排查

也就是说，Tomcat 这一卷到这里，已经不只是“把源码讲过一遍”，而是已经形成：

- 机制主线
- 实现边界
- 集成桥
- 生产投影
- 反向定位框架

从这个角度看，**Tomcat 完整卷第一阶段已经具备阶段性收口条件。**
