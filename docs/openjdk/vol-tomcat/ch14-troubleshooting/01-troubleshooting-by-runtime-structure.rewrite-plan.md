## 一句话困惑

为什么线上看起来千奇百怪的 Tomcat 问题——启动失败、连接打满、线程耗尽、超时、类加载器泄漏、慢请求——最后往深了排，几乎都会重新落回前面已经讲过的那几条运行时主线？

## 一句话顿悟

Tomcat 的故障表面是现象，底层却是结构：**排障真正要做的，不是先背命令，而是先判断当前故障卡在启动链、入口链、执行链、偏离链、状态链还是退场链。**

## 读者理解路径

1. 从“为什么命令很多，但真正有效的排障总是要回到结构位置”切入。
2. 建立最小总图：启动故障 / 入口故障 / 执行链故障 / 偏离路径故障 / 长期运行故障。
3. 解释“先分层，再追主线”为什么比“先搜错误名词”更稳。
4. 用几类典型问题做结构映射：
   - 启动失败
   - 连接打满 / 线程耗尽
   - async/timeout 问题
   - 类加载器泄漏
   - 慢请求
5. 最后收束：真正的排障能力，不是记住多少命令，而是知道现象背后属于哪一条主线。

## 失败方案推演

### 失败方案一：先找错误关键词，看到异常就开搜

这是最自然的排障直觉：
- 看日志
- 找异常名
- 搜错误关键词

这个方法并不是完全没用，但它最大的问题是：
- 它只能让你知道“哪里看起来坏了”
- 却不一定能告诉你“它为什么会坏、卡在主线哪一段”

所以它适合作为起点，不适合作为主线。

### 失败方案二：Tomcat 故障就是容器自己的问题，和应用逻辑可以切开

这也是很常见的误解。

很多人会把故障先分成：
- Tomcat 层
- 应用层

但真实运行中，二者经常是纠缠的：
- 线程耗尽可能源于下游业务阻塞
- 连接打满可能源于执行链释放太慢
- Session / 类空间问题可能在容器里爆炸，但根因在应用残留引用

所以排障时不能假设“容器故障”和“应用故障”一定可硬切开。

### 失败方案三：性能、安全、排障是三套彼此平行的知识

前面两篇已经说明：
- 性能问题会回到结构
- 安全与运维是在守结构边界

如果到排障这篇又把它们彻底切开，就会失去前文已经建立的整卷视角。

更准确的说法应该是：
- 性能告诉你“哪里可能压住了”
- 安全与运维告诉你“哪些边界要守住”
- 排障则是在现象真的爆出来之后，沿主线把它们重新追回去

## 必须澄清的误解

1. 排障不是命令清单竞赛，而是结构定位能力。
2. 异常关键词只能提供入口，不能自动给出主线位置。
3. 很多看起来是 Tomcat 故障的问题，根因可能出在应用占用了容器某一段主线。
4. 本篇讲的是“怎么沿主线定位”，不是完整事故百科全书。
