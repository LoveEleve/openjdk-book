# Tomcat 为什么没高调谈对象池，却处处都在管理对象生命史

> 本文基于 Tomcat 10.1.34 当前源码。本文只讲“对象复用 / 对象生命史管理”这条线：Tomcat 虽然不像某些中间件那样直接摆出一套显眼的对象池 API，但从 `Request/Response` 的 recycle、输入输出缓冲的 nextRequest，到 `StandardWrapper` 的实例管理，再到类空间退场时的清理链，都在围绕同一个问题打转——对象如何被重复使用、状态如何被清干净、生命史如何在继续复用和最终退场之间正确收束。

## 为什么 Tomcat 没有高调讲对象池，但你一路读下来总觉得它在到处复用东西

很多人第一次系统读 Tomcat 时，都会有一种很奇怪的感觉。

从表面上看，Tomcat 并没有像某些框架那样，一上来就把“对象池”当成主角：

- 没有特别醒目的池化总图
- 没有大段围绕 borrow / return 的统一 API
- 没有非常显眼的“这里就是核心对象池系统”这种入口

所以很容易下一个判断：

- Tomcat 可能更偏运行时流程组织
- 但对象复用应该不是它特别独立的一条线

可只要真的把前面几篇串起来，你又会不断碰到另一种事实：Tomcat 几乎到处都在反复处理“对象怎么再次使用”这件事。

例如：

- `Request` 会 `recycle()`
- `Response` 会 `recycle()`
- `Http11InputBuffer.nextRequest()` 会继续推进下一轮请求
- `Http11OutputBuffer.nextRequest()` 也会把输出状态带入下一轮
- `StandardWrapper` 在请求到来时要 `allocate()`，结束后要 `deallocate()`，容器退出时还要 `unload()`
- `WebappClassLoaderBase` 在应用退场时还要做一整轮引用清理

这些东西如果分散着看，很容易只是“这里有个 recycle，那里有个 unload”。

但如果把它们放在一起，就会看见一条更深的主线：

**Tomcat 也许没有高调地说“对象池”，但它其实一直在做一件更本质的事：管理对象怎样被再用、怎样被清干净、怎样真正退出。**

所以，本文真正想回答的问题不是“Tomcat 有没有对象池”，而是：

**为什么 Tomcat 虽然没有显眼的统一池化门面，却处处都在处理对象生命史的复用与退场？**

## 先看失败方案：为什么不能把复用理解成“顺手省几个 new”

### 失败方案一：Tomcat 没有明显对象池，所以没有独立的对象复用主线

这是最常见的第一反应。

因为和一些把池化系统摆到台前的框架相比，Tomcat 看起来更像是在讲：

- 容器树
- 请求主线
- 生命周期
- 路由和执行链

而不是在讲：
- 一个统一的大对象池体系

于是就很容易得出一个结论：

- Tomcat 当然会复用一点对象
- 但那只是局部小优化，不构成独立主线

这个结论的问题在于，它会把 Tomcat 里反复出现的复用事实统统看轻。

因为只要回看前面的几条主线，就会发现：

- 协议层对象会 recycle
- 请求结束后状态会 nextRequest
- Servlet 实例不是一次性对象，而是被长期管理和分配的对象
- 类空间退场时，残留引用链还要被显式清理

这说明 Tomcat 关心的并不是“有没有一个统一池化 API”，而是：

- 这批对象会不会被重复使用
- 再次使用前状态有没有被清干净
- 不再使用时能不能真的退出

所以，Tomcat 的对象复用主线不是不存在，而是更分散、更贴着运行时生命史本身。

### 失败方案二：对象复用就是性能技巧，和正确性没多大关系

这是第二个很容易发生的误解。

因为一说复用，最先想到的通常是：

- 少 new 一些对象
- 少 GC 一些垃圾
- 提高一点吞吐

这些当然都是真的，但如果只把复用理解成性能技巧，就会看不到 Tomcat 里更关键的一层：

**复用成功的前提是状态必须被清干净。**

也就是说，在容器场景下，对象复用不是“节省分配”这么简单，它还必须回答：

- 下一轮请求会不会看到上一轮残留状态
- 某个对象是不是被过早拿去复用
- 某个实例是不是在应该退场时还挂着不走

所以复用问题同时也是正确性问题。对 Tomcat 这种长期运行容器来说，这一层甚至比“省多少分配”更关键。

### 失败方案三：recycle 是运行时的事，clearReferences 是退场时的事，两者彼此无关

从字面上看，这种切分很自然：

- recycle 是请求处理时的小复用动作
- clearReferences 是应用停止时的大清场动作

两者看起来像两个世界。

但真正把它们放回“对象生命史”里看，就会发现它们其实在回答同一个更大的问题：

**对象到底怎样才算“可以安全继续活下去”，或者“应该彻底退场”。**

如果只把 recycle 当作快路径优化，把 clearReferences 当作事故兜底，就会看不见两者在逻辑上其实是前后相接的：

- recycle 关心的是“继续复用前，状态有没有回到干净起点”
- clearReferences 关心的是“已经不用了，残留引用链有没有真正断干净”

也就是说，它们都是对象生命史管理，只是分别发生在继续使用前和彻底退场时。

## Tomcat 对象复用主线的最小总图

如果把 Tomcat 里的对象复用主线先压缩成最小模型，它可以写成下面这样：

```text
create / load
   -> use
   -> reset / recycle
   -> reuse
   -> stop / clear / unload
```

如果再换一种更容易理解的拆法，这条线可以分成三段职责：

```text
[继续复用]
Request / Response / buffers / keep-alive

   ->

[分配与持有]
Servlet instance / StandardWrapper

   ->

[最终退场]
ClassLoader stop / clearReferences / unload
```

这张图最重要的价值，不是把一堆“会复用的对象”列出来，而是先把三个问题分开：

### 一、继续复用
回答：哪些运行时对象会在多轮请求之间继续被使用？

### 二、分配与持有
回答：哪些对象不会每次都新建，而是被长期持有、按请求分配？

### 三、最终退场
回答：对象和它所属的类空间，在彻底不用时怎么真正退出？

只要把这三段职责分开，Tomcat 为什么处处都在管理对象生命史，就不再显得零散。

## 一、协议层对象：`Request/Response` 不是一次性对象，而是会被反复清理与再用

前面在 HTTP 处理纵深篇里已经讲过：

- `Http11Processor` 不只是“懂协议”的解析器
- 它还在组织一组输入、请求、响应、输出对象的运行时生命史

其中最典型的就是：

- `Request.recycle()`
- `Response.recycle()`
- `Http11InputBuffer.nextRequest()`
- `Http11OutputBuffer.nextRequest()`

也就是说，对 Tomcat 来说，请求和响应对象并不是“这次请求来就 new 一次、处理完就算了”的一次性消耗品，而是会在多轮请求之间被重置、清理、再用的一组协议层对象。

这条线最关键的，不是它们会被复用本身，而是：

- 在下一轮请求到来之前，状态必须已经被清回到可复用的起点

如果这一点做不好，问题就不是“少复用了一个对象”，而是“下一轮请求读到了上一轮残留状态”。

所以协议层对象复用的第一原则，不是快，而是干净。

## 二、Servlet 实例：`StandardWrapper` 管的不是“某个请求的对象”，而是长期持有与按需分配

对象复用主线并不只发生在协议层。

在前面的 `StandardWrapper` 深挖篇里我们已经看到，Servlet 实例也不是“请求来了 new 一个、请求走了就没了”的对象。相反，它被组织成了一条完整的实例生命史：

- `loadServlet()`
- `initServlet()`
- `allocate()`
- `deallocate()`
- `unload()`
- unavailable

这说明另一层完全不同的复用事实：

- 协议层对象更像“多轮请求之间反复重置再用”
- Servlet 实例更像“容器长期持有，按请求分配使用”

也就是说，Tomcat 的对象复用不是一个统一动作，而是至少有两种不同模式：

1. **快路径对象复用**：典型是 `Request/Response`、缓冲区
2. **长期持有 + 按需分配**：典型是 Servlet 实例

这也解释了为什么不能用“有没有对象池”来概括 Tomcat 的复用逻辑。因为 Tomcat 真正在管理的是多种不同对象生命史，而不是只有一种统一池化协议。

## 三、为什么复用和退场其实是同一条线的前后两半

如果只盯运行时，很容易觉得对象复用的重点就在：

- recycle
- nextRequest
- allocate / deallocate

但 Tomcat 这条主线真正完整起来，必须把“最终退场”也放进来一起看。

前面在类加载器泄漏篇里已经看见：

- `WebappClassLoaderBase.stop()`
- `clearReferences()`
- JDBC / 线程 / ThreadLocal / 缓存 / RMI targets 清理

这说明什么？

说明容器在意的不只是“对象能不能继续复用”，还在意：

- 它什么时候不该继续活着
- 它所属的类空间什么时候必须真正退出
- 如果退场失败，旧对象和旧类空间会怎样拖住整个应用

所以 recycle 和 clearReferences 看起来一个是“小复用动作”，一个是“大清场动作”，但在对象生命史视角下，它们其实在回答同一个大问题：

**对象在继续活和彻底退之间，容器是怎么管理它的。**

这也是为什么对象复用专题必须同时把运行时复用和退场清理讲到一条线上。

## 四、为什么 Tomcat 真正关心的不是“池没池化”，而是“状态有没有被清干净”

看到这里，就能把 Tomcat 和很多一提对象池就先看“池大不大、命中率高不高”的系统区分开了。

Tomcat 当前这条线最值得记住的，不是“它池化了哪些对象”，而是：

- 它一直在反复处理状态能否干净重置
- 它一直在反复处理对象是否该继续被持有
- 它一直在反复处理退场时引用链是否真正断开

也就是说，Tomcat 的对象复用主线更像一种 **对象生命史管理**，而不只是“提高性能的小技巧”。

这也是为什么：

- 协议层对象的 recycle 很关键
- Servlet 实例的 allocate/deallocate 很关键
- 类空间退场时的 clearReferences 也很关键

因为这三类动作都在守同一个底层原则：

**对象无论是继续活下去，还是准备彻底退场，都不能把上一轮的历史包袱偷偷带到下一轮。**

## 到了这里，Tomcat 的对象复用已经不可能再被理解成“有没有池”了

现在再回头看最开始那个问题：Tomcat 有没有对象池？

看到这里，更稳妥的回答已经不应该是简单的“有”或“没有”。

更准确的说法应该是：

- Tomcat 没有把“对象池”做成一个统一高调的显式门面
- 但它在运行时里处处都在管理对象的继续复用、状态重置、按需分配和最终退场

也就是说，Tomcat 真正的重点不是“池”这个外形，而是：

**对象生命史有没有被管理好。**

这也是为什么这篇必须单独存在。因为如果不把这条线抽出来，前面那些 recycle、allocate、clearReferences 看起来就只是散落在不同专题里的局部事实；只有把它们放在一起，读者才会第一次看见它们其实都在回答同一个问题。

## 这篇真正立住的，是“对象生命史管理”这个概念

如果只从表面看，这篇很容易被讲成：

- Tomcat 复用了一些协议对象
- Tomcat 长期持有了 Servlet 实例
- Tomcat 停止时会清理引用

这种说法当然不算错，但还是太碎。

从前面整卷主线归纳回来，更稳妥的理解方式应该是：

1. 协议层对象在多轮请求之间被 recycle 和再用
2. Servlet 实例被长期持有并按请求分配
3. 类空间退场时容器还要尝试清理残留引用
4. 所以 Tomcat 在做的不是零散优化，而是在管理对象如何继续活、如何正确再用、以及如何真正退场

也就是说，这篇真正补上的，不是“Tomcat 也有点复用机制”，而是一种更统一的看法：

**Tomcat 的对象复用，本质上是对象生命史管理。**

## 这篇之后，Tomcat 还剩下哪些值得补的线

到这里，Tomcat 完整卷里“主干层 + 集成层 + 规范层 + 机制补深层”的骨架已经被压得相当实了。

如果继续往下补，比较自然的方向只剩两类：

1. 继续补机制补深层：
   - `StandardContext` 启停主线
   - Servlet / Filter / Listener 注册体系纵深
   - 线程池 / Executor 专题

2. 或者继续向生产层/案例层落：
   - 更细的生产案例
   - 典型故障链专题

如果按当前你定下的嵌入式主线收束节奏，更自然的下一步是：

- **`StandardContext` 启停主线**

因为到这里，对象生命史已经讲清楚了，再回头把 Context 内部组件的启动/停止/销毁顺序压透，整个嵌入式 Tomcat 的“活起来 -> 跑起来 -> 收起来”链条就会更完整。
