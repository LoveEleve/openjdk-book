# 03 · GC 与回收策略：专家级答案

## 1. 垃圾回收器有哪些？怎么选？

**标准答案**

常见回收器有 Serial、Parallel、CMS、G1、ZGC、Shenandoah。不同收集器的目标不同：有的偏吞吐，有的偏低停顿。

**进程 / OS 视角**

从进程视角看，GC 的差别不是“名字不同”，而是**暂停时间花在哪里、CPU 常驻开销花在哪里、内存冗余花在哪里**。你最终在操作系统里看到的，是：

- GC 线程数不同；
- 堆的地址组织不同（连续代际空间 vs Region）；
- 某些收集器把大量成本推到 barrier 上，让 mutator 每次访问对象都多付一点点；
- 某些收集器把成本集中到 stop-the-world 时刻，换取平时线程运行更干净。

这就是为什么“哪个 GC 更好”永远是伪问题，正确问题是：**你要吞吐、停顿，还是稳定的尾延迟？**

**HotSpot 实现视角**

- **Serial / Parallel**：基于 `GenCollectedHeap` 的代际堆，核心是 stop-the-world 回收，只是 Parallel 把 GC worker 并行化，吞吐更高；
- **CMS**：老年代并发标记 + 并发清扫，但不压缩，所以换来的是更低停顿和长期碎片；
- **G1**：Region + RSet + SATB，目标不是“最少指令”，而是把 pause 工作集缩小到一批可预算的 Region 和它们的入边；
- **ZGC / Shenandoah**：进一步把难题转移到并发 relocation 和访问屏障，目标是极低停顿，但要付更高的屏障和元数据复杂度。

**演进边界**

- JDK 8 默认是 Parallel；JDK 11 默认改成 G1；
- CMS 在 JDK 9 开始标记弃用，JDK 14 移除；
- ZGC/Shenandoah 在不同发行版和版本里的成熟度不同，不能把一篇博客里的结论直接当成所有版本事实。

**收束句**

这题真正考的不是“你背了几个收集器名字”，而是你知不知道 **每个收集器把复杂性放在了暂停、并发还是屏障哪一边。**

## 2. 什么情况会触发 Full GC？

**标准答案**

常见触发 Full GC 的场景包括：老年代空间不足、`System.gc()`、Metaspace 阈值、晋升失败、某些并发收集器的失败退化路径。

**进程 / OS 视角**

从进程角度看，Full GC 不是“堆满了就执行一次大扫除”，而是 JVM 在“继续分配已经不安全了”的情况下，尝试拿到一次更强的全局一致窗口。它可能是因为堆空间不足，也可能是因为 native metadata（Metaspace）已经到阈值，需要借 GC 的 class unloading 能力回收一整仓类元数据。

**HotSpot 实现视角**

典型触发源：

- **老年代分配失败**：对象复制/晋升无法继续，GC 退化到 Full GC；
- **Metaspace 失败**：`Metaspace::allocate()` 失败后调 `Universe::heap()->satisfy_failed_metadata_allocation(...)`，原因码是 `_metadata_GC_threshold`；
- **`System.gc()`**：显式 GC 请求，一般对应 `GCCause::_java_lang_system_gc`；
- **promotion failure / concurrent mode failure**：并发或增量路径没兜住，需要更重的全堆回收。

**演进边界**

- 不同收集器对 Full GC 的实现路径不一样：
  - **Serial / Parallel** 的 Full GC 比较接近“传统 stop-the-world 整体整理”；
  - **CMS** 在并发路径失效时（如 concurrent mode failure）会退化到更重的 stop-the-world 路线；
  - **G1** 的 Full GC 虽然也是全局回收，但实现并不是简单复用传统代际堆逻辑，而是要和 Region / Humongous / remembered set 世界兼容。
- 所以面试里说“Full GC 就是把整个堆重新整理一遍”太粗，只能当极简口语，不是 collector 级别的准确答案。
- Metaspace 触发 GC 很容易被误答成“方法区在堆里所以要 GC”，这在 JDK 8 之后已经错了。

**收束句**

Full GC 真正的触发条件不是“内存快满”，而是 **JVM 判断：再不拿一次更强的全局一致窗口，分配和生命周期判定都不安全了。**

## 3. `System.gc()` 一定立刻执行吗？

**标准答案**

不一定。它只是向 JVM 发出一个显式 GC 请求，JVM 可能执行，也可能被配置忽略。

**进程 / OS 视角**

从进程角度看，`System.gc()` 不是 CPU 的中断指令，也不是内核命令。它只是应用线程发给 JVM 的一个“建议”。因此它天然要服从 JVM 的调度、collector 的策略和当前运行状态。

**HotSpot 实现视角**

- `System.gc()` 通常对应 `GCCause::_java_lang_system_gc`；
- `-XX:+DisableExplicitGC` 可以让它直接失效；
- 某些 collector 对显式 GC 有特殊处理，比如 G1 可能走自己的 Full GC 路径；
- 老版本里 RMI 还会周期性触发 `System.gc()`，这也是为什么生产环境常见的排障经验是先关掉显式 GC。

**演进边界**

- “一定会 Full GC”这个说法太粗。不同收集器、不同 flag、不同版本下处理并不完全一致；
- 面试里如果能主动补一句“`DisableExplicitGC` 是先看的一条线”，说明你见过真实生产环境。

**收束句**

`System.gc()` 不是真命令，而是 **应用线程向 JVM 提的一个请求，至于什么时候、怎么执行，最终由 collector 和 VM 决定。**

## 4. 什么是 STW？为什么不能消除？

**标准答案**

STW（Stop-The-World）是 JVM 暂停所有 Java 应用线程，以便安全执行 GC 或其他需要全局一致状态的 VM 操作。

**进程 / OS 视角**

STW 本质上不是“GC 喜欢卡你一下”，而是 JVM 必须在一个没有应用线程继续改对象图的窗口里，才能安全地：

- 扫描线程栈；
- 移动对象；
- 判断哪些对象已不可达；
- 重建/更新某些全局状态。

没有这个窗口，就没有“冻结对象图”的前提。

**HotSpot 实现视角**

SafePoint 协议负责把线程拉到可停位置，GC 再利用 OopMap / InterpreterOopMap 扫描栈。即便像 ZGC/Shenandoah 这样把大量工作并发化，仍然不能完全消灭 STW，只能压缩 STW 到更短、更少的窗口——例如并发 relocation 仍然要靠额外的屏障和元数据协议换来停顿减少。

**演进边界**

- “低停顿”不等于“无 STW”；
- 把 GC 问题答成“有没有 stop-the-world”是低级误区，真正该答的是**哪些工作被并发化了，哪些工作仍然必须进入 STW**。

**收束句**

STW 不是一个 collector 的缺点，而是 **JVM 在某些关键时刻为了一致性必须支付的窗口成本。**

## 5. G1 和 CMS 的核心区别？

**标准答案**

CMS 追求并发标记/清扫、减少停顿，但不压缩；G1 用 Region 化堆、RSet 和 SATB 来做可预测停顿和增量回收。

**进程 / OS 视角**

在进程层面，两者的差别体现在：

- CMS 倾向于保持老年代整体空间语义，长期运行容易碎片化；
- G1 把堆切成很多 Region，每次只针对一小批工作集做 evacuation；
- CMS 的“停顿换并发”体现在并发标记/清扫；G1 的“停顿换元数据”体现在 RSet、SATB 和 pause budgeting。

**HotSpot 实现视角**

- **CMS**：不压缩，所以 free list 管理和碎片是核心代价；它经典上依赖 incremental update 方向的并发可达性维护；
- **G1**：用 SATB 保护并发标记快照，用 RSet 回答“谁从外面指向我”，把 pause 成本从“老年代体量”改写成“本次 Collection Set 的大小”。

这是最该说出的区别：**CMS 和 G1 不只是堆布局不同，而是连并发可达性记录方向都不同。**

**演进边界**

- JDK 11 默认 G1，不再默认 CMS；
- 讲 CMS 时别忘了说明它在现代 JDK 中已退出主线，不是推荐答案，但它仍然是理解并发收集 trade-off 的经典案例。

**收束句**

G1 和 CMS 真正的分水岭，不是 Region，而是 **一个把复杂性放在碎片和清扫上，一个把复杂性放在工作集压缩和元数据上。**

## 6. 什么是晋升失败？为什么危险？

**标准答案**

晋升失败是指年轻代存活对象在 GC 时无法成功复制到老年代或目标空间，导致 GC 退化或触发更重的回收。

**进程 / OS 视角**

你可以把它想成：年轻代对象本来要“搬家”，但老年代没有足够连续空间/目标空间接收它们。这样 JVM 就失去了“继续按当前 GC 协议前进”的能力。

**HotSpot 实现视角**

晋升失败通常出现在：

- 老年代空间不足；
- 大对象或 survivor 对象太多；
- 当前 collector 的复制/转移策略无法继续。

后果不是立即 OOM，而是先退化：

- 尝试更大范围的 GC；
- 可能触发 Full GC；
- 最后才 OOM。

它危险的地方在于：这往往意味着堆布局和对象年龄结构已经走到了 collector 的坏路径上。

**演进边界**

- 晋升失败与普通分配失败不同；
- G1、Parallel、CMS 遇到晋升失败时的退化路径不同，面试答到“collector-specific failure path”会显得很专业。

**收束句**

晋升失败本质上是 **collector 的对象移动协议失灵了**，而不只是“老年代快满了”。

## 7. 强/软/弱/虚引用的区别？

**标准答案**

- 强引用：只要强引用存在，对象就不会回收；
- 软引用：内存紧张时才清；
- 弱引用：下一次 GC 就可能清；
- 虚引用：`get()` 永远返回 null，用于对象真正结束生命周期后的通知。

**进程 / OS 视角**

从进程层看，这不是四种“指针类型”，而是 JVM 在 GC 阶段对同一个 `Reference` 对象采取不同处理策略。它们的差别体现在 ReferenceProcessor 的四阶段顺序上，而不是平时普通代码执行时有什么特别的存储形式。

**HotSpot 实现视角**

ReferenceProcessor 的四阶段是关键：

1. **Phase1**：软引用重新考虑，按 LRU 策略决定是否保留；
2. **Phase2**：软/弱/final 清理；
3. **Phase3**：final 复活；
4. **Phase4**：phantom 清理。

所以虚引用最关键的语义不是“死后通知”，而是：**它一定发生在 Finalizer 复活之后**，因此代表对象真正不可达且不可复活的最终阶段。软引用也不是“按存活时间决定”，而是按“上次访问到现在的间隔”来决定。

这里还要补一层经常被答错的边界：**ReferenceQueue 不是 GC，本身也不负责回收对象，它只是通知通道。** 真正负责发现、裁断和清除的是 `ReferenceProcessor` 的四阶段；而 `ReferenceHandler` / Finalizer 线程负责消费 pending/queue 上的引用对象。把 `ReferenceQueue` 说成“回收队列”不够准确——它更像“对象生命周期变化后的通知出站口”。

**演进边界**

- 很多人把 Finalizer 和 PhantomReference 混为一谈，这在生产里非常危险；
- SoftReference 的 LRU 策略受 heap 大小和 `SoftRefLRUPolicyMSPerMB` 影响，不是一个写死的秒数。

**收束句**

这题真正该答出来的是：**四种引用的区别，不在于定义，而在于它们在 ReferenceProcessor 阶段序列里的位置。**

## 8. 对象什么时候进入老年代？

**标准答案**

对象通常在年轻代多次存活后晋升到老年代；大对象可能直接进入老年代（或 G1 的 humongous 区域）。

**进程 / OS 视角**

从进程角度看，“进入老年代”不是一个抽象升级动作，而是对象在下一次 GC 搬迁时，从年轻代的地址范围被复制/移动到另一片更长期保留的地址范围。也就是说，它本质上是**内存位置的跨区迁移**，不是给对象打个标签。

**HotSpot 实现视角**

常见触发：

- **年龄阈值**：对象经历若干次 young GC 仍然存活，达到 `MaxTenuringThreshold`；
- **动态年龄判定**：如果某个年龄段对象总和已超过 Survivor 空间的一半，更年轻的对象也可能一起提早晋升；
- **大对象**：比如 G1 的 humongous 对象直接占用多个 Region，不走普通 Eden → Survivor → Old 的路线；
- **空间分配担保**：GC 前如果 JVM 估计 to-space 不够，会直接走更激进的回收或晋升策略。

这题真正要补的一刀是：**对象进入老年代，不只是“活得够久”这一条路。** 在压力场景下，collector 可能因为 Survivor 放不下、to-space 预算不足、空间分配担保失败，选择让对象提前晋升。也就是说，老年代不只是“长寿对象养老院”，它有时是 collector 在空间压力下做出的布局妥协区。这个补充一出来，答案就从教科书变成生产语义了。

**演进边界**

- “大对象直接进老年代”这种说法对不同 collector 不完全等价；在 G1 里更准确地说是进 humongous 区域；
- 对象年龄不是每次分配时决定的，而是在 GC 搬迁过程中更新。

**收束句**

对象进老年代，不是“长大了打标签”，而是 **某次 GC 里被判定该搬到更长期的内存区域。**

## 9. 为什么新生代要分 Eden / S0 / S1 三个区域？

**标准答案**

为了支持复制算法。Eden 放新对象，Survivor0 / Survivor1 轮流作为 from-space 和 to-space，在 young GC 时把存活对象复制过去。

**进程 / OS 视角**

如果只说“为了复制算法”，还是太抽象。更精确地说：新生代必须预留一块**完全空白的目标空间**，让 GC 把活对象搬进去。如果只有 Eden 和一个 Survivor，那么复制时目标区不够隔离，GC 无法保证“源区与目标区”语义清晰分开。

**HotSpot 实现视角**

每轮 young GC 前：

- Eden 和其中一个 Survivor 是源区（from-space）；
- 另一个 Survivor 完全空着，作为目标区（to-space）。

GC 完成后，两个 Survivor 交换角色。这个交换就是经典的“from/to flip”。存活对象在复制过程中顺便把年龄加 1，这样下一轮 GC 再决定是否继续留在 Survivor 还是晋升到 Old。

**演进边界**

- G1 里虽然不再是固定的连续 Eden/S0/S1 三块，但“预留 to-space 做复制”的思想仍然存在，只是落到了 Region 语义上；
- 所以面试时最好答成“年轻代复制协议为什么需要目标空间”，而不是拘泥在“S0/S1 就是两个小堆”。

**收束句**

Eden/S0/S1 的本质不是“三块内存”，而是 **为了让复制式年轻代回收始终保有一块干净的目标空间。**

## 10. 三种基础 GC 算法（标记-清除 / 复制 / 标记-整理）的适用场景？

**标准答案**

- **标记-清除**：标记存活对象后直接清理垃圾，优点是实现简单，缺点是碎片多；
- **复制**：把存活对象复制到新区域，优点是分配快、碎片少，缺点是浪费一半空间；
- **标记-整理**：标记后压缩存活对象，优点是无碎片，缺点是移动成本高。

**进程 / OS 视角**

从进程层看，三种算法本质上是在权衡：

- 是不是接受碎片；
- 是不是额外保留一块空白空间；
- 是不是在回收时付出移动对象的成本。

也就是说，这不是“教科书上三种图形”，而是**内存布局和分配成本的三种基本交易方式。**

**HotSpot 实现视角**

- CMS 典型地带着“标记-清除”的思路，所以碎片是核心代价；
- 新生代常用复制，因为大部分对象朝生夕死，复制活对象的成本远小于整理整个区域；
- Full GC 或某些老年代路径需要整理，因为长期碎片化会把分配成本推爆。

这也是为什么现代 collector 不会纯粹使用某一种算法，而是组合使用：年轻代偏复制，老年代在适当时候整理，并发 collector 在停顿和碎片之间再做 trade-off。

**演进边界**

- 面试里如果只答“哪种快哪种慢”会显得很浅；
- 真正加分的是指出：算法不是为了“分类而分类”，而是为了匹配对象生存期分布和暂停目标。

**收束句**

三种基础算法真正的区别，不在名字，而在于：**你把空间浪费、对象移动和碎片成本这三笔账，分配给了谁。**
