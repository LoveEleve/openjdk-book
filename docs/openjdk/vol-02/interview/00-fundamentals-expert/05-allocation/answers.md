# 05 · 对象分配、逃逸分析与运行时结构：专家级答案

## 1. 对象是怎么创建出来的？

**标准答案**

大多数对象创建会经历：申请内存、清零、写对象头、执行构造函数。

**进程 / OS 视角**

如果从进程视角回答，“对象创建”不是一条单一路径，而是一个**先尝试线程本地快路径、再退回共享分配、最后再考虑 GC** 的分层协议。也就是说，`new Object()` 通常不会一上来就去和整个 JVM 抢一把全局堆锁；它先在当前线程自己的分配缓冲里尝试 bump 一小段地址。

所以对象创建的真正第一问不是“分配了多少字节”，而是：**这次分配是在本线程局部完成的，还是已经升级成了全 JVM 共享路径？**

**HotSpot 实现视角**

HotSpot 里典型的创建链是：

1. **先试 TLAB**：当前线程的 `_top` 往前 bump，如果空间够，整条路径无锁完成；
2. **TLAB 不够 → 慢路径**：向堆申请新的 TLAB，或者直接走共享分配路径；
3. **大对象 / Humongous**：绕开普通 TLAB，直接走更重的路径；
4. **写对象头**：`mark word` 不是固定常量，而是从 `Klass::prototype_for_object` 复制 prototype header，`_metadata` 写 `Klass*` 或 `narrowKlass`；
5. **执行 `<init>`**：构造函数真正赋业务字段，直到 `invokespecial <init>` 完成，对 verifier 来说它都还不是“正常对象”。

所以 “对象创建” 在 HotSpot 里至少分成两段：**对象物理落位** 和 **对象语义完成**。

**演进边界**

- JDK 8 默认 Parallel，JDK 11 默认 G1，底层 collector 不同会让慢路径和老年代/Region 交互不同；
- `mark word` 是否带偏向锁 prototype 与版本有关，JDK 15 起默认禁用，JDK 18 移除实现。

**收束句**

对象创建真正考的不是“new 会调用构造器”，而是你能不能讲清：**对象什么时候只是“占到了一块地址”，什么时候才真正“成为一个 Java 对象”。**

## 2. 什么是 TLAB？为什么快？

**标准答案**

TLAB（Thread Local Allocation Buffer）是每个线程在堆里预留的一块私有分配区，线程在里面用 bump pointer 无锁分配对象，所以非常快。

**进程 / OS 视角**

从系统角度看，TLAB 的收益不是“少几条指令”，而是**把高频小对象分配从共享竞争问题，降成线程内部的指针推进问题**。你可以把它理解成 JVM 主动给每个线程分了一段“小型 Eden 切片”，线程自己在里面切对象，不用每次都去碰全局分配状态。

这就是为什么 TLAB 本质上不是“更大的栈”，也不是“把对象放到线程局部”。它只是**把对象在共享堆上的申请动作局部化**。

**HotSpot 实现视角**

TLAB 的快路径就是 bump `_top`。如果空间够，返回对象地址；如果不够，慢路径再决定：

- 申请新的 TLAB；
- 或直接走堆共享分配；
- 或在 collector 语义下触发更大范围的分配/GC 决策。

TLAB 的“快”来自两个方面：

1. 分配线程无锁；
2. 清零成本通常被摊进整块 TLAB 的准备阶段，而不是每个对象单独清零。

**演进边界**

- TLAB 是 collector 感知的：不同 collector 的 Eden/Region 语义会影响 TLAB 慢路径；
- 大对象、Humongous 对象和某些特殊分配不会走普通 TLAB；
- TLAB 太大浪费空间，太小频繁 refill，所以这不是“越大越好”。

**收束句**

TLAB 不是让对象“更靠近线程”，而是让**对象分配这个动作先在本线程内部消化掉。**

## 3. 什么是逃逸分析？

**标准答案**

逃逸分析（Escape Analysis, EA）分析对象引用会不会逃出当前方法、当前线程或当前作用域，以便做分配消除、锁消除等优化。

**进程 / OS 视角**

如果你从进程视角看，EA 真正减少的不是“对象有多大”，而是**对象有没有必要在进程堆里真实存在**。这和“放到栈上”是两回事。很多人把 EA 简化成“栈上分配”，这几乎是 JVM 面试里最常见的误答之一。

**HotSpot 实现视角**

HotSpot 里，EA 的关键是 `ConnectionGraph` 这类分析阶段；但分析本身只负责**证明**对象不会逃逸。真正把 `Allocate` 节点删掉的是后面的 `MacroExpand` / 优化收敛阶段。

所以应该把它分成两层：

- **EA 证明可消除**；
- **后续编译阶段真正删分配或删锁**。

这就是为什么说“C2 没有真正的栈上分配，只有分配消除”更准确。对象要么真实分配在堆上，要么根本不分配；不是说 C2 另辟了一块真正的“对象栈区”。

**演进边界**

- EA 是 C2 世界里的重要优化，不是解释器或普通 Java 语义；
- 一旦对象引用逃逸到字段、返回值、参数或线程外，EA 的收益就会急剧下降；
- EA 和内联强相关，内联不够时，EA 往往看不到完整的数据流。

**收束句**

逃逸分析真正考的是：**这个对象必须真实存在吗，还是只是编译器证明过程中的一个临时逻辑实体？**

## 4. OOM 有几种？

**标准答案**

常见的 OOM 至少有：Java heap space、Metaspace、Direct buffer memory，还有更广义上的 unable to create new native thread 等。

**进程 / OS 视角**

从进程角度看，“OOM”不是一种病，而是一组完全不同来源的资源枯竭：

- 堆 OOM：Java 对象放不下；
- Metaspace OOM：类元数据的 native memory 放不下；
- Direct Buffer OOM：堆外直接内存放不下；
- Native Thread OOM：进程再也创建不出新的 pthread / 栈空间。

如果你不先区分是哪一层内存资源枯竭，后面的调参和排查基本都会走歪。

**HotSpot 实现视角**

- **Java heap OOM**：通常在一次分配失败后，先尝试 GC；GC 后仍不够才抛 `OutOfMemoryError: Java heap space`；
- **Metaspace OOM**：`Metaspace::allocate()` 失败后会先借一次 GC/safepoint 尝试 class unloading，再决定是否抛错；
- **Direct buffer OOM**：本质是 native memory 分配失败，和 Java heap 大小不是同一个池；
- **unable to create new native thread**：线程数/栈空间/系统限制耗尽，是进程级资源问题，不是 GC 能救的那种 OOM。

**演进边界**

- JDK 8 之后 `PermGen` 消失，别再把 Metaspace OOM 说成“方法区在堆里满了”；
- OOM 前经常已有一次 GC 尝试，所以“为什么 Full GC 后还 OOM”本来就是正常现象；
- 容器环境里很多 OOM 不只是 `-Xmx` 太小，而是 cgroup 限制和 native 内存共同作用。

**收束句**

OOM 真正考的不是“你会背哪几种报错”，而是**你能不能先分清 JVM 到底是哪一层资源先枯竭了。**

## 5. 什么是 `allocateInstance`？

**标准答案**

`Unsafe.allocateInstance` 会分配一个对象实例，但不会执行构造函数。

**进程 / OS 视角**

从进程和运行时角度看，它做的是：**只完成对象的物理落位，不完成对象的语义初始化**。这就意味着：

- 对象头已经存在；
- Klass 已经写好；
- 但字段不会经过构造函数和实例初始化器赋值；
- 你拿到的是一个“存在于堆上、但业务语义未完成”的对象。

这也是为什么它非常危险——它绕开了 Java 语言层最重要的对象构造协议。

**HotSpot 实现视角**

HotSpot 角度看，它本质上还是在堆上分配对象，只是跳过了 `<init>`。也就是说，verifier 不会阻止它，因为 verifier 管的是字节码对 `new`/`<init>` 的合法性，不管 Unsafe 直接走 VM 内部后门。这个对象随后如果直接被业务代码使用，就可能落入“字段默认值仍然保留、对象不满足类的不变量”的危险状态。

反序列化、框架代理和某些底层库会用这条路，但这是内部能力，不是普通对象创建协议。

**演进边界**

- JDK 9+ 强封装之后，`Unsafe` 获取路径受模块影响更大；
- `allocateInstance` 能分配抽象语义上“不该直接 new”的对象，但不代表这些对象已经可安全使用。

**收束句**

`allocateInstance` 真正危险的不是“它能分配对象”，而是它让**对象存在**和**对象完成构造**这两件事彻底脱钩了。**

## 6. 什么是热点代码？JIT 怎么判定？

**标准答案**

热点代码是被频繁执行的方法或循环。HotSpot 通过方法调用计数器和回边计数器判断热点，再决定是否提交给编译器。

**进程 / OS 视角**

从进程视角看，JIT 不是“你调用几次就立刻编译”，而是在解释执行阶段一边运行、一边统计“这段代码值不值得把 CPU 时间花在编译上”。所以热点判定本质上是一个**预算问题**：现在花 CPU 去编译，未来能省下多少解释执行开销。

**HotSpot 实现视角**

HotSpot 至少看两类热度：

- **方法调用计数器**：方法被调用了多少次；
- **回边计数器**：循环回边执行了多少次。

前者回答“这个方法整体热不热”，后者回答“这个循环值不值得尽快编译”。达到阈值后，请求通过 `CompileBroker` 进入 C1/C2（或 JVMCI）编译链。分层编译下，不同级别和不同路径的阈值又不同，所以“CompileThreshold 达到就编译”只是粗口语，不是完整事实。

**演进边界**

- JDK 8 与 JDK 11 的默认 collector 变化不会改变热点判定本质，但会影响编译和 GC 的竞争关系；
- `-Xcomp` / `-Xint` / `-XX:-TieredCompilation` 都会极大改变热点判定和编译行为。

**收束句**

热点代码不是“跑得多就一定编译”，而是**JVM 判断：这段代码的未来收益值得现在为它支付编译成本。**

## 7. 什么是方法内联？为什么对性能影响大？

**标准答案**

方法内联是编译器把被调用方法的代码直接展开到调用者里，消掉一次调用开销，并让后续优化看到更大的上下文。

**进程 / OS 视角**

从机器角度看，方法调用的成本不只是一次 jump/call，还包括：

- 建立/拆除栈帧；
- 传参；
- 保留调用边界导致的优化屏障；
- 返回值装配。

一旦内联，这些边界很多都消失了，更重要的是：编译器突然能看到“跨方法”的常量、类型和逃逸关系。

**HotSpot 实现视角**

在 HotSpot/C2 里，内联不是孤立优化，而是很多高级优化的前提：

- 逃逸分析通常依赖内联后才能看见完整对象流；
- 常量折叠和分支消除在跨方法边界后会更激进；
- 一些 intrinsic 本质上也是更激进的“语义接管式内联”。

所以 “内联能省调用开销” 只是最浅的一层。真正的收益是：**它把原本被方法边界遮住的信息重新暴露给优化器。**

**演进边界**

- 过度内联会让代码膨胀、CodeCache 压力上升，所以不是“越多越好”；
- `-XX:MaxInlineSize`、`FreqInlineSize` 等 flag 只是表面参数，真正的内联决策还会看热度、大小、递归深度和编译预算。

**收束句**

方法内联真正的威力不在“少了一次调用”，而在**你拆掉了一道优化器原本看不穿的边界。**
