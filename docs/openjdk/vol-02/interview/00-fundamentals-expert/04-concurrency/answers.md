# 04 · 线程、锁与并发：专家级答案

## 1. `synchronized` 和 `volatile` 的区别？

**标准答案**

`volatile` 解决的是可见性和禁止特定重排，不保证复合操作原子性；`synchronized` 既提供互斥，也提供进入/退出临界区时的内存语义。

**进程 / OS 视角**

从 CPU 和缓存一致性角度看，这两者根本不是同一类工具：

- `volatile` 更像“让这个内存位置的读写按约定被别的核心看见”；
- `synchronized` 更像“先拿到进入临界区的资格，再在退出时把这段临界区里的写发布出去”。

也就是说，一个解决的是**单一共享位置的可见性和顺序**，一个解决的是**一段代码块的互斥和发布**。

**HotSpot 实现视角**

- `volatile` 在 HotSpot 里通过 `OrderAccess` / `Access API` 落地。x86 TSO 已保证 `loadload`/`storestore`/`loadstore`，所以最贵的是 `storeload`，在 x86 上通常用 `lock addl $0,0(%rsp)` 实现。
- `synchronized` 走 `monitorenter/monitorexit` 语义，轻量锁时对象头 mark word 改成指向栈上 `BasicLock` 的 tagged pointer；竞争加剧后 `inflate` 成 `ObjectMonitor`，monitor 的 owner/entry list/wait set 负责阻塞与唤醒。

这就是为什么 `volatile` 不能替代 `synchronized`：它不会建立互斥，也不会保护复合动作（比如检查再修改）。

这里要专门纠正一句面试里最常见的烂话：**“volatile 更轻，所以能用 volatile 就别用 synchronized。”** 这是把“性能偏好”放在了“语义正确性”前面。真正的顺序应该是：先判断语义够不够，再谈成本。如果一个场景需要互斥、需要把多步操作捆成事务，那 `volatile` 再便宜也不能用；只有在“单一共享位置的可见性和顺序”已经足够时，才谈得上用 `volatile` 替代锁。

**演进边界**

- JDK 15 起偏向锁默认禁用，JDK 18 移除实现，所以现在答 `synchronized` 时不该再把“偏向锁命中”当作默认前提；
- `volatile` 的语义由 JMM 定义，但具体屏障成本随架构不同而不同，x86 比 ARM 更“便宜”。

**收束句**

这题真正考的不是“一个有锁一个没锁”，而是**一个控制共享位置的可见性，一个控制临界区的所有权。**

## 2. 什么是死锁？如何检测？

**标准答案**

死锁是多个线程互相等待对方持有的资源，形成 wait-for graph 的环，导致谁也无法继续执行。

**进程 / OS 视角**

从线程系统看，死锁不是“线程卡住了”这么简单，而是系统已经进入一个**没有外力就无法前进的等待拓扑**。如果只是某个线程一直拿不到锁，那可能是饥饿；如果图里有环，才是死锁。

**HotSpot 实现视角**

HotSpot 检测死锁的方法，本质上就是构造 wait-for graph：

- 线程 A 当前在等哪个 monitor；
- 这个 monitor 的 owner 是哪个线程；
- 再看 owner 在等谁；
- 如果最后回到 A，自环闭合，就检测到死锁。

`jstack` 最后那段 `Found one Java-level deadlock` 和 `ThreadMXBean.findDeadlockedThreads()` 依赖的都是这条思路。真正的难点不在“怎么印出来”，而在 `ObjectMonitor` 的 owner / entry / wait set 语义要分清，否则图就画错了。

这里再补一刀非常关键：**死锁检测不是内核替 JVM 做的，而是 JVM 自己根据 monitor owner / waiting thread 关系拼出来的。** 操作系统只知道线程阻塞在某个 futex 或 park 点上，不知道哪把 Java monitor 归谁持有；“Java 级死锁”是 HotSpot 在对象监视器语义之上额外恢复出来的那张等待图。

**演进边界**

- `wait()` 会释放 owner，所以“线程在 WAITING”不一定是死锁；
- `notify()` 不是直接把 owner 交出去，只是把线程从 wait set 放回竞争路径，所以“被唤醒”也不等于“立刻继续执行”。

**收束句**

死锁的本质不是“都卡住”，而是**等待关系已经形成闭环。**

## 3. 什么是内存屏障？JMM 为什么需要？

**标准答案**

内存屏障是限制编译器和 CPU 对内存访问重排的机制。JMM 通过这些屏障实现 happens-before 语义。

**进程 / OS 视角**

对一个多核进程来说，线程并不是“立即共享同一份现实”。每个核心有自己的缓存、store buffer 和执行顺序优化。如果不加约束，一个线程完成的写，另一个线程未必立刻按你以为的顺序看到。

所以内存屏障不是“JVM 的奇怪发明”，而是 JVM 为了让 Java 的并发语义在真实硬件上成立，不得不付出的约束成本。

**HotSpot 实现视角**

HotSpot 把屏障抽象成 `OrderAccess` 四个操作：`loadload`、`storestore`、`loadstore`、`storeload`。在 x86 上前三者通常只是 `compiler_barrier()`，只有 `storeload` 需要真正的硬件屏障；在弱一致性平台上，acquire/release 需要显式 `dmb`/`ldar`/`stlr` 一类指令。

因此，JMM 不是“运行时检查图”，而是通过在正确位置插入正确的屏障，让 happens-before 在实现上自然成立。

**演进边界**

- 不同 CPU 架构的硬件模型不同，JMM 选择的是跨平台都能满足的最小契约，不是 x86 专用模型；
- 面试时如果你把“volatile = 加个内存屏障”讲成一句话，通常还是太浅，因为真正的成本只在某些顺序上才成立。

**收束句**

内存屏障本质上是**把语言级别的可见性承诺，翻译成 CPU 愿意遵守的执行顺序。**

## 4. 偏向锁的版本变化？

**标准答案**

偏向锁在 JDK 8 默认开启；JDK 15 起默认禁用；JDK 18 完全移除实现。

**进程 / OS 视角**

偏向锁的收益只在一个条件下成立：同一个锁长期只被同一个线程获取。如果线程竞争很少，这能避免每次都做原子 CAS；如果竞争频繁，撤销和 rebias 的代价反而会让它变成负资产。

**HotSpot 实现视角**

偏向锁通过对象头里的 mark word 记录“当前偏向哪个线程”，同线程再次进入时不用 CAS；只有其他线程来抢时才撤销/重偏向。这个设计对低竞争场景很划算，但随着现代硬件和工作负载变化，它的收益越来越不稳定，所以 JDK 15 默认禁用，JDK 18 彻底移除。

还要纠正一个很容易讲错的点：**偏向锁不是“更轻一点的轻量锁”。** 它和轻量锁不是同一个成本模型上的前后两档，而是两个不同的竞争假设：

- 偏向锁假设“几乎总是同一个线程来”，所以连 CAS 都不想做；
- 轻量锁假设“可能会有别的线程来，但阻塞还不值得”，所以用一次 CAS 抢占栈上 displaced mark。

一旦竞争成立，偏向锁要做的不是“再轻量一点升级”，而是先撤销“这个锁归某个线程长期独占”的假设，然后才退回轻量/重量路径。

**演进边界**

- 如果你用 JDK 8 的经验回答 JDK 17/21 面试，直接把偏向锁当默认路径，会暴露版本感知不足；
- 面试里最加分的说法是：偏向锁的变化不是“某个优化没了”，而是 HotSpot 对现代负载下收益/复杂度权衡的重新判断。

**收束句**

偏向锁的演化史，本质上是在说明：**JVM 的锁实现不是教条，而是在版本里不断重算收益与复杂度。**

## 5. 什么是 CAS？ABA 问题？

**标准答案**

CAS（Compare-And-Swap）是“比较并交换”的原子操作。ABA 问题指一个值从 A 变成 B 又回到 A，CAS 只看到“还是 A”，却看不到中间发生过变化。

**进程 / OS 视角**

在多核机器上，CAS 不是“比较再赋值”的语法糖，而是一次带缓存一致性成本的原子事务。x86 上的 `lock cmpxchg` 会让对应 cache line 的其他副本失效，这才是它真正贵的地方——不是那条指令长什么样，而是所有其他核心都要配合。

**HotSpot 实现视角**

HotSpot 的 `Atomic::cmpxchg` 最终在 x86 上落到 `lock cmpxchg`。这条指令天然提供足够强的内存序，所以基于 CAS 的很多路径（对象头竞争、某些并发数据结构）同时拿到了原子性和可见性。

ABA 问题的本质不是“CAS 坏了”，而是“你只比较了值，没有比较历史”。Java 层通常用 `AtomicStampedReference` 或 `AtomicMarkableReference` 补充版本戳；VM 里则更常见的是把状态位、计数器、epoch、指针一起编码进同一个机器字。

**演进边界**

- x86 上的 CAS 成本和语义，与 ARM 上的 LL/SC 并不一样；
- `volatile` 不能替代 CAS，因为它没有“比较后更新”的条件性。

**收束句**

CAS 真正的价值不是“无锁”，而是**把共享状态更新变成一个可原子判定、可失败重试的事务。**

## 6. 锁升级过程（无锁→偏向→轻量→重量）？

**标准答案**

对象锁大致会经历：无锁、偏向锁、轻量锁、重量锁。竞争加剧时，状态逐步升级。

**进程 / OS 视角**

从进程层看，这其实是在回答一个问题：**同一个 monitor，当前用哪个代价模型最划算？**

- 完全没人竞争时，最好什么都不做；
- 总是同一线程进入时，最好记住“这个锁基本上归我”；
- 偶发竞争时，最好只付一次 CAS；
- 真正出现阻塞/等待时，才值得建立完整的 monitor 状态机。

**HotSpot 实现视角**

对象头 mark word 是状态机的载体：

- **无锁**：mark word 处于 neutral / biasable 原型状态；
- **偏向**：mark word 记录偏向线程；
- **轻量**：对象头改成指向栈上 `BasicLock` 的指针，原 mark 存 displaced header；
- **重量**：`inflate` 成 `ObjectMonitor`，对象头改成 monitor 指针。

中间还有一个容易漏掉的临时状态：`INFLATING`（通常是 0），表示某个线程正在膨胀 monitor。这个状态的存在说明“升级”不是瞬间跳变，而是一条带并发保护的过渡路径。

**演进边界**

- 偏向锁在新版本里已退出默认/实现主线，但无锁→轻量→重量这条路径仍成立；
- 有些资料把“锁升级”讲成绝对单向链，这太粗。现实里对象可能长时间停在轻量或重量路径，也可能不经过偏向阶段。

**收束句**

锁升级本质上不是四个名词，而是**JVM 在不同竞争强度下切换不同成本模型。**

## 7. 什么是 ThreadLocal？为什么可能内存泄漏？

**标准答案**

`ThreadLocal` 给每个线程一份独立变量副本。它可能泄漏，是因为 `ThreadLocalMap` 的 key 是弱引用，而 value 仍是强引用，线程不退出时 value 可能长期残留。

**进程 / OS 视角**

从进程角度看，ThreadLocal 泄漏的根源不是“对象没人回收”，而是**线程本身还活着**。线程不死，`ThreadLocalMap` 就一直跟着线程对象存在；key 弱引用断了，但 value 还在那张表里。线程池场景下，这就特别危险，因为 worker 线程寿命极长。

**HotSpot / JDK 实现视角**

`ThreadLocalMap.Entry` 是 `WeakReference<ThreadLocal<?>>`，这意味着 key 可以被 GC 清掉，但 value 不会自动跟着走。只有在后续对这张 map 的访问过程中，JDK 才会顺手清理 stale entry。没有访问、线程又长时间不退出时，value 就会留在那里。

所以这题真正要答的不是“弱引用导致泄漏”，而是：**弱的是 key，不是 value；真正的 owner 是长寿线程。**

**演进边界**

- 在线程池里不调用 `remove()` 是经典坑；
- 把 ThreadLocal 用作“请求上下文”却不清理，最容易在容器线程池里堆积脏值。

**收束句**

ThreadLocal 泄漏的本质不是 GC 失效，而是**长寿线程替你把那张脏表一直保着。**

## 8. 线程池的核心参数有哪些？

**标准答案**

`ThreadPoolExecutor` 的核心参数包括：`corePoolSize`、`maximumPoolSize`、`keepAliveTime`、`workQueue`、`threadFactory`、`RejectedExecutionHandler`。

**进程 / OS 视角**

这几个参数本质上在回答三个问题：

1. 多大规模以内直接开线程？
2. 超过以后是排队还是继续扩线程？
3. 两者都撑不住了怎么办？

也就是说，线程池不是“线程数量配置器”，而是一个**任务接纳与背压策略器**。

**HotSpot / JDK 实现视角**

- `corePoolSize` 决定常驻 worker 数；
- `workQueue` 决定你是更偏向“排队等待”还是“继续扩线程”；
- `maximumPoolSize` 决定在队列撑满之前最多还能新建多少线程；
- `RejectedExecutionHandler` 是最终背压出口，不是异常小细节。

在 JVM 角度看，线程池参数直接映射到：线程数量、栈数量、上下文切换压力、锁竞争和队列长度，所以不是“业务层配置题”，而是会反馈到 HotSpot 线程与内存行为的。

如果你想把这题答得更像工程师，而不是业务开发，最好再补一句进程视角：**每多一条线程，进程里就多一根 pthread 栈、多一组栈守卫页、多一份 `ThreadLocalMap`/TLS 状态、一个调度实体以及更多上下文切换机会。** 所以线程池参数不是简单的“并发度开关”，它们最终会变成真实的内存占用、调度压力和锁竞争成本。

**演进边界**

- `LinkedBlockingQueue` 常让 `maximumPoolSize` 形同虚设，因为队列几乎永远先吸收任务；
- `CallerRunsPolicy` 不是“更温柔的拒绝”，而是一种把背压反推给调用线程的策略。

**收束句**

线程池参数真正控制的，不是“线程数”，而是**任务在系统压力上升时先扩线程、先排队，还是先拒绝。**

## 9. volatile 能保证原子性吗？

**标准答案**

不能。`volatile` 只能保证单次读写的可见性和特定重排约束，不能保证复合操作原子性，比如 `i++` 仍然不是线程安全的。

**进程 / OS 视角**

从 CPU 角度看，`i++` 至少包含三步：**load → add → store**。`volatile` 只保证这个内存位置的读写按语义对别的核心可见，不会把这三步捆成一个事务。

**HotSpot 实现视角**

HotSpot 对 `volatile` 的处理是插屏障，不是插锁。它不会把 `i++` 自动改写成 `lock xadd` 或 `cmpxchg` 重试循环。所以 `volatile` 变量上的复合更新，如果没有更高层同步，仍然会丢失更新。

真正能保证原子更新的是：

- `synchronized`
- CAS / 原子类（`AtomicInteger.incrementAndGet()`）
- 更高级的锁或并发容器协议

**演进边界**

- 很多初学者因为“volatile 可见性”误以为“看见最新值就不会写丢”，这是两回事；
- x86 上 volatile 已经比 ARM 便宜，但再便宜也不会自动变成原子事务。

**收束句**

volatile 解决的是**看见什么和什么时候看见**，不是**这次更新能不能独占完成**。

## 10. happens-before 规则有哪些？

**标准答案**

JMM 里的典型 happens-before 规则包括：

- 程序次序规则（同一线程内前面的操作先行发生于后面的操作）
- 监视器锁规则（解锁先行发生于后续加锁）
- volatile 变量规则（写先行发生于后续读）
- 线程启动规则（`start()` 先行发生于被启动线程中的动作）
- 线程终止规则（线程中的所有动作先行发生于其他线程检测到其终止）
- 传递性

**进程 / OS 视角**

happens-before 不是运行时的一张“可查询关系图”，而是一套**让不同线程看到一致结果的证明规则**。也就是说，它回答的是“这次读为什么必须能看到那次写”，而不是“JVM 运行时怎么去查这条边”。

**HotSpot 实现视角**

HotSpot 并不在运行时维护一个 happens-before 图，而是通过：

- `volatile` 屏障
- monitor acquire/release 语义
- 线程状态转换（`start()` / `join()` / 终止）
- `final` 字段构造期屏障

让这些规则在实现上自然成立。

所以这题如果答成“happens-before 有几条规则”，仍然太浅。更好的答法是：**JMM 用规则描述结果，HotSpot 用屏障和协议去兑现这些结果。**

**演进边界**

- 规则本身不太变，但不同架构上兑现它们的成本变化很大；
- 虚拟线程引入后，线程调度方式变了，但 happens-before 的语言级语义不变。

**收束句**

happens-before 真正考的不是你能不能背六条，而是你知不知道：**JMM 是证明规则，HotSpot 用屏障和状态协议把它变成现实。**
