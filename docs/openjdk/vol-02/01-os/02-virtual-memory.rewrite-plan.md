# 02-virtual-memory 重写规划

> 状态：重写前大纲
> 适用规范：`docs/openjdk/WRITING-GUIDELINES.md`
> 目标：把“虚拟内存、大页面、栈保护”重构成一篇围绕地址空间生命周期与失败安全的机制文

## 1. 选题判断

本篇值得独立成篇，但不能继续写成三个并列专题：

- reserve/commit/uncommit/release
- 大页面
- 栈保护

更好的统一问题是：

**JVM 如何把一块地址空间变成可管理的运行时内存：需要时兑现物理页，不需要时撤回物理页，访问越界时快速失败，性能敏感路径上再用大页面减少地址翻译成本？**

这样三块内容就不再是“虚拟内存 + 两个附录”，而是同一套设计哲学的三个应用：

- 地址空间和物理页分离
- 资源生命周期可逆
- 错误尽早暴露
- 性能优化必须服从生命周期边界

## 2. 读者困惑

`-Xmx16g` 明明比机器的 8GB 物理内存还大，为什么 JVM 可以先启动？

启动以后，JVM 又怎么保证：

- 没有真正用到的页不占物理内存
- 回收后的页能还给 OS，但地址空间不被破坏
- 新提交的内存访问不会踩进未提交区域
- 栈无限增长时能抛出 `StackOverflowError`，而不是直接把整个进程打崩
- 大页面的性能收益不会反过来破坏 GC 的 region 边界

## 3. 一句话顿悟

**JVM 把“地址空间的占有”和“物理内存的兑现”拆成了可逆生命周期：先 reserve 地址，再按需 commit，回收时 uncommit，彻底结束才 release；所有优化和保护机制都围绕这条生命周期展开。**

## 4. 版本边界

正文开头必须明确：

- 基于 `OpenJDK 11u / HotSpot / Linux / x86_64`
- `mmap`、`mprotect`、`madvise`、hugetlbfs、System V SHM 等实现是 Linux 端实现
- `reserve/commit` 是 HotSpot 内部抽象，不等于操作系统规范中一个统一的四态 API
- uncommit 的具体实现随 JDK 更新版本和平台变化，本文只讨论当前源码对应实现
- 页大小、大页面行为、THP 行为与 Linux 内核配置有关

## 5. 旧稿主要问题

### 5.1 已有优点

- reserve/commit/uncommit/release 的核心事实完整
- `PROT_NONE`、`MAP_NORESERVE`、`MAP_FIXED` 等关键参数有源码
- 能解释 `-Xmx16g` 与 RSS/VSZ 的差异
- 大页面和栈保护都有具体实现细节

### 5.2 必须修复的问题

- 旧稿把四态生命周期、大页面、栈保护切成并列说明，统一设计主线不够强
- “commit 真正分配物理页”说法过满，需要区分建立可访问映射、记账、按需 fault 和实际物理页兑现
- `PROT_NONE` 的安全语义与 SIGSEGV 之间没有形成完整因果链
- `mmap(MAP_FIXED)` 的前置条件和风险需要更具体地推演
- uncommit 与 release 的差异需要用“地址空间是否保留”重新收束
- 大页面数字和 TLB miss 率属于硬件/工作负载相关事实，不能写成普遍固定值
- 栈保护部分“递归 10 万次”标题过于绝对，必须改成边界条件下的保护机制叙事
- 栈保护区应明确“保护区如何被触发、信号如何进入异常处理、何时不可恢复”，并与下一篇信号篇建立边界
- 需要补充至少三组失败方案推演

## 6. 结构大纲（按理解路径）

### 第一节：事故开场——为什么 16GB 堆能在 8GB 机器上启动

目标：从 VSZ/RSS 反直觉现象引出“地址空间不是物理内存”。

必须讲清：

- VSZ 与 RSS 分别表示什么
- `-Xmx` 更接近地址空间上限，不等于启动时立刻占满物理内存
- 如果 JVM 直接要求 16GB 物理页，会发生什么
- 本篇要解决的不只是“虚拟内存是什么”，而是 JVM 如何管理生命周期

预估字数：1000-1200

### 第二节：先建立四态总图——地址空间和物理页为什么必须拆开

目标：先给全篇心智模型，再进入系统调用。

文字图：

```text
reserve   → 地址范围归 JVM 所有，但暂不可访问
commit    → 让指定范围变得可访问，物理页按需兑现
uncommit  → 撤回物理页/可访问权限，地址范围继续保留
release   → 地址范围也归还给 OS
```

必须回答：

- 为什么不能一次 malloc 到底
- 为什么 GC、Metaspace、CodeCache 都需要这个抽象
- 四态分别由谁触发、失败会怎样

预估字数：900-1100

### 第三节：reserve——JVM 为什么先圈地，再让页面不可访问

目标：完整讲 `anon_mmap` 的动机和安全边界。

子层次：

- `MAP_PRIVATE | MAP_ANONYMOUS | MAP_NORESERVE` 各自解决什么问题
- `PROT_NONE` 为什么比“可读写但没有物理页”更安全
- reserve 成功不等于未来 commit 一定成功
- overcommit 策略如何影响 reserve
- 失败方案：直接 malloc、直接可读写 mmap、依赖 brk

预估字数：1700-2000

### 第四节：commit——同一块地址为什么要再次 mmap

目标：讲清 `MAP_FIXED`、权限变化、按需 fault 的完整链路。

子层次：

- 为什么 commit 必须回到已经 reserve 的地址
- `MAP_FIXED` 为什么危险，HotSpot 为什么敢用
- “可访问映射建立”与“物理页实际兑现”不能混为一谈
- 第一次访问触发 page fault 的时序
- pretouch 为什么把 fault 成本从运行期搬到启动/扩容期
- 失败方案：malloc 不保证连续地址、brk 无法独立管理多个区域

预估字数：1900-2200

### 第五节：uncommit 与 release——回收时到底还什么

目标：用生命周期反转讲清两个动作的边界。

必须明确：

- uncommit：物理页/访问权限撤回，地址空间保留
- release：地址空间本身撤回
- 为什么 GC 需要大量 uncommit，而不是每次都 release
- 为什么保留地址空间有利于 region、指针、元数据布局稳定
- 当前 Linux 实现为什么用 `PROT_NONE + MAP_FIXED` 重映射
- 与 `madvise(MADV_DONTNEED)` 的语义/实现边界

预估字数：1500-1800

### 第六节：大页面——性能优化为什么会和 GC 边界发生冲突

目标：把大页面从“性能技巧”提升为“地址翻译层的权衡”。

子层次：

- TLB 缓存什么，页越大为什么能减少翻译压力
- 4KB / 2MB 页的数量级示例，但明确数字依赖硬件和工作负载
- hugetlbfs、SHM、THP 三种路径的约束差异
- THP 为什么可能跨越 G1 region 边界
- 大页面收益如何被拆页、TLB shootdown、回收边界抵消
- 失败方案：无条件启用大页面、把 THP 当作固定收益

预估字数：1800-2200

### 第七节：栈保护——同一个生命周期如何变成“失败时还能报错”

目标：把栈保护从孤立的 zone 表格改成“错误处理的预留空间”。

子层次：

- 栈向下增长与保护区位置
- Yellow / Red / Reserved / Shadow 各自防什么
- `mprotect(PROT_NONE)` 如何把越界变成 SIGSEGV
- Yellow 为什么可以恢复，Red 为什么不可恢复
- Reserved/Shadow 为什么是“为了处理失败本身而预留的空间”
- 与下一篇信号处理篇的边界：本篇讲保护区和触发条件，下一篇讲信号分发
- 失败方案：只设一个 guard page、没有异常处理余量、把所有越界都当成可恢复

预估字数：1900-2200

### 第八节：收网——同一套思想贯穿地址、页、性能和失败

必须收束为四句话：

- reserve/commit 把地址空间和物理兑现分离
- uncommit/release 把回收拆成“撤页”和“退地址”
- 大页面是对地址翻译成本的优化，但必须尊重 GC 的管理边界
- 栈保护是对失败路径的预留，本质仍是“先划边界，再按状态处理”

预估字数：700-900

## 7. 必须展开的失败方案

1. 直接 `malloc(16GB)`：物理承诺、连续性、多个区域独立回收都不满足
2. reserve 后使用可读写权限：未 commit 区域可能被错误访问，失败不再快速暴露
3. 只用 `madvise` 释放页面且不恢复权限：生命周期语义不完整，后续误访问边界不清
4. 无条件启用 THP：大页面可能跨越 G1 region，回收时触发拆页和额外开销
5. 栈只设置一个保护页：异常构造、信号处理本身没有安全余量

## 8. 必须澄清的误解

1. reserve 成功不等于物理内存已经分配
2. commit 成功不等于所有物理页都已经实际驻留
3. VSZ 大不等于 RSS 已经同样大
4. uncommit 不等于 release
5. 大页面不是越大越好，收益与内核、硬件、访问模式和 GC 边界相关
6. StackOverflowError 不是任何栈越界都能保证抛出
7. `PROT_NONE` 触发的 SIGSEGV 需要由 JVM 的信号处理链解释，不能简单等同于进程崩溃
