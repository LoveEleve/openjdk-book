## 现在真正该问的，不再是“框架支不支持分布式事务”，而是“事务边界到底有没有真的穿过代理、线程、连接、协调器和补偿链”

前两篇已经把理论路线讲清了：

- 2PC/XA 把多个 RM 绑进一个全局协调；
- TCC 把锁等待改写成业务预留、确认、取消；
- Saga、Outbox、事务消息和最大努力通知把失败显式变成状态、重试和补偿。

可一旦你真把这些方案接进工程，最常见的问题并不是“概念不会背”，而是：

- `@Transactional` 明明写了，异常却没回滚；
- XA 已经 `PREPARE` 了，恢复后没人处理；
- Seata AT 看起来零侵入，结果 undo/log 和全局锁把数据库拖慢；
- TCC 三套接口都写了，但补偿顺序、空回滚和悬挂场景根本没测；
- 框架功能清单里说“支持”，但真正一故障，日志、状态表、线程上下文和恢复任务全部露底。

所以实战真正的主线不是“框架有没有”，而是：**调用有没有经过正确的代理边界、分支资源有没有真的注册、协调器和本地资源的状态有没有被一致地记录、异常路径有没有可重放和可补偿的证据。**

先把总图记住：

```text
数据库层:
  XA START / END / PREPARE / COMMIT / ROLLBACK / RECOVER

Spring 本地事务:
  AOP proxy
  → TransactionInterceptor
  → TransactionSynchronizationManager(ThreadLocal)
  → commit / rollback / cleanup

Seata:
  TM / TC / RM
  → AT / TCC / Saga / XA

Hmily / ShardingSphere:
  TCC 元数据 / 恢复日志
  或 分片路由 + XA 协调

实战验证:
  调用是否经过代理
  → 分支资源是否注册
  → 故障注入
  → 检查日志、undo、消息、最终账务
```

这篇最该先记住的一句话是：**分布式事务框架不是“一行注解获得全局原子性”，而是本地代理/线程上下文、RM/TM 状态、日志/锁和重试恢复共同组成的运行时系统。**

## 一、MySQL XA：数据库层的两阶段状态机

### 1. 最朴素的错误世界：数据库既然支持 XA，跨库事务就天然安全了

这个误解很常见，因为 XA 确实提供了正式的事务接口：

- `XA START`；
- `XA END`；
- `XA PREPARE`；
- `XA COMMIT/ROLLBACK`；
- `XA RECOVER`。

于是很多人自然会觉得：

“既然数据库都支持这一套，那跨库事务应该已经算解决了。”

问题在于，XA 只是把本地资源管理器的协调接口标准化，并没有自动替你解决：

- 协调者状态持久化；
- 应用超时与重试语义；
- 全局事务对账；
- 悬挂的 prepared 分支清理；
- 业务幂等和人工恢复流程。

### 2. XA 的最小数据库接口图

```text
XA START xid
  → 执行 INSERT/UPDATE
XA END xid
  → 结束分支工作
XA PREPARE xid
  → 资源管理器持久化 prepared 状态
XA COMMIT xid / XA ROLLBACK xid
  → 协调者最终决策

协调者恢复:
  XA RECOVER
  → 列出遗留 prepared xid
  → 根据外部事务状态逐一决策
```

这里最重要的边界是：`PREPARE` 不等于“几乎提交成功”，它只是让 RM 把自己推进到一个不能擅自反悔、但又还没完成全局最终决定的中间状态。

### 3. 为什么 `XA RECOVER` 是生产必需而不是调试命令

假设：

- XA 分支已经 `PREPARE`；
- 协调者在第二阶段前崩了；
- RM 保留锁和 prepared 状态；
- 应用恢复后业务继续跑，但 prepared xid 还挂着。

此时如果没有恢复流程：

- 锁会继续占着；
- 资源会继续冻结；
- 运维不知道这笔全局事务到底应该 commit 还是 rollback。

所以 `XA RECOVER` 的角色，不是“给 DBA 看看状态”，而是把遗留 prepared 分支纳回恢复闭环。这里还要钉死一个边界：`XA RECOVER` 只能告诉你 RM 侧还有哪些 `prepared xid` 留着，它不能单独判定全局事务最终应该 commit 还是 rollback；真正的决定证据仍然来自 TM 的持久化状态、外部协调日志或人工对账结果。

### 4. 一个更具体的失败场景：`PREPARED` 事务挂住，业务看到的不是事务失败，而是莫名其妙的资源长期占用

假设：

- 订单库和库存库都进入 `PREPARED`；
- 协调者状态损坏或不可达；
- RM 侧没人继续推动决定；
- 结果业务侧只看到锁等待、库存占用、订单状态悬空。

这时你会发现：框架层“支持 XA”并不等于系统层“有恢复能力”。真正让人出事故的，往往是 prepared 分支与协调器日志分离后的悬空状态。

### 5. 本节最该记住的结论：MySQL XA 提供的是数据库级两阶段状态机接口，不是业务级全局正确性的自动证明；`PREPARE` 只是中间态，`RECOVER` 和全局决策持久化才是生产闭环

一句最短人话是：**XA 像银行分行提供统一的“预冻结/确认/撤销”接口，但总行仍需保存每笔全局订单号和恢复决定。**

## 二、Spring `@Transactional`：AOP 代理与线程上下文的失效边界

### 1. 第二个朴素误解：方法上加了 `@Transactional`，异常发生后数据库自然就会回滚

这是 Java 业务系统里最常见也最危险的幻觉。因为注解看起来太像语言内建：

- 方法上写了；
- 代码照常跑；
- 抛异常；
- 那数据库当然会回滚。

问题是，Spring 声明式事务不是语法，它是运行时代理行为。也就是说：**你先得经过代理，事务拦截器才有机会工作。**

### 2. Spring 本地事务的最小运行图

```text
外部调用 proxy.method()
  → TransactionInterceptor
  → begin / join / suspend transaction
  → TransactionSynchronizationManager(ThreadLocal)
  → target method
  → commit 或 rollback
  → cleanup ThreadLocal/resources
```

这张图最关键的地方有两个：

- 事务逻辑挂在代理上，不是挂在方法定义本身；
- 事务资源绑定在当前线程上下文里，不会自动跨线程、跨 RPC 传播。

### 3. 为什么 `@Transactional` 最常失效在“代理根本没经过”的地方

常见失效场景几乎都能还原到这一点：

- `private/final` 或不可代理方法；
- `this.method()` 同类自调用，绕过代理；
- 代理配置不匹配；
- 新线程里没有当前事务上下文；
- `checked exception` 未配置 `rollbackFor`；
- 异常被 catch 掉后不再往外抛；
- 底层引擎/驱动本身不支持事务。

把这些经验项压成机制项，就是：默认回滚语义依赖三件事同时成立——调用必须经过拦截器、异常类型必须命中回滚规则、异常必须传播到拦截器能看见的边界。三者只要断掉一个，`@Transactional` 都可能看起来“配置了却没生效”。所以当你看到“加了注解但没回滚”，第一反应不该是怀疑数据库，而该先问：**这个调用到底经过代理了吗？异常真的触发了拦截器的回滚规则吗？**

### 4. 为什么 Spring 本地事务不能自动跨 RPC

因为它的作用域根本就是当前线程与当前资源：

- 本地 JDBC 连接；
- 当前线程的 `TransactionSynchronizationManager`；
- 当前代理链。

而且这不只是 ThreadLocal 丢失的问题：哪怕你想办法把某些上下文继续传到远端，远端服务仍然有自己独立的连接、资源管理器和故障边界，所以本地事务语义也不会自动延伸成全局事务。一旦跨 RPC：

- 远端服务有自己的连接；
- 有自己的本地事务；
- 有自己的超时和故障；
- 根本不共享你的 ThreadLocal。

所以 `REQUIRES_NEW` 是新建本地事务，不是跨服务全局协调；`@Transactional` 也不是“服务间自动原子”的魔法注解。

### 5. 一个更具体的失败场景：同类自调用绕过代理，数据库成功提交但你还以为自己在事务里

假设：

- `serviceA.method1()` 标了 `@Transactional`；
- `method1()` 内部用 `this.method2()` 调另一个也标了 `@Transactional` 的方法；
- 实际执行时，`method2()` 并没有经过代理；
- 某处异常被 catch 处理掉，外层拦截器也没触发回滚。

这时开发者看到的是“注解都写了，怎么还提交了？”实际问题并不在 SQL，而在代理和异常边界被绕开了。

### 6. 本节最该记住的结论：Spring 声明式事务不是语法糖，而是 AOP 代理 + 线程上下文；失效的根源通常不是事务理论，而是调用没过代理、异常没命中规则、线程已经换了，或者底层资源根本不支持事务

一句最短人话是：**`@Transactional` 像给本地柜台套了一层自动收银流程；走内部员工通道、换另一个柜台或换一座城市，这套流程不会自动跟着走。**

## 三、Seata：TC、TM、RM 与四种模式的不同代价

### 1. 第三个朴素误解：Seata 一接入，就自动帮你选好了分布式事务正确姿势

Seata 确实把很多协调逻辑抽成了框架，但它没有替你消灭模式之间的取舍。相反，它只是把取舍放到了一个更集中、但仍要你自己拍板的位置：

- 选 AT 还是 TCC 还是 Saga 还是 XA；
- 接受多少业务侵入；
- 接受多少锁/undo/log 代价；
- 接受多少中间态和补偿复杂度。

### 2. TC / TM / RM 的最小角色图

```text
TC:
  维护 GlobalSession / 分支状态 / 超时恢复

TM:
  开始 / 提交 / 回滚全局事务

RM:
  注册分支、锁/日志/提交或回滚本地资源

AT:
  自动记录前后镜像/undo_log
  → 框架尝试自动回滚

TCC:
  Try/Confirm/Cancel 业务实现

Saga:
  状态机/步骤补偿

XA:
  依赖资源管理器的 XA prepare/commit
```

这张图最重要的是：Seata 不是一个单一协议，而是一套把不同事务模型挂进同一协调外壳里的框架。

### 3. 为什么 Seata AT 不是“零成本零侵入”

AT 模式最容易被宣传成“最省改造”。它的代价并没有消失，而是换成了：

- SQL 代理；
- 前后镜像记录；
- `undo_log` 维护；
- 全局锁管理；
- 对数据库类型、DDL、SQL 形态的限制。

也就是说，它减少的是业务层手写 Try/Cancel 的工作，但增加的是框架层对数据库路径的介入。这里要再钉一句：AT 不是对任意 SQL 和任意副作用都自动安全。只要 SQL 形态超出前后镜像/回滚日志的可控边界，或者业务副作用已经跑出数据库资源层，AT 的“自动回滚”就不再能被简单理解成全局语义正确。

### 4. 一个更具体的失败场景：AT 模式看起来省代码，实际上把问题压进了 undo/log 和锁冲突里

假设：

- 业务基本没改代码；
- Seata AT 自动代理 SQL；
- 压测时全局锁冲突明显升高；
- `undo_log` 体量上涨，回滚和恢复成本也更重。

这时如果你只看“接入成本低”，会误判成“总体成本低”。真正的问题是：框架把一部分业务侵入换成了资源层的日志和锁代价。

### 5. 本节最该记住的结论：Seata 不是一个单一事务协议，而是一套承载 AT/TCC/Saga/XA 多种路线的协调框架；它不会替你消灭取舍，只会把取舍集中暴露出来

## 四、Hmily 与 ShardingSphere：框架定位比“谁更快”更重要

### 1. 第四个朴素误解：框架只要支持 XA/TCC，剩下的都是性能问题

这个误解会把框架看成“功能开关”：

- 支持 TCC；
- 支持 XA；
- 支持分片事务；
- 那剩下不就是调性能吗？

问题是，不同框架的定位根本不同：

- Hmily 更偏业务补偿和 TCC 元数据恢复；
- ShardingSphere 更偏分库分表路由与 XA 协调；
- Seata 则是更广义的全局协调容器。

所以框架比较的第一维，从来不是“谁快”，而是“它到底站在哪个边界上替你扛哪类复杂度”。

### 2. 最小定位图

```text
Hmily:
  偏 TCC / 业务补偿
  → Try/Confirm/Cancel 元数据 / 恢复日志
  → 定时重试未完成动作

ShardingSphere + XA manager:
  偏分库分表路由 + XA 协调
  → Atomikos / Narayana 等 TM
  → 跨分片资源 prepare / commit

共同检查:
  幂等 / 重试 / 超时 / 恢复 / 监控 / 回滚
  → 不能只看注解是否生效
```

### 3. 为什么“支持 XA/TCC”不等于能自动覆盖所有异常

因为还有大量复杂度根本不在框架接口里：

- 驱动和数据库的兼容性；
- 代理层与连接池边界；
- 线程切换与异步调用；
- 业务副作用与补偿幂等；
- 协调器日志丢失、恢复任务失败、告警无人处理。

所以框架最多替你包一部分协调逻辑，不能替你包业务语义和生产恢复能力。

### 4. 本节最该记住的结论：Hmily、ShardingSphere、Seata 的核心差异首先是定位差异，不是跑分差异；支持矩阵不是业务语义保证，框架只是协调层，不能替代业务幂等、故障演练和恢复闭环

## 五、把本篇收成一张图：分布式事务最常见的 bug，不是协议不会背，而是边界根本没被正确接上

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：代码加了 `@Transactional`，异常发生后数据库为什么还提交。答案已经闭环了。

MySQL XA 把数据库级两阶段状态机暴露出来，但 Prepared 与 Recover 仍然需要全局决策和运维闭环。Spring 声明式事务只是 AOP 代理和线程上下文，不会自动跨 RPC。Seata 把 AT/TCC/Saga/XA 挂进统一协调体系，但不会消灭模式取舍。Hmily 和 ShardingSphere 各自站在不同边界上承担复杂度。真正最常见的 bug，不是理论没学会，而是代理没经过、线程变了、分支没注册、恢复任务没跑、补偿语义没对齐。

把这一切压成最短总图，就是：

```text
本地注解 / 框架配置
  → 确认调用经过代理 / 协调器
  → 确认分支资源注册
  → 注入异常 / 超时 / 进程宕机 / 重复回调
  → 检查数据库、消息、undo/log、全局状态
  → 验证重试 / 补偿 / 恢复与幂等
```

这里还要多记一句：验证不能只覆盖 happy path 提交，更要覆盖恢复路径——例如 coordinator 宕机后 prepared 分支如何处理、回调丢失后幂等是否仍成立、补偿重试后最终账务是否重新收敛。

所以本篇最该记住的一句话是：**分布式事务框架不是“一行注解获得全局原子性”，而是本地代理/线程上下文、RM/TM 状态、日志/锁和重试恢复共同组成的运行时系统。**

## 六、几个最容易说错的地方

### `@Transactional` 写了就一定回滚？

不是。前提是调用经过代理、异常命中回滚规则、线程没换、底层资源支持事务。

### `REQUIRES_NEW` 就等于跨服务新开一个全局事务？

不是。它只是新开本地事务，不会自动穿过 RPC 边界。

### Seata AT 零侵入，就等于零成本？

不是。它把业务侵入换成了 SQL 代理、undo_log、全局锁和恢复代价。

### Hmily / ShardingSphere / Seata 的差别主要是谁更快？

不是。第一维是它们各自站在哪个边界上承担协调复杂度。

### 框架支持 XA/TCC，就等于故障时一定能恢复？

不是。恢复任务、日志持久化、告警、幂等和人工对账都仍然要自己负责。

## 收束：框架最大的价值，不是帮你藏掉复杂度，而是把复杂度集中到几个你必须正视的边界上

回到开头那个问题：代码加了 `@Transactional`，异常发生后数据库为什么还提交。答案已经闭环了：因为框架永远不会比它真实接住的边界更强。只要代理没经过、线程没带上上下文、协调器状态没落盘、补偿没有幂等，注解和配置就只是表面语法。分布式事务框架真正提供的，不是免费原子性，而是把原本分散的复杂度集中暴露给你，让你有机会真正测、真正恢复、真正对账。

这就是为什么说：**分布式事务框架不是“一行注解获得全局原子性”，而是本地代理/线程上下文、RM/TM 状态、日志/锁和重试恢复共同组成的运行时系统。** 只要这条主线站稳，后面进入失败检测、Leader 选举、可靠广播与 Gossip 时，你就不会再把“框架帮我兜底”和“系统真的可恢复”混为一谈，而会自然回到更底层的问题：这些协调动作到底由谁检测、谁广播、谁确认。
