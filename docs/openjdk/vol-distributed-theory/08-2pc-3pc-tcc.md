## 现在真正该问的，不再是“有没有一个分布式事务注解”，而是“多个资源分别提交、分别故障时，系统怎样让最终状态仍然可解释”

上一篇我们讨论 Paxos 变种时，已经看到了共识协议如何让多个节点对一个值达成决定。但分布式事务又多了一层难度：

- 共识要决定一个值；
- 事务要把多个资源的本地修改绑在同一个全局业务动作里。

这两个问题有关，但不是同一个问题。

想象一个最小业务：

- 订单服务在 A 库创建订单；
- 库存服务在 B 库扣库存；
- 支付服务在 C 库扣款。

单机里，你可以把它们放进同一个本地事务：

```text
BEGIN
  写订单
  扣库存
  扣款
COMMIT / ROLLBACK
```

跨服务以后，现实变成：

```text
A 库本地提交
  → RPC B 库
  → B 库本地提交
  → RPC C 库
  → 网络超时 / 响应丢失 / 进程崩溃
```

此时本地 rollback 只能回滚当前资源，救不了已经在另一个资源上提交的动作。你必须回答：

- 谁负责做全局决定；
- 参与者何时可以释放本地锁；
- 协调者挂了，参与者是否能继续；
- 超时究竟意味着失败、未知，还是已经提交；
- 如果最终一致，业务补偿由谁执行。

先把总图记住：

```text
强协调路线:
  2PC / XA
  → 参与者先 Prepare
  → 协调者统一 Commit / Rollback
  → 原子性更直接, 阻塞更明显

时间改进路线:
  3PC
  → CanCommit / PreCommit / DoCommit
  → 尝试用阶段与超时减少阻塞
  → 仍不能消灭真实分区不确定性

业务补偿路线:
  TCC
  → Try 预留 / Confirm 确认 / Cancel 取消
  → 少依赖长时间数据库锁
  → 把复杂度转给业务状态机、幂等和补偿
```

这篇最该先记住的一句话是：**分布式事务方案不是“更强的 ACID 开关”，而是在原子性、阻塞、性能、开发复杂度和故障恢复之间重新分配成本。**

## 一、2PC：Prepare 与 Commit 如何协调多个资源管理器

### 1. 最朴素的错误世界：协调者发一句“提交”，所有数据库自然就一起提交了

这个直觉把最难的部分藏掉了：

- 协调者发出的消息可能丢；
- 参与者可能已经 Prepare 但没收到最终决定；
- 协调者可能在参与者都准备好后崩溃；
- 参与者在不知道全局决定时，不能随意猜提交或回滚。

所以 2PC 的核心不是“广播 COMMIT”，而是先把所有参与者推进到一个知道自己可以提交、但还没有擅自提交的中间状态。这里还要多记一句：参与者明确返回 `NO` 和协调者因超时未收齐 `YES`，在工程上都是“无法直接进入全局提交”，但它们不是同一类证据；前者是明确否决，后者只是协调者拿到的信息不足。

### 2. 2PC 的最小两阶段流程

```text
Phase 1 Prepare:
  Coordinator → all RM: prepare
  RM:
    执行业务/写日志/持有资源
    → YES(已准备提交) 或 NO(无法提交)

Phase 2 Decision:
  全部 YES → Coordinator 广播 COMMIT
  任一明确 NO → 广播 ROLLBACK
  Prepare 阶段若协调者超时未拿齐 YES
    → 仍需依据已收集状态与协议规则决定回滚/等待
    → 超时本身不等于“全局一定回滚成功”

RM:
  COMMIT/ROLLBACK
  → 释放锁/资源
```

这里的角色分工是：

- Coordinator 负责形成全局决定；
- Resource Manager（RM）负责本地事务与 Prepare 状态；
- 全部 RM 进入 Prepared，并不意味着已经提交，而是意味着它们已经把提交所需状态准备好，可以等待最终决定。

### 3. 为什么 2PC 会阻塞

假设：

- 所有参与者都已经返回 YES；
- 协调者在发送第二阶段决定前宕机；
- 参与者只知道“我已经准备好了”，却不知道全局到底要 Commit 还是 Rollback。

这时参与者不能擅自提交：

- 如果全局其实要回滚，它提交就破坏原子性；
- 它也不能擅自回滚，因为全局可能已经在别处提交。

于是它只能保留锁和资源，等待协调者恢复、日志恢复或外部人工决策。

这就是 2PC 的核心阻塞边界：**参与者在 Prepare 后缺少最终决定时，不能仅凭本地状态安全地继续。**

### 4. 一个更具体的失败场景：A、B 都 Prepared，协调者却在第二阶段前失联

假设：

- MySQL-A 已经 Prepare；
- MySQL-B 也已经 Prepare；
- 协调者的全局决定还没可靠传播；
- 两边都持有锁，业务新请求开始排队。

这时你不能通过“把超时改小”直接解决原子性问题。超时只能告诉你协调者暂时没回，不告诉你它到底决定了什么。协调者高可用和持久化日志能降低恢复时间，但不能把协议的未知状态变成已知状态。

### 5. 本节最该记住的结论：2PC 把多个 RM 先推进到 Prepared，再由 Coordinator 广播统一决定；它的原子性更直接，但协调者失联时参与者可能长期持锁阻塞

一句最短人话是：**2PC 像多家银行先冻结并核对余额，最后由总行发统一结算指令；冻结后总行失联，分行不能自行猜提交还是回滚。**

## 二、3PC：多一阶段能否用超时打破阻塞

### 1. 第二个朴素误解：2PC 只是阶段太少，加一个 PreCommit 就能安全自动恢复

这个想法有一定道理：

- 2PC 的问题是参与者不知道协调者最后决定；
- 那就在最终 Commit 前增加一个中间状态；
- 让大家先知道“全局已经准备提交”；
- 超时后就可以自己继续。

3PC 的确试图这样做，但它没有免费获得完美安全性，而是引入了更强的时间与网络假设。

### 2. 3PC 的最小三阶段流程

```text
CanCommit:
  询问参与者是否可能提交

PreCommit:
  协调者确认所有参与者准备好
  → 参与者进入中间状态

DoCommit:
  最终提交

超时:
  参与者根据所处阶段尝试推断动作
```

相比 2PC，3PC 试图把“大家都同意”这件事先传播开，让参与者进入一个比 Prepared 更接近提交的中间状态。

### 3. 为什么 3PC 仍不能在真实分区下提供无条件安全

因为超时永远只是信息不足：

- 一侧可能已经收到 PreCommit；
- 另一侧可能还停在 CanCommit；
- 协调者可能已经发出 DoCommit，但消息没到；
- 网络分区两边可能基于不同阶段做出不同判断。

如果参与者根据超时自决，就可能出现：

- 一侧提交；
- 另一侧回滚；
- 仍然违反全局原子性。

所以 3PC 的价值是减少部分阻塞窗口，而不是在任意异步分区下消灭不确定性。它增加通信阶段，也增加了状态机复杂度和时间模型要求。更直白地说，3PC 之所以敢让参与者基于超时和阶段自决，是因为它依赖比 2PC 更强的同步/故障检测假设；一旦这些假设在真实分区里失效，“超时后自己决定”就不再能无条件保证原子性。

### 4. 本节最该记住的结论：3PC 用 CanCommit/PreCommit/DoCommit 和更强时间假设尝试减少 2PC 阻塞，但超时仍不能证明协调者真实决定，不能替代共识和故障检测

一句最短人话是：**3PC 像总行先发“准备结算”通知，再发最终指令；通知能减少等待，但断线时分行仍不能绝对知道总行最后决定。**

## 三、XA/DTP：2PC 如何落到数据库接口

### 1. 第三个朴素误解：有了 XA 接口，应用就自动拥有跨数据库事务正确性

XA/DTP 解决的是一个非常重要但边界明确的问题：

- 应用如何和事务管理器协作；
- 事务管理器如何和资源管理器协作；
- 资源管理器如何暴露 Prepare/Commit/Rollback/Recover 能力。

它不自动解决：

- 业务幂等；
- 超时重试；
- 用户补偿；
- 参与者长期阻塞后的运营处理。

### 2. DTP 与 XA 的最小生命周期

```text
AP(Application)
  → TM(Transaction Manager)
  → RM(Resource Manager: database)

XA lifecycle:
  XA START xid
  → SQL operations
  → XA END xid
  → XA PREPARE xid
  → XA COMMIT/ROLLBACK

TM recovery:
  崩溃重启
  → XA RECOVER 查询 PREPARED 事务
  → 根据持久化决定逐个 commit/rollback
```

这张图最重要的是把角色边界分开：

- AP 负责业务调用；
- TM 负责全局事务协调和决定持久化；
- RM 负责本地资源和 prepared 状态。

### 3. 为什么 XA PREPARED 事务会成为运维事故

因为协调者和参与者状态可能暂时分离：

- TM 已经记录全局决定，但 RM 还没收到；
- RM 已经 prepared，但 TM 的恢复记录损坏或不可达；
- 一笔忘记恢复的 prepared transaction 长期占用锁和资源。

所以 XA 的 `RECOVER` 不是一个“调试辅助命令”，而是恢复闭环的重要组成部分。这里还要钉死一个边界：`XA RECOVER` 只能枚举 RM 侧仍处于 prepared 的分支，它不能单独告诉你全局事务最终应该 commit 还是 rollback；这个决定仍依赖 TM 的持久化日志、外部协调状态或人工对账。运维必须能知道：

- 哪些全局事务处于 prepared；
- 这些事务应该 Commit 还是 Rollback；
- 谁拥有最终决定证据；
- 如果证据缺失，业务如何对账。

### 4. 本节最该记住的结论：XA 把 2PC 落成了 AP、TM、RM 之间的标准协调接口，但接口标准不等于业务自动正确；Prepared 状态、恢复决定和超时补偿仍然需要系统显式管理

一句最短人话是：**XA 像银行分行提供统一的“预冻结/确认/撤销”接口，但总行仍需保存每笔全局订单号和恢复决定。**

## 四、TCC：把数据库锁换成业务预留与补偿

### 1. 第四个朴素误解：2PC 长时间持锁太慢，那 TCC 没有长锁，应该就简单了

TCC 确实可以缩短数据库资源被长时间锁住的路径，但它没有消灭事务复杂度，而是把复杂度从数据库协议转移到了业务代码：

- Try 如何预留资源；
- Confirm 如何确认；
- Cancel 如何释放或补偿；
- 重试是否幂等；
- 空回滚如何处理；
- Cancel 先到时如何防悬挂。

### 2. TCC 的最小业务状态机

```text
Try:
  预留业务资源
  例如冻结库存/额度

Confirm:
  预留成功后确认扣减/转账

Cancel:
  释放冻结/补偿已执行动作

工程保护:
  幂等:
    重试 Confirm/Cancel 不重复执行
  空回滚:
    Try 未成功却收到 Cancel → 安全返回并记录分支状态
  防悬挂:
    Cancel 先到, 后续 Try 不能再次占用资源
    → 需要用事务/分支状态显式阻止迟到 Try 重新预留资源
```

这张图最关键的是：TCC 把“锁住一行数据等待协调者”改写成“业务状态机里先预留，再确认或取消”。空回滚和防悬挂其实是同一条状态机边界的两面：一方面 Cancel 可能先于成功 Try 到达，另一方面迟到的 Try 也不能在 Cancel 之后重新占用资源。没有分支状态记录，这两件事都很难做对。

### 3. 为什么 TCC 不是“没有锁所以更简单”

因为它要处理更多业务级异常：

- Confirm 重试多次；
- Cancel 重试多次；
- Try 还没成功就收到了 Cancel；
- Cancel 先完成后，延迟到达的 Try 又想占资源；
- 业务动作已经对外产生副作用，但补偿失败。

所以 TCC 的正确性依赖业务补偿语义，框架不能自动推导“一个任意 SQL 的业务反向动作”。它也不是“没有长锁的 2PC”；它表达的是业务级预留、确认、取消与补偿语义，而不是资源层的瞬时全局原子提交。

### 4. 一个更具体的失败场景：Cancel 先到，延迟的 Try 又把库存冻结了一次

假设：

- 协调器判断 Try 超时，先发 Cancel；
- Cancel 在库存服务落地，释放或标记了这笔业务；
- 之后原先延迟的 Try 请求才到；
- 如果没有防悬挂标记，Try 可能重新冻结库存。

这时问题不是“网络偶尔乱序”这么简单，而是业务状态机没有把请求顺序和幂等边界显式记录下来。

### 5. 本节最该记住的结论：TCC 把数据库锁与全局等待换成业务预留、确认、取消和补偿；它可能缩短锁持有，但把协议复杂度转移给业务状态机、幂等和异常顺序处理

一句最短人话是：**TCC 像库存先贴“已预订”标签，Confirm 才出库，Cancel 才解冻；标签状态和异常订单必须有独立账本。**

## 五、方案选择：原子性、阻塞、性能与开发量的四角权衡

### 1. 第五个朴素误解：只要业务要求原子性，就应该优先使用最强的 XA/2PC

这句话忽略了业务对“原子”的真正定义。

- 有些业务要求多个资源必须同一时刻成功；
- 有些业务接受几秒或几分钟内最终一致；
- 有些业务可以用冻结和补偿表达；
- 有些长流程本来就不能长时间持有数据库锁。

所以协议选择必须从业务不变量和故障窗口开始，而不是从“最强协议”开始。

### 2. 方案选择的最小矩阵

```text
XA / 2PC:
  资源支持标准事务接口
  → 强原子性更直接
  → 锁 / 阻塞 / 协调者恢复成本

TCC:
  业务可表达 Try / Confirm / Cancel
  → 可缩短数据库锁持有
  → 开发与补偿复杂

Saga / 可靠消息:
  长流程 / 最终一致 / 可补偿
  → 牺牲即时全局原子性
  → 换可用性与业务可恢复性

决策:
  业务不变量
    → 故障窗口
    → 幂等/补偿能力
    → 运维能力
    → 性能
```

### 3. 为什么没有“分布式事务银弹”

因为每种方案都在不同地方付账：

- 2PC 把复杂度放在协调和锁；
- 3PC 把复杂度放在更多状态和更强时间假设；
- XA 把复杂度放在接口、prepared 状态和恢复；
- TCC 把复杂度放在业务补偿和异常顺序；
- Saga/可靠消息把复杂度放在最终一致、重试、对账和补偿。

而且这些补偿并不总是可逆或必然成功：退款、券回收、外部回调撤销、库存释放都可能失败或需要人工介入，所以“有补偿”不等于“代价已经消失”。

所以选型报告必须显式写出：

- 失败后用户看到什么；
- 哪些操作允许最终一致；
- 谁负责重试；
- 谁负责对账；
- 谁负责人工修复。

### 4. 本节最该记住的结论：2PC 把账压在协调与锁，TCC 压在业务补偿，Saga/消息压在最终一致与重试；方案选择必须从业务不变量、故障窗口、幂等能力和运维能力反推

## 六、把本篇收成一张图：分布式事务方案是在重新安排失败成本

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：A 库扣款成功、B 库收款失败，单机 rollback 为什么救不了跨库状态。答案已经闭环了。

2PC 通过 Prepare/Commit 把多个 RM 绑进一个全局决定，但参与者在未知决定时可能阻塞。3PC 增加 PreCommit 和时间阶段，尝试减少阻塞，却仍受分区与时间假设约束。XA 把 2PC 落成 AP/TM/RM 的标准接口，但 prepared 状态和恢复决定仍要被运维管理。TCC 则把数据库锁改写成业务预留、确认、取消和补偿，降低部分锁等待，却把复杂度交给业务状态机。Saga/可靠消息将在下一篇继续把最终一致和长流程补偿展开。

把这一切压成最短总图，就是：

```text
跨资源操作
  → 明确业务不变量
  → 选择 2PC / XA、TCC、Saga / 消息
  → 定义提交 / 回滚 / 超时 / 重试
  → 设计幂等、对账和恢复
  → 故障演练验证最终状态
```

所以本篇最该记住的一句话是：**分布式事务协议的真正差异，不是阶段数，而是把不确定性和失败成本放在哪里：2PC 放在锁与协调者，3PC 放在更强时间假设，XA 放在接口与恢复，TCC 放在业务补偿。**

## 七、几个最容易说错的地方

### 2PC 就是把几个本地 COMMIT 广播出去？

不是。它先让参与者 Prepare 并进入等待决定的状态，再由协调者统一 Commit/Rollback。

### 3PC 增加一阶段就能彻底消除阻塞？

不是。它依赖更强时间假设，真实分区下超时仍不能证明协调者的最终决定。

### XA 接口一上，跨服务事务就自动正确？

不是。Prepared 恢复、协调者日志、幂等、超时与业务补偿仍然需要显式设计。

### TCC 没有长数据库锁，所以比 2PC 简单？

不是。它把复杂度转移到了 Try/Confirm/Cancel、幂等、空回滚、防悬挂和补偿。

### 所有订单/库存/支付流程都应该使用同一种协议？

不是。业务不变量、故障窗口、最终一致容忍度和补偿能力不同，方案也应不同。

## 收束：分布式事务的第一原则，不是追求最强协议，而是先说清失败后业务应该长什么样

回到开头那个问题：A 库扣款成功、B 库收款失败，单机 rollback 为什么救不了跨库状态。答案已经闭环了：因为跨资源以后，没有一个本地事务能自动覆盖所有参与者。你要么用协调协议让多个资源进入共同决定，要么把原子性拆成预留、确认、取消、补偿与最终对账。

这就是为什么说：**分布式事务协议的真正差异，不是阶段数，而是把不确定性和失败成本放在哪里：2PC 放在锁与协调者，3PC 放在更强时间假设，XA 放在接口与恢复，TCC 放在业务补偿。** 只要这条主线站稳，下一篇进入 Saga、可靠消息和最大努力通知时，你就不会再把它们看成“事务不够强的退而求其次”，而会自然去问：在长流程和高可用场景里，最终一致与补偿是不是反而更符合业务真实边界。
