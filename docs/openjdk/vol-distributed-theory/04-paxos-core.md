## 现在真正该问的，不再是“大家投票选一个值不就行了”，而是“在旧消息可能晚到、节点可能挂掉、提案还会相互竞争时，怎样保证不会出现两个不同决定”

走到这里，分布式理论线已经把前置世界观铺得很清楚了：

- 网络可能分区，系统必须定义一致性和可用性的取舍；
- 节点可能 crash、超时、恢复，超时只是怀疑不是证明；
- 事件先后不能只靠物理时钟，要靠逻辑顺序和因果关系重新定义。

只要这些前提站稳，你就会自然碰到共识问题真正尖锐的版本：

“既然每个节点都可能慢、消息都可能晚到、提案还可能互相竞争，那三个副本怎样才能最终决定同一个值，而不是 A 说选 1，B 说选 2，大家各自都有理由？”

这时很多人第一次接触共识，会本能地想：

- 少数服从多数；
- 投个票；
- 票多的赢。

可这套朴素民主直觉一进分布式世界就立刻不够了。因为真正的问题不是“这一轮谁票多”，而是：

- 旧轮次的消息可能晚到；
- 新提案者可能不知道旧提案已经走到哪里；
- 节点可能在不同时间看见不同历史；
- 如果你不先读取已有约束，就可能在后来的轮次里把已经被多数派接受过的值覆盖掉。

所以 Paxos 解决的，不是“如何投票选 leader”，而是：**如何在竞争提案和故障环境下，让所有未来提案都无法绕过已经形成的历史约束。**

先把总图记住：

```text
需要保证什么:
  Agreement / Validity / Termination

Prepare(N):
  proposer 带编号 N 询问 acceptor
  → 你愿不愿意承诺不再接受更低编号?
  → 你手里有没有更早已接受的值?

Promise:
  acceptor 承诺拒绝更低编号
  + 返回本地已接受历史(如有)

Accept(N, V):
  proposer 根据多数 Promise 选择 value
  → 发送 Accept(N, V)
  → acceptor 在未承诺更高编号前接受

Chosen:
  某个 value 被多数 acceptor 接受
  → learner / 其他节点学习该决定
```

这篇最该先记住的一句话是：**Paxos 的核心不是“多数投票选谁”，而是 Prepare 先读取历史约束，Accept 再写入新值，多数派交集让新提案无法绕过已决定的值。**

## 一、共识问题：先定义“怎样才算正确”

### 1. 最朴素的错误世界：只要最后大多数节点都看起来差不多，就算达成共识了

这是很多人对共识的第一层直觉：

- 三个节点里两个觉得值是 1；
- 另一个节点一时半会儿还没跟上；
- 反正多数都差不多，那应该就够了。

问题在于，“看起来差不多”不是协议正确性的定义。共识协议真正需要先钉死的是：

- 两个正确节点不能决定不同值；
- 决定的值必须来自某个合法提案；
- 在假设满足时，正确节点最终应该能决定。

如果不先把“正确”定义清楚，后面任何投票、重试、选主、日志复制都只是在堆技巧，而不是在证明什么。

### 2. 共识的最小性质图

```text
Agreement:
  两个正确节点不能决定不同值

Validity:
  决定的值必须来自某个合法提案

Termination:
  在假设满足时, 正确节点最终决定

Paxos核心:
  Safety 在任意消息延迟/节点故障下保持
  Liveness 需要多数派可达、竞争收敛等额外条件
```

这张图最关键的地方是：**Safety 和 Liveness 不是同一件事。**

- Safety 要求“别做错决定”；
- Liveness 要求“别永远做不出决定”。

而在 FLP 世界里，你不可能无条件同时把两者都许诺到无限强。Paxos 的策略很清楚：先守住 Safety，再在工程条件足够好时争取 Liveness。

### 3. 为什么 Paxos 不能承诺所有情况下都终止

因为上一讲我们已经知道：在异步系统里，只要存在至少一个 crash failure，你就不能要求所有执行都保证终止。

所以 Paxos 并不说：

- 任何网络状态下都一定立刻决定；
- 任意多 proposer 竞争也总能平滑结束；
- 多数派时刻都自动存在。

它说的是：

- 在协议允许的故障模型内，即便消息延迟、节点故障和提案竞争都存在，只要决定形成，就不能形成两个不同决定；
- 这里默认参与者仍按协议运行，持久状态与成员配置满足协议前提，不是在 Byzantine 或任意恶意行为下无条件保证安全；
- 实际工程里，再通过稳定 leader、超时、退避和部分同步把活性尽量拉起来。

### 4. 一个更具体的失败场景：系统迟迟决定不了，但这不等于协议已经错了

假设：

- 两个 proposer 几乎同时发起提案；
- 网络又让消息顺序不断交错；
- acceptor 一会儿承诺给编号 10，一会儿又承诺给编号 11；
- 两边都在推进，却谁都还没收齐稳定多数。

这时系统可能暂时不活跃，但只要它没有让两个不同值都被多数派接受，Safety 仍然没破。共识协议最怕的不是“暂时没决定”，而是“在不同节点上决定出两个冲突值”。

### 5. 本节最该记住的结论：Paxos 不是先讨论谁当 leader，而是先把 Agreement、Validity、Termination 三件事分开；它优先守住 Safety，再在工程假设下争取 Liveness

一句最短人话是：**会议可以暂时开不出结论，但不能同时通过两份互相矛盾的正式决议。**

## 二、Prepare / Promise：先获取历史，再提出新值

### 1. 第二个朴素误解：新 proposer 直接把自己的值发给多数派，谁先拿到票谁赢就行

这是多数投票直觉最容易犯的错误：

- 我想提 7；
- 我直接问大家接不接受 7；
- 只要先收齐多数同意，应该就够了。

问题在于，这样你完全不知道：

- 有没有旧提案已经在别处被部分接受；
- 有没有 acceptor 手里握着更早的历史约束；
- 你是不是正在把一个已经接近被选中的旧值直接覆盖掉。

所以 Paxos 的第一阶段不是“提值”，而是“先查档案”。

### 2. Prepare / Promise 的最小流程

```text
Proposer:
  选择唯一 proposal number N
  → 向 Acceptor 发送 Prepare(N)

Acceptor 收到:
  若 N 高于已承诺编号
    → Promise: 不再接受低于 N 的提案
    → 返回自己已接受的最高编号/value(如有)
  否则拒绝/忽略

Proposer:
  收集多数派 Promise
  → 得到历史约束
```

这张图最重要的地方是：Promise 不只是“我支持你”。它同时包含了两笔约束，而且 Acceptor 返回的 accepted 历史仍然只是本地状态报告，只有形成 quorum 才能称为 chosen：

- **向前看**：我承诺以后不再接受更低编号；
- **向后看**：我把自己手里已经接受过的最高历史告诉你。

也就是说，Prepare 的作用不是拉票，而是**冻结一部分未来，并读取一部分过去。**

### 3. 为什么 proposal number 必须全局可比较且不断向前推进

因为 Paxos 不是靠“值大小”决定胜负，而是靠“谁有资格代表更晚的一轮尝试”来串起历史。这里的“全局”不是指必须有一个中心发号器，而是指所有参与者都能比较这些编号，并且同一个协议实例中的编号唯一、不会把新轮次误认成旧轮次；常见做法是用本地计数器配合 proposer ID 构造可比较的组合编号。

如果编号不唯一、不可比较或可能倒退，就会出现：

- acceptor 无法判断该拒绝谁；
- proposer 无法证明自己比旧轮次更新；
- 更晚提案无法稳定覆盖更早提案的竞争窗口。

所以编号的核心角色不是“排序值”，而是“排序提案尝试本身”。

### 4. 一个更具体的失败场景：没有 Prepare，后来的 proposer 根本看不见已经被部分接受的旧值

假设：

- proposer P1 用编号 10 提议值 A；
- 两个 acceptor 已经接受了 A，但 learner 还没来得及学到；
- 这时 proposer P2 直接发起值 B，如果它不先做 Prepare，就根本不知道 A 已经被多数派接受过。

于是它可能试图把 B 再推给另一批 acceptor，系统就会面临“一个已经被多数接受的值 A”和“一个后续想重新推动的值 B”同时竞争的危险。

Prepare 的存在，就是为了防止这种“新提案在黑暗里乱撞”。

### 5. 本节最该记住的结论：Prepare 的作用不是拉票，而是用 proposal number 冻结更低编号未来，并通过 Promise 读取 acceptor 手里的历史约束；新 proposer 先查档案，再谈新值

一句最短人话是：**Prepare 像新任书记先查旧决议档案，并宣布“编号更低的草案不再受理”，而不是直接把自己的草案拿去盖章。**

## 三、Accept / Chosen：为什么必须继承已有值

### 1. 第三个朴素误解：既然我已经收齐了多数 Promise，那我当然可以继续提自己最想要的值

这也是最容易忽略 Paxos 真正安全核心的地方。很多人会觉得：

- Prepare 已经成功；
- 多数 acceptor 都答应不再接更低编号；
- 那我现在当然可以继续推我自己的值。

问题就在这里：多数 Promise 让你拿到了“资格”，但没有自动让你摆脱“历史”。

### 2. Accept 阶段的最小继承规则

```text
多数 Promise 返回:
  有 accepted proposal?
    → 选其中 proposal number 最高的 value
  无 accepted proposal?
    → 可选自己的 value

发送:
  Accept(N, V) → Acceptors

Acceptor:
  若尚未承诺更高编号
    → 接受(N,V)

Chosen:
  某 value 被足够多数 Acceptors 接受
  → Learner/其他节点学习该决定
```

这条规则最关键的地方是：**新 proposer 不能自由选值，它必须继承 Promise 里已知的最高 accepted value。**

这里要严格区分两个状态：单个 Acceptor 已经 `accepted` 某个 `(proposal number, value)`，只说明它本地接受过；只有同一个 value 被满足 quorum 的 Acceptor 接受，才形成 `chosen`。因此“返回了 accepted 历史”不等于“返回的 value 已经 chosen”，但它仍然可能是后续安全性必须继承的约束。

如果没有这个约束，Prepare 阶段读取历史就失去了意义，Agreement 也会立刻失守。

### 3. 为什么“继承最高已接受值”能保护 Agreement

因为任意两个多数派必然相交。

- 如果某个值已经被一个多数派接受；
- 那后来的 proposer 再去收集另一个多数 Promise 时；
- 两个多数集合一定至少在一个 acceptor 上相交；
- 这个交点会把“已有历史”带给新 proposer；
- 新 proposer 就不能再随意绕过旧值。

所以 Paxos 的安全性不是来自“大家都很听话”，而是来自一条连续的三步链：

1. 某个 value 已经被一个 quorum 接受，于是它成为 `chosen`；
2. 后续 proposer 的 Prepare quorum 必然和这个 chosen quorum 相交，因此至少会看到一份相关 accepted 历史；
3. 新 proposer 必须继承 Promise 中最高编号的 accepted value，于是不能把另一个 value 推成冲突决定。

这条“chosen quorum → 后续 Prepare 必见历史 → 新 proposal 必须继承”的链，才是 Agreement 的核心，而不是一句“多数派相交”单独就能完成全部证明。

### 4. 一个更具体的失败场景：不继承旧值，会让两个不同值都各自拿到一批多数历史

假设：

- 值 A 已经被一批 acceptor 接受；
- 新 proposer 拿到多数 Promise，但故意忽略返回的旧值 A；
- 它继续推动自己的值 B；
- 那么系统就可能出现：旧历史已经让 A 很接近被最终学习，而新历史又开始给 B 铺路。

如果允许这种行为，Agreement 就不再有保障。也就是说，**Accept 阶段真正难的不是“把值发出去”，而是“承认自己不能自由选值”。**

### 5. Learner 的角色为什么通常放在最后讲

因为 Learner 回答的是：

- 既然某值已经被 quorum 接受并成为 `chosen`，系统怎样把这个“已选中事实”传播给其他节点。

Learner 负责观察和传播决定，通常不参与 Proposer/Acceptor 对安全值的核心投票；把它放在最后，是为了先把“谁提议、谁承诺、谁接受”的 Safety 骨架站稳。

但在教学上，真正必须先站稳的是：

- 谁能提；
- 谁能承诺；
- 为什么新值必须继承旧值；
- 为什么多数派相交能阻止冲突决定。

没有这条 Safety 骨架，Learner 只是一个传播角色，而不是协议核心。

### 6. 本节最该记住的结论：Accept 阶段的关键不是“把 proposer 的值广播出去”，而是“新 proposer 必须继承 Promise 中已知的最高 accepted value”；多数派交集和历史继承一起守住 Agreement

一句最短人话是：**新决议起草前必须继承档案中已经进入正式流程的最高版本；否则不同会议都可能给同一事项盖上不同结论。**

## 四、多数派与故障：三节点为什么能容忍一个故障

### 1. 第四个朴素误解：三节点容忍一个故障，是因为两个节点一投票就自然代表了多数人的意见

这个说法只说对了表面。真正关键的不是“人数够多”，而是：

- 多数派集合为什么必须相交；
- 少数派为什么必须被禁止单独决定。

### 2. 最小 quorum 图

```text
N=3:
  quorum=2
  可容忍 1 个节点故障

N=2f+1:
  quorum=f+1
  最多容忍 f 个故障并继续形成多数

网络分区:
  多数侧 → 可能继续决定
  少数侧 → 不能安全提交新决定

注意:
  能继续决定 ≠ 所有请求都立即成功
  还受 Leader、网络和存储状态影响
```

这张图最关键的地方是：**多数派公式不是算术装饰，而是为了保证任意两个 quorum 必然相交。**

这里的 `N=2f+1`、`quorum=f+1` 是固定成员、基础 Paxos 模型下的表达。成员变更、节点加入/离开和 quorum 变化不能直接修改这个数字，而要通过单独的重配置协议，确保新旧成员集合的安全交集。只要这个交集性质没了，后来的 proposer 就可能完全看不见旧历史，协议安全性立刻崩掉。

### 3. 为什么两个节点都活着却可能仍然不能提交

因为“活着”不等于“组成多数”。

- 三节点系统里，如果分区后两边变成 2 和 1，多数侧可能继续；
- 如果变成 1 和 1 加一个彻底失联，那任何单侧都拿不到多数；
- 即使某侧节点都在线，如果它们之间的关键消息到不了，也仍然不意味着可以安全决定。

所以 Paxos 的可用性不是“节点活着就行”，而是“多数派可达且竞争收敛”。

### 4. 一个更具体的失败场景：三个节点都没真正宕机，但任何一侧都不敢提交新值

假设：

- A 和 B 网络互通；
- C 与 A、B 都间歇性抖动；
- 某些 proposer 轮次里，消息总在 quorum 形成前被打断；
- 节点并没全死，但多数历史无法稳定收敛。

这时系统的问题不是“服务器挂了”，而是“多数派可达性和提案竞争都不稳定”。Paxos 在这里宁可暂时不活跃，也不能错决定。

### 5. 本节最该记住的结论：三节点能容忍一个故障，不是因为“两个人说了算”这么简单，而是因为多数派相交让任何新提案都逃不开旧历史；少数派之所以不能提交，是 Safety 的代价

## 五、Multi-Paxos：为什么稳定 Leader 能减少 Prepare

### 1. 第五个朴素误解：每次共识都两阶段，那连续日志就只是机械重复 Prepare/Accept

这在 Basic Paxos 的抽象里没错，但一旦你把共识拿去做复制日志，很快就会发现：

- 每个日志 slot 都重新 Prepare；
- 每次都收集 Promise；
- RTT 和协调成本太高；
- 生产系统不可能长期这么跑。

于是工程界自然会问：**既然已经有一个稳定 proposer/leader，为什么还要每次重新查一遍档案？**

### 2. Multi-Paxos 的最小优化图

```text
初始:
  Leader 先完成一次 Prepare/Promise

稳定期:
  每个 log slot / instance
  → Leader 直接提议 Accept(instance, value)
  → 多数派接受
  → entry Chosen

故障:
  新 Leader 重新获取历史约束
  → 补空洞 / 恢复日志
  → 继续后续 instance
```

Multi-Paxos 的本质不是把 Paxos 变成“一阶段协议”，而是：

- 在 leader、ballot 和成员稳定时，复用 Prepare 阶段已经建立的资格；
- 让后续多个日志实例主要走 Accept 路径；
- 一旦 leader 变化或稳定条件被破坏，再重新回到“先读历史约束”的模式。

### 3. 为什么不能简单说“Paxos 变成了一阶段”

因为那会掩盖它最重要的前提：

- 稳定 leader；
- 稳定 ballot；
- 稳定成员；
- 历史空洞和恢复另有处理。

只在这些条件都站住时，Prepare 才像“被摊薄”了一样。它没有消失，只是被 amortize 到了一段稳定期里。

### 4. 本节最该记住的结论：Multi-Paxos 的优化，不是把 Prepare 消灭掉，而是在稳定 leader 期间复用它已经建立的历史约束；一旦 leader 或成员变化，系统仍要重新面对旧历史

一句最短人话是：**议会选出稳定主席后，后续议案不必每次重查主持资格；主席换人时，仍要重新查档案。**

## 六、把本篇收成一张图：Paxos 的骨架不是投票，而是历史约束

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：三个节点分别提议不同值，网络还会延迟消息；最终结果怎样才能保证两个正确节点不会决定不同值。答案已经闭环了。

共识首先要分清 Safety 和 Liveness。Prepare 阶段不是拉票，而是用 proposal number 读取历史并冻结更低编号未来。Promise 的真正价值，是把 acceptor 手里的旧值历史交给新 proposer。Accept 阶段最关键的不是“发一个值”，而是“必须继承 Promise 中已知的最高 accepted value”。多数派交集把旧历史带进新提案里，从而保证 Agreement。三节点能容忍一个故障，也不是因为“人多势众”，而是因为 quorum 相交让历史不会被绕开。Multi-Paxos 再把这条骨架推广到连续日志与稳定 leader 场景。

把这一切压成最短总图，就是：

```text
Prepare(N)
  → Promise(拒绝低编号 + 返回历史)
  → 选择必须继承的 value
  → Accept(N, V)
  → 多数派接受
  → Chosen / Learned

安全性:
  ballot 顺序 + 历史继承 + quorum intersection
活性:
  多数派可达 + 竞争收敛 + 稳定 leader / 超时策略
```

所以本篇最该记住的一句话是：**Paxos 的核心不是“多数投票选谁”，而是 Prepare 先读取历史约束，Accept 再写入新值，多数派交集让新提案无法绕过已决定的值。**

## 七、几个最容易说错的地方

### Paxos 就是多数投票？

不是。多数派只是骨架的一部分，真正关键的是新提案必须看到并继承旧历史。

### Promise 就是支持某个 proposer？

不是。它同时意味着“拒绝更低编号未来”和“返回本地已接受历史”。

### 收齐多数 Promise 后，proposer 就能继续提自己最想要的值？

不是。如果 Promise 中已经带回旧值历史，新的 proposer 必须继承其中最高 accepted value。

### 三节点容忍一个故障，就是因为两个节点说了算？

不是。真正关键的是任意两个多数派相交，因此旧历史不会被后续提案绕开。

### Multi-Paxos 就是把 Paxos 简化成一阶段？

不是。Prepare 只是被稳定 leader 的阶段性资格复用掉了，一旦 leader 或成员变化，历史约束仍要重新获取。

## 收束：Paxos 之所以难，不是因为步骤多，而是因为它逼你承认“新提案不能随意无视旧历史”

回到开头那个问题：三个节点分别提议不同值，怎样保证最终不会决定出两个不同结果。答案已经闭环了：共识的关键不在“票数”，而在“后来的提案永远逃不开先前已经形成的历史约束”。Prepare 先读历史，Accept 再写新值，多数派交集把这两步钉成了一个安全骨架。只要这一点站稳，后面的 leader、日志、恢复和成员变更才能继续往上长。

这就是为什么说：**Paxos 的核心不是“多数投票选谁”，而是 Prepare 先读取历史约束，Accept 再写入新值，多数派交集让新提案无法绕过已决定的值。** 只要这条骨架站稳，下一篇进入 Multi-Paxos 与 Raft 时，你就不会再把 leader、日志复制和任期当成孤立技巧，而会自然地把它们理解成“如何把这套安全骨架工程化到连续日志里”的问题。
