## 现在真正该问的，不再是“哪个 Paxos 版本更新”，而是“为了减少一种成本，协议愿意牺牲哪一种约束”

前几篇已经把 Paxos 家族的主线铺开了：

- Basic Paxos 用 Prepare/Accept 和 quorum 交集保证单值安全；
- Multi-Paxos 用稳定 Leader 复用 Prepare，推进连续日志；
- Raft 用更强的 term、日志前缀和提交规则换来可解释性；
- ZAB 为协调服务强化全序和恢复；
- EPaxos 把全局顺序成本转成冲突依赖图成本。

读到这里，看到 Fast Paxos、Disk Paxos、Cheap Paxos、Generalized Paxos、Flexible Paxos、Stoppable Paxos 这些名字时，最容易产生一种错觉：

“是不是 Paxos 还不够好，所以不断修补出新版本？”

更准确的理解是：这些变种不是单调升级，而是在不同系统约束下重新分配账单：

- 想少一轮消息，就扩大 quorum；
- 网络不可靠但有共享存储，就把状态放进磁盘；
- 想降低常态硬件成本，就把故障恢复复杂度抬高；
- 命令本来可以交换，就不必强求所有命令全序；
- 想让 quorum 更贴合读写拓扑，就允许跨阶段不对称；
- 想安全停机维护，就把“停止”本身也变成一致决定。

所以本篇最该先记住的一句话是：**Paxos 变种不是把共识变魔法，而是明确把成本从一个地方搬到另一个地方。**

先把总图记住：

```text
Fast Paxos:
  更大 quorum
  → 低冲突时尝试少一轮消息

Disk Paxos:
  共享稳定存储
  → 用磁盘状态替代部分消息状态

Cheap Paxos:
  较少常态处理器
  → 故障时辅助处理器补位

Generalized Paxos:
  可交换命令
  → 只为不可交换命令建立顺序

Flexible Paxos:
  不对称 Prepare/Accept quorum
  → 用交集条件调路径成本

Stoppable Paxos:
  停止状态也进入协议
  → 为维护和切换划出安全边界
```

## 一、Fast Paxos：没有冲突时尝试一轮决定

### 1. 最朴素的错误世界：既然 Prepare 只是查历史，那客户端直接把值发给 Acceptor 就行

这个想法确实抓住了 Basic Paxos 的一部分成本：

- Prepare 要一轮消息；
- Promise 要返回历史；
- Accept 还要再发一轮；
- 如果命令本来没有冲突，为什么不能直接进 Accept？

Fast Paxos 的回答不是“删掉 Prepare 后一切照旧”，而是：**在低冲突条件下尝试快路径，同时重新设计 Fast quorum、Classic quorum 和恢复路径之间的交集条件，弥补少了历史协调的风险。**

### 2. Fast Round 的最小图

```text
Fast Round:
  client/proposer 直接发送 value
  → Fast quorum 收到/接受
  → 无冲突且满足交集条件
  → value chosen

冲突:
  多个 value 同时到达
  → 无法唯一确定
  → 回退 Classic Round
  → Prepare/Promise/Accept 解决

核心:
  Fast quorum 通常比 Classic quorum 更大
  → 不是越大越好, 而是必须满足 Fast/Classic 之间的交集证明
  → 用更强交集换跳过一轮的机会
```

这张图最关键的地方是：Fast Paxos 不是无条件快，而是把“正常低冲突路径”和“发生竞争后的恢复路径”拆开。

### 3. 为什么 Fast Paxos 不是“少一轮、所有场景都更快”

跳过 Prepare，就少了一次发现历史和协调冲突的机会。为了保证安全，协议必须重新设计 quorum 交集：

- Fast quorum 要更大；
- 不同 fast proposal 的交集要足够强；
- 冲突时必须能识别并回退 Classic Round。

所以 Fast Paxos 的收益是：

- 低冲突时减少一轮延迟；

代价是：

- 更大的 quorum；
- 更高的冲突恢复复杂度；
- 更差的最坏路径；
- 对故障与网络条件更敏感。

具体 quorum 公式还要结合容错参数、Fast/Classic 两类 quorum 和冲突恢复协议定义，不能把某个 N 的数字当成通用配置；真正的安全条件是相关 quorum 之间满足协议要求的交集，而不是简单追求“参与节点越多越安全”。

### 4. 一个更具体的失败场景：低冲突时很快，两个客户端同时直提不同值后进入复杂回退

假设：

- 客户端 A 直接提值 X；
- 客户端 B 几乎同时直接提值 Y；
- 不同 Acceptor 先后看到不同值；
- Fast quorum 无法确认唯一值；
- 系统必须回退 Classic Round，重新 Prepare/Promise/Accept。

这时 Fast Paxos 不但没有比普通路径快，最坏还增加了冲突识别与回退成本。它真正适合的是冲突率足够低、网络路径足够稳定、团队能够接受复杂回退的场景。

### 5. 本节最该记住的结论：Fast Paxos 用更大 quorum 换低冲突时少一轮消息，但它没有消灭历史约束，只是把约束转成更严格的交集条件和冲突回退路径

## 二、Disk Paxos：把 Acceptor 状态放进共享存储

### 1. 第二个朴素误解：节点之间网络不可靠，那就让大家写共享磁盘，问题自然更简单

这个想法把通信介质换了：

- 不靠节点之间发消息；
- 每个节点读写自己分配的磁盘区域；
- Proposer 通过扫描共享磁盘观察 Acceptor 状态。

Disk Paxos 确实沿着这个方向走，但它并没有消灭故障，只是把故障边界从“消息网络”搬到了“共享存储”。

### 2. Disk Paxos 的最小状态图

```text
Acceptor state:
  accepted ballot/value
  → 写入为其分配的共享磁盘区域

Proposer:
  读取多个区域
  → 计算 quorum/历史状态
  → 写入更高 ballot/value

安全前提:
  共享存储读写/故障模型满足协议假设
  → 仍需要 quorum 与原子性/可见性条件
```

这张图最重要的是：共享磁盘承担了原来由消息和节点内存承担的部分协议状态，但它必须提供协议所依赖的读写可见性和持久性语义。共享存储也不是天然的共识写入服务，Proposer 仍然要依据 ballot、quorum 和历史约束判断哪个状态有效；磁盘写成功只说明一次存储操作完成，不自动说明一个共识值已经 chosen。

### 3. 为什么共享磁盘不能简单说成“比网络可靠”

共享存储自己也会坏：

- 设备故障；
- 存储路径故障；
- 写缓存与持久化边界；
- 部分写入；
- 存储网络分区；
- 不同节点看到的读写结果不一致。

所以 Disk Paxos 的本质不是“从网络升级到磁盘”，而是“把共识状态放到另一种共享媒介，并重新声明这个媒介的故障模型”。

### 4. 本节最该记住的结论：Disk Paxos 用共享存储承载 Acceptor 状态，换掉了部分消息通信成本，但共享设备的原子性、可见性、持久性和故障边界会成为新的协议前提

一句最短人话是：**多个办公室不互相打电话，而是共用一本带锁的登记簿；电话问题少了，但登记簿和存储柜成了新的关键基础设施。**

## 三、Cheap、Generalized、Flexible、Stoppable：变种各自换什么

### 1. 第三个朴素误解：剩下这些变种只是论文命名差异，核心算法基本一样

它们确实都围绕 Paxos 安全骨架展开，但每一种放宽的约束不同：

- Cheap Paxos 放宽常态硬件冗余；
- Generalized Paxos 放宽所有命令必须全序；
- Flexible Paxos 放宽 Prepare/Accept 必须使用同一种 quorum；
- Stoppable Paxos 放宽系统必须无限接受新决定。

所以读这些变种，最好的方法不是背名称，而是问：**它把哪笔账推迟了，哪条约束改写了。**

### 2. 四种路线的最小对照图

```text
Cheap Paxos:
  少数主处理器参与正常协议
  → 辅助处理器在故障时补位
  → 降低常态硬件成本, 恢复更复杂

Generalized Paxos:
  可交换/不冲突命令允许不同顺序
  → 只对不可交换命令建立顺序约束
  → 需要定义命令冲突/交换关系

Flexible Paxos:
  Prepare quorum 与 Accept quorum 可不相同
  → 安全交集条件必须满足
  → 可按读/写路径和拓扑优化

Stoppable Paxos:
  进入停止状态, 不再接受新决定
  → 为维护/升级提供安全边界
  → 停止本身也要被一致决定
```

### 3. Cheap Paxos：少花常态硬件，故障时多付恢复成本

Cheap Paxos 的核心取舍很直观：

- 正常运行时，让较少的主处理器参与；
- 故障时，再让辅助处理器补位；
- 用故障期间的恢复复杂度，换常态硬件成本下降。

它不是免费减少副本，而是把“常态冗余”与“故障恢复复杂度”重新交换。辅助处理器也不是普通热备节点：故障后需要重构协议参与集合、恢复可用 quorum，并在这个窗口里承受更长的恢复时间或活性下降。适不适合，取决于你更在意长期硬件成本，还是更在意故障时的恢复简单度与切换速度。

### 4. Generalized Paxos：命令可交换时，不必强求全序

如果两个命令在协议定义的状态机语义下满足交换性：

- 先执行 A 再执行 B；
- 先执行 B 再执行 A；
- 在相关状态、返回结果和业务约束上都保持等价；

那么系统就没有必要为它们强行建立同一个全局顺序。Generalized Paxos 尝试把全序约束缩小到真正不可交换的命令之间。单看一个最终状态样例并不足以证明交换性，还要说明命令对后续状态和可观察结果的影响。

但这条路最难的地方也在这里：**交换关系必须被准确声明。**

- 不同 key 不一定业务上就无关；
- 同一个 key 不一定所有操作都不可交换；
- 业务约束可能跨越多个物理对象。

所以 Generalized Paxos 的收益依赖于可靠的命令语义和冲突分析。

### 5. Flexible Paxos：不对称 quorum 不是任意 quorum

Flexible Paxos 的核心想法是：

- Prepare quorum 和 Accept quorum 不一定必须相同；
- 但跨阶段 quorum 必须满足安全交集条件。

这给了系统更多拓扑优化空间：

- 读路径和写路径可以有不同成本；
- 某些数据中心可以承担更多 Prepare；
- 某些场景可以降低一条路径的参与数量。

但它绝不是“两个 quorum 随便挑”：**安全要求的是跨阶段交集，不是每个阶段都简单多数，也不是每组参与者都任意可配。** Flexible Paxos 不是降低整体容错要求，而是把“同阶段必须相交”的限制改成“Prepare 与 Accept 之间必须相交”；降低一侧参与成本，可能会把成本转移到另一侧或降低可用性。

### 6. Stoppable Paxos：停止也必须是共识决定

很多系统维护时希望“先停住，不再接受新决定”。如果每个节点各自决定停止，就可能出现：

- 一部分节点认为系统已经停止；
- 另一部分节点仍在接受新值；
- 恢复后两边对停止边界理解不同。

Stoppable Paxos 把停止状态本身也纳入一致决定，让维护、升级、切换拥有一个可解释的协议边界。这里的停止通常意味着协议拒绝新的决定或进入安全维护状态，不等于所有节点立刻物理关机；恢复时仍要重新确认协议状态、成员和可接受的后续 quorum。

### 7. 本节最该记住的结论：Cheap Paxos 调整硬件冗余，Generalized Paxos 调整命令顺序，Flexible Paxos 调整 quorum 结构，Stoppable Paxos 调整运行状态；每次放宽一条约束，都要重新写清安全条件

## 四、选择矩阵：论文收益必须匹配系统约束

### 1. 第四个朴素误解：理论上低延迟，生产里就应该直接选 Fast Paxos 或 EPaxos

这是从论文结果到生产决策最容易跳过的一步：

- 纸面上少一轮消息；
- benchmark 里延迟很好；
- 所以直接上线。

问题是，变种收益高度依赖：

- 冲突率；
- 网络拓扑；
- quorum 形成时间；
- 回退频率；
- 故障恢复复杂度；
- 团队能不能把异常路径维护好。

### 2. 最小选择矩阵

```text
通用复制状态机:
  Raft / Multi-Paxos
  → 生态、理解和维护优先

低冲突/低延迟:
  Fast Paxos:
    → 主要优化消息轮次, 依赖 Fast quorum 与冲突回退
  EPaxos:
    → 主要优化多点提议与冲突命令依赖执行
  → 分别验证冲突率、跨地域延迟、quorum 和回退频率

共享存储:
  Disk Paxos
  → 先验证共享设备的故障/性能/运维

可交换命令多:
  Generalized Paxos
  → 先定义交换关系与执行语义

成本/维护模式:
  Cheap / Stoppable / Flexible
  → 评估故障时复杂度和成员变更
```

### 3. 为什么理论最优不等于生产最优

因为协议复杂度本身也要被监控、测试和运维：

- 快路径和慢路径是否可观测；
- quorum 条件是否可演练；
- 故障回退是否可恢复；
- 命令冲突率是否会随业务增长改变；
- 共享存储的风险是否比网络风险更可控。

没有代表性 workload 和故障模型验证，纸面收益很容易被冲突、网络、设备或运维成本抵消。

### 4. 本节最该记住的结论：变种选型必须先看故障模型、冲突率、拓扑和团队能力，再看论文里的延迟或硬件收益；没有回退路径和故障演练，理论优化可能只是把成本藏起来

## 五、把本篇收成一张图：Paxos 变种不是升级树，而是一张成本搬运图

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：Basic/Multi-Paxos 已经能工作，为什么还要发明一堆变种。答案已经闭环了。

Fast Paxos 用更强的 Fast/Classic quorum 交集换低冲突时少一轮消息；Disk Paxos 用共享存储承载 Acceptor 状态；Cheap Paxos 用故障时的恢复复杂度换常态硬件成本；Generalized Paxos 用命令交换性减少不必要的全序；Flexible Paxos 用跨阶段不对称 quorum 调整路径成本；Stoppable Paxos 则把停止本身纳入协议边界。它们不是从弱到强的升级树，而是面向不同约束的成本搬运图。

把这一切压成最短总图，就是：

```text
Basic / Multi-Paxos:
  经典 quorum + Promise/Accept

Fast:
  更大 quorum 换一轮延迟

Disk:
  共享存储承载 Acceptor 状态

Generalized:
  可交换命令减少全序

Flexible:
  不对称 quorum 调整路径成本

Cheap / Stoppable:
  调整硬件 / 运行状态与维护边界
```

所以本篇最该记住的一句话是：**Paxos 变种不是把共识变魔法，而是明确把成本从一个地方搬到另一个地方：延迟换 quorum，消息换共享存储，全序换依赖分析，硬件成本换恢复复杂度。**

## 六、几个最容易说错的地方

### Fast Paxos 就是少一轮、所有场景都更快？

不是。它依赖低冲突和更大 quorum，冲突时还要回退 Classic Round。

### Disk Paxos 让网络故障消失了？

不是。它把部分通信状态搬到共享存储，设备、路径、缓存和原子性又变成新的故障前提。

### Generalized Paxos 可以把不同 key 操作都当成可交换？

不是。交换性必须由命令语义和业务约束证明，物理 key 不同不等于业务一定无关。

### Flexible Paxos 可以任意选择 Prepare/Accept quorum？

不是。必须满足跨阶段 quorum 的安全交集条件。

### Stoppable Paxos 就是每个节点自己停机？

不是。停止本身也要进入一致决定，才能形成可解释的维护边界。

### 变种论文收益等于生产收益？

不是。冲突率、拓扑、故障回退、监控和团队维护成本都要一起验证。

## 收束：Paxos 家族真正展示的，不是算法越来越多，而是系统设计者不断重新安排“哪种代价值得支付”

回到开头那个问题：Basic/Multi-Paxos 已经能工作，为什么还要发明这么多变种。答案已经闭环了：因为不同系统面对的瓶颈不同。有人缺低延迟，有人缺硬件预算，有人缺全序并发，有人需要共享存储，有人需要把维护边界也纳入一致决定。Paxos 变种不是把共识变成没有代价的魔法，而是把代价重新放到更适合当前工作负载的位置。

这就是为什么说：**Paxos 变种不是把共识变魔法，而是明确把成本从一个地方搬到另一个地方：延迟换 quorum，消息换共享存储，全序换依赖分析，硬件成本换恢复复杂度。** 只要这条主线站稳，下一篇进入 2PC、3PC、XA、TCC 时，你就会更容易看清：分布式事务协议也不是“谁更强”，而是在原子提交、阻塞、补偿、幂等和可用性之间重新安排代价。
