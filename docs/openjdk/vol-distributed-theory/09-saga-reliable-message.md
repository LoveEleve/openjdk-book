## 现在真正该问的，不再是“能不能瞬时原子提交”，而是“如果跨服务本来就不可能永远同步，那系统怎样把失败显式变成可补偿、可重试、可对账的状态机”

上一讲我们已经把强协调路线和业务补偿路线的大框架分开了：

- 2PC/XA 用协调者和 Prepared 状态保住更强原子性；
- 3PC 试图用更多阶段和更强时间假设减少阻塞；
- TCC 把资源层长锁改写成业务级预留、确认和取消。

但很多真实业务并不适合这些强协调方案：

- 流程太长；
- 参与方太多；
- 外部系统无法提供 XA/TCC 接口；
- 锁住资源太贵；
- 用户更在意“最终结果正确”，而不是“所有资源在一个瞬间同时提交”。

这时系统要回答的新问题就不是：

“如何让多个资源像单机事务一样同时 commit？”

而是：

“既然不能依赖一个全局锁，那怎样通过补偿、可靠投递、重试、查询和对账，让最终状态仍然可解释？”

先把总图记住：

```text
Saga:
  长事务拆成本地事务 + 补偿动作
  → 暴露中间态
  → 用状态机和补偿收敛

本地消息表:
  业务记录 + 待发消息同库同事务
  → 后台扫描投递
  → 幂等消费

事务消息:
  half message
  → 本地事务
  → COMMIT / ROLLBACK message
  → 回查兜底

最大努力通知:
  push 通知
  + pull 查询/对账
```

这篇最该先记住的一句话是：**最终一致不是“放弃正确性”，而是把原子提交改写成可补偿步骤、可靠投递和可重试状态机；越少阻塞数据库，越多复杂度会转移到业务和运维。**

## 一、Saga：长事务拆成短事务，但中间态会暴露

### 1. 最朴素的错误世界：既然 2PC/XA 太重，那把长流程拆成几步，每步自己提交就行

这是很多系统面对跨服务事务时最自然的第一反应：

- 先订机票；
- 再订酒店；
- 再扣库存；
- 再支付。

每一步自己本地提交，看起来就把“大事务”自然拆散了。

问题在于，你只是把原子提交拆开了，却没有自动得到“失败后怎么收拾残局”的答案。只要最后一步失败，你前面已经成功提交的本地事务都不会自己消失。

所以 Saga 的难点从来不是“拆步骤”，而是：**每一步成功后，后续失败时，前面的状态怎么撤、谁来撤、撤到什么程度才算收敛。**

### 2. Saga 的最小补偿链

```text
T1: 订机票   ↔ C1: 取消机票
T2: 订酒店   ↔ C2: 取消酒店
T3: 扣库存   ↔ C3: 恢复库存
T4: 支付     ↔ C4: 退款/关闭支付单

执行:
  T1 → T2 → T3 → T4
  任一步失败:
    前向恢复(重试当前/后续)
    或向后恢复(按 Cn...C1 补偿)
```

这条图里最重要的不是“补偿 SQL”四个字，而是：

- 每个本地事务都必须有可解释的反向动作；
- 补偿顺序要和原流程严格对应；
- 补偿本身也可能失败、重试或需要人工接管。

### 3. 为什么 Saga 的难点不在“写几条补偿 SQL”

因为现实世界的补偿很少是数学逆操作：

- 退款不一定能瞬时到账；
- 优惠券回滚可能受规则限制；
- 机票取消可能产生手续费；
- 外部合作方接口可能只接受“再次发起撤销”，不支持真正原地回滚。

更麻烦的是，中间态会暴露：

- 机票已订；
- 酒店未订；
- 库存已扣；
- 支付未完成。

这意味着其他请求和用户页面都可能观察到这些“半完成世界”。所以 Saga 必须结合：

- 业务状态机；
- 语义锁；
- 幂等补偿；
- 人工兜底。

### 4. 一个更具体的失败场景：酒店预订失败，前面的机票和库存都得按规则逐步撤销

假设：

- T1 订机票成功；
- T2 订酒店失败；
- T3/T4 尚未开始；
- 你不能指望机票订单自己消失；
- 只能显式执行 C1，且 C1 可能因为外部航司接口暂时不可达而需要重试。

这时你看到的，不是一个“自动回滚”的原子世界，而是一条需要被持续收敛的补偿链。这里也要再补一刀：补偿动作并不总是机械地按 `Cn...C1` 逆序执行到完，真实系统还要看当前哪些子事务真的成功、哪些补偿已经落地、哪些需要人工介入。Saga 不是让失败消失，而是让失败变成一条可管理的业务流程。

### 5. 本节最该记住的结论：Saga 不是把全局事务变简单，而是把全局原子性改写成本地事务 + 补偿链；难点不在拆步骤，而在中间态暴露、补偿失败和业务语义的可逆程度

一句最短人话是：**Saga 像旅行社分步下单，每一步都单独确认，失败时靠一张逆序撤销清单把前面订单逐个取消。**

## 二、本地消息表：同库同事务，把“发消息资格”先写进数据库

### 1. 第二个朴素误解：下单后发 MQ 就行，只要消息队列够可靠，最终总会送到

这个直觉在工程里非常常见：

- 订单写库；
- 发送一条 MQ 给库存/营销；
- MQ 很可靠；
- 所以整体应该没问题。

真正危险的窗口是：**订单提交和发 MQ 之间。**

- 订单已经 commit；
- 应用还没来得及发消息就崩了；
- 消费侧永远看不到这笔本该存在的异步事件。

这时问题不是 MQ 不可靠，而是“这条消息到底有没有资格被发送”没有和订单记录绑在一个本地事务里。

### 2. 本地消息表的最小图

```text
本地事务:
  INSERT order(...)
  INSERT outbox_message(msg_id, payload, status=INIT)
COMMIT

后台投递器:
  扫描 status=INIT
  → 发送 MQ/HTTP
  → 成功: 标记 SENT
  → 失败: retry_count++ / 下次重试 / 告警

消费者:
  按 msg_id 做幂等去重
```

这张图最关键的地方是：**业务数据和“待发消息资格”同库同事务提交。**

也就是说，订单一旦成功落库，待发消息记录一定存在；至于消息什么时候真正发出，是后续投递器要解决的问题，而不是和订单原子性绑死在一瞬间。

### 3. 为什么本地消息表“简单”却很常用

因为它把最大的不确定性缩回单库事务里：

- 订单记录在；
- outbox 记录也在；
- 之后即使应用崩了，投递器重启后仍能继续扫到它。

这条路的代价也非常清楚：

- 要自己写扫描器；
- 要维护重试、清理和告警；
- 要处理重复投递；
- 要让消费者幂等。

所以本地消息表解决的是“消息是否应该发”，而不是“消费者处理是否一定成功”；它保证的是业务记录与待发消息资格的同库原子性，不替你解决跨库消费结果的一致性。

### 4. 一个更具体的失败场景：订单成功提交，应用进程在发 MQ 之前宕机

假设：

- 本地事务已经把 `order` 和 `outbox_message` 一起提交；
- 发送 MQ 的线程还没跑；
- 应用就被重启了。

如果没有本地消息表，这笔消息就彻底丢了；而有了 outbox，重启后的投递器仍能扫到 `status=INIT` 的记录，并继续发送。

### 5. 本节最该记住的结论：本地消息表的核心不是“消息发得快”，而是把“消息是否该发”缩回单库事务；它保证的是消息资格与业务记录同库提交，代价是投递器、重试、清理和幂等都要自己养

一句最短人话是：**本地消息表像订单系统给快递室留下一张待发货单；只要订单入账成功，这张单就一定存在，哪怕快递员稍后再来取。**

## 三、事务消息：让 MQ 参与“消息是否可见”的决策

### 1. 第三个朴素误解：事务消息就是 MQ 替你把本地消息表自动做了

事务消息确实在试图降低你自建 outbox 的工作量，但它不是“万能 outbox 替代品”。

它真正做的是：

- 先把消息写成消费者不可见的半消息；
- 等生产者本地事务完成；
- 再让 broker 根据生产者的提交/回滚决定，决定消息是否对消费者可见。

所以它内建的是“消息可见性决策”，不是“下游业务一定成功”。更关键的是，broker 并不天然知道生产者本地事务的最终真相；它最终仍要依赖生产者回查接口能正确、可重复地回答“本地事务到底 commit 了还是 rollback 了”。如果回查逻辑本身不可靠，broker 也只能继续把消息挂在未决状态上。

### 2. 事务消息的最小图

```text
Producer:
  发送 half message(消费者不可见)
  → 执行本地事务
  → COMMIT message 或 ROLLBACK message

Broker:
  若生产者迟迟未决
  → 发起事务回查
  → 询问生产者本地事务状态
  → 决定提交或回滚消息
```

这条链里最关键的角色不是消费者，而是 broker 的“可见性仲裁”。

### 3. 为什么事务消息不是“万能 outbox 替代品”

因为它只是把一部分可靠投递逻辑移进了消息系统：

- 回查要不要成功，仍然依赖生产者状态查询；
- 消费端仍然要幂等；
- 顺序消息、重复消费、下游补偿仍然存在；
- 系统也更深地绑定在特定 MQ 语义上。

所以它不是“消息事务自动帮你搞定了所有最终一致性问题”，而是“消息 broker 替你承担了消息可见性的那一小段协议责任”。

### 4. 一个更具体的失败场景：half message 已写入，生产者本地事务提交结果却迟迟没报回

假设：

- Producer 已经成功发送 half message；
- 本地事务执行过程中进程挂了；
- Broker 一直看不到 commit/rollback；
- 于是发起事务回查；
- 如果生产者无法给出明确本地状态，消息就会卡在 broker 的“未决可见性”里。

这时事务消息的难点，不是“有没有消息”，而是“消息什么时候可以被看见”，以及谁能提供足够证据让 broker 做决定。也就是说，事务消息把“消息资格”与“消息可见性”拆开了，但它没有绕开生产者本地状态的可证明性。

### 5. 本节最该记住的结论：事务消息把消息可见性决策内建到 MQ 协议里，但没有消灭幂等、回查、顺序和下游补偿问题；它降低了一部分 Outbox 负担，却增加了对消息中间件语义的依赖

一句最短人话是：**事务消息像快递站先收下一件“暂存包裹”，只有商家确认订单成功后才放上配送带；确认超时则由快递站回拨商家问状态。**

## 四、最大努力通知：接收方也要参与对账

### 1. 第四个朴素误解：通知发出去了，接收方没成功处理只是对方的事

这在系统边界上非常常见，尤其是银行回调商户、支付平台通知业务方这类场景：

- 发送方尽力通知；
- 接收方最好处理；
- 没处理上就多发几次。

但如果接收方无法确认自己有没有收到、有没有处理成功，最终一致就永远缺一半。

### 2. 最大努力通知的双通道图

```text
发送方:
  发送通知
  → 失败/超时则重试 N 次
  → 保留状态与告警

接收方:
  幂等处理通知
  → 若没收到/不确定
     主动 queryOrder/queryStatus
     与发送方对账

双通道:
  push 通知
  + pull 查询校对
```

这套模式最关键的地方是：**最终一致不能只靠 push，还要有 pull 校对。**

因为“通知没成功”与“通知其实到了但我没处理完”这两种情况，对接收方来说都需要进一步查证。更重要的是，查出来的远端状态不能停留在“我知道了”，而必须和本地业务状态机对齐：

- 如果本地还没处理，就按幂等规则补处理；
- 如果本地已经处理过，就拒绝重复推进；
- 如果本地状态和远端冲突，就进入对账/人工修复路径。

### 3. 为什么最大努力通知不适合“必须一次提交完成”的核心事务

因为它接受的是：

- 短期不一致；
- 事后重试；
- 事后查询；
- 最终对账。

这非常适合：

- 支付回调；
- 账单通知；
- 对外合作方交互；
- “最终知道结果即可”的状态同步。

但它不适合：

- 必须在一次请求里立即给出全局原子结果的内部扣款链路。

### 4. 一个更具体的失败场景：商户没收到支付回调，但查询接口里订单已成功

假设：

- 支付平台已经成功扣款；
- 回调请求发出后超时；
- 商户没收到明确结果；
- 如果商户只等下一次 push，就可能长时间处于未知；
- 如果商户还能主动 `queryOrder`，就能把状态拉回来，对账补齐。

这说明最大努力通知真正依赖的是双通道：发送方尽力推，接收方也必须会查，而且查询结果还必须重新并入本地状态机，而不是只停留在“人工知道了结果”这一层。

### 5. 本节最该记住的结论：最大努力通知不是严格消息事务，而是一种“通知 + 查询 + 对账”的兜底路线；它接受短期不一致，把最终收敛责任分给发送方和接收方共同承担

一句最短人话是：**最大努力通知像快递员多次敲门并留电话，收件人不确定时再主动打电话确认；它尽力而为，但不承诺第一次一定交付。**

## 五、把本篇收成一张图：最终一致路线不是更弱，而是把失败显式化

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：订单已写库，但发券消息没送到；如何在不锁住所有资源的前提下，最终把订单、库存、支付和通知对平。答案已经闭环了。

Saga 把长事务拆成本地事务和补偿动作，但中间态会暴露；本地消息表把“发消息资格”缩回单库事务，代价是自建投递器和幂等；事务消息把消息可见性决策内建到 MQ 协议里，但仍依赖回查和下游幂等；最大努力通知则把收敛责任进一步拆成 push 通知与 pull 对账双通道。所有这些路线都不再追求一个瞬时的全局原子提交，而是把失败显式变成状态、流程、重试和补偿。

把这一切压成最短总图，就是：

```text
Saga:
  本地事务 + 补偿动作
  → 暴露中间态, 需要业务状态机

本地消息表:
  单库事务 + 后台投递
  → 最朴素稳健, 需要自建投递器/清理器

事务消息:
  MQ half message + 回查
  → 降低自建轮询成本, 增加中间件耦合

最大努力通知:
  push + query
  → 适合外部回调/对账场景
```

所以本篇最该记住的一句话是：**最终一致方案的关键不是“异步”两个字，而是如何把失败显式变成状态，并给出重试、补偿、幂等和对账路径；越少阻塞数据库，越多复杂度会转移到业务和运维。**

## 六、几个最容易说错的地方

### Saga 就是把大事务拆成几步，失败时回滚几条 SQL？

不是。真正难的是中间态暴露、补偿失败、语义锁和业务状态机，而不是补一条反向 SQL。

### 本地消息表只是过时土办法？

不是。它的价值恰恰在于把“消息是否该发”缩回单库事务，这一点非常稳。

### 事务消息能替代所有 Outbox 方案？

不是。它只把消息可见性决策内建到 MQ，幂等、回查、顺序和消费者处理仍需自己承担。

### 最大努力通知就是不断重试回调？

不是。它真正成立靠的是 push 通知 + pull 查询 + 对账双通道。

### 最终一致就是放弃正确性？

不是。它是把正确性从“瞬时原子提交”改写成“可补偿、可重试、可对账、最终收敛”。

## 收束：最终一致路线真正做的，不是降低要求，而是把“失败后怎么办”从协议深处拖到业务表面

回到开头那个问题：订单已写库，但发券消息没送到，怎样最终把账对平。答案已经闭环了：当系统不再依赖全局锁和瞬时原子提交，它就必须把失败显式变成状态机、补偿动作、待发消息、回查流程和对账策略。最终一致方案不是比强事务更“弱”，而是把原本隐藏在协议里的失败成本，提前暴露给业务和运维去管理。

这就是为什么说：**最终一致方案的关键不是“异步”两个字，而是如何把失败显式变成状态，并给出重试、补偿、幂等和对账路径；越少阻塞数据库，越多复杂度会转移到业务和运维。** 只要这条线站稳，下一篇进入 Spring、ShardingSphere、Hmily、Seata 等框架实战时，你就不会再把它们看成“框架帮你自动解决分布式事务”，而会先追问：这些框架到底把哪一部分协议成本帮你包了，又把哪一部分复杂度留给了业务代码。
