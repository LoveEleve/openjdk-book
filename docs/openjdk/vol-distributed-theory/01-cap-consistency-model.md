## 现在真正该问的，不再是“服务有没有拆开”，而是“服务拆开之后，网络断了、请求重试了、节点状态不同了，系统到底还向用户承诺什么”

很多团队把系统从单体拆成微服务以后，最先感受到的不是“优雅”，而是困惑。

明明在单体里这件事很简单：

- 开一个本地事务；
- 扣库存；
- 生成订单；
- 支付成功就提交；
- 失败就回滚。

逻辑看起来完整，数据看起来一致，开发者也很有安全感。

可一旦这条链路拆成：

- 订单服务；
- 库存服务；
- 支付服务；
- 甚至消息队列、搜索索引、积分服务；

问题突然就变味了。你开始遇到一连串单机时代不需要认真思考的问题：

- 订单服务调用库存服务时超时了，到底是库存没扣，还是扣了但响应丢了？
- 支付服务成功了，但订单状态没更新，系统该相信谁？
- 主库刚写成功，读请求被路由到副本，为什么页面还显示旧库存？
- 一个用户连点两次支付，为什么系统会出现“扣了两次库存，但只出了一单”？

这时候很多人会本能地说：

“我们缺的是分布式事务。”

这句话有时对，但还不够深。因为在更底层，你真正缺的是一套共同语言，去定义：

- 网络断开时你到底是继续服务，还是暂停一部分请求；
- 用户能否读到旧值；
- 自己刚写的值能否立刻读回来；
- 各节点状态不同步时，你到底承认谁是“真相”；
- 一个本地事务边界出了本机以后，为什么就不再自动成立。

这就是 CAP 与一致性模型存在的原因。它们不是为了面试背缩写，而是为了回答：**在分布式里，什么叫“看起来还算正确”，什么叫“系统准备承诺的边界”。**

先把总图记住：

```text
网络可能分区
  → CAP / PACELC / BASE
  → 定义故障与正常状态下的一致性 / 可用性 / 延迟取舍

读写语义可能不同
  → 线性一致 / 顺序一致 / 因果一致 / 最终一致
  → 客户端中心一致性: read-your-writes / monotonic reads / monotonic writes

数据一旦扩展
  → 分片 / 复制 / 读写分离
  → 旧读、冲突、路由边界开始出现

服务一旦拆开
  → 本地事务不再自动覆盖全链路
  → 需要幂等、补偿、状态机、Outbox / Saga / 2PC 等方案
```

这篇最该先记住的一句话是：**分布式系统的难点不是服务数量，而是网络可能分区、节点状态可能不同、一个本地事务无法覆盖所有服务；CAP 和一致性模型回答的不是“哪个系统更高级”，而是故障发生时系统到底准备向用户承诺什么。**

## 一、CAP：网络分区发生时，系统必须暴露取舍

### 1. 最朴素的错误世界：CAP 就是给系统贴 CP、AP、CA 三种标签

这是 CAP 最常见也最偷懒的打开方式：

- 这个数据库是 CP；
- 那个数据库是 AP；
- 某个系统据说是 CA。

看起来像掌握了概念，实际上经常是在回避真正的问题。尤其 `CA` 这类说法最容易误导：一旦你认真把 P 当成分布式现实约束，讨论重点就不再是“有没有一个稳定工作的 CA 分布式类别”，而是“分区发生时系统准备怎么退化”。因为 CAP 真正讨论的，不是“系统平时长什么样”，而是：

**当网络分区真的发生时，你准备怎样在一致性和可用性之间做选择。**

如果你不先把“故障时怎么办”说清，给系统贴再多标签，也只是分类游戏。

### 2. CAP 的最小故障选择图

```text
C(Consistency):
  读取满足系统定义的最新/线性化语义

A(Availability):
  每个非故障请求最终得到响应

P(Partition tolerance):
  网络分区/消息丢失时系统仍需做选择

发生 P:
  选择更强 C
    → 可能拒绝/等待部分请求
  选择更高 A
    → 可能返回旧值/冲突值
```

这张图最关键的地方是：P 不是一个可选项，而是分布式系统迟早会遇到的现实。你真正能选的，是：

- 分区发生时，宁可拒绝一部分请求，也要保证更强的一致性；
- 还是宁可继续响应一部分请求，也接受旧值、冲突或补偿成本。

### 3. 为什么 CAP 不是“三选二”的产品排行榜

因为现实系统远比教科书里的三角形更复杂：

- 一致性有多种语义强弱；
- 可用性不只是“响应不响应”，还包括延迟和体验；
- 分区不只是“完全断网”，还可能是抖动、丢包、半失联；
- 业务还能做补偿、重试、只读降级和人工对账。

所以 CAP 的价值不是帮你给产品排名，而是帮你强迫自己面对一个问题：**断桥时到底承认哪一笔账，拒绝哪一类请求。**

### 4. 一个更具体的失败场景：订单节点和库存节点断链后，系统既想继续下单，又想所有读都立刻看到最新库存

假设：

- 订单服务和库存服务分居两个机房；
- 机房之间突然断链；
- 业务又要求“用户下单不能失败”；
- 同时还要求“所有页面都必须立刻显示全局最新库存”。

这时问题不是实现得还不够聪明，而是要求本身在分区场景下互相拉扯：

- 你继续接单，就可能接受了和另一侧不同步的状态；
- 你暂停接单，就伤害了可用性；
- 你想两边都立刻知道对方最新写入，在断链时本来就没有免费方案。

CAP 的价值，就是逼你把这种取舍提前说清，而不是等线上断桥时临时相信奇迹。

### 5. 本节最该记住的结论：CAP 不是系统标签，而是分区故障下的一套选择框架；它逼你先定义故障时的承诺边界，再诚实回答愿意付哪种代价

一句最短人话是：**两座城市断桥时，必须决定是暂停售票保证两边账本一致，还是继续售票并接受稍后对账；断桥时两边都立刻知道全部最新交易并继续无损营业，不是免费选项。**

## 二、PACELC 与 BASE：网络正常时，系统也还在为延迟和一致性付账

### 1. 第二个朴素误解：只要没有分区，分布式系统就能同时强一致、低延迟、低成本地工作

很多人理解 CAP 后，会自然滑向另一个误解：

“那只要网络正常，问题不就解决了吗？”

可现实系统即使在没有明显分区时，也仍然要在：

- 等更多副本确认；
- 更快向用户返回；
- 更强读新鲜度；
- 更低基础延迟；

之间持续取舍。

### 2. PACELC 的最小图

```text
P:
  Partition 时 → Availability vs Consistency

Else:
  正常无分区时 → Latency vs Consistency

BASE:
  Basically Available
  Soft State
  Eventually Consistent
  → 允许中间状态, 通过异步复制/修复最终收敛
```

PACELC 的价值，是提醒你：就算不分区，系统仍然在为延迟和一致性付账。BASE 的价值，则是提醒你：最终一致不是“以后会好”，而是“允许中间状态，同时必须有收敛机制”。这里还要补一句边界：BASE 更像一种工程立场或设计倾向，不是和线性一致、顺序一致、因果一致并排的一条严格理论阶梯节点。

### 3. 为什么“最终一致”不等于“先乱着，反正以后总会一致”

这是 BASE 最容易被误解的地方。

最终一致真正需要你说清楚的是：

- 什么时候开始算“最终”；
- 冲突怎么解决；
- 是否保证读己之写；
- 是否保证单调读；
- 修复和补账流程在哪里；
- 在不一致窗口里用户能看到什么。

所以最终一致描述的是一种时间性质，不是对业务正确性的自动担保。商品浏览可能接受短暂旧读，支付和库存通常不行。

### 4. 本节最该记住的结论：CAP 只讨论分区时的取舍，PACELC 继续把正常状态下的延迟/一致性取舍也拉进来；BASE 不是“随便乱，最后会好”，而是“允许中间状态，但必须定义收敛机制”

一句最短人话是：**BASE 像多地库存账本允许短暂不同，但必须有补账、冲突处理和最终对平流程；“以后会一致”不是没有流程。**

## 三、一致性模型：用户到底读到什么，不是一个 0/1 问题

### 1. 第三个朴素误解：一致性只有两种，要么强一致，要么最终一致

这个误解非常普遍，因为“强”与“弱”最容易记。

可真正设计系统时，你经常需要区分很多不同层次：

- 是不是必须满足真实时间顺序；
- 只要求存在一个全局序列，还是必须紧贴现实时间；
- 有因果关系的操作要不要严格有序；
- 用户自己刚写的值能不能马上读回来。

如果只用“强/弱一致”两个词，很多决策会被说得过粗。

### 2. 一致性模型的最小阶梯

```text
Linearizability:
  每个操作看起来在某个真实时间点原子发生
  → 读不能返回已被覆盖的旧值(满足实时顺序)

Sequential consistency:
  存在一个全局操作序列符合各线程自身顺序
  → 不一定满足真实时间顺序

Causal consistency:
  有因果关系的操作保持顺序
  → 无因果操作可并行/不同序

Eventual consistency:
  没有新写入后, 副本最终收敛

客户端中心:
  read-your-writes / monotonic reads / monotonic writes
  → 从用户视角补强体验
```

这张图最关键的地方在于：一致性不是一个按钮，而是一条阶梯。不同系统、不同操作，真正要的是阶梯上的不同层级。这里也要补一刀：`read-your-writes`、`monotonic reads`、`monotonic writes` 更像客户端体验侧的补强承诺，不应简单理解成和线性一致、顺序一致处于同一理论维度的“强弱档位”。

### 3. 为什么线性一致不是“所有副本永远同时相同”

这是一个很容易被望文生义误解的点。线性一致说的是：

- 从外部观察，每个操作像在某个真实时间点原子发生；
- 后发生的读，不该再看见已被覆盖的旧值。

它不是说所有副本在物理时间上永远完全同步，而是说系统要向观察者提供这样的可见语义。做到这一点，往往需要协调、共识、特定路由或拒绝一部分请求。

所以一致性模型描述的是**可观察结果**，不是内部实现外观。协议只是实现手段，不是语义本身。

### 4. 为什么客户端中心一致性能在工程上非常重要

很多时候业务并不需要全局线性一致，但非常在意：

- 我刚改过昵称，刷新页面能不能立刻看见；
- 我刚支付成功，订单页能不能别先显示“未支付”；
- 我已经看到一个更新过的结果，后面能不能别又退回旧值。

这些问题常常更贴近用户感知，因此 `read-your-writes`、`monotonic reads`、`monotonic writes` 这类客户端中心一致性，在工程上经常比抽象的大词更直接。

### 5. 本节最该记住的结论：一致性模型描述的是“用户到底读到什么”的可观察语义，从线性一致到最终一致再到客户端中心保证是一条阶梯，而不是强弱二元对立

一句最短人话是：**线性一致像银行柜台有一条严格时间线，因果一致像聊天消息按回复关系排序，最终一致像各分店账本稍后对齐。**

## 四、分片、复制与读写分离：旧读和冲突从哪里来

### 1. 第四个朴素误解：写主读从就够了，副本只是“便宜一点的读节点”

这是很多系统在最初扩容时的自然直觉：

- 写请求去主库；
- 读请求去副本；
- 主从复制会把数据跟上。

问题在于，一旦你真正开始读写分离，你马上会遇到：

- 副本延迟；
- 读己之写失败；
- 故障切换后路由错乱；
- 多主冲突；
- 分片后跨片查询和跨片事务。

也就是说，旧读和冲突不是“系统坏了才有”，而是扩展策略本身就会引入的新边界。

### 2. 分片/复制的最小扩展图

```text
分片:
  Range / Hash / 一致性哈希等
  → 降低单机容量/流量
  → 跨片查询/事务/聚合变复杂

复制:
  同步 / 半同步 / 异步
  → 读可扩展 / 容灾
  → 延迟副本可能旧读

读己之写:
  关键读回主
  或等待副本追上位点/GTID
  或携带 session consistency token

多主冲突:
  LWW / 版本向量 / CRDT / 应用合并
  → 选择取决于业务是否允许丢失/合并
```

### 3. 为什么读写分离不是简单“写主、读从”

因为路由必须同时考虑：

- 事务上下文；
- 用户是否要求 read-your-writes；
- 副本延迟；
- 故障切换后连接状态；
- 连接池/代理缓存的旧拓扑。

所以写主读从从来不是一条完整方案，它只是一个开始。

### 4. 为什么多主冲突不能总靠 LWW 糊过去

LWW（last-write-wins）看起来简单：时间戳最新的赢。

但它真正隐含的问题是：

- 时钟可能偏；
- 字段可能需要合并而不是覆盖；
- 旧写被丢掉可能意味着真实业务信息丢失。

所以多主冲突处理一定要回到业务语义：你到底是能接受覆盖，还是要合并，还是要显式冲突暴露。

### 5. 本节最该记住的结论：分片和复制会把旧读、冲突和路由边界一起带进系统；扩展不是把压力平均摊开，而是把新的语义成本重新引入

## 五、分布式事务与并发控制：本地 `@Transactional` 为什么跨不了服务

### 1. 第五个朴素误解：本地事务都已经有了，跨服务只要调用顺序写对，就自然也能保持原子性

这是很多业务系统从单体拆成微服务后最容易踩的坑。

在单机里：

- `BEGIN`；
- 多条 SQL；
- `COMMIT/ROLLBACK`；

同一个资源管理器能统一控制。

可一旦跨服务，世界立刻变成：

- Service A 本地提交；
- RPC 调用 Service B；
- B 可能超时；
- B 可能已提交但响应丢失；
- 调用方无法光靠超时异常判断“远端到底做没做”。

这时本地事务的直觉就断了。

### 2. 最小跨服务事务图

```text
单机:
  BEGIN → 多条 SQL → COMMIT/ROLLBACK
  → 同一资源管理器可统一控制

跨服务:
  Service A 本地提交
  → RPC Service B
  → B 可能超时/重试/已提交但响应丢失
  → 需要幂等、状态机、Outbox/Saga/2PC 等方案

并发控制:
  悲观全局锁 → 协调器瓶颈
  乐观版本/CAS → 冲突重试
  MVCC/时间戳 → 读版本与提交顺序
```

### 3. 为什么分布式事务不是“给本地注解再套一层”

因为跨服务之后，真正新增的问题不是 SQL 本身，而是：

- 网络超时的语义不明确；
- 多个资源管理器有独立日志；
- 各服务故障状态彼此不同步；
- 幂等、重试和补偿都得显式设计。

所以 2PC、Saga、Outbox/TCC 这些方案不是“可选装饰”，而是在回答：当本地原子性无法天然跨网络时，还能怎样重组正确性。

最小业务反例其实很简单：订单服务本地事务已经把订单状态写成“待扣库存”，随后调用库存服务扣减库存；库存服务本地事务已经提交成功，但响应在网络上丢了。此时订单服务看到的是超时异常，可这个异常并不等价于“库存没扣”。如果它天真地重试，而链路里又没有幂等键、去重和状态机，你就可能得到“库存扣了两次，订单状态却只推进了一次”的结果。真正困难的地方，不在本地 ACID，而在跨网络以后“调用失败”和“远端未执行”不再是同一句话。

### 4. 一个更具体的失败场景：库存服务已经扣成功，但订单服务以为失败并重试

假设：

- 订单服务调用库存服务扣库存；
- 库存服务本地事务已提交；
- 但响应在网络上丢了；
- 订单服务超时后以为“扣库存失败”，于是重试；
- 如果没有幂等键和状态机，你就可能看到重复扣减。

这时系统缺的不是“再多一层重试”，而是对“超时 != 未执行”的承认，以及由此引出的幂等、去重、补偿和状态机设计。

### 5. 本节最该记住的结论：本地事务边界不会自动穿过网络；跨服务后，真正要解决的是幂等、重试语义、补偿和状态机，而不是把 `@Transactional` 当作跨服务魔法

一句最短人话是：**本地事务像一个柜台一次盖完所有章，分布式事务像多个城市分别盖章；快递可能丢回执，所以必须额外设计编号、幂等和补偿流程。**

## 六、把本篇收成一张图：分布式理论不是背概念，而是定义故障时你到底承诺什么

现在可以把整篇彻底收回来。

一开始我们要解决的问题是：订单为什么可能扣两次库存，系统到底缺的是事务、幂等还是一致性模型。答案已经闭环了。

CAP 先逼你面对网络分区下的一致性/可用性选择；PACELC 和 BASE 告诉你即便网络正常，也仍在为延迟、一致性和收敛流程付账；一致性模型进一步说明“用户到底读到什么”不是一个 0/1 问题；分片、复制和读写分离把旧读、冲突和路由边界带进系统；而分布式事务与并发控制则说明，本地事务语义一跨服务就必须重新组织。

把这一切压成最短总图，就是：

```text
故障模型
  → CAP / PACELC 选择一致性 / 可用性 / 延迟
  → 一致性模型定义读写承诺
  → 分片 / 复制决定数据放置与副本进度
  → 分布式事务 / 并发控制决定跨服务修改
  → 业务幂等 / 补偿 / 监控把理论落地
```

所以本篇最该记住的一句话是：**分布式系统的难点不是服务数量，而是网络可能分区、节点状态可能不同、一个本地事务无法覆盖所有服务；CAP 和一致性模型回答的不是“哪个系统更高级”，而是故障发生时系统到底准备向用户承诺什么。**

## 七、几个最容易说错的地方

### CAP 就是系统的永久标签？

不是。它讨论的是分区故障发生时的一致性与可用性取舍，不是平时的产品排行榜。

### 最终一致就是“先乱着，最后自然会好”？

不是。它必须配套冲突解决、收敛条件、读己之写和补账流程。

### 线性一致就是所有副本永远同时相同？

不是。它描述的是对外可观察的操作语义，而不是内部副本物理同步外观。

### 写主读从只是简单路由问题？

不是。它还涉及副本延迟、读己之写、事务上下文和故障切换后的路由边界。

### 本地 `@Transactional` 理论上能扩展成跨服务原子性？

不是。网络超时让“失败”和“未执行”不再等价，跨服务后必须额外引入幂等、补偿和状态机设计。

## 收束：分布式的第一课，不是背共识算法，而是先学会承认系统会在故障和延迟前暴露取舍

回到开头那个问题：订单为什么可能扣两次库存，系统到底缺的是事务、幂等还是一致性模型。答案已经闭环了：它缺的首先不是某一种具体中间件，而是对分布式边界的诚实定义。只要网络会抖、节点会分裂、请求会重试，本地事务直觉就不再足够。你必须先定义故障时的承诺，再反推复制、路由、事务和补偿方案。

这就是为什么说：**分布式系统的难点不是服务数量，而是网络可能分区、节点状态可能不同、一个本地事务无法覆盖所有服务；CAP 和一致性模型回答的不是“哪个系统更高级”，而是故障发生时系统到底准备向用户承诺什么。** 只要这条共同语言站稳，后面进入故障模型、时钟、Paxos、Raft、事务和广播时，你就不会再把它们看成一堆分散名词，而会理解它们都在试图回答同一件事：系统如何在不可靠世界里仍保持可解释。
