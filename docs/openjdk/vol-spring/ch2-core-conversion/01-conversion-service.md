# Spring 为什么不直接 `Integer.parseInt`：`ConversionService` 如何把字符串、安全类型和泛型集合接成一条统一转换链

> 本文基于 Spring Framework 6.x 当前源码。本文只讲 Spring 类型转换主线的第一层：为什么容器不能把配置绑定、`@Value` 注入、MVC 参数解析里的类型转换都散落成一堆 `parseXxx()` 调用，而必须引入 `ConversionService`、`Converter` 家族、`TypeDescriptor`、`GenericConversionService` 与 `TypeConverterDelegate` 这一整套统一机制。`Environment` 如何先把 `${...}` 解析成字符串、MVC 参数解析器如何在请求链里调用这套机制，会在后续篇章继续展开。

## 为什么一个看起来很普通的“字符串转整数”，最后会长成 Spring 的一整条转换主线

第一次接触 Spring 的类型转换时，很多人都会本能地把它想简单。

表面上看，场景似乎都差不多：

- `@Value("${server.port}") int port`
- `@RequestParam("page") int page`
- `@ConfigurationProperties` 里把 `"10s"` 绑定成 `Duration`
- 把 `"1,2,3"` 绑定成 `List<Integer>`

如果站在普通 Java 程序的视角，这类问题看上去好像完全可以直接写死：

- 转 `int` 就 `Integer.parseInt()`
- 转 `long` 就 `Long.parseLong()`
- 转布尔就 `Boolean.parseBoolean()`

这样想并不蠢，因为对单个、局部、一次性的转换来说，它往往确实够用。

可一旦把视角切到 Spring 这种容器框架，问题就会马上变得完全不同。

第一层变化是：**Spring 面对的不是一种转换，而是一整族“值语义转换”。**

这里的“值语义”很关键。

因为 Spring 要处理的并不只是：

- `String -> int`

还包括：

- `String -> Enum`
- `String -> Duration`
- `String -> Resource`
- `String[] -> List<Long>`
- `Collection<A> -> Collection<B>`
- 带注解、带泛型、带嵌套容器语义的转换
- 甚至某些并非字符串起点，而是“一个已有对象如何进入另一个更符合容器语义的表示”

也就是说，Spring 真正统一的不是“字符串怎么 parse”，而是：

- 一个值现在以什么形态到来
- 它在当前上下文里应该被理解成什么目标语义
- 后续该由哪种转换协议把它推进过去

这样再回头看 `@Value("${server.port}") int port`，它才不只是“把字符串转成整数”的小技巧，而是整套值语义转换主线里最容易被看见的一个入口。

因此，一旦把转换放回容器环境，它就不再是“我会不会调某个 parse 方法”的问题，而变成：

**系统如何在很多不同入口里，用同一套规则组织不同形状的值转换。**

第二层变化是：**转换不再只是工具调用，而是容器契约的一部分。**

对 Spring 来说，转换发生的位置并不统一：

- Bean 属性填充时会发生
- `@Value` 注入时会发生
- MVC 参数绑定时会发生
- `@ConfigurationProperties` 绑定时会发生
- 某些集合元素、数组元素、嵌套对象属性里也会继续发生

如果每条主线都各自写一套转换逻辑，最后一定会出现几种很典型的失控：

- 同样的输入在不同入口表现不一致
- 一种新类型支持了这里，忘了支持那里
- 集合、泛型、嵌套容器转换到处复制逻辑
- 错误信息、失败语义、扩展方式互相冲突

所以 Spring 真正要解决的，不只是“怎么把一个值转成另一个值”，而是：

**如何让整套容器都依赖同一个类型转换协议。**

第三层变化是：**转换不只关心类，还要关心“这个类在什么上下文里出现”。**

这也是很多人第一次看 Spring 转换体系时最容易低估的一点。

比如：

- `String -> Integer` 很简单
- 但 `String -> List<Integer>` 就不是只看目标类 `List.class` 能解决的

因为真正重要的不只是“目标是个 List”，还包括：

- 里面元素是什么类型
- 源值是不是逗号分隔字符串
- 是不是还带着字段注解、方法参数注解等附加语义

这就意味着，Spring 要管理的不是“裸类之间的转换”，而是更丰富的类型描述。

因此，本文真正要回答的问题不是“Spring 有个 `ConversionService` 做类型转换”，而是：

**为什么对 Spring 来说，一个看似简单的值转换问题，最后必须被提升成一套统一入口 + 多形态转换器 + 泛型类型描述 + 容器桥接的机制？**

## 先看失败方案：为什么 `parseXxx()`、大 `if/else` 和“局部自己转”都不够

理解 Spring 的转换体系，最好的方式不是先背接口，而是先看几种看起来非常自然、但一放到容器里就会失效的朴素方案。

### 失败方案一：每种基础类型都直接调用 `parseXxx()`

这是最符合普通业务代码直觉的方案。

因为对单个值来说，很多转换确实都长得像：

- `Integer.parseInt("8080")`
- `Long.parseLong("42")`
- `Boolean.parseBoolean("true")`

如果问题永远只停在这里，那 Spring 根本不需要一整套转换体系。

但问题在于，容器面对的类型远远不止这些基础数值。

一旦继续往外扩，马上就会出现几类 `parseXxx()` 无法优雅覆盖的场景：

- `String -> Enum`
- `String -> Charset`
- `String -> Locale`
- `String -> Duration`
- `String -> Collection<T>`
- `String -> Optional<T>`

也就是说，`parseXxx()` 的真正问题不是“功能太少”，而是它只适合一种非常局部的转换文化：

- 每个类型自己暴露一个静态解析入口
- 调用方提前知道该调哪一个
- 转换上下文基本不重要

但 Spring 需要的是另一种能力：

**调用方先只提出“我现在要从 A 转到 B”，而不是自己决定该调用哪个具体工具方法。**

换句话说，`parseXxx()` 更像“单点工具”，不是“容器级转换协议”。

### 失败方案二：那就做一个巨大的 `if (targetType == ...)` 分发表

如果意识到 `parseXxx()` 太分散，第二种很自然的思路就是：

- Spring 自己维护一个大分支
- 目标是 `Integer.class` 就走这里
- 目标是 `Long.class` 就走那里
- 目标是 `Boolean.class` 再走另一条路

这个方案在早期也许能跑，但它会很快撞上两个结构性问题。

第一个问题是：**扩展性崩掉。**

只要有新类型、新模块、新框架扩展，核心分发表就必须继续长大。最后容器内部会出现一个不断膨胀的“类型大全”。

第二个问题是：**很多转换不是一对一静态分支。**

比如：

- `String -> Integer/Long/Short/BigDecimal` 本质是一类问题
- `Collection<S> -> Collection<T>` 又是另一类“结构化转换”问题
- `Object -> Optional<T>` 更像包装协议问题

如果全塞进一个大分支，最后不是分支爆炸，就是逻辑重复。

所以 Spring 真正需要的不是“中央硬编码所有转换”，而是：

**把转换定义和转换调度拆开。**

调用方只提需求；具体哪种转换器来接手，由注册表和查找策略去决定。

### 失败方案三：每个上层入口自己做自己的转换

还有一种更隐蔽、也更危险的朴素方案：

- `@Value` 那边自己搞一套
- MVC 参数绑定自己搞一套
- 配置绑定再搞一套
- Bean 属性填充如果需要再单独补一套

这个方案的最大问题，不在于代码多，而在于它会把 Spring 最珍贵的一种能力彻底打碎：

- **同一套类型语义在不同入口保持一致**

一旦每个入口自己转换，就会马上出现：

- 这里支持 `String -> Duration`
- 那里不支持
- 这里的集合拆分规则和那里不一样
- 这里失败抛这个异常，那里抛另一个

也就是说，最后丢掉的不只是“代码复用”，而是整个框架对类型转换的统一语言。

所以 Spring 在这里真正要做的，不是简单封装几个工具类，而是：

**先在框架内部建立一套统一转换协议，再让不同入口把自己的值问题都挂到这套协议上。**

## Spring 类型转换的最小总图

如果把这条主线先压缩成最小模型，它可以写成下面这样：

```text
source value
   -> ConversionService
   -> converter lookup
   -> matching Converter / ConverterFactory / GenericConverter
   -> converted target value
```

如果再换一种更容易理解的拆法，这条链可以分成四段职责：

```text
[统一入口]
ConversionService

   ->

[转换器家族]
Converter / ConverterFactory / GenericConverter

   ->

[类型语义]
TypeDescriptor

   ->

[注册与调度]
GenericConversionService

   ->

[容器桥接]
TypeConverterDelegate
```

这张图最重要的价值，不是让读者记住几个接口名，而是先把五个问题分开：

### 一、统一入口

回答：调用方究竟依赖哪一个稳定协议，而不是依赖哪个具体转换器？

### 二、转换器家族

回答：为什么 Spring 不只要一种 `Converter`，而要三种不同形态？

### 三、类型语义

回答：为什么只看 `Class<?>` 还不够，泛型和注解上下文为什么也要进来？

### 四、注册与调度

回答：这么多转换器是怎么被组织、查找、缓存和命中的？

### 五、容器桥接

回答：Bean 注入、`@Value`、属性填充为什么最终都能复用同一套转换体系？

只要先把这五层职责分开，`ConversionService` 就不再像“Spring 的 parse 工具箱”。

## 一、`ConversionService`：Spring 要的不是“怎么转”，而是“先统一怎么提问”

`ConversionService` 的定义位置是：

- `org/springframework/core/convert/ConversionService.java:29`

它最关键的地方，不是方法多，而是方法少。

从接口层面看，它反复围绕的其实就是两个问题：

- `canConvert(...)`
- `convert(...)`

这说明 Spring 在第一层抽象上的取舍非常明确：

**调用方不该先关心具体转换器是谁，而该先提出两个统一问题：我能不能转？如果能，结果是什么？**

这一步看起来简单，实际上非常关键。因为它把：

- `@Value`
- MVC 参数解析
- 配置绑定
- Bean 属性填充

这些不同来源的调用者，先统一成了同一种姿态：

- 我手里有源值
- 我知道目标类型
- 剩下的转换细节交给 Spring 的转换体系

这也解释了为什么 `ConversionService` 不能被理解成“某种转换器的集合接口”。

它更像一个统一问询入口：

- 先抽象调用方的需求
- 再把具体转换逻辑延后给后面的注册与匹配机制

所以 `ConversionService` 的真正意义，不是“定义怎么实现转换”，而是：

**先把整个框架都约束到同一个转换提问方式里。**

## 二、为什么 Spring 不只要 `Converter`，还要 `ConverterFactory` 和 `GenericConverter`

只要看到 `Converter<S, T>`，很多人第一反应都会觉得这已经够了。

它确实很直观：

- 一个源类型 `S`
- 一个目标类型 `T`
- 一次 `convert(S)`

对于很多最朴素的场景，这完全成立。

但 Spring 很快就会遇到两类 `Converter` 单独扛不住的场景。

### `ConverterFactory`：一对多目标族不能靠手写几十个单独转换器硬撑

像下面这种类型族，就很典型：

- `String -> Integer`
- `String -> Long`
- `String -> Short`
- `String -> BigInteger`
- `String -> BigDecimal`

这些转换彼此当然不完全相同，但它们显然共享同一种“源是字符串，目标是一整个数值家族”的结构。

如果 Spring 只允许 `Converter<S, T>`，那最直接的后果就是：

- 你要么给每个目标类型写一个独立转换器
- 要么把很多目标类型硬塞进一个大分支里

这两种都不优雅。

所以 Spring 引入 `ConverterFactory<S, R>`，本质上是在表达：

**某些转换不是“一个源到一个固定目标”，而是“一个源到一整个目标家族”。**

这样，工厂只要声明：

- 我的源是 `String`
- 我的目标家族是 `Number`

后续再按具体目标类型产出真正转换器。

这就把“一对多”的结构性问题单独抽出来了。

### `GenericConverter`：有些转换根本不是普通泛型接口能描述的

第二类更棘手的场景，是结构化转换，例如：

- `String -> Collection<Integer>`
- `Array -> List<T>`
- `Collection<S> -> Collection<T>`
- `Object -> Optional<T>`

这些转换的问题在于，它们并不只是“源类 A 到目标类 B”。

因为真正决定转换行为的，往往还包括：

- 容器元素类型
- 注解上下文
- 嵌套结构信息

这时候单纯的 `Converter<S, T>` 泛型签名已经装不下真实语义了。

所以 Spring 再引入 `GenericConverter`，本质是在承认：

**有些转换不是简单的单点映射，而是依赖更丰富类型描述的结构化转换。**

因此，Spring 保留三种形态不是接口设计过度，而是在覆盖三种真实不同的扩展场景：

```text
Converter         = 一对一
ConverterFactory  = 一对多目标家族
GenericConverter  = 结构化 / 泛型化 / 上下文相关转换
```

这就是它们必须并存的根本原因。

## 三、`TypeDescriptor`：Spring 关心的不是“类是什么”，还关心“这个类在什么上下文里出现”

只要继续往集合、泛型、嵌套容器这些场景走，就会碰到一个特别关键的问题：

- `Class<?>` 到底够不够表达目标类型？

答案是不够。

原因很简单。

如果目标只是：

- `Integer.class`

那当然很好办。

可一旦目标变成：

- `List<Integer>`
- `Map<String, Long>`
- 某个带注解的字段类型

这时真正重要的信息已经不只是：

- 它是个 `List.class`

还包括：

- 元素类型是 `Integer`
- 这个目标是不是来自某个字段、方法参数或属性描述
- 上面是否附着了需要参与转换判断的注解语义

这就是 `TypeDescriptor` 出现的原因。

Spring 在这里并不是“觉得 `Class` 不够优雅”，而是在解决一个容器级事实：

**框架中的很多转换，目标语义天然比一个裸类名更丰富。**

也正因为如此，`ConversionService` 里才会有一组更强的重载形式，不只接受源类和目标类，还接受 `TypeDescriptor`。

这里必须再把一层关系压实：`TypeDescriptor` 不是独立于转换器家族存在的漂亮抽象，它在 Spring 里最直接服务的，恰恰就是前面提到的 `GenericConverter` 这一类结构化转换。

因为：

- `Converter<S, T>` 更适合单点类型映射
- `ConverterFactory<S, R>` 更适合目标家族映射
- 真正需要读取“容器元素是什么、注解语义是什么、嵌套目标是什么”的，往往是 `GenericConverter`

也就是说，这两节不是平行知识点，而是同一条主线的前后半段：

```text
GenericConverter 提出“有些转换不能只看裸类型”
   ->
TypeDescriptor 提供“那就把更完整的类型语义带进来”
```

所以 `TypeDescriptor` 的真正意义，不是“再包一层类型对象”，而是：

**让 Spring 能把泛型、注解、容器元素信息一起带进结构化转换决策。**

没有这一层，后面很多看起来理所当然的转换——尤其是集合元素级转换——都不可能被干净地组织起来。

## 四、`GenericConversionService`：统一入口背后，真正干活的是注册表、查找链和缓存

前面几层立住之后，Spring 还要解决一个非常现实的问题：

- 这么多转换器到底怎么组织？
- `canConvert()` 和 `convert()` 到底如何找到正确实现？
- 查不到时怎么办？
- 每次都重新遍历，会不会太贵？

这就是 `GenericConversionService` 的位置。

它不是“某个默认实现”这么简单，而是 Spring 转换体系里真正的注册与调度中心。

从职责上看，它至少同时承担三件事：

### 1. 它是注册表

也就是说，`Converter`、`ConverterFactory`、`GenericConverter` 不只是被定义出来，还得被统一收纳进某种可查找结构。

否则 `ConversionService` 接口永远只是一句抽象口号。

### 2. 它是查找链

调用方提出：

- 源是什么
- 目标是什么

后面就必须有人去决定：

- 有没有匹配转换器
- 是精确命中，还是父子类型兼容命中
- 是直接转换器，还是工厂产出的转换器
- 如果都没有，是不是该给一个默认兜底，还是直接失败

这一步才是整条转换链真正开始“工作”的地方。

### 3. 它是缓存层

如果每次转换都重新走：

- 反射拿泛型参数
- 遍历注册表
- 判断源目标兼容关系

那高频容器场景下很快就会把转换系统本身拖成热点。

所以 `GenericConversionService` 不只缓存“找到了谁”，还会缓存“这个源到这个目标就是找不到”。

这一点特别关键。

很多人第一次看这种设计时会觉得：

- 找不到还缓存干什么？

但对 Spring 来说，这恰恰是在表达另一种性能现实：

**高频失败匹配和高频成功匹配一样，都是应该被记住的结果。**

而且这里不只是性能优化，它还直接碰到失败路径的组织问题。

因为在真实容器里，最常见的“失败”往往不是抛出异常后再也不来了，而是：

- 同一种属性绑定反复尝试同一种不支持的目标类型
- 同一种参数解析在很多请求里不断走到同一条失败查找链
- 某个集合元素转换缺口在整批绑定过程中被重复触发

如果这些“查不到转换器”的结果不被缓存，Spring 就会在高频绑定主线里反复为同一个不成立的转换关系支付全套匹配成本。

所以 `NO_MATCH` 负缓存的真正意义是：

- 性能上，避免重复做同一种无效查找
- 语义上，把“当前源目标对就是不成立”也当成一种可复用的查找结果

换句话说，Spring 在这里缓存的不只是成功路线，也在缓存失败边界本身。

所以它真正组织出来的是这样一条链：

```text
convert request
   -> 查缓存
   -> 缓存 miss 再查注册表
   -> 找到则缓存命中结果
   -> 找不到也缓存 NO_MATCH
```

这说明 `GenericConversionService` 的角色远比“默认实现”更重。它实际上是在把前面那套抽象变成真实可运行系统。

## 五、`DefaultConversionService`：Spring 不是只提供 SPI，还先给出一套默认世界

如果只有 `GenericConversionService` 这种注册与调度骨架，Spring 仍然只完成了一半。

因为从框架使用者角度看，另一个更现实的问题是：

- 默认情况下，到底有哪些常见转换已经帮我准备好了？

这就是 `DefaultConversionService` 的意义。

它最重要的价值不是“内置很多转换器”这么表面，而是：

**Spring 不只提供扩展点，还主动提供一套足够实用的默认转换世界。**

也就是说，很多日常类型之所以看起来“天然能转”，不是因为 JVM 自己会，而是因为 Spring 已经在默认注册表里预装了这些能力。

例如：

- 标量类型转换
- 枚举转换
- 集合和数组互转
- `Optional` 等包装型语义转换

这一步很关键，因为它把整套系统从“可以扩展”推进到了“默认就好用”。

也正因为如此，后面 Bean 注入、MVC 参数绑定、配置绑定这些链路才能默认站在一块已经相对完整的转换地基上，而不是要求每个应用先手工注册一堆基本转换器。

## 六、`TypeConverterDelegate`：容器不是直接碰转换器，而是先走一层桥接

只要把转换体系讲到这里，接下来最自然的问题就是：

- Bean 属性填充、`@Value` 注入这些容器动作，怎么真正接到 `ConversionService` 上？

答案不是容器代码直接手写调用某个转换器，而是通过一层专门的桥接：`TypeConverterDelegate`。

这层桥非常关键，因为它不只是在“调用转换服务”，而是在协调两套历史机制：

- 老的 `PropertyEditor`
- 新的 `ConversionService`

这也解释了为什么 Spring 的容器级类型转换不能被简单讲成：

- 框架一有值就直接 `conversionService.convert(...)`

真实情况更复杂。

Spring 这里还背着历史兼容包袱：

- 老配置体系可能注册了自定义 `PropertyEditor`
- 新的注解驱动、现代绑定主线则更依赖 `ConversionService`

同时，它也要把这套转换真正接回 Bean 容器主线，而不是让转换体系悬空飘着。

更准确地说，`TypeConverterDelegate` 站的位置，是：

- 上游接住 BeanFactory、属性填充、依赖解析、`@Value` 注入这些容器动作
- 下游再把“这个值现在该怎么转”送进 `ConversionService` / `PropertyEditor` 协调链

所以它不是一个纯工具类，而是容器主线和转换主线真正碰头的地方。

也正因为如此，前面讲的注册表、查找链、缓存层，在这里才第一次真正“落地”成容器行为：

- 属性值要填到 Bean 上
- 占位符解析后的字符串要注入目标字段
- 方法参数值要进入目标签名

这些都不是抽象转换场景，而是 Spring 日常运行里最常见的真实入口。

所以 `TypeConverterDelegate` 干的不是“纯转发”，而是：

**先协调优先级，再把值真正送进统一转换体系，并把这套体系接回容器主线。**

这一步如果不单独讲清楚，后面读者很容易误以为 Spring 的转换世界从来只有 `ConversionService` 一套。

而更准确的说法应该是：

- Spring 现在把 `ConversionService` 作为主流统一协议
- 但在容器桥接层，仍然要照顾旧时代 `PropertyEditor` 的兼容语义

这正是框架真实世界比抽象接口更复杂的地方。

## 七、为什么 `PropertyEditor` 兼容不是枝节，而是 Spring 演进路径的一部分

很多人第一次看到 `TypeConverterDelegate` 里对 `PropertyEditor` 的优先级处理时，会本能地觉得：

- 这大概只是为了兼容老项目
- 现在主流应该都走 `ConversionService`
- 所以这部分是不是可以略讲

这个判断不够稳。

因为它会让读者错过一个非常关键的框架事实：

**Spring 的现代类型转换体系不是凭空出现的，它是在旧机制之上逐步替换、逐步接管的。**

但这里还必须再把态度说得更硬一点：

- 从今天的正文主线看，`ConversionService` 才是 Spring 统一转换协议的中心
- `PropertyEditor` 在现代 Spring 里更像历史兼容桥，而不是与 `ConversionService` 并列推荐的新扩展首选

如果这层态度不讲清，读者很容易误会成：

- 两套体系现在仍然同等重要
- 新项目扩展时可以任意二选一

这就会把框架演进方向讲反。

更准确的说法应该是：

- **理解行为边界时，必须知道 `PropertyEditor` 仍然在场**
- **设计新扩展、理解现代主线时，应优先把 `ConversionService` 视为中心机制**

也就是说，`PropertyEditor` 在今天也许不是最值得推荐的新扩展点，但它在容器桥接层仍然有两个教学价值：

- 解释为什么容器转换逻辑不是一句 `conversionService.convert()` 就完
- 解释为什么 Spring 的设计很多时候不是“纯新架构”，而是“新协议逐步接管旧世界”

这类历史兼容点如果完全不讲，后面很多真实行为边界就会显得很怪；但如果把它讲成与 `ConversionService` 并列主角，又会误导读者对现代扩展路径的判断。

所以这部分不是“陈旧知识附录”，而是整套转换主线里必须交代、但也必须摆正主次的一块桥接现实。

## 八、几个最容易错的判断

### 1. Spring 类型转换本质上就是一堆 `parseXxx()`

不成立。

`parseXxx()` 只是某些局部目标类型的底层实现方式。Spring 解决的是整个容器怎样统一提出转换问题、组织转换器并调度它们。

### 2. `Converter<S, T>` 一种接口就足够了

不成立。

一对一、一对多目标家族、泛型/结构化转换是三类不同问题，所以 Spring 才需要 `Converter`、`ConverterFactory` 和 `GenericConverter` 并存。

### 3. 类型转换只看源类和目标类就行

不成立。

像 `List<Integer>`、`Optional<Long>` 这类场景，真正需要的不只是 `Class<?>`，还要有泛型和上下文语义，这就是 `TypeDescriptor` 的位置。

### 4. `GenericConversionService` 只是默认实现，没什么设计重量

不成立。

它同时承担注册表、查找链和缓存层职责，是真正把转换抽象变成可运行系统的中心。

### 5. 现在 Spring 都用 `ConversionService`，`PropertyEditor` 可以完全忽略

不完整。

主流新链路确实更依赖 `ConversionService`，但容器桥接层仍然要处理 `PropertyEditor` 的历史兼容，这会直接影响真实转换行为和优先级。

## 收网：Spring 要统一的从来不是“某个值怎么转”，而是“整个框架怎样提出和兑现转换”

现在可以回到开头那个问题：为什么 Spring 不直接 `Integer.parseInt()`？

因为对 Spring 这种容器框架来说，它真正要面对的不是一次局部转换，而是：

- 很多不同入口都要发生类型转换
- 很多不同目标类型都要被统一支持
- 泛型、集合、包装类型、注解上下文都可能参与转换判断
- 新类型和新模块还必须能平滑扩展进来

所以 Spring 的答案不是继续在各处散落工具调用，而是重新立一条统一主线：

```text
ConversionService     = 统一转换入口
Converter 家族        = 三种形态的扩展协议
TypeDescriptor        = 比 Class 更丰富的类型语义
GenericConversionService = 注册、查找与缓存中心
TypeConverterDelegate = 容器桥接层
```

因此，这篇真正该带走的结论不是“Spring 有个类型转换接口”，而是：

**Spring 把值转换问题从“某个调用点怎么手动转”提升成了“整个容器如何统一提出、组织、调度并桥接类型转换”的框架级协议。**

这也留下了下一篇最自然的问题：如果转换体系已经准备好了，那 `@Value("${server.port}")` 里最前面的 `${...}` 又是谁先解析出来的？

也就是说，类型转换并不是第一步，它前面还有一层更靠近配置来源的问题：

- 属性值从哪里来
- 多个配置源怎么排优先级
- 占位符到底是谁解析的
