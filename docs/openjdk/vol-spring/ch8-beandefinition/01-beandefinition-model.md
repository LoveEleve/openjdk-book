# Spring 为什么先定义 Bean 再创建 Bean：`BeanDefinition` 如何把 XML、注解和 `@Bean` 统一成一张容器蓝图

> 本文基于 Spring Framework 6.x 当前源码。本文只讲 Spring IoC 容器主线的第一块地基：为什么容器不会一看到 `@Component`、`<bean>` 或 `@Bean` 方法就立刻创建对象，而必须先把它们统一整理成 `BeanDefinition`、`AbstractBeanDefinition` 这一套元数据蓝图。`RootBeanDefinition` 与 `GenericBeanDefinition` 的合并机制、BeanFactory 读取这些蓝图之后如何真正创建对象，会在后续篇章继续展开。

## 为什么 Spring 不会一看到 `@Component` 就直接 `new` 一个对象

从业务开发者视角看，Spring 最容易给人一种“好像很直接”的印象。

比如：

- 类上写了 `@Component`
- 配置类里写了 `@Bean`
- XML 里写了 `<bean class="...">`

然后容器一启动，对象似乎就都“自己出现了”。

如果只停在这种表面印象里，很容易自然得出一个看起来很顺手的理解：

- Spring 看到一个 Bean 声明
- 直接把这个对象创建出来
- 再顺手做依赖注入和初始化

这套理解在直觉上很合理，因为它很像很多轻量工具框架的工作方式：

- 读到配置
- 立刻执行
- 结果马上就出来

但对 Spring 这种 IoC 容器来说，这种做法从一开始就不够。

第一层问题是：**Spring 面对的不是一种定义方式，而是很多种。**

同一个 Bean，在真实项目里可能来自：

- XML `<bean>`
- `@Component` 扫描
- `@Bean` 方法
- 后续还可能来自父子定义合并、编程式注册、框架内部基础设施注册

如果容器一读到这些来源就立刻创建对象，它会马上失去一个很重要的能力：

- 先把不同来源统一翻译成同一种内部表示
- 再让后面的创建、注入、初始化主线只依赖这套统一表示

也就是说，Spring 真正需要的不是“读一种配置就直接 new”，而是：

**先把不同来源的 Bean 定义统一收束成一张容器能理解的蓝图。**

第二层问题是：**对象真正创建之前，容器还需要先知道很多元数据。**

比如：

- 这个 Bean 的类名是什么
- 作用域是 singleton 还是 prototype
- 是否 lazy-init
- 依赖顺序是什么
- 初始化和销毁方法是什么
- 是直接构造，还是通过 `factoryBean + factoryMethod` 生产出来

这些都说明，Spring 在“实例化对象”之前，必须先拥有一个足够丰富的元数据阶段。

这里还要再把一句核心判断提前钉死：`BeanDefinition` 解决的从来不是“现在已经有什么对象”，而是“将来应该如何创建、组织和管理这个对象”。

所以容器真正面对的问题不是：

- 现在能不能创建一个对象

而是：

- **我是否已经拥有了创建这个对象所需的完整蓝图。**

第三层问题是：**Bean 的定义和 Bean 的实例，在 Spring 里本来就是两种完全不同的东西。**

这也是第一次系统学 IoC 时最容易混淆的一点。

`UserService.class`、`<bean ...>`、`@Bean userService()` 这些东西，都还不是“正在运行的 Bean 实例”；它们更接近：

- 一个将来要创建什么对象、按什么规则创建、在容器里该怎么对待它的定义说明书

这就意味着，Spring 需要把“定义阶段”和“实例阶段”明确拆开。

因此，本文真正要回答的问题不是“Spring 有个 `BeanDefinition` 接口描述 Bean”，而是：

**为什么对 Spring 来说，一个 Bean 不能在被声明时就立刻等同于对象实例，而必须先被整理成一张统一的容器蓝图？**

## 先看失败方案：为什么不能边读配置边直接创建对象

理解 `BeanDefinition` 最好的方式，不是先背字段，而是先看几种看起来很顺、但一放到 IoC 容器里就会迅速失效的朴素方案。

### 失败方案一：读到一种定义，就直接创建一种对象

这是最符合直觉的方案。

比如：

- 扫描到 `@Component` 就立刻 `new`
- 解析到 XML `<bean>` 就立刻 `new`
- 读到 `@Bean` 方法就立刻调用方法返回实例

如果系统面对的永远只是单一路径、单次创建、没有后续组合的对象工厂，这么做甚至很合理。

但 Spring 容器面对的问题完全不是这样。

因为一旦走到真实框架环境，就会立刻出现几个结构性难题：

- 不同来源的定义方式完全不同，但后续创建主线不能跟着分裂
- 某些 Bean 还没到创建时机，不能一读到就实例化
- Bean 之间可能有依赖、作用域、lazy、初始化回调、销毁回调等复杂元数据要先被记录
- 容器还需要在正式创建前允许 `BeanFactoryPostProcessor` 这类机制修改定义

也就是说，如果“边读边建”，后面的 IoC 主线几乎就失去了统一入口。

所以 Spring 真正需要的，不是“定义来源自己负责创建”，而是：

**定义来源先负责把信息翻译成统一蓝图，创建动作留给后续容器主线统一处理。**

### 失败方案二：先用一个 `Map<String, Class<?>>` 把 Bean 类记下来就够了

如果意识到“边读边建”太早，第二种很自然的思路就是：

- 好，那先别创建
- 先把 Bean 名和类名存起来
- 真正需要时再 `new`

这个方案比第一种前进了一步，因为它至少已经区分了：

- 定义阶段
- 实例阶段

但它仍然远远不够。

因为对 Spring 来说，Bean 定义绝不只是“这个名字对应哪个类”。

容器还必须继续回答：

- 这个 Bean 是 singleton 还是 prototype
- 它是不是 lazy-init
- 是否依赖其他 Bean 先初始化
- 初始化方法、销毁方法是什么
- 它是不是通过工厂方法创建
- 它在容器里属于应用 Bean、支持性 Bean 还是基础设施 Bean

也就是说，一个简单的 `Map<String, Class<?>>` 只能回答“类是什么”，却无法回答“这个类应该被怎样对待”。

所以 Spring 真正要管理的不是“类注册表”，而是：

**Bean 的容器级元数据模型。**

### 失败方案三：每种来源各有自己的内部结构，BeanFactory 自己适配就行

还有一种很诱人的框架实现思路：

- XML 定义就保留 XML 的内部对象
- 注解扫描保留扫描结果对象
- `@Bean` 方法保留配置方法模型
- 最后 BeanFactory 看到什么就适配什么

这个方案短期看似灵活，长期却会把容器拖进一种非常糟糕的状态：

- BeanFactory 必须知道所有定义来源细节
- 新增一种定义来源，就要继续侵入创建主线
- 后处理器、作用域、生命周期逻辑无法只依赖统一模型

也就是说，Spring 会失去它最重要的一种能力：

- **把“配置读入”和“Bean 创建”彻底解耦。**

所以 Spring 真正要的不是“BeanFactory 能适配很多来源”，而是：

**所有来源都必须先降维成同一种内部蓝图。**

这就是 `BeanDefinition` 必须存在的根本原因。

## Spring Bean 定义系统的最小总图

如果把这条主线先压缩成最小模型，它可以写成下面这样：

```text
XML / annotation / @Bean / programmatic registration
   -> BeanDefinition
   -> BeanFactory stores definition metadata
   -> later creation / injection / initialization use the same blueprint
```

如果再换一种更容易理解的拆法，这条链可以分成四段职责：

```text
[定义来源]
XML / @Component / @Bean / 编程式注册

   ->

[统一蓝图]
BeanDefinition / AbstractBeanDefinition

   ->

[关键元数据]
scope / lazy / dependsOn / role / factory metadata / init-destroy metadata

   ->

[容器消费方]
BeanFactory / 后处理器 / 生命周期主线
```

这张图最重要的价值，不是让读者记几个类名，而是先把四个问题分开：

### 一、定义来源

回答：Spring 为什么要统一很多不同的 Bean 声明方式？

### 二、统一蓝图

回答：`BeanDefinition` 究竟统一了什么，而不只是统一了类名？

### 三、关键元数据

回答：为什么 Bean 在实例化之前，就必须先把作用域、依赖、生命周期、工厂信息都编码进去？

### 四、容器消费方

回答：为什么后续 BeanFactory、后处理器、生命周期链都必须站在这张蓝图之上？

只要先把这四层职责分开，`BeanDefinition` 就不再像一个“普通配置对象”。

## 一、`BeanDefinition`：Spring 要统一的不是“类是什么”，而是“这个对象以后该怎样进入容器世界”

只要从接口层看，`BeanDefinition` 最容易被理解成：

- 这是个描述 Bean 的接口

这句话当然没错，但它还不够深。

因为 Spring 真正通过 `BeanDefinition` 统一的，不只是：

- 目标类是什么

而是：

- 这个对象以后该怎样进入容器世界

也就是说，`BeanDefinition` 面对的从来不是“类信息存档”，而是：

- 这个定义该不该被提前实例化
- 这个定义以后是单例还是原型
- 它初始化和销毁要不要带额外回调
- 它是不是通过工厂方法间接创建
- 它在容器里处于应用、支持还是基础设施角色

这说明 `BeanDefinition` 真正站的位置非常靠前：

- 它不是实例化阶段的附属对象
- 它是后面整条 IoC 主线的元数据起点

从整卷前八篇一起回头看，这种写法也很一致：

- `Resource` 统一资源句柄
- `ConversionService` 统一值转换契约
- `Environment` 统一配置读取入口
- `Ordered` 统一顺序语义
- 注解元数据系统统一注解语义搜索与映射
- `@Profile` 统一条件装配裁决
- `TaskExecutor` 统一任务执行协议
- 而 `BeanDefinition` 统一的，则是：

**Bean 在真正创建出来之前，容器该如何先理解它。**

这里还必须再把它和后面实例世界的边界说得更硬一些。

`BeanDefinition` 里保存的很多信息，并不是对象运行起来以后动态变化的状态，而是：

- 容器未来做决策时的输入
- 创建之前就已经要确定的规则
- 后续实例化、注入、初始化、销毁主线共同依赖的静态蓝图

也就是说：

- 实例世界关心“对象现在是什么状态”
- 定义世界关心“容器以后应该如何对待这个对象”

这就是为什么 `BeanDefinition` 不能被误看成“Bean 的一部分运行时状态对象”。它首先属于定义阶段、决策阶段，而不是实例阶段。

所以 `BeanDefinition` 最关键的意义，不是“保存一些字段”，而是：

**把 Bean 从“将来会出现的对象”先提升成“当前就可被容器处理的定义实体”。**

## 二、为什么 XML、注解和 `@Bean` 方法必须先被翻译成同一种蓝图

只要 `BeanDefinition` 的位置立住之后，下一步最自然的问题就是：

- Spring 为什么非要把 XML、注解、`@Bean` 方法这些完全不同的来源都统一成同一种内部模型？

答案恰恰说明 Spring 的 IoC 容器从一开始就不是“配置读取器”，而是“定义消费器”。

因为对 BeanFactory 来说，后面的创建、注入、初始化、销毁主线根本不应该关心：

- 这个定义最初是 XML 里来的
- 还是组件扫描来的
- 还是配置类方法来的

BeanFactory 真正该关心的是：

- 这个定义现在已经是一张完整蓝图了吗
- 如果是，我就按统一规则继续往下处理

这意味着 Spring 在设计上做了一个很重的切割：

- **配置读入层** 负责把各种来源翻译成定义模型
- **容器消费层** 负责只依赖定义模型继续往下走

所以这里真正统一的，不是“不同来源最后看起来差不多”，而是：

**它们在进入 BeanFactory 之前，必须全部降到同一个容器决策接口。**

也就是说，统一的核心不是表面长相，而是后续容器主线提问时，只需要面对同一种定义协议。

这也解释了为什么同一个系统里会同时出现：

- `GenericBeanDefinition`
- `ScannedGenericBeanDefinition`
- `ConfigurationClassBeanDefinition`

它们的来源语义不同，但对更下游的容器消费方来说，最重要的是：

- 最终都得先落回统一的 `BeanDefinition` 语义空间

所以这里真正被统一的不是“语法长相”，而是：

**Bean 定义如何被容器看见。**

## 三、scope、lazy、dependsOn、role：Bean 定义里真正重要的不是类名，而是容器决策信息

只要继续往 `BeanDefinition` 深处看，很快就会发现一个特别关键的事实：

- Bean 定义里最重要的东西，很多都不是类名本身

因为类名只回答：

- 将来要实例化什么

但容器真正需要的，往往是另一类更靠近决策层的信息：

### 1. scope：这个定义以后是共享的，还是每次都重新创建

这直接决定了：

- BeanFactory 以后是缓存单例，还是每次新建实例

也就是说，scope 在这里不是附加注释，而是后续创建策略的一部分。

### 2. lazy：这个定义是否允许延后进入实例化阶段

这又直接影响：

- 容器启动时预实例化是否该碰到它
- 它什么时候才真正从“定义”进入“实例”

所以 lazy 也不是性能开关，而是实例化时机元数据。

### 3. dependsOn：这个定义在进入创建主线前，是否要显式等待别人先完成

这说明 Spring 容器处理的不是孤立对象，而是：

- 一组有顺序关系的定义图

`dependsOn` 在这里回答的就是：

- 容器在正式创建我之前，要不要先保证某些定义已经完成

### 4. role：这个定义在容器里属于什么层次角色

这是特别容易被低估的字段。

因为很多人会本能把 Bean 都看成“应用 Bean”。

但对 Spring 来说，定义本来就不只一类：

- 应用 Bean
- 支持性 Bean
- 基础设施 Bean

也就是说，BeanDefinition 从一开始就在告诉容器：

- 我不只是什么类
- 我还属于容器世界里的哪一层角色

而且这里的 `role` 也不是一个给人看的装饰标签。它真正重要的地方在于：

- 容器后续能区分“这是业务定义”还是“这是框架内部基础设施”
- 一些工具、诊断、可视化、后处理与管理逻辑可以按角色分层理解定义世界
- Spring 自己的大量内部 Bean 能在定义阶段就被标识为基础设施，而不和普通业务 Bean 混成一片

也就是说，`role` 解决的不是“多一个分类字段”，而是：

**容器如何在定义阶段就看懂这是谁的 Bean、处在哪一层世界里。**

因此，`scope / lazy / dependsOn / role` 这些字段的意义，不是“描述更全”，而是：

**它们直接参与后续容器决策。**

## 四、`factoryBean` / `factoryMethod`：Spring 先描述“如何得到实例”，再真正去得到实例

只要继续往下看，BeanDefinition 里还有一类特别能说明问题的元数据：

- `factoryBeanName`
- `factoryMethodName`

这组字段非常关键，因为它直接说明：

- Spring 定义的从来不只是“将来 new 哪个类”
- 它还能定义“将来应该通过什么生产路径得到这个实例”

这一步在 `@Bean` 场景里尤其明显。

因为配置类里的：

- `@Bean public DataSource dataSource()`

并不是在说：

- 容器以后直接 `new DataSource`

而是在说：

- 容器以后应该通过某个工厂 Bean、调用某个工厂方法，得到最终实例

这再次说明 `BeanDefinition` 真正建模的不是“对象长什么样”，而是：

**对象将来应当通过哪种容器级路径被生产出来。**

也就是说，Spring 在定义阶段就已经把创建策略的一部分编码进蓝图里了。

这里还要再补一个失败边界：一旦采用 `factoryBean + factoryMethod` 这条路径，容器未来面对的失败就不再只是“普通构造器创建失败”，还可能是：

- 工厂 Bean 本身没准备好
- 工厂方法解析失败
- 工厂方法调用链抛异常

这意味着工厂路径不是“另一种语法糖”，而是会直接改变后续创建主线的成功路径和失败路径。

这也解释了为什么 `BeanDefinition` 不能被讲成“类名 + scope”这么浅。

因为有时候它甚至在说：

- 这个 Bean 根本不是直接构造出来的
- 它是容器未来沿某条工厂路径解析出来的结果

## 五、init / destroy 元数据：Spring 在定义阶段就已经把生命周期回调安排进蓝图里

如果再往后看，另一个特别重要的事实也会浮出来：

- BeanDefinition 不只描述“怎么创建”，还提前描述“创建后怎么初始化、退出时怎么销毁”

这就是 `initMethodNames`、`destroyMethodNames` 这类元数据的意义。

很多人第一次看到这些字段时，会把它们当成附属配置，觉得无非就是：

- 初始化后顺手调一下方法
- 销毁前再顺手调一下方法

这个理解太轻了。

因为对容器来说，这意味着：

- 生命周期回调不是实例创建之后的临时选择
- 而是定义阶段就已经被明确写进蓝图的容器契约

也就是说，当后面 `initializeBean(...)`、销毁主线真正开始工作时，它并不是“看心情调哪些回调”，而是：

- 回过头来消费 BeanDefinition 里早就写好的生命周期元数据

换句话说，容器在这里不是“记住几个方法名”而已，而是在定义阶段就已经把：

- 初始化如何收口
- 销毁如何退场
- 哪些回调属于这个 Bean 的生命周期契约

提前编码进了蓝图本身。

这说明 Spring 在这里做的不是“动态猜测”，而是：

**先在定义阶段把生命周期约束编码进去，再在运行时按这张蓝图兑现。**

这也就是为什么 `BeanDefinition` 必须放在生命周期篇之前先讲清楚。

因为没有定义模型，后面的创建、初始化、销毁链都会失去元数据来源。

## 六、为什么 `BeanDefinition` 不是“实例的一部分”，而是“实例之前的容器世界”

看到这里，最值得回收的一个问题就是：

- `BeanDefinition` 究竟和 Bean 实例是什么关系？

很多人第一次学 Spring 时，容易把两者混在一起：

- 好像 BeanDefinition 就是 Bean 的配置对象
- Bean 创建时顺手读一下而已

这个理解不够稳。

更准确的说法应该是：

- Bean 实例属于运行时对象世界
- BeanDefinition 属于实例出现之前的容器世界

也就是说，在对象真正被创建出来之前，容器已经可以围绕定义做很多事：

- 注册
- 覆盖
- 合并
- 排序
- 条件裁决
- 后处理器修改

这说明 Spring 的 IoC 主线本质上不是“遇到对象就处理对象”，而是：

- **先处理定义，再处理实例。**

而 `BeanDefinition` 恰恰就是这条定义世界里的基本单位。

这也是为什么它必须被放在 BeanFactory、生命周期、循环依赖这些篇章之前先讲透。

因为后面那些机制，几乎都默认这张蓝图已经存在。

## 七、几个最容易错的判断

### 1. `BeanDefinition` 就是“Bean 的类名配置”

不成立。

它真正描述的是这个对象以后怎样进入容器主线，包括作用域、依赖、生命周期、工厂路径、角色语义等。

### 2. Spring 读到 `@Component` 就直接实例化 Bean

不成立。

Spring 先把不同来源统一翻译成定义模型，真正创建对象是后续 BeanFactory 主线的工作。

### 3. `scope`、`lazy`、`dependsOn` 只是附加属性，不影响主干机制

不成立。

这些字段本来就在参与后续创建时机、缓存策略、依赖顺序等核心容器决策。

### 4. `@Bean` 方法对应的 Bean 只是另一种类名定义

不成立。

它经常通过 `factoryBean + factoryMethod` 表达“未来如何生产实例”的路径，而不是简单直接构造。

### 5. 生命周期回调是实例创建完以后临时决定的

不成立。

初始化/销毁回调本来就在定义阶段先被写进蓝图，后续生命周期链只是按图执行。

## 收网：Spring 要统一的从来不是“从哪里 new 对象”，而是“容器如何先理解一个 Bean”

现在可以回到开头那个问题：为什么 Spring 不会一看到 `@Component` 就直接创建对象？

因为对 Spring 这种 IoC 容器来说，它真正要面对的不是“对象怎么 new”，而是：

- 很多不同来源的定义如何统一进容器世界
- 对象创建前需要哪些作用域、依赖、生命周期、工厂路径元数据
- 后续 BeanFactory、后处理器、生命周期主线如何共享同一张蓝图

所以 Spring 的答案不是边读边建，而是先建立一套统一定义主线：

```text
BeanDefinition / AbstractBeanDefinition = 统一蓝图
scope / lazy / dependsOn / role         = 容器决策元数据
factoryBean / factoryMethod             = 实例生产路径元数据
init / destroy metadata                 = 生命周期回调元数据
```

因此，这篇真正该带走的结论不是“Spring 有个 BeanDefinition 接口描述 Bean”，而是：

**Spring 把 Bean 问题从“某个对象怎么被创建”提升成了“容器如何先把一个对象未来的创建、依赖、生命周期和角色语义编码成统一蓝图”的 IoC 基础协议。**

这也留下了下一篇最自然的问题：既然 Bean 定义蓝图已经存在了，那容器真正存放这些定义、按名字查它们、按层次组织它们、并最终把定义推进成实例的，又是谁？

也就是说，描述蓝图只是第一步；接下来要进入的是：

- 这些蓝图到底存在哪
- 谁在管理它们
- `BeanFactory` 这棵层次树到底在统一什么
