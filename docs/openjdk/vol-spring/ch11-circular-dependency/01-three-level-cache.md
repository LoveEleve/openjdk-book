# 为什么有的循环依赖 Spring 能解，有的直接炸：三级缓存与 `getEarlyBeanReference` 的精确协作

> 本文基于 Spring Framework 6.x 当前源码。本文只讲 Spring 循环依赖主线的第一层：为什么容器既不会把所有循环依赖一概拒绝，也不会神奇地把所有环都自动解开，而是依赖 `singletonObjects`、`earlySingletonObjects`、`singletonFactories` 与 `getEarlyBeanReference(...)` 这一套精确协作机制，只处理特定形态的单例循环依赖。`@Autowired` / `@Qualifier` 的候选选择规则、`doGetBean()` 入口调度和 AOP 代理细节，会在后续篇章继续展开。

## 为什么 Spring 一边说“循环依赖能解决”，一边又会在启动时报 `BeanCurrentlyInCreationException`

第一次系统看 Spring 循环依赖时，最容易被搞乱的不是类名，而是结论本身。

因为你会同时看到两种完全相反的现象：

- 两个 Bean 互相 `@Autowired` 字段，项目居然能启动
- 两个构造器互相注入，项目却直接报 `BeanCurrentlyInCreationException`

这会让人自然产生一种困惑：

- Spring 到底能不能解决循环依赖？

如果只用一句“Spring 用三级缓存解决循环依赖”来回答，这个问题其实并没有被真正回答。

因为它省略掉了最关键的边界：

- **不是所有循环依赖都能解**
- **能解的，也不是因为缓存本身神奇，而是因为生命周期时序恰好给出了一个可被提前暴露的窗口**

第一层问题是：**循环依赖不是“有没有环”这么简单，而是“环发生在生命周期哪一段”。**

这也是第一次读源码时最容易忽略的一点。

因为从依赖图看：

- A 依赖 B
- B 依赖 A

两种写法都长得一样。

但从生命周期主线看，它们差别巨大：

- 构造器注入要求对象出生时依赖就已经完整
- 字段 / Setter 注入允许对象壳子先出生，依赖稍后再补

也就是说，Spring 最终能不能解环，首先取决于：

- **这个环要求的是“出生前就完整”，还是“出生后还能补齐”。**

第二层问题是：**Spring 真正暴露出去的不是“完整 Bean”，而是“某个阶段上的可提前引用”。**

很多人第一次听“提前暴露”时，会本能地把它理解成：

- 对象都没准备好，就强行拿去用了

这个理解不完全错，但还不够精确。

更准确地说，Spring 暴露出去的不是随便一个半成品，而是：

- 某个已经出生、但尚未完成全部生命周期步骤的对象引用
- 并且这个引用还可能先经过 `getEarlyBeanReference(...)` 这一层被代理化处理

也就是说，循环依赖可解性背后真正要回答的是：

- Spring 愿意在什么时间点、以什么形态，把一个尚未最终完成的对象提前给别人看见

第三层问题是：**三级缓存的重点不是“有三级”，而是“每一级各自代表生命周期的不同阶段”。**

这里还要先把范围边界提前说清：本文讨论的是 **单例 Bean 的循环依赖**。也就是说，这里默认成立的前提是：

- 对象会进入 Spring 的单例创建与缓存主线
- 生命周期可以围绕单例缓存逐步推进

而像原型 Bean、某些 FactoryBean 变体、作用域代理等更宽场景，并不简单落在这一套单例三级缓存语义里。

这不是一个小备注，而是整篇结论成立的前提。脱离“单例生命周期主线”去谈 Spring 循环依赖，结论很容易被误泛化成“Spring 一般都能解环”，而这恰恰是这篇最想避免的误解。

如果只把它们背成三个 Map：

- `singletonObjects`
- `earlySingletonObjects`
- `singletonFactories`

那其实仍然抓不住重点。

因为真正重要的不是容器里有几个 Map，而是：

- 一级里放的是什么阶段的对象
- 二级里放的是什么阶段的对象
- 三级里放的为什么不是对象，而是工厂

也就是说，Spring 在这里不是在做普通缓存优化，而是在做：

**把单例对象从“还没暴露”到“可提前引用”再到“最终可用”的不同阶段拆成不同存放语义。**

因此，本文真正要回答的问题不是“Spring 有三级缓存解决循环依赖”，而是：

**为什么对 Spring 来说，循环依赖能否解决，真正取决于对象在生命周期链上的哪个阶段可以被提前暴露，以及三级缓存怎样精确承载这种阶段性暴露。**

## 先看失败方案：为什么“有环就缓存一下”“拿半成品凑合用”“构造器也一样能解”都不成立

理解 Spring 循环依赖机制，最好的方式不是先背缓存字段，而是先看几种看起来非常顺手、但一放到生命周期链里就会迅速失效的朴素方案。

### 失败方案一：只要发现 A 和 B 互相引用，就先建一个，再缓存起来给对方用

这是最符合很多人直觉的方案。

因为从很粗的层面看，循环依赖似乎就是：

- A 要 B
- B 要 A
- 那就先把一个对象放起来，另一个取这个引用不就行了

这个想法的问题在于，它把“对象引用出现了”误当成了“对象已经到了可被别人看见的阶段”。

但对 Spring 来说，Bean 生命周期链本来就分很多段：

- 实例刚出生
- 依赖还没填
- 初始化还没做
- 后置处理器还没跑
- 代理也还没最终决定

也就是说，Spring 真正面对的不是“有没有引用可以先放起来”，而是：

- **容器现在是否允许别的 Bean 看见这个阶段的对象。**

所以循环依赖从来不是“发现环就放缓存”这么粗糙，而是一个非常严格的生命周期时序问题。

### 失败方案二：那就把半成品对象直接塞给别人，反正后面再补齐

如果意识到简单缓存不够，第二种更激进的思路就是：

- 好，那对象一构造出来就先拿给别人
- 后面属性和初始化慢慢补

这个方案看起来比第一种更接近 Spring 实际做法，但它仍然不对。

因为对 Spring 来说，“半成品”不是一个可以随便暴露的抽象词，它至少还要继续回答：

- 这个对象当前是否已经有稳定身份
- 这个对象未来会不会被 AOP 代理替换
- 提前暴露给别人的是原始对象，还是早期代理对象
- 后面如果再包装一次，会不会让前后看到的不是同一个东西

这就是为什么 Spring 不能只说“提前给半成品”，而必须再引入：

- `singletonFactories`
- `getEarlyBeanReference(...)`

也就是说，它真正要提前暴露的不是“一个随便的半成品对象”，而是：

**一个经过容器认可、可用于早期引用、并且未来能和最终结果保持一致性的对象形态。**

### 失败方案三：既然字段注入的环能解，构造器注入的环应该也能用同样办法解

这是最常见、也最容易让人误判 Spring 能力边界的一种想法。

因为从依赖图看，两者都是：

- A 依赖 B
- B 依赖 A

于是很容易下意识认为：

- 既然有三级缓存，那构造器注入也该能靠提前暴露解决

这个判断的问题在于，它忽略了生命周期阶段完全不同。

构造器注入意味着：

- 对象出生时就必须拿到依赖

而字段 / Setter 注入意味着：

- 对象可以先出生
- 依赖稍后在 `populateBean` 阶段补

也就是说，构造器注入的环失败，不是因为 Spring 忘了查缓存，而是因为：

- **在对象还没出生之前，根本没有东西可以提前暴露。**

这就是为什么“构造器环不可解”不是一个局部技巧限制，而是从生命周期起点就已经决定了的结构性边界。

## Spring 循环依赖处理的最小总图

如果把这条主线先压缩成最小模型，它可以写成下面这样：

```text
singleton creation
   -> bean currently in creation
   -> may expose early reference window?
   -> singletonFactories -> earlySingletonObjects -> singletonObjects
   -> circular dependency resolved or fails
```

如果再换一种更容易理解的拆法，这条链可以分成四段职责：

```text
[最终单例]
singletonObjects

   ->

[早期引用]
earlySingletonObjects

   ->

[早期引用工厂]
singletonFactories

   ->

[提前暴露形态控制]
getEarlyBeanReference(...)
```

这张图最重要的价值，不是让读者记住三个 Map 名字，而是先把四个问题分开：

### 一、最终单例

回答：生命周期完全收口之后，真正可用的单例对象最终放在哪里？

### 二、早期引用

回答：当对象已经可以被别人暂时看见，但还没完全进入最终形态时，它在哪一层被缓存？

### 三、早期引用工厂

回答：为什么 Spring 不直接缓存一个原始半成品对象，而要先缓存一个能“生成早期引用”的工厂？

### 四、提前暴露形态控制

回答：在 AOP 等场景里，别人提前拿到的到底应该是原始对象，还是早期代理对象？

只要先把这四层职责分开，三级缓存就不再像一套“神秘 Map 组合拳”。

## 一、为什么构造器注入的循环依赖天然不可解：对象出生前就要依赖，根本没有暴露窗口

如果先从最容易误解的地方切入，Spring 循环依赖最重要的第一条边界其实是：

- **构造器注入的循环依赖天然不可解。**

这里的“不可解”不是某个 if 分支没写，而是生命周期时序自己决定的。

因为只要一个 Bean 走构造器注入，它在 `createBeanInstance` 阶段就必须先拿到构造器参数。

也就是说：

- A 要出生，先要 B
- B 要出生，先要 A

这时 Spring 面对的不是“有没有缓存命中”，而是：

- A 还没出生完，根本来不及进入可提前暴露阶段

这就是为什么构造器循环依赖在 Spring 里会直接落到：

- `BeanCurrentlyInCreationException`

不是因为 Spring 不愿意解，也不只是因为“三级缓存没查到”，而是因为：

**容器根本还没有机会把 A 放进三级缓存中的任何一层。**

更准确地说，失败的根因是：

- `addSingletonFactory(...)` 这个可提前暴露窗口尚未发生
- A 还卡在“为了出生必须先拿到 B”的阶段
- 所以容器连“我愿意先把你早期暴露出去”这一步都还来不及做

换句话说，三级缓存想成立，前提是：

- 对象壳子已经先被创建出来

而构造器环恰恰卡死在壳子出生之前。

所以这一节最核心的结论不是“构造器注入有 bug”或者“构造器注入不友好”，而是：

- **构造器注入要求依赖在出生时就完整，因此它和提前暴露机制在时序上天然冲突。**
- **在构造器模型里，对象引用必须晚于依赖解析完成，所以提前暴露根本找不到宿主。**

这也解释了为什么上一篇在讲 `createBeanInstance` 时强调：

- 构造器注入和字段 / Setter 注入不是语法偏好，而是生命周期差异

这里正是那条差异第一次变成硬边界的地方。

## 二、字段 / Setter 注入为什么可解：因为 Spring 终于拿到了一个“对象已经出生、依赖尚未补齐”的窗口

当生命周期从构造器注入切换到字段 / Setter 注入时，局面就变了。

原因很简单，但特别关键：

- 对象可以先通过无参构造或较简单构造路径出生
- 真正的依赖填充推迟到 `populateBean` 阶段

这就意味着，Spring 第一次拿到了一个非常宝贵的时间窗口：

- **对象壳子已经存在**
- **依赖还没补齐**
- **但容器已经可以决定是否让别人先看到它的早期引用**

这正是字段 / Setter 循环依赖可解的根本原因。

也就是说，Spring 不是突然在这里变得更聪明了，而是生命周期结构本身终于给了它一个可操作空间。

但这里也必须把边界说清：可解并不等于“此时对象已经完整可用”，它只意味着：

- 引用现在终于可以先出现
- 而完整依赖、初始化、增强这些动作仍然要在后续生命周期阶段继续补齐

也正因为如此，B 在这一阶段拿到的 A，本质上更接近“早期引用语义”，而不是那个已经完成全部收口、可以被当成最终单例结果理解的 A。

如果把顺序压成一句话，就是：

- 先出生
- 再提前暴露
- 再在后续 `populateBean` 中补依赖

这和构造器注入正好相反。

构造器环要求的是：

- 先补依赖
- 才能出生

而字段 / Setter 注入允许的是：

- 先出生
- 再补依赖

也就是说，循环依赖能不能解，真正决定因素并不是“有没有三个 Map”，而是：

- **生命周期是否允许对象先出生出一个可暴露窗口。**

这就是为什么 `addSingletonFactory(...)` 会出现在 `createBeanInstance(...)` 之后、`populateBean(...)` 之前。那不是随意排的顺序，而是整个循环依赖可解性的时间窗口本身。

## 三、为什么三级缓存真正重要的不是“有三级”，而是“每一级都代表不同阶段的对象语义”

只要讲到这里，很多人就会自然问：

- 二级缓存不够吗？
- 为什么非得三级？

这个问题如果只从“缓存个数”去想，很容易走偏。

因为 Spring 这里真正重要的根本不是数字，而是：

- 每一级在生命周期里承载的对象阶段不同

### 一级：`singletonObjects` 是最终可用世界

这层很容易理解。

它放的是：

- 生命周期已经收口
- 容器已经认可为最终单例结果
- 后续正常 `getBean()` 直接应返回的对象

也就是说，这一层代表的是：

- **最终形态。**

### 二级：`earlySingletonObjects` 是已经生成好的早期引用

这层放的不是最终单例，而是：

- 某个 Bean 在生命周期中途被提前暴露出去后
- 已经真正生成好的“早期引用结果”

它的意义是：

- 一旦这个 Bean 的早期引用已经被算出来
- 后面再有人要同一个早期对象，就不必重复生成

所以这一层代表的是：

- **可被别人看到，但还没进入最终单例世界的阶段性对象。**

### 三级：`singletonFactories` 不是对象缓存，而是“如何生成早期引用”的工厂缓存

这一层最关键。

因为它解释了为什么 Spring 不直接一开始就把半成品对象塞进二级缓存。

答案就在于：

- 容器在对象出生后、依赖还没补齐时，并不想立刻拍板“别人应该看到哪个形态的我”

因为这里还牵涉 AOP 等增强问题：

- 别人提前看到的，到底是原始对象？
- 还是一个早期代理对象？

所以 Spring 先缓存的不是对象本身，而是：

- **一个按需生成早期引用的工厂。**

这说明三级缓存最核心的价值不是“多一层性能优化”，而是：

**把“早期引用形态还未决定”单独建模出来。**

这就是为什么三级不能简单删成两级。

因为只要少掉工厂层，Spring 就会失去：

- 在真正有人需要时，按当前 Bean 的增强语义决定“早期引用到底长什么样”的机会
- 也会过早把某个原始对象形态冻结成“唯一可见结果”，后面即使发现它本该被代理，也已经来不及把前面拿到引用的人一起纠正过来

也就是说，三级比二级多出来的，不只是一次延迟创建，而是避免“早期对象形态被过早拍板”。

一旦拍板过早，后果就不只是 AOP 少包了一层那么简单，而是容器内部可能开始同时存在“有人看见的是原始对象、有人看见的本该是代理对象”这种前后不一致的可见形态。

## 四、`getEarlyBeanReference(...)`：Spring 提前暴露的不是“随便一个半成品”，而是“未来要和最终结果保持一致的早期形态”

只要三级缓存的层次立住之后，就必须继续回答另一个特别关键的问题：

- 那工厂真正生成的“早期引用”到底是什么？

这就是 `getEarlyBeanReference(...)` 的位置。

它的存在说明一件非常重要的事：

- Spring 不是把原始对象壳子直接扔给别人就完了
- 它要先判断：这个 Bean 在提前暴露时，是否应该已经体现某种增强形态

也就是说，`getEarlyBeanReference(...)` 解决的首先不是“当前 Bean 生命周期是不是已经完成”，而是“此刻**给别人看的形态**应该是什么”。

更准确地说，它处理的是“面向外部依赖方的可见对象语义”，而不是“当前 Bean 自己对自己的认识”。

这一步在 AOP 场景里尤其关键。

因为如果某个 Bean 后面注定要被代理，而循环依赖时别人提前拿到的却是原始对象，那容器最终就可能出现：

- 一部分地方看到代理对象
- 一部分地方提前拿到原始对象

这会直接破坏 Spring 想维持的一个核心一致性：

- **别人提前看到的那个东西，应该尽量和最终可用世界里看到的是同一个逻辑对象。**

所以 `getEarlyBeanReference(...)` 真正解决的不是“能不能提前给个引用”，而是：

- **提前给出去的这个引用，应不应该已经经过某些关键增强。**

也就是说，三级缓存之所以必须有工厂层，正是为了把这个问题留到“真正有人需要时”再决定。

### 为什么早期代理和最终代理不能各搞各的

这一步非常关键。

因为如果 Spring 允许：

- 早期引用是一套对象
- 初始化后最终又包装出另一套不同代理对象

那循环依赖虽然表面上“解开了”，但容器内部对象一致性会立刻崩掉。

所以 Spring 真正想维持的是：

- 提前暴露时如果已经需要代理，那就尽早决定这个形态
- 后面初始化后不要再让这个 Bean 突然换一个完全不同的包装结果

也就是说，`getEarlyBeanReference(...)` 背后真正要守住的，不只是循环依赖，而是：

- **生命周期前后，别人看到的这个 Bean 是否仍然站在同一条对象身份线上。**

这也是为什么 `AbstractAutoProxyCreator` 会对 early reference 做专门记录，后面再避免重复包装。

## 五、为什么三级缓存不是普通缓存优化，而是单例生命周期的阶段性存储模型

看到这里，其实就能把“三级缓存”这个词再重新理解一遍了。

如果只从名字看，它很容易让人想到：

- 一级快一点
- 二级再快一点
- 三级也许只是优化层次

这个理解对 Spring 来说完全抓错重点。

因为这里三层最大的区别不是“速度层级”，而是：

- **对象生命周期阶段层级。**

更准确地说：

```text
singletonObjects        = 最终单例结果
earlySingletonObjects   = 已确定的早期引用结果
singletonFactories      = 尚未最终决定形态的早期引用工厂
```

也就是说，Spring 这里缓存的从来不只是对象，而是：

- 对象在单例生命周期主线上的不同状态

这也是为什么它会和普通缓存系统很不一样。

普通缓存通常在回答：

- 为了少算几次结果，我把结果先存起来
- 重点是命中率、复用率和访问成本

而 Spring 这里真正回答的是：

- **为了让生命周期不同阶段各自有稳定语义，我把不同阶段的对象表示分开存。**

也就是说，这里的设计目标首先不是缓存优化，而是阶段语义与对象一致性治理；缓存只是它采取的实现外形。

所以它们虽然长得像缓存结构，但容器在这里真正管理的不是值复用热度，而是单例生命周期时序本身。

这就是三级缓存真正的“框架味”。

## 六、为什么循环依赖专题必须放在 `doCreateBean()` 之后，而不是当成缓存技巧独立讲

看到这里，最值得回收的一个问题就是：

- 为什么循环依赖不能单独当一篇“三级缓存技巧”来讲？

因为它根本不是技巧问题，而是生命周期问题。

前一篇已经立住了：

- `doCreateBean()` 不是一次构造，而是一条从定义走到可用实例的创建链
- `createBeanInstance`、`populateBean`、`initializeBean`、销毁登记各自有阶段边界

而这一篇真正做的，是把其中最敏感的一个边界继续打开：

- 在 `createBeanInstance` 和 `populateBean` 之间，Spring 为什么会拿到一个“可提前暴露窗口”

也就是说，循环依赖不是一个外挂技巧，而是：

**生命周期主线在遇到互相引用时暴露出来的最复杂边界之一。**

同样，后面 `BeanPostProcessor` 体系为什么也必须紧跟着看，就更清楚了。

因为：

- 提前暴露窗口为什么危险
- AOP 代理为什么要通过 `getEarlyBeanReference(...)` 提前参与
- 为什么不同 BPP 插点会影响最终看到的对象形态

这些都和当前篇在讲的三级缓存、早期引用是同一个根节点。

所以这篇之所以必须放在 `doCreateBean()` 之后，恰恰是因为它不是缓存技巧，而是 Bean 生命周期主线的一个尖锐分叉点。

## 七、几个最容易错的判断

### 1. Spring 能解决所有循环依赖

不成立。

Spring 只会在特定生命周期窗口内解决特定形态的单例循环依赖，构造器注入的环天然不可解。

### 2. 三级缓存只是为了性能优化

不成立。

三层最大的区别不是缓存速度，而是承载 Bean 在单例生命周期中的不同阶段语义。

### 3. 二级缓存就够了，三级只是历史实现习惯

不成立。

如果没有 `singletonFactories` 这一层，Spring 就失去了按需决定“早期引用到底是原始对象还是早期代理对象”的机会。

### 4. 提前暴露给别人的就是原始半成品对象

不完整。

Spring 真正要提前暴露的，是经过 `getEarlyBeanReference(...)` 处理后、尽量能与最终结果保持一致的早期形态。

### 5. 字段注入的循环依赖能解，只是因为 Spring 更宽容

不成立。

本质原因是字段 / Setter 注入让对象壳子可以先出生，从而给出了一个可提前暴露的时间窗口。

## 收网：Spring 要统一的从来不是“怎么绕过一个环”，而是“生命周期在哪个阶段允许提前暴露对象”

现在可以回到开头那个问题：为什么有的循环依赖 Spring 能解，有的直接炸？

因为对 Spring 来说，真正要面对的不是“依赖图里有没有环”，而是：

- 这个环要求依赖在对象出生前就完整，还是出生后还能补
- 当前 Bean 是否已经进入可提前暴露阶段
- 提前暴露出去的形态是否还能和最终结果保持一致
- 三级缓存怎样按不同生命周期阶段承载这些对象表示

所以 Spring 的答案不是“发现环就缓存一下”，而是重新立出一条严格的阶段化单例主线：

```text
singletonFactories      = 尚未决定最终形态的早期引用工厂
earlySingletonObjects   = 已生成好的早期引用
singletonObjects        = 最终可用单例
getEarlyBeanReference   = 早期引用形态协调点
```

因此，这篇真正该带走的结论不是“Spring 用三级缓存解决循环依赖”，而是：

**Spring 把循环依赖问题从“有没有环”提升成了“Bean 生命周期在哪个阶段允许被提前暴露、又如何保证提前暴露与最终对象语义一致”的容器级协议。**

这也留下了下一篇最自然的问题：既然 Spring 已经能把引用问题在某些场景下解开，那真正把 `@Autowired`、`@Qualifier`、`@Resource` 这些依赖注入请求变成“应该注哪个 Bean”的，又是谁？

也就是说，循环依赖这一篇主要解决了：

- 引用能不能先出现

接下来要进入的则是另一条同样关键、但完全不同的主线：

- 候选 Bean 是怎么被找出来的
- 同类型多个实例时怎么消歧
- `@Autowired` 和 `@Resource` 又为什么不是同一种注入协议
