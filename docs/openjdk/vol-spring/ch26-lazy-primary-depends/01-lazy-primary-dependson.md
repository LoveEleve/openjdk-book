# 为什么 `@Lazy`、`@Primary`、`@DependsOn` 不是三个小注解：Spring 如何用它们继续操纵定义世界对实例世界的控制信号

> 本文基于 Spring Framework 6.x 当前源码。本文只讲 Spring 定义控制主线的第一层：为什么 `@Lazy`、`@Primary`、`@DependsOn` 不能被理解成三个零散的小注解，而必须被看作 BeanDefinition 上三类不同的控制信号——它们分别继续影响实例创建时机、依赖候选裁决和创建顺序。AOT / Native Image、`@Conditional` 自动装配细化和更复杂的 Bean 注册控制，会在后续篇章继续展开。

## 为什么几个看起来只是“注解参数”的小开关，最后会直接改变容器行为

前面这卷已经把很多主线拆得比较清楚了：

- `BeanDefinition` 负责定义世界的蓝图
- `BeanFactory` 负责容器能力树
- `doCreateBean()` 负责单个 Bean 的创建链
- 循环依赖、依赖注入、BPP / BFPP 分别在不同阶段切进来
- scope 又继续把同一张定义蓝图分流成不同生命周期策略

走到这里，一个很自然的问题就会出现：

- 那些看起来像“小控制项”的注解，到底是在什么时候真正生效的？

比如：

- `@Lazy`
- `@Primary`
- `@DependsOn`

如果只从使用层看，它们确实很容易显得很轻：

- 一个决定要不要懒加载
- 一个决定多个候选时优先选谁
- 一个决定谁先创建

但只要往容器主线里一放，你就会立刻发现：

- 这三个问题根本不站在同一个阶段
- 却都在做同一件更大的事：

**继续把定义世界里的控制意图，压回实例世界的执行顺序、候选裁决和生命周期时机。**

第一层问题是：**这些注解不是在 Bean 实例上生效，而是在 BeanDefinition 上先留下控制信号。**

也就是说，Spring 面对的不是：

- 对象创建完以后再看看要不要 lazy
- 注入发生时再现猜哪个是 primary
- 出问题了再临时决定 dependsOn

而是：

- 在定义阶段就先把这些控制语义编码进去
- 到后面的容器主线再按这些信号分流

这说明它们真正属于的是：

- **定义世界里的控制元数据**

而不是实例世界里的后期选项。

第二层问题是：**虽然都写在定义上，但它们影响的是三条不同的实例主线。**

例如：

- `@Lazy` 主要影响“什么时候开始创建”
- `@Primary` 主要影响“多候选时谁赢”
- `@DependsOn` 主要影响“谁必须先于我被拉起”

也就是说，这三者看起来都是“小注解”，但它们最终会分别打到：

- 预实例化阶段
- 依赖解析阶段
- 创建顺序阶段

所以它们不能被当成一组零散附属知识点，而应被理解成：

- **Spring 定义世界控制信号的三个典型样本。**

第三层问题是：**这些注解虽然“很小”，但它们恰恰最能说明 Spring 的一条深层设计习惯。**

也就是：

- 容器不会等事情真的发生了再补判断
- 而是尽量在定义阶段先把后续世界的控制信号编码进去

这和前面整卷很多主题其实是同一种写法：

- scope 提前写在定义里
- 条件语义提前写在定义里
- 工厂方法路径提前写在定义里
- 初始化 / 销毁元数据提前写在定义里

也就是说，`@Lazy`、`@Primary`、`@DependsOn` 不是例外，而是这条设计习惯在三个很高频场景下的集中体现。

因此，本文真正要回答的问题不是“这三个注解分别怎么用”，而是：

**为什么对 Spring 来说，它们必须被理解成定义世界向实例世界发出的三类控制信号，而不是三个分散的小功能开关？**

## 先看失败方案：为什么不能“启动时再决定”“多候选时临时选一个”“等创建时再猜顺序”

理解这三个注解，最好的方式不是分别背语义，而是先看几种特别自然、但一放到容器主线里就会迅速失效的朴素方案。

### 失败方案一：先都按默认规则跑，启动时再临时决定是否 lazy

这是最容易产生的想法。

因为从效果看，`@Lazy` 似乎只是在回答：

- 当前这个 Bean 是现在建，还是以后建

于是很容易进一步觉得：

- 这种事等到预实例化时再临时看一下就行

这个判断的问题在于，它低估了定义世界信号的重要性。

因为对 Spring 来说，`lazy` 不是一个“到时候再猜”的运行时偏好，而是：

- BeanDefinition 上明确携带的创建时机策略

也就是说，预实例化阶段之所以知道“跳过哪些 singleton”，前提恰恰是：

- 这些 Bean 在定义阶段就已经被标记成 lazy

所以 `@Lazy` 的真正价值不是“晚一点建”，而是：

- **定义世界提前告诉实例世界：这个 Bean 不应该进入默认 eager singleton 主线。**

### 失败方案二：多候选时临时选一个最像的就行，不需要定义层信号

如果意识到时机不能太晚，第二种自然想法就会变成：

- 好，那注入时发现有多个候选，再现场挑一个就行
- 反正字段名、实现类名、注册顺序总能给点线索

这个方案的问题在于，它会让依赖注入主线重新退化成大量临时猜测。

因为只要没有 `@Primary` 这种定义层信号，多候选世界就会变得非常脆：

- 这次字段名碰巧能消歧
- 下次字段名不行就炸
- 某些全局默认候选永远没有稳定表达方式

也就是说，Spring 真正要的不是“临时选一个”，而是：

- **在定义阶段先声明：如果只按类型注入，大多数情况下默认先选我。**

这就是 `@Primary` 存在的真正背景。

### 失败方案三：创建顺序等真正 getBean 时沿调用链自然推出来，不必显式声明

这也是很多人第一次看 `@DependsOn` 时会自然产生的想法。

因为在很多情况下，依赖顺序确实能被容器自己推导出来：

- A `@Autowired` B
- 那么 A 创建时自然会触发 B 先创建

于是很容易进一步觉得：

- 既然依赖图都能推出来，那 `@DependsOn` 也许只是多余语法糖

这个判断的问题在于，它忽略了“并不是所有顺序依赖都体现在注入关系里”。

例如：

- 某个 Bean 的 `@PostConstruct` 里会主动碰另一个 Bean
- 某个工厂初始化先要求另一个基础设施先起来
- 两者之间未必存在直接注入边

也就是说，容器自动推导依赖图只能覆盖“显式注入依赖”，却覆盖不了“开发者知道但容器从对象图里看不出来的先后约束”。

这就是为什么 `@DependsOn` 必须存在。

它真正表达的是：

- **这里有一条实例世界必须尊重、但不能只靠 DI 图自动推出的顺序信号。**

## Spring 定义控制信号的最小总图

如果把这条主线先压缩成最小模型，它可以写成下面这样：

```text
bean definition control metadata
   -> affects pre-instantiation / dependency resolution / creation order
   -> changes instance-world behavior without changing bean class itself
```

如果再换一种更容易理解的拆法，这条链可以分成三类控制信号：

```text
[创建时机控制]
@Lazy

   ->

[候选选择控制]
@Primary

   ->

[顺序控制]
@DependsOn
```

这张图最重要的价值，不是让读者记三个注解名字，而是先把三个问题分开：

### 一、创建时机控制

回答：为什么有些 singleton 不应在 Step 11 里默认 eager 创建？

### 二、候选选择控制

回答：为什么多候选时，容器需要一个定义层面的全局默认优先信号？

### 三、顺序控制

回答：为什么有些创建顺序依赖不能从注入图自动推导，而必须由开发者显式告诉容器？

只要先把这三类控制信号分开，`@Lazy`、`@Primary`、`@DependsOn` 就不再像三个互不相关的小注解。

## 一、`@Lazy`：Spring 真正控制的不是“要不要创建”，而是“要不要进入默认 eager singleton 主线”

先从 `@Lazy` 看，最容易被讲浅的一点就是：

- 懒加载 = 晚点创建

这句话当然没错，但对 Spring 主线来说还不够。

更准确的说法应该是：

- `@Lazy` 真正切断的，不是创建本身
- 而是“当前这个 Bean 是否应该进入默认的 eager singleton 预实例化主线”

这一步特别关键。

因为前面 `refresh()` 那篇已经讲过：

- Step 11 `finishBeanFactoryInitialization()` 会统一拉起非 lazy singleton 的预实例化

也就是说，Spring 默认世界其实是：

- singleton 会在容器启动时尽早建出来

那 `@Lazy` 干的就不是“发明一个全新生命周期”，而是：

- **把某个定义从这条默认 eager singleton 主线里摘出去。**

这也解释了为什么 `@Lazy` 的最强语义场景，其实主要就在 singleton 世界里。

因为：

- prototype 本来就是按需创建
- request/session 也天然依赖外部上下文才会出现

所以 `@Lazy` 最有意义的地方，不是“所有作用域都能写”，而是：

- **它在 singleton 世界里重新定义了创建时机。**

也就是说，`@Lazy` 真正重要的不是语法，而是：

- 它把“现在就建”改成了“第一次真正需要时再建”

从定义信号角度看，这就是一条非常典型的：

- 定义世界提前影响实例世界时机

## 二、为什么 `@Lazy` 不是“性能优化开关”，而是生命周期分流信号

很多人第一次用 `@Lazy`，会本能把它理解成：

- 为了加快启动速度

这当然经常是真的，但如果只停在性能层面，就会把它讲浅。

因为从容器主线看，`@Lazy` 真正改变的不是“启动慢不慢”这么单薄，而是：

- 这个 Bean 的出生时间从容器统一 eager 阶段，被推迟到首次真实需求时刻

也就是说，它直接改变了：

- 某个 Bean 何时进入生命周期链
- 某些初始化失败会在启动时报，还是在首次访问时报
- 某些依赖图问题会在 Step 11 暴露，还是在运行期才暴露

这说明 `@Lazy` 不是性能小技巧，而是：

- **生命周期时机分流信号。**

这也解释了为什么它必须写在定义世界里，而不是等实例世界里临时再决定。

## 三、`@Primary`：Spring 真正需要的不是“临场猜谁更像”，而是一个定义层面的全局默认候选信号

只要从 `@Lazy` 转到依赖注入，多候选问题就会变成下一块高频控制信号。

前面依赖注入篇已经讲过：

- `@Autowired` 先按类型找候选
- 再进入 `@Primary`、名字匹配、`@Qualifier`、`@Priority` 这条裁决链

到这里最值得继续压实的一点就是：

- `@Primary` 为什么必须单独存在？

因为对 Spring 来说，它真正解决的不是“这次碰巧该选谁”，而是：

- **在没有更强局部限定时，容器级默认应偏向谁。**

也就是说，`@Primary` 面对的不是某一个注入点的个性化需求，而是：

- 大多数按类型注入场景里的全局默认候选

这也解释了为什么它的信号强度这么高。

因为它不是局部注解，而是在定义阶段就对容器说：

- 如果大家只按类型来问，大多数情况下先把我当默认答案

所以 `@Primary` 不是“多候选的小补丁”，而是：

- **定义层面对依赖注入裁决主线的全局偏置。**

## 四、为什么 `@Primary` 不是 `@Qualifier` 的简化版，而是“全局默认”与“局部覆盖”的层级区分

只要讲到这里，就必须再把一个特别容易混的点说清楚：

- `@Primary` 和 `@Qualifier` 到底差在哪？

很多人会直觉地觉得：

- 都是在多候选时帮忙选一个
- 好像只是粒度不同

这句话方向没错，但还不够深。

更准确的说法应该是：

- `@Primary` 站在定义世界里，声明“我在全局默认语义下优先”
- `@Qualifier` 站在注入点世界里，声明“这一次我要更精确地只选这一类候选”

也就是说，它们不是同一层控制信号：

- 一个是全局默认
- 一个是局部覆盖

这也解释了为什么前面依赖注入篇里，`@Primary` 会比名字匹配和 `@Qualifier` 更早参与裁决链。

因为它先表达的是：

- 容器在整体上更偏向谁

而 `@Qualifier` 后面再来表达：

- 当前这个注入点，我要局部打破那个默认偏向

所以 `@Primary` 不是弱化版 `@Qualifier`，而是：

- **依赖注入世界里的全局默认控制信号。**

## 五、`@DependsOn`：Spring 为什么还需要一个显式顺序信号，明明依赖注入图已经能推导很多创建顺序

只要再往后看，第三类控制信号就出现了：

- `@DependsOn`

它最容易被低估的地方是：

- 前面注入图不是已经能推导很多顺序了吗
- 那这个注解是不是只是很边缘的补充

这个判断不稳。

因为 Spring 自动推导顺序，真正依赖的是：

- Bean 之间存在可见的注入关系

但现实里有很多顺序需求，并不会体现在注入图上。

例如：

- 某个 Bean 的 `@PostConstruct` 里会主动去调用另一个基础设施 Bean
- 某个 listener 或初始化组件要求另外一套系统先准备好
- 某些 side-effect 依赖顺序，是开发者知道、但对象图本身看不出来的

也就是说，容器自动推导依赖图解决的是：

- 隐式可见的依赖顺序

而 `@DependsOn` 解决的是：

- **开发者显式知道、但注入图未必能表达出来的顺序约束。**

这就是为什么它必须存在。

它不是为了和 `@Autowired` 重复，而是为了补上另一类完全不同的顺序来源。

## 六、为什么 `@DependsOn` 不等于依赖注入：它控制的是创建顺序，不是对象引用本身

这里必须再把一个特别容易混淆的边界钉死。

因为很多人一看到 `@DependsOn`，就会自然把它理解成：

- 哦，那不就是另一个依赖注入声明吗

这当然不对。

更准确地说：

- `@Autowired` / `@Resource` 最终是要把某个对象引用注进去
- `@DependsOn` 则是在说：在创建我之前，你先把另一个 Bean 拉起来

也就是说，它真正控制的是：

- **创建顺序**

而不是：

- **对象引用关系**

所以它即使不产生字段注入，也依然可以深刻影响实例世界主线。

这一步特别重要，因为它说明：

- Spring 里“依赖”这个词并不总等于“对象图上的引用”
- 有时它只是“生命周期顺序约束”

所以 `@DependsOn` 真正属于的是：

- 定义世界对实例世界启动顺序的显式控制协议

## 七、为什么这三个注解必须合在一起看：它们共同构成“定义世界如何继续压住实例世界”的三个典型样本

看到这里，最值得回收的一个问题就是：

- 为什么这篇不把 `@Lazy`、`@Primary`、`@DependsOn` 当三个零散小注解分别讲完？

答案就在于，它们虽然作用点不同，却都在做同一件更大的事：

- **让定义世界继续控制实例世界。**

也就是说：

- `@Lazy` 控制创建时机
- `@Primary` 控制候选默认偏向
- `@DependsOn` 控制创建顺序

看起来各不相同，但它们都说明了 Spring 一条特别稳定的设计习惯：

- 不等实例真的跑起来以后再猜怎么处理
- 而是在定义阶段就先把后续实例世界的控制信号编码进去

这和前面：

- scope
- 条件装配
- 工厂方法路径
- 生命周期回调元数据

其实是同一类设计。

也就是说，这篇真正想立住的不是三个注解知识点，而是：

- **定义世界如何继续通过一组控制信号，操纵实例世界的时机、选择和顺序。**

## 八、几个最容易错的判断

### 1. `@Lazy` 只是启动优化开关

不成立。

它真正改变的是 Bean 何时进入实例生命周期链，是定义世界对创建时机的重新分流。

### 2. `@Primary` 只是多个候选时临时选一个的简化写法

不成立。

它表达的是定义层面的全局默认偏向，而不是局部注入点的临场选择。

### 3. `@DependsOn` 和 `@Autowired` 只是两种写依赖的方式

不成立。

`@Autowired` 控制的是对象引用注入，`@DependsOn` 控制的是创建顺序，语义层完全不同。

### 4. 这三个注解只是一些边角控制项，不影响主干机制

不成立。

它们分别直接打到预实例化、依赖裁决和创建顺序主线，是定义世界压住实例世界的高频控制信号。

### 5. prototype、request、session 也天然都该和 `@Lazy` 一样讨论

不完整。

`@Lazy` 最核心的战场在 eager singleton 世界里；其他作用域天然就已经有不同的按需创建语义。

## 收网：Spring 要统一的从来不是“给几个小注解一点特权”，而是“让定义世界继续决定实例世界怎么开始、选谁、先后怎样”

现在可以回到开头那个问题：为什么 `@Lazy`、`@Primary`、`@DependsOn` 看起来只是三个很小的控制项，Spring 却值得为它们单独拉出一条主线？

因为对 Spring 这种 IoC 容器来说，它真正要面对的不是“注解参数怎么读”，而是：

- 哪些 singleton 要不要进入默认 eager 启动链
- 多候选世界里默认偏向谁
- 哪些创建顺序约束不能只靠依赖注入图自动推导

所以 Spring 的答案不是在实例世界里临时猜，而是在定义世界里先编码控制信号：

```text
@Lazy      -> 控制 eager singleton 是否延后进入实例链
@Primary   -> 控制多候选世界的全局默认偏向
@DependsOn -> 控制显式的创建顺序约束
```

因此，这篇真正该带走的结论不是“Spring 还有三个小注解可以调行为”，而是：

**Spring 把这些控制项从“使用层小技巧”提升成了“定义世界继续操纵实例世界的时机、候选和顺序”的容器级控制信号。**

这也留下了下一篇最自然的问题：既然主干卷已经把定义世界、实例世界、配置类扩张、条件装配、作用域、上下文实现和事件基础设施都立住了，那回到 Spring 生态里最直接让人感知到“配置类驱动容器行为”的那层 AOT / Native Image 支持，为什么又必须在定义世界阶段把很多运行时行为前移成编译时贡献？

也就是说，接下来最自然的继续点就是：

- AOT
- RuntimeHints
- BeanRegistrationAotContribution
- 为什么 Native Image 支持会逼 Spring 重新思考“哪些事情必须在运行时做”
