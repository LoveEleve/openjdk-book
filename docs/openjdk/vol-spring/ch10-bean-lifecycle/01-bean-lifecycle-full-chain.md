# 一个 Bean 是怎么活起来的：Spring 为什么把生命周期压成 `doCreateBean()` 这一整条创建链

> 本文基于 Spring Framework 6.x 当前源码。本文只讲 Bean 生命周期主线的第一层：为什么容器在拥有 `BeanDefinition` 蓝图和 `BeanFactory` 能力树之后，并不会简单地 `new` 出对象就结束，而必须继续经过 `createBeanInstance`、`populateBean`、`initializeBean`、`registerDisposableBean` 等一整条创建链。循环依赖的三级缓存细节、`BeanPostProcessor` 体系纵深和 `doGetBean()` 入口控制，会在后续篇章继续展开。

## 为什么 “创建一个 Bean” 在 Spring 里从来不只是一次构造函数调用

从普通 Java 程序的视角看，创建对象通常是一件非常局部的事。

你最熟悉的路径往往是：

- `new UserService()`
- 构造函数跑完
- 对象就已经可以用了

即使稍微复杂一点，也不过是：

- 构造之后再 set 几个属性
- 再手工调用一个 `init()`

但一旦把视角切到 Spring IoC 容器，问题立刻变得完全不同。

因为对 Spring 来说，一个 Bean 从“定义”走到“可用对象”，中间至少还要经过几类完全不同的阶段：

- 实例到底怎么创建
- 依赖什么时候填进去
- `@Autowired` / `@Value` 这些注入点在哪里被处理
- `@PostConstruct`、`afterPropertiesSet()`、自定义 init-method 什么时候执行
- AOP 代理又是在 Bean 生命周期的哪一刻包上去
- 最后销毁回调又是在哪一步被登记下来

也就是说，Spring 真正面对的从来不是：

- 现在怎么 new 一个对象

而是：

- **如何把“定义世界里的蓝图”推进成“容器世界里的可用实例”。**

第一层问题是：**Bean 的构造、注入、初始化，本来就不是一件事。**

这是第一次系统读 Spring 时最容易混成一团的地方。

在普通代码里，这几件事经常贴得很近：

- 构造函数里顺手做点初始化
- 外面再 set 一些值
- 最后就开始使用

但 Spring 容器里，这三件事必须被显式拆开。

因为它们依赖的信息、依赖的扩展点、以及失败后的语义都不同：

- 构造阶段解决“对象壳子怎么出来”
- 属性填充阶段解决“依赖怎么进来”
- 初始化阶段解决“对象何时才算真正可用”

这说明 Spring 要组织的不是一次单点动作，而是一条阶段化创建链。

第二层问题是：**后处理器、感知接口、注解回调、AOP 代理，都想插进这条链。**

如果 Bean 生命周期只是一次 `new`，那像下面这些能力几乎都无处安放：

- `BeanNameAware`
- `BeanFactoryAware`
- `@PostConstruct`
- `InitializingBean`
- 自定义 `init-method`
- `BeanPostProcessor`
- `AbstractAutoProxyCreator`

也就是说，Spring 的 Bean 创建不是一个封闭动作，而是一条：

- 允许很多容器级机制按顺序插入、修改、增强的管线

这也是为什么它不能被讲成“实例化 + 注入 + 初始化”三个词就完事。

第三层问题是：**Bean 进入可用状态之后，容器还要提前为它的退出做安排。**

这是很多人第一次读 `doCreateBean()` 时容易忽略的一点。

因为大家天然更关注：

- 对象怎么活起来

却容易忘了容器从创建阶段就已经在布局：

- 以后这个 Bean 要怎么退场
- 哪些 destroy 回调要登记
- 哪些销毁逻辑以后由容器统一收口

这说明 Bean 生命周期在 Spring 里从来不是“生成对象之后就结束”，而是：

- **从创建开始，就已经连着后续退场链一起被组织。**

这里还要把边界再说得更硬一点：本文讲的是**单个 Bean 从定义走到可用实例的创建主链**，不是整个 `ApplicationContext.refresh()` 的容器生命周期。也就是说：

- 容器生命周期关心“整个上下文什么时候启动、什么时候关闭”
- 本篇 Bean 生命周期关心“单个 Bean 在容器内部怎样被创建、填充、初始化、登记退出”

因此，本文真正要回答的问题不是“Spring 有个 `doCreateBean()` 做 Bean 创建”，而是：

**为什么对 Spring 来说，一个 Bean 不能被理解成“调用构造器之后就可用了”，而必须被组织成一条可插入、可增强、可登记退出动作的完整生命周期链？**

## 先看失败方案：为什么不能把 Bean 生命周期理解成 `new -> set -> init` 三步

理解 `doCreateBean()` 最好的方式，不是先背 13 个内部步骤，而是先看几种看起来非常合理、但一放到 IoC 容器里就会迅速失效的朴素方案。

### 失败方案一：一读到 BeanDefinition，就直接 `new` 一个对象

这是最符合普通程序员直觉的方案。

因为从类的角度看，一个对象最自然的出生方式当然就是：

- 找到构造函数
- 调用构造函数
- 返回实例

如果 Spring 只是一个普通对象工厂，这么做几乎完全够用。

但 Spring 容器面对的不是“只要有个对象就行”，而是：

- 这个对象之后还要参与依赖注入
- 还要接受 `Aware` 回调
- 还要走前后置处理器
- 还可能在初始化之后被代理包裹
- 还要登记销毁回调

也就是说，单纯 `new` 出来的只是“对象壳子”，远不是“Spring 可用 Bean”。

所以 Spring 真正要做的不是一次构造，而是：

**把一个对象从裸实例推进成容器可用实例。**

### 失败方案二：那就 `new` 完以后把属性 set 进去，再调一次 init，不就够了

如果意识到单纯构造不够，第二种很自然的思路就是：

- 先构造实例
- 再做依赖注入
- 最后统一调 init

这比第一种前进了很多，因为它已经开始承认生命周期是分阶段的。

但它仍然不够。

因为对 Spring 来说，问题不只是“这三步都要做”，而是：

- 每一步中间都可能插入容器扩展点
- 某些步骤执行前后顺序有严格约束
- 初始化前后分别会触发不同类型的后处理器
- 代理生成不能随便放在任何位置

例如最典型的一条：

- AOP 代理为什么通常不是在构造后立刻生成，而是在初始化链更后的位置出现

这就说明，Spring 生命周期主线并不是三步动作拼接，而是：

- **一条带有插入点、顺序约束和增强阶段的创建管线。**

### 失败方案三：后处理器能改什么就随便插，顺序不重要

第三种特别容易被低估的看法是：

- 既然 Spring 给了 `BeanPostProcessor`
- 那它们爱在什么时候改 Bean 都行
- 反正最后都能改到对象

这个判断在容器里非常危险。

因为只要顺序稍微错位，后果就会立刻出现：

- 还没填完依赖就开始做代理
- `@PostConstruct` 在对象没准备好时就执行
- 感知接口还没回调就进入初始化逻辑
- destroy 元数据还没登记，对象已经被外层当成完整 Bean 使用

也就是说，Spring 生命周期链最重要的特征之一，不只是“有很多扩展点”，而是：

- **这些扩展点必须插在正确阶段。**

所以 `doCreateBean()` 的关键不在于步骤多，而在于它把这些阶段边界强行组织起来了。

## Spring Bean 生命周期的最小总图

如果把这条主线先压缩成最小模型，它可以写成下面这样：

```text
BeanDefinition
   -> instantiate bean
   -> expose early lifecycle hooks
   -> populate dependencies
   -> initialize bean
   -> wrap if necessary
   -> register destroy metadata
```

如果再换一种更容易理解的拆法，这条链可以分成五段职责：

```text
[实例准备]
createBeanInstance

   ->

[定义后处理与提前暴露]
applyMergedBeanDefinitionPostProcessors / early exposure

   ->

[依赖填充]
populateBean

   ->

[初始化与增强]
initializeBean / BeanPostProcessor / proxy creation

   ->

[退场登记]
registerDisposableBeanIfNecessary
```

这张图最重要的价值，不是让读者记住若干内部方法名，而是先把五个问题分开：

### 一、实例准备

回答：Bean 的“对象壳子”到底是怎么出来的？

### 二、定义后处理与提前暴露

回答：为什么对象还没完全初始化，容器就已经开始围绕它布局后续主线？

### 三、依赖填充

回答：`@Autowired`、`@Value` 这类注入点到底在哪个阶段被处理？

### 四、初始化与增强

回答：`Aware`、`@PostConstruct`、`afterPropertiesSet()`、自定义 init-method 和 AOP 代理到底如何排顺序？

### 五、退场登记

回答：为什么 Bean 还没真正进入使用期，容器就已经开始安排它未来的销毁路径？

只要先把这五层职责分开，`doCreateBean()` 就不再像一个又长又密的内部实现函数。

## 一、`doCreateBean()`：Spring 不是在“创建对象”，而是在“推进定义进入实例世界”

只要从整个生命周期主线看，`doCreateBean()` 最容易被误读成：

- Bean 创建函数

这当然没错，但还不够深。

更准确地说，它真正组织的不是一次局部对象构造，而是：

**把一张定义蓝图持续推进成一个容器可用对象。**

这句话特别重要。

因为它直接区分了两件很容易混在一起的事：

- “构造出一个 Java 对象”
- “得到一个 Spring 世界里真正可用的 Bean”

在普通程序里，这两者经常可以近似等同。

但在 Spring 容器里，它们之间隔着一整条创建链：

- 实例创建
- 元数据后处理
- 依赖填充
- 初始化回调
- 后置增强
- 销毁登记

这里还要补一个和下一篇 `doGetBean()` 之间的边界：`doCreateBean()` 虽然是核心创建链，但它并不是每次 `getBean()` 调用都会完整穿透到这里。只要单例缓存已经命中，`doGetBean()` 往往就会直接返回，根本不会再进入这条创建主线。

也就是说：

- `doGetBean()` 负责判断“这次是不是需要真正创建”
- `doCreateBean()` 负责在“确实要创建时”推进完整生命周期链

所以 `doCreateBean()` 的价值不在于“步骤很多”，而在于：
- 它把定义世界和实例世界之间的过渡，组织成了一条可被容器控制的流水线

从整卷前十篇一起回头看，这种写法也很一致：

- `BeanDefinition` 已经告诉容器“以后应该如何创建这个对象”
- `BeanFactory` 已经把容器能力按读取、枚举、配置、组合分层立住
- 到这里，`doCreateBean()` 才真正开始回答：

**这些能力最终怎样把定义蓝图推进成一个实例。**

所以这条主线的起点不是对象，而是定义；终点也不是“new 完”，而是“容器可以把它当成完整 Bean 继续使用”。

## 二、`createBeanInstance`：生命周期第一步不是注入，而是先决定“对象壳子怎么出来”

只要继续往里看，生命周期链第一块最底层的工作并不是注入，也不是初始化，而是：

- 先把对象壳子弄出来

这就是 `createBeanInstance` 这一段的意义。

它之所以重要，是因为它回答的不是“要不要创建”，而是：

- **到底通过哪条实例化路径创建。**

例如：

- 走普通构造器
- 走带参数构造器
- 走工厂方法

也就是说，Spring 生命周期的第一步不是“给对象加功能”，而是：

- 先解决最原始的出生路径

这一步特别值得强调，因为很多人第一次学 Bean 生命周期时，容易直接把注意力放到：

- `@Autowired`
- `@PostConstruct`
- AOP

可这些都发生在对象壳子已经出现之后。

所以 `createBeanInstance` 的教学意义在于：

**生命周期再复杂，也必须先回答“Bean 是怎么出生的”。**

### 为什么构造器注入和字段/Setter 注入不是同一件事

只要实例化这一段展开之后，另一个非常重要的问题也会自然冒出来：

- 构造器注入和字段注入到底为什么不只是语法喜好？

答案就在生命周期阶段划分本身里。

因为：

- 构造器注入是在对象壳子出生时就把关键依赖一起带进来
- 字段或 setter 注入则要等到后面的 `populateBean` 阶段才真正填进去

这说明两者的差异不只是“代码风格”，而是：

- **依赖是在对象出生时就完整，还是对象出生后再补齐。**

也正因为如此，构造器注入通常更接近“对象一出生就是完整的”；而字段注入则让对象在生命周期链的前半段暂时处于“壳子已在、依赖未齐”的状态。

这层差异对后面理解提前暴露、循环依赖和初始化边界非常关键。

再往前推一步，它还会直接影响“循环依赖到底有没有解”的可能性：

- 构造器注入要求依赖在对象出生时就完整到位
- 字段 / Setter 注入则允许对象壳子先存在，依赖稍后再补

也就是说，为什么有些循环依赖可以被三级缓存化解、有些却天然会失败，根子其实从这里就已经埋下了。

## 三、为什么 Bean 还没完全准备好，Spring 就已经在布局后续主线

只要对象壳子出来以后，Spring 并不会立刻冲去填依赖。

它中间还会先做几件看起来有点“未卜先知”的事情，例如：

- 应用合并后的定义后处理器
- 某些场景下的提前暴露准备

很多人第一次看到这一段都会自然困惑：

- 对象都还没准备好，为什么容器这么早就开始布置后续链路？

这恰恰说明 Spring 的生命周期管理，从来不是一条线性“想到哪做哪”。

更准确地说，它从很早就已经在同时考虑两件事：

- 当前这个对象接下来怎么继续变完整
- 以及它未来在其他主线里如何被看见、被引用、被增强

也就是说，生命周期链不是“做完一步再想下一步”，而是：

- **对象一出生，容器就已经开始为它未来进入更复杂主线做准备。**

这也就是为什么后面循环依赖那一篇不能脱离 `doCreateBean()` 来看。

因为很多“为什么对象还没完全初始化就先暴露”的疑问，根其实都在这里。

同样，后面 `BeanPostProcessor` 体系为什么会在不同阶段拥有不同插点，也不是从空中掉下来的复杂性，而是从这里开始分岔：

- 哪些动作发生在实例化之后、注入之前
- 哪些动作发生在初始化之前
- 哪些动作发生在初始化之后

也就是说，这一段不是旁枝，而是后续循环依赖与 BPP 纵深篇共同的根节点。

## 四、`populateBean`：`@Autowired`、`@Value` 不是 Bean 自己干的，而是容器在这个阶段把依赖灌进去

只要生命周期推进到依赖填充阶段，很多开发者最熟悉的“魔法”就开始真正出现了：

- `@Autowired`
- `@Value`
- XML property 注入

这些能力之所以值得单独拎出来，是因为它们特别容易给人错觉：

- 好像对象自己知道该怎么把依赖拿进来

这当然不是真的。

更准确地说，`populateBean` 的真正意义在于：

**容器在这一阶段接管对象，把定义世界里的依赖信息真正灌进实例壳子里。**

这一步非常关键，因为它把两个世界真正接上了：

- 定义里早就写好的依赖与属性元数据
- 当前已经出生但还不完整的 Java 对象

也就是说，`populateBean` 不是“多做一点 set 操作”，而是：

- Bean 实例从“壳子”走向“内部依赖开始成型”的阶段

更准确地说，这一阶段不是对象自己“主动拿依赖”，而是容器开始兑现定义蓝图里早就写好的依赖契约，把这些契约真正落到实例身上。

这也解释了为什么前面那篇 `BeanDefinition` 不能省。

因为如果没有定义世界里提前记录的那些元数据，`populateBean` 根本无从知道：

- 应该往哪里注入
- 注入什么类型
- 某些值是不是还要先经过 `Environment` 与 `ConversionService`

所以 `populateBean` 真正的教学位置，不是“注入点在哪里”，而是：

**IoC 容器第一次把定义元数据真正落进实例内部。**

## 五、`initializeBean`：一个 Bean 什么时候才算真正可用，不由构造函数决定，而由初始化链决定

很多人学 Spring 生命周期时，最熟悉的几个名字通常都集中在这里：

- `BeanNameAware`
- `BeanFactoryAware`
- `@PostConstruct`
- `afterPropertiesSet()`
- 自定义 `init-method`

这会让人很容易产生一个错觉：

- 初始化阶段不就是调几个回调吗

这个理解太轻了。

因为 `initializeBean` 真正回答的问题不是“调哪些方法”，而是：

**Spring 世界里，一个 Bean 到底从哪一刻开始才算真正可用。**

这一步特别重要。

因为从容器视角看：

- 构造完成，不等于可用
- 依赖注入完成，也不一定等于可用
- 只有当感知回调、前置处理器、初始化方法链都跑过以后，容器才更接近说“这个 Bean 已经准备好了”

这就是为什么初始化链必须被单独组织起来，而不能混在实例化或属性填充里随便做。

### 为什么 AOP 代理通常在初始化后阶段出现

这一点是理解整个初始化链最值得停一下的地方。

因为很多人会本能问：

- 既然最后 Bean 可能是代理对象，为什么不早点直接产代理？

答案在于 Spring 要保证：

- 代理包裹的目标对象，先已经是一个尽量完整、已完成初始化语义的对象

也就是说，AOP 代理放得太早，问题就会立刻出现：

- 对象自身依赖还没填完
- `@PostConstruct` 还没跑
- 初始化主线还没真正收口

这就说明初始化后置阶段之所以重要，不只是因为“顺序规定如此”，而是因为：

- **Spring 要先把目标对象推进到足够完整，再让增强机制包住它。**

所以 `initializeBean` 不只是回调集合，而是：

- 容器对“Bean 已经可用”这件事的最终收口阶段

这也正是为什么下一篇不能直接跳去讲某个单独的 `BeanPostProcessor` 实现，而要先补全 `BeanPostProcessor` 体系全景：只有把这条初始化收口线看清，读者才会知道每类 BPP 到底插在生命周期的哪一段、为什么必须插在那里。

## 六、`registerDisposableBeanIfNecessary`：Spring 在创建阶段就已经开始安排对象未来怎么退场

只要 Bean 初始化链走到尾声，很多人会下意识觉得生命周期差不多讲完了。

但对 Spring 来说，创建链到这里还没真正结束。

因为容器在对象正式交给外部使用之前，还要先做一件非常关键的事：

- 把它未来的销毁路径登记好

这就是 `registerDisposableBeanIfNecessary` 这类动作的重要性。

它特别值得强调的一点是：

**Spring 在创建阶段就已经把退出路径一起布置进生命周期链了。**

这说明 Bean 生命周期在 Spring 里从来不是：

- 出生阶段先讲完
- 死亡阶段以后再随便补

而是：

- 一旦对象被创建出来，容器就已经开始安排它以后如何退场

这和前面 `BeanDefinition` 那篇的结论其实完全一致：

- 生命周期契约在定义阶段就提前编码进蓝图
- 到 `doCreateBean()` 末尾，容器又把这些销毁语义真正挂回自己的后续退场主线

也就是说，Spring 这里从来不是“先活起来再说”，而是：

- **从出生开始，就同时安排未来如何退出。**

## 七、为什么 `doCreateBean()` 不是“13 个步骤很多”，而是“很多世界在同一条链里汇合”

看到这里，最值得回收的一个问题就是：

- 为什么 `doCreateBean()` 会显得这么重要、这么长、这么容易反复被讲？

答案其实不在于“步骤数量”，而在于它恰好是很多前置主线第一次真正汇合的地方。

至少到目前为止，整卷前十篇已经铺过的主线都会在这里重新碰头：

- `BeanDefinition` 提供创建蓝图
- `BeanFactory` 提供定义世界与容器能力树
- `Environment` 和 `ConversionService` 会参与 `@Value` 这类属性注入
- 顺序体系和注解元数据体系会影响后处理器和注入链的组织方式
- 条件装配体系更早决定了哪些定义根本不会走到这条链

也就是说，`doCreateBean()` 之所以核心，不是因为它只是“创建函数”，而是因为：

**前面铺开的很多协议，到这里第一次真正变成一条实例创建流水线。**

这也解释了为什么这一篇必须紧接在 `BeanDefinition` 和 `BeanFactory` 之后写，而不是等到 `BeanPostProcessor`、循环依赖或 AOP 全讲完再回头补。

因为不先把这条主创建链立住，后面那些专题都容易变成“局部技巧”，而看不到它们插入的到底是哪条大链。

## 八、几个最容易错的判断

### 1. Bean 生命周期本质上就是 `new -> set -> init`

不成立。

Spring 组织的是一条带有后处理器、感知回调、增强阶段和销毁登记的完整创建链，而不是三步脚本。

### 2. 构造完成就说明 Bean 已经可用

不成立。

构造完成往往只代表对象壳子出现了，依赖填充、初始化回调和后置增强都还没发生。

### 3. `@Autowired`、`@Value` 是 Bean 自己完成的

不成立。

它们是在 `populateBean` 阶段由容器主线统一处理的，不是对象自身魔法。

### 4. AOP 代理只是最后顺手包一下，无所谓放前放后

不成立。

代理出现的位置直接关系到对象是否已经完成注入和初始化，这是一条严格的生命周期边界。

### 5. 销毁逻辑和创建逻辑无关，后面再看就行

不成立。

Spring 在创建阶段末尾就已经开始登记未来退场路径，生命周期从一开始就是前后连着的。

## 收网：Spring 要统一的从来不是“如何构造对象”，而是“如何把定义推进成可用 Bean”

现在可以回到开头那个问题：为什么 Spring 里的 Bean 生命周期不能被理解成一次构造函数调用？

因为对 Spring 这种 IoC 容器来说，它真正要面对的不是“对象怎么 new”，而是：

- 定义蓝图如何进入实例世界
- 依赖如何在正确阶段灌进去
- 初始化、感知回调、后处理器和代理如何按顺序插入
- 销毁路径如何在创建阶段就被登记进来

所以 Spring 的答案不是“边创建边顺手补点逻辑”，而是明确立出一条生命周期主线：

```text
createBeanInstance                 = 对象壳子如何出生
applyMergedBeanDefinition...       = 定义后处理与准备阶段
populateBean                       = 依赖填充阶段
initializeBean                     = 初始化与增强收口阶段
registerDisposableBeanIfNecessary  = 退场登记阶段
```

因此，这篇真正该带走的结论不是“Spring 有个 `doCreateBean()` 很核心”，而是：

**Spring 把 Bean 问题从“如何构造一个对象”提升成了“如何让一张定义蓝图经过依赖填充、初始化、增强和退场登记，最终进入容器可用世界”的生命周期协议。**

这也留下了下一篇最自然的问题：既然 Bean 生命周期主链已经立住了，那其中最常插进来的那套扩展世界——`BeanPostProcessor`——到底是如何按层次切进实例化前、属性填充前后、初始化前后，甚至销毁阶段的？

也就是说，接下来最自然的继续点就是：

- `InstantiationAwareBeanPostProcessor`
- `SmartInstantiationAwareBeanPostProcessor`
- `DestructionAwareBeanPostProcessor`
- `CommonAnnotationBeanPostProcessor`
- `AbstractAutoProxyCreator`
