# Spring 里的 `${server.port}` 到底从哪来：`Environment`、`PropertySource` 与占位符解析如何组成一条配置主线

> 本文基于 Spring Framework 6.x 当前源码。本文只讲 Spring 配置属性主线的第一层：为什么容器不能把配置值理解成“某个 properties 文件里的一行字符串”，而必须引入 `PropertyResolver`、`Environment`、`PropertySource`、`MutablePropertySources`、`PropertySourcesPropertyResolver` 与占位符解析器这一整套机制。Spring Boot 更复杂的 ConfigData 外部化配置优先级、`@ConfigurationProperties` 绑定和条件注解读取环境的具体链路，会在后续篇章继续展开。

## 为什么一个看起来很普通的 `${...}`，最后会长成 Spring 的一整条环境主线

第一次看到 Spring 里的配置属性时，很多人都会先把它想成一个很轻的能力。

因为表面上最常见的写法通常只是：

- `@Value("${server.port}")`
- `@Value("${server.port:8080}")`
- `environment.getProperty("server.port")`

直觉上，这看起来像一件很朴素的事：

- 找一个 key
- 拿到一个字符串值
- 没有的话用默认值

如果站在单个配置文件的视角，这种理解当然不离谱。

因为在最简单的程序里，配置经常确实只有一份来源：

- 一个 `application.properties`
- 一个 `Map<String, String>`
- 或者一个启动脚本里的参数对象

但一旦把视角切到 Spring 这种容器框架，问题会立刻变得复杂得多。

第一层变化是：**Spring 面对的不是一个配置文件，而是一组可能互相覆盖的配置来源。**

同一个 key 例如 `server.port`，在真实系统里可能同时出现在：

- Java 系统属性 `-Dserver.port=9090`
- 操作系统环境变量
- `application.properties`
- 外部追加的 `PropertySource`
- Web 容器里的 servlet / JNDI 上下文

这时 Spring 真正要回答的就不再只是“值是什么”，而是：

- 这些来源谁优先
- 同名 key 冲突时谁覆盖谁
- 运行时还能不能动态插入一个新来源

也就是说，它要统一的不是“某个配置文件的读取”，而是：

**很多来源如何被组织成一条有优先级的配置查找链。**

第二层变化是：**配置值最终不只是字符串，还会继续进入后面的类型转换和容器装配主线。**

前一篇已经讲过，Spring 不会把值转换散落成一堆 `parseXxx()`。这篇刚好站在它的前一步：

- 在进入 `ConversionService` 之前，值得先从哪里来？

所以 `${server.port}` 这件事并不只是“字符串替换”，而是整套链路里的前半段：

- 先从环境里按优先级找值
- 再解析默认值、嵌套占位符、转义
- 最后才把结果继续交给类型转换体系

如果这一层没有统一起来，上一章建立起来的转换主线就没有稳定输入源。

第三层变化是：**`${...}` 不是配置值本身，而是一种语法。**

这也意味着，`environment.getProperty("server.port")` 和 `@Value("${server.port}")` 虽然最后都可能拿到同一个值，但它们并不是同一层动作。

更准确地说：

- `environment.getProperty("server.port")` 更像直接向环境来源链提问
- `@Value("${server.port}")` 则先有一层占位符语法解释，再把其中的 key 交给环境来源链求值

这两条路径在结果上经常相交，所以最容易被误看成一件事；但对 Spring 来说，它们其实对应的是环境系统里的两条不同主线。

也就是说，当 Spring 看到：

- `${server.port}`
- `${server.port:8080}`
- `${a.${b}}`
- `\${literal}`

它首先面对的不是“值是什么”，而是：

- 这段文本里哪些是普通文本
- 哪些是占位符
- 默认值分隔符在哪里
- 嵌套结构怎么递归解析
- 未命中时是保留原文还是直接抛错

这就说明，环境系统里其实同时存在两条相关但不同的主线：

- **配置来源主线**：值从哪里来
- **占位符语法主线**：值如何从文本模板里被解释出来

因此，本文真正要回答的问题不是“Spring 有个 `Environment` 可以读配置”，而是：

**为什么对 Spring 来说，一个看似简单的 `${server.port}`，最后必须被提升成“有序配置来源 + 查找责任链 + 占位符解析器”的统一环境主线？**

## 先看失败方案：为什么单个 `Map`、单个配置文件和正则替换都不够

理解 Spring 的环境系统，最好的方式不是先背接口，而是先看几种看起来很自然、但一放到容器里就会失效的朴素方案。

### 失败方案一：所有配置都塞进一个 `Map<String, String>`

这是最符合普通应用直觉的方案。

因为对很多简单程序来说，配置最终确实都能长成这样：

- key 是字符串
- value 也是字符串
- 读取时 `map.get(key)`

如果 Spring 面对的永远只有一份来源，这么做甚至很合理。

但问题在于，容器面对的是真实运行环境，而不是一个静态配置对象。只要来源一多，`Map` 模型立刻会暴露一个关键缺口：

- **它只能告诉你“现在值是什么”，很难告诉你“这个值是在哪个优先级关系里胜出的”。**

也就是说，一旦同时存在：

- 系统属性里的 `server.port=9090`
- 文件里的 `server.port=8080`

如果一开始就把它们拍平进一个 `Map`，你会失去两类非常重要的信息：

- 这些值原本来自哪个来源
- 如果后面再插入一个新来源，它应该如何进入已有优先级体系

所以 Spring 需要的不是“最终拍平后的配置结果”，而是：

**带来源身份、带顺序语义的配置来源集合。**

### 失败方案二：就按固定顺序读几个配置文件，谁后读谁覆盖

如果意识到单个 `Map` 不够，第二种自然的做法就是：

- 好，那我保留多个来源
- 按固定顺序读取
- 后读的覆盖先读的

这个方案在某些小框架里也常见，但它仍然不够 Spring 用。

因为 Spring 真正面对的问题，不只是“我有多个来源”，而是：

- 来源种类本身是开放的
- 顺序可能在运行时被调整
- 某些子环境（例如 Servlet 环境）会额外补进自己的来源
- 上层框架（例如 Spring Boot）还会继续往里插很多来源

换句话说，Spring 需要的是：

- 一个可以动态增删的来源容器
- 一套清晰的优先级语义
- 一个统一查找入口，而不是让调用方自己知道每个来源该怎么遍历

所以它真正要组织的不是“几个文件的覆盖规则”，而是一条：

**配置来源责任链。**

### 失败方案三：`${...}` 解析用正则替换就行

很多人一看到占位符语法，第一反应是：

- 这不就是字符串模板替换吗
- 正则找出 `${...}`
- 替换掉里面的 key 就完了

这个方案最大的诱惑在于，它对最简单的 `${server.port}` 确实能跑。

但只要语法往前走一步，正则方案就很快撑不住：

- `${server.port:8080}` 有默认值分隔
- `${a.${b}}` 有嵌套占位符
- `\${literal}` 有转义
- 严格模式和宽松模式对未命中占位符的行为还不同

也就是说，占位符不是简单模式串，而是一种带递归和边界语义的小语法。

所以 Spring 在这里真正需要的不是“替换一下字符串”，而是：

**先把占位符当成语法对象解析，再按环境查找链去求值。**

这就是为什么环境系统不能只是一堆 `Map` 和 `replaceAll()`。

## Spring 环境系统的最小总图

如果把这条主线先压缩成最小模型，它可以写成下面这样：

```text
property sources
   -> ordered property source container
   -> property resolver
   -> placeholder parser
   -> raw string value
   -> conversion service
   -> target typed value
```

如果再换一种更容易理解的拆法，这条链可以分成五段职责：

```text
[统一读取入口]
PropertyResolver / Environment

   ->

[来源抽象]
PropertySource

   ->

[有序来源容器]
MutablePropertySources

   ->

[查找责任链]
PropertySourcesPropertyResolver

   ->

[语法解析]
Placeholder parser / PropertyPlaceholderHelper
```

这张图最重要的价值，不是让读者记住几个类名，而是先把五个问题分开：

### 一、统一读取入口

回答：调用方究竟依赖哪一组稳定动作来取配置，而不是自己遍历每个来源？

### 二、来源抽象

回答：为什么 Spring 不直接让所有来源都拍平成一个 `Map`？

### 三、有序来源容器

回答：多个来源如何被组织成一条可调整的优先级链？

### 四、查找责任链

回答：同一个 key 到底是怎样按顺序命中“第一个有效值”的？

### 五、语法解析

回答：`${...}`、默认值、嵌套和转义这些语法是如何被解释出来的？

只要先把这五层职责分开，`Environment` 就不再像“读配置的小工具”。

## 一、`PropertyResolver` 和 `Environment`：Spring 先统一“怎么提问”，再统一“从哪里回答”

如果先站在调用方视角，Spring 的环境系统第一层抽象其实很克制。

它并没有要求调用方先知道：

- 现在是不是该读系统属性
- 还是该读环境变量
- 还是该读某个外部配置文件

相反，它先提供了一个更统一的问题接口：

- `containsProperty(...)`
- `getProperty(...)`
- `getProperty(key, defaultValue)`
- `getProperty(key, targetType)`

这就是 `PropertyResolver` 的位置。

它最重要的价值，不是方法多，而是：

**先把所有环境读取请求统一成一种提问方式。**

调用方只说：

- 我要取这个 key
- 我希望要么拿到字符串，要么拿到某个目标类型
- 如果没有，也许我接受默认值

这和上一章 `ConversionService` 的设计取向其实高度一致：

- 上层先统一“怎么提问”
- 具体值怎么找、怎么转，延后给后面的系统处理

`Environment` 则在这个基础上再往前走一步。

它不是替代 `PropertyResolver`，而是在“属性读取”之上，继续把：

- active profiles
- default profiles

这些与环境切换强相关的能力合进来。

也就是说，`Environment` 在 Spring 里回答的已经不只是：

- 一个 key 的值是什么

还包括：

- 当前容器站在什么环境集合里运行

这一步特别重要，因为它说明 Spring 的“环境”从来不是纯配置字典，而是：

**配置读取语义 + 环境选择语义的统一入口。**

## 二、`PropertySource`：Spring 要组织的不是一张配置表，而是一组有身份的来源

只要统一读取入口立住之后，下一步最自然的问题就是：

- 这些值到底从哪里来？

Spring 对这个问题的回答不是直接给你一张大 `Map`，而是先引入 `PropertySource`。

这一步的核心价值，不是“再包一层 key-value 存储”，而是：

**让每一种配置来源都先保留自己的身份。**

为什么这个身份这么重要？

因为对容器来说，配置来源差异不是噪声，而是语义本身的一部分。

例如：

- 系统属性和环境变量的优先级不同
- Servlet 上下文来源和普通本地来源不是一回事
- 某个来源以后可能要被动态插到最前面或最后面

如果这些来源一开始就被压平，后面的优先级、调试、扩展、覆盖关系都会变得模糊。

所以 Spring 引入 `PropertySource` 的本质，不是为了“包装配置”，而是为了建立一个更准确的世界模型：

```text
配置值不是天上掉下来的
它总是属于某一个来源
```

而且这里不只是“身份信息”问题，还涉及运行时取值语义本身可能不同。

因为不同来源回答 `getProperty(key)` 的方式，本来就未必一样：

- 有的来源更接近普通 key-value 映射
- 有的来源可能带着环境变量命名兼容规则
- 有的来源来自容器上下文，本身就站在另一套资源边界上

也就是说，`PropertySource` 不是给同一种 `Map` 多套一个壳，而是在表达：

**这些来源不只顺序不同，连“如何解释和提供一个值”都可能不同。**

也正因为如此，`PropertySource` 在这里的角色更像：

- 带名字的来源节点
- 对外暴露统一的 `getProperty(key)` 能力
- 但不丢掉“我是谁”这层身份信息
- 也不抹平“我是如何给出这个值”的来源语义差异

这一步如果不讲清，后面的优先级链、调试能力和来源特化行为都会显得平白无故。

## 三、`MutablePropertySources`：Spring 不是只有多个来源，而是有一条可调整的优先级链

有了 `PropertySource` 之后，真正的问题才刚刚开始。

因为一组来源只是“多个节点”，但 Spring 还必须进一步回答：

- 它们谁在前
- 谁在后
- 冲突时谁优先
- 运行时还能不能被重排

这就是 `MutablePropertySources` 的位置。

它最关键的意义不在于“维护一个列表”，而在于：

**Spring 把配置来源明确组织成了一条可变的优先级链。**

这一点和“多个来源放进集合里”完全不是一回事。

因为只要顺序有意义，整个环境系统就会立刻拥有新的行为能力：

- `addFirst(...)` 表示我要让这个来源压过已有来源
- `addLast(...)` 表示它只是兜底来源
- 遍历顺序天然就是查找优先级顺序

也就是说，Spring 不是在维护“来源集合”，而是在维护：

**一个按顺序组织起来的配置世界。**

这也解释了为什么 `MutablePropertySources` 在名称里不只是 `PropertySources`，而是 `Mutable`。

因为对 Spring 来说，来源顺序不是初始化时一次写死的。不同环境、不同上层框架、不同运行阶段，都可能继续往这条链前后插东西。

而这层“可插可调”的价值，最终一定要回到读者最熟悉的覆盖现象上才真正落地。

例如同一个 `server.port`：

- 如果系统属性来源被 `addFirst(...)` 放在前面，而文件来源在后面
- 那查找时系统属性会先命中
- 文件里的同名值即使存在，也不会参与这次返回结果

反过来，如果某个上层框架在运行时把新的来源继续插到最前面，它就不是“多了一份配置”，而是“整个覆盖关系被重新裁决了一次”。

所以 `addFirst/addLast` 不是容器内部的小 API，而是 Spring 把“谁覆盖谁”这件事真正固化进结构里的方式。

所以它真正承担的是：

- 结构上，组织多个来源
- 语义上，表达优先级
- 运维上，允许后续继续调整
- 教学上，把大家熟悉的“为什么这个值覆盖了那个值”落回一条真实可操作的结构链

没有这一层，后面责任链式查找就没有稳定基础。

## 四、`PropertySourcesPropertyResolver`：查找不是聚合，而是“首个非 null 即返回”的责任链

有了统一入口、有身份的来源、有顺序的来源容器之后，真正的配置查找才开始成立。

这一层的关键角色就是 `PropertySourcesPropertyResolver`。

它最值得抓住的，不是它会“遍历所有来源”，而是它遍历的方式非常有立场：

**首个非 null 即返回。**

这句话看起来朴素，实际上就是整套优先级语义的真正落地点。

也就是说，Spring 并不是把所有来源值收集起来再做复杂合并，而是：

- 按当前顺序一个个问过去
- 谁先给出非空答案，谁就赢
- 后面的来源就不再继续参与这次 key 的裁决

这正是一条标准责任链。

不过这里还要补一层边界，避免把这句话理解得过扁：

- “首个非 null 即返回”描述的是来源命中规则
- 命中后的值并不一定就是最终可直接交付给调用方的最后结果

因为一旦当前入口是占位符语法，比如 `@Value("${outer}")`，那么首个命中的原始值仍然可能包含：

- 嵌套占位符
- 默认值语法片段
- 需要继续解释的文本模板

也就是说，`PropertySourcesPropertyResolver` 在这里首先做的是：

**把值从哪一个来源赢出来。**

而“这个赢出来的值还要不要继续解析占位符语法”，则是下一层占位符主线要继续接手的问题。

这也是为什么环境系统不能被粗暴简化成“找到第一个值就完了”。

它最重要的教学意义是：

- Spring 的环境优先级不是一个抽象概念
- 而是每次 `getProperty()` 时都会被重新执行的一条查找协议
- 但来源裁决完成，并不等于语法解释也已经完成

所以像下面这种现象才会成立：

- `-Dserver.port=9090`
- 文件里 `server.port=8080`

只要系统属性来源排在前面，那么：

- 第一个命中就是 9090
- 后面的 8080 根本不会进入这次返回值决策

这也说明 `PropertySourcesPropertyResolver` 不是“把多来源封装一下”的平凡实现，而是：

**把来源顺序真正翻译成查找行为。**

### 为什么“找不到返回 null”不是软弱，而是上层语义留白

这一层还有个特别容易被误解的点：

- 为什么找不到值时很多接口直接返回 `null`？

这不是因为 Spring 在这里不够严格，而是因为它要给更上层语义留出空间。

例如：

- 有的调用方接受默认值
- 有的占位符解析处于宽松模式，允许原文保留
- 有的调用方则会继续走“required”语义并最终抛错

也就是说，“没找到”在 Spring 里不是单一结局，而只是：

- 当前查找链没有命中

真正要不要失败、怎么失败，取决于更上层语义。

这和前一篇里“查不到转换器不一定立刻崩，而要交给桥接层继续处理”的设计风格是一致的。

## 五、`StandardEnvironment`：默认环境不是空白画布，而是先带着一组基本来源进场

只要讲到责任链，就不能不回答另一个实际问题：

- 一条默认的 Spring 环境链，最开始都有什么来源？

这就是 `StandardEnvironment` 的意义。

它特别值得强调的一点是：

**Spring 默认环境不是一张空白配置表，而是一开始就带着一组基础来源进场。**

至少在标准环境里，最核心的两类来源就是：

- Java 系统属性
- 操作系统环境变量

而且顺序本身就已经带着默认立场：

- 系统属性在前
- 环境变量在后

这说明 Spring 在环境系统这里并不只是给你一个“可扩展接口”，它还主动给出了一套最基础、最通用的默认优先级世界。

这一步非常关键，因为它让很多日常行为看起来像“理所当然”：

- `-D` 参数为什么经常能覆盖环境变量
- 即使你还没接 Spring Boot，基本环境系统也已经能工作

所以 `StandardEnvironment` 的作用，不是“某个默认实现”这么轻，而是：

**把环境主线的默认世界先搭起来。**

## 六、占位符解析器：`${...}` 不是正则替换，而是一套小语法

前面讲的来源容器和查找责任链，解决的是：

- 一个 key 的值从哪里来

但 `${...}` 这件事还有另一半问题：

- 一段文本里的占位符语法怎么被解释出来

这就是占位符解析器的角色。

Spring 在这里真正要面对的，不是简单模板替换，而是一种带规则的小语法。至少它要处理：

- 普通占位符 `${key}`
- 默认值 `${key:default}`
- 嵌套占位符 `${a.${b}}`
- 转义字面量 `\${literal}`

只要把这些放在一起看，就会发现一件事：

- 这已经不是正则替换能轻松表达的东西

因为一旦出现嵌套，解析器就必须知道：

- 哪一段是文本
- 哪一段是占位符
- 默认值分隔符是不是当前层的
- 什么时候该递归求内部表达式
- 当前失败是“语法没切开”，还是“切开了但值没找到”

这最后一点尤其关键。

也就是说，Spring 这里的解析器不是在做一轮随手替换，而更像一个很小但很完整的内部状态机：

- 先把输入拆成普通文本 Part 和占位符 Part
- 占位符 Part 再继续区分 key、本层默认值分隔、是否还有内层占位符
- 只有在这一层结构被切清之后，才轮到后面的 resolver 去向环境来源链提问
- 如果失败，失败也必须先被归因：到底是语法结构有问题，还是来源里没有值

这就是为什么它不能靠一个“从左到右的正则替换”硬撑过去。正则当然能抓到最简单的 `${key}`，但一旦语法进入：

- 嵌套
- 转义
- 默认值
- 层级分隔

它就不再是“匹配文本模式”这么简单，而变成“解释一段小语言”。

所以 Spring 这里更像是在做：

**先把字符串拆成可解析片段，再以递归和分层求值的方式推进这套小语法。**

这也解释了为什么今天新的占位符解析器实现会往 `Part` 列表和递归求值的方向走，而不是继续堆复杂正则。

从方法论角度看，这一点尤其重要，因为它说明：

- 环境系统不只是在管理值来源
- 它还在管理值语法
- 而语法解析失败和来源查找失败，本来就是两种不同的边界

这两条线缺一不可。

## 七、宽松模式和严格模式：Spring 不只要“会解析”，还要保留失败语义选择权

占位符解析里还有一层特别关键、但很容易被低估的设计：

- 未命中占位符时，到底怎么办？

很多框架在这里会直接选一种固定行为：

- 要么必须报错
- 要么静默保留原文

Spring 的做法更克制：

- 它保留两种模式
- 让上层在不同场景下自己决定失败语义

这背后的原因其实很深。

因为对不同入口来说，“没找到值”并不一定意味着同一件事：

- 有的地方把它当成致命配置缺失
- 有的地方只想先保留原文，后面再由别的阶段报更精准的错误

所以这里真正被设计出来的，不只是“语法支持”，而是：

**环境系统对失败语义也不急着一刀切，而是把最后裁决权交给更上层。**

但这里还必须再把责任边界说得更细一点。

- `PropertyResolver` / `Environment` 这一层，更靠近“来源查找”：某个 key 在当前责任链里有没有命中
- `PropertyPlaceholderHelper` / 占位符解析阶段，更靠近“语法求值”：一段模板文本里未解析的占位符，最后该保留、该补默认值，还是该抛错

这两者当然会前后衔接，但它们不是同一个开关。

也就是说：

- `getProperty("missing")` 返回 `null`，首先是在说“来源链没命中”
- `${missing}` 在占位符解析时是否报错，则还要看当前解析模式是宽松还是严格

如果把这两层混成一个判断，读者就很容易误会成：

- Spring 对“找不到值”的所有处理都由同一个布尔开关控制

而真实情况更细：

- 先有来源层事实判断
- 再有语法层失败语义裁决

这与 `PropertySourcesPropertyResolver` 找不到值先返回 `null` 的取向，其实是同一条设计哲学：

- 当前层先把事实判断出来
- 更上层再决定它要变成宽松结果，还是严格错误

这就是为什么 Spring 的环境系统看起来温和，但其实边界很严谨。

## 八、这条链最终怎么接回上一篇的类型转换主线

到这里，环境系统已经把自己的问题回答得比较完整了：

- 值从哪里来
- 谁优先
- `${...}` 怎么解析
- 默认值、嵌套、转义怎么处理

但它还不是完整闭环。

因为对 Spring 来说，一个环境值最终常常不会停在“原始字符串”上，而是要继续进入上一篇讲过的类型转换主线。

也就是说，这两篇实际上拼成的是一条前后紧接的链：

```text
配置来源责任链
   -> 占位符语法解析
   -> 原始字符串值
   -> ConversionService / TypeConverterDelegate
   -> 目标类型值
```

这也是为什么本篇必须紧接在 `ConversionService` 前后去看，而不能完全孤立。

因为：

- 没有环境系统，转换系统就没有稳定输入
- 没有转换系统，环境系统就只能停在字符串层

所以这两篇并不是两个平行话题，而是：

**Spring 配置值从“来源”走到“目标类型”的一条连续主线。**

## 九、几个最容易错的判断

### 1. `Environment` 就是一张大配置表

不成立。

Spring 真正组织的是一组带身份、带顺序、可调整的配置来源，而不是一张拍平后的 `Map`。

### 2. 多个 `PropertySource` 的优先级只是约定，不影响真实查找行为

不成立。

优先级最终会直接落在 `PropertySourcesPropertyResolver` 的“首个非 null 即返回”责任链上。

### 3. `${...}` 只是正则替换一下

不成立。

默认值、嵌套占位符和转义都说明它是一套小语法，而不是简单模板替换。

### 4. 找不到配置值直接报错才更合理

不完整。

Spring 在环境系统里故意保留了宽松与严格两种失败语义，让不同上层自己决定如何解释“未命中”。

### 5. 环境系统和类型转换系统是两个互不相关的话题

不成立。

环境系统负责回答“原始值从哪里来”，类型转换系统负责回答“这个原始值如何变成目标类型”，两者是一条连续链。

## 收网：Spring 要统一的从来不是“某个配置文件怎么读”，而是“整套环境值如何被组织、裁决和解释”

现在可以回到开头那个问题：为什么 `${server.port}` 看起来那么简单，Spring 却要做出 `Environment` 这整条主线？

因为对 Spring 这种容器框架来说，它真正要面对的不是“一个配置文件里某个 key 的读取”，而是：

- 多个来源并存
- 来源之间要有优先级
- 同一段文本里还带着占位符语法
- 解析出来的原始值后面还要继续进入类型转换与容器装配

所以 Spring 的答案不是继续堆 `Map` 和字符串替换，而是重新立一条统一环境链：

```text
PropertyResolver / Environment = 统一提问入口
PropertySource                 = 带身份的配置来源
MutablePropertySources         = 可调整的优先级容器
PropertySourcesPropertyResolver = 首个命中即返回的查找责任链
Placeholder parser             = 占位符语法解析器
```

因此，这篇真正该带走的结论不是“Spring 有个 `Environment` 可以读配置”，而是：

**Spring 把配置问题从“某个文件怎么读某个 key”提升成了“整套环境值如何被分来源组织、按优先级裁决、按语法解释，并继续送入容器主线”的框架级协议。**

这也留下了下一篇最自然的问题：既然配置来源和占位符解析都已经立住了，那多个来源、多个后处理器、多个监听器、多个拦截器之间的顺序问题，又为什么最后会反复回到 `Ordered`、`PriorityOrdered` 和 `@Order` 这套优先级体系？
