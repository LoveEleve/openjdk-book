# 02. 先选问题类型，再选事件 —— 事件与采样参数

> **前置依赖**：已经能用 `asprof` 对一个目标 JVM 跑一次最短采样
> → **后续**：输出格式与火焰图 —— 采样完以后结果该给谁看、怎么读
>
> 场景：你已经能把 profiler 跑起来，但一到现场就会遇到更关键的问题：CPU 高、堆分配多、线程阻塞、锁竞争，这些现象看起来都叫“性能问题”，却不能用同一组事件和同一颗旋钮去看。
>
> 本篇参数和示例已回对 async-profiler 当前 `README.md`、`docs/GettingStarted.md`、`docs/ProfilerOptions.md` 与容器/排障文档。这里讲的是“面对哪类问题时该选什么事件、怎么调最常用参数”，不是 AP-2 那种底层引擎实现细节；但会提前守住一些使用层必须知道的边界，例如 `-e` 选的是问题类型，不是输出标签，`-i` 调的是精度/成本平衡，`memlimit` 和容器权限属于使用层就要先承认的现实约束。

## 先把真正的困惑摆出来：同样都叫“性能问题”，为什么不能拿同一组事件去看

很多人第一次把 async-profiler 跑通之后，会自然形成一个错觉：既然已经有一个统一的 profiler 工具，那现场遇到性能问题时，先上最熟的命令就行。这个直觉最常见的表现就是：不管 CPU 高、对象分配多、线程在睡、锁竞争严重，第一反应都还是 `-e cpu`。

这恰恰是最该先纠正的地方。对 async-profiler 来说，`-e` 从来不只是一个标签，它是在告诉采样器“这次到底想观察哪类运行时现象”。CPU 热点、分配压力、锁竞争、阻塞等待，这几件事虽然都叫“性能问题”，但它们根本不是同一种观测对象。

如果问题问错了，后面命令写得再熟也没用。CPU 事件最擅长回答“时间花在哪”；alloc 更擅长回答“谁在制造对象压力”；lock 更擅长回答“谁在因为锁竞争付成本”；wall 更擅长回答“线程总的墙钟时间都耗在哪里，尤其是等待、阻塞和睡眠”。

所以最常见的失败方案，其实不是参数没调细，而是问题类型先选错了。明明在排查阻塞，却还只看 CPU；明明在看分配风暴，却还指望 flame graph 上的 CPU 宽度自己把答案讲出来。这样会得到很多“看上去有热点”的图，但热点并不一定对应你真正想问的问题。

可以先把这条决策链压成一张图：

```text
先问问题类型
  ├─ CPU 热点       → -e cpu
  ├─ 分配压力       → -e alloc
  ├─ 锁竞争         → -e lock
  └─ 阻塞 / 等待 / 睡眠 → -e wall

再调三颗基础旋钮
  → -d 采多久
  → -i 采多密
  → -f 结果往哪条消费链走

再决定结果聚焦与自保护
  → threads / include / exclude / filter
  → memlimit
  → 容器 / perf / fdtransfer / ctimer 等环境边界
```

*关键设计（斜体）：* *async-profiler 的事件和参数不是平铺选项表，而是一条决策链：先分清你在观察哪类问题，再决定采样时长、密度、输出去向以及如何聚焦结果、保护采样器自身。*[模式: 问题类型优先 + 精度/成本平衡]

先记住这一句总领：别先问“我最熟哪条命令”，先问“我到底在看 CPU、分配、锁竞争，还是阻塞”。后面的事件和参数选择，都是这个问题的后继问题。

## 第一层：`-e` 选的不是输出格式，而是问题类型

当前 README 明确列出了 async-profiler 能覆盖的主要对象：CPU 时间、Java 堆分配、native memory、锁竞争，以及更多硬件/软件计数器（`README.md:12-19`）。如果只看最常见的生产排查入口，通常先记四个：

- `-e cpu`：看 CPU 热点；默认场景往往也是它；
- `-e alloc`：看谁在大量分配对象；
- `-e lock`：看谁在锁竞争；
- `-e wall`：看线程总墙钟时间，更容易暴露阻塞、等待和睡眠。

这里最关键的不是记命令本身，而是意识到：这四个事件回答的不是同一个问题。比如：

```bash
asprof -e alloc -d 30 -f alloc.html 8983
```

这条命令和 `-e cpu` 在 CLI 层写法很像，但它真正要回答的已经变成“30 秒里对象分配热点是谁”，而不是“CPU 时间花在哪”。如果现场问题是 GC 压力、堆 churn 或对象风暴，alloc 往往比 cpu 更直接；反过来，如果你拿 alloc 去理解“为什么线程一直占 CPU”，也会自然偏掉。

同样，wall 和 cpu 也非常容易被混。CPU 更像“线程真正在消耗 CPU 时间”；wall 更像“线程整个墙钟时间花在哪，包括睡眠、等待、阻塞”。如果你面对的是慢请求、线程卡顿、下游阻塞或睡眠时间长，wall 往往比 cpu 更接近你真正的问题类型。

所以 `-e` 最不该被理解成“随手挑一个标签”。它选的是观察对象，是问题类型，不是输出样式。

*关键设计（斜体）：* *使用层只暴露一个 `-e`，但这颗旋钮真正切换的是“你在观察哪类运行时现象”；CPU、alloc、lock、wall 虽然共用入口，却不共享同一个问题语义。*[模式: 统一入口 + 问题类型分流]

## 第二层：`-d`、`-i`、`-f` 三颗最常调的旋钮，真正调的是什么权衡

选完事件之后，最常动的三颗旋钮通常就是 `-d`、`-i`、`-f`。它们之所以重要，不是因为记住它们最省事，而是因为它们几乎决定了“这次采样在现场到底是更轻、更粗，还是更细、更重”。

### `-d`：你愿意观察多长一段窗口

Getting Started 已经把 `-d <seconds>` 讲得很清楚：它控制采样时长（`docs/GettingStarted.md:51-56`）。对使用层来说，`-d` 的意义不是简单的“等多久”，而是你愿意观察多长的一段现象窗口。

太短，热点可能没来得及显影；太长，现场噪声可能混进来，或者你只是把多个问题混在同一张图里。比如瞬时 CPU 抖动和长时间稳定高负载，对 `-d` 的理想取值就不一样。

### `-i`：你愿意用多高成本换多细的统计颗粒

Getting Started 同时给了另一个关键事实：默认 CPU 采样频率是 100Hz，也就是每 10ms 一次（`docs/GettingStarted.md:58-59`）。这已经足够说明 `-i` 的本质：它不是一个“越小越专业”的参数，而是在调统计精度与现场成本的平衡。

比如：

```bash
asprof -e wall -d 60 -i 5ms -f block.html 8983
```

这条命令对使用层的直观意义就是：用 wall 事件观察 60 秒，并把采样间隔调得更密，试图更细地捕捉阻塞相关路径。这样命中热点的概率更高，但额外开销也更大。

这里必须打掉一个特别常见的失败方案：`-i` 越小越好。事实恰恰相反。太短的间隔可能让 profiler 自己变得过于频繁，给高负载系统带来额外扰动。官方 `Troubleshooting.md` 甚至明确提醒，过短间隔可能导致对重 CPU 负载代码的连续中断，建议的 workaround 就是简单地把 interval 调大（`docs/Troubleshooting.md:109-112`）。

所以 `-i` 不是“把质量开到最高”的旋钮，而是“你愿意为更细粒度付多少现场成本”的旋钮。

### `-f`：不只是存哪儿，还在决定结果走哪条消费链

`-f` 最容易被误解成“只是文件路径”。但 Getting Started 已明确指出：当输出文件名以 `.html` 结尾时，flame graph 会自动选中（`docs/GettingStarted.md:92-109`）。也就是说，`-f` 不只是“存哪儿”，它还会反向决定“结果将往哪条消费链路走”。

同一个结果如果落到终端，更像即时文本；落到 `.html`，更像浏览器里的 flame graph；落到 `.jfr`，则意味着你打算把它交给 JFR 工具链或 converter 继续消费。也正因为如此，下一篇才会专门把“输出格式与火焰图读法”单独拎出来讲，而不是在参数篇里一笔带过。

*关键设计（斜体）：* *`-d`、`-i`、`-f` 看起来像三颗普通旋钮，实质上分别在决定：你观察多长窗口、你愿意付多大统计成本，以及结果最后要进入哪条消费链。*[模式: 观察窗口 + 精度/成本 + 消费去向]

## 第三层：线程、过滤和 `memlimit` 为什么不改变“采什么”，却决定结果能不能看、采样器能不能稳

选对事件、调好时长和间隔之后，使用层很快还会遇到另一类参数：它们不直接改变“采什么”，却显著影响结果能不能聚焦，以及采样器自身能不能稳住。

最常见的几类是：

- `-t` / `--threads`：按线程拆分结果；
- `-I` / `-X`：只保留或排除某些栈路径；
- `--filter`：在特定模式下只看指定线程；
- `--memlimit`：限制 call trace storage 可用内存。

### 为什么这些参数不该被理解成“另一种事件”

它们的共同点是：不会把 CPU 突然变成 alloc，也不会把 wall 变成 lock；它们改的是“结果如何聚焦”和“采样器怎样自我保护”。

比如 `--threads` 会让你从“全局热点总图”切换成“线程分开看”，这不是在换观测对象，而是在换结果切片方式。`-I` / `-X` 也是一样，它们不是改事件语义，而是在控制哪些栈路径被保留、哪些被丢开。

### `memlimit` 为什么对使用层同样重要

`--memlimit` 更是一个特别值得在 AP-0 就先建立意识的参数。`ProfilerOptions.md` 已明确写出：它限制的是 call trace storage 使用的内存，一旦超过限制，就不再记录新的 stack traces；最低有效值 10MB，默认无限制（`docs/ProfilerOptions.md:60`）。

这一步的意义，不只是告诉你“有个内存选项”，而是在提醒你：async-profiler 并不是一个无限缓存、无限容纳调用栈的黑盒。它本身也是一个要在生产环境里控制成本、保护自己的 native 组件。

也就是说，当你在现场提高线程拆分、提高栈深、拉长时间窗口或提升采样密度时，不只是在换结果清晰度，也是在改变 profiler 自身对内存和存储的压力。使用层如果不先建立这个意识，后面看到 overflow 或样本边界时就会完全措手不及。

所以线程、过滤和 `memlimit` 这一层，更准确的定位应该是：让结果更能看，让采样器更能活，而不是“再来几种事件”。

## 第四层：为什么容器和权限问题在使用层就必须先承认，而不能等看源码时再说

如果说前面三层还主要在做“使用决策”，那么容器与权限这一层其实是在提醒你：async-profiler 的事件选择从来不只是业务语义问题，它常常还叠着系统边界。

README 把 `CPU Sampling Engines` 和 `Profiling In Container` 单独列成文档（`README.md:97-110`），这本身就已经说明：平台差异不是底层细节，而是使用层一开始就得面对的现实。容器文档进一步明确指出，在 Docker 默认限制下，`perf_event_open` 可能拿不到；常见退路包括放开 seccomp、使用 `fdtransfer`，或者退到 `ctimer`（`docs/ProfilingInContainer.md:17-24`）。

这里必须故意收紧一句边界：官方容器文档给出的 `ctimer` 是常见退路，但这不等于“CPU 事件只有这一种降级路径”。后面进入 AP-2 时还会专门拆开 `perf`、`itimer`、`ctimer` 等不同引擎，不把它们混成同一个“CPU 事件实现”。

之所以要在 AP-0 提前提这件事，是因为它直接决定你第一条命令能不能跑通。如果你在容器里一看到 `-e cpu` 失败，就把问题理解成“命令写错了”或“async-profiler 不支持容器”，那排查从起点就偏了。更准确的理解应该是：你面对的是 CPU 事件在当前系统边界下的实现约束。

同样，`Troubleshooting.md` 里关于 `perf_event_open()` 失败、locked memory limit、`ulimit -l`、`kernel.perf_event_mlock_kb` 这些说明（`docs/Troubleshooting.md:7-16、57-68`），也都在提醒一件事：很多“看起来像事件问题”的现象，实际上是系统权限和内核约束在起作用。

所以使用层必须先承认一个现实：事件选择不是抽象问题类型这么简单，它常常还叠着“当前系统允许你用哪条路径去观察这个问题”。

*关键设计（斜体）：* *对 async-profiler 来说，事件选择从来不是纯语义开关，它常常同时受平台、容器、权限和内核能力约束；这类差异越早在使用层承认，后面越不会把环境问题误判成命令问题。*[模式: 事件语义 + 系统边界叠加]

## 收网：先选问题类型，再选事件，再调旋钮

如果把整篇话压成一句话，async-profiler 的事件和参数从来不是一张平铺选项表，而是一条面向现场的决策链：先分清你面对的是 CPU、分配、锁竞争还是阻塞；再用 `-d/-i/-f` 平衡观察窗口、统计成本和消费链；最后再用线程、过滤、`memlimit` 以及环境退路让结果更能看、采样器更能稳。

```text
先问问题类型
  ├─ CPU 热点       → -e cpu
  ├─ 分配压力       → -e alloc
  ├─ 锁竞争         → -e lock
  └─ 阻塞 / 等待 / 睡眠 → -e wall

再调三颗基础旋钮
  → -d 采多久
  → -i 采多密
  → -f 结果往哪条消费链走

再决定结果聚焦与自保护
  → threads / include / exclude / filter
  → memlimit
  → 容器 / perf / fdtransfer / ctimer 等环境边界
```

到这里，主线只发生了三件事。

第一，`-e` 选的不是输出格式标签，而是你在观察哪类问题类型；CPU、alloc、lock、wall 虽然共用入口，但不共享同一种问题语义。

第二，`-d/-i/-f` 三颗最常用旋钮，真正控制的是观察窗口、统计成本和消费去向，而不是“参数越大越全面、越小越专业”这种简单线性关系。

第三，线程、过滤、`memlimit` 与容器/权限边界提醒你：让结果更能看、让采样器更能活、让命令能在当前环境里真正跑通，同样属于使用层必须先做的决策。

*关键设计（斜体）：* *使用 async-profiler 时，真正该先做的不是翻选项表，而是先回答三个问题：我在看什么问题、我愿意付多少现场成本、结果最后要往哪条消费链走；事件和参数只是这三个问题的落地方式。*[模式: 问题类型优先 + 精度/成本 + 结果去向]

**本篇的一句话困惑**：同样都叫“性能问题”，为什么 async-profiler 不能拿同一组事件和同一组参数去看？

**本篇的一句话顿悟**：因为 `-e` 选的是问题类型，`-d/-i/-f` 调的是观察窗口、统计成本和消费去向，线程/过滤/`memlimit` 则继续决定结果能不能看、采样器能不能稳；它们不是平铺选项，而是一条决策链。
