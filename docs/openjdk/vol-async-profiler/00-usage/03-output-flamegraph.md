# 03. 先决定给谁看，再决定输出什么 —— 输出格式与火焰图读法

> **前置依赖**：已经知道常见事件和基础采样参数
> → **后续**：与 Arthas 衔接 —— 同一采样内核在两套工具里的落点和使用边界
>
> 场景：你已经跑出一次采样，但结果并不是一个固定对象；有时要给自己看，有时要给脚本、JMC 或可观测平台看，如果不先分清消费方，就会把 flamegraph、JFR、文本栈和 OTLP 混成一团。
>
> 本篇示例和格式说明已回对 async-profiler 当前 `README.md`、`docs/GettingStarted.md`、`docs/ConverterUsage.md`。这里讲的是“结果该给谁消费、该走什么工作流”，不是 AP-5 那种格式内部实现细节；但会提前守住几个使用层必须知道的边界，例如火焰图不是时间线、`minwidth` 不是采样期丢样、`reverse` 与 `inverted` 不是同一个开关。

## 先把真正的困惑摆出来：同一份样本，为什么不能只固定导成一种格式

很多人第一次跑 async-profiler 时，会自然地把“结果”想成一个固定对象：采完以后总该有一份 profile，然后你打开看看就行。但真正用起来很快会发现，这个直觉是错的。同一份样本面对不同消费者时，完全可能需要变成完全不同的东西。

如果你只是想自己尽快找热点，浏览器里的 flame graph 往往最顺手；如果你想把结果交给 shell 脚本继续加工，collapsed、flat、traces 这种文本形态会更方便；如果你要把档案带回本地、让 JMC 或 converter 工具继续分析，JFR 更像一个可复用中间件；如果最终结果是要送进可观测平台，那么机器真正想吃的是 OTLP 之类的 profile 协议，而不是 HTML。

也就是说，“采样结果是什么”这件事，从来不是独立于消费方存在的。你不先问“谁要消费这份结果”，后面就很容易陷入几个常见误区。

第一个误区，是把所有输出都看成“同一份数据换个后缀”。如果真这么理解，就会以为 `.html`、`.jfr`、`.collapsed`、`.pb` 只是导出样式差别，仿佛谁都能互相替代。可它们背后站着的并不是同一类读者：浏览器、人类、脚本、JFR 生态、可观测平台，各自关心的结构完全不同。

第二个误区，是觉得只要有一种最通用格式，所有场景都统一用它就行。比如统一只保留 HTML，或者统一只保留 JFR。前者会让脚本和平台消费变得别扭，后者则会让“我只想快速看热点”这种最常见场景徒增一层中间格式成本。

第三个误区，是拿错了读图模型。尤其是火焰图，很多人会下意识把横向宽度读成程序执行时间线，仿佛从左到右就是“先做了什么，后做了什么”。但火焰图从来不是时间顺序回放，它表达的是样本或计数占比。只要这个直觉没先纠正，后面 flamegraph 读法就会整篇跑偏。

所以这一篇真正要回答的不是“有哪些输出选项”，而是：为什么 async-profiler 把输出格式本身当成消费契约，以及面对不同消费方时应该怎样选。

可以先把这件事压成一张图：

```text
同一份采样样本
  → 先问消费方是谁
    ├─ 人类浏览器视图   → flamegraph / tree / html
    ├─ 终端 / 脚本       → collapsed / flat / traces
    ├─ JFR 生态 / 离线分析 → jfr
    └─ 可观测平台       → otlp

服务器现场
  → 低开销采集
    → JFR 存档
      → 本地 jfrconv / jfr-converter.jar
        → html / collapsed / heatmap / otlp
```

*关键设计（斜体）：* *async-profiler 的输出格式不是“采样之后随手挑个皮肤”，而是消费契约：先分清谁要吃这份结果，再决定该直接导 HTML、保留 JFR，还是走转换链。*[模式: 消费方优先 + 采集/消费分层]

先记住这一句总领：对 async-profiler 来说，输出格式不是附属修饰，而是结果要交给谁消费的协议选择。后面所有具体格式和工作流，都是围绕这句话展开的。

## 第一层：先按消费方分，而不是先按命令行选项分

如果从 README、Getting Started 和当前卷主干文章把输出族重新整理一遍，其实最稳的切法不是“按格式名罗列”，而是“按消费方分层”。

### 第一类：flamegraph / tree / `.html` —— 主要给人看

这一类的核心目标，是尽快让人类看出热点分布。`flamegraph` 对应的是交互式 HTML 火焰图，`tree` 对应的是浏览器里的树状调用视图。它们不是交换格式，也不是脚本协议，而是最终展示物。

Getting Started 已经明确说明：如果输出文件名以 `.html` 结尾，工具会自动选 flame graph（`docs/GettingStarted.md:92-109`）。这说明很多“格式选择”其实在文件名层就已经提前完成了。

如果你只是想最快看 CPU 热点，最短命令依旧是：

```bash
asprof -d 30 -f /tmp/flamegraph.html 8983
```

这里之所以“最快”，不是因为 HTML 更底层，而是因为它最贴合“人自己先看一眼”这个消费方。

### 第二类：collapsed / flat / traces —— 更适合终端、脚本和二次加工

这一类输出比 HTML 更接近文本或半结构化结果。collapsed 适合后续文本处理或与转换器互转；flat 和 traces 则分别偏热点方法列表和栈文本展开。它们对人也不是不能读，但真正的优势在于：容易在终端里直接扫、容易喂给脚本、容易做简单自动化。

所以不要把它们误解成“比 HTML 更原始，因此更正确”。更准确的说法是：它们服务的是另一类工作流——脚本、终端、二次加工，而不是浏览器交互展示。

### 第三类：JFR —— 给 JFR 生态和离线转换链消费

JFR 是当前 async-profiler 非常重要的一条“中间档案”路径。它既能被 JMC、`RecordingFile`、`jfr` 等 JFR reader 消费，又能继续喂给 `jfrconv` / `jfr-converter.jar` 转成 flame graph、collapsed、heatmap 甚至 OTLP。

所以它和 HTML 的差异，不在于“谁更高级”，而在于工作流角色不同。HTML 更像最终展示物；JFR 更像可再消费、可带走、可复用、可比较的档案格式。

### 第四类：OTLP —— 给可观测平台吃的机器协议

OTLP 则是另一个世界：它不是给浏览器的，也不是给 JFR reader 的，而是给 OpenTelemetry / 可观测平台消费的 profile 协议。你一般不会直接在终端里“看” OTLP，你更常做的是把它送进平台，让平台去索引、聚合和关联 traces / metrics / logs。

所以如果你要把结果接入平台生态，继续执着于 flamegraph 或 JFR 本身就不对了——那已经不是它们最擅长的消费方。

到这里可以先压成一句非常实用的判断：先别急着问“我导哪种格式”，先问“最后到底是人自己看、脚本看、JFR 工具看，还是平台看”。格式选择是这个问题的后继问题，而不是先导问题。

*关键设计（斜体）：* *输出格式真正区分的不是“文件长什么样”，而是“谁来消费它”：浏览器、人类、脚本、JFR 工具链和平台生态，各自需要的不是同一种结果对象。*[模式: 消费方分层 + 结果对象分化]

## 第二层：为什么“服务器采样，本地分析”会自然把 JFR 放在中间

一旦消费方分清了，下一步就会遇到一个很常见的生产现实：目标机器不一定适合在现场做所有分析动作。服务器上也许只适合低开销采集，不适合再做复杂渲染、比较和交互分析。

这时 README 和 `ConverterUsage.md` 给出的一条工作流就非常重要：

- 服务器上先采 JFR；
- 把 JFR 文件拿回本地；
- 用 `jfrconv` 或独立的 `jfr-converter.jar` 转成 HTML、collapsed、heatmap 或 OTLP（`README.md:99-110`，`docs/ConverterUsage.md:1-27`）。

当前仓库给出的转换工具用法是：

```bash
jfrconv [options] <input> [<input>...] <output>
```

最短示例可以是：

```bash
jfrconv --cpu foo.jfr foo.html
```

如果不用包内自带二进制，也可以直接运行独立 jar：

```bash
java -jar jfr-converter.jar --cpu foo.jfr --reverse --title "Application CPU profile"
```

这里最容易犯的错误，是把这条链路理解成“现场条件不行时的权宜之计”。更准确的说法是：采集与渲染分离，本来就是 async-profiler 部署形态的一部分。服务器现场只负责低开销采样和落盘，本地分析环境再负责更重的转换、对比和展示。

为什么这条路天然更适合 JFR，而不是 HTML？因为 JFR 本身就是一份更可再消费的中间档案。HTML 已经更接近最终展示物了，带回本地再转价值有限；collapsed 虽然也能带走，但它没有 JFR 那样丰富和标准化的档案语义。

所以如果你一开始就知道现场只是“先采下来，回来慢慢看”，那 JFR 往往应该优先于 HTML。这不是因为 HTML 不够好，而是因为 JFR 更像一个可复用的中间桥。

*关键设计（斜体）：* *“服务器采样，本地分析”不是格式使用技巧，而是 async-profiler 设计里对生产成本与分析体验的明确切分：现场先落可复用档案，后续再在更合适的环境里渲染和比较。*[模式: 在线采集 + 离线转换]

## 第三层：为什么 flame graph 的第一原则是“横向宽度不是时间线”

说到输出格式，最容易被误读的还是 flame graph。因为它长得太像一种“程序运行展开图”了，于是很多人会自然以为：从左到右，就是程序执行的先后顺序。

这恰恰是最该先扔掉的直觉。火焰图的横向宽度不是时间线，它表达的是样本或计数占比。也就是说，越宽通常表示某条调用路径被命中的比例越高；纵向表示栈深，往上是更深层的被调用者；最宽的顶部块，通常就是最值得先看的热点。

这也是为什么 flame graph 特别适合回答“CPU 去哪了”“哪条路径最热”，却不适合回答“某次请求按时间先后做了什么”。后者属于 tracing 或 timeline 类工具要回答的问题，不是火焰图的模型。

如果这一点不先讲透，后面很多用法都会被误读。例如你看到一个块横向很宽，并不能得出“它执行得比左边那个块更晚或更早”，只能得出“它占比更大，值得优先关注”。

所以对使用层来说，火焰图最重要的入门原则其实只有一句：宽度代表占比，不代表时序。这比记住一堆按钮和颜色更重要。

## 第四层：`reverse`、`inverted`、`minwidth` 为什么在使用层就必须先分清边界

`ConverterUsage.md` 列出来的 flame graph 选项，本身就是对读图维度的反向提示（`docs/ConverterUsage.md:84-96`）：

- `--minwidth`：过滤过窄的帧，减少视觉噪声；
- `--reverse`：反转栈方向；
- `--inverted`：切换 flame / icicle 布局；
- `--tree`：改为调用树视图；
- `--include` / `--exclude`：只看部分调用路径。

这里最容易混的就是两组边界。

第一组是 `reverse` 和 `inverted`。很多人会把它们都理解成“把图翻一下”。但当前卷在 AP-5 里已经明确校正过：`reverse` 更多作用在栈组织方向上，`inverted` 更多作用在最终图形朝向上。对使用层来说，你不一定要掌握内部实现细节，但至少要知道它们不是一个开关的两种别名。

第二组是 `minwidth`。使用层当然可以把它理解成“减少太窄的小块，看图更清爽”，但不能顺手把它误讲成“采样时就把低频样本扔掉了”。当前实现里，`minwidth` 是输出阶段的视觉裁剪，不是采样期丢样。这个边界如果不先守住，后面“为什么某些细枝在图上看不到，但统计仍然影响祖先宽度”就会完全说不清。

也就是说，AP-0 这一层虽然不重讲内部机制，但必须先把使用层最容易踩错的消费边界钉住。否则用户以为自己在调“图形显示方式”，实际上脑子里已经把采样语义讲歪了。

## 第五层：什么时候直接选 HTML，什么时候优先保留 JFR，什么时候干脆要 OTLP

到这里，真正实用的决策已经可以压成三问了。

### 如果我只是想尽快自己看热点？

优先 HTML / flamegraph。理由不是它更“标准”，而是它最贴近“人自己先看一眼”的场景：直接、交互式、浏览器友好。

### 如果我想把结果带走、复用、比较、本地慢慢分析？

优先 JFR。它更像中间档案，适合后续用 JMC、`jfrconv`、`jfr-converter.jar` 再渲染成 HTML、collapsed、heatmap，甚至做 differential flame graph（`docs/ConverterUsage.md:136-167`）。

### 如果最终消费者是可观测平台？

优先 OTLP。因为这时真正的读者已经不是人或 JFR 工具，而是平台的 profile ingestion 逻辑。继续纠结 flamegraph 或 JFR 本身，就已经不是站在最终消费方思考了。

所以更准确的说法不是“哪个格式最好”，而是“哪个格式最适合当前工作流的最后一跳”。HTML 更像最终展示物，JFR 更像可复用档案，OTLP 更像平台协议，collapsed/flat/traces 更像脚本与终端结果。

## 收网：先决定给谁看，再决定输出什么

如果把整篇话压成一句话，async-profiler 的输出格式从来不是“采样完以后再随手挑个文件后缀”，而是“先分清消费方，再选契约”。

```text
同一份采样样本
  → 先问消费方是谁
    ├─ 人类浏览器视图   → flamegraph / tree / html
    ├─ 终端 / 脚本       → collapsed / flat / traces
    ├─ JFR 生态 / 离线分析 → jfr
    └─ 可观测平台       → otlp
```

到这里，主线只发生了三件事。

第一，同一份样本面对不同消费者时，结果对象根本不是同一个东西，所以格式选择必须先按消费方分层。

第二，JFR 之所以重要，不只是因为它能被 JMC 读，更因为它天然适合作为“服务器现场采集、本地离线转换”的中间档案。

第三，火焰图虽然最常见，但它的横向宽度表示的是样本或计数占比，不是时间线；`reverse`、`inverted`、`minwidth` 这些开关也必须在使用层先守住语义边界。

*关键设计（斜体）：* *选择输出格式时，真正该先问的不是“我喜欢哪种图”，而是“结果最后要交给谁消费”；异步采样的同一份样本，会因为消费方不同而被翻译成完全不同的结果契约。*[模式: 消费方优先 + 结果契约分化]

**本篇的一句话困惑**：同一份采样结果，为什么不能只固定输出成一种格式？

**本篇的一句话顿悟**：因为 flamegraph、collapsed、JFR、OTLP 服务的根本不是同一类读者；先分清“谁来消费”，才能知道该直接出 HTML、保留 JFR，还是走转换链。
