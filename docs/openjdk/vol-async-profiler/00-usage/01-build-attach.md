# 01. 先跑起来，再看原理 —— 构建、attach 与第一次采样

> **前置依赖**：知道什么是 Java 进程、`jps`/`pgrep`、基础 shell 命令
> → **后续**：事件与参数 —— `-e cpu`、`-d 30`、`-f out.html` 这些选项真正控制了什么
>
> 场景：你已经知道 async-profiler 是 native 采样器，但还没亲手把它挂到一个正在运行的 JVM 上；第一次上手时，真正的目标不是先背内部机制，而是先在 5 分钟内跑通一条“构建 → attach → 采样 → 输出结果”的最短闭环。
>
> 本篇命令示例已回对 async-profiler 当前 `README.md`、`docs/GettingStarted.md`、`docs/ProfilerOptions.md` 与相关排障文档。这里讲的是“怎么先把工具落地并跑出第一份结果”，不是后面 AP-1 那种 attach 内部机制；但会提前守住一些使用层必须知道的边界，比如 `asprof` 是独立 native 工具、`-d` 是一键工作流、`.html` 后缀已经在决定消费链，以及 attach/容器/chroot 限制不是命令手误而是系统边界。

## 先把真正的困惑摆出来：第一次上手时，真正的第一步不是看 `recordSample()`，而是先跑通工具闭环

很多人第一次接触 async-profiler，会本能地往源码主链里扎：attach 怎么做、采样器怎么走栈、FlameGraph 怎么出图。可对第一次上手的人来说，真正的第一个门槛并不是这些内部机制，而是更朴素的一件事：你手上到底有没有一个能跑的 `asprof`，以及它能不能真的挂到目标 JVM 上并吐出第一份结果。

也就是说，第一次上手最该先回答的问题不是“采样器内部怎么实现”，而是“这东西到底怎么落地”。你需要先把以下这条链真正跑通：

```text
源码目录
  → make
    → build/bin/asprof
      → 选定目标 JVM（PID / jps / 应用名）
        → attach 并采样
          → start/stop 或 -d
            → text / html / jfr 输出
```

这里最容易出现的几个失败直觉，其实都很常见。

第一个，是觉得“先把源码看懂，再跑命令更稳”。现实往往正相反。没有第一条成功命令，你后面看到的 attach、参数协议、输出格式都会缺少使用层参照物；很多看似抽象的机制也会因为没有现场体验而更难落地。

第二个，是把 `make` 看成一个无聊的构建细节，仿佛它和后续 attach 没什么关系。实际上，构建产物形态本身就在告诉你 async-profiler 的部署姿势：它不是一个“先把 Java 依赖塞进应用，再由框架托起来”的工具，而是一个可以单独分发、单独拿去 attach 目标 JVM 的 native 采样器。

第三个，是把 `-d 30 <pid>` 和 `start` / `stop` 看成两种差不多的命令写法，好像只是风格不同。其实它们代表的是两种不同的使用场景：一种强调一键闭环，一种强调手工控制采样窗口。

所以这一篇真正要做的，不是给你一份命令清单，而是把“第一次先跑起来”这件事压成一条最短可用路径：先拿到自包含工具，再定位目标 JVM，再用最低心智负担跑完一次 attach + 采样 + 停止 + 输出。

*关键设计（斜体）：* *上手 async-profiler 时，真正要先跨过去的门槛不是内部机制，而是“能不能拿到一个尽量自包含的 `asprof`，并把 attach + 采样 + 输出闭环压成一条最短可用路径”。*[模式: 先落地工具，再进入机制]

先记住这句总领：第一次上手先别急着钻源码，先把 `asprof` 跑起来。后面所有 attach、参数和采样机制，都是在解释这条使用层闭环是怎么被压缩出来的。

## 第一层：为什么仓库强调先 `make` 出 `build/bin/asprof`，而不是先谈 Java 依赖

当前 README 的构建说明给出了最直接的路径：在源码根目录执行 `make`，产物会出现在 `build/bin/asprof`（`README.md:64-76`）。文档还明确列出了最低要求：

- `make`；
- GCC 7.5+ 或 Clang 7.0+；
- 静态版 `libstdc++`；
- JDK 11+（`README.md:64-76`）。

这几条看起来像普通构建前提，但真正重要的是它们共同传递出一个部署姿势：async-profiler 不是“Java 应用先集成一个库，再在应用内部调用”的工具起点，而是一个可以独立构建、独立分发、独立拿去 attach 目标 JVM 的 native launcher。

尤其是 README 明确要求静态 `libstdc++` 这一点，背后不是“构建偏好”，而是部署现实：这个采样器要被拿到各种目标机器上跑，最好别把自己的运行时依赖也变成现场故障源。如果构建出来的 `asprof` 还要额外和目标机器的某个 C++ 运行时版本博弈，那它就不够像一个可以放心带去线上 attach 的自包含工具。

所以 `make -> build/bin/asprof` 这一步的意义，不只是“终于有个可执行文件”，而是在宣告 async-profiler 的使用姿势：先生成一个尽量自包含的外部工具，再去碰目标 JVM。

*关键设计（斜体）：* *先生成一个尽量自包含的 `asprof`，再去碰目标 JVM；这不是构建习惯，而是 async-profiler 作为独立 native 采样器的部署前提。*[模式: 自包含工具链]

## 第二层：为什么只给一个 PID、`jps` 关键字或应用名，`asprof` 就能把 agent 挂进去

工具有了之后，第二个上手门槛就是目标选择。Getting Started 给出的最常见工作流是先找到目标 Java 进程，再 `start` / `stop`（`docs/GettingStarted.md:17-56`）：

```bash
jps
asprof start 8983
asprof stop 8983
```

当前文档同时还确认了三种目标写法：

- 直接写数字 PID，例如 `8983`（`docs/GettingStarted.md:36-44`）；
- 写关键字 `jps`，当系统里只有一个 Java 进程时自动定位（`docs/GettingStarted.md:46-49`）；
- 写应用名，例如 `Computey`（`docs/GettingStarted.md:46-49`）。

这里最容易形成的错觉是：好像 `asprof` 只是“认出一个目标名字”，剩下 attach 是 JVM 自然会发生的。但恰恰相反，真正值得记住的是：对使用者来说，`asprof` 已经把“识别目标 JVM -> attach -> 交付参数 -> 启动动作”压缩进了一个统一入口。你表面上只给了一个 PID、关键字或应用名，实际上已经在触发一条完整的目标解析和注入链。

这就是为什么 Getting Started 的示例命令看起来往往没有“先 attach、再 load、再 start”那种多段动作：不是因为内部没有这些步骤，而是因为入口刻意把它们折叠掉了。

也正因为如此，第一次上手时最该建立的不是“我已经懂 attach 内部实现”，而是“我知道对使用层来说，目标选择已经被压成了一个简短参数，而后面的复杂性被入口藏起来了”。这会让你后面读 `main.cpp`、`run_jattach()` 和参数协议时，更容易知道自己到底在解释哪条使用层现象。

## 第三层：为什么 `-d 30 <pid>` 才是最适合第一次上手的最短闭环

README 和 Getting Started 都给了同一个最短命令：

```bash
asprof -d 30 8983
```

它表示对目标 JVM 采 30 秒，然后把结果直接输出到控制台（`README.md:44-56`，`docs/GettingStarted.md:51-83`）。在没有显式指定事件时，默认事件是 CPU；对这条默认 CPU 路径，默认频率是 100Hz，也就是每 10ms 一次 CPU 时间采样（`docs/GettingStarted.md:58-83`，`docs/ProfilerOptions.md:35`）。

这条命令之所以重要，不是因为它短，而是因为它把第一次上手最需要的几件事压成了一条闭环：

- 你不必先学一堆动作子命令；
- 你不必担心忘记 stop；
- 你能最快得到一份真实结果；
- 你后面再去看 `start` / `stop` / `status` / 输出格式时，脑子里已经有一条成功路径作为参照。

这正是这里必须打掉的一个失败方案：第一次就坚持用最细粒度的 `start` / `stop` / 自己控制窗口，仿佛这样才更“专业”。对上手阶段来说，恰恰是 `-d` 这种一键闭环路径更稳。它天然自带自动停止，更不容易因为操作失误把采样遗留在目标进程里，也更适合一次性抓取或 CI / 批处理式的简单使用。

### `start/stop` 为什么不是过时用法，而是另一种更适合已知窗口的工作流

这并不意味着 `start` / `stop` 没价值。Getting Started 其实明确给了两种常见用法（`docs/GettingStarted.md:31-56`）：

- 交互式：`asprof start <pid>` -> 压测/复现问题 -> `asprof stop <pid>`；
- 定时式：`asprof -d 30 <pid>`。

它们代表的不是“旧写法”和“新写法”，而是两类不同场景。

如果你已经知道问题大概什么时候发生，或者你正要手工触发一段特定业务动作，那么 `start` / `stop` 更适合把采样窗口与那段动作精确对齐。反过来，如果你只是想先拿到一份样本看看热点大致在哪，或者你在自动化环境里做一次固定长度抓取，`-d` 会更省心。

所以更准确的说法是：`-d` 是第一次上手最短闭环，`start` / `stop` 则是当你已经知道问题窗口时更灵活的工作流。

*关键设计（斜体）：* *`-d` 的价值不只是“少打一条命令”，而是把 attach + start + 等待 + stop + dump 压成一条最短闭环；而 `start/stop` 的价值则在于把采样窗口对齐到你已知的问题时段。*[模式: 一键闭环 + 手工窗口控制]

## 第四层：为什么输出文件名看起来只是路径，实际上已经在决定结果往哪条链走

第一次上手除了“能不能采到”，第二个很实际的问题就是“第一份结果长什么样”。当前文档推荐的常见写法是：

```bash
asprof -d 30 -f /tmp/flamegraph.html 8983
```

Getting Started 已明确指出：当输出文件名以 `.html` 结尾时，当前实现会自动选择 flame graph 输出（`docs/GettingStarted.md:92-109`）。

这意味着 `-f` 在上手阶段就已经不只是“存到哪儿”，它还隐含着“结果准备往哪条消费链路走”。

- 不写文件，结果更像即时控制台文本；
- 写成 `.html`，结果就更像浏览器里的 flame graph；
- 写成 `.jfr`，结果则开始偏向 JFR 工具链和后续离线转换。

所以这又是一个很典型的失败方案：把 `.html` 看成无关紧要的文件后缀，好像只是自己随便起了个名字。实际上，你在起这个名字的时候，就已经在决定结果更适合由谁消费。

也正因为这样，下一篇才必须把“事件与参数”和“输出格式与火焰图读法”拆开讲。前一篇是在决定怎么采，这一步已经开始触碰“结果要给谁看”的问题了。

## 第五层：为什么 attach、容器和 chroot 边界在上手阶段就必须先承认

如果说前面几层还主要是在讲“如何形成第一条成功闭环”，那么最后还必须先承认一个现实：第一条命令能不能跑通，常常不只是命令本身的问题，而是系统边界问题。

`Troubleshooting.md` 里已经明确列出了几类典型 attach / 装载失败场景：比如 attach 机制文件找不到、目标 JVM 无法加载 `libasyncProfiler.so`、运行时 attach 带来的可见性边界等（`docs/Troubleshooting.md:26-52、114-119`）。容器与 chroot 文档也在提醒：PID namespace、库路径、seccomp、`fdtransfer` 等条件，都会直接决定这条“最短命令”到底能不能成功跑完。至于 `perf_event_open()` 失败，更适合放到下一篇事件选择里和 CPU 采样路径一起理解，而不是和 attach 失败混成同一层问题。

这里必须打掉另一个常见误解：只要命令写对了，attach 失败就是偶发现象。事实上，很多 attach 或 CPU 采样失败从来就不是命令问题，而是系统条件不满足。

例如：

- 目标 JVM 是否处在可 attach 的 namespace；
- 目标环境是否能让 JVM 真正加载 `libasyncProfiler.so`；
- 容器里是否允许 `perf_event_open`；
- 是否需要 `fdtransfer` 这类权限桥；
- runtime attach 是否导致某些早期编译方法缺少更完整的可见性。

之所以要在 AP-0 第一篇就把这类边界点出来，不是为了讲排障细节，而是为了让第一次上手的人尽早建立一个正确预期：`asprof` 的确把 attach + start + stop 压成了很短的命令，但它并没有抹掉 native 工具对系统边界的真实依赖。

所以更准确的说法应该是：上手阶段要先把“命令是否写对”和“系统是否允许这条命令生效”分开。前者属于工具入口，后者属于 native 采样器的现实边界。

*关键设计（斜体）：* *第一次跑不起来时，别先把所有问题都归咎为命令没写对；对 async-profiler 这类 native attach 工具来说，系统边界——库装载、命名空间、权限、perf 能力——从第一条命令开始就在参与结果。*[模式: 上手闭环 + 系统边界前置]

## 收网：先跑起来，再回头看原理

如果把整篇话压成一句话，第一次上手 async-profiler 时，真正该先跨过去的门槛不是“内部机制懂不懂”，而是“能不能拿到一个尽量自包含的 `asprof`，定位目标 JVM，并跑完 attach + 采样 + 停止 + 输出这一条最短闭环”。

```text
源码目录
  → make
    → build/bin/asprof
      → 选定目标 JVM（PID / jps / 应用名）
        → attach 并采样
          → start/stop 或 -d
            → text / html / jfr 输出
```

到这里，主线只发生了三件事。

第一，`make -> build/bin/asprof` 说明 async-profiler 的起点是一个尽量自包含、可独立分发的 native 工具，而不是先把 Java 依赖塞进应用。

第二，`-d` 与 `start/stop` 不是两种无差别写法：前者更适合第一次上手的一键闭环，后者更适合对齐已知问题窗口。

第三，目标选择、输出文件名和 attach/容器边界一起决定了你的第一条命令能否真正跑通；它们不是零散技巧，而是这条上手闭环不可分开的几段。

*关键设计（斜体）：* *对第一次使用者来说，最重要的不是先理解 profiler 内核，而是先把“自包含工具 -> 目标 JVM -> 一次完整采样结果”这条路径跑通；只有先把这条路径跑通，后面的 attach、参数和采样机制才有了真实落点。*[模式: 上手闭环优先 + 先工具后机制]

**本篇的一句话困惑**：第一次上手 async-profiler 时，真正的第一步到底是什么？

**本篇的一句话顿悟**：先别急着钻 `recordSample()`，先 `make` 出 `build/bin/asprof`，选定目标 JVM，再用 `-d` 或 `start/stop` 跑通 attach + 采样 + 输出的第一条闭环；原理是在解释这条闭环为什么能成立。
