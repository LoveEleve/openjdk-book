# 02-events-options 重写规划

> 状态：本轮按一轮闭环执行；保留该 plan 作为后续二轮 consistency pass 的工件
> 适用规范：`docs/openjdk/WRITING-GUIDELINES.md`
> 目标：把当前“事件列表 + 参数说明”重写成一篇围绕“遇到 CPU、分配、锁竞争、阻塞这几类不同问题时，为什么不能拿同一组事件和同一颗旋钮去看；以及 `-e/-d/-f/-i` 和线程/过滤/memlimit 分别在帮助你做什么使用层决策”的面向用户机制文章

## 1. 读者困惑

- 为什么同样都叫“性能问题”，CPU、alloc、lock、wall 却不能用同一组事件去看？
- `-e` 选的到底是什么：输出格式、标签，还是问题类型？
- `-d`、`-f`、`-i` 这几个最常用参数分别在控制什么权衡？
- 线程、过滤、`--memlimit` 为什么不改变“采什么”，却又会显著影响结果能不能看、采样器能不能稳？
- 容器、权限和 `perf_event_open` 为什么会让“CPU 事件”在使用层就出现平台分歧？

## 2. 一句话顿悟

**async-profiler 的事件和参数不是一堆平铺选项，而是一条决策链：先判断你面对的是 CPU、分配、锁竞争还是阻塞，再用 `-d/-i` 在统计精度和现场成本之间取舍，用 `-f` 决定结果往哪种消费链路走，再用线程/过滤/memlimit 把结果聚焦并保护采样器自身。**

## 3. 总图

```text
先问问题类型
  ├─ CPU 热点      → -e cpu
  ├─ 分配压力      → -e alloc
  ├─ 锁竞争        → -e lock
  └─ 阻塞/等待/睡眠 → -e wall

再调三颗基础旋钮
  → -d 采多久
  → -i 采多密
  → -f 结果往哪条消费链走

再决定结果聚焦与自保护
  → threads / include / exclude / filter
  → memlimit
  → 容器 / perf / fdtransfer / ctimer 等环境边界
```

## 4. 关键边界

- 本篇是面向使用者的“事件选择与参数决策”文章，不重讲 AP-2 / AP-5 的内部实现细节；只提前守住那些使用层必须知道的边界。
- `-e` 选的是问题类型与观察对象，不是输出格式标签。
- `cpu`、`alloc`、`lock`、`wall` 在底层不是同一路径换名字，但本篇只讲“怎么选”和“什么时候用”，不深入内部引擎。
- `-d/-i` 的本质是精度/成本平衡，不是“数值越小越好”。
- `-f` 不只是文件路径，还会把结果送进不同的消费链路（终端、HTML、JFR 等）。
- 线程、过滤、`memlimit` 改变的是结果聚焦和采样器自保护，不是“换一种事件”。
- 容器权限文档给出的 `ctimer` 是常见退路，不应被误写成 CPU 事件唯一降级路径。

## 5. 本轮重写主线

1. 用“问题类型不一样，就不能拿同一组事件看”开场。
2. 否定：所有性能问题都先上 `-e cpu`、`-i` 越小越好、`-f` 只是路径、容器失败只是命令没写对。
3. 先按问题类型讲事件选择，而不是先平铺选项表。
4. 再讲 `-d/-i/-f` 三颗基础旋钮分别在调什么权衡。
5. 再讲线程、过滤、`memlimit` 这些“让结果更能看、让采样器更能活”的参数。
6. 最后把容器/权限边界拉回“使用层就必须先承认平台差异”。
