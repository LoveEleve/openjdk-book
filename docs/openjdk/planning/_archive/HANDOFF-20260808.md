| 等级 | 名称 | Pass 0 | Pass 1 | Pass 2 | Pass 3 | 说明 |

| 🔴A | 全深度 | ✅ 强制 | ✅ 强制 | ✅ ≥3 闭环 | ✅ 强制 + 时空溯源 + 极简复现 | 核心域 |
| 🟡B | 标准分析 | ✅ 强制 | ✅ 强制 | ✅ ≥3 闭环 | 可选（≥5 标记时才做） | 支撑域 |

### 0.2 执行流程（01-三层循环框架）

#### 每个域的完整流程

```
Pass 0: 读设计上下文
  ├── git log --oneline -20 查看设计变更历史
  ├── git log --grep="bug|fix|refactor|issue" 搜索关键提交
  └── 读 README + 设计文档（如果有）

Pass 1: 扫轮廓 → 产出 #{N}-pass1.md
  ├── 包结构扫描（find + grep 核心类声明）
  ├── 继承树/调用图（ASCII 图）
  ├── 基本元素分解（每个元素带 file:line 源码锚点）
  ├── ≥8 个标记问题（🔴A）/ ≥5 个（🟡B）——每个带源码位置
  └── 至少读 2 个测试文件

Pass 2: 盯关键点 → 产出 pass2-q*.md
  ├── 对 ≥3 个标记问题做闭环笔记
  │   每个闭环: 假设 → grep 追踪 → Read 方法体 → 验证 → 结论
  ├── 每个闭环标注代码类型: Glue/Interface/Implementation/Algorithmic
  └── 检查: 是否每个闭环 ≥200 字？是否有 ≥2 个源码位置证据？

Pre-Pass 3: 文章拆分判定
  ├── 统计 Pass 2 闭环笔记数 N
  ├── 普通大域 (6 ≤ N < 20): 拆 2-5 篇，同一大纲文件内列出
  ├── 巨型域 (N ≥ 20 或 源码 >30000 行 或 文件 >100): 拆 8+ 篇
  │   └── 每篇独立大纲文件，整个域占一卷篇幅
  └── 呈报文章规划给用户确认后再开始写

Pass 3: 写文章大纲 → 产出 #{N}-{name}.md
  ├── 叙事计划（8-9 层递进，每层 2-3 段落）
  ├── 概念依赖（声明先修域）
  ├── 设计权衡（≥4 个，每个 3-5 行分析）
  ├── 核心悬念（一句话，不是 "X+Y+Z 怎么工作"）
  ├── 开篇场景（具体情境，非概念总结）
  ├── 负面空间表（对比型域: 列出"故意不做"的优化）
  └── 预估（行数）
```

#### Pass 1 检查清单

- [ ] 继承树/调用图已画出
- [ ] 已回答"这个模块由哪几个基本元素组成？"
- [ ] ≥8 个标记问题（🔴A）/ ≥5 个（🟡B），每个有源码位置
- [ ] 至少读了 2 个测试文件

#### Pass 2 检查清单

- [ ] ≥3 个标记问题已完成闭环（非全部标记问题；Pass 2 只要求 ≥3，不等同于 Pass 1 的全部标记数）
- [ ] 每个闭环 ≥2 个源码位置证据
- [ ] 每个闭环标注了代码类型
- [ ] 没有"我猜"——全部有源码佐证

### 0.3 巨型域拆分规则（NEW）

> 此规则为方法论 v2 新增。源码 >30000 行或文件 >100 的域为"巨型域"。

**判定条件**: Pass 2 闭环笔记 N ≥ 20，或源码行数 ≥ 30000，或文件数 ≥ 100。

**拆分要求**:

| | 普通大域 (6≤N<20) | 巨型域 (N≥20) |
|------|:--:|:--:|
| 拆分篇数 | 2-5 | 8-15 |
| 大纲组织 | 同一文件内列出 | 每篇独立大纲文件 |
| 文件命名 | 无特殊要求 | `{域}/01-{标题}.md` 到 `{N}-{标题}.md` |
| 所占篇幅 | 域内 | 一整卷 |
| 验证粒度 | 域级 | **逐篇验证** |

### 0.4 深度标准（03-分析深度标准）

判断分析深度是否足够：

**必须深挖**（承载设计决策）:
- 数据结构选择（为什么用 A 不用 B）
- 并发策略（为什么用锁 A 不用锁 B）
- 内存管理策略（为什么要这样分配）
- 压缩/编码选择（为什么压缩中间节点）
- 异常处理策略（为什么吞掉/传播/转换）

**可以跳过**（无设计决策）:
- getter/setter/toString/hashCode — 纯数据访问
- 日志打印、异常包装 — 无决策
- 纯转发 delegate — `return target.doX()`
- deprecated 的旧代码路径

**深度不足的检测信号**:
- 描述全是"它做了什么"，没有"为什么这样做"
- 没有任何跨域关联提及
- 说不出来这个设计的替代方案是什么
- 每个闭环笔记 < 200 字

### 0.6 深审要求

**每个域的大纲必须至少两轮深审（R1+R2）**。

| 轮次 | 维度 | 检查内容 |
|:--:|------|------|
| R1 | 准确性 | grep 逐条验证声明（机制名/行号/默认值）。每声明对照源码。数值声明必须 `wc -l` 或 `grep -c` 验证。禁止凭记忆估计。 |
| R2 | 完整性 | 追问"还有哪个机制漏了？""这个类的完整职责只描述了 1/4 吗？""生命周期管理缺失吗？""防护/限制机制被忽略了吗？" |

**R1 检查清单**:
- [ ] grep-verified ≥3 条声明
- [ ] 至少发现 ONE 处内容不准确或遗漏
- [ ] 全部数值声明已对照源码检查
- [ ] 全部基于类名的推断已对照实际方法体验证
- [ ] 锚点数量达标（🔴A≥8, 🟡B≥4）

**R2 检查清单**:
- [ ] 核心类是否有 4 道以上职责被遗漏？
- [ ] 生命周期管理是否缺失？
- [ ] 桥接层/中间转换层是否缺失？
- [ ] 跨域依赖是否正确声明？

**反模式: 格式审查陷阱**
```
错误: R1-R2 全部查格式（桥/结构/锚点/前向引用）→ 全部通过 → 宣称完成
正确: 至少一轮切换到"另一个 AI 拿到这篇大纲能写出文章吗？"
       → 如果不能 → 大纲不合格，不管格式多完整
```

### 0.7 全视角提问验证（NEW — 强制步骤）

> 大纲深审通过后、呈报用户确认前，必须执行。

**核心原则**: 大纲的完备性不由"看起来全不全"判断——由"7 个身份的人分别读这篇大纲，能回答他们的问题吗"判断。

**七身份**（JVM/GC 域标准集，其他域调整为域相关角色）:

| 身份 | 视角 | 适用条件 |
|------|------|------|
| 开发者 | "我要改这部分的代码" | 所有域 |
| 性能工程师 | "我怎么把它调好" | 有调优参数的域 |
| 架构师 | "为什么这样设计" | 所有域 |
| SRE/运维 | "线上出问题了" | 生产可用的域 |
| 研究者 | "和替代方案对比" | 有多个实现的域 |
| 子系统开发者 | "上层/下层怎么配合" | 有跨层交互的域 |
| 学生 | "我第一次看" | 所有域 |

**执行步骤**:
1. 列出域的 8-10 个子主题
2. 对每个身份 × 每个子主题 → 出 2-5 个"该身份真正会问的"问题
3. 每题标注大纲覆盖: ✅/⚠️/❌
4. 汇总 ❌ 和 ⚠️ → **AI 自主补全缺口** → 再次验证
5. 全部 ✅ 后 → 保留提问文档（`{域}-completeness-questions.md`）
6. 呈报用户时附覆盖统计（❌/⚠️/✅ 数量）

**数量基准**（总问题数，跨所有适用身份）:

| 域类型 | 源码行数 | 最少总问题数 | 最少身份数 | 验证粒度 |
|------|:--:|:--:|:--:|------|
| 普通域 | <10000 | 30 | 5 | 域级 |
| 大域 | 10000-30000 | 50 | 6 | 域级或篇级 |
| 巨型域 | >30000 | 80 | 7 | **逐篇验证** |

**反模式**:
```
错误: 全部问题都是"XX 是什么"（What）——面试题视角
正确: 追问"为什么"（Why）+"和 YY 比呢"（Compare）+"如果出错了怎么办"（Fail）

错误: 用户每次提醒才补提问文档
正确: 每个大纲完成后自动产出
```

### 0.8 全量审查维度（07-全量系统性审查维度）

全部域大纲完成后，按以下维度执行跨域审查：

| 维度 | 检查内容 |
|------|------|
| 桥一致性 | 每域 IN/OUT 桥匹配 + 卷边界桥 |
| 结构完整性 | 概念依赖/设计权衡/核心悬念/预估/叙事计划 |
| 源码锚点密度 | 🔴A≥8 / 🟡B≥4 |
| 前向引用 | 依赖声明不指向未讲域 |
| 横切关注点 | 线程/GC屏障/信号链覆盖矩阵 |
| 负面空间/开篇质量 | 对比域有"不做的事"表 + 开篇场景具体化 |

**反模式补充**:
- 格式审查通过 ≠ 内容合格 — 必须做反写测试
- 巨型域不能用普通拆分 — N≥20 必须逐篇独立大纲
- 大纲完成不执行提问验证 — 强制步骤
- 审查收敛是"当前维度集收敛" — 不是所有可能维度穷尽
- **回退质量检查**: 当前方法论文档升级后（如新增巨型域/全视角提问规则），必须对所有已完成的早期域做逐域回退检查——对比当前质量基准。早期域"当时通过了"不等于"现在仍合格"。

## §一 问题根因（前 AI 的失误）

**9 轮审查全部通过的原因**：审查维度全部是"格式维度"——

| 轮次 | 查了什么 | 为什么 G1 GC 通过了 |
|:--:|------|------|
| R1 | 桥一致性 | 有 `→从 StubRoutines` + `→下一域 CDS` ✅ |
| R2 | 前向引用 | 无未来域依赖 ✅ |
| R3 | 结构完整性 | 有概念依赖/叙事计划/设计权衡/核心悬念/预估 ✅ |
| R4 | 锚点密度 | 有 `heapRegion.hpp:191` 等 2 个锚点 (阈值≥2) ✅ |
| R5+ | 其他维度 | 不检查内容深度 ❌ |
| — | 反写测试 | G1 57行大纲能指导另一个 AI 写 45692 行源码的文章吗？**不能** ❌ |
| — | 巨型域拆分 | G1 应拆 8-10 篇独立大纲，实际只有 1 篇 57 行 ❌ |
| — | 全视角提问 | 从未产出提问文档验证大纲完备性 ❌ |

**结果**：G1 GC（45692行源码/195文件/🔴A 强制拆多篇）的大纲只有 57 行 6 层——每一层是一段话。C1 Compiler（41074行/49文件/🔴A）的大纲是 166 行 9 层——每层多段落+负面空间+设计权衡展开。

## §三 正确的 🔴A 大纲长什么样

以 C1 Compiler（166行）为基准：

1. **8-9 层递进**（非 5-6 层）——每层至少 2-3 段落
2. **每层有源码锚点** — `file:line` 格式，至少 8 个
3. **负面空间表** — 列出域"故意不做"的优化（如果是对比型域）
4. **4 个设计权衡** — 每个展开为 3-5 行分析
5. **开篇场景具体化** — 从代码/运维场景出发，非概念总结
6. **核心悬念一句话** — 不是"X + Y + Z 怎么工作？"而是"X 怎么做到了 Y？"
