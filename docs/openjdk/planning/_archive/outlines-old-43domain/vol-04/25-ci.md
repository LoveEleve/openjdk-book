> **→ 从 VTable/IC**：虚方法怎么分派搞定了——但 JIT 编译器要优化方法时，不能直接读 VM 内部的 Klass 和 Method 数据结构。需要一层 ci——把 VM 状态拍成 immutable 快照。

## 概念依赖

依赖 OOPs（Klass/Method 元数据）+ ClassFile（类层级信息）。ci 是 JIT 和 VM 之间的隔离层——编译器只通过 ci 访问 VM 状态，不直接触碰 `Klass*`/`Method*` 等内部指针。

## 叙事计划

**开篇场景**：JIT 要编译 `Dog.speak()` 方法——它需要知道 `Dog` 有哪些字段、`speak()` 的字节码是什么、这个方法被调了多少次、每次调用的 receiver 都是什么类型。但它不能直接读 `InstanceKlass::_methods` 或 `MethodData::_data`——那些是 VM 内部数据结构，随时可能被 GC 移动或并发修改。ci 层把 VM 内部状态"拍快照"成编译器可见的 immutable 对象。

**第一层：ciEnv——每次编译的独立上下文**

`ciEnv`（`ciEnv.hpp:44`，`StackObj`）是编译的入口。每次 JIT 编译一个方法时创建——持有 `ciObjectFactory`（ci 对象缓存）、`Dependencies`（编译假设记录）。编译完成后自动析构——栈上生存，不需 `delete`。C1 的 `Compilation` 和 C2 的 `Compile` 都持有 `ciEnv* _env`。

**第二层：ciObjectFactory——一 oop 一 ci 的不变式**

`ciObjectFactory`（`ciObjectFactory.hpp:38`）保证 invariant：一个 VM 对象只对应一个 ci 对象。编译器通过 `get_metadata(Metadata* key)` 获取 ci 表示——重复请求同一个 `Klass*` 返回同一个 `ciKlass*`。ci 对象是 immutable 快照——编译器通过 ci 只能读 VM 状态，不能修改。用 `Handle` 保护快照不被 GC 移动。

**第三层：ci 对象的层级**

`ciObject` → `ciMetadata` → `ciKlass` / `ciMethod` / `ciField` / `ciMethodData`。`ciKlass` 暴露类的层级信息（父类、接口、字段列表）。`ciMethod` 暴露方法的字节码（通过 `ciStreams`）、异常处理器表、调用次数。`ciMethodData` 是 `MethodData` 的 copy——暴露 profiling 数据（分支频率、类型分布）。

注意坑：`ciMethodData::load_data()` 的 copy 不是原子的（JDK-8216987）——并发 profiling 更新可能导致 ciMethodData 中数据不一致，影响 C2 优化决策。

**第四层：ciTypeFlow——在 ci 层做类型推断**

`ciTypeFlow`（3048 行 `.cpp`）在 ci 的 immutable 快照上推演字节码的类型流——每个字节码执行后操作数栈和局部变量的类型。C2 用类型流的结果做内联决策（"这个调用点的 receiver 类型是什么？"）、逃逸分析（"这个对象逃逸了吗？"）。ciTypeFlow 和 C2 的 `Type::meet()` 是两层——ciTypeFlow 在 ci 层做初步分析，C2 在优化层做更精细的类型合并。

**第五层：Dependencies——编译假设的记录器**

`Dependencies` 记录编译器做的假设。C2 优化时假设"`Animal.speak()` 只有 `Dog` 一个实现" → 把虚调用变成直接调用→ 记录一条 `unique_concrete_method` dependency。后续如果加载了 `Cat` 类（破坏了只有一个实现的假设）→ Dependencies 系统通知 VM → 触发去优化——把已编译的 `speak()` 帧退回解释器。

**第六层：ciStreams——安全字节码访问**

`ciStreams` 提供字节码流的 ci 层迭代器。比直接读 `Method::code_base()` 安全——因为它是 immutable 副本，不受 GC 移动影响。`ciBytecodeStream::get_klass()` 解析常量池引用——在 ci 的安全上下文中完成，不需要持有 VM 内部的 `SystemDictionary_lock`。

**设计权衡**

一、immutable snapshot vs 直接访问。ci 隔离了编译器对 VM 内部状态的直接依赖——编译器不需要关心 Klass 的布局或 GC 的对象移动。代价是每次编译都要创建 ci 对象的完整副本。

二、ciMethodData 的权衡——完整性 vs 性能。ciMethodData 的 copy 不是原子的——追求零锁性能，接受偶尔的 profiling 数据不一致。C2 的优化决策需要 profiling 数据但不需要 100% 精确。

## 核心悬念

**JIT 编译器怎么知道当前编译的方法有多少字段、被调了多少次、receiver 是什么类型——不能直接读 `InstanceKlass`，要通过 ci 层的 immutable 快照？**
