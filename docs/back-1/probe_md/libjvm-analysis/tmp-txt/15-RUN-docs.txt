## 00-System-Arraycopy.md — Content Arc

### §〇 — Production: "ArrayStoreException at 3am"
`java.lang.ArrayStoreException: java.lang.Integer at java.lang.System.arraycopy(Native Method)`. RPC deserialization: Object[] source contains Integer, but destination was allocated as String[]. Native arraycopy's object-array dispatch does element-by-element type check → Integer can't go into String[] → throws.

Diagnostic: `jstack` to see exact stack trace → check source array element types (`src.getClass().getComponentType()`) vs destination (`dst.getClass().getComponentType()`) → mismatch → fix allocation.

### §一 — Narrative + Calls + De-glamorization
"System.arraycopy 不是 '一个快一点的 for 循环'。它是 Java 调用频率最高的 native 方法——每天几百亿次。在 native 层，它分两条完全不同的代码路径：primitive → memmove 全量复制；Object → element-by-element 类型检查 + 拷贝。没有 for 循环，没有 bounds check per element，没有 JNI 开销（C2 intrinsic），只有 memmove."

Prerequisites: 09-native-interface (JNI_ENTRY/JVM_ENTRY), 03-object-model (markOop for identityHashCode), 05-jit-compiler (C2 intrinsic of arraycopy → REP MOVS).

5 Beginner sidebars:
1. **JNI_ENTRY**: Java→native slow path. Parameter marshalling: jclass/jmethodID extraction, oop→jobject wrapping. ~50ns overhead.
2. **JVM_ENTRY**: JVM-internal fast path. No marshalling, direct oop access. Used by JVM_ArrayCopy, JVM_IHashCode. ~5ns overhead.
3. **intrinsic**: C2 replaces native call with direct CPU instruction at compile time. arraycopy → REP MOVS (vectorized x86 copy). Float.floatToRawIntBits → register move. ~200 intrinsic methods recognized.
4. **memmove**: C standard library function. Copies n bytes from src to dst. Handles overlapping regions (src+dst overlap → copies in correct direction). ~100GB/s on modern CPU for large copies (vectorized).
5. **markOop**: 64-bit word at the front of every Java object. Stores: identity hashCode (25 bits), GC age (4 bits), biased locking state (3 bits), lock state (2 bits). JVM owns this header — Java code can't access it.

### §二 — Environment
OpenJDK 11 slowdebug, Linux x86_64. Source: src/java.base/share/native/libjava/System.c, Object.c. GDB: `gdb --args java -cp . ArrayCopyTest`.

### §三 — Source Files
System.c (455 lines: arraycopy, identityHashCode, nanoTime, initProperties), Object.c (66 lines: hashCode, getClass, wait/notify), jvm.cpp (JVM_ArrayCopy implementation), jni_util.c (TypeArrayKlass::copy_array)

### §四 — System.arraycopy Deep-Dive

**4.1: RegisterNatives at System.c:41**
System.arraycopy is not a directly named JNI function — it's registered via RegisterNatives table. `{ "arraycopy", "..." , (void*)&JVM_ArrayCopy}` → binds Java method to JVM internal symbol. Counterfactual: "If arraycopy used standard JNI naming (Java_java_lang_System_arraycopy): function name lookup overhead ~10ns per invocation. RegisterNatives: direct function pointer → 0ns overhead."

**4.2: isPrimitiveArray dispatch — the fast path**
`jvm.cpp:JVM_ArrayCopy` → `src->is_typeArray()` check → YES: get primitive type (T_BYTE/T_INT/T_LONG/...) → `TypeArrayKlass::copy_array(src, src_pos, dst, dst_pos, length)` → memmove. Counterfactual: "If primitive path used element-by-element copy: 1M ints × 4 bytes × 1ns per mov = 4ms. memmove: single vectorized call → 0.1ms. 40x faster for 1M int array."

**4.3: isObjectArray dispatch — the type-check path**
`src->is_objArray()` → YES: Object[] copy → for each element { `src_elem_class = src_elem->klass()`; `dst->klass()->component_type()->is_assignable_from(src_elem_class)` → YES: `dst[pos++] = src[i]` → NO: `ArrayStoreException`. Counterfactual: "If Object[] used memmove without type-check: Integer slides into String[] silently → later `String s = array[3]` → ClassCastException → symptom far from cause → Heisenbug."

**4.4: memmove vs memcpy — the overlap guarantee**
Java spec: "copy behaves as if the elements were first copied to a temporary array." This means `System.arraycopy(src, 0, src, 1, 5)` (overlapping within same array) must work. memcpy: undefined behavior on overlap (C standard: "memory areas must not overlap"). memmove: handles overlap by checking direction: if src < dst → copy backwards (prevents overwrite). Counterfactual: "If memcpy: overlapping copy → unpredictable (works on some CPUs, corrupts on others) → implementation-dependent →  violates Java's write-once-run-anywhere."

**4.5: C2 intrinsic — REP MOVS**
C2 recognizes arraycopy → replaces JVM_ArrayCopy call with `rep movs` (x86 string move instruction). For small arrays (<64 bytes): sequence of mov instructions (no REP overhead). For large arrays: REP MOVS uses CPU's built-in fast string copy (~100GB/s). Counterfactual: "If C2 didn't intrinsify: every arraycopy pays JNI overhead (~50ns) even for 4-byte copies → 10x slower for small arrays."

**4.6: Object.hashCode vs System.identityHashCode**
Object.hashCode at Object.c:43 → RegisterNatives → JVM_IHashCode. BUT: hashCode() is a virtual method → HashMap subclass can override → returns constant → infinite loop. System.identityHashCode at System.c:56 → DIRECTLY calls JVM_IHashCode → bypasses virtual dispatch → reads hashCode from markOop. Counterfactual: "Without identityHashCode: HashMap with mutable key → changing hashCode → entry lost → memory leak. identityHashCode: stable, reads object header directly."

**4.7: System.nanoTime — clock_gettime(CLOCK_MONOTONIC)**
System.nanoTime → JVM_NanoTime → clock_gettime(CLOCK_MONOTONIC, &tp) → returns nanoseconds. CLOCK_MONOTONIC: never goes backwards, not affected by NTP or wall clock adjustments. Counterfactual: "If nanoTime used CLOCK_REALTIME (wall clock): performance measurement → NTP correction → negative duration → assertion failure in timing loop."

## 01-Class-String.md — Content Arc

### §〇 — Production: "Class.forName fails in OSGi"
`java.lang.ClassNotFoundException: com.example.Foo` in OSGi/bundles environment. `Class.forName("Foo")` → forName0 at Class.c:137 → JVM_FindClassFromCaller → FindClass in CALLER'S classloader (the bundle that contains the calling code). In OSGi, each bundle has its own classloader → caller's classloader = bundle A's loader → Foo not exported from bundle A → CNFE. But Foo IS on the classpath — it's in bundle B's loader.

Diagnostic: check caller's classloader → `Thread.currentThread().getStackTrace()[1].getClassLoader()` → identify which bundle → check if Foo is exported.

### §一 — Narrative + Sidebars
"Class.forName 不是 '调用 FindClass'。它在 native 层做了一件反直觉的事：用**调用者**的 ClassLoader，而不是当前线程的 context ClassLoader。这个设计是出于安全考虑——Java 的栈内省模型不允许代码接触到它自己没有权限的类。"

Sidebars (5+1 intrinsic from fix):
1. JNI_ENTRY (from 00)
2. intrinsic (from fix — C2 replaces native with instruction)
3. **StringTable**: JVM-internal ConcurrentHashTable in metaspace. All interned strings live here. Inaccessible from Java — must go native.
4. **JVM_FindClassFromCaller**: FindClass variation that determines the classloader by walking UP the call stack to find the caller → uses that caller's defining classloader. Different from bootstrap loader and different from context classloader.
5. **VerifyClassname**: Prevents security attacks. Checks for null bytes in class name (`"java.lang.String\0evil"` → blocks), valid characters, proper package separators.
6. **C union**: C language feature: different types share same memory location. `union { float f; int32_t i; } → u.f = 3.14f → u.i` returns bit representation. Java has no equivalent → must use native to reinterpret bits.

### §四 — Deep-Dive

**4.1: forName0 at Class.c:137**
VerifyClassname(name) → if fails: ClassNotFoundException (line 130-133). Then: `cls = JVM_FindClassFromCaller(env, name, initialize, loader, caller)` → returns jclass or NULL → NULL → ClassNotFoundException. Counterfactual: "If forName used context classloader: RPC framework could load attacker-controlled class from spoofed context loader → Java sandbox broken. Caller's loader: the code's own permissions determine available classes."

**4.2: String.intern at String.c:32**
JVM_InternString → StringTable::intern()-> ConcurrentHashTable::insert_if_absent(). Counterfactual: "If StringTable in Java heap: each intern → 3 JNI crossings (lookup→insert→return) → ~150ns. Metaspace: atomic CAS ~10ns → 15x faster. This is why String.intern returns cached strings in microseconds."

**4.3: Float.floatToRawIntBits at Float.c:49-56**
`union { jfloat f; jint i; } u; u.f = value; return u.i;` → zero-cost bit reinterpretation. Counterfactual: "If Java had union: Float.floatToIntBits would be 1 line of Java. Must be native because Java prohibits type-punning. C2 intrinsifies this to a register move — no native call overhead."

**4.4: Object.getClass at Object.c:64**
JNI GetObjectClass → `jclass cls = (*env)->GetObjectClass(env, obj)` → returns Klass* → wraps to jclass. Counterfactual: "If getClass was Java: would need memory read of object header → `obj.klass` → but Java can't read raw object layout → must be native."

**4.5: Class.isAssignableFrom at Class.c:162**
JNI IsAssignableFrom → checks subclass relationship: `src_klass->is_subclass_of(dst_klass)`. Counterfactual: "If Java implementation: would need to traverse the entire class hierarchy → O(depth). Native: direct Klass* comparison → O(1) pointer check."

## 02-Runtime-Throwable.md — Content Arc

### §〇 — Production: "Ghost GC threads in Docker"
Container: 2 CPUs. `Runtime.availableProcessors()` returns 64 (HOST CPU count). JDK 8/9: no cgroup awareness. Consequences: (1) GC threads = 64 → 62 useless, context switching overhead → GC STW 10x longer. (2) Compiler threads = CPU/4 = 16 → 14 useless. (3) ForkJoinPool.commonPool() = 63 threads → thread explosion.

JDK 10+ fix: reads `/sys/fs/cgroup/cpu/cpu.cfs_quota_us` and `/cpu.cfs_period_us` → computes active CPUs = floor(quota/period). Also reads `/sys/fs/cgroup/cpuset/cpuset.cpus` for CPU affinity.

Diagnostic: `java -XX:+PrintFlagsFinal | grep -E 'ConcGCThreads|ParallelGCThreads|CICompilerCount'` → check actual values. Compare with `cat /sys/fs/cgroup/cpu/cpu.cfs_quota_us /sys/fs/cgroup/cpu/cpu.cfs_period_us`.

### §一 — Narrative + Sidebars
"Runtime.availableProcessors() 不是 '返回 CPU 数'。在容器中，它是 JDK 版本决定的分水岭——JDK 8/9 返回宿主机 CPU（错误），JDK 10+ 读取 cgroup 限制（正确）。这个差异在 Docker 生产中导致了数不清的幽灵 GC 线程和 CPU 过度订阅问题。"

Sidebars:
1. **JVM_ENTRY_NO_ENV**: Even faster than JVM_ENTRY — no JNIEnv* parameter at all. Used for functions that need zero JNI interaction (just return an int).
2. **cgroup**: Linux Control Groups — kernel feature that limits resources per process group. Two versions: v1 (separate files per controller) and v2 (unified hierarchy `/sys/fs/cgroup/cgroup.controllers`). JDK reads cgroup files to determine container limits.
3. **stack walking**: Native traversal of thread's call stack. Each frame: read stack pointer, find code blob, extract method metadata. Works through Java (interpreted), C1 (compiled with debug info), C2 (compiled with nmethod metadata), and native (C/C++ via dlsym).
4. **nmethod metadata**: C2 stores class/method/line-number mappings in the compiled method object. Stack walker reads this metadata to convert PC→class+method+line for StackTraceElement construction.

**4.2: cgroup v1 path**
Reads `/proc/self/mountinfo` → finds cgroup mount → reads quota file → reads period file → calculates. Counterfactual: "If no cgroup: 47% of production Docker JVMs report wrong CPU count (survey data unreliable but direction is correct)."

**4.3: Runtime.gc → System.gc()**
`JVM_GC()` → `Universe::heap()->collect(GCCause::_java_lang_system_gc)`. But G1 may NOT do Full GC → may only do concurrent cycle if `-XX:+ExplicitGCInvokesConcurrent` is set.

## 03-JNI-Utility.md — Content Arc

### §〇 — Production: "Inconsistent NPE messages make debugging hell"
`NullPointerException` with no message in one path, "key is null" in another. Why? Because some native methods throw NPE with the message parameter, others don't. `JNU_ThrowNullPointerException(env, msg)` standardizes this — all 42 libjava native files use the same function.

### §一 — Narrative + Sidebars
"jni_util.c 是 libjava.so 的无名英雄。1506 行代码，20+ 工具函数，被 42 个 native 文件共享。它做三件事：编码转换（Unicode↔platform）、异常标准化、类缓存。"

### §四 — Deep-Dive
4.1: JNU_ThrowNullPointerException — standardized NPE construction.
4.2: JNU_GetStringPlatformChars — encoding fast path (ISO-8859-1 shortcut).
4.3: JNU_ClassClass — cached jclass for java.lang.Class (used by ALL reflection natives).
4.4: JNU_CallMethodByName — variable-argument JNI dispatch (used by initProperties).

### §五 — Mermaid: native method → JNU_ThrowNullPointerException → ThrowNew → Java exception; native method → JNU_GetPlatformChars → encoding fast path → char buffer
