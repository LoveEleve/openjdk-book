### §四 — InlineTree: the recursive decision engine

**4.1 The 5-step decision**
`InlineTree::should_inline(ciMethod* callee, int bci)`:
1. Force-inline? `callee->force_inline()` — @ForceInline annotation → YES
2. Force-don't? `callee->should_not_inline()` — @DontInline, native method, synchronized (C2 can inline sync), abstract → NO
3. Depth? `inline_level() > MaxInlineLevel(9)` → NO. Counterfactual: "Why 9? Because each call site is a tree node → depth 9 = 2^9 possible callees if each calls 2 others → 512 methods in 1 nmethod. Depth 10 = 1024 methods → 4x compile time. 9 is where compile time crosses compilation benefit."
4. Size? `callee->code_size() > MaxInlineSize(35)` → NO unless frequency overrides. Counterfactual: "If no size limit: inline everything → CodeCache 10x bigger → sweeper overwhelmed → emergency flush storms."
5. Frequency? `callee->call_count() / total_calls > InlineFrequencyRatio` → YES if called enough.

**4.2 CHA (Class Hierarchy Analysis)**
"When C2 sees `invokevirtual hashCode()`, it doesn't know which class's hashCode. CHA checks: how many concrete subclasses of the receiver's declared type exist?"

- `ciKlass::is_leaf_type()` → 1 concrete class → monomorphic → inline as direct call + CHA guard.
  Compiled code: `cmp [recv+klass_offset], expected_klass; jne uncommon_trap; call hashCode_direct`.
  If guard passes (99.9% of calls): direct call, 1 cycle. If guard fails: deopt, ~5000 cycles.
  Counterfactual: "Without CHA: every invokevirtual = vtable dispatch = 4 memory reads (klass→vtable→itable→entry) = ~20 cycles. With CHA: 1 cmp + direct call = 2 cycles. 10x faster for monomorphic calls."

- `ciKlass::has_subklass()` → multiple subclasses → bimorphic → inline BOTH as guards.
  `cmp [recv+klass], HashMap; je hashMap_code; cmp ArrayList; je arrayList_code; jmp vtable_dispatch`
  Counterfactual: "Without bimorphic: monomorphic + deopt for TreeMap. TreeMap freq < 0.01% → deopt rate negligible. But if TreeMap freq = 40% → 40% deopt rate → recompile loop. Bimorphic handles 2 common cases without deopt."

**4.3 Type Profile from C1 (ciCallProfile)**
"CHA is blind to empirical frequencies. CHA says 'subclass X exists' → possible. Profile says 'subclass X was NEVER seen in 100000 calls' → don't guard for it."

- `ciCallProfile::count()`: total invocations = counter_count + data_count
- `ciCallProfile::receiver_count(i)`: how many times was Klass_i the receiver?
- `ciCallProfile::receiver_projected_type(i)`: type of the i-th argument (not just receiver)

Counterfactual: "If no profiling: C2 must guard for ALL possible subclasses. 5 subclasses → 5-way guard → 25 cycles per call. With profiling: 99.9% = HashMap → 1-way guard + slow path = 3 cycles + rare deopt."

**4.4 Late Inline (post-IGVN)**
After IGVN: some calls were optimized away (dead code). Remaining calls are the IMPORTANT ones.
`PhaseIdealLoop::do_call()` registers late inline candidates → `Compile::inline_incrementally()`.

Counterfactual: "If you inline BEFORE IGVN: you inline into a graph with redundant computations → 2x Nodes → slower IGVN. After IGVN: graph is clean → inline adds fewer Nodes → faster."

**4.5 Downstream Cascade Effect**
```
process() { hash(a); hash(b); hash(c); hash(d); }
```
Before inline: 4 × `call hash()` = 4 × 40 cycles overhead = 160 cycles
After inline: 4 × hashCode() code VISIBLE to IGVN. But hashCode() computes the SAME value 4 times → IGVN eliminates 3 of them → 1 × hashCode() = 40 cycles total.
"That's 4x speedup from inline + IGVN together — not inline alone. Inline is a MULTIPLIER."

**4.6 Production: PrintInlining log interpretation**
Full guide: what each message means, what flags to change, what the consequences are.
- `(hot)`: candidate, being considered
- `already compiled into a big method`: inline elsewhere → won't inline again → prevents CodeCache explosion
- `callee is too large`: size > MaxInlineSize → `-XX:MaxInlineSize=500`
- `inline level too deep`: depth > MaxInlineLevel → `-XX:MaxInlineLevel=12`
- `no static binding`: virtual call with multiple subtypes, CHA cannot monomorphize

## 03-Chaitin-RegAlloc.md — Content Arc

### §〇 Production: "perf top shows 48.67% spills"
```
Samples: 128K of event 'cycles', 4000 Hz
  22.12%  [JIT compiled code]    mov %rax, -0x10(%rbp)    ← spill
  18.34%  [JIT compiled code]    mov -0x10(%rbp), %rcx    ← fill
   8.21%  [JIT compiled code]    mov %rsi, -0x18(%rbp)    ← spill
```

### §一 Narrative + Beginner sidebars
"x86_64 只有 16 个通用寄存器。C2 为每个临时值创建一个虚拟寄存器——可能 50+ 个。Chaitin 着色把虚拟寄存器映射到物理寄存器。能映射的：1 cycle。不能映射的：spill 到栈上，5 cycles + store-forwarding 延迟。"

Sidebars: Virtual Register, Physical Register, Live Range, IFG, Spill, Coalesce, Simplify, Select

### §三 Source files (6)

### §四 — The CORRECT algorithm sequence

**CRITICAL: This is HotSpot's ACTUAL order from chaitin.cpp:336-583, which differs from Chaitin 1982.**

**Step 1: Live Ranges (line 418)**
`PhaseLive::compute()` — for each Node: `_first_use` to `_last_use` = live range.
Example: `int x = a+b; int y = c+d; return x+y;`
x lives from `a+b` to `x+y`. y lives from `c+d` to `x+y`. Overlap at `x+y` → x and y need DIFFERENT registers.

**Step 2: Virtual IFG (build_ifg_virtual)**
For each vreg pair: do their live ranges overlap? If yes → IFG edge → cannot share a register.
At this point: IFG uses VIRTUAL registers (50+). Many edges.

**Step 3: AggressiveCoalesce (line 425)**
`PhaseAggressiveCoalesce::coalesce_driver()` — for each `mov v1, v2` instruction: if v1 and v2 DON'T interfere → merge into one vreg → eliminate the mov.
Example: `mov v1, v2; add v2, v3` → if v1+ v2 don't interfere → merge → `add v1, v3`. Saved: 1 instruction + 1 cycle.
Counterfactual: "If you coalesce AFTER coloring: the `mov v1, v2` instruction was COUNTED as a register use in IFG → v1 and v2 each took up a GPR → 2 registers for what should be 1 → extra spill that didn't need to exist."
Why AGGRESSIVE? At this stage, IFG is on VIRTUAL registers — less strict than physical IFG. Merge as many as possible before "hardening" to physical IFG.

**Step 4: Physical IFG (build_ifg_physical)**
NOW build IFG with real 16 GPR constraints. Virtual regs that survived coalesce → mapped to physical IFG nodes.

**Step 5: Simplify (line 515)**
Iteratively remove low-degree nodes from IFG. If a node has degree < 16 → push onto "simplified" stack → can ALWAYS color (guaranteed by Chaitin's theorem).

**Step 6: Select (line 519)**
Pop from simplified stack → assign first available color (GPR) not used by neighbors.
If stack is empty AND uncolored nodes remain → all remaining nodes have degree ≥ 16 → CANNOT color → must spill.

**Step 7: Spill + Split + ConservativeCoalesce (line 546-575)**
Choose lowest-cost Node (not in a loop, not frequently used) → `PhaseChaitin::Split()` cuts its live range → creates new vreg → insert `mov reg→stack` (spill) + `mov stack→reg` (fill) instructions.
ConservativeCoalesce: after spill → same idea but CONSERVATIVE: only merge if it WON'T force another spill.

**Step 8: Loop back to Step 1**
With new vregs from spill → recompute live ranges → rebuild IFG → retry.

**Step 9: fixup_spills (line 680)**
Insert actual x86 spill instructions into the compiled code.

**Why THIS order, not textbook order?**
Textbook Chaitin 1982: Build → Coalesce → Spill Cost → Simplify → Select. No physical IFG, no AggressiveCoalesce.
HotSpot: Build virtual → AggressiveCoalesce → Build physical → Simplify → Select → Spill + ConservativeCoalesce.
Key differences: (1) AggressiveCoalesce BEFORE physical IFG — eliminates movs at virtual stage when IFG is looser. (2) Separate physical IFG — maps vregs to real 16 GPR constraints. (3) ConservativeCoalesce AFTER spill — avoids inflaming the spill cycle.

### §五 — Spill Cost Calculation
`Node::_cnt` = estimated execution frequency. Loop-nested Node → _cnt higher → more expensive to spill.
"If a Node lives entirely in a loop body: spilling it means 1 store + 1 load PER ITERATION. 10^6 iterations → 2M extra memory ops. Don't spill this Node."

Timeline of live ranges → IFG construction → coloring → spill.

Step through AggressiveCoalesce → print vreg count before/after. Verify Simplify stack.

"Chaitin 着色算法的核心思想？"
Correct sequence + Coalesce-before-Coloring key insight.

### §四 — nmethod Lifecycle + CodeCache Architecture

**4.1 nmethod 5-state lifecycle**
```
alive → not_entrant → zombie → unloaded → freed
```

**alive**: Compiled and in use. Can be entered by any thread. Has `_state == alive`.

**alive → not_entrant**: C2 recompiled this method (e.g., better profile data → different inline decisions → need nmethod v2).
New version: `Method::set_code(nmethod_v2)` — swaps entry point atomically.
Old version: `nmethod::make_not_entrant()` — sets `_state = not_entrant`. Existing threads CAN finish. New threads CANNOT enter.
Counterfactual: "If you freed the old nmethod immediately: thread A is inside `getfield` in the old nmethod when CodeCache frees it → SIGSEGV. Two-stage shutdown (not_entrant→zombie) prevents use-after-free."

**not_entrant → zombie**: All threads have exited. `nmethod::can_be_zombie()` returns true → `NMethodSweeper::possibly_flush()` marks `_state = zombie`.

**zombie → freed**: `NMethodSweeper::sweep_code_cache()` at safepoint → `nmethod::flush()` → `CodeCache::free(nmethod)` → space reclaimed.

**freed → ...**: Space reused for new compilation.

**4.2 CodeCache 3-segment layout**
```
Segment 1: non-profiled (C1 L1 + C2 without profile data)
Segment 2: profiled (C1 L2/L3 with profile data)
Segment 3: non-method (adapters, stubs, BufferBlob)
```
Each segment has independent free list. Why 3 segments? C2 nmethod uses more space than C1 → separate allocation prevents C2 from starving C1.

**4.3 NMethodSweeper: background cleanup**
Sweep cycle: every `NmethodSweepFraction` (16) safepoints.
At each cycle: check `_traversals` → `sweep_code_cache()` if threshold reached.
sweep_code_cache(): iterate all nmethods → zombie? → `nmethod::flush()` → free.
Why safepoint-based? Deferred cleanup: mark now, free later. "Concurrent free while threads might still hold references → ABA problem in free list."

**4.4 Emergency flush**
Trigger: `CodeCache::allocate()` fails → `CodeCache::needs_flushing()` → `NMethodSweeper::handle_full_code_cache()`.
Aggressive sweep: skip normal traversal → sweep ALL → free more aggressively.
Threshold: `-XX:StartAggressiveSweepingAt=80` (start at 80% CodeCache usage).

**4.5 Speculative disconnect**
`nmethod::speculative_disconnect()`: if deoptimized within first `SpecTrapLimit` invocations → mark as "unstable" → never recompile → saves CodeCache from recompilation loop.
