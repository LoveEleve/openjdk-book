## 1. JLI_Launch Trace Completeness — 15 pts (00 §四)

This is THE core section of the entire phase. If the 8-step trace in 00 §四 fails, nothing else in 13 matters.

### What "perfection" looks like:
The reader can follow `bash$ java -jar app.jar` through 8 steps, each with:
1. **Source evidence**: exact file:line, actual C code snippet (2-5 lines, not paraphrased)
2. **What happens**: concrete description of what the code DOES at this step
3. **Why this way**: counterfactual with quantified alternative. "If JLI_Launch only got 2 params (argc, argv) instead of 12: every platform's main() would need to extract version strings / flags / product name differently → 3× code duplication across Windows/Unix/Mac."
4. **Transition**: clear handoff to next step. "Step 4 returns control to Step 5 with the ifn.CreateJavaVM function pointer populated."

### Detailed verification checklist (1.5 pts per step, 8 steps, max 12 + 3 bonus for Mermaid/timing):

**Step 1: JLI_Launch entry (java.c:220)**:
- 12-parameter signature shown? YES/NO
- Each parameter EXPLAINED (not just listed)? "jargc/jargv = JVM-specific args from platform launcher" — yes, explained. "cpwildcard = whether CLI parser already expanded wildcards" — yes, explained.
- Counterfactual: "Why 12 not 2?" — must be present with specific rationale (platform pre-processing).
- Off-by-one check: line 220 confirmed correct (was 219, fixed in review)?

**Step 2: SelectVersion (java.c:1056)**:
- JAR manifest reading for JRE version explained? "Created-By: 11" → SelectVersion knows JAR needs JDK 11.
- Counterfactual present? "Without SelectVersion: JVM 11 starts, encounters JDK 17 bytecodes → ClassFormatError → 2s wasted."
- Line 1056 verified?

**Step 3: CreateExecutionEnvironment (java_md_solinux.c:284)**:
- JAVA_HOME preference explained? "checked FIRST as performance shortcut, saving 5-10 syscalls."
- /proc/self/exe fallback explained?
- stat(lib/libjava.so) as JRE anchor explained?
- Counterfactual present?

**Step 4: LoadJavaVM → dlopen (java_md_solinux.c:571)**:
- RTLD_NOW vs RTLD_LAZY tradeoff quantified? "RTLD_LAZY saves ~200ms but risks runtime undefined symbol crash."
- RTLD_GLOBAL rationale? "Required for -agentlib dlsym(RTLD_DEFAULT, ...) calls."
- Line 571 verified?

**Step 5: JVMInit → JavaMain → thread creation (java_md_solinux.c:786)**:
- 3 reasons for separate thread cited? (primordial thread problems, custom stack size, guard page disable)
- java.c:202-204 comment quoted? "Running Java code in primordial thread caused many problems."
- Counterfactual: "If JVM ran in main thread: stack overflow corrupts launcher data structures."

**Step 6: ParseArguments (java.c:1296)**:
- Overview (details in doc 01). Mode detection: LM_JAR/LM_CLASS/LM_MODULE/LM_SOURCE.
- "-jar overrides -cp" at java.c:338-340 mentioned?
- Transition: "→ details in [01-Argument-Parsing] §四"

**Step 7: LoadMainClass → JNI CreateJavaVM call (java.c:1545 + java.c:523)**:
- This is the 13→01 handoff. MUST be clearly marked: "→ enters 01-jvm-startup territory"
- JNI_CreateJavaVM called at java.c:1545. What happens AFTER it returns? LoadMainClass at java.c:523.
- Counterfactual: "If JNI_CreateJavaVM fails (returns != JNI_OK): JVM_ERROR1 at emessages.h:60 → fprintf + exit(1). libjli NEVER enters Java."

**Step 8: CallStaticVoidMethod (java.c:566)**:
- The IRREVERSIBLE transition. "libjli's C stack freezes. JVM's Java stack takes over."
- Exception handling: ExceptionOccurred → ExceptionDescribe → exit(1).
- "libjli never RETURNS from this call" — emphasized?

**Bonus 3 pts**:
- Timing analysis: libjli 0.05s vs libjvm 2s. Percentage breakdown.
- Mermaid diagram: 4-lane sequence (Shell, libjli, libjvm, Java). From `bash$ java` to `main()`.
- The 13/01 responsibility split is CLEARLY visualized.

## 2. Production Authenticity — 10 pts

### Per-doc opener verification:

- Exact error string from emessages.h:60? "Error: Could not create the Java Virtual Machine. Error: A fatal exception has occurred. Program will exit."
- 3-branch diagnosis present? DLL_ERROR1 / JVM_ERROR1 / CLS_ERROR1 with exact line triggers?
- Diagnostic commands: stat, ldd, ulimit -v, strace — ALL 4 present?
- Fix: which branch → which command → which resolution path?

**01 §〇 — ZGC on JDK 11** (2.5 pts):
- Exact crash signature? ZBarrierSetC2::emit_barrier_stub → NullPointerException → SIGSEGV. The SIGSEGV address appears in hs_err.
- Root cause explanation: experimental flag, forwarded by libjli, dangerous but not blocked.
- Diagnostic: PrintFlagsFinal | grep zgc → confirmed flag was set.
- Exclusion verification (Gap 1 fix): -XX:-UseZGC exclusion confirmation step present? 3 resolution paths (UnlockExperimentalVMOptions / upgrade JDK / remove flag)?
- Counterfactual: "If libjli BLOCKED experimental flags: false positives — many production JVMs use experimental flags. If libjli ALLOWED everything: ZGC crash. The middle ground is: forward all flags, let JVM validate."

**02 §〇 — JAVA_HOME conflict** (2.5 pts):
- Exact error? JRE_ERROR8 from emessages.h:98. "Error: could not find libjava.so"
- Scenario: JAVA_HOME=JDK8, /proc/self/exe=JDK11 → JDK8 has no libjava.so → error.
- Diagnostic: readlink -f, echo JAVA_HOME, stat, unset JAVA_HOME bypass — ALL 4 commands?
- Quantified: "unset JAVA_HOME in systemd → eliminates ~60% of JRE_ERROR8 faults."

**03 §〇 — Spring Boot fat JAR** (2.5 pts):
- Exact error? CLS_ERROR1 from emessages.h:68. Full class name in error.
- Root cause: nested JAR layout. Standard JVM classpath sees outer JAR only → FindClass fails for JarLauncher inside BOOT-INF/lib/.
- Diagnostic: jar xf manifest, unzip -l, unzip -p extract nested JAR, jar tf verify — ALL 4 steps?
