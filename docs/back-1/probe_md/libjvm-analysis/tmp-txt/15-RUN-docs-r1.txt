## 00-System-Arraycopy.md — Content Arc

### §〇 Production
`java.lang.ArrayStoreException: java.lang.Integer` — Object[] source has Integer, destination is String[]. Native arraycopy does element-by-element type check → Integer can't go into String[].

Diagnostic: check src.getClass().getComponentType() vs dst.getClass().getComponentType().

### §一 Narrative + 5 sidebars
JNI_ENTRY, JVM_ENTRY, intrinsic, memmove, markOop — each 2-3 sentences, defined before first code use.

### §四 Deep-Dive (8 groups)
4.1: RegisterNatives at System.c:41 — direct function pointer binding. Counterfactual: "If named JNI: ~10ns overhead per call. RegisterNatives: 0ns."
4.2: isPrimitiveArray → memmove fast path. Counterfactual: "1M ints element-by-element: 4ms. memmove: 0.1ms. 40x faster."
4.3: isObjectArray → element-by-element type check. Counterfactual: "memmove without type-check: Integer slides into String[] → ClassCastException later."
4.4: memmove vs memcpy — Java spec overlap guarantee. Counterfactual: "memcpy on overlap: UB → implementation-dependent behavior."
4.5: C2 intrinsic → REP MOVS on x86. Counterfactual: "If no intrinsic: every call pays JNI overhead (~50ns) even for 4-byte copy."
4.6: Object.hashCode at Object.c:43 → JVM_IHashCode → markOop. Counterfactual: "If hashCode not in header: generate each time → non-deterministic."
4.7: identityHashCode vs hashCode — virtual dispatch bypass. Counterfactual: "Without identityHashCode: HashMap infinite loop with mutable keys."
4.8: nanoTime → clock_gettime(CLOCK_MONOTONIC). Counterfactual: "CLOCK_REALTIME: NTP adjustment → negative duration."

### §五 Mermaid: arraycopy dispatch table — isTypeArray→YES:memmove / NO:Object[]→type-check→assignable?→YES:copy / NO:ArrayStoreException
