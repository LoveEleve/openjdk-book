Does it explain HOW to exclude the crashing method (`-XX:CompileCommand=exclude`)? Is there a concrete WORKFLOW: "find method in hs_err → grep -r for method name in logs → add CompileCommand → restart"?

**P02 Inline Decision**: Does §〇 show REAL `-XX:+PrintInlining` output with inline tree depth? The key symptom is "already compiled into a big method" — is this explained? Does it show the CASCADE: "1 method inlines 2000+ callees → single nmethod 2MB → CodeCache full → CompileBroker disabled"?

**P03 Chaitin RegAlloc**: Does §〇 show REAL `perf top` output with `mov %rax, disp(%rbp)` spill instructions? Does it show the spill storm ratio (>5% spills = problematic)? Does it explain the ROOT CAUSE: "too many live ranges → register pressure > 16 → Chaitin spills → mov instructions dominate"?

**P04 CodeCache**: Does §〇 show the EXACT log line `"CodeCache is full. Compiler has been disabled."`? Does it quantify the IMPACT: "3 minutes at 100% → QPS drops 80% → after sweeper cleans, CodeCache back to 85% but damage done"? Does it connect to P02's inline-depth problem?

**P05 Deopt**: Does §〇 show REAL `-XX:+PrintDeoptimizationDetails` output? Does it explain the deopt LOOP: "compile → deopt → recompile → deopt → ..."? Does it show the CPU cost (50% CPU in deopt blob)?

**P06 OopMap**: Does §〇 show REAL hs_err with `bad oop`? The exact line: `G1ParScanThreadState::copy_to_survivor` with the bad oop address? Does it explain WHY the OopMap was wrong?

**P07 Profile Data Flow**: Does §〇 show the profile pollution scenario concretely? "Warmup receiver = HashMap 100%. Production receiver = TreeMap 50%. Profile says 100% HashMap → C2 generates monomorphic guard → production trips guard → deopt → recompile → deopt again."

## 2. First-principles depth — 10 pts per prompt

For EACH prompt, check §四 question groups:

**Counterfactual check**: For each question group, is there a clear "if you designed this without X"? If at least 4 of 6-7 groups have explicit counterfactuals, the prompt passes.

**Quantification check**: Are tradeoffs QUANTIFIED? 
- Good: "Without inline: 40 cycles per call overhead × 1000 calls = 40000 cycles"
- Bad: "Without inline, it would be slower"

**Specific checks per prompt:**

P01: Does §4.3 explain "Sea of Nodes vs Linear IR" with concrete tradeoff? "Sea of Nodes allows floating nodes → better GVN. But graph matching is NP-hard → HotSpot uses ADL patterns not automorphic matching."

P02: Does §4.5 show the BEFORE/AFTER inline cascade with actual instruction counts? Not "it gets faster" — "67 instructions → 31 instructions, 54% reduction."

P03: Does §4.5 explain Coalesce BEFORE coloring? "AggressiveCoalesce happens at line 425, BEFORE physical IFG at line 490. This is different from standard Chaitin 1982 where coalesce is post-coloring."

P04: Does §4.5 explain WHY sweeper uses safepoint-based sweeping? "Sweeper marks nmethod as zombie → waits for all threads to exit → code cache sweep at safepoint. Free at safepoint: no concurrent free, no ABA problem."

P05: Does §4.2 explain WHY frame rebuild needs OopMap? "Without OopMap: deopt can't tell if R10 contains int or oop → can't write to correct interpreter frame slot."

P06: Does §4.1 explain WHY OopMap is a BITMASK not a list? "Compressed bitmask: each safepoint ~10 bytes. List: each oop = 8-byte pointer × 5 oops = 40 bytes. 1M methods × 5 safepoints × 30 bytes saved = 150MB CodeCache savings."

P07: Does §4.5 explain Profile Maturity with COUNTERFACTUAL? "Without maturity: C2 uses 10 warmup calls → 100% HashMap → wrong inline → deopt loop. With maturity: 500+ invocation counter → real traffic patterns → correct inline."

### Scoring per prompt:
9-10: 4+ groups have explicit counterfactuals with quantification
7-8: 3 groups have counterfactuals
5-6: groups describe mechanisms but don't counterfactualize
3-4: groups are "what" not "why"
1-2: no first-principles reasoning
