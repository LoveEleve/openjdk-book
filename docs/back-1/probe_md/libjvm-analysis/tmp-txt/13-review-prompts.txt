### What "bad" looks like:

## 2. First-Principles Depth — 10 pts per prompt

### What "good" looks like:
Each §四 question group starts from "If you designed the java launcher from scratch..." and DERIVES HotSpot's choice as the logical consequence of constraints. The counterfactual is QUANTIFIED: "RTLD_LAZY instead of RTLD_NOW: saves 200ms symbol resolution at dlopen time, but threads crash LATER with undefined symbol errors — tradeoff is startup speed vs runtime reliability."

### What "bad" looks like:
Question groups describe mechanisms: "JLI_Launch has 12 parameters." No counterfactual, no "why," no alternative cost. Just documentation restated as questions.

### Per-prompt checks (≥6 out of 8 groups must be counterfactual-driven):

**P00 checks — spot-check 3 groups**:
- 4.1 JLI_Launch 12 parameters: "Why 12 params not 2 (argc, argv)?" → Because platform-specific startup flags are pre-resolved. Counterfactual: "If libjli only got argc/argv: every platform's main() would need to extract version/flags/eproduct name differently → duplicate logic across Windows/Mac/Linux."
- 4.4 LoadJavaVM/dlopen: RTLD_NOW vs RTLD_LAZY tradeoff — quantified? "RTLD_LAZY saves ~200ms at startup but crashes later with 'undefined symbol' in production traffic."
- 4.5 Thread creation: "If JVM ran in primordial thread: stack overflow corrupts launcher stack." Quantified: "pthread stack = 8MB separate → 10 threads × 8MB = 80MB overhead. Tradeoff between isolation and memory."

**P01 checks**:
- 4.2 LaunchMode: "4 modes, 4 execution paths. Counterfactual: if -jar and -cp path shared logic → classpath conflict between jar mode (overwrite) and cp mode (append) → non-deterministic class loading." Explicit classpath overwrite mechanism at java.c:338-340.
- 4.5 Wildcard expansion: "Why expand at startup not at class load? opendir 1000 JARs = ~2ms. Per-class opendir: 1000 classes × 2ms = 2s startup. 1000x difference."
- 4.8 -version flag: "Why handle BEFORE JNI_CreateJavaVM? Saving 2s of JVM startup for printing a version string."

**P02 checks**:
- 4.3 JAVA_HOME preference: "JAVA_HOME is checked before /proc/self/exe as a performance shortcut — saves 5-10 syscalls. But the cost: stale JAVA_HOME → wrong JVM loaded → startup failure with misleading error."
- 4.6 dlopen(RTLD_NOW|RTLD_GLOBAL): "RTLD_GLOBAL: why not RTLD_LOCAL? -agentlib needs dlsym(RTLD_DEFAULT, 'JNI_GetCreatedJavaVMs') → requires JVM symbols in global table."
- 4.8 libjsig preloading: "Why signal chain setup BEFORE JVM starts? Because JVM's signal handlers install in Threads::create_vm → if signal chain isn't ready → SIGPROF from profiler delivered to raw JVM handler → crash."

**P03 checks**:
- 4.4 LauncherHelper indirection: "Why Java helper instead of direct FindClass? JNI FindClass returns null → 4-step exception handling in C vs 1-step catch block in Java. LauncherHelper wraps JNI complexity for better error messages."
- 4.6 CallStaticVoidMethod: "After this call, libjli never executes again. JVM owns the process. What if main() throws and there's no catch? ExceptionDescribe + exit(1) — the JVM exits, not the launcher."
- 4.7 Class-Path vs wildcard: "Timing difference: wildcard expanded at ParseArguments (before JVM). Class-Path appended at java.class.path init (after JVM starts). Class-Path JARs load AFTER system classes → can't override java.lang.String."

### Scoring per prompt:
9-10: 6+ groups have explicit counterfactuals with quantified tradeoffs
7-8: 4-5 groups counterfactual-driven
5-6: 2-3 groups
3-4: mostly "what" questions
1-2: no counterfactuals
