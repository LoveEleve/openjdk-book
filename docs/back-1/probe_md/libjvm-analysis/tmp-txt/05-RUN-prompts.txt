### §四 Deep Dive (7 question groups)

**4.1 Parse: bytecode → Node transformation**
Counterfactual: "If you didn't use Parse→Node, you'd have to optimize bytecodes directly — but bytecodes have implicit operand stack & local variables, making optimization NP-hard. Nodes make data dependencies EXPLICIT."
- `parse1.cpp:do_one_bytecode()` — how does iload_0 become a ParmNode?
- `parse2.cpp:do_one_block()` — how does IF_ICMPNE become IfNode + BoolNode + CmpNode?
- Why does Parse create a `new SafePointNode` at each basic block boundary?

**4.2 IGVN: hash-consing + iterative optimization**
Counterfactual: "If you did GVN in ONE pass: AddI(a,b) and AddI(b,a) wouldn't be unified because the commutation check is iterative."
- `phaseX.cpp:transform()` — hash lookup: `_table.hash_find(opcode, in(1), in(2))`
- How does `Node::Ideal(PhaseGVN*, bool)` return the optimized version? Example: AddI(0, x) → x
- Why does IGVN iterate until no changes? Because one optimization (inline) can expose new opportunities (GVN) → cascade

**4.3 Sea of Nodes design rationale**
Counterfactual: "If you used a linear IR (like LLVM's) — instructions are in order, and optimizations move them around. With Sea of Nodes: there IS no order — Nodes float until pinned."
- Why "sea"? No control flow ordering — edges are data+control dependencies, not sequential
- `Node::is_CFG()` — control nodes (If, Start, Return) are the ONLY pinned nodes
- Tradeoff: graph matching (instruction selection) is NP-hard on DAGs → HotSpot uses ADL patterns with manual Node selection, not automorphic matching

**4.4 Loop Optimization: peeling + unrolling + range check elimination**
- `PhaseIdealLoop::build_and_optimize()` — `loopnode.cpp:build_loop_tree()`
- Peeling: `PhaseIdealLoop::do_peeling()` — why 1 iteration? (makes invariant code obvious to IGVN)
- Range check elimination: `PhaseIdealLoop::rc_predicate()` — compare loop variable bounds

**4.5 Escape Analysis: object allocation → scalar replacement**
Counterfactual: "If you allocate on heap and don't EA: every `new Point(x,y)` = 40 cycles (TLAB bump) + GC overhead. EA: `x = 5; y = 7` — zero allocation."
- `ConnectionGraph::compute_escape()` — stream analysis: follow object through method calls
- When does EA FAIL: object stored to field → escapes; object argument to non-inlined call → escapes
- `PhaseMacroExpand::scalar_replacement()` — allocation node removed, fields become local variables

**4.6 Matching + Output: Ideal Node → x86 instruction**
- `Matcher::match()` — ADL patterns: `match_rule_supported(Op_AddI)` → finds `addI_reg_reg` in x86_64.ad
- `PhaseOutput::install_code()` → `CodeCache::allocate()` → `nmethod::nmethod()`
- OopMap generation per safepoint: `OopMapSet::add_gc_map(pc_offset, oopmap)`

**4.7 Full pipeline trace (the "100 bytecodes → 10 instructions" walk)**
Pick a concrete method: `int hash(String s) { return s == null ? 0 : s.hashCode(); }`
Show actual bytecodes, actual Nodes created, actual optimizations applied, actual x86 output.
BEFORE/AFTER for each phase with Node counts.

## PROMPT-02: Inline Decision (P0 — biggest optimization lever)

### §〇 Production Scenario
"启动后前 2 分钟——CodeCache 从 0% 到 97% 满。`-XX:+PrintInlining` 显示 1 个方法内联了 2000+ 层——InlineTree 深度没有限制，生成单个 nmethod 2MB。CodeCache full → CompileBroker 停止 → 热方法卡在解释器 → QPS 跌 80%。"

Real PrintInlining output:
```
@ 12 java.util.HashMap::hash (62 bytes)   inline (hot)
  @ 4 java.util.Objects::hashCode (12 bytes)   inline (hot)
    @ 4 java.lang.String::hashCode (49 bytes)   inline (hot)
      @ 19 java.lang.String::value (5 bytes)   accessor
    @ 8 java.lang.String::hashCode (49 bytes)   already compiled into a big method
```

### §一 Task + Narrative
"内联是 C2 最重要的单一优化——不是因为内联本身快，而是因为内联让其他优化 '看见' 更多代码。没有内联 = GC 在隔壁房间观察你的程序，只能看到 'call 0x...'。有了内联 = GC 看到了 callee 的 load/add/cmp 指令——可以跨方法消除重复计算。"

"Reader knows from 04 that CompileBroker triggers C2. This doc answers: C2's first optimization decision — should I inline this method call or not?"

Beginner callouts: InlineTree, CHA, type profile, hot count, uncommon trap

### §三 Source Files
| File | Role |
|------|------|
| doCall.cpp | Inline decision logic — inline_limit + frequency + call site analysis |
| inline.cpp | InlineTree construction — should_inline / should_not_inline |
| ciMethod.cpp | Compiler Interface methods — get bytecodes, profiles, method size |
| ciCallProfile.hpp | Call profile data from C1 |
| parse1.cpp | Parses inline method's bytecodes into callee's Nodes |
| ciKlass.hpp | Klass hierarchy used for CHA |

### §四 Deep Dive (6 question groups)

**4.1 InlineTree: the recursive decision engine**
- `InlineTree::should_inline(ciMethod* callee)` — decision chain:
  1. `callee->should_inline()` — is callee marked @ForceInline? force-inline?
  2. `callee->should_not_inline()` — is callee marked @DontInline? too big? native method?
  3. `inline_level() > MaxInlineLevel` — recursion limit (default 9)
  4. `callee->code_size() > MaxInlineSize` — size limit (default 35 bytes)
  5. `InlineTree::should_inline_always() || compute_freq()->_freq > InlineFrequencyRatio`
- The frequency FILTER: why count calls, not method size? Small uncalled methods waste CodeCache.

**4.2 CHA (Class Hierarchy Analysis): type-based inline**
Counterfactual: "Without CHA: invokevirtual = virtual dispatch = cannot inline. With CHA: if only 1 subclass exists → inline as direct call."
- `ciKlass::subklass_of(ciKlass* super)` — checks klass hierarchy
- `ciKlass::is_leaf_type()` — only one concrete implementation → monomorphic virtual call → inline as static call
- The guard: optimized virtual call → `cmp [recv+klass], expected_klass; jne uncommon_trap` → if guard fails: deopt
- Risk: CHA caches the hierarchy at compile time. If a new subclass is loaded later → deopt → recompilation loop

**4.3 Type profile from C1: the empirical data**
- `ciCallProfile::count()` — how many times was this method called?
- `ciCallProfile::receiver_count(i)` — how many times was the i-th receiver type observed?
- "If 99% of calls are to HashMap → inline HashMap's hashCode() → guard check for other 1% → 99% time: 2% overhead from guard, 98% saved from inline → net +96%"
- `ciCallProfile::argument_projected_type(i)` — type propagation through arguments

**4.4 Late inline: after IGVN**
Counterfactual: "If you inline everything before IGVN: large graph → slow IGVN → compile time explosion. Late inline: do IGVN first (reduces graph), then inline hot callees that survived."
- `PhaseIdealLoop::do_call()` — registers late inline candidates
- Why wait? After IGVN, some calls were optimized away (dead code). Remaining calls are the important ones.

**4.5 Inline + downstream optimization: the cascade effect**
Concrete example:
```
Before inline: process() calls hash() calls hashCode()
  process(): 10 instructions
  hash(): 8 instructions
  hashCode(): 49 instructions
  Total: 10 + 8 + 49 = 67 instructions + 2 call overheads

After inline: all 67 instructions in process()
  IGVN eliminates 3 redundant hashCode() calls → 49 → 16
  Total: 10 + 8 + 16 - 3 = 31 instructions ← 54% reduction
```
This is WHY inline is the most important optimization — it's a multiplier on ALL other optimizations.

**4.6 Production: inline log interpretation**
- `(hot)` = called enough, being considered
- `already compiled into a big method` = caller reached MaxInlineSize for THIS call site
- `callee is too large` = callee > MaxInlineSize
- `inline level too deep` = recursion depth > MaxInlineLevel
- `no static binding` = virtual call with multiple subtypes, cannot CHA-guard efficiently

### §六 Writing Requirements
- "你需要知道的": InlineTree, CHA, type profile, hot count
- Mermaid: InlineTree recursion showing decision tree with yes/no branches
- GDB: break at `InlineTree::should_inline()`, print callee name + decision + reason
- Production: `-XX:+PrintInlining` log interpretation workflow
- Story-format interview answer at end

## PROMPT-03: Chaitin RegAlloc (P2 — deep but narrow)

### §〇 Production Scenario
"perf top 显示编译后的方法中 40% 指令是 `mov`——不是计算，而是寄存器→栈的 spill/fill 操作。方法在编译后被 spill 到栈上——每次 spill = ~5 周期 L1 访问 + store-forwarding 延迟。寄存器分配失败导致性能比预期慢 3 倍。"

Real perf output:
```
Samples: 128K of event 'cycles', 4000 Hz
  40.12%  [JIT compiled code]  mov %rax, -0x10(%rbp)  ← spill
  15.23%  [JIT compiled code]  add %rdx, %rax
   8.21%  [JIT compiled code]  mov -0x10(%rbp), %rcx  ← fill
```

### §一 Task + Narrative
"x86_64 只有 16 个通用寄存器。C2 可能为 1 个方法生成 50+ 个虚拟寄存器。Chaitin 着色算法将这些虚拟寄存器映射到 16 个物理寄存器——把冲突的寄存器 spill 到栈上。这不是 1982 年论文的数学版本——这是 HotSpot 的具体实现。"

"Reader knows from 01 that Matcher produces an Ideal Graph. This doc answers: how those graph nodes — each requiring a register — get assigned to real hardware registers."

Beginner callouts: virtual register, physical register, live range, interference graph, spill, coalesce

### §三 Source Files
| File | Role |
|------|------|
| chaitin.cpp | Main allocator — Register_Allocate() at :336-583 |
| ifg.cpp | Interference graph construction |
| coalesce.cpp | Coalesce — eliminate moves by merging registers |
| live.cpp | Live range computation |
| output.cpp | Post-allocation code emission |

### §四 Deep Dive (6 question groups)

**4.1 Live ranges: "when is this value alive?"**
- `PhaseLive::compute()` — for each Node: `_first_use` to `_last_use` = live range
- WHY live ranges exist: if two values' ranges overlap → they need DIFFERENT registers → IFG edge between them
- Example: `int x = a+b; int y = c+d; return x+y;` → x lives from `a+b` to `x+y`, y lives from `c+d` to `x+y`. Overlap at `x+y`. x and y need different registers.

**4.2 IFG (Interference Graph) construction**
- `PhaseIFG::PhaseIFG()` — for each virtual register pair: do their live ranges overlap? If yes → add edge
- `PhaseChaitin::build_ifg_virtual()` → then `AggressiveCoalesce` (at line 425: `coalesce.coalesce_driver()`) — merge virtual registers that are connected by a `mov` but don't interfere
- `PhaseChaitin::build_ifg_physical()` — NOW build the physical IFG with real 16 GPRs

**4.3 The correct algorithm order (verified from chaitin.cpp:336-583)**
```
1. PhaseLive (compute live ranges)
2. IFG_virtual (virtual register interference)
3. AggressiveCoalesce (line 425) — merge vregs BEFORE physical IFG
4. IFG_physical (real 16 GPR interference)
5. Simplify (line 515) — iteratively remove low-degree nodes
6. Select (line 519) — color: if degree < 16 → success; else → spill
7. If spill: split + ConservativeCoalesce (line 546-575) → loop to step 1
```
CRITICAL: Coalesce happens BEFORE coloring, not after. This is the difference between HotSpot's implementation and standard textbook presentation.

**4.4 Spill: when 16 registers aren't enough**
Counterfactual: "If you had 32 GPRs: no spill needed for most methods. But x86_64 has 16 — and 7 are reserved: RSP, RBP, R12(heapbase), R15(thread), R10/R11(scratch), RAX(return). So only 9 are available for compiler use."
- Spill cost: `Node::_cnt` — loop-nested Node has higher cost (don't spill it!)
- Spill mechanism: `PhaseChaitin::Select()` → degree ≥ 16 → `PhaseChaitin::choose_color()` returns -1 → `PhaseChaitin::select_spill()` → marks Node for spill → `PhaseChaitin::Split()` creates new vreg
- After spill: split Node's live range into pre-spill (write to stack) + post-spill (read from stack) → redo step 1 with new vreg
- `PhaseChaitin::fixup_spills()` at line 680: insert actual `mov reg→[rsp+offset]` instructions

**4.5 Coalesce: the art of removing `mov` instructions**
Counterfactual: "If you don't coalesce: `mov r1, r2; add r2, r3` — WHY not just use r1 everywhere? Coalesce merges r1 and r2 → `add r1, r3` — saves 1 instruction + 1 cycle."
- AggressiveCoalesce: `PhaseAggressiveCoalesce::coalesce_driver()` — iterates all `mov` instructions, attempts to merge
- Why aggressive BEFORE physical IFG? Because merging vregs reduces IFG degree → easier coloring → fewer spills
- ConservativeCoalesce (after spill): more conservative — only merge if it WON'T force a spill (check: `adjacent.num_of_elements() + degree < 16`)

**4.6 Production: spill storm diagnostics**
- perf top shows `mov %rax, disp(%rbp)` followed by `mov disp(%rbp), %rcx` — spill + fill pair
- Spill frequency: >5% of total instructions = problematic → reduce inline depth → fewer live ranges
- `-XX:+PrintOptoAssembly` shows post-regalloc assembly — spots spills
- Chaitin's algorithm is FAST in common case: 5ms for 50 Node method. Spill-only case: 350ms for 800 Node method.

### §六 Writing Requirements
- "你需要知道的": virtual register, live range, IFG, spill, coalesce, simplify, select
- Mermaid: live ranges timeline → IFG graph → coloring process with spill
- GDB: break at `Register_Allocate()`, step through AggressiveCoalesce, verify vreg count before/after
- Production: spill storm diagnosis → perf + PrintOptoAssembly workflow
- CRITICAL: correct algorithm order as verified from chaitin.cpp

## PROMPT-04: CodeCache + NMethodSweeper (P2)

### §〇 Production Scenario
"CodeCache is full. Compiler has been disabled." — 每条 JVM 日志都是这个。CodeCache 从 240MB 的 97% 涨到 100% 时，CompileBroker 拒绝接收新编译——热方法 forever 解释执行。3 分钟后 CodeCache → 85%（Sweeper 清理了 zombie nmethods），但 QPS 已经掉了 80%。"

### §一 Task + Narrative
"nmethod 是 JVM 中最复杂的生命周期对象——从'编译器分配 CodeCache 空间'到'GC 回收 zombie nmethod'共 5 个阶段。CodeCache 是 JVM 的'第二个堆'——和 Java 堆一样管理空间。"

Beginner callouts: nmethod, CodeBlob, CodeCache, zombie, not_entrant, sweeper

### §三 Source Files
nmethod.cpp, codeCache.cpp, nmethodSweeper.cpp, codeBlob.cpp, compiledMethod.cpp, compileBroker.cpp

### §四 Deep Dive (6 groups)

**4.1 nmethod lifecycle (5 states)**
- `alive`: compiled and in use — can be entered by any thread
- `not_entrant`: new version compiled (C2 recompiled this method) — existing threads can finish, no NEW threads enter
- `zombie`: all threads have exited not_entrant nmethod — ready for sweeper to reclaim
- `unloaded`: class unloaded → nmethod's metadata invalid → must be reclaimed
- `freed`: CodeCache space reclaimed

**4.2 CodeCache 3-segment layout**
- Non-profiled (no nmethods): compile level < 4
- Profiled (nmethods with profile data): C1 L2/L3
- Non-method: adapters, stubs, buffered blobs
Each segment has independent free list.

**4.3 NMethodSweeper: background cleanup**
Counterfactual: "Without sweeper: CodeCache never shrinks → full → dead. Stop-the-world CodeCache cleanup = stop-the-world JVM."
- Sweep cycle: every NmethodSweepFraction safepoints (default 16)
- Zombie detection: `nmethod::can_be_zombie()` — is not_entrant AND no stack references?
- Flush: `NMethodSweeper::sweep_code_cache()` → mark zombie → flush queue → `CodeCache::free(nmethod)`

**4.4 Emergency flush**
Counterfactual: "If CodeCache is 99% full: emergency flush. Sweeper aggressively marks ALL zombie nmethods → immediate CodeCache::free → no patience for normal cycle."
- 3 situations: (1) allocation fails → trigger emergency, (2) CodeCache approaching limit, (3) explicit `-XX:StartAggressiveSweepingAt=80`

**4.5 Speculative disconnect (frequent deopt → zombie)**
If nmethod is deoptimized within first N invocations (SpecTrapLimit) → mark as "unstable" → never recompile. Saves CodeCache from recompilation loop.

### §六 Writing Requirements
- "你需要知道的": nmethod states, CodeCache segments, sweeper cycle
- Mermaid: nmethod lifecycle state diagram with transitions
- GDB: break at `NMethodSweeper::sweep_code_cache()`, print zombie count, verify flush
- Production: `jcmd <PID> Compiler.CodeHeap_Analytics` → CodeCache usage

## PROMPT-06: OopMap + GC Roots (P1 — JIT↔GC bridge)

### §〇 Production Scenario
"GC crash in G1ParScanThreadState::copy_to_survivor — bad oop reference in compiled method. OopMap said 'register r10 has an oop at PC 0x...' but r10 contained 0x7f8b... (a valid pointer but to a dead object). OopMap was generated for the wrong safepoint — GC traversed compiled code with wrong root set."

### §一 Task + Narrative
"GC 怎么找到 JIT 编译代码中的 live object pointers？编译后没有'局部变量表'了——值分散在 16 个寄存器和栈槽中。OopMap = 每个 safepoint 的位掩码——一行一行告诉 GC：'在 PC 0x... 处，R10 有 oop，RDI 有 oop，[RSP+0x18] 有 oop'。"

Beginner callouts: OopMap, OopMapSet, safepoint, GC root, bitmask, debug info

### §三 Source Files
oopMap.cpp, oopMap.hpp, debugInfoRec.cpp, output.cpp, nmethod.cpp

### §四 Deep Dive (6 groups)

**4.1 OopMap generation at compile time**
- `PhaseOutput::install_code()` → `DebugInformationRecorder::describe_scope()` → `OopMapSet::add_gc_map()`
- Each safepoint generates 1 OopMap. OopMap = `OopMapValue` stream → compressed bitmask
- Size: ~10 bytes per safepoint (typical: 2-3 oop values)

**4.2 OopMap consumption at GC time**

## PROMPT-07: Profile Data Flow (P1 — C1→C2 bridge)

### §〇 Production Scenario

### §一 Task + Narrative
"C2 不是瞎子——它透过 ci/ 目录读取 C1 编译器收集的 profile 数据。每次 invokevirtual 调用：C1 记录 '这个方法被调用了 N 次，receiver klass 是 X Y% 时间'。ciMethod/ciKlass/ciCallProfile = C2 的'市场调研'。"

Beginner callouts: ciMethod, ciKlass, ciCallProfile, type profile, receiver count, maturity

### §三 Source Files

### §四 Deep Dive (6 groups)

**4.1 MethodData: the raw profile storage**
- `Method::method_data()` — returns `MethodData*`, the raw C1-collected data
- `MethodData::DataLayout` — compact storage: invocation counter, backedge counter, call site profiles

**4.2 ciMethod: C2's view of a method**

**4.3 ciCallProfile: how C2 reads call counts**
