## 🔴 GAP 1: Container/Cgroup Document (NEW — biggest missing piece)

Create: probe_md/libjvm-analysis/01-jvm-startup/19-Container-Cgroup-Support.md

### Why this matters
In 2025, >80% of production JVMs run in containers. Without this doc, a reader whose Pod OOMKilled before JVM starts has ZERO diagnostic guidance from phase 01.

### Content
1. **Production opener** (3 real scenarios, not 1):
   - "Pod memory limit 512Mi, -Xms512m, JVM OOMKilled during heap init — `kubectl describe pod` shows Exit Code 137, no hs_err, no GC log"
   - "Pod CPU limit 2 cores, but `java -version` prints `-XX:ActiveProcessorCount=16` — GC threads over-provisioned, CPU throttled, STW pauses explode"
   - "Two JVMs on same K8s node, both expect 4GB heap, node has 6GB — OOM score battle"

2. **os::init_container_support() walkthrough** (osContainer_linux.cpp, ~500 lines, give file:line for each):
   - `OSContainer::init()`: the detection entry
   - cgroup v1 vs v2 detection: read `/proc/self/mountinfo`, check for `cgroup2` filesystem type vs `cgroup` with specific controller
   - v1 path: `/sys/fs/cgroup/cpu/cpu.cfs_quota_us` and `cpu.cfs_period_us` → `active_processor_count = ceil(quota / period)`; if quota=-1 (unlimited) → read `cpu.shares` → `min(available_processors(), ceil(shares / 1024))`
   - v1 path: `/sys/fs/cgroup/memory/memory.limit_in_bytes` → if < physical RAM → `MaxRAM` = limit; if < `-Xmx` → override; if > 2^63-1 → "unlimited" (container has no memory limit)
   - v2 path: `/sys/fs/cgroup/cpu.max` (format: `$MAX $PERIOD`), `/sys/fs/cgroup/memory.max`
   - `-XX:ActiveProcessorCount` → feeds `ParallelGCThreads`, `ConcGCThreads`, `CICompilerCount`

3. **What happens when limits clash**:
   - `memory.limit_in_bytes` (512M) < `-Xms512m` → JVM can't commit initial heap → `os::commit_memory()` fails → `vm_exit_out_of_memory()` → exit code 1 (not 137!)
   - `memory.limit_in_bytes` (1G) < `-Xmx2G` → JVM starts OK, heap grows to 1G, next GC sees free memory exhausted → kernel OOM killer → exit 137 — no hs_err, no log
   - CPU limit < actual cores → `ActiveProcessorCount` = 2 → GC threads = 2 → concurrent mark starves mutators → STW non-stop

4. **`-XX:+UseContainerSupport` decision flow**:
   - Default true since JDK 10 (JDK 8u191+ backported)
   - Disabled → uses host /proc/cpuinfo and /proc/meminfo (reads physical machine, not container limits)
   - Why you'd disable: VM running on dedicated node (no other containers) — wants full machine resources

5. **Dynamic GC threads**: `-XX:+UseDynamicNumberOfGCThreads` (since JDK 11) — GC thread count adjusts when container CPU limit changes

6. **Multi-tenant JVM on K8s**:
   - `memory.limit_in_bytes` = total pod limit, `memory.usage_in_bytes` = total pod usage — includes JVM + agent + OS page cache
   - JVM sees `MaxRAM` = total limit, but actual available = limit - agent overhead - OS overhead
   - OOM score: kernel assigns per-process OOM score based on memory usage ratio → larger JVM killed first

7. **GDB verification** (full session format, with `(gdb)` prompts):
   ```
   (gdb) break os::Linux::init_container_support
   (gdb) run
   (gdb) p Arguments::_cpu_count
   $1 = 4
   (gdb) p Arguments::_max_physical_memory
   $2 = 536870912  ← 512MB from cgroup, not 64GB from /proc/meminfo
   ```

8. **Production checklist**: "Pod restart loop → 1) check `kubectl describe pod` exit code (137=OOMKilled, 1=JVM exit) → 2) check cgroup limits match -Xms/-Xmx → 3) enable `-Xlog:gc+ergo*=debug` for heap sizing decisions → 4) check `-XX:+PrintFlagsFinal | grep -i container` for final flag values"

9. **Mermaid**: cgroup detection v1/v2 decision tree → ActiveProcessorCount computation → MaxRAM override flow

10. **Cross-reference**: 01 (heap init), 04 (Arguments::parse at Stage 8), 06 (Universe/heap creation), 07 (G1 12-step init with heap size from container), 15 (thread count depends on CPU count)

### Style

## 🔴 GAP 2: Arguments::parse() Flow Document (NEW — structural hole)

Create: probe_md/libjvm-analysis/01-jvm-startup/20-Arguments-Parse-Flow.md

### Why this matters
README §三 shows Arguments::parse() as Stage 8 of create_vm(). The JVMFlag struct is covered in doc 15 §十八 — but the PARSE FLOW ITSELF has no walkthrough. For an entry-point phase promising "every millisecond explained," the reader never sees how their flags become memory addresses.

### Content
1. **Production opener** (2 scenarios):
   - "-XX:+PrintGCDetails doesn't work at 3am → because JAVA_TOOL_OPTIONS=-XX:-PrintGCDetails overrides your command line"
   - "GC logs show G1 but you used -XX:+UseParallelGC → because _JAVA_OPTIONS's UseG1GC takes precedence"

2. **4-source priority chain** (with `arguments.cpp` file:line for each):
   - `-XX:Flags=<file>` (lowest priority — `arguments.cpp:parse_java_tool_options_flags_file()`)
   - `JAVA_TOOL_OPTIONS` env var
   - `_JAVA_OPTIONS` env var  
   - Command line (highest priority)
   - Source order: read in LOWER-priority order first, so HIGHER priority overwrites. This is the #1 cause of "my flag doesn't work" production issues.

3. **parse_each_vm_init_arg()** detailed walkthrough (arguments.cpp):
   - String parsing: `-Xms8g` → split at '=' or ':' → name="Xms", value="8g", origin=JVMFlagsOrigin_COMMAND_LINE
   - `-XX:+/-FlagName` → `set_bool_flag()` → `JVMFlag::boolAtPut(origin, &cmd_line_bool)`
   - `-XX:FlagName=value` → `JVMFlag::set_flag_from_env()` → type detection → constraint check → range check
   - Constraint check: `-Xms > -Xmx` → `vm_exit_during_initialization("Incompatible...")`
   - Range check: `-XX:ObjectAlignmentInBytes=7` → fails (must be power of 2, 8-256)
   - Diagnostic flag gate: `-XX:+UnlockDiagnosticVMOptions` must precede diagnostic flags

4. **Specific flag parsing** (most common flags):
   - `-Xms/-Xmx`: `Arguments::set_heap_size()` → `MinHeapSize`/`MaxHeapSize`/`InitialHeapSize` with byte-to-GB conversion + alignment to page size
   - `-Xss`: `set_thread_stack_size()` → minimum 144k (64-bit), maximum 1G, alignment to page
   - `-XX:+UseG1GC`: sets `UseG1GC=true` and clears `UseSerialGC`/`UseParallelGC`/`UseConcMarkSweepGC`/`UseShenandoahGC`
   - `-Xlog:gc*=info`: `LogConfiguration::parse_log_arguments()` → creates LogOutput + LogTagSet + LogDecorator chain

5. **JVMFlag write toggles**: `FLAG_SET_DEFAULT` vs `FLAG_SET_CMDLINE` vs `FLAG_SET_ERGO` — origin determines if later override is allowed

6. **Ergo phase**: `Arguments::apply_ergo()` — for all flags where origin=FLAG_SET_DEFAULT:
   - Heap size: `RAM <= 1GB → MaxHeapSize = RAM/2`, else `RAM <= 192GB → MaxHeapSize = RAM/4`
   - GC threads: `ParallelGCThreads = cpu_count <= 8 ? cpu_count : 8 + (cpu_count-8)*5/8`
   - CICompilerCount: `CICompilerCount = max(1, min(4, cpu_count/2))`
   - CodeCache size: tiered compilation → 240MB, non-tiered → 48MB

7. **Constraint violations**: what prints what error, where in startup the exit happens, exit code

8. **GDB session**: break at `parse_vm_init_args()`, step through parsing of `-Xms512m`, show JVMFlag before/after write, verify origin byte

9. **Production diagnostic**: "Which source set my flag?" → `-XX:+PrintFlagsFinal | grep <flagname>` → check the `origin` column → map to source priority

10. **Mermaid**: 4-source chain → parse_each_vm_init_arg → set_flag → constraint/range → ergo
