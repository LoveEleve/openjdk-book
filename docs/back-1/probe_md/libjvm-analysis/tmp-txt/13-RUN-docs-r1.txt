### §四 — JLI_Launch Full Trace (the CORE of the doc)
This is the MARQUEE section. Eight-step walkthrough with source code snippets:

**Step 1: JLI_Launch entry at java.c:220**
Show the 12-parameter signature. Explain EACH parameter: argc/argv from bash, jargc/jargv from JVM-specific args (Windows, MacOS pre-processing), appclassc/appclassv from platform launcher, fullversion/dotversion from JDK version strings, pname/lname for process naming, javaargs for -X/-XX flags already classified by platform launcher, cpwildcard for wildcard expansion flag, javaw for Windows-specific, ergo for ergonomic tuning.

"Why 12 instead of 2? Because the `java` command is NOT always launched from bash. On Windows: WinMain pre-processes. On MacOS: NSApplicationMain pre-processes. Each platform resolves different startup flags BEFORE JLI_Launch is called. The 12 parameters are the COMMON protocol all platforms agree on."

**Step 2: SelectVersion at java.c:1056**
Reads JAR manifest or release file to determine required JRE version. If JAR was compiled with JDK 17 but system has JDK 11 → SelectVersion switches jrepath to JDK 17's JRE. Counterfactual: "If SelectVersion didn't exist: JNI_CreateJavaVM starts JDK 11 → ClassLoader encounters JDK 17 bytecodes → ClassFormatError → wasted 2s startup + guaranteed failure."

**Step 3: CreateExecutionEnvironment at java_md_solinux.c:284**
Finds the JRE installation. Priority: $JAVA_HOME (if set, shortcut) → /proc/self/exe (zero-config fallback). Walks up from bin/java → lib/libjava.so as JRE anchor file.

**Step 4: LoadJavaVM at java.c:300 → dlopen at java_md_solinux.c:571**
dlopen(libjvm.so, RTLD_NOW|RTLD_GLOBAL). RTLD_NOW = resolve ALL symbols immediately — fail NOW if missing, not LATER during production. RTLD_GLOBAL = JVM symbols visible to all future dlopen calls (required for -agentlib). Counterfactual: "RTLD_LAZY saves ~200ms at startup but crashes with 'undefined symbol: JVM_FindSignal' during JIT compilation → 2s wasted → crash → restart → crash again."

**Step 5: JVMInit → JavaMain → thread creation at java_md_solinux.c:786**
pthread_create with custom stack size (8MB), disabled guard page. "Running Java code in primordial thread caused many problems" (java.c:202). Counterfactual: "If JVM ran in primordial thread: pthread stack is shared with launcher → JVM startup modifies stack unpredictably → launcher's local variables corrupted → undefined behavior."

**Step 6: ParseArguments at java.c:1296** (overview — details in 01)
Separates JVM options from application arguments. Mode detection: -jar → LM_JAR, -cp → LM_CLASS, -m → LM_MODULE.

**Step 7: LoadMainClass at java.c:523** (overview — details in 03)
LoadMainClass → LauncherHelper.checkAndLoadMain() → Class.forName(mainClassName) → find main(String[]).

**Step 8: CallStaticVoidMethod at java.c:566**
The IRREVERSIBLE transition. After this call, libjli's C stack is dormant — JVM's Java stack takes over. If main() returns → exit. If main() throws → ExceptionDescribe → exit(1). "libjli never RETURNS from CallStaticVoidMethod. The JVM OWNS the process now."

### §〇 — Production: "ZGC on JDK 11 — experimental flag, silent crash"
JDK 11 production. Engineer adds `-XX:+UseZGC` for lower latency. ZGC is experimental in JDK 11 (requires `-XX:+UnlockExperimentalVMOptions`). The flag passes through libjli's ParseArguments → classified as JVM option → passed to JNI_CreateJavaVM. JVM starts normally → 1s warmup → C2 compilation begins → `ZBarrierSetC2::emit_barrier_stub()` → NullPointerException → SIGSEGV → hs_err shows `V [libjvm.so+0x...] ZBarrierSetC2::emit_barrier_stub`. Root cause: JVM flag was forwarded correctly but was dangerous.

Diagnostic: `-XX:+PrintFlagsFinal | grep -i zgc` → confirms flag was set → `-XX:-UseZGC` exclusion → if crash stops → ZGC was the cause → report to OpenJDK or wait for JDK 15.

### §四 — ParseArguments Deep-Dive (8 steps)

**4.1: ParseArguments entry at java.c:1296**
~300 lines of state-machine logic. Initialized with mode=LM_UNKNOWN. Iterates through argv parsing each token.

**4.2: Mode detection — -jar, -cp, -m, --source**
First non-flag argument determines mode:
- Starts with `-jar` → mode=LM_JAR, what=next_arg
- Starts with `-cp` or `-classpath` → mode=LM_CLASS, classpath=next_arg
- Starts with `-m` → mode=LM_MODULE
- Starts with `--source` → mode=LM_SOURCE
- Otherwise → mode=LM_CLASS, what=first non-flag arg

Counterfactual: "If mode detection was order-independent: `java app.jar -jar` would be valid but ambiguous — is app.jar the JAR or the class? Mode detection ORDER prevents ambiguity."

**4.3: JVM option classification — AddOption**
`-Xms8g` → AddOption("-Xms8g") → push to _java_args linked list. `-XX:+UseG1GC` → AddOption → push. `-Dfoo=bar` → AddOption → push. At JNI_CreateJavaVM time: convert linked list → JavaVMOption[] array. Counterfactual: "If libjli didn't classify: JVM would receive `app.jar` as a JVM option → Arguments::parse() → 'unrecognized option: app.jar' → fatal error → exit. Classification IS the boundary between JVM and application."

**4.4: -Xms/-Xmx dual parsing**
Why parse heap size in BOTH libjli and libjvm? libjli: extract for `ShowSettings()` output and early error detection. libjvm: actual heap allocation with GC-specific constraints. Counterfactual: "If libjli tried to validate heap size: needs GC-specific knowledge (G1 min heap 1MB, Parallel min 768KB). Duplicate GC logic in launcher → maintenance nightmare."

**4.5: Wildcard expansion — opendir + readdir**
`java -cp 'lib/*' MyClass` → lib/ → opendir → readdir entries → isJarFileName(name) → only .jar/.JAR → qsort alphabetically → join with `:` separator → SetClassPath(expanded_paths). Counterfactual: "If wildcards NOT expanded at startup: ClassLoader must opendir for every class load → 1000 classes × 2ms opendir = 2s wasted per class → 2000s for 1000 classes."

**4.6: Classpath construction — -jar vs -cp conflict**
Mode=LM_JAR: java.c:338-340 `if (mode == LM_JAR) SetClassPath(what)` OVERWRITES ALL classpath. User's `-cp` is IGNORED. All classes MUST come from JAR + manifest Class-Path. Counterfactual: "If -cp supplemented -jar classpath: same class (com.Foo) in JAR and external directory → which one loads first? depends on classpath order → non-deterministic → Heisenbug."

**4.7: -version specification — BEFORE JNI_CreateJavaVM**
-version, -Xinternalversion, -showversion → handled BEFORE LoadJavaVM → save 2s JVM startup for printing version. Counterfactual: "If -version waited until JVM starts: every `java -version` costs 2s → CI/CD pipeline with 100 version checks → 200s wasted daily."

**4.8: Mutually exclusive arguments**
`-jar` and `-cp` together → error (java.c:1757). `-m` and `-jar` together → error. Counterfactual: "If mutually exclusive args were silently accepted: last flag wins → user thinks -cp works but JAR mode overwrites → class loading fails with 'ClassNotFoundException' not 'bad arguments' → 3am debugging nightmare."
