## Fix 1: Break P05↔P06 circular dependency

This is the most impactful fix — it affects the READING ORDER of ALL 7 docs.

### Background
OopMaps are generated during the C2 Output phase (P01 §九). They are bitmasks recording "at this safepoint PC, register R10 contains an oop pointer." Deoptimization (P05) CONSUMES OopMaps to rebuild interpreter frames — "at deopt PC 0x..., read the OopMap bitmask to find which registers hold oops."

So P06 (generation) is logically BEFORE P05 (consumption). The dependency is: P01 (generates OopMaps during Output) → P06 (explains HOW OopMaps work) → P05 (consumes OopMaps during deopt).

### Fix action
**prompt-05-Deoptimization.md §一**: Verify it says "前置: [06-OopMap-GC-Roots]" — this is CORRECT. Deopt consumes OopMaps → reader should know what OopMaps are first. Keep it.

**prompt-06-OopMap-GC-Roots.md §一**: REMOVE ALL references to 05. Current text likely says "前置: [05-Deoptimization]" or "Reader has read 05". Replace with:

```
前置: [01-C2-Pipeline] §九(Output) — OopMaps are generated during PhaseOutput::install_code().
[05-Deoptimization] will consume the OopMaps generated here, but OopMaps exist independently of deopt —
they are GC's bridge into compiled code, not deopt's private data structure.
```

Also remove any "Reader has read 05" language from §一 narrative paragraph. Replace "After understanding deoptimization" with "After understanding how C2 generates compiled code (01 §九)".

### Quality impact
- Depth: reader now understands OopMaps as a compilation artifact, not a deopt artifact
- Coherence: reading order P01→P06→P05 is linear, no circular reference
- Interview: reader can explain "OopMaps are generated at compile time, consumed by GC AND deopt at runtime"

### Fix action

### Quality impact

### P02: Add PrintInlining output
In prompt-02-Inline-Decision.md §〇:

```
Actual -XX:+PrintInlining output:

@ 12 java.util.HashMap::hash (62 bytes)   inline (hot)
  @ 4 java.util.Objects::hashCode (12 bytes)   inline (hot)
    @ 4 java.lang.String::hashCode (49 bytes)   inline (hot)
      @ 19 java.lang.String::value (5 bytes)   accessor
    @ 8 java.lang.String::hashCode (49 bytes)   already compiled into a big method
  @ 9 java.lang.Integer::hashCode (10 bytes)   inline (hot)

Interpreting this inline tree:
- "@ 12" = the call site is at bytecode offset 12 in the caller method
- "inline (hot)" = C2 profiled this call site > InlineFrequencyRatio threshold
- "already compiled into a big method" = this callee was ALREADY inlined into ANOTHER caller.
  C2 won't inline it twice — this is the mechanism that prevents CodeCache explosion
- "accessor" = trivial field access (e.g., just "return value"), always inlined
```

### P03: Add perf top output
In prompt-03-Chaitin-RegAlloc.md §〇:

```
Actual perf top output from a method with register pressure > 16:

Samples: 128K of event 'cycles', 4000 Hz
Overhead  Shared Object          Symbol
  22.12%  [JIT compiled code]    mov %rax, -0x10(%rbp)    ← spill
  18.34%  [JIT compiled code]    mov -0x10(%rbp), %rcx    ← fill
  15.23%  [JIT compiled code]    add %rdx, %rax
   8.21%  [JIT compiled code]    mov %rsi, -0x18(%rbp)    ← spill

Spill ratio: (22.12 + 18.34 + 8.21) / total = 48.67% of instructions are mov reg↔stack.
Normal compiled code: <5% mov to/from stack → CPU spends time computing, not shuttling data.
This is what Chaitin spill looks like at the CPU level — the compiler ran out of registers
and had to "park" values on the stack, then "retrieve" them later.
```

### P05: Add PrintDeoptimizationDetails output
In prompt-05-Deoptimization.md §〇:

```
Actual -XX:+PrintDeoptimizationDetails output:

Uncommon trap happened in java.util.HashMap::putVal
  @ 42 java.util.HashMap::hashCode (5 bytes)
  reason: class_check
  action: maybe_recompile
  trap_request: 5

Reading deopt output:
- "@ 42 java.util.HashMap::hashCode" = the call site at bytecode offset 42 was compiled
  with a CHA guard that assumed a specific receiver class
- "reason: class_check" = at runtime, the guard failed — the receiver's class was NOT
  the one C2 expected. This is a CHA invalidation.
- "action: maybe_recompile" = C2 will attempt recompilation with updated profile data,
  BUT only if this doesn't happen too many times (SpecTrapLimit prevents recompile loops)
- "trap_request: 5" = the deopt reason bitmask: reason_class_check = bit 2 (value 4) +
  action_maybe_recompile = bit 0 (value 1) = 5
```

- Beginner: reader sees "this is what your JVM actually prints" — demystifies JIT diagnostics
