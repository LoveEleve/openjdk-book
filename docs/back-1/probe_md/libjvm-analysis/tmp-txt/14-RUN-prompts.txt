## prompt-00 (Zip-Class-Loading) — EXACT specifications

### §〇: "Corrupted app.jar at 3am"
`java.util.zip.ZipException: invalid entry CRC (expected 0xabcd1234 but got 0xdeadbeef)` — CRC32 verification in Java ZipFile layer failed. JAR was corrupted during network transfer or disk write. Every class load from this JAR will fail until the JAR is replaced.

### §四 groups:
4.1: ZIP_Open at zip_util.c:XXX — how does the JVM "open" a JAR? mmap entire file or buffered read? Find the exact mechanism.
4.2: readCEN at zip_util.c:568 — builds chained hash table from Central Directory. Counterfactual: "If binary search instead of hash: O(log n) = 12 comparisons for 3000 entries. Hash: 1-2 probes at 75% load factor. 10x faster." 
4.3: ZIP_GetEntry2 at zip_util.c:1172 — hash%tablelen lookup + chain walk for collision resolution. Counterfactual: "If linear scan of CEN instead of hash: 1500 comparisons average for 3000 entries → 750x slower per class load."
4.4: ZIP_GetFromCache — handle reuse across class loads from same JAR. Counterfactual: "If no cache: each class load = re-open JAR + re-read CEN (0.5ms) → 3000 classes × 0.5ms = 1.5s."
4.5: DEFLATE decompression for entry — Inflater.c bridge → zlib inflate(). Cached Inflater state.
4.6: ZIP_Lock/ZIP_Unlock — concurrent class loading from same JAR. Multiple threads reading different entries → lock on ZIP handle.

### §十 GDB: break at zip_util.c:568 (readCEN), zip_util.c:1172 (ZIP_GetEntry2), Inflater.c:XXX (inflate). Show hash table structure, entry offset, inflated bytes.

## prompt-01 (Jimage-Format) — EXACT specifications

### §〇: "JDK upgrade → FindException"
`java.lang.module.FindException: Module java.base not found`. JIMAGE_Open at jimage.cpp:XXX → checks magic 0xCAFEDADA → fails (wrong version, corrupted file, or partial JDK upgrade).

### §四 groups:
4.1: JIMAGE_Open at jimage.cpp:XXX — magic check, version check, redirect/location/string table parsing.
4.2: Perfect hashing — HASH_MULTIPLIER = 0x01000193. `hash = 1; for each char c: hash = hash * HASH_MULTIPLIER + c`. Counterfactual: "If standard hash with collisions: need secondary probe for each miss → 1.2x more probes. Perfect hash: 0 collisions by construction (all known at image build time)."
4.3: Location table — `location_table[name_hash]` = offset in resource data. O(1) guaranteed. Counterfactual: "If ZIP's table: O(1) average but not guaranteed → worst case O(n) with degenerate hash. jimage perfect hash → always O(1)."
4.4: String table — shared strings extracted from class data → deduplication → better compression.
4.5: imageDecompressor.cpp:83 → dlopen("libzip.so") → reuse ZIP_InflateFully. Counterfactual: "If jimage had its own inflate: code duplication + possible zlib version mismatch. dlopen libzip: single zlib, single inflate pipeline, zero duplication."
4.6: Pre-processing — shared constant pool strings extracted → stored ONCE in string table → entries reference via offset. Class data compressed WITHOUT duplicate strings → 20-30% better compression than raw DEFLATE.

## prompt-02 (Compression-Zlib) — EXACT specifications

### §〇: "corrupt compressed data at startup"
`java.util.zip.ZipException: invalid stored block lengths` — zlib's inflate() encountered malformed DEFLATE stream. Root cause: JAR was built with incompatible compressor or truncated during copy.

### §四 groups:
4.1: Inflater.c native bridge — `Java_java_util_zip_Inflater_inflateBytes()` → inflate().
4.2: zlib bundled at zlib.h:26 (version 1.2.11). Counterfactual: "If system zlib: Linux/Windows version mismatch → inflate fails → ClassNotFoundException for all classes. Bundled: known version, verified behavior."
4.3: inflateInit2_ → inflate → inflateEnd pipeline. Caching Inflater state across entries.
4.4: CRC32 vs Adler-32 — dual verification. Adler-32 in zlib stream (catches decompression errors). CRC32 in ZIP entry (catches disk corruption).
4.5: DEFLATE compression ratio analysis — class files: ~50% typical. Constant pools highly compressible. Bytecodes moderately compressible.

## prompt-03 (ClassLoader-Bridge) — EXACT specifications

### §〇: "NoClassDefFoundError but class IS in JAR"
`java.lang.NoClassDefFoundError: com/example/Foo`. JAR is on classpath, Central Directory has "com/example/Foo.class" entry, but ClassLoader.defineClass1 returns null. Root cause: ZIP entry is a directory stub (size=0, name ends with '/'), not a file entry. Fix: rebuild JAR without directory entries.

### §四 groups:
4.1: ClassLoader.c → Java_java_lang_ClassLoader_defineClass1() — receives byte[] FROM JAVA, not reads bytes. Counterfactual: "If defineClass1 called ZIP_GetEntry directly: native code handles I/O + zlib + CRC32. Java exception handling unavailable → crash. ZipFile handles I/O in Java → proper IOException → ClassNotFoundException."
4.2: Architecture: ZipFile.getInputStream() → native Inflater → bytes → ClassLoader.defineClass1(bytes). Separation of concerns.
4.3: JNI_SetByteArrayRegion — copies inflated bytes from native to Java heap.
4.4: defineClass1 → JVM internal: SystemDictionary::define_class → ClassFileParser (02 territory).

## prompt-04 (Jar-URL-Nesting) — EXACT specifications

### §〇: "Spring Boot fat JAR — ZipException"
ZipException accessing nested JAR: `BOOT-INF/lib/spring-core.jar` inside `app.jar`. Standard java.util.zip.ZipFile only handles real .jar files → fails on zip entry within another zip.

### §四 groups:
4.1: Standard ZipFile limitation — ZIP_Open expects real file path → nested path fails.
4.2: JarURLConnection protocol — `jar:file:///app.jar!/BOOT-INF/lib/spring-core.jar!/META-INF/MANIFEST.MF`.
4.3: Spring Boot LaunchedURLClassLoader — custom URL stream handler for nested JARs.
4.4: JDK 13+ zipfs — ZipFileSystemProvider → treats nested JAR as filesystem.
4.5: Performance — nested JAR = 2x decompression (inflate outer entry → parse inner CEN).
