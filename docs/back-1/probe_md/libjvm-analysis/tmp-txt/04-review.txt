## 2. First-principles depth — 10 pts

Each doc must have at least one section that STARTS from "if you built a bytecode interpreter from scratch..." and DERIVES the JVM design as the logical consequence of constraints.

Key first-principles questions this phase MUST answer:
- "If you built a bytecode interpreter, would you put a type checker before every instruction? If not, how do you guarantee type safety?" → ANSWER: TOS state machine — compile-time type safety via per-TOS template variants. The verifier (02-class-loading) guarantees bytecode correctness, so the interpreter can skip runtime checks.
- "If you built a bytecode interpreter, how would you decide which code to execute for bytecode X?" → ANSWER: dispatch table — 256-entry jump table. O(1) lookup. switch-case = O(n) average.
- "If you built a bytecode interpreter, where would you check for safepoints?" → ANSWER: backward branches. Forward-only code naturally exits. Polling every bytecode costs too much.
- "If you built a bytecode interpreter, how would you decide when to compile to native code?" → ANSWER: dual counters. Invocation for whole method, BackEdge for hot loops. Decay prevents transient compilation.

Checklist per doc:
- Does the doc DERIVE the design or just DESCRIBE it?
- Does it present the ALTERNATIVE (what would happen if they did it differently) and quantify the cost?
- Does it connect the first-principles reasoning to the actual source code?

### Scoring
9-10: 4+ docs derive designs from first principles with quantified alternatives
7-8: 2-3 docs derive
5-6: docs describe designs but don't derive
3-4: "why" is presented as "because the code does it this way" (circular)
1-2: no design rationale at all
